The MPU and how faults happen

A bad pointer does not crash the chip politely. It raises an exception, and which exception depends on the core you are running on.

By the end of this lesson you can say which fault exceptions the RP2040's Cortex-M0+ and the STM32F103's Cortex-M3 can raise, whether each part has an MPU, and which status register you would read first after a fault.

The idea

A fault is an exception the core raises when an access or instruction cannot complete: a bad address, a memory protection violation, or an illegal instruction. Like any exception, it stops normal execution and runs a handler, found through the vector table.

The memory protection unit (MPU) is the hardware that makes some addresses off limits to some code. You program it with regions: each region has a base, a size, and access permissions. An access that breaks a rule raises a fault. The MPU is optional in Cortex-M cores, and it differs between the two parts in this course.

Which faults each core has

Core and partFault exceptionsMPU
Cortex-M0+ (RP2040)HardFault only8 regions
Cortex-M3 (STM32F103)MemManage, BusFault, UsageFault, and HardFaultNone on this part

On the RP2040, the datasheet says that MPU mismatches and permission violations invoke the HardFault handler. RP2040 datasheet, section 2.4.6.1 (About the MPU). The MPU has eight unified regions with overlapping priorities, where region 7 is the highest priority (sections 2.4.2.5 and 2.4.6.1). The SDK's startup vector table agrees: its entries for MemManage, BusFault and UsageFault are reserved slots that never fire on the RP2040 (src/rp2_common/pico_crt0/crt0.S, pico-sdk 2.3.1).

The STM32F103's vector table has separate handlers for MemManage_Handler, BusFault_Handler and UsageFault_Handler (startup_stm32f103xb.s). The ST device header sets __MPU_PRESENT to 0 and says that "other STM32 devices does not provide an MPU". So the MPU is absent on this part, even though the core has the MPU architecture.

Do not assume an MPU exists because the core is a Cortex-M3. The MPU is an option the chip maker chooses. Check __MPU_PRESENT in the device header before you write any MPU code.

Reading the fault status

The Cortex-M3 keeps its fault information in the System Control Block (SCB). The base is 0xE000ED00. The configurable fault status register CFSR is at offset 0x28, so its address is 0xE000ED28. It combines the MemManage, BusFault and UsageFault status bits. The HardFault status register HFSR is at offset 0x2C, and its FORCED bit (bit 30) says that a configurable fault was escalated to HardFault because the configurable fault could not be taken on its own. All of these come from core_cm3.h in the CMSIS sources.

The workflow after a fault is short. Read HFSR to see whether it was forced. Read CFSR to see which kind of fault it was. Only then look at the stacked program counter in the exception frame, which tells you where the fault happened. Lesson 34 explains that frame.

The CMSIS header is the source for the register addresses and bit names used here. The meaning of each CFSR bit is in the Cortex-M3 programming manual, PM0056, in its fault section. This course has not yet checked those bit meanings against that text, so look them up before you rely on one.

"A Cortex-M3 board hard-faults after a pointer bug. What do you read, and in what order?" Answer out loud in 60 seconds, then compare.

Model answer

Read HFSR first, to see whether the HardFault was forced by a configurable fault that could not be handled. Then read CFSR for the specific cause, such as a bus error or a usage fault bit. If the status says the address is valid, read the MMFAR or BFAR address register, which holds the faulting address. Finally, read the stacked program counter from the exception frame to find the instruction that faulted. On a Cortex-M0+, such as the RP2040, there is only HardFault, so the cause has to be found from the stacked frame and the program's own state.

RP2040 datasheet: section 2.4.6 (MPU), 2.4.6.1 (About the MPU), and the MPU register summary in 2.4.6.2. Read it for the one-fault model on the M0+. For the M3 fault bits, read PM0056 next, in its fault exception section.
