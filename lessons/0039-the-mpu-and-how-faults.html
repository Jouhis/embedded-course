The MPU and how faults happen

A bad pointer does not crash the chip politely. It raises an exception, and which exception depends on the core you are running on.

By the end of this lesson you can say which fault exceptions the RP2040's Cortex-M0+ and the STM32F103's Cortex-M3 can raise, whether each part has an MPU, and which status register you would read first after a fault.

Where we are and why it matters

Lesson 34 showed the core's exception mechanism: when an exception fires, the core saves a frame of registers on the stack, then runs the handler whose address it reads from the vector table. Lesson 38 showed how a peripheral register is just an address. Both ideas matter here, because a fault is simply an exception that the core raises when something goes wrong with an access or an instruction.

The problem this lesson solves is the field failure. A device runs for days, then resets, and the only evidence is what the firmware left behind. In industry the usual first step is a fault handler that stores the fault registers somewhere that survives the reset. To write that handler, or to read one, you need to know which faults exist on your chip and which registers record them. Those depend on the core and the part, so this lesson compares the two chips you use.

What a fault is

A fault is an exception that the core raises when it cannot complete an access or an instruction. Three kinds of problem usually cause one: the program touches an address that is forbidden or that has no device behind it, the program executes an instruction the core does not accept, or the program breaks a protection rule. The core does not guess. It stops the normal flow, saves the frame, and jumps to the handler for that fault, exactly as it does for an interrupt.

The Cortex-M3 separates faults into families. Each family has its own handler and its own status bits. The families are MemManage for protection violations, BusFault for errors reported by the bus, and UsageFault for instruction-level problems such as an undefined instruction. A fourth exception, HardFault, is the catch-all. It is taken when a configurable fault cannot be handled on its own, and when the core has no other place to go.

The memory protection unit

The memory protection unit (MPU) is an optional block that checks each access against a list of rules. Each rule is a region, with a base address, a size, and permissions that say what code may read, write or execute there. An access that matches no permitted region, or breaks the rule of the region it falls in, causes a fault. The MPU lets an operating system keep one task out of another task's memory, and it can stop a stray pointer from overwriting a stack.

The MPU is optional. ARM defines the Cortex-M cores with or without it, and the chip maker chooses. That is the first fact to check, and the two chips in this course answer it differently.

On the RP2040, the datasheet says that MPU mismatches and permission violations invoke the HardFault handler. The MPU has eight unified regions, with overlapping priorities where region 7 is the highest (RP2040 datasheet, section 2.4.6.1 (About the MPU) and the feature list in 2.4.2.5). The SDK's vector table agrees. Its entries for MemManage, BusFault and UsageFault are marked "Reserved, should never fire" on the RP2040, and the four slots after HardFault are all isr_invalid (src/rp2_common/pico_crt0/crt0.S, pico-sdk 2.3.1). The M0+ has no such exceptions, so it has no handler for them.

The STM32F103's vector table has separate handlers for MemManage_Handler, BusFault_Handler and UsageFault_Handler. They sit at words 4, 5 and 6 of the table, right after HardFault_Handler at word 3 (third_party/cmsis-device-f1/Source/Templates/gcc/startup_stm32f103xb.s). The device header sets __MPU_PRESENT to 0 for this part, with the comment "Other STM32 devices does not provide an MPU" (third_party/cmsis-device-f1/Include/stm32f103xb.h, line 50). The XL-density variant, stm32f103xg.h, sets it to 1 with the comment "STM32 XL-density devices provide an MPU". So the same core can come with or without an MPU, depending on the chip.

Do not assume an MPU exists because the core is a Cortex-M3. Check __MPU_PRESENT in the device header for your exact part before you write any MPU code. On the Blue Pill it is 0, and MPU register writes do nothing useful.

The status registers, one at a time

The Cortex-M3 keeps its fault information in the System Control Block (SCB), a block of registers in the core's own address space. The header computes its base as SCS_BASE + 0x0D00, where SCS_BASE is 0xE000E000, so the SCB starts at 0xE000ED00 (third_party/CMSIS_5/CMSIS/Core/Include/core_cm3.h). Four offsets matter for faults. The struct in the same header lists them:

  • CFSR, the Configurable Fault Status Register, at offset 0x28, so address 0xE000ED28. It holds the MemManage, BusFault and UsageFault status bits in one word.
  • HFSR, the HardFault Status Register, at offset 0x2C, address 0xE000ED2C.
  • MMFAR, the MemManage Fault Address Register, at offset 0x34.
  • BFAR, the BusFault Address Register, at offset 0x38.

The CFSR word is three status bytes packed together. The header gives each group its bit range: bits 0 to 7 belong to MemManage, bits 8 to 15 to BusFault, and bits 16 to 31 to UsageFault. Inside each group, the header names every bit with a position. The bits this lesson uses are these:

The HFSR has one bit that matters first. FORCED is bit 30, and the header defines it as 1UL << 30. It is set when a configurable fault was escalated to HardFault. The header gives the names and positions, and that is what this lesson relies on. What each bit means in detail, and when the core sets it, is in the Cortex-M3 programming manual PM0056, which this course has not yet checked against its text. Read that section before you rely on the meaning of any bit.

A worked example: decoding a fault

Suppose your fault handler stored these two words in RAM, and you are now reading them on your desk. HFSR = 0x40000000 and CFSR = 0x00008200. Decode them in order, the same order you would use on a real board.

  1. HFSR first. Write 0x40000000 in binary: a single 1 at bit 30. That is FORCED. The core reached HardFault because a configurable fault was escalated, so the real cause is in CFSR.
  2. Split CFSR into its groups. 0x00008200 has bits 9 and 15 set. Bit 9 and bit 15 are both in the BusFault group, bits 8 to 15. The MemManage and UsageFault bytes are zero.
  3. Add the bit values. Bit 15 is 0x8000 and bit 9 is 0x0200. Their sum is 0x8200, which matches the register.
  4. Name the bits. Bit 9 is PRECISERR, and bit 15 is BFARVALID, the names the header gives them. From the names, bit 15 says that BFAR holds the faulting address, and bit 9 says that the bus error is precise. PM0056 is the place to confirm both meanings.
  5. Read the address. Because BFARVALID is set, the next step is to read BFAR. Had that bit been 0, BFAR would not hold a fault address you could trust, and you would look at the stacked program counter instead.

Now try a UsageFault. CFSR = 0x01000000 is 224, so bit 24 is set. In the UsageFault group that is bit 8 (24 minus 16), and the header names it UNALIGNED. The fault came from an unaligned access, and you find the offending instruction from the stacked PC. Lesson 34 explains the frame that holds that PC.

The code that reads the registers

The project projects/0039-mpu-and-faults prints the registers without a fault, so you can see the reading code work. The key lines are these: 

print_line("SCB->CFSR (fault status):  ", SCB->CFSR);
print_line("SCB->HFSR (hard fault):     ", SCB->HFSR);
print_line("__MPU_PRESENT (header):     ", __MPU_PRESENT);   /* 0 on STM32F103 */

SCB is a macro in the CMSIS header that points at the SCB struct, at 0xE000ED00. The expression SCB->CFSR is therefore a load from 0xE000ED28, the same address you computed above from the offset. The compiler does this sum for you, as lesson 38 showed. __MPU_PRESENT is not a register at all. It is a constant from the header, so the value it prints is decided at build time. The project prints it as hex with print_hex, which is why the serial line reads 0x00000000 and not 0.

The print_line helper is the only part that talks to the serial port. It sends the label, the hex value and a carriage return and line feed (\r\n). The UART setup in the same file routes that output to the simulator's serial monitor on PA9, as the template describes.

The SCB base is 0xE000ED00. Add the CFSR offset 0x28 to get 0xE000ED28, and add 0x2C for HFSR. The HFSR bit FORCED is bit 30, so its mask is 0x40000000.

Common mistakes

Each mistake below is one that people make on their first fault investigation. The symptom is what you see, and the fix is what to change.

Mistake 1: writing MPU code on a part without an MPU

Symptom: the code configures regions, the build passes, and the protection you expected never triggers. A stray pointer overwrites memory without a fault. Fix: check __MPU_PRESENT in the device header before any MPU code. Guard MPU setup with #if __MPU_PRESENT so the build fails or skips the code on a part that has no MPU.

Mistake 2: reading CFSR and skipping HFSR

Symptom: the log says "fault", and you look for a cause in the bus status bits, but you find nothing that matches. The actual fault was a UsageFault escalated to HardFault. Fix: read HFSR first. If FORCED is set, the cause is in CFSR, and you should decode that group. If you only read CFSR, you may decode a fault that was never the one that fired.

Mistake 3: trusting BFAR or MMFAR without checking the valid bit

Symptom: your log shows a faulting address, but it looks random, and it does not point at the code you expected. Fix: check BFARVALID (bit 15) before you read BFAR, and MMARVALID (bit 7) before you read MMFAR. If the valid bit is clear, the address register does not hold the fault address, so use the stacked program counter instead.

Mistake 4: looking for a MemManage handler on the RP2040

Symptom: you set a breakpoint on MemManage_Handler in a Pico project, and it never fires, even though an MPU rule was broken. Fix: on the M0+, MPU violations go to HardFault. Put the breakpoint on the HardFault handler, which is the only fault handler on that core.

In real projects

Production firmware usually has one fault handler per family, or one shared handler that saves the frame and the status registers into a region of RAM that the startup code does not clear. The RAM region and the reset reason are then read on the next boot, and the team has a crash log. Such a handler is short, and a senior engineer will ask three things in review: does it read HFSR before CFSR, does it check the valid bits before it reports an address, and does it avoid calling the functions that might fault again. Each of those checks comes straight from the sections above.

In interviews, the question is usually "a hard fault happened, what do you read?" The answer that shows understanding names the registers, gives the reading order, and states which parts of the answer depend on the chip. Saying "the M0+ has only HardFault, so the cause comes from the stacked frame and the program state" is a strong answer, because it shows you know the core, not only the register names.

Summary

  • A fault is an exception the core raises when an access or instruction cannot complete.
  • The RP2040's Cortex-M0+ has an 8-region MPU and only HardFault. MPU violations go to HardFault.
  • The STM32F103's Cortex-M3 has MemManage, BusFault and UsageFault, plus HardFault, and the Blue Pill has no MPU (__MPU_PRESENT is 0).
  • The SCB is at 0xE000ED00. CFSR is at offset 0x28, HFSR at 0x2C, MMFAR at 0x34 and BFAR at 0x38.
  • CFSR packs three groups: MemManage in bits 0 to 7, BusFault in bits 8 to 15, UsageFault in bits 16 to 31.
  • Read HFSR first, then decode CFSR, then check the valid bit before you use an address register.
  • The meaning of each bit is in PM0056, and the header only gives names and positions.

"A Cortex-M3 board hard-faults after a pointer bug. What do you read, and in what order?" Answer out loud in 60 seconds, then compare.

Model answer

Read HFSR first, to see whether the HardFault was forced by a configurable fault that could not be handled on its own. Then read CFSR and decode its group for the specific cause, such as a bus error or a usage fault bit. If the valid bit for an address is set, read BFAR or MMFAR, which holds the faulting address. Finally, read the stacked program counter from the exception frame to find the instruction that faulted. On a Cortex-M0+, such as the RP2040, there is only HardFault, so the cause has to be found from the stacked frame and the program's own state.

RP2040 datasheet: section 2.4.2.5 (MPU features), 2.4.6.1 (About the MPU) and 2.4.6.2 (MPU register summary). Read it for the one-fault model on the M0+. For the M3 fault bits, read PM0056 next, in its fault exception section.
