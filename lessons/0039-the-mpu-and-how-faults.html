The MPU and how faults happen

Memory protection and the fault exceptions of Cortex-M cores

By the end of this lesson you can say which fault exceptions the RP2040's Cortex-M0+ and the STM32F103's Cortex-M3 can raise, whether each part has an MPU, and which status register you would read first after a fault.

Faults in the field

Lesson 34 showed the core's exception mechanism, in which the core saves a frame of registers on the stack and runs the handler whose address it reads from the vector table, and lesson 38 showed that a peripheral register is just an address. Both ideas matter here, because a fault is simply an exception the core raises when something goes wrong with an access or an instruction.

The practical problem is the field failure. A device runs for days, then resets, and the only evidence is whatever the firmware left behind, so the usual first step in industry is a fault handler that stores the fault registers somewhere that survives the reset. Writing or reading such a handler requires knowing which faults exist on the chip and which registers record them, and since both depend on the core and the part, this lesson compares the two chips used in the course.

Faults and fault families

A fault is an exception that the core raises when it cannot complete an access or an instruction. Three kinds of problem usually cause one: touching an address that is forbidden or has no device behind it, executing an instruction the core does not accept, or breaking a protection rule. Like an interrupt, a fault stops the normal flow, saves the frame and jumps to its handler.

The Cortex-M3 divides faults into families, each with its own handler and status bits: MemManage for protection violations, BusFault for errors reported by the bus, and UsageFault for instruction-level problems such as an undefined instruction. A fourth exception, HardFault, is the catch-all, taken when a configurable fault cannot be handled on its own and when the core has nowhere else to go. PM0056 Rev 7 lists the fault types and their handlers in section 2.4.1 (Table 18) and describes escalation to HardFault in section 2.4.2.

The memory protection unit

The memory protection unit (MPU) is an optional block that checks each access against a list of rules. Each rule is a region with a base address, a size and permissions stating what code may read, write or execute there, and an access that matches no permitted region, or breaks the rule of its region, causes a fault. An operating system uses the MPU to keep one task out of another task's memory, and it can stop a stray pointer from overwriting a stack.

Because ARM defines the Cortex-M cores with or without an MPU, the chip maker decides whether to include one. PM0056 Rev 7, section 4.2, notes that the MPU is implemented in some STM32 microcontrollers and that the device datasheet shows whether a given part has one. That is the first fact to check, and the two chips in this course answer it differently.

The MPU works like a badge reader on every door of an office. Each access presents its badge, made up of the address, the kind of access and the privilege level, a refused badge raises the alarm, which is the fault, and the fault status registers are the security log recording which rule was broken and, when the valid bit says so, at which door. A real badge system can let a guard wave someone through, but the MPU has no such exception: a refused access always faults.

On the RP2040 the datasheet states that MPU mismatches and permission violations invoke the HardFault handler, and that the MPU has eight unified regions with overlapping priorities, region 7 being the highest (RP2040 datasheet, section 2.4.6.1 (About the MPU) and the feature list in 2.4.2.5). The SDK's vector table agrees, marking its MemManage, BusFault and UsageFault entries "Reserved, should never fire" on the RP2040 and filling the four slots after HardFault with isr_invalid (src/rp2_common/pico_crt0/crt0.S, pico-sdk 2.3.1). The M0+ has no such exceptions and therefore no handlers for them.

The STM32F103's vector table has separate handlers, MemManage_Handler, BusFault_Handler and UsageFault_Handler, at words 4, 5 and 6, right after HardFault_Handler at word 3 (third_party/cmsis-device-f1/Source/Templates/gcc/startup_stm32f103xb.s). The device header, however, sets __MPU_PRESENT to 0 for this part, with the comment "Other STM32 devices does not provide an MPU" (third_party/cmsis-device-f1/Include/stm32f103xb.h, line 50), while the XL-density header stm32f103xg.h sets it to 1 with the comment "STM32 XL-density devices provide an MPU". The same core can therefore come with or without an MPU, depending on the chip.

Do not assume an MPU exists because the core is a Cortex-M3. Check __MPU_PRESENT in the device header for your exact part before writing any MPU code, as PM0056 Rev 7, section 4.2, also advises via the device datasheet. On the Blue Pill it is 0, and MPU register writes do nothing useful.

The Cortex-M3 fault status registers

The Cortex-M3 keeps its fault information in the System Control Block (SCB), a block of registers in the core's own address space. The header computes its base as SCS_BASE + 0x0D00, with SCS_BASE at 0xE000E000, so the SCB starts at 0xE000ED00 (third_party/CMSIS_5/CMSIS/Core/Include/core_cm3.h), the same base PM0056 Rev 7 gives in section 4.4.15. Four offsets in the header's struct matter for faults:

  • CFSR, the Configurable Fault Status Register, at offset 0x28, address 0xE000ED28, holding the MemManage, BusFault and UsageFault status bits in one word (PM0056 Rev 7, section 4.4.10).
  • HFSR, the HardFault Status Register, at offset 0x2C, address 0xE000ED2C (PM0056 Rev 7, section 4.4.11).
  • MMFAR, the MemManage Fault Address Register, at offset 0x34 (PM0056 Rev 7, section 4.4.12).
  • BFAR, the BusFault Address Register, at offset 0x38 (PM0056 Rev 7, section 4.4.13).

The CFSR word packs three status groups together, which the header assigns to bits 0 to 7 for MemManage, 8 to 15 for BusFault and 16 to 31 for UsageFault, matching PM0056 Rev 7, section 4.4.10 and Figure 20. Within each group the header names every bit with its position, and the table lists the bits used in this lesson, whose positions and names PM0056 gives in the same section.

In the HFSR one bit matters first. FORCED is bit 30, defined in the header as 1UL << 30, and according to PM0056 Rev 7, section 4.4.11, it is set when a fault with configurable priority is escalated to a hard fault, in which case the hard fault handler must read the other fault status registers. The header supplies the names and positions, while the programming manual PM0056 defines what each bit means, so read section 4.4.10 for the CFSR bits and section 4.4.11 for HFSR before relying on any bit's meaning.

Worked example: decoding a BusFault

Suppose a fault handler stored two words in RAM, HFSR = 0x40000000 and CFSR = 0x00008200, which we now read at the desk. We decode them in the order used on a real board, and before starting it is worth guessing which fault family the CFSR value belongs to.

  1. Read HFSR first. 0x40000000 in binary is a single 1 at bit 30, which is FORCED, so the core reached HardFault through an escalated configurable fault and the real cause lies in CFSR.
  2. Split CFSR into its groups. 0x00008200 has bits 9 and 15 set, both within the BusFault group of bits 8 to 15, while the MemManage and UsageFault bytes are zero.
  3. Check the bit values. Bit 15 is 0x8000 and bit 9 is 0x0200, which sum to 0x8200, matching the register.
  4. Name the bits. The header calls bit 9 PRECISERR and bit 15 BFARVALID, and PM0056 Rev 7, section 4.4.10, confirms their meanings: PRECISERR means that the PC stacked for the return points to the instruction that caused the fault, with the faulting address written to BFAR, and BFARVALID means that BFAR holds a valid fault address.
  5. Read the address. Since BFARVALID is set, the next step is to read BFAR. Had the bit been 0, BFAR would not hold a trustworthy fault address, and the stacked program counter would be the place to look instead.

A UsageFault decodes the same way. CFSR = 0x01000000 is 224, so bit 24 is set, which is bit 8 within the UsageFault group (24 minus 16), named UNALIGNED in the header and in PM0056 Rev 7, section 4.4.10. The fault came from an unaligned access, and the offending instruction is found from the stacked PC, whose frame lesson 34 explains.

Reading the registers in code

The project projects/0039-mpu-and-faults prints the registers without a fault so that the reading code can be seen working, and its key lines are these. 

print_line("SCB->CFSR (fault status):  ", SCB->CFSR);
print_line("SCB->HFSR (hard fault):     ", SCB->HFSR);
print_line("__MPU_PRESENT (header):     ", __MPU_PRESENT);   /* 0 on STM32F103 */

SCB is a CMSIS header macro pointing at the SCB struct at 0xE000ED00, so SCB->CFSR is a load from 0xE000ED28, the address computed above from the offset, with the compiler doing the sum as lesson 38 showed. __MPU_PRESENT is not a register but a header constant, so the value it prints is fixed at build time, and since the project prints it in hex with print_hex, the serial line reads 0x00000000 rather than 0.

The print_line helper is the only part that talks to the serial port, sending the label, the hex value and a carriage return and line feed (\r\n), and the UART setup in the same file routes that output to the simulator's serial monitor on PA9, as the template describes.

Common mistakes and how to spot them

MPU code on a part without an MPU

The code configures regions and the build passes, but the expected protection never triggers, and a stray pointer overwrites memory without any fault. Check __MPU_PRESENT in the device header before writing MPU code, and guard the setup with #if __MPU_PRESENT so that the build fails or skips it on a part without an MPU.

CFSR read and HFSR skipped

The log reports a fault, and a search through the bus status bits finds nothing that matches, because the real fault was a UsageFault escalated to HardFault. Read HFSR first, and if FORCED is set, decode the CFSR group it points to, as PM0056 Rev 7, section 4.4.11, requires of the hard fault handler; reading only CFSR risks decoding a fault that never fired.

BFAR or MMFAR trusted without the valid bit

The log shows a faulting address that looks random and does not point at the expected code. Check BFARVALID (bit 15) before reading BFAR and MMARVALID (bit 7) before reading MMFAR (PM0056 Rev 7, section 4.4.14), and if the valid bit is clear, use the stacked program counter instead, because the address register does not hold the fault address.

A MemManage handler expected on the RP2040

A breakpoint on MemManage_Handler in a Pico project never fires even though an MPU rule was broken. On the M0+ MPU violations go to HardFault, so put the breakpoint on the HardFault handler, the only fault handler on that core.

Fault handlers in production firmware

Production firmware usually has one fault handler per family, or a single shared handler, that saves the frame and the status registers into a RAM region the startup code does not clear. On the next boot that region and the reset reason are read back, giving the team a crash log. Such a handler is short, and a senior engineer reviewing it asks whether it reads HFSR before CFSR, whether it checks the valid bits before reporting an address and whether it avoids calling functions that might fault again, each check following directly from the sections above.

Summary

  • A fault is an exception the core raises when an access or instruction cannot complete.
  • The RP2040's Cortex-M0+ has an 8-region MPU and only HardFault, to which MPU violations go.
  • The STM32F103's Cortex-M3 has MemManage, BusFault and UsageFault in addition to HardFault, and the Blue Pill has no MPU (__MPU_PRESENT is 0).
  • The SCB is at 0xE000ED00, with CFSR at offset 0x28, HFSR at 0x2C, MMFAR at 0x34 and BFAR at 0x38.
  • CFSR packs three groups: MemManage in bits 0 to 7, BusFault in bits 8 to 15 and UsageFault in bits 16 to 31.
  • Read HFSR first, then decode CFSR, and check the valid bit before using an address register.
  • Each bit's meaning is defined in PM0056 Rev 7, sections 4.4.10 to 4.4.13, while the header only gives names and positions.
RP2040 datasheet: section 2.4.2.5 (MPU features), 2.4.6.1 (About the MPU) and 2.4.6.2 (MPU register summary). Read it for the one-fault model on the M0+. For the M3 fault bits, read PM0056 Rev 7 next: section 2.4 (fault handling), and sections 4.4.10 to 4.4.13 (the fault registers).
