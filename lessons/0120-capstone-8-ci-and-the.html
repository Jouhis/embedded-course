Capstone 8: CI and the finished capstone

A capstone is finished when a machine can check it on every change and a person can explain what those checks do not cover. This last stage shows the pipeline, and then it takes stock of the whole project.

By the end of this lesson you can read the dryer's CI workflow job by job, say which failures block a change and which only report, run the host tests and the static analysis the way CI runs them, and name the capstone lesson where each part of the dryer was taught.

Where we are and why it matters

Lessons 113 to 119 built the dryer part by part: its requirements, its drivers, its control loop, its Modbus interface and its bootloader. This lesson covers the last piece, the checks that run on every change, and then the capstone as a whole.

Continuous integration (CI) was introduced in lesson 82, where a sample workflow ran on a small project. Lesson 83 added static analysis with cppcheck, and lesson 80 introduced the host unit tests. The workflow in this project puts those pieces together for the dryer. It runs the same checks, on the same sources, that a developer runs on a laptop.

What CI runs on every change

Continuous integration is a service that runs a fixed list of commands on every change, so a broken change is caught before it reaches a board. The dryer's workflow has four jobs. A job is a set of steps that run on a fresh machine, and its needs line says which jobs must pass before it starts. A job whose needed job fails is skipped, and so is every job that depends on it.

JobNeedsWhat it doesWhat a failure blocks
host-testsnothingBuilds the host test project with CMake and Ninja, then runs ctest on its ten test programsThe firmware job and, through it, the simulation
static-analysisnothingRuns cppcheck on the firmware sources, and fails on any warning or style findingThe firmware job and, through it, the simulation
firmwarehost-tests, static-analysisBuilds the bootloader and the application as one ELF, prints the sizes, and keeps the ELF, the hex and the map fileThe simulation
simulatefirmwareRuns the firmware in Wokwi and expects the banner DRYER RTOS OK within 10 seconds, when the token is setOnly the run itself, because nothing waits after it

The two jobs with no needs line start together, and the other two wait for them. A change that fails a test therefore never produces a firmware image, and a change that fails static analysis never reaches the simulator. The order is the design. Each job checks something more basic than the job after it, and the cheap checks run first, so a failure stops the expensive steps early.

The workflow file, step by step

The workflow is projects/0118-dryer-modbus-bootloader/.github/workflows/ci.yml. It is adapted from the sample in lesson 82. GitHub reads workflows only from the .github/workflows folder at the root of a repository, so the copy inside the project folder is there for reading. To make it run, copy it to the root of the repository and keep the course layout, because the paths in the file and in the CMake files are relative to the root. The file's first comment says the same thing.

The excerpts below leave out the comments in the file. Each one is followed by what its lines do.

The triggers and the shared settings

name: dryer-ci

on:
  push:
  pull_request:

env:
  FIRMWARE: projects/0118-dryer-modbus-bootloader/solution
  HOST_TESTS: projects/0120-dryer-host-tests/solution
  • name is the label that appears in the Actions tab and on the pull request.
  • on lists the events that start the workflow. Here a push to any branch and a pull request both start it. A pull request from a branch in the same repository therefore runs twice, once for the push and once for the pull request. A branch filter can reduce that cost.
  • env sets two variables for every job. FIRMWARE is the folder of the firmware, and HOST_TESTS is the folder of the host test project. Later lines use $FIRMWARE and $HOST_TESTS, so a path changes in one place.

The host-tests job

  host-tests:
    name: Host unit tests and closed loop
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - name: Install CMake and Ninja
        run: sudo apt-get update && sudo apt-get install -y cmake ninja-build
      - name: Build and run the unit tests (ctest)
        run: |
          cmake -S $HOST_TESTS -B build-host -G Ninja
          cmake --build build-host
          ctest --test-dir build-host --output-on-failure
  • runs-on: ubuntu-latest asks for a fresh Linux machine. Nothing from an earlier run is kept on it, which is why every job begins with a checkout.
  • uses: actions/checkout@v4 downloads the repository into the job. Without it the machine has no source files.
  • The install step adds CMake and Ninja. The host tests use the Ninja generator, so the commands here match the ones you run locally.
  • cmake -S $HOST_TESTS -B build-host -G Ninja configures the project. -S names the source folder and -B names the build folder, which is created inside the job.
  • cmake --build build-host compiles the test programs and the application sources they use.
  • ctest --test-dir build-host --output-on-failure runs every test program. The flag prints the output of a failing test, so the log says what failed without a second run. The step fails if any test fails.

The static-analysis job

  static-analysis:
    name: Static analysis (cppcheck)
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - name: Install cppcheck
        run: sudo apt-get update && sudo apt-get install -y cppcheck
      - name: Check the firmware sources
        run: >
          cppcheck --enable=warning,style --inline-suppr --error-exitcode=1 --std=c11 --quiet
          -I $FIRMWARE/app -I $FIRMWARE/rtos -I $FIRMWARE/boot -I $FIRMWARE
          $FIRMWARE/app $FIRMWARE/rtos/tasks.c $FIRMWARE/boot/bootloader.c $FIRMWARE/boot/app_vectors.c $FIRMWARE/main.c
  • The job follows the same checkout and install pattern as the others, with cppcheck in place of CMake.
  • run: > folds the following lines into one shell command, so the three lines below it are read as one long command.
  • --enable=warning,style turns on the warning and style checks. Lesson 83 explains what each class catches.
  • --inline-suppr lets a source file silence a single finding with a comment. Each suppression is then visible in the code and in review.
  • --error-exitcode=1 is the flag that makes this job a gate. cppcheck returns 1 when it reports any finding, and returns 0 otherwise. Without the flag, the job would show a green result even with findings in the log. The Try it in this lesson tests this on purpose.
  • --std=c11 sets the language standard, and --quiet hides the progress lines, so the log holds only the findings.
  • -I adds the include folders, so cppcheck can resolve the headers that the sources include. The last line lists the folders and files to check. The folder $FIRMWARE/app is checked recursively.

The firmware job

  firmware:
    name: Build the firmware (bootloader + application, one ELF)
    needs: [host-tests, static-analysis]
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - name: Install the Arm GCC toolchain
        uses: carlosperate/arm-none-eabi-gcc-action@v1
        with:
          release: '15.3.Rel2'
      - name: Install CMake and Ninja
        run: sudo apt-get update && sudo apt-get install -y cmake ninja-build
      - name: Build (Debug, with the ELF, the hex and the map file)
        run: |
          cmake -S $FIRMWARE -B $FIRMWARE/build -G Ninja -DCMAKE_BUILD_TYPE=Debug
          cmake --build $FIRMWARE/build
          arm-none-eabi-size $FIRMWARE/build/dryer.elf
      - name: Keep the build outputs
        uses: actions/upload-artifact@v4
        with:
          name: firmware
          path: |
            ${{ env.FIRMWARE }}/build/dryer.elf
            ${{ env.FIRMWARE }}/build/dryer.hex
            ${{ env.FIRMWARE }}/build/dryer.map
  • needs: [host-tests, static-analysis] makes this job wait for both. If either one fails, the firmware is not built at all.
  • The Arm action installs the cross compiler, pinned to release 15.3.Rel2. The local workspace uses Arm GNU 14.2, so the two builds can differ slightly, as the note in lesson 119 says. A real project pins one release in both places.
  • The Debug build type is the configuration that lesson 119 measured. The build writes the ELF, the hex and the map file into the build folder.
  • arm-none-eabi-size prints the text, data and bss columns that lesson 119 reports, so the size of every build is in the log.
  • upload-artifact@v4 keeps the three files after the job ends. A reviewer can download the exact image that CI built, and the simulate job uses the same files.

The simulate job

  simulate:
    name: Simulate in Wokwi (only when the token is set)
    needs: firmware
    runs-on: ubuntu-latest
    env:
      WOKWI_CLI_TOKEN: ${{ secrets.WOKWI_CLI_TOKEN }}
    steps:
      - uses: actions/checkout@v4
      - name: Check that the token is present
        id: token
        run: |
          if [ -n "$WOKWI_CLI_TOKEN" ]; then echo "present=true" >> "$GITHUB_OUTPUT"; else echo "present=false" >> "$GITHUB_OUTPUT"; echo "WOKWI_CLI_TOKEN not set: the simulation is skipped"; fi
      - name: Download the firmware
        if: steps.token.outputs.present == 'true'
        uses: actions/download-artifact@v4
        with:
          name: firmware
          path: ${{ env.FIRMWARE }}/build
      - name: Run the simulation and expect the banner
        if: steps.token.outputs.present == 'true'
        uses: wokwi/wokwi-ci-action@v1
        with:
          token: ${{ secrets.WOKWI_CLI_TOKEN }}
          path: ${{ env.FIRMWARE }}
          timeout: 10000
          expect_text: 'DRYER RTOS OK'
  • needs: firmware means the simulation runs only on an image that has already built. It downloads that image rather than building it again.
  • env passes the repository secret into the job as the variable WOKWI_CLI_TOKEN. The expression ${{ secrets.WOKWI_CLI_TOKEN }} reads the secret without writing its value into the file.
  • The token check is a short shell script. It tests whether the variable is empty, and it writes present=true or present=false to $GITHUB_OUTPUT. Later steps read that output in their if: lines.
  • The check is a step, not an if: on the whole job, and the comment in the file gives the reason: a secret cannot be tested in a job-level condition. The step writes the result out, and the other steps read it.
  • The download step restores the firmware into the build folder, so the simulator runs the same image that the firmware job produced.
  • wokwi/wokwi-ci-action@v1 runs the simulation for at most 10000 ms, which is the timeout. It fails unless the serial output contains DRYER RTOS OK, the expect_text. This is the same check that lesson 82 described, with the same inputs.

This job differs from the sample in lesson 82. The sample skipped the whole job for a pull request from a fork, while this file runs the job and skips only its steps. Both give a green result for a fork, so the difference matters for how you read the log. A green simulate job for a fork contains no simulation. The token step prints a line that says so, and a reviewer who reads only the green tick would miss it.

How the host tests run in CI

The host-tests job builds one project, projects/0120-dryer-host-tests/solution, and runs ten test programs from it. The project is a CMake project that compiles with the PC's compiler, not with the Arm compiler. Its CMake file shows how the same application code is tested on a PC and built for the board.

The file starts by building Unity, the test framework, from the copy in the third_party folder. Unity becomes a static library, a single archive that each test program links against. The next block holds the central idea. It builds a library called dryer_app from the application sources in projects/0118-dryer-modbus-bootloader/solution/app, which are the same files the firmware compiles. The tests therefore check the code that ships, not a copy of it. The thermal model used by the closed-loop test comes from the plant of lesson 108, and it is compiled into the same library.

The last block is the list of tests. It is a loop over ten names, and each name becomes one executable and one test: 

enable_testing()
foreach(t ntc safety dryer ui debounce filters controller closed_loop modbus regmap)
  add_executable(test_${t} test/test_${t}.c)
  target_link_libraries(test_${t} dryer_app unity)
  add_test(NAME ${t} COMMAND test_${t})
endforeach()
  • enable_testing() turns on the test runner, ctest, for this project.
  • The foreach line lists the test names. Each name stands for a file in the test folder, so ntc means test_ntc.c.
  • add_executable compiles one test file into a program. target_link_libraries links that program to the application library and to Unity.
  • add_test registers the program with ctest. The name is what the summary prints.

Each test program is a small main() that runs its Unity tests and returns the failure count. The Unity header states that the return value of the test's main() becomes the exit code of the program. A test that fails therefore makes its program exit with a non-zero code, and ctest marks that test as failed. The CI step fails when any of the ten is marked failed.

The foreach list is the one place where a new test file must be named. Creating test/test_fan.c is not enough. If its name is not in the list, CMake never builds it and ctest never runs it. That is mistake 2 below, and it is easy to make, because nothing reports an error. The count in the summary is the only sign, which is why it is worth reading every time.

Review the finished project

Open the repository and walk through the requirements table from lesson 113, with each acceptance criterion pointing to a test. Run the host tests live, then show the closed-loop output and explain what the 80.4 s runaway means: a dead heater, at full power with no rise in temperature, is caught after 80.4 s, inside the 300 s limit the test sets. Show the linker script and the header, and explain why the bootloader needs no copy of RAM. Finally show the CI workflow and the cppcheck line. Be honest about the limits: the sizes are the simulator's, the PID was not tuned on a real chamber, the presets are a compile-time table, and the display flush takes a large share of the CPU. Writing those limits down first makes the project more credible than claiming a perfect design.

Common mistakes and how to spot them

Each of these mistakes lets a broken change through without a visible error. Each entry gives the symptom first.

Mistake 1: a check that reports but cannot fail

Symptom: the static-analysis job is green, and the log lists style findings a few lines above the end. Cause: the step runs cppcheck without --error-exitcode=1, so cppcheck exits with 0 even when it reports findings. Fix: keep the flag, and run the probe in the Try it to see the exit code change. A check that cannot fail is a log, not a gate.

Mistake 2: a new test file that is not in the list

Symptom: you add a test file with a failing check, push, and the summary still reads 100% tests passed out of 10, when it should read 11. Cause: the file's name is not in the foreach list in CMakeLists.txt, so the program is never built. Fix: add the name to the list. Then check that the count rises by one. If it does not, the test is not running.

Mistake 3: the workflow in the wrong folder

Symptom: the pull request shows no checks at all, and the Actions tab lists no run for the dryer. Cause: the file is in projects/0118-dryer-modbus-bootloader/.github/workflows/, which GitHub does not read. Only the root of the repository is read. Fix: copy ci.yml to the root's .github/workflows folder. The paths in the file are relative to the root, so keep the course layout beside it.

Mistake 4: a skipped check that looks like a pass

Symptom: the simulate job is green on every branch, including the main branch, and nobody has seen the banner in the log. Cause: the token is missing on that branch, so the token step writes present=false, prints the skip line and every later step is skipped. The job still completes. Fix: read the skip line in the log, and decide on purpose whether a missing token should fail the run on the main branch. If it should, add a condition that fails on that branch, and say so in the repository's README.

In real projects

A team decides what CI blocks and what it only reports, and the choice matters more than the tools. A pipeline that only reports is easy to ignore, while one that fails the merge gets fixed. Most teams make the required checks part of the repository's protection rules, so that a change cannot be merged until those checks pass. The four jobs here follow that rule: a failing test stops the firmware build, and a cppcheck finding fails its job.

Some results in this pipeline are reported and not gated. The size of the firmware is printed in the log, but no limit fails the job. A slow growth in size, one feature at a time, is then visible only to a reader who looks at the log. Teams that care about size usually add a threshold that fails the job, or they store the sizes per commit so that the trend can be drawn. Either change is a small edit to this file.

What the simulation proves is also a limit. The Wokwi run shows that the firmware boots in the simulator and prints the banner. It does not show that the sensor reads correctly on a real chamber, that the heater switches at the right current, or that the fan runs at the right speed. Lesson 82 covers this in detail. A real product adds hardware-in-the-loop tests on a board for those parts, and the CI pipeline is where those tests would be started.

Extensions: where to take it next
  • Move to real hardware. Build the heater stage on a board with a logic-level MOSFET, a fan with a flyback diode, and a bimetal thermal cutoff in series with the heater (lesson 109 for the board). Replace the LED with the heater and measure the real step response. Tune the PID on that data, not on the model.
  • Add a humidity sensor. An SHT31 or a BME280 on the same I2C bus would show the moisture the filament still holds. Each has its own I2C address and its own measurement sequence, and the datasheet gives both. Add it as a driver behind the same kind of interface as the NTC, and test its conversion on the PC with a fake.
  • Log to flash. Keep the last fault and its time in the last flash page, so a field failure can be read after a reset. Writing flash needs an unlock, and erasing works on whole pages (RM0008 Rev 21, section 3.3.3, "Programming and erasing the Flash memory"), so put the log in one page and wear-level it if you write often. Lesson 85 covers what a useful field log contains.
  • Sign the image. Replace the header's reserved words with a CRC and then a signature, and check it in the bootloader before the jump. This is the step that makes the update path safe against a tampered image (lesson 106).

Summary

  • The dryer's CI has four jobs: host tests, static analysis, the firmware build and the simulation. The needs lines decide what runs after a failure.
  • A check gates a change only when its failure stops the run. cppcheck gates because of --error-exitcode=1, and without that flag its findings are only text in the log.
  • The host tests build the application sources that ship. Each test program's return value becomes its exit code, and ctest reports the failure.
  • A new test file must be named in the foreach list. The count in the summary shows whether the test ran.
  • Without a token, the simulate job is green and says that the simulation was skipped. Read that line before you trust the tick.
  • The capstone's eight lessons, 113 to 120, build the dryer from requirements to a checked image, and each one leaves a test or a check behind.
  • Name the limits first: the simulator's numbers, a PID that was not tuned on a real chamber, and a bootloader that does not check a signature yet.
