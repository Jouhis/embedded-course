volatile, const, and static

Three keywords decide where a value lives and whether the compiler may skip a read. Getting volatile wrong is the most common cause of firmware that works at -O0 and hangs at -O2.

By the end of this lesson you can explain why a flag shared with an interrupt needs volatile, show the difference in the compiler's output with and without it, and say where const and static data is stored.

The idea

The compiler is allowed to assume that nothing outside the current function changes a variable between two reads, unless the code shows otherwise. That assumption is what makes an optimised loop fast. It is wrong for two kinds of memory: a memory-mapped register, whose value the hardware changes, and a variable that an interrupt service routine (ISR) writes while main reads it. A timer or a UART can change a register between two of your reads, with no C statement in between. The ISR can run at any point in the loop.

volatile tells the compiler that every access to the object is an observable side effect. It must be performed in the order the abstract machine says, and it cannot be removed or merged with another read. cppreference, volatile

volatile is not a synchronisation primitive. The same page says volatile variables are not suitable for communication between threads: they give no atomicity, no synchronisation and no memory ordering. A flag can still be lost if the ISR writes between your read and your clear, and a read-modify-write such as count++ can still interleave. Lesson 57 covers the fix, a critical section, and the rules for ISRs.

The loop that compiles away

Here are two wait loops. The first reads a plain static flag, and the second reads a volatile flag. Each was compiled with arm-none-eabi-gcc -mcpu=cortex-m3 -mthumb -O2 -S, using the toolchain in C:\Program Files (x86)\Arm GNU Toolchain arm-none-eabi\14.2 rel1\bin. This is the real output, trimmed to the loops: 

/* void wait_nv(void) { while (gflag == 0) { } }   -- gflag is a plain uint32_t */
wait_nv:
        ldr     r3, .L5
        ldr     r3, [r3]          /* the flag is loaded ONCE */
        cbz     r3, .L3
        bx      lr
.L3:
        b       .L3               /* then the loop branches to itself: it never reads again */

/* void wait_v(void) { while (flag == 0) { } }    -- flag is volatile uint32_t */
wait_v:
        ldr     r2, .L11
.L8:
        ldr     r3, [r2]          /* the flag is loaded on EVERY pass */
        cmp     r3, #0
        beq     .L8
        bx      lr

The non-volatile loop has no read inside it. The compiler has proved, from its own point of view, that the value cannot change, so it removed the read from the loop. An ISR that sets the flag will never be seen. The volatile loop keeps the load inside the loop, and that is the behaviour you wanted. The output above is from GCC 14.2.1 for Cortex-M3 (-mcpu=cortex-m3 -mthumb). Your toolchain may name the labels differently, but the shape of the loop is the point.

Memory-mapped registers need it too

A hardware register is a fixed address. Reading it can have a side effect, for example clearing a flag, and the value can change without any write from your code. The pattern for a register is (*(volatile uint32_t *)address), which lesson 47 uses in full. The same reasoning applies to the RP2040 and the STM32: any location the hardware can change needs volatile.

const: data in flash

A const object cannot be changed through its own name. That promise lets the linker put it in read-only memory. In the STM32 linker script used in this course (templates/common/stm32f103c8.ld), the output section .rodata is placed in FLASH, which starts at 0x08000000, so a const table costs flash and no RAM. Initialised writable globals are the opposite case. Their starting values sit in flash, and the startup code copies them to RAM at boot. That is the .data section, and it is why RAM use is not the same as the size of your initialised data.

static: two meanings

At file scope, static gives a variable internal linkage: other files cannot refer to it. Inside a function, static gives static storage duration: the object exists for the whole run of the program, is initialised once before main, and keeps its value between calls. cppreference, storage duration and linkage 

static volatile bool tick_seen = false;   /* file scope: this file only, and volatile for the ISR */

void count_calls(void) {
    static uint32_t n = 0;    /* initialised once; keeps its value between calls */
    n++;
}
A static local is not volatile. If an ISR reads or writes it, it needs volatile too, for the same reason as any shared flag.

"A variable is set in an ISR and read in a polling loop. The code works at -O0 and hangs at -O2. Why, and what do you change?" Answer out loud in 60 seconds, then compare.

Model answer

At -O2 the compiler sees that nothing in the loop writes the variable, so it loads it once and keeps the value in a register. The ISR's writes never reach the loop. The fix is to declare the variable volatile, so every read reloads it. volatile is not enough for a shared counter or any read-modify-write: those need a critical section or an atomic type, because the ISR can run between the read and the write.
