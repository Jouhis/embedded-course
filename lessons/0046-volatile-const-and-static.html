volatile, const, and static

Qualifiers for storage, visibility and compiler access in C

By the end of this lesson you can explain why a flag shared with an interrupt needs volatile, show the difference in the compiler's output with and without it, and say where const and static data is stored.

Where a variable lives and how it is accessed

Lesson 45 covered the arithmetic of C types, and this lesson covers the other half of a variable, namely where it lives in memory and how often the compiler is allowed to touch it. Lesson 38 showed that the chip has flash, RAM and peripheral registers at fixed addresses, and lesson 42 that the startup code copies the initial values of writable globals from flash into RAM before main runs.

The problem comes up often in real firmware. A button handler in an interrupt sets a flag and a loop in main waits for it, and while the team builds at -O0 during development everything works, but the -O2 release build stops responding after the first press. Nothing in the source changed, only the compiler's view of the flag, so this lesson shows what the compiler assumes and how the three keywords change that assumption.

The optimiser's assumptions

A C compiler may rearrange and remove code as long as the program behaves as if it ran the statements in order, which is known as the as-if rule. To do so it tracks what it knows about each variable, and if nothing in a function writes a variable, it may keep the value in a CPU register and never read memory again. That assumption makes an optimised loop fast and is correct for ordinary variables.

It is wrong, however, for two kinds of memory. The first is a memory-mapped register, a peripheral register at a fixed address whose value the hardware changes, as a timer count or a UART status flag changes between reads with no C statement in between. The second is a variable that an interrupt service routine (ISR) writes while main reads it, an ISR being a function the CPU calls when a hardware event occurs and which can interrupt main at any instruction. The compiler analyses one function at a time and cannot see an interrupt, so to it the ISR is a function that never runs during the loop. The assumption is consistent within the compiler's view but false in a program that an interrupt can change.

The volatile qualifier

The volatile qualifier tells the compiler that the object may change in ways it cannot see. Every read and write of a volatile object then counts as an observable action, which the compiler must perform in source order without merging two reads into one, so a volatile flag is reloaded from memory on every use. cppreference, volatile

The optimiser behaves like an assistant who remembers answers. Asked twice whether the flag is set, the assistant answers the second time from memory, because as far as they could see nobody touched the flag in between, while in fact an interrupt or a peripheral changed it out of their sight. volatile instructs the assistant to go and look every time for this one variable. The comparison stops at intent, though, because the compiler holds no belief about the flag and simply follows the rules of the language.

The qualifier fixes visibility, and that is all it fixes, which is the boundary the next box draws.

volatile is not a synchronisation primitive: it does not make an operation atomic and gives no ordering guarantee between an ISR and main. A flag can still be lost if the ISR writes between your read and your clear, and a read-modify-write such as count++ can still be interrupted midway, because the compiler performs it as a load, an add and a store. Lesson 57 covers the fix, a critical section, together with the rules for ISRs.

The volatile register pattern

A hardware register sits at a fixed address, and reading it can have a side effect such as clearing a flag. The usual C pattern is a pointer cast to volatile, written (*(volatile uint32_t *)address), which lesson 47 uses in full. The CMSIS headers do the same, declaring the struct fields in stm32f103xb.h with the macro __IO, which expands to volatile, and every register on the RP2040 and the STM32 that the hardware can change needs this treatment.

const data and flash placement

A const object cannot be changed through its own name, so a direct assignment is a compile error, reported by GCC as error: assignment of read-only variable, and the compiler can place the object in read-only memory. The linker puts read-only data in the .rodata section, which the course's STM32 linker script, templates/common/stm32f103c8.ld, places in FLASH starting at 0x08000000, so a const table uses flash and no RAM.

Writable initialised globals are the opposite case. Their starting values sit in flash in the .data section, and the startup code copies them to RAM at boot, so an initialised writable array uses flash for its starting values and RAM for its live values. That is why RAM use differs from the size of the initialised data, the same split for .data that the lab's map file showed.

The two meanings of static

The keyword static means different things in two places. At file scope it gives a variable internal linkage, so other files cannot refer to it by name and the linker does not export it, while inside a function it gives static storage duration, so the object exists for the whole run of the program, is initialised once and keeps its value between calls. cppreference, storage duration and linkage

The two meanings are often confused, but a file-scope static concerns who can see the name and a local static how long the value lasts. Neither makes a variable volatile, so a static flag set by an ISR still needs volatile.

Worked example: a wait loop compiled away

The two wait loops below were compiled with arm-none-eabi-gcc -mcpu=cortex-m3 -mthumb -O2 -S, using GCC 14.2.1 from the toolchain in C:\Program Files (x86)\Arm GNU Toolchain arm-none-eabi\14.2 rel1\bin. The C code uses a global flag defined in another file, so the compiler cannot see every write to it, and the plain version comes first. Before reading it, predict how many times the loop reads the flag. 

/* extern uint32_t gflag;   defined in another file.   void wait_nv(void) { while (gflag == 0) { } } */
wait_nv:
        ldr     r3, .L5
        ldr     r3, [r3]          /* the flag is loaded ONCE, before the loop */
        cbz     r3, .L3
        bx      lr
.L3:
        b       .L3               /* then the loop branches to itself: it never reads again */

We read the listing step by step. The first ldr loads the address of gflag from a literal word near the function and the second loads the value through that address, after which cbz, "compare and branch if zero", jumps to .L3 if the flag is zero. At .L3 stands b .L3, a branch to itself that spins forever, so the compiler has moved the read out of the loop and an ISR that sets the flag will never be seen.

The same loop with the flag declared volatile compiles differently. 

/* extern volatile uint32_t vflag;   void wait_v(void) { while (vflag == 0) { } } */
wait_v:
        ldr     r2, .L11          /* address of vflag, loaded once */
.L8:
        ldr     r3, [r2]          /* the flag is loaded on EVERY pass */
        cmp     r3, #0
        beq     .L8               /* loop back to the load, not to the branch itself */
        bx      lr

The load now sits inside the loop at label .L8, and the branch returns to it, so each pass reads memory again and an ISR's write is seen on the next pass. The address is still loaded only once, because it never changes, so the compiler kept the access and removed nothing else.

The labels and register numbers change between compiler versions and between flags, so compare the shape of the loop rather than the exact text. The signs to look for are a load inside the loop and a branch back to that load, while a loop ending in a b to itself with no load is the bug.

The widget below runs the two listings. Step through the loop, fire the interrupt that sets the flag and keep stepping, and the plain version never looks at memory again; then switch to the volatile listing and repeat.

Memory-mapped registers and const tables

The same reasoning applies to a register. A timer status register changes on its own, so every read must reach the hardware, which volatile ensures, and the CMSIS struct provides it through __IO, which is why the struct fields are preferable to a raw number for the address.

A const table is the complementary case. A lookup table for a sensor curve never changes, so declaring it const is a promise that also tells the linker the data can stay in flash, and the lab's build confirms it, the const array appearing in .rodata rather than .data. A const global that is never written costs flash and no RAM, which matters on a 20 KiB device.

The volatile-flag project line by line

The project for this lesson, projects/0046-volatile-flag, runs on the Pico rather than the Blue Pill, because its timer call comes from the Pico SDK. The starter declares the flag without a qualifier. 

/* Set by the timer callback. The callback runs in interrupt context,
 * while main() runs in thread context, so main() must see every write. */
static bool tick_seen = false;   /* TODO(learner): this flag needs one qualifier. */

/* Runs in interrupt context, once per TICK_MS. */
static bool on_tick(repeating_timer_t *rt) {
    (void)rt;
    tick_seen = true;
    return true;
}

The word static at file scope gives tick_seen internal linkage, so no other file can change it by accident, and its zero starting value, which false is, places it in .bss, which the startup code zeroes before main, whereas a non-zero starting value would put it in .data. The declaration is the line that needs a qualifier: the callback on_tick writes tick_seen from interrupt context and main reads it from thread context, so without volatile the compiler sees no write inside main and may load the flag once.

The callback returns true, telling the SDK's repeating timer to keep firing, and (void)rt; marks the unused parameter so that the compiler does not warn about it. The solution adds volatile, making the declaration static volatile bool tick_seen = false;, with a comment that states what volatile does and does not do, the same boundary this lesson draws.

The bug shows in the starter's main loop, whose first wait is the empty loop while (!tick_seen) { }. With the flag not volatile, the compiler reads it once and, since it is false at that moment, compiles the loop into a branch to itself, so when the timer later sets the flag, the loop never sees it.

Hands-on: find the missing qualifier

The project's repeating timer sets a flag every 100 ms from a callback running in interrupt context, main waits for the flag, and the starter lacks one qualifier.

  2. Build with Ctrl+Shift+B. The build uses -O2, so the compiler can optimise the wait, and it should finish without errors.

  4. Find the one qualifier that tick_seen needs and add it, remembering that the variable is shared with an ISR, so the compiler must reload it on every pass. The fix works when the serial monitor prints VOLATILE FLAG OK and then a tick line every 100 ms while the LED toggles.

Common mistakes and how to spot them

A shared flag without volatile

The device stops responding after a button press or a timer event in the optimised build although the debug build works, and the debugger shows the loop running while the flag never changes. The compiler hoisted the read out of the loop, so declare the flag volatile and confirm in the disassembly that the loop contains a load.

volatile used as a lock

A count comes out slightly low under load, by an amount that changes from run to run, because the ISR and main both change a volatile counter with count++. The qualifier alone does not make the increment safe, so protect the shared access with a critical section or use an atomic operation, as lesson 57 describes.

A static local expected to reset

A count stays at one, or a value never clears, because a function declares static uint32_t n = 0; and expects n to start at zero on each call. The initialiser runs only once, so set the value explicitly on the call where a reset is needed.

A write to a const table

The program behaves wrongly in a way that depends on the chip, because a developer removed the const from a lookup table or cast it away to write it, and the write went to the .rodata copy in flash. A direct assignment to a const name is caught at compile time but a cast is not, so keep the table const and put any value that changes in RAM.

The three qualifiers in production firmware

Teams use the qualifiers in three places. Register access goes through the vendor's struct or macro, so every register read is a volatile access, variables shared with an ISR are declared volatile and accessed inside a short critical section whenever more than one access is needed, and read-only data such as lookup tables and version strings is declared const so that the linker keeps it in flash.

Code review checks every variable an ISR touches, asking where it is written and read, whether each access is volatile and whether any read-modify-write is protected. The same reviewer checks that static is used for file-private helpers and that no static local is accidentally relied on as a reset value.

Summary

  • The optimiser may keep a value in a register, so a flag written only by an ISR can be loaded once and the wait loop never sees the change.
  • volatile makes every access real, so the compiler reloads the flag on every pass, but it is neither atomic nor a synchronisation mechanism.
  • A read-modify-write such as count++ can still be interrupted midway, so a shared counter needs a critical section or an atomic operation, as lesson 57 covers.
  • A const object cannot be changed through its own name, and the course's STM32 linker script places .rodata in FLASH, so a const table uses flash and no RAM.
  • Initialised writable globals keep their starting values in flash in .data, and the startup code copies them to RAM at boot.
  • A file-scope static gives internal linkage, hiding the name from other files, while a static local is initialised once and keeps its value between calls.
  • static does not make a variable volatile, so a static flag set by an ISR still needs volatile.
