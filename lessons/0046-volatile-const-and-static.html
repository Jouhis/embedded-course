volatile, const, and static

Three keywords decide where a value lives and whether the compiler may skip a read. Getting volatile wrong is a common cause of firmware that works at -O0 and hangs at -O2.

By the end of this lesson you can explain why a flag shared with an interrupt needs volatile, show the difference in the compiler's output with and without it, and say where const and static data is stored.

Where we are and why it matters

Lesson 45 covered the arithmetic of C types. This lesson covers the other half of a variable: where it lives in memory and how often the compiler is allowed to touch it. You already know from lesson 38 that the chip has flash, RAM and peripheral registers at fixed addresses. Lesson 42 showed that the startup code copies the initial values of writable globals from flash into RAM before main runs.

This comes up often in real firmware. A button handler in an interrupt sets a flag, and a loop in main waits for it. The team builds the project at -O0 while they write it, and it works. The release build uses -O2, and the device stops responding after the first press. Nothing in the source code changed, but the compiler's view of the flag did. This lesson shows what the compiler assumes and how the three keywords change that assumption.

Concepts, one at a time

What the optimiser assumes

A C compiler may rearrange and remove code, as long as the program behaves as if it ran the statements in order. This is the as-if rule. To do that, the compiler tracks what it knows about each variable. If nothing in a function writes a variable, the compiler may keep its value in a CPU register and never read memory again. That assumption makes an optimised loop fast, and it is correct for ordinary variables.

The assumption is wrong for two kinds of memory. The first is a memory-mapped register, a peripheral register at a fixed address whose value the hardware changes. A timer count or a UART status flag changes between your reads, with no C statement in between. The second is a variable that an interrupt service routine (ISR) writes while main reads it. An ISR is a function that the CPU calls when a hardware event happens, and it can interrupt main at any instruction. The compiler sees one function at a time, and it cannot see an interrupt. From its point of view, the ISR is a function that never runs during the loop. The assumption holds in the compiler's view, but not in a program that an interrupt can change.

volatile: every access is a real access

The volatile qualifier tells the compiler that the object may change in ways it cannot see. Each read and write of a volatile object is an observable action, so the compiler must perform it, in the order the source gives, and it may not merge two reads into one. A volatile flag is reloaded from memory on every use. cppreference, volatile

The optimiser is an assistant who remembers answers. Ask "is the flag set?" twice and the second time they answer from memory, because as far as they can see nobody touched the flag in between. An interrupt or a peripheral changes it behind their back. volatile tells the assistant: for this variable, go and look every time.

volatile is not a synchronisation primitive. It does not make an operation atomic, and it gives no ordering guarantee between an ISR and main. A flag can still be lost if the ISR writes between your read and your clear. A read-modify-write such as count++ can still be interrupted in the middle, because the compiler performs it as a load, an add and a store. Lesson 57 covers the fix, a critical section, and the rules for ISRs.

The register pattern

A hardware register is a fixed address, and reading it can have a side effect, for example clearing a flag. The usual C pattern is a pointer cast to volatile, written as (*(volatile uint32_t *)address). Lesson 47 uses it in full. The CMSIS headers do the same thing for you: the struct fields in stm32f103xb.h are declared with the macro __IO, which expands to volatile. Every register on the RP2040 and the STM32 that the hardware can change needs this treatment.

const: read-only, and placed in flash

A const object cannot be changed through its own name. A direct assignment is a compile error, and the compiler can place the object in read-only memory. The GCC message for a write is error: assignment of read-only variable. The linker places read-only data in the .rodata section. In the course's STM32 linker script, templates/common/stm32f103c8.ld, the .rodata section is placed in FLASH, which starts at 0x08000000. A const table therefore uses flash and no RAM.

Writable initialised globals are the opposite case. Their starting values sit in flash, in the .data section, and the startup code copies them to RAM at boot. So an initialised writable array uses flash for its starting values and RAM for its live values. This is why RAM use is not the same as the size of your initialised data, and the lab's map file showed the same split for .data.

static: two meanings

The keyword static means different things in two places. At file scope, static gives a variable internal linkage: other files cannot refer to it by name, and the linker does not export it. Inside a function, static gives static storage duration: the object exists for the whole run of the program, is initialised once, and keeps its value between calls. cppreference, storage duration and linkage

The two meanings are often confused. A file-scope static is about who can see the name. A local static is about how long the value lasts. Neither one makes a variable volatile, and a static flag set by an ISR still needs volatile.

Worked example: the wait loop that compiles away

Here are two wait loops, compiled with arm-none-eabi-gcc -mcpu=cortex-m3 -mthumb -O2 -S, using the toolchain in C:\Program Files (x86)\Arm GNU Toolchain arm-none-eabi\14.2 rel1\bin. The version of GCC was 14.2.1. The C code uses a global flag that is defined in another file, so the compiler cannot see every write to it. First the plain version: 

/* extern uint32_t gflag;   defined in another file.   void wait_nv(void) { while (gflag == 0) { } } */
wait_nv:
        ldr     r3, .L5
        ldr     r3, [r3]          /* the flag is loaded ONCE, before the loop */
        cbz     r3, .L3
        bx      lr
.L3:
        b       .L3               /* then the loop branches to itself: it never reads again */

Read the listing as a sequence of steps. The first ldr loads the address of gflag from a literal word near the function. The second ldr loads the value through that address. cbz means "compare and branch if zero": if the flag is zero, jump to .L3. At .L3 the code is b .L3, a branch to itself, which spins forever. The compiler has removed the read from the loop. An ISR that sets the flag will never be seen.

Now the same loop with the flag declared volatile: 

/* extern volatile uint32_t vflag;   void wait_v(void) { while (vflag == 0) { } } */
wait_v:
        ldr     r2, .L11          /* address of vflag, loaded once */
.L8:
        ldr     r3, [r2]          /* the flag is loaded on EVERY pass */
        cmp     r3, #0
        beq     .L8               /* loop back to the load, not to the branch itself */
        bx      lr

The load is now inside the loop, at label .L8, and the branch goes back to it. Each pass reads memory again, so an ISR's write is seen on the next pass. The address is still loaded once, because the address never changes. The compiler kept the access and removed nothing else.

The compiler's labels and register numbers change between versions and between flags, so compare the shape of the loop, not the exact text. The key signs are a load inside the loop, and a branch that goes back to that load. A loop that ends in b to itself, with no load, is the bug.

Run the two listings above. Step the loop, fire the interrupt that sets the flag, and keep stepping: the plain version never looks at memory again. Then switch to the volatile listing and do the same.

Memory-mapped registers and const tables

The same reasoning applies to a register. A timer status register changes on its own, so reads of it must reach the hardware every time, and volatile makes them do so. The CMSIS struct does this through __IO, which is why you should use the struct fields and not a raw number for the address.

A const table is the other side of the coin. A lookup table for a sensor curve never changes, so declaring it const is a promise. It also tells the linker that the data can stay in flash. You can check this with the lab's build: a const array appears in .rodata, not in .data. A const global that is never written costs flash and no RAM, which matters on a 20 KiB device.

The code, line by line

The project for this lesson is projects/0046-volatile-flag. It runs on the Pico, not the Blue Pill, because its timer call comes from the Pico SDK. The starter has the flag without a qualifier: 

/* Set by the timer callback. The callback runs in interrupt context,
 * while main() runs in thread context, so main() must see every write. */
static bool tick_seen = false;   /* TODO(learner): this flag needs one qualifier. */

/* Runs in interrupt context, once per TICK_MS. */
static bool on_tick(repeating_timer_t *rt) {
    (void)rt;
    tick_seen = true;
    return true;
}

Line by line: the word static at file scope gives tick_seen internal linkage, so no other file can change it by accident. A starting value of zero, which false is, puts the variable in .bss, and the startup code zeroes that section before main. A non-zero starting value would go to .data instead. The line that needs a qualifier is the declaration. The callback on_tick writes tick_seen from interrupt context, and main reads it from thread context. Without volatile, the compiler sees no write to the flag inside main, so it may load the flag once.

The callback returns true, which tells the SDK's repeating timer to keep firing. The line (void)rt; marks the unused parameter, so the compiler does not warn about it. The solution adds volatile, so the declaration reads static volatile bool tick_seen = false;. The solution also has a comment that says what volatile does and what it does not do, which is the same boundary this lesson draws.

The main loop in the starter is where the bug shows. Its first wait is while (!tick_seen) { }, an empty loop. With the flag not volatile, the compiler reads the flag once, and if the flag is false at that moment, it compiles the loop into a branch to itself. The timer then sets the flag, and the loop never sees it.

Hands-on: find the missing qualifier

The project has a repeating timer that sets a flag every 100 ms. Its callback runs in interrupt context, and main waits for the flag. The starter has one missing qualifier.

  1. Open projects/0046-volatile-flag/starter in VS Code (File → Open Folder).
  2. Build: Ctrl+Shift+B. The build uses -O2, so the compiler can optimise the wait. Expected: the build finishes with no errors.
  3. Start the simulator: F1 → Wokwi: Start Simulator. The serial monitor prints waiting for the first tick. Then it prints nothing more, because the first wait loop runs forever. (If your Wokwi token is not set, you cannot run the simulator; read the disassembly in step 5 instead.)
  4. Your task: find the one qualifier that tick_seen needs, and add it. The variable is shared with an ISR, so the compiler must reload it on every pass. You will know it works when the serial monitor prints VOLATILE FLAG OK, and then a tick line every 100 ms while the LED toggles.
  5. Check the compiler output. Run arm-none-eabi-objdump -d -C build/blink.elf and find the first wait loop in main. In the starter you should see b to its own address (encoding e7fe) with no load before it. After your fix, the wait loop should contain a byte load (ldrb) and a branch that goes back to that load.

Common mistakes and how to spot them
  1. A shared flag without volatile. The program works in a debug build and hangs in the optimised build. The symptom is a device that stops responding after a button press or a timer event, and its debugger shows the loop running with no change in the flag. The fix is to declare the flag volatile, and to check the loop in the disassembly for a load inside it.
  2. volatile used as a lock. A team declares a counter volatile, and the ISR and main both change it with count++. The counts come out a little low, and the error changes from run to run. The symptom is a count that is slightly wrong only under load. The fix is a critical section around the shared access, or an atomic operation, as lesson 57 describes. The qualifier alone does not make the increment safe.
  3. A static local believed to reset. A function declares static uint32_t n = 0; and expects n to start at zero on each call. The symptom is a count that stays at one, or a value that never clears. The fix is to remember that the initialiser runs once, and to set the value explicitly on the call where you need a reset.
  4. Writing to a const table. A developer removes the const from a lookup table, or casts it away to write it. If the write goes to the .rodata copy in flash, the program is wrong, and the result depends on the chip. A direct assignment to a const name is caught at compile time, but a cast is not. The fix is to keep the table const, and to put any value that changes in RAM.

In real projects

Teams use volatile in three places. Register access goes through the vendor's struct or macro, so every register read is a volatile access. Variables shared with an ISR are declared volatile and accessed inside a short critical section when more than one access is needed. Read-only data, such as lookup tables and version strings, is declared const, so the linker keeps it in flash.

A code review checks every variable that an ISR touches. A reviewer asks where it is written, where it is read, whether each access is volatile, and whether any read-modify-write is protected. The same reviewer checks that static is used for file-private helpers and that no static local is relied on as a reset value by accident.

Summary

  • The optimiser may keep a value in a register. A flag written only by an ISR can then be loaded once, and the wait loop never sees the change.
  • volatile makes every access a real access, so the compiler reloads the flag on every pass. It is not atomic and gives no synchronisation.
  • A read-modify-write such as count++ can still be interrupted in the middle, so a shared counter needs a critical section or an atomic operation, as lesson 57 covers.
  • A const object cannot be changed through its own name. The course's STM32 linker script places .rodata in FLASH, so a const table uses flash and no RAM.
  • Initialised writable globals keep their starting values in flash, in .data, and the startup code copies them to RAM at boot.
  • A file-scope static gives internal linkage, so other files cannot see the name. A static local is initialised once and keeps its value between calls.
  • static does not make a variable volatile, so a static flag set by an ISR still needs volatile.
