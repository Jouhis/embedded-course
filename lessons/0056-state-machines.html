State machines: switch-based and table-driven

Most firmware is a set of modes that react to events: a light changes, a door opens, a button is pressed. Writing that as nested if statements works until the fourth mode. A state machine makes the modes and the transitions explicit, so you can check them and print them.

By the end of this lesson you can write a traffic-light controller as a table of transitions, feed it debounced button events, and print each transition, such as STATE RED->GREEN, on the serial monitor.

The idea

A state machine has a set of states, a set of events, and a rule that says, for each state and event, which state comes next. The state is a variable. An event is one thing that happened, such as a timer expiring or a debounced press. Your main loop turns raw inputs into events, and the state machine decides what they mean. The machine sees events, not raw pins. The debouncer from lesson 52 turns a noisy pin into one press event, and the state machine never has to think about bounce.

Miro Samek's free video course builds the same idea from bare metal to event-driven designs, and it shows the generated code for each step. Its state-machine material is the source to read after this lesson (Samek, Modern Embedded Systems Programming).

Switch-based

The switch-based form is one function with a switch on the state, and a second switch or if on the event. It reads like the diagram, and it is the right first step. Each case returns the next state, so the transition is in one place. 

static state_t on_event(state_t s, event_t e) {
    switch (s) {
        case ST_RED:
            if (e == EV_TIMEOUT) return ST_GREEN;
            return s;                     /* a request in RED is ignored */
        case ST_GREEN:
            if (e == EV_TIMEOUT || e == EV_REQUEST) return ST_YELLOW;
            return s;
        case ST_YELLOW:
            if (e == EV_TIMEOUT) return ST_RED;
            return s;
    }
    return s;
}

The weakness shows as the machine grows. Every new event adds a condition to every state, and nothing tells you whether you forgot one. Each state's code is spread across the function, so a reviewer must read the whole thing to see what state RED does.

Table-driven

The table-driven form stores the same rules as data. A two-dimensional array indexed by state and event gives the next state, and one dispatch function does the work for every transition. Adding a state means adding a row. A missing cell is easy to see, because the table has a fixed shape. 

static const state_t next_state[ST_COUNT][EV_COUNT] = {
    /*            TIMEOUT     REQUEST   */
    /* RED    */ { ST_GREEN,  ST_RED    },
    /* GREEN  */ { ST_YELLOW, ST_YELLOW },
    /* YELLOW */ { ST_RED,    ST_YELLOW },
};

static void dispatch(event_t e, uint32_t now_us) {
    state_t next = next_state[state][e];
    if (next == state) return;      /* no change: print nothing */
    printf("STATE %s->%s\n", state_name[state], state_name[next]);
    state = next;
    gpio_put_masked(LIGHT_PINS, light_mask[state]);
    deadline_us = now_us + state_ms[state] * 1000u;
}

The table is static const, so it lives in flash and costs no RAM, as lesson 46 explains. The per-state data, the duration and the light, are also tables, so the rules for each state sit together. The cost is a less flexible action: an action that depends on more than the table has to go in the dispatch code.

Events, not pins

The button is an input with bounce, and the lights are outputs. Keep them out of the transition table. The debounced press from lesson 52 becomes EV_REQUEST, and the timer becomes EV_TIMEOUT. The state machine is then easy to test: you can call it with a list of events and check the transitions, without any hardware (lesson 80 covers host testing).

A state machine that reads GPIO inside its transition code is hard to test and easy to break. Read the pins in the main loop, turn them into events, and pass the events in.

Try it in Wokwi

The project is projects/0056-state-machine. Three LEDs on GP2 (red), GP3 (yellow) and GP4 (green) show the light, and a button on GP14 is the pedestrian request. The starter has the switch-based function from above, with TODO(learner) in each case, and a loop that only handles the timer.

  1. Open projects/0056-state-machine/starter in VS Code (File → Open Folder). Build with Ctrl+Shift+B, then start the simulator with F1 → Wokwi: Start Simulator.
  2. Observe the starter. The red light stays on for 3 s and then never changes, because the timeout is not connected to a transition yet.
  3. Your task, in two places. First, in on_event(), write the transitions from the table: RED to GREEN on a timeout, GREEN to YELLOW on a timeout or a request, and YELLOW to RED on a timeout. A request in RED or YELLOW returns the same state. Second, in the loop, print STATE old->new whenever the state changes, and handle the button press as a EV_REQUEST.
  4. You will know it works when the serial monitor prints STATE MACHINE OK at startup, then one STATE RED->GREEN-style line for each change, and the lights follow the lines. Pressing the button during green makes the light turn yellow early.
Hint for the button

The starter's comments say that a press is an event. The lesson 52 integrator debounce returns true once per confirmed press. Call the state machine with EV_REQUEST when that happens, and keep the timeout check as it is.

Hint for the printed line

Compare the state before and after the call. If they differ, print the old name, an arrow, and the new name. The solution uses state_name[], an array of strings indexed by the state.

The reference solution is in projects/0056-state-machine/solution. Try first, compare after. It uses the table-driven form, so compare its dispatch() with your switch-based version to see what each one buys.

You turned a set of modes into a table of transitions, connected debounced button events to it, and printed every change. You can read the machine's behaviour from the serial log, which is how you check it.

"How would you design a controller with many modes and events, and how would you test it?" Answer out loud in 60 seconds, then compare.

Model answer

I'd list the states and the events first, then write the transitions as a table, one cell per state and event, with an explicit entry for every combination, even the ones that do nothing. Inputs become events in the main loop, so the state machine is pure logic: it takes an event and returns the next state and an action. I'd test it on the host by feeding event sequences and checking the state after each one, including the ignored events. On the target I'd log each transition with a level, so a field problem leaves a trace of the states the device went through.
