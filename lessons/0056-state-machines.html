State machines

Modes, events and transitions as explicit code or data

By the end of this lesson you can write a traffic-light controller as a table of transitions, feed it debounced button events, and print each transition, such as STATE RED->GREEN, on the serial monitor.

Modes that react to events

Lesson 52 turned a bouncing button into one clean press with an integrator that counted up and down, and lesson 55 gave the deadline pattern, storing the time at which something should happen and checking it on every pass of a loop that never blocks. Both lessons end with a loop that knows what happened, that the button was pressed or the timer is due, and this lesson answers the question of what the loop does next.

In a small program the answer is one if, but a traffic light has three colours, a timer for each, a button that can change the timing and rules about which change is allowed when, and written as nested conditions that logic spreads across the loop so that no reviewer can see all the rules at once. Real products meet the same problem in a motor controller that must refuse a start while braking, a battery charger moving between charge, hold and fault, or a Bluetooth stack passing through advertising, connecting and bonding. Each has a small set of modes and events that cause changes between them, and the state machine is the standard way to write that down.

States as variables

A state machine consists of four ideas, each simple on its own, and the first is the state, one of a fixed set of modes the program can be in. In C the modes are named with an enum and the current one kept in a variable such as static state_t state = ST_RED;. The CPU has no notion of being in RED, only a register or RAM location holding a small number that the code reads to decide what to do, so the state is data and can be stored, printed and tested. A state variable is a few bytes of RAM, while the machine's behaviour lives in the code and in the table.

Events

An event is a single occurrence the machine should react to, such as a timer reaching its deadline, a debounced press being confirmed or a sensor crossing a limit, and events are named with an enum too, such as EV_TIMEOUT and EV_REQUEST. An event carries no raw electrical signal, because the input code in the main loop turns raw samples into events and the state machine sees only the events, a split that matters later for testing.

Transitions

A transition is the rule that in state S, when event E arrives, the machine moves to state T, and it can also keep the same state, meaning that the event is ignored there. The complete set of rules lists every pair of a state and an event with its answer, so a machine with three states and two events has six pairs and needs six answers. That is the main discipline: every pair has an answer, including those that do nothing.

A vending machine is a state machine in everyday use, with the states idle, credit inserted and dispensing. Pressing a drink button is one event whose effect depends on the state, the machine asking for money when idle, dispensing when there is enough credit and ignoring the press while dispensing, and that pattern of one event giving different results in different states is exactly what a transition table records.

Event dispatch

Dispatch is the code that takes the current state and one event, looks up the rule and applies the answer. It runs once per event rather than once per loop pass, and since the state does not change between two events, the machine can sleep, wait or do other work without losing its place, the state being stored in memory and read back each time, so nothing has to be kept on the stack between events.

Switch-based and table-driven forms

The rules can be written as code or as data, both forms giving the same behaviour and both being common in professional firmware. The switch-based form is the right first step because it reads like the diagram, while the table-driven form is preferable once the machine has more than a handful of states.

The switch-based form is one function with a switch on the state and a second switch or if on the event, each case returning the next state, so that each transition sits in one place. 

static state_t on_event(state_t s, event_t e) {
    switch (s) {
        case ST_RED:
            if (e == EV_TIMEOUT) return ST_GREEN;
            return s;                     /* a request in RED is ignored */
        case ST_GREEN:
            if (e == EV_TIMEOUT || e == EV_REQUEST) return ST_YELLOW;
            return s;
        case ST_YELLOW:
            if (e == EV_TIMEOUT) return ST_RED;
            return s;
    }
    return s;
}

The code reads as a list of questions: the outer switch asks which state the machine is in, and each case asks with an if which event arrived and returns the next state. The return s; at the end of each case answers every event the case does not name, and without it the function would fall through to the next case, a bug the compiler will not report because the code is valid C.

The weakness shows as the machine grows, because every new event adds a condition to every state with nothing to reveal a forgotten one, and each state's code is spread across the function, so a reviewer must read all of it to see what RED does.

The table-driven form stores the same rules as data, a two-dimensional array indexed by state and event giving the next state, with one dispatch function doing the work for every transition. Adding a state then means adding a row, and a missing cell is easy to see because the table has a fixed shape. 

static const state_t next_state[ST_COUNT][EV_COUNT] = {
    /*            TIMEOUT     REQUEST   */
    /* RED    */ { ST_GREEN,  ST_RED    },
    /* GREEN  */ { ST_YELLOW, ST_YELLOW },
    /* YELLOW */ { ST_RED,    ST_YELLOW },
};

static void dispatch(event_t e, uint32_t now_us) {
    state_t next = next_state[state][e];
    if (next == state) return;      /* no change: print nothing */
    printf("STATE %s->%s\n", state_name[state], state_name[next]);
    state = next;
    gpio_put_masked(LIGHT_PINS, light_mask[state]);
    deadline_us = now_us + state_ms[state] * 1000u;
}

The table is static const, so it lives in flash and costs no RAM, as lesson 46 explains, and the per-state data, the duration and the light, are tables as well, keeping each state's rules together. The cost is less flexible actions, since an action that depends on more than the table must go into the dispatch code.

Worked example: one cycle of the light

We trace the table-driven machine with real numbers, since the trace is what the serial monitor will confirm. The solution's durations are RED 3 000 ms, GREEN 3 000 ms and YELLOW 1 000 ms, time is counted in milliseconds from power-up, and the machine starts in RED with its deadline at 3 000 ms. Before following the steps, predict what a button press does while the light is red.

  1. t = 0 ms. The state is RED with its deadline at 3 000 ms, and since no event has arrived, nothing is printed.
  2. t = 3 000 ms. The timer is due, so the loop calls dispatch(EV_TIMEOUT, 3000), whose table cell for RED and TIMEOUT is GREEN. Because that differs from RED, the function prints STATE RED->GREEN, changes the state to GREEN, turns on the green LED and sets the deadline to 3 000 + 3 000 = 6 000 ms.
  3. t = 4 200 ms. The integrator from lesson 52 confirms a button press and the loop calls dispatch(EV_REQUEST, 4200), whose cell for GREEN and REQUEST is YELLOW, so the function prints STATE GREEN->YELLOW, turns on the yellow LED and sets the deadline to 4 200 + 1 000 = 5 200 ms, ending the green phase early after 1.2 s instead of 3 s.
  4. t = 5 200 ms. The timer is due, and the cell for YELLOW and TIMEOUT is RED, so the function prints STATE YELLOW->RED and sets the deadline to 8 200 ms.
  5. t = 5 800 ms. A second press arrives while the machine is in RED, and since the cell for RED and REQUEST is RED itself, the function returns at its first if and prints nothing, ignoring the request as the table's design choice records.

The serial log for the trace therefore has three lines, STATE RED->GREEN, STATE GREEN->YELLOW and STATE YELLOW->RED, each appearing only when the state changes and naming the old and the new state. If a log shows a different sequence, the first line that differs identifies the wrong cell.

Events instead of pin reads

The button is an input with bounce and the lights are outputs, and both belong outside the transition table: the debounced press of lesson 52 becomes EV_REQUEST and the timer becomes EV_TIMEOUT. The state machine is then easy to test, because it can be called with a list of events and its transitions checked without any hardware (lesson 80 covers host testing).

A test on a PC cannot press a button, but it can call dispatch() with EV_REQUEST and check the state afterwards, whereas if the machine read gpio_get() itself, the same test would need a pin, a simulator or a mock of the SDK. Keeping the pin reads in the main loop costs one function call and buys a test that runs in milliseconds.

A state machine that reads GPIO inside its transition code is hard to test and easy to break. Read the pins in the main loop, turn them into events and pass the events in.

The dispatch function line by line

The solution's dispatch() is short and each line has a job, so going through it once makes the table-driven form concrete.

  1. state_t next = next_state[state][e]; is a single lookup indexed by the current state and the event, whose result is always a valid state, and the lookup cannot run off the end of the table because both enums end with a _COUNT entry that sizes the array.
  2. if (next == state) return; handles the ignored cells, printing nothing, leaving the lights unchanged and keeping the deadline, so a cell that keeps the state is a complete answer rather than a missing one.
  3. printf("STATE %s->%s\n", ...) writes the transition, taking the names from state_name[], an array of strings indexed by the state, so the log uses the same enum as the code, and printing only on a change keeps the log readable.
  4. state = next; stores the new state, the only write to the state variable, so every transition passes through one place.
  5. gpio_put_masked(LIGHT_PINS, light_mask[state]); sets all three lights in one write that changes only the bits in LIGHT_PINS, so the lights change together and no intermediate state with two lights on ever appears on the pins.
  6. deadline_us = now_us + state_ms[state] * 1000u; starts the timer for the new state, the multiplication converting milliseconds into the microseconds that time_us_32() returns. The deadline is set from now_us, the time the event was handled, so a late event does not shorten the next phase by more than the delay.

The main loop calls dispatch() only for events, sampling the button, checking the deadline and sleeping for a millisecond, and the is_due() helper of lesson 55 makes the comparison wraparound-safe, so the timeout still works when the 32-bit microsecond counter wraps.

Common mistakes and how to spot them

The deadline not reset on a change

The serial log prints RED->GREEN, GREEN->YELLOW and YELLOW->RED within a few milliseconds while the lights flash through all three colours, because the old deadline is still in the past and the next pass sees a timeout at once. Set deadline_us in the same place that changes the state, as the last line of the solution's dispatch() does.

A missing case in the switch

The light goes from RED to GREEN and stays green for ever, because the GREEN case has no timeout branch, and since the code compiles and runs, nothing gives a warning. Write a line for every state and event, including those that return the same state, and check that every case ends in a return.

A print on every pass

The serial monitor fills with the same line many times a second and the useful transitions scroll away, because the print sits outside the change test and runs on every loop pass. Print only after the comparison that detects a change, as dispatch() does with its early return.

A pin read inside the transition

A test on the PC needs a fake GPIO before it can run, and a bounce can cause two transitions from one press, although the machine behaves correctly with the button in the simulator, because the transition code reads the raw pin. Move the gpio_get() call into the main loop, pass in an event and let the integrator of lesson 52 decide when a press is confirmed.

State machines in protocols and products

Professional firmware uses state machines for anything with modes, from protocol stacks, power management and motor control to bootloaders and communication links. A reviewer checks that every state is named in one place, that every event that can arrive in each state has an answer and that transitions are the only code writing the state variable, and a table that fits on one screen is easy to review, whereas a switch statement spanning three pages hides bugs.

Testing follows from the same structure. Because the machine takes events and returns states, a host test can feed it a list of events and check the states, which is how lesson 80 tests real code, the event list serving as a script and the expected states as the table, so that the test and the design say the same thing.

Summary

  • A state is a variable holding one of a fixed set of modes, an event is one thing that happened, and a transition is the rule mapping a state and an event to the next state.
  • The switch-based form puts the rules in code and the table-driven form in a static const array, where a missing cell is easy to see.
  • Every pair of state and event needs an answer, and an ignored event is an answer in which the table keeps the current state.
  • Dispatch runs once per event, looking up the next state, returning early when nothing changes, printing the change, updating the outputs and restarting the timer.
  • Reading the pins in the main loop and passing events in lets the machine be tested on a PC without hardware.
  • The deadline is set in the same place as the state change, so that the next timeout is measured from the new phase.
  • The serial log checks the machine, one line per transition, and the first wrong line points at the wrong cell.
