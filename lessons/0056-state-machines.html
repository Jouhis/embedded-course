State machines: switch-based and table-driven

Most firmware is a set of modes that react to events: a light changes, a door opens, a button is pressed. Writing that as nested if statements works until the fourth mode. A state machine makes the modes and the transitions explicit, so you can check them and print them.

By the end of this lesson you can write a traffic-light controller as a table of transitions, feed it debounced button events, and print each transition, such as STATE RED->GREEN, on the serial monitor.

Where we are and why it matters

Lesson 52 turned a bouncing button into one clean press, using an integrator that counted up and down. Lesson 55 gave you the deadline pattern: store the time at which something should happen, and check it on every pass of a loop that never blocks. Both lessons end with a loop that knows what happened, such as "the button was pressed" or "the timer is due". The question this lesson answers is what the loop does next.

In a small program the answer is one if. A traffic light has three colours, a timer for each colour, a button that can change the timing, and rules about which change is allowed when. Written as nested conditions, that logic spreads across the loop, and a reviewer cannot see all the rules at once. In real products the same problem appears as a motor controller that must refuse a start while it is braking, a battery charger that moves between charge, hold and fault, or a Bluetooth stack that moves through advertising, connecting and bonding. Each has a small set of modes and events that cause changes between them. The state machine is the standard way to write that down.

The concepts, one at a time

Four ideas make up a state machine. Take them one at a time, because each one is simple on its own.

A state is a variable

A state is one of a fixed set of modes that the program can be in. In C you name the modes with an enum and keep the current one in a variable, such as static state_t state = ST_RED;. The CPU has no notion of "being in RED". It only has a register or a RAM location that holds a small number, and the code reads that number to decide what to do. The state is data, which is why it can be stored, printed and tested. A state variable is a few bytes of RAM. The machine's behaviour lives in the code and in the table, not in the variable.

An event is one thing that happened

An event is a single occurrence that the machine should react to: a timer reached its deadline, a debounced press was confirmed, a sensor crossed a limit. Events are named with an enum too, such as EV_TIMEOUT and EV_REQUEST. An event does not carry the raw electrical signal. The input code in the main loop turns raw samples into events, and the state machine only sees the events. That split matters later, when we talk about testing.

A transition is a rule

A transition is the rule that says: in state S, when event E arrives, move to state T. A transition can also keep the same state, which means the event is ignored there. The complete set of rules for a machine is the list of every pair of a state and an event, with the answer for each pair. A machine with three states and two events has six pairs, so six answers must exist. That is the main discipline: every pair has an answer, including the ones that do nothing.

The dispatch step

Dispatch is the code that takes the current state and one event, looks up the rule, and applies the answer. Dispatch runs once per event, not once per loop pass. Between two events the state does not change, so the machine can sleep, wait or do other work without losing its place. The state is stored in memory, and the CPU reads it back each time, so nothing has to be kept on the stack between events.

Two ways to write the same rules

The rules can be written as code or as data. Both forms give the same behaviour, and both are common in professional firmware. The switch-based form is the right first step, because it reads like the diagram. The table-driven form is the one to prefer once the machine has more than a handful of states.

Switch-based

The switch-based form is one function with a switch on the state, and a second switch or if on the event. Each case returns the next state, so the transition is in one place. 

static state_t on_event(state_t s, event_t e) {
    switch (s) {
        case ST_RED:
            if (e == EV_TIMEOUT) return ST_GREEN;
            return s;                     /* a request in RED is ignored */
        case ST_GREEN:
            if (e == EV_TIMEOUT || e == EV_REQUEST) return ST_YELLOW;
            return s;
        case ST_YELLOW:
            if (e == EV_TIMEOUT) return ST_RED;
            return s;
    }
    return s;
}

Read the code as a list of questions. The outer switch asks "which state am I in?". Each case asks "which event arrived?" with an if, and returns the next state. The return s; at the end of each case is the answer for every event that the case does not name. Without it, the function would fall through to the next case, which is a bug the compiler will not report, because the code is valid C.

The weakness shows as the machine grows. Every new event adds a condition to every state, and nothing tells you whether you forgot one. Each state's code is spread across the function, so a reviewer must read the whole thing to see what state RED does.

Table-driven

The table-driven form stores the same rules as data. A two-dimensional array indexed by state and event gives the next state, and one dispatch function does the work for every transition. Adding a state means adding a row. A missing cell is easy to see, because the table has a fixed shape. 

static const state_t next_state[ST_COUNT][EV_COUNT] = {
    /*            TIMEOUT     REQUEST   */
    /* RED    */ { ST_GREEN,  ST_RED    },
    /* GREEN  */ { ST_YELLOW, ST_YELLOW },
    /* YELLOW */ { ST_RED,    ST_YELLOW },
};

static void dispatch(event_t e, uint32_t now_us) {
    state_t next = next_state[state][e];
    if (next == state) return;      /* no change: print nothing */
    printf("STATE %s->%s\n", state_name[state], state_name[next]);
    state = next;
    gpio_put_masked(LIGHT_PINS, light_mask[state]);
    deadline_us = now_us + state_ms[state] * 1000u;
}

The table is static const, so it lives in flash and costs no RAM, as lesson 46 explains. The per-state data, the duration and the light, are also tables, so the rules for each state sit together. The cost is a less flexible action: an action that depends on more than the table has to go in the dispatch code.

Worked example: one cycle of the light, event by event

Trace the table-driven machine with real numbers, because the trace is what you will check against the serial monitor. The durations are the ones in the solution: RED 3000 ms, GREEN 3000 ms, YELLOW 1000 ms. Time is in milliseconds from power-up, and the machine starts in RED with its deadline at 3000 ms.

  1. t = 0 ms. The state is RED, and the deadline is 3000 ms. No event has arrived, so nothing is printed.
  2. t = 3000 ms. The timer is due, so the loop calls dispatch(EV_TIMEOUT, 3000). The table cell for RED and TIMEOUT is GREEN. That differs from RED, so the function prints STATE RED->GREEN, changes the state to GREEN, turns on the green LED, and sets the deadline to 3000 + 3000 = 6000 ms.
  3. t = 4200 ms. The button was pressed. The integrator from lesson 52 confirms the press, and the loop calls dispatch(EV_REQUEST, 4200). The cell for GREEN and REQUEST is YELLOW. The function prints STATE GREEN->YELLOW, turns on the yellow LED, and sets the deadline to 4200 + 1000 = 5200 ms. The green phase ended early, after 1.2 s instead of 3 s.
  4. t = 5200 ms. The timer is due. The cell for YELLOW and TIMEOUT is RED, so the function prints STATE YELLOW->RED and sets the deadline to 8200 ms.
  5. t = 5800 ms, a second press. The machine is in RED. The cell for RED and REQUEST is RED, the same state. The function returns at the first if and prints nothing. The request is ignored, which is the design choice the table records.

The serial log for that trace is three lines: STATE RED->GREEN, STATE GREEN->YELLOW, STATE YELLOW->RED. A line appears only when the state changes, and each line names the old state and the new one. If your log shows a different sequence, the first line that differs tells you which cell is wrong.

Replay the worked example, then drive the machine yourself. Each event lights up its table cell, its arrow and its line of the switch. Change a cell, for example make a request in RED turn the light green, and the diagram and the code follow.

Events, not pins

The button is an input with bounce, and the lights are outputs. Keep them out of the transition table. The debounced press from lesson 52 becomes EV_REQUEST, and the timer becomes EV_TIMEOUT. The state machine is then easy to test: you can call it with a list of events and check the transitions, without any hardware (lesson 80 covers host testing).

The reason is that a test on a PC cannot press a button. It can call dispatch() with EV_REQUEST and check the state afterwards. If the machine read gpio_get() itself, the same test would need a pin, a simulator or a mock of the SDK. Keeping the pin reads in the main loop costs one function call and buys a test that runs in milliseconds.

A state machine that reads GPIO inside its transition code is hard to test and easy to break. Read the pins in the main loop, turn them into events, and pass the events in.

The code, line by line

The solution's dispatch() is short, and each line has a job. Going through it once makes the table-driven form concrete.

  1. state_t next = next_state[state][e]; is one lookup. The two indexes are the current state and the event. The result is a number in the range of states, so the lookup cannot run off the end of the table, because both enums end with a _COUNT entry that sizes the array.
  2. if (next == state) return; handles the "ignored" cells. Nothing is printed, the lights do not change, and the deadline keeps its value. A cell that keeps the state is therefore a complete answer, not a missing one.
  3. printf("STATE %s->%s\n", ...) writes the transition. The names come from state_name[], an array of strings indexed by the state, so the log uses the same enum as the code. Printing happens only on a change, which keeps the serial log readable.
  4. state = next; stores the new state. This is the only write to the state variable, so every transition goes through one place.
  5. gpio_put_masked(LIGHT_PINS, light_mask[state]); sets all three lights in one write. The mask has a bit for each pin, and the write changes only the bits in LIGHT_PINS. One write also means the three lights change together, so no intermediate state with two lights on is ever visible on the pins.
  6. deadline_us = now_us + state_ms[state] * 1000u; starts the timer for the new state. The multiplication converts milliseconds to microseconds, which is the unit time_us_32() returns. The deadline is set from now_us, the time the event was handled, so a late event does not shorten the next phase by more than the delay.

The main loop calls dispatch() only for events. It samples the button, checks the deadline, and sleeps for a millisecond. The is_due() helper from lesson 55 does the wraparound-safe comparison, so the timeout still works when the 32-bit microsecond counter wraps.

  1. Open projects/0056-state-machine/starter in VS Code (File → Open Folder). Build with Ctrl+Shift+B, then start the simulator with F1 → Wokwi: Start Simulator.
  2. Observe the starter. The red light stays on for 3 s and then never changes, because the timeout is not connected to a transition yet.
  3. Your task, in two places. First, in on_event(), write the transitions from the table: RED to GREEN on a timeout, GREEN to YELLOW on a timeout or a request, and YELLOW to RED on a timeout. Common mistakes and how to spot them

Mistake 1: the deadline is not reset on a change. Symptom: the serial log prints RED->GREEN, then GREEN->YELLOW, then YELLOW->RED within a few milliseconds, and the lights flash through all three colours. The old deadline is still in the past, so the next pass sees a timeout at once. Fix: set deadline_us in the same place that changes the state, as the solution's last line of dispatch() does.

Mistake 2: a missing case in the switch. Symptom: the light goes RED to GREEN and then stays green for ever, because the GREEN case has no timeout branch. The code compiles and runs, so nothing warns you. Fix: write a line for every state and event, even the ones that return the same state, and check that every case ends in a return.

Mistake 3: printing on every pass. Symptom: the serial monitor fills with the same line many times a second, and the useful transitions scroll away. The print is outside the change test, so it runs every time the loop runs. Fix: print only after the comparison that detects a change, as dispatch() does with its early return.

Mistake 4: reading the pin inside the transition. Symptom: the machine behaves correctly with the button in the simulator, but a test on the PC needs a fake GPIO before it can run. A bounce can also cause two transitions from one press, because the transition code sees the raw pin. Fix: move the gpio_get() call into the main loop, pass in an event, and let the integrator from lesson 52 decide when a press is confirmed.

In real projects

Professional firmware uses state machines for anything with modes: protocol stacks, power management, motor control, bootloaders and communication links. A reviewer looks for three things. Every state has a name in one place. Every event that can arrive in each state has an answer. Transitions are the only place that writes the state variable. A table that fits on one screen is easy to review, and a switch statement that spans three pages hides bugs.

Testing follows from the same structure. Because the machine takes events and returns states, a host test can feed it a list of events and check the states, which is how lesson 80 tests real code. The event list is a script, and the expected states are the table, so the test and the design say the same thing.

Summary

  • A state is a variable that holds one of a fixed set of modes. An event is one thing that happened. A transition is the rule that maps a state and an event to the next state.
  • The switch-based form puts the rules in code. The table-driven form puts them in a static const array, so a missing cell is easy to see.
  • Every pair of state and event needs an answer. An ignored event is an answer: the table keeps the current state.
  • Dispatch runs once per event. It looks up the next state, returns early when nothing changes, prints the change, updates the outputs and restarts the timer.
  • Read the pins in the main loop and pass events in. A machine that takes events can be tested on a PC without hardware.
  • Set the deadline in the same place as the state change, so the next timeout is measured from the new phase.
  • Check the machine by its serial log. Each line is one transition, and the first wrong line points at the wrong cell.
