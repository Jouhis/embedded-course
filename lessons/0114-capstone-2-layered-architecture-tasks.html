Capstone 2: layered architecture, tasks, and the pin map

The state machine from lesson 113 has to run on a chip, with five jobs at different rates and ten pins that each do one thing. This lesson sorts the code into layers so that the logic never touches a register, sets the task priorities from the periods, and maps every pin before the first board is built.

By the end of this lesson you can draw a layered architecture and check its dependency rule, assign rate-monotonic priorities and test a utilisation sum, read a pin map with its alternate functions, and build the skeleton that prints DRYER SKELETON OK.

Where we are and why it matters

Lesson 113 gave you the requirements, the failure table and the state machine. This lesson turns them into a structure. Lesson 76 introduced the hardware abstraction layer (HAL) for one driver (if you did the optional Zephyr part, lesson 98 showed the same idea as a driver model). Here the same idea is applied to the whole product. Lesson 87 set up FreeRTOS tasks, and lesson 93 gave the deadline and rate-monotonic rules that you use below.

The pins come from the GPIO lessons. Lesson 52 covered buttons and debouncing, lesson 12 covered the MOSFET that switches the heater, and lesson 16 covered pull-up resistors and open-drain outputs. Each pin has one function that the schematic and the code must agree on.

The skeleton at the end of this lesson has the layers and the start-up sequence but no behaviour. It builds, it links every module, and it prints one banner. Lesson 115 writes the NTC driver and the first unit tests, lesson 116 adds the heater PWM, buttons, display and safety checks, and lesson 117 adds the RTOS threads and PID control.

The layered architecture

A layer is a group of files with one job, and each layer calls only the layer below it. From the CPU's side, a peripheral is a set of addresses on the bus. If application code writes those addresses directly, it depends on one chip and one board. A layer in between means that only one file changes when the chip changes, and the rest can be compiled and tested on a PC.

Figure 2 shows the five layers of the dryer, from the application at the top to the board file at the bottom. The arrows point down. A layer never calls up, and that rule is the one the rest of the lesson depends on.

The rule that matters most is the dependency direction: nothing in the application may include a register header.

Calls go one way: a button, end to end

A HAL is the set of functions a layer exposes to the layer above it. A driver is the code that talks to one piece of hardware and turns it into plain values: an ADC code, a debounced button level, a duty cycle. The board file is the lowest layer, the only place that knows the register addresses of one chip on one board. Follow one button press down through the layers and back up.

The Start button is wired from PB12 to ground, and the chip's internal pull-up holds the pin high while the button is open. The board file reads the pin and returns 1 when it is low, which is what a press means. The button service samples that value through a debounce (lesson 52) and sets an event flag when the debounced level goes from released to pressed. The control code reads the flag once, and only then does the state change. Nothing reaches up.

This is why the same state machine can run in the simulator, on the Blue Pill and on the PC. The PC build swaps the board file for a fake that returns scripted values (lesson 81), and the rest of the code does not notice. The rule to remember is the dependency direction: no file in the application may include a register header.

Tasks and priorities with rate-monotonic reasoning

The product runs five jobs in parallel: the safety monitor, the control loop, the Modbus comms, the user interface, and the logger. In FreeRTOS each is a task with a priority (lesson 87). Rate-monotonic scheduling (lesson 93) gives the rule for periodic tasks: the shorter the period, the higher the priority. With that rule and the execution times, you can check that every deadline holds before you write any task code.

Words for scheduling

A task is a function that the RTOS runs as if it had its own processor, with its own stack. The scheduler decides which ready task runs. In FreeRTOS each task has a number priority, and the higher number wins: when a higher-priority task becomes ready, it preempts the running task, which means the CPU is taken away at once. A period is the time between two starts of a periodic task. The execution time is the CPU time one run needs, and a deadline is the time by which a run must finish. The utilisation of a task is its execution time divided by its period. The total utilisation is the sum over all periodic tasks. A utilisation of 0.5 means that half the processor is busy with that task, on average.

The rate-monotonic test is a sum. For n periodic tasks, the utilisation sum of execution time ÷ period stays below n(21/n − 1) if deadlines are guaranteed. For four tasks that bound is 0.757. Your estimates go into the sum. The display flush is the big term: a 1 KB frame at 100 kHz I2C takes about 90 ms, and the UI task spends it every 200 ms, so about 0.45 of the processor goes to drawing. That is high, and it is the first thing to measure on real hardware: lesson 117 has to schedule around it.

A worked example of the sum

Take estimates for the four periodic tasks and add them up step by step. These numbers are examples chosen for practice, not measurements from the project. The safety check takes 1 ms every 50 ms, giving 1 ÷ 50 = 0.02. The control cycle takes 5 ms every 100 ms, giving 5 ÷ 100 = 0.05. The UI task has two periods, so it contributes two terms: the button scan takes 0.5 ms every 20 ms, giving 0.025, and the redraw takes 90 ms every 200 ms, giving 0.45. The logger takes 1 ms every 100 ms, giving 0.01. The total is 0.02 + 0.05 + 0.025 + 0.45 + 0.01 = 0.555. That is below the bound of 0.757 for four tasks, so the rule says every deadline holds.

Treating the UI task as one task with two periods is a simplification. A stricter analysis splits it into two jobs, which makes five periodic jobs and a bound of 5 × (21/5 − 1) = 0.743. The total of 0.555 still passes. The design lesson is that the display flush uses most of the headroom, so it is the first thing to measure and reduce. The bound is a sufficient test: a sum below it guarantees the deadlines, provided the estimates are right. A sum above it does not prove a miss; it only means the test cannot promise anything, and you must measure.

Why the shortest period gets the highest priority

A task with a short period has the tightest deadline, and it runs most often. If it had a low priority, a long task that was already running could delay it past its deadline, and the delay grows with the length of that task. Giving it the highest priority lets it preempt the others, so the running task is paused at once and resumed later. The rule is not a guess about importance. Lesson 93 gives the result behind it: for independent periodic tasks whose deadlines equal their periods, rate-monotonic priorities are optimal among fixed-priority schemes.

What the sum leaves out

The sum assumes that the estimates are right and that no task blocks. A polled I2C transfer, a blocking delay or a mutex held too long adds time that the sum does not see. The display flush is such a job, and lesson 117 must schedule around it.

Estimates, not measurements. The execution times above are rough figures from reading the code, marked as estimates. A real design measures them with a GPIO toggle around each task, or a trace tool, and puts the measured numbers in the README.

The pin map

Pins are the first thing a schematic review checks. The table lists every pin the design uses, with its alternate function, which is the built-in peripheral that the pin can be handed to. The alternate functions were checked against a community pin table that agrees with the vendor's pin definitions, because the ST server refused the datasheet download while this lesson was prepared. Before you build a board, confirm each row in the STM32F103x8/xB datasheet (ST), in its pin definitions table. Lesson 43 shows how to read such a table, and the RM0008 reference manual describes the registers that set each pin's function.

What a pin does

A pin is a leg of the chip that connects a signal inside it to the outside world. Each general-purpose pin (a GPIO, for general-purpose input and output) can be an input, an output, or handed over to a built-in peripheral such as a timer or a serial port. That handover is the alternate function, and the table gives it for each pin. On the STM32F103, the setup of each pin is four bits in the port's configuration registers, CRL for pins 0 to 7 and CRH for pins 8 to 15: two bits choose the direction and speed, and two bits choose the kind of pin, such as push-pull output, open-drain output, or input with a pull-up. Chapter 9 of RM0008 describes these fields. The skeleton's code writes those bits by hand, so that you can find them again in the reference manual.

Reading the table means asking three questions for each row: which pin, which peripheral, and what electrical condition. PA6 is TIM3_CH1, the timer channel that makes the heater PWM. The timer can drive the pin only when the pin is configured for the alternate function. A pin set up as a plain GPIO output still switches, but the timer no longer controls it, so the heater would not follow the PWM at all.

An input with a pull-up is a pin that the chip holds high through a weak internal resistor. A button wired from the pin to ground pulls the pin low when it is pressed, so the pin reads 0 when pressed and 1 when released. This is active low: the active state is the low level. Active-low inputs are the normal case for buttons. The board file inverts the reading, so the rest of the code sees 1 for "pressed". Forgetting that inversion is one of the common mistakes below.

The OLED's I2C pins work differently. In open-drain mode a pin can only pull the line low, and a resistor on the board pulls it high. Lesson 60 explains why the I2C bus is built that way. That is why the table says 4.7 kΩ external pull-ups on PB6 and PB7.

The real circuit behind the LED

In Wokwi the heater is a red LED, and the fan is a green one. On the real dryer, the microcontroller never drives a heater: it switches a power MOSFET. The gate is driven from PA6 through a series resistor of about 100 Ω, with a pull-down of about 10 kΩ so the heater stays off while the chip resets. The MOSFET's drain feeds the 24 V heater, and a logic-level N-channel part is chosen so its gate turns fully on at 3.3 V (lesson 12 and lesson 109 cover the parts and the layout). The fan is a motor, which is inductive, so it gets a flyback diode across its terminals (lesson 14).

A MOSFET (metal-oxide-semiconductor field-effect transistor) is a switch that the chip controls with voltage. Between its drain and source it either conducts well or almost not at all, and the gate voltage decides which. The part you choose must be specified to be fully on when its gate sees the 3.3 V that the pin produces. The gate resistor and pull-down values above are a starting point. Check them against the MOSFET's datasheet before you build anything.

Each component has a reason to be there. The gate resistor limits the current that the pin must supply when it charges the gate, and it slows the edge so that the switch does not ring. The pull-down matters in the window before the firmware runs. Until the firmware configures PA6, the pin is an input and its level is not defined, so the pull-down holds the gate low and keeps the heater off. Software cannot protect the heater before software starts, so this part of the circuit does that job.

The code, line by line

The skeleton's main.c is short, and it follows the architecture's rule: it calls only hal.h and the application modules. Read it as the start-up sequence of the product. These are the lines that matter. 

hal_init();                               /* board: clock, serial log, pins, timers, ADC, I2C */
dryer_init();                             /* application: the state machine starts in IDLE */
const material_t *m = materials_get(0);   /* the first preset: PLA */
(void)m;                                  /* linked in, not used yet */
hal_log("DRYER SKELETON OK");
for (;;) { }                              /* the RTOS tasks of lesson 117 do the work later */

hal_init() is the only call that touches registers, and it runs first, because everything after it assumes a configured clock and configured pins. dryer_init() puts the state machine in IDLE. materials_get(0) returns a pointer to the first row of a constant table, so the skeleton proves that the materials module is linked. The (void)m; line tells the compiler that the unused variable is deliberate, so it does not warn. hal_log() writes the banner. The final loop never ends, because a bare-metal program must not return from main(): returning would jump into whatever the start-up code left on the stack.

The serial log is the only real hardware in the skeleton, so it shows what a register write does. In hw/hal_bluepill.c, the line RCC->APB2ENR |= RCC_APB2ENR_IOPAEN | RCC_APB2ENR_USART1EN; switches on the clocks of port A and of USART1. Without a clock, a peripheral's registers do nothing. The line GPIOA->CRH = (GPIOA->CRH & ~(0xFU << 4)) | (0xBU << 4); clears the four configuration bits of PA9 and writes 0xB in their place: configuration 10 (alternate-function push-pull) and mode 11 (output at up to 50 MHz). The mask keeps the other seven pins of CRH unchanged, which is why the code reads the register, changes four bits, and writes it back, instead of assigning a whole value.

The baud rate comes from USART1->BRR = SystemCoreClock / LOG_BAUD;. The clock is the default 8 MHz internal oscillator, which the template's main.c states (lesson 67 explains that oscillator). The divider is 8 000 000 ÷ 115 200 = 69.4, and the register takes the whole number, 69. The baud rate that results is 8 000 000 ÷ 69 = 115 942, which is 0.6 % faster than 115 200. A UART tolerates a few per cent of error, so the log works, and you can check that number with a calculator. The last line of setup, USART1->CR1 = USART_CR1_TE | USART_CR1_UE;, turns on the transmitter and the peripheral. In hal_log(), each byte waits until the transmit-data-empty flag (TXE) is set before the next byte is written to the data register, so the loop never overwrites a byte that has not left yet.

Common mistakes and how to spot them

1. Priorities chosen by importance instead of period. Symptom: the display looks right, but when the control loop slows, the temperature is sampled late and the overshoot grows. The serial log shows the control cycle at 130 ms instead of 100 ms. Fix: give the shortest period the highest priority, measure each task's execution time with a GPIO pin that you toggle around it, and add the utilisations again.

2. Active-low input read as active-high. Symptom: the Start button appears to start a cycle when it is released and does nothing when it is pressed. The debug view shows the raw pin at 1 while the button is held down. Fix: check the wiring (button to ground, pin with pull-up), then make the board file return 1 for a low pin, as hal_button_pressed() does. A unit test with a fake that returns 1 for "pressed" catches the inversion on the PC.

3. A register include in the application. Symptom: the PC build of the state machine fails with a missing header, or it compiles only because a copy of the chip's header is on the PC's include path. Either way, the test no longer runs on the PC alone. Fix: move the register access behind a hal.h function, as hal_heater_set_permille() does, and treat an app/ file that includes a vendor header as a defect in review.

4. The serial log prints garbage or nothing. Symptom: the monitor shows no text, or random symbols. Cause: PA9 was left as an input (its CRH bits were not written), the port or USART clock was not enabled, or the baud divider is wrong. Fix: check IOPAEN and USART1EN in the clock register, then the 0xB nibble for PA9 in CRH, then the value of BRR.

5. A pin configured in the wrong place. Symptom: a second file writes to PA6 directly, and the heater PWM jitters whenever that file runs. Cause: two owners for one pin, and no single place that shows which function the pin has. Fix: keep every pin setup in the board file, and keep the pin map as one table next to it, so a review can compare the two.

In real projects

Teams settle the layers before the first driver is written. The rule that the application never includes a register header is easy to state and easy to break under deadline pressure, so reviewers check the include lines first. A search of the application folder for vendor headers finds most violations, and a continuous integration job can run that search on every change.

Pin maps are reviewed twice: against the schematic, and against the datasheet's pin definitions. Priorities are reviewed as a table too. A new task adds a row, and the sum is recomputed before the code is merged. Teams that use an RTOS usually measure execution times on the target, because the estimates are the first numbers to change once the code runs on hardware.

Summary

  • Each layer calls only the layer below it. Only the board file contains register addresses, so the logic also runs on a PC.
  • The HAL is the interface between the application and the chip. A driver turns hardware into plain values.
  • Rate-monotonic priorities give the shortest period the highest priority.
  • A utilisation sum below n(21/n − 1) guarantees every deadline, provided the estimates are right and no task blocks for long.
  • Each pin's configuration bits choose its function, and a timer drives a pin only in alternate-function mode.
  • An active-low input needs its reading inverted in the board file.
  • Check a UART baud rate with arithmetic: 8 MHz ÷ 69 gives 115 942 baud, which is 0.6 % above 115 200.
