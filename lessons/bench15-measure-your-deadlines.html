Bench lab 15: Measure your deadlines

FreeRTOS response times on a logic analyzer

By the end of this lab you can capture a FreeRTOS schedule on a logic analyzer, read response times off it, compare them with a response-time calculation, and fix a priority assignment that misses a deadline under load.

The task set

Lesson 93 checked a task set against the utilisation bound on paper, and the simulator could not run FreeRTOS on its STM32 model. On a real board with one pin per task, the logic analyzer draws the schedule, and a missed deadline becomes a gap you can point at. The lab is optional, needing the NUCLEO-U545RE-Q from bench lab 9 and a logic analyzer with PulseView, it does not count towards your progress, and it takes about 55 minutes.

projects/bench15-measure-deadlines runs FreeRTOS on the U5 with the Cortex-M33 port for chips without TrustZone, ARM_CM33_NTZ (FreeRTOS: Using FreeRTOS on ARMv8-M microcontrollers). The configuration is ready, and compared with lesson 93's Blue Pill file, the handler renames are gone, because this port defines SVC_Handler, PendSV_Handler and SysTick_Handler itself, while configENABLE_TRUSTZONE, configENABLE_MPU and configENABLE_FPU are new. Three periodic tasks each hold a pin high while they run.

TaskPeriod = deadlineWorkWork with B1 heldPin
control5 ms1 ms1 msPA6, CN10 pin 13
sensor20 ms4 ms4 msPA7, CN10 pin 15
logger50 ms8 ms16 msPC8, CN10 pin 33
(idle)PC6, CN10 pin 19, toggles while idle

The work is a loop on the Cortex-M33's cycle counter, DWT->CYCCNT, that counts only its own cycles, so while the task is preempted, the loop does not advance. A task's pin is therefore high from its start to its finish, including the time others ran in between, and that high time is the response time. Each task checks its own deadline with xTaskDelayUntil(), which returns pdFALSE when the next release time is already in the past, and the report task prints the counts once a second on the VCP.

The utilisation is 1/5 + 4/20 + 8/50 = 0.56, and 0.72 with B1 held, whereas the Liu and Layland bound for three tasks is 3 × (21/3 − 1) = 0.780 (lesson 93). Both are below it, so a rate-monotonic assignment meets every deadline, but the starter's assignment is not rate-monotonic.

On the board: capture the starter

  1. Connect analyzer D0 to PA6, D1 to PA7, D2 to PC8, D3 to PC6 and GND to GND.
  2. Build projects/bench15-measure-deadlines/starter, copy build/deadlines.bin to the ST-LINK drive and open the VCP, which prints one BENCH15 idle: ... line per second with the misses and runs for each task.
  3. Capture 200 ms at 1 MS/s, find a logger run (D2 high for about 8 ms) and measure the sensor's high time when a logger run starts just before it.
  4. Hold B1 and capture again. The VCP switches to LOAD, and the sensor's miss count starts to climb.

The starter's priorities go by importance, control 4, logger 3 and sensor 2. Before reading the capture, predict whether the sensor can meet its 20 ms deadline under load, then work out its worst-case response time with the response-time equation that lesson 93 introduced,

R = C + Σj ⌈R ÷ Tj⌉ × Cj(1)

where R is the task's response time, C its own work, and the sum runs over each higher-priority task j with period Tj and work Cj, counting every release that falls inside the window, iterated until R stops changing.

  • Without load: R = 4 + 8 + ⌈R/5⌉ × 1. Start with R = 12: 12 + ⌈12/5⌉ = 15; 4 + 8 + ⌈15/5⌉ = 15. R = 15 ms ≤ 20 ms: met.
  • With load: R = 4 + 16 + ⌈R/5⌉ × 1. Start with R = 20: 20 + 4 = 24; 20 + ⌈24/5⌉ = 25; 20 + 5 = 25. R = 25 ms > 20 ms: missed.

The equation uses one logger release per sensor window, which holds because the logger's period is longer than the window. Compare the 15 and 25 ms with the longest sensor pulses you captured.

On the board: fix it

Assign rate-monotonic priorities, control 4, sensor 3 and logger 2, then rebuild, flash and capture with B1 held. The logger is now the lowest periodic task, so check it with the same equation under load.

R = 16 + ⌈R/5⌉ × 1 + ⌈R/20⌉ × 4. From R = 16: 16 + 4 + 4 = 24; 16 + 5 + 8 = 29; 16 + 6 + 8 = 30; 16 + 6 + 8 = 30. R = 30 ms ≤ 50 ms.

The VCP's miss counts stay at zero, with and without load. On the analyzer the logger's pin now has gaps in it where control and sensor run, and its high time stretches towards 30 ms under load. The logger is still on time, only no longer first, which is what its 50 ms deadline allows.

You predicted a missed deadline on paper, watched it happen on real hardware and fixed it with priorities the theory chose, lesson 93 confirmed by measurement.

Common mistakes and how to spot them

The high time read as the execution time

A task seems to take far longer than its work, because the pin is high while the task is preempted, too. Subtract the pulses of higher-priority tasks inside the high time to get the execution time.

Priorities assigned by importance

A fast task misses its deadline although utilisation is low, because an important slow task with high priority blocks it for its whole run. Give the shorter period the higher priority, as rate-monotonic theory says.

The utilisation test trusted alone

The task set passes 0.72 < 0.78 and still misses deadlines, because the bound is a guarantee only for rate-monotonic priorities. With any other assignment, compute the response times.

Sampling too slowly

The idle pin's short pulses are missing from the capture, because the sample rate is below what they need. Sample at 1 MS/s, where each sample is 1 µs, plenty for millisecond tasks.

Summary

  • One pin per task turns the schedule into a picture, and a pin's high time is the task's response time.
  • The response-time equation R = C + Σ ⌈R/Tj⌉ Cj over higher-priority tasks predicts the worst case, iterated until R stops changing.
  • The starter's sensor task met its deadline idle (15 ms) and missed it under load (25 ms), and rate-monotonic priorities fixed it, the logger, now lowest, still finishing within 30 ms of its 50 ms.
  • FreeRTOS on the U5 uses the ARM_CM33_NTZ port, and xTaskDelayUntil() reports a missed release.
FreeRTOS's xTaskDelayUntil() in third_party/FreeRTOS-Kernel/tasks.c: about 80 lines. Find where it decides whether to block, and the comment explaining how it handles a tick count that has wrapped. That decision is the pdFALSE this lab counts as a miss.
