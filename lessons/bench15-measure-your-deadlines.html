Bench lab 15: Measure your deadlines

Lesson 93 checked a task set against the utilisation bound on paper, and the simulator couldn't run FreeRTOS on its STM32 model. On a real board with one pin per task, the logic analyzer draws the schedule, and a missed deadline is a gap you can point at.

This bench lab is optional. It needs the NUCLEO-U545RE-Q from bench lab 9 and a logic analyzer with PulseView. It doesn't count towards your progress. Time: about 55 minutes.
By the end of this lab you can capture a FreeRTOS schedule on a logic analyzer, read response times off it, compare them with a response-time calculation, and fix a priority assignment that misses a deadline under load.

The task set

projects/bench15-measure-deadlines runs FreeRTOS on the U5, with the Cortex-M33 port for chips without TrustZone, ARM_CM33_NTZ (FreeRTOS: Using FreeRTOS on ARMv8-M microcontrollers). The configuration is ready: compared with lesson 93's Blue Pill file, the handler renames are gone (this port defines SVC_Handler, PendSV_Handler and SysTick_Handler itself) and configENABLE_TRUSTZONE, configENABLE_MPU and configENABLE_FPU are new. Three periodic tasks each hold a pin high while they run:

TaskPeriod = deadlineWorkWork with B1 heldPin
control5 ms1 ms1 msPA6, CN10 pin 13
sensor20 ms4 ms4 msPA7, CN10 pin 15
logger50 ms8 ms16 msPC8, CN10 pin 33
(idle)PC6, CN10 pin 19, toggles while idle

The work is a loop on the Cortex-M33's cycle counter, DWT->CYCCNT, that counts only its own cycles: while the task is preempted, the loop doesn't advance. So a task's pin is high from its start to its finish, including the time others ran in between. The high time is the response time. Each task checks its own deadline with xTaskDelayUntil(), which returns pdFALSE when the next release time is already in the past. The report task prints the counts once a second on the VCP.

Utilisation: 1/5 + 4/20 + 8/50 = 0.56, and 0.72 with B1 held. The Liu and Layland bound for three tasks is 3 × (21/3 − 1) = 0.780 (lesson 93). Both are below it, so a rate-monotonic assignment meets every deadline. The starter's assignment isn't rate-monotonic.

On the board: capture the starter

  1. Connect analyzer D0 to PA6, D1 to PA7, D2 to PC8, D3 to PC6, and GND to GND.
  2. Build projects/bench15-measure-deadlines/starter and copy build/deadlines.bin to the ST-LINK drive. Open the VCP: one BENCH15 idle: ... line per second, with misses and runs for each task.
  3. Capture 200 ms at 1 MS/s. Find a logger run (D2 high for about 8 ms). Measure the sensor's high time when a logger run starts just before it.
  4. Hold B1 and capture again. The VCP switches to LOAD, and the sensor's miss count starts to climb.

The starter's priorities are "by importance": control 4, logger 3, sensor 2. Work out the sensor's worst-case response time with the response-time equation (lesson 93 introduced response-time analysis): its own work, plus each higher-priority task's work for every release that falls inside the window.

  • Without load: R = 4 + 8 + ⌈R/5⌉ × 1. Start with R = 12: 12 + ⌈12/5⌉ = 15; 4 + 8 + ⌈15/5⌉ = 15. R = 15 ms ≤ 20 ms: met.
  • With load: R = 4 + 16 + ⌈R/5⌉ × 1. Start with R = 20: 20 + 4 = 24; 20 + ⌈24/5⌉ = 25; 20 + 5 = 25. R = 25 ms > 20 ms: missed.

The equation uses one logger release per sensor window, which holds because the logger's period is longer than the window. Compare the 15 and 25 ms with the longest sensor pulses you captured.

On the board: fix it

Assign rate-monotonic priorities: control 4, sensor 3, logger 2. Rebuild, flash, and capture with B1 held. Then check the logger, now the lowest periodic task, with the same equation under load:

R = 16 + ⌈R/5⌉ × 1 + ⌈R/20⌉ × 4. From R = 16: 16 + 4 + 4 = 24; 16 + 5 + 8 = 29; 16 + 6 + 8 = 30; 16 + 6 + 8 = 30. R = 30 ms ≤ 50 ms.

The VCP's miss counts stay at zero, with and without load. On the analyzer the logger's pin now has gaps in it where control and sensor run, and its high time stretches towards 30 ms under load. The logger is still on time; it just isn't first. That's what its 50 ms deadline allows.

Common mistakes

  1. Reading the high time as the execution time. The pin is high while the task is preempted, too. The execution time is the high time minus the pulses of higher-priority tasks inside it.
  2. Assigning priorities by importance. Rate-monotonic theory says the shorter period gets the higher priority. An "important" slow task with high priority blocks fast tasks for its whole run.
  3. Trusting the utilisation test alone. 0.72 < 0.78 is a guarantee only for rate-monotonic priorities. With another assignment, compute the response times.
  4. Sampling too slowly. At 1 MS/s each sample is 1 µs: plenty for millisecond tasks. A slower rate can miss the idle pin's short pulses.

Summary

  • One pin per task turns the schedule into a picture; a pin's high time is the task's response time.
  • The response-time equation R = C + Σ ⌈R/Tj⌉ Cj over higher-priority tasks predicts the worst case; iterate until R stops changing.
  • The starter's sensor task met its deadline idle (15 ms) and missed it under load (25 ms). Rate-monotonic priorities fixed it, and the logger, now lowest, still finished within 30 ms of its 50 ms.
  • FreeRTOS on the U5 uses the ARM_CM33_NTZ port, and xTaskDelayUntil() reports a missed release.
You've predicted a missed deadline on paper, watched it happen on real hardware, and fixed it with priorities the theory chose. That's lesson 93 confirmed by measurement.
