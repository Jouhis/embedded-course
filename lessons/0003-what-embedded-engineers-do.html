What embedded engineers do

By the end of this lesson you can classify a device as MCU-based or Linux-based, say why, and name the job roles that work on each part of a product like a 3D printer.

Where we are and why it matters

Lessons 1 and 2 gave you the tools and a first program that runs on a chip. You can now make a Pico blink, which is the mechanical part of the work. This lesson answers a different question: what does a working engineer do with that skill, and which parts of a product need which kind of engineer? Knowing the answer early shapes what you practise. An engineer who knows the job asks, at each step, "what would a reviewer check here?" rather than "did it compile?"

The question also comes up in every product decision. A team building a new device must decide what the computing part looks like before anything else is designed. Choosing a microcontroller or a Linux computer sets the budget for power, memory, cost and development time. Getting that choice wrong is expensive, because the whole board and the software built on it depend on it. Later lessons assume you can tell which kind of device you are looking at, so this lesson gives you the test.

Concepts, one at a time

An embedded system

An embedded system is a computer built into a product that does one job, usually controlling something physical. A 3D printer is one: it moves a print head, heats a nozzle and reads a temperature, and it does those things without you typing commands at a keyboard. The computer is hidden inside the product. The user sees only the printer.

The brain of many embedded systems is a microcontroller (MCU): one chip that contains a CPU core, flash memory for the program, RAM for variables, and peripherals. A peripheral is a block of hardware that does a specific job, such as the pin driver that switches an output, a timer, or a converter that turns a voltage into a number. Each peripheral is controlled through registers, which the CPU reads and writes like memory. Lessons 38 and 51 build that picture in detail.

Firmware and the operating system question

The program that runs on an MCU is called firmware. It is usually written in C and stored in flash. Firmware can run in one of two ways. In bare-metal firmware, your main function is the whole program, and nothing sits between it and the hardware. In an RTOS (real-time operating system) firmware, a small kernel runs several tasks and decides which one runs when. Lesson 86 covers the RTOS in detail.

A Linux-based device is different in kind. It has an application processor, a larger chip that can run a full operating system with a file system, networking and many programs at once. That needs much more memory, typically hundreds of megabytes or more, compared with the kilobytes an MCU has on chip. Each is built for a different job. An application processor is built to run a general-purpose operating system, and an MCU is built to run a few tasks on time with little power. The next section shows why the difference matters on a real product.

Real-time: the deadline is part of the requirement

A real-time requirement is one where a result must arrive by a deadline. The result is correct only if it is on time. A hard real-time deadline means a late result is wrong. A soft real-time deadline means a late result is worse, but still usable. A printer's motor step is a hard deadline: the pulse that moves the motor must fire at the moment it was scheduled, or the motion is wrong. A web page that loads a little late is a soft deadline.

Operating systems on application processors are designed to share resources fairly between many programs. That fairness means they cannot promise that one program runs at an exact moment, because another program may be busy. An MCU running a few tasks, or a single loop, can promise timing, because nothing else competes for the processor. This is the core of the MCU-or-Linux decision.

Sensors, actuators and the pin

Embedded firmware sits between the physical world and the rest of the system. A sensor turns a physical quantity into an electrical signal: a thermistor's resistance changes with temperature, for example. An actuator does the reverse: a heater, a motor or a relay turns an electrical signal into motion or heat. The MCU reads sensors and drives actuators through its pins. An analogue input reads a continuous voltage, and an analogue-to-digital converter (ADC) turns it into a number the program can use. A PWM output (pulse-width modulation) switches a pin fully on and off, and the fraction of each cycle that it is on sets the average power delivered. Lessons 58 and 59 cover those peripherals.

Development, bring-up and test

Firmware work has a distinct vocabulary. Bring-up is the first time a new board is powered and checked, pin by pin, with a meter, an oscilloscope or a logic analyzer. It is usually done with simple test code, because a bug in the board and a bug in the software look the same until you separate them. A driver is the code that talks to one piece of hardware, such as a display or a sensor, and hides its register details behind a few functions. A hardware abstraction layer (HAL) is a layer of such drivers that lets the rest of the code run on different chips. The job titles below use these words, and the course teaches each of them in order.

A worked example: the printer's motor steps

Many 3D printers run Klipper, an open firmware that splits its work between two computers. This example follows one motor step through that split, using Klipper's own description of its design. The step count is simplified, but the division of work is accurate.

  1. The host plans the move. Klipper's host code, Klippy, is designed to run on a low-cost computer. Its ToolHead class handles look-ahead and tracks the timing of printing actions. Klipper's documentation says the host "uses an iterative solver to generate the step times for each stepper." So the host works out a list of times at which each motor must step.
  2. The host sends the schedule ahead. The host sends those times to the MCU in advance, as a list of commands. The MCU does not have to know what the printer is trying to do. It only needs to know when to act.
  3. The MCU stores the schedule. Klipper's documentation says that, on the MCU side, the incoming command "just appends the parameters of each queue_step command to a per stepper queue." Each queued step is a time, held until it is due.
  4. A hardware timer fires the pulse. The MCU sets a hardware timer for the time of the first queued step. When the timer expires, the interrupt runs the step code. The documentation says the step code "generates a step pulse and then reschedules itself to run at the time of the next step pulse." The next pulse is then set up in the same way.
  5. The pin changes. The pulse goes out on the stepper driver's input pin, and the motor moves one step. No Linux process is in that path, so a busy host can slow down planning, but it cannot make the pulse late, as long as the schedule is already on the MCU.

Read the example with a question in mind: which part is hard real-time, and which part is not? The MCU's pulse is the hard part, because a late pulse is a wrong step. The host's planning is not hard real-time, because the MCU has the schedule already, and a little delay in planning is harmless.

The pins on the MCU

The MCU's pins are used for the rest of the printer too. Klipper's configuration reference describes a heater section with two pins that matter here. The sensor_pin is an "analog input pin connected to the sensor", which for the hotend is the thermistor. The heater_pin is a "PWM output pin controlling the heater". So the MCU reads the temperature as a voltage through an ADC, and it sets the heater's average power through PWM. The heater output itself is a switch. Lesson 12 explains why a transistor, not a pin, carries the heater current.

Those two pins illustrate the general pattern of embedded work. Each pin has a job, the software must read or drive it at the right time, and the hardware around it, such as the thermistor's voltage divider or the heater's switch, must be designed to work with it. A firmware engineer has to understand all three parts, as well as the C.

Kinds of product, and kinds of engineer

Embedded work shows up in many industries: automotive (a car's door or brake controller), medical (an infusion pump), industrial (a motor drive on a factory line), consumer (a kettle, a fitness tracker, a printer) and aerospace (flight-control and satellite subsystems). The industries differ in their rules. Medical and aerospace work usually has strict documentation and testing requirements, and some products must meet a formal safety standard, which lesson 112 introduces. Consumer work is more about cost and time to market. The core skills are the same.

Job titles vary by company, but these five roles cover most of the field:

RoleWhat the day looks like
Firmware engineerWrites and debugs C for an MCU. Reads datasheets and reference manuals, and brings up new peripherals.
Embedded software engineerBuilds drivers, state machines and RTOS tasks on top of the hardware layer.
Embedded Linux engineerWorks on the boot chain, kernel drivers and user-space services on an application processor.
Hardware or firmware bring-up engineerPowers up a new board for the first time, checks each pin and rail with a scope or logic analyzer, and writes the first code that talks to it.
Test and validation engineerWrites test plans, builds hardware-in-the-loop rigs and maintains the automated regression tests.

A typical week mixes coding with debugging a board on the bench, reading a schematic with the hardware team, reviewing code, and answering a question about a field failure. The practitioner articles on the Interrupt blog cover the debugging and tooling side in depth.

Which device is which?

The deciding question is whether the device needs an operating system. Work through four questions in order, and stop when one of them decides it.

  1. Does a result have a hard deadline? If a late result is wrong, as with motor steps, an MCU with predictable timing is the default choice.
  2. Does the software need many programs, a browser, networking or a large file system? If yes, the device needs a full operating system, so it is Linux-based.
  3. What is the power budget? A battery device that sleeps most of the time usually suits an MCU, because the MCU draws far less power at idle.
  4. What does each option cost in parts, software and maintenance? A Linux board brings an operating system to update, patch and secure for the life of the product. Pick the option that meets the requirements at the lowest total cost and risk.

Neither kind is better in general. An MCU is a poor fit for a browser, and a Linux board is a poor fit for a motor that must step on time. A common real design uses both: an MCU for the timed work and a Linux processor for the user interface and networking, which is how a Klipper printer is built.

Common mistakes and how to spot them

  1. Choosing Linux because it looks more capable. Symptom: the product boots slowly, uses a lot of memory and power, and its timed outputs jitter under load. Cause: the team treated the timing requirement as a detail. Fix: move the timed control to an MCU, and keep Linux for the work that needs it.
  2. Choosing an MCU for work that needs an operating system. Symptom: the team cannot fit the networking stack or the user interface into the memory, and each new feature forces a rewrite. Cause: the requirement list asked for a browser or many programs at once, and the team did not check the memory. Fix: count the memory and the number of concurrent programs before you commit.
  3. Treating the schematic as someone else's problem. Symptom: the board resets at random when a motor starts, and the firmware gets blamed. Cause: the supply rail dips under the load, which only a meter or scope shows. Fix: a firmware engineer checks the power rails and the sensor wiring on the bench, as the bring-up role does, before changing the code.
  4. Assuming a simulator matches the product. Symptom: a loop that runs perfectly in the simulator misses a deadline on the real board. Cause: the simulator does not reproduce every timing detail of the hardware. Fix: test timing on the real board for any hard deadline, and treat the simulator as evidence, not proof.

In real projects

A product team usually includes a firmware engineer for the MCU, an embedded software engineer for the drivers and the control logic, and often a Linux engineer if the product has an application processor. A bring-up engineer is involved early, when the first boards arrive, and a test engineer keeps the regression tests running as the code changes. Code review in these teams checks timing, power and failure behaviour, as well as whether the code is correct.

Summary

  • An embedded system is a computer built into a product that does one job, usually controlling something physical. Its brain is often an MCU, which holds a CPU core, flash, RAM and peripherals in one chip.
  • Firmware runs either bare-metal, where your main function is the whole program, or on an RTOS, where a small kernel runs several tasks.
  • A real-time requirement is one where a result must arrive by a deadline. A hard deadline makes a late result wrong, and a soft deadline makes it worse but still usable.
  • A printer's motor step is a hard deadline. The MCU must fire the pulse on time, while the host's planning is not hard real-time because the MCU already holds the schedule.
  • An MCU is the default choice when a result has a hard deadline or the power budget is tight. A Linux-based device is needed when the software needs many programs, a browser, networking or a large file system.
  • Five roles cover most of the field: firmware engineer, embedded software engineer, embedded Linux engineer, hardware or firmware bring-up engineer, and test and validation engineer.
  • Many real designs use both: an MCU for the timed work and a Linux processor for the user interface and networking, which is how a Klipper printer is built.
  • Bring-up is the first time a new board is powered and checked, pin by pin, with a meter, an oscilloscope or a logic analyzer.

Optional task: read a real printer configuration

This task needs no hardware. Klipper publishes example configurations for many printers, so you can read a real one in your browser.

  1. Open any printer configuration from the config/ folder of the Klipper repository, for example one whose name starts with printer-. If you own a Klipper printer, its own printer.cfg works too.
  2. Find the [extruder] section. Find sensor_pin and heater_pin.
  3. For each pin, write down whether it is an analogue input or a PWM output, using the Klipper configuration reference's wording.
  4. Then answer: which of the two is the MCU reading, and which is the MCU driving? Expected answer: sensor_pin is read, and heater_pin is driven.
