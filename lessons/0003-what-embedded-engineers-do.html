Microcontrollers, Linux devices and the work around them

Lessons 1 and 2 gave you the tools and a first program running on a chip, which covers the mechanical part of the work. This lesson turns to a different question: what does a working engineer do with that skill, and which parts of a product need which kind of engineer? Knowing the answer early shapes how you practise, because an engineer who knows the job asks at each step what a reviewer would check, rather than only whether the code compiled.

The same question comes up at the start of every product. Before anything else is designed, a team must decide what the computing part looks like, and choosing a microcontroller or a Linux computer sets the budget for power, memory, cost and development time. A wrong choice is expensive, since the whole board and the software built on it depend on it. Later lessons assume you can tell which kind of device you are looking at, so this lesson gives you a test for it.

Embedded systems and microcontrollers

An embedded system is a computer built into a product to do one job, usually controlling something physical. A 3D printer is a good example: it moves a print head, heats a nozzle and reads a temperature without anyone typing commands at a keyboard. The computer stays hidden inside the product, and the user only sees the printer.

Many embedded systems are built around a microcontroller (MCU), a single chip that contains a CPU core, flash memory for the program, RAM for variables and peripherals. A peripheral is a block of hardware with a specific job, such as the driver that switches an output pin, a timer, or a converter that turns a voltage into a number. The CPU controls each peripheral through registers, which it reads and writes like memory, and lessons 38 and 51 build that picture in detail.

Firmware, bare metal and operating systems

The program that runs on an MCU is called firmware. It is usually written in C and stored in flash, and it runs in one of two ways. In bare-metal firmware, your main function is the whole program and nothing sits between it and the hardware. In firmware built on an RTOS (real-time operating system), a small kernel runs several tasks and decides which one runs when; lesson 86 covers this in detail.

A Linux-based device differs in kind. It has an application processor, a larger chip that can run a full operating system with a file system, networking and many programs at once. That requires far more memory, typically hundreds of megabytes or more, compared with the kilobytes an MCU has on chip. The two are built for different jobs: an application processor runs a general-purpose operating system, whereas an MCU runs a few tasks on time with little power. The next section explains why that difference decides so much.

Real-time requirements and deadlines

A real-time requirement is one where a result must arrive by a deadline, so it is correct only if it is on time. Under a hard real-time deadline a late result is simply wrong, while under a soft real-time deadline it is worse but still usable. A printer's motor step is a hard deadline, because the pulse that moves the motor must fire at its scheduled moment or the motion is wrong. A web page that loads slightly late is a soft one.

Operating systems on application processors are designed to share resources fairly between many programs. That fairness means they cannot promise that a given program runs at an exact moment, since another program may be using the processor. An MCU running a few tasks, or a single loop, can make that promise, because nothing else competes for the processor. This is the core of the decision between an MCU and Linux.

Sensors, actuators and pins

Embedded firmware sits between the physical world and the rest of the system. A sensor turns a physical quantity into an electrical signal, as a thermistor does when its resistance changes with temperature. An actuator does the reverse, turning an electrical signal into motion or heat, as a heater, a motor or a relay does. The MCU reads sensors and drives actuators through its pins.

Two kinds of pin appear constantly. An analogue input reads a continuous voltage, and an analogue-to-digital converter (ADC) turns that voltage into a number the program can use. A PWM output, short for pulse-width modulation, switches a pin fully on and off, and the fraction of each cycle it spends on determines the average power delivered. Lessons 58 and 59 cover both peripherals.

Bring-up, drivers and hardware abstraction

Firmware work has its own vocabulary. Bring-up is the first time a new board is powered and checked, pin by pin, with a meter, an oscilloscope or a logic analyzer. It is usually done with simple test code, since a fault in the board and a fault in the software look the same until you separate them. A driver is the code that talks to one piece of hardware, such as a display or a sensor, and hides its register details behind a few functions. A hardware abstraction layer (HAL) is a layer of such drivers that lets the rest of the code run on different chips. The roles described later use these terms, and the course teaches each of them in turn.

Worked example: motor steps on a Klipper printer

Many 3D printers run Klipper, an open firmware that splits its work between two computers. We can follow one motor step through that split using Klipper's own description of its design. The step count is simplified, but the division of work is accurate.

  1. The host plans the move. Klipper's host code, Klippy, is designed to run on a low-cost computer. Its ToolHead class handles look-ahead and tracks the timing of printing actions, and the documentation says the host "uses an iterative solver to generate the step times for each stepper." The host therefore produces a list of times at which each motor must step.
  2. The host sends the schedule ahead. It sends those times to the MCU in advance as a list of commands. The MCU does not need to know what the printer is trying to do, only when to act.
  3. The MCU stores the schedule. According to the documentation, the incoming command on the MCU side "just appends the parameters of each queue_step command to a per stepper queue." Each queued step is a time, held until it is due.
  4. A hardware timer fires the pulse. The MCU sets a hardware timer for the first queued step, and when the timer expires the interrupt runs the step code. That code "generates a step pulse and then reschedules itself to run at the time of the next step pulse", so the next pulse is prepared the same way.
  5. The pin changes. The pulse goes out on the stepper driver's input pin and the motor moves one step. Since no Linux process sits in that path, a busy host can slow down the planning but cannot make a pulse late, as long as the schedule has already reached the MCU.

Before reading on, decide which part of this chain is hard real-time and which is not. The MCU's pulse is the hard part, because a late pulse is a wrong step. The host's planning is not, since the MCU already holds the schedule and a small delay in planning does no harm.

  1. The host plans the move. It works out when each motor step must happen, as a time on the MCU's clock: here 1000, 1250 and 1500 ticks.
  2. The host sends those times ahead, as queue_step commands. The MCU only appends them to a queue for that stepper; it does not need to know what is being printed.
  3. The host gets busy with something else. That is allowed: the schedule is already inside the MCU.
  4. The MCU's hardware timer reaches 1000. Its interrupt pulses the step pin, and the motor moves one step.
  5. At 1250 the timer fires again, from the queue, with no help from the host.
  6. At 1500 the third step goes out. The pulses are evenly spaced although the host was busy: the MCU does the hard real-time part, and the host's planning only has to stay ahead.

Heater and sensor pins on the MCU

The MCU's pins serve the rest of the printer as well. Klipper's configuration reference describes a heater section with two relevant pins. The sensor_pin is an "analog input pin connected to the sensor", which on the hotend is the thermistor, and the heater_pin is a "PWM output pin controlling the heater". The MCU thus reads the temperature as a voltage through an ADC and sets the heater's average power with PWM. The heater output itself is a switch, and lesson 12 explains why a transistor rather than the pin carries the heater current.

These two pins show the general pattern of embedded work. Each pin has a job, the software must read or drive it at the right time, and the hardware around it, such as the thermistor's voltage divider or the heater's switch, must be designed to work with it. A firmware engineer therefore needs to understand all three parts as well as the C.

Industries and engineering roles

Embedded work appears in many industries: automotive (a car's door or brake controller), medical (an infusion pump), industrial (a motor drive on a factory line), consumer (a kettle, a fitness tracker, a printer) and aerospace (flight-control and satellite subsystems). Their rules differ considerably. Medical and aerospace work usually comes with strict documentation and testing requirements, and some products must meet a formal safety standard, which lesson 112 introduces, while consumer work is driven more by cost and time to market. The core skills, however, are the same.

Job titles vary between companies, but these five roles cover most of the field:

RoleWhat the day looks like
Firmware engineerWrites and debugs C for an MCU. Reads datasheets and reference manuals, and brings up new peripherals.
Embedded software engineerBuilds drivers, state machines and RTOS tasks on top of the hardware layer.
Embedded Linux engineerWorks on the boot chain, kernel drivers and user-space services on an application processor.
Hardware or firmware bring-up engineerPowers up a new board for the first time, checks each pin and rail with a scope or logic analyzer, and writes the first code that talks to it.
Test and validation engineerWrites test plans, builds hardware-in-the-loop rigs and maintains the automated regression tests.

A typical week mixes coding with debugging a board on the bench, reading a schematic with the hardware team, reviewing code and investigating a field failure. The practitioner articles on the Interrupt blog cover the debugging and tooling side in depth.

Choosing between an MCU and a Linux device

The deciding question is whether the device needs an operating system. Work through four questions in order and stop as soon as one of them settles it.

  1. Does a result have a hard deadline? If a late result is wrong, as with motor steps, an MCU with predictable timing is the default choice.
  2. Does the software need many programs, a browser, networking or a large file system? If so, the device needs a full operating system and is therefore Linux-based.
  3. What is the power budget? A battery device that sleeps most of the time usually suits an MCU, since an MCU draws far less power at idle.
  4. What does each option cost in parts, software and maintenance? A Linux board brings an operating system that must be updated, patched and secured for the life of the product. Choose the option that meets the requirements at the lowest total cost and risk.

Neither kind is better in general, since an MCU is a poor fit for a browser and a Linux board is a poor fit for a motor that must step on time. Many real designs therefore use both: an MCU for the timed work and a Linux processor for the user interface and networking, which is exactly how a Klipper printer is built.

Optional task: reading a printer configuration

This task needs no hardware. Klipper publishes example configurations for many printers, so you can read a real one in your browser.

  1. Open any printer configuration from the config/ folder of the Klipper repository, for example one whose name starts with printer-. If you own a Klipper printer, its own printer.cfg works too.
  2. Find the [extruder] section, and in it sensor_pin and heater_pin.
  3. For each pin, write down whether it is an analogue input or a PWM output, using the wording of the Klipper configuration reference.
  4. Then decide which of the two the MCU reads and which it drives. Expected answer: sensor_pin is read and heater_pin is driven.

Common mistakes and how to spot them

Choosing Linux because it looks more capable

The product boots slowly, uses a lot of memory and power, and its timed outputs jitter under load. In this case the team treated the timing requirement as a detail. The fix is to move the timed control to an MCU and keep Linux for the work that actually needs it.

Choosing an MCU for work that needs an operating system

The networking stack or the user interface does not fit in memory, and each new feature forces a rewrite. The requirements asked for a browser or many programs at once, and nobody checked the memory against them. Count the memory and the number of concurrent programs before committing to a part.

Leaving the schematic to someone else

The board resets at random when a motor starts, and the firmware gets the blame. The real cause is a supply rail that dips under the load, which only a meter or an oscilloscope reveals. A firmware engineer should check the power rails and sensor wiring on the bench, as the bring-up role does, before changing any code.

Assuming the simulator matches the product

A loop that runs perfectly in the simulator misses a deadline on the real board, because the simulator does not reproduce every timing detail of the hardware. Test every hard deadline on the real board, and treat the simulator as evidence rather than proof.

Embedded product teams

A product team usually includes a firmware engineer for the MCU, an embedded software engineer for the drivers and control logic, and often a Linux engineer when the product has an application processor. A bring-up engineer joins early, when the first boards arrive, and a test engineer keeps the regression tests running as the code changes. Code review in such teams checks timing, power and failure behaviour as well as correctness.

Summary

  • An embedded system is a computer built into a product to do one job, usually controlling something physical. Its core is often an MCU, which holds a CPU core, flash, RAM and peripherals in one chip.
  • Firmware runs either bare-metal, where your main function is the whole program, or on an RTOS, where a small kernel runs several tasks.
  • A real-time requirement is one where a result must arrive by a deadline. A hard deadline makes a late result wrong, and a soft deadline makes it worse but still usable.
  • A printer's motor step is a hard deadline. The MCU must fire the pulse on time, while the host's planning is not hard real-time because the MCU already holds the schedule.
  • An MCU is the default when a result has a hard deadline or the power budget is tight. A Linux-based device is needed when the software requires many programs, a browser, networking or a large file system.
  • Five roles cover most of the field: firmware engineer, embedded software engineer, embedded Linux engineer, hardware or firmware bring-up engineer, and test and validation engineer.
  • Many real designs use both: an MCU for the timed work and a Linux processor for the user interface and networking, as in a Klipper printer.
  • Bring-up is the first time a new board is powered and checked, pin by pin, with a meter, an oscilloscope or a logic analyzer.
