The idea

An embedded system is a computer built into a product that does one job, usually controlling something physical. Your 3D printer is one. Its mainboard has a microcontroller (MCU) with a CPU core, flash and RAM, and peripherals that drive the motors and read the sensors. Elecia White's Making Embedded Systems describes this profession, and the book is the best practical overview of it. Making Embedded Systems, 2nd ed. A microcontroller is different from a Linux computer in one important way: it runs your code directly, with no operating system between you and the hardware.

Your printer as an embedded system

Klipper, the firmware for your QIDI Q2, splits the work between two computers. A host computer runs Klippy, which plans the moves and works out when each motor step should happen. The MCU on the mainboard does not plan anything. It executes the step pulses it was told to produce, at the times it was given. Klipper's documentation describes this split in its code overview. Klipper: Code Overview

The MCU's hardware pins are used for the rest of the printer too. A thermistor is read through an analogue input, which the MCU converts into a number. A heater is driven by a PWM output, which turns it on for a fraction of each cycle. Klipper: Config Reference names sensor_pin as the analogue input connected to the sensor and heater_pin as the PWM output that controls the heater. On your board, the heater output drives a power switch, which lesson 12 explains.

Kinds of product, and kinds of engineer

Embedded work shows up in many industries: automotive (a car's door or brake controller), medical (an infusion pump), industrial (a motor drive on a factory line), consumer (a kettle, a fitness tracker, a printer) and aerospace (flight-control and satellite subsystems). The industries differ in their rules. Medical and aerospace work usually has strict documentation and testing requirements. Consumer work is more about cost and time to market. The core skills are the same.

Job titles vary by company, but these five roles cover most of the field:

RoleWhat the day looks like
Firmware engineerWrites and debugs C for an MCU. Reads datasheets and reference manuals, and brings up new peripherals.
Embedded software engineerBuilds drivers, state machines and RTOS tasks on top of the hardware layer.
Embedded Linux engineerWorks on the boot chain, kernel drivers and user-space services on an application processor.
Hardware or firmware bring-up engineerPowers up a new board for the first time, checks each pin and rail with a scope or logic analyzer, and writes the first code that talks to it.
Test and validation engineerWrites test plans, builds hardware-in-the-loop rigs and maintains the automated regression tests.

A typical week mixes coding with debugging a board on the bench, reading a schematic with the hardware team, reviewing code, and answering a question about a field failure. The practitioner articles on the Interrupt blog cover the debugging and tooling side in depth.

Which device is which?

The deciding question is whether the device needs an operating system. An MCU runs bare-metal firmware, or an RTOS, and has its own memory and pins; it suits control with tight timing and low power. A Linux-based device runs a full operating system on an application processor with much more memory; it suits work that needs a browser, many programs at once, or large storage. Neither is the better choice in general. The right one is the one that meets the requirements at the lowest cost and risk.

Check your understanding

Each question describes a device. Pick the best fit, then read why. The tempting answer is in the explanation.

You can look at a product and say which part is an MCU job and which is a Linux job, and give the reason. That judgement is what you will use in every design review.

"A new product has a battery-powered sensor with a radio and a small display. Would you choose an MCU or Linux, and what would you test first?" Answer out loud in 60 seconds, then compare.

Model answer

I would start with an MCU: the sensor and radio need low power, the display needs little software, and there is no reason for a full operating system. The first things to test are the power budget in each state, the radio link under bad signal, and the boot and recovery path when the battery runs low. I would also check that the sensor's timing holds while the radio is busy.
