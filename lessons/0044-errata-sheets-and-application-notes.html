Errata sheets and application notes

Silicon has bugs, and the vendor writes them down. A firmware engineer who checks the errata before trusting a peripheral saves days of debugging.

By the end of this lesson you can find the errata for an RP2040 or an STM32F103, read one item (its summary, affected revisions and workaround), work out the register value the workaround needs, and decide whether it affects your code.

Where we are and why it matters

The last lessons taught you how to read a reference manual. Lesson 43 showed how to find a register's address, offset and reset value in the RP2040 datasheet and in the STM32 reference manual, RM0008. That work assumes the document is correct. This lesson covers the part of the paperwork where the vendor admits it is not always correct, and tells you how to check.

The problem appears in real jobs. A product ships with a watchdog that resets the board after a few seconds, even though the code loads a 5 second timeout. The engineer who finds the cause is often the one who checks the chip's errata sheet, finds the item that matches, and applies the one-line workaround. Without that check, the team spends days rewriting correct code. The same happens with a peripheral that works on one batch of boards and not on another. The batch differs in silicon revision, and the errata tell you which revisions have the bug.

Concepts, one at a time

The datasheet describes the design, and the silicon can differ

A datasheet is the vendor's description of a chip: its pins, electrical limits, clocks, and the registers that control its peripherals. A reference manual is the longer version of the register part. The description is what the vendor intends, and the chip is what the factory makes. Sometimes a block does not behave as described. A counter runs at the wrong rate, a flag clears too early, or a bit does nothing.

An errata sheet, or errata, is the vendor's list of these gaps. Each entry is called an erratum, with a number, and the list is part of the specification. Treat it that way. If the datasheet says a register does X and the errata says it does Y on some revisions, the errata describes the chip you hold. The errata list is written after the hardware is made, so it is always incomplete for new chips. A new revision can fix an old bug, or add a new one. Read the list for your exact revision, not for the chip family in general.

What one erratum item contains

Every item has the same parts, so you can read any item the same way. The RP2040 datasheet writes them as labelled fields. You will see these fields in Appendix B, the errata appendix at page 627:

FieldWhat it tells you
ReferenceThe item's ID, such as RP2040-E1. Use it in code comments and bug reports.
SummaryOne line that says what goes wrong. Read it first, to decide whether the item is about your block.
DescriptionThe mechanism and its effect, with the numbers. Read it in full before you apply anything.
WorkaroundWhat software does to avoid the problem. Sometimes it is a register write, and sometimes it is "do not use this register".
AffectsThe silicon revisions with the bug.
Fixed byWhether the fix is in the hardware revision, the bootrom, the software or the documentation. "Not fixed" means you must work around it.

The Affects and Fixed by fields are the ones beginners skip, and they decide the outcome. A workaround you apply to a chip that does not have the bug is harmless but confusing. Leaving it out of a chip that does have the bug is the real risk.

Revisions: the same name can be a different chip

A silicon revision is a version of the physical chip, identified by a letter or number that the vendor prints on the package or in the datasheet. Vendors fix bugs by making a new revision, and the old chips stay on sale. So two boards with the same part name can behave differently.

The RP2040 has three revisions named in the datasheet: B0, B1 and B2. The bootrom, the small program in read-only memory that runs first after reset, also has versions. The datasheet says that bootrom versions 1, 2 and 3 correspond to the B0, B1 and B2 silicon, respectively, and that the bootrom source is at the pico-bootrom repository. So the bootrom version is a clue to the silicon revision.

The table below shows how the Affects and Fixed by fields work for three items, using the datasheet's wording:

ItemBlockAffectsFixed by
RP2040-E1WatchdogB0, B1, B2Documentation, software
RP2040-E6GPIO / ADCB0, B1RP2040B2 bootrom; on B0 and B1 in the SDK, which disables the input early
RP2040-E9BootromB0, B1, B2Documentation and software

E6 shows why the revision matters. On B2 the bootrom already disables the digital input on the ADC pins. On B0 and B1 your code must do it early after startup, and the SDK's platform setup does that. A learner who reads only the summary would not know that a B2 board does not need the workaround.

Application notes and reference designs

An application note is a short document from the vendor that explains one job: a recommended circuit, a power-up sequence, or the steps to set up a peripheral. It is not a specification. It shows one correct way, and it may simplify.

For the RP2040 the most useful one is the hardware design guide, Hardware design with RP2040, which the datasheet calls the Minimal Design Example. The datasheet's section 2.16.3 says the reference design runs the crystal oscillator (XOSC) at 12 MHz, and that the default startup delay suits that design. Use an application note for the circuit. Use the datasheet for register behaviour. An application note can contain a register value that differs from the datasheet, so check any number you copy from it against the datasheet, as you would check any other source.

The watchdog, the block behind RP2040-E1

A watchdog is a countdown timer that resets the chip when it reaches zero. Its purpose is to recover from software that gets stuck. The program must write to the watchdog before the count runs out, and each write restarts the countdown. A program that hangs stops writing, so the count reaches zero and the chip restarts. The RP2040 datasheet describes this in section 4.7 in the same terms: the programmer must periodically write a value to the watchdog to stop it from reaching zero.

Four pieces of the RP2040 watchdog matter here. The LOAD register, at offset 0x04 from the watchdog's base address, holds the value the count restarts from. The counter itself is 24 bits wide, so LOAD can hold at most 0xFFFFFF. The counter counts down once per tick, and the tick is generated from the reference clock. Section 4.7.2 gives the tick as nominally 1 µs, and the Pico SDK's header says the watchdog gets a 1 MHz clock. The micro sign is lost in the PDF's text, so read the figure in the PDF if you doubt it.

STM32F1: find the sheet that matches your part

ST publishes a separate errata sheet for each density of the STM32F1 family. Density means the amount of flash, so the high-density parts (the C, D and E suffixes) and the medium-density parts (the 8 and B suffixes) have different bugs. The Blue Pill uses the STM32F103C8, which is medium density. The errata sheet ES0340 covers only the high-density STM32F101xC/D/E and STM32F103xC/D/E parts, so it is the wrong document for a Blue Pill. The sheet for medium density is titled along the lines of "STM32F101x8/B, STM32F102x8/B and STM32F103x8/B medium-density device limitations". This course has not yet opened the current revision of that sheet, so download it from the ST documentation page for the STM32F1 series before you rely on any item. Check the revision letter of your chip against the sheet's list too.

Do not assume an errata sheet from another family or density applies to your part. The same peripheral name, such as a timer or a USB block, can have different bugs on the F1, the F4 and the RP2040. Match the sheet to the exact part and revision.

Worked example: a 5 second watchdog on RP2040-E1

The description of RP2040-E1 says the counter decrements twice per tick instead of once. The datasheet's summary of the fix is one sentence: "Use double the desired value in LOAD." Work through what that means with numbers.

  1. Without the bug. One tick is 1 µs, so a 5 second timeout is 5,000,000 ticks. The counter must count down 5,000,000 ticks, so LOAD would be 5,000,000.
  2. With the bug. The counter takes two steps per tick. To count 5,000,000 ticks, it needs LOAD = 10,000,000, because each tick removes two from the count.
  3. Check the field. 10,000,000 in hexadecimal is 0x989680. That fits in the 24-bit LOAD field, because the largest value is 0xFFFFFF, which is 16,777,215.
  4. Find the longest timeout. With the bug, the largest LOAD is 0xFFFFFF, which gives 16,777,215 ÷ 2 = 8,388,607 ticks, about 8.39 seconds. Without the bug it would be about 16.8 seconds. The datasheet rounds these to about 8.3 and about 16.7 seconds, in its text on RP2040-E1.

The numbers show the pattern. Any code that programs the watchdog must double the count, or the timeout is half as long as written. A 5 second timeout written as LOAD = 5,000,000 fires at about 2.5 seconds. The next section shows that the Pico SDK already does the doubling for you.

The code, line by line

You do not need to write the workaround yourself on the Pico SDK, because watchdog_enable() already applies it. Open the SDK source and read the part that matters. The file is src/rp2_common/hardware_watchdog/watchdog.c in the SDK folder, version 2.3.1. The lines below are excerpts from it, with the comment that the SDK authors wrote: 

// Note, we have x2 here as the watchdog HW currently decrements twice per tick (errata RP2040-E1)
#define WATCHDOG_XFACTOR 2

// inside _watchdog_enable(), when delay_ms is not zero:
load_value = delay_ms * (1000 * WATCHDOG_XFACTOR);
if (load_value > WATCHDOG_LOAD_BITS)
    load_value = WATCHDOG_LOAD_BITS;
watchdog_update();    /* writes load_value into watchdog_hw->load */

Read the code one line at a time. The first line is a comment that names the erratum, so anyone who searches for "RP2040-E1" finds this code. The second line defines the factor 2 as a named constant, which is the workaround written as a number with a reason. Naming it makes it easy to find and to remove when a future chip has no bug.

The line load_value = delay_ms * (1000 * WATCHDOG_XFACTOR); converts milliseconds to ticks. One millisecond is 1000 ticks of 1 µs, and the factor 2 doubles the count for the bug. For watchdog_enable(5000) the result is 5000 × 2000 = 10,000,000, the value from the worked example.

The third and fourth lines clamp the value to the largest LOAD the 24-bit field can hold. Without the clamp, a large delay would wrap or be cut off by the hardware, and the timeout would be wrong without any error. The last line calls watchdog_update(), which writes load_value into the hardware register watchdog_hw->load. Each later call to that function restarts the countdown from the same value. That is how a program feeds the watchdog.

Now the version without the workaround, which is the mistake the SDK avoids: 

watchdog_hw->load = 5000000;   /* meant as 5 s, but RP2040-E1 halves it: fires near 2.5 s */

This line compiles and runs. It is wrong only because of the silicon, so no compiler or static check finds it. Only the errata or a timing test shows it.

Common mistakes and how to spot them

Each of these mistakes is common, and each has a symptom you can see without a debugger.

  1. Writing the milliseconds or microseconds straight into LOAD. The symptom is a reset at about half the timeout you asked for. On a 5 second test the board resets after about 2.5 seconds, and the reset reason is the watchdog. The fix is to double the count, or to call watchdog_enable() and let the SDK do it.
  2. Applying a workaround from the wrong revision. A team copies a fix from a forum post about B0 silicon and applies it to B2 boards. The symptom is a timing error on the B2 board that did not exist before. The fix is to read the Affects field and check the revision of the board in your hand.
  3. Reading the summary and skipping the Fixed by line. E6 is fixed in the bootrom on B2, so a B2 board does not need your code change. Without the Fixed by line you add a workaround that is harmless but hides the real fix, and the next engineer does not know why the line is there.
  4. Using the errata sheet for a different density. A Blue Pill engineer opens ES0340, finds no item about the bug, and concludes the chip is clean. The symptom is a bug that the team cannot reproduce in the sheet they read. The fix is to find the sheet by its exact part title and density.
  5. Copying a register value from an application note without checking the datasheet. The note is correct for its own example. A different clock or a different board may need another value. The symptom is a peripheral that runs at the wrong speed on your board only. The fix is to recompute the value from the datasheet formula, as the worked example did.

In real projects

Professional teams check errata at three points. When they choose a chip, they read the errata for the revision they will buy, and they note any item that touches a block they use. When they bring up a board, they read the items for each block as they enable it, and they record the revision of every board they test. When a peripheral misbehaves, the first question is whether an item matches, before anyone suspects the code.

A good code review expects a workaround to name its erratum, to state the revisions it applies to, and to say when it can be removed. The SDK's comment about RP2040-E1 is a model: it names the item, explains the factor, and sits next to the one place that uses it. A reviewer who sees a magic number such as * 2 in a timer setup should ask which erratum it implements.

Interviewers ask about errata because the answer shows how you handle uncertainty. A strong answer does not claim that the silicon is always right, and does not claim that every odd behaviour is a bug. It describes a process: match the part and the revision, read the item, reproduce the problem with the smallest code, and document the decision. The drill at the end of this lesson uses that process.

Summary

  • An errata sheet lists known differences between the datasheet and the silicon. Treat it as part of the specification.
  • Each item has a Reference, Summary, Description, Workaround, Affects and Fixed by. Read Affects and Fixed by before you act.
  • Revisions differ. The RP2040 has B0, B1 and B2, and the bootrom versions 1, 2 and 3 correspond to them.
  • RP2040-E1 halves the watchdog's effective count. The workaround is to load double the count, which is 2000 per millisecond with a 1 µs tick.
  • The Pico SDK's watchdog_enable() applies the workaround with the named constant WATCHDOG_XFACTOR.
  • The Blue Pill's STM32F103C8 is medium density, so use the medium-density errata sheet, not ES0340.
  • An application note shows one correct circuit or sequence. Check its register values against the datasheet.

Hands-on: read an erratum and check the SDK

This lesson has no Wokwi project, because an errata item describes a chip bug that a simulator does not reproduce. The exercise uses the documents and the SDK source. You can do it on any computer with the Pico SDK 2.3.1 installed.

  1. Open the RP2040 datasheet and go to Appendix B, page 627. Find the block heading "Watchdog" and read the item RP2040-E1 in full.
  2. Write down its Affects and Fixed by values. Expected: Affects B0, B1 and B2, and Fixed by Documentation, Software.
  3. Open src/rp2_common/hardware_watchdog/watchdog.c in the SDK folder (on Windows usually %USERPROFILE%\.pico-sdk\sdk\2.3.1). Search for WATCHDOG_XFACTOR. Expected: a line that reads #define WATCHDOG_XFACTOR 2, with a comment that names RP2040-E1.
  4. Calculate the LOAD value that watchdog_enable(3000) writes, using the formula in the SDK. Expected: 6,000,000. Then check your answer against the quiz below.
Hint for step 4

Multiply 3000 by 1000 to get microseconds, then by the factor 2. Compare with the largest LOAD, 0xFFFFFF, which the SDK clamps to.

Model answer

Check the errata sheet for the exact part and silicon revision, and search the item summaries for the peripheral. If an item matches, read its revision list and workaround, and confirm the batch's revision matches. If no item matches, reproduce the bug with the smallest code you can, check the datasheet's register description, and only then suspect the silicon. Document the revision and the workaround in the code, so the next engineer knows why the odd line is there.
