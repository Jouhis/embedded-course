Errata sheets and application notes

Silicon has bugs, and the vendor writes them down. A firmware engineer who checks the errata before trusting a peripheral saves days of debugging.

By the end of this lesson you can find the errata for an RP2040 or an STM32F103, read one item (its summary, affected revisions and workaround), and decide whether it affects your code.

The idea

An errata sheet lists known differences between what the datasheet says and what the silicon does. Each item has a summary, a description, the silicon revisions it affects, and a workaround, and some are fixed in a later revision. Application notes are the other half: short documents that show how to use a block correctly, such as a recommended circuit or a start-up sequence. Errata are not rare. A reference manual describes the intended design, and the errata describe the gap between it and the manufactured chip. Treat them as part of the specification.

The RP2040 errata: Appendix B of the datasheet

The RP2040 datasheet keeps its errata in Appendix B, grouped by hardware block and numbered within each block. RP2040 datasheet, Appendix B (Errata). A few examples, using the summaries exactly as the datasheet writes them:

ItemBlockSummary
RP2040-E1WatchdogWatchdog count is decremented twice per tick.
RP2040-E5USBUSB device fails to exit RESET state on busy USB bus.
RP2040-E9BootromROM bootloader cannot boot directly into XIP cache-as-SRAM.
RP2040-E14BootromSparse or mis-aligned flash-binary UF2 may not be written to flash correctly.

RP2040-E5 is a real item, but it is about USB, so it matters only if your code uses the USB device. RP2040-E1 is the one most firmware writers meet, because it changes how a watchdog timeout works. The datasheet says it affects B0, B1 and B2 silicon, and that the fix is in the documentation and software, not in hardware.

Read the whole item, not just the summary. The workaround in E1 is one line: "Use double the desired value in LOAD". The workaround is what you apply, and the affected revisions tell you whether it applies to your chip.

Worked example: the watchdog bug

The datasheet's description of RP2040-E1 says the 24-bit counter decrements twice per tick instead of once. In the recommended setup, with a tick every second, this halves the maximum time between watchdog feeds, from about 16.7 seconds to about 8.3 seconds. The workaround is to write double the desired value into the watchdog's LOAD register. For a 5 second timeout with a 1 second tick, you load 10, not 5.

The chip revision matters. The datasheet's bootrom section notes that the bootrom versions 1, 2 and 3 correspond to the B0, B1 and B2 silicon. Check which revision your board has before you assume the workaround applies, and read the "Fixed by" line of each item.

The STM32F103 errata

The ST errata sheet ES0340 covers the high-density parts, the STM32F101xC/D/E and STM32F103xC/D/E. The Blue Pill uses the medium-density STM32F103C8, so ES0340 is the wrong document for it. The medium-density sheet is titled "STM32F10xx8 STM32F10xxB Errata sheet". This course has not yet fetched the current revision from st.com, so download it yourself from the ST documentation page for the STM32F1 series before you rely on any item. The title, not the number, is the reliable way to find it.

Do not assume an errata sheet from a different family applies to your part. The same peripheral name can have different bugs on the F1, the F4 and the RP2040. Match the sheet to the exact part and revision.

Application notes

An application note is a focused document: a circuit, a power sequence, or a peripheral setup. The RP2040 datasheet points to its hardware design guide, "Hardware design with RP2040", for the minimal design example, which uses a 12 MHz crystal (section 2.15.2.2). Use the application notes for the circuit, and use the datasheet and errata for the register behaviour. An application note can be wrong about a register, so check its numbers against the datasheet, the same way you check any other source.

"A peripheral misbehaves on one batch of boards. How do you decide whether it is a silicon bug, and what do you do next?" Answer out loud in 60 seconds, then compare.

Model answer

Check the errata sheet for the exact part and silicon revision, and search the item summaries for the peripheral. If an item matches, read its revision list and workaround, and confirm the batch's revision matches. If no item matches, reproduce the bug with the smallest code you can, check the datasheet's register description, and only then suspect the silicon. Document the revision and the workaround in the code, so the next engineer knows why the odd line is there.
