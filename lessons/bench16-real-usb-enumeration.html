Bench lab 16: Real USB enumeration

Lesson 102 described enumeration on paper. Your Pico 2 has been enumerating as a USB serial port since bench lab 0. Now read its descriptors with your operating system's own tools, change them, and watch the device side of the conversation.

This bench lab is optional. It needs only a Pico 2 and its USB cable. It doesn't count towards your progress. Time: about 40 minutes.
By the end of this lab you can find a USB device's vendor ID, product ID, strings and interfaces with OS tools, change the strings in firmware, and explain when a CDC device counts as "connected".

What the host asks, and where the answers come from

Lesson 102 walked through enumeration: when a device is plugged in, the host resets it, gives it an address, and asks for its descriptors with GET_DESCRIPTOR requests. The device descriptor carries the vendor ID (VID), the product ID (PID) and indexes of three strings: manufacturer, product and serial number. The configuration descriptor lists the interfaces, and a CDC serial port has two: a control interface and a data interface. The operating system picks a driver from those answers.

On the Pico 2, the SDK's pico_stdio_usb library answers all of it, with TinyUSB underneath. Its file stdio_usb_descriptors.c sets the defaults: VID 0x2E8A (Raspberry Pi), PID 0x0009 on the RP2350, manufacturer "Raspberry Pi", product "Pico", and a serial number made from the board's unique flash ID. The strings come from the macros USBD_MANUFACTURER and USBD_PRODUCT, which you can override from CMake.

The simulator can't take part in any of this. Wokwi's Pico 2 model supports USB CDC only in part, and nothing connects the simulated chip to your PC's USB stack, so no descriptor ever reaches your operating system. This lab exists only on the bench, so it has no simulator stage. The program in projects/bench16-usb-enumeration lights the LED while stdio_usb_connected() is true, and logs when that changes and how many milliseconds after boot.

On the board

  1. Flash the starter (BOOTSEL as in bench lab 0). Don't open a terminal yet. The LED is off.
  2. Find the descriptors.
    • Windows: Device Manager → Ports (COM & LPT) → the new port → Properties → Details → "Hardware Ids" shows USB\VID_2E8A&PID_0009. For the full descriptors, Microsoft's USBView shows the device, configuration, interface and endpoint descriptors; it comes with the Windows SDK's Debugging Tools for Windows (Microsoft Learn: USBView).
    • Linux: lsusb lists 2e8a:0009; lsusb -v -d 2e8a:0009 prints the whole tree. dmesg shows the enumeration as it happens.
    • macOS: system_profiler SPUSBDataType, or ioreg -p IOUSB -l.
  3. Write down: VID, PID, manufacturer, product, serial number, the number of interfaces and their class codes. The serial number matches the board's unique ID: two Pico 2 boards on one PC get different serial numbers, which is how the OS keeps their COM port names apart.
  4. Open the port. Start the Serial Monitor on the board's port. The LED lights and the log prints BENCH16 host opened the port N ms after boot. Close the port: the LED goes out.
  5. Task: your own strings. In CMakeLists.txt, add target_compile_definitions(blink PRIVATE USBD_MANUFACTURER="Embedded Course" USBD_PRODUCT="Bench lab 16"). Rebuild, flash, and look the device up again. On Windows, the device may keep its old name in Device Manager until you uninstall it, because Windows caches what it learned about a VID/PID/serial combination; Linux and macOS show the new strings at once.

When is a USB serial port "connected"?

The LED doesn't light at enumeration. It lights when a terminal opens the port. stdio_usb_connected() checks the DTR signal, a flag that the host's terminal program sets in a CDC control request when it opens the port. That's why the SDK's printf drops USB output until a terminal is listening, and why the template waits up to 3 s at start-up for one.

This trips people up: some terminal programs and libraries don't set DTR by default, and then the device thinks nobody is there and sends nothing. The SDK has a switch for that case, PICO_STDIO_USB_CONNECTION_WITHOUT_DTR, which treats an enumerated device as connected. It also means output goes out even when nobody reads it.

Common mistakes

  1. Reusing someone else's VID/PID in a product. 0x2E8A belongs to Raspberry Pi. For a product, you need your own VID (from the USB-IF) or a PID allocated under someone's VID, such as the ones Raspberry Pi assigns under its VID 0x2E8A through an application form (raspberrypi/usb-pid on GitHub).
  2. Expecting output before a terminal opens the port. Without DTR, stdio_usb discards output. Log important start-up state again later, or wait for the connection.
  3. Trusting Windows' displayed name after changing strings. Windows caches device names; check with USBView or reinstall the device.
  4. Calling USB "a serial port with a baud rate". The baud rate in a CDC port is a setting the device may read, but the data moves in USB packets at USB speed.

Summary

  • The SDK's pico_stdio_usb enumerates the Pico 2 as a CDC serial device: VID 0x2E8A, PID 0x0009, two interfaces.
  • OS tools (Device Manager and USBView, lsusb -v, system_profiler) show every descriptor field.
  • USBD_MANUFACTURER and USBD_PRODUCT set the strings; the serial number is the board's unique ID.
  • A CDC port counts as connected when the terminal sets DTR, not at enumeration.
  • Wokwi doesn't connect a simulated USB device to your PC, so enumeration is bench-only.
You've seen enumeration from both ends: the descriptors the host read and the moment the device saw the port open. When a USB device "doesn't show up", you now know which side to check first.
The SDK source file src/rp2_common/pico_stdio_usb/stdio_usb_descriptors.c in your Pico SDK folder: about 200 lines that build the device, configuration and string descriptors you just read with the OS tools. Read it next to your lsusb -v or USBView output.
