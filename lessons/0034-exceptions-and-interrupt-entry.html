Exceptions and interrupt entry

How the core stops a program, saves its state and runs a handler

By the end of this lesson you can list the eight words the core stacks on interrupt entry, trigger an interrupt in the simulator, and read the saved frame and the restored registers after the return.

Events that interrupt the program order

Until now every program in this course has run in one order: main calls a function, the function returns and the next line runs. Lesson 33 showed how a caller and a callee agree on arguments, on the registers that must survive a call and on the stack, and lesson 31 introduced the registers themselves. This lesson adds the one thing that breaks that order, an event that stops the program at any instruction and runs a different function first, changing PC and LR on the program's behalf and writing to the stack.

A 3D printer shows the problem clearly. Each axis has an endstop switch that closes when the carriage reaches the end of its travel, and the firmware must stop the motor at that moment while its main loop is busy planning the next move. If the main loop checks the switch only between moves, the carriage can travel past it before anyone looks. An interrupt solves this, because the hardware calls a short function the moment the pin changes and the main loop never has to ask.

Exceptions, interrupts and the vector table

An exception is an event that makes the core stop what it is doing and run a function called a handler. Reset is an exception, and so are the faults and the system timer. An interrupt is an exception raised by a peripheral or a pin, as when the endstop pin changes state, and its handler is called an interrupt service routine (ISR). In this course handler and ISR mean the same thing when the exception is an interrupt.

The core can run the right handler only if the program tells it which one, so every exception has a number. Exception 11 is SVCall, which lesson 35 uses (DDI0337G, Table 5-1), and the first external interrupt, IRQ0, is exception 16 according to the TRM's exception table, so the STM32F1's EXTI0_IRQn, which the header sets to 6, is exception 22. The vector table is an array in memory listing the address of each handler, indexed by exception number, and on entry the core reads the entry for the exception at

vector address = table base + 4 × exception number(1)

where each entry is one 4-byte word, as Arm's TRM states (Arm Cortex-M3 TRM DDI0337G, §5.5, Table 5-4).

On the STM32F103 the table is written in the startup file, which lists handler names in order so that each name's position is its exception number. .word SVC_Handler is on line 142 of third_party/cmsis-device-f1/Source/Templates/gcc/startup_stm32f103xb.s and .word EXTI0_IRQHandler on line 153. Lesson 42 covers the startup file in full, and for now the point is that the handler's name in the C code must match the name in that list.

A UART at 115 200 baud receives a byte about every 87 µs, since a byte takes 10 bits and 10 ÷ 115 200 bit/s ≈ 87 µs. Its receive register holds only one byte or a few, so the firmware must collect each byte before the next arrives, and polling from the main loop would mean checking more than 11 000 times a second. With the receive interrupt, the core runs a short handler only when a byte is waiting and spends the rest of its time on real work.

The stacked frame

A handler can run at any instruction of the main program, which may be halfway through a calculation with values in R0 to R3. The handler is an ordinary C function and will use those registers for its own work, so if nothing restored them, the main program would resume with the handler's numbers in its registers. The core therefore saves them itself, before the handler's first instruction runs.

It saves a fixed set of eight words, the stacked frame. The TRM names them as the program counter (PC), the status register (xPSR), R0, R1, R2, R3, R12 and the link register (LR), but that is the order of naming rather than of memory: from the lowest address up, the frame holds R0, R1, R2, R3, R12, LR, PC and xPSR (Figure 1). The TRM states that "the SP is decremented by eight words by the completion of the stack push" (DDI0337G §5.5.1), and with four bytes per word the frame takes 32 bytes.

Each word has a reason to be there. PC is the address of the instruction the main program was about to run, so the core can resume there, and xPSR holds the condition flags, the active exception number and the Thumb bit. R0 to R3 and R12 are the registers an AAPCS callee may change (lesson 33), so the hardware saves them on the handler's behalf, and LR is saved because the core is about to overwrite it. R4 to R11 are not in the frame, so a handler that uses one must save it itself, a point the TRM also makes about the kernel, which "only requires to save the eight registers not pushed by hardware, r4-r11" (§5.4). This is why the C compiler saves R4 to R11 in any handler that uses them.

The xPSR is one register made of three parts, and the part that matters here is the Interrupt Program Status Register (IPSR), which according to the TRM "contains the Interrupt Service Routine (ISR) number of the current exception activation" (§2.3.2) in bits [8:0]. While a handler runs, IPSR holds its exception number, and on return the core reads the number back from the stacked xPSR. The T bit is bit 24, and since executing an instruction while it is clear causes an INVSTATE exception (§2.3.2), a return that restored a cleared T bit would fault.

When the phone rings while you are reading, you put a bookmark in, answer, and come back to the exact line. Exception entry is that bookmark: the core pushes the return address and the registers the interrupted code may be using before the handler runs, and on a Cortex-M the hardware places the bookmark itself, so a handler can be a plain C function. Unlike a bookmark, though, the frame saves only part of the state, and R4 to R11 are left for the handler to protect.

EXC_RETURN in the link register

On entry the core also loads LR with a special value called EXC_RETURN, which is not an address: its low four bits say where to return and which stack to use. The TRM's Table 5-6 lists the values that matter here.

EXC_RETURNBits [3:0]Returns toStack after return
0xFFFFFFF10001Handler mode (a nested handler)Main stack
0xFFFFFFF91001Thread modeMain stack
0xFFFFFFFD1101Thread modeProcess stack

A handler ends by loading a value of the form 0xFFFFFFFX into PC, which the TRM allows in three ways: POP or LDM with PC in the list, LDR with PC as the destination, and BX with any register (§5.8.2). In a C project the compiler's own return sequence does this, and in hand-written assembly it is usually BX LR. When the processor sees such a value, it does not branch but treats it as the signal to unstack the frame.

The entry sequence step by step

The TRM's Table 5-4 lists the steps the processor takes before entering an ISR, and reading them in order shows the hardware sequence.

  1. Push the frame. The core pushes the eight words onto the stack the interrupted code was using. This is the first step the TRM lists, and the one that cannot be restarted.
  2. Read the vector. The core reads the handler address from the vector table, a read the TRM says can be restarted if a higher-priority exception arrives. It uses the instruction bus while the frame goes out on the data bus, so the two can overlap.
  3. Set PC and load the pipeline. PC takes the handler address and the pipeline reloads from there, discarding instructions fetched from the interrupted address, as in a pipeline flush.
  4. Set LR. LR takes the EXC_RETURN value, so that the handler's last instruction can return.
  5. Start the handler. IPSR now holds the exception number, and the handler's first instruction enters the execute stage.

Figure 5-2 in the TRM shows the timing of this sequence on a Cortex-M3, with a twelve-cycle latency from the assertion of the interrupt to the execution of the first ISR instruction (DDI0337G §5.5, Figure 5-2). Twelve cycles is the standard case with no other exception in the way, and it is a TRM figure rather than a promise for every chip. The STM32F103 uses the same core, but the bus timing around it can differ, so check your own chip's documentation before relying on the exact count.

  1. Main runs in thread mode. IPSR is 0, meaning no exception is active, and SP is 0x20000100.
  2. An interrupt arrives, IRQ 0, which is exception number 16. The core accepts it between two instructions of main.
  3. The core pushes eight words, the stacked frame: xPSR, PC, LR, R12 and R0 to R3. SP drops 32 bytes to 0x200000E0. Main's half-finished state is now safe.
  4. In parallel the core reads entry 16 of the vector table: the address of the handler.
  5. PC takes the handler address, IPSR becomes 16, and LR is loaded with EXC_RETURN, 0xFFFFFFF9, which means: return to thread mode, on the main stack.
  6. The handler runs as an ordinary C function. It may use R0 to R3 and R12 freely, because the hardware saved them.
  7. bx lr with 0xFFFFFFF9 is not a normal return: the core pops the eight words, SP is back at 0x20000100, IPSR is 0, and main continues at the saved PC as if nothing happened.

Tail-chaining, late arrival and exit

Interrupts often arrive together, and the TRM describes two shortcuts for that case in addition to the normal return path.

  • Tail-chaining (§5.6): when a handler returns while a pending interrupt has higher priority than all stacked exceptions, the core skips the unstacking and restacking and starts the next handler directly. The TRM's Figure 5-3 shows six cycles from the end of one ISR to the start of the next, against twelve for a fresh entry.
  • Late arrival (§5.7): a higher-priority interrupt can take over from one still being entered, provided the earlier handler's first instruction has not yet reached the execute stage, and the state is saved only once, for the first interrupt. The TRM states that a late-arriving exception is not processed until the first instruction of the handler starts to execute (Table 5-4), and after that point the new interrupt is an ordinary pre-emption.
  • Exit (§5.8): when the handler returns through EXC_RETURN, the core unstacks the frame. If the stacked IPSR bits [8:0] are zero, it returns to thread mode, and otherwise to the interrupt that was pre-empted.

The frame is written to the stack the interrupted code was using, the main stack for a plain program, and lesson 35 shows what that means for an RTOS task. Because the frame lives in memory, anything the handler does to R0 to R3 is undone on return, which you will check in the simulator below.

Worked example: a frame at 0x20000100

A program in thread mode is running a loop with SP at 0x20000100 when an interrupt arrives. The register values below are chosen for the arithmetic rather than read from a board: R0 is 3, R1 is 4, R2 is 0, R3 is 9, R12 is 0, LR holds a return address of 0x08000199, PC holds the next instruction, 0x08000244, and xPSR is 0x01000000, with only the T bit set. Before working through it, predict the value of R0 after the handler returns.

  1. Work out the new SP. The frame is eight words of four bytes, 32 bytes or 0x20, so the new SP is 0x20000100 − 0x20 = 0x200000E0, and the frame occupies 0x200000E0 to 0x200000FF.
  2. Write the frame. With the offsets of Figure 1, the words sit at the addresses in the table below.

  1. Load the new state. PC becomes the handler address, LR becomes EXC_RETURN, and the handler runs on the same stack at SP 0x200000E0. Suppose it sets R0 to 99 and writes 1 to a counter in RAM, so that R0 now holds 99.
  2. Return. The handler ends with BX LR, and LR is 0xFFFFFFF9, meaning thread mode on the main stack. The core unstacks the eight words, so R0 becomes 3 again because the frame held 3, PC becomes 0x08000244 so that the loop resumes at the instruction it was about to run, and SP returns to 0x20000100.

R0 is back at the main program's value of 3, while the counter in RAM is 1, because a write to memory is not part of the frame. The program's state is intact, and the handler's one useful result sits in memory where the main loop can read it.

Handler changes to R0 to R3 are undone on return, because the frame restores them. A handler that needs to pass information back must write to memory, such as a variable, a buffer or a peripheral register, since a value left in R0 is lost.

Try it in the CPU simulator

The program loops adding 1 to R1, and its interrupt handler adds 1 to a counter in RAM at 0x20000000. Press IRQ ⚡ while the loop runs; the button appears only because the program defines a label called IRQ_Handler.

  1. Press Run, then Pause after a moment, and note the stack pointer and R1. Predict the SP value after the interrupt is taken; from a starting SP of 0x20000100 the answer is 0x200000E0.
  2. Press IRQ ⚡, then Step until the message says the interrupt was taken. The stack view now shows eight words with SP at 0x200000E0, R0 at the lowest address and, as the seventh word at +0x18, the saved PC, the address of the loop instruction that was about to run.
  3. Press Instruction until the handler returns to the loop, and check that the counter at 0x20000000 is now 1 while R2 and R3 are back at 0 and SP at 0x20000100.
  4. Press IRQ ⚡ a second time and let the handler return, after which the counter should read 2. The memory write survives each return, while the registers the handler used are restored every time.
Hint

The starting SP is 0x20000100 and an eight-word frame is 32 bytes, so the SP after entry is 0x200000E0. The counter lives in memory, which is why it survives the return while R2 and R3 do not.

The program and its C equivalent

The main program has three working lines. MOV R0, #0 sets R0 to zero, a value the program never reads again, included to show that an interrupt restores R0 even when the main program does not use it. MOV R1, #0 sets the counter that the loop increments, ADD R1, R1, #1 adds one to it, and B loop branches back to the add forever; since the branch is a plain jump rather than a call, the loop never touches LR.

The handler has five instructions. MOV R2, #0x20000000 loads the counter's address into R2, written out because the simulator has no variables, whereas a real program would take it from a variable. LDR R3, [R2] reads the word at that address into R3, ADD R3, R3, #1 adds one, and STR R3, [R2] writes the result back. That memory write is the only part of the handler that affects the program's future, because it is the only part the frame does not undo, and BX LR returns through EXC_RETURN, which triggers the unstacking.

A C version of the same handler looks like this. The compiler may use R0 to R3 freely for the work, because the frame restores them, and saves R4 to R11 only if the body needs them. 

volatile uint32_t counter = 0;    /* in SRAM: the value survives the return */

void IRQ_Handler(void) {
    counter = counter + 1;           /* a load, an add and a store, as above */
}

The volatile keyword tells the compiler that the variable can change outside the code it sees, so every access must really take place (glossary: volatile). Lesson 46 covers it in full, and for now the rule is that any variable shared between the main loop and a handler is declared that way.

The simulator is a teaching model of interrupt entry and differs from a real Cortex-M in several ways. It has one interrupt, no priorities and no NVIC, and no vector table, so the handler address is simply a label, and it models neither tail-chaining, late arrival nor the twelve-cycle latency. The stacked frame and the return are the parts that match the real core.

Common mistakes and how to spot them

Each of these mistakes has a symptom visible either in the simulator or in a debugger on the board.

A handler with the wrong name

The program stops working the moment the interrupt fires, and a debugger shows the program counter inside Infinite_Loop. The vector table holds names that the linker connects to functions, so a function called EXTI0_Handler instead of EXTI0_IRQHandler is never referenced, and the startup file's weak alias sends the interrupt to Default_Handler, which is Infinite_Loop: b Infinite_Loop (lines 112 to 116). Copy the name exactly from the startup file and define the handler in C, which does not mangle names.

A handler that returns with a plain branch

The stack view shows SP dropping by 0x20 on every interrupt and never recovering, and on a real board the stack eventually runs into the variables below it. A handler ending in B main_loop seems to work because the main loop runs again, but the TRM states that an ISR completes only when its last instruction loads an EXC_RETURN value into PC (§5.8), so the frame is never popped and the main loop resumes with the handler's registers. End the handler with BX LR in assembly, or write it as a C function and let the compiler return.

A result expected in R0

The main loop never sees a new reading although the handler ran, because the handler wrote its result to R0 and the return undid it, as the warning above describes. Write the result to a volatile variable or a buffer that the main loop reads.

R4 used without being saved

A variable in the main loop changes at random, but only after an interrupt has fired, which makes the bug hard to trace. The hardware does not save R4 to R11, so a hand-written handler that uses R4 without pushing it changes the main program's R4. Push every register the handler uses and pop it before returning, which a C compiler does automatically.

A peripheral flag left set

The main loop barely runs and the handler seems to run all the time. A peripheral keeps its request asserted until the handler clears the flag that caused it, so a flag left set makes the core take the same interrupt again as soon as the handler returns. The header names the flags, for example EXTI_PR_PR0, the pending bit for line 0 in stm32f103xb.h. Find the clearing action for that flag in the peripheral manual and perform it in the handler, checking the method first, because some flags clear by writing a 1 and others in a different way.

Interrupt handlers in production firmware

Professional firmware keeps ISRs short. A typical handler reads the data from the peripheral, stores it in a buffer, sets a flag and returns, leaving slow work such as parsing a message or updating a display to the main loop or a task. A code reviewer checks that the handler name matches the vector table, that every variable shared with the main code is volatile, that the handler clears the flag that raised it, and that it never waits, since a delay or a call that waits on a peripheral inside an ISR stops the main program until the handler ends.

The same entry sequence supports an RTOS, whose kernel switches tasks through an exception so that the work happens at a known point. Lesson 35 covers the privilege and stack rules that make this safe, and lesson 88 builds a context switch on the same mechanism. The TRM's table of exception types lists PendSV as a "software pend request", the usual way for a kernel to request a switch (DDI0337G, the exception type table).

Summary

  • An exception stops the program and runs a handler, and an interrupt is an exception raised by a peripheral or a pin.
  • The vector table maps each exception number to a handler address, and on the STM32F1 the handler names are in the startup file.
  • On entry the core pushes eight words, from the lowest address R0, R1, R2, R3, R12, LR, PC and xPSR, and leaves R4 to R11 unsaved.
  • LR is loaded with EXC_RETURN, and a handler returns by loading that value into PC, which triggers the unstacking; a plain branch does not return.
  • The TRM shows twelve cycles from the interrupt to the first ISR instruction, and six for a tail-chained handler.
  • Changes to R0 to R3 are undone on return, so a handler passes its results through memory.
  • A handler must have the right name, clear the flag that raised it and save any register it uses beyond the frame.
