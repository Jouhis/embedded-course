Exceptions and interrupt entry

An interrupt does not ask the program for permission. The core saves eight registers on the stack by itself, and the handler runs before the next line of your main loop. Watching that happen is the best way to understand interrupts.

By the end of this lesson you can list the eight words the core stacks on interrupt entry, trigger an interrupt in the simulator, and read the saved frame and the restored registers after the return.

The idea

An exception is an event that makes the core stop its current code and run a handler. An interrupt is an exception raised by a peripheral or a pin. On entry the core does three things in hardware: it pushes a frame of eight words onto the stack, it loads LR with a special value that tells it how to return, and it jumps to the handler. Your code does none of this.

Arm's TRM gives the frame: "the processor automatically stores the following eight registers to the SP", which are the program counter, xPSR, R0 to R3, R12 and LR (Arm Cortex-M3 TRM DDI0337G, §5.5.1). The TRM's Figure 5-1 shows the order on the stack. The simulator uses the usual layout, with R0 at the lowest address and xPSR at the highest. Check that against Figure 5-1 when you use the TRM. The TRM describes a configuration bit, STKALIGN, that can insert one padding word so that the stack is 8-byte aligned before the frame is stacked (§5.5.1). The simulator never adds that word.

Latency, return and the other cases

The TRM's exception entry timing figure shows a twelve-cycle latency from asserting the interrupt to the first instruction of the ISR (DDI0337G, §5.5 and Figure 5-2). That is the entry timing for the standard case. The three cases below change the sequence.

  • Tail-chaining (§5.6): when one handler finishes and another interrupt is already pending, the core starts the next handler without restoring and saving the frame again. The TRM calls it "back-to-back interrupt processing without the overhead of state saving and restoration".
  • Late arrival (§5.7): a higher-priority interrupt that arrives while the core is still stacking takes over. The stacking is kept, and the new handler runs first.
  • Return: the handler returns with a special EXC_RETURN value in LR, using BX LR or a POP {..., PC}. The core then unstacks the frame and restores the registers. The TRM's exit section (§5.8) says that when the stacked IPSR's active-interrupt bits [8:0] are zero, the processor returns to thread mode.

Exceptions always stack on the main stack (§2.2.1, and lesson 35). The frame lives in memory, so anything the handler changes in R0 to R3 is restored on return. This is the most useful fact of the lesson, and you will see it in the simulator below.

Handler changes to R0 to R3 are undone on return, because the frame restores them. A handler that wants to pass information back must write to memory, such as a variable, a buffer or a peripheral register. Writing to R0 in the handler is lost.

Try it in the CPU simulator

The program loops, adding 1 to R1. Its interrupt handler adds 1 to a counter in RAM at 0x20000000. Press IRQ ⚡ while the loop runs. The button only appears because the program defines a label called IRQ_Handler.

  1. Press Run, then Pause after a moment. Note the stack pointer and R1. Predict the SP value after the interrupt is taken.
  2. Press IRQ ⚡, then Step until the message says the interrupt was taken. Check the stack view: eight words are now on the stack. Find the saved PC, which is the address of the loop instruction that was about to run.
  3. Press Instruction until the handler returns to the loop. Check that the counter at 0x20000000 is now 1, while R2 and R3 are back to 0 and the SP is back at its starting value.
Hint

The starting SP is 0x20000100, and an eight-word frame is 32 bytes, so the SP after entry is 0x200000E0. The counter lives in memory, which is why it survives the return even though R2 and R3 do not.

The simulator is a teaching model of interrupt entry, and it differs from a real Cortex-M in the following ways. It has one interrupt, no priorities and no NVIC. It has no vector table, so the handler address is simply a label. It does not model tail-chaining or late arrival, and it does not model the twelve-cycle latency. The stacked frame and the return are the parts that match the real core.

You triggered an interrupt, read the eight-word frame on the stack, and showed that a handler's register changes are undone while its memory writes are kept.

"Walk me through what the Cortex-M does between an interrupt line going high and the first line of the ISR running." Answer out loud in 60 seconds, then compare.

Model answer

The core finishes or abandons the current instruction, then stacks eight words (PC, xPSR, R0 to R3, R12, LR) onto the stack. It loads LR with the EXC_RETURN value and fetches the handler address from the vector table. On the M3 this takes twelve cycles to the first ISR instruction. Tail-chaining and late arrival change that sequence when interrupts pile up. The handler then runs, and a return through EXC_RETURN unstacks the frame.
