Exceptions and interrupt entry

An interrupt does not wait for the program to allow it. The core saves eight registers on the stack by itself, and the handler runs before the next line of your main loop. Watching this happen makes the sequence concrete.

By the end of this lesson you can list the eight words the core stacks on interrupt entry, trigger an interrupt in the simulator, and read the saved frame and the restored registers after the return.

Where we are and why it matters

Until now every program in this course has run in one order. main calls a function, the function returns, and the next line runs. Lesson 33 showed how a caller and a callee agree on arguments, on which registers must survive a call, and on the stack. This lesson adds the one thing that breaks that order: an event that stops the program at any instruction and runs a different function first. Lesson 31 introduced the registers the core uses, and this lesson depends on them. An interrupt changes PC and LR on your behalf, and it writes to the stack.

Here is the problem in a real product. A 3D printer has an endstop switch on each axis. The switch closes when the carriage reaches the end of its travel, and the firmware must stop the motor at that moment. The firmware is also busy planning the next move in its main loop. If the main loop checks the switch only between moves, the carriage can travel past the switch before anyone looks. An interrupt solves this. The hardware calls a short function the moment the pin changes, and the main loop never has to ask.

The concepts, one at a time

Exceptions and interrupts

An exception is an event that makes the core stop what it is doing and run a function called a handler. Reset is an exception, and so are the faults and the system timer. An interrupt is an exception raised by a peripheral or by a pin. The endstop switch raises an interrupt when its pin changes state. A handler for an interrupt is called an interrupt service routine (ISR). In this course the words handler and ISR mean the same thing when the exception is an interrupt.

The core cannot know which handler to run unless the program tells it. Every exception has a number. Exception 11 is SVCall, which lesson 35 uses (DDI0337G, Table 5-1). The first external interrupt, IRQ0, is exception 16 (the TRM's exception table lists it), so the STM32F1's EXTI0_IRQn, which the header sets to 6, is exception 22. The vector table is an array in memory that lists the address of each handler, indexed by its exception number. On entry the core reads the table entry for the exception. Arm's TRM gives the address as the table base plus four times the exception number (Arm Cortex-M3 TRM DDI0337G, §5.5, Table 5-4).

On the STM32F103 the table is written in the startup file. The file lists handler names in order, so the position of a name is its exception number. .word SVC_Handler is on line 142 of third_party/cmsis-device-f1/Source/Templates/gcc/startup_stm32f103xb.s, and .word EXTI0_IRQHandler is on line 153. Lesson 42 covers the startup file in full. For now, note that the handler's name in your C code must match the name in that list.

Why the core saves registers for you

A handler can run at any instruction of the main program. The main program may be halfway through a calculation with values in R0 to R3. The handler is an ordinary C function, and it will use those registers for its own work. If nothing put the values back, the main program would resume with the handler's numbers in its registers. So the core does the saving itself, before the handler's first instruction runs.

The core saves a fixed set of eight words, called the stacked frame. The TRM lists them in this order: the program counter (PC), the status register (xPSR), R0, R1, R2, R3, R12 and the link register (LR). That is the order the TRM names them in, not their order in memory: from the lowest address up, the frame holds R0, R1, R2, R3, R12, LR, PC and xPSR (Figure 1). The TRM says that "the SP is decremented by eight words by the completion of the stack push" (DDI0337G §5.5.1). Each word is four bytes, so the frame takes 32 bytes.

Each word in the frame has a reason to be there. PC is the address of the instruction the main program was about to run, so the core can resume there. xPSR holds the condition flags, the exception number that is active and the Thumb bit. R0 to R3 and R12 are the registers that an AAPCS callee is allowed to change (lesson 33), so the hardware saves them for the handler. LR is saved because the core is about to overwrite it. The registers R4 to R11 are not in the frame. A handler that uses one of them must save it. The TRM makes the same point when it describes the kernel: it "only requires to save the eight registers not pushed by hardware, r4-r11" (§5.4). This is why the C compiler saves R4 to R11 in a handler that uses them.

The xPSR is one register made of three parts, and the part that matters here is the Interrupt Program Status Register (IPSR). The TRM says that the IPSR "contains the Interrupt Service Routine (ISR) number of the current exception activation" (§2.3.2). It is the bits [8:0] of xPSR. While a handler runs, IPSR holds that handler's exception number, and when the handler returns, the core reads the number back from the stacked xPSR. The T bit is bit 24. The TRM says that executing an instruction while the T bit is clear causes an INVSTATE exception (§2.3.2), so a return that restores a cleared T bit would fault.

The return value in LR

On entry the core also loads LR with a special value called EXC_RETURN. It is not an address. The low four bits say where to return and which stack to use. The TRM's Table 5-6 lists the values that matter here.

0xFFFFFFF10001Handler mode (a nested handler)Main stack

A handler ends by loading a value of the form 0xFFFFFFFX into PC. The TRM lists three ways to do it: POP or LDM with PC in the list, LDR with PC as the destination, and BX with any register (§5.8.2). The most common one in a C project is the compiler's own return sequence, and in hand-written assembly it is BX LR. When the processor sees the value, it does not branch. It treats the value as the signal to unstack the frame.

What the core does, in order

The TRM's Table 5-4 lists the steps the processor takes before it enters an ISR. Read them in order to follow the hardware sequence.

  1. Push the frame. The core pushes the eight words onto the stack that the interrupted code was using. This is the first step the TRM lists, and it is the one that cannot be restarted.
  2. Read the vector. The core reads the handler address from the vector table. The TRM says this read can be restarted if a higher-priority exception arrives. The read uses the instruction bus while the frame is written on the data bus, so the two can overlap.
  3. Set PC and load the pipeline. PC takes the handler address, and the pipeline reloads from there. Instructions that were fetched from the interrupted address are discarded, as in a pipeline flush.
  4. Set LR. LR takes the EXC_RETURN value, so the handler's last instruction can return.
  5. Start the handler. IPSR now holds the exception number, and the handler's first instruction enters the execute stage.

Figure 5-2 in the TRM shows the timing of this sequence on a Cortex-M3. It shows a twelve-cycle latency from the moment the interrupt is asserted to the moment the first ISR instruction executes (DDI0337G §5.5, Figure 5-2). Twelve cycles is the standard case, with no other exception in the way. The number is a figure from the TRM, not a promise for every chip. The STM32F103 uses the same core, but the bus timing around it can differ, so check the timing in your own chip's documentation before you rely on the exact count.

Three cases that change the sequence

Interrupts often arrive together, and the TRM describes two shortcuts for that case, plus the return path.

  • Tail-chaining (§5.6): when a handler returns and a pending interrupt has higher priority than all stacked exceptions, the core skips the unstacking and the stacking. It starts the next handler directly. The TRM's Figure 5-3 shows six cycles from the end of one ISR to the start of the next, compared with twelve for a fresh entry.
  • Late arrival (§5.7): a higher-priority interrupt can take over from one that is still being entered, as long as the first instruction of the earlier handler has not yet reached the execute stage. The state is saved once, for the first interrupt. The TRM says that a late-arriving exception is not processed until the first instruction of the handler starts to execute (Table 5-4). After that point, the new interrupt is a normal pre-emption.
  • Exit (§5.8): when the handler returns through EXC_RETURN, the core unstacks the frame. If the stacked IPSR bits [8:0] are zero, the core returns to thread mode. Otherwise it returns to the interrupt that was pre-empted.

The frame is written to the stack the interrupted code was using, which is the main stack for a plain program. Lesson 35 shows what that means for an RTOS task. Because the frame lives in memory, anything the handler does to R0 to R3 is undone on return. You will check this in the simulator below.

Handler changes to R0 to R3 are undone on return, because the frame restores them. A handler that wants to pass information back must write to memory, such as a variable, a buffer or a peripheral register. Writing to R0 in the handler is lost.

A worked example with real numbers

Take a program in thread mode with SP at 0x20000100. It is in a loop, and an interrupt arrives. Assume these values at the moment of the interrupt. These are example values, chosen for the arithmetic, not readings from a board: R0 is 3, R1 is 4, R2 is 0, R3 is 9, R12 is 0, LR holds a return address of 0x08000199, PC holds the next instruction, 0x08000244, and xPSR is 0x01000000, which has only the T bit set.

  1. Work out the new SP. The frame is eight words of four bytes each, which is 32 bytes, or 0x20. The new SP is 0x20000100 − 0x20 = 0x200000E0. The frame occupies addresses 0x200000E0 to 0x200000FF.
  2. Write the frame. Using the offsets from Figure 1, the words sit at these addresses:

0x200000E0+0x00R00x00000003
0x200000E4+0x04R10x00000004
0x200000E8+0x08R20x00000000

0x200000F4+0x14LR0x08000199
0x200000F8+0x18PC0x08000244
0x200000FC+0x1CxPSR0x01000000
  1. Load the new state. PC becomes the handler address, LR becomes EXC_RETURN, and the handler runs on the same stack at SP 0x200000E0. Suppose the handler sets R0 to 99 and writes 1 to a counter in RAM. R0 now holds 99.
  2. Return. The handler's last instruction is BX LR, and LR is 0xFFFFFFF9, which is thread mode on the main stack. The core unstacks the eight words. R0 becomes 3 again, because the frame held 3. PC becomes 0x08000244, and the loop resumes at the instruction it was about to run. SP returns to 0x20000100.

R0 is back to 3, which is the value the main program had, and the counter in RAM is 1, because a write to memory is not part of the frame. The program's state is correct, and the handler's one useful result is in memory where the main loop can read it.

Try it in the CPU simulator

The program loops, adding 1 to R1. Its interrupt handler adds 1 to a counter in RAM at 0x20000000. Press IRQ ⚡ while the loop runs. The button only appears because the program defines a label called IRQ_Handler.

  1. Press Run, then Pause after a moment. Note the stack pointer and R1. Predict the SP value after the interrupt is taken. With the starting SP at 0x20000100, the answer is 0x200000E0.
  2. Press IRQ ⚡, then Step until the message says the interrupt was taken. Check the stack view: eight words are now on the stack and SP reads 0x200000E0. The word at the lowest address is R0. The saved PC, the seventh word at +0x18, is the address of the loop instruction that was about to run.
  3. Press Instruction until the handler returns to the loop. Check that the counter at 0x20000000 is now 1, while R2 and R3 are back to 0 and the SP is back at 0x20000100.
  4. Press IRQ ⚡ a second time and let the handler return. The counter should read 2. The memory write survives each return, while the registers it used are restored every time.
Hint

The starting SP is 0x20000100, and an eight-word frame is 32 bytes, so the SP after entry is 0x200000E0. The counter lives in memory, which is why it survives the return even though R2 and R3 do not.

Line by line

The main program has three lines that do work. MOV R0, #0 sets R0 to zero. The program never reads it again, and it is there to show that an interrupt will restore R0 even though the main program does not use it. MOV R1, #0 sets the counter that the loop increments. ADD R1, R1, #1 adds one to R1, and B loop branches back to the add, which runs forever. The branch is a plain jump, not a call, so the loop never touches LR.

The handler has five instructions. MOV R2, #0x20000000 loads the address of the counter into R2. In a real program this address would come from a variable, but the simulator has no variables, so the address is written out. LDR R3, [R2] reads the word at that address into R3. ADD R3, R3, #1 adds one, and STR R3, [R2] writes the result back to the same address. The memory write is the only part of the handler that changes the program's future, because it is the only part the frame does not undo. BX LR returns through EXC_RETURN, which is what triggers the unstacking.

A C version of the same handler would look like this. The compiler is free to use R0 to R3 for the work, because the frame restores them, and it will save R4 to R11 only if the body needs them. 

volatile uint32_t counter = 0;    /* in SRAM: the value survives the return */

void IRQ_Handler(void) {
    counter = counter + 1;           /* a load, an add and a store, as above */
}

The volatile keyword tells the compiler that the variable can change outside the code it sees, and that every access must really happen (glossary: volatile). Lesson 46 covers it in full. For this lesson, note that a variable shared between the main loop and a handler should always be declared that way.

The simulator is a teaching model of interrupt entry, and it differs from a real Cortex-M in the following ways. It has one interrupt, no priorities and no NVIC. It has no vector table, so the handler address is simply a label. It does not model tail-chaining or late arrival, and it does not model the twelve-cycle latency. The stacked frame and the return are the parts that match the real core.

Common mistakes and how to spot them

Each of these mistakes has a symptom you can see, either in the simulator or in a debugger on the board.

1. The handler has the wrong name

The vector table holds names, and the linker connects each name to the function with that name. If your function is called EXTI0_Handler instead of EXTI0_IRQHandler, nothing in the table points to it. The startup file gives every handler a weak alias to Default_Handler, and that function is Infinite_Loop: b Infinite_Loop (lines 112 to 116). The symptom is that the program stops working the moment the interrupt fires. In a debugger the program counter sits inside Infinite_Loop. The fix is to copy the name from the startup file exactly, and to define the handler in C, which does not mangle names.

2. The handler returns with a plain branch

A handler that finishes with B main_loop looks like it works, because the main loop runs again. The TRM says the ISR is complete only when the last instruction loads an EXC_RETURN value into PC (§5.8). With a plain branch, the frame is never popped. SP falls by 32 bytes each time the interrupt fires, and the main loop resumes with the handler's registers. The symptom in the simulator is the stack view: SP drops by 0x20 on each interrupt and never comes back. On a real board the stack eventually runs into the variables below it. The fix is to end the handler with BX LR in assembly, or to write it as a C function and let the compiler return.

3. The handler expects a return value in R0

The warning above describes this one. A handler that writes a result to R0 has its change undone, so the caller sees the old value. The symptom is a main loop that never sees the new reading, even though the handler ran. The fix is to write to a volatile variable or a buffer that the main loop reads.

4. A hand-written handler uses R4 without saving it

The hardware does not save R4 to R11. A handler that uses R4 without pushing it changes the main program's R4. The bug shows up later, in the main code, and only after an interrupt has fired, which makes it hard to trace. The symptom is a variable in the main loop that changes at random. The fix is to push every register the handler uses, and to pop it before the return. In C the compiler does this for you.

5. The handler does not clear the peripheral's flag

A peripheral keeps its request asserted until the handler clears the flag that caused it. If the flag stays set, the core takes the same interrupt again as soon as the handler returns. The main loop barely runs, and the handler appears to run all the time. The header names the flags. For example, EXTI_PR_PR0 is the pending bit for line 0, defined in stm32f103xb.h. The fix is to read the peripheral manual, find the clearing action for that flag, and do it at the start or end of the handler. Check the peripheral manual before you rely on the clearing method, because some flags clear by writing a 1 and others clear in a different way.

In real projects

Professional firmware keeps ISRs short. A typical handler reads the data from the peripheral, stores it in a buffer, sets a flag, and returns. The main loop or a task does the slow work, such as parsing a message or updating a display. A code reviewer looks for four things: that the handler name matches the vector table, that any variable shared with the main code is volatile, that the handler clears the flag that raised it, and that the handler never waits. A call to a delay or to a function that waits on a peripheral inside an ISR is an error, because the main program cannot run again until the handler ends.

The same entry sequence supports an RTOS. When the kernel switches tasks, it uses an exception to do the work at a known point. Lesson 35 covers the privilege and stack rules that make this safe, and lesson 88 builds a context switch on the same mechanism. The TRM's table of exception types lists PendSV as a "software pend request", which is the usual way a kernel asks for a switch (DDI0337G, the exception type table).

Summary

  • An exception stops the program and runs a handler. An interrupt is an exception raised by a peripheral or a pin.
  • The vector table maps each exception number to a handler address. On the STM32F1 the names are in the startup file.
  • On entry the core pushes eight words onto the stack. From the lowest address up, they are R0, R1, R2, R3, R12, LR, PC and xPSR. Registers R4 to R11 are not pushed.
  • LR is loaded with EXC_RETURN. A handler returns by loading that value into PC, which triggers the unstacking. A plain branch does not return.
  • The TRM shows twelve cycles from the interrupt to the first ISR instruction, and six cycles for a tail-chained handler.
  • Changes to R0 to R3 are undone on return, so a handler passes results through memory.
  • A handler must have the right name, clear the flag that raised it, and save any register it uses beyond the frame.
