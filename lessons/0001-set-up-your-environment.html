The idea

Firmware is not written and run on the same machine. You type C on your Windows PC, but the code has to run on an Arm Cortex-M chip. So the PC runs a cross-compiler, a compiler that runs on one kind of processor and produces machine code for another. The Arm GNU toolchain is one, and it produces an ELF file, which holds the firmware along with symbols and debug information. The Pico SDK book describes the same flow: CMake drives the compiler and linker, and the result is a firmware image for the RP2040.

The chain has three stages. The compiler turns each .c file into an object file, one file at a time. It cannot see the other files, so the call to a function defined elsewhere stays unresolved. The linker reads all the object files and the libraries, resolves those calls, places every piece at an address from the linker script, and writes one ELF file. A build system (here CMake with Ninja) decides which of those commands to run, and in what order. Raspberry Pi Pico C/C++ SDK book

Once you have an ELF file, two more kinds of tool take over. A simulator runs the ELF on a virtual chip. A debugger attaches to the running program and sets breakpoints. This course uses Wokwi as the simulator, and the Arm GDB debugger through VS Code's Cortex-Debug extension. A logic analyzer records signal edges on pins, and a viewer such as PulseView decodes them into protocols. Wokwi runs the ELF file directly, which is why the template turns off the Pico UF2 converter.

Install the tools

Shortcut: setup.cmd (Windows) or ./setup.sh (macOS, Linux) in the course folder does every install in this lesson for you and test-builds the templates. Read on anyway: you should know what each tool is for, and an interviewer may ask.

Open PowerShell for each step. Commands are copy-paste ready. Do all six steps, then run the check in step 6.

  1. Install VS Code from code.visualstudio.com. Then install its extensions from the command line: 
    code --install-extension wokwi.wokwi-vscode
code --install-extension ms-vscode.cpptools
code --install-extension marus25.cortex-debug
# Optional:
code --install-extension ms-vscode.cmake-tools
  2. Install the build and version-control tools with winget. Each package is installed by its exact ID: 
    winget install -e --id Arm.GnuArmEmbeddedToolchain
winget install -e --id Ninja-build.Ninja
winget install -e --id Kitware.CMake
winget install -e --id Git.Git
winget install -e --id Python.Python.3.13
winget install -e --id Sigrok.PulseView
winget install -e --id BrechtSanders.WinLibs.POSIX.UCRT
winget install -e --id Cppcheck.Cppcheck
    The Arm toolchain installs version 14.2 to C:\Program Files (x86)\Arm GNU Toolchain arm-none-eabi\14.2 rel1\bin, which is where the build tools look for it. The last two are for your PC, not the microcontroller: WinLibs is a MinGW-w64 GCC that compiles programs for Windows itself. The Pico SDK uses it to build its PIO assembler (lesson 65), and you use it to run unit tests on your PC (lesson 80). Cppcheck is a static analyser (lesson 83).
  3. Clone the Pico SDK, version 2.3.1, into your home folder. Then fetch the one submodule that the build needs: 
    git clone --depth 1 -b 2.3.1 https://github.com/raspberrypi/pico-sdk "$HOME\.pico-sdk\sdk\2.3.1"
cd "$HOME\.pico-sdk\sdk\2.3.1"
git submodule update --init --depth 1 lib/tinyusb
cd "$HOME\embedded-course"
    If you keep the course somewhere other than %USERPROFILE%\embedded-course, change the last cd to your folder.
  4. Request your Wokwi license. In VS Code, press F1, then choose Wokwi: Request a New License. A browser window opens. Sign in to a free Wokwi account, confirm, and VS Code shows License activated. The license is a personal license for 30 days. It is free for open-source projects; commercial use needs a paid license. The docs do not describe renewal, so when it expires, run the same command again and check the Wokwi license page.
    Source: Wokwi for VS Code: getting started, and the Wokwi license page.
  5. Optional for automated checks: set up the Wokwi CLI. You need a CI token from the Wokwi dashboard. Save it once, then put the CLI where the course tools look for it. Download wokwi-cli from the wokwi-cli releases page and save it as %USERPROFILE%\.wokwi\bin\wokwi-cli.exe: 
    setx WOKWI_CLI_TOKEN "<your token>"
New-Item -ItemType Directory -Force "$HOME\.wokwi\bin"
Move-Item "$HOME\Downloads\wokwi-cli.exe" "$HOME\.wokwi\bin\wokwi-cli.exe"
    The check in step 6 also looks for wokwi-cli.exe, so it shows MISSING until this file is in place. setx takes effect in new terminals only.
  6. Verify everything. Open a new PowerShell window, so it picks up the new PATH entries, and run the check in the course folder: 
    cd "$HOME\embedded-course"
python tools/build.py --check
    Every line should start with [OK. The Zephyr line may say MISSING. That is expected: Zephyr is set up in lesson 92.
Troubleshooting
  • A tool says MISSING right after you installed it. Close the terminal and open a new one. Installers change PATH, and only new terminals read the new PATH.
  • winget says the package is already installed. That is fine. It means the tool is there, and you can continue.
  • code is not recognised. Open a new terminal first. If it still fails, reinstall VS Code and keep the option that adds VS Code to PATH.
  • The Wokwi CLI line says MISSING. Finish step 5, then open a new terminal and run the check again.
  • The Pico SDK line says MISSING. The clone must end up in %USERPROFILE%\.pico-sdk\sdk\2.3.1, which must contain pico_sdk_init.cmake. Re-run step 3 if it does not.

"What does the linker do that the compiler cannot, and why does it matter for a firmware build?" Answer out loud in 60 seconds, then compare.

Model answer

The compiler translates one translation unit at a time, so it can only emit references to symbols defined elsewhere. The linker reads all object files and libraries, resolves those references, assigns every section an address from the linker script, and writes one image. That is why an undefined reference error shows up at link time, not compile time, and why the linker script decides where code and data sit in flash and RAM.
