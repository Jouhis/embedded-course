The tools that build, run and debug firmware

By the end of this lesson you can run python tools/build.py --check in the course folder, see every required line marked OK, and say what each tool on that list does.

From a C program on a PC to firmware on a chip

This is the first lesson, so it assumes nothing from the course. You need a Windows 11 PC (the course is written for it; macOS and Linux work through setup.sh), a web browser, an internet connection and some patience, since the installers download several hundred megabytes. You already know C, so the real question is how a program written on a PC ends up running on a small chip that has no keyboard, no screen and no operating system.

Closing that gap takes a whole toolchain, and every later lesson depends on it. When you change a timer or an interrupt in lesson 57, the change only matters if the build, the simulator and the debugger still work. A broken tool tends to surface as a confusing error several lessons later, far from its cause, and firmware teams can lose days to the same problem. This lesson therefore explains what each tool is for, so that when one fails you know where to look.

The host and the target

Every embedded project involves two computers, and keeping them apart is the first skill. The host is the computer you sit at, here a Windows PC, which runs VS Code, the compiler, the linker and the simulator. The target is the chip the firmware runs on. In this course it is a Raspberry Pi Pico, whose RP2040 chip has CPU cores from Arm's Cortex-M0+ family. Since your PC has a completely different processor, the two cannot share machine code.

Machine code is the binary instructions a processor executes, and each processor family has its own instruction set. A normal compiler on your PC therefore produces code that a Cortex-M0+ cannot execute. What you need instead is a cross-compiler, a compiler that runs on the host but produces machine code for the target. The Arm GNU toolchain, installed as arm-none-eabi-gcc, is one. Its name describes the target: arm for the processor family, none for no operating system, and eabi for the embedded binary interface, which defines how functions pass arguments on that processor.

The two computers also differ in what they have. Your PC has gigabytes of memory, a file system and an operating system, whereas the Pico has a few hundred kilobytes of memory and runs only the code you load into it. The host consequently does all the heavy work, and the target only runs the finished result. Every tool in this lesson either runs on the host to make the firmware, or runs on the host to imitate or observe the target.

Compiling source files into object files

Building firmware happens in stages, each with one job. The first stage is the compiler, which reads one .c file, checks the C and writes an object file with the extension .o. The object file holds the machine code for the functions in that one source file. It also holds a symbol table, a list of the names the file defines, such as main, and the names it uses without defining, such as gpio_put.

The compiler works on one file at a time for a good reason. It does not know where the other files are or which addresses the final program will use. When main.c calls a function that lives in the Pico SDK, the compiler cannot write that function's real address, so it writes a placeholder and records the name as unresolved. The same design means that changing main.c only requires that one file to be compiled again, which is why a large firmware build can finish in seconds.

It follows that an object file is not yet a program. Its code still contains those placeholders, so it cannot be loaded onto the Pico as it is.

Linking object files into one program

The second stage is the linker. It reads every object file it is given, together with the libraries they use, and does four jobs: it matches each unresolved name with its definition in another file, places every piece of code and data at an address, writes the result as one file, and reports any name it cannot match.

Think of a book written by several authors. Each writes a chapter alone and leaves gaps such as "see the table on page ?", because nobody knows the final page numbers yet. That is the compiler: one chapter, one object file. The linker binds the chapters, numbers the pages and fills in every gap, and a chapter that points to a table nobody wrote makes the binding fail with an undefined reference error. The comparison stops at memory, since the linker also decides which pieces go into flash and which into RAM, and a book has nothing like that.

We can follow the call from main.c through both stages. The compiler emits a call to gpio_put with a placeholder address and an unresolved symbol. The linker then finds gpio_put defined in an object file built from the SDK's GPIO code, places that code in the program, works out its real address and patches the placeholder. Only the linker can do this, because only the linker sees all the object files at once. This is why a missing function is reported at link time and not at compile time.

Where each piece ends up is determined by a linker script. This text file names the memory regions of the chip, such as flash, where the program is stored and runs from, and RAM, where variables live while the program runs, and it states which sections of the program go into each region. The Pico SDK supplies its own script at src/rp2040/pico_platform/memmap_default.ld. You rarely need to edit it, but it is worth knowing that it exists, because you write one yourself in lesson 68.

The linker writes an ELF file, named blink.elf in this course. ELF stands for Executable and Linkable Format, a standard layout that holds the machine code and data in named sections, together with a symbol table and, when the build asks for it, debug information that maps machine addresses back to lines of your C. A debugger relies on that information to show variable names and to stop at line 20 of main.c. Some boards are programmed from a plain .bin file, which holds only the raw bytes. The Pico SDK can also produce a UF2 file for drag-and-drop flashing, but the course turns it off, since Wokwi runs the ELF directly; the template's CMakeLists.txt does this by setting PICO_NO_PICOTOOL to 1.

  1. main.c calls gpio_put(25, 1). The function is not in this file: it is in the Pico SDK.
  2. The compiler turns main.c into main.o. It emits the call instruction, but it cannot know where gpio_put will live, so the address is a placeholder and the name is listed as unresolved.
  3. The SDK's GPIO code was compiled the same way into its own object file, gpio.o. That file defines gpio_put.
  4. The linker reads every object file at once, and the linker script tells it where flash and RAM are.
  5. The linker places gpio_put at an address in flash and patches the placeholder in main.o's call with it. Only the linker can do this, because only the linker has all the files.
  6. The result is one file, blink.elf: the machine code, a symbol table and debug information. Wokwi runs it and GDB reads it.
  7. If gpio.o is not linked, every file still compiles, and the linker stops with undefined reference to `gpio_put'. A missing function is a link error, not a compile error.

The build system: CMake and Ninja

A real project has many source files, flags and libraries, so nobody runs the compiler and linker by hand. A build system does it instead. The course uses CMake to describe the project and Ninja to run the commands. You describe the project once in CMakeLists.txt, giving its name, its source files and the libraries it links. CMake reads that file and writes build.ninja, which lists every compile and link command in order, and Ninja then runs them.

Ninja compares the time each source file was changed with the time its object file was made, and skips every command whose inputs have not changed. It can also run independent compile commands in parallel. You can see the result in each project's solution/build folder, which holds build.ninja, a CMakeCache.txt with the settings CMake found, and finally blink.elf. Since the folder is output and not source, you can delete it at any time and the next build recreates it.

Libraries and the Pico SDK

Your program calls gpio_put, stdio_init_all and sleep_ms, none of which belongs to the C language. They come from the Pico SDK, a library written by the chip's maker, Raspberry Pi, that wraps the chip's hardware registers in C functions. The course pins the SDK to version 2.3.1, so you get the same source and the same functions every time. Pinning matters because a newer SDK may rename a function or change a default, and a project that worked last week would then stop building for a reason you did not cause.

CMake finds the SDK through an environment variable, a named value that the operating system passes to every program it starts. The variable is PICO_SDK_PATH, and the course's build tools set it to %USERPROFILE%\.pico-sdk\sdk\2.3.1 if it is not already set. Inside that folder, external/pico_sdk_import.cmake is how each project connects to the SDK, and pico_sdk_init.cmake is the file the build tool looks for when it reports the SDK as present.

The SDK in turn depends on other libraries. One of them is TinyUSB, which provides USB serial, and the SDK keeps it in a git submodule, a separate repository stored inside another one at a fixed commit. A plain clone does not download submodules, so the setup fetches TinyUSB explicitly. It fetches only that one, not every submodule the SDK has, to keep the download small.

Simulator, debugger and logic analyser

Once the ELF file exists, three kinds of tool take over, each with a different relationship to the target. A simulator runs the ELF on a virtual Pico inside your PC, with no hardware at all; the course uses Wokwi, which runs inside VS Code. A debugger attaches to a running program, sets breakpoints and reads memory. The course uses the Arm GNU debugger, arm-none-eabi-gdb, which ships with the Arm toolchain, through the Cortex-Debug extension for VS Code. A logic analyzer records the voltage changes on pins over time, and PulseView displays those recordings and decodes protocols such as I2C and UART from them. PulseView is not needed until lesson 60, but it is installed now so the setup is complete.

The simulator is a good stand-in for the chip, although not a perfect one. It runs your code faithfully but does not model every timing detail of real hardware, and the course notes list what it does not simulate. Lesson 2 relies on it, so treat a simulator result as strong evidence and a real board as the final word.

Host tools: package manager, compilers and terminal

Some tools run on the host and never touch a chip. A package manager installs software from a central list, and on Windows the course uses winget, which is built into recent versions. Each package has an exact ID, such as Kitware.CMake, so the same command installs the same tool on every PC.

Two tools run on the host and also target the host rather than the Pico. The host C compiler is a normal Windows compiler, here MinGW-w64 GCC from the WinLibs package. The SDK uses it to build its PIO assembler in lesson 65, and you use it to run unit tests on your PC in lesson 80. Cppcheck is a static analyser that reads C without running it and reports likely bugs, and it appears from lesson 83. In addition, Git tracks changes to files and Python runs the course's tools.

You will also work in a terminal, a window that runs commands; in this course it is PowerShell. Two details commonly trip beginners. The PATH is the list of folders the terminal searches when you type a program name such as cmake, and an installer that adds a tool to it only affects terminals opened afterwards, so an open window keeps the old list. Furthermore, a command like winget install may fail because the tool is already installed, which is harmless, as the mistakes section explains.

Open PowerShell for each step, copy the commands as they are, and run the check in step 6 at the end.

  1. Install VS Code from code.visualstudio.com. VS Code is the editor and the front end for the simulator and the debugger. Keep the option that adds code to PATH, because the extension commands below need it. Then install the extensions from the command line: 
    code --install-extension wokwi.wokwi-vscode
code --install-extension ms-vscode.cpptools
code --install-extension marus25.cortex-debug
# Optional:
code --install-extension ms-vscode.cmake-tools
    Each line prints a short message ending with "successfully installed", or a note that the extension is already installed. The three extensions are the Wokwi simulator, the C/C++ language support for autocompletion and error underlines, and Cortex-Debug, which lets VS Code talk to the GDB debugger. CMake Tools is optional, since the course's tasks run CMake for you.
  2. Install the build and version-control tools with winget. Each package is installed by its exact ID. Run the eight commands in one block: 
    winget install -e --id Arm.GnuArmEmbeddedToolchain
winget install -e --id Ninja-build.Ninja
winget install -e --id Kitware.CMake
winget install -e --id Git.Git
winget install -e --id Python.Python.3.13
winget install -e --id Sigrok.PulseView
winget install -e --id BrechtSanders.WinLibs.POSIX.UCRT
winget install -e --id Cppcheck.Cppcheck
    Each command prints a progress bar and then "Successfully installed", or "already installed" if the package is there. The first five are needed in every lesson: the Arm compiler, Ninja, CMake, Git and Python. The Arm toolchain installs version 14.2 to C:\Program Files (x86)\Arm GNU Toolchain arm-none-eabi\14.2 rel1\bin, which is where the build tools look for it. PulseView is for lesson 60 onwards, and WinLibs and Cppcheck are host tools, as described above.
  3. Clone the Pico SDK, version 2.3.1, into your home folder. A clone copies a git repository; --depth 1 copies only the latest commit, which is much smaller, and -b 2.3.1 selects the tagged version. Then fetch the one submodule the build needs: 
    git clone --depth 1 -b 2.3.1 https://github.com/raspberrypi/pico-sdk "$HOME\.pico-sdk\sdk\2.3.1"
cd "$HOME\.pico-sdk\sdk\2.3.1"
git submodule update --init --depth 1 lib/tinyusb
cd "$HOME\embedded-course"
    The clone prints the objects it receives and ends without an error, and the submodule command ends with a line naming the TinyUSB path. The folder must end up exactly at %USERPROFILE%\.pico-sdk\sdk\2.3.1, because that is where the build looks. If you keep the course somewhere other than %USERPROFILE%\embedded-course, change the last cd to your folder.
  4. Request your Wokwi license. In VS Code, press F1 and choose Wokwi: Request a New License. A browser window opens; sign in to a free Wokwi account and confirm, and VS Code shows License activated. The license is personal and lasts 30 days. It is free for open-source projects, while commercial use needs a paid license. The documentation does not describe renewal, so when it expires, run the same command again and check the Wokwi license page.
    Source: Wokwi for VS Code: getting started, and the Wokwi license page.
  5. Optional for automated checks: set up the Wokwi CLI. You need a CI token from the Wokwi dashboard. Save it once, then download the CLI to where the course tools look for it. The file on the wokwi-cli releases page is called wokwi-cli-win-x64.exe, and the commands save it as %USERPROFILE%\.wokwi\bin\wokwi-cli.exe. Alternatively, setup.cmd --wokwi-cli does the download for you: 
    setx WOKWI_CLI_TOKEN "<your token>"
New-Item -ItemType Directory -Force "$HOME\.wokwi\bin"
Invoke-WebRequest https://github.com/wokwi/wokwi-cli/releases/latest/download/wokwi-cli-win-x64.exe -OutFile "$HOME\.wokwi\bin\wokwi-cli.exe"
    The token is a secret, like a password, so keep it out of any file you share. setx saves it for your Windows user account, prints "SUCCESS", and only affects terminals opened afterwards. The download command prints nothing when it succeeds, and the check in step 6 lists the Wokwi CLI as optional until the file is in place.
  6. Verify everything. Open a new PowerShell window, so that it picks up the new PATH entries, and run the check in the course folder: 
    cd "$HOME\embedded-course"
python tools/build.py --check
    Every line should start with [OK. The Zephyr line may say MISSING, which is expected, since Zephyr is set up in lesson 94. The next section explains what each line tests.

Reading the output of the check

build.py --check looks for each tool in the places the course expects and prints the path where it found it. It confirms that a tool is present, not that it works, so a line starting with [OK only means the tool exists at that path. The first real test is the build in lesson 2.

The lines appear in this order: the Arm compiler, Ninja, CMake, Git, the host C compiler, Cppcheck, the Pico SDK, the Wokwi CLI, Rust, the Zephyr workspace and the three VS Code extensions. Of these, only the Arm compiler, Ninja, CMake, Git, the Pico SDK and the three extensions are required from lesson 1, and the check reports the others as optional. Each MISSING line names the lesson that needs the tool, so you can tell at once whether it blocks you now.

You can run the toolchain check and read its output, and you can say what each tool does and which stage of the build it belongs to. From the next lesson on, every build you run goes through this chain.

Common mistakes and how to spot them

Each of these is a real mistake on this setup, described by what you see, what causes it and how to fix it.

A tool reported as missing right after its install

You have just run a winget command, yet a line such as [MISSING] CMake still appears in the same window. The window was opened before the install, so its PATH is still the old list. Open a new PowerShell window and run the check again. If the line is still missing there, read the install output for an error.

The Pico SDK in the wrong folder

The check prints [MISSING] Pico SDK, or a CMake configure step stops because it cannot find the SDK. In that case the clone went to a folder other than %USERPROFILE%\.pico-sdk\sdk\2.3.1, or it was interrupted. Check that pico_sdk_init.cmake sits directly in the folder and that external\pico_sdk_import.cmake exists. If either is missing, move the folder away and run step 3 again.

The host compiler used for the Pico

Compiling main.c with a plain gcc on the PC stops with fatal error: pico/stdlib.h: No such file or directory. The Pico headers and libraries exist only in the SDK, and the host compiler produces code for Windows, not for the Cortex-M0+. Always build through tools/build.py or the VS Code build task, which use the Arm cross-compiler and the Pico SDK.

A library missing from the link

Every file compiles without error, and then the linker stops with a message such as undefined reference to gpio_put. The compiler found the declaration in a header, but no object file given to the linker defines the function. Add the library to the project's target_link_libraries line. The template already links pico_stdlib there, so a broken edit to that line is the usual cause.

A Wokwi licence that is missing or expired

The Wokwi simulator opens with a license error, or does not open at all. Either no license has been requested on this PC, or the current one has expired after 30 days. Press F1, run Wokwi: Request a New License again, and then start the simulator.

Toolchains in real projects

Professional teams treat the toolchain as part of the product. They pin the compiler and the SDK to exact versions, as this course does with Arm GCC 14.2 and the Pico SDK 2.3.1, so that a build made on one machine matches a build made on another. The same versions go into the team's continuous integration server, which runs the build on every change (lesson 82). When a new compiler release fixes a bug, the team upgrades deliberately, tests the result and records the change.

Reviewers treat build changes with the same care. A change that adds a library dependency, edits a linker script or adds a compiler flag is reviewed as carefully as a change to a function, because it can break every build that follows. An engineer who knows what the compiler, the linker and the build system each do can usually trace a broken build in minutes, whereas one who only knows the buttons may spend an afternoon on it.

Summary

  • The host is your PC and the target is the Pico's Cortex-M0+ chip, and they use different machine code.
  • A cross-compiler runs on the host and emits machine code for the target; the course uses arm-none-eabi-gcc.
  • The compiler makes one .o object file per source file and leaves calls to other files unresolved.
  • The linker resolves those calls, places the code according to a linker script, and writes one ELF file that a simulator or debugger can load.
  • CMake describes the build and Ninja runs it, rebuilding only what changed.
  • The Pico SDK 2.3.1 supplies the C functions for the chip, and CMake finds it through PICO_SDK_PATH.
  • The simulator (Wokwi), the debugger (GDB) and the logic analyzer (PulseView) all work on the ELF or on its signals.
  • build.py --check shows that each tool is present, not that it works; the first real test is the build in lesson 2.
