Where we are and why it matters

This is the first lesson, so it assumes nothing from the course. You need a Windows 11 PC (the course is written for it; macOS and Linux work through setup.sh), a web browser, an internet connection and some patience, because the installers download several hundred megabytes. You already know C, so the question here is how a program you write on a PC ends up running on a small chip that has no keyboard, no screen and no operating system.

That gap is the reason for a whole toolchain. Every later lesson in the course depends on it. When you change a timer or an interrupt in lesson 57, the change only matters if the build, the simulator and the debugger all still work. A broken tool shows up as a confusing error several lessons later, far from its cause. Professional firmware teams have the same problem: when the build environment is wrong, a team can lose days before anyone notices. The skill this lesson teaches is knowing what each tool is for, so that when one fails you know which one to look at.

Two computers: the host and the target

Every embedded project has two computers in it, and keeping them apart in your head is the first skill. The host is the computer you sit at, here a Windows PC. It runs VS Code, the compiler, the linker and the simulator. The target is the chip the firmware will run on. In this course the target is a Raspberry Pi Pico, whose RP2040 chip has CPU cores from Arm's Cortex-M0+ family. Your PC has a completely different processor, so the two do not share machine code.

Machine code is the binary instructions a processor executes. Each processor family has its own instruction set, so a program compiled for one family cannot run on another. A normal compiler on your PC produces code for the PC's processor. That is useless for a Cortex-M0+, which cannot execute it. The tool you need is a cross-compiler: a compiler that runs on the host but produces machine code for the target. The Arm GNU toolchain, which the course installs as arm-none-eabi-gcc, is one. The name tells you the target: arm for the processor family, none for no operating system, and eabi for the embedded binary interface that defines how functions pass arguments on that processor.

The host and the target also differ in what they have. Your PC has gigabytes of memory, a file system and an operating system. The Pico has a few hundred kilobytes of memory and runs only the code you load into it. So the host does all the heavy work, and the target only runs the finished result. Keep that picture in mind for the rest of the lesson: every tool either runs on the host to make the firmware, or runs on the host to imitate or watch the target.

Stage 1: the compiler turns each file into an object file

Building firmware happens in stages, and each stage has one job. The first stage is the compiler. It reads one .c file, checks the C, and writes an object file, with the extension .o. An object file holds machine code for the functions in that one source file. It also holds a symbol table: a list of the names the file defines, such as main, and the names it uses but does not define, such as gpio_put.

The compiler works on one file at a time, and it has good reason to. It does not know where the other files are, or what address the final program will use. When main.c calls a function that lives in the Pico SDK, the compiler cannot write the real address of that function, because it does not have it. It writes a placeholder and records the name as unresolved. Working on one file at a time also means that when you change main.c, only that file needs compiling again. The rest of the project is reused. That is why a large firmware build can finish in seconds.

An object file is not a program yet. You cannot load it onto the Pico, because its code still has holes in it.

Stage 2: the linker joins the pieces

The second stage is the linker. It reads every object file you give it, plus the libraries they use, and it does four jobs. It matches each unresolved name with the definition in another file. It places every piece of code and data at an address. It writes the result as one file. And it reports any name it cannot match.

Here is the call from main.c traced through the stages. The compiler emits a call to gpio_put with a placeholder address and an unresolved symbol. The linker sees that gpio_put is defined in an object file that came from the SDK's GPIO code. It places that object file's code in the program, works out the real address, and patches the placeholder with it. Only the linker can do this, because only the linker has all the object files at once. That is why a missing function is reported at link time, not compile time.

Where the code goes is decided by a linker script. It is a text file that names the memory regions of the chip, such as flash (where the program is stored and runs from) and RAM (where variables live while the program runs), and says which sections of the program go in each region. The Pico SDK supplies its own script. You can read it in the SDK at src/rp2040/pico_platform/memmap_default.ld. Most of the time you never edit it, but you should know it exists, because lesson 68 writes one yourself.

The linker writes an ELF file, named blink.elf in this course. ELF stands for Executable and Linkable Format, a standard file layout. An ELF file holds the machine code and data in named sections, along with a symbol table and, when the build asks for it, debug information that maps machine addresses back to lines of your C. A debugger uses that information to show you variable names and stop at line 20 of main.c. Some boards are programmed from a plain .bin file, which holds only the raw bytes and none of that information. The Pico SDK can also produce a UF2 file for drag-and-drop flashing, but the course turns that off, because Wokwi runs the ELF directly. The template's CMakeLists.txt sets PICO_NO_PICOTOOL to 1 to say so.

  1. main.c calls gpio_put(25, 1). The function is not in this file: it is in the Pico SDK.
  2. The compiler turns main.c into main.o. It emits the call instruction, but it cannot know where gpio_put will live, so the address is a placeholder and the name is listed as unresolved.
  3. The SDK's GPIO code was compiled the same way into its own object file, gpio.o. That file defines gpio_put.
  4. The linker reads every object file at once, and the linker script tells it where flash and RAM are.
  5. The linker places gpio_put at an address in flash and patches the placeholder in main.o's call with it. Only the linker can do this, because only the linker has all the files.
  6. The result is one file, blink.elf: the machine code, a symbol table and debug information. Wokwi runs it and GDB reads it.
  7. If gpio.o is not linked, every file still compiles, and the linker stops with undefined reference to `gpio_put'. A missing function is a link error, not a compile error.

The build system runs the stages in order

A real project has many source files, many flags and several libraries, so nobody runs the compiler and linker by hand. A build system does that. The course uses CMake to describe the project and Ninja to run the commands. You describe the project once in a file called CMakeLists.txt: its name, its source files, and the libraries it links. CMake reads that file and writes a Ninja file, build.ninja, which lists every compile and link command in order. Ninja then runs them. It compares the time each source file was changed with the time its object file was made, and skips any command whose inputs have not changed. Ninja can also run independent compile commands in parallel.

You can see the output of this step. Each project's solution/build folder holds a build.ninja file, a CMakeCache.txt with the settings CMake found, and finally blink.elf. The folder is the build's output, not your source, so you can delete it at any time and the build will recreate it.

Libraries and the Pico SDK

Your program calls gpio_put, stdio_init_all and sleep_ms. None of those is part of the C language. They come from the Pico SDK, a library written by the chip's maker, Raspberry Pi, that wraps the chip's hardware registers in C functions. The course pins the SDK to version 2.3.1, which means you get the same source and the same functions every time. Pinning matters: a newer SDK may rename a function or change a default, and a project that worked last week would stop building for no reason you made.

CMake needs to know where the SDK is. It finds it through an environment variable, a named value the operating system passes to every program it starts. The variable is PICO_SDK_PATH, and it points at the SDK folder. The build tools in this course set it for you if it is not already set, to %USERPROFILE%\.pico-sdk\sdk\2.3.1. Inside that folder, the file external/pico_sdk_import.cmake is how each project connects to the SDK, and pico_sdk_init.cmake is the file the build tool checks for when it reports the SDK as present.

The SDK itself uses other libraries. One is TinyUSB, which provides USB serial. The SDK keeps TinyUSB in its own git submodule, which is a separate repository stored inside another one at a fixed commit. A plain clone does not download submodules, so the setup step fetches the one the build needs. The setup script fetches only TinyUSB, not every submodule the SDK has, to keep the download small.

Tools that run and watch the program

Once the ELF file exists, three kinds of tool take over, and each has a different relationship to the target. A simulator runs the ELF on a virtual Pico inside your PC, with no hardware. This course uses Wokwi, which runs inside VS Code. A debugger attaches to a running program, sets breakpoints and reads memory. The course uses the Arm GNU debugger, arm-none-eabi-gdb, which comes with the same Arm toolchain you install, through the Cortex-Debug extension for VS Code. A logic analyzer records the voltage changes on pins over time. PulseView is the program that displays those recordings and decodes protocols such as I2C and UART from them. You will not need PulseView until lesson 60, but it is installed now so the setup is complete.

The simulator is a good stand-in for the chip, but not a perfect one. It runs your code faithfully, but it does not model every timing detail of real hardware. Lesson 2 uses it, and the course notes list what it does not simulate. Treat a simulator result as strong evidence, and a real board as the final word.

Tools on your PC

Some tools run on the host and do not touch a chip at all. A package manager installs software from a central list. On Windows the course uses winget, which is built into recent Windows versions. Each package has an ID, such as Kitware.CMake, and winget installs that exact package. Because the ID is exact, the same command installs the same tool on every PC that runs it.

Two tools run on the host but target your PC, not the Pico. The host C compiler is a normal compiler for Windows, here MinGW-w64 GCC from the WinLibs package. The SDK uses it to build its PIO assembler in lesson 65, and you use it to run unit tests on your PC in lesson 80. Cppcheck is a static analyser that reads C without running it and reports likely bugs. It is used from lesson 83. Git tracks changes to files, and Python runs the course's tools.

You will also use a terminal. It is a window that runs commands for you. PowerShell is the one in this course. Two details trip beginners. First, the PATH is a list of folders the terminal searches when you type a program name, such as cmake. An installer that adds a tool to PATH changes the list only for terminals opened after the install, so an open window keeps the old list. Second, a command like winget install may fail because a tool is already installed, and that is harmless, as the troubleshooting section says.

Do all six steps, then run the check in step 6.

  1. Install VS Code from code.visualstudio.com. VS Code is the editor and the front end for the simulator and the debugger. Keep the option that adds code to PATH, because the extension commands below need it. Then install its extensions from the command line: 
    code --install-extension wokwi.wokwi-vscode
code --install-extension ms-vscode.cpptools
code --install-extension marus25.cortex-debug
# Optional:
code --install-extension ms-vscode.cmake-tools
    Each line prints a short message that ends with "successfully installed" or a note that the extension is already installed. The three extensions are the Wokwi simulator, the C/C++ language support (for autocompletion and error squiggles), and Cortex-Debug, which lets VS Code talk to the GDB debugger. The CMake Tools extension is optional, because the course's tasks run CMake for you.
  2. Install the build and version-control tools with winget. Each package is installed by its exact ID. Run the eight commands in one block: 
    winget install -e --id Arm.GnuArmEmbeddedToolchain
winget install -e --id Ninja-build.Ninja
winget install -e --id Kitware.CMake
winget install -e --id Git.Git
winget install -e --id Python.Python.3.13
winget install -e --id Sigrok.PulseView
winget install -e --id BrechtSanders.WinLibs.POSIX.UCRT
winget install -e --id Cppcheck.Cppcheck
    Each command prints a progress bar, then "Successfully installed", or "already installed" if the package is there. The first five matter for every lesson: the Arm compiler, Ninja, CMake, Git and Python. The Arm toolchain installs version 14.2 to C:\Program Files (x86)\Arm GNU Toolchain arm-none-eabi\14.2 rel1\bin, which is where the build tools look for it. PulseView is for lesson 60 onwards. WinLibs and Cppcheck are for your PC, not the microcontroller, as explained in the section on tools on your PC above.
  3. Clone the Pico SDK, version 2.3.1, into your home folder. A clone copies a git repository, and --depth 1 copies only the latest commit of that branch, which is much smaller. The -b 2.3.1 option picks the tagged version. Then fetch the one submodule the build needs: 
    git clone --depth 1 -b 2.3.1 https://github.com/raspberrypi/pico-sdk "$HOME\.pico-sdk\sdk\2.3.1"
cd "$HOME\.pico-sdk\sdk\2.3.1"
git submodule update --init --depth 1 lib/tinyusb
cd "$HOME\embedded-course"
    The clone prints the names of the objects it receives and ends without an error. The submodule command ends with a line naming the TinyUSB path. The folder must end up exactly at %USERPROFILE%\.pico-sdk\sdk\2.3.1, because that is where the build looks. If you keep the course somewhere other than %USERPROFILE%\embedded-course, change the last cd to your folder.
  4. Request your Wokwi license. In VS Code, press F1, then choose Wokwi: Request a New License. A browser window opens. Sign in to a free Wokwi account, confirm, and VS Code shows License activated. The license is a personal license for 30 days. It is free for open-source projects; commercial use needs a paid license. The docs do not describe renewal, so when it expires, run the same command again and check the Wokwi license page.
    Source: Wokwi for VS Code: getting started, and the Wokwi license page.
  5. Optional for automated checks: set up the Wokwi CLI. You need a CI token from the Wokwi dashboard. Save it once, then download the CLI to where the course tools look for it (the file on the wokwi-cli releases page is called wokwi-cli-win-x64.exe; this saves it as %USERPROFILE%\.wokwi\bin\wokwi-cli.exe). Or run setup.cmd --wokwi-cli, which does the download for you: 
    setx WOKWI_CLI_TOKEN "<your token>"
New-Item -ItemType Directory -Force "$HOME\.wokwi\bin"
Invoke-WebRequest https://github.com/wokwi/wokwi-cli/releases/latest/download/wokwi-cli-win-x64.exe -OutFile "$HOME\.wokwi\bin\wokwi-cli.exe"
    The token is a secret, like a password, so do not paste it into a file you share. setx saves it for your Windows user account and prints "SUCCESS". It takes effect only in terminals opened afterwards. The download command prints nothing when it succeeds. The check in step 6 lists the Wokwi CLI as optional until this file is in place.
  6. Verify everything. Open a new PowerShell window, so it picks up the new PATH entries, and run the check in the course folder: 
    cd "$HOME\embedded-course"
python tools/build.py --check
    Every line should start with [OK. The Zephyr line may say MISSING. That is expected: Zephyr is set up in lesson 94. Read the check section below to see what each line tests.

Reading the check

build.py --check looks for each tool in the places the course expects, and prints the path where it found it. It does not test that the tool works, only that it is present. A line that says [OK means the tool exists at that path. The first real test is the build in lesson 2.

The lines are, in order: the Arm compiler, Ninja, CMake, Git, the host C compiler, Cppcheck, the Pico SDK, the Wokwi CLI, Rust, the Zephyr workspace, and then the three VS Code extensions. Only the Arm compiler, Ninja, CMake, Git, the Pico SDK and the three extensions are required from lesson 1. The others are marked as needed from a later lesson, and the check reports them as optional. Each line that says MISSING tells you which lesson needs that tool, so you know whether it blocks you now.

Common mistakes and how to spot them

Each of these is a real mistake a beginner makes on this setup. The symptom is what you see, and the fix is what to do.

  1. The check says MISSING right after an install. Symptom: you just ran a winget command, and a line such as [MISSING] CMake still appears in the same window. Cause: the window was opened before the install, so its PATH is the old one. Fix: open a new PowerShell window and run the check again. If the line is still missing in a new window, read the install output for an error.
  2. The Pico SDK is in the wrong folder. Symptom: the check prints [MISSING] Pico SDK, or a CMake configure step stops and says it cannot find the SDK. Cause: the clone went to a folder other than %USERPROFILE%\.pico-sdk\sdk\2.3.1, or the clone was interrupted. Fix: check that pico_sdk_init.cmake sits directly in the folder, and that external\pico_sdk_import.cmake exists. If either is missing, move the folder away and run step 3 again.
  3. Using the host compiler for the Pico. Symptom: you compile main.c with a plain gcc on the PC and get fatal error: pico/stdlib.h: No such file or directory. Cause: the Pico headers and libraries exist only in the SDK, and the host compiler produces code for Windows, not for the Cortex-M0+. Fix: always build through tools/build.py or the VS Code build task, which uses the Arm cross-compiler and the Pico SDK.
  4. A library is not linked. Symptom: the build compiles every file without error, then the linker stops with a message like undefined reference to gpio_put. Cause: the compiler found the declaration in a header, but no object file was given to the linker that defines the function. Fix: add the library to the project's target_link_libraries line. The template does this with pico_stdlib, so a broken edit to that line is the usual cause.
  5. The simulator does not start. Symptom: the Wokwi simulator opens with an error about a license, or does not open at all. Cause: no Wokwi license has been requested on this PC, or it has expired after 30 days. Fix: press F1 and run Wokwi: Request a New License again, then start the simulator.

In real projects

Professional teams treat the toolchain as part of the product. They pin the compiler and the SDK to exact versions, as this course does with Arm GCC 14.2 and the Pico SDK 2.3.1, so a build made on one machine matches a build made on another. The same versions go into the team's continuous integration server, which runs the build on every change (lesson 82). When a new compiler release fixes a bug, the team upgrades on purpose, tests the result, and records the change.

Reviewers look at build problems too. A change that adds a library dependency, changes a linker script or adds a compiler flag is reviewed as carefully as a change to a function, because it can break every build that follows. An engineer who can say from memory what the compiler, the linker and the build system each do will debug a broken build in minutes, while one who only knows the buttons may spend an afternoon.

Summary

  • The host is your PC; the target is the Pico's Cortex-M0+ chip. They use different machine code.
  • A cross-compiler runs on the host and emits machine code for the target. The course uses arm-none-eabi-gcc.
  • The compiler makes one .o object file per source file, and leaves calls to other files unresolved.
  • The linker resolves those calls, places code using a linker script, and writes one ELF file that a simulator or debugger can load.
  • CMake describes the build and Ninja runs it, rebuilding only what changed.
  • The Pico SDK 2.3.1 supplies the C functions for the chip. CMake finds it through PICO_SDK_PATH.
  • The simulator (Wokwi), the debugger (GDB) and the logic analyzer (PulseView) all work on the ELF or on its signals.
  • build.py --check proves that each tool is present, not that it works. The first real test is the build in lesson 2.
