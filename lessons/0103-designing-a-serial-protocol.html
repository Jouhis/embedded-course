Designing a serial protocol: framing, checksums, CRC

A UART gives you a stream of bytes with no beginnings and no ends. A protocol turns that stream into messages that a receiver can find, check and, when a message is lost, ask again for. You will implement COBS byte stuffing and CRC-16/CCITT-FALSE, test them on the PC, and frame sensor readings on the Pico.

By the end of this lesson you can implement COBS encoding and decoding and a CRC-16/CCITT-FALSE, check the CRC against its standard value, and frame a sensor reading so that a receiver can find it and verify it.

Where we are and why it matters

Lesson 101 sent Modbus RTU frames over a UART and RS-485, and lesson 102 showed how USB carries its own packets with its own checks. In both cases someone else designed the framing. Lesson 101 used a CRC-16 that the Modbus standard fixes, and the Modbus slave in this course relies on a silent gap on the line to find where each frame starts. This lesson is about the other case: you have a UART, a sensor and a Pico, and nothing defines the messages yet. You must design them.

The problem comes up often in real products. A printer's control board talks to a touchscreen over a UART. A battery pack talks to a charger. A factory tester talks to a device under test. Each of these links is a serial line that someone designed, and each one fails in the same ways: a byte is lost, a byte is flipped, or the receiver starts reading in the middle of a message and never recovers. A well-designed protocol makes each of those failures visible and recoverable.

What a UART actually gives you

A UART (universal asynchronous receiver-transmitter) is the peripheral in the microcontroller that turns a parallel byte into a serial bit stream and back (glossary: UART). It has no clock wire. Each byte is sent as a start bit, eight data bits and a stop bit, at an agreed baud rate. The receiver sees a falling edge, waits half a bit time, and samples each bit in the middle of its slot. That is all the hardware promises.

Notice what is missing. The UART does not say where a message starts or ends. It does not say whether a byte is correct. If the receiver's clock drifts by a few percent, or a spike on the wire flips a bit, the byte arrives wrong and nothing signals it. The receiver just gets a stream of numbers. Every guarantee above the byte level is the protocol's job.

The idea: a stream needs framing

A receiver that reads a UART byte by byte cannot tell where one message stops and the next starts, and line noise can add or drop bytes. A protocol has to solve two problems. Framing marks where each message begins and ends. Error detection tells the receiver whether the bytes are intact. Three common framing styles solve the first problem:

  • Length prefix. The first byte gives the length of the body. It is simple, but one corrupted length byte loses synchronisation for every message after it, because the receiver counts the wrong number of bytes and then reads the next message's first byte as a length.
  • Delimiter with escaping. A special byte ends each frame, and the body is rewritten so the delimiter never appears inside it. SLIP does this by escaping the end byte (RFC 1055, RFC 1055, in RESOURCES.md). In the worst case it can double the length of a frame, because every byte that needs escaping costs two.
  • COBS. Consistent Overhead Byte Stuffing rewrites the body so it contains no zero at all. Then 0x00 is free to mark every frame end. Its overhead is bounded, and a receiver can resynchronise after any noise: the next zero is the next frame.

Cheshire and Baker's paper defines COBS and proves its bound: in the worst case the stuffing adds no more than one byte in 254 to any packet (Cheshire and Baker, "Consistent Overhead Byte Stuffing", IEEE/ACM Transactions on Networking, 1999). That makes COBS the usual choice for a binary stream that must resynchronise after noise. The paper's publisher identifier is S 1063-6692(99)03826-1. Why zero is the special value

A zero is a convenient marker for a reason that comes from the bit pattern. Many real signals are idle low or idle high, and a line that is disconnected or shorted often reads as all zeros. A zero delimiter therefore shows up when the wire goes quiet. The bigger reason is that a delimiter only works if the body can never contain it. COBS makes that true by construction, and the rest of this lesson is about how.

Consider the alternative of a frame that uses 0x7E as its end marker, with the data unchanged. A sensor value of 0x7E in the middle of a reading would end the frame early. The receiver would then see half a message, fail its check, and wait for a delimiter that has already passed. Escaping fixes this by rewriting every 0x7E as two bytes, which costs bandwidth in proportion to how often the byte appears. COBS fixes it differently: it removes the marker from the body entirely, so the cost is a fixed small amount no matter what the data contains.

COBS: the rule in one example

COBS splits the data at its zeros. Each block starts with a code byte that gives the distance to the next zero, counting the code byte itself, and the data bytes of the block follow. Take 11 22 00 33. The first block holds 11 22, and its code is 3 (two data bytes plus one). The zero is replaced by the code. The last block holds 33, with code 2. The encoding is 03 11 22 02 33, which has no zero in it. Decoding reverses it: read a code, copy the block, and put back the zero that the code stood for.

Walk through the encoder on that example, one byte at a time. The encoder starts with a code of 1, meaning "zero data bytes so far", and it reserves position 0 for the code. It reads 11: nonzero, so it copies it to position 1 and the code becomes 2. It reads 22: copies it to position 2 and the code becomes 3. It reads 00: a zero, so it writes the code 3 into position 0, starts a new block whose code goes in position 3, and moves on. It reads 33: copies it to position 4, and the code for that block becomes 2. The input has ended, so it writes 2 into position 3. The output is five bytes long, and the one zero of the input has been replaced by a code.

The cost of COBS, bit by bit

The overhead is easy to state once you see the block structure. Every block costs one code byte, and a block ends at a zero or at 254 data bytes. A body with no zeros and fewer than 254 bytes gets exactly one code byte. A body of 254 nonzero bytes gets one code byte of 0xFF and then the 254 data bytes. The body ends exactly on a block boundary, so the encoder adds an empty last block with code 0x01, and 254 bytes encode to 256 bytes, as the project's test_full_block_of_254_bytes checks. That final byte is the "plus one" in the overhead rule. The paper's bound of one byte in 254 comes from the case where every block is full. The worst realistic case is a body that is mostly zeros, because each zero costs a code byte and removes one data byte, so its encoding is about as long as the input.

The code value 0xFF is the special case, and the paper says so directly: code 0xFF stands for 254 data bytes with no implicit zero after them (Cheshire and Baker, section III.A). Codes 0x01 to 0xFE each stand for their data bytes followed by one implicit zero. Code 0x00 is never valid. A decoder that reads 0x00 where a code belongs has found a corrupted stream.

Checksums and CRC: what they can catch

A checksum adds the bytes together, and it catches a single flipped bit. It misses a reordering of bytes, and it misses many pairs of errors that cancel. A cyclic redundancy check (CRC) treats the message as a long binary number and takes its remainder when divided by a fixed polynomial. Its detection power depends on the polynomial, and it catches all burst errors up to its width. Choosing a polynomial is a research problem: Philip Koopman's tables list the best polynomials for each size and Hamming distance (Koopman, "Best CRC Polynomials", Carnegie Mellon University).

The remainder catches so many errors for a mathematical reason. Think of the sender's bits as a polynomial over the binary field, and of the CRC as the remainder after dividing by the generator polynomial. An error pattern changes the message by adding another polynomial. The receiver's remainder is then the remainder of the error pattern alone. If the error is a burst no longer than the CRC's width, that remainder is never zero, because a short burst is never a multiple of the generator. That is the mathematical reason a 16-bit CRC catches every burst of up to 16 bits.

A CRC has three parameters that must match on both ends: the polynomial, the initial value, and how the bits are ordered. Two variants can share a polynomial and still disagree, because one reflects the bits and the other does not. Pick the variant by name, not by polynomial. The check value in the table is the test that catches a mismatch. If you feed the nine ASCII characters "123456789" into a correct CRC-16/CCITT-FALSE, you get 0x29B1, and a different number means one of the three parameters is wrong.

The bitwise version works one bit at a time: eight shifts per byte, and no table. A table-driven version looks up 256 precomputed values, one per byte, which is faster but costs 512 bytes of flash. On a small microcontroller, the bitwise form is often the right trade. Append the CRC big-endian to a frame and the CRC of the whole frame becomes zero, which lets the receiver check a frame in one call. This works for CCITT-FALSE because it has no final XOR.

Sequence numbers and retries

A CRC tells the receiver that a frame is damaged, but it cannot tell it that a frame is missing. Add a sequence number to each frame. The receiver answers with an ACK for a good frame or a NACK for a bad one, and the sender retries after a timeout. The sequence number also lets the receiver drop a duplicate when an ACK was lost. Stop-and-wait, one frame in flight at a time, is the simplest scheme that works. Lesson 101's Modbus avoids the problem by making every request a question that gets an answer.

The retry loop has two failure modes that a beginner often forgets. If the ACK is lost, the sender times out and resends a frame the receiver already has, so the receiver must recognise the repeated sequence number and ignore the payload. If the sender's timeout is shorter than the round trip, it resends frames that were never lost, and the receiver sees a flood of duplicates. The timeout must be longer than the time for a full frame to cross the line and the ACK to come back, which at 115200 baud is a few milliseconds for a short frame.

Hint for the encoder

Keep two indexes: code_at, where the current code byte goes, and w, the next free output byte. At each zero, write the code into code_at and reserve the next code byte. At 254 data bytes, close the block the same way, without a zero.

Hint for the decoder

Read a code c, reject a zero code, and copy c - 1 bytes. After any block except one whose code is 0xFF, put back a zero, unless the input has ended.

Worked example: one frame, byte by byte

Take the first frame: sequence 0, sensor 0x21, reading 2250 (22.50 C). The reading is 2250 decimal, which is 0x08CA in hex. Stored little-endian, the low byte comes first, so the two value bytes are 0xCA and 0x08. The first four body bytes are therefore 00 21 CA 08. Next, the CRC-16/CCITT-FALSE is computed over those four bytes, and its result is appended high byte first. The body is six bytes, the CRC of all six is zero, and COBS encodes it. You do not need to compute the CRC by hand: the host test already checks the algorithm. What matters is the order of the steps and the byte at each position.

The COBS step is where the frame loses its zeros. The first body byte is 0x00, so the first block is empty: its code is 1. The next run of nonzero bytes becomes one block, and the code tells the receiver where the next zero used to be. The encoded frame is at most seven bytes long, because one code byte is added to the six body bytes, and then the 0x00 delimiter is appended on the wire. The receiver sees eight bytes ending in 0x00, decodes everything before the zero, and checks the result.

Common mistakes and how to spot them

Mistake 1: putting the code byte in the wrong place. The encoder must write each code into the position it reserved, which is the position of the zero it replaced, not the position of the next data byte. Symptom: the host test for {11 22 00 33} fails with the expected length 5 but the bytes differ at index 0 or 3. Fix: keep code_at as its own variable, and update it only when you reserve a new code byte.

Mistake 2: forgetting the implicit zero after a block. A block with a code below 0xFF ends with a zero in the decoded data, except at the end of the input. Symptom: the decoded output is one byte shorter than the input, or the round-trip test fails on {00} only. Fix: in the decoder, emit the zero after every block whose code is not 0xFF, unless the input has ended.

Mistake 3: computing the CRC over the wrong bytes. The CRC must cover the four payload bytes when you build the frame, and all six bytes when you check it. Symptom: the receiver reports every frame as corrupted, even though the sender's bytes look correct. Fix: check that frame_decode() computes the CRC over the full six-byte body, and that frame_encode() computes it over only the first four. A quick test is to take the CCITT check value first: if the CRC of "123456789" is not 0x29B1, the function is wrong before the frame code is involved.

Mistake 4: byte order in the CRC. Appending the CRC low byte first is a common habit from Modbus (lesson 101), and it breaks the zero-residue property. Symptom: the CRC of the whole frame is nonzero on good frames, so every frame looks damaged. Fix: append the CRC high byte first, as the code comment says. Modbus RTU is the opposite, which is why the two CRC functions in crc16.c must not be mixed up.

In real projects

Professional firmware rarely hand-rolls a framing format for a product that outlives one prototype. Teams usually choose between a standard (Modbus, a vendor protocol, or a framed format such as HDLC or SLIP) and their own COBS-framed format. A reviewer will expect three things from a custom format. First, a version field, so a new firmware can refuse an old frame clearly. Second, a documented CRC with its parameters written in the protocol document, not just in the code. Third, a test vector file that any implementation, on the PC or on the device, must pass. The check value in this lesson is exactly that kind of vector.

Summary

  • A UART sends bytes with no message boundaries and no error check, so a protocol must supply framing and error detection.
  • COBS removes every zero from the body, so 0x00 can mark each frame end. Overhead is at most one byte in 254, plus one.
  • A COBS code byte gives the distance to the next zero. Code 0xFF means 254 data bytes with no implied zero. Code 0x00 is never valid.
  • CRC-16/CCITT-FALSE has polynomial 0x1021, initial value 0xFFFF, and no reflection or final XOR. Its check value for "123456789" is 0x29B1.
  • Check a CRC implementation against its check value before you trust any frame code built on it.
  • Append the CRC high byte first. The CRC of a good frame, with its CRC appended, is then zero.
  • A CRC detects damage but not a missing frame. Sequence numbers, ACK and NACK, and a timeout handle loss.
