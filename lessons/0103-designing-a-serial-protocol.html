Designing a serial protocol

Framing, checksums and CRCs on a byte stream

By the end of this lesson you can implement COBS encoding and decoding and a CRC-16/CCITT-FALSE, check the CRC against its standard value, and frame a sensor reading so that a receiver can find it and verify it.

Links without a defined message format

Lesson 101 sent Modbus RTU frames over a UART and RS-485 and lesson 102 showed how USB carries its own packets with its own checks, but in both cases someone else designed the framing, lesson 101 using a CRC-16 that the Modbus standard fixes, while the course's Modbus slave relies on a silent gap on the line to find where each frame starts. This lesson concerns the other case, a UART, a sensor and a Pico with nothing yet defining the messages, which you must design.

The problem comes up often in real products, a printer's control board talking to a touchscreen over a UART, a battery pack to a charger and a factory tester to a device under test, each link being a serial line someone designed and each failing in the same ways, a byte lost, a byte flipped or a receiver starting to read in the middle of a message and never recovering. A well-designed protocol makes each of those failures visible and recoverable.

What a UART provides

A UART (universal asynchronous receiver-transmitter) is the microcontroller peripheral that turns a parallel byte into a serial bit stream and back (glossary: UART), without a clock wire, each byte being sent as a start bit, eight data bits and a stop bit at an agreed baud rate. The receiver sees a falling edge, waits half a bit time and samples each bit in the middle of its slot, which is all that the hardware promises.

The UART therefore says neither where a message starts or ends nor whether a byte is correct, so if the receiver's clock drifts by a few percent or a spike on the wire flips a bit, the byte arrives wrong without any signal, the receiver simply getting a stream of numbers. Every guarantee above the byte level is the protocol's job.

Framing styles for a byte stream

A receiver reading a UART byte by byte cannot tell where one message stops and the next starts, and line noise can add or drop bytes, so a protocol must solve two problems, framing, which marks where each message begins and ends, and error detection, which tells the receiver whether the bytes are intact. Three common framing styles solve the first.

  • Length prefix. The first byte gives the length of the body. It is simple, but one corrupted length byte loses synchronisation for every message after it, because the receiver counts the wrong number of bytes and then reads the next message's first byte as a length.
  • Delimiter with escaping. A special byte ends each frame, and the body is rewritten so the delimiter never appears inside it. SLIP does this by escaping the end byte (RFC 1055, RFC 1055, in RESOURCES.md). In the worst case it can double the length of a frame, because every byte that needs escaping costs two.
  • COBS. Consistent Overhead Byte Stuffing rewrites the body so it contains no zero at all. Then 0x00 is free to mark every frame end. Its overhead is bounded, and a receiver can resynchronise after any noise: the next zero is the next frame.

Cheshire and Baker's paper defines COBS and proves its bound, that in the worst case the stuffing adds no more than one byte in 254 to any packet (Cheshire and Baker, "Consistent Overhead Byte Stuffing", IEEE/ACM Transactions on Networking, 1999), which makes COBS the usual choice for a binary stream that must resynchronise after noise. The paper's publisher identifier is S 1063-6692(99)03826-1. This lesson did not find a DOI, so cite the paper by its authors, title and journal.

Zero as the delimiter

A zero is a convenient marker for a reason rooted in the bit pattern, because many real signals idle low or high and a disconnected or shorted line often reads as all zeros, so a zero delimiter shows up when the wire goes quiet. The bigger reason is that a delimiter works only if the body can never contain it, which COBS makes true by construction, as the rest of this lesson shows.

The alternative of a frame using 0x7E as its end marker with the data unchanged shows the problem, because a sensor value of 0x7E in the middle of a reading would end the frame early, so the receiver would see half a message, fail its check and wait for a delimiter that has already passed. Escaping fixes this by rewriting every 0x7E as two bytes, at a bandwidth cost proportional to how often the byte appears, whereas COBS removes the marker from the body entirely, at a small fixed cost whatever the data contains.

The COBS block rule

COBS splits the data at its zeros, each block starting with a code byte that gives the distance to the next zero, counting the code byte itself, followed by the block's data bytes. For 11 22 00 33 the first block holds 11 22 with code 3, two data bytes plus one, the zero being replaced by the code, and the last block holds 33 with code 2, so the encoding 03 11 22 02 33 contains no zero, and decoding reverses it, reading a code, copying the block and putting back the zero the code stood for.

The encoder can be followed on that example one byte at a time, starting with a code of 1, meaning zero data bytes so far, and reserving position 0 for the code. It reads 11, nonzero, so it copies it to position 1 and the code becomes 2, then reads 22, copies it to position 2 and the code becomes 3, and then reads 00, a zero, so it writes the code 3 into position 0 and starts a new block whose code goes in position 3. Finally it reads 33, copies it to position 4, the code for that block becoming 2, and since the input has ended, writes 2 into position 3, giving an output five bytes long in which the input's one zero has been replaced by a code.

Zero resembles the full stop that ends a sentence, which would leave the reader unsure where the sentence ends if it could also appear inside one, so COBS removes every zero from inside the frame and writes in its place how many bytes ahead the next zero would have been, leaving the one real zero at the end. The comparison breaks because a reader can usually guess a sentence's end from its meaning, whereas a receiver has nothing but the zero, so a single corrupted code byte misplaces every zero after it until the next delimiter.

The overhead of COBS

The overhead is easy to state once the block structure is clear, every block costing one code byte and ending at a zero or at 254 data bytes, so a body with no zeros and fewer than 254 bytes gets exactly one code byte, whereas a body of 254 nonzero bytes gets one code byte of 0xFF followed by the 254 data bytes. That body ends exactly on a block boundary, so the encoder adds an empty last block with code 0x01, and 254 bytes encode to 256 bytes, as the project's test_full_block_of_254_bytes checks, the final byte being the "plus one" in the overhead rule.

The paper's bound of one byte in 254 comes from the case where every block is full, while a body that is mostly zeros, each zero costing a code byte and removing one data byte, encodes to about its own length. The code value 0xFF is the special case, the paper saying directly that it stands for 254 data bytes with no implicit zero after them (Cheshire and Baker, section III.A), whereas codes 0x01 to 0xFE each stand for their data bytes followed by one implicit zero, and code 0x00 is never valid, so a decoder reading 0x00 where a code belongs has found a corrupted stream.

Checksums and CRCs

A checksum adds the bytes together and catches a single flipped bit but misses a reordering of bytes and many pairs of errors that cancel, whereas a cyclic redundancy check (CRC) treats the message as a long binary number and takes its remainder when divided by a fixed polynomial, its detection power depending on the polynomial, and catches all burst errors up to its width. Choosing a polynomial is a research problem, Philip Koopman's tables listing the best polynomials for each size and Hamming distance (Koopman, "Best CRC Polynomials", Carnegie Mellon University).

The remainder catches so many errors for a mathematical reason, the sender's bits forming a polynomial over the binary field and the CRC being the remainder after division by the generator polynomial, so an error pattern changes the message by adding another polynomial and the receiver's remainder becomes the remainder of the error pattern alone. A burst no longer than the CRC's width is never a multiple of the generator, so its remainder is never zero, which is why a 16-bit CRC catches every burst of up to 16 bits.

A CRC has three parameters that must match on both ends, the polynomial, the initial value and the bit order, so two variants sharing a polynomial can still disagree when one reflects the bits and the other does not, which is why the variant is picked by name rather than by polynomial. The check value in the table catches a mismatch, since feeding the nine ASCII characters "123456789" into a correct CRC-16/CCITT-FALSE gives 0x29B1, and any other number means that one of the three parameters is wrong.

The bitwise version works one bit at a time, with eight shifts per byte and no table, whereas a table-driven version looks up 256 precomputed values, one per byte, which is faster but costs 512 bytes of flash, so on a small microcontroller the bitwise form is often the right trade. Appending the CRC big-endian to a frame makes the CRC of the whole frame zero, which lets the receiver check a frame in one call, a property CCITT-FALSE has because it uses no final XOR.

Sequence numbers and retries

A CRC tells the receiver that a frame is damaged but cannot tell it that a frame is missing, which a sequence number in each frame solves, the receiver answering with an ACK for a good frame or a NACK for a bad one while the sender retries after a timeout, and the sequence number also letting the receiver drop a duplicate when an ACK was lost. Stop-and-wait, with one frame in flight at a time, is the simplest scheme that works, whereas lesson 101's Modbus avoids the problem by making every request a question that gets an answer.

The retry loop has two failure modes that beginners often forget, a lost ACK making the sender time out and resend a frame the receiver already has, so that the receiver must recognise the repeated sequence number and ignore the payload, and a timeout shorter than the round trip making the sender resend frames that were never lost, so that the receiver sees a flood of duplicates. The timeout must therefore exceed the time for a full frame to cross the line and the ACK to come back, a few milliseconds for a short frame at 115200 baud.

Worked example: one sensor frame byte by byte

The first frame carries sequence 0, sensor 0x21 and the reading 2250, 22.50 °C. Before following the steps, predict how many bytes this frame occupies on the wire, delimiter included.

  1. The reading in hex. The reading 2250 decimal is 0x08CA, and stored little-endian, low byte first, its two value bytes are 0xCA and 0x08.
  2. The payload. The first four body bytes are therefore 00 21 CA 08.
  3. The CRC. The CRC-16/CCITT-FALSE is computed over those four bytes and appended high byte first, making a six-byte body whose CRC as a whole is zero, so you need not compute the CRC by hand, the host test already checking the algorithm, while the order of the steps and the byte at each position are what matter.
  4. The COBS step. The frame loses its zeros here, the first body byte being 0x00, so the first block is empty with code 1, while the next run of nonzero bytes becomes one block whose code tells the receiver where the next zero used to be, the encoded frame being at most seven bytes, one code byte added to the six body bytes.
  5. The delimiter. The 0x00 delimiter is appended on the wire, so the receiver sees eight bytes ending in 0x00, decodes everything before the zero and checks the result.

Hint for the encoder

Keep two indexes: code_at, where the current code byte goes, and w, the next free output byte. At each zero, write the code into code_at and reserve the next code byte. At 254 data bytes, close the block the same way, without a zero.

Hint for the decoder

Read a code c, reject a zero code, and copy c - 1 bytes. After any block except one whose code is 0xFF, put back a zero, unless the input has ended.

Common mistakes and how to spot them

The code byte in the wrong place

The host test for {11 22 00 33} fails with the expected length 5 but bytes differing at index 0 or 3, because the encoder wrote a code at the position of the next data byte instead of the position it reserved, the position of the zero it replaced. Keep code_at as its own variable and update it only when you reserve a new code byte.

The implicit zero after a block forgotten

The decoded output is one byte shorter than the input, or the round-trip test fails on {00} only, because a block with a code below 0xFF ends with a zero in the decoded data, except at the end of the input, and the decoder left it out. Emit the zero after every block whose code is not 0xFF, unless the input has ended.

The CRC computed over the wrong bytes

The receiver reports every frame as corrupted, although the sender's bytes look correct, because the CRC must cover the four payload bytes when the frame is built and all six bytes when it is checked. Make sure that frame_decode() computes the CRC over the full six-byte body and frame_encode() over only the first four, testing the CCITT check value first, since a CRC of "123456789" other than 0x29B1 shows the function to be wrong before the frame code is involved.

The CRC appended low byte first

The CRC of the whole frame is nonzero on good frames, so every frame looks damaged, because the CRC was appended low byte first, a habit from Modbus (lesson 101) that breaks the zero-residue property. Append the CRC high byte first, as the code comment says, remembering that Modbus RTU is the opposite, which is why the two CRC functions in crc16.c must not be mixed up.

Custom framing formats in products

Professional firmware rarely hand-rolls a framing format for a product that outlives one prototype, teams usually choosing between a standard, such as Modbus, a vendor protocol or a framed format like HDLC or SLIP, and their own COBS-framed format. A reviewer expects a custom format to have a version field, so that new firmware can refuse an old frame clearly, a documented CRC with its parameters written in the protocol document rather than only in the code, and a test vector file that any implementation, on the PC or the device, must pass, the check value in this lesson being exactly that kind of vector.

Summary

  • A UART sends bytes without message boundaries or an error check, so a protocol must supply framing and error detection.
  • COBS removes every zero from the body, so 0x00 can mark each frame end, at an overhead of at most one byte in 254, plus one.
  • A COBS code byte gives the distance to the next zero, code 0xFF meaning 254 data bytes without an implied zero and code 0x00 never being valid.
  • CRC-16/CCITT-FALSE has polynomial 0x1021, initial value 0xFFFF and no reflection or final XOR, its check value for "123456789" being 0x29B1.
  • A CRC implementation is checked against its check value before any frame code built on it is trusted.
  • With the CRC appended high byte first, the CRC of a good frame including its CRC is zero.
  • A CRC detects damage but not a missing frame, which sequence numbers, ACK and NACK and a timeout handle.
