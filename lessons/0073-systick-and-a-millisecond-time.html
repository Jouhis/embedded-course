SysTick and a millisecond time base

Almost every firmware timeout needs a clock that ticks at a known rate. The Cortex-M core has one built in: SysTick. Get the reload value right, and make the timeout arithmetic survive the counter wrap.

By the end of this lesson you can start SysTick at 1 kHz with SysTick_Config, keep a volatile uint32_t millisecond counter in the handler, write a wrap-safe millis() and timeout check, and explain why the HAL's HAL_Delay depends on the SysTick priority.

The idea

SysTick is a 24-bit down counter in the core, not in the STM32 peripherals. It counts from its reload value, LOAD, to zero, then reloads and sets its flag. With the interrupt enabled, it raises an exception each time it reaches zero. The Cortex-M3 Programming Manual describes the registers, and the CMSIS names them SysTick->LOAD, SysTick->VAL and SysTick->CTRL. PM0056, the SysTick section Because SysTick is in the core, it works on every STM32F1 variant the same way. The timers in lesson 71 are chip peripherals, so their names and clock trees differ between parts.

The reload value sets the period. At an 8 MHz core clock, a reload of 8000 − 1 = 7999 gives one interrupt every millisecond. The subtraction of one is the same off-by-one rule as in lesson 71: the counter counts from the reload down to zero, which is reload + 1 ticks per period.

SysTick_Config: one call that does three things

SysTick_Config(ticks) in core_cm3.h writes the reload value, sets SysTick's interrupt to the lowest priority ((1 << __NVIC_PRIO_BITS) − 1, which is 15 on this device), clears the counter, and enables the counter and the interrupt. It returns 1 when the reload does not fit in 24 bits, and 0 on success. The largest reload is 224 − 1, so at 8 MHz the longest single period is about 2.1 s. CMSIS-Core reference 

volatile uint32_t g_ms;               /* written in the ISR, read in main */

void SysTick_Handler(void) {
    g_ms++;                          /* one millisecond has passed */
}

/* in main(): 8 MHz / 1000 = 8000 ticks per millisecond */
if (SysTick_Config(SystemCoreClock / 1000U) != 0U) {
    /* reload too large: pick a bigger tick period */
}

The variable is volatile because the handler changes it outside the normal flow of main (lesson 46). A 32-bit aligned load is a single bus access on the Cortex-M3, so reading g_ms cannot tear. A timestamp of two or more words, such as a 64-bit count, would need a critical section (lesson 57).

Wrap-safe millis() and timeouts

g_ms is a 32-bit counter, so it wraps after 232 ms, which is about 49.7 days. A check such as now >= deadline is wrong after the wrap: the deadline is then larger than the current time, and the timeout never expires, or expires at once. The fix is to subtract the start time, and do the subtraction in uint32_t. Unsigned arithmetic is modulo 232 (lesson 45), so the difference is the elapsed time as long as it is less than 231 ms. 

static uint8_t timed_out(uint32_t start_ms, uint32_t timeout_ms) {
    return (uint32_t)(millis() - start_ms) >= timeout_ms;
}
Compare with the unsigned subtraction, not with a deadline you computed as start + timeout. The deadline itself can wrap. Lesson 55 uses the same rule for the non-blocking blink, and the solution checks the wrap by starting the counter 256 ms before zero.

Why HAL_Delay depends on the SysTick priority

The STM32F1 HAL keeps its own counter, uwTick, and HAL_Delay() busy-waits until that counter has advanced. The counter moves only when HAL_IncTick() runs, which the template calls from SysTick_Handler. HAL_Init() starts SysTick through HAL_InitTick() with the priority TICK_INT_PRIORITY, which the template's configuration file sets to 0x0F, the lowest priority (stm32f1xx_hal.c, stm32f1xx_hal_conf.h).

Now the hazard. If code runs at a higher priority than SysTick (a lower number) and calls HAL_Delay(), SysTick cannot preempt it. uwTick stops moving, and the loop never ends. The delay is not slow: it is blocked forever.

Never call HAL_Delay() from an interrupt or from code that runs with a higher priority than SysTick. Either move the work to the main loop, or give SysTick a higher priority with HAL_NVIC_SetPriority(SysTick_IRQn, ...) and accept that the timebase now runs inside your critical path.

Model answer

Configure SysTick for a 1 kHz interrupt with SysTick_Config, or the reload for your clock. In the handler, increment a volatile uint32_t. millis() returns that value. For timeouts, never compare absolute times, because they wrap after about 49.7 days. Store the start time, and test (uint32_t)(now - start) against the timeout. The unsigned subtraction is correct across the wrap, as long as the timeout is shorter than half the range. Two more points: the SysTick priority must be low enough that it does not starve, and it must be high enough that a blocking HAL_Delay still sees it advance.
