SysTick and a millisecond time base

Almost every firmware timeout needs a clock that ticks at a known rate. The Cortex-M core has one built in: SysTick. Get the reload value right, and make the timeout arithmetic survive the counter wrap.

By the end of this lesson you can start SysTick at 1 kHz with SysTick_Config, keep a volatile uint32_t millisecond counter in the handler, write a wrap-safe millis() and timeout check, and explain why the HAL's HAL_Delay depends on the SysTick priority.

Where we are and why it matters

Lesson 55 showed a super-loop that blinks an LED without stopping the CPU, and it needed a clock to decide when the next toggle was due. Lesson 71 built timers from hardware counters, and it showed the plus-one rule for the reload. This lesson uses the same idea for the one timer that every Cortex-M part has, and it uses it for a job that most products need: a millisecond clock for timeouts, retries, debouncing and periodic work.

A product needs this constantly. A sensor driver waits for a conversion and gives up after 50 ms. A modem is retried every 500 ms. A display refreshes at 60 Hz and a watchdog must be fed before a deadline. Each of these needs a counter that a person can read in milliseconds, and each of them can fail in a way that only shows after days of running. The counter wraps, or the priority of the wrong interrupt blocks the clock, or the clock was configured for the wrong frequency. This lesson covers all three.

Concept 1: SysTick is in the core, not the chip

The SysTick timer is a small counter built into the Cortex-M3 core itself. The STM32F1 peripherals in lesson 71, such as TIM2, are chip blocks with their own clocks and pins. SysTick is part of the processor, so it has the same register block on every STM32F1 part, and its name is the same whatever the vendor. The Cortex-M3 Programming Manual calls it the SysTick timer, and CMSIS gives its registers the names SysTick->LOAD, SysTick->VAL and SysTick->CTRL. PM0056 Rev 7, section 4.5, the SysTick timer Because SysTick is in the core, the same code works on every STM32F1 part. The timers in lesson 71 are chip peripherals, so their names and clock trees differ between parts.

The counter is 24 bits wide. The CMSIS header defines the reload mask as 0xFFFFFF, so the largest value that LOAD can hold is 224 − 1 (core_cm3.h). It is a down counter. It loads the value from LOAD, counts down to zero, and then reloads and starts again. When it reaches zero, it sets its flag, and if the interrupt is enabled it raises the SysTick exception (PM0056 Rev 7, section 4.5.1). The VAL register holds the current count, and writing to it clears the counter (PM0056 Rev 7, section 4.5.3).

Concept 2: the reload sets the period

The period of the interrupt is the number of clock cycles between two zero crossings. The counter goes from LOAD down to 0, which is LOAD + 1 values, and then reloads. So the period is LOAD + 1 cycles, and to get a period of N cycles you write LOAD = N − 1 (PM0056 Rev 7, section 4.5.2). This is the same off-by-one rule as in lesson 71, with the direction reversed: a timer that counts up stops at ARR, and SysTick counts down to zero.

At an 8 MHz core clock, a tick of 1 ms is 8000 cycles, so the reload is 8000 − 1 = 7999. The solution uses the same calculation in code: SystemCoreClock / 1000U gives 8000, and SysTick_Config() subtracts one. The interrupt then fires once per millisecond. Figure 1 shows the sawtooth the counter draws.

Concept 3: an interrupt turns the counter into a clock

SysTick does not keep a time by itself. It only raises an exception once per period. The clock is the software that counts those exceptions. The handler adds one to a global variable, and the rest of the program reads that variable. This pattern is common in embedded C, and the variable is the time base. It is a count of milliseconds since the start, and it is useful only if every reader sees the same, current value.

The handler and main() share the variable, so it must be volatile. The handler changes it outside the normal flow of main, and the compiler cannot see that. Without volatile, the compiler may keep the value in a register inside a loop that waits for it to change, and the loop never ends (lesson 46). A 32-bit aligned load is a single bus access on the Cortex-M3, so reading the counter cannot tear, which means the reader never sees half an old value and half a new one. That is true for 32 bits on this core. A timestamp of two or more words, such as a 64-bit count, would need a critical section (lesson 57).

Concept 4: SysTick_Config does three jobs

The CMSIS function SysTick_Config(ticks) in core_cm3.h does the setup in one call. It checks that the reload fits, writes LOAD = ticks − 1, sets the SysTick interrupt to the lowest priority, clears the counter, and enables the counter, its clock source and the interrupt. It returns 1 if the reload does not fit in 24 bits, and 0 on success. The lowest priority is (1 << __NVIC_PRIO_BITS) − 1, which is 15 on this device (PM0056 Rev 7, section 4.4.8, gives the 0 to 15 range of the system handler priority fields). That is the code's own statement of the rule in lesson 72. CMSIS-Core reference

The largest reload is 224 − 1 (PM0056 Rev 7, section 4.5.2, range 0x00000001 to 0x00FFFFFF), so the longest single period is 224 cycles. At 8 MHz that is 2 097 152 µs, about 2.1 s. A longer period needs a prescaled clock, or a count of several SysTick periods. 

volatile uint32_t g_ms;               /* written in the ISR, read in main */

void SysTick_Handler(void) {
    g_ms++;                          /* one millisecond has passed */
}

/* in main(): 8 MHz / 1000 = 8000 ticks per millisecond */
if (SysTick_Config(SystemCoreClock / 1000U) != 0U) {
    /* reload too large: pick a bigger tick period */
}

The handler is one increment. Its name, SysTick_Handler, is the name the vector table expects, so the linker places its address in the right slot (lesson 68). The g_ms variable is at file scope and volatile, so every read and write goes to memory. The call to SysTick_Config() uses SystemCoreClock, which holds the core clock frequency that SystemCoreClockUpdate() reads from the clock registers. Using the variable instead of the number 8 000 000 means the same line works after the clock changes. The if checks the return value, so a clock too fast for a 24-bit reload is caught at start-up.

Worked example: the reload, the wrap and the elapsed time

Take the solution's configuration, and walk through what the counter does with real numbers.

  1. The clock is 8 MHz, so SystemCoreClock / TICK_HZ is 8 000 000 ÷ 1000 = 8000. SysTick_Config(8000) writes LOAD = 7999.
  2. The counter loads 7999 and counts down. It reaches zero after 8000 cycles, which is 1 ms. The exception runs, g_ms goes up by one, and the counter reloads.
  3. The solution then sets g_ms = 0xFFFFFF00. That number is 232 − 256, or −256 if you read it as a signed value. It is 256 ms before the counter wraps back to zero.
  4. After 256 ms the handler has added 256, so g_ms is 0, and the solution prints WRAP passed on the line after its START line. Seeing that line is the first check that the timer is running.
  5. The timeout starts at 0xFFFFFF00 and is 2000 ms long. When the time is 2000 ms after the start, g_ms is 2000 − 256 = 1744 after the wrap. The unsigned subtraction 1744 − 0xFFFFFF00 is taken modulo 232, which is 1744 + 256 = 2000. So the elapsed time is 2000 ms, and the timeout expires.

Step 5 is the important one. The raw comparison of 1744 with the deadline 0xFFFFFF00 + 2000 gives the wrong answer, and the next section explains why. The subtraction gives the right answer because it is done in unsigned arithmetic, which wraps around at 232.

Concept 5: wrap-safe millis() and timeouts

g_ms is a 32-bit counter, so it wraps after 232 ms. That is 4 294 967 296 ms, or about 49.7 days. A product that runs for longer than that will see the wrap, so the code must handle it from the start. A check such as now >= deadline is wrong after the wrap. If the deadline was computed as start + timeout and it passes 232, the deadline is a small number, and the check is true at once. Or the deadline is a large number, and the check never becomes true.

The fix is to store the start time, and to subtract it from the current time in uint32_t. Unsigned arithmetic is modulo 232 (lesson 45), so the difference is the elapsed time, as long as it is less than 231 ms. A timeout longer than that is a different design problem, and it needs a longer counter. The solution's timed_out() is written in exactly this way. 

static uint8_t timed_out(uint32_t start_ms, uint32_t timeout_ms) {
    return (uint32_t)(millis() - start_ms) >= timeout_ms;
}

The line subtracts the start from the current time, which is millis(), and casts the result to uint32_t. The cast is not needed on a 32-bit core, but it states the intent: the subtraction is unsigned and wraps. The comparison with timeout_ms is then a comparison of two small numbers, and it is correct no matter where the wrap happened.

Compare with the unsigned subtraction, not with a deadline you computed as start + timeout. The deadline itself can wrap. Lesson 55 uses the same rule for the non-blocking blink, and the solution checks the wrap by starting the counter 256 ms before zero.

Follow the worked example on a timeline. The counter starts at 0xFFFFFF00, 256 ms before the wrap, and the timeout is 2000 ms. The deadline computed as start + timeout wraps to 1744, so the comparison with it says the timeout has expired before any time has passed. The subtraction is right the whole way.

Concept 6: the HAL's time base uses the same SysTick

The STM32 HAL has its own millisecond counter, uwTick, and it sets SysTick up for that counter. HAL_Init() calls HAL_InitTick(), which uses the reload of one millisecond and sets the SysTick priority to TICK_INT_PRIORITY (stm32f1xx_hal.c). The template's configuration file sets that value to 0x0FU, which is the lowest priority, 15 (stm32f1xx_hal_conf.h). The template's SysTick_Handler calls HAL_IncTick(), which adds the tick frequency to uwTick (templates/stm32-hal/main.c).

HAL_Delay() is a busy-wait. It reads HAL_GetTick() at the start, and then loops until the value has moved on by the requested amount (stm32f1xx_hal.c). The loop does not sleep. It needs SysTick to run, so that uwTick advances. And that brings in the priority.

Here is the hazard. If code runs at a higher priority than SysTick (a lower number) and calls HAL_Delay(), SysTick cannot preempt it, because the rule from lesson 72 says a handler is only preempted by a more urgent interrupt. uwTick stops moving, so the loop never ends and the delay blocks forever. This is why a HAL program that calls HAL_Delay() inside a high-priority interrupt hangs, and why the HAL sets SysTick to the lowest priority by default.

Never call HAL_Delay() from an interrupt or from code that runs with a higher priority than SysTick. Either move the work to the main loop, or give SysTick a higher priority with HAL_NVIC_SetPriority(SysTick_IRQn, ...) and accept that the timebase now runs inside your critical path.

Common mistakes and how to spot them

The first mistake is a wrong clock. The reload is calculated from a clock frequency that is not the real one. Suppose the code assumes 72 MHz, which is the PLL output from lesson 40, but the core is still on the 8 MHz HSI. The reload is 72 000 − 1, so each tick takes 72 000 cycles at 8 MHz, which is 9 ms. The symptom is that a 2000 ms timeout appears to take 18 seconds, and the LED blinks at a ninth of the expected rate. The fix is to use SystemCoreClock, after SystemCoreClockUpdate() has read the real clock, as the solution does.

The second mistake is forgetting the minus one. A reload of 8000 gives 8001 cycles per tick, which is 1.000125 ms. The error is small, about 0.0125 %, and it is hard to notice in a short test. Over one hour the clock drifts by 0.45 s. The symptom is a time base that is slightly slow, which shows up only in a long test or in a comparison with a reference clock. The fix is the rule LOAD = ticks − 1, which SysTick_Config() applies for you.

The third mistake is the raw comparison after a wrap. A timeout written as if (millis() >= start + 2000) looks correct, and it works until the counter passes 232. With start = 0xFFFFFF00, the deadline wraps to 1744, and the test is true at once. The symptom is a TIMEOUT line that prints immediately after the wrap, or a timeout that never fires. The fix is the unsigned subtraction in timed_out().

The fourth mistake is calling HAL_Delay() at a high priority. A handler at priority 0 calls it, and SysTick at priority 15 cannot preempt the handler. The symptom is that the board stops responding: no more output on the serial monitor, the LED stops, and a debugger shows the program stuck in the busy-wait loop of HAL_Delay. The fix is to move the delay out of the interrupt, or to give SysTick a higher priority, as the warning above says.

The fifth mistake is a time base without volatile. The handler increments g_ms, and a loop waits for it to reach a value. In an optimised build, the compiler may read g_ms once and keep it in a register, so the loop never sees the change. The symptom is a program that works in a debug build and hangs in a release build. The fix is the volatile qualifier on the variable, as in the code above.

In real projects

On a product, the millisecond time base is one of the first things a team writes, and it is usually the same few lines as in this lesson. Most firmware exposes it as a function, such as millis() or get_tick(), and every other module uses it for timeouts. A real-time kernel needs a periodic tick too, and on Cortex-M parts it is common to use SysTick for that tick. The glossary calls this the tick, and it is usually 1 kHz, so one tick is 1 ms.

A senior engineer reviewing timer code checks four things. The clock frequency comes from a variable that is updated when the clock changes, and not from a constant. The reload has the minus one, ideally inside a helper such as SysTick_Config(). Every timeout uses the unsigned subtraction, and no deadline is stored as an absolute time that can wrap. The priority of SysTick is documented, and every blocking call is checked for the priority it runs at.

Summary

  • SysTick is a 24-bit down counter in the Cortex-M core. It raises SysTick_Handler each time it reaches zero.
  • The period is LOAD + 1 cycles, so a 1 kHz tick at 8 MHz uses LOAD = 7999.
  • SysTick_Config() writes LOAD, sets SysTick to the lowest priority (15), clears the counter and starts it. It returns 1 if the reload does not fit in 24 bits.
  • The millisecond counter is a volatile uint32_t that the handler increments and the rest of the program reads.
  • A 32-bit millisecond counter wraps after about 49.7 days. Timeouts must subtract the start time in unsigned arithmetic, never compare absolute times.
  • The HAL's HAL_Delay() busy-waits on uwTick, which SysTick advances. Called from a higher-priority handler, it hangs.
  • Use SystemCoreClock, not a constant, for the reload, so a clock change does not silently slow every timeout.
