SysTick and a millisecond time base

The core timer behind every firmware timeout

By the end of this lesson you can start SysTick at 1 kHz with SysTick_Config, keep a volatile uint32_t millisecond counter in the handler, write a wrap-safe millis() and timeout check, and explain why the HAL's HAL_Delay depends on the SysTick priority.

A clock for timeouts and periodic work

Lesson 55 showed a super-loop that blinks an LED without stopping the CPU, which needed a clock to decide when the next toggle was due, and lesson 71 built timers from hardware counters with the plus-one rule for the reload. This lesson applies the same idea to the one timer every Cortex-M part has, for a job most products need, a millisecond clock for timeouts, retries, debouncing and periodic work.

A product needs this constantly: a sensor driver waits for a conversion and gives up after 50 ms, a modem is retried every 500 ms, a display refreshes at 60 Hz and a watchdog must be fed before a deadline. Each needs a counter readable in milliseconds, and each can fail in a way that shows only after days of running, because the counter wraps, the wrong interrupt's priority blocks the clock or the clock was configured for the wrong frequency, and this lesson covers all three.

SysTick as part of the Cortex-M core

The SysTick timer is a small counter built into the Cortex-M3 core itself. The STM32F1 peripherals of lesson 71, such as TIM2, are chip blocks with their own clocks and pins, whereas SysTick belongs to the processor, so it has the same register block on every STM32F1 part and the same name whatever the vendor, the Cortex-M3 Programming Manual calling it the SysTick timer and CMSIS naming its registers SysTick->LOAD, SysTick->VAL and SysTick->CTRL (PM0056 Rev 7, section 4.5, the SysTick timer). Because SysTick is in the core, the same code works on every STM32F1 part. The timers in lesson 71 are chip peripherals, so their names and clock trees differ between parts.

The counter is 24 bits wide, the CMSIS header defining the reload mask as 0xFFFFFF, so the largest value LOAD can hold is 224 − 1 (core_cm3.h). It counts down, loading the value from LOAD, counting to zero and then reloading, and on reaching zero it sets its flag and, with the interrupt enabled, raises the SysTick exception (PM0056 Rev 7, section 4.5.1), while VAL holds the current count and a write to it clears the counter (PM0056 Rev 7, section 4.5.3).

The reload value and the period

The interrupt period is the number of clock cycles between two zero crossings, and since the counter goes from LOAD down to 0, LOAD + 1 values, before reloading, the period is

T = (LOAD + 1) ÷ fcore(1)

where fcore is the core clock, so a period of N cycles needs LOAD = N − 1 (PM0056 Rev 7, section 4.5.2), the off-by-one rule of lesson 71 with the direction reversed, an up-counting timer stopping at ARR while SysTick counts down to zero.

At an 8 MHz core clock a 1 ms tick is 8 000 cycles, so the reload is 8 000 − 1 = 7 999, which the solution computes in code, SystemCoreClock / 1000U giving 8 000 and SysTick_Config() subtracting one, so that the interrupt fires once per millisecond. Figure 1 shows the sawtooth the counter draws.

A software time base from the SysTick interrupt

SysTick keeps no time by itself, raising only one exception per period, and the clock is the software counting those exceptions, the handler adding one to a global variable that the rest of the program reads. This common pattern in embedded C makes the variable the time base, a count of milliseconds since the start, useful only if every reader sees the same, current value.

The handler and main() share the variable, so it must be volatile, because the handler changes it outside the normal flow of main where the compiler cannot see it, and without the qualifier the compiler may keep the value in a register inside a waiting loop that then never ends (lesson 46). A 32-bit aligned load is a single bus access on the Cortex-M3, so reading the counter cannot tear and the reader never sees half an old value and half a new one, which holds for 32 bits on this core, whereas a timestamp of two or more words, such as a 64-bit count, would need a critical section (lesson 57).

SysTick resembles a kitchen timer that rings every millisecond and restarts itself, keeping no time on its own, while the handler is someone making a tally mark at each ring and millis() is counting the marks, so a missed ring, because interrupts were off too long, leaves the tally behind the real time. A person would notice a ring missed while busy, however, whereas the firmware loses the tick silently, since the NVIC holds only one pending SysTick at a time.

The three jobs of SysTick_Config

The CMSIS function SysTick_Config(ticks) in core_cm3.h does the setup in one call, checking that the reload fits, writing LOAD = ticks − 1, setting the SysTick interrupt to the lowest priority, clearing the counter and enabling the counter, its clock source and the interrupt, and returning 1 if the reload does not fit in 24 bits and 0 on success. The lowest priority is (1 << __NVIC_PRIO_BITS) − 1, 15 on this device (PM0056 Rev 7, section 4.4.8, gives the 0 to 15 range of the system handler priority fields), the code's own statement of the rule of lesson 72 (CMSIS-Core reference).

The largest reload is 224 − 1 (PM0056 Rev 7, section 4.5.2, range 0x00000001 to 0x00FFFFFF), so the longest single period is 224 cycles, at 8 MHz 2 097 152 µs or about 2.1 s, and a longer period needs a prescaled clock or a count of several SysTick periods. 

volatile uint32_t g_ms;               /* written in the ISR, read in main */

void SysTick_Handler(void) {
    g_ms++;                          /* one millisecond has passed */
}

/* in main(): 8 MHz / 1000 = 8000 ticks per millisecond */
if (SysTick_Config(SystemCoreClock / 1000U) != 0U) {
    /* reload too large: pick a bigger tick period */
}

The handler is one increment, and its name, SysTick_Handler, is the one the vector table expects, so the linker places its address in the right slot (lesson 68), while g_ms is a file-scope volatile variable, so every read and write goes to memory. The call to SysTick_Config() uses SystemCoreClock, the core clock frequency that SystemCoreClockUpdate() reads from the clock registers, so the same line stays correct after a clock change, unlike the literal 8 000 000, and the if checks the return value, catching at start-up a clock too fast for a 24-bit reload.

Worked example: the reload, the wrap and the elapsed time

We take the solution's configuration and follow the counter with real numbers. Before reading the steps, predict what a 2 000 ms timeout started 256 ms before the wrap reports as its elapsed time.

  1. Compute the reload. At 8 MHz SystemCoreClock / TICK_HZ is 8 000 000 ÷ 1 000 = 8 000, so SysTick_Config(8000) writes LOAD = 7999.
  2. Run one tick. The counter loads 7 999 and counts down, reaching zero after 8 000 cycles, 1 ms, when the exception runs, g_ms rises by one and the counter reloads.
  3. Move to the wrap. The solution sets g_ms = 0xFFFFFF00, which is 232 − 256, or −256 read as a signed value, 256 ms before the counter wraps to zero.
  4. Pass the wrap. After 256 ms the handler has added 256, so g_ms is 0 and the solution prints WRAP passed on the line after its START line, the first sign that the timer runs.
  5. Measure the timeout. The 2 000 ms timeout starts at 0xFFFFFF00, so 2 000 ms later g_ms is 2 000 − 256 = 1 744, and the unsigned subtraction 1744 − 0xFFFFFF00, taken modulo 232, gives 1 744 + 256 = 2 000, so the elapsed time is 2 000 ms and the timeout expires.

Step 5 is the important one, because the raw comparison of 1 744 with the deadline 0xFFFFFF00 + 2 000 gives the wrong answer, as the next section explains, while the subtraction is right because unsigned arithmetic wraps at 232.

Wrap-safe millis() and timeouts

g_ms is a 32-bit counter, so it wraps after 232 ms, 4 294 967 296 ms or about 49.7 days, and a product running longer than that will meet the wrap, so the code must handle it from the start. A check such as now >= deadline fails after the wrap, because a deadline computed as start + timeout that passes 232 becomes a small number, making the check true at once, or else stays large, so that the check never becomes true.

The fix is to store the start time and subtract it from the current time in uint32_t, giving

telapsed = (now − start) mod 232(2)

where now and start are millisecond counts, a result that unsigned arithmetic produces by itself (lesson 45) and that is the true elapsed time as long as it is below 231 ms, a longer timeout being a different design problem that needs a longer counter. The solution's timed_out() is written exactly this way. 

static uint8_t timed_out(uint32_t start_ms, uint32_t timeout_ms) {
    return (uint32_t)(millis() - start_ms) >= timeout_ms;
}

The line subtracts the start from the current time, millis(), and casts the result to uint32_t, a cast unnecessary on a 32-bit core but stating the intent that the subtraction is unsigned and wraps, so the comparison with timeout_ms is between two small numbers and correct wherever the wrap happened.

Compare with the unsigned subtraction, not with a deadline you computed as start + timeout. The deadline itself can wrap. Lesson 55 uses the same rule for the non-blocking blink, and the solution checks the wrap by starting the counter 256 ms before zero.

The deadline computed as start + timeout wraps to 1 744, so the comparison with it reports the timeout as expired before any time has passed, while the subtraction stays right throughout.

The HAL time base on the same SysTick

The STM32 HAL keeps its own millisecond counter, uwTick, and sets SysTick up for it, HAL_Init() calling HAL_InitTick(), which uses a one-millisecond reload and sets the SysTick priority to TICK_INT_PRIORITY (stm32f1xx_hal.c), a value the template's configuration file sets to 0x0FU, the lowest priority, 15 (stm32f1xx_hal_conf.h). The template's SysTick_Handler calls HAL_IncTick(), which adds the tick frequency to uwTick (templates/stm32-hal/main.c).

HAL_Delay() is a busy-wait, reading HAL_GetTick() at the start and looping until the value has moved on by the requested amount (stm32f1xx_hal.c), without sleeping, so it needs SysTick running for uwTick to advance, which brings in the priority.

Code running at a higher priority than SysTick, a lower number, that calls HAL_Delay() cannot be preempted by SysTick, because by the rule of lesson 72 only a more urgent interrupt preempts a handler, so uwTick stops, the loop never ends and the delay blocks forever. This is why a HAL program calling HAL_Delay() inside a high-priority interrupt hangs, and why the HAL gives SysTick the lowest priority by default.

Never call HAL_Delay() from an interrupt or from code that runs with a higher priority than SysTick. Either move the work to the main loop, or give SysTick a higher priority with HAL_NVIC_SetPriority(SysTick_IRQn, ...) and accept that the timebase now runs inside your critical path.

Common mistakes and how to spot them

A reload computed for the wrong clock

A 2 000 ms timeout appears to take 18 s and the LED blinks at a ninth of the expected rate, because the code assumed 72 MHz, the PLL output of lesson 40, while the core still runs on the 8 MHz HSI, so a reload of 72 000 − 1 makes each tick 72 000 cycles at 8 MHz, or 9 ms. Use SystemCoreClock after SystemCoreClockUpdate() has read the real clock, as the solution does.

The minus one forgotten

The time base runs slightly slow, which shows only in a long test or against a reference clock, because a reload of 8 000 gives 8 001 cycles per tick, 1.000125 ms, an error of about 0.0125 % that drifts by 0.45 s per hour. Apply LOAD = ticks − 1, which SysTick_Config() does automatically.

A raw comparison after the wrap

A TIMEOUT line prints immediately after the wrap, or a timeout never fires, because if (millis() >= start + 2000) works only until the counter passes 232, and with start = 0xFFFFFF00 the deadline wraps to 1 744 and the test is true at once. Use the unsigned subtraction of timed_out().

HAL_Delay called at a high priority

The board stops responding, the serial output and the LED stopping while a debugger shows the program stuck in the busy-wait of HAL_Delay, because a handler at priority 0 called it and SysTick at priority 15 cannot preempt the handler. Move the delay out of the interrupt, or give SysTick a higher priority, as the warning above says.

A time base without volatile

The program works in a debug build and hangs in a release build, because without volatile on g_ms the optimiser may read it once into a register, so a loop waiting for it to reach a value never sees the change. Declare the variable volatile, as in the code above.

Millisecond time bases in products and kernels

On a product the millisecond time base is among the first things a team writes, usually in the same few lines as here, exposed as a function such as millis() or get_tick() that every other module uses for timeouts. A real-time kernel also needs a periodic tick, commonly taken from SysTick on Cortex-M parts, the tick of the glossary, usually at 1 kHz, so that one tick is 1 ms.

A senior engineer reviewing timer code checks that the clock frequency comes from a variable updated when the clock changes rather than from a constant, that the reload includes the minus one, ideally inside a helper such as SysTick_Config(), that every timeout uses the unsigned subtraction with no deadline stored as an absolute time that can wrap, and that the SysTick priority is documented, with every blocking call checked for the priority it runs at.

Summary

  • SysTick is a 24-bit down counter in the Cortex-M core that raises SysTick_Handler each time it reaches zero.
  • The period is LOAD + 1 cycles, so a 1 kHz tick at 8 MHz uses LOAD = 7999.
  • SysTick_Config() writes LOAD, sets SysTick to the lowest priority (15), clears the counter and starts it, returning 1 if the reload does not fit in 24 bits.
  • The millisecond counter is a volatile uint32_t that the handler increments and the rest of the program reads.
  • A 32-bit millisecond counter wraps after about 49.7 days, so timeouts subtract the start time in unsigned arithmetic instead of comparing absolute times.
  • The HAL's HAL_Delay() busy-waits on uwTick, which SysTick advances, so called from a higher-priority handler it hangs.
  • The reload is computed from SystemCoreClock rather than a constant, so a clock change cannot silently slow every timeout.
