Bench lab 10: Measure interrupt latency

Pin-to-pin interrupt response time

By the end of this lab you can measure the time from a pin edge to an ISR's first output, convert it to CPU cycles, and say which part is the hardware and which part is your handler.

What the analyzer can see

Lesson 34 gave a number, twelve cycles from an interrupt request to the first instruction of the handler, and lesson 72 wired a button to the NVIC. This lab puts both ends of that path on a logic analyzer and counts what your own code adds. It is optional, needing the NUCLEO-U545RE-Q from bench lab 9 and a logic analyzer with PulseView, it does not count towards your progress, and it takes about 50 minutes.

Lesson 34's twelve cycles come from the Cortex-M3 Technical Reference Manual and assume memory with no wait states. Arm's own table of zero-wait-state interrupt latencies lists 12 cycles for the Cortex-M3 and M4, 15 for the M0+ and 16 for the M0 (Arm community blog: interrupt latency of the Cortex-M processors), but it does not include the Cortex-M33 in your Nucleo, so this lab measures it together with everything around it.

A logic analyzer cannot see the first instruction of the handler, because it sees only pins. The measurement therefore runs from the edge that causes the interrupt to the edge your handler makes, and that path holds more than the core's entry sequence.

  1. the GPIO input synchroniser and the EXTI edge detector, a few clock cycles;
  2. the NVIC and exception entry: stacking eight registers and fetching the vector;
  3. the handler's instructions up to and including the store to GPIOA->BSRR;
  4. the bus write reaching the GPIO port and the output driver switching.

The core runs from MSIS at 4 MHz, its reset clock, so one cycle is 250 ns. A 24 MS/s analyzer samples every 41.7 ns, about six samples per cycle, which is enough to count cycles.

Wiring

  • Analyzer D0 to PC13 (ST morpho CN7 pin 23): the B1 button, high while pressed.
  • Analyzer D1 to PA5 (CN10 pin 11, also Arduino D13): the response pin, which also lights LD2.
  • Analyzer GND to any GND pin of the Nucleo.

The on-board button is enough, although a pushbutton from a 3.3 V pin to PC13 works the same way if B1 is hard to reach with the probes on. Keep PC13 an input with its pull-down, because UM3062 warns against driving it low, since pressing B1 then shorts 3.3 V to the pin.

On the board: measure the starter

  1. Build projects/bench10-irq-latency/starter and copy build/blink.bin to the ST-LINK drive, as in bench lab 9. The VCP prints BENCH10 ready at 4000000 Hz.
  2. In PulseView, sample at 24 MHz (or the highest your analyzer offers), trigger on a rising edge of D0 and press B1.
  3. Put cursors on the PC13 rising edge and the PA5 rising edge and write down the time, repeating for ten presses. A button bounces (bench lab 4), so use only the first edge of each press.
  4. Convert to cycles as time ÷ 250 ns.

The starter is written the way a generic driver layer often is. Its handler loops over all sixteen EXTI lines to find the pending one and calls a callback through a function pointer, and the callback formats a log entry with snprintf() before it drives the pin, so every one of those steps runs before the edge you measure.

On the board: make the response fast

Change the handler so that the pin write is its first statement and the bookkeeping comes afterwards, as projects/bench10-irq-latency/solution does. 

void EXTI13_IRQHandler(void) {
    GPIOA->BSRR = 1U << LED_PIN;                     /* respond first */
    EXTI->RPR1 = EXTI_RPR1_RPIF13;                   /* then clear: writing 1 clears the flag */
    presses++;
}

Measure again, then account for the result in a table. It lists the measured cycles, the cycles you expect for exception entry, the instructions before the store (look at them with arm-none-eabi-objdump -d build/blink.elf and find EXTI13_IRQHandler) and the remainder, which is the synchroniser, EXTI and output path. Lesson 34 gave the M3's entry, so your remainder tells you how close the M33 is to it.

Two experiments finish the lab.

  • Jitter. Over ten presses the delay is not constant, because the main loop is in the middle of some instruction when the request arrives, and the core finishes or abandons it first. Note the spread in cycles.
  • The instruction cache. The U5's ICACHE is off after reset. Add ICACHE->CR |= ICACHE_CR_EN; at the start of main() and measure again. At 4 MHz the flash needs no wait states, so expect the effect to be small, and see whether your numbers agree.
You have timed an interrupt to the cycle on real silicon, and you can tell which part of the delay is yours to fix.

Common mistakes and how to spot them

The pin-to-pin time called the interrupt latency

Your figure is larger than the core's published entry time, because the pin-to-pin time includes the input path and your handler's first instructions. Say exactly what you measured.

A bounce edge measured

One press shows a suspiciously short delay, because a later bounce edge landed in the middle of the handler. Use the first rising edge after a long low.

The pending flag cleared as the very last instruction

The handler runs twice for one press, because the clearing write can still be on its way through the bus when the handler returns, so the NVIC sees the request still asserted. Clear the flag early, right after the response, as the solution does.

Sampling too slowly

You see that the starter is slow but cannot count the solution's cycles, because at 1 MS/s the analyzer resolves only 4 cycles. Sample at 24 MS/s.

Summary

  • A pin-to-pin measurement contains the input synchroniser, EXTI, the NVIC, exception entry, the handler's first instructions and the output path.
  • At 4 MHz one cycle is 250 ns, and a 24 MS/s analyzer resolves about a sixth of that.
  • A generic dispatcher and logging before the response cost far more than the hardware does, so the handler responds first and does the bookkeeping afterwards.
  • Arm's twelve-cycle figure is for the M3 and M4 with zero-wait-state memory, and the M33's figure is what you measured minus your accounted extras.
The disassembly of your handler: arm-none-eabi-objdump -d build/blink.elf, then search for <EXTI13_IRQHandler>:. In the solution it's a handful of instructions; in the starter, follow the call into the callback and count how much runs before the store to BSRR.
