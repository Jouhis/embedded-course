PWM: dimming, servos, tones

A pin cannot output 1.6 V, but it can switch fast enough that the average looks like 1.6 V. PWM does that with a counter, a wrap value and a compare. The same three numbers give you a dimmed LED, a 50 Hz servo signal and a buzzer tone.

By the end of this lesson you can compute the PWM frequency and duty cycle of an RP2040 slice from the system clock, the clock divider and the wrap value, and set up a dimmed LED, a 50 Hz servo signal and a 440 Hz tone with the Pico SDK.

Where we are and why it matters

Lesson 58 read an analogue voltage into the Pico. This lesson goes the other way. A GPIO pin can only be high or low, at the supply voltage or at 0 V, so it cannot set a motor to half speed or a heater to 40 per cent. Lesson 25 showed a shift register that drives outputs in bulk, but it still only switches them on and off. PWM is the standard way to get an average voltage out of a digital output: switch the pin fast, and vary how long it stays high.

You will see PWM in many products that move something or dim something. A printer's hotend and bed heaters are driven by PWM through a MOSFET, so the controller can set the average power. A brushless fan or a DC motor takes a PWM speed signal. A hobby servo reads the width of a pulse to choose its angle, and a piezo buzzer makes a tone at the frequency of the signal on its pin. The Pico has dedicated PWM hardware for all of these, so the CPU does not have to toggle the pin in software.

The concepts, one at a time

Four ideas make up PWM: the duty cycle, the counter that defines the period, the compare value that sets the duty cycle, and the clock divider that sets the speed of the counter. Each one is simple, and the formula that combines them is short.

Duty cycle is the fraction of time high

A PWM output is a square wave: it is high for part of each period and low for the rest. The duty cycle is the fraction of one period that the output spends high, usually given in percent. A 1 kHz signal that is high for 250 µs of each 1 ms period has a duty cycle of 25 %. The datasheet describes the output in these terms: the fraction of time spent high is the duty cycle, and the averaged output voltage follows that fraction RP2040 datasheet, section 4.5.1. The output of a filtered PWM signal is its duty cycle times the supply. A 25 % duty cycle on a 3.3 V pin averages to about 0.83 V, once any ripple has been filtered out.

The reason it works is that the load responds to the average, not the peaks. An LED's brightness and a heater's temperature both follow the energy delivered over many periods. A motor's speed follows its average voltage. None of them can follow a 1 kHz square wave one edge at a time, so they see the average.

Flick a light switch on and off very fast, on for a quarter of each cycle. The room looks a quarter as bright, because your eye averages the flashes. The LED is never half on: it is fully on or fully off, and the duty cycle sets the share of time it spends on.

The counter sets the period

Each PWM slice is a 16-bit counter that counts from 0 up to a wrap value, which the datasheet calls TOP. When it reaches TOP, it wraps back to 0 and starts again. The RP2040 has eight identical slices, and each slice has two outputs, A and B, so there are 16 PWM channels in total. All 30 GPIO pins can drive PWM RP2040 datasheet, section 4.5.1.

The pin map is fixed. GP0 is slice 0 A, GP1 is slice 0 B, GP2 is slice 1 A, and so on up to GP15 as slice 7 B. The mapping repeats from GP16, so GP16 is slice 0 A again RP2040 datasheet, section 4.5.2, Table 515. Two outputs in the same slice share one counter, so they share one period. Two outputs on different slices can have different periods.

The compare sets the duty cycle

Each channel has a compare value, called CC, that is compared with the counter on every tick. The output is high while the counter is below CC, and low once it reaches CC. So a larger CC means a longer high time. The datasheet puts it as: when the input value is higher than the counter, the output is driven high RP2040 datasheet, section 4.5.2.1. The average output, as a fraction of the supply, is CC divided by TOP + 1.

The two ends are clean. A CC of 0 keeps the output always low, which is 0 %. A CC equal to TOP + 1 keeps it always high, which is 100 %, and the datasheet says both ends are glitch-free RP2040 datasheet, section 4.5.2.2. That is why the solution's LED can reach fully on without a special case.

  1. The slice's counter climbs one step per tick from 0 to TOP, then wraps to 0. With TOP = 9 one period is 10 ticks; two periods are drawn.
  2. Set CC = 3. On every tick the output is high while the counter is below CC, so it is high for counts 0, 1 and 2: 3 ticks of 10, a 30 % duty cycle.
  3. Raise CC to 7. The period does not change, because TOP sets it; only the high time grows, to 70 %.
  4. CC = 0: the counter is never below 0, so the output stays low. 0 %, with no glitch.
  5. CC = TOP + 1 = 10: the counter is always below it, so the output never goes low. 100 %, which is why an LED can reach full brightness without a special case.

The clock divider sets the speed

The clock divider DIV slows the counter. It is an 8-bit integer with a 4-bit fraction, so it can divide the system clock by 1.0 up to 255.9375, and the datasheet states that it slows the count by up to a factor of 256 RP2040 datasheet, section 4.5.2.4. The SDK's header puts the same rule in one line: the counter runs at the system clock divided by the divider pico-sdk, hardware/pwm.h.

The datasheet's period rule is built from these pieces. The slice counts from 0 to TOP, which is TOP + 1 steps, and each step lasts DIV system clock cycles. So the period in clock cycles is (TOP + 1) × DIV, and the frequency is the system clock divided by that RP2040 datasheet, section 4.5.2.6. The equation itself is an image in the PDF, so the SDK's rule is the one to check against. 

/* frequency = clk_sys / (DIV * (TOP + 1)) */
/* duty cycle = compare / (TOP + 1)        */
/* example: 125 MHz, DIV 125, TOP 19999 gives 125e6 / (125 * 20000) = 50 Hz */
Read the system clock with clock_get_hz(clk_sys) instead of assuming 125 MHz. The code in this lesson does that.

Worked example: a 50 Hz servo frame, one number at a time

A hobby servo expects a frame of 20 ms, which is 50 Hz, and it reads the width of a pulse inside that frame. Build the PWM setup for it from the three numbers, with the system clock at 125 MHz.

  1. Pick the tick. Choose a counter rate that makes the pulse easy to count. A divider of 125 gives 125 MHz ÷ 125 = 1 MHz, so one tick is exactly 1 µs. Now the compare value is the pulse width in microseconds.
  2. Count the ticks in one frame. A 20 ms frame at 1 µs per tick is 20,000 ticks. The counter counts from 0 to TOP and then wraps, so TOP + 1 must equal 20,000.
  3. Set TOP. TOP = 20,000 − 1 = 19,999. Check the frequency with the formula: 125 MHz ÷ (125 × 20,000) = 50 Hz.
  4. Set the pulse. A pulse of 1.5 ms is 1500 ticks, so CC = 1500. The duty cycle is 1500 ÷ 20,000 = 7.5 %, which is the 1.5 ms pulse divided by the 20 ms frame.

The same three steps give any PWM output. Pick the divider so the tick is convenient, count the ticks in one period, and set TOP to that count minus one. Then the compare is a count, and it is always a count of ticks, never a percentage. The starter's planted bug is the second step: it sets TOP to 1999, which is 2000 ticks, or 2 ms, and that gives 500 Hz.

Check the worked example in the configurator, then load the starter's TOP = 1999 and see the frequency it really gives. Type a target such as 1 kHz at 25 % to find DIV, TOP and CC for the dimmer.

Dimming, a servo, and a tone

The same three numbers serve three jobs. Each job chooses different values.

A PC fan with a 4-pin connector is driven the same way. The fourth wire carries a PWM signal at about 25 kHz, above what people hear, and the duty cycle sets the fan speed. The motherboard changes one compare value as the CPU gets warmer, which is the same call you make for a dimmer LED.

Dimming. Choose a frequency high enough that the eye does not see flicker, such as 1 kHz. Then set the compare to a fraction of TOP + 1 with the potentiometer. The LED's brightness follows the average, so a 25 % duty cycle looks dimmer than full on, although how much dimmer depends on how the eye responds at this frequency and on the LED.

Servo. The servo reads the pulse width in each 20 ms frame. Wokwi's servo part has a PWM input, a 5 V supply pin and ground, and it sweeps from 0 to 180 degrees between hard stops Wokwi, servo part. The pulse widths that match those two ends are not given on that page. Most hobby servos use about 1 ms for one end and 2 ms for the other, but the exact limits vary from model to model, so check the datasheet of the servo you buy. The solution maps the potentiometer onto 1000 to 2000 µs, and the comment marks those values as the usual range.

Tone. A piezo buzzer makes a sound at the frequency of the square wave on its pin, so a 50 % duty cycle at 440 Hz gives a clean A4 tone. Wokwi's buzzer part is driven from its pins 1 and 2 Wokwi, buzzer part. For 440 Hz, a DIV of 8 keeps TOP inside 16 bits: 125 MHz ÷ (8 × 440) − 1 = 35,510.4, which the code truncates to 35,510. At that TOP the frequency is 440.0 Hz, to within a tenth of a hertz.

The code, line by line

The solution's pwm_start() helper sets up one slice, and main() uses it three times. Read the helper first, because every output goes through it. 

static void pwm_start(uint gpio, float div, uint16_t top) {
    gpio_set_function(gpio, GPIO_FUNC_PWM);
    uint slice = pwm_gpio_to_slice_num(gpio);
    pwm_config cfg = pwm_get_default_config();
    pwm_config_set_clkdiv(&cfg, div);
    pwm_config_set_wrap(&cfg, top);
    pwm_init(slice, &cfg, true);
}
  1. gpio_set_function(gpio, GPIO_FUNC_PWM) routes the pin to the PWM block instead of the GPIO logic. Without it, the pin stays an ordinary output and never switches on its own.
  2. pwm_gpio_to_slice_num(gpio) finds the slice from the pin, using the mapping in Table 515. The caller never has to remember which slice a pin belongs to.
  3. pwm_get_default_config() returns a configuration with the SDK defaults, so the fields you do not set are known values.
  4. pwm_config_set_clkdiv(&cfg, div) stores the divider. The SDK takes a float and converts it to the 8.4 fixed-point register field, which is why the solution passes 125.0 and 8.0 as floats.
  5. pwm_config_set_wrap(&cfg, top) stores TOP, the 16-bit wrap value.
  6. pwm_init(slice, &cfg, true) writes the configuration to the slice and starts it. The final argument is true, so the counter runs at once.
int main(void) {
    /* ... setup omitted ... */
    uint32_t sys_hz = clock_get_hz(clk_sys);   /* usually 125 MHz, but read it, do not assume it */

    /* LED: 1 kHz, TOP = sys / (div * 1 kHz) - 1, with div chosen so the tick is 1 MHz. */
    float tick_div = (float)sys_hz / (float)TICK_HZ;   /* 125 MHz / 1 MHz = 125 */
    uint16_t led_top = (uint16_t)(TICK_HZ / LED_HZ - 1);   /* 1000 ticks per period: TOP = 999 */
    pwm_start(LED_PIN, tick_div, led_top);

    /* Servo: 50 Hz on the 1 MHz tick. TOP + 1 = 1,000,000 / 50 = 20,000 ticks, so TOP = 19999. */
    uint16_t servo_top = (uint16_t)(TICK_HZ / SERVO_HZ - 1);
    pwm_start(SERVO_PIN, tick_div, servo_top);

    /* Buzzer: 440 Hz with a 50 % duty cycle. Its TOP is found from the frequency, not guessed. */
    uint16_t tone_top = (uint16_t)((float)sys_hz / (TONE_DIV * TONE_HZ) - 1.0f);
    pwm_start(BUZZER_PIN, TONE_DIV, tone_top);
    pwm_set_gpio_level(BUZZER_PIN, (tone_top + 1) / 2);
    /* ... */
}
  1. clock_get_hz(clk_sys) reads the system clock the chip is actually running at. Every TOP in the program is derived from this number, so a different clock setting gives correct frequencies without editing the code.
  2. The LED's divider is tick_div, which is 125 at the default clock. The LED's TOP is 999, so the period is 1000 ticks of 1 µs, which is 1 kHz.
  3. The servo uses the same divider, so its tick is the same 1 µs. Its TOP is 19,999, which makes the frame 20,000 ticks, or 20 ms.
  4. The buzzer's TOP comes from the formula, not from a memorised number. It divides the clock by the divider and by 440, then subtracts 1. The cast to uint16_t truncates the result to 35,510.
  5. pwm_set_gpio_level(BUZZER_PIN, (tone_top + 1) / 2) sets the compare to half of TOP + 1. That is a 50 % duty cycle, which gives a square wave.
while (true) {
    uint16_t pot = read_pot();

    /* LED duty: pot 0..4095 maps to level 0..TOP+1. A level equal to TOP+1 would be 100 %. */
    uint32_t led_level = (uint32_t)pot * (led_top + 1) / (POT_FULL + 1);
    pwm_set_gpio_level(LED_PIN, (uint16_t)led_level);

    /* Servo: the pulse width is the level in ticks (1 us each). Map the pot to 1000..2000 us. */
    uint32_t servo_us = SERVO_MIN_US + (uint32_t)pot * (SERVO_MAX_US - SERVO_MIN_US) / POT_FULL;
    pwm_set_gpio_level(SERVO_PIN, (uint16_t)servo_us);
    /* ... */
}
  1. pot is the 12-bit reading from lesson 58, from 0 to 4095. Both outputs are scaled from it.
  2. The LED's level is pot × (TOP + 1) ÷ 4096. The multiplication is done in 32 bits before the division, so the intermediate value cannot overflow. With the pot at its top code of 4095, the level is 999, which is TOP, not TOP + 1, so the LED runs just short of 100 % from the pot. That is harmless, and the comment states the rule for the 100 % case.
  3. The servo's level is a count of microseconds, because each tick is 1 µs. The formula maps 0 to 4095 onto 1000 to 2000 ticks, so the pulse is the value in microseconds.
  4. pwm_set_gpio_level() writes the compare register for the channel. The write takes effect at the next wrap, so the output does not glitch mid-period.

Common mistakes and how to spot them

Mistake 1: TOP is the count, not the period. Symptom: the servo frequency is twice what you wanted. Setting TOP to 1999 gives 2000 ticks, which is 2 ms, so the frame is 500 Hz, and a servo that expects 20 ms may jitter or not settle. Fix: the number of ticks in one period is TOP + 1, so set TOP to that count minus one, and check the frequency with the formula.

Mistake 2: the compare is a count, not a percentage. Symptom: the servo hardly moves. A compare of 50 is 50 ticks, which is 50 µs at a 1 MHz tick, far shorter than the 1 ms pulse a servo needs. Fix: compute the compare from the tick count, so 1.5 ms at 1 µs per tick is 1500.

Mistake 3: two outputs on one slice with different frequencies. Symptom: the second output runs at the first one's frequency, however you set it. The two channels share TOP and DIV, so one setting covers both. Fix: put the outputs that need different frequencies on different slices. The starter's three outputs are on three slices for exactly this reason. Check the pin map before you assign pins.

Mistake 4: assuming the clock. Symptom: all the frequencies are off by the same ratio after you change the clock setting. The formula uses the system clock, and the constant 125 MHz is only the default. Fix: read the clock with clock_get_hz(clk_sys), as the solution does.

Mistake 5: no function set on the pin. Symptom: the LED stays on or off and never dims, and the PWM registers look right in the debugger. The pin is still an ordinary GPIO output, so the PWM block drives nothing. Fix: call gpio_set_function(pin, GPIO_FUNC_PWM) before starting the slice, as pwm_start() does.

In real projects

Professional PWM use is about the power stage, not the pin. A heater, a fan or a motor is driven through a MOSFET or a motor driver, and the PWM frequency is chosen to avoid audible whine and to keep the switching losses low. The datasheet mentions this use: the PWM block is used for switch-mode power electronics, and its 0 % and 100 % outputs are glitch-free, which the datasheet says matters when a MOSFET is driven at its minimum and maximum current levels RP2040 datasheet, sections 4.5.1 and 4.5.2.2.

A reviewer expects three things in a PWM driver. The frequency is computed from the clock, not written as a constant. The compare is clamped to the range from 0 to TOP + 1, so a bad input cannot produce a wrong pulse. And the duty cycle is documented in the unit the caller uses, which is percent for a fan and microseconds for a servo.

Summary

  • PWM sets an average voltage by switching a pin, and the duty cycle is the fraction of each period the output is high.
  • The RP2040 has eight slices and 16 channels, and all 30 GPIO pins can drive PWM. Table 515 maps each pin to its slice and channel.
  • The period is (TOP + 1) × DIV system clock cycles, so the frequency is the clock divided by that. The SDK's header gives the counter rate as the clock divided by DIV.
  • The compare is a count of ticks, and the duty cycle is CC ÷ (TOP + 1). CC = 0 gives 0 %, and CC = TOP + 1 gives 100 %.
  • Both outputs of a slice share one period. Put outputs with different frequencies on different slices.
  • Read the clock with clock_get_hz(clk_sys). Set the pin's function to PWM before starting the slice.
  • A servo reads the pulse width in a 20 ms frame. The usual pulse range is about 1 to 2 ms, but check the datasheet of the servo you use.
RP2040 datasheet, section 4.5 (PWM): read 4.5.2.1 for the duty cycle, 4.5.2.2 for the glitch-free ends, 4.5.2.4 for the clock divider, 4.5.2.6 for the period, and Table 515 for the pin map. The period equation in 4.5.2.6 is an image in the PDF, so check it against the SDK's pwm.h.
