PWM

Pulse-width modulation for dimming, servos and tones

By the end of this lesson you can compute the PWM frequency and duty cycle of an RP2040 slice from the system clock, the clock divider and the wrap value, and set up a dimmed LED, a 50 Hz servo signal and a 440 Hz tone with the Pico SDK.

An average voltage from a digital pin

Lesson 58 read an analogue voltage into the Pico, and this lesson goes the other way. A GPIO pin can only be high or low, at the supply voltage or at 0 V, so it cannot run a motor at half speed or a heater at 40 per cent, and the shift register of lesson 25 drives outputs in bulk but still only switches them on and off. PWM is the standard way to get an average voltage out of a digital output, switching the pin fast and varying how long it stays high.

PWM appears in many products that move or dim something. A printer's hotend and bed heaters are driven by PWM through a MOSFET so that the controller can set the average power, a brushless fan or a DC motor takes a PWM speed signal, a hobby servo reads the width of a pulse to choose its angle, and a piezo buzzer makes a tone at the frequency of the signal on its pin. The Pico has dedicated PWM hardware for all of these, so the CPU need not toggle the pin in software.

Duty cycle

Four ideas make up PWM, the duty cycle, the counter that defines the period, the compare value that sets the duty cycle and the clock divider that sets the counter's speed, each simple and combined by a short formula. A PWM output is a square wave, high for part of each period and low for the rest, and its duty cycle is the fraction of one period spent high, usually given in percent, so a 1 kHz signal that is high for 250 µs of each 1 ms period has a duty cycle of 25 %. The datasheet describes the output in these terms, the fraction of time spent high being the duty cycle, which the averaged output voltage follows RP2040 datasheet, section 4.5.1. A filtered PWM signal settles at its duty cycle times the supply, so a 25 % duty cycle on a 3.3 V pin averages to about 0.83 V once the ripple has been filtered out.

It works because the load responds to the average rather than the peaks. An LED's perceived brightness and a heater's temperature both follow the energy delivered over many periods and a motor's speed follows its average voltage, and since none of them can follow a 1 kHz square wave edge by edge, they see the average.

Flicking a light switch on and off very fast, on for a quarter of each cycle, makes the room look a quarter as bright, because the eye averages the flashes. The LED is never half on but fully on or fully off, the duty cycle setting its share of time on. The comparison breaks for slow loads, though, because a hand on a switch cannot reach the switching rate at which a heater or motor stops following individual pulses.

The PWM counter and its period

Each PWM slice is a 16-bit counter that counts from 0 up to a wrap value, which the datasheet calls TOP, and then wraps back to 0 and starts again. The RP2040 has eight identical slices, each with two outputs, A and B, giving 16 PWM channels in total, and all 30 GPIO pins can drive PWM RP2040 datasheet, section 4.5.1.

The pin map is fixed, GP0 being slice 0 A, GP1 slice 0 B, GP2 slice 1 A and so on up to GP15 as slice 7 B, with the mapping repeating from GP16, which is slice 0 A again RP2040 datasheet, section 4.5.2, Table 515. The two outputs of a slice share one counter and therefore one period, whereas outputs on different slices can have different periods.

The compare value

Each channel has a compare value, CC, which is compared with the counter on every tick, the output being high while the counter is below CC and low once it reaches CC, so a larger CC means a longer high time. The datasheet puts it as the output being driven high when the input value is higher than the counter RP2040 datasheet, section 4.5.2.1, and the duty cycle is

D = CC ÷ (TOP + 1)(1)

where CC is the compare value and TOP + 1 the number of ticks per period. The two ends are clean, a CC of 0 keeping the output always low at 0 % and a CC of TOP + 1 keeping it always high at 100 %, and the datasheet states that both ends are glitch-free RP2040 datasheet, section 4.5.2.2, which is why the solution's LED can reach fully on without a special case.

  1. The slice's counter climbs one step per tick from 0 to TOP, then wraps to 0. With TOP = 9 one period is 10 ticks; two periods are drawn.
  2. Set CC = 3. On every tick the output is high while the counter is below CC, so it is high for counts 0, 1 and 2: 3 ticks of 10, a 30 % duty cycle.
  3. Raise CC to 7. The period does not change, because TOP sets it; only the high time grows, to 70 %.
  4. CC = 0: the counter is never below 0, so the output stays low. 0 %, with no glitch.
  5. CC = TOP + 1 = 10: the counter is always below it, so the output never goes low. 100 %, which is why an LED can reach full brightness without a special case.

The clock divider and the frequency formula

The clock divider DIV slows the counter. It is an 8-bit integer with a 4-bit fraction, dividing the system clock by 1.0 up to 255.9375, and the datasheet states that it slows the count by up to a factor of 256 RP2040 datasheet, section 4.5.2.4, while the SDK's header states the same rule in one line, the counter running at the system clock divided by the divider pico-sdk, hardware/pwm.h.

The datasheet's period rule follows from these pieces. The slice counts from 0 to TOP, which is TOP + 1 steps of DIV system clock cycles each, so the frequency is

f = fsys ÷ (DIV × (TOP + 1))(2)

where fsys is the system clock RP2040 datasheet, section 4.5.2.6. The equation appears only as an image in the PDF, so the SDK's rule is the text to check against, and the code comment below states both formulas. 

/* frequency = clk_sys / (DIV * (TOP + 1)) */
/* duty cycle = compare / (TOP + 1)        */
/* example: 125 MHz, DIV 125, TOP 19999 gives 125e6 / (125 * 20000) = 50 Hz */
Read the system clock with clock_get_hz(clk_sys) instead of assuming 125 MHz, as the code in this lesson does.

Worked example: a 50 Hz servo frame

A hobby servo expects a 20 ms frame, 50 Hz, and reads the width of a pulse inside it, so we build its PWM setup from the three numbers with the system clock at 125 MHz. Before starting, predict what TOP must be if each tick lasts 1 µs.

  1. Pick the tick. A counter rate that makes the pulse easy to count is best, and a divider of 125 gives 125 MHz ÷ 125 = 1 MHz, exactly 1 µs per tick, so that the compare value equals the pulse width in microseconds.
  2. Count the ticks in one frame. A 20 ms frame at 1 µs per tick is 20 000 ticks, and since the counter counts from 0 to TOP before wrapping, TOP + 1 must equal 20 000.
  3. Set TOP. TOP = 20 000 − 1 = 19 999, and equation (2) confirms the frequency, 125 MHz ÷ (125 × 20 000) = 50 Hz.
  4. Set the pulse. A 1.5 ms pulse is 1 500 ticks, so CC = 1 500, and equation (1) gives a duty cycle of 1 500 ÷ 20 000 = 7.5 %, the 1.5 ms pulse divided by the 20 ms frame.

The same steps give any PWM output: pick the divider so that the tick is convenient, count the ticks in one period and set TOP to that count minus one, after which the compare is always a count of ticks and never a percentage. The starter's planted bug lies in the second step, setting TOP to 1999, which is 2 000 ticks, or 2 ms, and gives 500 Hz.

The configurator below confirms the worked example. Then load the starter's TOP = 1999 to see the frequency it really gives, and type a target such as 1 kHz at 25 % to find DIV, TOP and CC for the dimmer.

Dimming, servo pulses and tones

The same three numbers serve three jobs, each choosing different values.

A PC fan with a 4-pin connector is driven the same way, its fourth wire carrying a PWM signal at about 25 kHz, above the range of hearing, whose duty cycle sets the fan speed. The motherboard changes one compare value as the CPU warms up, the same call that dims an LED.

For dimming, the frequency must be high enough that the eye sees no flicker, such as 1 kHz, and the potentiometer sets the compare as a fraction of TOP + 1. The LED's brightness follows the average, so a 25 % duty cycle looks dimmer than full on, although how much dimmer depends on how the eye responds at this frequency and on the LED.

A servo reads the pulse width in each 20 ms frame. Wokwi's servo part has a PWM input, a 5 V supply pin and ground and sweeps from 0 to 180 degrees between hard stops Wokwi, servo part, but that page does not give the pulse widths matching the two ends. Most hobby servos use about 1 ms for one end and 2 ms for the other, with exact limits varying from model to model, so check the datasheet of the servo you buy; the solution maps the potentiometer onto 1 000 to 2 000 µs, with a comment marking those values as the usual range.

A piezo buzzer sounds at the frequency of the square wave on its pin, so a 50 % duty cycle at 440 Hz gives a clean A4 tone, and Wokwi's buzzer part is driven from its pins 1 and 2 Wokwi, buzzer part. For 440 Hz a DIV of 8 keeps TOP within 16 bits, since 125 MHz ÷ (8 × 440) − 1 ≈ 35 510.4, which the code truncates to 35 510, giving 440.0 Hz to within a tenth of a hertz.

The PWM setup code line by line

The solution's pwm_start() helper sets up one slice and main() uses it three times, so the helper comes first, since every output goes through it. 

static void pwm_start(uint gpio, float div, uint16_t top) {
    gpio_set_function(gpio, GPIO_FUNC_PWM);
    uint slice = pwm_gpio_to_slice_num(gpio);
    pwm_config cfg = pwm_get_default_config();
    pwm_config_set_clkdiv(&cfg, div);
    pwm_config_set_wrap(&cfg, top);
    pwm_init(slice, &cfg, true);
}
  1. gpio_set_function(gpio, GPIO_FUNC_PWM) routes the pin to the PWM block instead of the GPIO logic, without which the pin stays an ordinary output and never switches on its own.
  2. pwm_gpio_to_slice_num(gpio) finds the pin's slice from the mapping in Table 515, so the caller never has to remember it.
  3. pwm_get_default_config() returns a configuration with the SDK defaults, so the fields left unset hold known values.
  4. pwm_config_set_clkdiv(&cfg, div) stores the divider, the SDK converting the float into the 8.4 fixed-point register field, which is why the solution passes 125.0 and 8.0 as floats.
  5. pwm_config_set_wrap(&cfg, top) stores TOP, the 16-bit wrap value.
  6. pwm_init(slice, &cfg, true) writes the configuration to the slice and, with its final argument true, starts the counter at once.
int main(void) {
    /* ... setup omitted ... */
    uint32_t sys_hz = clock_get_hz(clk_sys);   /* usually 125 MHz, but read it, do not assume it */

    /* LED: 1 kHz, TOP = sys / (div * 1 kHz) - 1, with div chosen so the tick is 1 MHz. */
    float tick_div = (float)sys_hz / (float)TICK_HZ;   /* 125 MHz / 1 MHz = 125 */
    uint16_t led_top = (uint16_t)(TICK_HZ / LED_HZ - 1);   /* 1000 ticks per period: TOP = 999 */
    pwm_start(LED_PIN, tick_div, led_top);

    /* Servo: 50 Hz on the 1 MHz tick. TOP + 1 = 1,000,000 / 50 = 20,000 ticks, so TOP = 19999. */
    uint16_t servo_top = (uint16_t)(TICK_HZ / SERVO_HZ - 1);
    pwm_start(SERVO_PIN, tick_div, servo_top);

    /* Buzzer: 440 Hz with a 50 % duty cycle. Its TOP is found from the frequency, not guessed. */
    uint16_t tone_top = (uint16_t)((float)sys_hz / (TONE_DIV * TONE_HZ) - 1.0f);
    pwm_start(BUZZER_PIN, TONE_DIV, tone_top);
    pwm_set_gpio_level(BUZZER_PIN, (tone_top + 1) / 2);
    /* ... */
}
  1. clock_get_hz(clk_sys) reads the system clock the chip is actually running at, and since every TOP in the program derives from it, a different clock setting still gives correct frequencies without code changes.
  2. The LED's divider is tick_div, 125 at the default clock, and its TOP is 999, so the period is 1 000 ticks of 1 µs, or 1 kHz.
  3. The servo uses the same divider and therefore the same 1 µs tick, and its TOP of 19 999 makes the frame 20 000 ticks, or 20 ms.
  4. The buzzer's TOP comes from the formula rather than a memorised number, dividing the clock by the divider and by 440 and subtracting 1, with the cast to uint16_t truncating the result to 35 510.
  5. pwm_set_gpio_level(BUZZER_PIN, (tone_top + 1) / 2) sets the compare to half of TOP + 1, a 50 % duty cycle that gives a square wave.
while (true) {
    uint16_t pot = read_pot();

    /* LED duty: pot 0..4095 maps to level 0..TOP+1. A level equal to TOP+1 would be 100 %. */
    uint32_t led_level = (uint32_t)pot * (led_top + 1) / (POT_FULL + 1);
    pwm_set_gpio_level(LED_PIN, (uint16_t)led_level);

    /* Servo: the pulse width is the level in ticks (1 us each). Map the pot to 1000..2000 us. */
    uint32_t servo_us = SERVO_MIN_US + (uint32_t)pot * (SERVO_MAX_US - SERVO_MIN_US) / POT_FULL;
    pwm_set_gpio_level(SERVO_PIN, (uint16_t)servo_us);
    /* ... */
}
  1. pot is the 12-bit reading of lesson 58, from 0 to 4 095, from which both outputs are scaled.
  2. The LED's level is pot × (TOP + 1) ÷ 4096, with the multiplication done in 32 bits before the division so that the intermediate value cannot overflow. At the pot's top code of 4 095 the level is 999, which is TOP rather than TOP + 1, so the pot leaves the LED just short of 100 %, which is harmless, and the comment states the rule for the 100 % case.
  3. The servo's level is a count of microseconds, because each tick is 1 µs, and the formula maps 0 to 4 095 onto 1 000 to 2 000 ticks.
  4. pwm_set_gpio_level() writes the channel's compare register, and the write takes effect at the next wrap, so the output does not glitch mid-period.

Common mistakes and how to spot them

TOP taken as the tick count

The servo frame runs at ten times the intended rate, so a servo that expects 20 ms may jitter or fail to settle, because TOP set to 1999 gives 2 000 ticks, 2 ms, or 500 Hz. The number of ticks per period is TOP + 1, so set TOP to that count minus one and check the frequency with the formula.

The compare written as a percentage

The servo hardly moves, because a compare of 50 is 50 ticks, 50 µs at a 1 MHz tick, far shorter than the 1 ms pulse a servo needs. Compute the compare from the tick count, so 1.5 ms at 1 µs per tick is 1 500.

Two frequencies on one slice

The second output runs at the first one's frequency however it is set, because the two channels share TOP and DIV. Put outputs that need different frequencies on different slices, as the starter's three outputs are, and check the pin map before assigning pins.

An assumed system clock

All the frequencies are off by the same ratio after a change to the clock setting, because the formula depends on the system clock and 125 MHz is only the default. Read the clock with clock_get_hz(clk_sys), as the solution does.

No PWM function on the pin

The LED stays on or off and never dims although the PWM registers look right in the debugger, because the pin is still an ordinary GPIO output that the PWM block does not drive. Call gpio_set_function(pin, GPIO_FUNC_PWM) before starting the slice, as pwm_start() does.

PWM power stages and driver reviews

Professional PWM work concerns the power stage more than the pin. A heater, fan or motor is driven through a MOSFET or a motor driver, with the PWM frequency chosen to avoid audible whine and to keep switching losses low, and the datasheet mentions this use, describing the PWM block as suitable for switch-mode power electronics and its glitch-free 0 % and 100 % outputs as important when a MOSFET is driven at its minimum and maximum current levels RP2040 datasheet, sections 4.5.1 and 4.5.2.2.

A reviewer expects a PWM driver to compute its frequency from the clock rather than a constant, to clamp the compare to the range 0 to TOP + 1 so that a bad input cannot produce a wrong pulse, and to document the duty cycle in the caller's unit, percent for a fan and microseconds for a servo.

Summary

  • PWM sets an average voltage by switching a pin, the duty cycle being the fraction of each period the output is high.
  • The RP2040 has eight slices and 16 channels, all 30 GPIO pins can drive PWM, and Table 515 maps each pin to its slice and channel.
  • The period is (TOP + 1) × DIV system clock cycles, so the frequency is the clock divided by that, and the SDK's header gives the counter rate as the clock divided by DIV.
  • The compare is a count of ticks and the duty cycle CC ÷ (TOP + 1), with CC = 0 giving 0 % and CC = TOP + 1 giving 100 %.
  • Both outputs of a slice share one period, so outputs with different frequencies belong on different slices.
  • The clock is read with clock_get_hz(clk_sys), and the pin's function is set to PWM before the slice starts.
  • A servo reads the pulse width in a 20 ms frame, usually about 1 to 2 ms, but the datasheet of the servo in use has the final say.
RP2040 datasheet, section 4.5 (PWM): read 4.5.2.1 for the duty cycle, 4.5.2.2 for the glitch-free ends, 4.5.2.4 for the clock divider, 4.5.2.6 for the period, and Table 515 for the pin map. The period equation in 4.5.2.6 is an image in the PDF, so check it against the SDK's pwm.h.
