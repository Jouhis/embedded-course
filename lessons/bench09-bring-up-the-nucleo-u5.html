Bench lab 9: Bring up the Nucleo-U5

Lesson 67's blink ran on a simulated Blue Pill. Here it moves to a real STM32U5 board, a newer chip with a different core, a different RCC, a different GPIO block and a programmer built into the board. Half the code carries over. This lab finds the other half.

This bench lab is optional. It needs a NUCLEO-U545RE-Q and a USB-C cable. It doesn't count towards your progress. Time: about 50 minutes.
By the end of this lab you can flash a Nucleo board over its ST-LINK, port register-level code from the STM32F1 to the STM32U5, and read the chip's ID and clock over the virtual COM port.

The board

The NUCLEO-U545RE-Q carries an STM32U545RE: a Cortex-M33 with 512 KB of flash and 272 KB of SRAM, running up to 160 MHz (kewl.org board notes). The "-Q" means the chip's internal SMPS supplies its core. The board manual, UM3062, gives the pins this lab needs (ST UM3062, Nucleo-64 boards MB1841):

  • LD2, the green user LED, on PA5, driven through a transistor: active high (section 6.5).
  • B1, the blue user button, on PC13: high while pressed (section 6.6).
  • The STLINK-V3EC on the top of the board: a debugger, a USB drive for drag-and-drop flashing, and a virtual COM port (VCP) wired to USART1 on PA9 (TX) and PA10 (RX).

The ST-LINK is the Blue Pill's missing piece. On the Blue Pill you needed a separate programmer and a USB-to-serial adapter; here one USB-C cable powers the board, flashes it and carries the serial log.

What changes between the F1 and the U5

The CMSIS core header is the same idea on both chips: SysTick, NVIC_EnableIRQ() and __WFI() work unchanged. The device header changes. The course now builds the U5 projects against ST's cmsis-device-u5 package in third_party/ (STMicroelectronics/cmsis-device-u5 on GitHub), and its stm32u545xx.h is where every name in this lab comes from.

The 4 MHz figure is in ST's system_stm32u5xx.c: "After each device reset the MSI (4 MHz) is used as system clock source". A baud-rate divisor written for 8 MHz gives half the baud rate, and the terminal shows garbage or nothing.

Build and flash

  1. Build the starter: python tools/build.py projects/bench09-nucleo-u5-bringup/starter. The build writes build/blink.elf and build/blink.bin. There is no Wokwi stage: Wokwi has no STM32U5 model.
  2. Plug the board in. A USB drive appears (the ST-LINK's mass storage), and a new serial port (the VCP). Copy blink.bin onto the drive. The ST-LINK's COM LED flickers while it programs the flash, the drive reconnects, and the chip runs the new program. STM32CubeProgrammer or OpenOCD over SWD do the same job if you prefer a tool.
  3. Open the Serial Monitor on the VCP at 115200 baud. With the starter: no LED, no text. The program runs, but every write goes to a port with no clock, a pin in analog mode, or a USART at the wrong speed.

On the board: port the four places

The starter's main.c marks four places. Fix them one at a time, rebuild, copy the .bin again, and watch what changes.

  1. Clock gating. Find the GPIOA enable in RCC_AHB2ENR1. Without it, writes to GPIOA are ignored (lesson 67's clock gating, same rule, different register).
  2. PA5 as an output. MODER5 = 01. Push-pull and low speed are the reset values. The LED now flashes once a second.
  3. PA9 as USART1_TX. MODER9 = 10 (alternate function) and AFSEL9 = 7 in AFR[1].
  4. The baud rate. Use SystemCoreClock instead of a constant. 4 000 000 / 115 200 = 34.7, so BRR = 35: 114 286 baud, 0.8 % slow, well inside the few percent a UART tolerates.

The VCP now prints BENCH9 OK: STM32 DEV_ID=0x... REV_ID=0x..., 4000000 Hz and one beat line per flash. The device ID is read from DBGMCU->IDCODE, the same register the debugger reads to tell which chip it is talking to. Compare yours with the "Device ID" STM32CubeProgrammer shows when it connects.

You've brought up a second ARM family from its registers and your own build. Every later Nucleo lab starts from this blink.

Common mistakes
  1. Copying the F1 register names. Most of them don't exist in the U5 header, so the compiler stops you. The dangerous ones are names that exist on both chips with a different meaning or position. Look every name up in stm32u545xx.h.
  2. Forgetting that U5 pins start in analog mode. A pin you never configured reads 0, whatever the voltage on it.
  3. Driving PC13 low. UM3062 warns that B1 connects PC13 to 3.3 V when pressed. Keep PC13 an input with a pull-down; an output driving low shorts the supply through the button.
  4. Hard-coding the clock. Use SystemCoreClock after SystemCoreClockUpdate(), so the divisors follow when you change the clock later.

Summary

  • The NUCLEO-U545RE-Q has LD2 on PA5, B1 on PC13 and an STLINK-V3EC with drag-and-drop flashing and a VCP on USART1 (PA9/PA10).
  • Porting from the F1 to the U5 changes the RCC enable registers, the GPIO configuration (MODER, AFR) and the USART register names; the CMSIS core API stays the same.
  • The U5 starts on MSIS at 4 MHz, and its pins start in analog mode.
  • The build writes a .bin for the ST-LINK drive; this board has no Wokwi model, so the bench is the only test.
ST's system_stm32u5xx.c in third_party/cmsis-device-u5/Source/Templates/: read SystemInit() and SystemCoreClockUpdate(), about 150 lines, and find where the 4 MHz comes from and how the function decodes the RCC registers to compute SystemCoreClock.
