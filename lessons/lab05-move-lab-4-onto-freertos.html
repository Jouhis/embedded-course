Lab 5: Move Lab 4 onto FreeRTOS

The Lab 4 monitor runs in one super-loop. In this lab you split it into four tasks with deadlines, share the I2C bus with a mutex, move the buttons to an interrupt and a queue, and let one logger task own the UART. The application modules stay the same; the structure changes.

By the end of this lab you can turn a super-loop into FreeRTOS tasks with vTaskDelayUntil(), feed an interrupt into a task through a queue, protect a shared bus with a mutex, route all output through one logger task, and read each task's stack high-water mark.

The idea

Lesson 86 showed the problem: in Lab 4, a 100 ms display redraw can make the 200 ms sensor sample miss its window. Lab 5 fixes that by giving the sensor its own higher-priority task. The UI task owns the display and the menu. A logger task owns the UART, so two tasks never write to the serial line at once. The I2C bus is shared by the sensor and the UI, so it has a mutex (lesson 91).

Where we are and why it matters

Lab 4 ran the whole monitor in one loop. Each pass read the sensor, updated the display, and checked the buttons, one after another. Lesson 86 showed why that breaks: the loop does work in a fixed order, so a long job delays everything behind it. There a 100 ms redraw made the 200 ms sensor sample start late and miss its window. Lessons 87 to 91 gave you the pieces that solve this: tasks with priorities, queues, semaphores and mutexes. This lab puts them together in a real firmware structure, which is what a product team builds when a super-loop stops being enough.

The same shape turns up in many products. A thermostat samples a sensor on a schedule, drives a display on demand, and logs to a serial port for service staff. A battery monitor must read its gauge on time while a user is pressing buttons. In each case the designer must answer three questions: which work is urgent, which resources are shared, and who is allowed to write to each output. The lab asks you to answer those questions in code.

Tasks, priorities and preemption

A task is an independent thread of execution with its own stack (lesson 87). The FreeRTOS scheduler decides which ready task runs on the core at each moment. Each task has a priority, and in FreeRTOS a larger number means more urgent. The project sets configUSE_PREEMPTION to 1, so when a more urgent task becomes ready, the scheduler switches to it at once, even if a less urgent task is in the middle of its work. This is called preemption.

The lab uses four tasks: sensor at priority 3, ui at 2, and logger and stats at 1. Priority 3 for the sensor reflects its timing: it must sample every 200 ms, and a late sample is simply lost time. The UI draws every 500 ms and can wait a few milliseconds without harm. The logger and the stats task only print text, so they are the least urgent. Notice that the sensor's priority does not stop it from sharing the bus, which the mutex handles separately.

A task that waits for time must not spin. The sensor uses vTaskDelayUntil(), which blocks the task until a fixed tick count, so the CPU runs other tasks during the wait. The UI waits on a queue with a timeout, which blocks it until either an event arrives or one draw period passes. A blocked task costs no CPU, and that is the reason the scheduler can be efficient.

Queues carry data between tasks and interrupts

A queue is a kernel object that copies fixed-size items from one place to another. xQueueSend() copies an item in, and xQueueReceive() copies one out. The copy matters: the sender does not keep a pointer to data that the receiver may still be reading. The lab's ui_queue holds ui_event_t structures, and log_queue holds text lines of 96 characters each.

Interrupts cannot wait. An interrupt service routine (ISR) runs in the middle of whatever the CPU was doing, and it must finish quickly so that the next interrupt is not delayed. FreeRTOS therefore provides separate calls for use inside an ISR, with the suffix FromISR. The lab's button handler uses xQueueSendFromISR(), which never blocks. If that send wakes a task that is more urgent than the one interrupted, the handler sets a flag, and portYIELD_FROM_ISR() makes the scheduler switch when the interrupt returns. The rule is simple: an ISR calls only FromISR functions, and it never waits.

A mutex guards the I2C bus

The sensor and the display both use the I2C bus. An I2C transfer is a sequence of bits on two wires, and two transfers at once corrupt each other. A mutex is a semaphore with an owner. Only the task that took it can give it back, and FreeRTOS supports priority inheritance on it, so a low-priority owner is raised while a higher-priority task waits (lesson 91). The lab sets configUSE_MUTEXES to 1 and creates i2c_mutex with xSemaphoreCreateMutex().

The rule is that a task takes the mutex only around the bus call, and gives it back before it does anything else. The glossary says a mutex is for tasks, not interrupts, and the lab keeps the ISR away from the bus for that reason. A binary semaphore would also stop two users at once, but it has no owner, so nothing stops a task from giving back a lock it does not hold, and it gives no priority inheritance. The mutex is the right tool for a shared bus.

One writer for the UART

The serial port is a single output. If the UI task and the sensor task each called the UART directly, their characters would interleave on the wire and produce garbled lines. The lab gives that job to one task, logger_task. The other tasks format their line and send it to log_queue. The logger receives each line in order and writes it. The queue is 8 items long, and the senders wait with portMAX_DELAY when it is full. That means lines are never dropped, but a slow logger can slow the senders, which is the trade-off to keep in mind when you size the queue.

The tick hook and the HAL's clock

The FreeRTOS tick is the periodic interrupt that drives the scheduler and the delays (1 kHz in this project, so one tick is 1 ms). The STM32 HAL has its own timeouts, for example the 100 ms I2C timeout, and those count with HAL_GetTick(). FreeRTOS owns the SysTick interrupt, so the HAL's counter must be driven from somewhere else. The lab sets configUSE_TICK_HOOK to 1 and defines vApplicationTickHook() in hal_bluepill.c, which calls HAL_IncTick() once per tick. Without that hook, the HAL timeouts never expire, and a stuck bus hangs the sensor task instead of returning an error.

Worked example: one button press, from interrupt to screen

Follow one press of button A through the system, with tick numbers. Suppose the press happens at tick 1000, which is 1000 ms after start.

  1. Tick 1000, interrupt. The falling edge on PB12 sets the EXTI pending flag, and the EXTI handler runs. It checks the flag for PB12, clears it, and calls the callback.
  2. Inside the callback. The callback fills an event with EV_BUTTON, the pin, and the tick from xTaskGetTickCountFromISR(), which is 1000. It calls xQueueSendFromISR(). If the UI task was waiting on the queue, the call sets woken to true, because the UI task is now ready to run.
  3. Return from the interrupt. The handler calls portYIELD_FROM_ISR(woken). The UI task is at priority 2, so if the sensor task is not running at a higher priority, the scheduler switches to the UI task as the interrupt returns.
  4. The UI task. It receives the event and calls ui_on_button(HAL_PIN_BTN_A, 1000). The module keeps the time of the last accepted press. The debounce window is 30 ms (DEBOUNCE_MS in ui.c), so a bounce at tick 1010 is ignored, because 1010 minus 1000 is less than 30.
  5. The screen changes. The press is accepted, the screen advances, and the function returns true. The UI calls draw_frame() at once, so the new screen appears within a few milliseconds of the press, well inside the 50 ms the acceptance criteria allow.

The example shows why each piece exists. Without the ISR, the screen would wait for the next 500 ms draw. Without the queue, the ISR would have to draw the display, which takes I2C time in interrupt context. Without the debounce, one switch bounce would advance the screen twice. Each part of the design is there to make one of those events cheap and safe.

Code explained line by line

The button callback runs in interrupt context. Here it is from the solution, with each line explained:

static int button_isr(hal_pin_t pin) {
    ui_event_t ev = { .kind = EV_BUTTON, .pin = pin, .centi = 0, .now = (uint32_t)xTaskGetTickCountFromISR() };
    BaseType_t woken = pdFALSE;
    xQueueSendFromISR(ui_queue, &ev, &woken);
    return woken == pdTRUE;
}

The first line builds the event with a designated initialiser, so every field has a known value. .now takes the tick count with the FromISR variant of the tick call, which is safe in an interrupt. The second line sets woken to pdFALSE, which is the value FreeRTOS expects if no task is woken. The third line sends the event without blocking. If the queue is full, the send fails and the event is lost, which the lab accepts for buttons because a missed press is less harmful than a blocked interrupt. The fourth line returns whether a more urgent task was woken, which the EXTI handler passes to portYIELD_FROM_ISR().

The sensor task shows the mutex discipline:

vTaskDelayUntil(&last_wake, pdMS_TO_TICKS(SAMPLE_PERIOD_MS));
xSemaphoreTake(i2c_mutex, portMAX_DELAY);
sensor_status_t st = sensor_poll(&centi);
xSemaphoreGive(i2c_mutex);
xQueueSend(ui_queue, &ev, portMAX_DELAY);

vTaskDelayUntil() keeps the period fixed, as lesson 93 explained. The mutex is taken with portMAX_DELAY, which means wait as long as needed, and released as soon as the poll returns. The queue send happens after the give, which matters: if the queue were full and the send blocked while the mutex was held, the display would wait for the bus, and the bus would wait for the display. Keeping the two operations apart prevents that tangle.

The EXTI handler itself clears the pending flag before calling the callback. If the flag were cleared last, it would still be set when the handler returned, and the interrupt would fire again at once. A single press would then generate several events, and the screen would advance several times. The project's comment says the same thing.

Design choices

  • Why four tasks and not one. Each task has one job and one deadline. The sensor's deadline is tight, the UI's is loose, and the logger and stats only print. Mixing them would give one priority to three different needs.
  • Why the stats task deletes itself. It reports at startup and after 5 seconds, then calls vTaskDelete(NULL). The lab enables INCLUDE_vTaskDelete for that, and a finished task that stays alive only uses stack and scheduler time.
  • Why the button uses an interrupt and not polling. A poll checks the pin at a fixed rate and can miss a short press. The interrupt sees every falling edge as it happens, and the debounce in the UI handles the bounces.
  • Why the stack sizes are in the code. Each xTaskCreate() gives a depth in words. The stats report shows how much each stack really used, so the sizes can be checked against measurement (lesson 92).
  • Why the lab deliberately has no overflow recovery. A stack overflow or a failed allocation is a bug. The hooks stop the system so the report and the debugger show it. Recovery code would hide the bug.

Common mistakes and how to spot them

Mistake 1: a non-FromISR call inside the ISR. Calling xQueueSend() from the callback is the most common error. The symptom is a freeze: the port's assertion fires when the interrupt priority is too urgent for an ISR-safe call, and the project's configASSERT disables interrupts and loops forever, so the board stops responding. The fix is xQueueSendFromISR() and portYIELD_FROM_ISR(), and an interrupt priority of 5 or more. The FreeRTOS port's comment at line 780 of port.c states the rule.

Mistake 2: clearing the pending flag too late. If the handler clears the EXTI flag after the callback, the flag is still set when the handler returns, and the interrupt fires again. The symptom is several events for one press: the screen advances two or three steps, or the setpoint goes up by several degrees. The fix is to clear the flag first, as the solution does.

Mistake 3: holding the bus mutex while waiting on a queue. If the sensor takes i2c_mutex and then sends to a full ui_queue, the sensor blocks while owning the bus. The UI task, which needs the bus to draw, then waits for the sensor, and the sensor waits for the UI. The symptom is that the display stops updating and the sample stops, with no error. The fix is to give the mutex back before the queue send, as the solution does.

Mistake 4: no tick hook. If configUSE_TICK_HOOK is 0, or the hook does not call HAL_IncTick(), the HAL's timeouts never expire. The symptom is a sensor that hangs silently when it stops answering, because the bus call waits forever instead of returning an error. The fix is the tick hook, which the project sets up.

Mistake 5: a stack that is too small. A task whose stack overflows reaches the overflow hook, which loops forever. The symptom is a system that stops printing after a while, and the stats lines show near-zero free words before it stops. The fix is to read the high-water marks, raise the depth in xTaskCreate() by a margin, and keep the margin when the second report looks safe.

In real projects

Production firmware usually has the same structure as this lab, with a sensor task on the tightest timing, a control or UI task, and one owner for each shared bus and output. Teams wrap the RTOS calls behind small modules, as the lab's hal.h does, so that a port to another board or RTOS touches one file. Code review looks for the same things this lab tests: no blocking call in an ISR, a mutex held only around the bus call, one writer per output, and a stack margin written down as a number. The bus and output rules are the ones most often broken, so reviewers check them first.

Summary

  • A super-loop runs its work in one order, so a long job delays the others. Tasks with priorities let the urgent work run first, with preemption.
  • Use vTaskDelayUntil() for periodic work and a queue wait with a timeout for event work. A blocked task costs no CPU.
  • An ISR uses only FromISR calls, never blocks, and calls portYIELD_FROM_ISR() when it wakes a more urgent task.
  • A mutex with an owner guards a shared bus. Take it around the bus call only, and never hold it across a blocking queue send.
  • One task owns each output. The logger is the only writer of the UART, and other tasks send lines to it.
  • The tick hook keeps the HAL's timeouts counting. Clear the EXTI flag first, and check every stack with its high-water mark.

Requirements

  1. Build starter/ and solution/ for the Blue Pill. The modules in app/ are shared by both folders, so you do not copy them: you change only app.c and hal_bluepill.c in your folder.
  2. Create four tasks: sensor (priority 3), ui (priority 2), logger (priority 1) and stats (priority 1, deleted after its second report).
  3. The sensor task samples every 200 ms with vTaskDelayUntil(), so its period does not drift when the bus is busy.
  4. The ui task draws the screen every 500 ms, and immediately when a button changes the screen. It waits on ui_queue with a timeout of one draw period.
  5. A button press is an interrupt on PB12 or PB13 (falling edge). The interrupt sends an event into ui_queue with xQueueSendFromISR() and requests a switch with portYIELD_FROM_ISR(). The interrupt does no printing and no I2C.
  6. The I2C bus is protected by i2c_mutex. Both the sensor and the display flush take it, and neither holds it across a delay.
  7. Only logger_task calls hal_log(). The ui task and the sensor task send lines to log_queue. The single exception is LAB5 OK, which main() prints before the scheduler starts.
  8. hal_millis() returns the FreeRTOS tick count, and vApplicationTickHook() calls HAL_IncTick() so that the HAL's I2C timeouts keep counting.
  9. At start-up and again 5 seconds later, the stats task prints each task's stack high-water mark as LAB5 stack <name> free=N words.
  10. Print LAB5 OK once, after the sensor and the display have both initialised.

Acceptance criteria

  • The serial monitor prints LAB5 OK once, then the four stack lines, then one LAB5 T=... line per second. Five seconds after start, the four stack lines appear a second time, and then the stats task is gone.
  • The OLED shows the temperature on LIVE, and the same value appears in the log within one second.
  • Button A cycles LIVE, MINMAX and SETPOINT, and the screen changes within 50 ms of the press, not within 500 ms.
  • On SETPOINT, button B raises the threshold from 28 to 35, then wraps to 20. The log shows ALARM=1 when the reading is above the threshold.
  • One click produces one screen change, even if the switch bounces.
  • Every stack keeps at least 16 free words in the second report. A smaller margin means the stack is too small.
  • You changed no file in app/. The shared modules are the Lab 4 modules, updated only in the two places this lab describes (hal.h and ui.c).

Hints

Hint for the sensor task

Take i2c_mutex with portMAX_DELAY, call sensor_poll(), and give the mutex back before you queue the result. Queue an EV_SAMPLE for a new sample, and EV_SENSOR_ERR for an error. Do not hold the mutex while you send to the queue: a full queue would then block the bus.

Hint for the button interrupt

The EXTI handler checks the pending flag of each line, clears it, and calls the callback for that pin. The callback fills an ui_event_t with EV_BUTTON, the pin, and xTaskGetTickCountFromISR() as the time, then calls xQueueSendFromISR(). Clear the flag first; if you clear it last, the interrupt fires again at once.

Hint if the screen does not change

The UI task uses the press time to debounce, so a press with a bad timestamp can be treated as a bounce. Check that the event's now field holds the tick from the interrupt. Then check that ui_on_button() returns true, and that the UI task calls draw_frame() when it does.

Hint if the system hangs or resets

A hang with no output is usually a heap or stack problem. Check that configTOTAL_HEAP_SIZE is large enough for four tasks and two queues, and that the stats lines print the stack margins. A reset with output stopping is often a stack overflow: the hook loops forever, so attach the debugger and read the task name in vApplicationStackOverflowHook. If the EXTI interrupt fires but the callback never runs, check that hal_set_button_callback() is called before the scheduler starts, and that the EXTI interrupt priority number is 5 or more. A lower number is a more urgent interrupt, and configMAX_SYSCALL_INTERRUPT_PRIORITY is 5, so only interrupts at 5 or above may call the FromISR functions.

Hint for the stack margins

A stack is in words. The high-water mark is the fewest words that were ever free. If a stack is too small, shrink nothing: raise the stack depth in the xTaskCreate() call by a power of two, and read the second report again. Keep the margin, because the simulator's run may not exercise the worst path.
