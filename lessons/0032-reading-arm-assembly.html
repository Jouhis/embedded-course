Reading ARM assembly

The compiler has already made every decision in your C code. The disassembly shows those decisions, and you can check them line by line.

By the end of this lesson you can find a C function in the disassembly of a real Pico build, match its loop to the C code, and step through its first instructions in a debugger.

Where we are and why it matters

Lessons 28 to 31 gave you the parts of the core: the fetch, decode and execute loop, the encodings of 16-bit instructions, the pipeline cost of a branch, and the registers and flags. This lesson puts them together on a real program. A disassembly is the text the toolchain prints from the machine code in an ELF file. It is the only honest view of what the compiler produced, and you need it when the C code and the behaviour on the board disagree.

Three situations in a job make this skill necessary. A release build crashes at an address that the source does not explain. A code review asks whether a loop is compiled to something sensible. And a performance question, such as "why does this function take so long", is answered by counting the instructions that run. In each case the C source tells you what the program means, and the disassembly tells you what the processor does.

The concepts, one at a time

Functions live at addresses

The compiler turns each C function into machine instructions. The linker then places those instructions at addresses in the program's memory map. For the Pico the program is stored in flash, and the RP2040 maps the flash at 0x10000000, where the core reads it directly. The RP2040 datasheet calls this execute in place, or XIP (RP2040 datasheet, §2.2.1). That is why the function addresses in the listing start at 10000280.

The file build/blink.elf keeps those addresses and the function names. The ELF file is the linker's output, with the firmware, the symbols and the debug information together. The tool arm-none-eabi-objdump reads it and prints each function as a listing: an address, the raw bytes, and the instruction. The listing for a function starts with a label line, such as 10000280 <sum_to>:, that gives the function's name and its first address.

A listing line has three parts

Each instruction line has the same three columns. The first is the address of the instruction in memory. The second is the raw bytes, in hex, as they sit in flash: a 16-bit instruction is four hex digits, and a 32-bit instruction is two halfwords of four digits each. The third is the instruction in assembly, with its operands. Lesson 29 decoded the 16-bit forms field by field, and the bytes column is the same encoding you learned there.

The bytes are stored little-endian, so a halfword that reads 2005 in the listing sits in memory as the bytes 05 20. The listing shows the halfword in its natural order, which is the order a human reads it. The lesson 29 quiz covers this.

The four things to find in a short function

You do not need to memorise the instruction set to read a short function. You need four things, and you can find each of them in a few seconds.

  • The function's address, which is the label line such as 10000280 <sum_to>:.
  • The argument registers on entry. The first argument arrives in R0 under the calling convention, and lesson 33 explains the rule in full.
  • The branches. A conditional branch backwards is a loop, and a bx lr is a return.
  • The return value. It leaves in R0.

The calling convention is the Arm Procedure Call Standard. The AAPCS says that "the first four registers r0-r3 (a1-a4) are used to pass argument values into a subroutine", and that "a word-sized Fundamental Data Type (e.g., int, float) is returned in r0" (Arm ABI, AAPCS, Core registers and Result Return). A uint32_t is a word-sized type, so sum_to takes its argument in R0 and returns its result in R0.

Branches and the flags they read

A branch changes the program counter. An unconditional branch, b, always does. A conditional branch, such as beq or bcs, reads the flags from xPSR and branches only if the condition holds. The flags come from the last instruction that set them, which in these listings is almost always a subs or a cmp. Lesson 31 showed how those flags come out of a subtraction.

A call is bl. It writes the return address into LR and then branches. A return is usually bx lr, which branches to the address in LR. The core takes the address from LR with bit 0 set. Bit 0 of a branch target is the Thumb state bit, and the TRM describes it as the T bit in xPSR (DDI0337G, Table 2-3). That is why the listing shows the function at 10000280, but the return address that the bl at 100002a0 writes is 100002a4 with bit 0 set, which is 100002a5 in LR. The TRM also says that "executing an instruction while the T bit is clear causes an INVSTATE exception", which is the fault you get when a branch clears bit 0 by mistake.

A bl is 32 bits long, not 16. The bl in the caller of sum_to is printed as two halfwords, f7ff ffee, and the bl to stdio_init_all is f003 fdfd. A listing that treats it as one 16-bit instruction will put the next address in the wrong place, which is one of the mistakes below.

The code

The function sums 1 to n. It is marked noinline so that it keeps its own symbol and the disassembly shows it as a unit. The starter main.c calls it with 100 and prints the result. 

__attribute__((noinline))
uint32_t sum_to(uint32_t n) {
    uint32_t total = 0;
    for (uint32_t i = 1; i <= n; i++) {
        total += i;
    }
    return total;
}

The disassembly, from a Release build

This listing is the output of arm-none-eabi-objdump -d --disassemble=sum_to build/blink.elf for the project in projects/0032-reading-arm-assembly, built with CMAKE_BUILD_TYPE=Release. We rebuilt the same main.c in a scratch folder with that setting, and the addresses and bytes match the listing exactly. Your addresses and bytes will match if you build the same code with the same toolchain and the same build type. 

10000280 <sum_to>:
10000280:	1e02      	subs	r2, r0, #0          @ r2 = n; set flags for n == 0
10000282:	d006      	beq.n	10000292            @ n == 0: return 0 at once
10000284:	2301      	movs	r3, #1              @ i = 1
10000286:	2000      	movs	r0, #0              @ total = 0
10000288:	18c0      	adds	r0, r0, r3         @ total += i   (loop starts here)
1000028a:	3301      	adds	r3, #1              @ i++
1000028c:	429a      	cmp	r2, r3              @ compare n with i
1000028e:	d2fb      	bcs.n	10000288            @ if n >= i (unsigned), loop back
10000290:	4770      	bx	lr                  @ return; the result is in R0
10000292:	2000      	movs	r0, #0              @ the n == 0 path
10000294:	e7fc      	b.n	10000290            @ go to the return

The compiler moved n into R2 at the start. The first two instructions handle the case n == 0, so the loop never has to run with an empty range. The loop body is the four instructions from 10000288 to 1000028e. The bcs.n is taken while n is at least i, which is the same as "while i ≤ n" in C. The .n suffix means the narrow, 16-bit form of the branch. The disassembler adds it so you can see the instruction size.

A worked example: tracing sum_to(3)

Take n = 3 and follow the registers one instruction at a time. The table shows the values after each step, so you can check your own trace against it.

StepInstructionR0 (total)R2 (n)R3 (i)Flags and branch
1subs r2, r0, #033-n is not zero, so beq is not taken
2movs r3, #1331-
3movs r0, #0031-
4adds r0, r0, r3131-
5adds r3, #1132-
6cmp r2, r31323 − 2 has no borrow, so C = 1; bcs taken
7adds r0, r0, r3332-
8adds r3, #1333-
9cmp r2, r33333 − 3 = 0, no borrow, C = 1; bcs taken

13bx lr634return with R0 = 6

The result is 6, which is 1 + 2 + 3. The loop body ran three times, once for each value of i. Notice that the flags come from the cmp in each pass, and the branch reads them one instruction later. The trace also shows why bcs is the right branch: it is taken while C = 1, which after a compare means the first operand is at least the second, as unsigned numbers. The same arithmetic on n = 100 gives 5050, which the program prints.

The branch targets can be checked by hand. For a 16-bit conditional branch the target is the branch's own address, plus 4, plus twice the signed 8-bit offset in the low byte. For the bcs.n at 1000028e, the offset byte is fb, which is −5. So the target is 1000028e + 4 − 10 = 10000288, which is the top of the loop, as the listing says. The beq.n at 10000282 with offset 6 gives 10000282 + 4 + 12 = 10000292, the n = 0 path. Both checks agree with the disassembler.

The caller, from the same build

10000298 <main>:
10000298:	b510      	push	{r4, lr}
1000029a:	f003 fdfd 	bl	10003e98 <stdio_init_all>
1000029e:	2064      	movs	r0, #100	@ 0x64: the argument n
100002a0:	f7ff ffee 	bl	10000280 <sum_to>
100002a4:	4b04      	ldr	r3, [pc, #16]
100002a6:	0001      	movs	r1, r0            @ the result goes to the printf argument

The caller puts 100 in R0 and calls sum_to with bl. The result comes back in R0, and the next line copies it to R1 for printf. This is the calling convention in action, and lesson 33 explains the rules. The two bl lines show the 32-bit form: each takes four bytes, so the next instruction is at the address 4 bytes further on, not 2.

Common mistakes and how to spot them

  1. Reading a Debug listing as if it were the Release one. The workspace's projects/0032-reading-arm-assembly/build folder was configured with CMAKE_BUILD_TYPE=Debug, not Release, so the sum_to in that folder is not the listing above. Its code is different: 
    10000280 <sum_to>:
10000280:	0002      	movs	r2, r0
10000282:	2301      	movs	r3, #1
10000284:	2000      	movs	r0, #0
10000286:	e001      	b.n	1000028c <sum_to+0xc>
10000288:	18c0      	adds	r0, r0, r3
1000028a:	3301      	adds	r3, #1
1000028c:	4293      	cmp	r3, r2
1000028e:	d9fb      	bls.n	10000288 <sum_to+0x8>
10000290:	4770      	bx	lr
    The Debug build has no n == 0 test in front of the loop. It tests the loop condition at the bottom, and its first instruction is a branch to that test. The symptom is that the addresses of the instructions differ from the text, even though the function name and the algorithm are the same. The fix: check CMAKE_BUILD_TYPE in build/CMakeCache.txt before you compare, and reconfigure the build with Release when you want the listing shown in this lesson.
  2. Calculating a branch target with the wrong base. A beginner who uses the branch's own address, without the +4, gets a target that is 4 bytes off. The symptom is a breakpoint or a jump that lands between two halfwords of an instruction, which the debugger shows as nonsense. The fix: use the rule in the worked example, which is the branch address plus 4 plus twice the offset, or read the target the disassembler prints.
  3. Treating bl as a 16-bit instruction. A bl takes four bytes. A listing where the next address is only 2 bytes on is a sign that the reader skipped the second halfword of the call. The symptom is that every address after the call is off by two, and the rest of the function looks like nonsense. The fix: read the two halfwords together as one instruction.
  4. Losing the Thumb bit. The listing shows the function at 10000280, with bit 0 clear, but a return address in LR carries bit 0 set. If you write an even address into LR or a register and branch to it with bx, bit 0 is cleared, and the TRM says that an instruction run while the T bit is clear "causes an INVSTATE exception". The symptom is that the program faults on the first instruction after the branch. The fix: branch to a function by its C name, or take the address from the debugger, and keep bit 0 set in any address you build yourself.

In real projects

A release build crash often starts with a fault address, such as the PC value in a HardFault dump. The engineer finds the function that contains the address with objdump or the map file, reads the listing around it, and then matches the instructions to the C source. The calling convention tells you which register holds which argument at that point. This is the workflow the interview question below describes.

Code review uses the same skill in a quieter way. A reviewer who suspects a loop is slow will look for the branches, count the instructions in the body, and check the cycle cost from lesson 30. A reviewer who suspects an optimisation has changed behaviour will compare two listings, one from each build setting. Many teams keep the ELF and the map file from each CI build as artifacts, so that a listing from the shipped build can be read later without a rebuild.

Summary

  • The ELF file holds the code and symbols. objdump -d prints each function as address, bytes and instruction.
  • On the Pico, flash is mapped at 0x10000000, so the function addresses start at 10000280 for this build.
  • The first argument of a function arrives in R0, and an int-sized result leaves in R0, under the AAPCS.
  • A conditional branch reads the flags set by the last subs or cmp. A 16-bit branch's target is its address plus 4 plus twice the offset.
  • A bl is four bytes. It writes the return address into LR with bit 0 set.
  • The Debug and Release builds of the same code give different listings. Check the build type before you compare.
  • The worked trace of sum_to(3) ends with R0 = 6, and each cmp sets C for the bcs that follows.

Try it: step through it in the debugger

The debugger shows the same instructions one at a time, with the registers beside them. You will use the GDB console. Lesson 54 covers GDB in depth.

  1. Open projects/0032-reading-arm-assembly in VS Code (File → Open Folder). Build with Ctrl+Shift+B.
  2. In a terminal, run arm-none-eabi-objdump -d build/blink.elf and find sum_to. The workspace's build folder is a Debug build, so the addresses will match the Debug listing in the mistakes section, not the Release listing above. To get the listing above, reconfigure the build with -DCMAKE_BUILD_TYPE=Release in a new build folder, and check the addresses again.
  3. Press F5 to start the simulator under GDB. In the GDB console, type break *0x10000280 and then continue. This stops on the first instruction of sum_to.
  4. In the GDB console, type disassemble sum_to and check that it matches the listing for your build type.
  5. Type stepi three times. After each one, type info registers r0 r2 r3 pc. Predict each PC before you look: it moves by 2 bytes at a time, and the first stepi lands on 10000282 in the Release build.
  6. For a visual view, right-click in the editor and open the disassembly view. The GDB command layout asm is for a terminal interface and does not work in VS Code.
Hint

If the stop comes from the start of the program instead, the address is wrong: check that the listing's first address for sum_to matches the one in your build. Use info registers pc to see where you are.

"You have a crash in a release build. How would you find the instruction that failed, starting from the ELF file?" Answer out loud in 60 seconds, then compare.

Model answer

Take the faulting address from the fault status or the debugger, and find the function that contains it with objdump or the map file. Read the listing around that address to see which instruction and which operands failed. Then match it to the C code, using the calling convention to find the arguments. The ELF keeps the symbols, so the listing can show the function names. Check first that the listing comes from the same build type as the crash, because a Debug and a Release build of the same code have different addresses.

RP2040 datasheet: §2.2.1 for the address map (XIP at 0x10000000). For the instruction-level meaning of each line, the Arm TRM is the authority: Arm Cortex-M3 TRM DDI0337G, §2.3 (the registers) and Table 2-3 (the T bit). For the argument and return registers, the Arm ABI documents, including the AAPCS, "Core registers" section.
