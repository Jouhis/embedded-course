Reading ARM assembly

The compiler has already made every decision in your C code. The disassembly shows those decisions, and you can check them line by line.

By the end of this lesson you can find a C function in the disassembly of a real Pico build, match its loop to the C code, and step through its first instructions in a debugger.

The idea

The compiler turns each C function into machine instructions, and the linker places them at addresses in flash. The file build/blink.elf keeps those addresses and the function names. The tool arm-none-eabi-objdump prints each function as a listing: an address, the raw bytes, and the instruction. You do not need to memorise the instruction set to read a short function. You need the four things below.

  • The function's address, which is the label line such as 10000280 <sum_to>:.
  • The argument registers on entry. The first argument arrives in R0 under the calling convention (lesson 33).
  • The branches. A conditional branch backwards is a loop, and a bx lr is a return.
  • The return value. It leaves in R0.

The Pico's program is stored in flash at 0x10000000, which the RP2040 datasheet calls XIP (execute in place) (RP2040 datasheet, §2.2.1). That is why the function addresses in the listing start at 10000280. The bytes in the listing are 16-bit Thumb instructions, two bytes each. A few are 32-bit, such as the bl call, which takes two halfwords. Lesson 29 decoded the 16-bit forms field by field.

The code

The function sums 1 to n. It is marked noinline so that it keeps its own symbol and the disassembly shows it as a unit. The starter main.c calls it with 100 and prints the result. 

__attribute__((noinline))
uint32_t sum_to(uint32_t n) {
    uint32_t total = 0;
    for (uint32_t i = 1; i <= n; i++) {
        total += i;
    }
    return total;
}

The disassembly, from a real build

This listing is the output of arm-none-eabi-objdump -d --disassemble=sum_to build/blink.elf on the project in projects/0032-reading-arm-assembly, built with CMAKE_BUILD_TYPE=Release (in build/CMakeCache.txt). Your addresses and bytes will match if you build the same code with the same toolchain. 

10000280 <sum_to>:
10000280:	1e02      	subs	r2, r0, #0          @ r2 = n; set flags for n == 0
10000282:	d006      	beq.n	10000292            @ n == 0: return 0 at once
10000284:	2301      	movs	r3, #1              @ i = 1
10000286:	2000      	movs	r0, #0              @ total = 0
10000288:	18c0      	adds	r0, r0, r3         @ total += i   (loop starts here)
1000028a:	3301      	adds	r3, #1              @ i++
1000028c:	429a      	cmp	r2, r3              @ compare n with i
1000028e:	d2fb      	bcs.n	10000288            @ if n >= i (unsigned), loop back
10000290:	4770      	bx	lr                  @ return; the result is in R0
10000292:	2000      	movs	r0, #0              @ the n == 0 path
10000294:	e7fc      	b.n	10000290            @ go to the return

The compiler moved n into R2 at the start. The first two instructions handle the case n == 0, so the loop never has to run with an empty range. The loop body is the four instructions from 10000288 to 1000028e. The bcs.n is taken while n is at least i, which is the same as "while i ≤ n" in C. The .n suffix means the narrow, 16-bit form of the branch. The disassembler adds it so you can see the instruction size.

The caller, from the same build

10000298 <main>:
10000298:	b510      	push	{r4, lr}
1000029a:	f003 fdfd 	bl	10003e98 <stdio_init_all>
1000029e:	2064      	movs	r0, #100	@ 0x64: the argument n
100002a0:	f7ff ffee 	bl	10000280 <sum_to>
100002a4:	4b04      	ldr	r3, [pc, #16]
100002a6:	0001      	movs	r1, r0            @ the result goes to the printf argument

The caller puts 100 in R0 and calls sum_to with bl. The result comes back in R0, and the next line copies it to R1 for printf. This is the calling convention in action, and lesson 33 explains the rules.

Try it: step through it in the debugger

The debugger shows the same instructions one at a time, with the registers beside them. You will use the GDB console. Lesson 54 covers GDB in depth.

  1. Open projects/0032-reading-arm-assembly in VS Code (File → Open Folder). Build with Ctrl+Shift+B.
  2. In a terminal, run arm-none-eabi-objdump -d build/blink.elf and find sum_to. Check that your addresses match the listing above.
  3. Press F5 to start the simulator under GDB. In the GDB console, type break *0x10000280 and then continue. This stops on the first instruction of sum_to.
  4. In the GDB console, type disassemble sum_to and check that it matches the listing.
  5. Type stepi three times. After each one, type info registers r0 r2 r3 pc. Predict each PC before you look: it moves by 2 bytes at a time, and the first stepi lands on 10000282.
  6. For a visual view, right-click in the editor and open the disassembly view. The GDB command layout asm is for a terminal interface and does not work in VS Code.
Hint

If the stop comes from the start of the program instead, the address is wrong: check that the listing's first address for sum_to matches the one in your build. Use info registers pc to see where you are.

"You have a crash in a release build. How would you find the instruction that failed, starting from the ELF file?" Answer out loud in 60 seconds, then compare.

Model answer

Take the faulting address from the fault status or the debugger, and find the function that contains it with objdump or the map file. Read the listing around that address to see which instruction and which operands failed. Then match it to the C code, using the calling convention to find the arguments. The ELF keeps the symbols, so the listing can show the function names.

RP2040 datasheet: §2.2.1 for the address map (XIP at 0x10000000). For the instruction-level meaning of each line, the Arm TRM is the authority: Arm Cortex-M3 TRM DDI0337G. Read the sections on the registers (§2.3) first.
