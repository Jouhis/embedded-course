USART and EXTI interrupts with a ring buffer

A serial command line should not miss a byte just because the main loop is busy. An interrupt takes each byte as it arrives, a ring buffer holds them until main is ready, and an EXTI interrupt catches a button press the same way.

By the end of this lesson you can enable the USART1 receive interrupt in the peripheral and the NVIC, write the handler so it clears its flags in the right order, implement a single-producer, single-consumer ring buffer that is safe on one core, and route PA0 to EXTI line 0 through AFIO.

Where we are and why it matters

Lessons 53 and 57 covered serial output and interrupts in general terms. Lesson 72 covers the NVIC, the interrupt controller inside the core, and lesson 73 covers SysTick. This lesson puts those ideas on two real STM32 peripherals: the USART, which receives bytes from a serial monitor or a GPS module, and the EXTI controller, which turns a pin edge into an interrupt.

The problem is a common one in industry. A device such as a GPS receiver or a Modbus slave sends bytes at a fixed rate, and the firmware does other work between them. If the code is busy for longer than one byte time, a byte is overwritten and lost. At 115200 baud, one byte takes about 87 microseconds, so a loop that takes a few milliseconds will lose data. The fix is to let an interrupt take each byte the moment it arrives, and to let main process the bytes later.

Concepts, one at a time

Polling and interrupts

A polled receiver checks a status flag in a loop: "is a byte ready?" If the loop does something slow, the flag is checked late. An interrupt reverses the arrangement. The peripheral raises a request line, the core stops what it is doing, saves its registers, and runs a short handler called the interrupt service routine (ISR). The handler does the minimum work, and the core then resumes. Lesson 34 described the entry sequence.

The request has to go through a chain. The peripheral raises a flag in its status register. If its interrupt-enable bit is set, the request goes to the NVIC, and the NVIC sends it to the core when its priority allows. Each link in that chain needs its own setting, and each setting is a separate register. A missing setting in any link means the handler never runs, and nothing reports why.

The NVIC and priorities

The Nested Vectored Interrupt Controller (NVIC) numbers each interrupt, and it enables and prioritises them. Each interrupt number, such as USART1_IRQn, selects an entry in the vector table. The STM32F1 implements four priority bits, so priorities run from 0 to 15, and a lower number is a higher priority. A pending interrupt with a higher priority can interrupt a running handler. The header confirms the four bits: __NVIC_PRIO_BITS is 4 in stm32f103xb.h. PM0056, the NVIC section

Status flags and write-1-to-clear

A flag is a bit in a status register that the hardware sets when an event happens. The handler must clear the flag, or the interrupt fires again the moment the handler returns. There are two common ways to clear a flag. Some flags clear when you read or write a data register. Others are write-1-to-clear: reading the bit shows 1 while the event is pending, and writing a 1 to that bit clears it. A write of 0 does nothing. The EXTI pending register works this way, and the HAL's own macro for it writes the line's bit directly.

The EXTI controller and AFIO

The External Interrupt controller (EXTI) turns an edge on a pin into an interrupt request. It has one line per pin number, lines 0 to 15, and each line can take its pin from any port. The choice of port is made in the Alternate Function I/O block (AFIO), which has four EXTICR registers. Each covers four lines, with four bits per line, and the port code is 0 for A, 1 for B and 2 for C. The EXTI lines have their own vectors: line 0 has EXTI0_IRQn, and lines 5 to 9 share one handler, while lines 10 to 15 share another.

Step 1: ask the USART for an interrupt

The receive interrupt is enabled by RXNEIE in USART1->CR1. RXNE is the flag in USART1->SR that means the receive data register holds a byte. With the enable bit set, the flag raises the interrupt. 

USART1->CR1 = USART_CR1_TE | USART_CR1_RE | USART_CR1_RXNEIE | USART_CR1_UE;

Line by line: TE enables the transmitter, RE the receiver, RXNEIE the receive interrupt, and UE the whole USART. The header defines each as a mask, so the | sets all four bits at once. The assignment overwrites CR1, which is safe here because this is the only code that sets the register. In a larger program, a read-modify-write with |= would keep settings that another function had made.

The peripheral's request is not enough on its own. The NVIC must enable the line. USART1_IRQn is 37 in the header, so it selects the entry at index 16 + 37 = 53 in the vector table. The startup file lists USART1_IRQHandler at that position, which is how the link finds the handler by name. NVIC_EnableIRQ() sets the enable bit for that number, and NVIC_SetPriority() sets its priority. 

NVIC_SetPriority(USART1_IRQn, 2U);   /* lower number is higher priority */
NVIC_EnableIRQ(USART1_IRQn);

Step 2: the handler clears its flags in order

The handler is named USART1_IRQHandler, which is the name the startup file gives that vector. RXNE clears when you read DR. The overrun flag, ORE, means a byte arrived before the last one was read, so the old byte was overwritten. The sequence for clearing ORE is a read of SR, followed by a read of DR. The HAL's own clear macro does the same two reads, in that order. So the handler reads SR first, then DR, and it does both even when only ORE is set. 

void USART1_IRQHandler(void) {
    uint32_t sr = USART1->SR;                 /* step 1: SR ... */
    if (sr & (USART_SR_RXNE | USART_SR_ORE)) {
        uint8_t byte = (uint8_t)USART1->DR;   /* step 2: ... then DR clears RXNE and ORE */
        if (sr & USART_SR_RXNE) {
            ring_put(&g_rx, byte);            /* hand the byte to main */
        }
    }
    if (sr & USART_SR_ORE) { g_rx_dropped++; }
}

Line by line: the first line copies SR into a local variable. Reading it once and testing the copy means that the bits the handler tests are the bits from one moment, not a mix. The if enters the body when either event happened. Reading DR returns the received byte and clears RXNE and ORE. The cast to uint8_t keeps the byte, because this course uses 8-bit frames. The inner test hands the byte to main only when RXNE was set, and the last line counts an overrun separately, so the loss is visible.

An interrupt that does not clear its flag is entered again as soon as it returns, and the program appears to hang. For RXNE, reading DR is the clear. For EXTI, the clear is a write of 1 to the pending bit, which the next section shows.

Step 3: a ring buffer between the interrupt and main

The interrupt is the producer: it adds bytes. Main is the consumer: it takes them out. A ring buffer is an array with a write index (the head) and a read index (the tail), and both wrap around the array. The size is a power of two, so index & (SIZE − 1) is the wrap, with no division. A ring is the usual structure for this, and it is in the glossary. Glossary: ring buffer 

typedef struct {
    volatile uint8_t  data[16];
    volatile uint16_t head;     /* written only by the interrupt */
    volatile uint16_t tail;     /* written only by main */
} ByteRing;

static int ring_put(ByteRing *r, uint8_t byte) {           /* producer: the ISR */
    uint16_t head = r->head;
    if ((uint16_t)(head - r->tail) == 16U) return 0;       /* full */
    r->data[head & 15U] = byte;                           /* 1. write the slot */
    r->head = (uint16_t)(head + 1U);                      /* 2. then publish it */
    return 1;
}

static int ring_get(ByteRing *r, uint8_t *byte) {          /* consumer: main */
    uint16_t tail = r->tail;
    if (tail == r->head) return 0;                          /* empty */
    *byte = r->data[tail & 15U];
    r->tail = (uint16_t)(tail + 1U);                      /* free the slot after reading it */
    return 1;
}

Line by line for ring_put. It reads head into a local, because only the producer writes it, so the local is always current. The full test subtracts the tail from the head and compares with 16, the size. The arithmetic is done in uint16_t, so the difference wraps the way the counters do. The slot is head & 15U, which is the index for a 16-entry array. The byte is written to the slot first, and only then is the head advanced. ring_get is the mirror image: it returns 0 when the counters are equal, reads the slot at the tail, and advances the tail last.

A worked trace across the wrap

The head and tail are free-running 16-bit counters, not indexes. They go up to 65535 and wrap to zero, and the slot number is always the low four bits. The difference head − tail still gives the number of bytes queued, as long as it is computed in 16 bits. Here is a trace with the tail just before the wrap.

The step that matters is the difference at the wrap. Between the second and third rows, the head went from 65535 to 0. The 16-bit subtraction 0 − 65534 gives 2 modulo 65536, which is the right answer, and it is 2 because the head is two bytes past the tail. A plain signed subtraction of two 32-bit values would give −65534, and the full test would never fire. The unsigned 16-bit form is why the code casts to uint16_t.

Why this needs no lock on one core

The argument for safety without a lock has four parts. The solution's self-test checks it in code before the hardware runs.

  1. Each index has one writer. Only the interrupt writes head, and only main writes tail. Each side reads the other's index and never writes it.
  2. Each index is read or written in one access. The argument assumes that a 16-bit access to an aligned address is not split into two bus transactions. That is the usual behaviour on this core, but it is an assumption, and the Arm Cortex-M3 Technical Reference Manual is the source to check before you reuse the argument on another core.
  3. The order is fixed. The producer writes the slot before it publishes the head, and volatile stops the compiler from swapping them. The consumer reads the head before it reads the slot, so it never reads a slot that has not been written.
  4. The interrupt cannot break main's half. If the interrupt runs between two steps of ring_get, it only adds a byte at the head. It does not touch the tail, so main's view of the tail stays valid.
This argument is for one core, with the interrupt as the only producer. Two cores, or a second producer, need memory barriers and atomic operations: the RP2040's second core is in lesson 64, and the RTOS queues and mutexes that handle this are in Part 7. The volatile qualifier gives ordering for the compiler, not atomicity. Lesson 46 made the same point.

Step 4: EXTI and a button on PA0

A button on PA0 can raise an interrupt through the EXTI controller. The choice of port for line 0 is made in AFIO->EXTICR. Line 0 is in EXTICR[0], and its field is the low four bits of that register. Port A has code 0, so PA0 is an all-zero field. Line 13 is in EXTICR[3], and PC13 is the value 2 there. 

RCC->APB2ENR |= RCC_APB2ENR_AFIOEN;       /* AFIO needs its clock to take writes */
AFIO->EXTICR[0] = (AFIO->EXTICR[0] & ~AFIO_EXTICR1_EXTI0) | AFIO_EXTICR1_EXTI0_PA;

EXTI->FTSR |= EXTI_FTSR_TR0;    /* falling edge: pressing pulls PA0 low */
EXTI->PR   = EXTI_PR_PR0;      /* clear any stale pending flag (write 1) */
EXTI->IMR |= EXTI_IMR_MR0;     /* unmask line 0 */
NVIC_EnableIRQ(EXTI0_IRQn);

void EXTI0_IRQHandler(void) {
    if (EXTI->PR & EXTI_PR_PR0) {
        EXTI->PR = EXTI_PR_PR0;          /* clear by writing 1, or this fires forever */
        g_button_presses++;
    }
}

Line by line. The first line enables the AFIO clock, because the EXTICR write is ignored without it, as lesson 67 found for the GPIO ports. The second line clears the four bits of the line-0 field with a mask, and then writes AFIO_EXTICR1_EXTI0_PA, which is zero. Because the value is zero, the mask-and-set pattern here mainly documents intent: it would matter if line 0 were routed to another port. FTSR, the falling-trigger register, selects the falling edge, because the button pulls the pin to ground when pressed. PR is cleared before the line is unmasked, so a stale pending flag from startup does not fire at once. IMR unmasks line 0, and the NVIC enables EXTI0_IRQn, which is interrupt number 6 in the header.

The handler checks that line 0 is the one pending, which matters if the shared lines are used later. It clears the pending bit by writing 1 to it, and then counts the press. The clear comes before the count, so the handler is ready for the next edge as soon as it returns.

A real button also bounces, so one press can raise several edges. Lesson 52 covered debouncing in polled code, and the same idea applies here. RM0008, the AFIO and EXTI sections

The EXTI0 interrupt is a different vector from the EXTI lines 5 to 9 and 10 to 15, which share two handlers. Line 0 has its own. If you move the button to PA5, the handler changes to EXTI9_5_IRQHandler, and you must check PR for the right line inside it.

Pin setup for the receive line and the button

The solution also configures the two GPIO pins that the code relies on, and the lesson's starter leaves one of them to you. PA10 is the receive pin. It is in CRH, with its field at bit 8, and it is a floating input, the CNF value 01 with MODE 00, which is 0x4. PA0 is the button, in CRL, with its field at bit 0, and it is an input with a pull-up. The pull-up input uses CNF 10 with MODE 00, which is 0x8, and the pull-up is selected by setting the pin's bit in ODR. 

GPIOA->CRL = (GPIOA->CRL & ~0xFU) | 0x8U;   /* PA0: input with pull-up */
GPIOA->BSRR = GPIO_BSRR_BS0;               /* ODR bit 0 = 1 selects the pull-up */

The HAL source confirms those encodings. Its constants for input with pull-up use CNF 10, floating input uses CNF 01, and its pull-up code sets the ODR bit. Lesson 67 gives the rest of the pattern.

Hint for the ring

Each function is three or four lines. The size is 16, so the index mask is 15. Use uint16_t casts on the arithmetic, so the difference wraps the same way the counters do.

Hint for the interrupt enable

Without RXNEIE, the peripheral never raises RXNE as an interrupt, and the ring stays empty. Without NVIC_EnableIRQ(USART1_IRQn), the request is pending and nothing runs.

Hint for EXTI

PA0 goes to line 0 with the port code 0, which means all zero bits in EXTICR[0]. The falling trigger is FTSR, and the unmask is IMR. Enable the AFIO clock first, or the EXTICR write does nothing.

Common mistakes and how to spot them

Mistake 1: RING OK prints, and typing does nothing

The self-test passes, but typed characters never echo. The usual cause is that RXNEIE is not set in CR1, or USART1_IRQn is not enabled in the NVIC. Without the first, the peripheral never raises RXNE as an interrupt, and without the second the request stays pending and nothing runs. The symptom is the same either way. The fix is both lines, as the hint describes. In the debugger, put a breakpoint in USART1_IRQHandler: it should be hit once per typed character.

Mistake 2: the button count climbs without presses

After the handler runs once, the st count keeps going up, or the program seems to stall. The cause is a missing clear. If the handler does not write 1 to EXTI->PR, the pending bit stays set, and the interrupt is taken again as soon as it returns. The fix is the clear, before the count. A quick test is to read EXTI->PR in the debugger after a press: bit 0 should be 0.

Mistake 3: the button does nothing

The button works in the polled version of the code, but the EXTI version never counts. Check the order: the AFIO clock comes first, because the EXTICR write is ignored without it. Then check FTSR for the falling edge, IMR for the unmask, and NVIC_EnableIRQ(EXTI0_IRQn) for the NVIC. Any one of those missing leaves the button silent, and each one is a single line to check.

Mistake 4: characters come out garbled, now and then

Most characters are right, and occasionally one is wrong or missing. A common cause is a producer that advances head before writing the slot. The consumer can then read a slot that still holds the old byte. The fix is the order in ring_put: write the slot, then publish the head. Because the bug depends on timing, it does not show in a simulator run as easily as on hardware. A host test of the ring is the best way to catch it, which is why the solution runs the self-test before any interrupt.

In real projects

Production firmware almost always uses interrupt-driven receive buffers, because a polled receiver cannot keep up with a busy main loop. A reviewer looks for three things in such code: that the handler does the minimum work, that the status flags are cleared in the order the reference manual gives, and that the buffer is safe for the number of producers and cores in the design. The third point is where a single-core argument like this one stops being enough. A second core, a DMA channel or a second interrupt that writes the same index all need a different design, usually an RTOS queue or a DMA ring with a half-transfer interrupt.

Interviewers ask about this design because it tests several skills at once: knowing the interrupt chain, knowing why the buffer needs no lock, and knowing what changes when the assumptions change. A strong answer names the assumptions before it uses them.

Summary

  • A peripheral interrupt needs three settings: the peripheral's enable bit, the NVIC enable and priority, and the handler's clear of the flag.
  • On the STM32F1, USART1_IRQn is 37, which is vector index 53, and EXTI0_IRQn is 6, which is vector index 22.
  • Clear an overrun by reading SR and then DR. Clear an EXTI pending bit by writing 1 to it.
  • A ring buffer uses free-running 16-bit counters, with the slot at counter & 15, and the difference computed in uint16_t is correct across the wrap.
  • On one core, with a single producer, the ring needs no lock if the producer writes the slot before it publishes the head.
  • AFIO routes a pin to an EXTI line through EXTICR, and its clock must be on before that write.
  • The lock-free argument depends on assumptions about access size and core count, and a design with more producers or cores needs a different structure.

Model answer

Enable the receive interrupt, so the handler takes each byte from the data register as it arrives. The handler only copies the byte into a ring buffer, and it clears the flags in the register sequence, reading the status register and then the data register. The ring has a power-of-two size, with a head written only by the interrupt and a tail written only by main. Main drains the ring in its own loop. On one core this needs no lock, because each index has one writer and the producer publishes the head after writing the slot. If the ring fills, the handler drops the byte and counts it, so the loss is visible.
