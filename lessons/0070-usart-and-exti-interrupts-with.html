USART and EXTI interrupts with a ring buffer

Interrupt-driven serial receive and button input

By the end of this lesson you can enable the USART1 receive interrupt in the peripheral and the NVIC, write the handler so it clears its flags in the right order, implement a single-producer, single-consumer ring buffer that is safe on one core, and route PA0 to EXTI line 0 through AFIO.

Bytes that arrive while main is busy

Lessons 53 and 57 covered serial output and interrupts in general terms, and lessons 72 and 73 will cover the NVIC, the interrupt controller inside the core, and SysTick. This lesson puts those ideas onto two real STM32 peripherals, the USART, which receives bytes from a serial monitor or a GPS module, and the EXTI controller, which turns a pin edge into an interrupt.

The problem is common in industry: a device such as a GPS receiver or a Modbus slave sends bytes at a fixed rate while the firmware does other work between them, and if the code stays busy for longer than one byte time, a byte is overwritten and lost. At 115 200 baud one byte takes about 87 µs, so a loop lasting a few milliseconds loses data, and the fix is to let an interrupt take each byte the moment it arrives and a ring buffer hold it until main is ready to process it.

Polling and interrupts

A polled receiver checks a status flag in a loop, asking whether a byte is ready, so if the loop does something slow, the flag is checked late. An interrupt reverses the arrangement, the peripheral raising a request line, the core stopping what it is doing, saving its registers and running a short handler called the interrupt service routine (ISR), which does the minimum work before the core resumes, following the entry sequence of lesson 34.

The request passes through a chain: the peripheral raises a flag in its status register, the request goes to the NVIC if the peripheral's interrupt-enable bit is set, and the NVIC sends it to the core when its priority allows. Each link of the chain needs its own setting in a separate register, and a missing setting in any link means that the handler never runs, with nothing reporting why.

The NVIC and interrupt priorities

The Nested Vectored Interrupt Controller (NVIC) numbers, enables and prioritises each interrupt, an interrupt number such as USART1_IRQn selecting an entry in the vector table. The STM32F1 implements four priority bits, so priorities run from 0 to 15 with a lower number meaning a higher priority (PM0056 Rev 7, section 4.3.7 and Table 42: the processor implements bits[7:4] of each priority field, and a lower value gives a higher priority), and a pending interrupt with a higher priority can interrupt a running handler. The header confirms the four bits, __NVIC_PRIO_BITS being 4 in stm32f103xb.h (PM0056 Rev 7, section 4.3.7 (NVIC_IPRx), the NVIC section).

Status flags and write-1-to-clear

A flag is a bit in a status register that the hardware sets when an event happens, and the handler must clear it, or the interrupt fires again the moment the handler returns. Flags are cleared in two common ways: some clear when a data register is read or written, while others are write-1-to-clear, reading 1 while the event is pending and clearing when a 1 is written to that bit, a write of 0 doing nothing. The EXTI pending register works the second way, and the HAL's own macro for it writes the line's bit directly.

The EXTI controller and AFIO

The External Interrupt controller (EXTI) turns an edge on a pin into an interrupt request, with one line per pin number, lines 0 to 15, each able to take its pin from any port. The port is chosen in the Alternate Function I/O block (AFIO), whose four EXTICR registers (RM0008 Rev 21, sections 9.4.3 to 9.4.6) each cover four lines with four bits per line, the port code being 0 for A, 1 for B and 2 for C. The EXTI lines have their own vectors, line 0 having EXTI0_IRQn while lines 5 to 9 share one handler and lines 10 to 15 another (RM0008 Rev 21, Table 63: EXTI0 is position 6, EXTI9_5 is 23 and EXTI15_10 is 40).

Enabling the USART receive interrupt

The receive interrupt is enabled by RXNEIE in USART1->CR1, while RXNE is the flag in USART1->SR meaning that the receive data register holds a byte, so with the enable bit set the flag raises the interrupt (RM0008 Rev 21, section 27.6.1, bit 5, and section 27.6.4, bit 5). 

USART1->CR1 = USART_CR1_TE | USART_CR1_RE | USART_CR1_RXNEIE | USART_CR1_UE;

TE enables the transmitter, RE the receiver, RXNEIE the receive interrupt and UE the whole USART, each defined in the header as a mask, so the | sets all four bits at once. The assignment overwrites CR1, which is safe here because no other code sets the register, whereas in a larger program a read-modify-write with |= would keep settings made by another function.

The peripheral's request is not enough on its own, because the NVIC must enable the line as well. USART1_IRQn is 37 in the header, selecting the vector table entry at index

vector index = 16 + IRQn(1)

where the first 16 entries are the core's own exceptions, so USART1 sits at 16 + 37 = 53 (RM0008 Rev 21, Table 63 lists USART1 at position 37; PM0056 Rev 7, Table 16 places IRQ n at exception 16 + n). The startup file lists USART1_IRQHandler at that position, which is how the link finds the handler by name, and NVIC_EnableIRQ() sets the enable bit for that number while NVIC_SetPriority() sets its priority. 

NVIC_SetPriority(USART1_IRQn, 2U);   /* lower number is higher priority */
NVIC_EnableIRQ(USART1_IRQn);

Clearing the receive flags in the handler

The handler is named USART1_IRQHandler, the name the startup file gives that vector. RXNE clears when DR is read, while the overrun flag, ORE, meaning that a byte arrived before the last one was read and overwrote it, clears through a read of SR followed by a read of DR (RM0008 Rev 21, section 27.6.1: RXNE is cleared by a read of USART_DR, and ORE by a read of USART_SR followed by a read of USART_DR), the same two reads in the same order as the HAL's own clear macro. The handler therefore reads SR first and then DR, doing both even when only ORE is set. 

void USART1_IRQHandler(void) {
    uint32_t sr = USART1->SR;                 /* step 1: SR ... */
    if (sr & (USART_SR_RXNE | USART_SR_ORE)) {
        uint8_t byte = (uint8_t)USART1->DR;   /* step 2: ... then DR clears RXNE and ORE */
        if (sr & USART_SR_RXNE) {
            ring_put(&g_rx, byte);            /* hand the byte to main */
        }
    }
    if (sr & USART_SR_ORE) { g_rx_dropped++; }
}

The first line copies SR into a local variable, so that the bits the handler tests all come from one moment rather than a mix, and the if enters the body when either event happened. Reading DR returns the received byte and clears RXNE and ORE, the cast to uint8_t keeping the byte, because this course uses 8-bit frames, and the inner test hands the byte to main only when RXNE was set, while the last line counts an overrun separately so that the loss stays visible.

An interrupt that does not clear its flag is entered again as soon as it returns, and the program appears to hang. For RXNE, reading DR is the clear. For EXTI, the clear is a write of 1 to the pending bit (RM0008 Rev 21, section 10.3.6), which the next section shows.

A ring buffer between the interrupt and main

The interrupt is the producer, adding bytes, and main the consumer, taking them out. A ring buffer is an array with a write index, the head, and a read index, the tail, both wrapping around the array, and with a power-of-two size the wrap is index & (SIZE − 1), needing no division. A ring is the usual structure for this job, as the glossary entry describes (Glossary: ring buffer). 

typedef struct {
    volatile uint8_t  data[16];
    volatile uint16_t head;     /* written only by the interrupt */
    volatile uint16_t tail;     /* written only by main */
} ByteRing;

static int ring_put(ByteRing *r, uint8_t byte) {           /* producer: the ISR */
    uint16_t head = r->head;
    if ((uint16_t)(head - r->tail) == 16U) return 0;       /* full */
    r->data[head & 15U] = byte;                           /* 1. write the slot */
    r->head = (uint16_t)(head + 1U);                      /* 2. then publish it */
    return 1;
}

static int ring_get(ByteRing *r, uint8_t *byte) {          /* consumer: main */
    uint16_t tail = r->tail;
    if (tail == r->head) return 0;                          /* empty */
    *byte = r->data[tail & 15U];
    r->tail = (uint16_t)(tail + 1U);                      /* free the slot after reading it */
    return 1;
}

ring_put reads head into a local, which is always current because only the producer writes it, and its full test subtracts the tail from the head and compares the result with 16, the size, the arithmetic being done in uint16_t so that the difference wraps the way the counters do. The slot is head & 15U, the index into a 16-entry array, and the byte is written to the slot first, the head advancing only afterwards. ring_get is the mirror image, returning 0 when the counters are equal, reading the slot at the tail and advancing the tail last.

A ring buffer resembles the circular conveyor belt of a sushi bar, the cook, here the interrupt, putting plates on at one point and the diner, main, taking them off at another. Each moves only their own marker, the head or the tail, so they never need to talk, and if the cook gets a whole lap ahead, there is nowhere for the next plate, a full buffer in which a byte is dropped. A real cook would simply wait, however, whereas an interrupt cannot wait for space, which is why the ring must be sized for the longest stretch during which main does not read it.

Worked example: the ring buffer across the 16-bit wrap

The head and tail are free-running 16-bit counters rather than indexes, counting up to 65 535 and wrapping to zero, while the slot number is always their low four bits, and the difference head − tail still gives the number of queued bytes as long as it is computed in 16 bits. The trace below starts with the tail just before the wrap, so before reading it, predict what head − tail gives once the head has wrapped and the tail has not.

The step that matters is the difference at the wrap, between the second and third rows, where the head goes from 65 535 to 0. The 16-bit subtraction 0 − 65534 gives 2 modulo 65 536, the right answer, since the head is two bytes past the tail, whereas a plain signed subtraction of two 32-bit values would give −65 534 and the full test would never fire, which is why the code casts to uint16_t.

  1. The ring has 16 slots. head and tail are free-running 16-bit counters, and the slot is the counter's low four bits. Both start at 65534, so the slot is 14 and the buffer is empty: head − tail = 0.
  2. The receive interrupt puts A. It writes slot 65534 & 15 = 14 and moves head to 65535. One byte is queued.
  3. It puts B into slot 15. head goes from 65535 to 0: the 16-bit counter wraps. Computed in 16 bits, head − tail = 0 − 65534 = 2 modulo 65536, still the right count.
  4. It puts C into slot 0 & 15 = 0. Three bytes are queued; the slots have wrapped from 15 to 0 as well.
  5. The main loop gets a byte: slot 65534 & 15 = 14, which is A, and tail moves to 65535. Only the ISR writes head and only main writes tail, which is why one core needs no lock here.

Lock-free safety on a single core

The argument that the ring is safe without a lock has four parts, and the solution's self-test checks the code before the hardware runs.

  1. Each index has one writer. Only the interrupt writes head and only main writes tail, each side reading the other's index without ever writing it.
  2. Each index is read or written in one access. The argument assumes that a 16-bit access to an aligned address is not split into two bus transactions, the usual behaviour on this core but still an assumption, for which the Arm Cortex-M3 Technical Reference Manual is the source to check before reusing the argument on another core.
  3. The order is fixed. The producer writes the slot before publishing the head, with volatile stopping the compiler from swapping the two, and the consumer reads the head before the slot, so it never reads a slot that has not been written.
  4. The interrupt cannot break main's half. An interrupt running between two steps of ring_get only adds a byte at the head without touching the tail, so main's view of the tail stays valid.
This argument is for one core, with the interrupt as the only producer. Two cores, or a second producer, need memory barriers and atomic operations: the RP2040's second core is in lesson 64, and the RTOS queues and mutexes that handle this are in Part 7. The volatile qualifier gives ordering for the compiler, not atomicity. Lesson 46 made the same point.

A button on PA0 through EXTI line 0

A button on PA0 can raise an interrupt through the EXTI controller, the port for line 0 being chosen in AFIO->EXTICR, where line 0 occupies the low four bits of EXTICR[0]. Port A has code 0, so PA0 is an all-zero field, while line 13 lives in EXTICR[3], where PC13 is the value 2 (RM0008 Rev 21, section 9.4.3 for EXTICR1 and section 9.4.6 for EXTICR4). 

RCC->APB2ENR |= RCC_APB2ENR_AFIOEN;       /* AFIO needs its clock to take writes */
AFIO->EXTICR[0] = (AFIO->EXTICR[0] & ~AFIO_EXTICR1_EXTI0) | AFIO_EXTICR1_EXTI0_PA;

EXTI->FTSR |= EXTI_FTSR_TR0;    /* falling edge: pressing pulls PA0 low */
EXTI->PR   = EXTI_PR_PR0;      /* clear any stale pending flag (write 1) */
EXTI->IMR |= EXTI_IMR_MR0;     /* unmask line 0 */
NVIC_EnableIRQ(EXTI0_IRQn);

void EXTI0_IRQHandler(void) {
    if (EXTI->PR & EXTI_PR_PR0) {
        EXTI->PR = EXTI_PR_PR0;          /* clear by writing 1, or this fires forever */
        g_button_presses++;
    }
}

The first line enables the AFIO clock, which RM0008 Rev 21 (section 10.2.5, note 1) says should be on before the EXTICR registers are configured, since without it the EXTICR write is ignored, as lesson 67 found for the GPIO ports. The second line clears the four bits of the line-0 field with a mask and writes AFIO_EXTICR1_EXTI0_PA, which is zero, so here the mask-and-set pattern mainly documents intent and would matter only if line 0 were routed to another port. FTSR, the falling-trigger register, selects the falling edge, because the button pulls the pin to ground when pressed, and PR is cleared before the line is unmasked, so that a stale pending flag from startup cannot fire at once. IMR unmasks line 0, and the NVIC enables EXTI0_IRQn, interrupt number 6 in the header and position 6 in RM0008 Rev 21, Table 63.

The handler checks that line 0 is the one pending, which matters if the shared lines are used later, then clears the pending bit by writing 1 to it and counts the press, the clear coming first so that the handler is ready for the next edge as soon as it returns.

A real button also bounces, so one press can raise several edges, and the debouncing of lesson 52, written there for polled code, applies here too (RM0008 Rev 21, the AFIO and EXTI sections (9.4.3 for EXTICR1, 10.2.5 for the line mapping, and 10.3.6 for the pending register)).

The EXTI0 interrupt is a different vector from the EXTI lines 5 to 9 and 10 to 15, which share two handlers. Line 0 has its own. If you move the button to PA5, the handler changes to EXTI9_5_IRQHandler, and you must check PR for the right line inside it.

Pin setup for the receive line and the button

The solution also configures the two GPIO pins the code relies on, the starter leaving one of them to you. PA10, the receive pin, lies in CRH with its field at bit 8 and is a floating input, CNF 01 with MODE 00, or 0x4, while PA0, the button, lies in CRL with its field at bit 0 and is an input with a pull-up, CNF 10 with MODE 00, or 0x8, the pull-up being selected by setting the pin's bit in ODR (RM0008 Rev 21, section 9.2.2 and Table 20). 

GPIOA->CRL = (GPIOA->CRL & ~0xFU) | 0x8U;   /* PA0: input with pull-up */
GPIOA->BSRR = GPIO_BSRR_BS0;               /* ODR bit 0 = 1 selects the pull-up */

The HAL source confirms those encodings, its constants for input with pull-up using CNF 10 and for floating input CNF 01, and its pull-up code setting the ODR bit, while lesson 67 gives the rest of the pattern.

Hint for the ring

Each function is three or four lines, the size of 16 giving an index mask of 15, and uint16_t casts on the arithmetic make the difference wrap the same way the counters do.

Hint for the interrupt enable

Without RXNEIE the peripheral never raises RXNE as an interrupt and the ring stays empty, and without NVIC_EnableIRQ(USART1_IRQn) the request stays pending and nothing runs.

Hint for EXTI

PA0 goes to line 0 with port code 0, all zero bits in EXTICR[0], the falling trigger is FTSR and the unmask IMR, and the AFIO clock must be enabled first (RM0008 Rev 21, section 10.2.5, note 1), or the EXTICR write does nothing.

The reference solution is in projects/0070-uart-exti-ring/solution, so try first and compare afterwards.

Common mistakes and how to spot them

RING OK printed but typing ignored

The self-test passes but typed characters never echo, usually because RXNEIE is not set in CR1 or USART1_IRQn is not enabled in the NVIC, the first leaving the peripheral without an interrupt for RXNE and the second leaving the request pending with nothing run, so the symptom is the same either way. Add both lines, as the hint describes, and in the debugger set a breakpoint in USART1_IRQHandler, which should be hit once per typed character.

A button count that climbs without presses

After the handler runs once, the st count keeps rising or the program seems to stall, because the handler never writes 1 to EXTI->PR, so the pending bit stays set and the interrupt is taken again as soon as it returns. Clear the bit before counting, and check in the debugger after a press that bit 0 of EXTI->PR reads 0.

A button that does nothing

The button works in the polled version of the code but the EXTI version never counts, so check the order, the AFIO clock coming first (RM0008 Rev 21, section 10.2.5, note 1) because the EXTICR write is ignored without it, then FTSR for the falling edge, IMR for the unmask and NVIC_EnableIRQ(EXTI0_IRQn) for the NVIC. Any one of them missing leaves the button silent, and each is a single line to check.

Occasionally garbled characters

Most characters are right but now and then one is wrong or missing, a common cause being a producer that advances head before writing the slot, so that the consumer can read a slot still holding the old byte. Keep the order in ring_put, writing the slot and then publishing the head. Because the bug depends on timing, it shows less readily in a simulator run than on hardware, and a host test of the ring is the best way to catch it, which is why the solution runs its self-test before any interrupt.

Interrupt-driven receive buffers in production

Production firmware almost always uses interrupt-driven receive buffers, because a polled receiver cannot keep up with a busy main loop. A reviewer checks that the handler does the minimum work, that the status flags are cleared in the order the reference manual gives (RM0008 Rev 21, section 27.6.1) and that the buffer is safe for the number of producers and cores in the design, the third point being where a single-core argument like this one stops being enough. A second core, a DMA channel or a second interrupt writing the same index all need a different design, usually an RTOS queue or a DMA ring with a half-transfer interrupt.

Summary

  • A peripheral interrupt needs the peripheral's enable bit, the NVIC enable and priority, and a handler that clears the flag.
  • On the STM32F1 USART1_IRQn is 37, vector index 53, and EXTI0_IRQn is 6, vector index 22 (RM0008 Rev 21, Table 63, positions 37 and 6).
  • An overrun is cleared by reading SR and then DR, and an EXTI pending bit by writing 1 to it.
  • A ring buffer uses free-running 16-bit counters with the slot at counter & 15, and their difference computed in uint16_t stays correct across the wrap.
  • On one core with a single producer the ring needs no lock, provided the producer writes the slot before publishing the head.
  • AFIO routes a pin to an EXTI line through EXTICR, with its clock enabled before that write (RM0008 Rev 21, section 10.2.5, note 1).
  • The lock-free argument rests on assumptions about access size and core count, so a design with more producers or cores needs a different structure.
