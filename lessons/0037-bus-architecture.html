Bus architecture: AHB, APB, and the bus matrix

The buses between the bus masters, memory and peripherals

By the end of this lesson you can trace one register write from the core to a peripheral on an RP2040 or an STM32F103, name the bus it crosses, and say which accesses can run in parallel.

Bus traffic in a running system

Lesson 36 named the memory tiers and said that the core reaches memory over the bus, and this lesson opens that bus up. The eight-word frame pushed at interrupt entry in lesson 34 is a run of bus writes, and lesson 38 will show how a bus address becomes a register. Here we cover what a bus is, which bus a given address uses and what each access costs in cycles.

A 3D printer's controller shows why this matters. The main loop updates a motor's step counter, an interrupt from a timer or the endstop switch writes to the register controlling the motor's enable pin, and a DMA controller copies sensor readings into RAM at the same time. Each of these is a bus master reaching a slave, whether RAM, a timer block or a GPIO block, and whether they proceed together and how long each waits depends on the bus design. A poor design makes the printer lose steps at the worst moment, so the bus is part of the firmware's timing.

Bus masters, slaves and transfers

A bus is a set of wires and rules carrying three things between devices: an address, data, and a control signal saying whether the transfer is a read or a write and how wide it is. The device that starts a transfer is the bus master, such as the core or a DMA controller, which moves data without the core, and the device that answers is the bus slave, such as memory or a peripheral's register block. A master picks an address, the bus routes the transfer to one slave, and that slave answers.

The shared bus has a familiar limitation. If every master and slave share one set of wires, only one transfer can happen at a time and the others wait, which is simple and cheap but slow when several masters want the bus at once.

The bus matrix and arbitration

A bus matrix, also called a crossbar, removes most of that limit by giving each master a path to each slave, so transfers to different slaves run at the same time. Two masters that want the same slave still take turns, and this turn-taking, called arbitration, is the only thing that makes a master wait. A crossbar with four masters and ten slave ports is a grid of up to forty possible paths and needs far more wiring than a shared bus. The area and power cost is why chips use it for memory, which needs bandwidth, rather than for every peripheral.

A crossbar resembles a road junction built with flyovers, where cars travelling between different pairs of places cross at the same time without meeting. They wait only when two head for the same destination, and the arbiter then lets one go first, like a traffic light at the exit. Real traffic can choose another route, though, whereas a bus transfer to a busy slave has no alternative and simply waits.

AHB-Lite, APB and the bridge

The RP2040 datasheet names two kinds of bus in its fabric. The fast side is the AHB-Lite crossbar connecting the masters to memory and the fast peripherals, and the datasheet states that "the bus fabric does not add wait states to any AHB-Lite slave access" (section 2.1). The slow side is the APB peripheral bus, reached through an APB bridge, a component that the datasheet describes as the interface between "the high-speed main AHB-Lite interconnect" and "the lower-bandwidth peripherals" (section 2.1.3), with the APB as the bus behind it.

The split is a matter of cost. Memory needs wide, fast paths and gets them, whereas peripheral registers need little bandwidth, since a timer register is written a few times per second rather than on every cycle, so a simpler, slower bus behind a bridge suits them. The price of the bridge is paid in cycles, which a later section puts into numbers.

Atomic register access

A read-modify-write is the usual way to change one bit of a register: the program reads the register, changes the bit in a copy and writes the copy back. If an interrupt arrives between the read and the write and changes another bit, the write-back overwrites that change, a problem the RP2040 datasheet names directly: "without this capability, it is difficult to safely access IO registers when an interrupt service routine is concurrent with code running in the foreground" (section 2.1.2).

The RP2040's answer is to give each peripheral register block four addresses, which the datasheet lists as Addr + 0x0000 for normal read and write, Addr + 0x1000 for an atomic XOR on write, Addr + 0x2000 for an atomic bitmask set on write and Addr + 0x3000 for an atomic bitmask clear on write. A write to the set or clear address changes only the bits in the mask, in one bus write with no read first; the glossary calls these addresses an atomic alias. The datasheet notes that "most peripherals on RP2040 provide this functionality natively, and atomic writes have the same timing as normal read/write access" (section 2.1.2).

The STM32F1 solves the same problem differently. Its GPIO block has a BSRR register, in which writing a 1 to a bit sets the matching output and writing a 1 to the corresponding bit in the upper half resets it, and the HAL's own comment explains the choice: "This function uses GPIOx_BSRR register to allow atomic read/modify accesses. In this way, there is no risk of an IRQ occurring between the read and the modify access" (stm32f1xx_hal_gpio.c). RM0008 Rev 21, section 9.1.2, states the same aim, that the output bits can be set or cleared in a single atomic APB2 write without disabling interrupts, so both chips reach one write with no read through different register layouts.

The aliases are visible in the address itself. The explorer below starts at the SET alias of the GPIO 25 control register, where bits 13 and 12 of the offset choose the access method and the rest of the offset names the same register. Click the register buttons, then change the alias part of the address by hand, and 0x400140CC, 0x400150CC, 0x400160CC and 0x400170CC turn out to be one register reached four ways.

The RP2040 bus fabric and SRAM banks

The RP2040 bus fabric connects four bus masters, core 0, core 1 and the DMA's read and write ports, to ten downstream ports leading to ROM, XIP flash, six SRAM banks, a shared port for the fast AHB-Lite peripherals and the APB bridge. The datasheet states that "up to four bus transfers can take place each cycle" (section 2.1), and a transfer to a free port starts at once with no wait states added by the fabric.

The SRAM is split so that parallel accesses rarely collide. Its first 256 kB is word-striped across four 64 kB banks, with two 4 kB banks above, six banks in all, and the datasheet's Table 153 shows consecutive words going to different banks. Each bank has its own crossbar port, which is why four masters can use four banks at once.

Worked example: striping and bandwidth

Four consecutive word addresses in SRAM illustrate the striping, with Table 153 giving the bank for each. Before looking, predict whether four masters reading these four words in one cycle would collide.

AddressWord in the bankBank
0x20000000word 0Bank 0
0x20000004word 0Bank 1
0x20000008word 0Bank 2
0x2000000Cword 0Bank 3

The four words sit in four different banks, so four masters can read them in the same cycle without waiting. The datasheet gives the total as "at a system clock of 125MHz the maximum sustained bus bandwidth is 2.0GBps", a number that can be checked. The bandwidth is

B = n × w × f(1)

where n is the number of transfers per cycle, w the bytes per transfer and f the clock frequency. Four masters each moving one 32-bit word of 4 bytes per cycle give 4 × 4 B × 125 MHz = 2 000 MB/s, or 2.0 GB/s. If all four hit the same bank, however, the bank serves them one at a time and the others wait.

  1. Four consecutive words, 0x20000000 to 0x2000000C. The RP2040 stripes its main SRAM, so each one lives in a different bank, 0 to 3.
  2. Four masters each read one of them in the same cycle. The crossbar gives every master its own path, and every bank serves one request, so all four finish together: 4 × 4 bytes × 125 MHz = 2.0 GB/s, the datasheet's figure.
  3. No master waited. That is the point of the crossbar and the striping together.
  4. Now core 1 asks for 0x20000010, which is word 1 of bank 0, while core 0 reads 0x20000000 in the same bank. A bank serves one master at a time, so core 1 waits a cycle.

Worked example: the cost of APB accesses

The datasheet gives the APB cost in three statements: an APB access "take[s] two cycles minimum (setup phase and access phase)", the bridge "adds an additional cycle to read accesses", and it "adds two additional cycles to write accesses" (section 2.1.3). Counting as the datasheet does, an APB read takes at least 2 + 1 = 3 cycles and an APB write at least 2 + 2 = 4 cycles.

Consider a loop that writes a register in the UART0 block, which sits on the APB side at 0x40034000 in the SDK's address map (addressmap.h). At 1 000 writes the APB writes cost at least 4 000 cycles, which at a 125 MHz system clock is 4 000 × 8 ns = 32 µs. A write to the SIO block, the single-cycle IO block, does not pass through the bridge, because according to the datasheet the SIO is "attached directly to the cores' IO ports" (section 2.1.2), which is why fast GPIO code uses the SIO.

The STM32F103 bus map

The STM32F1 uses the same idea under different names. Its ST device header defines three peripheral bus regions from the peripheral base 0x40000000, APB1 at 0x40000000, APB2 at 0x40010000 and AHB at 0x40020000, and then places the blocks used in this course: GPIOC_BASE is APB2PERIPH_BASE + 0x1000, or 0x40011000, and RCC_BASE is AHBPERIPH_BASE + 0x1000, or 0x40021000, so GPIOC is on APB2 and the clock controller RCC on AHB (third_party/cmsis-device-f1/Include/stm32f103xb.h). RM0008 Rev 21, Table 3 (section 3.3, Register boundary addresses), gives the same boundaries: APB1 from 0x4000 0000, APB2 from 0x4001 0000, the AHB peripherals from 0x4002 0000, GPIO port C at 0x4001 1000 and RCC at 0x4002 1000.

The demo enables the peripheral clocks in RCC before using GPIOC and USART1, following the course's convention for these projects. The bit positions come from the header, and the rule that a peripheral needs its clock enabled comes from the project's comment and is confirmed by RM0008 Rev 21, section 3.1 (System architecture, AHB/APB bridges): after each device reset all peripheral clocks are disabled, and a peripheral's clock must be enabled before use. In the RCC chapter, section 7.3.7 (RCC_APB2ENR, address offset 0x18), RCC_APB2ENR_IOPAEN is bit 2, RCC_APB2ENR_IOPCEN bit 4 and RCC_APB2ENR_USART1EN bit 14. Since the RCC block is on the AHB side, the clock enable is a write to one bus and the GPIO register write a write to another.

The bus matrix and bridge details for the STM32F1 are in section 3.1 (System architecture) of RM0008 Rev 21, with Figure 1. That section states that the BusMatrix arbitrates between the core and the DMA with a Round Robin algorithm, and that APB1 is limited to 36 MHz while APB2 runs up to 72 MHz, but it gives no cycle count for an APB access. The register descriptions give the wait-state rule for each register instead; section 7.3.7, for example, says that RCC_APB2ENR has no wait states except when an access to a peripheral in the APB2 domain is still in progress. Check the rule for your register there before quoting a cycle count.

Try it in Wokwi

The project projects/0037-bus-architecture is a single demo that prints the base address of each bus region and of two blocks on them, then sets the GPIOC clock enable and prints the RCC register.

  1. Open projects/0037-bus-architecture in VS Code, build with Ctrl+Shift+B, and start the simulator with F1 → Wokwi: Start Simulator.
  2. Before reading the output, work out from the header addresses above which bus GPIOC base and RCC base belong to. The output should print GPIOC base: 0x40011000 (APB2) and RCC base: 0x40021000 (AHB).
  3. Check the APB2ENR line, which reads the register after IOPAEN, USART1EN and IOPCEN have been set in that order. On a real board the value is 0x00004014, but the simulator prints 0x00000000, as the last recorded run shows. This is a simulator limit rather than a code error, so treat the header bits as the expected value.
Hint

The bus region is the address with the offset removed: GPIOC base, 0x40011000, lies in the APB2 region starting at 0x40010000. Bit 4 is the value 0x10, and the three bits 0x4, 0x10 and 0x4000 add up to 0x4014.

The demo code line by line

The demo's main is short, and every line either prints a base address or touches the clock enable. 

int main(void) {
    SystemCoreClockUpdate();
    uart_init();
    print_line("APB1 base:  ", APB1PERIPH_BASE);
    print_line("APB2 base:  ", APB2PERIPH_BASE);
    print_line("AHB base:   ", AHBPERIPH_BASE);
    print_line("GPIOC base: ", GPIOC_BASE);   /* on APB2 */
    print_line("RCC base:   ", RCC_BASE);     /* on AHB */

    RCC->APB2ENR |= RCC_APB2ENR_IOPCEN;       /* enable the GPIOC bus clock */
    print_line("APB2ENR:    ", RCC->APB2ENR);
    while (1) { }
}

SystemCoreClockUpdate() reads the clock configuration so that the UART divisor is correct, and uart_init sets up the serial output. The next five lines print base addresses taken from header macros rather than typed-in numbers, which matters because the macro is the one place to fix if the header changes.

The line RCC->APB2ENR |= RCC_APB2ENR_IOPCEN; is a read-modify-write, in which the compiler reads the register, sets bit 4 in a copy and writes the copy back. That is safe here because no interrupt in this demo writes to RCC, but in a program where an interrupt changes the same register it would be the race described above, and the remedy would be to make the change only in the main loop or to use a method the chip provides for atomic changes.

The last print reads RCC->APB2ENR back, and the value should contain the bits set in uart_init plus the bit set on this line. The simulator does not keep this register's value and prints zero, so the code is correct and the expected readback has to be checked against the header.

Common mistakes and how to spot them

The wrong bus base

A pin does not change while the serial output says it did. GPIOC is on APB2, but counting from the first bus region gives APB1PERIPH_BASE + 0x1000, or 0x40001000, which is not GPIOC, and since the write does not fault in this demo and the program prints the same lines, the mistake is easy to miss. Use the header macro GPIOC_BASE, and check the printed address against the header.

A simulator readback taken as the hardware value

A debugging session goes nowhere because the APB2ENR line prints zero even after the code sets three bits, which suggests that the clock enable is broken and tempts you to change correct code. Compute the expected value from the header bits, 0x00004014, and note the simulator's limit so that the search is not repeated.

A read-modify-write broken by an interrupt

An output is wrong only now and then, which is hard to reproduce. The main loop sets an output bit with reg |= bit while an interrupt changes another bit in the same register, and if the interrupt lands between the read and the write, its change is lost on write-back. Use the atomic path, the set or clear alias on the RP2040 or the BSRR register on the STM32, which changes only the pins whose bits are 1 in that store (RM0008 Rev 21, section 9.2.5).

A set alias on a register without one

The intended bits do not change, or the write raises a bus error. The RP2040 datasheet states that the SIO "does not support atomic accesses at the bus level, although some individual registers (e.g. GPIO) have set/clear/xor aliases" (section 2.1.2), so a write to 0xD0000000 + 0x2000, the generic set address, does not reach an alias, and "unmapped address ranges raise a bus error when accessed" (section 2.2). Use the register's own set or clear offset, such as GPIO_OUT_SET at 0x014, listed in lesson 38.

Many small writes where one would do

A routine takes four times longer than expected. Each APB register write costs at least 4 cycles, so setting four bits with four separate writes costs at least 16 cycles against 4 for one combined write. Combine the bits into a single write, as BSRR allows on the STM32, where one store can set one pin and reset another, which is exactly what the HAL's toggle code does.

Bus contention and register access in real designs

Firmware engineers examine the bus when timing matters, checking which masters can touch a shared buffer and whether a DMA transfer and the CPU can collide on the same RAM bank. Some designs place DMA and CPU buffers in different banks so that the two rarely compete for a port. Engineers also check the clock enables, because switching off an unused peripheral's clock is how firmware saves power.

A code reviewer asks three questions about any change to shared registers: whether the register is changed by an interrupt as well as by the main code, whether the change is then a single atomic write, and whether every address comes from a header macro rather than a typed number. Those checks catch many bus-related bugs before they reach the bench.

Summary

  • A bus carries an address, data and a control signal from a master to a slave, and a crossbar gives each master its own path to each slave so that different slaves can be used in parallel.
  • The RP2040 fabric has four masters and ten downstream ports, adds no wait states to AHB-Lite accesses and allows up to four transfers per cycle, 2.0 GB/s at 125 MHz.
  • The first 256 kB of SRAM is striped across four 64 kB banks, so consecutive words use different banks.
  • Through the bridge, an APB access takes at least two cycles plus one more for a read and two more for a write.
  • RP2040 atomic aliases at +0x1000, +0x2000 and +0x3000 change bits in one write, and the STM32's BSRR does the same job for GPIO.
  • On the STM32F1 GPIOC is on APB2 and RCC on AHB, with their bases given by the header macros.
  • The simulator's RCC readback prints zero, so compute the expected value from the header bits.
