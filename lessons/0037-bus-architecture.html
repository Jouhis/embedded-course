Bus architecture: AHB, APB, and the bus matrix

Every register write you make travels over a bus. Knowing which bus, and what it costs, explains why two accesses can finish in the same cycle or one can wait.

By the end of this lesson you can trace one register write from the core to a peripheral on an RP2040 or an STM32F103, name the bus it crosses, and say which accesses can run in parallel.

Where we are and why it matters

Lesson 36 named the memory tiers, and it said that the core reaches memory "on the same bus". This lesson opens that bus. Lesson 34 showed the core pushing an eight-word frame at interrupt entry, and that push is a run of bus writes. Lesson 38 comes next and shows how a bus address becomes a register. Here we learn what a bus is, which bus a given address uses, and what each access costs in cycles.

Consider a 3D printer's controller again. The main loop updates a motor's step counter. An interrupt, from a timer or from the endstop switch, also writes to a register that controls the motor's enable pin. A DMA controller copies sensor readings into RAM at the same time. Each of these is a bus master, and each one reaches a slave: RAM, a timer block or a GPIO block. Whether they can proceed together, and how long each one waits, depends on the bus design. If the design is wrong, the printer loses steps at the worst moment. So the bus is part of the firmware's timing.

The concepts, one at a time

A bus is wires and a protocol

A bus is a set of wires and a set of rules that carry three things from one device to another: an address, data, and a control signal that says whether the transfer is a read or a write and how big it is. The device that starts a transfer is the bus master. On a Cortex-M the core is a master, and so is a DMA controller, which can move data without the core. The device that answers is the bus slave. Memory is a slave, and so is a peripheral's register block. A master picks an address, the bus routes the transfer to one slave, and the slave answers.

Your architecture course will know the shared-bus problem. If every master and every slave share one set of wires, only one transfer can happen at a time, and the others wait. That is simple and cheap, and it is slow when several masters want the bus at once.

A crossbar gives each master its own path

A bus matrix, also called a crossbar, removes most of that limit. Each master has a path to each slave, so transfers to different slaves can run at the same time. Two masters that want the same slave still take turns. The turn-taking is called arbitration, and it is the only part that makes one master wait.

A crossbar with four masters and ten slave ports is a grid of up to forty possible paths, and it is much more wiring than a shared bus. The area and power cost is why chips use it for memory, which needs bandwidth, and not for every peripheral.

AHB-Lite, APB and the bridge between them

The RP2040 datasheet names two kinds of bus in its fabric. The fast side is the AHB-Lite crossbar, which connects the masters to memory and to the fast peripherals. The datasheet says that "the bus fabric does not add wait states to any AHB-Lite slave access" (section 2.1). The slow side is the APB peripheral bus, which is reached through an APB bridge. The bridge is a component, and the APB is the bus behind it. The datasheet describes the bridge as the interface between "the high-speed main AHB-Lite interconnect" and "the lower-bandwidth peripherals" (section 2.1.3).

The reason for the split is cost. Memory needs wide, fast paths, and it gets them. Peripheral registers need little bandwidth: a timer register is written a few times per second, not thousands of times per cycle. So a simpler, slower bus with a bridge is the right design for them. The price of the bridge is cycles, which the next section puts in numbers.

Atomic register access

A read-modify-write is a common way to change one bit of a register. The program reads the register, changes the bit in a copy, and writes the copy back. If an interrupt arrives between the read and the write and changes another bit, the write-back overwrites that change. The RP2040 datasheet names the problem directly: "without this capability, it is difficult to safely access IO registers when an interrupt service routine is concurrent with code running in the foreground" (section 2.1.2).

The chip's answer is that each peripheral register block has four addresses. The datasheet lists them: Addr + 0x0000 for a normal read and write, Addr + 0x1000 for an atomic XOR on write, Addr + 0x2000 for an atomic bitmask set on write, and Addr + 0x3000 for an atomic bitmask clear on write. A write to the set or clear address changes only the bits in the mask, in one bus write, with no read first. The atomic alias is the glossary's name for these addresses. The datasheet notes that "most peripherals on RP2040 provide this functionality natively, and atomic writes have the same timing as normal read/write access" (section 2.1.2).

The STM32F1 solves the same problem in a different way. Its GPIO block has a BSRR register, where writing a 1 to a bit sets the matching output and writing a 1 to the bit in the upper half resets it. The HAL's own comment says why the register is used: "This function uses GPIOx_BSRR register to allow atomic read/modify accesses. In this way, there is no risk of an IRQ occurring between the read and the modify access" (stm32f1xx_hal_gpio.c). The two chips reach the same goal, one write with no read, by different register layouts.

Counting the cycles: the RP2040 fabric

The RP2040 bus fabric connects four bus masters, which are core 0, core 1, and the read and write ports of the DMA, to ten downstream ports. Those ports lead to ROM, XIP flash, six SRAM banks, a shared port for the fast AHB-Lite peripherals, and the APB bridge. The datasheet says that "up to four bus transfers can take place each cycle" (section 2.1). A transfer to a port that is free starts at once, and the fabric adds no wait states.

The SRAM is split so that parallel accesses rarely collide. The first 256 kB is word-striped across four 64 kB banks, and two 4 kB banks sit above it. That makes six banks in all. The datasheet's Table 153 shows that consecutive words go to different banks. Each bank has its own port on the crossbar, which is why four masters can use four banks at once.

A worked example with real numbers

Two calculations show what the bus does in practice. The first is the striping. The second is the cost of the APB bridge.

Striping and bandwidth

Take four consecutive word addresses in SRAM. Table 153 gives the bank for each one:

AddressWord in the bankBank
0x20000000word 0Bank 0
0x20000004word 0Bank 1
0x20000008word 0Bank 2
0x2000000Cword 0Bank 3

Four masters that each read one of these four words in the same cycle use four different banks, so none of them waits. The datasheet gives the total: "at a system clock of 125MHz the maximum sustained bus bandwidth is 2.0GBps". You can check that number. Four masters each move one 32-bit word, which is 4 bytes, per cycle. That is 4 × 4 bytes × 125 MHz = 2,000 MB per second, which is 2.0 GB/s. If the four masters all hit the same bank, the bank serves one of them at a time, and the others wait.

The cost of an APB access

The datasheet gives the APB cost in three lines. An APB access "take[s] two cycles minimum (setup phase and access phase)". The bridge "adds an additional cycle to read accesses", and it "adds two additional cycles to write accesses" (section 2.1.3). Counting the way the datasheet does, an APB read takes at least 2 + 1 = 3 cycles, and an APB write takes at least 2 + 2 = 4 cycles.

Consider a loop that writes a register in the UART0 block, which sits on the APB side, at 0x40034000 in the SDK's address map (addressmap.h). If the loop writes 1,000 times, the APB writes cost at least 4,000 cycles, and at a 125 MHz system clock that is 32 microseconds. A write to the SIO block, the single-cycle IO block, is not behind the bridge. The datasheet says the SIO is "attached directly to the cores' IO ports" (section 2.1.2). Fast GPIO code uses SIO for that reason.

The STM32F103 bus map, from its header

The STM32F1 uses the same idea with different names. The ST device header defines three peripheral bus regions from the peripheral base 0x40000000: APB1 at 0x40000000, APB2 at 0x40010000, and AHB at 0x40020000. The header then places the blocks you will use: GPIOC_BASE is APB2PERIPH_BASE + 0x1000, which is 0x40011000, and RCC_BASE is AHBPERIPH_BASE + 0x1000, which is 0x40021000. So GPIOC is on APB2 and the clock controller RCC is on AHB. Source: third_party/cmsis-device-f1/Include/stm32f103xb.h.

The demo enables the peripheral clocks in RCC before it uses GPIOC and USART1, which is the course's convention for these projects. The bit positions come from the header. The rule that a peripheral needs its clock enabled comes from the project's own comment, and the RM0008 clock chapter is where to confirm it, since this course has not yet checked that section. RCC_APB2ENR_IOPAEN is bit 2, RCC_APB2ENR_IOPCEN is bit 4, and RCC_APB2ENR_USART1EN is bit 14. The RCC block is on the AHB side, so the clock enable is a write to one bus and the GPIO register write is a write to another.

The bus matrix and bridge details for the STM32F1 are in the bus architecture chapter of RM0008, with the bus figure. This course has not yet checked that chapter against the vendor text, so this lesson relies only on the header addresses. Read RM0008 for the matrix itself, and check the cycle counts there before you quote them.
You can name the bus behind any address in the RP2040 or STM32 memory map, and you can explain why a write through the APB bridge is slower than a write to SRAM.

Try it in Wokwi

The project projects/0037-bus-architecture is a single demo. It prints the base address of each bus region and of two blocks on them, then sets the GPIOC clock enable and prints the RCC register.

  1. Open projects/0037-bus-architecture in VS Code, build with Ctrl+Shift+B, and start the simulator with F1 → Wokwi: Start Simulator.
  2. Before you read the output, work out which bus GPIOC base and RCC base belong to, using the header addresses above. The output should print GPIOC base: 0x40011000 (APB2) and RCC base: 0x40021000 (AHB).
  3. Check the APB2ENR line. It reads the register after three bits were set in this order: IOPAEN, USART1EN, then IOPCEN. On a real board the value is 0x00004014. The simulator prints 0x00000000 for this line, as the last recorded run shows. That is a simulator limit, not a code error. Treat the header bits as the expected value.
Hint

The bus region is the address with the offset removed. GPIOC base is 0x40011000, which is in the APB2 region that starts at 0x40010000. Bit 4 is the value 0x10. The three bits are 0x4, 0x10 and 0x4000, which add to 0x4014.

The code, explained line by line

The demo's main is short, and every line either prints a base address or touches the clock enable. 

int main(void) {
    SystemCoreClockUpdate();
    uart_init();
    print_line("APB1 base:  ", APB1PERIPH_BASE);
    print_line("APB2 base:  ", APB2PERIPH_BASE);
    print_line("AHB base:   ", AHBPERIPH_BASE);
    print_line("GPIOC base: ", GPIOC_BASE);   /* on APB2 */
    print_line("RCC base:   ", RCC_BASE);     /* on AHB */

    RCC->APB2ENR |= RCC_APB2ENR_IOPCEN;       /* enable the GPIOC bus clock */
    print_line("APB2ENR:    ", RCC->APB2ENR);
    while (1) { }
}

SystemCoreClockUpdate() reads the clock configuration so that the UART divisor is right, and uart_init sets up the serial output the learner reads. The next five lines print the base addresses. Each one comes from the header macro, not from a number typed in by hand. This matters, because a macro is the one place to fix if the header is updated.

The line RCC->APB2ENR |= RCC_APB2ENR_IOPCEN; is a read-modify-write. The compiler reads the register, sets bit 4 in a copy, and writes the copy back. That is safe here, because no interrupt in this demo writes to RCC. In a program where an interrupt does change the same register, the read-modify-write would be the race described above, and the fix would be to make the change in the main loop only, or to use a method the chip provides for atomic changes.

The last print reads RCC->APB2ENR back. The value should contain the three bits set in uart_init and the bit set on this line. The simulator does not keep this register's value, so it prints zero. The code is correct, and the readback is the thing to check against the header.

Common mistakes and how to spot them

1. Using the wrong bus base

GPIOC is on APB2, but a beginner who counts from the first bus region may write APB1PERIPH_BASE + 0x1000. That address is 0x40001000, which is not GPIOC. The write does not fault in this demo, and the program prints the same lines as before, so the mistake is easy to miss. The symptom is a pin that does not change, while the serial output says that it did. The fix is to use the header macro GPIOC_BASE, and to check the printed address against the table in the header.

2. Reading a simulator readback as the hardware value

The APB2ENR line prints zero in the simulator, even after the code sets three bits. A learner who trusts that line may decide the clock enable does not work, and change correct code. The symptom is a debugging session that goes nowhere. The fix is to compute the expected value from the header bits, which is 0x00004014, and to record the simulator's limit in your notes so you do not repeat the search.

3. A read-modify-write that an interrupt can break

Suppose the main loop sets an output bit with reg |= bit, and an interrupt also changes a bit in the same register. If the interrupt lands between the read and the write, its change is lost when the main loop writes back. The symptom is an output that is wrong only now and then, and that is hard to reproduce. The fix is the atomic path: the set or clear alias on RP2040, or the BSRR register on STM32, which changes only the pins whose bits are 1 in that store and leaves the others alone.

4. Writing a set alias to a register that does not support one

The RP2040 datasheet says the SIO "does not support atomic accesses at the bus level, although some individual registers (e.g. GPIO) have set/clear/xor aliases" (section 2.1.2). A learner who writes to 0xD0000000 + 0x2000, the generic set address, is writing to an address the SIO does not treat as an alias. The datasheet also says that "unmapped address ranges raise a bus error when accessed" (section 2.2). The fix is to use the register's own set or clear offset, such as GPIO_OUT_SET at 0x014, which lesson 38 lists.

5. Many small writes where one would do

Each write to an APB register costs at least 4 cycles. Setting four bits with four separate writes therefore costs at least 16 cycles, while one combined write costs 4. The fix is to combine the bits into one write. BSRR does this on STM32, because its one store can set one pin and reset another. The HAL's toggle code does exactly that, writing the set bits and the reset bits in one store.

In real projects

Firmware engineers look at the bus when timing matters. They check which masters can touch a shared buffer, and whether a DMA transfer and the CPU can collide on the same RAM bank. Some designs place the buffers that DMA and the CPU use at addresses in different banks, so the two rarely compete for the same port. They also check the clock enables, because turning a peripheral's clock off is how firmware saves power when the peripheral is not needed.

A code reviewer asks three questions about any change that touches shared registers. Is the register changed by an interrupt as well as the main code? If so, is the change a single atomic write? Does every address come from a header macro and not from a typed number? Those three checks catch many bus-related bugs before they reach a bench.

Interviewers ask about buses to see whether you can reason about contention. A good answer names the cost trade-off, the bridge's cycles, and the atomic alias or BSRR as the fix for the race.

Summary

  • A bus carries an address, data and a control signal from a master to a slave. A crossbar gives each master its own path to each slave, so different slaves can be used in parallel.
  • The RP2040 fabric has four masters and ten downstream ports, and it adds no wait states to an AHB-Lite access. It reaches up to four transfers per cycle, which gives 2.0 GB/s at 125 MHz.
  • The SRAM is striped across four 64 kB banks for the first 256 kB, so consecutive words use different banks.
  • An APB access takes at least two cycles, one more for a read and two more for a write, through the bridge.
  • RP2040 atomic aliases at +0x1000, +0x2000 and +0x3000 change bits in one write. STM32 BSRR does the same job for GPIO.
  • On the STM32F1, GPIOC is on APB2 and RCC is on AHB, with the bases set by the header macros.
  • The simulator's RCC readback prints zero, so compute the expected value from the header bits.

"Why do peripherals usually sit on a slower bus than SRAM, and what does the bridge cost you?" Answer out loud in 60 seconds, then compare.

Model answer

Memory needs bandwidth, so it gets wide, zero-wait paths on a crossbar with its own ports. Peripherals need little bandwidth and their register blocks are simple, so a shared, lower-speed bus behind a bridge is much cheaper in silicon and power. The bridge costs cycles: on the RP2040 an APB read takes one more cycle than the APB minimum, and an APB write takes two more. A register poll or a write-heavy loop feels that cost. Where two parts of the program change one register, the answer is an atomic write, such as the set or clear alias, not a read-modify-write.
