Instruction sets

An instruction is just a number with fields in it. Once you can read those fields by hand, a disassembly stops being a mystery.

By the end of this lesson you can split a 16-bit Thumb instruction into its fields, decode MOVS and ADDS by hand, and encode MOVS R5, #200.

Where we are and why it matters

Lesson 27 showed that a Cortex-M keeps its program and its data in memory, and lesson 28 showed the loop the core runs: fetch an instruction from the address in the program counter, decode it, execute it. Until now the instructions in that loop were written for you in a simulator. In a real project they are numbers in flash, and the only way to see them is to ask a tool to turn the numbers back into text.

That matters in three everyday situations. A HardFault in a debugger points at an address, and you need to know which instruction lives there. A compiler flag such as -mcpu=cortex-m0plus decides which instructions the compiler is allowed to emit, and you need to know what a wrong flag does to the code. And a code review may ask you why a function is 40 bytes long. Each of these starts with the same skill: reading the bits of an instruction and knowing which part means what.

What an instruction set is

An instruction set architecture (ISA) is the set of operations a CPU understands, together with the binary form of each one. The binary form is called the encoding. Software compiled for one ISA does not run on a CPU that implements a different one, because the bits mean different things to each core.

The CPU does not know the words "add" or "move". Its instruction decoder looks at fixed groups of bits and decides what to do. Those bits come from flash over the bus, one fetch at a time, exactly as lesson 28 described. Nothing in the chip stores the name of an instruction. The name exists only in the assembler and in the disassembler, which translate between the name and the bits.

The bus explains why the difference matters. A CISC instruction such as "add this value to the number at this address" can cause a read, an add and a write, all from one instruction. On a RISC core the same work is three instructions: a load, an add on registers, and a store. Each memory access is a separate bus transaction that the core must wait for. The RISC style is easier to pipeline, which lesson 30 explains, because every instruction has the same shape.

An instruction set is a restaurant's menu together with the rules for writing the order slip. It lists what you may ask for and exactly how to write each order. Different kitchens can cook from the same menu in different ways, with more cooks or faster ovens, and the customer's order stays the same. In the same way, the Cortex-M0+ and the Cortex-M3 run the same 16-bit Thumb encodings on different hardware.

Which instruction set the Cortex-M cores use

The Cortex-M3 runs Thumb-2. Arm's TRM says the core implements a Thumb instruction set subset of "all base Thumb instructions, 16-bit and 32-bit", and that it "cannot execute ARM instructions" (Arm Cortex-M3 TRM DDI0337G, §1.1 and §2.1.2). So a Cortex-M3 program mixes 16-bit and 32-bit instructions. The Cortex-M0+ implements the Armv6-M architecture (Arm Cortex-M0+ datasheet), which has only 16-bit instructions plus a few 32-bit ones such as BL.

Why mix sizes? Flash is a limited, expensive resource, and most instructions in a real program are short. A 16-bit form takes half the bytes of a 32-bit form, so the same program fits in less flash. The 32-bit forms exist for the operations that do not fit in 16 bits, such as large immediate values and some branches. The core tells the two sizes apart from the first halfword. The TRM says the prefetch unit "detects Thumb 32-bit instructions and presents these as a single instruction word" (DDI0337G, §1.4).

Fixed bits and fields

An encoding is the rule that maps one instruction to bits. Every 16-bit Thumb encoding has two kinds of bits. The fixed bits are the same for every instance of that instruction, and they identify the operation. The fields change from one instance to the next, and they hold register numbers and immediate values. An immediate is a constant written into the instruction itself, such as the 5 in MOVS R0, #5.

Bits are numbered from the right. The rightmost bit is bit 0, and a 16-bit instruction runs from bit 15 on the left to bit 0 on the right. Hexadecimal makes this easy to read, because each hex digit is exactly four bits, which is called a nibble. The digit 2 is 0010, the digit 0 is 0000, and so on. Write the value out in 16 binary digits before you split it, and count from the right when you name a bit position.

The fixed bits tell you which instruction you are looking at. You match them first, then read the fields at the positions the encoding gives. If the fixed bits do not match any form you know, the bytes are probably not an instruction at all: they may be data, a literal pool or the middle of a 32-bit instruction. This is one reason a disassembly must start at the right address.

A worked example: decoding 0x2005 bit by bit

Take the halfword 0x2005 and decode it step by step. First write it in binary, with a space after each nibble so the groups are easy to see: 0010 0000 0000 0101.

  1. Bits 15 to 11 are the first five digits, 00100. That is the fixed pattern for MOVS Rd, #imm8. So the instruction is a move of an 8-bit immediate into a register.
  2. Bits 10 to 8 are 000. That is the destination register Rd, which is 0, so the register is R0.
  3. Bits 7 to 0 are 0000 0101. That is the immediate, which is 5 in decimal.

Put the three results together and the instruction is MOVS R0, #5. You did not need the assembler or a table to get there, only the pattern and the bit positions. The widget below shows the same register with the bit numbers and the three fields drawn under it, so you can check that each bit lands where you think it does.

ADDS Rd, Rn, Rm (the register form) has the fixed bits 0001100 in bits 15 to 9, then Rm in bits 8 to 6, Rn in bits 5 to 3 and Rd in bits 2 to 0. Decode 0x18D1 the same way. In binary it is 0001 1000 1101 0001. Bits 15 to 9 are 0001100, the fixed pattern. Bits 8 to 6 are 011, which is R3, the second source. Bits 5 to 3 are 010, which is R2, the first source. Bits 2 to 0 are 001, which is R1, the destination. So 0x18D1 is ADDS R1, R2, R3.

The fields are the same for every instance of an instruction. Only their values change. The examples in this lesson were checked by assembling the instructions with the Arm GNU toolchain (arm-none-eabi-gcc 14.2) and reading the bytes back, so the bit patterns are the ones the tools produce. The formal encoding tables are in the Armv7-M Architecture Reference Manual (Armv7-M ARM, DDI0403), which we did not read for this lesson, so use the disassembler output as the working reference. Each register field here is 3 bits wide, so it can name only R0 to R7. That is why the 16-bit forms are limited to the low registers.

The code, as the toolchain prints it

The assembler and disassembler are the tools you will use on real code. Assembling the two instructions above for a Cortex-M3 target and disassembling the result gives the following listing. Each line has the address, the raw bytes in hex, then the instruction the bytes decode to. 

0:	2005      	movs	r0, #5
2:	25c8      	movs	r5, #200	@ 0xc8
4:	18d1      	adds	r1, r2, r3

Line by line: the address 0 is where the instruction sits in the output file, and each 16-bit instruction takes two bytes, so the next address is 2 and then 4. The field 2005 is the halfword value you decoded above. The mnemonic movs is the operation, and the operands are the destination register and the immediate. The second line, 25c8, is the encoding of MOVS R5, #200, which you will build yourself in the hands-on task. The third line is the register form of ADDS from the previous section.

Immediates and their limits

The 16-bit MOVS form has an 8-bit immediate field, so it can hold only the values 0 to 255. Its largest value is therefore 0xFF, which is 255. The field is 8 bits wide because 8 bits is what fits in the 16 bits of the encoding after the fixed opcode and the 3-bit register are placed.

What happens when a value is too big depends on your target. We assembled movs r0, #300 for two targets. For a Cortex-M3 the assembler chose the 32-bit form, movs.w r0, #300, which takes four bytes. For a Cortex-M0+, which has no 32-bit MOVS, it stopped with the error invalid immediate: 300 is out of range. The Pico is a Cortex-M0+, so on a Pico the error is the one you will see.

The ADDS register form has a 3-bit immediate in its other form, ADDS Rd, Rn, #imm3. Three bits hold only 0 to 7. Assembling adds r0, r1, #8 for the Cortex-M0+ gives the error immediate value out of range. A value that does not fit is a limit of the encoding, not a bug in your code, and the fix is to load the constant another way, for example from a literal in memory. Lesson 32 shows what the compiler does with such constants.

Try it: encode an instruction

Your task: set the bits in the empty register below so that they encode MOVS R5, #200. Work out the fields first: Rd is 5, and the immediate is 200. Then click the bits. The widget shows the hex value, which you can check against the quiz answer.

  1. Write Rd as 3 binary digits, then put them in bits 10 to 8, and add the fixed 00100 in bits 15 to 11.
  2. Write 200 as 8 binary digits, and put them in bits 7 to 0.
  3. Compare your value with the hex result. You will know it works when the widget shows 0x25C8.
Hint

200 is 1100 1000 in binary. Rd = 5 is 101. Put 101 in bits 10 to 8, and the fixed 00100 in bits 15 to 11. Then combine them.

You read a real 16-bit Thumb instruction field by field, and you encoded one from its assembly form. That is the skill you need to read any disassembly line.

Common mistakes and how to spot them

The mistakes below are the ones beginners make most often when they first read machine code. Each one has a symptom you can see, so you can tell which one you have made.

  1. Using the wrong bit range. 0x2005 has its register at bits 10 to 8, not 11 to 9. If you count from the wrong bit, you get a register number that looks plausible but is wrong. The symptom is a disassembly that names a different register from the one you expected. The fix is to write 16 binary digits and label each field before you read it.
  2. Reading the bytes in the wrong order. The Cortex-M is little-endian, which means the low byte of a halfword is stored first. The instruction 0x2005 sits in memory as the two bytes 05 20. We checked this by assembling it and dumping the section. If you read the memory view of a debugger as "20 05", you will decode a different instruction. The symptom is that the disassembly of a memory range looks wrong, while the same bytes read in the opposite order look right. The fix is to read the memory view in halfwords, or let the debugger's disassembly view do the work.
  3. Using MOVS with a high register. The 16-bit MOVS and ADDS forms can name only R0 to R7, because their register fields are 3 bits wide. Writing movs r8, #1 for a Cortex-M0+ gives the error cannot honor width suffix. The fix is to use MOV, which has a form for R8 to R12, or to move the value through a low register. On a Cortex-M3 the same line assembles as a 32-bit movs.w, so the error appears only when you move the project to a smaller core.
  4. Assuming the immediate is a value you can write freely. A line such as movs r0, #300 works on the Cortex-M3 and fails on the Cortex-M0+. The symptom is a build that succeeds on one board and stops on another. The fix is to check the immediate range for the core you build for, or to load large constants from memory.

In real projects

Nobody on a professional team memorises encodings. Engineers read the disassembly when they need to, and they lean on three habits. First, they check the target flags. A project that builds for cortex-m0plus must not contain instructions that only a Cortex-M3 has, and a link or assembly error is the cheapest way to find out. Second, they use the disassembler on the ELF file, not on the source, when they want to know what the compiler really did. Third, they keep a short reference sheet of the encodings they use most. This course keeps one in the Thumb-2 quick reference.

In a code review, a reviewer who sees a long sequence of instructions for a simple operation will ask whether the immediate is out of range, or whether the code uses a high register that forces a 32-bit form.

Summary

  • An instruction set is the set of operations a CPU understands, and an encoding is the bit pattern for each one.
  • RISC keeps memory access to loads and stores. CISC allows arithmetic on memory operands. Each style sets how many bus transactions one instruction can cause.
  • The Cortex-M3 runs Thumb-2, which mixes 16-bit and 32-bit instructions. The Cortex-M0+ implements Armv6-M.
  • A 16-bit encoding has fixed bits, which identify the instruction, and fields, which hold registers and immediates.
  • Bits are numbered from 0 on the right. Write 16 binary digits before you split a halfword.
  • The 16-bit MOVS takes an 8-bit immediate (0 to 255), and the register fields of the 16-bit forms name only R0 to R7.
  • A Cortex-M halfword is stored little-endian, so 0x2005 sits in memory as 05 20.
