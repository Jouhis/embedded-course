Instruction sets

The operations a CPU understands and their binary encodings

By the end of this lesson you can split a 16-bit Thumb instruction into its fields, decode MOVS and ADDS by hand, and encode MOVS R5, #200.

Instructions as numbers in flash

Lesson 27 showed that a Cortex-M keeps its program and its data in memory, and lesson 28 the loop the core runs: fetch the instruction at the address in the program counter, decode it, execute it. So far the instructions in that loop were written for you in a simulator, but in a real project they are numbers in flash, and the only way to see them as text is to have a tool translate the numbers back.

That skill is needed in three everyday situations. A HardFault in a debugger points at an address, and you need to know which instruction lives there. A compiler flag such as -mcpu=cortex-m0plus decides which instructions the compiler may emit, so you need to know what a wrong flag does to the code. And a code review may ask why a function is 40 bytes long. Each of these starts with reading the bits of an instruction and knowing which part means what.

Instruction set architectures

An instruction set architecture (ISA) is the set of operations a CPU understands, together with the binary form of each, which is called its encoding. Software compiled for one ISA does not run on a CPU implementing another, because the same bits mean different things to each core.

The CPU knows nothing of the words "add" or "move". Its instruction decoder looks at fixed groups of bits and decides what to do, and those bits arrive from flash over the bus one fetch at a time, as lesson 28 described. Nothing in the chip stores an instruction's name, which exists only in the assembler and the disassembler, the tools that translate between names and bits.

ISAs fall broadly into two styles. A CISC (complex instruction set) design allows arithmetic directly on memory operands, so an instruction such as "add this value to the number at this address" can cause a read, an add and a write on its own. A RISC (reduced instruction set) design such as Arm restricts memory access to loads and stores, so the same work takes three instructions: a load, an add on registers and a store. Each memory access is then a separate bus transaction the core waits for, and because every instruction has the same simple shape, the RISC style is easier to pipeline, as lesson 30 explains.

An instruction set resembles a restaurant's menu together with the rules for writing the order slip: it lists what may be ordered and exactly how to write each order. Different kitchens can cook from the same menu in different ways, with more cooks or faster ovens, while the customer's order stays the same, just as the Cortex-M0+ and the Cortex-M3 run the same 16-bit Thumb encodings on different hardware. The comparison stops at the menu itself, since some cores accept a longer menu than others, as the next section shows.

The instruction sets of the Cortex-M cores

The Cortex-M3 runs Thumb-2. Arm's TRM states that the core implements a Thumb instruction set subset of "all base Thumb instructions, 16-bit and 32-bit", and that it "cannot execute ARM instructions" (Arm Cortex-M3 TRM DDI0337G, §1.1 and §2.1.2), so a Cortex-M3 program mixes 16-bit and 32-bit instructions. The Cortex-M0+ implements the Armv6-M architecture (Arm Cortex-M0+ datasheet), which has only 16-bit instructions plus a few 32-bit ones such as BL.

Mixing sizes saves flash, which is limited and expensive, while most instructions in a real program are short. A 16-bit form takes half the bytes of a 32-bit form, so the same program fits in less flash, and the 32-bit forms cover the operations that cannot fit in 16 bits, such as large immediate values and some branches. The core distinguishes the two sizes from the first halfword, and the TRM notes that the prefetch unit "detects Thumb 32-bit instructions and presents these as a single instruction word" (DDI0337G, §1.4).

Fixed bits and fields

Every 16-bit Thumb encoding contains two kinds of bits. The fixed bits are identical in every instance of an instruction and identify the operation, while the fields change between instances and hold register numbers and immediate values. An immediate is a constant written into the instruction itself, such as the 5 in MOVS R0, #5.

Bits are numbered from the right, so a 16-bit instruction runs from bit 15 on the left to bit 0 on the right. Hexadecimal makes this easy to read, because each hex digit is exactly four bits, a group called a nibble; the digit 2 is 0010 and the digit 0 is 0000. Write the value out as 16 binary digits before splitting it, and count from the right when naming a bit position.

The fixed bits identify the instruction, so you match them first and then read the fields at the positions the encoding specifies. If the fixed bits match no known form, the bytes are probably not an instruction at all but data, a literal pool or the middle of a 32-bit instruction, which is one reason a disassembly must start at the right address.

Worked example: decoding 0x2005 bit by bit

We decode the halfword 0x2005 step by step, starting by writing it in binary with a space after each nibble so that the groups are easy to see: 0010 0000 0000 0101. The value 5 in the last nibble suggests an answer already, but the fields must be read in order.

  1. Bits 15 to 11 are the first five digits, 00100, which is the fixed pattern for MOVS Rd, #imm8, so the instruction moves an 8-bit immediate into a register.
  2. Bits 10 to 8 are 000, the destination register Rd, which is 0, so the register is R0.
  3. Bits 7 to 0 are 0000 0101, the immediate, which is 5 in decimal.

Combining the three results gives MOVS R0, #5, reached without an assembler or a lookup table, only from the pattern and the bit positions. The widget below shows the same register with the bit numbers and the three fields drawn under it, so you can check that each bit lands where you expect.

The register form of ADDS Rd, Rn, Rm has the fixed bits 0001100 in bits 15 to 9, followed by Rm in bits 8 to 6, Rn in bits 5 to 3 and Rd in bits 2 to 0. Decoding 0x18D1 the same way starts from its binary form, 0001 1000 1101 0001. Bits 15 to 9 are 0001100, the fixed pattern; bits 8 to 6 are 011, so the second source is R3; bits 5 to 3 are 010, so the first source is R2; and bits 2 to 0 are 001, so the destination is R1. The halfword 0x18D1 is therefore ADDS R1, R2, R3.

The field positions are the same in every instance of an instruction, and only their values change. The examples in this lesson were checked by assembling the instructions with the Arm GNU toolchain (arm-none-eabi-gcc 14.2) and reading the bytes back, so the bit patterns are the ones the tools produce. The formal encoding tables are in the Armv7-M Architecture Reference Manual (Armv7-M ARM, DDI0403), which this lesson does not quote, so treat the disassembler output as the working reference. Each register field here is 3 bits wide and can name only R0 to R7, which is why the 16-bit forms are limited to the low registers.

Disassembler output

The assembler and the disassembler are the tools used on real code. Assembling the instructions above for a Cortex-M3 target and disassembling the result gives the listing below, in which each line holds the address, the raw bytes in hex and the instruction those bytes decode to. 

0:	2005      	movs	r0, #5
2:	25c8      	movs	r5, #200	@ 0xc8
4:	18d1      	adds	r1, r2, r3

The address 0 is where the first instruction sits in the output file, and since each 16-bit instruction occupies two bytes, the next addresses are 2 and 4. The field 2005 is the halfword decoded above, movs is the operation, and the operands are the destination register and the immediate. The second line, 25c8, encodes MOVS R5, #200, which you will build yourself in the hands-on task, and the third line is the register form of ADDS from the previous section.

Immediate ranges

The 16-bit MOVS form has an 8-bit immediate field and so holds only the values 0 to 255, with 0xFF, or 255, as its largest value. An n-bit unsigned field holds values up to

max = 2n − 1(1)

where n is the field width in bits. The MOVS field is 8 bits wide because 8 bits is what remains of the 16 after the fixed opcode and the 3-bit register field are placed.

What happens to a value that is too large depends on the target. Assembling movs r0, #300 for a Cortex-M3 made the assembler choose the 32-bit form, movs.w r0, #300, which takes four bytes, while for a Cortex-M0+, which has no 32-bit MOVS, it stopped with the error invalid immediate: 300 is out of range. The Pico is a Cortex-M0+, so that error is the one you will see on a Pico.

The ADDS instruction also has an immediate form, ADDS Rd, Rn, #imm3, whose 3-bit field holds only 0 to 7, and assembling adds r0, r1, #8 for the Cortex-M0+ gives the error immediate value out of range. A value that does not fit is a limit of the encoding rather than a bug in the code, and the remedy is to load the constant another way, for example from a literal in memory, which lesson 32 shows the compiler doing.

Common mistakes and how to spot them

The wrong bit range

The disassembly names a different register from the one you decoded, because the count started at the wrong bit: in 0x2005 the register is in bits 10 to 8, not 11 to 9, and a shifted range still gives a plausible register number. Write out all 16 binary digits and label each field before reading it.

Bytes read in the wrong order

The disassembly of a memory range looks wrong, while the same bytes read in the opposite order look right. The Cortex-M is little-endian, storing the low byte of a halfword first, so 0x2005 sits in memory as the two bytes 05 20, which we confirmed by assembling it and dumping the section, and reading a debugger's memory view as "20 05" decodes a different instruction. Read the memory view in halfwords, or let the debugger's disassembly view do the work.

MOVS with a high register

Writing movs r8, #1 for a Cortex-M0+ gives the error cannot honor width suffix, because the 16-bit MOVS and ADDS forms have 3-bit register fields that name only R0 to R7. On a Cortex-M3 the same line assembles as a 32-bit movs.w, so the error appears only when the project moves to a smaller core. Use MOV, which has a form for R8 to R12, or pass the value through a low register.

An immediate treated as unlimited

A build succeeds on one board and stops on another, because a line such as movs r0, #300 assembles for the Cortex-M3 and fails for the Cortex-M0+. Check the immediate range of the core you build for, or load large constants from memory.

Encodings in day-to-day work

Nobody on a professional team memorises encodings. Engineers read the disassembly when needed and rely on three habits. They check the target flags, because a project built for cortex-m0plus must not contain instructions only a Cortex-M3 has, and an assembly or link error is the cheapest way to find out. They run the disassembler on the ELF file rather than reading the source when they want to know what the compiler really did. And they keep a short reference sheet of the encodings they use most, which this course provides as the Thumb-2 quick reference.

A reviewer who sees a long sequence of instructions for a simple operation will ask whether an immediate is out of range or whether the code uses a high register that forces a 32-bit form.

Summary

  • An instruction set is the set of operations a CPU understands, and an encoding is the bit pattern for each one.
  • RISC restricts memory access to loads and stores while CISC allows arithmetic on memory operands, and the style sets how many bus transactions one instruction can cause.
  • The Cortex-M3 runs Thumb-2, mixing 16-bit and 32-bit instructions, and the Cortex-M0+ implements Armv6-M.
  • A 16-bit encoding has fixed bits that identify the instruction and fields that hold registers and immediates.
  • Bits are numbered from 0 on the right, so write 16 binary digits before splitting a halfword.
  • The 16-bit MOVS takes an 8-bit immediate (0 to 255), and the register fields of the 16-bit forms name only R0 to R7.
  • A Cortex-M halfword is stored little-endian, so 0x2005 sits in memory as 05 20.
