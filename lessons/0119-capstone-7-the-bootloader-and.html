Capstone 7: the bootloader and the image layout

Image checks before the jump to the application

By the end of this lesson you can lay out a bootloader and an application slot in one linker script, read the 32-byte image header and the vector table, explain each step of the jump to the application, and say from a map file and a size report whether an image fits.

Firmware updates in the field

Lesson 118 gave the dryer a bus, so that a host can read its status and start a cycle, but the firmware is still fixed at the factory, so a bug fix, a new feature or a new material table means a new image that has to reach a dryer already installed in a customer's workshop. A product that cannot be updated in the field has to be replaced in the field, and without an update path every change is a service visit.

The usual answer is a bootloader (lesson 104), a small program that runs first after every reset, checks the application image and jumps to it only if the image looks valid, and since it is the one part of the firmware an update must never damage, it is kept small and fixed. Lesson 84 added a watchdog, which belongs with the bootloader, because when a hung application stops feeding the watchdog, the watchdog resets the chip and the bootloader is the code that runs again.

The bootloader and the image in one ELF

A product normally keeps the bootloader and the application as two separate images, joined by a flash tool or by a library such as MCUboot (lesson 104), whereas this build keeps both in one ELF and one hex file, so that it stays simple to simulate and flash, the linker script deciding where each part of the image goes, which is what this lesson is about.

An ELF file is the standard output of the linker, holding the code, the data and the addresses they must be loaded at, as well as the symbol names a debugger uses, while the hex file holds the same bytes as text, which a programmer tool writes to flash. The linker can also write a map file listing where every section and symbol was placed, the best tool for checking the layout, which you will use in the size check and the hands-on task.

The linker script, boot/boot.ld, splits the flash into two regions, the same split lesson 104 described for a combined image.

RegionAddress and sizeWhat is in it
BOOT0x08000000, 16 KBThe startup code, the bootloader's main(), and the initial values of .data.
APP0x08004000, 48 KBThe image header (32 bytes), the application's vector table at +0x200, and everything else: FreeRTOS, the HAL, the drivers and the application.
RAM0x20000000, 20 KBShared by both. The startup code initialises it once, so the jump does not copy anything again.

Flash is the chip's non-volatile memory, where the program lives and survives a power cut, whereas RAM is the working memory, whose contents are lost at reset, and since the CPU reads flash at fixed addresses, the header and the vector table must sit at fixed offsets. The bootloader therefore does not search the flash for the application but knows that the slot starts at 0x08004000 and reads the header from that address.

Section placement by input file

The script places each section by the input file it came from, the bootloader's objects (the startup, system and bootloader files) being matched by name and going to BOOT, while every other input goes to the application slot through the catch-all rules. The .data section needs a special arrangement, its initial values being stored in BOOT and copied to RAM by the startup code, because C requires initialised global variables to start with their initial values and RAM loses its contents at reset, and since the RAM is shared, the copy is done once, so the application needs no copy of its own.

Two lines at the end of the script check the layout the bootloader relies on, ASSERT statements that make the link fail if they are false. 

ASSERT(ADDR(.app_header) == ORIGIN(APP), "the image header must be the first thing in the slot")
ASSERT(ADDR(.app_vectors) == ORIGIN(APP) + 0x200, "the vector table must be at slot + 0x200")

The first line requires the header to be the first thing in the application slot, at 0x08004000, because the bootloader reads it from that address, and the second requires the vector table to start 0x200 bytes into the slot, so if a later change moves either one, the link fails and no image is produced, the cheapest kind of test in the project, because it runs during the build, before any board sees the image.

The image header and the vector table

The bootloader does not trust the application slot until it has read a header, a C structure at the first byte of the slot, a static assertion in the same file making the build fail if the structure is not exactly 32 bytes. 

typedef struct {
    uint32_t magic;          /* must equal APP_IMAGE_MAGIC */
    uint32_t version;        /* (major << 16) | minor */
    uint32_t image_end;      /* address one past the last byte of the image */
    uint32_t vector_offset;  /* the vector table, as an offset from this header */
    uint32_t reserved[4];    /* room for a CRC and a signature (lesson 106); zero here */
} app_header_t;

_Static_assert(sizeof(app_header_t) == 32u, "the image header is 32 bytes");

Every field is a uint32_t, a 32-bit unsigned integer, so the structure has no hidden padding and its size is simply the sum of the fields, 4 + 4 + 4 + 4 + 16 = 32 bytes, an arithmetic the static assertion checks at compile time, and the table below gives each field its offset from the start of the header and the value this build stores.

The header fields

OffsetFieldThis build's value
+0magic0x41505031, the ASCII letters "APP1", so a stray pattern of bytes is unlikely to match
+4version(major << 16) | minor, so 1.0 is 0x00010000
+8image_endThe address one past the last byte of the image, taken from the linker
+12vector_offset0x200, the offset of the vector table from the header (512-byte aligned for VTOR)
+16 to +31reserved[4]Zero here; room for a CRC and a signature (lesson 106)

The magic is four ASCII letters, 0x41 being 'A', 0x50 'P', 0x50 'P' and 0x31 '1' in the byte order the table shows, and since erased flash reads as all ones and a leftover program has no reason to contain this exact pattern at offset 0, a match is a useful sign that the slot holds an image of this kind, although not proof that the image is intact, which is what the later fields and, in a product, a signature are for.

The version is one 32-bit number with the major version in the top half and the minor version in the bottom half, which the application draws on the display and the host can read, so a field technician and a host see the same answer, while the image_end field lets the bootloader reject an image claiming to run past the end of its slot.

The application's vector table

The vector table is the list of addresses the CPU reads on reset and on each exception, word 0 holding the initial stack pointer, the top of the stack, and word 1 the reset handler, the first code to run (lesson 42), while the rest holds the handler for each system exception and device interrupt, so when an interrupt fires, the core reads the entry for that exception number from the active table and branches to it.

The application's table is at +0x200, its first word at 0x08004200 (PM0056 Rev 7, section 4.4.4, requires the table offset to be 512-byte aligned), and since the header is 32 bytes, the linker leaves 480 bytes of padding between the header and the table, padding that is neither code nor data but exists only so that the table lands on the required boundary. 

__attribute__((section(".app_vectors"), used))
const vector_fn app_vectors[APP_VECTOR_COUNT] = {
    [0 ... APP_VECTOR_COUNT - 1] = app_fault,
    [0]  = (vector_fn)(uintptr_t)&_estack,
    [1]  = app_reset,
    [11] = SVC_Handler,                       /* SVCall */
    [14] = PendSV_Handler,
    [15] = SysTick_Handler,
    [16 + APP_IRQ_USART1] = USART1_IRQHandler,
};
  • __attribute__((section(".app_vectors"), used)) places the array in the section that boot.ld puts at +0x200. used stops the compiler from discarding it, since nothing in the C code calls it.
  • APP_VECTOR_COUNT is 16 system entries plus 60 device interrupts, 76 entries in all. Each entry is 4 bytes, so the table is 304 bytes, which is the 0x130 that the map file reports for .app_vectors.
  • [0 ... APP_VECTOR_COUNT - 1] = app_fault fills every entry with a handler that loops forever. An interrupt the application does not expect therefore stops in a known place, where a debugger can show it.
  • [0] = &_estack stores the top of RAM as the initial stack pointer. The symbol comes from the linker script, so the value is never typed by hand.
  • [1] = app_reset stores the reset handler. Its address has bit 0 set, as it does for every Thumb function, and the bootloader checks that bit.
  • The entries at 11, 14, 15 and 16 + 37 are the SVCall, PendSV and SysTick exceptions and the USART1 interrupt. The first 16 entries belong to the core, so device interrupt number 37 sits at index 53. The USART1 number is taken from the STM32F1 reference manual, as the header comment records.

The bootloader's checks

Before jumping, the bootloader checks the header and the two words it will use, in a fixed order, any failure stopping the boot.

  1. The magic equals APP_IMAGE_MAGIC. If not, the slot holds no image of this kind.
  2. The vector_offset equals 0x200. If not, the header describes a layout that this bootloader cannot jump into.
  3. The image_end lies after the first vector word and no further than the end of the 48 KB slot. This rejects an image that claims to be empty or to run past its slot.
  4. The initial stack pointer, word 0 of the table, lies inside RAM.
  5. The reset handler, word 1, has bit 0 set. Cortex-M cores run only Thumb code, and bit 0 marks a Thumb address.
  6. The reset handler lies inside the image, between the start of the slot and image_end.

Each check removes one way for a bad image to crash the boot, whereas the bootloader checks neither a CRC nor a signature, although the header has room for them and lesson 106 covers why a signature is the real protection, so an image passing these checks can still have wrong contents, the checks preventing crashes rather than tampering.

When every check passes, the bootloader prints BOOT: image valid, jumping over USART1 and makes the jump, and when one fails, it prints BOOT: no valid image, staying in the bootloader and loops, so the board waits for a new image rather than running a bad one, these two lines being the first thing a serial monitor shows and telling you which path the boot took. The application reads its own header from flash and draws FW 1.0 on the bottom line of the display, which is how a field technician checks which image is running and how the host learns it too.

The jump gives up the bootloader. After __set_MSP() and the branch, the bootloader's code never runs again, and it cannot recover a hung application. A watchdog that resets the chip brings the bootloader back, which is why lesson 84's watchdog and this bootloader belong together.

The jump to the application

The jump is a short function with four steps in a fixed order.

  1. Interrupts off. The bootloader disables interrupts, so that none runs in the middle of the hand-over.
  2. The vector table. It points the vector table register (VTOR) at the application's table, so that exceptions now use the application's handlers.
  3. The stack. It sets the main stack pointer (MSP) to the value in word 0 of that table.
  4. The branch. It calls the reset handler from word 1 as a function that never returns.
static void jump_to_app(void) {
    const uint32_t *vectors = (const uint32_t *)(uintptr_t)(APP_BASE_ADDR + APP_VECTOR_OFFSET);
    uint32_t sp = vectors[0];
    uint32_t reset = vectors[1];

    __disable_irq();                                  /* no interrupt may run in the middle of the hand-over */
    SCB->VTOR = APP_BASE_ADDR + APP_VECTOR_OFFSET;    /* exceptions now use the application's table */
    __set_MSP(sp);
    ((void (*)(void))(uintptr_t)reset)();             /* never returns */
}
  • The first line computes the address of the application's table, 0x08004200. The cast through uintptr_t converts the integer to a pointer, which is how C code reads a fixed hardware address.
  • sp and reset copy words 0 and 1 of that table into local variables before anything changes. The later steps then use values that were read while the old state was still in place.
  • __disable_irq() clears the interrupt mask in the core, so no interrupt can start during the steps that follow.
  • SCB->VTOR = ... writes the new table address into the vector table register. From this point on, the core finds every handler in the application's table.
  • __set_MSP(sp) moves the main stack pointer to the top of the application's stack. The bootloader's own stack is left behind.
  • The last line casts reset to a function pointer and calls it. The call does not return, because the application's reset handler never returns. It sets up its own state and then runs app_main().

Each step depends on the one before, because if step 2 is skipped, the first interrupt in the application runs a handler from the bootloader's table, and if step 3 is skipped, the application starts on the stack pointer the bootloader left behind rather than the top of its own stack, which is why a mistake here shows up as a crash that looks random.

The jump neither copies the application into RAM nor reloads .data, both having been handled once by the startup code before main() ran, so it changes only which table and which stack the core uses and then hands over control.

  1. The bootloader is running from 0x08000000 with its own vector table and stack. It has already checked the application's header and decided to boot it.
  2. It reads words 0 and 1 of the application's vector table at 0x08004200: the initial stack pointer, 0x20005000, the top of the 20 KB RAM, and the address of the application's reset handler.
  3. __disable_irq() masks interrupts, so no handler can run halfway through the hand-over.
  4. VTOR is set to 0x08004200. From now on every exception finds its handler in the application's table; skipping this would send the first interrupt to a bootloader handler.
  5. MSP is set to 0x20005000. The bootloader's stack is abandoned, and the application starts at the top of its own.
  6. The reset handler from word 1 is called and never returns. The application's startup code copies .data, clears .bss and runs app_main(); the jump itself only changed the table and the stack.

The size report gives totals and the map file the exact addresses, showing that the bootloader uses about 1 KB of its 16 KB and that the application ends at 0x08008FC0. Before reading the arithmetic below, predict how much of the 48 KB slot is still free. 

application end   0x08008FC0
slot start        0x08004000
image span        0x08008FC0 - 0x08004000 = 0x4FC0 = 20416 bytes (about 19.9 KB)
slot size         48 KB = 49152 bytes
free in the slot  49152 - 20416 = 28736 bytes (about 28 KB)

Flash used by both regions together is about 21 KB of the 64 KB part and RAM use about 10 KB of 20 KB, including the 8 KB FreeRTOS heap that holds the task stacks, while the data figure of 104 bytes is stored in BOOT and copied to RAM at startup, so it counts against both regions, which is why the flash total is a little larger than the text section alone.

The text section is the largest term, the linker removing functions that nothing calls (--gc-sections, set in CMakeLists.txt) and the logic being compiled at -Og, which keeps the code easy to step through in a debugger. If the image ever did not fit, the trims in order would be -Os for the release build, a font reduced to the characters the status screen uses and the log strings moved out of the application, each trade-off costing debuggability, which is why the course keeps the debug build for the simulator.

The 28 KB of free space is the room a future feature has to fit into, so a plan needing more would need either a smaller application or a larger slot, the second meaning a different linker script and a new layout the bootloader must accept, which makes the size report the first thing to check before a design review asks for a feature.

  2. Open the map file and search for .app_header and .app_vectors, expecting the header at 0x08004000 with size 0x20 and the vector table at 0x08004200 with size 0x130.
  3. Open projects/0118-dryer-modbus-bootloader/starter in VS Code, press Ctrl+Shift+B to build and then F1 → Wokwi: Start Simulator, expecting BOOT: checking application slot followed by BOOT: image valid, jumping on the serial monitor. The application's own lines follow the jump on a real board, but since the application runs FreeRTOS, which does not start in the simulator (see lesson 87), they may not appear there, whereas a real board prints DRYER RTOS OK, the first line of the solution's main.c.
  4. Break the header on purpose by changing the first field of the header initialiser in starter/boot/app_vectors.c from APP_IMAGE_MAGIC to 0u, then rebuild and start the simulator again, expecting BOOT: no valid image, staying in the bootloader and no application output, because this change touches only the header, so the bootloader's check is the one that fails.
  5. Undo the change, so that the magic is APP_IMAGE_MAGIC again, and rebuild, after which the serial monitor should show the jump again.
Hint for step 4

The first field of the header initialiser in app_vectors.c is the magic. The bootloader compares it with APP_IMAGE_MAGIC in app_image.h, and that comparison is the first of its checks. Change only the header, not the define, so the two sides disagree.

Common mistakes and how to spot them

Each of these has happened to someone building a bootloader, and each entry gives the symptom first, so that you can recognise it before finding the cause.

A stale image on the board

You change APP_VERSION to 1.1 and rebuild, but the display still reads FW 1.0, because the programmer flashed an old .hex file, often from an earlier build folder, so the header on the board is the old one. Flash the file from the build you just made, check its time stamp and read the version from the display or from the header in the flash, since a version not checked on the device is only a guess.

A header offset the linker does not match

The boot prints BOOT: no valid image, staying in the bootloader after someone changed APP_VECTOR_OFFSET in app_image.h, because the header and the bootloader then agree on the new offset while the linker still places the table at +0x200, so the bootloader reads its words from the wrong place, whereas moving the table in boot.ld instead makes the link fail with the second ASSERT message. The header, the table and the linker script must agree on one layout, so keep APP_VECTOR_OFFSET, the ALIGN(512) placement and the two ASSERT lines in step, and read the map file to confirm where .app_vectors landed before flashing.

A hand-written reset address with bit 0 clear

The magic, the offset and the stack pointer all look right in the hex file, but the bootloader prints BOOT: no valid image, staying in the bootloader and never jumps, because someone wrote the vector table by hand, or copied an address from a listing, leaving the reset handler address with bit 0 clear, which the check in step 5 rejects, since a Cortex-M core cannot run an address without the Thumb bit. Take every table entry from the compiler and the linker rather than from a calculation on paper, and if you must write a table by hand, set bit 0 on every code address.

An image that outgrows its region

The build stops in the linker with a message naming the region that overflowed, BOOT or APP, because the application has grown past 48 KB or the bootloader past 16 KB, so a section no longer fits its region. Look at the size report first and then read the map file to see which input files grew, trimming the larger ones or moving the boundary in boot.ld and accepting that the two regions change size, and since the linker writes no image that does not fit, a bad layout fails the build rather than the board.

Production bootloaders and their reviews

A production bootloader is rarely written from scratch, teams usually starting from an existing open bootloader, such as MCUboot (its design document is listed in RESOURCES.md), and adapting it to their own flash layout and signing keys, MCUboot's design describing primary and secondary image slots and swap types, so that a new image can be written while the old one still boots and a failed update can be rolled back. This project's header is its own design rather than MCUboot's format, which is worth knowing before comparing the two.

The bootloader is reviewed harder than any other code in the product, because a bug there can make a device unrecoverable in the field, reviewers asking every time what happens if power is lost during the write, what happens if the new image is bad and what can reach the jump without passing every check, and a short bootloader with a clear list of checks is easier to review than a long one, one reason this build keeps the list in plain code.

Teams shipping a bootloader also test it with bad images on purpose, a test image with a wrong magic, a wrong offset or a reset address with bit 0 clear having to be rejected with the reject message while a good image boots, and the hands-on task in this lesson does one of those tests by hand. The bootloader itself runs only on the board, so the host tests in lesson 120 cover the application's logic rather than this file.

Summary

  • One linker script, boot.ld, places the bootloader in BOOT at 0x08000000 and the application slot in APP at 0x08004000, and two ASSERT lines fail the link if the layout changes.
  • The image header is 32 bytes, magic, version, image end and vector offset followed by four reserved words, and the vector table sits 0x200 bytes into the slot, as PM0056 section 4.4.4 requires for VTOR alignment.
  • The bootloader checks six things before the jump, the magic, the offset, the image end, the stack pointer in RAM, the Thumb bit of the reset handler and that the reset handler lies inside the image, but neither a CRC nor a signature.
  • The jump disables interrupts, moves VTOR, sets MSP from word 0 and calls the reset handler from word 1, an order that matters, and the bootloader never runs again after it.
  • A map file and a size report show whether an image fits, the application ending at 0x08008FC0 in the measured build, which leaves about 28 KB free in its slot.
  • When a board runs old code, the hex file's time stamp is the first thing to check, because the header on the board is the one that was flashed rather than the one you built.
PM0056: STM32F10xxx Cortex-M3 Programming Manual (ST): read section 4.4.4 for the vector table offset register (VTOR) and its 512-byte alignment rule, which the header's vector offset follows, and the exception and reset sections for the table layout. Then compare this project's header in app_image.h with the header format in the MCUboot design document. The two differ in magic and fields, and the comparison shows what a production format adds.
