Writing a driver from a datasheet

A sensor driver built from its register map

By the end of this lesson you can find the address, register map, data format and data-ready rule in a datasheet, and write the three driver functions that use them, checking the part with its WHO_AM_I register first.

A new sensor and its datasheet

Lesson 60 showed the I2C bus as a logic analyser records it, with start, address, acknowledge, register pointer, repeated start and data, lesson 61 wrote a driver for an OLED with a control byte, page addressing and a framebuffer, and lesson 45 showed how a cast changes the meaning of a number. This lesson joins the three into one job, writing a driver for an unknown sensor called the MYS-1 from nothing but its short datasheet.

The job is common: a new sensor arrives on a new board with its datasheet as the only documentation, and the engineer must find the bus address, learn which registers hold what and turn the raw bytes into a number a human can read. Assuming that it works like the last one is not an option, because the driver must match the datasheet and the engineer must prove it, since a wrong temperature in a heater controller or a battery charger can cause real damage.

The driver as a layer between application and bus

A device driver is the code that turns device operations into bus transactions. The application calls something like mystery_read_celsius(), which means nothing to the bus, and underneath the driver writes a control register, polls a status register and reads two bytes, each an I2C transfer that the I2C hardware turns into wire-level conditions, to which the sensor answers on its pins.

Each layer hides one detail from the layer above. The application does not know the register numbers, the driver does not know the pin numbers, which are set in one mystery_init() call, the SDK's i2c_write_blocking() knows nothing of the register map, and the RP2040's I2C hardware turns a queued byte into a START, a byte and a STOP or repeated START. The layering matches the one in computer architecture, where an instruction becomes a memory transaction and the transaction becomes a signal on a bus, a driver doing that translation for one device.

The layers also decide where bugs live: a wrong temperature points to the conversion layer rather than the bus, while a missing acknowledge points to the address or the wiring rather than the conversion. The lesson's structure makes this easy to check, because each of the three public functions corresponds to one layer's job.

A driver acts as an interpreter between two people without a shared language, the application speaking in temperatures and in whether a new reading is ready, the sensor in register addresses, status bits and pairs of bytes. The interpreter translates both ways, so neither side has to learn the other's language, and swapping the sensor means hiring a new interpreter rather than retraining the application. A human interpreter can ask for clarification, however, whereas a driver must already contain every rule the datasheet states.

Five questions a datasheet answers

For a register-based sensor a datasheet answers five questions, and each answer should be found before writing code and noted next to the code that uses it.

  1. Address: the 7-bit I2C address the device answers to, which for the MYS-1, with no address pin, is fixed at 0x48 (datasheet section 2).
  2. Register map: the registers, their addresses, the meaning of their bits and whether each is readable or writable (section 3.1).
  3. Protocol: how the register pointer is set and whether a read moves on to the next register (section 3.2).
  4. Data format: the scale, the sign and the byte order of each value (section 4.1).
  5. Timing: when a new sample is ready, how long it remains and what reading the data does to the flags (section 4.2).

All the answers are in the MYS-1 datasheet, which is laid out like a real one, its register table, transaction table and timing rules being the parts this lesson uses. Read the whole datasheet once, and then return to the three sections below while working.

The register pointer and the repeated start

Many register-based I2C devices work the same way: the master writes one byte that sets a register pointer inside the device, later bytes in the same transaction are data for the register the pointer names, and a read returns the byte at the pointer and moves the pointer on by one. The MYS-1 works this way, as section 3.2 of its datasheet states.

Reading one register therefore means writing the pointer and then reading the data, and the question is whether the bus is released in between. A STOP between the two would release it, letting another master use the bus in the gap, whereas a repeated start (RESTART) begins the second part without a STOP, so the bus stays claimed. The datasheet's transaction table asks for the RESTART and warns that a STOP would let another master in.

The RP2040 generates these conditions in its I2C hardware, whose START, STOP and RESTART generation its datasheet describes in section 4.3.7, and the SDK exposes the choice as one argument: i2c_write_blocking() called with nostop = true leaves the bus claimed, so the next transfer starts with a repeated start, the SDK source setting restart_on_next from that argument in i2c.c at line 241.

Polling the data-ready flag

The MYS-1 measures on its own schedule, a new sample being ready every 500 ms once measurement is enabled, and each sample sets DRDY, the data-ready flag, bit 0 of the STATUS register at address 0x27. Samples are not queued, so if one is not read before the next arrives, the older value is lost (datasheet section 4.2).

The driver therefore waits for DRDY before reading the temperature, reading STATUS in a loop with a short sleep between reads until bit 0 is set. A loop without a limit could hang the whole firmware if the sensor were unplugged, so it also has a deadline, the datasheet's usage steps advising to give up after about 2 s, and the SDK provides make_timeout_time_ms() in pico/time.h to set it and time_reached() in hardware/timer.h to test it.

Polling is simple and sufficient for a sensor that updates twice a second, the alternative being an interrupt on a DRDY pin, which the MYS-1 lacks, so the lesson's choice follows from the part and a different part could change it.

A signed temperature from two bytes

The temperature is a signed 16-bit value in units of 1/64 °C, stored, as the datasheet says, in two's complement, the standard way of storing negative integers in binary, in which the top bit is the sign and a negative value is the bit pattern obtained by subtracting the magnitude from 216, with the full rule in the glossary entry on two's complement. Converting the raw value gives the temperature

T = (int16_t)((TEMP_H << 8) | TEMP_L) ÷ 64(1)

where TEMP_L at 0x28 is the low byte and TEMP_H at 0x29 the high byte. A burst read from 0x28 returns TEMP_L first and then TEMP_H, because the pointer increments after each byte, and the driver shifts the high byte into the top 8 bits, casts the result to a signed type so that the sign bit is read as a sign, and only then divides by 64.

The order of the cast matters, because a value stored as unsigned is always positive, turning a negative temperature into a large number. Lesson 45 explains the conversion rules, and the worked example below shows the difference with real numbers.

Worked example: one temperature read

We follow every transfer of the driver's first read after power-up, using the datasheet's example bytes, 0x05 for TEMP_H and 0xA0 for TEMP_L, so that the answer is known in advance. Before starting, estimate the temperature from those two bytes.

  1. Identify the part. Write the pointer 0x0F, restart and read one byte, which should be 0xA7, and if it is not, stop, because nothing else in the datasheet applies to the device.
  2. Enable measurement. Write 0x01 to CTRL at 0x20, setting bit 0, MEAS_EN, after which the first sample arrives 500 ms later.
  3. Wait for DRDY. Read STATUS at 0x27 every 10 ms, the first reads returning 0x00 until, about 50 reads later, bit 0 is set, the status reads 0x01 and the loop ends.
  4. Read the pair in one burst. Write the pointer 0x28, restart and read two bytes, the first being TEMP_L, 0xA0, and the second TEMP_H, 0x05, the sensor having latched the sample when TEMP_L was read and clearing DRDY when TEMP_H is read.
  5. Combine the bytes. (0x05 << 8) | 0xA0 is 0x0500 | 0x00A0, or 0x05A0, which is 1 440 in decimal.
  6. Scale. 1 440 is positive, so the cast changes nothing, and equation (1) gives 1 440 ÷ 64 = 22.5 °C.

The negative case shows why the cast matters. With TEMP_L 0xC0 and TEMP_H 0xFF the combined value is 0xFFC0, or 1111 1111 1100 0000 in binary, whose top bit is set, so as a signed 16-bit number it is 0xFFC0 − 65 536 = −64, and −64 ÷ 64 = −1.0 °C. Read as unsigned, the same bits are 65 472, and 65 472 ÷ 64 = 1 023.0, a plausible-looking but wrong temperature.

  1. Identify the part: write the register pointer 0x0F, repeated start, read one byte. It must be 0xA7; if it is not, nothing else in the datasheet applies.
  2. Enable measurement: write 0x01 to CTRL at 0x20. Bit 0 is MEAS_EN, and the first sample is ready 500 ms later.
  3. Wait for DRDY: read STATUS at 0x27 every 10 ms. It reads 0x00 about 50 times, then 0x01.
  4. Burst-read two bytes from 0x28: TEMP_L = 0xA0, then TEMP_H = 0x05. Reading TEMP_L latched the sample, and reading TEMP_H clears DRDY.
  5. Combine: (0x05 << 8) | 0xA0 = 0x05A0, which is 1440.
  6. Cast to int16_t and scale: 1440 ÷ 64 = 22.5 °C. The cast matters for negative values: 0xFFC0 is −64, −1.0 °C, but read as unsigned it would be 1,023 °C.

The driver code line by line

The excerpts below come from the reference solution, mystery.c. The starter provides the two register helpers and you write the three public functions, so the helpers come first, since every public function uses them. 

static bool reg_write(uint8_t reg, uint8_t value) {
    uint8_t frame[2] = { reg, value };          /* pointer, then data */
    return i2c_write_blocking(MYSTERY_I2C, MYSTERY_ADDR, frame, 2, false) == 2;
}

A write to one register is a two-byte transfer, the pointer followed by the value, ending with a STOP because the argument false releases the bus afterwards. The function returns true only if the SDK reports both bytes written, the SDK returning the number of bytes written or PICO_ERROR_GENERIC, a negative value, when no device acknowledges the address, so the comparison with 2 catches both a missing sensor and a partial write. 

static bool reg_read(uint8_t reg, uint8_t *buf, size_t len) {
    if (i2c_write_blocking(MYSTERY_I2C, MYSTERY_ADDR, &reg, 1, true) != 1) {
        return false;                              /* pointer not accepted */
    }
    return i2c_read_blocking(MYSTERY_I2C, MYSTERY_ADDR, buf, len, false) == (int)len;
}

This is the repeated-start pattern in two SDK calls. The first writes the pointer with nostop = true, keeping the bus claimed and making the SDK set up a RESTART for the next transfer, and the second reads len bytes, its false argument ending the transfer with a STOP. If the pointer write fails, the function returns before reading, so the caller never receives bytes from an unknown register, and the cast to int lets the SDK's signed return value be compared with the unsigned length. 

bool mystery_init(void) {
    i2c_init(MYSTERY_I2C, MYSTERY_BAUD_HZ);             /* I2C0 at 100 kHz */
    gpio_set_function(MYSTERY_SDA_PIN, GPIO_FUNC_I2C);  /* GP4 is I2C0 SDA */
    gpio_set_function(MYSTERY_SCL_PIN, GPIO_FUNC_I2C);  /* GP5 is I2C0 SCL */
    gpio_pull_up(MYSTERY_SDA_PIN);                      /* weak internal pulls */
    gpio_pull_up(MYSTERY_SCL_PIN);
    return reg_write(REG_CTRL, CTRL_MEAS_EN);       /* CTRL bit 0 starts measurement */
}

i2c_init() turns the I2C0 block on at the given rate, and the two gpio_set_function() calls connect the pins to it, as in lesson 60, GP4 and GP5 being I2C0's default pins in the RP2040's GPIO function table (RP2040 datasheet, section 2.19.2, Table 279). The pull-up calls enable the chip's internal resistors, 50 to 80 kΩ according to the electrical table (section 5.5.3.4), which are too weak for a real bus, so the diagram adds external 4.7 kΩ resistors as the MYS-1 datasheet asks. The last line writes 0x01 to CTRL, starting measurement. 

bool mystery_read_celsius(float *celsius) {
    absolute_time_t deadline = make_timeout_time_ms(DRDY_TIMEOUT_MS);
    for (;;) {
        uint8_t status = 0;
        if (!reg_read(REG_STATUS, &status, 1)) {  /* bus error: give up */
            return false;
        }
        if (status & STATUS_DRDY) {               /* bit 0: a sample is ready */
            break;
        }
        if (time_reached(deadline)) {             /* no sample in 2 s: the sensor is gone */
            return false;
        }
        sleep_ms(DRDY_POLL_MS);                    /* 10 ms between polls */
    }
    uint8_t raw[2];
    if (!reg_read(REG_TEMP_L, raw, 2)) {      /* one burst: TEMP_L, then TEMP_H */
        return false;
    }
    int16_t counts = (int16_t)(((uint16_t)raw[1] << 8) | raw[0]);
    *celsius = (float)counts / TEMP_LSB_PER_C;   /* 1/64 degC per count */
    return true;
}

The deadline is set once, before the loop, so the limit covers the whole wait, and reg_read() returning false on a bus error passes that error up. The loop tests DRDY with a bit mask, and only then does the temperature read happen, as a burst that takes both bytes from the same latched sample. The conversion first builds an unsigned uint16_t, which keeps the exact bit pattern of the two bytes, and then casts it to int16_t, which reads the top bit as the sign, before dividing by TEMP_LSB_PER_C, the float 64.0, so the result is a float in degrees Celsius.

Its source is projects/0063-mystery-sensor/chip/mystery.chip.c, but avoid opening it until you have finished, because it is the datasheet written as code and gives the answers away.

  1. Open projects/0063-mystery-sensor/starter in VS Code (File → Open Folder), and keep the MYS-1 datasheet open in a second window.
  2. Build with Ctrl+Shift+B.
  3. Start the simulator with F1 → Wokwi: Start Simulator. The serial monitor now prints MYSTERY whoami failed every second, because mystery_whoami() is not yet written.
  4. Replace the three TODO(learner) functions in mystery.c: mystery_init brings up I2C0 on GP4 and GP5, enables the pulls and starts measuring, mystery_whoami reads WHO_AM_I into *id, and mystery_read_celsius polls DRDY with a timeout, reads TEMP_L and TEMP_H in one burst and converts the value.
  5. The serial monitor should print MYSTERY OK id=0xA7 temp=22.xx C once a second, the first temperature lying between 22.5 and 23 °C and the values changing slowly from line to line. On a timeout the solution prints MYSTERY read timed out and the starter MYSTERY read failed, id=0xA7.

The steps are those of lesson 60, i2c_init, then gpio_set_function on both pins, then the pulls, followed by one reg_write to CTRL with bit 0 set, the bit the datasheet names MEAS_EN.

Common mistakes and how to spot them

Measurement never enabled

The WHO_AM_I read succeeds and prints 0xA7, but every temperature read fails after its timeout, the starter printing MYSTERY read failed, id=0xA7 and the solution MYSTERY read timed out. The write to CTRL is missing or writes the wrong value, so DRDY never sets, while the identity check passes because WHO_AM_I is a fixed value independent of measurement. Check that the CTRL write puts 0x01 at address 0x20, and check its return value.

The cast to a signed type missing

A cold reading shows about 1 023 °C, because the two bytes are combined into an unsigned value and divided by 64, so −1.0 °C, with the bits 0xFFC0, reads as 65 472 and gives 1 023.0. Cast to int16_t before the division, as the solution does. The simulated sensor stays above 22 °C, so the simulator never shows this bug, and the conversion should be tested with the raw value 0xFFC0, which must give −1.0 °C, a test that lesson 80 shows how to write on the PC.

The bytes combined in the wrong order

The temperature lies far outside the room range, −383.92 °C for the datasheet's example, because the driver used raw[0] as the high byte, taking the sign and the magnitude from TEMP_L, so the example becomes 0xA005, −24 571 counts. The high byte is TEMP_H, raw[1] in a burst read starting at 0x28, so compare each index with the register it was read from.

The two bytes read in separate transactions

A reading can jump by up to about 4 °C from the previous one in a steady room, because the sensor latches a sample when TEMP_L is read, so if TEMP_H is read in its own transaction before TEMP_L, the high byte comes from the previous latch and the low byte from the new one, and one step of the high byte is 256 counts, or 4 °C. Read TEMP_L and TEMP_H in one burst from 0x28, as the driver does, so that both bytes come from the same latch.

No pull-ups on a real board

On a breadboard with longer wires WHO_AM_I fails or the sensor does not acknowledge its address, the starter printing MYSTERY whoami failed, because the RP2040's internal 50 to 80 kΩ pulls are too weak for a bus with long wires and fast edges, while the datasheet requires external 4.7 kΩ pull-ups to 3.3 V (section 2). Add the two resistors, as the diagram does, and leave the internal pulls enabled as well, since they cost nothing.

Production drivers and debugging a wrong reading

A production driver is a small, reviewed file holding the address and the register map as named constants, each commented with its datasheet section, with public functions that return a status so that the caller can react to a missing sensor and a conversion written as a pure function that a unit test can call with known raw bytes. A reviewer's first questions are those of this lesson: whether the value is signed where the datasheet says so, whether the read is a burst where the datasheet requires it, whether there is a timeout and what happens when the bus returns an error.

The same pattern covers most sensors, the register map, the conversion and the protocol details changing while the structure of the driver stays the same, so an engineer who can read a datasheet's register table, transaction table and timing rules can write a driver for almost any register-based part.

When a reading is wrong on a real board, check the four facts in the order this lesson read them: the address and the identity value on the bus, then whether measurement is enabled, then the byte order and the sign in the conversion, and finally the timing on a logic analyser, which shows whether the bytes came from one sample. Most sensor bugs are found in one of those four places.

Summary

  • A driver turns device operations into bus transactions, each layer hiding one detail from the layer above.
  • A datasheet answers five questions, address, register map, protocol, data format and timing, each of which is answered before code is written.
  • A register is read with the pointer write set to nostop = true, so the read follows a repeated start and the bus stays claimed.
  • The driver waits for the data-ready flag with a deadline, so that a missing sensor cannot hang the firmware.
  • TEMP_L and TEMP_H are read in one burst, because the sensor latches the sample on the low-byte read, so the two bytes match.
  • The bytes are combined, cast to a signed 16-bit type and divided by 64, and the negative case is tested with the raw value 0xFFC0, which must give −1.0 °C.
