Writing a driver from a datasheet: the "mystery sensor"

Most firmware jobs start with a datasheet and a part number on the desk. This lesson gives you a short datasheet for an unknown I2C sensor, and asks you to write the driver from it, without guessing.

By the end of this lesson you can find the address, register map, data format and data-ready rule in a datasheet, and write the three driver functions that use them, checking the part with its WHO_AM_I register first.

The idea

A driver is the code that turns device operations (start measuring, read the temperature) into bus transactions. Your application calls mystery_read_celsius(). Only the driver knows that this means a write to a control register, a poll of a status register and a two-byte read. The layers are the same as in a CPU. An instruction becomes a bus transfer, and the bus transfer becomes a register write. The driver is the layer that does that translation for one device.

A datasheet answers five questions for a register-based sensor. Find each answer before you write any code:

  1. Address: the 7-bit I2C address. Here it is 0x48.
  2. Register map: which register holds what, and which bits are which.
  3. Protocol: how the register pointer works, and whether reads auto-increment.
  4. Data format: the scale, the sign and the byte order.
  5. Timing: when a new sample is ready, and what reading the data does to the flags.

The I2C bus carries the protocol. A register read is two transactions in one bus cycle: the master writes the register number, then sends a repeated start and reads the bytes. The RP2040 generates these START, STOP and RESTART conditions in hardware (RP2040 datasheet, section 4.3.7). The Pico SDK call i2c_write_blocking with nostop = true leaves the bus claimed, so that the read becomes that repeated start (Pico SDK, hardware_i2c).

Read the datasheet first

The sensor for this lesson is the MYS-1. It is fictional, but its datasheet is laid out like a real one. Open it in a second window, and keep it open while you work: MYS-1 datasheet.

Look for these three facts first. Each one is a bug if you get it wrong:

  • WHO_AM_I is at 0x0F and reads 0xA7. If that check fails, nothing else you read matters.
  • Start measuring means setting bit 0 of CTRL (0x20). Until you do, no sample ever arrives.
  • Data-ready is bit 0 of STATUS (0x27). A new sample arrives every 500 ms, so read the temperature only after DRDY is set.

Turn the bytes into degrees

The temperature is a signed 16-bit number in units of 1/64 degC. The low byte comes first on the wire, at 0x28, and the high byte is at 0x29. Read them in one burst, then combine them. Cast to a signed type before you divide: a negative value stored as unsigned is about 65,000, not a small negative number. The datasheet's example is 0x05A0. That is 1440, and 1440 ÷ 64 = 22.5 degC. Lesson 45 explains why the cast has to come first. 

/* raw[0] is TEMP_L (0x28), raw[1] is TEMP_H (0x29) */
int16_t counts = (int16_t)(((uint16_t)raw[1] << 8) | raw[0]);
float celsius = (float)counts / 64.0f;
Real sensors often have a latch. The MYS-1 latches the sample when you read TEMP_L and releases the data-ready flag when you read TEMP_H. If you read the two bytes in separate transactions, the sample can change between them. Read them in one burst.

Try it in Wokwi

The MYS-1 is a Wokwi custom chip: C code compiled to WebAssembly, which the simulator runs as if it were a real part on the I2C bus. Its source is projects/0063-mystery-sensor/chip/mystery.chip.c. Try not to open it until you have finished. It is the datasheet written as code, so it gives the answers away.

  1. Open projects/0063-mystery-sensor/starter in VS Code (File → Open Folder).
  2. Build: Ctrl+Shift+B.
  3. Start the simulator: F1 → Wokwi: Start Simulator. Right now every line says that a step failed.
  4. Your task: in mystery.c, replace the three TODO(learner) functions. mystery_init brings up I2C0 on GP4 and GP5, turns on the pulls, and starts measuring. mystery_whoami reads WHO_AM_I. mystery_read_celsius polls DRDY with a timeout, reads TEMP_L and TEMP_H in one burst, and converts the value.
  5. You will know it works when the serial monitor prints MYSTERY id=0xA7 temp=22.50 C every second, with the temperature changing slowly.
Hint for the init function

The same steps as lesson 60: i2c_init, then gpio_set_function on both pins, then the pulls. The last step is one reg_write to CTRL with bit 0 set. The datasheet names that bit MEAS_EN.

Hint for the read function

Poll STATUS in a loop. Break out when bit 0 is set. Return false if time_reached(deadline) is true first. Then use reg_read(REG_TEMP_L, raw, 2), and do the conversion from the section above.

The reference solution is in projects/0063-mystery-sensor/solution. Try first, compare after. The diagram adds 4.7 kΩ pull-ups on SDA and SCL, which a real board would also need.

You turned a three-page datasheet into a driver. You checked the identity register, enabled measurement, waited for data-ready, and read a signed value from two registers. That is the job, and it works the same way for any register-based sensor.

"A sensor driver returns 65,472 when the room is cold. The datasheet says the register is signed. What went wrong, and how would you prevent it?" Answer out loud in 60 seconds, then compare.

Model answer

The driver treated the 16-bit value as unsigned. Negative values in two's complement become large unsigned numbers: 0xFFC0 is 65472. The fix is to combine the bytes into a uint16_t and then cast to int16_t before scaling. The prevention is a unit test with a negative raw value, such as 0xFFC0, that must produce −1.0 degC, and a rule that every signed register is read through an int16_t.
