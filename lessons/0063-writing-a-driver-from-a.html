Writing a driver from a datasheet: the "mystery sensor"

Most firmware jobs start with a datasheet and a part number on the desk. This lesson gives you a short datasheet for an unknown I2C sensor, and asks you to write the driver from it, without guessing.

By the end of this lesson you can find the address, register map, data format and data-ready rule in a datasheet, and write the three driver functions that use them, checking the part with its WHO_AM_I register first.

Where we are and why it matters

Lesson 60 showed the I2C bus as a logic analyzer records it: start, address, acknowledge, register pointer, repeated start, data. Lesson 61 wrote a driver for an OLED, with a control byte, page addressing and a framebuffer. Lesson 45 showed how a cast changes the meaning of a number. This lesson joins those three ideas into one job.

The job is common. A new sensor arrives on a new board, and the only documentation is its datasheet. The engineer must find the bus address, learn which registers hold what, and turn the raw bytes into a number a human can read. Nobody on the team can say "it probably works like the last one". The driver must match the datasheet, and the engineer must prove it, because a wrong temperature in a heater controller or a battery charger can cause real damage.

Concept 1: a driver is a layer between the application and the bus

A device driver is the code that turns device operations into bus transactions. The application calls something like mystery_read_celsius(), which means nothing to the bus. Underneath, the driver writes a control register, polls a status register, and reads two bytes, and each of those is an I2C transfer. The I2C hardware then turns each transfer into wire-level conditions, and the sensor answers on the pins.

Each layer hides one detail from the layer above it. The application does not know the register numbers. The driver does not know the pin numbers, which are set in one mystery_init() call. The SDK's i2c_write_blocking() does not know the register map at all. The RP2040's I2C hardware turns a queued byte into a START, a byte, and a STOP or a repeated START. This is the same layering you already know from computer architecture: an instruction becomes a memory transaction, and the memory transaction becomes a signal on a bus. A driver is the layer that does that translation for one device.

The layers also decide where bugs live. If the temperature is wrong, the bug is in the conversion layer, not in the bus. If the bus shows no acknowledge, the bug is in the address or the wiring, not in the conversion. This lesson's structure makes this easy to check, because the three public functions each correspond to one layer's job.

Concept 2: five questions a datasheet answers

For a register-based sensor, a datasheet answers five questions. Find each answer before you write code, and write the answer down next to the code that uses it.

  1. Address: the 7-bit I2C address the device answers to. The MYS-1 has no address pin, so its address is fixed at 0x48 (datasheet section 2).
  2. Register map: the registers, their addresses, which bits do what, and whether each is readable or writable (section 3.1).
  3. Protocol: how the register pointer is set, and whether a read moves on to the next register (section 3.2).
  4. Data format: the scale, the sign and the byte order of each value (section 4.1).
  5. Timing: when a new sample is ready, how long it stays, and what reading the data does to the flags (section 4.2).

The answers are all in the MYS-1 datasheet, which is laid out like a real one. Its register table, its transaction table and its timing rules are the parts you will use. Read the whole datasheet once, and then read the three facts below again while you work.

Concept 3: the register pointer and the repeated start

Many register-based I2C devices work the same way. The master writes one byte, which sets a register pointer inside the device. Later bytes in the same transaction are data for the register the pointer names. A read returns the byte at the pointer, and the pointer moves on by one. The MYS-1 works this way, and section 3.2 of its datasheet says so.

To read one register, the master must first write the pointer and then read the data. The question is whether the bus is released in between. A STOP between the two would release it, and another master could use the bus in the gap. A repeated start (also called RESTART) starts the second part without a STOP, so the bus stays claimed. The datasheet's transaction table asks for the RESTART, and says that a STOP would let another master use the bus in between.

The RP2040 generates these conditions in its I2C hardware. Its datasheet describes START, STOP and RESTART generation in section 4.3.7. The SDK exposes the choice as one argument. Calling i2c_write_blocking() with nostop = true leaves the bus claimed, and the next transfer starts with a repeated start. The SDK source sets restart_on_next from that argument in i2c.c, at line 241.

Concept 4: the data-ready flag and why you poll it

The MYS-1 measures on its own schedule. A new sample is ready every 500 ms once measurement is enabled, and each sample sets a flag called DRDY, the data-ready flag. DRDY is bit 0 of the STATUS register, at address 0x27. Samples are not queued: if you do not read one before the next arrives, the older value is lost (datasheet section 4.2).

The driver therefore waits for DRDY before it reads the temperature. It reads STATUS in a loop, with a short sleep between reads, and stops when bit 0 is set. A loop with no limit can hang the whole firmware if the sensor is unplugged, so the loop also has a deadline. The datasheet's usage steps say to give up after about 2 s. The SDK provides make_timeout_time_ms() for the deadline, in pico/time.h, and time_reached() to test it, in hardware/timer.h.

Polling is simple and enough for a sensor that updates twice per second. The alternative is an interrupt on a DRDY pin, which the MYS-1 does not have. The lesson's choice follows from the part, and a different part would change it.

Concept 5: a signed number from two bytes

The temperature is a signed 16-bit value, in units of 1/64 °C. The datasheet calls it two's complement, which is the standard way to store negative integers in binary. In two's complement, the top bit is the sign, and a negative value is the bit pattern you get by subtracting the magnitude from 2 to the power 16. The two's complement entry in the glossary has the rule in full.

The two bytes are TEMP_L at 0x28 (the low byte) and TEMP_H at 0x29 (the high byte). A burst read from 0x28 returns TEMP_L first, then TEMP_H, because the pointer increments after each byte. The driver combines them as (TEMP_H << 8) | TEMP_L, which puts the high byte in the top 8 bits. Then it casts the result to a signed type, so that the sign bit is read as a sign. Only after that cast does it divide by 64.

The order of the cast matters. A value stored as unsigned is always positive, so a negative temperature becomes a large number. Lesson 45 explains the conversion rules. The worked example below shows the difference with real numbers.

Worked example: one temperature read, step by step

Start with the driver's first read after power-up, and follow every transfer. The steps below use the datasheet's example bytes, 0x05 for TEMP_H and 0xA0 for TEMP_L, so the answer is known in advance.

  1. Identify the part. Write the pointer 0x0F, restart, and read one byte. The result is 0xA7. If it is not, stop, because nothing else in the datasheet applies to this device.
  2. Enable measurement. Write 0x01 to CTRL at 0x20. Bit 0 is MEAS_EN, and the first sample arrives 500 ms later.
  3. Wait for DRDY. Read STATUS at 0x27 every 10 ms. The first reads return 0x00. About 50 reads later, bit 0 is set and the status reads 0x01. The loop breaks.
  4. Read the pair in one burst. Write the pointer 0x28, restart, and read two bytes. The first byte is TEMP_L, 0xA0. The second is TEMP_H, 0x05. The sensor latched the sample when TEMP_L was read, and reading TEMP_H clears DRDY.
  5. Combine the bytes. (0x05 << 8) | 0xA0 is 0x0500 | 0x00A0, which is 0x05A0, or 1440 in decimal.
  6. Scale. 1440 is a positive value, so the cast changes nothing. Divide by 64: 1440 ÷ 64 = 22.5 °C.

The negative case shows why the cast matters. Suppose the bytes are TEMP_L 0xC0 and TEMP_H 0xFF. Combined, they give 0xFFC0, which in binary is 1111 1111 1100 0000. As a signed 16-bit number, the top bit is set, so the value is 0xFFC0 − 65536 = −64. Then −64 ÷ 64 = −1.0 °C. Read as unsigned, the same bits are 65,472, and 65,472 ÷ 64 = 1,023.0, which is a plausible-looking but wrong temperature.

The code, explained line by line

The excerpts below come from the reference solution, mystery.c. The starter provides the two register helpers, and you write the three public functions. Start with the helpers, because every public function uses them. 

static bool reg_write(uint8_t reg, uint8_t value) {
    uint8_t frame[2] = { reg, value };          /* pointer, then data */
    return i2c_write_blocking(MYSTERY_I2C, MYSTERY_ADDR, frame, 2, false) == 2;
}

A write to one register is a two-byte transfer. The first byte is the pointer, and the second is the value. The transfer ends with a STOP, because the argument false means the bus is released afterwards. The function returns true only if the SDK reports that both bytes were written. The SDK returns the number of bytes written, or PICO_ERROR_GENERIC (a negative value) when no device acknowledges the address. Comparing with 2 catches both a missing sensor and a partial write. 

static bool reg_read(uint8_t reg, uint8_t *buf, size_t len) {
    if (i2c_write_blocking(MYSTERY_I2C, MYSTERY_ADDR, &reg, 1, true) != 1) {
        return false;                              /* pointer not accepted */
    }
    return i2c_read_blocking(MYSTERY_I2C, MYSTERY_ADDR, buf, len, false) == (int)len;
}

This is the repeated-start pattern from Concept 3, in two SDK calls. The first call writes the pointer with nostop = true, so the bus stays claimed and the SDK sets up a RESTART for the next transfer. The second call reads len bytes, and its false argument ends the transfer with a STOP. If the pointer write fails, the function returns before reading, so the caller never receives bytes from an unknown register. The cast to int compares the SDK's signed return value with the unsigned length. 

bool mystery_init(void) {
    i2c_init(MYSTERY_I2C, MYSTERY_BAUD_HZ);             /* I2C0 at 100 kHz */
    gpio_set_function(MYSTERY_SDA_PIN, GPIO_FUNC_I2C);  /* GP4 is I2C0 SDA */
    gpio_set_function(MYSTERY_SCL_PIN, GPIO_FUNC_I2C);  /* GP5 is I2C0 SCL */
    gpio_pull_up(MYSTERY_SDA_PIN);                      /* weak internal pulls */
    gpio_pull_up(MYSTERY_SCL_PIN);
    return reg_write(REG_CTRL, CTRL_MEAS_EN);       /* CTRL bit 0 starts measurement */
}

i2c_init() turns the I2C0 block on at the given rate. The two gpio_set_function() calls connect the pins to the I2C block, as lesson 60 showed. GP4 and GP5 are I2C0's default pins in the RP2040's GPIO function table (RP2040 datasheet, section 2.19.2, Table 279). The pull-up calls turn on the chip's internal resistors, which are 50 to 80 kΩ according to the electrical table (section 5.5.3.4). They are too weak for a real bus. The diagram adds external 4.7 kΩ resistors, which is what the datasheet asks for. The last line writes 0x01 to CTRL, which starts measurement. 

bool mystery_read_celsius(float *celsius) {
    absolute_time_t deadline = make_timeout_time_ms(DRDY_TIMEOUT_MS);
    for (;;) {
        uint8_t status = 0;
        if (!reg_read(REG_STATUS, &status, 1)) {  /* bus error: give up */
            return false;
        }
        if (status & STATUS_DRDY) {               /* bit 0: a sample is ready */
            break;
        }
        if (time_reached(deadline)) {             /* no sample in 2 s: the sensor is gone */
            return false;
        }
        sleep_ms(DRDY_POLL_MS);                    /* 10 ms between polls */
    }
    uint8_t raw[2];
    if (!reg_read(REG_TEMP_L, raw, 2)) {      /* one burst: TEMP_L, then TEMP_H */
        return false;
    }
    int16_t counts = (int16_t)(((uint16_t)raw[1] << 8) | raw[0]);
    *celsius = (float)counts / TEMP_LSB_PER_C;   /* 1/64 degC per count */
    return true;
}

The deadline is set once, before the loop, so the time limit covers the whole wait. reg_read() returns false on a bus error, and the function passes that error up. The loop tests DRDY with a bit mask, and only then does the temperature read happen. The burst read takes both bytes in one transfer, so they come from the same latched sample. The conversion first builds an unsigned uint16_t, which keeps the exact bit pattern of the two bytes, and then casts it to int16_t, which reads the top bit as the sign. The division uses TEMP_LSB_PER_C, which is 64.0 as a float, so the result is a float in degrees Celsius.

Common mistakes and how to spot them

Mistake 1: measurement is never enabled

Symptom: the WHO_AM_I read succeeds and prints 0xA7, but every temperature read fails after its timeout. The starter prints MYSTERY read failed, id=0xA7, and the solution prints MYSTERY read timed out. Cause: the write to CTRL is missing or writes the wrong value, so DRDY never sets. The identity check passes, because WHO_AM_I is a fixed value that does not depend on the measurement. Fix: check the CTRL write, which must be 0x01 to address 0x20, and check its return value.

Mistake 2: the cast to a signed type is missing

Symptom: a cold reading shows about 1,023 °C. Cause: the two bytes are combined into an unsigned value and divided by 64. A negative temperature such as −1.0 °C has the bits 0xFFC0, and read as unsigned that is 65,472, so the result is 1,023.0. Fix: cast to int16_t before the division, as the solution does. The simulated sensor stays above 22 °C, so the simulator will never show the bug. Test the conversion with the raw value 0xFFC0, which must give −1.0 °C. Lesson 80 shows how to write that test on the PC.

Mistake 3: the bytes are combined in the wrong order

Symptom: the temperature is far outside the room range, and it is not the same every time, for example −383.92 °C for the datasheet's example. Cause: the driver used raw[0] as the high byte, so the sign and the magnitude come from TEMP_L. For the datasheet example, 0xA005 is −24,571 counts, or −383.92 °C. Fix: the high byte is TEMP_H, which is raw[1] in a burst read that starts at 0x28. Compare each index with the register it was read from.

Mistake 4: reading the two bytes in separate transactions

Symptom: a reading can jump by up to about 4 °C from the one before it, even when the room is steady. Cause: the sensor latches a sample when TEMP_L is read. If TEMP_H is read in its own transaction before TEMP_L, the high byte comes from the previous latch and the low byte from the new one. One step of the high byte is 256 counts, which is 4 °C, so the error can be that large. Fix: read TEMP_L and TEMP_H in one burst from 0x28, as the driver does, so the two bytes always come from one latch.

Mistake 5: no pull-ups on a real board

Symptom: on a breadboard with longer wires, WHO_AM_I fails, or the sensor does not acknowledge its address. The starter prints MYSTERY whoami failed. Cause: the RP2040's internal pulls are 50 to 80 kΩ, which is too weak for a bus with long wires and a fast edge. The datasheet says external 4.7 kΩ pull-ups to 3.3 V are required (section 2). Fix: add the two resistors, as the diagram does. Keep the internal pulls on as well, because they cost nothing.

In real projects

A production driver is a small, reviewed file. It has the address and the register map as named constants, each with a comment that names the datasheet section. Its public functions return a status, so the caller can react to a missing sensor. Its conversion is a pure function that a unit test can call with known raw bytes. The reviewer's first questions are the ones in this lesson: is the value signed where the datasheet says so, is the read a burst where the datasheet requires it, is there a timeout, and what happens when the bus returns an error.

The same pattern covers most sensors. The register map changes, the conversion changes, and the protocol details change, but the structure of the driver does not. An engineer who can read a datasheet's register table, its transaction table and its timing rules can write a driver for almost any register-based part. That is why interviewers ask about drivers. They are testing whether the candidate reads the datasheet before writing code.

When a reading is wrong on a real board, check the four facts in the order they were read in this lesson. Confirm the address and the identity value on the bus. Confirm that measurement is enabled. Check the byte order and the sign in the conversion. Then look at the timing on a logic analyzer, which shows whether the bytes came from one sample. Most sensor bugs are found in one of those four places.

Summary

  • A driver turns device operations into bus transactions. Each layer hides one detail from the layer above it.
  • A datasheet answers five questions: address, register map, protocol, data format and timing. Find each answer before you write code.
  • Read a register with the pointer write set to nostop = true, which makes the read a repeated start, so the bus stays claimed.
  • Wait for the data-ready flag, and give the wait a deadline, so that a missing sensor does not hang the firmware.
  • Read TEMP_L and TEMP_H in one burst. The sensor latches the sample on the low-byte read, so the two bytes match.
  • Combine the bytes, cast to a signed 16-bit type, then divide by 64. Test the negative case with the raw value 0xFFC0, which must give −1.0 °C.
You turned a short datasheet into a driver. You checked the identity register, enabled measurement, waited for data-ready, and read a signed value from two registers. The same steps work for any register-based sensor.

"A sensor driver returns 65,472 when the room is cold. The datasheet says the register is signed. What went wrong, and how would you prevent it?" Answer out loud in 60 seconds, then compare.

Model answer

The driver treated the 16-bit value as unsigned. Negative values in two's complement become large unsigned numbers: 0xFFC0 is 65472. The fix is to combine the bytes into a uint16_t and then cast to int16_t before scaling. The prevention is a unit test with a negative raw value, such as 0xFFC0, that must produce −1.0 degC, and a rule that every signed register is read through an int16_t.
