STM32 HAL and CubeMX-generated code

Most STM32 jobs use ST's Hardware Abstraction Layer, and most HAL projects start from CubeMX. This lesson shows what the HAL asks of you, what CubeMX writes, and how to decide between HAL, LL and registers.

By the end of this lesson you can use HAL handles and check HAL_StatusTypeDef results, override a weak HAL callback, read the structure of CubeMX-generated code, and name the trade-off between HAL, LL and direct register access for a given task.
CubeMX cannot be installed in this workspace: it needs an ST account to download. This lesson describes what it generates and how to read that code, and it does not show generated output that was not produced here. The HAL code you build below is the same kind that CubeMX writes around your own code.

Where we are and why it matters

Lessons 66 to 68 wrote every register access yourself, which was the right way to learn the chip. Lesson 67 showed how many steps a single LED needs: a clock enable, a mode field, a mask-and-set, and a SysTick deadline. A product with a dozen peripherals and a team of five cannot keep all of that in each person's head, so most companies use ST's HAL for application code. Lesson 70 will return to the USART and the EXTI controller in the register style, and this lesson gives you the vocabulary to read the HAL version of the same peripherals.

A typical job brings you into an existing STM32 project that was generated by CubeMX, with a main.c full of MX_*_Init() calls and a few USER CODE blocks. Reading that project without knowing the HAL is slow. Writing a driver that is checked and easy to review requires knowing what the HAL promises and what it does not.

Concepts, one at a time

What a HAL is

A hardware abstraction layer is a software layer that exposes hardware through a portable API, so that the application calls functions such as "initialise this UART" and does not name a register. The STM32 HAL is ST's library of these functions for each STM32 family. It is C code, and it sits between your code and the registers you saw in lessons 66 to 68. The glossary's definition calls it a layer of this kind, and the HAL is ST's specific implementation. Glossary: hardware abstraction layer

The HAL user manual, UM1850, describes the functions and their callbacks. Each peripheral has an init function that takes a handle and returns a status. The handle holds the peripheral's instance and its configuration, so a call reads like an action on an object. The HAL then writes the registers underneath. UM1850, Description of STM32F1 HAL and low-layer drivers

Handles and status codes

A handle is a struct that holds a peripheral's instance (which hardware block, such as USART1) and its configuration. The HAL passes the handle to every call for that peripheral, so the handle is where the state lives. A status code is the value a function returns to say whether it worked. For HAL functions it is HAL_StatusTypeDef, which takes one of four values: HAL_OK, HAL_ERROR, HAL_BUSY or HAL_TIMEOUT.

The reason to check the status is that a failed init does not stop the program. It returns an error, and the code keeps going with a half-configured peripheral. The symptom can appear much later, in a different function, which makes the cause hard to find.

Callbacks and weak symbols

A callback is a function the HAL calls when something happens, such as a transmit finishing. The HAL defines a default version of each callback, and marks it weak. A weak symbol is a default definition that a strong definition in another file replaces at link time (the glossary has the term). A project overrides a callback by defining a function with the same name, and the linker uses the project's version. That is how your code runs when the HAL's interrupt code finishes a job, without you editing the HAL.

The MspInit hooks: where the chip-specific setup goes

The HAL is portable across boards, so it does not know which pins your board uses. The MspInit functions, which ST's documents call MSP functions (for MCU support package), are the hooks where the chip-specific setup lives: the clock enables and the alternate-function pin configuration for a peripheral. Do not confuse this MSP with the main stack pointer in the glossary, which is a different thing with the same abbreviation. HAL_UART_MspInit() is weak, and the project can define it to enable the clock and set the pins, which is what CubeMX generates into stm32f1xx_hal_msp.c. This course's project does those steps inside its own uart_init() instead, which does the same job in one place.

Handles and status codes in code

The UART setup in the project shows the pattern. The handle is a file-scope variable, the fields are filled in, and the status of the init is checked: 

static UART_HandleTypeDef huart1;

static HAL_StatusTypeDef uart_init(void) {
    __HAL_RCC_USART1_CLK_ENABLE();
    GPIO_InitTypeDef tx = { .Pin = GPIO_PIN_9, .Mode = GPIO_MODE_AF_PP, .Speed = GPIO_SPEED_FREQ_HIGH };
    HAL_GPIO_Init(GPIOA, &tx);

    huart1.Instance = USART1;
    huart1.Init.BaudRate = 115200;
    huart1.Init.WordLength = UART_WORDLENGTH_8B;
    huart1.Init.StopBits = UART_STOPBITS_1;
    huart1.Init.Parity = UART_PARITY_NONE;
    huart1.Init.Mode = UART_MODE_TX;             /* this lesson only transmits */
    huart1.Init.HwFlowCtl = UART_HWCONTROL_NONE;
    return HAL_UART_Init(&huart1);
}

/* in main: */
if (uart_init() != HAL_OK) {
    Error_Handler();          /* never continue with a failed peripheral */
}

Line by line: huart1 is static, so only this file sees it, and it lives for the whole program. __HAL_RCC_USART1_CLK_ENABLE() is the macro that sets the clock bit that lesson 67 set by hand. The pin for PA9, the transmit pin, is configured as alternate-function push-pull, which the HAL's GPIO_MODE_AF_PP names directly. HAL_GPIO_Init takes a port and a configuration struct, and it writes the CRH field for us. The UART fields come next: the baud rate, the frame and the mode. The HAL works out the divisor from the clock and the BaudRate field, so the handle must carry the whole frame setup. The last line calls the init, and the caller checks the returned status.

Error_Handler() in the project disables interrupts and loops forever. That is deliberate: a failure is visible on the serial monitor or the debugger, and the program does not carry on with a broken UART.

The time base: HAL_Init, SysTick and HAL_Delay

HAL_Init() does three things that matter here. It sets the NVIC priority grouping to 4, which means four bits of the priority are the preemption part. It starts the SysTick timer through HAL_InitTick(), configured to interrupt once per millisecond. And it sets the SysTick interrupt priority. The tick count is then read with HAL_GetTick(), and HAL_Delay() waits on it. The HAL source defines all four of these functions as weak, which means a project can replace any of them. UM1850, and third_party/stm32f1xx-hal-driver/Src/stm32f1xx_hal.c.

The count only moves if your SysTick interrupt calls HAL_IncTick(). The project does that with one line: 

void SysTick_Handler(void) { HAL_IncTick(); }   /* without this, the startup's default handler stops the program */

The vendor startup file defines SysTick_Handler as a weak alias for the default handler, which loops forever. The project's strong definition replaces it at link time, so the SysTick interrupt runs HAL_IncTick() instead. Lesson 73 builds a millisecond time base from SysTick without the HAL, and comparing the two shows what the HAL does for you. The HAL's HAL_GetTick() returns a 32-bit count of milliseconds, which wraps back to zero after about 49.7 days. The code must handle that wrap, as the next section shows.

Worked example: deadlines that survive the wrap

The project schedules each LED with a deadline, as lesson 67 did. With the HAL the deadline is a 32-bit tick value, and the naive check is now >= next. That check breaks at the wrap. Suppose the deadline is 0xFFFFFFFE, two milliseconds before the wrap, and the tick has just wrapped, so now is 0x00000002. Then now >= next is false, because 2 is less than 4294967294, and the LED waits for almost fifty days.

The solution uses (int32_t)(now - next) >= 0 instead. Subtraction in unsigned 32-bit arithmetic gives the true distance even across the wrap: 0x00000002 − 0xFFFFFFFE is 0x00000004, which is 4 ms, a positive number. Casting that difference to a signed type makes the test read it as "the deadline has passed by this much". The difference is correct as long as the two times are less than about 24.8 days apart, which is far more than any deadline in this code.

The button uses the same arithmetic. The lockout is 20 ms, and the code ignores a press if (now − last_press) >= 20 is false. A press at tick 500 blocks presses until tick 520. Bounces at 502 and 505 are ignored, and a press at 540 counts. That is the whole debounce rule in this project, and lesson 52 covered the polled version of the same idea.

What CubeMX generates

CubeMX is ST's configurator. You pick the chip, set each pin's function, enable the peripherals, and set the clocks in a graphical tool, and it writes the C code. The generated layout is typical of the STM32F1 HAL projects it makes, and the exact file names and comments depend on the CubeMX version. Read the code for your version, rather than trusting this list.

  • main.c: main() calls HAL_Init(), then SystemClock_Config(), then one MX_*_Init() function for each peripheral you enabled, such as MX_GPIO_Init() and MX_USART1_UART_Init(). Each init function fills a handle and calls the HAL.
  • The USER CODE blocks: your code goes between /* USER CODE BEGIN 2 */ and /* USER CODE END 2 */, and between other pairs like them. CubeMX keeps the text inside those markers when it regenerates. Code outside the markers is overwritten, so never put your logic there.
  • stm32f1xx_hal_msp.c: HAL_MspInit() and a HAL_UART_MspInit() for each UART. They enable the clocks and configure the alternate-function pins, which is the lesson 67 work done by generated code.
  • stm32f1xx_it.c: the interrupt handlers, including SysTick_Handler(), which calls HAL_IncTick(), and the HAL's HAL_UART_IRQHandler() calls.
  • stm32f1xx_hal_conf.h: which HAL modules are compiled in. The course's stm32-hal template already has this file, with the modules enabled.
  • Error_Handler(): the function the generated code calls when an init fails. It is usually an infinite loop, so a failure stops the program where you can see it.
The workflow is: CubeMX regenerates, then you read the diff. Put your code inside USER CODE blocks, or in your own files, and check every generated change in version control before you commit it.

The project's CMake file shows how a HAL build is wired. It adds the HAL sources with stm32_use_hal(blink), which compiles every file in the HAL's Src/ folder and defines USE_HAL_DRIVER, and it adds the project folder to the include path so the project's stm32f1xx_hal_conf.h is found.

HAL, LL or registers

Three ways to drive the same peripheral, and each one trades readability, portability and control. Pick the lowest layer you can justify, and keep the reason in a comment.

QuestionRegisters (CMSIS)LL (low-layer)HAL
Who checks the arguments and the states?YouYou, with a few inline functionsThe HAL returns a status you can check
How much of the register sequence is visible?All of itMost of it, namedHidden in the calls
Code size and call overheadSmallestSmall, inlinedLargest, with the full driver linked
Portable across STM32 familiesNoPartly, per familyPartly, per family, with the same API
Best forStartup, timing-critical code, learning the chipPerformance-critical drivers that still want named functionsApplications that need quick, checked setup, and CubeMX projects

For the course, the rule is simple. Lessons 66 to 68 use registers so you see every step. Lesson 69 uses the HAL because most industry STM32 code does. Lesson 76 returns to this choice when it designs a driver layer.

Common mistakes and how to spot them

Mistake 1: HAL_Delay never returns

The program starts, prints HAL OK, and then everything freezes: PC13 stops and the button does nothing. The cause is usually the SysTick handler. If SysTick_Handler does not call HAL_IncTick(), the tick count never moves, and HAL_Delay spins forever. The fix is the one-line handler shown above. In the debugger, read uwTick: if it stays at zero, the handler is missing.

Mistake 2: the pin never changes, and no error appears

HAL_GPIO_Init returns no status, so a missing clock looks like success. If you configure PB0 without __HAL_RCC_GPIOB_CLK_ENABLE(), the call completes, and the LED stays dark, exactly as in lesson 67. The fix is to enable the clock before the first HAL_GPIO_Init on that port. Check the return value of the status functions that do return one, such as HAL_UART_Init, and treat the others with the same care.

Mistake 3: the button prints ten lines per press

Pressing the button once prints several button pressed lines. The button bounces, so the pin changes state several times in a few milliseconds, and each falling edge counts. The fix is the lockout, which ignores falling edges for 20 ms after a counted press. A common error is never updating last_button. The test then stays true for as long as the button is held, and the message repeats on every loop.

Mistake 4: a change to the vendor file disappears

A developer edits stm32f1xx_hal_uart.c to add a print, and the change works. A week later CubeMX regenerates the project, or the HAL is updated, and the print is gone. The fix is to put the code in a weak callback in your own file, or in a USER CODE block, where the next regeneration keeps it.

In real projects

Teams use the HAL for application code because it gives a checked, reviewable setup, and because CubeMX makes the initial code quickly. Code review of HAL projects focuses on three things: whether every status is checked, whether the vendor files are untouched, and whether any register access outside the HAL has a comment that says why. A direct register write inside an otherwise HAL project is a warning sign, and it needs a reason.

Performance-critical drivers, such as a motor control loop, often use LL, because LL functions are inline and the register sequence stays visible. Startup and clock code is often written with registers. Interviewers ask which layer you would use, and a good answer names the trade-off for the specific task, not one layer for everything.

Summary

  • The HAL exposes peripherals through handles, and most init functions return a HAL_StatusTypeDef that you must check.
  • HAL callbacks are weak, so a project overrides one by defining a function with the same name in its own file.
  • HAL_Init starts SysTick at 1 ms, and the tick moves only when SysTick_Handler calls HAL_IncTick().
  • Compare tick deadlines with (int32_t)(now − deadline) >= 0, which is correct across the 32-bit wrap.
  • The HAL does not enable clocks for you in this project, so enable each port's clock before its first init.
  • Put your code in USER CODE blocks or in your own files, because CubeMX and vendor updates overwrite everything else.
  • Choose HAL for application code, LL for drivers where the register sequence must stay visible, and registers for startup and tight timing.

"When would you use the HAL, LL or direct registers on an STM32?" Answer out loud in 60 seconds, then compare.

Model answer

The HAL is the default for application code: its handles and status codes make setup checkable, its callbacks are easy to override, and CubeMX can generate it. LL is for a driver where performance or code size matters, and where the team wants named functions with the register sequence visible. Direct registers are for startup, clock setup, tight timing, and any case where the HAL's overhead or hidden sequence gets in the way. A good answer also says that the choice is per peripheral, and that the team should write it down.
