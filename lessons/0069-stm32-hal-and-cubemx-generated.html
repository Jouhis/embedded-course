ST's driver library and its generated projects

From register code to the HAL

Lessons 66 to 68 wrote every register access by hand, the right way to learn the chip, and lesson 67 showed how many steps a single LED needs, a clock enable, a mode field, a mask-and-set and a SysTick deadline. A product with a dozen peripherals and a team of five cannot keep all of that in each person's head, so most companies use ST's HAL for application code. Lesson 70 returns to the USART and the EXTI controller in register style, and this lesson provides the vocabulary for reading the HAL version of the same peripherals.

A typical job brings an engineer into an existing STM32 project generated by CubeMX, with a main.c full of MX_*_Init() calls and a few USER CODE blocks, and reading such a project without knowing the HAL is slow. Writing a driver that is checked and easy to review requires knowing what the HAL promises and what it does not.

The hardware abstraction layer

A hardware abstraction layer is a software layer exposing hardware through a portable API, so that the application calls functions such as one that initialises a UART without naming a register. The STM32 HAL is ST's library of these functions for each STM32 family, C code sitting between the application and the registers of lessons 66 to 68, and the glossary's definition describes a layer of this kind, of which the HAL is ST's specific implementation (Glossary: hardware abstraction layer).

A HAL resembles the pedals and steering wheel of a car, the same on every car, so a driver need not know whether the steering is hydraulic or electric. As with a car, the controls allow what they were designed for, and anything else means opening the bonnet, here the registers. The comparison breaks where a car's controls never change, whereas HAL functions can differ between STM32 families, so code is portable only as far as the families share the same API.

The HAL user manual, UM1850, describes the functions and their callbacks. Each peripheral has an init function that takes a handle and returns a status, the handle holding the peripheral's instance and configuration so that a call reads like an action on an object, while the HAL writes the registers underneath (UM1850, Description of STM32F1 HAL and low-layer drivers).

Handles and status codes

A handle is a struct holding a peripheral's instance, the hardware block such as USART1, and its configuration, and the HAL passes it to every call for that peripheral, so the handle is where the state lives. A status code is the value a function returns to report whether it worked, for HAL functions a HAL_StatusTypeDef taking one of four values, HAL_OK, HAL_ERROR, HAL_BUSY or HAL_TIMEOUT.

The status must be checked because a failed init does not stop the program: it returns an error and the code carries on with a half-configured peripheral, so the symptom may appear much later in a different function, which makes the cause hard to find.

Callbacks and weak symbols

A callback is a function the HAL calls when something happens, such as a transmit finishing. The HAL defines a default version of each callback marked weak, a weak symbol being a default definition that a strong definition in another file replaces at link time, as the glossary explains, so a project overrides a callback by defining a function with the same name and the linker uses that version instead. This is how application code runs when the HAL's interrupt code finishes a job, without any edit to the HAL.

The HAL ships, for example, a default HAL_UART_RxCpltCallback that does nothing, so leaving it undefined in the project means that a completed receive passes silently, whereas defining it makes the linker pick the project's version.

The MspInit hooks for chip-specific setup

The HAL is portable across boards, so it does not know which pins a board uses, and the MspInit functions, which ST's documents call MSP functions (for MCU support package), are the hooks holding the chip-specific setup, the clock enables and the alternate-function pin configuration of a peripheral. This MSP is unrelated to the main stack pointer of the glossary, which shares the abbreviation. HAL_UART_MspInit() is weak, so a project can define it to enable the clock and set the pins, which is what CubeMX generates into stm32f1xx_hal_msp.c, while this course's project does the same steps inside its own uart_init(), keeping the job in one place.

A UART handle in code

The project's UART setup shows the pattern, a file-scope handle whose fields are filled in before the status of the init is checked. 

static UART_HandleTypeDef huart1;

static HAL_StatusTypeDef uart_init(void) {
    __HAL_RCC_USART1_CLK_ENABLE();
    GPIO_InitTypeDef tx = { .Pin = GPIO_PIN_9, .Mode = GPIO_MODE_AF_PP, .Speed = GPIO_SPEED_FREQ_HIGH };
    HAL_GPIO_Init(GPIOA, &tx);

    huart1.Instance = USART1;
    huart1.Init.BaudRate = 115200;
    huart1.Init.WordLength = UART_WORDLENGTH_8B;
    huart1.Init.StopBits = UART_STOPBITS_1;
    huart1.Init.Parity = UART_PARITY_NONE;
    huart1.Init.Mode = UART_MODE_TX;             /* this lesson only transmits */
    huart1.Init.HwFlowCtl = UART_HWCONTROL_NONE;
    return HAL_UART_Init(&huart1);
}

/* in main: */
if (uart_init() != HAL_OK) {
    Error_Handler();          /* never continue with a failed peripheral */
}

huart1 is static, so only this file sees it, and it lives for the whole program, while __HAL_RCC_USART1_CLK_ENABLE() is the macro that sets the clock bit lesson 67 set by hand. PA9, the transmit pin, is configured as alternate-function push-pull, which the HAL names directly as GPIO_MODE_AF_PP, and HAL_GPIO_Init takes a port and a configuration struct and writes the CRH field. The UART fields follow, the baud rate, the frame and the mode, the HAL working out the divisor from the clock and the BaudRate field, so the handle must carry the whole frame setup, and the last line calls the init whose status the caller checks.

The project's Error_Handler() disables interrupts and loops forever, deliberately, so that a failure becomes visible on the serial monitor or in the debugger instead of the program carrying on with a broken UART.

The HAL time base: HAL_Init, SysTick and HAL_Delay

HAL_Init() does three things that matter here: it sets the NVIC priority grouping to 4, making four bits of the priority the preemption part, it starts the SysTick timer through HAL_InitTick() to interrupt once per millisecond, and it sets the SysTick interrupt priority. The tick count is then read with HAL_GetTick(), on which HAL_Delay() waits, and the HAL source marks HAL_InitTick, HAL_IncTick, HAL_GetTick and HAL_Delay as weak, so that a project can replace any of them, while HAL_Init itself is not weak (UM1850, and third_party/stm32f1xx-hal-driver/Src/stm32f1xx_hal.c).

The count moves only if the SysTick interrupt calls HAL_IncTick(), which the project does with one line. 

void SysTick_Handler(void) { HAL_IncTick(); }   /* without this, the startup's default handler stops the program */

The vendor startup file defines SysTick_Handler as a weak alias for the default handler, which loops forever, so the project's strong definition replaces it at link time and the SysTick interrupt runs HAL_IncTick() instead. Lesson 73 builds a millisecond time base from SysTick without the HAL, and comparing the two shows what the HAL does on the application's behalf. The HAL's HAL_GetTick() returns a 32-bit count of milliseconds, which wraps back to zero after about 49.7 days. The code must handle that wrap, as the next section shows.

Worked example: deadlines across the tick wrap

The project schedules each LED with a deadline, as lesson 67 did, but with the HAL the deadline is a 32-bit tick value, and the naive check now >= next breaks at the wrap. Suppose the deadline is 0xFFFFFFFE, two milliseconds before the wrap, and the tick has just wrapped, so now is 0x00000002; before reading on, predict what the naive check does.

  1. Apply the naive test. now >= next is false, because 2 is less than 4 294 967 294, so the LED waits for almost fifty days.
  2. Subtract instead. In unsigned 32-bit arithmetic, 0x00000002 − 0xFFFFFFFE is 0x00000004, the true distance of 4 ms across the wrap.
  3. Read the sign. The solution's (int32_t)(now - next) >= 0 casts that difference to a signed type, so the test reads it as the deadline having passed by 4 ms, which is correct while the two times lie less than about 24.8 days apart, far more than any deadline in this code.

The button uses the same arithmetic with a 20 ms lockout, the code ignoring a press while (now − last_press) >= 20 is false, so a press at tick 500 blocks presses until tick 520, bounces at 502 and 505 are ignored and a press at 540 counts. That is the whole debounce rule of this project, the interrupt-free counterpart of the polled idea in lesson 52.

The structure of CubeMX-generated projects

CubeMX is ST's configurator, a graphical tool in which the developer picks the chip, sets each pin's function, enables the peripherals and sets the clocks, after which it writes the C code. The layout below is typical of the STM32F1 HAL projects it generates, but file names and comments depend on the CubeMX version, so the code of the version in use is the authority rather than this list.

  • main.c: main() calls HAL_Init(), then SystemClock_Config(), then one MX_*_Init() function for each enabled peripheral, such as MX_GPIO_Init() and MX_USART1_UART_Init(), each filling a handle and calling the HAL.
  • The USER CODE blocks: application code goes between /* USER CODE BEGIN 2 */ and /* USER CODE END 2 */ and similar pairs, whose contents CubeMX keeps when it regenerates, while code outside the markers is overwritten, so no logic belongs there.
  • stm32f1xx_hal_msp.c: HAL_MspInit() and a HAL_UART_MspInit() for each UART, enabling the clocks and configuring the alternate-function pins, the work of lesson 67 done by generated code.
  • stm32f1xx_it.c: the interrupt handlers, including SysTick_Handler(), which calls HAL_IncTick(), and the calls into the HAL's HAL_UART_IRQHandler().
  • stm32f1xx_hal_conf.h: the selection of HAL modules compiled in, a file that the course's stm32-hal template already contains with the modules enabled.
  • Error_Handler(): the function the generated code calls when an init fails, usually an infinite loop, so that a failure stops the program where it can be seen.
The workflow is: CubeMX regenerates, then you read the diff. Put your code inside USER CODE blocks, or in your own files, and check every generated change in version control before you commit it.

The project's CMake file shows how a HAL build is wired, adding the HAL sources with stm32_use_hal(blink), which compiles every file in the HAL's Src/ folder and defines USE_HAL_DRIVER, and adding the project folder to the include path so that the project's stm32f1xx_hal_conf.h is found.

Choosing between HAL, LL and registers

The same peripheral can be driven in three ways, each trading readability, portability and control, so the rule is to pick the lowest layer that can be justified and to keep the reason in a comment.

QuestionRegisters (CMSIS)LL (low-layer)HAL
Who checks the arguments and the states?YouYou, with a few inline functionsThe HAL returns a status you can check
How much of the register sequence is visible?All of itMost of it, namedHidden in the calls
Code size and call overheadSmallestSmall, inlinedLargest, with the full driver linked
Portable across STM32 familiesNoPartly, per familyPartly, per family, with the same API
Best forStartup, timing-critical code, learning the chipPerformance-critical drivers that still want named functionsApplications that need quick, checked setup, and CubeMX projects

Within the course the rule is simple: lessons 66 to 68 use registers so that every step is visible, lesson 69 uses the HAL because most industry STM32 code does, and lesson 76 returns to the choice when it designs a driver layer.

Common mistakes and how to spot them

HAL_Delay that never returns

The program starts and prints HAL OK, and then everything freezes, PC13 stopping and the button doing nothing, usually because SysTick_Handler does not call HAL_IncTick(), so the tick count never moves and HAL_Delay spins forever. Add the one-line handler shown above, and in the debugger check uwTick, which stays at zero when the handler is missing.

A pin that never changes without any error

HAL_GPIO_Init returns no status, so a missing clock looks like success: PB0 configured without __HAL_RCC_GPIOB_CLK_ENABLE() completes the call while the LED stays dark, exactly as in lesson 67. Enable the clock before the first HAL_GPIO_Init on that port, check the return value of the functions that do return a status, such as HAL_UART_Init, and treat the others with the same care.

Several lines printed per button press

One press prints several button pressed lines, because the button bounces, changing state several times in a few milliseconds, and each falling edge counts. The lockout fixes this by ignoring falling edges for 20 ms after a counted press, and a related error, never updating last_button, keeps the test true for as long as the button is held, repeating the message on every loop.

An edit to a vendor file that disappears

A developer adds a print to stm32f1xx_hal_uart.c and it works, but a week later CubeMX regenerates the project or the HAL is updated and the print is gone. Put the code into a weak callback in the project's own file or into a USER CODE block, where the next regeneration keeps it.

HAL, LL and registers in product teams

Teams use the HAL for application code because it gives a checked, reviewable setup and because CubeMX produces the initial code quickly. Review of HAL projects focuses on whether every status is checked, whether the vendor files are untouched and whether any register access outside the HAL carries a comment explaining why, since a direct register write inside an otherwise HAL project is a warning sign that needs a reason.

Performance-critical drivers, such as a motor control loop, often use LL, whose functions are inline and keep the register sequence visible, while startup and clock code is often written with registers.

Summary

  • The HAL exposes peripherals through handles, and most init functions return a HAL_StatusTypeDef that must be checked.
  • HAL callbacks are weak, so a project overrides one by defining a function of the same name in its own file.
  • HAL_Init starts SysTick at 1 ms, and the tick moves only when SysTick_Handler calls HAL_IncTick().
  • Tick deadlines are compared with (int32_t)(now − deadline) >= 0, which stays correct across the 32-bit wrap.
  • The HAL does not enable clocks in this project, so each port's clock is enabled before its first init.
  • Application code belongs in USER CODE blocks or the project's own files, because CubeMX and vendor updates overwrite everything else.
  • The HAL suits application code, LL drivers whose register sequence must stay visible, and registers startup and tight timing.
