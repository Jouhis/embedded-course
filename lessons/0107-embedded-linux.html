Embedded Linux: when to use it instead of an MCU

The 3D printer on your desk is already a hybrid. A Linux computer runs the interface and the planning; a small microcontroller fires the stepper pulses on time. Knowing when to add Linux, and when it gets in the way, is a common interview question.

By the end of this lesson you can say whether a product needs an MCU, Linux on an application processor, or both; name what Linux adds and what it costs; and explain how Klipper splits its work between a Linux host and a microcontroller.

This lesson is optional. Embedded Linux is a large topic, and this is an overview. It is useful for hardware interviews and for reading a product's architecture. No board is needed: the exercises are decision questions.

Where we are and why it matters

Until now the course has treated the microcontroller as the whole computer. You have built firmware that starts at the reset vector, sets up the clock tree from lesson 40, and runs one program directly from flash. Startup code and the vector table from lesson 42 were the only "operating system" in the project. That model works very well for a thermostat, a motor controller or a sensor node.

It stops working when the product needs a web interface, a file system, a secure network stack and many programs that must not interfere with each other. A product manager then asks whether the team should move to Linux. The question is not about taste. It is a trade between timing, power, cost, and the work of keeping an operating system updated in the field. This lesson gives you the vocabulary and the decision rules to answer it, starting from the constraints rather than the tools.

Concept 1: what a microcontroller is

A microcontroller (MCU) puts the processor core, the flash memory that holds the program, the SRAM that holds variables, and the peripherals such as timers, GPIO and UART on one chip. The core fetches each instruction from flash or SRAM, decodes it, and executes it, with no layer in between. When the chip is reset, the core reads the vector table and starts your code within microseconds. Lesson 42 showed that sequence in detail.

The key property is that the program sees physical addresses. When your C code writes to 0x40020000, the bus carries that address to a peripheral, and nothing translates it first. That makes timing predictable, because every access takes a known path, and it makes the system cheap, because no translation hardware is needed. The cost is that nothing separates one part of the program from another, so a wild pointer in one task can overwrite another task's data.

Concept 2: application processors, the MMU and virtual memory

An application processor (AP) is a bigger class of chip. It has a faster core, usually external DRAM rather than a few hundred kilobytes of SRAM, and a memory management unit (MMU). An MMU is hardware that translates each address a program uses, called a virtual address, into a physical address in memory. The translation is done with tables that the operating system's kernel builds and maintains, and each process gets its own set of tables. This is called virtual memory.

Virtual memory gives you two things an MCU cannot easily provide. First, each process sees its own address space, so two programs can both use address 0x1000 and never touch each other's data. Second, the kernel can leave parts of memory unmapped and catch the access, which is how a crash in one program is contained. Compare this with the MPU that lesson 39 covered. The Cortex-M MPU has a small number of regions that software defines, each with access permissions. It checks accesses against those regions, but it does not translate addresses, and it cannot give each program its own view of memory. The RP2040 core has 8 MPU regions (see the MPU entry in the glossary).

The MMU is the reason Linux can run many programs safely, and it is also the reason a Linux system is harder to make predictable. A translation can miss the cache or require a table walk, and the kernel can schedule other work between your instructions. Both effects are small on average, but they change from run to run, which is what real-time engineers worry about.

Concept 3: the kernel, drivers and user space

The kernel is the part of Linux that runs with full access to the hardware. It schedules processes, handles interrupts, manages memory and talks to devices through drivers. Everything else, including your Python script, a web server or a shell, runs in user space. A user-space program asks the kernel for help through system calls, such as opening a file or sending a packet, and the kernel checks the request before it acts.

The benefit of this split is reuse. The kernel already contains drivers for USB, Wi-Fi, displays, storage and cameras, and the TCP/IP stack, TLS and a file system such as ext4. An MCU project needs a library for each of those, and the library must be ported and maintained. The price is that every service and every driver is code you must patch when a security fix arrives, which is the attack surface that lesson 103 discusses.

Concept 4: the boot chain

A Linux product does not start with one program. It starts with a chain of programs, each loading the next. The boot ROM inside the chip runs first, and it finds a bootloader on storage such as an SD card or eMMC. The bootloader loads the kernel and a device tree, then hands over control. The kernel mounts the root filesystem, which holds the programs, libraries and configuration files, and starts the first user-space process.

Each step is a place where an update can break the product. The chain is also why a Linux product takes seconds to boot: the bootloader, the kernel's own initialisation, the file system mount, and every service that starts all add time. On an MCU, the chain is one reset vector and your main. Lesson 102 covers the slot scheme that lets a field update fall back safely when one of those steps fails.

Concept 5: the device tree

An MCU project describes its pins and peripherals in code or a header file. Linux, which runs the same kernel on many boards, reads that description from a device tree. A device tree is a text file made of nodes, each with properties, that describes the hardware on one board. The bootloader passes the compiled form to the kernel at boot, and the kernel matches each node to a driver by its compatible property. 

/ {
    uart0: serial@40000000 {          /* node name, label and address (invented here) */
        compatible = "example,uart";  /* the kernel looks for a driver with this string */
        reg = <0x40000000 0x1000>;   /* base address and size of the registers */
        status = "okay";              /* the node is enabled and should be probed */
    };
};

Read the example line by line. The serial@40000000 node name carries the unit address, and the label uart0: lets other nodes refer to it. The compatible string is how the kernel picks a driver, so a typo here means the driver never binds. The reg property gives the register block, which the driver then maps. The address in this example is invented for illustration; a real board's address comes from its SoC datasheet. Lesson 94 shows the same idea in Zephyr's devicetree, and the reason is the same: the hardware description changes per board, and the code that drives it should not.

Worked example: a boot budget and a power budget

Suppose a device must show a status screen within 50 ms of power-on. Linux cannot do that, because its boot chain alone takes seconds, as described above. An MCU with a simple startup takes microseconds to reach main, and the display driver then needs only a few milliseconds more. The 50 ms requirement rules out Linux before any other factor is considered.

Now the power budget. Assume a coin-cell battery of 230 mAh (an illustrative size, not a product), a sensor node that sleeps at 10 µA and wakes for 5 ms every 10 minutes at 30 mA. The average current is the sleep current plus the active current weighted by its duty cycle. The duty cycle is 5 ms divided by 600 s, which is 0.0000083, and 30 mA times that is 0.25 µA. The average is therefore 10.25 µA. Dividing 230 mAh by 0.01025 mA gives about 22,400 hours, or roughly 2.6 years.

Now assume the same node runs Linux, which draws about 300 mA all the time (an illustrative figure). The same battery lasts 230 divided by 300, which is 0.77 hours, or about 46 minutes. The MCU design is about 2,000 times better here. The numbers are invented, but the method is the one you will use with real datasheet values: compute the average current, not the peak, and compare it with the battery.

A third calculation is about timing. Linux's scheduler can run another task for a millisecond before your task gets the core, and the latency varies from run to run. At 48 MHz, one millisecond is 48,000 clock cycles. A motor loop that must act within 10 microseconds has a budget of 480 cycles. A single late scheduling event is one hundred times the budget, which is why that loop belongs on the MCU, whatever else the product does.

Hands-on: how Klipper splits the work

Your QIDI Q2 runs Klipper, and Klipper is a hybrid by design. The host is a Linux computer running the Python software. It reads the printer's configuration, parses G-code and plans the motion. The microcontroller runs firmware that generates the step pulses. The host computes when each step must happen, and sends compressed queue_step commands ahead of time. The Klipper Code Overview says these commands are normally parsed and queued at least 100 ms before their first step Klipper Code Overview.

The MCU stores each queued move and fires the pulses itself. The Code Overview describes the step as scheduled on the MCU's hardware timer, with each step pulse rescheduling the next one. Because the host sends times well ahead of the pulses, a host that is late by a few milliseconds does not make any step late. The step times are stored as MCU clock values, so the MCU fires them on its own clock, not the host's. That is the design: the timing-critical work runs on the device with the deterministic clock, and the heavy, flexible work runs on Linux.

The following sketch shows the idea in C. It is not Klipper's code; the helper functions are hypothetical and the real firmware is more involved. 

#include <stdint.h>

typedef struct {
    uint32_t next_clock;   /* MCU clock value at which the next step must fire */
    uint32_t interval;     /* clock ticks between steps in this queued move */
    uint32_t remaining;    /* steps left in the move */
} step_move_t;

static step_move_t move;

void step_timer_isr(void) {
    if (move.remaining == 0) {           /* nothing queued: leave the timer idle */
        return;
    }
    step_pin_pulse();                    /* hypothetical helper: pulse the driver's step pin */
    move.remaining--;
    move.next_clock += move.interval;    /* plan the next step on the MCU's own clock */
    timer_set_alarm(move.next_clock);    /* hypothetical helper: re-arm the hardware timer */
}

Line by line: the struct holds the schedule that the host sent, in MCU clock ticks, not in seconds, so it does not depend on the host's clock. The if handles an empty queue, so the timer does nothing until the host sends more work. The pulse happens inside the interrupt, which runs at a fixed moment, and the code then advances next_clock by a fixed interval. The last line arms the timer for that clock value. If the host is late, the queue is simply empty for a while, and the pulses already queued still arrive on time.

Open the Klipper Code Overview and find the paragraph about the queue. Then answer for yourself: which part of the printer would notice a 5 ms host delay, and which would not? The answer is the reason the split exists.

Decision exercise: MCU, Linux, or hybrid?

Each product below has one dominant need. Pick the architecture that meets it with the least complexity. Start from the constraint that cannot be relaxed: a deadline, a power budget, or a network stack you do not want to write.

Common mistakes and how to spot them

The first mistake is choosing Linux because it is familiar. A team that has written Python for years may reach for a Linux board by default. The symptom appears late: a battery prototype that works on the bench lasts a day in the field, and the power budget was never calculated. The fix is the calculation from the worked example, done before the architecture is chosen.

The second mistake is treating Linux timing as real-time. A developer writes a 1 kHz control loop as a Linux thread, tests it for a minute, and sees it work. Under load, a few iterations come late by several milliseconds, and the output jumps. The symptom is intermittent and depends on what else is running. The fix is to measure the worst-case latency with a tool such as cyclictest under realistic load, and to move any hard deadline to an MCU, as Klipper does.

The third mistake is updating only part of the software. A team ships a new application and leaves the kernel or the root filesystem on the old version, or it updates the kernel and forgets that its modules were built for the old one. The symptom is a device that boots but whose driver is missing, or modules that the kernel refuses to load. The fix is to release the bootloader, kernel, device tree and root filesystem as one versioned set, with a rollback path, as lesson 102 describes.

The fourth mistake is a wrong device tree. A new board is brought up with the kernel and the device tree of the previous board, and one peripheral never appears. The symptom is a missing device in the boot log and no driver bound to a node. The fix is to check the compatible string and the status property of that node, and to confirm the register address against the SoC datasheet.

The fifth mistake is assuming that the MCU memory model protects tasks. A developer who knows Linux processes may expect a crash in one task to be contained, and then builds an MCU design with shared globals and no MPU regions. The symptom is a corrupted variable in an unrelated task, with a fault far from the cause. The fix is to give each task its own data and, where the design needs it, to configure MPU regions for the stacks and shared buffers, as lesson 39 shows.

In real projects

Teams that build Linux products usually start from a generator. Buildroot describes itself as "a simple, efficient and easy-to-use tool to generate embedded Linux systems through cross-compilation" (Buildroot). It produces the toolchain, the root filesystem, the kernel and the bootloader from one configuration, which suits a small, fixed product. The Yocto Project is built from layers and recipes, which suits a company that ships many products from one base and must maintain them for years (The Yocto Project). Bootlin's training covers both Bootlin embedded Linux training.

In a code review of a hybrid product, a senior engineer looks for where each deadline is enforced. The review asks which loop has a hard deadline, which device runs it, and what happens to the product if the Linux side stops responding. A good answer names the MCU watchdog and the safe state that the MCU enters, which connects to the safety work in lesson 109.

In interviews, the question is usually open-ended: "MCU or Linux for this product?" The strong answer starts from the hard constraints, not from the feature list. It computes the power budget or names the deadline, chooses the architecture, and then lists what Linux adds and what it costs in boot time, updates and security. The interview model answer below follows that order.

You can decide MCU, Linux or hybrid for a product from its deadline, power budget and network needs, and explain how Klipper gives its timing to the microcontroller while the Linux host plans the moves.

"MCU or Linux for a battery-powered environmental sensor that sends readings over LoRa?" Answer out loud in 60 seconds, then compare.

Model answer

An MCU. The product wakes rarely, sends a small packet and sleeps, so the power budget dominates, and a booted Linux board would drain the battery in days. Boot time and update complexity also count against Linux. Linux would make sense if the device needed a browser, a local database or many concurrent services. Mention the trade-off: an MCU needs a LoRa driver library and a bootloader for updates, which is more work than a Linux image gives you for free, but it wins on power.

Summary

  • An MCU runs one program from flash with physical addresses, which makes timing predictable and the system cheap.
  • An application processor with an MMU gives each process its own virtual address space, at the cost of a kernel, DRAM and a longer boot.
  • The MPU checks accesses against a few regions; the MMU translates addresses. They are different tools.
  • Linux boots through a chain: boot ROM, bootloader, kernel with device tree, root filesystem, then services.
  • Calculate the average power and the worst-case latency before choosing an architecture; boot time is a hard limit too.
  • Klipper's host plans the moves and sends them ahead of time; the MCU fires each pulse on its own clock.
  • Update the bootloader, kernel, device tree and root filesystem as one versioned set, with rollback.
