Embedded Linux: when to use it instead of an MCU

The 3D printer on your desk is already a hybrid. A Linux computer runs the interface and the planning; a small microcontroller fires the stepper pulses on time. Knowing when to add Linux, and when it gets in the way, is a common interview question.

By the end of this lesson you can say whether a product needs an MCU, Linux on an application processor, or both; name what Linux adds and what it costs; and explain how Klipper splits its work between a Linux host and a microcontroller.

This lesson is optional. Embedded Linux is a large topic, and this is an overview. It is useful for hardware interviews and for reading a product's architecture. No board is needed: the exercises are decision questions.

The idea: MCU or application processor

A microcontroller (MCU) puts the CPU, flash, SRAM and peripherals on one chip. It runs your code directly from flash, with no operating system. An application processor is a bigger CPU with a memory management unit (MMU) and external DRAM, and it boots an operating system from storage. The MMU is the key difference: it translates the addresses each program uses, and it gives each process its own memory. The MPU on a Cortex-M only checks accesses against fixed regions; it does not translate them the MPU and the MMU in the glossary, and lesson 39 covers the Cortex-M MPU.

What Linux brings

  • Memory protection and processes. The MMU lets many programs run safely side by side, and a crash in one does not corrupt the others.
  • Drivers and hardware support. The kernel already drives USB, Wi-Fi, displays, storage and cameras, so you write less of that code.
  • Networking and filesystems. A full TCP/IP stack, TLS, SSH and ext4 come with the kernel; an MCU needs a library for each.
  • Packages. Python, a web server or a database is one install away, rather than a port.

What Linux costs

  • Boot time. A Linux system takes seconds to tens of seconds to boot. An MCU runs its first instruction in microseconds after reset.
  • Power. An application-processor board at idle draws far more than a sleeping MCU. A battery device that wakes every few minutes cannot afford a booted Linux.
  • Real-time determinism. Stock Linux schedules tasks with latency that varies by milliseconds. The PREEMPT_RT patch set makes the kernel preemptible almost everywhere and cuts that latency, but it does not turn Linux into an RTOS for microsecond work Bootlin embedded Linux training.
  • Update complexity. You now update a root filesystem, a kernel and a bootloader, with a rollback plan. Lesson 102 covers the slot scheme that makes this safe.
  • Attack surface. Every open service and package is a possible entry point. Lesson 103 covers the security side.

Building the system: Buildroot and Yocto

You do not hand-build a Linux image for a product. Two build systems generate one. Buildroot describes itself as "a simple, efficient and easy-to-use tool to generate embedded Linux systems through cross-compilation", and it produces the toolchain, the root filesystem, the kernel and the bootloader from one configuration. Use it for a small, fixed product. The Yocto Project is a community effort that helps developers build custom Linux systems for embedded products; it is built from layers and recipes, with more flexibility and a steeper learning curve. Use it when many products share a base and need long-term maintenance. Bootlin's training covers both Bootlin embedded Linux training.

Device tree in Linux

Linux learns the board's hardware from a device tree: a text description of the nodes, their addresses and their properties, compiled into a binary that the bootloader hands to the kernel. It is the same idea as Zephyr's devicetree in lesson 94 Zephyr: Devicetree. The kernel then matches a driver to each node, so the same kernel runs on a board with different pins once the tree changes.

The hybrid pattern: Klipper

Your QIDI Q2 runs Klipper, and Klipper is a hybrid by design. The host is a Linux computer running the Python software: it reads the printer's configuration, parses G-code and plans the motion. The microcontroller runs the firmware that generates the step pulses. The host computes when each step must happen, then sends compressed "queue step" commands ahead of time. The MCU stores them and fires each pulse from a hardware timer interrupt Klipper Code Overview.

Each command carries a clock value, which is the MCU's own time when the step must happen. The host can be late by milliseconds without any step being late, because the MCU fires them on its clock, not the host's Klipper Protocol. That is the whole design: put the timing-critical work on the device with the deterministic clock, and put the heavy, flexible work on the Linux computer. This is the same split as a robot, a car or a drone: a Linux or Android computer for the interface and the map, and an MCU for the motor loops.

Decision exercise: MCU, Linux, or hybrid?

Each product below has one dominant need. Pick the architecture that meets it with the least complexity. Start from the constraint that cannot be relaxed: a deadline, a power budget, or a network stack you do not want to write.

You can decide MCU, Linux or hybrid for a product from its deadline, power budget and network needs, and explain how Klipper gives its timing to the microcontroller while the Linux host plans the moves.

"MCU or Linux for a battery-powered environmental sensor that sends readings over LoRa?" Answer out loud in 60 seconds, then compare.

Model answer

An MCU. The product wakes rarely, sends a small packet and sleeps, so the power budget dominates, and a booted Linux board would drain the battery in days. Boot time and update complexity also count against Linux. Linux would make sense if the device needed a browser, a local database or many concurrent services. Mention the trade-off: an MCU needs a LoRa driver library and a bootloader for updates, which is more work than a Linux image gives you for free, but it wins on power.
