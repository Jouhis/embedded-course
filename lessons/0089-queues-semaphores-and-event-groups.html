Queues, semaphores and event groups

Tasks need to hand data and signals to each other without sharing variables by hand. A queue carries data, a semaphore carries a signal, and an interrupt can use the FromISR versions of both. Pick the right one and most concurrency bugs never happen.

By the end of this lesson you can send data between tasks with a queue, signal a task from an interrupt with a binary semaphore, use the FromISR calls and portYIELD_FROM_ISR() correctly, and say when an event group is the better choice.

The idea

A queue is a fixed-length FIFO of items. xQueueSend() copies an item in, and xQueueReceive() copies it out. Because the kernel copies the item, the sender may reuse its variable at once. A receiver that finds the queue empty blocks, so it uses no CPU until something arrives. The FreeRTOS API reference documents both calls, and the queue implementation is queue.c in the kernel source.

A semaphore carries a count rather than data. A binary semaphore is 0 or 1: it is the signal "this happened, once". A counting semaphore counts events up to a limit, such as the number of free buffers. Lesson 90 covers the mutex, which is a semaphore with an owner.

Interrupts use the FromISR versions

An interrupt cannot block, and it must not call a kernel function that might. So FreeRTOS has xQueueSendFromISR(), xSemaphoreGiveFromISR() and so on. Each takes a pxHigherPriorityTaskWoken pointer. If the call makes a task ready that has a higher priority than the interrupted task, the flag becomes pdTRUE. At the end of the ISR, portYIELD_FROM_ISR(woken) requests the switch (portmacro.h line 111 maps it to the port's end-of-switching macro). The event-group documentation gives the same pattern (event_groups.h around line 603). 

void EXTI15_10_IRQHandler(void) {
    if ((EXTI->PR & EXTI_PR_PR12) != 0U) {
        EXTI->PR = EXTI_PR_PR12;              /* clear the flag, or the ISR runs again at once */
        BaseType_t woken = pdFALSE;
        xSemaphoreGiveFromISR(button_sem, &woken);
        portYIELD_FROM_ISR(woken);            /* switch now if the button task is more urgent */
    }
}
An ISR that calls the plain xSemaphoreGive() or xQueueSend() is a bug, and it often works in the simulator and fails on silicon. Also, the ISR's NVIC priority must be at or below configMAX_SYSCALL_INTERRUPT_PRIORITY (5 in this course's template): a more urgent interrupt may not call FromISR functions.

Event groups

An event group is a word of flags. Several sources set bits with xEventGroupSetBits(), and a task waits with xEventGroupWaitBits() for a combination: all of the bits, or any of them. Use it when one task waits for several conditions, such as "sensor ready and button pressed". Use a queue when the data matters, and a semaphore when a single event is enough. The API reference lists the wait functions, and the event-group source is event_groups.c.

The rules that matter in interviews

  • A binary semaphore remembers at most one give. Two presses before the task runs make one wake-up. If you need every press, use a counting semaphore or a queue.
  • A queue copies its items. Passing a pointer to a local variable is a bug, because the local is gone when the receiver runs.
  • Block with a timeout or with portMAX_DELAY on purpose. A receiver that waits forever is fine for a worker; a sender that waits forever on a full queue hides a stuck consumer.

Model answer

The ISR clears the interrupt flag first, then calls xSemaphoreGiveFromISR with a pointer to a local BaseType_t. The call does not block, and it sets the flag if the woken task has a higher priority than the interrupted one. The ISR then calls portYIELD_FROM_ISR with that flag, so the switch happens at the end of the interrupt. If the ISR called xSemaphoreGive, the call could try to take a lock or change the ready list from interrupt context, which the port does not allow, and the kernel's critical sections would be corrupted. The ISR's priority must also be at or below configMAX_SYSCALL_INTERRUPT_PRIORITY.
