Bench lab 6: The OLED that doesn't answer

Lesson 61's display code works in Wokwi every time. On the bench the screen can stay black, and the code doesn't tell you why. Make it scan the bus, check every acknowledge, and recover a bus that a device is holding low.

This bench lab is optional. It needs a Pico 2, an SSD1306 128×64 I2C OLED module, two 4.7 kΩ resistors and the logic analyzer. It doesn't count towards your progress. Time: about 55 minutes.
By the end of this lab you can find a device's real I2C address with a bus scan, read address and acknowledge bits on a logic analyzer, and clear a stuck bus with nine clock pulses.

Three things the simulator gets right that a module might not

Lesson 61's driver starts the panel at the fixed address 0x3C and never looks at whether a byte was acknowledged. In Wokwi the panel is always at 0x3C, always powered and always listening, so that's fine. A real module can differ in three ways:

  • The address. The SSD1306 has a pin, SA0, that sets the lowest bit of its address: 0x3C with SA0 low, 0x3D with SA0 high (SSD1306 datasheet, section 8.1.5). Modules tie it one way or the other, often with a solder jumper or a resistor you can move.
  • The silkscreen. Many modules print "0x78" and "0x7A". Those are the 7-bit addresses shifted left by one, the first byte on the wire with the read/write bit as 0. The SDK, like lesson 60, takes the 7-bit form: 0x78 means 0x3C.
  • A stuck bus. If the Pico resets in the middle of a transfer, a device may be in the middle of sending a 0 bit or an acknowledge, holding SDA low. It waits for clock pulses that never come. The new firmware's first START fails, and keeps failing.

The I2C specification gives the cure for the third: if SDA is stuck low, the controller sends nine clock pulses on SCL, after which the device should have released the line; if it hasn't, the device needs a hardware reset or a power cycle (NXP UM10204 rev. 7, section 3.1.16 "Bus clear"). Nine is enough because a byte is eight bits plus one acknowledge: whatever bit the device was in the middle of, it reaches the end of its byte within nine clocks.

Stage 1: in Wokwi

  1. Open projects/bench06-oled-scan/starter. It's lesson 61's code on the Pico 2, with the pull-up resistors in the diagram. Build and run: the panel shows text.
  2. In diagram.json, give the OLED part the attribute "i2cAddress": "0x3d" and run again. The panel stays black and the log shows no error at all. That's the fault you'll meet on the bench, and the starter can't tell you about it.
  3. Put the attribute back to 0x3c (or remove it).

Stage 2: on the board

Wire the module: VCC to 3V3, GND to GND, SDA to GP4, SCL to GP5, with a 4.7 kΩ resistor from each of SDA and SCL to 3V3. Many modules already carry pull-ups; with both, you get about 2.4 kΩ, still fine at 400 kHz. Connect the analyzer: D0 to SCL, D1 to SDA, GND to GND.

  1. Flash the starter. If your module is at 0x3C, it works; if it's at 0x3D, it stays black. Either way, read the address on the module's back.
  2. Task 1: scan. Write bus_scan(): for each address from 0x08 to 0x77, try a one-byte read and print the addresses that return a non-negative result. Addresses 0x00 to 0x07 and 0x78 to 0x7F are reserved (UM10204, section 3.1.12).
  3. Task 2: check the acknowledges. The project's ssd1306_init() now takes the address and returns false on a NACK. Start the panel at the address the scan found, and print an error if it fails.
  4. Decode it. In PulseView add the I2C decoder (SCL = D0, SDA = D1) and capture the scan. You'll see a stream of address bytes each followed by NACK, and one followed by ACK: the panel. Look at the raw first byte for that one: 0x78 or 0x7A, the silkscreen's number.
  5. Task 3: bus recovery. Before i2c_init(), take SDA and SCL as plain GPIOs with pull-ups. If SDA reads low, pulse SCL low and high up to nine times, stopping as soon as SDA goes high, then send a STOP: SDA low, SCL released, SDA released. Release lines; never drive them high.

A stuck bus is hard to cause on purpose with a write-only device like the SSD1306, which only drives SDA while acknowledging. To exercise the code path, hold SDA to GND through a jumper while the board boots. Your recovery should print the pulses, find that SDA is still low (a jumper doesn't release), and print the power-cycle message instead of hanging. With a sensor that sends data, such as a temperature sensor read in a loop, resetting the board by shorting RUN (pin 30) to GND mid-read can leave a genuinely stuck bus, and then the nine pulses free it.

The solution's log on a working board reads BENCH6 device at 0x3C, BENCH6 scan done: 1 device(s), BENCH6 OLED at 0x3C, and the panel shows the address it found.

Your I2C bring-up now tells you what is on the bus, at which address, and whether it answered. That turns "the screen is black" into one log line pointing at the cause.

Common mistakes
  1. Using the silkscreen number in code. 0x78 is the 8-bit form; the SDK wants 0x3C. If the scan finds the device but your code doesn't, compare the two.
  2. Driving SDA or SCL high during recovery. I2C lines are open-drain: if a device holds SDA low while you drive it high, that's a short between two outputs. Set the pin as an input and let the pull-up do it.
  3. No pull-ups at all. Without any resistor the lines can't go high, and the scan finds nothing. Wokwi doesn't need them; the bench does.
  4. Ignoring return values. Every i2c_write_blocking() returns the bytes written or a negative error. Code that throws it away can't tell a missing panel from a working one.

Summary

  • The SSD1306 answers at 0x3C or 0x3D depending on SA0; module silkscreens often print the shifted forms 0x78 and 0x7A.
  • A bus scan finds the real address in a second; do it first on any new I2C board.
  • Check every acknowledge, so a missing device is reported rather than silently ignored.
  • A device left holding SDA low is freed by up to nine SCL pulses and a STOP; if not, it needs a power cycle.
  • On open-drain lines, release to go high; never drive high.
NXP UM10204, I2C-bus specification and user manual, rev. 7: section 3.1.16 "Bus clear", and section 3.1.12 on reserved addresses. Both are under a page.
