Bench lab 6: The OLED that doesn't answer

I2C bus scans, acknowledges and bus recovery

By the end of this lab you can find a device's real I2C address with a bus scan, read address and acknowledge bits on a logic analyzer, and clear a stuck bus with nine clock pulses.

Simulated and real OLED modules

Lesson 61's display code works in Wokwi every time, whereas on the bench the screen can stay black without the code telling you why, so this lab makes it scan the bus, check every acknowledge and recover a bus that a device is holding low. It is optional, needing a Pico 2, an SSD1306 128×64 I2C OLED module, two 4.7 kΩ resistors and the logic analyzer, it does not count towards your progress, and it takes about 55 minutes.

Lesson 61's driver starts the panel at the fixed address 0x3C and never looks at whether a byte was acknowledged, which is fine in Wokwi, where the panel is always at 0x3C, always powered and always listening, whereas a real module can differ in three ways.

  • The address. The SSD1306 has a pin, SA0, that sets the lowest bit of its address: 0x3C with SA0 low, 0x3D with SA0 high (SSD1306 datasheet, section 8.1.5). Modules tie it one way or the other, often with a solder jumper or a resistor you can move.
  • The silkscreen. Many modules print "0x78" and "0x7A". Those are the 7-bit addresses shifted left by one, the first byte on the wire with the read/write bit as 0. The SDK, like lesson 60, takes the 7-bit form: 0x78 means 0x3C.
  • A stuck bus. If the Pico resets in the middle of a transfer, a device may be in the middle of sending a 0 bit or an acknowledge, holding SDA low. It waits for clock pulses that never come. The new firmware's first START fails, and keeps failing.

The I2C specification gives the cure for the third, the controller sending nine clock pulses on SCL if SDA is stuck low, after which the device should have released the line, and a device that has not needs a hardware reset or a power cycle (NXP UM10204 rev. 7, section 3.1.16 "Bus clear"). Nine is enough, because a byte is eight bits plus one acknowledge, so whatever bit the device was in the middle of, it reaches the end of its byte within nine clocks.

Stage 1: in Wokwi

  1. Open projects/bench06-oled-scan/starter, lesson 61's code on the Pico 2 with the pull-up resistors in the diagram, then build and run it, the panel showing text.
  2. In diagram.json, give the OLED part the attribute "i2cAddress": "0x3d" and run again, the panel staying black while the log shows no error at all, the fault you will meet on the bench and one the starter cannot report.
  3. Put the attribute back to 0x3c, or remove it.

Stage 2: on the board

Wire the module with VCC to 3V3, GND to GND, SDA to GP4 and SCL to GP5, adding a 4.7 kΩ resistor from each of SDA and SCL to 3V3, and since many modules already carry pull-ups, with both you get about 2.4 kΩ, still fine at 400 kHz, then connect the analyzer, D0 to SCL, D1 to SDA and GND to GND.

  1. Flash the starter, which works if your module is at 0x3C and stays black if it is at 0x3D, and either way read the address on the module's back.
  2. Task 1: scan. Write bus_scan(), which tries a one-byte read for each address from 0x08 to 0x77 and prints the addresses returning a non-negative result, addresses 0x00 to 0x07 and 0x78 to 0x7F being reserved (UM10204, section 3.1.12).
  3. Task 2: check the acknowledges. The project's ssd1306_init() now takes the address and returns false on a NACK, so start the panel at the address the scan found and print an error if it fails.
  4. Decode it. In PulseView add the I2C decoder (SCL = D0, SDA = D1) and capture the scan, which shows a stream of address bytes each followed by NACK and one followed by ACK, the panel, whose raw first byte is 0x78 or 0x7A, the silkscreen's number.
  5. Task 3: bus recovery. Before i2c_init(), take SDA and SCL as plain GPIOs with pull-ups, and if SDA reads low, pulse SCL low and high up to nine times, stopping as soon as SDA goes high, then send a STOP by taking SDA low, releasing SCL and releasing SDA, always releasing lines rather than driving them high.

A stuck bus is hard to cause on purpose with a write-only device like the SSD1306, which drives SDA only while acknowledging, so to exercise the code path, hold SDA to GND through a jumper while the board boots, your recovery then printing the pulses, finding that SDA is still low (a jumper does not release) and printing the power-cycle message instead of hanging. With a sensor that sends data, such as a temperature sensor read in a loop, resetting the board by shorting RUN (pin 30) to GND mid-read can leave a genuinely stuck bus, which the nine pulses then free.

The solution's log on a working board reads BENCH6 device at 0x3C, BENCH6 scan done: 1 device(s) and BENCH6 OLED at 0x3C, and the panel shows the address it found.

Your I2C bring-up now tells you what is on the bus, at which address and whether it answered, which turns a black screen into one log line pointing at the cause.

Common mistakes and how to spot them

The silkscreen number used in code

The scan finds the device but your code does not, because 0x78 is the 8-bit form while the SDK wants 0x3C. Compare the scan's address with the one in the code.

SDA or SCL driven high during recovery

Two outputs fight on the line, because I2C lines are open-drain, so if a device holds SDA low while you drive it high, the result is a short between them. Set the pin as an input and let the pull-up raise the line.

No pull-ups at all

The scan finds nothing, because without any resistor the lines cannot go high, which Wokwi does not need but the bench does. Fit the pull-up resistors.

Ignored return values

A missing panel looks the same as a working one, because every i2c_write_blocking() returns the bytes written or a negative error, which the code throws away. Check the return value of every transfer.

Summary

  • The SSD1306 answers at 0x3C or 0x3D depending on SA0, and module silkscreens often print the shifted forms 0x78 and 0x7A.
  • A bus scan finds the real address in a second, so it comes first on any new I2C board.
  • Every acknowledge is checked, so that a missing device is reported rather than silently ignored.
  • A device left holding SDA low is freed by up to nine SCL pulses and a STOP, and otherwise needs a power cycle.
  • On open-drain lines a pin is released to go high, never driven high.
NXP UM10204, I2C-bus specification and user manual, rev. 7: section 3.1.16 "Bus clear", and section 3.1.12 on reserved addresses. Both are under a page.
