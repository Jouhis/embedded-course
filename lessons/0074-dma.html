DMA

A DMA controller moves bytes between a peripheral and memory while the CPU runs other code. It is how a UART can receive a whole frame, or an ADC can scan six channels, without an interrupt per byte.

By the end of this lesson you can set up a DMA transfer on paper: choose the direction, the count and the increment settings, use circular mode with half-transfer and transfer-complete interrupts to build a receive buffer, and explain when cache coherence matters.
Concept-only lesson. The Wokwi simulator does not model DMA on the Blue Pill. The course's NOTES.md records this, and the Wokwi Blue Pill documentation lists DMA as not implemented. So this lesson has no Wokwi project. The exercises below are calculations and configuration reasoning. To try the transfers yourself, use a real Blue Pill or an STM32 Nucleo board with the CMake build used in these projects, and the HAL from lesson 69.

Where we are and why it matters

Lesson 70 showed how a UART receives bytes with an interrupt. Each byte raises an interrupt, the handler reads the data register, and it stores the byte in a ring buffer. That works well at 115200 baud, but it has a cost. Every byte is a separate interrupt, with its own entry and exit sequence, and the CPU stops its main work for each one. Lesson 71 used timers that count clock ticks, and lesson 73 used SysTick for a time base. Those lessons show that the CPU is the only place where work happens in the firmware you have written so far.

The problem this lesson solves is simple to state. A sensor sends a stream of bytes, and the firmware must store every byte without losing any, while it also runs control code, drives a display and answers buttons. A product such as a 3D printer controller receives serial data from a host computer, and a battery monitor samples an ADC many times a second. In both cases the copy work is repetitive, and the CPU is the wrong tool for it. A direct memory access (DMA) controller is a small piece of hardware whose only job is to copy data from a peripheral to memory, or back. Once you have set it up, it does the copying with no CPU involvement at all.

The concepts, one at a time

The bus and the bus master

To understand DMA you need one idea from computer architecture (lesson 37). The CPU reads and writes memory and peripherals over a bus. A bus carries an address, a direction and data. Something on the bus that starts transfers is called a bus master. Normally the CPU is the only master. A DMA controller is a second bus master: it can issue reads and writes on the same bus, on its own, while the CPU is busy with something else. On the STM32F1 the bus matrix (bus matrix) connects the CPU and the DMA to flash and SRAM. When both want the same memory in the same cycle, the matrix picks one and the other waits a few cycles.

A transfer through DMA works like this. The DMA reads a value from a peripheral's data register, which is a memory-mapped address, and then writes it to an address in SRAM. Each read and write is an ordinary bus access. The DMA does not know what the bytes mean. It only knows three things: where to read, where to write, and how many items to move. Those three values are the core of every DMA setup.

The DMA registers of one channel

The STM32F1 has two DMA controllers, DMA1 and DMA2, and each has several channels. A channel is one independent copy engine with its own four registers. The CMSIS header describes them as a structure, DMA_Channel_TypeDef, with four members in this order: CCR (the control register), CNDTR (the number of data to transfer), CPAR (the peripheral address) and CMAR (the memory address). You can check the layout in third_party/cmsis-device-f1/Include/stm32f103xb.h. The names are the ones you will see in every STM32F1 DMA example.

  • CPAR holds the address the DMA reads from or writes to on the peripheral side. For a UART receive this is the address of the receive data register.
  • CMAR holds the address in memory. For a receive buffer this is the first element of the array.
  • CNDTR holds how many items are still to move. It starts at the buffer length and counts down, one item per transfer.
  • CCR holds the control bits. It selects the direction, the sizes, the increments, the interrupt enables and the enable bit EN that starts the channel.

The reference manual defines the bits of CCR. The ones this lesson uses are DMA_CCR_EN (channel enable), DMA_CCR_DIR (the direction), DMA_CCR_CIRC (circular mode), DMA_CCR_PINC and DMA_CCR_MINC (peripheral and memory increment), DMA_CCR_PSIZE and DMA_CCR_MSIZE (the data width on each side), DMA_CCR_HTIE, DMA_CCR_TCIE and DMA_CCR_TEIE (the half-transfer, transfer-complete and transfer-error interrupt enables). Channels and requests

A peripheral does not talk to a DMA channel directly. When the UART has a byte ready, it raises a DMA request, a signal that says "I need a transfer now". The request reaches the DMA controller, and the controller serves it on the channel that is wired to that peripheral. Each peripheral request is fixed to a channel, so the programmer chooses the channel that matches the peripheral. The mapping table is in the DMA chapter of RM0008, and it is not repeated here. Read it for the part you use, rather than trusting a number from memory.

Each channel also has its own interrupt line in the vector table. The CMSIS header defines DMA1_Channel1_IRQn through DMA1_Channel7_IRQn (stm32f103xb.h), and the flags for each channel sit in the DMA_ISR register. A flag such as DMA_ISR_HTIF5 says that channel 5 has reached the half-way point. To clear a flag you write a one to the matching bit in DMA_IFCR, for example DMA_IFCR_CHTIF5. The interrupt does not clear itself, so a handler that forgets to clear the flag runs again and again.

Peripheral and memory sizes, and increments

Each side of a transfer has a size and an increment setting. The size tells the DMA how wide each item is: 8, 16 or 32 bits. The increment setting tells it whether the address moves after each item. A UART data register is one fixed address, so the peripheral side has no increment. The buffer is an array, so the memory side does increment. This is the difference between PINC and MINC, and it is the source of one of the most common DMA bugs, which we discuss below.

The sizes must match what the peripheral produces. A UART delivers one 8-bit byte per request, so the peripheral size is 8 bits. An ADC with 12-bit results delivers 16-bit words, so its peripheral size is 16 bits. If the sizes do not match the data, the DMA reads the wrong number of bytes per item, and the buffer contents are shifted or garbled.

Normal mode and circular mode

In normal mode a transfer stops when CNDTR reaches zero. The channel then stops, and the buffer is full. Normal mode is right for a single block, such as sending one frame over the UART, where the firmware knows the length in advance.

In circular mode, DMA_CCR_CIRC is set, and the controller reloads the count and the address at the end of the buffer. The transfer starts again from the beginning, and the DMA writes into the buffer forever. The receive buffer therefore never runs out. The CPU reads behind the write position, in the same way a producer and consumer share a ring buffer in lesson 70. The difference is who the producer is. In lesson 70 the producer was an interrupt handler. Here it is the DMA.

Two interrupts tell the CPU how far the DMA has got. The half-transfer interrupt (DMA_CCR_HTIE) fires when the DMA has written the first half of the buffer. The transfer-complete interrupt (DMA_CCR_TCIE) fires when it has written the second half, which is also the point where it wraps back to the start. The handler processes the half that is ready, while the DMA fills the other half. Figure 1 shows the arrangement.

A worked example: the timing budget of a UART receive

Before you write any code, check that the handler can keep up. This is the calculation that decides the buffer size, and it is the one most engineers skip. Take a UART receiving at 115200 baud into a 256-byte circular buffer. Each byte is sent as 10 bits: one start bit, eight data bits and one stop bit. The baud rate is the number of bits per second on the line, so the time for one byte is: 

one byte  = 10 bits ÷ 115200 bits/s  = 86.8 µs
half buffer = 128 bytes × 86.8 µs        = 11.11 ms

So the DMA fills the first half of the buffer in 11.11 ms, and then the second half in another 11.11 ms. The handler for the half-transfer interrupt has that long, measured from the moment the interrupt fires, to finish reading the first half before the DMA starts to overwrite it. The deadline is the time for the DMA to write the second half, because that is when the DMA reaches the first half again. The handler must therefore be faster than the time to fill one half, with some margin to spare for the interrupt entry.

Compare this with the per-byte design from lesson 70. At 115200 baud a byte arrives every 86.8 µs, so the per-byte handler gets 86.8 µs for each interrupt. Each interrupt costs a few microseconds of entry and exit, and that cost is paid 11 520 times a second. With DMA the CPU is interrupted only twice per 256 bytes, so it is interrupted 90 times a second instead. The arithmetic is simple, but it explains why DMA is the usual answer for a stream of bytes at high speed.

The control word, bit by bit

Now the register value itself. Suppose the channel must be circular, with memory increment, the half-transfer and transfer-complete interrupts enabled, and the defaults for direction and sizes. Build the value from the bits, one at a time. Each bit has a value that is a power of two, so you add the values of the bits you set. 

DMA_CCR_CIRC  bit 5  = 0x20
DMA_CCR_MINC  bit 7  = 0x80
DMA_CCR_HTIE  bit 2  = 0x04
DMA_CCR_TCIE  bit 1  = 0x02
sum                  = 0xA6
then DMA_CCR_EN bit 0 = 0x01, written last: 0xA7

The bit positions come from the header. DMA_CCR_TCIE_Pos is 1, DMA_CCR_HTIE_Pos is 2, DMA_CCR_CIRC_Pos is 5 and DMA_CCR_MINC_Pos is 7. The direction bit is clear, which for a peripheral-to-memory copy is the normal setting. Two details matter here. The enable bit is the last thing you set, so that the channel never starts with a half-configured address or count. And the sizes are zero, which means 8 bits on both sides, which is what the UART delivers.

The code, explained line by line

The following sketch sets up a receive ring buffer for USART1 on DMA1 channel 5. It uses only the register names from the CMSIS header. Read it line by line, and check each name against the header yourself. 

static uint8_t rx_buf[256U];        /* the ring buffer, in SRAM */

void uart_rx_dma_start(void) {
    RCC->AHBENR |= RCC_AHBENR_DMA1EN;              /* 1: clock the DMA1 block */
    DMA1_Channel5->CCR &= ~DMA_CCR_EN;             /* 2: make sure the channel is off */
    DMA1_Channel5->CPAR = (uint32_t)&USART1->DR; /* 3: where the bytes come from */
    DMA1_Channel5->CMAR = (uint32_t)rx_buf;         /* 4: where they go */
    DMA1_Channel5->CNDTR = 256U;                   /* 5: how many items */
    DMA1_Channel5->CCR = DMA_CCR_CIRC | DMA_CCR_MINC
                         | DMA_CCR_HTIE | DMA_CCR_TCIE; /* 6: mode and interrupts */
    USART1->CR3 |= USART_CR3_DMAR;                 /* 7: UART requests DMA */
    DMA1_Channel5->CCR |= DMA_CCR_EN;              /* 8: start the channel */
}

Line 1 turns on the clock to the DMA block. A peripheral with no clock does nothing, and the DMA registers read as their reset values, so a missing clock looks like a DMA that never fires. Line 2 clears the enable bit before the other registers are written. The reference manual says that the channel must be disabled while its address and count registers are being written. Line 3 sets the peripheral address to the address of USART1->DR, the receive data register. The & takes the address of that register, which is a fixed address, not a value.

Line 4 gives the memory address, the first element of the buffer. Line 5 writes the count, 256. The DMA counts this down with each transfer. Line 6 writes the control word from the worked example. It overwrites the whole register, which is safe here because the channel is off. Line 7 tells the UART to make a DMA request for each byte it receives. Without this bit the UART never asks, and the DMA waits forever. Line 8 sets the enable bit, and the transfers begin.

The handler is short, because all the byte work is in the interrupt-free copy. It runs when either half is ready: 

void DMA1_Channel5_IRQHandler(void) {
    if (DMA1->ISR & DMA_ISR_HTIF5) {
        DMA1->IFCR = DMA_IFCR_CHTIF5;               /* clear the flag first */
        process_bytes(&rx_buf[0U], 128U);       /* the first half is full */
    }
    if (DMA1->ISR & DMA_ISR_TCIF5) {
        DMA1->IFCR = DMA_IFCR_CTCIF5;               /* clear the flag first */
        process_bytes(&rx_buf[128U], 128U);     /* the second half is full */
    }
}

The handler reads the status register, DMA1->ISR, to see which event happened. It clears the flag by writing to DMA1->IFCR, the interrupt flag clear register. The clear comes before the work, so that a new event during the work is not lost. The two if blocks handle the two halves. The handler does not need to know where the DMA is inside the buffer, because the two interrupts tell it which half is safe to read. process_bytes() is the consumer, and it must finish before the DMA writes that half again.

Cache coherence: an M7 issue, not an F1 issue

A DMA writes to RAM directly, without going through the CPU. If the CPU has a data cache, the cache can hold an old copy of part of that RAM, and the CPU reads the stale value. The data was changed behind the cache's back. This is called a coherence problem, and it is not specific to DMA; any device that writes memory directly can cause it.

The fix is to invalidate the cache lines of the buffer before the CPU reads it, or to place the buffer in a memory region the cache does not cover. The Cortex-M3 on the STM32F1 has no data cache, so this issue does not arise on the course's Blue Pill. It does arise on Cortex-M7 parts, which have a data cache, so the habit is worth learning now. The course's Cortex-M3 reference is in lesson 72.

Common mistakes and how to spot them

Beginners make the same few mistakes with DMA. Each one has a symptom that you can see without a debugger, if you know what to look for.

Mistake 1: memory increment left off

The most common error is leaving DMA_CCR_MINC out of the control word. The DMA then writes every byte to the same address, CMAR, because the address never moves. Symptom: the buffer holds one repeated value, and it is the last byte received. Fix: set MINC, which moves the memory pointer by one item after each transfer. Check it by reading the buffer after a known string, such as ABCDEFGH, and confirm that all eight letters are there.

Mistake 2: the sizes do not match the peripheral

If the code sets the memory size to 8 bits but the peripheral delivers 16-bit ADC results, each item is read as the wrong width. Symptom: the values look like two interleaved sensors, or they are about half of what you expect, and the pattern repeats every few samples. Fix: set PSIZE and MSIZE to the width the peripheral produces and the width of the array element. Make them equal when you copy into an array of the same type.

Mistake 3: the handler does not clear the flag

If a handler does not write to DMA1->IFCR, the flag stays set, and the interrupt fires again as soon as the handler returns. Symptom: the handler runs continuously, the main loop barely gets time, and a debugger shows the same interrupt line pending again and again. Fix: clear the flag at the start of the handler, before the work.

Mistake 4: the handler is too slow for the buffer

The buffer is circular, so if the handler takes longer than the time to fill one half, the DMA overwrites bytes the handler has not read. Symptom: the data is correct for the first part of each buffer, then drops or repeats bytes, and the errors appear only under load. Fix: make the handler short, copy the half into a larger software queue, or enlarge the buffer. Recalculate the deadline from the baud-rate arithmetic in the worked example.

Mistake 5: the clock is off

If the DMA clock is not enabled, nothing happens, because the peripheral's registers are not clocked. Symptom: the buffer stays at its initial value, no interrupt fires, and the UART itself works fine. Fix: set RCC_AHBENR_DMA1EN before the DMA registers are written. The same rule applies to every peripheral, and lesson 69 showed the clock-enable pattern in the HAL.

In real projects

Production firmware uses DMA almost everywhere data moves in bulk. A serial link to a host, a sensor that streams audio or telemetry, an ADC that scans several channels for a battery monitor, and a display that receives a frame buffer all use DMA. The usual pattern is the one in this lesson: a circular buffer for a stream that never stops, and a normal-mode transfer for a block of known size. Reviewers look for three things. They check the buffer size against the worst-case handler time. They check the sizes and increments against the peripheral's data width. And they check that the buffer is not shared with another DMA channel or with the CPU without a rule about who owns it at each moment.

On the Cortex-M7 parts used in many larger products, reviewers also ask about cache. A buffer that a DMA writes and the CPU reads needs either an invalidate before the read, or an address range marked non-cacheable in the memory protection setup. This is a common question in interviews for embedded roles, because it combines the bus, the cache and the memory map in one answer.

Vendor HALs hide most of the register work behind calls such as HAL_UART_Receive_DMA(), and the course's Lab 4 uses the HAL for that reason. Learn the registers first anyway. A HAL call that fails silently has the same causes as the mistakes above, and you can only debug it if you know which register it wrote.

Summary

  • DMA is a second bus master. It copies data between a peripheral and memory without the CPU, using the same bus accesses the CPU would make.
  • Each channel has four registers: CPAR (peripheral address), CMAR (memory address), CNDTR (count, counting down) and CCR (control bits).
  • Circular mode reloads the count and the address at the end of the buffer, so a receive buffer never runs out.
  • The half-transfer and transfer-complete interrupts tell the CPU which half of the buffer is safe to read.
  • Size the buffer from the baud rate: at 115200 baud with 10 bits per byte, a 256-byte buffer's half fills in 11.11 ms, and the handler must be faster than that.
  • Write EN last, clear the interrupt flags in the handler, and set MINC whenever the memory address must advance.
  • Cache coherence matters on Cortex-M parts with a data cache. The Cortex-M3 on the Blue Pill has none.

"You receive a 1 kHz sensor stream over UART. Why would you use DMA with a circular buffer instead of a receive interrupt per byte?" Answer out loud in 60 seconds, then compare.

Model answer

Per-byte interrupts cost a context switch for every byte. At a few kilobytes per second that is a lot of entries, and each one adds latency to everything else. With DMA the hardware moves each byte without the CPU. A circular buffer with half-transfer and transfer-complete interrupts means the CPU wakes twice per buffer, and it processes a whole half at a time. The trade-off is buffer sizing: the handler must finish one half before the DMA fills the other, and the DMA cannot tell you about a framing error on its own. Use the UART error interrupt as well, and check the handler's worst-case time against the fill time.
