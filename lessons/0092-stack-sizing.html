Stack sizing: high-water marks and overflow checks

A task that runs out of stack writes over memory that belongs to something else, and the bug may appear long after its cause. This lesson shows how to measure each task's stack with the kernel's high-water mark, and how to make the kernel stop the system the moment an overflow happens.

By the end of this lesson you can read a task's stack high-water mark in bytes, decide whether its margin is large enough, enable the stack-overflow check, and explain why an overflow hook that returns hides the bug.

Where we are and why it matters

Lesson 78 introduced the stack: the region of RAM where a function keeps its local variables and its return address, and what happens when that region is too small. Lesson 87 set up FreeRTOS tasks, lesson 88 showed how the kernel switches between them, and lesson 91 added mutexes. In all of those lessons the code worked the first time in a demo. A demo runs the shallow paths of the code, though, and a product also runs the deep ones, the rare command and the error branch that a demo never reaches.

This lesson covers the memory half of a design review. Each task's stack size should be justified by a measurement, and the overflow check should be on, so that a mistake shows up at once instead of years later. The timing half, which asks whether each task finishes before its deadline, is in lesson 93. A motor controller or a medical device has a fixed amount of RAM, and a stack that is too small there overwrites a variable that another task depends on. Teams that ship such products treat the stack numbers as evidence, and a senior engineer will ask where each number came from.

The stack of each task

A stack is a block of RAM that the CPU uses as a last-in, first-out store. The stack pointer, SP, is a register that holds the address of the top of the stack. On the Cortex-M3 it is register R13. Each push writes a word and moves SP, and each pop reads a word and moves SP back. Lesson 33 described the layout as a full-descending stack: SP points at the last item pushed, and a push moves SP down before it writes.

The CPU does not know what the stack is for. A function call pushes a return address and its local variables. An exception pushes a frame of registers, as lesson 34 showed. Each of those writes travels over the bus to RAM in the same way as any other write. Nothing in the hardware stops a write from landing in the wrong place, so the size of the stack is a promise that the program has to keep by itself.

In FreeRTOS, every task has its own stack, and the kernel allocates it when the task is created. Lesson 88 showed what happens to that stack on every switch. When a running task is interrupted, the hardware pushes an eight-word frame onto that task's stack, and the switch handler pushes the eight registers R4 to R11 below it. A task that is switched out therefore keeps 16 words of its own context on its stack before any of its function calls are counted. The stack must hold that context and also the deepest chain of calls the task can make.

You choose each stack's size when you create the task. The depth is the third argument of xTaskCreate(). In the project, the call looks like this (projects/0093-stack-and-timing/solution/main.c): 

xTaskCreate(fast_task, "fast", FAST_STACK_WORDS, NULL, 3U, &fast_handle);

The FreeRTOS header says that the depth is "the number of variables the stack can hold - not the number of bytes" (third_party/FreeRTOS-Kernel/include/task.h, the xTaskCreate documentation). On the Cortex-M3 a stack variable is a 32-bit word, so a depth of 128 is 512 bytes. Forgetting that factor of four is one of the most common sizing errors, and it is covered in the mistakes section below.

A stack on the Cortex-M3 grows downward in memory. Each push moves the stack pointer toward the bottom of the task's block. The bottom is the dangerous end. If a deep call chain or a large local array pushes past it, the write lands in whatever memory sits below, which may be another task's stack or a global variable. The CPU does not stop that write, and the hardware keeps no record of where one task's stack ends and the next begins.

The depth is therefore the value most likely to be a guess when the code is first written. The rest of this lesson is about replacing that guess with a measurement.

Painting the stack: the high-water mark

Lesson 78 showed how to see how deep a stack went by filling the unused part with a known pattern, a technique called stack painting. The kernel does the same for every task it creates. When it creates a task, it fills the whole stack with a known byte pattern. The fill byte is defined in tasks.c as tskSTACK_FILL_BYTE, which is 0xa5 (line 120). The stacks are filled only if the kernel is configured to need the information (the condition is at line 130 of tasks.c, which is true when the high-water mark function is enabled). When the task runs, its stack pointer moves down and overwrites some of the pattern. Words that still hold the pattern were never touched.

Later, uxTaskGetStackHighWaterMark() scans from the bottom of the stack upward, counting words that still hold the fill pattern. The function is defined at tasks.c line 6429, and it is enabled by INCLUDE_uxTaskGetStackHighWaterMark, which the project sets to 1. The return value is the fewest free words ever seen, in words, and the header says so: "the minimum amount of stack space that has remained for the task since the task was created" (include/task.h). The high-water mark is the name for that low point. The smaller the number of free words, the closer the task came to overflowing.

The high-water mark is a record of the past. It is correct for the paths that actually ran. A rarely taken branch that makes a deep call can still overflow after your test passed, and the high-water mark will not warn you, because the mark records only what happened. So the procedure is: size the stack for the worst path you can reason about from the code, run the system through its busiest scenario for long enough, read the mark, and keep a margin. The project uses 16 words as the margin, which is 64 bytes.

Worked example: is one stack big enough?

Suppose the fast task was created with a depth of 128 words, and the report prints a high-water mark of 40 free words for it. The numbers below are made up for the arithmetic. What matters is the order of the steps.

Step 1: convert the free space to bytes. Each word is 4 bytes, so 40 words is 40 × 4 = 160 bytes free.

Step 2: find the peak use. The peak use is the depth minus the fewest free words ever seen: 128 − 40 = 88 words. In bytes that is 88 × 4 = 352 bytes. Check the total: 352 bytes used plus 160 bytes free is 512 bytes, which is the whole 128-word stack. If the two numbers do not add up to the depth, something is in the wrong unit.

Step 3: compare with the margin. The project asks for at least 16 free words, which is 64 bytes. The task has 40 free words, which is more than 16, so it passes, with 24 words to spare.

Step 4: ask what the mark did not see. Suppose a rarely taken branch makes a call chain that needs 50 more words than the test ever used. The peak becomes 88 + 50 = 138 words. The stack has only 128 words, so the call would overflow by 10 words. The test passed and the mark said 40 free words, because that branch never ran during the test. The margin of 40 words is the only protection against this case, and here it is not enough.

Step 5: choose a fix. One option is to raise the depth to 192 words, which is 768 bytes. The measured paths would then have 192 − 88 = 104 words free, and the rare path would have 192 − 138 = 54 words free. Both are above the 16-word margin. The cost is 256 bytes more RAM for this task, and the team should record that cost next to the measurement, so the trade-off is visible in review.

Catching an overflow before it spreads

A high-water mark tells you about the past. A stack overflow check tells you the moment one happens. The option configCHECK_FOR_STACK_OVERFLOW controls it, and the project sets it to 2. With level 2, at every task switch the kernel checks two things: whether the saved stack pointer has gone below the stack's limit, and whether the fill pattern is still present at the bottom of the stack (the four words checked are the 0xa5a5a5a5 pattern, in the macro in include/stack_macros.h). If either check fails, the kernel calls vApplicationStackOverflowHook().

The check is a warning, and it does not stop the write. An overflow has already overwritten memory by the time the next switch happens. What the check buys is the moment of detection. Without it, the corrupted memory keeps being used, and the symptom appears somewhere else, usually in a task that has nothing to do with the stack that overflowed.

The hook is a function you write, with the signature void vApplicationStackOverflowHook(TaskHandle_t t, char *name). The project's version does nothing except loop forever, which is deliberate. It stops the system at the moment of the bug, so a debugger shows which task overflowed and where. A hook that returns quietly hides the bug, and the corrupted memory keeps spreading. Real systems often log the task name to non-volatile memory and then reset, but the principle is the same: a stack overflow is a bug, and the system must not continue as if it were not.

The check runs at task switches. A task that overflows and then blocks in a way that does not switch can corrupt memory before the hook runs. The high-water mark and the hook catch most overflows, not every one. This is one reason for the margin.

Reading the code, line by line

The project's sizing is spread over a few lines. Here are the definitions, with the margin and the stack depth of the fast task: 

#define FAST_STACK_WORDS   128U
#define STACK_MARGIN_WORDS 16U

FAST_STACK_WORDS is the depth in words that the task is created with. The U suffix makes it an unsigned constant, which matches the unsigned type of the kernel's arguments. STACK_MARGIN_WORDS is the smallest number of free words the report accepts. Keeping both as named constants means that a reader can see the sizing decision in one place, and a change to either one is visible in review. The comment in the solution gives the margin in bytes as well, so that the unit is never a guess.

The call to xTaskCreate() was shown above. Its arguments are the task function, a name string used for debugging, the depth in words, a parameter that is NULL because the task takes no data, the priority, and a pointer that receives the task's handle. The handle is the value the report needs later to ask the kernel about this task. The priority argument is the subject of lesson 93.

The report function reads the high-water mark for one task: 

UBaseType_t free_words = uxTaskGetStackHighWaterMark(h);
uint32_t used_words = depth_words - free_words;
return free_words >= STACK_MARGIN_WORDS;

The first line asks the kernel for the fewest free words the task has ever had, using the handle h that the report stored at creation. The second line subtracts it from the depth requested at creation, which gives the peak use in words. Both values are in words, so the report multiplies by four before it prints bytes. The last line compares the free words with the margin and returns the result, so that the caller can print a verdict. The starter's version of this function is the one you change in the hands-on task.

The overflow hook is a single line in the solution: 

void vApplicationStackOverflowHook(TaskHandle_t t, char *name) { (void)t; (void)name; for (;;) {} }

The kernel calls the hook with the handle of the task that overflowed and its name. The two (void) casts tell the compiler that the parameters are deliberately unused, which keeps the warning list clean. The empty for (;;) loop never returns, so the system stops at the point of the overflow, and a debugger can read the state. The same pattern appears in the project's malloc hook, and it is the usual way to stop on a fatal error in firmware.

Common mistakes and how to spot them

Mistake 1: leaving the placeholder in the report. The starter's report_one() sets the free words to 0 until you call the kernel function. The symptom on the serial monitor is clear: every task shows free=0 B and the verdict says STACK LOW, even for a stack that has plenty of room. The fix is to call uxTaskGetStackHighWaterMark(h) and remove the placeholder. The lesson here is that a report which always prints the same value is not a measurement. A quick test is to change a stack depth and check that the number moves.

Mistake 2: confusing words with bytes. A stack depth of 128 is 128 words, which is 512 bytes on the Cortex-M3. If you size a stack in bytes by mistake and pass 512, the task gets 2048 bytes, and its memory use is four times what you planned. The symptom is the opposite one: the heap runs out sooner than you expect, because each task reserves four times the memory. The fix is to read the header comment of xTaskCreate, keep one unit throughout the code, and put the conversion in one place, as the report does.

Mistake 3: reading the high-water mark too early. The mark records only what has run. If you read it a few milliseconds after startup, the deepest path may not have run yet. The symptom is a comfortable margin in the first report and an overflow in the field, when a rare command arrives. The fix is to read the mark after the system has run its busiest scenario, and to keep a margin on top. The project's report task reads the marks every second, which is a practical habit: the kernel keeps the worst value, so the last reading is the peak so far.

Mistake 4: an empty overflow hook. A hook that returns, or a missing configCHECK_FOR_STACK_OVERFLOW, means an overflow is silent. The symptom is a task that behaves strangely a long time later, with no error message. The fix is a hook that stops the system, as in the project, and a debugger session that reads the task name. The hook is only a few lines of code.

In real projects

Teams that ship RTOS products treat stack use as a measured quantity. A common practice is to record the high-water mark of every task after a long soak test, and to keep it in the test report. A change that uses more stack then shows up as a number in code review rather than as a crash in the field. Some teams also keep the stack check on in the production build, so that a field overflow stops the system instead of corrupting memory without a trace.

In a code review, a senior engineer looks for three things about stacks. Each stack size should be justified by a number, and not left at a default or a round guess. The number should come from the busiest scenario that the team can produce, with a margin on top for the paths that were not exercised. And the overflow check and its hook should be enabled, so that a bug stops the system. Be ready to say that the high-water mark covers only the paths that ran, and that the context saved by a switch sits on the same stack as the task's calls.

Try it: measure the stacks

The project projects/0093-stack-and-timing runs a fast task every 10 ms, a slow task every 100 ms, and a report task every second. The report prints each task's stack use, its free words, and its worst measured time in microseconds. Lesson 93 uses the timing half of the same project. This lesson uses the stack lines. It prints STACK OK if every free margin is at least 16 words.

In the simulator the output stops after the first task's first output, or prints nothing, so the report may never appear. The steps below are still how you check the work. Build and read the code.   1. Open projects/0093-stack-and-timing/starter in VS Code, build with Ctrl+Shift+B, then start the simulator with F1 → Wokwi: Start Simulator. The build should finish with no errors.
  2. In report_one(), find the TODO(learner). Replace the placeholder value of free_words with the call uxTaskGetStackHighWaterMark(h), and delete the (void)h; line, since the handle is now used. Leave the priority TODO(learner) in main() for lesson 93.
  3. Build again and simulate. In the simulator the report may not appear. On a real Blue Pill the report should show a stack line for each task with its used bytes and free bytes, and the verdict line STACK OK: every task keeps a margin.   4. Predict before you change anything. In the starter, change FAST_STACK_WORDS from 128U to 256U, build, and simulate.   5. Restore FAST_STACK_WORDS to 128U. Compare the stack lines with the solution's output in projects/0093-stack-and-timing/solution/main.c. The exact digits depend on the simulated run, so compare the size of each number rather than the digits.
Hint

uxTaskGetStackHighWaterMark() takes one argument, the task handle, and returns the fewest free words as a value of type UBaseType_t. Assign its result to free_words, which is already declared, and the rest of the function will use it.

The report task measures nothing and runs at the lowest priority, so it cannot delay the other two. Its own stack is still reported, because an overflow in the report task would also corrupt memory.

Summary

  • Each FreeRTOS task has its own stack, and the depth in xTaskCreate() is in words, which are 4 bytes on the Cortex-M3.
  • A switch saves 16 words of context on the task's own stack: eight by the hardware and eight by the switch handler.
  • The kernel paints each new stack with 0xa5. uxTaskGetStackHighWaterMark() returns the fewest free words the task has had, which is a record of the paths that ran.
  • Peak use is the depth minus the high-water mark. Keep a margin on top for paths that the test did not reach.
  • configCHECK_FOR_STACK_OVERFLOW set to 2 checks at each task switch, and calls vApplicationStackOverflowHook() when the stack limit or the bottom pattern fails.
  • The hook should stop the system, not return. A hook that returns hides the bug and lets the corrupted memory spread.
