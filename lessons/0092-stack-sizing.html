Stack sizing

Measured task stacks and overflow checks

By the end of this lesson you can read a task's stack high-water mark in bytes, decide whether its margin is large enough, enable the stack-overflow check, and explain why an overflow hook that returns hides the bug.

Stack sizes as part of a design review

Lesson 78 introduced the stack, the region of RAM where a function keeps its local variables and its return address, and what happens when that region is too small, while lesson 87 set up FreeRTOS tasks, lesson 88 showed how the kernel switches between them and lesson 91 added mutexes. In all of them the code worked the first time in a demo, but a demo runs the shallow paths of the code, whereas a product also runs the deep ones, the rare command and the error branch that a demo never reaches.

This lesson covers the memory half of a design review, in which each task's stack size is justified by a measurement and the overflow check is on, so that a mistake shows up at once instead of years later, while the timing half, whether each task finishes before its deadline, is in lesson 93. A motor controller or a medical device has a fixed amount of RAM, where a stack that is too small overwrites a variable another task depends on, so teams shipping such products treat the stack numbers as evidence, and a senior engineer will ask where each number came from.

The stack of each task

A stack is a block of RAM that the CPU uses as a last-in, first-out store, the stack pointer SP, register R13 on the Cortex-M3, holding the address of its top, each push writing a word and moving SP and each pop reading a word and moving SP back. Lesson 33 described the layout as a full-descending stack, SP pointing at the last item pushed and a push moving SP down before writing.

The CPU does not know what the stack is for, a function call pushing a return address and its local variables and an exception pushing a frame of registers, as lesson 34 showed, each write travelling over the bus to RAM like any other. Nothing in the hardware stops a write from landing in the wrong place, so the size of the stack is a promise the program must keep by itself.

In FreeRTOS every task has its own stack, allocated by the kernel when the task is created, and lesson 88 showed what happens to it on every switch, the hardware pushing an eight-word frame onto the interrupted task's stack and the switch handler pushing the eight registers R4 to R11 below it. A switched-out task therefore keeps 16 words of its own context on its stack before any of its function calls are counted, so the stack must hold that context as well as the deepest chain of calls the task can make.

Each stack's size is chosen when the task is created, as the third argument of xTaskCreate(), the project's call looking like this (projects/0093-stack-and-timing/solution/main.c). 

xTaskCreate(fast_task, "fast", FAST_STACK_WORDS, NULL, 3U, &fast_handle);

The FreeRTOS header says that the depth is "the number of variables the stack can hold - not the number of bytes" (third_party/FreeRTOS-Kernel/include/task.h, the xTaskCreate documentation), a stack variable on the Cortex-M3 being a 32-bit word, so the size in bytes is

bytes = depth × 4(1)

where the depth is in words, a depth of 128 thus being 512 bytes, and forgetting that factor of four is one of the commonest sizing errors, covered in the mistakes section below.

A stack on the Cortex-M3 grows downward in memory, each push moving the stack pointer toward the bottom of the task's block, which is the dangerous end, because if a deep call chain or a large local array pushes past it, the write lands in whatever memory sits below, perhaps another task's stack or a global variable. The CPU does not stop that write, and the hardware keeps no record of where one task's stack ends and the next begins.

The depth is therefore the value most likely to be a guess when the code is first written, and the rest of this lesson replaces that guess with a measurement.

Stack painting and the high-water mark

Lesson 78 showed how to see how deep a stack went by filling its unused part with a known pattern, a technique called stack painting, which the kernel applies to every task it creates, filling the whole stack with a known byte, tskSTACK_FILL_BYTE, defined in tasks.c as 0xa5 (line 120). The stacks are filled only if the kernel is configured to need the information (the condition at line 130 of tasks.c, true when the high-water mark function is enabled), and as the task runs, its stack pointer moves down and overwrites some of the pattern, so words still holding it were never touched.

uxTaskGetStackHighWaterMark() later scans from the bottom of the stack upward, counting words that still hold the fill pattern, the function being defined at tasks.c line 6429 and enabled by INCLUDE_uxTaskGetStackHighWaterMark, which the project sets to 1. It returns the fewest free words ever seen, which the header describes as "the minimum amount of stack space that has remained for the task since the task was created" (include/task.h), the high-water mark being the name for that low point, so the smaller the number of free words, the closer the task came to overflowing.

The high-water mark is a record of the past, correct for the paths that actually ran, so a rarely taken branch making a deep call can still overflow after a test passed without the mark giving any warning. The procedure is therefore to size the stack for the worst path that can be reasoned about from the code, run the system through its busiest scenario for long enough, read the mark and keep a margin, the project using 16 words, 64 bytes.

Worked example: checking one stack against its margin

Suppose the fast task was created with a depth of 128 words and the report prints a high-water mark of 40 free words for it, numbers made up for the arithmetic, the order of the steps being what matters. Before reading on, predict whether this stack survives a rare branch needing 50 more words than the test used.

  1. Convert the free space to bytes. Each word is 4 bytes, so 40 words is 40 × 4 = 160 bytes free.
  2. Find the peak use. The peak use is the depth minus the fewest free words ever seen, 128 − 40 = 88 words, or 88 × 4 = 352 bytes, and as a check, 352 bytes used plus 160 bytes free make 512 bytes, the whole 128-word stack, so two numbers that do not add up to the depth reveal a wrong unit.
  3. Compare with the margin. The project asks for at least 16 free words, 64 bytes, and the task has 40, so it passes with 24 words to spare.
  4. Ask what the mark did not see. If a rarely taken branch makes a call chain needing 50 more words than the test ever used, the peak becomes 88 + 50 = 138 words, and since the stack has only 128, the call overflows by 10 words, although the test passed with 40 free words, because that branch never ran, so the margin of 40 words, the only protection against this case, is not enough here.
  5. Choose a fix. Raising the depth to 192 words, 768 bytes, leaves the measured paths 192 − 88 = 104 words free and the rare path 192 − 138 = 54, both above the 16-word margin, at a cost of 256 bytes more RAM for this task, which the team should record next to the measurement so that the trade-off is visible in review.

Stack overflow detection at task switches

A high-water mark tells about the past, while a stack overflow check reports the moment one happens, controlled by the option configCHECK_FOR_STACK_OVERFLOW, which the project sets to 2. At that level the kernel checks at every task switch whether the saved stack pointer has gone below the stack's limit and whether the fill pattern is still present at the bottom of the stack (the four words checked holding the 0xa5a5a5a5 pattern, in the macro in include/stack_macros.h), calling vApplicationStackOverflowHook() if either check fails.

The check is a warning that does not stop the write, since an overflow has already overwritten memory by the next switch, and what it buys is the moment of detection, without which the corrupted memory keeps being used and the symptom appears elsewhere, usually in a task that has nothing to do with the overflowing stack.

The hook is a function you write with the signature void vApplicationStackOverflowHook(TaskHandle_t t, char *name), the project's version deliberately doing nothing but loop forever, which stops the system at the moment of the bug so that a debugger shows which task overflowed and where, whereas a hook that returns quietly hides the bug and lets the corrupted memory spread. Real systems often log the task name to non-volatile memory and then reset, on the same principle that a stack overflow is a bug and the system must not continue as if it were not.

The check runs at task switches. A task that overflows and then blocks in a way that does not switch can corrupt memory before the hook runs. The high-water mark and the hook catch most overflows, not every one. This is one reason for the margin.

The sizing code line by line

The project's sizing is spread over a few lines, the definitions giving the margin and the stack depth of the fast task. 

#define FAST_STACK_WORDS   128U
#define STACK_MARGIN_WORDS 16U

FAST_STACK_WORDS is the depth in words the task is created with, its U suffix making it an unsigned constant matching the unsigned type of the kernel's arguments, and STACK_MARGIN_WORDS is the smallest number of free words the report accepts. Keeping both as named constants shows the sizing decision in one place and makes any change visible in review, and the solution's comment also gives the margin in bytes, so the unit is never a guess.

The xTaskCreate() call shown above takes the task function, a name string for debugging, the depth in words, a parameter of NULL because the task takes no data, the priority and a pointer receiving the task's handle, the value the report later needs to ask the kernel about this task, while the priority argument is the subject of lesson 93. The report function reads the high-water mark for one task. 

UBaseType_t free_words = uxTaskGetStackHighWaterMark(h);
uint32_t used_words = depth_words - free_words;
return free_words >= STACK_MARGIN_WORDS;

The first line asks the kernel for the fewest free words the task has ever had, using the handle h stored at creation, and the second subtracts it from the depth requested at creation, giving the peak use in words, so the report multiplies both by four before printing bytes. The last line compares the free words with the margin and returns the result for the caller to print as a verdict, and the starter's version of this function is the one you change in the hands-on task. The overflow hook is a single line in the solution. 

void vApplicationStackOverflowHook(TaskHandle_t t, char *name) { (void)t; (void)name; for (;;) {} }

The kernel calls the hook with the handle and the name of the task that overflowed, the two (void) casts telling the compiler that the parameters are deliberately unused, which keeps the warning list clean, and the empty for (;;) loop never returns, so the system stops at the point of the overflow where a debugger can read the state, the same pattern as the project's malloc hook and the usual way to stop on a fatal error in firmware.

Common mistakes and how to spot them

The placeholder left in the report

Every task shows free=0 B and the verdict says STACK LOW, even for a stack with plenty of room, because the starter's report_one() sets the free words to 0 until the kernel function is called. Call uxTaskGetStackHighWaterMark(h) and remove the placeholder, remembering that a report always printing the same value is not a measurement, which a quick change of a stack depth reveals when the number fails to move.

Words confused with bytes

The heap runs out sooner than expected, because a stack sized in bytes by mistake, passing 512 for 512 bytes, gives the task 512 words, 2 048 bytes, so each task reserves four times the memory planned. Read the header comment of xTaskCreate, keep one unit throughout the code and put the conversion in one place, as the report does.

The high-water mark read too early

The first report shows a comfortable margin, yet the stack overflows in the field when a rare command arrives, because the mark was read a few milliseconds after startup, before the deepest path had run. Read the mark after the system has run its busiest scenario and keep a margin on top, the project's report task reading the marks every second, a practical habit, since the kernel keeps the worst value, so the last reading is the peak so far.

An empty overflow hook

A task behaves strangely long afterwards without any error message, because a hook that returns, or a missing configCHECK_FOR_STACK_OVERFLOW, makes an overflow silent. Write a hook that stops the system, as in the project, only a few lines of code, and read the task name in a debugger session.

Stack measurements as test evidence

Teams shipping RTOS products treat stack use as a measured quantity, a common practice being to record the high-water mark of every task after a long soak test and keep it in the test report, so that a change using more stack shows up as a number in code review rather than a crash in the field. Some teams also keep the stack check on in the production build, so that a field overflow stops the system instead of corrupting memory without a trace.

In a code review a senior engineer expects each stack size to be justified by a number rather than left at a default or a round guess, the number to come from the busiest scenario the team can produce with a margin on top for unexercised paths, and the overflow check and its hook to be enabled, so that a bug stops the system. Be ready to say that the high-water mark covers only the paths that ran and that the context saved by a switch sits on the same stack as the task's calls.

Summary

  • Each FreeRTOS task has its own stack whose depth in xTaskCreate() is in words, 4 bytes each on the Cortex-M3.
  • A switch saves 16 words of context on the task's own stack, eight by the hardware and eight by the switch handler.
  • The kernel paints each new stack with 0xa5, and uxTaskGetStackHighWaterMark() returns the fewest free words the task has had, a record of the paths that ran.
  • Peak use is the depth minus the high-water mark, with a margin on top for paths the test did not reach.
  • configCHECK_FOR_STACK_OVERFLOW set to 2 checks at each task switch and calls vApplicationStackOverflowHook() when the stack limit or the bottom pattern fails.
  • The hook should stop the system rather than return, because a hook that returns hides the bug and lets the corrupted memory spread.
