RS-485 and Modbus RTU

Modbus is a protocol that many factory meters, drives and PLCs speak, and RS-485 is the wire it usually runs on. You will write a Modbus slave for the Pico that the lesson's firmware serves over UART0, and talk to it from a Python master on your PC.

By the end of this lesson you can build a Modbus RTU request and response with CRC-16/MODBUS, answer function 03 (read holding registers) and 06 (write single register), and find the end of a frame from the silent interval.

Where we are, and why this matters

Lesson 53 gave you the UART: a start bit, eight data bits and a stop bit per byte, at an agreed baud rate. The Pico's UART0 in this project uses that format, 8N1, at 115200 baud. Lesson 70 gave you the ring buffer that moves bytes from the interrupt into the main loop. Lesson 100 introduced the differential pair, two wires carrying one signal as a voltage difference. RS-485 uses the same idea, and this lesson adds the rules for many devices sharing one pair of wires.

This setup is common in factories and buildings. An energy meter, a motor drive and a temperature controller hang off one pair of wires, and a supervisory computer asks each of them for values in turn. That conversation needs a wire standard that holds up over long cable and a message format that says who is being asked and whether the answer arrived intact. RS-485 supplies the first. Modbus RTU supplies the second. The rest of this lesson builds the second, and tests it on a PC before it touches the board.

The idea: RS-485 is the wire, Modbus is the language

RS-485 carries each bit as the voltage difference between two wires, A and B, the same differential idea as CAN in lesson 100. Its transceiver is the chip between the UART and the wires. Two control pins decide what the chip does. On the TI SN65HVD3082E, a 5 V RS-485 transceiver used here as a reference, the driver is enabled by a logic high on DE, and when DE is low both bus outputs go high-impedance and the driver stops affecting the line. The receiver is enabled by a logic low on RE. With DE left open, the driver is disabled by default, because the pin has an internal pull-down (Texas Instruments, SN65HVD3082E datasheet, sections 8.4 and Table 8-1).

A differential pair is two people carrying a plank across a field. A gust of wind, the noise, pushes both ends up or down by the same amount, so the plank's tilt does not change. The receiver reads only the tilt, the difference between the two wires, so the noise that hits both wires alike disappears.

That makes RS-485 half-duplex: one pair carries traffic in both directions, so only one node may drive the line at a time. Every node that talks must switch its driver on for its own reply and off again afterwards. The datasheet's application section recommends a termination resistor at each cable end, matched to the cable's characteristic impedance, to stop reflections on a long line (datasheet, section 9.2). A stub, the short run from the main cable to one node, should be kept as short as possible for the same reason (section 9.2.1.2). The Pico's UART0 is a TTL serial port, not RS-485. In Wokwi there is no transceiver, so the firmware has no DE pin to drive. On a real board you would set DE high before each reply and drop it once the last byte has been sent.

Modbus defines what the bytes mean. Modbus RTU (glossary) is the binary version: each byte is sent as-is, with a CRC at the end. The master starts every exchange, and a slave answers only when it is addressed. The Modbus organisation publishes the specifications (modbus.org specifications): the serial-line specification covers the frame and the timing, and the application protocol specification covers the function codes. Those PDFs could not be downloaded for this lesson, so the section numbers you will see in the project's comments are unchecked, and you should read the originals before you cite one.

The RTU frame

The fields are the slave address (1 in this project), the function code, the data, and a 16-bit CRC. Multi-byte fields are big-endian, meaning the most significant byte comes first, which is the opposite of the CRC: the CRC's low byte is sent first. The CRC is CRC-16/MODBUS, with the reflected polynomial 0xA001, an initial value of 0xFFFF and no final XOR. You will check your code against the standard test value: the ASCII string "123456789" gives 0x4B37.

A frame has no start or end byte and no length field. The receiver decides that a frame has ended when the line is silent for 3.5 character times. At 115200 baud, one 8N1 character is 10 bit times, or 86.8 µs, so 3.5 characters are 35 bit times, about 304 µs. The serial-line specification fixes the silence at 1.750 ms above 19200 baud instead of computing it, and both the firmware and the Python master use 1750 µs. The specification itself was not opened for this lesson, so check that rule there before you rely on it.

How the CRC is computed, one bit at a time

A CRC is a checksum built from polynomial division. You do not need the algebra to use it. You need the procedure, which the project's crc16_modbus() function follows exactly. Start with the register crc set to 0xFFFF. For each byte, XOR the byte into the low eight bits of crc. Then repeat eight times: look at the bit that falls off the right end. If it is 1, shift right and XOR with 0xA001. If it is 0, just shift right. After the last byte, crc is the checksum.

Look at shift 2. The bit shifted out is 1, so the shifted value 0x7FFF is XORed with 0xA001, which gives 0x9FFE. The XOR is what makes the checksum depend on every bit, not only on the byte's value. The result after one byte is 0x807E. Each further byte is folded in the same way, so the checksum of a whole frame depends on its order as well as its contents.

Two more facts help you check your work. The request 01 03 00 00 00 02 has CRC 0x0BC4, which is sent as C4 0B, low byte first. The reply 01 03 04 12 34 AB CD has CRC 0x2000, sent as 00 20. If you run the CRC over a whole frame, including its two CRC bytes, the result is zero for both of these frames. That is a quick self-test, because a wrong byte order breaks it and a wrong polynomial does too.

Worked example: a request and its reply, field by field

A master asks slave 1 for registers 0 and 1. The request has four fields: the address 01, the function 03, the start address 00 00 (register 0), and the quantity 00 02 (two registers). The CRC of those six bytes is 0x0BC4, so the frame on the wire is 01 03 00 00 00 02 C4 0B.

The slave reads the registers and answers with 01 03 04 12 34 AB CD, then the CRC 00 20. The fields are: the address 01, the function 03, the byte count 04 (two registers at two bytes each), the register 0 value 12 34, the register 1 value AB CD, and the CRC. The values 0x1234 and 0xABCD are the ones the C host test loads into the registers before it asks. Those bytes are repeated in the C host tests and in the Python selftest, so the two implementations check each other.

When the slave cannot honour a request, it sends an exception: the function code with its high bit set (0x83 for a 03 request), then an exception code. Code 01 is an illegal function, 02 an illegal data address and 03 an illegal data value. The project's header defines these three codes. Take a master that asks for three registers starting at register 2 from a slave that has only three. The start plus the quantity runs past the end, so the slave answers 01 83 02 with CRC C0 F1, which is 01 83 02 C0 F1 on the wire. A bad CRC or a frame for another address gets no reply at all.

Hint for the CRC loop

XOR each byte into the low byte of crc. Then loop eight times: if the bit that falls off the right end is 1, shift right and XOR with 0xA001, otherwise just shift.

Hint for function 03

The quantity is the value field. Build the response in rsp: address, function, byte count (twice the quantity), then each register big-endian starting at index 3. Pass the total length to finish_frame().

Common mistakes and how to spot them

The first mistake is to send the CRC high byte first, because data fields are big-endian and it is tempting to treat everything the same way. The symptom is a slave that never replies, so the master prints reply: (none). The Python selftest still passes, because it checks only the master's own frames and says nothing about what the firmware sends. The fix is to append the low byte first, as the finish_frame() function does. Run the residue check from this lesson on a captured frame. A swapped CRC gives a non-zero result.

The second mistake is to end a frame too early or too late. A fixed delay of a few milliseconds may work at one baud rate and fail at another, and a delay started from the wrong event splits a request in two. The symptom is a master that reads a reply of (none) for a request that was valid, or a slave that answers only the first half of a frame. The fix is to measure the silence from the last received byte, as the firmware does with last_byte_us, and to compare it with FRAME_SILENCE_US every time through the loop.

The third mistake is to forget to clear the receive buffer after a frame that gets no reply. A bad CRC or a frame for another address is still a frame, and if rx_len is not reset, the next request is appended to the old bytes. The symptom is a slave that answers a while, then stays silent: each later request is appended to the old bytes, so its CRC fails. The fix is to reset the length after every attempt, whether or not a reply was sent, as the solution does.

The fourth mistake is to leave the driver on. On a real RS-485 board, a slave whose DE pin stays high after its reply keeps driving the line while the master starts its next request. The symptom is garbage on the master's side, and on a scope the two drivers fight. The fix is to raise DE just before the reply and lower it after the last byte has gone out. The TI datasheet's Table 8-1 shows that a low DE puts the bus outputs in high impedance, which is the state the slave must return to.

In real projects

In industry, Modbus RTU is a polling protocol. A supervisory computer, the master, sends each device a request in turn, and each device answers only its own address. Engineers expect a master to handle silence: a timeout, a retry, and a decision about what to show when a meter stops answering. A slave is expected to be strict. A bad CRC gets silence, and a request it cannot serve gets an exception code, so a master can tell a corrupt frame from a refusal.

A review of this kind of firmware looks for three things. The CRC must be checked against the standard test value, independent of the code under test. The frame parser must be separate from the hardware, so it can run on a PC, which is how this project is built. And the bus direction must be handled explicitly, because RS-485 is half-duplex. The TI datasheet notes that a node can keep its receiver enabled while it transmits, so that it hears its own reply and can check it. That is a useful design choice when a bus collision would otherwise go unnoticed.

Summary

  • RS-485 is a differential, half-duplex bus, so one node drives the pair at a time and every reply needs DE switched on and then off.
  • Modbus RTU frames have no start or end byte. The silence of 3.5 character times, fixed at 1.750 ms above 19200 baud, marks the end.
  • CRC-16/MODBUS starts at 0xFFFF, uses the reflected polynomial 0xA001, and checks as 0x4B37 on the ASCII string 123456789.
  • The CRC goes on the wire low byte first, while the data fields are big-endian.
  • Function 03 reads holding registers, with a byte count of twice the quantity. Function 06 writes one register and is answered with an echo.
  • An exception sets the high bit of the function code and adds a code: 01 illegal function, 02 illegal address, 03 illegal value.
  • A bad CRC or an address for another slave gets no reply, so a master must time out and retry.
Modbus organisation: specifications: the Modbus over Serial Line specification for the RTU framing and timing, and the Modbus Application Protocol specification for the function codes and exceptions. This lesson did not open the PDFs, so read the sections yourself before you cite a number.
