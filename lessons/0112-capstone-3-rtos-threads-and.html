Capstone 3: RTOS threads and PID heater control

Bang-bang control from lesson 111 switches the heater hard and overshoots. This lesson puts the dryer on FreeRTOS, runs a PID controller at a fixed 10 Hz, and gives a supervisor task the job of kicking the watchdog only when every other task has proved it is alive.

By the end of this lesson you can split a product into FreeRTOS tasks with rate-monotonic priorities, use a queue, a mutex and an event group, run a PID loop with anti-windup and derivative on measurement at a fixed rate with vTaskDelayUntil(), and check the whole loop on the PC against a thermal plant, with numbers.

Where we are and why it matters

Lesson 111 gave you a temperature the safety rules can trust, and a state machine tested on the PC. Its control code was a bang-bang switch. This lesson turns the dryer into a set of concurrent jobs. Lesson 87 introduced FreeRTOS tasks, lesson 89 queues and event groups, lesson 90 mutexes, and lesson 84 the watchdog that resets a stuck chip. Lesson 105 gave you the PID controller on its own. Here it runs on the dryer at a fixed rate.

The problem is timing. A PID controller is only as good as its time step. If the control loop runs at irregular intervals, the integral and derivative terms are computed with the wrong step, and the heater no longer behaves like the one you tuned. A supervisor that watches the control loop and resets the chip when the loop stops is the standard answer. It is the reason a product can survive a software fault without leaving the heater on. The real dryer runs its control loop at 10 Hz, and it uses a watchdog to catch any task that stops.

The idea: tasks with deadlines, and a supervisor

Lesson 110 chose five tasks and their priorities by the rate-monotonic rule. This lesson builds four of them (the Modbus comms task arrives in lesson 113) and gives each one a single job, a period, and a way to report that it ran. The safety monitor is the one task whose job is to check the others, so it runs at the highest priority and never shares logic with the control code.

TaskPriorityPeriodJob
safety450 ms, vTaskDelayUntil()Independent checks on the published state; cuts the heater on a trip; kicks the watchdog
control3100 ms, vTaskDelayUntil()Sensor, filter, state machine, PID, outputs, and the snapshot for the others

logger1100 ms check-in, one line a secondCheck in with the watchdog; print the status line

The periods are constants, the priorities follow the rule in lesson 91, and the tasks never call each other directly. They share data through three kinds of object, each with a reason:

  • A queue (lesson 89) carries button presses from the UI task to the control task. A queue is a copy in, copy out, so the sender never holds a pointer into the receiver's data.
  • A mutex (lesson 90) protects the snapshot of the control state, and the I2C bus. A mutex, unlike a binary semaphore, has priority inheritance, so a low-priority task that holds it does not stall the safety monitor for long.
  • An event group is the check-in board. Each monitored task sets its bit each cycle, and the supervisor reads the board.

The snapshot, and why tasks do not wait on each other

The safety task and the logger must read the control state without waiting for the control loop to finish. The control task therefore publishes a snapshot: a copy of the state the others need, written while it holds the state mutex. Readers take the same mutex, copy the structure, and release it. The mutex is held only for the time it takes to copy a structure. Nobody keeps a pointer into the control task's working data, so the control task can change its own variables freely. The price is that readers see the state as of the last publish, and a watchdog needs exactly that.

The watchdog, and why the check-in board

A watchdog resets the chip unless the code kicks it on time (lesson 84). If the safety monitor kicked it every 50 ms no matter what, a stalled control loop would never be noticed: the monitor itself would keep the chip alive. The fix is that the monitor kicks only when every monitored task has set its bit since the last kick. A stalled task leaves its bit clear, the kick does not happen, and the window expires.

The Blue Pill's window watchdog (WWDG) runs from the bus clock, with a counter that falls from 0x7F to 0x3F in about 262 ms at the settings used here. The window register is 0x7F, so any refresh before the counter reaches 0x3F is accepted. The logger therefore checks in every 100 ms, even though it prints only once a second: a once-a-second check-in would expire the watchdog between prints. That detail is the kind of thing a reviewer looks for.

On real hardware, use the IWDG. The independent watchdog (IWDG) runs from its own 40 kHz low-speed clock, so it keeps counting when the bus clock fails. The WWDG does not, and it cannot detect a stopped clock. The IWDG is not simulated by Wokwi (NOTES.md), so the course uses the WWDG here. The check-in logic is the same for both; only the peripheral changes, and the IWDG cannot be stopped once started, just like the WWDG.

The window, worked through

A window watchdog (WWDG) is a down-counter with a window. The counter starts at its reload value and falls by one on each tick. A refresh, which is the kick, reloads the counter. The reset happens if the counter falls to 0x3F without a refresh. The counter's clock is PCLK1 ÷ 4096 ÷ 8, as the board file's comment states. At 8 MHz that is 8 000 000 ÷ 4096 ÷ 8 = 244 Hz, so one count lasts 4.096 ms. Falling from 0x7F to 0x3F is 64 counts, and 64 × 4.096 ms = 262 ms. The window register is 0x7F, which is the top of the counter, so a refresh is accepted at any time before the count reaches 0x3F.

Now a stall. The supervisor kicks at time 0, after all three check-in bits are set, and the counter reloads to 0x7F. The control task then stops. The UI and logger keep setting their bits, but the control bit is never set again, so the supervisor never sees all three bits and never kicks. The counter falls to 0x3F at about 262 ms, and the chip resets. Without the check-in board, the supervisor would kick every 50 ms regardless, the monitor itself would keep the chip alive, and the stall would never be seen. That is the whole reason for the board.

The PID controller

A PID controller adds three terms to form its output from the error e = setpoint − measurement. The proportional term reacts to the error now, the integral term removes the steady offset a proportional controller leaves, and the derivative term damps the approach (lesson 105 derived the discrete form). The module has the same update equations as lesson 105, and the same code is tested on the PC and runs on the board.

Two details make the difference between a textbook loop and one that works on a heater. The first is anti-windup: the integral is clamped to the actuator's range, so while the heater is saturated at full power the integral cannot keep growing and overshoot badly later. The second is derivative on measurement: the derivative uses the measured temperature, not the error, so a setpoint step does not kick the output. A rising temperature reduces the output, which is why the derivative term has the minus sign.

The controller runs at 10 Hz with CONTROL_DT_S = 0.1. The integral and derivative terms are written in per-second units, so the gains keep their meaning if the period changes. The gains still need the closed-loop test, because the period also changes how the discrete loop behaves. The dryer's gains are kp = 0.04, ki = 0.0005 and kd = 0.5, from app/tuning.h.

The update, line by line

float error = setpoint - measurement;                  /* degrees C */
float p_term = p->kp * error;
p->integral += p->ki * error * p->dt;               /* area under the error */
p->integral = clampf(p->integral, p->out_min, p->out_max);
float d_term = 0.0f;
if (!p->first) {
    d_term = -p->kd * (measurement - p->last_meas) / p->dt;
}
p->first = false;
p->last_meas = measurement;
return clampf(p_term + p->integral + d_term, p->out_min, p->out_max);

The first line is the error, in degrees. The proportional term scales it. The integral line adds the error times the period times ki, which is the area under the error curve for one sample. The clamp on the next line keeps the stored integral between 0 and 1, the output limits, so it cannot grow while the heater is saturated. The derivative needs a previous measurement, so the first call skips it. After that, the change in the measurement, in degrees, is divided by the period to get degrees per second, multiplied by kd, and subtracted. The minus sign is the damping: a rising chamber lowers the output. The last line adds the three terms and clamps the result to the actuator range.

Work two samples. The chamber is at 25.00 °C and the setpoint is 45.00 °C. In sample 1, the error is 20.00, so the proportional term is 0.04 × 20 = 0.800. The integral is 0.0005 × 20 × 0.1 = 0.001. There is no derivative yet, so the output is 0.801, which is 801 permille. In sample 2 the chamber has risen to 25.13 °C. That is 0.13 °C in 0.1 s, or 1.3 °C per second. The error is 19.87, so the proportional term is 0.7948, and the integral is 0.001 + 0.0005 × 19.87 × 0.1 = 0.001994. The derivative is −0.5 × 1.3 = −0.65. The output is 0.7948 + 0.001994 − 0.65 = 0.147, which is 147 permille. At full power the plant starts near 80 ÷ 60 = 1.3 °C per second, so that rate is realistic. The derivative pulled the output from 801 to 147 as soon as the chamber began to move. That damping is what the D term is for.

The filter on the temperature

The NTC reading jitters by a few codes from sample to sample, and the derivative term turns that jitter into large output swings. A filter smooths the signal before the controller sees it. The filter here is an IIR filter, which means that each output depends on the previous output as well as the new input. Its update is one line: the state moves by a fraction of the gap between the state and the new sample. In the code the fraction is 1 ÷ 2k, and with k = 2 it is one quarter.

The NTC reading has noise of a few codes, and the derivative term amplifies noise, so the temperature is filtered before the controller sees it. The filter is the exponential moving average from lesson 104, with k = 2, so alpha is one quarter. Its time constant is −1 ÷ ln(1 − 1/4) ≈ 3.5 samples, which is 0.35 s at 10 Hz. That lag is small against the thermal time constant of the chamber, about a minute, so the filter costs little response and removes most of the jitter.

The filter's step response

Suppose the sensor jumps from 25.00 °C to 45.00 °C in one step. The filter moves a quarter of the gap at each sample. After sample 1 the gap is 20 °C, and the filter moves 5 °C, to 30.00 °C. After sample 2 the gap is 15 °C, and the filter moves 3.75 °C, to 33.75 °C. After sample 3 the gap is 11.25 °C, and the filter moves 2.81 °C, to 36.56 °C. Each step leaves 0.75 of the gap, so the gap shrinks geometrically. The time constant is the number of samples to reach 63 % of a step, and here it is −1 ÷ ln(0.75) = 3.48 samples, which is 0.35 s at 10 Hz. The lag is about a third of a second, which the chamber's minute-long time constant can absorb, and the filter removes most of the jitter before the derivative sees it.

Measured: the closed loop against the plant

A physical heater is not on your desk, so the loop is closed in the host test. The thermal plant is the first-order model from lesson 105: 25 °C ambient, 80 °C rise at full power, and a 60 s time constant. The test does not use a copy of the control code. It calls controller_step(), the same function the control task calls, with the plant's temperature turned into an ADC code through the NTC divider and the beta equation, and then converted back by the firmware's ntc_centi_from_raw(). The only simulated part is the sensor and the heater.

The simulated sensor, line by line

double t = celsius + 273.15;
double r = 10000.0 * exp(3950.0 * (1.0 / t - 1.0 / 298.15));
double code = 4095.0 * r / (r + 10000.0);

These three lines run the Beta equation in reverse. The first converts the plant's temperature to kelvin. The second computes the NTC's resistance, R = R25 × eB(1/T − 1/T25), with R25 = 10 kΩ and B = 3950. The third is the divider from lesson 111, with the NTC as the lower resistor, so the ADC code is 4095 × R ÷ (R + 10 kΩ). The firmware's own ntc_centi_from_raw() then converts the code back to a temperature. If the two directions agree, the sensor adds no conversion error, and any error in the result must come from the control code or the plant.

The test reports two numbers. The settling time is measured from the press to the last sample outside the 1 °C band around 45 °C. The overshoot is the highest the temperature gets above 45 °C after the press. Both are checked against the requirements in lesson 110.

The real output of the host test, from the solution, is:

They do not show that your printer's chamber behaves this way. The model's gain and time constant are assumptions, and the gains were not retuned for a real chamber. Measure the step response of the real dryer, fit a model, and tune against that before you trust the numbers. Lesson 105 shows the Ziegler-Nichols method for that job.

Common mistakes and how to spot them

1. One task kicks the watchdog for everybody. Symptom: the control loop stops publishing, but the chip never resets, and the heater stays at its last duty. Cause: the kick does not look at the check-in board. Fix: kick only when every monitored task has set its bit since the last kick, and clear the bits after each kick.

2. A check-in once a second. Symptom: the banner repeats on the serial monitor about every quarter of a second, because the chip resets each time the window expires and main() starts again. Cause: the logger is the only task that checks in slowly, and the board requires every bit. Fix: check in on every cycle, at 100 ms as the logger does, and keep the status line at one per second.

3. An integral with no clamp. Symptom: the closed-loop overshoot is far above 2 °C. Cause: the integral keeps summing while the heater is at full power, so it is large when the setpoint is reached. Fix: clamp the stored integral to the output range, as pid_update() does. Clamping only the final output does not stop the windup.

4. Derivative on the error. Symptom: pressing start drives the heater to full power for a sample, then back down. Cause: a setpoint step is a step in the error, and the derivative of a step is a spike. Fix: differentiate the measurement, as the module does.

5. The wrong unit. Symptom: the duty is 1000 permille whatever the chamber temperature. Cause: the state machine keeps hundredths of a degree and the PID wants degrees, so a setpoint of 4500 is read as 4500 °C. Fix: divide by 100 before the call, and check that the first duty is about 800 permille for a 20 °C error, as the controller test expects.

In real projects

Production heater control adds several things this lesson leaves out: sensor fault handling in the control path, output rate limits, and tuning on the real plant. The usual tuning method is a step-response test on the device, with the Ziegler–Nichols rule from lesson 105 as a starting point, and the simulated numbers here are only as good as the model. An interviewer will ask how you know the simulation matches the printer. The honest answer is that it does not yet, and the measurement comes first.

The watchdog pattern is standard. Commercial firmware uses an independent watchdog with its own low-speed clock, so a stopped bus clock still resets the chip, and it uses a check-in board or a similar scheme so that one task cannot hide another. Fixed-rate control with a timed delay (vTaskDelayUntil()) is the usual way to keep the time step of a PID loop honest. A reviewer will look for a fixed period, a clamped integral and a derivative on the measurement, in that order.

Summary

  • Tasks run at fixed periods with vTaskDelayUntil(), and their priorities follow the rate-monotonic rule: the shorter the period, the higher the priority.
  • A queue carries events by copy, a mutex protects shared data, and an event group records which tasks have checked in.
  • A supervisor kicks the watchdog only when every monitored task has checked in since the last kick, so a stalled task causes a reset.
  • The WWDG window here is 64 counts of 4.096 ms, about 262 ms, so every monitored task must check in faster than that.
  • A PID update takes the error, its integral clamped to the output range, and the derivative of the measurement, which damps the response without kicking on a setpoint step.
  • An IIR filter with k = 2 moves a quarter of the gap per sample and has a time constant of about 3.5 samples.
  • A closed-loop test calls the same controller as the firmware, against a model of the plant, and checks settling time and overshoot against the requirements.

Hint for the units

The state machine keeps the setpoint and the temperature in hundredths of a degree, and the PID works in degrees as floats. Divide by 100 before the call. The output is a fraction, so multiply by 1000 and round before you store it as a duty.

Hint for the test that fails

The controller test checks the first step after starting: the duty should be above 700 permille, because the error is 20 °C and kp is 0.04. A duty of 0 means the PID is not running at all, which points at the heating branch.

"How do you stop a watchdog from hiding a stalled task?" Answer out loud in 60 seconds, then compare.

Model answer

I don't let one task kick the watchdog. A supervisor kicks it only when every monitored task has set its check-in bit since the last kick. Each task sets its bit on every cycle, not once a second, because the window is shorter than a slow task's period. The supervisor runs at the highest priority, so it is not starved, and it uses data from the other tasks through a snapshot under a mutex, so it can decide without holding them up. On real hardware I would use the independent watchdog, which keeps counting even if the bus clock stops.
