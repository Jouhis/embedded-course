Threads and kernel services

Zephyr's kernel has the same building blocks as FreeRTOS: threads, message queues, semaphores, mutexes and deferred work. The names differ, and the priority numbers run the other way. This lesson builds all five on the Pico and maps each one to its FreeRTOS counterpart.

By the end of this lesson you can define a thread with K_THREAD_DEFINE, pass events with a message queue, guard a counter with a mutex, and explain how a Zephyr priority compares with a FreeRTOS one.

The idea

A thread is a function with its own stack, which the scheduler runs. K_THREAD_DEFINE(name, stack, entry, p1, p2, p3, prio, options, delay) reserves the stack and the thread control block at build time, and starts the thread after delay milliseconds (include/zephyr/kernel.h:1029). A preemptive priority is K_PRIO_PREEMPT(x), where x counts from 0, the most urgent. A cooperative priority, K_PRIO_COOP(x), is negative, so a cooperative thread is never preempted by a preemptive one. The numbers run the opposite way to FreeRTOS. In FreeRTOS a larger number is more urgent. In Zephyr a smaller number is more urgent. Check that before you copy a priority from a FreeRTOS project.

The five objects in the solution

  1. Threads: button_thread (priority 2), ui_thread (5) and blink_thread (7). Lower numbers run first when several are ready.
  2. Message queue: K_MSGQ_DEFINE(button_q, sizeof(struct button_event), 8, 4). It copies fixed-size messages, so the sender does not share memory with the receiver. k_msgq_put(…, K_NO_WAIT) drops the event when the queue is full, instead of blocking the button thread.
  3. Semaphore: K_SEM_DEFINE(tick_sem, 0, 1). The timer gives it once a second, and the blink thread takes it. A semaphore is a counter, not a lock.
  4. Mutex: K_MUTEX_DEFINE(stats_lock) guards total_presses. The mutex has priority inheritance, so a low-priority thread holding it is boosted while a higher one waits (Zephyr mutexes, "Priority Inheritance").
  5. Timer and work: K_TIMER_DEFINE(tick_timer, tick_expired, NULL). The expiry runs in interrupt context, so it only gives the semaphore and submits report_work to the system work queue. The work handler runs in a thread, where it can take the mutex and print (Zephyr timers, and the system workqueue).
Never take a mutex, or call printk() for long, inside a timer expiry. The expiry is an interrupt handler, and it may not block. The timer docs say the expiry runs in interrupt context and must be kept short.

FreeRTOS has no equivalent to K_NO_WAIT as a named constant, and it has no negative cooperative priority. Both exist in Zephyr. The priority difference is the one that causes the most bugs when people move code.

"Why should an interrupt handler not take a mutex?" Answer out loud in 60 seconds, then compare.

Model answer

A mutex can block the caller until another thread releases it. An interrupt has no thread to block, and the thread that holds the mutex may be the one the interrupt interrupted, so the system deadlocks. The fix is to make the handler give a semaphore or submit work, and let a thread take the mutex.
