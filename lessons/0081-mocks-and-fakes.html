Mocks and fakes

Stand-ins for hardware in host tests

By the end of this lesson you can test a sensor driver on the PC by faking i2c_write and i2c_read with FFF, and check the calls the driver made.

Testing a driver without its bus

Lesson 80 tested a module on the PC with Unity, writing the test first and keeping the logic away from the hardware on purpose, whereas this lesson deals with code that cannot be kept away, a sensor driver that must call a bus existing only on the board. Lesson 76 answered the layout question, the driver calling a small interface and the target deciding what sits behind it, and this lesson uses that seam for testing.

A driver for a temperature sensor on an I2C bus is written once and then changed for years, and a bug that sends the wrong pointer byte, or reads before the sensor has a sample, may surface only on a customer's board after a release. A host test that replaces the bus runs in a fraction of a second on every change and can drive the error paths that are hard to reach on real hardware, such as a sensor that never acknowledges its address, while also seeing the exact bytes the driver put on the wire, which a scope on the board shows only if someone thinks to look.

The sensor is the MYS-1 from lesson 63, whose driver in projects/0081-mocks-and-fakes talks to the bus only through two functions declared in src/i2c_bus.h, which wrap the vendor SDK on the board and are replaced by the tests on the PC, without the driver knowing which it has.

The unit under test and its dependencies

The module being tested is the unit under test, and everything it calls that should not be tested in this run is a dependency, so in the MYS-1 driver the unit under test is mys1.c and its dependencies are i2c_write and i2c_read. A unit test replaces each dependency with a stand-in, so that a failure points at the unit rather than the bus.

The stand-in is a test double, a name taken from the stunt double of film, defined in the glossary (test double). Gerard Meszaros named the kinds of double in his book on xUnit test patterns, and Martin Fowler explains them in Mocks Aren't Stubs, each kind answering the question of what the test needs from the dependency.

Dummies, stubs, spies, fakes and mocks

Fowler's article gives five kinds of double. A dummy fills a parameter and is never used, such as a logger the code does not touch in this test, a stub returns prepared answers, so that a test can say "the read returns 0xA7", and a spy is a stub that also records how it was called, so the test can check the calls afterwards. A fake is a working but simplified implementation, such as a bus that keeps an array of registers, and a mock is loaded with the calls it expects and fails the test when a call is missing, extra or wrong.

DoubleWhat it does (Fowler's wording, paraphrased)Driver test example
DummyPassed along to fill a parameter, never useda NULL logger
FakeA working but simplified implementationa bus that keeps a register array
StubReturns prepared answers to calls"the read returns 0xA7"
SpyA stub that also records how it was called"the bus saw two writes"
MockPreloaded with the calls it expects, and checks them"fail if the pointer write sends a STOP"

The table is a vocabulary, and the habit behind each label is what matters, which is asking what the test checks. A test that only checks return values needs a stub, while one that checks the bytes on the wire needs a spy, because it must see every call and its arguments, and in C a single fake function that records its arguments and returns a chosen value usually plays both roles. That is why this lesson calls its test doubles "fakes" in the everyday sense and why the labels blur in practice, Fowler's distinction being that a mock checks the calls it expects while a stub does not.

The glossary warns against one common slip. Calling every double a mock is wrong, because a stub only answers and a fake works. Say "fake" for a fake function that records calls, unless the test really checks expectations.

The Fake Function Framework (FFF)

FFF (Fake Function Framework) is a single C header of macros, kept in third_party/fff, needing no code generator or scripting language, which suits a workspace with only a C compiler. A fake is declared with a macro, the line FAKE_VALUE_FUNC(int, i2c_read, uint8_t, uint8_t *, size_t) writing a function named i2c_read that returns an int, takes three arguments and records every call, the first macro argument being the return type, the second the name and the rest the argument types in order.

The generated function keeps its state in a struct named after the function with the suffix _fake, so the state of i2c_read lives in i2c_read_fake, whose fields that matter in a test are listed below.

FieldMeaning
call_countHow many times the function was called
arg0_val, arg1_val, ...The value of each argument at the most recent call
arg0_history[i], ...Every value of each argument, in call order (up to 50 calls by default)
return_valWhat the fake returns when no sequence or custom fake is set
return_val_seqAn array of answers, one per call, set with SET_RETURN_SEQ
custom_fakeA function pointer: when set, the fake calls it and returns its result

Two macros manage the state, DEFINE_FFF_GLOBALS, appearing once in the test program to define the shared history FFF keeps for all fakes, and RESET_FAKE(i2c_read), clearing one fake's counters, history and settings, both defined in the header while the FFF README in third_party/fff lists the rest. When the test file defines both custom_fake and return_val_seq, FFF checks custom_fake first, the header's value-function template calling the custom fake and returning its result, so a set custom_fake hides the sequence, as the generated code in fff.h confirms.

If custom_fake is set, return_val and return_val_seq are ignored. The test in test_mys1.c sets custom_fake to NULL before it sets a return sequence, for exactly this reason. Forgetting that line is a common cause of a test that appears to ignore its own setup.

I2C transactions as the driver sees them

Before faking the bus, we need to know what the driver sends on it. I2C is a two-wire bus with one master and several slaves, each transaction starting with a START condition, after which the master sends a 7-bit address and one more bit for read or write, the slave answers with an acknowledge (ACK) or a not-acknowledge (NACK), and a STOP condition ends the transaction. Lesson 60 covers the wire in detail, and three facts suffice here.

The MYS-1 has a register pointer, set by the first byte the master writes in a transaction, each later byte being data for the register at the pointer, which then increments. The datasheet gives the transactions for one register write, one register read and a two-byte temperature read (MYS-1 datasheet, section 3.2), so a read in its simplest form takes two transactions, a write setting the pointer and a read returning the data.

The datasheet asks for the two steps to be joined without a STOP, a repeated start, also called a RESTART, replacing the STOP with another START. It says the sensor accepts both forms, but a STOP lets another master use the bus in between and costs time, so the driver follows the datasheet, reg_read writing the pointer with stop = false so that the following read is a repeated start, and the test checking this rule is the one that reads arg3_val.

The MYS-1 driver and its fake sensor

The driver has four public functions in src/mys1.h, among them mys1_start, which writes bit 0 of the CTRL register to start periodic measurement, mys1_whoami, which reads the identity register, holding 0xA7 on this part, and mys1_read_celsius, which waits for the data-ready bit in the STATUS register and then reads two bytes of temperature. Two private helpers in mys1.c do the work, reg_write sending a register address and a value in one transaction with a STOP and reg_read setting the pointer and reading.

The test file adds a small fake sensor, an array of 64 registers with a pointer and a counter of status reads, the fake bus updating the pointer on each write, returning register contents on each read and reporting data-ready on a chosen poll, so the test can check the waiting loop. The fake follows the datasheet's pointer rule but not its STOP rule, so a driver sending a STOP before its read would still pass most tests and only the test checking arg3_val would catch it, because a fake models only the rules written into it, and this one is simpler than the real chip by design.

A fake resembles a crash-test dummy, a stand-in that car makers put in the seat because it behaves like a person in the ways that matter and records what happened to it, just as a fake I²C bus answers like a sensor would while the test afterwards reads how often it was called and with which arguments. The comparison breaks on fidelity, though, because a dummy is built to match a body closely, whereas a fake knows only the rules someone wrote into it and passes a driver that breaks any rule left out.

Worked example: tracing one WHO_AM_I read

The test test_whoami_returns_identity asks for the identity register and expects 0xA7, and we trace every step with the project's real values, MYS1_ADDR = 0x48, MYS1_REG_WHO_AM_I = 0x0F and MYS1_WHO_AM_I_VALUE = 0xA7. Before following it, predict where the pointer ends up after the read.

  1. Call the driver. The test calls mys1_whoami(&id), which calls reg_read(0x0F, id, 1), because MYS1_REG_WHO_AM_I is 0x0F.
  2. Write the pointer. reg_read calls i2c_write(0x48, &reg, 1, false), which the fake records, call_count becoming 1, arg0_val 0x48, arg1_val the address of reg, arg2_val 1 and arg3_val false.
  3. Run the custom fake. Because custom_fake is set to fake_bus_write, the fake runs its body instead of returning return_val, setting dev_ptr to data[0], which is 0x0F, while the loop from index 1 to len has nothing to do for a length of 1, and returns 1.
  4. Check the write. reg_read compares the return value with 1 and, finding them equal, continues, the check that stops a read after a NACK, since a return of -1 would have returned false here.
  5. Read the register. reg_read calls i2c_read(0x48, buf, 1), the fake recording a second call and running fake_bus_read, which, the pointer 0x0F not being the STATUS register (0x27), copies dev_regs[0x0F] into the buffer, the value 0xA7 that setUp() stored there, and then increments the pointer to 0x10.
  6. Return. The fake returns 1, equal to len, so reg_read returns true with the identity byte now 0xA7.
  7. Assert. The test asserts that the return value is true and the byte 0xA7, and both assertions pass.

The same walk explains the CTRL write in test_start_sets_measurement_enable, a two-byte frame of 0x20 and 0x01 sent with a STOP, in which the fake sets the pointer to 0x20 from data[0] and copies 0x01 into dev_regs[0x20] from data[1]. The test then checks that dev_regs[MYS1_REG_CTRL] equals MYS1_CTRL_MEAS_EN, reading the fake's memory, the sensor's view of the write, and since the driver never reads it back, only the fake can show that the byte arrived.

The timeout test shows how counting works. With status_ready_after at 1000, the fake never reports data-ready, so the loop in mys1_read_celsius, which runs while polls is below MYS1_MAX_POLLS, 5, makes five polls of one reg_read each, a pointer write and a read per poll, and the driver then returns false. The test checks that status_reads is 5, that i2c_write_fake.call_count is 5 and that the temperature register was never addressed, the last check mattering because a driver that read the temperature anyway would produce more writes than polls.

The fakes and the driver code line by line

The fake declarations sit near the top of test/test_mys1.c, each line doing one specific job. 

DEFINE_FFF_GLOBALS;                                                  /* one copy of FFF's shared history per test program */
FAKE_VALUE_FUNC(int, i2c_write, uint8_t, const uint8_t *, size_t, bool); /* int return; addr, data pointer, length, stop */
FAKE_VALUE_FUNC(int, i2c_read, uint8_t, uint8_t *, size_t);          /* int return; addr, buffer pointer, length */

The first line must appear once, or the linker reports the shared globals twice, and the next two generate the fakes, whose argument types must match src/i2c_bus.h. Since the test file includes that header, a mismatch normally appears as a conflicting-declaration error at build time, so keeping the two in step lets the compiler catch any difference. 

static int fake_bus_write(uint8_t addr, const uint8_t *data, size_t len, bool stop) {
    (void)addr;                     /* the fake has one sensor, so the address is not needed */
    (void)stop;                     /* the fake ignores STOP: see the warning in the explainer */
    dev_ptr = data[0];              /* the first byte of a write sets the pointer */
    for (size_t i = 1; i < len; i++) {
        dev_regs[dev_ptr++] = data[i];   /* later bytes are data; the pointer moves on */
    }
    return (int)len;                /* report every byte as accepted: an ACK on each */
}

The (void) casts tell the compiler and the reader that the arguments are unused on purpose, and the function sets the pointer from the first byte, then writes each remaining byte to the register at the pointer while moving the pointer on. Returning len means that every byte was acknowledged, whereas a NACK test replaces this body with one returning -1, which is what the test with return_val_seq does. 

static int fake_bus_read(uint8_t addr, uint8_t *data, size_t len) {
    (void)addr;
    for (size_t i = 0; i < len; i++) {
        if (dev_ptr == MYS1_REG_STATUS) {            /* reading STATUS counts as one poll */
            status_reads++;
            data[i] = (status_reads >= status_ready_after) ? MYS1_STATUS_DRDY : 0u;
        } else {
            data[i] = dev_regs[dev_ptr];             /* any other register returns its stored value */
        }
        dev_ptr++;                                   /* the pointer increments after each byte */
    }
    return (int)len;
}

The read fake has the same shape, its interesting part being the STATUS branch, which counts the poll and reports data-ready only from the poll the test chose, modelling a sensor that needs time without a clock. The pointer advances after each byte, which makes a two-byte burst read return TEMP_L and then TEMP_H, and the test for a positive temperature sets those bytes to 0xA0 and 0x05, which the driver's conversion turns into 22.5 degrees. 

static bool reg_read(uint8_t reg, uint8_t *buf, size_t len) {
    if (i2c_write(MYS1_ADDR, &reg, 1, false) != 1) {   /* pointer write, no STOP */
        return false;                                  /* NACK: do not start a read */
    }
    return i2c_read(MYS1_ADDR, buf, len) == (int)len;  /* read as a repeated start */
}

This is the one-line rule the tests check, the pointer write returning the number of bytes written, 1, any other value meaning a bus error, and since a NACK stops the function before the read, the test test_whoami_does_not_read_after_nack can assert that i2c_read_fake.call_count is 0.

A pointer argument is recorded as a pointer. FFF's history stores the address that the caller passed, not a copy of the bytes. Here reg_read passes the address of its own parameter reg. That storage ends when reg_read returns. A test that reads i2c_write_fake.arg1_val[0] after mys1_whoami has returned reads storage that no longer belongs to the variable. C calls that undefined behaviour. The byte is usually still there, so such a test passes, but it passes by luck. The fix is to copy the bytes inside custom_fake, while the caller's buffer still exists, into a variable the test owns. The project's fake bus does exactly that: fake_bus_write saves data[0] in last_write_first, and the test checks last_write_first instead of i2c_write_fake.arg1_val[0].

Common mistakes and how to spot them

These mistakes are common when people first use fakes, and each has a symptom visible in the test output.

No reset in setUp

A test passes alone but fails in the full suite with a message such as Expected 1 Was 2 on a call count, because the fake keeps its counts from one test to the next. Call RESET_FAKE in setUp() for every fake the test uses, as the project does for both fakes, and follow the same pattern in new tests.

A stale custom fake

A test expecting false gets true, because it set a return sequence to simulate a bus error while custom_fake was still set from setUp(), so the fake ran its body and the driver saw success. Set i2c_write_fake.custom_fake = NULL before SET_RETURN_SEQ, as test_start_reports_bus_error does.

A fake that is too permissive

The failure appears on real hardware rather than in the host run, on a shared bus where a STOP lets another master take the bus between the pointer write and the read, as the datasheet warns, because the fake accepts every byte and ignores STOP, so a driver sending the wrong flag passes almost every test. Make the important rule explicit, with one test asserting the flag and a note in the fake saying what it does not model.

A pointer read after the call

A test passes in one build and fails after a small change to the driver, because it checks arg1_val[0] after the caller has returned, when the pointed-to storage no longer exists and the stack has been reused. Copy the bytes inside custom_fake, while the caller's buffer is still alive.

A passing test that was never red

Two tests in the starter pass before the driver is written, because the starter returns false everywhere and the failure paths expect false, and a test that passes for the wrong reason tells nothing. Apply the discipline of lesson 80, running the test, seeing it fail for the expected reason and only then writing the code.

CMock and generated mocks

CMock is a generator that takes a header and writes a mock source file, so that for a header line such as int DoesSomething(int a, int b); the CMock summary lists generated functions including DoesSomething_ExpectAndReturn(int a, int b, int toReturn) and DoesSomething_IgnoreAndReturn(int toReturn), together with a _Verify function to call after each test (CMock Summary). In CMock's style the test declares the calls it expects, in order and with their arguments, and the generated code fails the test when a call is missing, extra or has the wrong arguments, a mock in Fowler's sense.

CMock is written in Ruby. This workspace has no Ruby, so you cannot run it here. The course uses FFF for the hands-on work, which needs only a C compiler. The choice between the two styles depends on what is checked. FFF records calls for inspection after the code runs, which suits a driver that must send exact bytes, while CMock enforces an expected sequence, which suits code whose job is to make the right calls in the right order. Both are used in industry, and in both the dependency is replaced by something the test controls while the test states what it expects.

Mocks, fakes and review in driver teams

Professional firmware teams use both styles, many generating mocks from headers with CMock or a similar generator, because the generated code keeps up with the header when the interface changes, while others write small fakes by hand, as this lesson does, because a hand-written fake can model the device, which a generated mock cannot. The common thread is the seam, the driver depending on an interface while the tests choose what sits behind it, and a reviewer looks for that seam first, since a driver calling a register address directly cannot be replaced in tests, which makes the review comment one about design rather than testing.

Reviewers also look at what a test checks, a test named test_read_ok that asserts only a return value being weak, whereas one checking the bytes on the wire, the order of calls, the stop flag and the error paths is strong. A hardware test still matters for the real bus, because a fake knows only the datasheet it was written from, so teams keep a small set of tests on the board and run the bulk of driver tests on the PC.

Summary

  • A unit test replaces each dependency of the unit under test with a test double, the dependencies of a driver being the bus functions.
  • In Fowler's terms a stub returns answers, a spy also records calls, a mock checks expected calls and a fake is a simplified working implementation.
  • FFF generates a fake with one macro, its state living in name_fake as call_count, the argument values and history, return_val, return_val_seq and custom_fake.
  • A set custom_fake hides the return value and the sequence, so it is cleared with NULL before a sequence is used.
  • RESET_FAKE for every fake in setUp() keeps counts from leaking between tests.
  • The datasheet's rules belong in the fake and in a test, and since the pointer write must use a repeated start, the test checks stop.
  • FFF records a pointer rather than the bytes, so the bytes are copied inside the fake while the caller's buffer still exists.
  • A host fake checks the driver's bytes and error paths, while a hardware test still checks the real bus.
