Mocks and fakes

Your driver talks to a bus you do not have on the PC. A fake bus lets you test it anyway, and check every byte it sends.

By the end of this lesson you can test a sensor driver on the PC by faking i2c_write and i2c_read with FFF, and check the calls the driver made.

The idea

A unit test runs one piece of code, so the code's neighbours must be replaced. For firmware, the neighbours are the hardware: the I2C bus, a GPIO, a timer. A replacement is a test double. Gerard Meszaros named five kinds, and Martin Fowler explains them in Mocks Aren't Stubs (section "The Difference Between Mocks and Stubs"). Fowler's article is the best short source for the vocabulary. Use his words when an interviewer asks what a mock is.

DoubleWhat it does (Fowler's wording, paraphrased)Driver test example
DummyPassed along to fill a parameter, never useda NULL logger
FakeA working but simplified implementationa bus that keeps a register array
StubReturns prepared answers to calls"the read returns 0xA7"
SpyA stub that also records how it was called"the bus saw two writes"
MockPreloaded with the calls it expects, and checks them"fail if the pointer write sends a STOP"

The words matter less than the habit: decide what your test checks. A test of return values needs a stub. A test of the bytes on the wire needs a spy. In C, a fake function that records its arguments often plays both the stub and the spy role, so the labels blur in practice.

FFF: fake functions in C

FFF (Fake Function Framework, in third_party/fff) is one header with macros. FAKE_VALUE_FUNC(int, i2c_read, uint8_t, uint8_t *, size_t) writes a function named i2c_read that returns int and records its arguments. Each call updates a struct named i2c_read_fake:

FieldMeaning
call_countHow many times the function was called
arg0_val, arg1_val…The last value of each argument
arg0_history[i]Every value of argument 0, in call order
return_valWhat the fake returns (a stub answer)
return_val_seqAn array of answers, one per call (set with SET_RETURN_SEQ)
custom_fakeA function pointer: when set, the fake calls it instead of returning return_val
RESET_FAKE(i2c_read) clears all of these. Call it in setUp() so one test cannot leak state into the next. The FFF README and examples are in third_party/fff.
If custom_fake is set, return_val and return_val_seq are ignored. The test in test_mys1.c clears custom_fake before it sets a return sequence, for this reason.

CMock: generating the fake from the header

CMock is a generator. You give it a header, and it writes a mock source file. For the header line int DoesSomething(int a, int b);, the CMock summary lists generated functions such as DoesSomething_ExpectAndReturn(int a, int b, int toReturn) and DoesSomething_IgnoreAndReturn(int toReturn), and a _Verify function to call after each test (CMock Summary). In CMock's style, the test declares the calls it expects, in order, with their arguments. The mock fails the test when a call is missing, extra, or has the wrong arguments. That is a mock in Fowler's sense.

CMock is written in Ruby. This workspace has no Ruby, so you cannot run it here. The course uses FFF for the hands-on work, which needs only a C compiler. Choose between the two styles by what you want to check. FFF records calls and lets you inspect them, which suits a driver that must send exact bytes. CMock enforces the expected sequence, which suits interaction-heavy code.

The driver under test

The driver is the MYS-1 sensor from lesson 63 (datasheet). Its functions call only i2c_write(addr, data, len, stop) and i2c_read(addr, data, len), declared in src/i2c_bus.h. On the target these wrap the SDK. In the tests, FFF replaces them. This is the hardware seam from lesson 76: the driver depends on an interface, and the test chooses what sits behind it. The Unity and test-first habits come from lesson 80.

The test file also has a small fake sensor: an array of registers and a register pointer, which the fake bus updates on every call. It follows the datasheet's pointer rule (section 3.2). The fake ignores the STOP flag, so only the test that checks arg3_val would catch a driver that sends a STOP before its read.

"How do you unit-test a driver for a sensor that is only reachable over I2C, when you have no board on your desk?" Answer out loud in 60 seconds, then compare.

Model answer

Put the bus behind a small interface, here i2c_write and i2c_read, and make the driver call only that interface. Compile the driver on the PC. Replace the two functions with fakes: one that records every call, and one that acts like the device, with a register array and a pointer. Then assert on the bytes sent, their order, the stop flag, and the error paths: a NACK, a timeout, and no read after a failed write. Keep a small hardware test for the real bus, because the fake only knows the datasheet you wrote it from.

Martin Fowler, "Mocks Aren't Stubs": read "The Difference Between Mocks and Stubs" for the five definitions. The FFF macros are documented in third_party/fff/README.md.
