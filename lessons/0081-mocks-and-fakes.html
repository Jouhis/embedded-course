Mocks and fakes

Your driver talks to a bus you do not have on the PC. A fake bus lets you test it anyway, and check every byte it sends.

By the end of this lesson you can test a sensor driver on the PC by faking i2c_write and i2c_read with FFF, and check the calls the driver made.

Where we are and why it matters

Lesson 80 showed how to test a module on the PC with Unity, and how to write the test first. That lesson kept the logic away from the hardware on purpose. This lesson deals with the code that cannot be kept away. A sensor driver has to call the bus, and the bus exists only on the board. Lesson 76 gave the answer to the layout question: the driver calls a small interface, and the target decides what sits behind it. This lesson uses that seam for testing.

This happens in real driver work. A driver for a temperature sensor on an I2C bus is written once and then changed for years. A bug that sends the wrong pointer byte, or that reads before the sensor has a sample, may only show up on a customer's board, after a release. A host test that replaces the bus runs in a fraction of a second on every change, and it can send the bus into error paths that are hard to reach on real hardware, such as a sensor that never acknowledges an address. The test also sees the exact bytes the driver put on the wire, which a scope on the board shows only if someone thinks to look.

The sensor in this lesson is the MYS-1 from lesson 63. Its driver is in projects/0081-mocks-and-fakes, and it talks to the bus only through two functions declared in src/i2c_bus.h. On the board, those two functions wrap the vendor SDK. On the PC, the tests replace them. The driver does not know which one it has.

The unit under test and its dependencies

The module you are testing is called the unit under test. Everything it calls that you do not want to test in this run is a dependency. In the MYS-1 driver, the unit under test is mys1.c, and its dependencies are i2c_write and i2c_read. A unit test replaces each dependency with a stand-in, so that a failure points at the unit and not at the bus.

The stand-in is a test double, a name taken from the stunt double in a film. The glossary entry has the definition (test double). Gerard Meszaros named the kinds of double in his book on xUnit test patterns, and Martin Fowler explains the kinds in Mocks Aren't Stubs. Each one answers a question: what does this test need from the dependency?

Test doubles: the vocabulary

Fowler's article gives five kinds of double. A dummy fills a parameter and is never used, such as a logger the code does not touch in this test. A stub returns prepared answers, so a test can say "the read returns 0xA7". A spy is a stub that also records how it was called, so the test can check the calls afterwards. A fake is a working but simplified implementation, such as a bus that keeps an array of registers. A mock is loaded with the calls it expects, and it fails the test when a call is missing, extra or wrong.

A fake is a crash-test dummy. Car makers do not test a crash with a person in the seat; they use a stand-in that behaves like one in the ways that matter and records what happened to it. A fake I²C bus does the same for a driver: it answers like a sensor would, and afterwards the test reads how often it was called and with which arguments.

DoubleWhat it does (Fowler's wording, paraphrased)Driver test example
DummyPassed along to fill a parameter, never useda NULL logger
FakeA working but simplified implementationa bus that keeps a register array
StubReturns prepared answers to calls"the read returns 0xA7"
SpyA stub that also records how it was called"the bus saw two writes"
MockPreloaded with the calls it expects, and checks them"fail if the pointer write sends a STOP"

The table is a vocabulary. The habit behind each label is what to learn. Ask what the test checks. A test that only checks return values needs a stub. A test that checks the bytes on the wire needs a spy, because it must see every call and its arguments. In C, a single fake function that records its arguments and returns a chosen value usually plays both the stub role and the spy role. That is why this lesson calls the test doubles "fakes" in the everyday sense, and why the labels blur in practice. In Fowler's words: a mock checks the calls it expects, and a stub does not.

The glossary warns against one common slip. Calling every double a mock is wrong, because a stub only answers and a fake works. Say "fake" for a fake function that records calls, unless the test really checks expectations.

FFF: fake functions in C

FFF (Fake Function Framework) is a single C header of macros, kept in third_party/fff. It needs no code generator and no scripting language, which makes it a good fit for a workspace with only a C compiler. You declare a fake with a macro. The line FAKE_VALUE_FUNC(int, i2c_read, uint8_t, uint8_t *, size_t) writes a function named i2c_read that returns an int, takes three arguments, and records every call. The first macro argument is the return type, the second is the name, and the rest are the argument types in order.

The generated function keeps its state in a struct with the name of the function and the suffix _fake. So the state of i2c_read lives in i2c_read_fake. The fields that matter in a test are these:

FieldMeaning
call_countHow many times the function was called
arg0_val, arg1_val, ...The value of each argument at the most recent call
arg0_history[i], ...Every value of each argument, in call order (up to 50 calls by default)
return_valWhat the fake returns when no sequence or custom fake is set
return_val_seqAn array of answers, one per call, set with SET_RETURN_SEQ
custom_fakeA function pointer: when set, the fake calls it and returns its result

Two macros manage the state. DEFINE_FFF_GLOBALS appears once in the test program, and it defines the shared history that FFF keeps for all fakes. RESET_FAKE(i2c_read) clears one fake's counters, history and settings. The header defines both, and the FFF README in third_party/fff lists the rest. When the test file defines custom_fake and return_val_seq, FFF checks custom_fake first. The header's value-function template calls the custom fake and returns its result, so a set custom_fake hides the sequence. The generated code in fff.h confirms this.

If custom_fake is set, return_val and return_val_seq are ignored. The test in test_mys1.c sets custom_fake to NULL before it sets a return sequence, for exactly this reason. Forgetting that line is a common cause of a test that appears to ignore its own setup.

The bus as the driver sees it

Before writing a fake of the bus, you need to know what the driver sends on it. I2C is a two-wire bus with one master and several slaves, and each transaction starts with a START condition. The master then sends a 7-bit address, with one more bit that says read or write. The slave answers with an acknowledge (ACK) or a not-acknowledge (NACK), and the transaction ends with a STOP condition. Lesson 60 covers the wire in detail. For this lesson, three facts are enough.

The MYS-1 has a register pointer. The first byte the master writes in a transaction sets the pointer, and each later byte is data for the register at the pointer, which then increments. The datasheet gives the transactions for one register write, one register read and a two-byte temperature read (MYS-1 datasheet, section 3.2). A read therefore takes two transactions in the simplest form: one write that sets the pointer, and one read that returns the data.

The datasheet asks for the two steps to be joined without a STOP between them. A repeated start, also called a RESTART, replaces the STOP with another START. The datasheet says the sensor accepts both forms, but a STOP lets another master use the bus in between, and it costs time. The driver follows the datasheet: reg_read writes the pointer with stop = false, so the read that follows is a repeated start. The test that checks this rule is the one that reads arg3_val.

The driver under test

The driver has four public functions in src/mys1.h. mys1_start writes bit 0 of the CTRL register to start periodic measurement. mys1_whoami reads the identity register, which should hold 0xA7 on this part. mys1_read_celsius waits for the data-ready bit in the STATUS register and then reads two bytes of temperature. The two private helpers in mys1.c do the work: reg_write sends a register address and a value in one transaction with a STOP, and reg_read sets the pointer and reads.

The test file adds a small fake sensor. It is an array of 64 registers, a pointer, and a counter of status reads. The fake bus updates the pointer on each write, and it returns register contents on each read. It also reports data-ready on a chosen poll, so the test can check the waiting loop. The fake follows the datasheet's pointer rule. It does not follow the STOP rule, so a driver that sends a STOP before its read would still pass most tests. Only the test that checks arg3_val would catch it. A fake models only the rules written into it. This one is simpler than the real chip by design.

A worked example: one WHO_AM_I read, traced

Take the test test_whoami_returns_identity. It asks for the identity register and expects 0xA7. Here is every step, with the real values from the project. The constants are MYS1_ADDR = 0x48, MYS1_REG_WHO_AM_I = 0x0F and MYS1_WHO_AM_I_VALUE = 0xA7.

  1. The test calls mys1_whoami(&id). That calls reg_read(0x0F, id, 1), because MYS1_REG_WHO_AM_I is 0x0F.
  2. reg_read calls i2c_write(0x48, &reg, 1, false). The fake records the call. call_count becomes 1, arg0_val is 0x48, arg1_val is the address of reg, arg2_val is 1, and arg3_val is false.
  3. Because custom_fake is set to fake_bus_write, the fake runs its body instead of returning return_val. It sets dev_ptr to data[0], which is 0x0F. The loop from index 1 to len has nothing to do, because the length is 1. It returns 1.
  4. reg_read compares the return value with 1, and it is equal, so it continues. This is the check that stops a read after a NACK: a return of -1 would have returned false here.
  5. reg_read calls i2c_read(0x48, buf, 1). The fake records a second call, and fake_bus_read runs. The pointer is 0x0F, which is not the STATUS register (0x27), so it copies dev_regs[0x0F] into the buffer. That value is 0xA7, because setUp() stored it there. The pointer then increments to 0x10.
  6. The fake returns 1, which equals len, so reg_read returns true. The identity byte is now 0xA7.
  7. The test asserts that the return value is true, and that the byte is 0xA7. Both assertions pass.

The same walk explains the CTRL write in test_start_sets_measurement_enable. The frame is two bytes, 0x20 and 0x01, sent with a STOP. The fake sets the pointer to 0x20 from data[0], then copies 0x01 into dev_regs[0x20] from data[1]. The test then checks that dev_regs[MYS1_REG_CTRL] equals MYS1_CTRL_MEAS_EN. That check reads the fake's memory, which is the sensor's view of the write. The driver never reads it back, so only the fake can show that the byte arrived.

The timeout test shows how counting works. status_ready_after is set to 1000, so the fake never reports data-ready. The loop in mys1_read_celsius runs while polls is below MYS1_MAX_POLLS, which is 5. Each poll is one reg_read, so each poll makes one pointer write and one read. After five polls the loop ends, the driver returns false, and the test checks three things: status_reads is 5, i2c_write_fake.call_count is 5, and the temperature register was never addressed. The last check matters: a driver that read temperature anyway would produce more writes than polls.

The code, line by line

The fake declarations sit near the top of test/test_mys1.c. Each line does a specific job: 

DEFINE_FFF_GLOBALS;                                                  /* one copy of FFF's shared history per test program */
FAKE_VALUE_FUNC(int, i2c_write, uint8_t, const uint8_t *, size_t, bool); /* int return; addr, data pointer, length, stop */
FAKE_VALUE_FUNC(int, i2c_read, uint8_t, uint8_t *, size_t);          /* int return; addr, buffer pointer, length */

The first line must appear once, or the linker reports the shared globals twice. The next two generate the fakes. Their argument types must match src/i2c_bus.h. The test file includes that header, so a mismatch normally shows up as a conflicting-declaration error when you build. Keep the two in step, and let the compiler catch the difference. 

static int fake_bus_write(uint8_t addr, const uint8_t *data, size_t len, bool stop) {
    (void)addr;                     /* the fake has one sensor, so the address is not needed */
    (void)stop;                     /* the fake ignores STOP: see the warning in the explainer */
    dev_ptr = data[0];              /* the first byte of a write sets the pointer */
    for (size_t i = 1; i < len; i++) {
        dev_regs[dev_ptr++] = data[i];   /* later bytes are data; the pointer moves on */
    }
    return (int)len;                /* report every byte as accepted: an ACK on each */
}

The (void) casts tell the compiler and the reader that the arguments are unused on purpose. The function sets the pointer from the first byte, then writes each remaining byte to the register at the pointer and moves the pointer on. Returning len means every byte was acknowledged. A test of a NACK would replace this body with one that returns -1, which is what the test with return_val_seq does. 

static int fake_bus_read(uint8_t addr, uint8_t *data, size_t len) {
    (void)addr;
    for (size_t i = 0; i < len; i++) {
        if (dev_ptr == MYS1_REG_STATUS) {            /* reading STATUS counts as one poll */
            status_reads++;
            data[i] = (status_reads >= status_ready_after) ? MYS1_STATUS_DRDY : 0u;
        } else {
            data[i] = dev_regs[dev_ptr];             /* any other register returns its stored value */
        }
        dev_ptr++;                                   /* the pointer increments after each byte */
    }
    return (int)len;
}

The read fake has the same shape. The STATUS branch is the interesting part. It counts the poll, and it reports data-ready only from the poll that the test chose. That is how the fake models a sensor that needs time, without a clock. The pointer advances after each byte, which is what makes a two-byte burst read return TEMP_L and then TEMP_H. The test for a positive temperature sets those two bytes to 0xA0 and 0x05, and the driver's conversion turns them into 22.5 degrees. 

static bool reg_read(uint8_t reg, uint8_t *buf, size_t len) {
    if (i2c_write(MYS1_ADDR, &reg, 1, false) != 1) {   /* pointer write, no STOP */
        return false;                                  /* NACK: do not start a read */
    }
    return i2c_read(MYS1_ADDR, buf, len) == (int)len;  /* read as a repeated start */
}

This is the one-line rule the tests check. The pointer write returns the number of bytes written, which is 1, and any other value means a bus error. A NACK stops the function before the read, which is why the test test_whoami_does_not_read_after_nack can assert that i2c_read_fake.call_count is 0.

A pointer argument is recorded as a pointer. FFF's history stores the address that the caller passed, not a copy of the bytes. Here reg_read passes the address of its own parameter reg. That storage ends when reg_read returns. A test that reads i2c_write_fake.arg1_val[0] after mys1_whoami has returned reads storage that no longer belongs to the variable. C calls that undefined behaviour. The byte is usually still there, so such a test passes, but it passes by luck. The fix is to copy the bytes inside custom_fake, while the caller's buffer still exists, into a variable the test owns. The project's fake bus does exactly that: fake_bus_write saves data[0] in last_write_first, and the test checks last_write_first instead of i2c_write_fake.arg1_val[0].

Common mistakes and how to spot them

Each of these mistakes is common when people first use fakes. Each has a symptom you can see in the test output.

Mistake 1: no reset in setUp. The fake keeps its counts from one test to the next. The symptom is a test that passes when you run it alone and fails in the full suite, with a message such as Expected 1 Was 2 on a call count. The fix is RESET_FAKE for every fake the test uses, in setUp(). The project does this for both fakes, so use the same pattern in new tests.

Mistake 2: a stale custom fake. The test sets a return sequence to simulate a bus error, but custom_fake is still set from setUp(). The fake runs its body, and the driver sees success. The symptom is a test that expects false and gets true, and the fix is to set i2c_write_fake.custom_fake = NULL before SET_RETURN_SEQ, as test_start_reports_bus_error does.

Mistake 3: a fake that is too kind. The fake accepts every byte and ignores STOP, so a driver that sends the wrong flag passes almost every test. The symptom appears on real hardware, not in the host run, when the bus is shared: a STOP lets another master take the bus between the pointer write and the read, which the datasheet warns about. The fix is to make the important rule explicit, which means one test that asserts the flag, and a note in the fake that says what it does not model.

Mistake 4: reading a pointer after the call. The test checks arg1_val[0] after the caller has returned, and the pointed-to storage no longer exists. The symptom is a test that passes in one build and fails after a small change to the driver, because the stack has been reused. The fix is to copy the bytes inside custom_fake, while the caller's buffer is still alive.

Mistake 5: a passing test that was never red. Two tests in the starter pass before the driver is written, because the starter returns false everywhere, and the failure paths expect false. A test that passes for the wrong reason tells you nothing. The fix is the discipline from lesson 80: run the test, see it fail for the reason you expect, then write the code.

CMock: the same idea, generated from the header

CMock is a generator. You give it a header, and it writes a mock source file. For a header line such as int DoesSomething(int a, int b);, the CMock summary lists generated functions, including DoesSomething_ExpectAndReturn(int a, int b, int toReturn) and DoesSomething_IgnoreAndReturn(int toReturn), and a _Verify function to call after each test (CMock Summary). In CMock's style, the test declares the calls it expects, in order, with their arguments, and the generated code fails the test when a call is missing, extra or has the wrong arguments. That is a mock in Fowler's sense.

CMock is written in Ruby. This workspace has no Ruby, so you cannot run it here. The course uses FFF for the hands-on work, which needs only a C compiler. Choose between the two styles by what you want to check. FFF records calls and lets you inspect them after the code runs, which suits a driver that must send exact bytes. CMock enforces an expected sequence, which suits code whose job is to make the right calls in the right order. Both are used in industry. The idea is the same in both: the dependency is replaced by something the test controls, and the test says what it expects.

In real projects

In a professional firmware team, you will see both styles. Many teams generate mocks from headers with CMock or a similar generator, because the generated code keeps up with the header when the interface changes. Other teams write small fakes by hand, as this lesson does, because a hand-written fake can model the device, which a generated mock cannot do. The common thread is the seam: the driver depends on an interface, and the tests choose what sits behind it. A reviewer looks for that seam first. If the driver calls a register address directly, the tests cannot replace it, and the review comment is about the design, not the test.

Reviewers also look at what the test checks. A test named test_read_ok that asserts only a return value is weak. A test that checks the bytes on the wire, the order of the calls, the stop flag and the error paths is strong. A hardware test still matters for the real bus, because a fake knows only the datasheet it was written from. Teams therefore keep a small set of tests on the board, and run the bulk of driver tests on the PC.

Summary

  • A unit test replaces each dependency of the unit under test with a test double. For a driver, the dependencies are the bus functions.
  • Fowler's kinds: a stub returns answers, a spy also records calls, a mock checks expected calls, and a fake is a simplified working implementation.
  • FFF generates a fake with one macro. Its state lives in name_fake: call_count, the argument values and history, return_val, return_val_seq and custom_fake.
  • A set custom_fake hides the return value and the sequence. Clear it with NULL before you use a sequence.
  • Call RESET_FAKE for every fake in setUp(), so counts do not leak between tests.
  • The datasheet's rules belong in the fake and in a test. The pointer write must use a repeated start, so the test checks stop.
  • FFF records a pointer, not the bytes. Copy the bytes inside the fake while the caller's buffer still exists.
  • A host fake checks the driver's bytes and error paths. A hardware test still checks the real bus.
