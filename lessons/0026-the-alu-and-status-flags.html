The ALU and status flags

The arithmetic unit and the four bits that describe each result

By the end of this lesson you can predict the N, Z, C and V flags after an add, a subtract or a compare, and say which flag a signed or an unsigned comparison uses, by running the same values in the CPU simulator.

Arithmetic and comparisons in the CPU

Lesson 23 built a full adder from gates and noted that a row of them forms the adder at the heart of the CPU's arithmetic, and lesson 25 supplied registers to hold the operands and the result. This lesson combines those pieces into the unit that performs the arithmetic of every instruction, and shows what it records about each result.

The main reason to understand it is comparison. A line such as if (count < limit) does not compare two numbers directly; the compiler emits a subtract or compare instruction followed by a conditional branch that reads a few bits the subtraction left behind. If those bits are misread, the branch goes the wrong way, and the bug appears only for some values, usually negative ones or ones near the top of the range. Lesson 32 shows the same compare in the disassembly of compiled C, and the flags are what connect the two.

By the end you should be able to take two values, predict the four flags and know which flag a given branch reads, at which point the disassembly and the debugger stop being mysterious.

The ALU as a combinational block

The ALU, or arithmetic logic unit, is the combinational block that computes addition, subtraction, AND, OR, exclusive OR and shifts on two operands. Like every combinational block from lesson 23, its outputs depend only on its present inputs: it takes two operands and an operation select, produces one result and has no memory of its own. The result goes to a register, and the ALU also produces four bits called the status flags, stored in what the Arm reference calls the Application PSR (APSR), the top four bits of the program status register xPSR, as the simulator shows.

The table gives the meaning of each flag, using the bit assignments of the Cortex-M3 Technical Reference Manual (Arm Cortex-M3 TRM DDI0337G, section 2.3.2, Table 2-1; PM0056 Rev 7, section 2.1.3, Table 4, gives the same bit positions).

The TRM's table says only "carry or borrow" for C, and which of the two it means after a subtraction depends on a convention that matters for comparisons. PM0056 Rev 7 (section 2.1.3, Table 4) states the convention: after a subtraction, C is 1 when the operation does not borrow. The Armv7-M Architecture Reference Manual defines the condition codes that branches read, and both the simulator and the rest of this lesson follow the Arm convention.

Subtraction by addition

The ALU has a single adder, so subtraction is performed as addition, using

a − b = a + NOT b + 1(1)

where NOT b flips every bit of b. Flipping every bit of an n-bit number gives 2n − 1 − b, so adding one more gives 2n − b, and adding that to a gives 2n + (a − b). The 2n term is the carry out of the top bit, and it is what the carry flag measures.

For unsigned numbers this has a direct meaning. If a is at least b, then a − b is not negative, so 2n + (a − b) is at least 2n and a carry comes out of the top bit; C = 1 therefore means no borrow, and a ≥ b. If a is less than b, the sum stays below 2n, no carry emerges, and C = 0 means a borrow occurred. The carry flag after a subtraction is thus the opposite of what many people expect, with 1 meaning "no borrow" rather than "borrowed", as both the simulator and PM0056 Rev 7 (section 2.1.3, Table 4) define it. A compare instruction is a subtraction that discards the result and keeps only the flags, so a compare is also a carry test.

The simulator's source makes this explicit, since its subtract routine calls the same adder as the add instruction with the second operand inverted and a carry-in of 1, which is exactly Equation 1. You can read it in assets/cpusim.js.

Unsigned and signed flags

The same 32 bits can be read as an unsigned number or as a two's-complement signed number. The adder cannot know which reading is intended, so it sets both C and V, and the choice of branch decides which flag matters.

A battery charger reads the cell temperature as a signed number and stops charging above 45 °C. If the comparison is compiled as unsigned, a cold reading of −5 °C becomes 0xFFFFFFFB, which is over four billion, so the charger concludes that the cell is far too hot and refuses to charge in winter. The bits and the ALU result are identical either way, and only the flag the branch tests differs, C for unsigned and N with V for signed.

  • C is the unsigned flag. It shows whether the true unsigned result left the 32-bit range, so after a compare C = 1 means that the first operand was at least the second, unsigned. The branch BHS (branch if higher or same) reads C = 1, and BLO (branch if lower) reads C = 0.
  • V is the signed overflow flag. It shows whether the signed result has the wrong sign, which happens when the true answer lies outside the signed range: two operands of the same sign produced a result of the other sign. For a − b the adder actually adds a and NOT b plus 1, so the rule applies to those inputs, and a and NOT b have the same sign when a and b have different signs. Signed comparisons use V together with N.
  • N is the sign of the 32-bit result. On its own it is simply bit 31, but combined with V it shows whether the true signed result is negative, which is what a signed less-than needs. The branch BLT (signed less than) is taken when N differs from V, and BGE (signed greater or equal) when N equals V.

The N XOR V rule works because V records when the 32-bit sign bit cannot be trusted. Normally N gives the sign, but when the subtraction overflows the sign bit is flipped and V is set to say so. N then shows the wrong sign, and N XOR V restores the right answer, so a signed less-than stays correct even when the subtraction overflows.

C and V are not interchangeable. In 8 bits, 0x7F + 1 is 127 + 1 = 128, which leaves the signed range without carrying out of bit 7, so C = 0 and V = 1. Read as unsigned, 0xFF + 1 is 255 + 1 = 256, which carries out, so C = 1 and V = 0. Use C for unsigned values and V for signed values, never the other way round.

Worked example: 3 − 5 bit by bit

An 8-bit subtraction, 0x03 − 0x05, shows every step of Equation 1. Before working it through, predict the sign of the result and whether a borrow occurs.

  1. Start: a = 0000 0011 (3) and b = 0000 0101 (5).
  2. Invert b: NOT b = 1111 1010, with every bit flipped.
  3. Add the two: 0000 0011 + 1111 1010 = 1111 1101. The sum fits in 8 bits, so there is no carry out of bit 7.
  4. Add the carry-in of 1: 1111 1101 + 1 = 1111 1110, still with no carry out of bit 7.
  5. Read the result: 1111 1110, or 0xFE, which in 8-bit two's complement is −2, the correct value of 3 − 5.
  6. Set the flags: N = 1 because bit 7 of the result is 1, and Z = 0 because the result is not zero. C = 0 because no carry came out, meaning a borrow, since 3 is less than 5 unsigned, and V = 0 because −2 is within the signed range.

Checking the flags against the branches confirms the reasoning. The signed less-than BLT is taken when N differs from V, and here N = 1 and V = 0, so it is taken and the signed test 3 < 5 is true. The unsigned less-than BLO is taken when C = 0, which holds, so it is taken too and 3 < 5 is also true unsigned. For these small values the two branches agree, and the next example uses a pair where they do not.

  1. The ALU has one adder, so it computes 3 − 5 as 3 + (NOT 5) + 1. Start with a = 0000 0011.
  2. Invert every bit of b: 0000 0101 becomes 1111 1010, 0xFA.
  3. Add a and NOT b: 0000 0011 + 1111 1010 = 1111 1101. Nothing carries out of bit 7.
  4. Add the carry-in of 1: 1111 1110, 0xFE. As a signed 8-bit number that is −2, the right answer.
  5. Set the flags. N = 1: bit 7 of the result is 1. Z = 0: the result is not zero. C = 0: no carry out, which for a subtraction means a borrow, so 3 < 5 unsigned. V = 0: −2 fits, so no signed overflow.
  6. The branches read the flags. BLT branches when N differs from V, and BLO branches when C is 0. Both branch here, because 3 is less than 5 both ways.

Worked example: −1 compared with 1

As 32-bit words, −1 is 0xFFFFFFFF and 1 is 0x00000001, so the compare computes 0xFFFFFFFF − 1. We read the result once as unsigned and once as signed.

  • Unsigned view: 0xFFFFFFFF is 4 294 967 295, the largest value, and greater than 1. The subtraction does not borrow, so C = 1, and the unsigned less-than BLO, which needs C = 0, is not taken; unsigned, the first value is not less than the second.
  • Signed view: the result 0xFFFFFFFE has bit 31 set, so N = 1, and −1 − 1 = −2 is within range, so V = 0. The signed less-than BLT is taken because N and V differ; signed, −1 is less than 1.

One comparison gives two correct answers because it answers two different questions, and the chosen branch is the question. With int values in C the compiler picks the signed branch, and with unsigned values the unsigned one, so mixing the two in one expression is where the bug comes from.

Hint for the signed rule

Look at the signs of the two operands and of the result. If the operands share a sign and the result has the other sign, V is 1, and that is all V measures.

The simulator's CMP is a subtraction that keeps only the flags, which is exactly what a compiler emits before a branch. Lesson 29 shows the branch instructions that read these flags, and lesson 32 the same compare in the disassembly of compiled C.
You ran real add and subtract instructions on values that set each flag, and you can say which flags an unsigned compare and a signed compare read. That is the step from an adder built of gates to an if statement in firmware.

Common mistakes and how to spot them

A signed comparison that branches on C

This is the case the warning above describes, and the most common. A test such as if (x < 1) works for small positive values and fails for negative ones; with the −1 example in the simulator, the unsigned BLO says "not less" while the signed BLT says "less". Make the comparison signed whenever the values are signed, which in C means declaring them int or int32_t rather than unsigned.

Flags overwritten between the compare and the branch

The branch goes the wrong way after a line that seems unrelated. A flag-setting instruction placed between the compare and the branch, such as an ADDS to a counter, means the branch reads the flags of that addition instead, which the simulator shows clearly because every arithmetic instruction sets the flags there. Compare immediately before the branch, and check the disassembly when unsure which instruction set the flags.

C read as a borrow flag with the wrong sense

A programmer who expects C = 1 to mean "borrowed" inverts every unsigned compare, so a loop runs one time too many or too few, or a range check accepts a boundary value it should reject. After a subtraction, C = 1 means no borrow, so the first operand was at least the second. Write the test as "C = 1 means greater or equal" and check it on a boundary pair such as 5 and 5.

Signed overflow tested in C after the addition

A check such as if (a + b < a) is a common way to detect overflow, but for signed int values the overflow in the addition is undefined behaviour in C, so the optimiser may remove the check. It then works in a debug build and fails in a release build. Check the range before adding, using the signed limits, or use unsigned arithmetic for the wrap test.

Flags in code review and debugging

Firmware reviewers check two things in comparisons: that the operand types match the branch, and that each compare sits next to the branch that uses it. Mixed signed and unsigned types are among the most common findings in embedded code review, and most static analysis tools warn about them. When debugging a branch in GDB, the flags are visible in the program status register, and reading N, Z, C and V there lets you verify the branch decision without guessing.

The RP2040 uses Cortex-M0+ cores, which implement a smaller instruction set than the M3 discussed here. Whether an instruction updates the flags depends on the instruction and its encoding rather than only on the core, so before relying on a flag after an unfamiliar instruction, read that instruction's entry in the Arm reference for your core.

Summary

  • The ALU is a combinational block that computes arithmetic and logic on two operands and produces the result plus four status flags.
  • Subtraction is addition: a − b is a + NOT b + 1, using the same adder.
  • After a subtraction, C = 1 means no borrow, so the first operand was at least the second, unsigned.
  • V means the signed result is out of range, and N is bit 31 of the result.
  • Unsigned branches read C, while signed branches read N and V, with BLT taken when N differs from V.
  • The same bits can give two correct answers, and the chosen branch decides which question is asked.
  • Compare right before the branch, and make sure the operand types match the branch you expect.
