The ALU and status flags

Every if (a < b) in your C code becomes a subtraction in the CPU, followed by a branch that reads four flags. Two of those flags, C and V, answer different questions, and mixing them up is a classic source of wrong comparisons.

By the end of this lesson you can predict the N, Z, C and V flags after an add, a subtract or a compare, and say which flag a signed or an unsigned comparison uses, by running the same values in the CPU simulator.

Where we are and why it matters

Lesson 23 built a full adder from gates, and said that a row of them makes the adder at the heart of the CPU's arithmetic. Lesson 25 gave you registers to hold the operands and the result. This lesson puts those pieces together into the unit that does the arithmetic on every instruction, and shows what it records about each result.

The reason to understand this is the comparison. A line like if (count < limit) does not compare two numbers directly. The compiler emits a subtract or a compare instruction, and then a conditional branch that reads a few bits the subtract left behind. If those bits are misread, the branch goes the wrong way, and the bug shows up only for some values, usually negative ones or ones near the top of the range. Lesson 32 shows the same compare in the disassembly of compiled C, and the flags are what link the two.

By the end you should be able to look at two values, predict the four flags, and know which flag a particular branch reads. Once you can do that, the disassembly and the debugger stop being mysteries.

Concept 1: the ALU is a combinational block

The ALU (arithmetic logic unit) is the combinational block that computes add, subtract, AND, OR, exclusive OR and shifts on two operands. A combinational block, from lesson 23, has outputs that depend only on its current inputs. The ALU takes two operands and an operation select, and produces one result. It has no memory of its own. The result is written to a register, and the ALU also produces four bits called the status flags. Those are stored in the program status register, which the Arm reference calls the Application PSR (APSR). The APSR is the top four bits of the program status register xPSR, as the simulator shows.

Here is what each flag means, using the Cortex-M3 Technical Reference Manual's bit assignments (Arm Cortex-M3 TRM DDI0337G, section 2.3.2, Table 2-1):

FlagBit in xPSRNameSet when
N31Negativebit 31 of the result is 1
Z30Zerothe result is 0
C29Carry or borrowan add carries out of bit 31, or a subtract borrows (see below)
V28Overflowthe signed result is out of range

The TRM's table says only "carry or borrow" for C. Which of the two it means for a subtract depends on the convention, and the convention matters for comparisons. The exact rules are in the Armv7-M Architecture Reference Manual, which defines the condition codes that branches read. The simulator in this lesson follows the Arm convention, and the rest of this lesson uses it.

Concept 2: subtraction is addition

The ALU has one adder, so a subtract is done as an add. The trick is that a − b equals a + NOT b + 1, where NOT b flips every bit of b. Flipping every bit of an n-bit number gives 2n − 1 − b, so adding one more gives 2n − b. Adding that to a gives 2n + (a − b). The 2n term is the carry out of the top bit, and it is what the carry flag measures.

Follow that through for unsigned numbers. If a is at least b, then a − b is not negative, so 2n + (a − b) is at least 2n, and a carry comes out of the top bit. C = 1 means no borrow, and it means a ≥ b. If a is less than b, the sum stays below 2n, no carry comes out, and C = 0 means a borrow happened. The carry flag after a subtract is therefore the opposite of what many people expect: 1 means "no borrow", not "borrowed". That is the convention the simulator uses, and the Arm reference uses it too. The compare instruction is a subtract that discards the result and keeps only the flags, so a compare is also a carry test.

The simulator's source makes this explicit. Its subtract routine calls the same adder as the add instruction with the second operand inverted and a carry-in of 1, which is the a + NOT b + 1 form. You can read it in assets/cpusim.js.

Concept 3: C and V answer different questions

The same 32 bits can be read as unsigned numbers or as two's-complement signed numbers. The adder does not know which reading you intend, so it sets both C and V, and the branch you choose decides which flag matters.

  • C is the unsigned flag. It says whether the true unsigned result left the 32-bit range. After a compare, C = 1 means the first operand was at least the second, unsigned. The branch BHS (branch if higher or same) reads C = 1. The branch BLO (branch if lower) reads C = 0.
  • V is the signed overflow flag. It says whether the signed result has the wrong sign, which happens when the true answer is outside the signed range. The rule is simple: two operands with the same sign produced a result with the other sign. For a subtraction a − b, the adder actually adds a and NOT b plus 1, so the rule applies to those inputs: a and NOT b have the same sign when a and b have different signs. Signed comparisons use V together with N.
  • N is the sign of the 32-bit result. On its own it is just bit 31. Combined with V, it tells you whether the true signed result is negative, and that is what a signed less-than needs. The branch BLT (signed less than) branches when N differs from V, and BGE (signed greater or equal) branches when N equals V.

The reason for N XOR V is that V records when the 32-bit sign bit cannot be trusted. Normally N tells you the sign. When the subtraction overflows, the sign bit is flipped, and V is 1 to say so. Then N is the wrong sign, and N XOR V gives the right answer again. A signed less-than is therefore correct even when the subtraction overflows.

C and V are not the same thing for signed numbers. In 8 bits, 0x7F + 1 is 127 + 1 = 128, which is out of the signed range but does not carry out of bit 7: C = 0, V = 1. In 8 bits, 0xFF + 1 as unsigned is 255 + 1 = 256, which carries out: C = 1, V = 0. Use C for unsigned values and V for signed values, never the wrong one.

Worked example: one subtraction, bit by bit

Take an 8-bit subtraction, 0x03 − 0x05, so that you can see every step. The working is a + NOT b + 1.

  1. Start: a = 0000 0011 (3) and b = 0000 0101 (5).
  2. Invert b: NOT b = 1111 1010. Every bit flipped.
  3. Add the two: 0000 0011 + 1111 1010 = 1111 1101. Check the carry out of bit 7: the sum fits in 8 bits, so there is no carry out.
  4. Add the carry-in of 1: 1111 1101 + 1 = 1111 1110. Still no carry out of bit 7.
  5. Read the result: 1111 1110, which is 0xFE. In 8-bit two's complement this is −2, which is 3 − 5. Correct.
  6. Set the flags: N = 1, because bit 7 of the result is 1. Z = 0, because the result is not zero. C = 0, because no carry came out, which means a borrow: 3 is less than 5 unsigned. V = 0, because 3 − 5 = −2 is in the signed range, so there is no overflow.

Now check the flags against the branches. A signed less-than, BLT, branches when N differs from V. Here N = 1 and V = 0 differ, so BLT branches, and the signed test 3 < 5 is true. An unsigned less-than, BLO, branches when C = 0. Here C = 0, so it also branches, and 3 < 5 is true unsigned. For these small values the two branches agree. The next example uses a pair of values where they disagree.

Worked example: the same bits, two answers

Compare −1 with 1. As 32-bit words, −1 is 0xFFFFFFFF, and 1 is 0x00000001. The compare computes 0xFFFFFFFF − 1.

  • Unsigned view: 0xFFFFFFFF is 4 294 967 295, the largest value, which is greater than 1. The subtract does not borrow, so C = 1. An unsigned less-than, BLO, reads C = 0 and does not branch. Unsigned, the first value is not less than the second.
  • Signed view: the result 0xFFFFFFFE has bit 31 set, so N = 1. The signed values are −1 − 1 = −2, which is in range, so V = 0. Signed less-than, BLT, branches when N differs from V. N = 1 and V = 0 differ, so it branches. Signed, −1 is less than 1.

The same comparison gives two correct answers, because it asks two different questions. The branch you choose is the question. If your C code uses int values, the compiler picks the signed branch, and if it uses unsigned values, it picks the unsigned one. Mixing them in one expression is where the bug comes from.

Hint for the signed rule

Look at the signs of the two operands and the result. If the operands have the same sign and the result has the other sign, V is 1. That is all V measures.

Common mistakes and how to spot them

Mistake 1: a signed comparison branches on C. This is the one the warning above describes, and it is the most common. Symptom: a test such as if (x < 1) works for small positive values and fails for negative ones. In the simulator, with the −1 example above, the unsigned branch BLO says "not less" while the signed branch BLT says "less". Fix: make the comparison signed when the values are signed. In C that means declaring the variables int or int32_t, not unsigned.

Mistake 2: the flags were overwritten between the compare and the branch. Symptom: the branch goes the wrong way after a line that seems unrelated. Put a flag-setting instruction, such as an ADDS to a counter, between the compare and the branch, and the branch reads the flags of that addition. In the simulator every arithmetic instruction sets the flags, so you can see this happen. Fix: compare immediately before the branch, and check the disassembly if you are unsure which instruction set the flags.

Mistake 3: reading C as a borrow flag with the wrong sense. A programmer who expects C = 1 to mean "borrowed" will invert every unsigned compare. Symptom: a loop runs one time too many or one time too few, or a range check accepts the boundary value that it should reject. Fix: remember that after a subtract, C = 1 means no borrow, which means the first operand was at least the second. Write the test as "C = 1 means greater or equal" and check it on a boundary value such as 5 and 5.

Mistake 4: testing for signed overflow in C after the add. A check such as if (a + b < a) is a common way to detect overflow. For signed int values, the overflow in the addition is undefined behaviour in C, so the compiler may remove the check when it optimises. Symptom: the check works in a debug build and fails in a release build. Fix: check the range before the add, using the signed limits, or use unsigned arithmetic for the wrap test.

In real projects

Firmware reviewers look for two things in comparisons: that the operand types match the branch, and that a compare is near the branch that uses it. A mismatch of signed and unsigned types is one of the most common findings in embedded code review, and most static analysis tools warn about it. When you debug a branch in GDB, the flags are visible in the program status register, and reading N, Z, C and V from it lets you check the branch decision without guessing.

The RP2040 uses Cortex-M0+ cores, which implement a smaller instruction set than the M3 in this lesson. Which instructions update the flags depends on the instruction and its encoding, not only on the core. Before you rely on a flag after an instruction you have not used before, read that instruction's entry in the Arm reference for your core.

In an interview, expect the question "how does a CPU decide whether a comparison is signed or unsigned, and what do the C and V flags mean?" A strong answer says the ALU always sets all four flags, and the branch decides which ones matter. It gives the no-borrow meaning of C after a subtract, the signed-overflow meaning of V, and the N XOR V rule for signed less-than.

Summary

  • The ALU is a combinational block. It computes add, subtract and logic on two operands, and it produces the result and four status flags.
  • A subtract is an add: a − b is a + NOT b + 1, using the same adder.
  • After a subtract, C = 1 means no borrow, which means the first operand was at least the second, unsigned.
  • V means the signed result is out of range. N is bit 31 of the result.
  • Unsigned branches read C. Signed branches read N and V, and BLT branches when N differs from V.
  • The same bits can give two correct answers. The branch you choose decides which question is asked.
  • Compare right before the branch, and make sure the types match the branch you expect.
You ran real add and subtract instructions on values that set each flag, and you can say which flag an unsigned compare and a signed compare each read. That is the step from an adder in gates to an if statement in firmware.

For unsigned values, C tells whether a carry or borrow crossed bit 31: after a subtract, C = 0 means a borrow, so the value was smaller.
