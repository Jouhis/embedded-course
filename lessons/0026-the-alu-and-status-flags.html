The ALU and status flags

Every if (a < b) in your C code becomes a subtraction in the CPU, followed by a branch that reads four flags. Two of those flags, C and V, answer different questions, and mixing them up is a classic source of wrong comparisons.

By the end of this lesson you can predict the N, Z, C and V flags after an add, a subtract or a compare, and say which flag a signed or an unsigned comparison uses, by running the same values in the CPU simulator.

The idea

The ALU (arithmetic logic unit) is the combinational block that computes add, subtract, AND, OR, EOR and shifts on two operands. You have built its adder in lesson 23. The result goes to a register, and the ALU also sets four status flags in the program status register (APSR, which the simulator shows as xPSR's top bits):

FlagNameSet when (add, or subtract as a + ~b + 1)
NNegativebit 31 of the result is 1
ZZerothe result is 0
CCarryadd: a carry came out of bit 31. Subtract: no borrow, so a ≥ b as unsigned numbers
VOverflowsigned overflow: two operands with the same sign gave a result with the other sign

The Arm architecture defines these flags for the M-profile cores in its architecture reference manual, and the Cortex-M3 programmer's guide describes the same program status register. Armv7-M Architecture Reference Manual is the definition; read the section on the APSR flags for the exact rules. Subtraction is an add. The ALU computes a + NOT b + 1, so the carry flag after a subtraction is the opposite of a borrow. That is why Arm's C flag is 1 when there is no borrow.

C and V answer different questions

The same bits can be read as unsigned or signed, so the ALU does not know which you meant. It sets both flags, and the branch you choose decides which one matters.

  • Unsigned: C says the result went out of the 32-bit range. For a compare, C = 1 means unsigned a ≥ b, so BHS (or BCS) is the unsigned greater-or-equal branch, and BLO (or BCC) is the unsigned less-than branch.
  • Signed: V says the sign of the result is wrong. A signed less-than uses N XOR V: BLT branches when N differs from V, and BGE when N equals V. Using N XOR V gives the right answer even when the subtraction overflows, because V records that the sign bit cannot be trusted.
C and V are not the same thing for signed numbers. 0x7F + 1 is 127 + 1 = 128, which is out of signed range but does not carry out of bit 31: C = 0, V = 1. 0xFF + 1 as unsigned is 255 + 1 = 256: C = 1, V = 0. Use C for unsigned values and V for signed values, never the wrong one.

Hint for the signed rule

Look at the signs of the two operands and the result. If the operands have the same sign and the result has the other sign, V is 1. That is all V measures.

The simulator's CMP is a subtract that keeps only the flags, which is exactly what a compiler emits before a branch. Lesson 29 shows the branch instructions that read these flags, and lesson 32 shows the same compare in the disassembly of compiled C.
You ran real add and subtract instructions on values that set each flag, and you can say which flag an unsigned compare and a signed compare each read. That is the step from an adder in gates to an if statement in firmware.

"How does a CPU decide whether a comparison is signed or unsigned, and what do the C and V flags mean?" Answer out loud in 60 seconds, then compare.

Model answer

The ALU always sets all four flags. The branch decides which ones matter. For unsigned values, C tells whether a carry or borrow crossed bit 31: after a subtract, C = 0 means a borrow, so the value was smaller. For signed values, V tells whether the sign of the result is wrong because the result left the signed range. A signed less-than branches on N XOR V, so it stays correct even when the subtraction overflows.
