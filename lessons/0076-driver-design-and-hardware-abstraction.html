Driver design and hardware abstraction layers

A good driver hides the chip from the code that uses it. Then the same logic runs on two boards, and on your PC, without changes. This lesson shows where to draw that line, and it critiques the HAL from Lab 4.

By the end of this lesson you can split an LED into an interface and two backends, choose one backend at link time, and name three weaknesses of a HAL header with the change that fixes each one.

The idea: layers and one direction

Firmware has layers. The top is the application, which says what the product does. Below it are services, which are reusable logic such as a filter, a menu or a protocol. Below those are drivers, which run one device, such as a sensor or a display. At the bottom is the HAL (hardware abstraction layer), or board support package, which talks to the chip and the board through the vendor SDK or the registers. The chip itself is the last layer. Elecia White's book is a practical overview of the profession, and its chapters on architecture cover this layering. Making Embedded Systems, 2nd ed. (O'Reilly)

The rule that makes the layers useful is the dependency direction. An upper layer includes the header of the layer below it. A lower layer never includes anything above it. So the application can be tested on a PC with a fake HAL, and the HAL can be replaced for a new board without touching the application.

A HAL is a seam, and the seam has two faces. For the application it is an interface: a header with function declarations and no pins. For the board it is an implementation: a file, or a set of files, that defines those functions with one SDK or one register map. Lab 4 used exactly this split (Lab 4), with hal.h on one side and a board file per board on the other.

Interface, handle and error return

A driver interface follows three habits. First, the header names what the driver does, not how. Second, the object the caller works on is an opaque handle: a pointer to a struct whose fields are hidden in the implementation file, so the caller cannot reach into it. Third, every call that can fail returns a status, so the caller can check it. The next code block is the LED interface you will build in the hands-on task. 

/* led.h: the whole interface. No pins, no SDK calls, no printf. */
#ifndef LED_H
#define LED_H
#include <stdbool.h>

void led_init(void);        /* call once, first; leaves the LED off */
void led_set(bool on);      /* true lights the LED */
bool led_get(void);         /* the level the driver last applied */
#endif

The LED interface has no handle, because there is only one LED in the program. A sensor with two instances needs one. The handle form is the same idea with a struct pointer as the first argument, and it is the pattern used by the HAL in the critique below. C has no classes, so "opaque" is a convention: the header forward-declares the struct, and the .c file defines it. Lab 4 meets the same idea in the STM32 HAL's UART_HandleTypeDef (see the HAL handle entry).

Keep the return type honest. A void init hides a failed bus. Lesson 84 covers how to report and recover from such failures in the field.

Choosing a backend at link time

The application needs an LED that works on the board, and a fake for a test or for a board that has no LED. Both backends define the same three functions. Only one of them is linked into the program. That choice is made by the build, not by the code, so the cost at run time is zero: the call goes straight to the chosen function. This is link-time substitution.

CMake makes the choice from a cache variable, and it compiles one source file into the program: 

set(LED_BACKEND "gpio" CACHE STRING "LED backend: gpio or fake")
if(LED_BACKEND STREQUAL "gpio")
    set(LED_SOURCE led_gpio.c)
elseif(LED_BACKEND STREQUAL "fake")
    set(LED_SOURCE led_fake.c)
endif()
add_executable(blink main.c ${LED_SOURCE})

If you add both files, the linker stops with multiple definition errors, because two functions share one name. That error is useful: it proves that the program has one backend, and it tells you which name to look for. The duplicate-symbol error is the linker enforcing the rule that each global name has one definition. Lesson 41 shows the link step that does this.

Ops tables: choosing at run time

The other way is an ops table: a struct of function pointers, plus a context pointer that the functions receive. The caller picks the table at run time, and each call goes through one pointer. Function pointers are lesson 49's callbacks; here they form the whole interface. 

typedef struct {
    void (*init)(void *ctx);
    void (*set)(void *ctx, bool on);
} led_ops_t;

typedef struct {
    const led_ops_t *ops;   /* which backend: gpio or fake */
    void *ctx;               /* the backend's own data, such as a pin number */
} led_t;

static inline void led_set(led_t *l, bool on) {
    l->ops->set(l->ctx, on);            /* one indirect call: a load and a branch */
}

The ops table can change the backend while the program runs, it can hold two LEDs with two different backends, and a test can pass in a fake without relinking. Its costs are one indirect call on every use, a context pointer for every object, and the table itself in flash. Most firmware uses link-time choice for a single board, and an ops table when one program must drive several devices of the same kind.

An ops table is not free polymorphism. If the caller can be given any table, the compiler cannot inline the call, and a missing field in the table is a null-pointer crash found on the device. Check every entry at init, or fill every entry in a static const table so the compiler checks the count.

Critique: the Lab 4 HAL header

Lab 4's hal.h is a good first HAL. It has one interface, two board files, and logical pin levels that hide wiring. Read it again with a reviewer's eye, and five weaknesses show up.

  1. The I2C result is a bare integer. hal_i2c_write() returns 0 or -1. A sensor that does not answer (a NACK, from the bus) and a bus that times out look the same to the caller, although the fix for each is different. The address is the plain 7-bit value, which the name addr7 records. Lab 4's hint explains that ST's HAL takes the address shifted left by one, so the unit in the name is what stops a mix-up.
  2. hal_init() returns void. A failed clock or bus start is invisible to the caller, so the application starts anyway.
  3. Unknown pins fail silently. hal_gpio_read() returns 0 for a pin it does not know, and a typo in the pin enum gives the same answer as a released button.
  4. Output and input pins share one enum. hal_gpio_write(HAL_PIN_BTN_A, 1) compiles. Split the enum into output and input pins so the compiler rejects the call.
  5. The state is global. Every function uses one board, with no context. Two I2C buses, or a host test with a fake board next to the real one, cannot coexist.

The improved header

The fix for all five items is an opaque handle with a status enum. The board file defines struct hal, and the application never sees its fields. The header needs stdint.h, stdbool.h and stddef.h, and a hal_pin_t enum like Lab 4's, which the excerpt leaves out. Lab 4's files are not changed by this lesson. 

typedef enum {
    HAL_OK = 0,
    HAL_ERR_ARG,        /* a null pointer or a zero-length transfer */
    HAL_ERR_PIN,        /* a pin the board does not have */
    HAL_ERR_BUS,        /* a NACK or an arbitration loss */
    HAL_ERR_TIMEOUT
} hal_status_t;

typedef struct hal hal_t;          /* opaque: the board file defines it */

typedef struct {
    uint8_t  i2c_port;
    uint32_t i2c_timeout_us;     /* units in the name, so no one guesses */
} hal_config_t;

hal_status_t hal_init(hal_t **out, const hal_config_t *cfg);
hal_status_t hal_gpio_read(hal_t *h, hal_pin_t pin, bool *pressed);
hal_status_t hal_i2c_write(hal_t *h, uint8_t addr7, const uint8_t *data, size_t len);

Three things changed. The handle is the first argument, which gives each board or test its own instance, and hal_init() hands the handle back. The status is returned, and the value goes out through a pointer, so the caller can check both. The config struct has named fields, with the units in the names, so a call site does not need a comment to be read. The board file can keep its handle in static storage, so nothing is allocated on the heap (lesson 78 covers why that matters). Item 4 asks for two enums, one for output pins and one for input pins. The header above keeps one enum to stay short; splitting it is the exercise in the critique list.

Why the seam matters for a beginner

Before this lesson, every program you have written in the course touched the chip directly. A blink calls gpio_put() from main(), and that is fine for one LED. It stops being fine when a second person needs the same LED on a different board, or when the logic has to run on a PC where no pin exists. The code that decides when the LED should be on is the same code in both cases. Only the code that decides how it is driven differs. A layer boundary separates those two kinds of code.

Earlier lessons put an LED on a pin with the SDK, and lesson 52 read a button the same way. Those lessons were about the hardware. This one is about the code that sits between the hardware and the product, which is where most firmware is actually written.

Concepts, one at a time

Header and source file

A C compiler works on one translation unit at a time: one .c file, with every header it includes pasted in. The result is an object file. The linker then joins the object files and resolves every name that one file uses and another defines. A symbol is that name, such as led_set, as the linker sees it. The header is a promise. It says which symbols exist and what they take, and every file that includes it is checked against that promise. The source file is the place where the promise is kept.

This split has a consequence that the rest of the lesson uses. If main.c includes only led.h, then main.c compiles without knowing which pin is used. The compiler never needs the pin number. Only the linker needs to know which definition of led_set to use.

A call, at the level of the CPU

When main.c calls led_set(true), the CPU core does what it does for any call. It saves the return address in the link register (LR), jumps to the function, and returns when the function finishes. Lesson 33 covers the stack frame that goes with the call. What matters here is the jump. A direct call names the target address in the instruction, so the linker can fill it in once. A call through a function pointer loads the address from memory first, then jumps to whatever it holds. That is one more memory access, and the compiler cannot see the target, so it cannot inline the body. Keep that difference in mind when you read the two designs below.

Opaque handle

An opaque handle is a pointer to a struct whose fields the caller cannot read, because the struct is defined only in the source file. The header says typedef struct hal hal_t; and nothing more. The caller can hold a hal_t * and pass it back to the driver, but it cannot write h->count, because the compiler does not know that field exists. The benefit is that the state can change without every caller being rebuilt, and that a caller cannot corrupt the state by accident.

Status return

A function that can fail returns a status code, and the real result, if any, goes out through a pointer argument. The caller writes if (hal_init(&h, &cfg) != HAL_OK). A void function cannot report anything, so the only way to learn of a failure is a side effect such as a log line, which the application may not read. Lesson 84 covers what to do after a failure.

A worked example with real numbers

Take the ops-table version of the LED and count what one call costs on a Cortex-M0+, the core of the RP2040. A pointer on this core is 32 bits, which is 4 bytes. The table led_ops_t holds two function pointers, so it takes 8 bytes. The handle led_t holds one pointer to the table and one void * context pointer, so it takes another 8 bytes. A table filled with static const lives in flash, and the handle can sit in RAM.

Now trace led_set(&led, true) one step at a time. First, the caller loads led->ops, which is one memory read. Second, it loads the set pointer from the table, which is a second read. Third, it loads led->ctx, a third read, and passes it along with true. Fourth, it jumps through the pointer. Inside the backend, the function turns the context into a pin number and calls gpio_put(). In this count, one logical call costs three loads and one indirect jump before any hardware is touched.

Compare that with the link-time version. The caller jumps directly to led_set, which is the GPIO function, so there is one jump and no table read. The difference is a handful of cycles per call. For a blink that runs twice a second it is nothing. For a driver called in a sampling loop of thousands of calls per second, it is worth knowing. Both numbers are estimates from the instruction sequence, not measurements; the lesson's point is the count of memory reads and jumps, which you can check in the disassembly of your own build.

The code, line by line

The ops-table version has four lines that carry the idea. Here is what each one does.

  1. typedef struct { void (*init)(void *ctx); void (*set)(void *ctx, bool on); } led_ops_t; declares a table of two function pointers. Each entry names a signature, not a function. Any backend whose functions match these two signatures can fill the table.
  2. const led_ops_t *ops; inside led_t stores a pointer to a table. The const means the driver may not write through it, so one table in flash can serve many LEDs.
  3. void *ctx; stores the backend's private data, such as a pin number boxed as a pointer. The caller never reads it. It is passed back to each function so that one backend can serve several instances.
  4. l->ops->set(l->ctx, on); is the call itself. It reads the table pointer, reads the set entry, and calls it with the context. If set is NULL, the jump goes to address zero, which is the first bug in the next section.

The link-time version has no line that does this work. The build file picks led_gpio.c or led_fake.c, and the linker binds every call in main.c to that one file. That is why the choice costs nothing at run time, and why it cannot be changed without rebuilding.

Common mistakes and how to spot them

Four mistakes come up again and again in this lesson's code. Each has a symptom you can see, and a fix.

  1. The interface header includes a chip header. A developer adds #include "hardware/gpio.h" to led.h so that a type is available. The symptom is that the PC test build fails with No such file or directory for hardware/gpio.h, because the PC has no Pico SDK. The fix is to move the include into the backend, and to pass only plain types through the interface.
  2. Both backends are added to the build. The symptom is a link error, multiple definition of led_init, which is the exercise in step 5 of the hands-on task. The fix is to add only the file that the cache variable selects, as the if block in CMakeLists.txt does. Do not list both files in add_executable().
  3. The cache variable is edited but the build does not change. You change the default from "gpio" to "fake", rebuild, and the monitor still prints nothing from the fake. The reason is that CMake keeps the cache value from the first configure in build/CMakeCache.txt, and a new default in the file does not overwrite it. The fix is the Clean build task, which deletes build/ so CMake reads the file again.
  4. A table entry is missing. A test passes a table with set left out, and the call jumps to address zero. The symptom on the device is a fault, which the lesson on faults (lesson 39) describes, at the first LED call; on a board without a fault handler the program may simply stop or restart. The fix is to fill every entry with a designated initialiser (.set = led_gpio_set), so the name is visible in review, and to check each pointer for NULL in init. Enable -Wmissing-field-initializers (part of -Wextra) so the compiler warns about a field left out of a brace initialiser.

In real projects

Vendor code uses this layering everywhere. The STM32 HAL that Lab 4 uses is one layer of it, and ST's low-layer drivers are a thinner one under it. Zephyr takes the ops-table idea further: each peripheral class has a driver API struct of function pointers, and the kernel looks up the struct for each device. The GPIO class is defined as struct gpio_driver_api in include/zephyr/drivers/gpio.h of the Zephyr tree, and each GPIO driver fills one in with DEVICE_API. A code review of a driver in a product team checks four things: that the header names no chip, that every failure has a status, that a fake exists for each interface, and that no call bypasses the handle. The interview question "how would you test firmware on a PC" is answered by this seam.

Summary

  • Layers call downward only. The application never includes a chip header, and the HAL never includes the application.
  • A header is a promise checked against each source file. The linker binds each name to one definition.
  • Choose a backend at link time when the board is fixed. Choose it at run time with an ops table when one program drives several devices of one kind.
  • An ops table costs one indirect jump and a few loads per call, and a missing entry jumps to a bad address.
  • An opaque handle hides the state and lets two instances coexist. A status return reports failure to the caller.
  • Lab 4's HAL is a good first draft. Its weaknesses are a bare int result, a void init, silent unknown pins, a shared pin enum and global state.
  • A fake behind the same interface lets the application be tested on a PC.

"How would you structure firmware for a board with a sensor, a display and a radio, so the logic can be tested on a PC?" Answer out loud in 60 seconds, then compare.

Model answer

I would split it into layers: an application that holds the product logic, services for the reusable parts, one driver per device, and a board layer that is the only code that knows the pins and the SDK. Each driver exposes an interface with an opaque handle and status returns. The board layer is one set of files per board, and the PC build links a fake board that records calls. I test the application and the services on the PC with those fakes, and I test the board layer on the target. Dependencies only point downward, so a new board changes one layer.
