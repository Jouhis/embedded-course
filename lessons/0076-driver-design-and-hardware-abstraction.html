Driver design and hardware abstraction layers

Interfaces that separate product logic from the chip

By the end of this lesson you can split an LED into an interface and two backends, choose one backend at link time, and name three weaknesses of a HAL header with the change that fixes each one.

The boundary between product logic and hardware

Every program in the course so far has touched the chip directly, a blink calling gpio_put() from main(), which is fine for one LED but stops being fine when a second person needs the same LED on a different board or the logic must run on a PC with no pin at all. The code deciding when the LED should be on is the same in both cases, and only the code deciding how it is driven differs, so a layer boundary separates the two kinds of code.

Earlier lessons put an LED on a pin with the SDK, and lesson 52 read a button the same way, both concerned with the hardware. This lesson concerns the code between the hardware and the product, which is where most firmware is written.

Header files, source files and the linker

A C compiler works on one translation unit at a time, a single .c file with every header it includes pasted in, producing an object file, and the linker then joins the object files and resolves every name that one file uses and another defines. A symbol is such a name, like led_set, as the linker sees it, and the header declares which symbols exist and what they take, every file that includes it being checked against the declaration, while the source file provides the definitions.

The rest of the lesson relies on a consequence of this split: if main.c includes only led.h, it compiles without knowing which pin is used, the compiler never needing the pin number, and only the linker needs to know which definition of led_set to use.

Direct calls and calls through a pointer

When main.c calls led_set(true), the CPU core does what it does for any call, saving the return address in the link register (LR), jumping to the function and returning when it finishes, with the stack frame that lesson 33 describes. What matters here is the jump. A direct call names the target address in the instruction, so the linker fills it in once, whereas a call through a function pointer first loads the address from memory and then jumps to whatever it holds, which costs one more memory access and hides the target from the compiler, so it cannot inline the body, a difference that matters for the two designs below.

Opaque handles and status returns

An opaque handle is a pointer to a struct whose fields the caller cannot read, because the struct is defined only in the source file while the header says no more than typedef struct hal hal_t;. The caller can hold a hal_t * and pass it back to the driver, but cannot write h->count, because the compiler does not know the field exists, so the state can change without every caller being rebuilt and no caller can corrupt it by accident.

A function that can fail returns a status code and passes any real result out through a pointer argument, so the caller writes if (hal_init(&h, &cfg) != HAL_OK). A void function cannot report anything, leaving a side effect such as a log line, which the application may not read, as the only sign of a failure, and lesson 84 covers what to do after one.

Firmware layers and the dependency direction

Firmware has layers: the application at the top, saying what the product does, services below it, reusable logic such as a filter, a menu or a protocol, then drivers, each running one device such as a sensor or a display, and at the bottom the HAL (hardware abstraction layer), or board support package, which talks to the chip and the board through the vendor SDK or the registers, above the chip itself. Elecia White's book is a practical overview of the profession, and its chapters on architecture cover this layering. Making Embedded Systems, 2nd ed. (O'Reilly)

The rule that makes the layers useful is the dependency direction, an upper layer including the header of the layer below and a lower layer never including anything above it, so the application can be tested on a PC with a fake HAL and the HAL replaced for a new board without touching the application.

A HAL is a seam with two faces, an interface for the application, a header of function declarations without pins, and an implementation for the board, one or more files defining those functions with one SDK or one register map. Lab 4 used exactly this split (Lab 4), with hal.h on one side and a board file per board on the other.

A driver interface resembles a wall socket: any appliance with the right plug works in any socket without caring whether the power behind the wall comes from a hydro plant or a wind farm, the header being the socket shape, led_gpio.c and led_fake.c two power plants behind it and the application the appliance. The comparison breaks on timing, however, because every socket delivers the same mains, whereas two backends behind one header can differ in speed and in how they fail, which the interface must state.

Interface, handle and error return

A driver interface follows three habits: the header names what the driver does rather than how, the object the caller works on is an opaque handle whose fields are hidden in the implementation file, and every call that can fail returns a status for the caller to check. The next code block is the LED interface built in the hands-on task. 

/* led.h: the whole interface. No pins, no SDK calls, no printf. */
#ifndef LED_H
#define LED_H
#include <stdbool.h>

void led_init(void);        /* call once, first; leaves the LED off */
void led_set(bool on);      /* true lights the LED */
bool led_get(void);         /* the level the driver last applied */
#endif

The LED interface has no handle, because the program has only one LED, whereas a sensor with two instances needs one, the handle form being the same idea with a struct pointer as the first argument, the pattern of the HAL in the critique below. C has no classes, so "opaque" is a convention: the header forward-declares the struct, and the .c file defines it. Lab 4 meets the same idea in the STM32 HAL's UART_HandleTypeDef (see the HAL handle entry).

Keep the return type honest. A void init hides a failed bus. Lesson 84 covers how to report and recover from such failures in the field.

Choosing a backend at link time

The application needs an LED that works on the board and a fake for a test or a board without an LED, both backends defining the same three functions while only one is linked into the program. The build makes that choice, so it costs nothing at run time, each call going straight to the chosen function, which is link-time substitution, and CMake makes the choice from a cache variable, compiling one source file into the program. 

set(LED_BACKEND "gpio" CACHE STRING "LED backend: gpio or fake")
if(LED_BACKEND STREQUAL "gpio")
    set(LED_SOURCE led_gpio.c)
elseif(LED_BACKEND STREQUAL "fake")
    set(LED_SOURCE led_fake.c)
endif()
add_executable(blink main.c ${LED_SOURCE})

Adding both files makes the linker stop with multiple definition errors, because two functions share one name, an error that is useful because it proves the program has one backend and names the function to look for. The duplicate-symbol error is the linker enforcing the rule that each global name has one definition. Lesson 41 shows the link step that does this.

Ops tables for run-time choice

The alternative is an ops table, a struct of function pointers plus a context pointer that the functions receive, the caller picking the table at run time and each call going through one pointer, so the callbacks of lesson 49 here form the whole interface. 

typedef struct {
    void (*init)(void *ctx);
    void (*set)(void *ctx, bool on);
} led_ops_t;

typedef struct {
    const led_ops_t *ops;   /* which backend: gpio or fake */
    void *ctx;               /* the backend's own data, such as a pin number */
} led_t;

static inline void led_set(led_t *l, bool on) {
    l->ops->set(l->ctx, on);            /* one indirect call: a load and a branch */
}

An ops table can change the backend while the program runs, hold two LEDs with two different backends and accept a fake from a test without relinking, at the cost of one indirect call per use, a context pointer per object and the table itself in flash. Most firmware uses link-time choice for a single board and an ops table when one program must drive several devices of the same kind.

An ops table is not free polymorphism. If the caller can be given any table, the compiler cannot inline the call, and a missing field in the table is a null-pointer crash found on the device. Check every entry at init, or fill every entry in a static const table so the compiler checks the count.

A critique of the Lab 4 HAL header

Lab 4's hal.h is a good first HAL, with one interface, two board files and logical pin levels that hide the wiring, but a reviewer's reading finds five weaknesses.

  1. The I2C result is a bare integer. hal_i2c_write() returns 0 or -1, so a sensor that does not answer (a NACK from the bus) and a bus that times out look the same to the caller, although each needs a different fix. The address is the plain 7-bit value, as the name addr7 records, and since Lab 4's hint explains that ST's HAL takes the address shifted left by one, the unit in the name is what prevents a mix-up.
  2. hal_init() returns void. A failed clock or bus start is invisible to the caller, so the application starts anyway.
  3. Unknown pins fail silently. hal_gpio_read() returns 0 for a pin it does not know, so a typo in the pin enum gives the same answer as a released button.
  4. Output and input pins share one enum. hal_gpio_write(HAL_PIN_BTN_A, 1) compiles, whereas split enums for output and input pins would make the compiler reject the call.
  5. The state is global. Every function uses one board without context, so two I2C buses, or a host test with a fake board beside the real one, cannot coexist.

An improved HAL header

The fix for all five items is an opaque handle with a status enum, the board file defining struct hal and the application never seeing its fields. The header needs stdint.h, stdbool.h and stddef.h and a hal_pin_t enum like Lab 4's, which the excerpt leaves out, and this lesson does not change Lab 4's files. 

typedef enum {
    HAL_OK = 0,
    HAL_ERR_ARG,        /* a null pointer or a zero-length transfer */
    HAL_ERR_PIN,        /* a pin the board does not have */
    HAL_ERR_BUS,        /* a NACK or an arbitration loss */
    HAL_ERR_TIMEOUT
} hal_status_t;

typedef struct hal hal_t;          /* opaque: the board file defines it */

typedef struct {
    uint8_t  i2c_port;
    uint32_t i2c_timeout_us;     /* units in the name, so no one guesses */
} hal_config_t;

hal_status_t hal_init(hal_t **out, const hal_config_t *cfg);
hal_status_t hal_gpio_read(hal_t *h, hal_pin_t pin, bool *pressed);
hal_status_t hal_i2c_write(hal_t *h, uint8_t addr7, const uint8_t *data, size_t len);

Three things changed. The handle is the first argument, giving each board or test its own instance, with hal_init() handing it back, the status is returned while the value goes out through a pointer, so the caller can check both, and the config struct has named fields carrying their units, so a call site reads without a comment. The board file can keep its handle in static storage, so nothing is allocated on the heap, which lesson 78 explains the importance of. Item 4 asks for two enums, one for output pins and one for input pins. The header above keeps one enum to stay short; splitting it is the exercise in the critique list.

Worked example: the cost of one ops-table call

We count what one call of the ops-table LED costs on a Cortex-M0+, the core of the RP2040. Before tracing it, predict how many memory loads happen before the backend's code runs.

  1. Size the structures. A pointer on this core is 32 bits, 4 bytes, so the table led_ops_t, holding two function pointers, takes 8 bytes, and the handle led_t, holding a pointer to the table and a void * context, takes another 8, the static const table living in flash and the handle in RAM.
  2. Load the table pointer. led_set(&led, true) first loads led->ops, one memory read.
  3. Load the function pointer. It then loads the set pointer from the table, a second read.
  4. Load the context. It loads led->ctx, a third read, and passes it along with true.
  5. Jump. It jumps through the pointer, and inside the backend the function turns the context into a pin number and calls gpio_put(), so one logical call costs three loads and one indirect jump before any hardware is touched.

The link-time version jumps directly to led_set, the GPIO function, with one jump and no table read, so the difference is a handful of cycles per call, nothing for a blink running twice a second but worth knowing for a driver called thousands of times a second in a sampling loop. Both numbers are estimates from the instruction sequence rather than measurements, the point being the count of memory reads and jumps, which can be checked in the disassembly of your own build.

The ops-table code line by line

The ops-table version has four lines that carry the idea.

  1. typedef struct { void (*init)(void *ctx); void (*set)(void *ctx, bool on); } led_ops_t; declares a table of two function pointers, each entry naming a signature rather than a function, so any backend whose functions match the two signatures can fill the table.
  2. const led_ops_t *ops; inside led_t stores a pointer to a table, the const forbidding the driver to write through it, so one table in flash can serve many LEDs.
  3. void *ctx; stores the backend's private data, such as a pin number boxed as a pointer, which the caller never reads and which is passed back to each function, so that one backend can serve several instances.
  4. l->ops->set(l->ctx, on); is the call itself, reading the table pointer and the set entry and calling it with the context, and if set is NULL, the jump goes to address zero, the last mistake listed below.

The link-time version has no line doing this work, because the build file picks led_gpio.c or led_fake.c and the linker binds every call in main.c to that one file, which is why the choice costs nothing at run time and cannot change without a rebuild.

Try it in Wokwi

The project is projects/0076-led-driver-interface, whose starter has the interface and a main.c that blinks the LED three times and reports LED DRIVER OK only if the driver reads back the level it was given, while the two backends are empty and marked TODO(learner).

  1. Open projects/0076-led-driver-interface/starter in VS Code (File → Open Folder), build with Ctrl+Shift+B and start the simulator with F1 → Wokwi: Start Simulator. The monitor prints LED DRIVER FAIL, because both backends do nothing.
  2. In led_gpio.c, fill in the three TODO(learner) functions for pin GP25, initialising it as an output, driving it with gpio_put() and reading it back with gpio_get_out_level(), then build and run, and the LED blinks while the monitor prints LED DRIVER OK.
  3. In led_fake.c, keep the state in s_on and print LED fake: on or LED fake: off on each change, then change the default "gpio" in CMakeLists.txt to "fake" and run Ctrl+Shift+B with the Clean build task, which is needed because the cache value is read only on a fresh configure.
  4. The fake works when the monitor prints LED fake: init, then six on and off lines, then LED DRIVER OK, the LED not blinking in this mode because the fake has no pin.
  5. Optionally, add led_fake.c to the sources while the GPIO backend is selected and read the linker error, which names the function defined twice, the point of link-time choice.
Hint for the GPIO backend

The three functions are gpio_init(), gpio_set_dir() with GPIO_OUT and gpio_put(), which takes 0 or 1, so write on ? 1 : 0, and the starter's comments name each function.

Hint if the monitor still prints LED DRIVER FAIL

led_get() must report what led_set() applied, so a stub that always returns false fails the check after the first led_set(true), and the output level should be read rather than a constant returned.

The reference solution is in projects/0076-led-driver-interface/solution, so try first and compare afterwards.

Common mistakes and how to spot them

Four mistakes come up again and again in this lesson's code, each with a visible symptom and a fix.

A chip header in the interface header

The PC test build fails with No such file or directory for hardware/gpio.h, because a developer added #include "hardware/gpio.h" to led.h to get a type, and the PC has no Pico SDK. Move the include into the backend and pass only plain types through the interface.

Both backends added to the build

The link fails with multiple definition of led_init, the exercise of step 5 of the hands-on task, because both files were compiled. Add only the file the cache variable selects, as the if block in CMakeLists.txt does, and never list both in add_executable().

A cache variable edited without effect

After the default changes from "gpio" to "fake" and a rebuild, the monitor still shows nothing from the fake, because CMake keeps the value from the first configure in build/CMakeCache.txt and a new default in the file does not overwrite it. Run the Clean build task, which deletes build/ so that CMake reads the file again.

A missing ops-table entry

The device faults at the first LED call, as described in the lesson on faults (lesson 39), or on a board without a fault handler simply stops or restarts, because a test passed a table with set left out and the call jumped to address zero. Fill every entry with a designated initialiser (.set = led_gpio_set), so the name is visible in review, check each pointer for NULL in init, and enable -Wmissing-field-initializers (part of -Wextra) so that the compiler warns about a field left out of a brace initialiser.

Driver layering in vendor code and Zephyr

Vendor code uses this layering everywhere, the STM32 HAL of Lab 4 being one layer of it and ST's low-layer drivers a thinner one beneath. Zephyr takes the ops-table idea further, giving each peripheral class a driver API struct of function pointers that the kernel looks up for each device, the GPIO class being defined as struct gpio_driver_api in include/zephyr/drivers/gpio.h of the Zephyr tree, with each GPIO driver filling one in with DEVICE_API. A product team's review of a driver checks that the header names no chip, that every failure has a status, that a fake exists for each interface and that no call bypasses the handle, and this seam is also how firmware gets tested on a PC.

Summary

  • Layers call downward only, so the application never includes a chip header and the HAL never includes the application.
  • A header is a promise checked against each source file, and the linker binds each name to one definition.
  • A backend is chosen at link time when the board is fixed, and at run time with an ops table when one program drives several devices of one kind.
  • An ops table costs one indirect jump and a few loads per call, and a missing entry jumps to a bad address.
  • An opaque handle hides the state and lets two instances coexist, while a status return reports failure to the caller.
  • Lab 4's HAL is a good first draft whose weaknesses are a bare int result, a void init, silent unknown pins, a shared pin enum and global state.
  • A fake behind the same interface lets the application be tested on a PC.
