Driver design and hardware abstraction layers

A good driver hides the chip from the code that uses it. Then the same logic runs on two boards, and on your PC, without changes. This lesson shows where to draw that line, and it critiques the HAL from Lab 4.

By the end of this lesson you can split an LED into an interface and two backends, choose one backend at link time, and name three weaknesses of a HAL header with the change that fixes each one.

The idea: layers and one direction

Firmware has layers. The top is the application, which says what the product does. Below it are services, which are reusable logic such as a filter, a menu or a protocol. Below those are drivers, which run one device, such as a sensor or a display. At the bottom is the HAL (hardware abstraction layer), or board support package, which talks to the chip and the board through the vendor SDK or the registers. The chip itself is the last layer. Elecia White's book is a practical overview of the profession, and its chapters on architecture cover this layering. Making Embedded Systems, 2nd ed. (O'Reilly)

The rule that makes the layers useful is the dependency direction. An upper layer includes the header of the layer below it. A lower layer never includes anything above it. So the application can be tested on a PC with a fake HAL, and the HAL can be replaced for a new board without touching the application.

A HAL is a seam, and the seam has two faces. For the application it is an interface: a header with function declarations and no pins. For the board it is an implementation: a file, or a set of files, that defines those functions with one SDK or one register map. Lab 4 used exactly this split (Lab 4), with hal.h on one side and a board file per board on the other.

Interface, handle and error return

A driver interface follows three habits. First, the header names what the driver does, not how. Second, the object the caller works on is an opaque handle: a pointer to a struct whose fields are hidden in the implementation file, so the caller cannot reach into it. Third, every call that can fail returns a status, so the caller can check it. The next code block is the LED interface you will build in the hands-on task. 

/* led.h: the whole interface. No pins, no SDK calls, no printf. */
#ifndef LED_H
#define LED_H
#include <stdbool.h>

void led_init(void);        /* call once, first; leaves the LED off */
void led_set(bool on);      /* true lights the LED */
bool led_get(void);         /* the level the driver last applied */
#endif

The LED interface has no handle, because there is only one LED in the program. A sensor with two instances needs one. The handle form is the same idea with a struct pointer as the first argument, and it is the pattern used by the HAL in the critique below. C has no classes, so "opaque" is a convention: the header forward-declares the struct, and the .c file defines it. Lab 4 meets the same idea in the STM32 HAL's UART_HandleTypeDef (see the HAL handle entry).

Keep the return type honest. A void init hides a failed bus. Lesson 84 covers how to report and recover from such failures in the field.

Choosing a backend at link time

The application needs an LED that works on the board, and a fake for a test or for a board that has no LED. Both backends define the same three functions. Only one of them is linked into the program. That choice is made by the build, not by the code, so the cost at run time is zero: the call goes straight to the chosen function. This is link-time substitution.

CMake makes the choice from a cache variable, and it compiles one source file into the program: 

set(LED_BACKEND "gpio" CACHE STRING "LED backend: gpio or fake")
if(LED_BACKEND STREQUAL "gpio")
    set(LED_SOURCE led_gpio.c)
elseif(LED_BACKEND STREQUAL "fake")
    set(LED_SOURCE led_fake.c)
endif()
add_executable(blink main.c ${LED_SOURCE})

If you add both files, the linker stops with multiple definition errors, because two functions share one name. That error is useful: it proves that the program has one backend, and it tells you which name to look for. The duplicate-symbol error is the linker enforcing the rule that each global name has one definition. Lesson 41 shows the link step that does this.

Ops tables: choosing at run time

The other way is an ops table: a struct of function pointers, plus a context pointer that the functions receive. The caller picks the table at run time, and each call goes through one pointer. Function pointers are lesson 49's callbacks; here they form the whole interface. 

typedef struct {
    void (*init)(void *ctx);
    void (*set)(void *ctx, bool on);
} led_ops_t;

typedef struct {
    const led_ops_t *ops;   /* which backend: gpio or fake */
    void *ctx;               /* the backend's own data, such as a pin number */
} led_t;

static inline void led_set(led_t *l, bool on) {
    l->ops->set(l->ctx, on);            /* one indirect call: a load and a branch */
}

The ops table can change the backend while the program runs, it can hold two LEDs with two different backends, and a test can pass in a fake without relinking. Its costs are one indirect call on every use, a context pointer for every object, and the table itself in flash. Most firmware uses link-time choice for a single board, and an ops table when one program must drive several devices of the same kind.

An ops table is not free polymorphism. If the caller can be given any table, the compiler cannot inline the call, and a missing field in the table is a null-pointer crash found on the device. Check every entry at init, or fill every entry in a static const table so the compiler checks the count.

Critique: the Lab 4 HAL header

Lab 4's hal.h is a good first HAL. It has one interface, two board files, and logical pin levels that hide wiring. Read it again with a reviewer's eye, and five weaknesses show up.

  1. The address unit is not written consistently. The header calls the I2C address addr7, a 7-bit value, and hal_pico.c passes it to the Pico SDK, which takes the 7-bit address (Pico SDK API documentation). Lab 4's quiz and hint say the HAL takes an 8-bit value such as 0x78. The code is correct and that text is not. A header comment that is wrong is a bug.
  2. hal_init() returns void. A failed clock or bus start is invisible to the caller, so the application starts anyway.
  3. Unknown pins fail silently. hal_gpio_read() returns 0 for a pin it does not know, and a typo in the pin enum gives the same answer as a released button.
  4. Output and input pins share one enum. hal_gpio_write(HAL_PIN_BTN_A, 1) compiles. Split the enum into output and input pins so the compiler rejects the call.
  5. The state is global. Every function uses one board, with no context. Two I2C buses, or a host test with a fake board next to the real one, cannot coexist.

The improved header

The fix for items 2 to 5 is an opaque handle with a status enum. The board file defines struct hal, and the application never sees its fields. This header compiles with -Wall -Wextra -Werror against a board stub, in this course's check. Lab 4's files are not changed by this lesson. 

typedef enum {
    HAL_OK = 0,
    HAL_ERR_ARG,        /* a null pointer or a zero-length transfer */
    HAL_ERR_PIN,        /* a pin the board does not have */
    HAL_ERR_BUS,        /* a NACK or an arbitration loss */
    HAL_ERR_TIMEOUT
} hal_status_t;

typedef struct hal hal_t;          /* opaque: the board file defines it */

typedef struct {
    uint8_t  i2c_port;
    uint32_t i2c_timeout_us;     /* units in the name, so no one guesses */
} hal_config_t;

hal_status_t hal_init(hal_t **out, const hal_config_t *cfg);
hal_status_t hal_gpio_read(hal_t *h, hal_pin_t pin, bool *pressed);
hal_status_t hal_i2c_write(hal_t *h, uint8_t addr7, const uint8_t *data, size_t len);

Three things changed. The handle is the first argument, which gives each board or test its own instance, and hal_init() hands the handle back. The status is returned, and the value goes out through a pointer, so the caller can check both. The config struct has named fields, with the units in the names, so a call site does not need a comment to be read. The board file can keep its handle in static storage, so nothing is allocated on the heap (lesson 78 covers why that matters). Item 4 asks for two enums, one for output pins and one for input pins. The header above keeps one enum to stay short; splitting it is the exercise in the critique list.

"How would you structure firmware for a board with a sensor, a display and a radio, so the logic can be tested on a PC?" Answer out loud in 60 seconds, then compare.

Model answer

I would split it into layers: an application that holds the product logic, services for the reusable parts, one driver per device, and a board layer that is the only code that knows the pins and the SDK. Each driver exposes an interface with an opaque handle and status returns. The board layer is one set of files per board, and the PC build links a fake board that records calls. I test the application and the services on the PC with those fakes, and I test the board layer on the target. Dependencies only point downward, so a new board changes one layer.
