Layered and event-driven architecture; active objects

A super loop works until a second feature needs a delay. Then every feature waits for every other one. An active object gives each part its own state and its own queue of events, so a part only runs when something happens to it.

By the end of this lesson you can split a super loop into two active objects, each with its own event queue and handler, connect them with a published event, and explain why a handler needs no lock.

The idea: events instead of waiting

In a super loop, each feature is a function call in order, and a slow call delays all the others (lesson 55 showed the deadline fix). An event-driven design turns each happening into a message: a press, a tick, a sensor value ready. The code that sees the happening posts an event to a queue, and the code that owns the feature takes the event out later and reacts to it. A queue is the same ring buffer as lesson 70, with one writer for the head and one for the tail. The only new part is what goes into it: events, not bytes.

An active object (AO) is a feature with three parts: its state, one event queue, and one handler, the function that the framework calls for each event. Nothing else touches the state. The handler is a state machine (lesson 56): it looks at the state and the event, changes the state, and returns. Miro Samek's active-object model is the usual reference (Samek, Modern Embedded Systems Programming). The QP/C reference describes it as "lightweight implementation of the asynchronous, event-driven, and non-blocking Active Object" model (QP/C Reference Manual, overview).

Run to completion, and why no lock

The dispatcher takes one event and calls the handler. The handler runs to its end and returns. Only then does the dispatcher take the next event. That rule is run to completion: no event can interrupt a handler that is running, so a handler sees its own state as it was when the event began.

On one core, with the posts and the dispatch in the main loop, no two handlers run at once. So the queue needs no lock, and neither does the state. The head of the queue is written only by the poster, and the tail only by the dispatcher (the same single-writer rule as lesson 70). An interrupt that posts would break this, and then the queue needs the protection that lesson 57 covers. Full RTOS queues and mutexes (Part 7) are for the case where threads truly run in parallel. The active-object model in this lesson needs neither, because the super loop is the only thread.

Publish and subscribe

Some events have several listeners. The button announces a press, and it should not know who cares. In publish and subscribe, each AO declares which events it wants, and the publisher sends the event to every AO that subscribed. The publisher's code does not change when a new listener is added. A subscription here is a bit mask, one bit for each signal. The button publishes SIG_PRESS, and only the AOs with that bit set receive it.

A published event copies into every subscriber's queue. If one queue is full, that event is lost for that subscriber only. The framework counts such losses, and a count that keeps rising means a handler is too slow or a queue is too small.

Layers around the events

The framework is a service, the two AOs are application features, and the button code is a driver (lesson 76). The dependencies point one way: the blinker depends on the event SIG_PRESS, and it never includes the button's pin code. The button depends on the framework and on nothing about the LED. You can change either AO without touching the other.

Why a super loop stops scaling

Lesson 55 gave the super loop a deadline. A deadline makes a single slow call survivable, but it does not fix the structure. Suppose the product grows a button, a blinking LED, a temperature sensor that takes 20 ms per read, and a serial report. In a super loop each of these is a call in one sequence. The LED must be updated every 500 ms, so the sensor read sits between two LED updates and delays them. Every new feature adds a wait to every other feature, and the timing of one part depends on the code of all the others. That is the coupling that the rest of this lesson removes.

The fix is not a faster loop. It is to give each feature its own state, so that it can be paused, reordered or replaced without touching the rest. Lesson 56 showed one state machine. Here there are several, and they must talk to each other without calling each other directly.

The concepts, one at a time

Event

An event is a small record that says something happened. In this framework it holds one number, the signal, which names the kind of happening: SIG_TICK for the 10 ms clock, SIG_PRESS for a confirmed button press. The event does not carry the code that handles it. That separation is the point. The button code knows that a press happened; it does not know what a press means.

The code declares the signals as an enum, which gives them consecutive integer values. SIG_TICK is 0 and SIG_PRESS is 1. Those integers are used as bit positions later, so the enum order matters.

Queue and ring buffer

A queue holds events until the object that owns it is ready to take them. This framework uses a ring buffer: an array with two indices, head and tail, and a rule that the indices wrap back to 0 at the end of the array. The queue is empty when head equals tail. A new event is written at head, then head moves on. An event is taken from tail, then tail moves on.

The size is a power of two, so the wrap is a single AND instruction instead of a comparison. AO_QUEUE_SIZE is 8, and the index mask is 8 − 1 = 7, binary 0b111. Lesson 70 uses the same trick for the UART receive buffer.

Why is one slot always empty? If the queue used all 8 slots, a full queue and an empty queue would look the same, because both would have head equal to tail. Leaving one slot empty gives the two states different indices. The cost is that a queue of size 8 holds 7 events.

Worked example: a queue, step by step

Start with an empty button queue, head = 0 and tail = 0. Three presses arrive before the dispatcher runs. Here is each step. Post one: the next head is (0 + 1) & 7 = 1. That is not equal to the tail 0, so the event goes into slot 0, and head becomes 1. Post two: the next head is 2, the event goes into slot 1, and head becomes 2. Post three: slot 2, and head becomes 3. Now the dispatcher runs. It takes slot 0 and moves tail to 1. It takes slot 1 and moves tail to 2. The queue is empty again when tail reaches 3.

Now suppose the queue has seven events, so head is 7 and tail is 0. The next post computes (7 + 1) & 7 = 0, which equals the tail, so the code counts a drop and returns false. The eighth event is lost. Every event before it is kept, in order.

Active object

An active object bundles three things: its state, its queue, and its handler. The handler is the function the dispatcher calls with each event. The struct in ao.h shows this directly: a handler pointer, a subscription mask, the queue array and the two indices. The first member of the feature's own struct is the ao_t, so that a pointer to the framework object can be cast back to the feature's struct. That is the same cast that lesson 49's callbacks use for their context.

Subscription mask

A subscription says which signals an object wants. The framework stores it as a 32-bit mask, where bit n means signal n. The macro AO_SUB(sig) expands to (1u << (sig)), which is a one in bit position sig. Here is the arithmetic for this program. AO_SUB(SIG_TICK) is 1 << 0, which is 0b01. AO_SUB(SIG_PRESS) is 1 << 1, which is 0b10. The button subscribes to the tick only, so its mask is 0b01. The blinker subscribes to both, so its mask is 0b11. When the button publishes SIG_PRESS, the framework tests 0b01 & 0b10 for the button, which is 0, so the button gets nothing. It tests 0b11 & 0b10 for the blinker, which is 2, so the blinker gets the event.

Dispatcher

The dispatcher is the loop that takes events out of queues and calls handlers. Here, ao_dispatch_all() walks the registry of objects, and for each one it takes events until the queue is empty. The main loop is therefore very small. It makes a tick every 10 ms and calls the dispatcher on every pass. All the feature logic lives in handlers.

A worked example: one press, from the pin to the LED

Follow one button press with the numbers in the code. The button is wired to GP14 with an internal pull-up, so pressed reads 0. The button handler counts agreeing samples in count, and it confirms a press when count reaches DEBOUNCE_TICKS, which is 3. Ticks come every 10 ms.

  1. t = 0 ms. The user presses the button. The pin goes low, but the first tick has not come yet.
  2. t = 10 ms. The main loop publishes SIG_TICK. Both queues receive it. The dispatcher runs the button handler, which sees pressed, and count goes from 0 to 1.
  3. t = 20 ms and t = 30 ms. Two more ticks see pressed. count reaches 3. The handler sets stable and publishes SIG_PRESS. The publish looks at each registered object. Only the blinker has bit 1 in its mask, so only its queue receives the press.
  4. Same pass, t = 30 ms. The dispatcher reaches the blinker. It takes its queued tick, which adds one to ticks, then the press. The press flips blinking to true, resets ticks to 0, and prints blink on.
  5. Later ticks. Each tick adds one to ticks. When ticks reaches HALF_PERIOD_TICKS, which is 50, the blinker flips the LED and resets the count. The first flip comes 50 ticks after the press, which is 500 ms after it.

Notice what did not happen. The button handler never named the LED. The blinker handler never read the pin. Each object changed only its own state, and the only shared thing was the event.

The code, line by line

The core of the framework is ao_post(), which is about ten lines. Its first line computes the next head, (uint8_t)((me->head + 1u) & (AO_QUEUE_SIZE - 1u)). The cast keeps the value in a uint8_t, which is the width of the index. The AND wraps it, as in the worked example. The second line, if (next == me->tail), is the full check, and the counter s_dropped records the loss. Only then is the event copied with me->queue[me->head] = e; and the head moved. The order matters: the copy happens before the head moves, so the dispatcher never sees a slot that is only half written. Because the dispatcher reads head only to compare it with tail, this order is enough on one core that runs the posts and the dispatch in one loop.

The dispatch loop, ao_dispatch_all(), has the nested while (take(...)). take() returns false when the queue is empty, so the loop drains one object's queue before it moves to the next object. Each call to the handler is a full run to completion, and no other handler starts in the middle of it.

Common mistakes and how to spot them

  1. A feature is never started. The object is declared and its handler written, but ao_start() is not called. The symptom is silence: the press handler never runs, the monitor prints nothing for the press, and no error appears, because a queue that no one registered is simply never dispatched. The fix is to call ao_start() in each init function, and to check that the startup line appears in the monitor.
  2. A subscription is missing. The blinker is started but subscribes only to the tick. The symptom is the same as above, with the tick still working. The fix is to print the mask at start-up or to read the AO_SUB line once more against the signals it needs. ao_dropped() does not help here, because a missing subscriber is not a full queue.
  3. A handler blocks. Someone adds sleep_ms(500) to the blinker to make the blink simpler. The symptom is that presses are answered late, sometimes by half a second, because the dispatcher cannot run the button while the blinker sleeps. The fix is to use the tick count, which is what the solution does, and to keep handlers short.
  4. The dropped count keeps rising. Under load the monitor shows presses that do not change the blink. A call to ao_dropped() returns a growing number. The cause is a full queue: a handler is too slow, or a burst of events is larger than 7. The fix is to make the handler faster, to raise AO_QUEUE_SIZE to the next power of two, or to lower the rate of the producer.
  5. An interrupt posts to a queue. A student moves the button read into an interrupt so that presses are not missed. The framework is not safe for that. An interrupt can arrive while the dispatcher is updating tail, and the two writes race. The symptom is a rare duplicate or lost event that never reproduces in the simulator. The fix is to keep the posts in the main loop, or to protect the queue with a critical section, which lesson 57 covers.

In real projects

The active-object model is the basis of the QP/C framework, which the state-machine.com reference describes as a lightweight implementation of this design. Miro Samek's course walks through the same ideas with code, so you can see what the compiler makes of each handler. Zephyr offers the same building blocks as kernel services: a message queue, k_msgq, carries events between threads, and its timeout forms let a thread wait for work instead of polling. A reviewer of an event-driven design asks three questions: where the events are posted, who subscribes to each one, and what happens when a queue fills. In an interview, the answer that a senior engineer gives is the one that names the queue sizes and the drop policy, not only the pattern.

Summary

  • An event is a record with a signal number. The sender does not know the handler.
  • A ring buffer with head and tail holds events. With size 8 it holds 7, because one slot stays empty to tell full from empty.
  • An active object is state, a queue and a handler. Only its handler touches its state.
  • A subscription is a bit mask, and AO_SUB(n) sets bit n. A published event goes only to masks with that bit set.
  • The dispatcher runs one handler to completion before it takes the next event, so one core needs no lock.
  • A press goes from a debounced pin, through a published event, to a state change in another object, with no direct call between them.
  • Watch three things in review: missing ao_start() or subscriptions, handlers that block, and a rising dropped count.

Try it in Wokwi

The project is projects/0077-active-objects-button-blinker. The framework, ao.c and ao.h, is complete in both folders. Together they are about a hundred lines with their comments (58 lines in ao.c and 41 in ao.h), so you can read the whole queue and dispatcher. The starter main.c is a working super loop: a press toggles the blink, and the LED flips every 500 ms. Your job is to move its logic into the two AO files and reduce main.c to a tick and a dispatch.

  1. Open projects/0077-active-objects-button-blinker/starter in VS Code (File → Open Folder). Build with Ctrl+Shift+B, then start the simulator with F1 → Wokwi: Start Simulator. Click the button in the diagram, and the monitor prints blink on, then blink off on the next click.
  2. Your task, part 1: in button_ao.c, write a handler that reacts to SIG_TICK, debounces the pin with the integrator from lesson 52, and calls ao_publish() with SIG_PRESS once per confirmed press. In button_ao_init(), set up the pin, and register the handler with ao_start().
  3. Your task, part 2: in blinker_ao.c, write a handler that toggles the blink on SIG_PRESS, flips the LED every 50 ticks while blinking, and prints blink on or blink off. Subscribe it to both signals in blinker_ao_init() with AO_SUB(SIG_TICK) | AO_SUB(SIG_PRESS).
  4. Your task, part 3: in main.c, delete the super loop body. Keep the 10 ms tick, publish SIG_TICK with ao_publish(), and call ao_dispatch_all() on every pass. Print AO OK once after the two init calls.
  5. You will know it works when the monitor prints AO OK at the start, and each click gives one blink on or blink off line, with the LED behaving as before.
Hint for the handler's switch

Each handler gets the AO as ao_t *. Cast it to your own struct, such as button_t *, because the first member is the ao_t. The solution's button_handler() and blinker_handler() show the cast and the switch.

Hint if nothing happens after the refactor

Check that each AO was registered with ao_start(), and that the blinker subscribed to SIG_PRESS. A missing subscription drops the press without an error. ao_dropped() counts the full queues; the framework does not count missing subscribers.

"A super loop works, but every new feature makes the loop slower to respond. How would you restructure it?" Answer out loud in 60 seconds, then compare.

Model answer

I would make each feature an object with its own state and its own event queue, and the main loop would only generate ticks and dispatch events. Hardware code would post events, not call the features directly. A handler runs to completion, so the state needs no lock on one core, and a slow feature only delays its own queue. Events that several features need go out by publish and subscribe, so the publisher does not change when a listener is added. I would watch the dropped-event count to find a queue that is too small or a handler that is too slow.
