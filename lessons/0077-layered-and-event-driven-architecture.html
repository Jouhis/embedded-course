Layered and event-driven architecture; active objects

A super loop works until a second feature needs a delay. Then every feature waits for every other one. An active object gives each part its own state and its own queue of events, so a part only runs when something happens to it.

By the end of this lesson you can split a super loop into two active objects, each with its own event queue and handler, connect them with a published event, and explain why a handler needs no lock.

The idea: events instead of waiting

In a super loop, each feature is a function call in order, and a slow call delays all the others (lesson 55 showed the deadline fix). An event-driven design turns each happening into a message: a press, a tick, a sensor value ready. The code that sees the happening posts an event to a queue, and the code that owns the feature takes the event out later and reacts to it. A queue is the same ring buffer as lesson 70, with one writer for the head and one for the tail. The only new part is what goes into it: events, not bytes.

An active object (AO) is a feature with three parts: its state, one event queue, and one handler, the function that the framework calls for each event. Nothing else touches the state. The handler is a state machine (lesson 56): it looks at the state and the event, changes the state, and returns. Miro Samek's active-object model is the usual reference (Samek, Modern Embedded Systems Programming). The QP/C reference describes it as "lightweight implementation of the asynchronous, event-driven, and non-blocking Active Object" model (QP/C Reference Manual, overview).

Run to completion, and why no lock

The dispatcher takes one event and calls the handler. The handler runs to its end and returns. Only then does the dispatcher take the next event. That rule is run to completion: no event can interrupt a handler that is running, so a handler sees its own state as it was when the event began.

On one core, with the posts and the dispatch in the main loop, no two handlers run at once. So the queue needs no lock, and neither does the state. The head of the queue is written only by the poster, and the tail only by the dispatcher (the same single-writer rule as lesson 70). An interrupt that posts would break this, and then the queue needs the protection that lesson 57 covers. Full RTOS queues and mutexes (Part 7) are for the case where threads truly run in parallel. The active-object model in this lesson needs neither, because the super loop is the only thread.

Publish and subscribe

Some events have several listeners. The button announces a press, and it should not know who cares. In publish and subscribe, each AO declares which events it wants, and the publisher sends the event to every AO that subscribed. The publisher's code does not change when a new listener is added. A subscription here is a bit mask, one bit for each signal. The button publishes SIG_PRESS, and only the AOs with that bit set receive it.

A published event copies into every subscriber's queue. If one queue is full, that event is lost for that subscriber only. The framework counts such losses, and a count that keeps rising means a handler is too slow or a queue is too small.

Layers around the events

The framework is a service, the two AOs are application features, and the button code is a driver (lesson 76). The dependencies point one way: the blinker depends on the event SIG_PRESS, and it never includes the button's pin code. The button depends on the framework and on nothing about the LED. You can change either AO without touching the other.

Try it in Wokwi

The project is projects/0077-active-objects-button-blinker. The framework, ao.c and ao.h, is complete in both folders, with about eighty lines of code, so you can read the whole queue and dispatcher. The starter main.c is a working super loop: a press toggles the blink, and the LED flips every 500 ms. Your job is to move its logic into the two AO files and reduce main.c to a tick and a dispatch.

  1. Open projects/0077-active-objects-button-blinker/starter in VS Code (File → Open Folder). Build with Ctrl+Shift+B, then start the simulator with F1 → Wokwi: Start Simulator. Click the button in the diagram, and the monitor prints blink on, then blink off on the next click.
  2. Your task, part 1: in button_ao.c, write a handler that reacts to SIG_TICK, debounces the pin with the integrator from lesson 52, and calls ao_publish() with SIG_PRESS once per confirmed press. In button_ao_init(), set up the pin, and register the handler with ao_start().
  3. Your task, part 2: in blinker_ao.c, write a handler that toggles the blink on SIG_PRESS, flips the LED every 50 ticks while blinking, and prints blink on or blink off. Subscribe it to both signals in blinker_ao_init() with AO_SUB(SIG_TICK) | AO_SUB(SIG_PRESS).
  4. Your task, part 3: in main.c, delete the super loop body. Keep the 10 ms tick, publish SIG_TICK with ao_publish(), and call ao_dispatch_all() on every pass. Print AO OK once after the two init calls.
  5. You will know it works when the monitor prints AO OK at the start, and each click gives one blink on or blink off line, with the LED behaving as before.
Hint for the handler's switch

Each handler gets the AO as ao_t *. Cast it to your own struct, such as button_t *, because the first member is the ao_t. The solution's button_handler() and blinker_handler() show the cast and the switch.

Hint if nothing happens after the refactor

Check that each AO was registered with ao_start(), and that the blinker subscribed to SIG_PRESS. A missing subscription drops the press without an error. ao_dropped() counts the full queues; the framework does not count missing subscribers.

"A super loop works, but every new feature makes the loop slower to respond. How would you restructure it?" Answer out loud in 60 seconds, then compare.

Model answer

I would make each feature an object with its own state and its own event queue, and the main loop would only generate ticks and dispatch events. Hardware code would post events, not call the features directly. A handler runs to completion, so the state needs no lock on one core, and a slow feature only delays its own queue. Events that several features need go out by publish and subscribe, so the publisher does not change when a listener is added. I would watch the dropped-event count to find a queue that is too small or a handler that is too slow.
