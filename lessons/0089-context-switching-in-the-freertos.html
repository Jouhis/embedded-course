Context switching in the FreeRTOS port

The PendSV switch handler in real code

By the end of this lesson you can read xPortPendSVHandler line by line, map each of its steps to the simulator's handler from lesson 88, and explain why PendSV runs at the lowest priority and what goes wrong at a higher one.

From the simulator to the real port

Lesson 87 set up the tick and said that the switch happens in PendSV, and lesson 88 explained what a switch does to the registers and the stacks with a two-task program and its own handler. This lesson reads the real FreeRTOS port in the same order, the tick that starts a switch, the first frame the kernel builds for a task, the first start and the switch itself.

Two earlier lessons set up the priority rules, lesson 72 defining the priority numbers, a lower number being more urgent on the NVIC and an interrupt of equal priority not preempting another, and lesson 73 covering SysTick, the timer that produces the tick in this port. The lowest-priority placement of PendSV follows from those rules, as the second half of this lesson works out.

Line numbers in this lesson refer to the kernel's own port file, third_party/FreeRTOS-Kernel/portable/GCC/ARM_CM3/port.c (FreeRTOS V11.2.0), and the port header beside it, portmacro.h, both compiled by the projects, and the code excerpts are copied from them without changes.

The tick requests a switch and PendSV performs it

On every tick the port calls xTaskIncrementTick() from the SysTick handler, which adds one to the tick count, wakes any task whose delay has ended and returns whether a switch is needed, the port's SysTick handler looking like this. 

void xPortSysTickHandler( void )
{
    /* The SysTick runs at the lowest interrupt priority, so when this interrupt
     * executes all interrupts must be unmasked.  There is therefore no need to
     * save and then restore the interrupt mask value as its value is already
     * known. */
    portDISABLE_INTERRUPTS();
    traceISR_ENTER();
    {
        /* Increment the RTOS tick. */
        if( xTaskIncrementTick() != pdFALSE )
        {
            traceISR_EXIT_TO_SCHEDULER();

            /* A context switch is required.  Context switching is performed in
             * the PendSV interrupt.  Pend the PendSV interrupt. */
            portNVIC_INT_CTRL_REG = portNVIC_PENDSVSET_BIT;
        }
        else
        {
            traceISR_EXIT();
        }
    }
    portENABLE_INTERRUPTS();
}

The handler brackets its work with portDISABLE_INTERRUPTS() and portENABLE_INTERRUPTS(), and the comment above the function explains that SysTick runs at the lowest interrupt priority, so all interrupts are already unmasked when it starts, which spares the port from saving and restoring the old mask, letting it simply enable interrupts again at the end.

When xTaskIncrementTick() reports a switch, the handler writes portNVIC_PENDSVSET_BIT to the interrupt control and state register, setting PendSV pending and changing nothing else, so the tick handler touches no stack or task but only records the request.

The switch runs later, and since PendSV sits at the lowest priority, it cannot interrupt any other handler, so a pending PendSV is taken at once when the tick handler returns with nothing else active, and waits if another interrupt is active until it finishes.

The first task frame in pxPortInitialiseStack

Lesson 88 built the first frames by hand with stores into the simulator's RAM, whereas the port does the same job in pxPortInitialiseStack, which the kernel calls when a task is created, a short function whose layout is the one the handler expects and which therefore rewards a slow reading. 

StackType_t * pxPortInitialiseStack( StackType_t * pxTopOfStack,
                                     TaskFunction_t pxCode,
                                     void * pvParameters )
{
    /* Simulate the stack frame as it would be created by a context switch
     * interrupt. */
    pxTopOfStack--;                                                      /* Offset added to account for the way the MCU uses the stack on entry/exit of interrupts. */
    *pxTopOfStack = portINITIAL_XPSR;                                    /* xPSR */
    pxTopOfStack--;
    *pxTopOfStack = ( ( StackType_t ) pxCode ) & portSTART_ADDRESS_MASK; /* PC */
    pxTopOfStack--;
    *pxTopOfStack = ( StackType_t ) portTASK_RETURN_ADDRESS;             /* LR */
    pxTopOfStack -= 5;                                                   /* R12, R3, R2 and R1. */
    *pxTopOfStack = ( StackType_t ) pvParameters;                        /* R0 */
    pxTopOfStack -= 8;                                                   /* R11, R10, R9, R8, R7, R6, R5 and R4. */

    return pxTopOfStack;
}

The function's first line, line 188, moves the pointer down one word, the port's comment explaining that this offset accounts for the way the MCU uses the stack on exception entry and exit, and line 189 stores portINITIAL_XPSR, which is 0x01000000 (defined at line 78), the same value lesson 88 wrote into the xPSR slot.

Lines 190 and 191 store the PC, the task's entry function masked with portSTART_ADDRESS_MASK, which is 0xfffffffe (line 90), clearing bit 0 of the address so that the stored PC is even, while the Thumb state itself comes from the xPSR bit that line 189 sets. Lines 192 and 193 store the LR, the value portTASK_RETURN_ADDRESS, which in this port is prvTaskExitError (line 110), so a task that ever returns from its function goes there, where it asserts and stops, as lesson 87 said a task must never return.

Line 194 moves the pointer down five words, past the slots for R12, R3, R2 and R1, to the R0 slot, where line 195 stores the parameter, the first argument of the task function, so the task receives it in R0, as the calling convention of lesson 33 requires. Line 196 moves down eight more words for R11 to R4 without writing anything into them, and the returned pointer, the lowest of those eight slots, is the value the kernel stores as the task's stack top.

That returned pointer is the saved block of lesson 88, though the port leaves R4 to R11 unwritten, so they start with whatever the stack memory held, while the simulator writes zeros into its block. This difference leaves the structure unchanged, since in both versions the handler loads the stack top, pops the block and then reaches the frame by moving up past it.

Starting the first task through SVC

The first task does not come from a switch, because no running task exists to save, so prvPortStartFirstTask prepares the stacks and raises an SVC and vPortSVCHandler starts the first task, both short functions whose source follows. 

static void prvPortStartFirstTask( void )
{
    __asm volatile (
        " ldr r0, =0xE000ED08   \n" /* Use the NVIC offset register to locate the stack. */
        " ldr r0, [r0]          \n"
        " ldr r0, [r0]          \n"
        " msr msp, r0           \n" /* Set the msp back to the start of the stack. */
        " cpsie i               \n" /* Globally enable interrupts. */
        " cpsie f               \n"
        " dsb                   \n"
        " isb                   \n"
        " svc 0                 \n" /* System call to start first task. */
        " nop                   \n"
        " .ltorg                \n"
        );
}

The SVC handler comes next, from the same file.

void vPortSVCHandler( void )
{
    __asm volatile (
        "   ldr r3, =pxCurrentTCB           \n" /* Restore the context. */
        "   ldr r1, [r3]                    \n" /* Get the pxCurrentTCB address. */
        "   ldr r0, [r1]                    \n" /* The first item in pxCurrentTCB is the task top of stack. */
        "   ldmia r0!, {r4-r11}             \n" /* Pop the registers that are not automatically saved on exception entry and the critical nesting count. */
        "   msr psp, r0                     \n" /* Restore the task stack pointer. */
        "   isb                             \n"
        "   mov r0, #0                      \n"
        "   msr basepri, r0                 \n"
        "   orr r14, #0xd                   \n"
        "   bx r14                          \n"
        "                                   \n"
        "   .ltorg                          \n"
        );
}

Line 250 loads into R0 the address 0xE000ED08, the vector table offset register, which the port's comment calls the NVIC offset register, and line 251 reads it, giving the base of the vector table. Line 252 reads the table's first word, the initial stack pointer, which line 253 writes to MSP, resetting the main stack to its top, lines 254 and 255 enable interrupts with cpsie i and cpsie f, and svc 0 on line 258 raises the call that starts the first task.

vPortSVCHandler saves nothing, the kernel having already chosen the first task, since this handler does not call vTaskSwitchContext(), so it reads pxCurrentTCB, loads the stack top and pops R4 to R11 with ldmia (line 234), the ! in ldmia r0! writing the moved address back into R0 so that R0 ends at the frame. Line 235 writes PSP, lines 237 and 238 clear BASEPRI to zero, and line 239 ORs 0xD into LR, turning the 0xFFFFFFF9 left by the SVC entry into 0xFFFFFFFD, after which the last line, bx r14, performs the return to thread mode on the PSP.

The simulator's switch handler line by line

The simulator's switch handler from lesson 88 is listed here in full, so that each group can be read against the port, following the three jobs of lesson 88: a short first group reads the running task, the next saves it, the one after stores the save and chooses the next task, and the last restores the next task and returns.

LDR R1, =0x20000000 and LDR R2, [R1] load the address of the slot and then its value, the task that was running, and CMP R2, #2 and BEQ first test for the very first switch, where there is nothing to save, a test on the saved state rather than a special case in the hardware.

MRS R0, PSP reads the running task's PSP into R0, the address of its hardware frame, and SUB R0, R0, #32 moves R0 down eight words to the room below the frame, where the next eight STR lines store R4 to R11 at offsets 0 to 28 from R0. This is the save, the step the hardware does not do for these registers, and the store order matches the load order in restore, so the same offsets find the same values.

LDR R3, =0x20000004 chooses the slot for task A, with CMP and BEQ moving to the slot for task B when CUR is 1, and STR R0, [R3] stores the new stack top into that slot, saving the task's state for next time, the stack top being the only value the kernel needs to find everything else in the block.

The next lines choose the next task, CMP R2, #0 and the pickb branch setting R2 to the other task's number and STR R2, [R1] writing it back to CUR, the simulator's version of vTaskSwitchContext(), which picks the next task and changes the current task pointer, in C in the real kernel and in a few instructions here.

restore loads the next task's saved block address and pops R4 to R11 with eight LDR lines, and ADD R0, R0, #32 moves R0 up to the next task's frame, because the saved block lies below it. MSR PSP, R0 sets the PSP to that frame for the exception return to pop, LDR LR, =0xFFFFFFFD sets the return value to thread mode on the PSP and BX LR performs the return, the branch to an EXC_RETURN value being what makes the core unstack the frame and the last thing the handler does.

The port's handler appears below as it stands in the file, C with inline assembly in strings, so the instructions are in quotes. 

void xPortPendSVHandler( void )
{
    /* This is a naked function. */

    __asm volatile
    (
        "   mrs r0, psp                         \n"
        "   isb                                 \n"
        "                                       \n"
        "   ldr r3, =pxCurrentTCB               \n" /* Get the location of the current TCB. */
        "   ldr r2, [r3]                        \n"
        "                                       \n"
        "   stmdb r0!, {r4-r11}                 \n" /* Save the remaining registers. */
        "   str r0, [r2]                        \n" /* Save the new top of stack into the first member of the TCB. */
        "                                       \n"
        "   stmdb sp!, {r3, r14}                \n"
        "   mov r0, %0                          \n"
        "   msr basepri, r0                     \n"
        "   bl vTaskSwitchContext               \n"
        "   mov r0, #0                          \n"
        "   msr basepri, r0                     \n"
        "   ldmia sp!, {r3, r14}                \n"
        "                                       \n" /* Restore the context, including the critical nesting count. */
        "   ldr r1, [r3]                        \n"
        "   ldr r0, [r1]                        \n" /* The first item in pxCurrentTCB is the task top of stack. */
        "   ldmia r0!, {r4-r11}                 \n" /* Pop the registers. */
        "   msr psp, r0                         \n"
        "   isb                                 \n"
        "   bx r14                              \n"
        "                                       \n"
        "   .ltorg                              \n"
        ::"i" ( configMAX_SYSCALL_INTERRUPT_PRIORITY )
    );
}

mrs r0, psp reads the running task's PSP (line 461), followed by an isb, an instruction synchronisation barrier that makes the core finish the earlier instructions before using the new value, and ldr r3, =pxCurrentTCB loads the address of the variable pointing to the current task's control block, with ldr r2, [r3] loading the block's address (lines 464 and 465).

stmdb r0!, {r4-r11} is the save (line 467), writing R4 to R11 into the eight words directly below the frame, with R4 at the lowest address, the ! leaving R0 pointing at that lowest word, and str r0, [r2] stores that address into the first member of the control block (line 468), which the comment on line 479 describes as the task's top of stack, the role the simulator's PSP slot plays.

stmdb sp!, {r3, r14} saves R3 and LR on the main stack (line 470), LR holding the EXC_RETURN value from the entry, both registers being needed again after the C call, which may change them. Lines 471 and 472 load the mask value the port passes in as the %0 operand, configMAX_SYSCALL_INTERRUPT_PRIORITY, and write it to BASEPRI, which masks interrupts whose priority number is equal to or greater than the value written, so the interrupts allowed to call FreeRTOS functions are held off during the call while those more urgent than the limit still run, the port's comment at lines 167 to 170 naming this value as the limit for interrupts that call the kernel.

bl vTaskSwitchContext calls the C function that chooses the next task and updates pxCurrentTCB (line 473), lines 474 and 475 clear BASEPRI again and line 476 restores R3 and LR from the main stack. Lines 478 and 479 then load the new task's stack top through the updated pointer, which is why those loads must come after the call, line 480 pops the new task's R4 to R11, line 481 writes PSP and line 483, bx r14, returns to the new task on its PSP.

The prototype at line 123 carries __attribute__( ( naked ) ), the comment at line 457 confirming that the function is naked, so it has no compiler prologue or epilogue, the first instruction of its body is the mrs and the port controls every register from there, and the mistakes section shows what goes wrong when the attribute is missing.

Why PendSV runs at the lowest priority

The port sets the priorities of the three system handlers in xPortStartScheduler, in short code whose comment states the design in one sentence. 

    /* Make PendSV and SysTick the lowest priority interrupts, and make SVCall
     * the highest priority. */
    portNVIC_SHPR3_REG |= portNVIC_PENDSV_PRI;
    portNVIC_SHPR3_REG |= portNVIC_SYSTICK_PRI;
    portNVIC_SHPR2_REG = 0;

The system handler priority registers hold one byte per system handler, SHPR2 at 0xE000ED1C holding the byte for SVCall and SHPR3 at 0xE000ED20 the byte for PendSV in bits 23 to 16 and the byte for SysTick in bits 31 to 24, the positions the port's shifts by 16 and 24 on lines 56 and 57 use, and the Cortex-M3 Technical Reference Manual gives the register map in the source box below.

The value written for PendSV and SysTick comes from portMIN_INTERRUPT_PRIORITY, which is 255 (line 55), and on a device implementing only the top four priority bits the lowest level is 15, as lesson 72 explains for the STM32F1, so a written value of 0xFF selects that lowest level, its top four bits all being set. SVCall gets 0, the most urgent level, because line 392 clears the whole SHPR2 register.

Lower numbers being more urgent (lesson 72), PendSV and SysTick are the least urgent handlers in the port and SVCall the most urgent, and since two sources at the same priority do not preempt each other, a rule stated in lesson 72, a tick cannot interrupt PendSV once it has started, SysTick having the same level.

PendSV resembles a caretaker who rearranges the meeting room only when every meeting is over, anyone being able to leave a note asking for the change, which is setting PendSV pending, while the caretaker waits until no interrupt handler is running, so a task switch never happens in the middle of a handler's work. The comparison breaks for urgent visitors, though, because a more urgent interrupt can still walk in during the rearranging, which a caretaker's locked door would prevent.

The lowest level has a second effect, because an exception return to a task is valid only when no other handler is still active, and PendSV, unable to preempt any handler, can start only when none is active, which is exactly the condition for a valid return to a task. A more urgent interrupt can still preempt PendSV, but it returns to PendSV before PendSV returns to the task, whereas a PendSV set higher than a running interrupt could preempt that interrupt and return to a task while the interrupt was still active, an invalid return that ends in a fault or a corrupted return.

Interrupts more urgent than PendSV can still arrive while it runs, since the lowest level does not block them and the core takes them at their own priority, and the BASEPRI lines protect only the call to vTaskSwitchContext(), because only the list operations inside it must not be interrupted by an interrupt that calls the kernel, while the save and the restore run with interrupts unmasked.

The simulator has no BASEPRI and no nesting, so a real interrupt can arrive in the middle of the switch on silicon in a way this simulator cannot show. Treat the simulator as a model of the order of operations, not of the timing.

Finally, lesson 72 describes tail-chaining, the core taking a pending PendSV as soon as another handler returns, without an extra save and restore of the frame, so in the common case the switch follows the tick work with very little delay.

  1. Task A runs in thread mode on its own stack. The scheduler is not running code at all; it waits for a tick.
  2. SysTick fires. xTaskIncrementTick() wakes task B, whose delay has ended, and says a switch is needed. The handler does not switch: it only sets the PendSV pending bit in ICSR and returns.
  3. A UART byte arrives. Its interrupt is more urgent than PendSV, so it runs first, and PendSV keeps waiting. A switch now would return to a task while the UART handler was still active, which is not a valid exception return.
  4. No other handler is active, so PendSV finally runs, tail-chained after the UART return. It saves R4 to R11 of task A on A's stack, asks vTaskSwitchContext() for the next task, and restores B's registers from B's stack.
  5. PendSV returns, and the exception return pops B's hardware frame: task B runs. PendSV sits at the lowest priority exactly so that it runs only when every other handler is finished.

Common mistakes and how to spot them

A switch handler written in plain C

The switch works in a short test and fails under load, when the compiler makes different choices, because a developer wrote it as an ordinary C function with asm inside and without the naked attribute, leaving the compiler free to add code around the assembly that changes registers the assembly expects to hold particular values. Use the naked attribute, as the port declares it on line 123, so that the assembly is the whole function.

PendSV above the interrupt it runs inside

A rare fault or corrupted return appears, looking like random data, because a developer set PendSV to a priority more urgent than a peripheral interrupt, so the switch can start while that interrupt is active and the return to a task is invalid. Give PendSV the lowest priority, as the port does at line 390.

The new stack top loaded before the switch

The same task runs again and the switch appears to do nothing, because a developer tidying the handler moved the two loads of the next task's stack top above the call to vTaskSwitchContext(), so they read pxCurrentTCB before the call changed it and still point at the task that just yielded. Keep the loads after the call, as lines 478 and 479 do.

The BASEPRI lines removed

Intermittent corruption appears under load, which the simulator cannot show, having no BASEPRI, because a developer removed lines 471 to 475 as noise, the handler having worked in a quick test without them, leaving the list operations inside vTaskSwitchContext() open to an interrupt that calls the kernel, so the ready list can change in the middle of an update. Restore the masking around the call with the same mask value the port passes.

Testing and reviewing a new port

Teams porting FreeRTOS to a new core test the handler with a two-task program like the one in lesson 88 before trusting it, and a code review of a port checks the split of saved registers, the priority of the switch exception, the EXC_RETURN values and the order of the loads around the call.

Summary

  • The tick handler calls xTaskIncrementTick() and, when a switch is needed, only pends PendSV rather than switching tasks itself.
  • pxPortInitialiseStack builds a task's first frame with xPSR at 0x01000000, the entry point as PC and the task return address in LR.
  • The first task starts through vPortSVCHandler, which pops the frame without saving anything, since no task is leaving.
  • xPortPendSVHandler saves R4 to R11 below the frame, stores the stack top in the control block, calls vTaskSwitchContext() with BASEPRI set and loads the new task's stack top after the call.
  • PendSV and SysTick sit at priority 255, the lowest level, and SVCall at 0, the highest, because a switch at a higher level could return to a task while another handler is still active.
  • Tail-chaining lets PendSV run as soon as the last other handler returns, which keeps the switch prompt.
