Context switching in the FreeRTOS port

The FreeRTOS port does the switch from lesson 88 in one assembly handler, PendSV, which runs at the lowest interrupt priority. The tick only asks for the switch. This lesson reads each step in the port's source, maps it to the simulator, and explains why PendSV is set to the lowest priority.

By the end of this lesson you can read xPortPendSVHandler line by line, map each of its steps to the simulator's handler from lesson 88, and explain why PendSV runs at the lowest priority and what goes wrong at a higher one.

Where we are, and why it matters

Lesson 87 set up the tick and said that the switch happens in PendSV. Lesson 88 explained what a switch does to the registers and the stacks, using a two-task program with its own handler. This lesson reads the real FreeRTOS port in the same order: the tick that starts a switch, the first frame the kernel builds for a task, the first start, and the switch itself.

Two earlier lessons set up the priority rules. Lesson 72 defined the priority numbers: on the NVIC a lower number is more urgent, and an interrupt of equal priority does not preempt another. Lesson 73 covered SysTick, the timer that produces the tick in this port. The lowest-priority placement of PendSV follows from those rules, and the second half of this lesson works through it.

Line numbers in this lesson refer to the kernel's own port file, third_party/FreeRTOS-Kernel/portable/GCC/ARM_CM3/port.c (FreeRTOS V11.2.0), and to the port header next to it, portmacro.h. The projects compile these files. The code excerpts are copied from them without changes.

Concept 1: the tick asks for a switch, and PendSV performs it

On every tick the port calls xTaskIncrementTick() from the SysTick handler. That function adds one to the tick count, wakes any task whose delay has ended, and returns whether a switch is needed. The SysTick handler in the port looks like this. 

void xPortSysTickHandler( void )
{
    /* The SysTick runs at the lowest interrupt priority, so when this interrupt
     * executes all interrupts must be unmasked.  There is therefore no need to
     * save and then restore the interrupt mask value as its value is already
     * known. */
    portDISABLE_INTERRUPTS();
    traceISR_ENTER();
    {
        /* Increment the RTOS tick. */
        if( xTaskIncrementTick() != pdFALSE )
        {
            traceISR_EXIT_TO_SCHEDULER();

            /* A context switch is required.  Context switching is performed in
             * the PendSV interrupt.  Pend the PendSV interrupt. */
            portNVIC_INT_CTRL_REG = portNVIC_PENDSVSET_BIT;
        }
        else
        {
            traceISR_EXIT();
        }
    }
    portENABLE_INTERRUPTS();
}

The handler brackets its work with portDISABLE_INTERRUPTS() and portENABLE_INTERRUPTS(). The comment above the function says that SysTick runs at the lowest interrupt priority, so all interrupts are already unmasked when it starts. The port therefore does not need to save the old mask and restore it. It can simply enable interrupts again at the end.

When xTaskIncrementTick() reports a switch, the handler writes portNVIC_PENDSVSET_BIT to the interrupt control and state register. That sets PendSV pending and changes nothing else. The tick handler does not touch any stack or task. It only records the request.

The switch runs later. PendSV is at the lowest priority, so it cannot interrupt any other handler. When the tick handler returns with nothing else active, the pending PendSV is taken at once. If another interrupt is active, PendSV waits for it to finish.

Concept 2: the first frame, built by the kernel

Lesson 88 built the first frames by hand, with stores into the simulator's RAM. The port does the same job in pxPortInitialiseStack, which the kernel calls when a task is created. The function is short, and its layout is the one the handler expects, so it is worth reading slowly. 

StackType_t * pxPortInitialiseStack( StackType_t * pxTopOfStack,
                                     TaskFunction_t pxCode,
                                     void * pvParameters )
{
    /* Simulate the stack frame as it would be created by a context switch
     * interrupt. */
    pxTopOfStack--;                                                      /* Offset added to account for the way the MCU uses the stack on entry/exit of interrupts. */
    *pxTopOfStack = portINITIAL_XPSR;                                    /* xPSR */
    pxTopOfStack--;
    *pxTopOfStack = ( ( StackType_t ) pxCode ) & portSTART_ADDRESS_MASK; /* PC */
    pxTopOfStack--;
    *pxTopOfStack = ( StackType_t ) portTASK_RETURN_ADDRESS;             /* LR */
    pxTopOfStack -= 5;                                                   /* R12, R3, R2 and R1. */
    *pxTopOfStack = ( StackType_t ) pvParameters;                        /* R0 */
    pxTopOfStack -= 8;                                                   /* R11, R10, R9, R8, R7, R6, R5 and R4. */

    return pxTopOfStack;
}

The first line of the function, line 188, moves the pointer down one word, and the port's comment says that this offset accounts for the way the MCU uses the stack on exception entry and exit. Line 189 stores portINITIAL_XPSR, which is 0x01000000 (defined at line 78). This is the same value that lesson 88 wrote into the xPSR slot.

Lines 190 and 191 store the PC. The task's entry function is masked with portSTART_ADDRESS_MASK, which is 0xfffffffe (line 90). That clears bit 0 of the address, so the stored PC is an even address. The Thumb state itself comes from the xPSR bit that line 203 sets. Lines 192 and 193 store the LR. The value is portTASK_RETURN_ADDRESS, which is prvTaskExitError in this port (line 110). If a task ever returns from its function, it goes there, and that function asserts and stops, as lesson 87 said a task must never return.

Line 194 moves the pointer down five words, past the slots for R12, R3, R2 and R1, to the R0 slot. Line 195 stores the parameter there. The parameter is the first argument of the task function, so the task receives it in R0, as the calling convention in lesson 33 says. Line 196 moves down eight more words for R11 to R4, and writes nothing into them. The returned pointer is the lowest of those eight slots, and it is the value the kernel stores as the task's stack top.

That returned pointer is the saved block from lesson 88. The port leaves R4 to R11 unwritten, so their starting values are whatever the stack memory held. The simulator writes zeros into its block, which is a difference between the two versions. It does not affect the structure: in both, the handler loads the stack top, pops the block, and then reaches the frame by moving up past it.

Concept 3: the first start, with no task to save

The first task does not come from a switch, because there is no running task to save. prvPortStartFirstTask prepares the stacks and raises an SVC, and vPortSVCHandler starts the first task. Both are short. Their source is shown below. 

static void prvPortStartFirstTask( void )
{
    __asm volatile (
        " ldr r0, =0xE000ED08   \n" /* Use the NVIC offset register to locate the stack. */
        " ldr r0, [r0]          \n"
        " ldr r0, [r0]          \n"
        " msr msp, r0           \n" /* Set the msp back to the start of the stack. */
        " cpsie i               \n" /* Globally enable interrupts. */
        " cpsie f               \n"
        " dsb                   \n"
        " isb                   \n"
        " svc 0                 \n" /* System call to start first task. */
        " nop                   \n"
        " .ltorg                \n"
        );
}

The SVC handler is next, from the same file.

void vPortSVCHandler( void )
{
    __asm volatile (
        "   ldr r3, =pxCurrentTCB           \n" /* Restore the context. */
        "   ldr r1, [r3]                    \n" /* Get the pxCurrentTCB address. */
        "   ldr r0, [r1]                    \n" /* The first item in pxCurrentTCB is the task top of stack. */
        "   ldmia r0!, {r4-r11}             \n" /* Pop the registers that are not automatically saved on exception entry and the critical nesting count. */
        "   msr psp, r0                     \n" /* Restore the task stack pointer. */
        "   isb                             \n"
        "   mov r0, #0                      \n"
        "   msr basepri, r0                 \n"
        "   orr r14, #0xd                   \n"
        "   bx r14                          \n"
        "                                   \n"
        "   .ltorg                          \n"
        );
}

Line 250 loads the address 0xE000ED08 into R0. That is the vector table offset register, which the port's comment calls the NVIC offset register. Line 251 reads it, and the value is the base of the vector table. Line 252 reads the first word of that table, which is the initial stack pointer. Line 253 writes it to MSP, which resets the main stack to its top. Lines 254 and 255 enable interrupts with cpsie i and cpsie f, and svc 0 on line 258 raises the call that starts the first task.

vPortSVCHandler does not save anything. The kernel has already chosen the first task, because this handler does not call vTaskSwitchContext(). It reads pxCurrentTCB, loads the stack top, and pops R4 to R11 with ldmia (line 234). The ! in ldmia r0! writes the moved address back into R0, so R0 ends at the frame. Line 235 writes PSP, lines 237 and 238 clear BASEPRI to zero, and line 239 ORs 0xD into LR. The SVC entry leaves 0xFFFFFFF9 in LR, so the result is 0xFFFFFFFD. The last line, bx r14, performs the return to thread mode on the PSP.

Code, line by line: the simulator's handler

The simulator's switch handler from lesson 88 is listed here in full, so that each group can be read against the port. The listing follows the three jobs from lesson 88. A short first group reads the running task. The next group saves it, the one after stores the save and chooses the next task, and the last group restores the next task and returns.

        LDR  R4, [R0, #0]

        LDR  R9, [R0, #20]
        LDR  R10, [R0, #24]

        MSR  PSP, R0

LDR R1, =0x20000000 and LDR R2, [R1] load the address of the slot and then the value in it, which is the task that was running. CMP R2, #2 and BEQ first test for the very first switch, where there is nothing to save. This is a test on the saved state, not a special case in the hardware.

MRS R0, PSP reads the running task's PSP into R0, which is the address of its hardware frame. SUB R0, R0, #32 moves R0 down eight words, to the room below the frame. The next eight STR lines store R4 to R11 at offsets 0 to 28 from R0. This is the save, and it is the step that the hardware does not do for these registers. The store order matches the load order in restore, so the same offsets find the same values.

LDR R3, =0x20000004 chooses the slot for task A, and CMP and BEQ move to the slot for task B when CUR is 1. STR R0, [R3] stores the new stack top into that slot. This is the store that saves the task's state for next time. The stack top is the only value the kernel needs to find everything else in the block.

The next lines choose the next task. CMP R2, #0 and the pickb branch set R2 to the other task's number, and STR R2, [R1] writes it back to CUR. This is the simulator's version of vTaskSwitchContext(), which picks the next task and changes the current task pointer. The real kernel does this in C, and the simulator does it in a few instructions.

restore loads the next task's saved block address and pops R4 to R11 with eight LDR lines. ADD R0, R0, #32 moves R0 up to the next task's frame, because the saved block is below the frame. MSR PSP, R0 sets the PSP to that frame, which the exception return will pop. LDR LR, =0xFFFFFFFD sets the return value to thread mode on the PSP, and BX LR performs the return. The branch to an EXC_RETURN value is what makes the core unstack the frame, and it is the last thing the handler does.

Map it to the FreeRTOS port

The real port does the same work in one handler, xPortPendSVHandler, in third_party/FreeRTOS-Kernel/portable/GCC/ARM_CM3/port.c. The table lines up each step of the simulator with the instruction or call that does the same job in the port. The port's column gives line numbers in that file.

Two rows differ in form only. The port's stmdb and ldmia save and pop all eight registers in one instruction each, and the write-back moves R0 across the block. The simulator adds 32 by hand instead.

The port's handler is shown below, as it appears in the file. The code is C with inline assembly in strings, so the instructions are in quotes. 

void xPortPendSVHandler( void )
{
    /* This is a naked function. */

    __asm volatile
    (
        "   mrs r0, psp                         \n"
        "   isb                                 \n"
        "                                       \n"
        "   ldr r3, =pxCurrentTCB               \n" /* Get the location of the current TCB. */
        "   ldr r2, [r3]                        \n"
        "                                       \n"
        "   stmdb r0!, {r4-r11}                 \n" /* Save the remaining registers. */
        "   str r0, [r2]                        \n" /* Save the new top of stack into the first member of the TCB. */
        "                                       \n"
        "   stmdb sp!, {r3, r14}                \n"
        "   mov r0, %0                          \n"
        "   msr basepri, r0                     \n"
        "   bl vTaskSwitchContext               \n"
        "   mov r0, #0                          \n"
        "   msr basepri, r0                     \n"
        "   ldmia sp!, {r3, r14}                \n"
        "                                       \n" /* Restore the context, including the critical nesting count. */
        "   ldr r1, [r3]                        \n"
        "   ldr r0, [r1]                        \n" /* The first item in pxCurrentTCB is the task top of stack. */
        "   ldmia r0!, {r4-r11}                 \n" /* Pop the registers. */
        "   msr psp, r0                         \n"
        "   isb                                 \n"
        "   bx r14                              \n"
        "                                       \n"
        "   .ltorg                              \n"
        ::"i" ( configMAX_SYSCALL_INTERRUPT_PRIORITY )
    );
}

mrs r0, psp reads the running task's PSP (line 461), and the isb after it is an instruction synchronisation barrier. It makes the core finish the earlier instructions before it uses the new value. ldr r3, =pxCurrentTCB loads the address of the variable that points to the current task's control block, and ldr r2, [r3] loads the block's address (lines 464 and 465).

stmdb r0!, {r4-r11} is the save (line 467). It writes R4 to R11 into the eight words directly below the frame, with R4 at the lowest address, and the ! leaves R0 pointing at that lowest word. str r0, [r2] stores that address into the first member of the control block (line 468). The comment on line 479 says the first item in the block is the task's top of stack, which is the same role the simulator's PSP slot plays.

stmdb sp!, {r3, r14} saves R3 and LR on the main stack (line 470). LR holds the EXC_RETURN value from the entry, and both registers are needed again after the C call, which may change them. Lines 471 and 472 load the mask value that the port passes in as the %0 operand, which is configMAX_SYSCALL_INTERRUPT_PRIORITY, and write it to BASEPRI. BASEPRI masks interrupts whose priority number is equal to or greater than the value written, so the interrupts that are allowed to call FreeRTOS functions are held off during the call. The port's comment at lines 167 to 170 names this value as the limit for interrupts that call the kernel. Interrupts more urgent than the limit still run.

bl vTaskSwitchContext calls the C function that chooses the next task and updates pxCurrentTCB (line 473). Lines 474 and 475 clear BASEPRI again, and line 476 restores R3 and LR from the main stack. Lines 478 and 479 then load the new task's stack top through the updated pointer. This is why the loads must come after the call. Line 480 pops the new task's R4 to R11, and line 481 writes PSP. Line 483, bx r14, returns to the new task on its PSP.

The prototype at line 123 carries __attribute__( ( naked ) ), and the comment at line 457 says the function is naked. A naked function has no compiler prologue or epilogue, so the first instruction of its body is the mrs, and the port controls every register from there. The next section, on common mistakes, shows what goes wrong when the attribute is missing.

Why PendSV is at the lowest priority

The port sets the priorities of the three system handlers in xPortStartScheduler. The code is short, and the comment above it gives the design in one sentence.

PendSV is the caretaker who rearranges the meeting room only when every meeting is over. Anyone can leave a note asking for the change, which is setting PendSV pending, but the caretaker waits until no interrupt handler is running. That way a task switch never happens in the middle of a handler's work.

    /* Make PendSV and SysTick the lowest priority interrupts, and make SVCall
     * the highest priority. */
    portNVIC_SHPR3_REG |= portNVIC_PENDSV_PRI;
    portNVIC_SHPR3_REG |= portNVIC_SYSTICK_PRI;
    portNVIC_SHPR2_REG = 0;

The system handler priority registers hold one byte for each system handler. SHPR2, at 0xE000ED1C, holds the byte for SVCall. SHPR3, at 0xE000ED20, holds the byte for PendSV in bits 23 to 16 and the byte for SysTick in bits 31 to 24. The port's shifts by 16 and 24 on lines 56 and 57 use those positions. The Cortex-M3 Technical Reference Manual gives the register map in the source box below.

The value written for PendSV and SysTick comes from portMIN_INTERRUPT_PRIORITY, which is 255 (line 55). On a device that implements only the top four priority bits, the lowest level is 15, as lesson 72 explains for the STM32F1. A written value of 0xFF therefore selects that lowest level, because its top four bits are all set. SVCall gets 0, the most urgent level, because line 392 clears the whole SHPR2 register.

Lower numbers are more urgent (lesson 72). So PendSV and SysTick are the least urgent handlers in the port, and SVCall is the most urgent. Two sources at the same priority do not preempt each other, which lesson 72 states as a rule. So once PendSV has started, a tick cannot interrupt it, because SysTick has the same level.

The lowest level has a second effect. An exception return to a task is valid only when no other handler is still active. PendSV can start only when no other handler is active, because it cannot preempt any handler. That is the condition for a valid return to a task. A more urgent interrupt can still preempt PendSV, but it returns to PendSV before PendSV returns to the task. If PendSV were set higher than a running interrupt, it could preempt that interrupt, and its return would go to a task while the interrupt was still active. That return is not valid, so the result is a fault or a corrupted return.

Interrupts more urgent than PendSV can still arrive while it runs. They are not blocked by the lowest level, and the core takes them on their own priority. The BASEPRI lines protect only the call to vTaskSwitchContext(), because only the list operations inside it must not be interrupted by an interrupt that calls the kernel. The save and the restore run with interrupts unmasked.

Finally, lesson 72 describes tail-chaining. When one handler returns and PendSV is pending, the core takes PendSV next, without an extra save and restore of the frame. For the tick, this means the switch follows the tick work with very little delay in the common case.

The simulator has no BASEPRI and no nesting, so a real interrupt can arrive in the middle of the switch on silicon in a way this simulator cannot show. Treat the simulator as a model of the order of operations, not of the timing.
  1. Task A runs in thread mode on its own stack. The scheduler is not running code at all; it waits for a tick.
  2. SysTick fires. xTaskIncrementTick() wakes task B, whose delay has ended, and says a switch is needed. The handler does not switch: it only sets the PendSV pending bit in ICSR and returns.
  3. A UART byte arrives. Its interrupt is more urgent than PendSV, so it runs first, and PendSV keeps waiting. A switch now would return to a task while the UART handler was still active, which is not a valid exception return.
  4. No other handler is active, so PendSV finally runs, tail-chained after the UART return. It saves R4 to R11 of task A on A's stack, asks vTaskSwitchContext() for the next task, and restores B's registers from B's stack.
  5. PendSV returns, and the exception return pops B's hardware frame: task B runs. PendSV sits at the lowest priority exactly so that it runs only when every other handler is finished.

Try it in the FreeRTOS project

This exercise reads the real port in the project from lesson 87. It needs no change to the code and does not need the simulator. It checks the names and lines that this lesson uses.

The FreeRTOS projects in this course build, but they cannot run in the Wokwi simulator. Checked on 2026-11-01 with Wokwi CLI 0.29.1, its STM32 model differs from a real Cortex-M3 in these ways:
  • cpsie and cpsid are inverted.
  • Byte reads of the NVIC and SHPR priority registers return 0.
  • BASEPRI is not implemented: writes are ignored and reads return 0.
  • PRIMASK does not mask SysTick or peripheral interrupts.
  • A software-pended exception such as PendSV is taken at the store that pended it and returns to that store, so it runs forever.

Common mistakes and how to spot them

Mistake 1: a switch written in plain C. A developer writes the switch as an ordinary C function with asm inside it, and the attribute is missing. The compiler is then free to add code around the assembly, and that code can change registers that the assembly expects to hold particular values. The symptom is a switch that works in a short test and fails under load, when the compiler makes different choices. The fix is the naked attribute, as the port declares it on line 123, so that the assembly is the whole function.

Mistake 2: PendSV at a higher priority than the interrupt it runs inside. A developer sets PendSV to a priority that is more urgent than a peripheral interrupt, so the switch can start while that interrupt is active. The return to a task is then not valid, and the symptom is a fault or a corrupted return. It may appear rarely and look like random data. The fix is the lowest priority for PendSV, as the port sets it at line 390.

Mistake 3: loading the new stack top before the switch. A developer moves the two loads of the next task's stack top above the call to vTaskSwitchContext(), perhaps while tidying the handler. The loads now read pxCurrentTCB before the call has changed it, so they still point at the task that just yielded. The symptom is that the same task runs again, and the switch appears to do nothing. The fix is to keep the loads after the call, as lines 478 and 479 do.

Mistake 4: removing the BASEPRI lines. A developer sees lines 471 to 475 as noise, because the handler works in a quick test without them. The list operations inside vTaskSwitchContext() are then open to an interrupt that calls the kernel, and the ready list can be changed in the middle of an update. The symptom is intermittent corruption under load, and the simulator cannot show it, because it has no BASEPRI. The fix is to restore the masking around the call, with the same mask value that the port passes.

In real projects

Teams that port FreeRTOS to a new core test the handler with a two-task program like the one in lesson 88 before they trust it. Code review of a port checks the split of saved registers, the priority of the switch exception, the EXC_RETURN values, and the order of the loads around the call.

Summary

  • The tick handler calls xTaskIncrementTick(), and when a switch is needed it only pends PendSV. It does not switch tasks itself.
  • pxPortInitialiseStack builds a task's first frame, with xPSR at 0x01000000, the entry point as PC, and the task return address in LR.
  • The first task starts through vPortSVCHandler, which pops the frame without saving anything, since no task is leaving.
  • xPortPendSVHandler saves R4 to R11 below the frame, stores the stack top in the control block, calls vTaskSwitchContext() with BASEPRI set, and then loads the new task's stack top after the call.
  • PendSV and SysTick are at priority 255, the lowest level, and SVCall is at 0, the highest. A switch at a higher level could return to a task while another handler is still active.
  • Tail-chaining lets PendSV run as soon as the last other handler returns, which keeps the switch prompt.
