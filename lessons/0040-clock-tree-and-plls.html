Clock tree and PLLs

Every timing number in your firmware, from a 500 ms delay to a UART baud rate, is a division of one clock. Learn the tree once and you can check any of them.

By the end of this lesson you can calculate the system clock of an RP2040 or an STM32F103 from its oscillator and PLL settings, and name the clock source each chip uses straight after reset.

The idea

A clock tree is the set of oscillators, multipliers, dividers and selectors between the crystal and the logic that needs a clock. An oscillator makes a reference frequency. A PLL (phase-locked loop) multiplies it up. Dividers and multiplexers pick the frequency each block uses. The core runs from the system clock, and the peripherals run from their own clocks, which may be divided from the same source.

The architecture course's point about the clock applies directly: the core executes one instruction per clock at best, so a timing number such as "one microsecond" is a count of cycles at a known frequency. If the frequency is wrong, every delay is wrong by the same ratio.

RP2040: 12 MHz crystal, PLL to 125 MHz

The RP2040 reference design uses a 12 MHz crystal. The crystal oscillator (XOSC) is off at power-up, and software must enable it and wait for the XOSC_STABLE flag before using it or starting the PLLs. Until then the system clock runs from a ring oscillator at about 6.5 MHz. RP2040 datasheet, sections 2.15.2.2 (Crystal Oscillator), 2.16 (XOSC) and 2.7 (Boot Sequence).

The system PLL, PLL_SYS, multiplies the 12 MHz reference. The datasheet's own example gives the arithmetic: 12 MHz ÷ 1 × 125 = 1500 MHz in the VCO, then ÷ 6 ÷ 2 = 125 MHz. The SDK's default settings produce this 125 MHz system clock. RP2040 datasheet, section 2.18.3 (PLL Configuration) and 2.15.6.1 (Configuring a clock generator).

The clock table gives the nominal frequency of clk_sys as 125 MHz, and says the chip cannot exceed 133 MHz across process, voltage and temperature. The same note says 200 MHz is possible with an elevated core supply. RP2040 datasheet, section 2.15.3.1 (Instances).

Notice the VCO. 1500 MHz is not the system clock, even though it is the largest number in the calculation. The post-dividers come after the VCO, and the answer you want is the output. This is the mistake most people make first.

STM32F103: HSI at reset, HSE through the PLL

After every reset the STM32F1 uses its internal 8 MHz RC oscillator, HSI, as the system clock. The ST system file says so directly: "After each device reset the HSI (8 MHz) is used as system clock source", and SystemInit() then configures the clock before main() runs (system_stm32f1xx.c).

The PLL input is the HSE crystal or the HSI divided by two, and the PLL multiplies it. The system file shows both formulas in the code path that sets SystemCoreClock: (HSE_VALUE / prediv1factor) * pllmull for HSE, and (HSI_VALUE >> 1U) * pllmull for HSI. The header defines the multiplier RCC_CFGR_PLLMULL9 as "PLL input clock*9". With HSE at its default of 8 MHz and the ×9 multiplier, the PLL gives 8 MHz × 9 = 72 MHz. The course's Zephyr board for the Blue Pill also runs HSE plus PLL at 72 MHz, as NOTES.md records.

The flash wait states must go up before the clock does. The HAL does this in the order described in lesson 36. A faster clock with the old wait states reads flash too early and returns bad data, so the order is part of the recipe, not a detail.
The 72 MHz maximum for the STM32F103 is the datasheet's limit, which this course has not yet checked against the datasheet text. The arithmetic above uses only the header and the system file.

Try it in Wokwi

The project projects/0040-clock-tree is a single demo. It prints SystemCoreClock, the clock source bits of RCC_CFGR, and the PLL multiplier field.

  1. Open projects/0040-clock-tree in VS Code, build with Ctrl+Shift+B, and start the simulator with F1 → Wokwi: Start Simulator.
  2. Read the SystemCoreClock line. It should be 8000000, which is HSI at 8 MHz. Explain why the PLL field reads zero.
  3. Press F5 to debug, stop at main, and type print/x RCC->CFGR in the debug console. Find the SWS bits, which are bits 2 and 3, and confirm they show HSI.
Hint

The SWS field is bits 3:2 of RCC_CFGR, so shift right by two and mask two bits. A value of 0 means HSI. The PLLMUL field is bits 21:18, so it is zero when the PLL is not selected.

You can calculate a system clock from a PLL configuration on both chips, and you know which oscillator each chip uses straight after reset.

"Your firmware boots on an STM32F103 at 8 MHz. How do you get to 72 MHz, and what must you change first?" Answer out loud in 60 seconds, then compare.

Model answer

Enable HSE and wait until it is ready. Set the PLL source to HSE, set the multiplier to ×9, and turn the PLL on, then wait for it to lock. Raise the flash wait states first, so the flash can keep up. Switch the system clock source to the PLL and check the status bits until the switch completes. Finally, update SystemCoreClock so your delays and baud rates use the new frequency. Changing the clock before the wait states go up is the classic mistake.

RP2040 datasheet: read section 2.15 (Clocks), especially the clock table in 2.15.3.1 and the PLL example in 2.15.6.1. It shows the same arithmetic as this lesson, with the register settings.
