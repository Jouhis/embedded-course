Digital filtering

Moving averages, IIR smoothing and median filters

By the end of this lesson you can implement a moving average with a running sum and a first-order IIR (exponential moving average) in integer C, predict the step response of each from its equation, and say what a median filter removes that the others cannot.

Noisy sensor readings and the control loop

Lesson 58 showed how the ADC turns a voltage into an integer code, lesson 21 how to hold fractions in integers and lesson 80 how to test C on the PC before it runs on the Pico, and this lesson uses all three, as well as lesson 8, because a thermistor is read through a voltage divider.

The problem is noise, a dryer's thermistor read through a divider giving a code that jitters by a few counts from one sample to the next even when the air temperature is steady, so if the heater controller of lesson 108 uses that jitter directly, it reacts to electrical hash rather than the real temperature and switches the heater on and off for no reason. A filter is a short program that turns the noisy stream into a smoother one before the control code sees it.

Real printer firmware does the same job, the Klipper configuration reference documenting a smooth_time option in its heater sections, which averages temperature measurements over a time window to reduce the impact of measurement noise, and a pid_deriv_time option that does the same for the PID derivative term (Klipper Config Reference). The option names are the ones a Klipper user meets, and the lesson's filters are the same idea in a few lines of C.

Samples, sample rate and aliasing

The ADC gives a number each time one is asked for, the number of samples per second being the sample rate, and a filter sees only those samples, never the analogue signal between them, which has two consequences every filter inherits.

The first is a limit on what can be measured, a signal having to change more slowly than half the sample rate, the Nyquist frequency, and the second is aliasing, in which a signal above the Nyquist frequency does not vanish when sampled but folds down and appears as a slower signal that was never there. A 90 Hz hum sampled at 100 samples per second thus shows up as a 10 Hz wobble, because 100 − 90 = 10, and no filter can tell that wobble from a real 10 Hz change. Aliasing happens during sampling, before any filter runs. A digital filter cannot remove an alias afterwards. Sample fast enough, or filter the analogue signal first with an RC low-pass filter (lesson 13).

A filter is therefore for the noise inside the band you care about, jitter, spikes and hum that is slow compared with the sample rate, and it cannot repair a signal that was undersampled.

FIR and IIR filters

A digital filter computes each output from past inputs, and sometimes from past outputs too, its impulse response being the output for an input of a single sample of 1 followed by zeros, which shows how long an input keeps influencing the output and so serves to compare filters.

There are two families, a FIR filter (finite impulse response) computing its output only from a finite window of past inputs, so that an input leaving the window has no effect at all, and an IIR filter (infinite impulse response) feeding its own previous output back in, so that an input's influence decays over time without ever reaching exactly zero and the memory has no end. The moving average is the FIR case and the exponential moving average the simplest IIR case.

The moving average with a running sum

A moving average of N samples is the mean of the last N inputs, whose naive code adds up the N values on every sample, so its work grows with N, whereas the running-sum version keeps the total from the last update and changes it by two numbers, adding the newest sample and subtracting the one that just left the window.

To know which sample is leaving, the filter stores the last N inputs in a ring buffer, an array with a write index that wraps back to zero at the end, so that the slot the index points at always holds the oldest sample, and each update then costs the same whatever N is. Computer scientists write that cost as O(1), meaning constant time, which is why the running sum is worth the extra state. 

int32_t ma_update(moving_avg_t *m, int32_t x) {
    m->sum += x - m->buf[m->idx];          /* add the new sample, remove the oldest */
    m->buf[m->idx] = x;                    /* the oldest slot now holds the newest sample */
    m->idx = (uint8_t)((m->idx + 1u) % m->window);   /* advance and wrap: this is the ring */
    return m->sum / (int32_t)m->window;      /* the mean of the window */
}

Line 1 reads buf[idx], the oldest sample, adding the new value and subtracting that old one in one statement, an order that is safe within the statement, whereas the order of the next two lines is not, because line 2 overwrites the slot and must therefore come after line 1 (the first common mistake below shows what goes wrong). Line 3 stores the newest sample in the slot the oldest one just vacated, line 4 moves the index on, the % wrapping it from N − 1 back to 0 and the cast keeping it in the one byte the struct declares, and line 5 divides the sum by the window size, C integer division truncating toward zero, which is fine for ADC counts, because they are never negative.

A moving average resembles the weather report's average of the last seven days, which one odd day barely moves, the smoothing, but which takes days to follow when the weather really turns, the lag, so a longer window gives more smoothing and more lag, and no setting gives one without the other. The comparison breaks at the window's edge, though, because a weather average is usually recomputed once a day, whereas the filter drops its oldest sample exactly when it adds a new one, so its output changes on every single sample.

The output rises in four equal quarters and then holds, because at sample 5 the first 1000 is removed and a new 1000 added, so the sum does not change, and since the filter is exact, the output lands on 250, 500, 750 and 1000 without rounding. The lag of a moving average is about

lag = (N − 1) ÷ 2(1)

where N is the window length and the lag is in samples, so for N = 4 the output's centre of mass trails the input by 1.5 samples. The falling step behaves the same way in reverse, with 750, 500, 250 and 0 as the four inputs of zero leave the window.

The exponential moving average

The first-order IIR filter, usually called the exponential moving average (EMA), feeds its own output back, its equation being one line,

y += (x − y) × α(2)

where x is the new input, y the stored output (the filter's state) and α, the smoothing factor, a number between 0 and 1, so that each new output moves a fraction α of the way from the old output towards the input. A small α smooths heavily and reacts slowly, while a large α follows the input closely and passes more noise, and when α is a power of one half, α = 1 ÷ 2k, the multiply becomes a shift, y += (x - y) >> k.

With k = 3, α = 1/8, so after one sample the output has moved 1/8 of the way, and after n samples of a step from 0 to 1000 the output is 1000 × (1 − (7/8)n), because the gap to the input shrinks by 7/8 each time, as the table shows with values rounded to whole codes.

The response never reaches 1000 in a finite time, so its speed is measured by the time constant, the number of samples the output takes to cover 63 % of the step,

τ = −1 ÷ ln(1 − α)(3)

where α is the smoothing factor and τ is in samples, so for α = 1/8 it is 7.49 samples, close to but not exactly the rule of thumb of about 2k, here 8. The same numbers give a cutoff frequency, the frequency at which the filter starts to attenuate, of about −fs ln(1 − α) ÷ 2π, where fs is the sample rate, so at 100 Hz it is 2.1 Hz.

Figure 1 plots the two step responses on the same axes, the moving average reaching the input after four samples while the EMA is still climbing after eight, each trading lag for smoothing in a different way, as the plot shows directly.

The shift is worth using here, because the Cortex-M0+ core has no divide instruction, so a / in C becomes a call to a helper routine, although the RP2040 adds an integer divider in its SIO block, onto which the Pico SDK maps the compiler's divide helper (Pico SDK 2.3.1, pico_divider/divider_hardware.S), a divider lesson 21 explains. Even so, a shift is the cheapest way to divide by a power of two, and a filter running every sample on a small core should use it.

Fixed point and the dead band

The Cortex-M0+ has no floating-point unit (lesson 21 compares the Arm cores), so a float EMA runs in software at many cycles per sample, which makes integer arithmetic the normal choice, although the integer EMA has one serious problem. With y += (x - y) >> 3, y = 0 and a steady input of 5, the difference is 5, and 5 ÷ 8 truncates to 0, so y never moves and the filter stalls at zero, five codes short of its input, forever, the range of inputs that the update rounds to zero being a dead band.

The fix is to keep the state with extra fraction bits, the state holding y × 256, the Q format of lesson 21 with eight fraction bits, so that a step of one unit in the state is 1/256 of an output code and the update can move the state even when the input is only a few codes away. The output is the state shifted back down by 8 bits, a shift that needs rounding, which adding 128, half of 256, before the shift provides, rounding to the nearest code.

Rounding matters for a steady input, because the update stops moving once the gap 1280 − state is smaller than 8, so the state settles between 1273 and 1280, and truncation reads 4 for any state from 1273 to 1279, showing a steady 5 as 4, whereas rounding reads 5 for the same states, which the host test test_ema_converges_to_a_small_steady_input checks.

The fixed-point EMA can be followed with numbers, priming the state at 0, as the host test does, and feeding a steady input of 5, whose target is 5 × 256 = 1280. The first update adds (1280 − 0) ÷ 8 = 160 to the state, giving an output of (160 + 128) ÷ 256 = 1 after rounding, and the second adds (1280 − 160) ÷ 8 = 140, making the state 300 with the output still 1, and as the state keeps climbing, the output first reaches 5 at sample 18, when the state passes 1152, 4.5 codes, whereas the integer version from the same start never moves at all. 

/* state holds y * 256 (EMA_FRAC_BITS = 8) */
int32_t target = x * (1 << 8);                      /* scale the input into the state's units */
if (!e->primed) { e->state = target; e->primed = true; }
else  e->state += (target - e->state) >> e->k;   /* the IIR update, alpha = 1 / 2^k */
return (e->state + 128) >> 8;              /* round to nearest on the way out */

The first line scales the input by 256, so that it lives in the same units as the state, the if primes the state on the first call, so that it starts at the first reading rather than at zero (common mistake 3 explains why), and the else applies equation (2) with the shift. The last line adds half of 256 and shifts by 8, dividing by 256 with rounding, and the state is never divided by 256 inside the loop, only the output, so the fraction bits survive from one sample to the next.

Right-shifting a negative signed value is implementation-defined in C, and gcc shifts arithmetically. Keep these filters on non-negative signals, or check the compiler's behaviour before you rely on it.

The median of three for spike removal

A loose wire, a switching transient or a noise burst gives one wild sample, which a moving average smears over its whole window, an 8-sample average adding one-eighth of the spike to each of eight outputs, while an EMA follows the spike at one-eighth of its size and then decays slowly. A median filter removes a lone spike completely, because the median of a set of values ignores the most extreme ones.

For a window of three samples the median is the middle value once the three are sorted, the median of (10, 1000, 10) being 10, so the spike is gone, at the cost of a delay of one sample on a real step, because the median needs the new value and the one before it. A worked sequence shows both effects, the inputs 10, 10, 10, 1000, 10 giving the outputs 10, 10, 10, 10, 10, and the inputs 10, 10, 10, 20, 20 giving 10, 10, 10, 10, 20, the real edge arriving one sample late, so the median runs first and the averaging second, so that the spike never reaches the average. 

int32_t median3_update(median3_t *m, int32_t x) {
    m->hist[0] = m->hist[1];               /* shift the three-sample history */
    m->hist[1] = m->hist[2];
    m->hist[2] = x;
    if (m->count < 2u) { m->count++; return x; }   /* no full window yet */
    int32_t a = m->hist[0], b = m->hist[1], c = m->hist[2];
    return max32(min32(a, b), min32(max32(a, b), c));  /* median, without sorting */
}

The first three assignments keep the last three inputs in a small history, oldest first, and the if passes the input straight through for the first two calls, because there are not yet three samples to compare, while the return line computes the median without sorting. min32(a, b) is the smaller of the two oldest values, max32(a, b) the larger and min32(max32(a, b), c) the smaller of that larger value and the newest one, so the outer max32, picking the larger of the two results, gives the middle value of the three, 10 for (10, 1000, 10) and 5 for (2, 9, 5).

The median of three resembles asking three witnesses and believing the one in the middle, so that a witness who saw something wildly different, a spike, is ignored however far off the answer, whereas an average would have been dragged towards the odd one out. The comparison breaks for two witnesses who agree on a wrong answer, because two neighbouring spikes outvote the single good sample, so the median of three removes only lone spikes.

Hint for the moving average

Subtract the oldest sample before you overwrite its slot. If you overwrite first, you subtract the new value from itself, the sum never changes, and the output stays at zero for any input.

Hint for the EMA

On the first call, set the state to the first sample rather than to 0. Otherwise the output ramps up from 0 and the step-response tests fail by the first few samples.

Common mistakes and how to spot them

A first implementation of these filters usually contains the mistakes below, each with a symptom visible in the test output, the serial monitor or the spreadsheet.

The slot overwritten before it is subtracted

The ma8 column stays flat at zero while raw moves, and the host test test_ma_step_response_rises_in_quarters fails with 0 instead of 250 on the first update, because the moving average stores the new sample first and then does sum += x - buf[idx], subtracting the value it has just written, so the sum stays at zero. Follow the order of the running-sum code, adding the new sample and subtracting the old one before the write.

An integer EMA without fraction bits

The ema column stops short of the raw column and never moves again, because the integer update y += (x - y) >> 3 stalls once the gap to the input is smaller than 8 codes, staying at 0 forever with an input of 5, as the host test test_integer_ema_without_fraction_stalls shows by repeating the same integer equation in its assertion. Use the scaled state with rounding on the way out, as in the code above.

The EMA started at zero

A slow ramp appears at start-up that the reading does not have, a steady reading of 1000 coming out as 125, 234, 330 and 414 in the first four samples, the step response of an empty filter, because the state starts at zero, so for a sensor starting at room temperature the first second of readings is wrong and a controller using them acts on a temperature that does not exist. Prime the state from the first sample, as the primed flag in the project does.

Averaging before spike removal

A rectangular bump appears in the averaged column at every spike, the 600-code spike showing as a rise of 600 ÷ 8 = 75 codes in the ma8 column for eight rows, because the moving average reads the raw signal and the median is computed afterwards, by which time the spike is already spread across eight outputs that the median cannot take back. Use the project's order, median first and then the averaging.

A window of zero, or one larger than the buffer

The program crashes or produces nonsense values that depend on the compiler, because a window of zero makes it divide by zero in sum / window, which C leaves undefined, while a window larger than the buffer writes past its end, both bugs lying in the configuration rather than the arithmetic. Clamp the window in the init function, as ma_init does, so that the function cannot be given a bad size.

Filter lag and tests in sensor drivers

Professional firmware filters sensor readings in the driver layer, close to the ADC, and documents each filter's time constant or cutoff next to the code, a reviewer asking of every filter what its lag is in samples or seconds and what happens to the control loop's stability when that lag is added to the loop's own delay. A filter with a long time constant inside a fast PID loop can make a stable loop oscillate, so the filter and the loop are tuned together (lesson 108).

Reviewers also expect the filter to come with tests, this lesson's host tests using the step response, because it shows in one picture how fast a filter moves, how far it goes and whether it lands exactly on the input, and since the same tests run on the PC in milliseconds, the project does its arithmetic there first. Klipper's documented smooth_time and pid_deriv_time options are the same design choice made in a shipping product, a documented window applied to the measurement before the control law uses it.

Summary

  • A filter sees samples, so it can remove noise inside the band of your signal but cannot undo aliasing from undersampling.
  • A moving average is FIR, a running sum and a ring buffer giving constant cost per sample, with a lag of about (N − 1) ÷ 2 samples.
  • A first-order EMA is IIR, y += (x − y) × α, a shift when α = 1 ÷ 2k, with a time constant of −1 ÷ ln(1 − α), about 7.5 samples for k = 3.
  • An integer EMA stalls in a dead band, so the state keeps 8 fraction bits and the output is rounded when shifted back down.
  • The EMA is primed from the first sample, so that it does not ramp up from zero.
  • A median of three removes a lone spike completely at the cost of one sample of delay on a real edge, and it runs before any averaging.
  • The old sample is subtracted before its slot is overwritten, and the window is clamped in the init function.
