Continuous integration for firmware

Every push builds the firmware, runs the tests, checks the code and simulates the board. A failing check blocks the change before a reviewer sees it.

By the end of this lesson you can run the firmware checks locally with verify_projects.py, and say what each job of a firmware CI workflow does and why.

Where we are and why it matters

The last three lessons gave you the checks one at a time. Lesson 80 ran unit tests on the PC, and lesson 81 faked the bus so a driver could be tested without a sensor. Lesson 41 showed the build from source to ELF, map and hex file, and lesson 1 installed the Arm toolchain on your PC. Each check works when you run it by hand. The problem this lesson solves is that people forget to run them, or run them on a different machine.

This happens often on teams. A colleague changes a shared driver, runs the tests on a laptop that has the right toolchain and a leftover file, and pushes. The build fails on the team's compiler, or the simulation shows a boot loop that nobody tested. Continuous integration (CI) removes both problems. A server, called a runner, takes every push, starts from a clean machine, and runs a fixed list of checks in the same order. The result is recorded against the commit, so a bad change is visible before a reviewer reads it.

In firmware work, a CI job usually has five stages: the host unit tests, static analysis (lesson 83), the firmware build, the simulation, and the keeping of outputs. The habits that decide what reaches the pipeline, such as branches and code review, are in lesson 79.

The vocabulary: runners, jobs, steps and exit codes

A runner is the machine that runs a job. The sample workflow uses a hosted Linux runner, ubuntu-latest, which GitHub starts fresh for every job. A clean machine means nothing from your laptop is present: no installed tools, no leftover build folder, no environment variable. If the job passes there, the change does not depend on something only you have.

A workflow is a YAML file that describes when to run and what to do. It has jobs, and each job has steps. A step is either an action, which is a packaged piece of automation someone else wrote, or a run: block of shell commands. Jobs run in parallel unless you link them with needs:, which says that one job waits for others to pass.

Every step reports success or failure through an exit code: a number a program returns when it stops. Zero means success, and any other value means failure. The CI server decides the outcome of a job from exit codes, not from what the program printed. This matters, because some tools print a warning and still exit with zero. You will see an example of that in the static-analysis job below, and it is one of the common mistakes.

An artifact is a file a job keeps after it finishes (glossary: artifact (CI)). For firmware, the useful artifacts are the .elf for a debugger, the .map for the memory layout (lesson 41), and the .hex for flashing. When a run fails on the server, the artifact lets you examine the same binary that failed, instead of a rebuilt one.

Why each job exists

The jobs are ordered by cost. The host unit tests run in seconds on a plain Linux runner, with no board toolchain at all. Static analysis (lesson 83) comes next, because it fails fast on warnings before anything is built for the board. The firmware build uses one Arm GCC release, pinned in the workflow, because a compiler change can move bugs and change code size. The simulation is last, because it needs the firmware and takes the longest.

The simulation checks what the compiler cannot: the boot path, the startup code, the clock setup and the serial output. A build that links cleanly can still hang at boot, and only a run shows it. In a real project, the simulation is also where a team checks the behaviour of the whole program with its peripherals, and the simulated board is a cheap way to do that for every push.

The local version: verify_projects.py

The course gives you the same checks on your own machine. tools/verify_projects.py builds a project, lints its Wokwi diagram, and checks that the paths in wokwi.toml point at real files. With --sim, it also runs the simulator. Its help text says where the expected serial text comes from: a line in main.c of the form // EXPECT: <text>. The script reads that line with a regular expression, //\s*EXPECT:\s*(.+), and then passes the text to the simulator as --expect. If the line is missing, the script still runs the simulator, but with no text to check.

That last point is the reason the convention matters. The course's tools/sim.py wraps the Wokwi command-line tool. Its job is to run the firmware for a time limit and decide pass or fail. With no expected text, a run that reaches its time limit without an error counts as a pass. So a missing EXPECT line weakens the check quietly.

The Wokwi CLI: the options that matter

wokwi-cli runs a project headless, which means without a window. Its options are documented on the CLI usage page. These are the ones a test needs:

OptionWhat it does
--timeout <ms>Simulated milliseconds before the run stops. The default is 30000. It is simulated time, not wall-clock time.
--expect-text <text>The run passes only if this text appears in the output (the serial monitor).
--fail-text <text>The run fails as soon as this text appears, for example HardFault.
--serial-log-file <path>Saves the serial output, so you can read the log of a failed run.
--scenario <path>Runs a YAML file of steps (below).
--timeout-exit-code <number>The process exit code when the timeout is reached. The default is 42.
The timeout is simulated time. A 10000 ms timeout is 10 simulated seconds, and the simulator may run faster or slower than the clock on the wall. The GitHub Action has its own default, 10000, and the sample sets it explicitly.

A worked example: one push, step by step

Follow one push to the sample workflow. The example uses the real numbers from the project. The LED period is 1000 ms, so led_half_period_ms(1000) returns 500 (the function in src/led_pattern.c halves the period). The firmware prints LED on, waits 500 ms, prints LED off, and repeats. The simulation timeout is 10000 ms of simulated time.

  1. The push starts the run. The workflow says on: push and on: pull_request, so GitHub starts the workflow on the runner pool for every push and every pull request.
  2. Three jobs start at once. host-tests and static-analysis have no needs: line, so they run in parallel. Each starts with actions/checkout, which copies the repository onto the clean runner.
  3. The host tests build and run. The job installs CMake and Ninja, configures the host-tests folder, builds it, and runs ctest --output-on-failure. The test led_half_period_ms checks 1000 gives 500, 5 gives 2, and 0 or 1 give 1. If any test fails, ctest exits with a failure code, and the job stops.
  4. Static analysis runs cppcheck. It checks the pure C sources and the host-test folder with --enable=warning,style. The flag --error-exitcode=1 is what makes a finding fail the job. Without it, the exit code is 0 and the job is green (the example in the mistakes section shows this).
  5. The firmware job waits. firmware has needs: [host-tests, static-analysis], so it starts only after both pass. It installs Arm GCC release 15.3.Rel2, builds in Debug, and uploads the .elf, .hex and .map as an artifact named firmware.
  6. The simulation runs last. simulate waits for firmware, downloads the artifact into the build folder, and runs the Wokwi action with timeout: 10000 and expect_text: 'LED on'. The first LED on appears soon after the boot, so the expected text is found early in the run. The run would stop at 10 simulated seconds, which is about ten blink cycles, if the text never appeared.
  7. The result comes back. If LED on appears, the simulator exits with 0, and the job passes. If the text never appears, the run fails at the timeout. The firmware job's artifacts stay available for a human to open, whichever way the run ends.

The local equivalent of steps 3 to 6 is python -I tools/verify_projects.py 0082 for the build, lint and path check, and the same command with --sim for the simulation. The local run cannot replace the pipeline, because it runs on your machine and its toolchain. It catches most problems early, so the pipeline only confirms what you already saw.

Scenarios: steps instead of one text match

--expect-text answers one question: does this text appear. A scenario answers a sequence of questions in order. A scenario is a YAML file of steps. The Wokwi docs mark the feature as alpha, which means its format may change. The sample has one, smoke.scenario.yaml: 

name: 'LED blinks on the serial monitor'
version: 1
author: 'course'
steps:
  - wait-serial: 'LED on'
  - delay: 500ms
  - wait-serial: 'LED off'

Read the file as a script for the simulator. The first step blocks until LED on appears. The second waits 500 ms of simulated time, which is one half period of the blink. The third waits for LED off. A test with this scenario checks that the LED toggles, which the single-text test does not. The automation page lists the other step types: expect-pin checks a pin level, set-control changes a part such as a button, and write-serial sends text to the firmware. Use the steps the docs list, and check the page before you depend on one, because the feature is alpha.

Run it from the project folder with wokwi-cli . --scenario smoke.scenario.yaml. The scenario path is relative to the project root, as the automation scenarios page describes.

The workflow file, line by line

GitHub reads workflows only from .github/workflows/ at the root of the repository. The sample's projects/0082-continuous-integration/.github/workflows/ci.yml is a copy for reading, not a file GitHub will run from this folder. The file has four jobs: host-tests, static-analysis, firmware and simulate. The lines that matter are these. 

on:
  push:
  pull_request:

The on: block lists the events that start the workflow. Here, a push to any branch and a pull request both start it. A pull request from your own branch then runs the workflow twice, once for the push and once for the pull request, which is a cost you can reduce later with a branch filter. 

static-analysis:
  steps:
    - name: Check the pure C sources
      run: >
        cppcheck --enable=warning,style --inline-suppr --error-exitcode=1 --std=c11 --quiet
        projects/0082-continuous-integration/src
        projects/0082-continuous-integration/host-tests

The run: > form folds the following lines into one shell command. --enable=warning,style turns on the warning and style checks, as in lesson 83. --inline-suppr lets a source file silence one finding with a comment, so that a known false alarm does not block the team, and each suppression is visible in review. --error-exitcode=1 makes cppcheck return 1 when it reports anything, so the step fails. --std=c11 sets the language standard. The two paths are the folders to check. 

firmware:
  needs: [host-tests, static-analysis]
  steps:
    - uses: carlosperate/arm-none-eabi-gcc-action@v1
      with:
        release: '15.3.Rel2'

needs: says the job waits until both listed jobs pass. The uses: line runs an action, a packaged step that another author wrote, and with: sets its inputs. The action's README gives 15.3.Rel2 as its example release, and the input chooses which Arm GCC release to install. A real project pins one release in both places: the workflow and the developer setup. Your laptop has Arm GNU 14.2 from lesson 1. Two releases can produce different code, so this difference is worth raising in review (the checklist is in lesson 79). 

simulate:
  if: github.event_name != 'pull_request' || github.event.pull_request.head.repo.full_name == github.repository

This is a condition. It says the job runs when the event is not a pull request, or when the pull request comes from this same repository. A pull request from a fork has a different repository name, so the job is skipped. GitHub does not pass repository secrets to a workflow triggered from a forked repository, so without this line the job would run with no token and fail. Skipping it is the correct result here: the simulation cannot run for an outside contributor, and the other jobs still do. 

- name: Run the simulation
  uses: wokwi/wokwi-ci-action@v1
  with:
    token: ${{ secrets.WOKWI_CLI_TOKEN }}
    path: projects/0082-continuous-integration
    timeout: 10000
    expect_text: 'LED on'

The action takes the token from the repository secret named WOKWI_CLI_TOKEN. The expression ${{ secrets.WOKWI_CLI_TOKEN }} is how the workflow reads a secret without writing its value into the file. The path input points at the folder with wokwi.toml, and timeout and expect_text match the CLI options in the table above. The action's README lists further inputs, such as fail_text and scenario.

Never put a token in the YAML file or in a commit. Anyone who can read the repository can read the file, and the token lets them run simulations under your account. Store it in the repository settings as a secret, and reference it as ${{ secrets.WOKWI_CLI_TOKEN }}. Pull requests from forks do not receive secrets, which is why the sample's simulate job has an if line.

Wokwi in CI: what the simulation proves

The simulation proves that the firmware boots on the simulated board, that the code path to the expected text runs, and that nothing faults before that text appears. It does not prove that the blink is the right speed on a real board, because the simulator's clock and peripherals are a model. The limits in NOTES.md matter here: some peripherals are not simulated on the Blue Pill, so a test that depends on them cannot pass in the pipeline. A good CI design uses the simulation for the things it can check, and keeps the rest for hardware tests.

The sample's main.c carries the expected text on a line of its own, // EXPECT: LED on. That is the convention the local script reads, and the pipeline's expect_text input repeats it. Keeping both in step prevents a common error, which the mistakes section describes.

In real projects

In a professional team, the pipeline is a gate. The team configures the repository so that a merge is blocked until the required checks pass. The names of those checks are part of the project's configuration, and a reviewer expects to see them listed in the pull request. A reviewer also reads changes to the workflow file itself with care, because a change there can weaken the gate, for example by removing --error-exitcode or by adding a job that skips the tests. Changing the pipeline is a code change, and it gets the same review.

Teams separate fast checks from slow ones, as the sample does, so that a developer learns about a compile error in minutes and a simulation failure later. They also keep the outputs of each run. When a field report arrives weeks later for a release, the artifact of that release's pipeline run is the binary to decode (lesson 84). A pipeline that keeps no artifacts makes that impossible.

Hint

The expect line is read by a regular expression, not by the C compiler. Look at tools/verify_projects.py, the lines that read EXPECT. The pattern looks for two slashes, optional spaces, the word EXPECT and a colon. It does not require the line to start at column 1.

Common mistakes and how to spot them

Mistake 1: cppcheck without --error-exitcode. The static-analysis job stays green while cppcheck prints findings. On this machine, cppcheck 2.22.0 run on the lesson 83 starter with the warning and style checks on printed several errors and style findings, and it still exited with 0. With --error-exitcode=1 the same run exited with 1. The symptom is a green job with error lines in its log. The fix is the flag, as in the sample.

Mistake 2: a missing or misspelled EXPECT line. The local script finds no expected text and runs the simulator without one. A run that reaches its timeout then counts as a pass, so the check that was supposed to prove LED on proves nothing. The symptom is a passing verify_projects.py --sim that never checked the text. The fix is to keep the line exactly in the form // EXPECT: text, with the two slashes, and to check the log once after you add it.

Mistake 3: a secret in the file. A developer pastes the token into ci.yml to test it, and commits the change. Now the token is in the history of the repository, and anyone who reads the history can run simulations under the account. The symptom is a token in git log. The fix is to revoke the token, create a new one, store it as a repository secret, and remove the value from the file before the next commit.

Mistake 4: a compiler that differs from the one on your laptop. The laptop has Arm GNU 14.2, and the workflow installs 15.3.Rel2. A warning that appears only in CI, or a map file whose sizes differ between the two, is the symptom. The fix is to pin the same release in the setup script and the workflow, or to record the difference in the project so that the next person knows it is there.

Mistake 5: a timeout in the wrong unit. A developer writes timeout: 10, meaning ten seconds, but the value is in simulated milliseconds, so the run lasts 10 ms. The symptom is a run that ends before the first line prints, with the expected text reported as missing. The fix is to write the unit in a comment next to the value, or to write the value in milliseconds as the sample does.

Summary

  • CI runs a fixed list of checks on a clean runner for every push, so a result does not depend on one laptop.
  • A workflow has jobs, jobs have steps, and needs: orders the jobs. A job passes or fails by exit code.
  • The firmware pipeline is host tests and static analysis first, then the build, then the simulation, with the build outputs kept as artifacts.
  • cppcheck exits with 0 even when it reports findings, unless you pass --error-exitcode=1.
  • The simulator's timeout is in simulated milliseconds. The default CLI timeout is 30000, which is 30 simulated seconds.
  • The expected serial text comes from a // EXPECT: line in main.c, and a missing line weakens the check quietly.
  • Secrets live in repository settings, and a fork's pull request does not receive them, so the simulation job is skipped for forks.
  • Pin the toolchain release in the workflow and in your setup, and treat a change to the workflow as a code change.
