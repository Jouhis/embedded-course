Continuous integration

Automatic checks on every push

By the end of this lesson you can run the firmware checks locally with verify_projects.py, and say what each job of a firmware CI workflow does and why.

Checks that people forget to run

The last lessons introduced the checks one at a time, lesson 80 running unit tests on the PC and lesson 81 faking the bus so a driver could be tested without a sensor, while lesson 41 showed the build from source to ELF, map and hex file and lesson 1 installed the Arm toolchain on your PC. Each check works when run by hand, and the problem this lesson solves is that people forget to run them, or run them on a different machine.

On teams this happens often. A colleague changes a shared driver, runs the tests on a laptop with the right toolchain and a leftover file, and pushes, after which the build fails on the team's compiler or the simulation shows a boot loop that nobody tested. Continuous integration (CI) removes both problems, a server called a runner taking every push, starting from a clean machine and running a fixed list of checks in the same order, with the result recorded against the commit, so that a bad change is visible before a reviewer reads it.

In firmware work a CI job usually has five stages, the host unit tests, static analysis (lesson 83), the firmware build, the simulation and the keeping of outputs, while the habits deciding what reaches the pipeline, such as branches and code review, are in lesson 79.

Runners, workflows, jobs, steps and exit codes

A runner is the machine that runs a job, the sample workflow using a hosted Linux runner, ubuntu-latest, which GitHub starts fresh for every job. On a clean machine nothing from your laptop is present, no installed tools, no leftover build folder and no environment variable, so a job that passes there shows that the change does not depend on something only you have.

A workflow is a YAML file describing when to run and what to do, organised into jobs, each made of steps, a step being either an action, a packaged piece of automation someone else wrote, or a run: block of shell commands. Jobs run in parallel unless linked with needs:, which makes one job wait for others to pass.

Every step reports success or failure through an exit code, the number a program returns when it stops, zero meaning success and any other value failure, and the CI server decides the outcome of a job from exit codes rather than from what the program printed. This matters because some tools print a warning and still exit with zero, as the static-analysis job below shows, a case that is also one of the common mistakes.

An artifact is a file a job keeps after it finishes (glossary: artifact (CI)), the useful firmware artifacts being the .elf for a debugger, the .map for the memory layout (lesson 41) and the .hex for flashing. When a run fails on the server, the artifact lets you examine the very binary that failed instead of a rebuilt one.

The order of the CI jobs

The jobs are ordered by cost. The host unit tests run in seconds on a plain Linux runner without any board toolchain, static analysis (lesson 83) comes next because it fails fast on warnings before anything is built for the board, and the firmware build uses one Arm GCC release pinned in the workflow, because a compiler change can move bugs and change code size, while the simulation comes last, because it needs the firmware and takes longest.

The simulation checks what the compiler cannot, the boot path, the startup code, the clock setup and the serial output, since a build that links cleanly can still hang at boot and only a run shows it. In a real project the simulation is also where a team checks the behaviour of the whole program with its peripherals, and a simulated board makes that check cheap enough for every push.

CI resembles a smoke alarm in a shared kitchen, checking the air every time someone cooks, which here means every push, so that a burnt pan is noticed while the cook is still at the stove rather than at dinner time, the release, when nobody remembers whose pan it was. The comparison breaks on coverage, though, because an alarm senses any smoke, whereas CI detects only the faults its checks were written for.

Local checks with verify_projects.py

The course provides the same checks on your own machine. tools/verify_projects.py builds a project, lints its Wokwi diagram and checks that the paths in wokwi.toml point at real files, and with --sim it also runs the simulator. Its help text says that the expected serial text comes from a line in main.c of the form // EXPECT: <text>, which the script reads with the regular expression //\s*EXPECT:\s*(.+) and passes to the simulator as --expect, while without the line the script still runs the simulator but with no text to check.

That last point is why the convention matters. The course's tools/sim.py wraps the Wokwi command-line tool, running the firmware for a time limit and deciding pass or fail, and with no expected text a run that reaches its time limit without an error counts as a pass, so a missing EXPECT line quietly weakens the check.

Wokwi CLI options for tests

wokwi-cli runs a project headless, without a window, its options being documented on the CLI usage page, and the table lists those a test needs.

OptionWhat it does
--timeout <ms>Simulated milliseconds before the run stops. The default is 30000. It is simulated time, not wall-clock time.
--expect-text <text>The run passes only if this text appears in the output (the serial monitor).
--fail-text <text>The run fails as soon as this text appears, for example HardFault.
--serial-log-file <path>Saves the serial output, so you can read the log of a failed run.
--scenario <path>Runs a YAML file of steps (below).
--timeout-exit-code <number>The process exit code when the timeout is reached. The default is 42.
The timeout is simulated time. A 10000 ms timeout is 10 simulated seconds, and the simulator may run faster or slower than the clock on the wall. The GitHub Action has its own default, 10000, and the sample sets it explicitly.

Worked example: one push through the pipeline

We follow one push through the sample workflow with the project's real numbers. The LED period is 1 000 ms, so led_half_period_ms(1000) returns 500, the function in src/led_pattern.c halving the period, and the firmware prints LED on, waits 500 ms, prints LED off and repeats, under a simulation timeout of 10 000 ms of simulated time. Before reading the steps, predict which jobs run in parallel and which wait.

  1. The push starts the run. The workflow says on: push and on: pull_request, so GitHub starts it on the runner pool for every push and every pull request.
  2. Two jobs start at once. host-tests and static-analysis have no needs: line, so they run in parallel, each starting with actions/checkout, which copies the repository onto the clean runner.
  3. The host tests build and run. The job installs CMake and Ninja, configures and builds the host-tests folder and runs ctest --output-on-failure, the test led_half_period_ms checking that 1000 gives 500, 5 gives 2 and 0 or 1 give 1, and if any test fails, ctest exits with a failure code and the job stops.
  4. Static analysis runs cppcheck. It checks the pure C sources and the host-test folder with --enable=warning,style, and the flag --error-exitcode=1 is what makes a finding fail the job, since without it the exit code is 0 and the job stays green, as the mistakes section shows.
  5. The firmware job waits. firmware has needs: [host-tests, static-analysis], so it starts only after both pass, installs Arm GCC release 15.3.Rel2, builds in Debug and uploads the .elf, .hex and .map as an artifact named firmware.
  6. The simulation runs last. simulate waits for firmware, downloads the artifact into the build folder and runs the Wokwi action with timeout: 10000 and expect_text: 'LED on', the first LED on appearing soon after boot, so the text is found early, while a run that never showed it would stop at 10 simulated seconds, about ten blink cycles.
  7. The result comes back. If LED on appears, the simulator exits with 0 and the job passes, whereas if it never appears, the run fails at the timeout, and either way the firmware job's artifacts stay available for a human to open.

The local equivalent of steps 3 to 6 is python -I tools/verify_projects.py 0082 for the build, lint and path check, and the same command with --sim for the simulation. The local run cannot replace the pipeline, because it runs on your machine with its toolchain, but it catches most problems early, so the pipeline only confirms what you already saw.

Wokwi automation scenarios

--expect-text answers one question, whether a given text appears, whereas a scenario answers a sequence of questions in order, being a YAML file of steps, a feature the Wokwi docs mark as alpha, so its format may change. The sample has one, smoke.scenario.yaml. 

name: 'LED blinks on the serial monitor'
version: 1
author: 'course'
steps:
  - wait-serial: 'LED on'
  - delay: 500ms
  - wait-serial: 'LED off'

The file reads as a script for the simulator, the first step blocking until LED on appears, the second waiting 500 ms of simulated time, one half period of the blink, and the third waiting for LED off, so a test with this scenario checks that the LED toggles, which the single-text test does not. The automation page lists the other step types, expect-pin checking a pin level, set-control changing a part such as a button and write-serial sending text to the firmware, and since the feature is alpha, the page is worth checking before depending on any step.

The scenario runs from the project folder with wokwi-cli . --scenario smoke.scenario.yaml, its path being relative to the project root, as the automation scenarios page describes.

The workflow file line by line

GitHub reads workflows only from .github/workflows/ at the root of the repository, so the sample's projects/0082-continuous-integration/.github/workflows/ci.yml is a copy for reading rather than a file GitHub runs from this folder. It has four jobs, host-tests, static-analysis, firmware and simulate, and the lines that matter follow. 

on:
  push:
  pull_request:

The on: block lists the events that start the workflow, here a push to any branch and a pull request, so a pull request from your own branch runs the workflow twice, once for the push and once for the pull request, a cost a branch filter can later reduce. 

static-analysis:
  steps:
    - name: Check the pure C sources
      run: >
        cppcheck --enable=warning,style --inline-suppr --error-exitcode=1 --std=c11 --quiet
        projects/0082-continuous-integration/src
        projects/0082-continuous-integration/host-tests

The run: > form folds the following lines into one shell command, in which --enable=warning,style turns on the warning and style checks, as in lesson 83, and --inline-suppr lets a source file silence one finding with a comment, so that a known false alarm does not block the team while each suppression stays visible in review. --error-exitcode=1 makes cppcheck return 1 when it reports anything, so the step fails, --std=c11 sets the language standard, and the two paths are the folders to check. 

firmware:
  needs: [host-tests, static-analysis]
  steps:
    - uses: carlosperate/arm-none-eabi-gcc-action@v1
      with:
        release: '15.3.Rel2'

needs: makes the job wait until both listed jobs pass, the uses: line runs an action, a packaged step by another author, and with: sets its inputs, the input here choosing which Arm GCC release to install, with 15.3.Rel2 given as the example in the action's README. A real project pins one release in both the workflow and the developer setup, and since your laptop has Arm GNU 14.2 from lesson 1 and two releases can produce different code, the difference is worth raising in review (the checklist is in lesson 79). 

simulate:
  if: github.event_name != 'pull_request' || github.event.pull_request.head.repo.full_name == github.repository

This condition runs the job when the event is not a pull request, or when the pull request comes from this same repository, so a pull request from a fork, having a different repository name, skips the job. GitHub does not pass repository secrets to a workflow triggered from a forked repository, so without this line the job would run without a token and fail, which makes skipping the correct result, the simulation being impossible for an outside contributor while the other jobs still run. 

- name: Run the simulation
  uses: wokwi/wokwi-ci-action@v1
  with:
    token: ${{ secrets.WOKWI_CLI_TOKEN }}
    path: projects/0082-continuous-integration
    timeout: 10000
    expect_text: 'LED on'

The action takes the token from the repository secret named WOKWI_CLI_TOKEN, the expression ${{ secrets.WOKWI_CLI_TOKEN }} letting the workflow read a secret without writing its value into the file. The path input points at the folder with wokwi.toml, timeout and expect_text match the CLI options in the table above, and the action's README lists further inputs such as fail_text and scenario.

Never put a token in the YAML file or in a commit. Anyone who can read the repository can read the file, and the token lets them run simulations under your account. Store it in the repository settings as a secret, and reference it as ${{ secrets.WOKWI_CLI_TOKEN }}. Pull requests from forks do not receive secrets, which is why the sample's simulate job has an if line.

What a CI simulation proves

The simulation proves that the firmware boots on the simulated board, that the code path to the expected text runs and that nothing faults before the text appears, but not that the blink has the right speed on a real board, because the simulator's clock and peripherals are a model. The limits in NOTES.md matter here, some peripherals not being simulated on the Blue Pill, so a test depending on them cannot pass in the pipeline, and a good CI design uses the simulation for what it can check and leaves the rest to hardware tests.

The sample's main.c carries the expected text on a line of its own, // EXPECT: LED on, the convention the local script reads and that the pipeline's expect_text input repeats, and keeping the two in step prevents a common error, which the mistakes section describes.

Common mistakes and how to spot them

cppcheck without an error exit code

The static-analysis job stays green with error lines in its log, because cppcheck exits with 0 even when it prints findings, as cppcheck 2.22.0 did on this machine when run on the lesson 83 starter with the warning and style checks on, printing several errors and style findings, whereas with --error-exitcode=1 the same run exited with 1. Add the flag, as the sample does.

A missing or misspelled EXPECT line

verify_projects.py --sim passes without ever checking the text, because the script found no expected text and ran the simulator without one, so a run reaching its timeout counted as a pass and the check meant to prove LED on proved nothing. Keep the line exactly in the form // EXPECT: text, with the two slashes, and check the log once after adding it.

A secret committed in the workflow file

A token appears in git log, because a developer pasted it into ci.yml to test it and committed the change, so anyone reading the history can run simulations under the account. Revoke the token, create a new one, store it as a repository secret and remove the value from the file before the next commit.

A CI compiler that differs from the laptop's

A warning appears only in CI, or the map file sizes differ between the two, because the laptop has Arm GNU 14.2 while the workflow installs 15.3.Rel2. Pin the same release in the setup script and the workflow, or record the difference in the project so the next person knows it is there.

A timeout in the wrong unit

The run ends before the first line prints and reports the expected text missing, because a developer wrote timeout: 10 meaning ten seconds, whereas the value is in simulated milliseconds, so the run lasted 10 ms. Write the unit in a comment next to the value, or give the value in milliseconds, as the sample does.

The pipeline as a merge gate

In a professional team the pipeline is a gate, the repository being configured so that a merge is blocked until the required checks pass, whose names belong to the project's configuration and appear in each pull request. Reviewers read changes to the workflow file itself with care, because such a change can weaken the gate, for example by removing --error-exitcode or adding a job that skips the tests, so changing the pipeline is a code change and receives the same review.

Teams separate fast checks from slow ones, as the sample does, so that a developer learns about a compile error in minutes and a simulation failure later, and they keep the outputs of each run, because when a field report for a release arrives weeks later, the artifact of that release's pipeline run is the binary to decode (lesson 84), which a pipeline keeping no artifacts makes impossible.

Summary

  • CI runs a fixed list of checks on a clean runner for every push, so a result does not depend on one laptop.
  • A workflow has jobs made of steps, needs: orders the jobs, and a job passes or fails by exit code.
  • The firmware pipeline runs host tests and static analysis first, then the build and then the simulation, keeping the build outputs as artifacts.
  • cppcheck exits with 0 even when it reports findings unless --error-exitcode=1 is passed.
  • The simulator's timeout is in simulated milliseconds, the default CLI timeout of 30000 being 30 simulated seconds.
  • The expected serial text comes from a // EXPECT: line in main.c, and a missing line quietly weakens the check.
  • Secrets live in repository settings and are withheld from a fork's pull request, so the simulation job is skipped for forks.
  • The toolchain release is pinned in both the workflow and the setup, and a change to the workflow is treated as a code change.
