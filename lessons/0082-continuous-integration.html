Continuous integration for firmware

Every push builds the firmware, runs the tests, checks the code and simulates the board. A failing check blocks the change before a reviewer sees it.

By the end of this lesson you can run the firmware checks locally with verify_projects.py, and say what each job of a firmware CI workflow does and why.

The idea

Continuous integration (CI) is a server that runs a fixed list of checks on every change. The checks are the same ones you run at your desk, but they run on every push, on a clean machine, so "it works on my laptop" cannot slip through. In firmware work, a CI job usually has five stages: build, host unit tests (lesson 80), static analysis, simulation, and keeping the outputs. The branch and review habits that decide what reaches the pipeline are in lesson 79. Interviewers ask "what does your pipeline look like?" to see whether you can separate fast checks from slow ones, and whether you keep the checks reproducible on a laptop.

Why each job exists

Host unit tests (lesson 80) run in seconds on a plain Linux runner, with no toolchain for the board. Static analysis (lesson 83) fails the job on warnings before anything is built for the board. The build uses the same Arm GCC release every time, pinned in the workflow, because a compiler change can move bugs and sizes. The simulation runs the firmware on a virtual board, so the boot path, the serial output and the timing are checked, not just the compile.

Artifacts are the build outputs the job keeps: the .elf for a debugger, the .map for the memory layout (lesson 41), and the .hex for flashing. When a test fails on the server, the artifact lets you look at the same binary.

Wokwi CLI: the flags that matter

wokwi-cli runs a project headless. The options that matter for a test (from the CLI usage page):

OptionWhat it does
--timeout <ms>Simulated milliseconds before the run stops. The default is 30000. It is simulated time, not wall-clock time.
--expect-text <text>The run passes only if this text appears on the serial monitor.
--fail-text <text>The run fails as soon as this text appears, for example HardFault.
--serial-log-file <path>Saves the serial output, so you can read the log of a failed run.
--scenario <path>Runs a YAML file of steps (below).
The timeout is simulated time. A 10000 ms timeout is 10 simulated seconds, and the simulator may run faster or slower than the clock on the wall.

Scenarios: steps instead of one text match

A scenario is a YAML file of steps that run in order. The Wokwi docs describe it as an alpha feature, so its format may change. The sample has one (smoke.scenario.yaml): 

name: 'LED blinks on the serial monitor'
version: 1
author: 'course'
steps:
  - wait-serial: 'LED on'
  - delay: 500ms
  - wait-serial: 'LED off'

The automation page lists steps such as set-control, which presses a virtual button, and expect-pin, which checks a pin level. Use the steps the docs list, and check the page before you rely on one. Run it from the project folder with wokwi-cli . --scenario smoke.scenario.yaml, as the automation scenarios page shows.

The workflow file

GitHub reads workflows from .github/workflows/ at the repository root. The sample's projects/0082-continuous-integration/.github/workflows/ci.yml has four jobs: host-tests, static-analysis, firmware and simulate. The last job uses the Wokwi action, wokwi/wokwi-ci-action@v1, from the action repository. It takes the token from a repository secret named WOKWI_CLI_TOKEN. The Arm toolchain comes from carlosperate/arm-none-eabi-gcc-action@v1.

Never put a token in the YAML file or in a commit. Anyone who can read the repository can read the file, and the token lets them run simulations under your account. Store it in the repository settings as a secret, and reference it as ${{ secrets.WOKWI_CLI_TOKEN }}. Pull requests from forks do not receive secrets, which is why the sample's simulate job has an if line.

The sample uses the Arm toolchain release 15.3.Rel2, which the action documents. Your laptop has Arm GNU 14.2 (lesson 1). Two releases can produce different code, so a real project pins one release in both places, and this is a reasonable thing to raise in review (the checklist is in lesson 79).

Model answer

Every push runs three things in parallel, first: host unit tests on a plain Linux runner, static analysis with the warning flags and cppcheck, and a cross-build with a pinned Arm GCC release. Only when those pass does the pipeline run the simulation, with a timeout and an expected serial line, and keep the ELF and map as artifacts. Secrets live in the repository settings, and the simulation is skipped for forks. Locally, a single script runs the same checks, so a failure reproduces on the laptop before anyone else sees it.
