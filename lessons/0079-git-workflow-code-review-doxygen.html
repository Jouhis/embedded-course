Git workflow, code review and Doxygen

Firmware teams live or die by their history. Small commits, short branches and a review checklist keep a change safe to merge, and a comment style that the tools can read keeps the code explained.

By the end of this lesson you can create a repository for a project copy, commit to it, make a branch, merge it with a merge commit, ignore the build/ folder, and list the five firmware review checks that a reviewer should look for.

The idea: branches that merge often

Two branching styles are common. In trunk-based development, everyone merges small changes into one main line, often every day, and the branches that exist are short-lived (trunkbaseddevelopment.com). In git-flow, the team keeps long-lived develop and release branches, and a change waits in a feature branch until its release. Trunk-based development fits firmware teams that ship often and test every merge; git-flow fits teams that must support several released versions at once.

A branch is only a name for a commit, and a merge joins two histories. Git stores each commit with its parents, so a merge creates a commit with two parents. The Pro Git book explains branching and merging in its basic chapter (Pro Git, chapter 3.2, Basic Branching and Merging).

Small commits and their messages

A commit should do one thing that you can name. The first line of the message is a short sentence in the imperative mood, such as Blink twice as fast, and the body, if any, explains why. A reviewer reads the messages first, so a message like fix stuff hides the change. A commit that you can revert on its own is the goal, because a bad change can then go back without losing the good ones around it.

Review: what a firmware reviewer checks

A pull request asks a second person to read the change before it reaches the main branch. For firmware, five checks catch most of the bugs that do not show up in a simulator.

  1. volatile on anything an interrupt and main both touch. Without it the compiler may keep the value in a register (lesson 46).
  2. ISR safety. The interrupt does little work, never blocks, clears its own flag, and shares data with main only through a safe path such as a ring buffer or a critical section (lesson 57).
  3. Integer overflow and sign. A subtraction of unsigned values wraps, a signed overflow is undefined, and a comparison of a timer must subtract first (lessons 45 and 73).
  4. Error paths. Every call that can fail is checked, and each early return undoes what the function already did, such as a pin left driven or a bus left busy.
  5. Magic numbers. Each literal that has a meaning has a name with its unit, such as DEBOUNCE_TICKS or I2C_TIMEOUT_US, so a reviewer can check it against the datasheet.
The checklist is a starting point, not a standard. The MISRA and Barr Group coding standards list many more rules, and the static analysis lesson (83) shows how a tool checks some of them.

.gitignore: keep the output out

The build/ folder is generated by CMake, and a fresh clone rebuilds it. A line build/ in .gitignore tells git to leave the whole folder alone, so git status shows only your source changes. Keep the VS Code files that the project needs (.vscode/launch.json and tasks.json), because they describe how to build and debug the project.

Doxygen: comments the tools can read

Doxygen reads special comments in the source and builds a reference from them. A block that starts with /** is documentation, and a tag such as @brief or @param marks each part. The Doxygen manual describes the blocks and their tags (Doxygen manual: documenting the code). 

/**
 * @file led.h
 * @brief LED driver interface. Backends: led_gpio.c (a pin) or led_fake.c (a log line).
 */

/**
 * @brief Turn the LED on or off.
 * @param on true lights the LED.
 * @note Safe to call only after led_init().
 */
void led_set(bool on);

A Doxyfile is the configuration file that tells Doxygen which files to read and what to write. The options you need first are PROJECT_NAME, INPUT (the folders to read), RECURSIVE (read subfolders too), GENERATE_HTML and OUTPUT_DIRECTORY. The option names are in the Doxygen configuration reference (Doxygen manual: configuration). The manual says a default file is named Doxyfile; the flag that writes one, doxygen -g, is not checked in this course, so run doxygen --help on your install before you rely on it.

Doxygen is optional for this course. It is not installed on the workspace PC. You can install it later with winget install DimitriVanHeesch.Doxygen, but the lesson does not run it. A comment with a wrong unit is worse than no comment, so write the units, and update a comment when you change the code.

Try it in Git Bash

The project is projects/0079-git-workflow. The starter is the blink project from lesson 2. You will copy it outside the course folder, make the copy a git repository, and practise the cycle of commit, branch and merge. The commands below were run in this order on a scratch copy during the course build. They give a clean git status after the build.

  1. Copy the starter to a folder of your own, outside the course. In Git Bash: cp -r /c/Users/juhos/embedded-course/projects/0079-git-workflow/starter ~/git-practice, then cd ~/git-practice. Remove any build/ folder that came with the copy, with rm -rf build: CMake stores the paths of the folder where it was configured, so a copied build cannot be reused.
  2. Create the repository and commit the project as it is: git init -b main, git add -A, git commit -m "Add blink project". If git asks for your name or email, set them once with git config --global user.name "Your Name" and git config --global user.email you@example.com.
  3. Create a .gitignore file that contains one line, build/. Commit it: git add .gitignore, then git commit -m "Ignore the CMake build folder".
  4. Make a feature branch and change the blink speed. Run git switch -c feature/faster-blink, then open main.c and change both sleep_ms(500) lines to sleep_ms(250). Commit with git commit -am "Blink twice as fast".
  5. Merge the branch back into main with a merge commit. Run git switch main, then git merge --no-ff feature/faster-blink -m "Merge feature/faster-blink". The --no-ff flag keeps the branch visible in the history even though a fast-forward was possible.
  6. Look at the result: git log --oneline --graph --decorate. You should see three commits and a branch that joins main.
  7. Check that the build folder is ignored. Build the copy with the course tool: python -I /c/Users/juhos/embedded-course/tools/build.py ~/git-practice. Then run git status. It should print nothing, because build/ is ignored.
Hint if git says "LF will be replaced by CRLF"

On Windows, git may print a warning about line endings. It comes from the line-ending setting of your machine, and it does not change the content of the commit. You can ignore it for this lesson.

Hint if the merge says "Already up to date"

You ran the merge on the feature branch instead of main. Check with git branch, which marks the current branch with *, then run git switch main and merge again.

"What do you check in a firmware code review, and what would you reject?" Answer out loud in 60 seconds, then compare.

Model answer

I check whether every variable shared with an interrupt is volatile, whether the interrupt does little work and never blocks, and whether arithmetic can overflow or compare signed values wrongly. I check that every error path releases what it took, and that every literal with a meaning has a named constant with its unit. I reject a change that mixes unrelated work in one commit, that has no test for new logic, or that adds a blocking call inside an interrupt. I ask for the change to be split when it does two things.
