Git workflow, code review and Doxygen

Firmware teams rely on their history. Small commits, short branches and a review checklist keep a change safe to merge, and a comment style that the tools can read keeps the code explained.

By the end of this lesson you can create a repository for a project copy, commit to it, make a branch, merge it with a merge commit, ignore the build/ folder, and list the five firmware review checks that a reviewer should look for.

The idea: branches that merge often

Two branching styles are common. In trunk-based development, everyone merges small changes into one main line, often every day, and the branches that exist are short-lived (trunkbaseddevelopment.com). In git-flow, the team keeps long-lived develop and release branches, and a change waits in a feature branch until its release. Trunk-based development fits firmware teams that ship often and test every merge; git-flow fits teams that must support several released versions at once.

A branch is only a name for a commit, and a merge joins two histories. Git stores each commit with its parents, so a merge creates a commit with two parents. The Pro Git book explains branching and merging in its basic chapter (Pro Git, chapter 3.2, Basic Branching and Merging).

Small commits and their messages

A commit should do one thing that you can name. The first line of the message is a short sentence in the imperative mood, such as Blink twice as fast, and the body, if any, explains why. A reviewer reads the messages first, so a message like fix stuff hides the change. A commit that you can revert on its own is the goal, because a bad change can then go back without losing the good ones around it.

Review: what a firmware reviewer checks

A pull request asks a second person to read the change before it reaches the main branch. For firmware, five checks catch many of the bugs that do not show up in a simulator.

  1. volatile on anything an interrupt and main both touch. Without it the compiler may keep the value in a register (lesson 46).
  2. ISR safety. The interrupt does little work, never blocks, clears its own flag, and shares data with main only through a safe path such as a ring buffer or a critical section (lesson 57).
  3. Integer overflow and sign. A subtraction of unsigned values wraps, a signed overflow is undefined, and a comparison of a timer must subtract first (lessons 45 and 73).
  4. Error paths. Every call that can fail is checked, and each early return undoes what the function already did, such as a pin left driven or a bus left busy.
  5. Magic numbers. Each literal that has a meaning has a name with its unit, such as DEBOUNCE_TICKS or I2C_TIMEOUT_US, so a reviewer can check it against the datasheet.
The checklist is a starting point, not a standard. The MISRA and Barr Group coding standards list many more rules, and the static analysis lesson (83) shows how a tool checks some of them.

.gitignore: keep the output out

The build/ folder is generated by CMake, and a fresh clone rebuilds it. A line build/ in .gitignore tells git to leave the whole folder alone, so git status shows only your source changes. Keep the VS Code files that the project needs (.vscode/launch.json and tasks.json), because they describe how to build and debug the project.

Doxygen: comments the tools can read

Doxygen reads special comments in the source and builds a reference from them. A block that starts with /** is documentation, and a tag such as @brief or @param marks each part. The Doxygen manual describes the blocks and their tags (Doxygen manual: documenting the code). 

/**
 * @file led.h
 * @brief LED driver interface. Backends: led_gpio.c (a pin) or led_fake.c (a log line).
 */

/**
 * @brief Turn the LED on or off.
 * @param on true lights the LED.
 * @note Safe to call only after led_init().
 */
void led_set(bool on);

A Doxyfile is the configuration file that tells Doxygen which files to read and what to write. The options you need first are PROJECT_NAME, INPUT (the folders to read), RECURSIVE (read subfolders too), GENERATE_HTML and OUTPUT_DIRECTORY. The option names are in the Doxygen configuration reference (Doxygen manual: configuration). The doxygen -g option writes a template configuration file, and when you run doxygen without a configuration argument it looks for a file named Doxyfile (Doxygen manual: usage). The command is not run in this course, so check the output of doxygen --help on your install before you rely on it.

Doxygen is optional for this course. It is not installed on the workspace PC. You can install it later with winget install DimitriVanHeesch.Doxygen, but the lesson does not run it. A comment with a wrong unit is worse than no comment, so write the units, and update a comment when you change the code.

Why a firmware team uses version control

A firmware project changes in small ways that have large effects. One constant changes from 500 to 250, and the blink doubles. One line in an interrupt handler moves, and a sensor starts losing samples. A team needs to know exactly which change did what, to undo one change without undoing the others, and to show that a release contains only reviewed code. Version control answers all three questions. Without it, the team's knowledge is in people's heads, the file on the shared drive, and the copy that was flashed last month.

Git is the tool that most teams use. Lesson 41 showed the build from the command line, and the build folder it produces is one of the things Git should not store. This lesson adds the history: a sequence of snapshots, each with a message, and a way to work on several lines of change at once.

The concepts, one at a time

Repository and commit

A repository is a folder whose history Git keeps in a hidden .git folder. A commit is a snapshot of the tracked files at one moment, with a message and a link to the commit before it. Git stores each snapshot as a set of objects identified by a hash of their content, so a commit cannot change without its identifier changing too. That property is why a history can be trusted: if someone edits an old commit, every later identifier changes, and the difference is visible.

Branch and merge

A branch is a name that points at one commit. When you commit on a branch, the name moves forward to the new commit. Creating a branch costs almost nothing, because it is only a name. A merge joins the history of two branches. The merge commit has two parents, which is how Git records that two lines of work were combined. The Pro Git book explains the same model in its basic branching chapter (Pro Git, chapter 3.2).

A merge can be a fast-forward, where the branch is simply ahead of main and Git moves the name. A --no-ff merge always creates the merge commit, even when a fast-forward is possible. The lesson's hands-on task uses it, so the history shows that a feature existed.

Worked example: counting commits through the lesson

Count the commits in the practice repository to see what the history records. The first commit adds the blink project. The second adds .gitignore. The third is on the feature branch and changes two lines. The fourth is the merge, which has two parents: the second commit on main, and the third on the feature branch. Four commits in total, and the merge commit is the only one with two parents. If you see a history with a different shape, a commit was made on the wrong branch, and the graph tells you which one.

The quiz at the end of this lesson uses the same count. Each commit adds one to the number, and a merge with --no-ff adds one more, even though it carries no new code of its own.

Small commits and their messages

A small commit is one that a reviewer can read in a minute, and that you can revert without reverting anything else. Revert is a commit that undoes an earlier one. If a blink change and an I2C change are in one commit, reverting the blink change also reverts the I2C change. Two commits make that impossible. The message is for the reviewer and for the person who reads the history in five years, so the first line should say what the change does in the imperative mood, such as Blink twice as fast, and the body should say why.

Code review

A code review is a second person reading a change before it reaches the main branch. In a hosted tool it is called a pull request or a merge request. The reviewer reads the diff, which is the set of lines that changed, and comments on the lines that need work. For firmware, the reviewer checks what a simulator cannot. The five checks below are a starting list.

Worked examples of the five checks

  1. volatile. A main loop waits for a flag that an interrupt sets: while (!flag) { }. The compiler reads flag once, sees that the loop body does not change it, and may turn the loop into an infinite loop with one load. The fix is volatile bool flag, so that each test reads memory. Lesson 46 covers the rule.
  2. ISR safety. An interrupt calls sleep_ms(1). The interrupt cannot finish until the time passes, and every other interrupt waits. The fix is to set a flag in the handler and do the work in main, which lesson 57 explains.
  3. Integer wraparound. A timer compares now < deadline with 32-bit unsigned values. Suppose deadline is 0xFFFFFFF0 and now is 0x00000005, which is 21 ticks later after the counter wraps. The comparison says now is smaller, so the deadline looks far away. Subtracting first, now - deadline, gives 0x15, which is 21 in unsigned arithmetic, and the test is right. Lesson 73 shows the same rule.
  4. Error paths. A function claims a bus, starts a transfer, and fails halfway. If the early return skips the release, the bus stays claimed, and every later call fails for a reason that is hard to see. Each early return must undo what the function did before it.
  5. Magic numbers. The starter has sleep_ms(500) in two places. A reviewer asks what 500 means. The answer is half a period, in milliseconds, and it should be a named constant such as HALF_PERIOD_MS. Then the two places change together, and the datasheet value can be checked against the name.

Common mistakes and how to spot them

  1. Everything in one commit. A developer commits a blink change, an I2C fix and a README update together with the message "updates". The symptom appears later: a revert removes the I2C fix, and the bug returns. The fix is to commit each change separately, using git add -p to pick the lines that belong together.
  2. The build folder is committed. The first git add -A adds build/, with absolute paths from one PC. The symptom is a diff of hundreds of generated files on every build, and a clone that fails because the paths do not exist on another machine. The fix is the .gitignore line from the hands-on task, and git rm -r --cached build to stop tracking files that were already added.
  3. Merging the wrong way round. A developer is on the feature branch and runs git merge on it. The output says Already up to date, and nothing reaches main. The symptom is that the change is missing from main after a successful merge command. The fix is git switch main first, then the merge, as the hint in the hands-on task says.
  4. A comment with a wrong unit. A Doxygen block says @param timeout ms and the function takes microseconds. The symptom is a timeout a thousand times too short, with the documentation saying it is correct. The fix is to write the unit in the name, as the timeout constant in the hal header does, and to update the comment in the same commit as the code.

Doxygen, briefly

Doxygen reads the /** ... */ blocks and builds a reference. A @file block describes the file, @brief gives a one-line summary, @param names each argument and its meaning, and @note gives a warning or a condition. Good Doxygen is short, accurate and placed next to the declaration. The tool does not check whether the text is right, so a reviewer reads the comments with the same care as the code.

In real projects

Teams that ship firmware often run trunk-based development, with short branches that merge to the main line most days, and they run tests on every merge. The review is a required step, and the reviewer is someone who knows the hardware. A typical review of a driver checks the five points above, asks for a test of the new logic, and rejects a change that mixes two unrelated fixes. In an interview, a candidate who can say what a clean commit looks like, how they keep a branch short, and what they check in a volatile or an ISR is showing the professional habits that the job depends on.

Summary

  • A commit is a named snapshot. A branch is a name that moves. A merge commit has two parents.
  • Keep commits small, so that a revert removes one change and nothing else.
  • Ignore the build folder with .gitignore. Keep the VS Code files the project needs.
  • Use --no-ff when the feature branch should stay visible in the history.
  • A review checks volatile, ISR safety, integer wraparound, error paths and named constants.
  • A Doxygen comment is only as good as its units and its last update.

The project is projects/0079-git-workflow. The starter is the blink project from lesson 2. You will copy it outside the course folder, make the copy a git repository, and practise the cycle of commit, branch and merge. The commands below were run in this order on a scratch copy during the course build. They give a clean git status after the build.

  1. Copy the starter to a folder of your own, outside the course. In Git Bash: cp -r /c/Users/juhos/embedded-course/projects/0079-git-workflow/starter ~/git-practice, then cd ~/git-practice. Remove any build/ folder that came with the copy, with rm -rf build: CMake stores the paths of the folder where it was configured, so a copied build cannot be reused.
  2. Create the repository and commit the project as it is: git init -b main, git add -A, git commit -m "Add blink project". If git asks for your name or email, set them once with git config --global user.name "Your Name" and git config --global user.email you@example.com.
  3. Create a .gitignore file that contains one line, build/. Commit it: git add .gitignore, then git commit -m "Ignore the CMake build folder".
  4. Make a feature branch and change the blink speed. Run git switch -c feature/faster-blink, then open main.c and change both sleep_ms(500) lines to sleep_ms(250). Commit with git commit -am "Blink twice as fast".
  5. Merge the branch back into main with a merge commit. Run git switch main, then git merge --no-ff feature/faster-blink -m "Merge feature/faster-blink". The --no-ff flag keeps the branch visible in the history even though a fast-forward was possible.
  6. Look at the result: git log --oneline --graph --decorate. You should see four commits: the two setup commits, the feature commit and the merge commit. The feature branch joins main at the merge, and the graph shows the fork and the join.
  7. Check that the build folder is ignored. Build the copy with the course tool: python -I /c/Users/juhos/embedded-course/tools/build.py ~/git-practice. Then run git status. It should print nothing, because build/ is ignored.
Hint if git says "LF will be replaced by CRLF"

On Windows, git may print a warning about line endings. It comes from the line-ending setting of your machine, and it does not change the content of the commit. You can ignore it for this lesson.

Hint if the merge says "Already up to date"

You ran the merge on the feature branch instead of main. Check with git branch, which marks the current branch with *, then run git switch main and merge again.

"What do you check in a firmware code review, and what would you reject?" Answer out loud in 60 seconds, then compare.

Model answer

I check whether every variable shared with an interrupt is volatile, whether the interrupt does little work and never blocks, and whether arithmetic can overflow or compare signed values wrongly. I check that every error path releases what it took, and that every literal with a meaning has a named constant with its unit. I reject a change that mixes unrelated work in one commit, that has no test for new logic, or that adds a blocking call inside an interrupt. I ask for the change to be split when it does two things.
