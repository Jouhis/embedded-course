Version history, peer review and code documentation

By the end of this lesson you can create a repository for a project copy, commit to it, make a branch, merge it with a merge commit, ignore the build/ folder, and list the five firmware review checks that a reviewer should look for.

Version control in a firmware team

A firmware project changes in small ways with large effects, a constant changed from 500 to 250 doubling the blink and one line moved in an interrupt handler making a sensor lose samples. A team needs to know exactly which change did what, to undo one change without the others and to show that a release contains only reviewed code, and version control answers all three needs, whereas without it the team's knowledge lives in people's heads, a file on the shared drive and the copy flashed last month.

Git is the tool most teams use. Lesson 41 ran the build from the command line, and the build folder it produces is one of the things Git should not store, while this lesson adds the history, a sequence of snapshots each with a message, and a way to work on several lines of change at once.

Repositories and commits

A repository is a folder whose history Git keeps in a hidden .git folder, and a commit is a snapshot of the tracked files at one moment, with a message and a link to the commit before it. Git stores each snapshot as a set of objects identified by a hash of their content, so a commit cannot change without its identifier changing too, which is why a history can be trusted, since editing an old commit changes every later identifier and makes the difference visible.

Branches, merges and fast-forwards

A branch is a name pointing at one commit, which moves forward to each new commit made on the branch, so creating one costs almost nothing. A merge joins the histories of two branches in a merge commit with two parents, which is how Git records that two lines of work were combined, a model the Pro Git book explains in its basic branching chapter (Pro Git, chapter 3.2).

A merge can be a fast-forward, where the branch is simply ahead of main and Git moves the name, whereas a --no-ff merge always creates the merge commit even when a fast-forward is possible, which the hands-on task uses so that the history shows the feature existed.

Small commits and commit messages

A small commit is one a reviewer can read in a minute and you can revert without reverting anything else, a revert being a commit that undoes an earlier one, so a blink change and an I2C change sharing one commit cannot be reverted separately, whereas two commits keep them apart. The message serves the reviewer and the person reading the history in five years, its first line saying what the change does in the imperative mood, such as Blink twice as fast, and its body why.

Code review and pull requests

A code review is a second person reading a change before it reaches the main branch, called a pull request or a merge request in a hosted tool, the reviewer reading the diff, the set of changed lines, and commenting on the lines that need work. For firmware the reviewer checks what a simulator cannot, and the five checks below are a starting list.

Trunk-based development and git-flow

Two branching styles are common. In trunk-based development everyone merges small changes into one main line, often daily, through short-lived branches (trunkbaseddevelopment.com), while in git-flow the team keeps long-lived develop and release branches and a change waits in a feature branch until its release. Trunk-based development suits firmware teams that ship often and test every merge, and git-flow teams that must support several released versions at once.

In both styles a branch is only a name for a commit and a merge joins two histories, Git storing each commit with its parents so that a merge creates a commit with two parents, as the Pro Git book explains in its basic chapter (Pro Git, chapter 3.2, Basic Branching and Merging).

Five checks for a firmware reviewer

A pull request asks a second person to read the change before it reaches the main branch, and for firmware five checks catch many of the bugs that a simulator does not reveal.

  1. volatile on anything an interrupt and main both touch. Without it the compiler may keep the value in a register (lesson 46).
  2. ISR safety. The interrupt does little work, never blocks, clears its own flag and shares data with main only through a safe path such as a ring buffer or a critical section (lesson 57).
  3. Integer overflow and sign. A subtraction of unsigned values wraps, a signed overflow is undefined, and a timer comparison must subtract first (lessons 45 and 73).
  4. Error paths. Every call that can fail is checked, and each early return undoes what the function already did, such as a pin left driven or a bus left busy.
  5. Magic numbers. Each meaningful literal has a name carrying its unit, such as DEBOUNCE_TICKS or I2C_TIMEOUT_US, so that a reviewer can check it against the datasheet.
The checklist is a starting point, not a standard. The MISRA and Barr Group coding standards list many more rules, and the static analysis lesson (83) shows how a tool checks some of them.

Keeping build output out of Git with .gitignore

The build/ folder is generated by CMake and rebuilt by a fresh clone, so a line build/ in .gitignore tells git to leave the whole folder alone, and git status then shows only source changes. The VS Code files the project needs (.vscode/launch.json and tasks.json) stay tracked, because they describe how to build and debug the project.

Doxygen documentation comments

Doxygen reads special comments in the source and builds a reference from them, a block starting with /** being documentation and a tag such as @brief or @param marking each part, as the Doxygen manual describes (Doxygen manual: documenting the code). 

/**
 * @file led.h
 * @brief LED driver interface. Backends: led_gpio.c (a pin) or led_fake.c (a log line).
 */

/**
 * @brief Turn the LED on or off.
 * @param on true lights the LED.
 * @note Safe to call only after led_init().
 */
void led_set(bool on);

A Doxyfile is the configuration file telling Doxygen which files to read and what to write, and the options needed first are PROJECT_NAME, INPUT (the folders to read), RECURSIVE (read subfolders too), GENERATE_HTML and OUTPUT_DIRECTORY, whose names are in the Doxygen configuration reference (Doxygen manual: configuration). The doxygen -g option writes a template configuration file, and doxygen run without a configuration argument looks for a file named Doxyfile (Doxygen manual: usage), but the command is not run in this course, so check the output of doxygen --help on your install before relying on it.

Doxygen is optional for this course. It is not installed on the workspace PC. You can install it later with winget install DimitriVanHeesch.Doxygen, but the lesson does not run it. A comment with a wrong unit is worse than no comment, so write the units, and update a comment when you change the code.

Good Doxygen is short, accurate and placed next to the declaration, and since the tool does not check whether the text is right, a reviewer reads the comments with the same care as the code.

Worked examples of the five review checks

Each check is easier to apply with a concrete case in mind, so for each one below predict what goes wrong before reading the explanation.

  1. volatile. A main loop waits for a flag that an interrupt sets, while (!flag) { }, and the compiler, reading flag once and seeing that the loop body does not change it, may turn the loop into an infinite loop with one load. Declaring volatile bool flag makes each test read memory, the rule of lesson 46.
  2. ISR safety. An interrupt calls sleep_ms(1), so it cannot finish until the time passes while every other interrupt waits, and the fix sets a flag in the handler and does the work in main, as lesson 57 explains.
  3. Integer wraparound. A timer compares now < deadline with 32-bit unsigned values, and with deadline at 0xFFFFFFF0 and now at 0x00000005, 21 ticks later after the counter wraps, the comparison finds now smaller, so the deadline looks far away. Subtracting first, now - deadline, gives 0x15, which is 21 in unsigned arithmetic, so the test comes out right, the rule lesson 73 shows.
  4. Error paths. A function claims a bus, starts a transfer and fails halfway, and if the early return skips the release, the bus stays claimed and every later call fails for a reason that is hard to see, so each early return must undo what the function did before it.
  5. Magic numbers. The starter has sleep_ms(500) in two places, and a reviewer asking what 500 means learns that it is half a period in milliseconds, which should be a named constant such as HALF_PERIOD_MS, so that the two places change together and the value can be checked against its name.

Try it in Git Bash

The project is projects/0079-git-workflow, whose starter is the blink project from lesson 2, which you copy outside the course folder, turn into a git repository and use to practise the cycle of commit, branch and merge. The commands below were run in this order on a scratch copy during the course build and give a clean git status after the build.

  1. Copy the starter to a folder of your own outside the course, in Git Bash with cp -r /c/Users/juhos/embedded-course/projects/0079-git-workflow/starter ~/git-practice and then cd ~/git-practice, and remove any build/ folder that came with the copy with rm -rf build, since CMake stores the paths of the folder where it was configured, so a copied build cannot be reused.
  2. Create the repository and commit the project as it is with git init -b main, git add -A and git commit -m "Add blink project", and if git asks for your name or email, set them once with git config --global user.name "Your Name" and git config --global user.email you@example.com.
  3. Create a .gitignore file containing the single line build/ and commit it with git add .gitignore and then git commit -m "Ignore the CMake build folder".
  4. Make a feature branch with git switch -c feature/faster-blink, change both sleep_ms(500) lines in main.c to sleep_ms(250) and commit with git commit -am "Blink twice as fast".
  5. Merge the branch back into main with a merge commit by running git switch main and then git merge --no-ff feature/faster-blink -m "Merge feature/faster-blink", the --no-ff flag keeping the branch visible in the history although a fast-forward was possible.
  6. Look at the result with git log --oneline --graph --decorate, which should show four commits, the two setup commits, the feature commit and the merge commit, with the graph showing the fork and the join where the feature branch meets main.
  7. Check that the build folder is ignored by building the copy with the course tool, python -I /c/Users/juhos/embedded-course/tools/build.py ~/git-practice, and running git status, which should print nothing, because build/ is ignored.
Hint if git says "LF will be replaced by CRLF"

On Windows git may warn about line endings, a message coming from your machine's line-ending setting that does not change the content of the commit, so it can be ignored for this lesson.

Hint if the merge says "Already up to date"

You ran the merge on the feature branch instead of main. Check with git branch, which marks the current branch with *, then run git switch main and merge again.

Common mistakes and how to spot them

Unrelated changes in one commit

A later revert removes an I2C fix and the bug returns, because a blink change, the I2C fix and a README update were committed together with the message "updates". Commit each change separately, using git add -p to pick the lines that belong together.

A committed build folder

Every build produces a diff of hundreds of generated files and a clone on another machine fails, because the first git add -A added build/ with absolute paths from one PC. Add the .gitignore line from the hands-on task and run git rm -r --cached build to stop tracking the files already added.

A merge run on the wrong branch

The merge command reports Already up to date and the change is missing from main, because the developer ran git merge while on the feature branch. Run git switch main first and then the merge, as the hint in the hands-on task says.

A documentation comment with a wrong unit

A timeout comes out a thousand times too short while the documentation says it is correct, because a Doxygen block states @param timeout ms for a function that takes microseconds. Write the unit in the name, as the timeout constant in the hal header does, and update the comment in the same commit as the code.

Branching and review in firmware teams

Teams that ship firmware often run trunk-based development, with short branches merging to the main line most days and tests running on every merge. Review is a required step performed by someone who knows the hardware, and a typical review of a driver checks the five points above, asks for a test of the new logic and rejects a change that mixes two unrelated fixes.

Summary

  • A commit is a named snapshot, a branch a name that moves, and a merge commit has two parents.
  • Small commits let a revert remove one change and nothing else.
  • .gitignore keeps the build folder out, while the VS Code files the project needs stay tracked.
  • --no-ff keeps a feature branch visible in the history.
  • A firmware review checks volatile, ISR safety, integer wraparound, error paths and named constants.
  • A Doxygen comment is only as good as its units and its last update.
