Bench lab 0: Blink on a real Pico 2

Take the lesson 2 blink off the simulator and onto a real board: build a UF2 file, flash it over USB, and read the board's serial log on your PC. Every later bench lab starts from this setup.

This bench lab is optional. The course, its labs and its checkpoints are complete without real hardware, and bench labs don't count towards your progress. Do them if you have the board and want to see where a simulator and a real chip part ways. Time: about 45 minutes, most of it the first-time setup.
By the end of this lab you can build a Pico 2 project to a UF2 file, flash it with BOOTSEL, and read its serial output over USB on your PC.

Why a real board at all

Wokwi runs your firmware on a model of the chip. The model executes the same instructions, so the logic of your program behaves the same. What it doesn't model is the physics around the chip: contacts that bounce, wires that pick up noise, pins that float, supplies that ripple, and clocks that a peripheral divides wrongly. The bench labs each take one exercise from the course onto a Raspberry Pi Pico 2 and show one of those gaps. In each one, the code works in the simulator first, and then you find out what the board does differently.

The Pico 2 carries the RP2350, the successor of the RP2040 that the course simulates. Its Arm cores are Cortex-M33s at 150 MHz (Raspberry Pi Pico 2 product page), and the Pico SDK you already use supports it: the only build change is set(PICO_BOARD pico2). Wokwi simulates the Pico 2 as well, as the part board-pi-pico-2 (Wokwi docs), so every bench project opens in the simulator exactly like the course's other projects.

How a program gets onto the board

In Wokwi, VS Code hands the simulator the .elf file directly. A real board has no simulator to hand it to: the program has to be written into the board's flash memory. The Pico 2 has 4 MB of QSPI flash, and the RP2350's boot ROM can write it for you over USB (Pico 2 datasheet, section 5.1).

It works like this. If you hold the BOOTSEL button while the board powers up, the boot ROM doesn't start your program. It starts a USB mass-storage device instead: a drive named RP2350 appears on your PC (RP2350 datasheet, section 5.5.1). This is BOOTSEL mode. You copy a UF2 file onto that drive. The boot ROM recognises the UF2 blocks, writes their data into flash, and reboots into your program when the whole file has arrived. The boot code is in ROM, so a bad download can never break this path: you can always go back to BOOTSEL and try again.

A UF2 file is your program cut into 512-byte blocks. Each block carries 256 bytes of data, the flash address they go to, and a family ID that says which chip the file is for. The RP2350 accepts only blocks with a family ID it knows (RP2350 datasheet, section 5.5.2). That's why the build must know the board: the SDK picks the family ID from PICO_BOARD.

The datasheet warns that an invalid UF2 file may write only partly, and that not every operating system reports the failed write (RP2350 datasheet, section 5.5.1). If the drive vanishes but nothing runs, rebuild and copy again before you suspect the code.

What changed in the build

The course's Wokwi projects set PICO_NO_PICOTOOL, because Wokwi needs only the .elf. The bench projects use the template templates/pico2-sdk, whose CMakeLists.txt differs in four lines: 

set(PICO_BOARD pico2)                 # RP2350, Pico 2 pin-out, LED on GPIO25
pico_enable_stdio_usb(blink 1)        # printf also goes to a USB serial port
target_compile_definitions(blink PRIVATE PICO_STDIO_USB_CONNECT_WAIT_TIMEOUT_MS=3000)
pico_add_uf2_output(blink)            # build/blink.uf2, made by picotool

Line 1 selects the board, which selects the chip, its linker script and the UF2 family ID. Line 2 adds USB to the outputs of printf. The serial monitor in Wokwi listens on UART0 (GP0 and GP1), and the template keeps that. On the bench you have no USB-to-serial adapter, so the board itself becomes a USB serial port. Line 3 makes stdio_init_all() wait up to 3 s for a terminal to open that port, so the first lines your program prints aren't lost before you connect. Line 4 asks for the UF2 file.

The UF2 conversion is done by picotool. If it isn't installed, the SDK downloads its source and builds it the first time. tools/build.py points the SDK at a shared folder, ~/.pico-sdk/picotool-build, so this happens once, not once per project. The first build of a bench project therefore takes a minute or two longer and needs the internet.

The program

Open projects/bench00-first-board/solution/main.c. It does two things worth a look. First, it reads the chip's identity register: 

uint32_t id = sysinfo_hw->chip_id;
unsigned revision = (unsigned)(id >> 28);
unsigned part = (unsigned)((id >> 12) & 0xFFFFu);
unsigned manufacturer = (unsigned)((id >> 1) & 0x7FFu);

SYSINFO is a small block of read-only registers, and CHIP_ID at offset 0 holds a JEDEC identifier: bits 31:28 are the revision, 27:12 the part number and 11:1 the manufacturer, with bit 0 always 1 (RP2350 datasheet, section 12.15.1). The SDK's struct sysinfo_hw maps that block, the same struct-overlay idea as lesson 47. The revision matters in bench lab 2: one of the RP2350's errata applies only to some revisions, and this is how firmware tells them apart.

Second, the LED doesn't blink evenly. It flashes for 100 ms once a second, a heartbeat. A 50 % blink and a stuck-on LED look alike at a glance across a room; a short flash once a second is unmistakably "running". Many products use this pattern on a status LED.

Stage 1: in Wokwi

  1. Open projects/bench00-first-board/starter in VS Code. Build with Ctrl+Shift+B. The first build also builds picotool, so give it a few minutes.
  2. Check that build/blink.uf2 exists next to build/blink.elf.
  3. Start the simulator: F1 → Wokwi: Start Simulator. The serial monitor shows BENCH0 chip id not read yet, then LED on and LED off.
  4. Task 1: fill in print_chip() so it prints CHIP_ID in hex and its three fields.
  5. Task 2: turn the even blink into the heartbeat, and print beat N after each flash.
  6. Rebuild and run in Wokwi. Write down the CHIP_ID the simulator reports.

Stage 2: on the board

  1. Install Microsoft's Serial Monitor extension in VS Code (it opens as a tab in the terminal panel).
  2. Unplug the Pico 2. Hold its BOOTSEL button, plug the USB cable in, then let go. A drive named RP2350 appears.
  3. Copy build/blink.uf2 onto the drive. The drive disappears: the board has rebooted into your program, and the LED starts its heartbeat.
  4. In the Serial Monitor, pick the new COM port (on Windows a new COMn; on Linux /dev/ttyACM0; on macOS /dev/cu.usbmodem…) and click Start Monitoring. The baud rate setting doesn't matter for a USB serial port: the data travels in USB packets.
  5. The Pico 2 has no reset button. To see the start-up lines again, unplug and replug without BOOTSEL, and open the port within 3 s.
  6. Compare the board's CHIP_ID with Wokwi's. Write the real revision field down: bench lab 2 needs it.

Diagnosis checklist

No RP2350 drive appears

The cable is the usual culprit: many micro-USB cables carry only power. Try a cable you know moves data, and a different USB port. BOOTSEL must be held at the moment the board powers up; pressing it later does nothing.

The drive disappears but the LED does nothing

Check that you copied the bench project's UF2, built with PICO_BOARD pico2. The course's Wokwi projects build for the RP2040 and make no UF2 at all. Rebuild and copy again: the datasheet says a failed write may go unreported.

The LED beats but the Serial Monitor shows nothing

You probably opened the port after the start-up lines had gone. The beat N lines keep coming once a second, so wait two seconds. If none come, check that you picked the right COM port: unplug the board and see which one disappears.

Your code runs on a real chip. From here on, each bench lab builds the same way, flashes the same way, and talks to you over the same serial port.

Common mistakes
  1. Copying the .elf instead of the .uf2. The drive accepts any file and keeps nothing useful. Symptom: nothing happens, the drive stays. Fix: copy build/blink.uf2.
  2. A charge-only cable. Symptom: the board's LED may light from a previous program, but no drive and no serial port appear. Fix: a data cable.
  3. Expecting the start-up lines without waiting. Symptom: the log starts at beat 3. Fix: open the port within the 3 s window, or print important state again later.
  4. Building the starter with the old template. Symptom: no UF2 in build/. Fix: bench projects use pico2-sdk; check the first lines of CMakeLists.txt.

Summary

  • The same source runs in Wokwi (board-pi-pico-2) and on a Pico 2; only PICO_BOARD and the outputs differ.
  • Holding BOOTSEL at power-up starts the boot ROM's USB drive, RP2350. Copying a UF2 file onto it writes flash and reboots.
  • A UF2 block carries 256 bytes, an address and a family ID; the RP2350 accepts only its own families.
  • On the bench, printf reaches the PC as a USB serial port; the template waits up to 3 s for a terminal.
  • SYSINFO CHIP_ID tells firmware which chip and revision it runs on.
  • A short heartbeat flash is a clearer "alive" signal than an even blink.
Raspberry Pi Pico 2 datasheet: read section 3.1 (the pin-out and the pins used on the board: GPIO23, 24, 25 and 29) and section 5.1 (programming the flash). Both are short and you'll use the pin-out in every bench lab.
