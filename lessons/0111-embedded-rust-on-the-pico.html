Embedded Rust on the Pico

Compiler-checked ownership of peripherals

By the end of this lesson you can build the Rust blink project on this machine, name the parts of a no_std binary against their C equivalents, and explain why a call to set_high() on an input pin does not compile.

Rust for embedded work

This lesson runs on the same RP2040 with the same vector table as the C projects, built by a compiler that checks who may touch each peripheral, going through the setup first, then the parts of a no_std binary and finally the compiler catching a mistake. It is optional, so skip it if you want to stay on the C path, although it is useful if you want to see what the compiler can do for you that C does not, and Parts 1 to 4 are enough to follow it.

Rust's main benefit on a microcontroller is that many C mistakes become compile errors with no run-time cost, three rules doing most of the work.

  1. Ownership of peripherals. Peripherals::take() returns Some only the first time. A second call returns None, so two parts of the program cannot each hold the GPIO block. The rp2040-pac 0.6.0 source shows this: take() returns None once a flag is set, and otherwise hands out the peripherals. The Embedded Rust Book describes the same pattern as a singleton, one instance of a peripheral (Embedded Rust Book, Singletons).
  2. Type-state pins. into_push_pull_output() returns a different type, so a write to the pin is only possible in output mode. The book gives the same kind of example: trying to change the output state of a pin configured in floating input mode "would raise a compile error" (Embedded Rust Book, Static Guarantees). In C, the same bug compiles, and the pin does not change, with no warning.
  3. No data races without unsafe. Safe Rust does not let two parts of the program mutate the same static unless the type shows that access is synchronised. Writing unsafe is then an explicit statement that the programmer takes responsibility. The code that is still unsafe is local, usually register access inside the PAC and HAL.

A fourth benefit is portability, because the embedded-hal 1.0 crate defines traits such as OutputPin, so a sensor driver written against those traits runs on any chip whose HAL implements them, the idea behind lesson 76's hardware abstraction layer, here enforced by the compiler.

Limits of the ownership model

Ownership removes whole classes of bugs, but it does not check your datasheet reading or your timing, and the main limit is ecosystem maturity, rp2040-hal being at version 0.11 while many drivers and RTOS integrations are still young. For safety-critical work, Ferrocene is a Rust toolchain from Ferrous Systems that the vendor markets for that use (Ferrous Systems, Ferrocene), whose qualification scope you check with the vendor before relying on it, lesson 112 explaining what a standard such as ISO 26262 asks for.

Setting up the Rust toolchain

Rust is installed with rustup, which manages toolchains and targets, by running the commands below in PowerShell or Git Bash, the first installing rustup itself and the rest adding the parts this course needs. 

winget install -e --id Rustlang.Rustup
rustup toolchain install stable-x86_64-pc-windows-gnu --profile minimal
rustup target add thumbv6m-none-eabi --toolchain stable-x86_64-pc-windows-gnu
rustup component add llvm-tools --toolchain stable-x86_64-pc-windows-gnu

The thumbv6m-none-eabi target is the Armv6-M architecture, the Cortex-M0+ core of the RP2040 (Arm Cortex-M0+ processor datasheet), and it is a compiler setting telling rustc which instructions and ABI to emit, the same job as -mcpu=cortex-m0plus in GCC, while llvm-tools gives you the LLVM binary tools, such as llvm-size, to inspect the ELF.

The GNU host toolchain is needed because rustup installs the MSVC toolchain by default on Windows, which links through Microsoft's linker and so needs Visual Studio, and Cargo build scripts, small programs that run on the PC during the build and are used by the crates here, are linked by the same linker and fail without it. The GNU toolchain (x86_64-pc-windows-gnu) uses MinGW instead, which this machine already has.

The project file rust-toolchain.toml pins the toolchain and target, so that anyone running cargo build in that folder gets the same compiler. 

[toolchain]
channel = "stable-x86_64-pc-windows-gnu"
targets = ["thumbv6m-none-eabi"]

The project's .cargo/config.toml also sets the default target and the linker flags, so that you never type --target, the same role as a CMake toolchain file, which fixes the target for the whole project. The project is built from the workspace root with the course build script, which runs cargo build --release, release builds keeping debug information, so that GDB works. 

python -I tools/build.py projects/0111-embedded-rust-on-the-pico/starter

The output is target/thumbv6m-none-eabi/release/blink, an ELF file with no .elf extension, to which wokwi.toml points, so that Wokwi runs the same file a debugger would load. Open the starter folder in VS Code, press Ctrl+Shift+B to build and then F1 → Wokwi: Start Simulator, and for debugging start the simulator and press F5.

Do not install extra Cargo tools such as probe-rs, flip-link or elf2uf2-rs for this lesson. Wokwi runs the ELF directly, and the course build does not need them.

The parts of a no_std binary

A normal Rust program starts with the standard library, which assumes an operating system, and since a microcontroller has none, the project declares #![no_std] (no standard library) and #![no_main] (no C-style main from a runtime), what remains being the same job you already know from C, split into crates.

The PAC is generated by svd2rust from the SVD file the chip vendor publishes, although you do not need the tool, because the crate is generated and checked in, as CMSIS headers are, while the HAL is a separate crate depending on the PAC (rp2040-hal 0.11.0 docs), and the register names come from the RP2040 datasheet.

The .boot2 section is what the blink program puts first in flash with #[link_section = ".boot2"], the memory.x file reserving the first 256 bytes for it, so that the vector table starts at 0x10000100, and lesson 42 covers the startup code that runs after the boot ROM has done its work. The RP2040 datasheet describes the second-stage bootloader in its boot sequence material (RP2040 datasheet, boot sequence), and the rp2040-boot2 crate supplies the 256-byte image itself.

The blink program's main is marked #[hal::entry]. That attribute is the crate's version of int main(void) in C: it puts main behind the reset handler that cortex-m-rt generates.

Interrupts and shared state in Rust

Lesson 57 shared a flag between an interrupt and main with volatile and protected the read-and-clear with a critical section, whereas in Rust the same job uses a critical_section::Mutex around a RefCell or a Cell, the Mutex handing out its contents only inside a critical section, while the compiler checks that you did not skip it.

In embedded Rust each peripheral resembles a physical key of which exactly one exists, so whoever holds the key can use the peripheral, and to let an interrupt use it too you put the key in a lockbox, the Mutex, that opens only inside a critical section, the compiler refusing to build a program in which two places hold the same key at once. The comparison breaks at unsafe, though, because inside an unsafe block code can reach a register without holding its key, so the guarantee covers only safe code.

// The button pin is owned here, so only the handler can clear its interrupt.
type ButtonPin = hal::gpio::Pin<Gpio14, FunctionSio<SioInput>, PullUp>;
static BUTTON: Mutex<RefCell<Option<ButtonPin>>> = Mutex::new(RefCell::new(None));

// Written by the handler, read by main.
static BLINK_ENABLED: Mutex<Cell<bool>> = Mutex::new(Cell::new(true));

The Option starts as None, because the pin does not exist until main configures it, after which main moves the pin into the Mutex and the handler takes it back out for each event, and since moving a value transfers ownership, main cannot use the pin afterwards, the same rule that rejects the snippet further down.

The bank 0 interrupt line is shared by every GPIO in the bank, so the handler checks interrupt_status for its own pin before acting, the rp2040-hal 0.11 GPIO code defining set_interrupt_enabled, interrupt_status and clear_interrupt on the pin (rp2040-hal 0.11.0, src/gpio/mod.rs, in the crate source under the cargo registry). The interrupt handler is written as #[interrupt] fn IO_IRQ_BANK0(), an attribute from the PAC naming the same vector-table entry that lesson 57 used, number 13.

The Mutex is a critical section, and it does not sleep. Keep it short, as lesson 57 says for ISRs. Turning interrupts off for long stretches hurts the latency of everything else.

Worked example: one button press, step by step

The interrupt code is easier to follow as a timeline, starting just after the program has begun, with the button released and the LEDs blinking, the RP2040's GPIO pull-up holding GP14 high while the switch is open, so that the pin reads 1, whereas pressing the button connects GP14 to ground and the pin reads 0, the falling edge being the event the interrupt is set up to catch. Before following the steps, predict what would happen if the handler did not clear the event.

  1. t = 0 ms. main is inside its loop. Each pass adds 1 to tick, toggles an LED when tick divides evenly, and then waits 50 ms with delay_ms(TICK_MS).
  2. The press. GP14 falls from high to low. The pin's interrupt status for EdgeLow is set in the GPIO block, and because bank 0 is shared, the bank 0 line goes active.
  3. The NVIC runs the handler. The NVIC was unmasked for IO_IRQ_BANK0 (number 13 in the RP2040 vector table), so the core stops main at its next instruction and enters IO_IRQ_BANK0().
  4. The handler checks its pin. It enters the critical section, borrows the pin from the Mutex, and calls interrupt_status(EdgeLow). That returns true, so the handler flips BLINK_ENABLED from true to false.
  5. The handler clears the event. clear_interrupt(EdgeLow) resets the pin's latched status. Without this step, the bank 0 line would still be active when the handler returned, and the handler would run again straight away.
  6. Main sees the flag. Within one loop pass (at most 50 ms later), main reads false, sets both LEDs low, and keeps the tick counter still. Releasing the button does not raise an edge on the falling-edge setting, so the blinking stays paused until the next press.

The timing numbers are the ones the solution uses, TICK_MS at 50 and LED1_TICKS at 10 making LED 1 change state every 500 ms, one full blink every second, while LED2_TICKS at 5 gives a change every 250 ms, two full blinks per second. The handler flips the flag on every falling edge, so the second press makes the flag true again and the blinking resumes, each press being one toggle, which is why the hands-on steps ask you to press the button twice and watch both LEDs stop and restart.

The solution's setup sequence

The handler and the Mutex declarations have already appeared, and the rest of main is the setup sequence, worth reading in order, because each line depends on the one before it.

  • pac::Peripherals::take().unwrap() takes the one owner of the chip's peripherals. unwrap() panics if the call were repeated, which is the singleton rule in action.
  • Watchdog::new(pac.WATCHDOG) and init_clocks_and_plls(XOSC_HZ, ...) start the 12 MHz crystal and configure the PLLs. The clock code takes &mut pac.RESETS because it resets and starts the clock blocks, so the borrow checker keeps other code from using them meanwhile.
  • hal::Timer::new(pac.TIMER, &mut pac.RESETS, &clocks) builds a delay from the RP2040's TIMER peripheral, which counts microseconds from the reference clock the clock setup started. This is why delay_ms(50) is accurate, rather than a loop that depends on the compiler. The DelayNs trait from embedded-hal supplies delay_ms. The Cortex-M SysTick delay (cortex_m::delay::Delay) works on the chip too, but it hangs in the Wokwi simulator, so the course uses the timer.
  • pins.gpio25.into_push_pull_output() and pins.gpio15.into_push_pull_output() each consume their pin and return a new value of an output type. The type change is what makes toggle() and set_low() available on those variables only.
  • into_pull_up_input() on GP14 gives an input type with the pull-up enabled, so set_interrupt_enabled(EdgeLow, true) is called on the value that will be moved into the Mutex. Just before it, clear_interrupt(EdgeLow) drops any edge latched while the pin changed from its reset pull-down to the pull-up. Without it, the handler can run as soon as the line is unmasked and pause the blink before anyone presses the button.
  • The unsafe block around NVIC::unmask is the only line in main that the compiler does not check for you. It must come after the pin is in the Mutex, or the handler could run and find None.
  • The loop reads BLINK_ENABLED inside a short critical section, then either toggles the LEDs or holds them low, and always waits TICK_MS.

Hint for the interrupt

Enable the edge on the pin before you move it into the Mutex. The handler needs interrupt_status and clear_interrupt on the same pin, so you must borrow it from the Mutex with borrow_mut() inside critical_section::with.

Hint for unmasking

The NVIC is re-exported as pac::NVIC. unmask is unsafe, because the interrupt can start at once. Wrap the call in an unsafe block, and do it after the pin is in the Mutex.

Compile errors for misused pins

Adding one line to the solution before the button is used, button.set_high().unwrap();, fails, because the pin is an input, so the output methods do not exist on its type, as the real output of the build from a scratch copy shows. 

error[E0599]: no method named `set_high` found for struct `rp2040_hal::gpio::Pin<I, F, P>` in the current scope
  --> src\main.rs:71:12
   |
71 |     button.set_high().unwrap();   // deliberate: GP14 is an input
   |            ^^^^^^^^ method not found in `rp2040_hal::gpio::Pin<Gpio14, FunctionSio<SioInput>, PullUp>`

In C, the equivalent write to GPIO_OE or gpio_put() on an input pin compiles and runs with nothing to stop it, the bug showing up as a pin that never changes, whereas here the type of button says it is an input and set_high belongs only to output types. The second mistake moves the button into a variable and then uses the original name. 

error[E0382]: use of moved value: `button`
  --> src\main.rs:76:28
   |
70 |     let button = pins.gpio14.into_pull_up_input();
   |         ------ move occurs because `button` has type `rp2040_hal::gpio::Pin<Gpio14, FunctionSio<SioInput>, PullUp>`, which does not implement the `Copy` trait
...
75 |     let _moved = button;   // deliberate: move
   |                  ------ value moved here
76 |     critical_section::with(|cs| BUTTON.borrow(cs).replace(Some(button)));
   |                            ^^^^ value used here after move     ------ use occurs due to use in closure

The pin cannot be used twice, so two parts of the code cannot both hold it, the ownership rule from the table above applied to a single pin, and since each mistake stops the build, the program never reaches the board with a pin used in the wrong mode or after a move.

You built a Rust program for the RP2040 on this machine, mapped each part of the no_std binary to C and watched the compiler reject a pin used in the wrong mode, the compiler check being the main point of this lesson.

Common mistakes and how to spot them

The interrupt unmasked before the pin is in the Mutex

The LEDs freeze in the simulator and stay that way, because main stops making progress, the handler running, finding None in the Option and doing nothing, and since the clear call sits inside the if let Some branch, the edge is never cleared, so the core re-enters the handler as soon as it returns. Follow the order in the solution, configuring the pin, moving it into the Mutex and only then calling NVIC::unmask.

A handler that does not clear its event

The handler re-enters without end once the first edge is seen, the same symptom as above, because a developer copied the handler and removed the clear_interrupt line, which looked optional, and tested with only one press. Clear the event for the pin that fired after acting on it, checking interrupt_status first when several pins share the bank.

A shared static mut without synchronisation

The build stops with the message below, from the scratch copy used for this lesson, because a developer who knows C added a plain global counter and incremented it in main. 

error[E0133]: use of mutable static is unsafe and requires unsafe function or block
  --> src\main.rs:82:5
   |
82 |     COUNT += 1;
   |     ^^^^^ use of mutable static
   |
   = note: mutable statics can be mutated by multiple threads: aliasing violations or data races will cause undefined behavior

Use the Mutex pattern from this lesson, or an explicit unsafe block with a comment saying why no interrupt can race with it, the compiler's note naming the risk exactly, since for this purpose an interrupt is another thread of execution.

A wrong blink period

The two LEDs seem to run at the wrong ratio, LED 2 blinking at 500 ms instead of 250 ms, because a developer set LED2_TICKS to 10, a number that looks like a half period. Use the arithmetic from the quiz, a half period being the number of ticks multiplied by TICK_MS.

Driver crates and code review in Rust teams

Teams shipping Rust on microcontrollers usually keep the PAC and HAL from crates.io and write their own driver crates against embedded-hal 1.0, so that a driver can be tested on a PC with a fake pin and then run unchanged on the RP2040 or another chip, the portability point from earlier and what senior engineers look for when reviewing a driver's trait bounds.

A code review asks the questions of a C review plus a few specific to ownership, where unsafe is and why it is correct, which value owns each peripheral and whether any interrupt handler takes a lock that main also takes, and in most teams an unsafe block without a comment is a review finding, as is a Mutex held across a long delay.

Summary

  • Rust on the Pico uses the same RP2040 and the same vector-table idea as the C projects, the crates generating the parts you would write by hand in C.
  • The build uses the GNU host toolchain pinned in rust-toolchain.toml, the thumbv6m-none-eabi target and the linker flags in .cargo/config.toml.
  • memory.x reserves the 256-byte BOOT2 region at 0x10000000, so the vector table starts at 0x10000100.
  • Peripherals::take() returns Some once, and the pin types then say which operations are legal in each mode.
  • A flag shared between an interrupt and main lives in a critical_section::Mutex, while other shared statics need an explicit unsafe block.
  • Each interrupt event is cleared after handling, and the NVIC line is unmasked only after the handler's data is in place.
  • The compiler rejects wrong-mode pin calls and use-after-move before the program runs, but it cannot check the datasheet or the timing.
