Lab 4: Port Lab 3 to the STM32 behind a HAL

The environment monitor from Lab 3 runs on a Pico. In this lab the same application runs on a Blue Pill too. You will write the Blue Pill board file, and the application code does not change, so you can prove it with a diff.

By the end of this lab you can run one application on two boards through a small hardware abstraction layer (hal.h), write the Blue Pill board file hal_bluepill.c with GPIO, I2C, UART and a millisecond clock, and show that the application folder is identical for both builds.

The idea

A hardware abstraction layer (HAL) is a header that the application includes, and one implementation file per board behind it. The application calls hal_gpio_read(), hal_i2c_write() and hal_millis(), and it never names a register, an SDK call or a pin. A Pico build and a Blue Pill build then compile the same source files, and only the board file differs. A HAL is a seam you design for testing as well as for porting. Part 6 uses the same header to put the application on a PC for unit tests, with a fake board file (lesson 80).

The application is the Lab 3 monitor: the MYS-1 sensor (the mystery custom chip from lesson 63), the SSD1306 OLED, two buttons, the three-screen menu, non-blocking deadlines and a UART log. Both boards use the same sensor and display, so the only wiring change is the pin numbers in each board file.

The project layout

The project is projects/lab04-port-lab3-to-stm32. The shared application is in app/ at the top. Each board has a starter and a solution folder, and each folder is a complete Wokwi project with its own CMakeLists.txt, diagram.json and wokwi.toml.

  1. starter/bluepill: the Blue Pill project with the board file left as TODO(learner).
  2. starter/pico: the Pico project, complete. It is the worked example for the Blue Pill file.
  3. solution/bluepill and solution/pico: both finished. Both must build and lint with verify_projects.py.
The alarm LED is the on-board LED of each board: PC13 on the Blue Pill (active low) and GP25 on the Pico (active high). The board file hides that difference, and the application calls hal_gpio_write(HAL_PIN_LED, on) on both.

Requirements

  1. Build starter/bluepill and solution/bluepill for the Blue Pill, and solution/pico for the Pico, with the shared app/ folder in each.
  2. In starter/bluepill/hal_bluepill.c, implement every TODO(learner): hal_init(), hal_gpio_write(), hal_gpio_read(), hal_i2c_write(), hal_i2c_read() and hal_log(). Do not change their signatures in app/hal.h.
  3. Use hal_pico.c as the worked example. The two files must do the same job with different registers and SDK calls.
  4. Drive the LED (PC13, active low) so that hal_gpio_write(HAL_PIN_LED, 1) lights it.
  5. Read button A (PB12) and button B (PB13), active low, so that hal_gpio_read() returns 1 while a button is held.
  6. Talk to the MYS-1 sensor (mystery chip, address 0x48) and the SSD1306 OLED (address 0x3C) on I2C1: PB6 is SCL and PB7 is SDA. Both devices use hal_i2c_write() and hal_i2c_read().
  7. Print each log line over USART1 (PA9, 115200 baud) from hal_log(), with the line ending added by the board file.
  8. Keep app/ and main.c identical to the solution. A diff between your app/ and the solution's must be empty, and the Pico build must still build from the same folder.
  9. Print LAB4 OK once, after the sensor and the display have both initialised.
  10. Optional stretch: make the Blue Pill and the Pico print the same log format for the same sensor readings. Note which lines differ, and why.

Milestones

  1. Milestone 1: the board boots. Implement hal_init() and hal_log(). The serial monitor prints LAB4 OK, which shows the UART, the clocks, and the sensor and display start-up.
  2. Milestone 2: the LED and the buttons. Implement hal_gpio_write() and hal_gpio_read(). The alarm LED follows the alarm state, and a button press moves the menu.
  3. Milestone 3: the sensor and the log. Implement the I2C read and write. The log line shows LAB4 T= values, and the readings change over a few seconds.
  4. Milestone 4: the OLED. The screen shows the temperature on LIVE, and the menu works from button A.
  5. Milestone 5: the whole device. Check every acceptance criterion, then build the Pico project and compare the two logs.

Acceptance criteria

  • The serial monitor prints LAB4 OK once, after the start-up, and then one log line per second.
  • The OLED shows the temperature on LIVE, and the same value appears in the log within one second.
  • Button A cycles LIVE, MINMAX and SETPOINT, and the log shows each screen name in turn.
  • On SETPOINT, button B raises the threshold from 28 to 35, then wraps to 20. At a threshold of 22 the log shows ALARM=1 and the LIVE screen shows ALARM.
  • One click produces one screen change. A second press within 30 ms counts as the same press.
  • Remove the sensor's SDA wire. Within about one second the LIVE screen shows SENSOR ERR, and the buttons and the log keep working.
  • The diff of app/ between your project and the solution is empty.

Differences from Lab 3, and why

  • Buttons are polled. Lab 3 used interrupts. The HAL has no interrupt call, so ui_poll() reads the pins on every pass of the loop and debounces each button by time. A press shorter than one pass of the loop can be missed. The OLED update takes about 90 ms, so a short tap during a redraw can be lost. Lesson 57 explains the interrupt version that Lab 3 uses.
  • Temperatures are integers. The sensor count is converted to hundredths of a degree with integer maths, so no board needs float printf.
  • The alarm drives the LED. This uses hal_gpio_write(), and is the only output the HAL needs for the alarm.

Hints

Hint for hal_init

Enable the GPIO clocks, the USART1 clock and the I2C1 clock before you call the HAL init functions. The pico file does the same in one hal_init() function, so use it as the checklist, and map each step to an STM32 call.

Hint for the I2C address

Two layers, two address conventions. The course's hal.h takes the plain 7-bit address (addr7), as the Pico SDK does. ST's HAL_I2C_Master_Transmit and HAL_I2C_Master_Receive instead take the 7-bit address shifted left by one, and set the read/write bit themselves (the source comment says the address "must be shifted to the left before calling the interface"). So hal_bluepill.c passes addr7 << 1 for both directions: the OLED's 0x3C becomes 0x78, and the mystery sensor's 0x48 becomes 0x90, for reads and writes alike. Mixing the conventions up is one of the most common I2C bugs: the device never acknowledges.

Hint for the buttons

A button held to ground reads 0. The board file turns that into 1 for pressed, and the application debounces the result. If the menu never moves, check the pull-up in hal_init() before you blame the debounce.

Hint if the screen or the sensor stays silent

The application prints LAB4 init failed when a device does not answer during start-up. Check the wiring first: SDA is PB7, SCL is PB6, both have 4.7 kΩ pull-ups to 3.3 V, and the OLED's VCC pin is on 3.3 V. Then check that each device has the address above.

Hint for the timing

A full-screen update sends 1025 bytes. At 100 kHz with 9 bit times per byte that is about 92 ms. The application redraws only when something changes, and at every 500 ms deadline. A faster bus, or a DMA transfer from lesson 74, would shorten the redraw.
