Lab 4: Port Lab 3 to the STM32 behind a HAL

The environment monitor from Lab 3 runs on a Pico. In this lab the same application runs on a Blue Pill too. You will write the Blue Pill board file, and the application code does not change, so you can prove it with a diff.

By the end of this lab you can run one application on two boards through a small hardware abstraction layer (hal.h), write the Blue Pill board file hal_bluepill.c with GPIO, I2C, UART and a millisecond clock, and show that the application folder is identical for both builds.

Where we are and why it matters

Lab 3 (Lab 3: Environment monitor) built a complete small device. It reads a temperature sensor over I2C, shows the value on an OLED, sets an alarm when the value passes a threshold, and logs each reading over a serial port. It runs on a Raspberry Pi Pico, and every line of its code that touches the hardware calls the Pico SDK. Earlier lessons supply the parts. Lesson 73 gave you a millisecond clock and wrap-safe timeouts, lesson 70 the UART, and lesson 74 the idea of moving bulk data without the CPU. This lab asks a question that product teams face: what happens when the hardware changes?

In a real company the answer is often "the board changes next year". A new revision uses a cheaper microcontroller, a different supplier, or a different pin layout. If the application is written against the registers and the SDK of one chip, every line that touches the hardware must be found and rewritten, and each rewrite can break something that used to work. A hardware abstraction layer (HAL) is the design that prevents this. It is a set of functions the application calls, with one implementation for each board. Porting then means writing one file, and every other file is untouched. The rule is easy to state and harder to follow, and the diff in this lab shows whether you followed it.

The concepts, one at a time

An interface and an implementation

A C header file declares functions, and a source file defines them. The header is the interface, a list of what the application may ask for. The source file is the implementation, the code that does the work for one particular board. If the header declares hal_gpio_write(hal_pin_t pin, uint8_t on), every board must provide that function with that signature. The application includes only the header, so the compiler checks that the application and the board agree on the interface, without knowing which board is used.

In this lab the interface is app/hal.h. It declares six functions and one enum. hal_init() starts the clocks and the peripherals. hal_gpio_write() and hal_gpio_read() drive and sample the logical pins. hal_i2c_write() and hal_i2c_read() talk to devices on the I2C bus. hal_millis() returns the time, and hal_log() writes a line to the serial port. The enum hal_pin_t names three logical pins: the alarm LED, button A and button B. The application never names a physical pin such as PC13 or GP25.

The two board files each define those six functions. hal_bluepill.c uses the ST HAL, and hal_pico.c uses the Pico SDK. Both are compiled into a project that also compiles the same app/ folder. The build system chooses one board file per project. The application cannot tell the difference, because it calls the same six functions.

Logical levels and active-low pins

A pin is a wire with two states, high and low. The application thinks in terms of "on" and "pressed", while the hardware thinks in terms of high and low voltage. The two can be opposite. The alarm LED on a Blue Pill is wired so that the pin must be driven low to light it, which is called active low. The LED on a Pico is wired the other way, so the pin must be driven high, which is active high. Button A on both boards pulls its pin to ground when pressed, so a pressed button reads 0 on the wire.

The header hides these differences. The comment on hal.h states the rule: hal_gpio_write(HAL_PIN_LED, 1) lights the LED on either board, and hal_gpio_read(HAL_PIN_BTN_A) returns 1 while the button is held. The board file performs the inversion. This is the reason for the abstraction on the GPIO side: the application states the meaning, and the board file states the wiring.

A pull-up resistor and open-drain outputs

A button that is not pressed must read a definite level, not a floating one. A pull-up resistor (pull-up resistor) connects the pin to the supply through a resistor, so the pin reads high when nothing pulls it low. The Blue Pill button uses the chip's internal pull-up, and the Pico button uses its internal pull-up as well, so no external resistor is needed for the buttons.

I2C is different. Its two lines, SCL (clock) and SDA (data), are open-drain (open-drain output). A device can only pull a line low, and nothing drives it high. Each line needs an external pull-up resistor to the supply, typically 4.7 kΩ, which the project wires on the diagram. The solution's comment in hal_bluepill.c says the same: the open-drain bus cannot drive a line high. A missing pull-up does not cause a short circuit, but it makes the bus stay low, so no device can talk.

I2C: addresses, read and write

I2C (I2C) lets several devices share two wires. Each device has an address, and each transaction starts with a START condition, then an address byte, then data bytes, then a STOP condition. The address byte carries seven bits of address and one bit that says whether the master writes to the device or reads from it. The eighth bit is the least significant bit, which is bit 0. A device that recognises its address sends an acknowledge (ACK) bit after the address byte, and it sends an ACK after each data byte.

The address is therefore a 7-bit number, and the byte on the wire is that number shifted left by one, with the read-or-write bit in position 0. This is the source of the most common I2C bug in this lab, so work through it carefully. The SSD1306 OLED has the 7-bit address 0x3C, which is 0011 1100 in binary. On the wire, a write uses the byte 0111 1000, which is 0x78, and a read uses 0111 1001, which is 0x79. The two conventions differ on purpose. The course's hal.h takes the plain 7-bit address, as the Pico SDK does. ST's HAL takes the address already shifted left by one, and it sets the read-or-write bit itself. The macro I2C_7BIT_ADD_READ in stm32f1xx_hal_i2c.h sets bit 0, and the header comment says the address "must be shifted to the left before calling the interface". So the board file must do the shift.

Polling, debouncing and deadlines

The Lab 3 monitor handled the buttons with interrupts (lesson 70). The Lab 4 HAL has no interrupt call, so the application reads the buttons in the loop, a technique called polling. A press has two problems. A mechanical switch bounces: the contacts make and break several times in a few milliseconds before they settle. And the loop must not block while it waits for a press. The application handles the first problem with a time window. A rising edge (a change from released to pressed) is accepted as a press only if the last accepted press on that button was at least 30 ms earlier. This is the rule DEBOUNCE_MS in ui.c, and it appears in the acceptance criteria.

The application's periodic work uses deadlines, as in lesson 55. The loop keeps a next-time value for the sensor sample (every 200 ms), the display update (every 500 ms) and the log line (every second). On each pass it compares the current time with each deadline. The comparison in app.c is (int32_t)(now - deadline) >= 0, which is a signed form of the unsigned subtraction from lesson 73. Both work across the 32-bit wrap, as long as the difference is less than half the range.

A worked example: porting the LED and the address

Take two functions from the Blue Pill file and trace them from the call in the application to the wire. The first is the LED. The application calls hal_gpio_write(HAL_PIN_LED, 1) when the alarm is active. The board file's implementation, as written in the solution, is: 

if (pin == HAL_PIN_LED) {
    /* Active low: drive the pin low to light the LED. */
    HAL_GPIO_WritePin(LED_PORT, LED_PIN, on ? GPIO_PIN_RESET : GPIO_PIN_SET);
}

Trace the values. on is 1, so the conditional chooses GPIO_PIN_RESET, which drives PC13 low. A low pin on an active-low LED lights it. Now take on = 0. The conditional chooses GPIO_PIN_SET, which drives PC13 high, and the LED goes dark. The application never sees the inversion. A reviewer who checks the file asks one question: is every place where the logical value becomes a pin level written in one line, with the wiring explained in a comment? Here it is.

The second function is the address. The application calls hal_i2c_write(0x3C, data, len) for the display. The board file must send the address in the form ST's HAL expects, so the value is shifted left by one before the call. Work it in binary: 

addr7          = 0x3C = 0011 1100
addr7 << 1     = 0111 1000 = 0x78   (bit 0 is now free for R/W)
HAL write      : sends 0x78, the HAL keeps bit 0 at 0 (write)
HAL read       : sends 0x78 | 1 = 0x79, the HAL sets bit 0 (read)

Each step is visible. The shift moves every address bit one place up, and the bit that was in position 7 is lost. That is harmless, because a 7-bit address never uses it. The result has bit 0 clear, which is the position of the read-or-write bit. The ST HAL then sets or clears that bit itself. If the board file forgot the shift, it would send 0x3C, and the bus would see the address 0x1E with a read-or-write bit of 0. The OLED would not answer, and the application would print LAB4 init failed. Without that one shift, the display stays silent.

The code, explained line by line

The Blue Pill file has one function that does the most work, hal_init(). It enables clocks, configures pins and starts the peripherals. Its structure is a checklist, and the Pico file has the same checklist in different calls. Read the start of the function: 

void hal_init(void) {
    HAL_Init();
    __HAL_RCC_GPIOA_CLK_ENABLE();
    __HAL_RCC_GPIOB_CLK_ENABLE();
    __HAL_RCC_GPIOC_CLK_ENABLE();
    __HAL_RCC_USART1_CLK_ENABLE();
    __HAL_RCC_I2C1_CLK_ENABLE();
    ...

HAL_Init() sets up the HAL's own state and starts SysTick at 1 kHz, which is the time base that hal_millis() returns. Lesson 73 explained why that interrupt must have the lowest priority. The next five lines enable the clocks of the GPIO ports A, B and C, the USART1 peripheral and the I2C1 peripheral. Each peripheral does nothing until its clock is on, and this is the same clock gating discussed in lesson 75. A missing line here produces a dead peripheral with no error message. 

GPIO_InitTypeDef g = {0};
g.Pin = LED_PIN;
g.Mode = GPIO_MODE_OUTPUT_PP;
g.Speed = GPIO_SPEED_FREQ_LOW;
HAL_GPIO_Init(LED_PORT, &g);
HAL_GPIO_WritePin(LED_PORT, LED_PIN, GPIO_PIN_SET);

The HAL configures a pin with a structure. GPIO_InitTypeDef g = {0} clears every field, so no value is left over from another pin. g.Pin names the pin, and g.Mode chooses push-pull output, which drives both high and low. The speed is set low, because an LED needs no fast edges. HAL_GPIO_Init() writes the configuration into the port's registers. The final line drives the pin high, which is the off state for an active-low LED. The comment in the file says exactly this, and it is what a reviewer looks for: the start state is set on purpose, not left to the reset value. 

g.Pin = BTN_A_PIN | BTN_B_PIN;
g.Mode = GPIO_MODE_INPUT;
g.Pull = GPIO_PULLUP;
HAL_GPIO_Init(BTN_A_PORT, &g);

The buttons are inputs with the internal pull-up enabled. The bitwise | combines two pin masks into one, so a single call configures both buttons. A pressed button connects the pin to ground, so it reads 0, which the board file turns into 1 for the application. Without the pull-up the pin would float, and it would read a random level when the button is released. 

g.Pin = GPIO_PIN_9;
g.Mode = GPIO_MODE_AF_PP;
g.Pull = GPIO_NOPULL;
g.Speed = GPIO_SPEED_FREQ_HIGH;
HAL_GPIO_Init(GPIOA, &g);

PA9 is the USART1 transmit pin. Its mode is alternate-function push-pull (GPIO_MODE_AF_PP), which hands the pin to the USART instead of to the GPIO register. The project sets the high output speed, which is a choice the solution makes, not a requirement of the protocol. The pin needs no pull, because a transmit pin is always driven by the USART. 

huart1.Instance = USART1;
huart1.Init.BaudRate = 115200;
huart1.Init.WordLength = UART_WORDLENGTH_8B;
huart1.Init.StopBits = UART_STOPBITS_1;
huart1.Init.Parity = UART_PARITY_NONE;
huart1.Init.Mode = UART_MODE_TX;
HAL_UART_Init(&huart1);

The serial format is 115200 baud, eight data bits, one stop bit and no parity, which is written as 8N1. The mode is transmit only, because the Lab 4 log does not read anything from the serial port. Each field is named, so a reviewer can compare the file with the Pico's stdio setup and see that both produce the same format. 

int hal_i2c_write(uint8_t addr7, const uint8_t *data, size_t len) {
    return (HAL_I2C_Master_Transmit(&hi2c1, (uint16_t)(addr7 << 1), (uint8_t *)data,
                                    (uint16_t)len, I2C_TIMEOUT_MS) == HAL_OK) ? 0 : -1;
}

This is the function from the worked example. The argument addr7 << 1 is the shift, and the cast to uint16_t keeps the value in the range the HAL expects. The HAL call returns HAL_OK on success, and the conditional converts that to the course's convention of 0 for success and -1 for an error. The timeout, I2C_TIMEOUT_MS, is set to 100 ms. The call is bounded, as the hal.h comment requires. A device that does not answer makes the call return an error, and the loop keeps running. 

uint32_t hal_millis(void) {
    return HAL_GetTick();
}

HAL_GetTick() returns uwTick, the millisecond counter that SysTick increments. It is the same counter that HAL_Delay() waits on, so a HAL delay and the application's deadlines share one clock. The application never names SysTick, which is the point of the abstraction: a different board could take its time from a hardware timer instead.

Common mistakes and how to spot them

Porting a driver fails in a small number of ways, and each one leaves a clear sign. The mistakes below are common in board ports, and they are the ones a reviewer checks first.

Mistake 1: the I2C address is not shifted

The board file passes 0x3C straight to ST's HAL. Symptom: the serial monitor prints LAB4 init failed at once, and the OLED stays dark. A logic analyser shows the start condition, then the address byte 0x3C, and no ACK. Fix: shift the address left by one before the HAL call, as the solution does, and check the mystery sensor at 0x48 in the same way, which becomes 0x90.

Mistake 2: the LED is driven the wrong way

The board file sets the pin high to light the LED, which is the active-high rule. On the Blue Pill that is backwards. Symptom: the LED is on when the alarm is off, and off when it should be on. The log shows ALARM=0 while the LED lights. Fix: make hal_gpio_write() invert the level for PC13, as the solution's comment says, and test with hal_gpio_write(HAL_PIN_LED, 1) alone before you test the alarm.

Mistake 3: a clock is left off

The GPIO clock for the buttons is not enabled, or the I2C clock is missing. Symptom: the buttons never move the menu, or the I2C transfers all return errors, and the sensor appears to be broken. The code looks correct, because the configuration calls run without error. Fix: check the clock list at the start of hal_init() against the peripherals you use. A peripheral with no clock ignores its register writes.

Mistake 4: the application is changed to fit the board

A developer finds that the Blue Pill needs a different button pin, and edits app/ui.c to read PB12 directly. Symptom: the build succeeds on the Blue Pill, but the Pico build fails, or the diff of app/ against the solution is no longer empty. Fix: put the pin in the board file, and change nothing in app/. The acceptance test in this lab is that diff, so the mistake is caught by the same check you run to finish.

Mistake 5: a blocking call on the main loop

A developer uses HAL_Delay(100) inside the redraw to wait for the OLED. Symptom: the buttons miss presses, because the loop is busy, and the log lines arrive late and in bursts. Fix: keep the bus calls bounded, as hal.h requires, and use the deadlines. A HAL delay in the main loop is a blocking call, and it is the same problem lesson 55 described.

In real projects

Production teams use this pattern for every product that may outlive its first microcontroller. The layer boundary is usually called a board support package (BSP) or a platform layer, and the names differ between companies. The rules are the same. The application calls only the layer. The layer's functions have fixed signatures. Each board port is reviewed as a unit, and each port is tested with the same application tests. Part 6 of this course (lesson 80) uses the same header to run the application on a PC with fake board files, which is the main benefit: the application can be tested without any hardware.

Reviewers look for three things in a port. They check that the abstraction does not leak, which means no SDK types or register names appear in the application. They check that each conversion between logical and physical levels is written in one place, with a comment that gives the wiring. And they check the timing: every call that waits must have a bound, so one missing device cannot stop the product. Porting a driver to a new chip comes down to this lab's rule: the interface is the contract, the board file is the only file that changes, and the diff proves it.

Note also that the two ports are not identical in speed. The Pico bus runs at 400 kHz, and the Blue Pill bus at 100 kHz, so a full screen update takes about a quarter of the time on the Pico. The application's deadlines are the same on both boards, and they still work, because the redraw is short compared with the 500 ms period. A port that is correct only at one speed is a port with a hidden assumption, and reviewers ask for the assumption to be written down.

Summary

  • A HAL is a header the application includes, plus one implementation file per board. Porting means writing one file, and the application folder stays the same.
  • Logical levels hide the wiring. The Blue Pill LED is active low, and the board file inverts the level once, in one place.
  • I2C addresses are 7-bit numbers. On the wire, the byte is the address shifted left by one, with the read-or-write bit in bit 0. ST's HAL expects the shifted form, and the course's hal.h does not.
  • I2C lines are open-drain, so each needs a pull-up resistor. Buttons use the chip's internal pull-up, and a pressed button reads 0.
  • Buttons are polled, and each press is debounced by a 30 ms window. A press shorter than one pass of the loop can be missed.
  • Periodic work uses deadlines compared with a wrap-safe difference, not with raw times.
  • The proof of a port is an empty diff of the application folder, plus a build for each board.

Acceptance criteria

  • The serial monitor prints LAB4 OK once, after the start-up, and then one log line per second.
  • The OLED shows the temperature on LIVE, and the same value appears in the log within one second.
  • Button A cycles LIVE, MINMAX and SETPOINT, and the log shows each screen name in turn.
  • On SETPOINT, button B raises the threshold from 28 to 35, then wraps to 20. At a threshold of 22 the log shows ALARM=1 and the LIVE screen shows ALARM.
  • One click produces one screen change. A second press within 30 ms counts as the same press.
  • Remove the sensor's SDA wire. Within about one second the LIVE screen shows SENSOR ERR, and the buttons and the log keep working.
  • The diff of app/ between your project and the solution is empty.

Differences from Lab 3, and why

  • Buttons are polled. Lab 3 used interrupts. The HAL has no interrupt call, so ui_poll() reads the pins on every pass of the loop and debounces each button by time. A press shorter than one pass of the loop can be missed. A full-screen OLED update takes about 100 ms on the Blue Pill bus, so a short tap during a redraw can be lost. Lesson 57 explains the interrupt version that Lab 3 uses.
  • Temperatures are integers. The sensor count is converted to hundredths of a degree with integer maths, so no board needs float printf.
  • The alarm drives the LED. This uses hal_gpio_write(), and is the only output the HAL needs for the alarm.

Hints

Hint for hal_init

Enable the GPIO clocks, the USART1 clock and the I2C1 clock before you call the HAL init functions. The pico file does the same in one hal_init() function, so use it as the checklist, and map each step to an STM32 call.

Hint for the I2C address

Two layers, two address conventions. The course's hal.h takes the plain 7-bit address (addr7), as the Pico SDK does. ST's HAL_I2C_Master_Transmit and HAL_I2C_Master_Receive instead take the 7-bit address shifted left by one, and set the read/write bit themselves (the source comment says the address "must be shifted to the left before calling the interface"). So hal_bluepill.c passes addr7 << 1 for both directions: the OLED's 0x3C becomes 0x78, and the mystery sensor's 0x48 becomes 0x90, for reads and writes alike. Mixing the conventions up is one of the most common I2C bugs: the device never acknowledges.

Hint for the buttons

A button held to ground reads 0. The board file turns that into 1 for pressed, and the application debounces the result. If the menu never moves, check the pull-up in hal_init() before you blame the debounce.

Hint if the screen or the sensor stays silent

The application prints LAB4 init failed when a device does not answer during start-up. Check the wiring first: SDA is PB7, SCL is PB6, both have 4.7 kΩ pull-ups to 3.3 V, and the OLED's VCC pin is on 3.3 V. Then check that each device has the address above.

Hint for the timing

A full-screen update is 8 pages. Each page sends three 2-byte commands and one 129-byte data frame (a control byte and 128 columns), so 1080 data bytes, plus one address byte for each of the 32 transactions. At 100 kHz with 9 bit times per byte (8 bits and an ACK) that is 1112 × 9 ÷ 100 000 s, about 100 ms. The application redraws only when something changes, and at every 500 ms deadline. The Pico's 400 kHz bus takes about a quarter of that. A DMA transfer from lesson 74 could shorten the redraw further, but the HAL in this lab does not use one.
