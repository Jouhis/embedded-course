Timing analysis, deadlines and stack sizing

An RTOS design is correct only if every task meets its deadline and every stack is big enough. You can check both: measure the stacks with the kernel's high-water mark, measure the time with a timer, and check the schedule with a utilisation bound.

By the end of this lesson you can read a task's stack high-water mark, enable the stack-overflow hook, time a code section with a hardware timer, assign rate-monotonic priorities, and check a task set against the Liu and Layland utilisation bound n(2^(1/n) − 1).

The idea

Lesson 78 introduced the stack and stack overflow. An RTOS task has a fixed stack, chosen when the task is created, and overflow of that stack writes over another task's data without any error from the CPU. So the question is how much of the stack a task really uses. FreeRTOS answers it with a high-water mark: at creation the kernel fills the stack with a known pattern, and uxTaskGetStackHighWaterMark() returns the fewest words that were ever still unused. The function's definition is in tasks.c near line 6362, enabled by INCLUDE_uxTaskGetStackHighWaterMark.

The high-water mark is a lower bound on the free space, and it covers only the paths that ran. A rarely taken branch that uses a deep call chain can still overflow after the test passed. Size the stack for the worst path you can reason about, then check it with the mark.

Catching an overflow

Set configCHECK_FOR_STACK_OVERFLOW to 2 (the template does) and FreeRTOS checks, at each switch, whether the stack pointer has gone below the stack's start. It also checks a pattern near the bottom. If the check fails, the kernel calls vApplicationStackOverflowHook(TaskHandle_t, char *). The template defines that hook, and it stops in an infinite loop, so a debugger can show which task failed. A hook that does nothing hides the bug.

The check runs at task switches. A task that overflows and then blocks in a way that does not switch can still corrupt memory before the hook runs. The high-water mark and the hook catch most overflows, not every one.

Measuring execution time

The most accurate local timer is a hardware counter. The Cortex-M3 has the DWT cycle counter (DWT->CYCCNT), and Wokwi's documentation lists DWT as implemented for the Blue Pill; we have not verified its counts against silicon, so this lesson uses TIM2 instead. TIM2 is a 16-bit counter on the APB1 clock, and the project sets its prescaler so that one count is one microsecond. Take the counter before and after the work, and subtract. The subtraction in 16-bit unsigned arithmetic is correct across one wrap, as long as one measurement is shorter than 65 ms. 

static void timed_work(uint32_t loops, volatile uint32_t *max_us) {
    uint16_t start = (uint16_t)TIM2->CNT;
    do_work(loops);
    uint32_t elapsed = (uint16_t)((uint16_t)TIM2->CNT - start);   /* wrap-safe */
    if (elapsed > *max_us) *max_us = elapsed;                    /* keep the worst case */
}

Keep the worst case, not the average. The deadline is about the worst case, and an average hides exactly the bursts that miss a deadline.

Rate-monotonic priorities

For periodic tasks with fixed priorities, the standard assignment is rate-monotonic: the shorter the period, the higher the priority. Liu and Layland proved in 1973 that for independent periodic tasks with deadlines equal to periods, this order is optimal among fixed-priority schemes, and that a set of n tasks is schedulable if its total utilisation U (the sum of execution time over period) satisfies

U = Σ (Ci / Ti)  ≤  n · (21/n − 1)

n = 1: 1.000     n = 2: 0.828     n = 3: 0.780     n → ∞: ln 2 ≈ 0.693

The bound is sufficient, not necessary: a set above it may still be schedulable, and you need an exact response-time analysis to decide. But a set below it is always schedulable under rate-monotonic priorities, so it is the check you do first. The project's three tasks use periods of 10 ms, 100 ms and 1000 ms, and the bound applies to them.

TaskPeriod TWork CC / T
fast (priority 3)10 msabout 1 ms0.10
slow (priority 2)100 msabout 5 ms0.05
report (priority 1)1000 msabout 1 ms0.001

The total is about 0.15, well below the three-task bound of 0.780, so the set is schedulable by construction. The measurement in the project confirms the work times.

Model answer

Use rate-monotonic priorities: the shortest period gets the highest priority. Measure the worst-case execution time C of each task, and compute the utilisation sum of C over T. If the sum is below n(2^(1/n) − 1), which is 0.780 for three tasks, the set is schedulable under fixed priorities with deadlines equal to periods. If it is above the bound, do not conclude that it fails: run an exact response-time analysis. Also say that the bound assumes independent tasks, so a mutex or a blocking call must be added to the analysis, and that the worst case, not the average, is what you measure. For the stacks, read the high-water mark after a long run, add a margin, enable the overflow check, and say that the mark covers only the paths that ran.
