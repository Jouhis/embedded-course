Timing analysis, deadlines and stack sizing

An RTOS design is correct only if every task meets its deadline and every stack is big enough. You can check both: measure the stacks with the kernel's high-water mark, measure the time with a timer, and check the schedule with a utilisation bound.

By the end of this lesson you can read a task's stack high-water mark, enable the stack-overflow hook, time a code section with a hardware timer, assign rate-monotonic priorities, and check a task set against the Liu and Layland utilisation bound n(2^(1/n) − 1).

Where we are and why it matters

Lesson 87 set up FreeRTOS and showed tasks being created and scheduled. Lesson 89 added queues and semaphores, and lesson 90 added mutexes and the problems they bring. In all of those lessons the code worked on the first try in the simulator, and that is the trap: a demo that runs once tells you nothing about whether the design survives a bad minute. A product has to meet its timing every time, with the worst input and the worst interrupt timing, and it has to do that in the RAM the chip actually has.

Two questions decide that. The first is whether each task has enough stack, the memory where its local variables and return addresses live (lesson 78 covered the stack and what overflow does). The second is whether each task finishes its work before its deadline, which is the time by which the work must be done or the system is wrong. A motor controller that runs its current loop 2 ms late can overheat a winding. A fitness tracker whose display update is late by 200 ms is only annoying. Real jobs in motor control, medical devices and automotive ECUs are judged on both questions, and a senior engineer will ask for the numbers. This lesson gives you the tools to produce them.

The stack of each task

In FreeRTOS, every task has its own stack, and you choose its size when you create the task. The size is the last argument we would expect to be a guess, and the first thing to replace with a measurement. The call looks like this in the project (projects/0091-stack-and-timing/solution/main.c): 

xTaskCreate(fast_task, "fast", FAST_STACK_WORDS, NULL, 3U, &fast_handle);

The third argument is the stack depth, and the FreeRTOS header says it is "the number of variables the stack can hold - not the number of bytes" (third_party/FreeRTOS-Kernel/include/task.h, the xTaskCreate documentation). On the Cortex-M3 a stack variable is a 32-bit word, so a depth of 128 is 512 bytes. Forgetting that factor of four is one of the most common sizing errors, and it is covered in the mistakes section below.

A stack grows downward in memory on the Cortex-M3. Each function call pushes a return address and its local variables, and the stack pointer moves toward the bottom of the task's block. The bottom is the dangerous end. If a deep call chain or a large local array pushes past it, the write lands in whatever memory sits below, which may be another task's stack or a global variable. The CPU does not stop that write. Nothing in the hardware knows where one task's stack ends and the next begins.

Painting the stack: the high-water mark

The kernel gives you a way to see how much of the stack was really used. When it creates a task, it fills the whole stack with a known byte pattern. The fill byte is defined in tasks.c as tskSTACK_FILL_BYTE, which is 0xa5 (line 120). The stacks are filled only if the kernel is configured to need the information (the condition is at line 130 of tasks.c, which is true when the high-water mark function is enabled). When the task runs, its stack pointer moves down and overwrites some of the pattern. Words that still hold the pattern were never touched.

Later, uxTaskGetStackHighWaterMark() scans from the bottom of the stack upward, counting words that still hold the fill pattern. The function is defined at tasks.c line 6429, and it is enabled by INCLUDE_uxTaskGetStackHighWaterMark, which the project sets to 1. The return value is the fewest free words ever seen, in words, and the header says so: "the minimum amount of stack space that has remained for the task since the task was created" (include/task.h). The smaller the number, the closer the task came to overflowing.

The most important property of the high-water mark is that it is a record of the past. It is correct for the paths that actually ran. A rarely taken branch that makes a deep call can still overflow after your test passed, and the high-water mark will not warn you, because the mark only records what happened. So the procedure is: size the stack for the worst path you can reason about, run the system through its busiest scenario for long enough, read the mark, and keep a margin. The project uses 16 words as the margin, which is 64 bytes.

Catching an overflow before it spreads

A high-water mark tells you about the past. A stack overflow check tells you the moment one happens. The option configCHECK_FOR_STACK_OVERFLOW controls it, and the project sets it to 2. With level 2, at every task switch the kernel checks two things: whether the saved stack pointer has gone below the stack's limit, and whether the fill pattern is still present at the bottom of the stack (the four words checked are the 0xa5a5a5a5 pattern, in the macro in include/stack_macros.h). If either check fails, the kernel calls vApplicationStackOverflowHook().

The hook is a function you write, with the signature void vApplicationStackOverflowHook(TaskHandle_t t, char *name). The project's version does nothing except loop forever, which is deliberate. It stops the system at the moment of the bug, so a debugger shows which task overflowed and where. A hook that returns quietly hides the bug, and the corrupted memory keeps spreading. Real systems often log the task name to non-volatile memory and reset, but the principle is the same: a stack overflow is a bug, and the system must not continue as if it were not.

The check runs at task switches. A task that overflows and then blocks in a way that does not switch can corrupt memory before the hook runs. The high-water mark and the hook catch most overflows, not every one. This is one reason for the margin.

Measuring execution time

Stack size answers the memory question. The timing question needs a clock that counts finer than a tick. The FreeRTOS tick in this project is 1 kHz (configTICK_RATE_HZ 1000), so one tick is 1 ms. That is too coarse for a 1 ms task, so the project times its work with a hardware timer, TIM2.

TIM2 is a 16-bit counter that counts clock pulses. Its prescaler (the PSC register) divides the input clock before it reaches the counter. The project divides the clock so that one count is one microsecond. The system clock is SystemCoreClock, and the project does not configure the phase-locked loop (PLL) that would raise it, so the value stays at the reset default of 8 MHz (the variable is initialised to 8000000 in system_stm32f1xx.c). The prescaler is therefore 8 minus one, which the code computes rather than hard-codes: 

TIM2->PSC = (SystemCoreClock / 1000000U) * TIMER_TICKS_PER_US - 1U;

The project computes the value from SystemCoreClock so that the one-microsecond count stays true if someone later changes the clock setup. A hard-coded 7 would silently make every measurement wrong after such a change.

The timing pattern is simple: read the counter, do the work, read the counter again, and subtract. The subtraction must use unsigned arithmetic, and the cast to uint16_t does the work. When the 16-bit counter wraps from 65535 back to 0 during the work, the difference still comes out right, as long as the work is shorter than the wrap time. At one microsecond per count, the wrap time is 65.536 ms, so one measurement must finish within that window. This is the wrap-safe timeout idea from the timing chapter of the course glossary. 

static void timed_work(uint32_t loops, volatile uint32_t *max_us) {
    uint16_t start = (uint16_t)TIM2->CNT;
    do_work(loops);
    uint32_t elapsed = (uint16_t)((uint16_t)TIM2->CNT - start);   /* wrap-safe */
    if (elapsed > *max_us) *max_us = elapsed;                    /* keep the worst case */
}

Keep the worst case, not the average. A deadline is about the worst case: one slow run that is 2 ms late is a failure even if the average is fine. An average hides exactly the bursts that miss a deadline, which is why the report prints the worst value.

Deadlines, periods and rate-monotonic priorities

A periodic task runs at a fixed rate. Its period T is the time between starts, and its work C (also called execution time) is the CPU time it needs per run. Its deadline is the time by which each run must finish. The usual simple case sets the deadline equal to the period, so the task must finish before its next start.

The fixed priorities of FreeRTOS decide which task runs when two are ready. For periodic tasks the standard choice is rate-monotonic assignment: the shorter the period, the higher the priority. The reason is intuitive once you picture it. A task that must run every 10 ms cannot wait behind a task that runs every second, because it would miss its window. A task that runs every second can always wait a few milliseconds. In FreeRTOS, a larger number means a higher priority (the port's configMAX_PRIORITIES sets the range), so the 10 ms task gets priority 3, the 100 ms task gets 2, and the 1000 ms report gets 1.

Liu and Layland published the key result in 1973. For independent periodic tasks whose deadlines equal their periods, rate-monotonic priorities are optimal among fixed-priority schemes. They also gave a test. Add up the utilisation of every task, where each task's utilisation is its work divided by its period, U = Σ Ci/Ti. If U is at most n(21/n − 1) for n tasks, every task meets its deadline. The right-hand side decreases as n grows, and it approaches ln 2, about 0.693, as n becomes large. 

U = Σ (Ci / Ti)  ≤  n · (21/n − 1)

n = 1: 1.000     n = 2: 0.828     n = 3: 0.780     n → ∞: ln 2 ≈ 0.693

The bound is sufficient, not necessary. A task set above the bound may still be schedulable, and then you need an exact response-time analysis to decide. But a set below the bound is always schedulable under rate-monotonic priorities, so the bound is the first check you run, and it costs one line of arithmetic.

A worked example with numbers

Take the three tasks of the project. The fast task runs every 10 ms, the slow task every 100 ms, and the report task every 1000 ms. Suppose the design targets are the work times in the table below. These are design targets, not measurements. Your report shows the real numbers, and you replace these with them.

TaskPriorityPeriod TWork C (target)C / T
fast310 ms0.3 ms0.030
slow2100 ms3 ms0.030
report11000 ms0.5 ms0.0005

Step by step: the fast task uses 0.3 ms out of every 10 ms, so its share is 0.3 divided by 10, which is 0.030. The slow task uses 3 ms out of 100 ms, which is 0.030 again. The report task uses 0.5 ms out of 1000 ms, which is 0.0005. The total is 0.0605. The bound for three tasks is 0.780, so the set passes the test with a wide margin. Even if the real work were ten times longer than the targets, the total would be 0.605 and still under the bound.

The margin is the point of the exercise. The bound says nothing about the stack, the shared bus or the interrupts, so a passing result is a necessary first step, not a proof of the whole system. Lesson 90 showed that a mutex can make a high-priority task wait for a low-priority one, and that wait is extra time the bound does not include. A review should ask for the blocking time as well.

Reading the code, line by line

The periodic task in the project is the piece that ties the timing together. Here is the fast task from the solution, with the important lines explained: 

static void fast_task(void *arg) {
    (void)arg;
    TickType_t last_wake = xTaskGetTickCount();
    for (;;) {
        timed_work(FAST_WORK_LOOPS, &fast_max_us);
        vTaskDelayUntil(&last_wake, pdMS_TO_TICKS(FAST_PERIOD_MS));
    }
}

last_wake holds the tick at which the task last started. It is set once, before the loop. (void)arg tells the compiler that the parameter is unused, which keeps the warning list clean. Inside the loop, timed_work() runs the work and records its worst time into fast_max_us. The last line is the important one. vTaskDelayUntil() sleeps until last_wake plus the period, and it then moves last_wake forward by exactly one period. A plain vTaskDelay(10) would instead sleep 10 ms after the work finished, so the period would drift by the work time on every cycle. Over a long run the drift adds up, and the measured rate is wrong. pdMS_TO_TICKS() converts milliseconds to ticks, and with a 1 kHz tick the conversion is the identity, so 10 ms is 10 ticks.

The report function reads the mark for one task: 

UBaseType_t free_words = uxTaskGetStackHighWaterMark(h);
uint32_t used_words = depth_words - free_words;

The first line asks the kernel for the fewest free words the task has ever had. The second line subtracts it from the depth that was requested at creation, which gives the peak use in words. Both values are in words, so the report multiplies by four to print bytes. The starter's version of this function is the one you change in the hands-on task.

Common mistakes and how to spot them

Mistake 1: leaving the placeholder in the report. The starter's report_one() sets the free words to 0 until you call the kernel function. The symptom on the serial monitor is clear: every task shows free=0 B and the verdict says STACK LOW, even for a stack that has plenty of room. The fix is to call uxTaskGetStackHighWaterMark(h) and remove the placeholder. The lesson here is that a report which always prints the same value is not a measurement.

Mistake 2: confusing words with bytes. A stack depth of 128 is 128 words, which is 512 bytes on the Cortex-M3. If you size a stack in bytes by mistake and pass 512, the task gets 2048 bytes and the memory use is four times what you planned. The symptom is the opposite one: the heap runs out sooner than you expect, because each task reserves four times the memory. The fix is to read the header comment of xTaskCreate and keep one unit throughout the code, with the conversion in one place, as the report does.

Mistake 3: reading the high-water mark too early. The mark records only what has run. If you read it a few milliseconds after startup, the deepest path may not have run yet. The symptom is a comfortable margin in the first report and an overflow in the field, when a rare command arrives. The fix is to read the mark after the system has run its busiest scenario, and to keep a margin on top. The project's report task reads the marks every second, which is a practical habit: the worst value is kept by the kernel, so the last reading is the peak so far.

Mistake 4: using a plain delay for a periodic task. A task written with vTaskDelay() runs at a period of work time plus delay time, not at the period you wrote. The symptom appears only over time: the measured rate drifts, and a task that should run 100 times in 10 seconds runs 98 times. The fix is vTaskDelayUntil(), as the solution uses, with the previous wake time kept between cycles.

Mistake 5: an empty overflow hook. A hook that returns, or a missing configCHECK_FOR_STACK_OVERFLOW, means an overflow is silent. The symptom is a task that behaves strangely a long time later, with no error message. The fix is a hook that stops the system, as in the project, and a debugger session that reads the task name. The hook is the cheapest insurance in the whole lesson.

In real projects

Teams that ship RTOS products run stack and timing analysis as a routine part of each release. A common practice is to record the high-water mark of every task after a long soak test and keep it in the test report, so that a change which eats stack shows up as a number in code review rather than as a crash in the field. Another common practice is to measure the worst-case execution time of each interrupt and each task on the real board, with a timer such as the one in this lesson, and to compare the sum against the deadlines. Some teams add a runtime statistics feature that reports the CPU share of each task, which the FreeRTOS configuration can enable.

In a code review, a senior engineer looks for three things. The stack size should be justified by a number, not left at a default. Each periodic task should use a delay until a fixed time, not a delay after the work. And the worst case should be the value that is checked, not the average. In interviews the same three points come up in the form of the question at the end of this lesson. Be ready to say that the utilisation bound is a sufficient test, that it assumes independent tasks and deadlines equal to periods, and that a mutex or a blocking call adds time the bound does not count.

Summary

  • Each FreeRTOS task has its own stack. The depth in xTaskCreate() is in words, which are 4 bytes on the Cortex-M3.
  • The kernel paints each new stack with 0xa5. uxTaskGetStackHighWaterMark() returns the fewest free words the task has had, which is a record of the paths that ran.
  • configCHECK_FOR_STACK_OVERFLOW set to 2 checks at each task switch, and calls vApplicationStackOverflowHook() when the stack limit or the bottom pattern fails.
  • Time a section by subtracting two counter reads in unsigned arithmetic. Keep the worst case, because a deadline is about the worst case.
  • Use vTaskDelayUntil() for periodic tasks, so the period does not drift with the work time.
  • Rate-monotonic priorities give the shortest period the highest priority. For n tasks, a total utilisation at or below n(21/n − 1) guarantees the deadlines. The bound is sufficient, not necessary.

"You have three periodic tasks and a deadline on each. How do you assign priorities, and how do you know the design is schedulable?" Answer out loud in 90 seconds, then compare.

Model answer

Use rate-monotonic priorities: the shortest period gets the highest priority. Measure the worst-case execution time C of each task, and compute the utilisation sum of C over T. If the sum is below n(2^(1/n) − 1), which is 0.780 for three tasks, the set is schedulable under fixed priorities with deadlines equal to periods. If it is above the bound, do not conclude that it fails: run an exact response-time analysis. Also say that the bound assumes independent tasks, so a mutex or a blocking call must be added to the analysis, and that the worst case, not the average, is what you measure. For the stacks, read the high-water mark after a long run, add a margin, enable the overflow check, and say that the mark covers only the paths that ran.
