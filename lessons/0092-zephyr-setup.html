Zephyr setup: west, the toolchain, and a first app on the Pico

Zephyr is the RTOS that Nordic, NXP and other chip makers ship with their SDKs. Before you write a single thread, you need to know how its tool, west, fetches the source and builds an application.

By the end of this lesson you can build a Zephyr application for the Pico with west build -b rpi_pico, change its blink period, and explain what west, the manifest and the project filter each do.

The idea

Zephyr is not one program. It is a source tree of many git repositories, plus the vendor HAL modules for each chip. west is the meta-tool that fetches those repositories, and it reads a manifest to know which repositories to fetch and at which revision. The manifest for upstream Zephyr is zephyr/west.yml. Your copy of the workspace records its own choices in .west/config. The manifest is a list of projects, each with a remote, a revision and a path. Industry teams often write their own manifest, which pins every repository to a tested commit. That is how a product gets reproducible builds.

Our workspace is ~/zephyrproject, at Zephyr v4.5.0. It uses a project filter. The filter keeps only the modules we need, so west update downloads less. Here is the exact setting, from ~/zephyrproject/.west/config: 

[manifest]
path = zephyr
file = west.yml
project-filter = -.*,+cmsis.*,+hal_rpi_pico,+hal_stm32

Read the filter left to right. -.* drops every project, then the + entries add back the CMSIS modules and the two HALs for the Pico (hal_rpi_pico) and the Blue Pill (hal_stm32). Run west list and you see exactly those projects. The Zephyr repository itself is always present, because it is the manifest repository.

The toolchain: gnuarmemb, not the SDK

Zephyr needs a compiler and a set of build tools. The Zephyr SDK bundles its own toolchains and host tools. We do not need it: our Zephyr uses the gnuarmemb toolchain variant, which means "the Arm GNU Embedded toolchain that is already installed on the PATH". You select it with ZEPHYR_TOOLCHAIN_VARIANT=gnuarmemb and GNUARMEMB_TOOLCHAIN_PATH. The course build script sets both for you (tools/build.py). See the Zephyr toolchain page for the variants that exist, and the getting-started guide for the SDK route. The trade-off is simple. The SDK gives you a known-good set of compilers for every board. gnuarmemb reuses the Arm toolchain you already use for the Pico SDK, which is what we do here.

Building for a board

The command is west build -b rpi_pico, run from the workspace, with the application folder named. -b picks the board, and the board's devicetree and defconfig come from zephyr/boards/raspberrypi/rpi_pico/. The build output goes to build/ inside the application. The course's tools/build.py runs exactly that command with -p auto (pristine when needed) and -d for the build folder. 

west build -p auto -b rpi_pico -d build /path/to/projects/0092-zephyr-setup/solution
Reproducing the workspace from scratch is three steps: create a virtual environment and install west; run west init on an empty folder; set the filter with west config manifest.project-filter "-.*,+cmsis.*,+hal_rpi_pico,+hal_stm32" and run west update. The venv must be the one tools/build.py expects, which is ~/zephyrproject/.venv. Check the result with west list and west manifest --path.
The name west manifest --active-path that some notes use does not exist in west v1.5.0. The flags are --resolve, --freeze, --validate, --path and --untracked, with --active-only as a modifier (run west manifest --help to see them). Use --path to find the manifest file.

Try it in Wokwi

Zephyr runs on the Pico in Wokwi like any other firmware. The first step is to see the blink work. In the starter, the period is a named constant that is set to 500 ms, with a TODO(learner) comment next to it. The solution uses 250 ms and prints each toggle.

  1. Open projects/0092-zephyr-setup/starter in VS Code (File → Open Folder).
  2. Build: Ctrl+Shift+B. The task calls tools/build.py, which calls west build.
  3. Start the simulator: F1 → Wokwi: Start Simulator.
  4. Your task: change BLINK_PERIOD_MS to 250, print the line "ZEPHYR SETUP OK" once before the loop, and add the toggle counter. You'll know it works when the serial monitor shows "toggle 1 at …" every 250 ms and the LED blinks twice as fast.
Hint

The starter has three TODO(learner) comments. Each one is one line of code. The toggle counter is a uint32_t that you increment after gpio_pin_toggle_dt(), then print with printk().

The reference solution is in projects/0092-zephyr-setup/solution. Try first, compare after.

Wokwi is a digital simulator and the Zephyr template runs in it through the same ELF file that the build produces. This course has no simulator token in its verified environment, so we confirmed the build, the ELF and the diagram lint, not a live simulation run. Check the blink in the simulator yourself.
You built a Zephyr application for the Pico with west, changed its timing from a named constant, and can say what the manifest, the project filter and the gnuarmemb variant each control.

"What is the difference between an RTOS's build system and the vendor SDK's build system, and how does Zephyr's tooling fit?" Answer out loud in 60 seconds, then compare.

Model answer

Zephyr's build is CMake plus Kconfig plus devicetree, driven by west. A vendor SDK usually has one build system tied to one family of chips. Zephyr builds the same application for many boards by selecting the board's devicetree and defconfig, and the repositories and their revisions are pinned by the west manifest. The toolchain is chosen separately (gnuarmemb here, or the Zephyr SDK).
