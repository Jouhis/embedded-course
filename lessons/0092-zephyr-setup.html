Zephyr setup: west, the toolchain, and a first app on the Pico

Zephyr is a real-time operating system with its own drivers, configuration and build system. Before you write a single thread, you need to know how its tool, west, fetches the source and builds an application.

By the end of this lesson you can build a Zephyr application for the Pico with west build -b rpi_pico, change its blink period, and explain what west, the manifest and the project filter each do.

Where we are and why it matters

Lessons 86 and 87 introduced the idea of an RTOS and showed FreeRTOS: a kernel with tasks, queues and a tick, and nothing else. Lessons 88 to 91 built on it for the STM32. FreeRTOS gives you the scheduler and the synchronisation objects, but the rest is yours to write. You choose the drivers, you decide how the board's pins are named in code, and you pick the build settings. Every project in a company then repeats those choices.

Zephyr is the other common choice. It is a kernel with threads, a driver model, a hardware description, a configuration system and a build tool, all designed together. Nordic Semiconductor's SDK is built on Zephyr (see the resources list in the course), and a firm that ships several boards from several chip families often picks Zephyr so that one application and one set of tools can cover all of them. The next four lessons cover how those parts fit together: this lesson is the workspace and the build, lesson 93 is the configuration, lesson 94 is the hardware description, and lesson 95 is threads and kernel services.

The workspace has two parts that are easy to confuse. The first is the Zephyr source tree, which is many git repositories fetched together, and the second is your application, which is a small folder with a CMakeLists.txt, a prj.conf and some C files. This lesson is about the first part, and about how the second is built against it.

What Zephyr is made of

Zephyr is not one program. It is a source tree of many repositories: the kernel and its libraries, the board definitions, the drivers, and the hardware abstraction layer (HAL) modules that vendors supply for their chips. A HAL is the vendor's code that talks to the registers of one chip family, so that the rest of Zephyr can use one API. The Pico's HAL comes from Raspberry Pi, and the Blue Pill's from ST. You do not need to know their internals yet. You do need to know that they are separate repositories, and that the workspace decides which ones to download.

Zephyr uses the word thread for what FreeRTOS calls a task. The glossary entry says to use the word thread inside Zephyr text, so this course does. A thread has its own stack, a priority in which a smaller number is more urgent (the opposite of FreeRTOS), and an entry function, just as a task does. The difference in numbering is a common source of confusion when you move between the two, and lesson 95 returns to it.

west: the meta-tool

West is the Zephyr meta-tool. It does three jobs. It fetches the repositories, it runs the build for a board, and it flashes the result. The first job is the one that makes a workspace, and it depends on a file called the west manifest. The manifest is a list of projects, each with a remote address, a revision and a path on disk. For upstream Zephyr the manifest is zephyr/west.yml, which lists every module the project knows about.

The workspace used by this course is at ~/zephyrproject, and it is pinned to Zephyr v4.5.0. Our copy of zephyr/west.yml lists the projects, and the workspace's own settings say which of them to keep. Those settings live in .west/config, and the relevant part is this: 

[manifest]
path = zephyr
file = west.yml
project-filter = -.*,+cmsis.*,+hal_rpi_pico,+hal_stm32

The path and file lines say where the manifest is. The project-filter line is the one to understand. A filter is a list of patterns, read from left to right, and each one either removes projects (with -) or keeps them (with +). The first pattern, -.*, removes every project. The next four keep the projects whose names match: any name starting with cmsis, and the two HAL modules for the Pico (hal_rpi_pico) and the Blue Pill (hal_stm32). Running west list in the workspace shows the result: the Zephyr repository itself (always present, because it holds the manifest), three CMSIS projects, and the two HALs.

The filter exists to save disk space and download time. The full Zephyr tree with every HAL and every module is several gigabytes. A filter that keeps only the Pico and the Blue Pill is a small fraction of that, and the course's setup script sets it for that reason.

Setting up the workspace

The course's setup script does the whole job for you. From the workspace root, run python tools/setup.py --zephyr. It is an optional step, and it downloads about 1 to 2 GB, so it is not part of the core setup. The script creates a virtual environment in ~/zephyrproject/.venv, installs west into it, runs west init with the Zephyr v4.5.0 manifest, sets the project filter, runs west update, and installs Zephyr's Python requirements. If zephyr/west.yml and the west program already exist, it reports the workspace as present and does nothing else.

The steps behind the script are worth knowing, because each one can fail on its own and the error message points at one step. Done by hand on Windows, they are these:

  1. Create the virtual environment: python -m venv ~/zephyrproject/.venv. On macOS and Linux the programs are in bin/ instead of Scripts/.
  2. Install west into it: ~/zephyrproject/.venv/Scripts/python -m pip install west.
  3. Create the workspace from the manifest: west init -m https://github.com/zephyrproject-rtos/zephyr --mr v4.5.0 ~/zephyrproject. The --mr option pins the revision.
  4. Set the filter. In the workspace, run west config manifest.project-filter -- "-.*,+cmsis.*,+hal_rpi_pico,+hal_stm32". The -- is needed because the value starts with a minus sign, which west would otherwise read as an option.
  5. Download the projects: west update. This is the step that takes most of the time.
  6. Install the Python packages that Zephyr's build needs: python -m pip install -r zephyr/scripts/requirements-base.txt, run with the venv's Python.

Check the result with two commands. west list should show the Zephyr repository and the six projects that the filter keeps. west manifest --path should print the path to zephyr/west.yml. The manifest command has several options, and the flags are --resolve, --freeze, --validate, --path and --untracked, with --active-only as a modifier. The name --active-path that some notes use does not exist in west v1.5.0, which is the version installed here.

The toolchain: gnuarmemb, not the SDK

Zephyr needs a compiler and the tools around it. Zephyr's own SDK bundles its own compilers and host tools, and it is the usual route for a new user. This course does not use it. Our workspace uses the gnuarmemb toolchain variant, which means "the Arm GNU Embedded toolchain that is already on this machine". The variant is chosen with two environment variables. ZEPHYR_TOOLCHAIN_VARIANT must be gnuarmemb, and GNUARMEMB_TOOLCHAIN_PATH must point at the folder that contains arm-none-eabi-gcc. The Zephyr CMake file for this variant checks that the path exists before it goes on (zephyr/cmake/toolchain/gnuarmemb/generic.cmake, lines 3 to 6).

The course's build script sets both variables for you when it finds the compiler, using the Arm GNU Toolchain 14.2 that the other lessons also use. You do not need to set them by hand for this course, but you should know where they come from, because a build that fails with GNUARMEMB_TOOLCHAIN_PATH is not set means the variable did not reach the build. The trade-off is simple. The SDK gives you a known set of compilers for every board. The gnuarmemb variant reuses the Arm toolchain that the Pico SDK and the STM32 lessons already need, so there is one compiler to maintain.

Building for a board

A Zephyr application is built for a board, and the board is named with -b. The Pico's board definition is in zephyr/boards/raspberrypi/rpi_pico/. Its main file, rpi_pico.dts, includes rpi_pico-common.dtsi, which describes the chip's common peripherals, and ../common/rpi_pico-led.dtsi, which describes the on-board LED. Lesson 94 looks at those files in detail. For now, the board name is the key: rpi_pico is the name that west and CMake look for. 

west build -p auto -b rpi_pico -d build /path/to/projects/0092-zephyr-setup/solution

The command runs from the workspace, and the last argument is the application folder. The option -p auto cleans the build folder when it is needed, so a change in the board or the configuration does not leave stale files behind. -d build sets the output folder, and the course's tools/build.py puts it at build/ inside the application, because wokwi.toml looks for it there. The result is build/zephyr/zephyr.elf, the program that Wokwi runs.

The course's build script does the same thing for you. It finds the application type from the files in the folder, chooses the board from the Wokwi diagram (a diagram with a wokwi-pi-pico part gives rpi_pico), and checks that the workspace's .venv contains west. If west is missing, it prints Zephyr workspace not found and tells you to set it up in this lesson.

The blink, line by line

The solution's src/main.c is short, and every line is a Zephyr idea that this course uses for the rest of the Zephyr lessons. Here are the important parts: 

static const struct gpio_dt_spec led = GPIO_DT_SPEC_GET(DT_ALIAS(led0), gpios);

This line creates a constant that describes the LED. DT_ALIAS(led0) looks up the devicetree node that the alias led0 names. The board defines that alias, and it points at the LED on GP25. GPIO_DT_SPEC_GET reads that node's gpios property and fills a struct with the GPIO controller, the pin number and the flags. The C code never writes GP25 or the port name. Lesson 94 explains how the alias is defined. The macro itself is in include/zephyr/drivers/gpio.h at line 376. 

if (!gpio_is_ready_dt(&led)) {
    printk("LED not ready\n");
    return 0;
}

gpio_is_ready_dt() asks whether the GPIO driver for this pin has started (gpio.h, line 982). Zephyr starts drivers during boot, and if a driver failed, this check tells you. The check is cheap, and the message is the only clue you get in a failed build, so the solution keeps it. The printk() call writes to the console, and the return 0 ends main() rather than entering the blink loop with an unready pin. 

if (gpio_pin_configure_dt(&led, GPIO_OUTPUT_ACTIVE) < 0) {
    printk("LED configure failed\n");
    return 0;
}

This line sets the pin as an output and drives it to its active level. gpio_pin_configure_dt() takes the struct from GPIO_DT_SPEC_GET, so the flags from the board, such as active-high, are already applied (gpio.h, line 1208). GPIO_OUTPUT_ACTIVE is the request "output, start high". A negative return value means the configuration failed. 

printk("ZEPHYR SETUP OK\n");

uint32_t toggles = 0U;
while (1) {
    gpio_pin_toggle_dt(&led);
    toggles++;
    printk("toggle %u at %lld ms\n", toggles, k_uptime_get());
    k_msleep(BLINK_PERIOD_MS);
}

The first line prints the marker that the simulator run looks for. The loop toggles the LED, which flips the pin from high to low or back (gpio.h, line 1924). The counter counts toggles, and k_uptime_get() returns the time since boot in milliseconds, as its header says. The format %lld is for that 64-bit value. Finally k_msleep() puts the thread to sleep for the period. While it sleeps, the scheduler can run other threads, which is why this loop is not a busy wait. The period constant is BLINK_PERIOD_MS, defined as 250 in the solution. That is half a cycle, so the full period, from high to high, is 500 ms, which is a 2 Hz blink.

Common mistakes and how to spot them

Mistake 1: the wrong board name. Typing -b pico instead of -b rpi_pico is easy to do, because the chip and the board are both called Pico in conversation. The symptom is a configure error that stops the build before any compiling: No board named 'pico' found. Did you mean:, followed by a short list, and the advice to run west boards. The fix is the name that the board folder uses, rpi_pico. We checked this with the workspace's west and its CMake files.

Mistake 2: running the build without the workspace. If the workspace is missing or the virtual environment was never created, the course's build script stops with Zephyr workspace not found at ... (set up in lesson 92). If you call west directly from another folder, the shell says it cannot find the program, because the venv's scripts folder is not on the PATH. The fix is to run the setup in this lesson, or to call west with the venv's full path, as the build script does.

Mistake 3: editing the period and not rebuilding. The simulator runs the file build/zephyr/zephyr.elf, not your C file. If you change BLINK_PERIOD_MS and start the simulator without building, the LED keeps its old speed, and the serial monitor shows the old interval. The symptom is that nothing changed, which looks like a bug in the simulator. The fix is to build first, with Ctrl+Shift+B, and then start the simulator.

Mistake 4: a misunderstood filter. If you add a board whose HAL is not in the filter, the build may fail to find a module, because west update never downloaded it. The symptom is a missing-module error during configure, and the check is west list, which shows the projects that are present. The fix is to add the project to the filter with the same west config command, and run west update again.

Mistake 5: using a command that does not exist. Notes from other sources sometimes use west manifest --active-path. The flag does not exist in west v1.5.0, so the command fails. The fix is west manifest --path, which prints the manifest file's path.

In real projects

A product team that uses Zephyr pins its manifest to exact commits, not to a branch. A branch moves, so an unpinned build can change without any change in the team's code, and a field failure can then be impossible to reproduce. The manifest is the single file that says which revision of each module the product uses, and reviewers read changes to it as carefully as changes to the code. The filter does the same job for the disk: the set of projects a build needs is written down, not left to chance.

Teams also keep one application that builds for several boards. The board is a command-line choice, and the hardware differences live in the board files, the overlays and the configuration, which lessons 93 and 94 cover. A continuous-integration job often builds the same application for each board in a list, so a change that breaks one board is found before it is merged. In an interview, a good answer to "what is the difference between a vendor SDK's build and Zephyr's" names the manifest, the board selection, and the separate toolchain choice.

Try it in Wokwi

Zephyr runs on the Pico in Wokwi like any other firmware. The first step is to see the blink work. In the starter, the period is a named constant set to 500 ms, and there are three TODO(learner) comments in src/main.c. The solution uses 250 ms and prints each toggle.

  1. Open projects/0092-zephyr-setup/starter in VS Code (File → Open Folder).
  2. Build with Ctrl+Shift+B. The task calls tools/build.py, which calls west build. The build should finish with no errors, and it creates build/zephyr/zephyr.elf.
  3. Start the simulator: F1 → Wokwi: Start Simulator.
  4. Make the three changes. Change BLINK_PERIOD_MS from 500 to 250, print the line ZEPHYR SETUP OK once before the loop, and add the toggle counter. The counter is incremented after gpio_pin_toggle_dt(), and the message is toggle N at X ms, where N is the counter and X is k_uptime_get().
  5. Build again and simulate. The serial monitor should first show ZEPHYR SETUP OK, then lines of the form toggle 1 at ... ms, one every 250 ms, and the LED should blink twice as fast as before.
Hint

The three TODO(learner) comments are one line each: the period constant, a printk() before the while loop, and a counter increment with a printk() inside the loop. The toggle counter is a uint32_t, and it is printed with %u. The solution's src/main.c is the reference, and you should read it after you have tried.

The reference solution is in projects/0092-zephyr-setup/solution. Try first, compare after.

Wokwi is a digital simulator, and the Zephyr template runs in it through the same ELF file that the build produces. The simulator token is not set in this workspace, so the course could confirm the build, the ELF and the diagram lint, but not a live simulation run. If the serial monitor shows nothing, check that the build finished and that build/zephyr/zephyr.elf exists, then start the simulator again.

Summary

  • Zephyr is a kernel plus drivers, a hardware description, a configuration system and a build tool. A Zephyr task is called a thread, and a smaller priority number is more urgent.
  • west reads the manifest in zephyr/west.yml, applies the project filter in .west/config, and fetches only the projects the filter keeps.
  • The filter is read left to right: -.* removes everything, then each + pattern keeps the matching projects. west list shows the result.
  • The gnuarmemb variant uses the Arm GNU toolchain already installed. It needs ZEPHYR_TOOLCHAIN_VARIANT and GNUARMEMB_TOOLCHAIN_PATH, which the course's build script sets.
  • west build -p auto -b rpi_pico -d build builds for the Pico. The board name must be exact, and the output is build/zephyr/zephyr.elf.
  • The C code finds the LED through an alias, with GPIO_DT_SPEC_GET(DT_ALIAS(led0), gpios), so no pin number is written in the code.

"What is the difference between an RTOS's build system and the vendor SDK's build system, and how does Zephyr's tooling fit?" Answer out loud in 60 seconds, then compare.

Model answer

Zephyr's build is CMake plus Kconfig plus devicetree, driven by west. A vendor SDK usually has one build system tied to one family of chips. Zephyr builds the same application for many boards by selecting the board's devicetree and defconfig, and the repositories and their revisions are pinned by the west manifest. The toolchain is chosen separately (gnuarmemb here, or the Zephyr SDK).

Zephyr documentation: West (meta-tool and workspace): read "West manifests" and the project filter section, then the "Getting started" pages for the toolchain variants. Compare the manifest with ~/zephyrproject/zephyr/west.yml, and the variable checks in zephyr/cmake/toolchain/gnuarmemb/generic.cmake.
