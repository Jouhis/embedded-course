GPIO input and debouncing

A mechanical button does not make one clean edge. It makes a burst of them over a few milliseconds. If your code counts every edge, one press becomes ten. Debouncing turns the burst back into one event.

By the end of this lesson you can enable the internal pull-up from C, explain why a raw button count is wrong, and count presses correctly with an integrator debounce that you wrote yourself.

Where we are and why it matters

In lesson 51 you drove pins as outputs. You wrote a level into the SIO output register, and the pad carried that level to an LED. This lesson goes the other way. A pin is an input when the chip reads the level on the pad, and a button, a limit switch, a rotary encoder or a door sensor all arrive that way. Almost every product has at least one of them, and the code that reads them is where many field bugs live: the printer that skips a step, the coffee machine that starts twice, the alarm that fires on its own.

Lesson 16 introduced the electrical reason an input needs a pull-up. Here you will see the software side of the same problem. A switch is a mechanical part, and mechanical parts do not change state cleanly. The pin reads what the switch does, bounce included, so the code has to decide which changes are real. That decision is debouncing.

The idea of an input register

A GPIO pin is an input when its output enable bit is 0, and the chip still reads the pad. The read path is a separate register. On the RP2040 the SIO block holds it at GPIO_IN, offset 0x004, and it holds one bit per pin (RP2040 datasheet §2.3.1.7, Table 16). The SDK function gpio_get() reads that register and tests the bit for the pin you name. It returns what the pad is at the moment of the read. It does not return the value your program last wrote, which is what GPIO_OUT holds. Reading the output register would report a level that the pin may not have, if an external part is pulling it the other way.

The SIO read takes one cycle, because it goes through the IOPORT and not the system bus. That is why a polling loop can sample a pin every few microseconds without a bus stall (§2.3.1). Each read is an ordinary load instruction on the Cortex-M0+. The SDK wraps it in a small inline function, so the compiler turns gpio_get(14) into a load from the SIO address, a shift to make a mask, and an AND.

Why an input needs a defined level

A pin that is not driven and not pulled has no defined level. The input buffer amplifies whatever small voltage or noise reaches it, so the reading can flip between 0 and 1 at random. This is a floating input. Your button code will then see presses that nobody made.

A pull-up resistor fixes this by connecting the pin to the supply through a high resistance. When the button is open, nothing else drives the pin, so the pull-up holds it at the supply level, which reads as 1. When the button closes, it connects the pin straight to ground. The pull-up is weak, so the button wins, and the pin reads 0. The RP2040 has a pull-up inside each pad. The datasheet gives its resistance as 50 to 80 kΩ (§2.19.4 and Table 625). You enable it with a bit in the pad control register, and you do not need an external part for a button.

The value of that resistance sets a current. With the button pressed and a 3.3 V supply, the current through the pull-up is 3.3 V ÷ 50 kΩ = 66 µA at most. That is small, so the internal pull-up is fine for a button. It is not fine for a long wire or a heavy load, where an external pull-up of a few kΩ is the right choice.

The pad is set up in the PADS_BANK0 block, and the pull-up enable is bit PUE (bit 3) of the GPIO0 pad register. The pull-down enable is PDE, and the two must not both be set unless you want a bus keeper (§2.19.4.1).

A button is a mechanical contact

A tactile switch is a small metal spring. When you press it, the spring pushes two contacts together. The contacts do not stop cleanly when they meet. The spring hits, separates a little, and hits again, several times, before it settles. From the chip's side, the pin changes level many times in a few milliseconds, although you pressed once.

A pressed contact behaves like a ball dropped on the floor. It hits, bounces up, hits again, and settles after a few smaller bounces. The input sees every hit as a new press. Debouncing means waiting until the ball has stopped bouncing before you say where it is.

The Wokwi pushbutton models this on purpose. Its bounce attribute is on by default, and setting it to "0" turns the effect off. The Wokwi documentation cites Horowitz and Hill's description of real contacts, which separate and reconnect many times over a period of about 1 ms (Wokwi pushbutton part, bounce attribute). The simulator does not publish its own bounce duration, so do not treat 1 ms as a fact about Wokwi. The figure from a real switch is the one that sets the window in your code, and you should check the switch's datasheet.

Active-low wiring

In this project the button connects GP14 to ground. The pull-up holds GP14 high while the button is open, and a press pulls it low. So the pin reads 1 when released and 0 when pressed. Engineers call this active low: the active state is the 0 level. The schematic shows it as a switch to ground, and the code has to invert the reading once, in one place. The starter does that with !gpio_get(BUTTON_PIN), so the rest of the program can use the word pressed with its usual meaning.

Mixing up the two levels is a common source of inverted logic. If your code checks gpio_get() == 1 to mean pressed, the program reports a press when the button is released, and it reports nothing when you press it. The symptom looks like a bug in the press logic, but the cause is the wiring convention.

The naive count, and why it is wrong

The first code most people write is an edge detector. It remembers the previous reading, and it counts when the current reading is pressed and the previous one was not. That is a correct edge detector for a clean signal. On a bouncing contact, each bounce is a real edge on the pin, so one click gives several counts.

The starter keeps this naive detector on purpose. It has two counters. raw_edges counts every edge, and presses is what the user should see. Watch the serial monitor and compare the two. Seeing the problem before you fix it makes the reason for debouncing clear.

Three ways to debounce

There are three common methods. Each one answers the same question: how long must a new level last before the code believes it?

Wait after the edge is the simplest. On an edge, the code calls sleep_ms(20) and reads the pin again. It works, but the call blocks the whole loop for 20 ms. During that time the program cannot sample other inputs or service other work. Lesson 55 explains why blocking calls break a super-loop, so this method suits a program that has nothing else to do.

An integrator keeps a small counter. The counter climbs while the raw pin reads pressed and falls while it reads released. It is clamped to a range, from 0 up to a fixed number of samples. The stable state changes only when the counter reaches one end of its range. A bounce lasts less than the window, so the counter moves up and down without reaching the top, and the stable state does not change. This is the method used in this lesson.

A timestamp records when the pin last changed. A new level is accepted only after it has been steady for a set time. It is the same idea, but it measures time on a clock instead of counting samples. It fits well with a timer tick, as lesson 73 shows, and it avoids a fixed sampling rate.

The integrator, line by line

Here is the function from the reference solution. It takes the raw pressed state, updates the counter, and returns true only once for each confirmed press. 

static bool debounce_press(bool raw_pressed) {
    static uint8_t integrator = 0;
    static bool stable_pressed = false;

    /* climb while pressed, fall while released, clamped to 0..DEBOUNCE_SAMPLES */
    if (raw_pressed) { if (integrator < DEBOUNCE_SAMPLES) integrator++; }
    else            { if (integrator > 0) integrator--; }

    if (!stable_pressed && integrator == DEBOUNCE_SAMPLES) {
        stable_pressed = true;      /* confirmed press: report it once, here */
        return true;
    }
    if (stable_pressed && integrator == 0) {
        stable_pressed = false;     /* confirmed release: re-arm */
    }
    return false;
}

Line by line, starting at the top. The two static variables keep their values between calls. Without static, integrator would be a fresh local on every call, and it would always start from 0. integrator is a uint8_t, which is plenty for a window of 10 samples. stable_pressed is the debounced state that the rest of the program is allowed to see.

The first if line moves the counter one step toward the raw reading. The counter goes up only while it is below DEBOUNCE_SAMPLES, and down only while it is above 0. Those two tests are the clamp. Without the clamp, a long hold would push the counter past the window, and a long release would drive it below 0 and wrap a uint8_t to 255. Either way the counter would take far too long to change direction.

The next block fires the press. A press is reported only when the counter has reached the top and the stable state was released. The !stable_pressed test is what makes the report happen once. While the button is held, the counter stays at the top, but the stable state is already true, so the function returns false on every call.

The last block re-arms the detector. When the counter has fallen back to 0, the stable state becomes released, and the next press can fire again. The function returns false in every other case.

The starter's main loop wraps this function. It reads the raw pin, counts raw edges for the comparison, and calls the debounce. Each step sleeps for SAMPLE_MS, which is 1 ms. The loop does not depend on the timing being exact, because the window is measured in samples.

Choosing the window

The window is the number of consecutive samples the input must agree before the change counts. At one sample per millisecond, 10 samples make a 10 ms window. The window has to be longer than the longest bounce you expect, or bounce will reach the top of the counter. It also has to be shorter than the fastest press you need to catch. A window of 500 ms would make a quick double-tap disappear, and a window of 1 ms would not stop the bounce.

The bounce length is a property of the switch, so look it up. Its datasheet gives contact bounce, or a manufacturer application note gives a typical value. Choose a window that is a few times longer than that. You can test the choice in the simulator too: change DEBOUNCE_SAMPLES, rebuild, and watch whether the press count stays at one per click. Make the window very short and the bounce starts to count again.

A plain edge detector on the raw pin is the most common bug in button code. It works on a bench with a good switch and fails on a cheap one. Always count presses after the debounce, and count raw edges only to show the bounce.

Test your window choice before you build it. The lab below runs the integrator from the reference solution on a bouncing button. Compare the naive count with the integrator's, then make the press shorter than the window, make the window a single sample, and add a noise spike.

The pull-up in code

The starter asks for three calls, and the order matters. gpio_init(BUTTON_PIN) routes the pin to the SIO function, which is function 5 for every GPIO (§2.19.2, Table 279), and it also makes the pin an input and drives it low in its output register. gpio_set_dir(BUTTON_PIN, GPIO_IN) then confirms the input direction, which clears the output-enable bit in GPIO_OE. gpio_pull_up(BUTTON_PIN) sets the pull-up enable bit in the pad register. In the Pico SDK, gpio_pull_up() is a call to gpio_set_pulls(gpio, true, false), so it turns on the pull-up and turns off the pull-down. Calling it before the pin is an input is harmless, but reading the code in the order it runs makes the intent clear.

Hint for the pull-up

An input needs three calls, in this order: gpio_init() for the SIO function, gpio_set_dir() with GPIO_IN, then gpio_pull_up(). Without the pull-up, the released pin floats, and the count is random.

Hint for the integrator

Keep integrator and stable_pressed as static variables inside the function, so they survive between calls. Return true only on the step where the integrator reaches the top while the stable state is still released. The release branch must reset the stable state when the integrator returns to 0.

Common mistakes and how to spot them

Mistake 1: no pull-up. If you skip the gpio_pull_up() step, the pin is not pulled to a defined level. Symptom: the serial monitor prints presses while you do nothing, or the count changes on a released button. Fix: enable the pull-up after gpio_set_dir(), then confirm that the released pin reads 1.

Mistake 2: inverted logic. Symptom: the program counts presses when the button is released and ignores the press. The pin reads 0 when the button is pressed and 1 when it is released, so a test for 1 means released. Fix: invert the read once, with !gpio_get(), and use the word pressed everywhere after that.

Mistake 3: the counter that is not static. Symptom: the debounced press count stays at 0, however often you click. A local integrator starts from 0 on every call, so it never climbs to the window's top. Fix: mark the integrator and the stable state static, so they keep their values between calls.

Mistake 4: no clamp. Symptom: after a long hold, the button needs many releases before it counts again. The counter kept climbing past the window. Fix: clamp the counter at both ends, as the if lines in the integrator do.

Mistake 5: a window that is too long. Symptom: fast double taps produce one press. The window is longer than the gap between the taps. Fix: measure the switch's bounce, then choose a window a few times longer than that, and no longer.

In real projects

Professional firmware rarely calls sleep_ms() to debounce. It reads all inputs in one periodic function, often driven by a timer interrupt, and stores the debounced state in a struct that the rest of the program reads. The read happens at a fixed rate, so the window is a count of ticks. Hardware designers add an RC filter or a Schmitt-trigger input when a switch is long wired or noisy. The software debounce still runs, because the filter reduces the bounce without removing it.

A code reviewer looks for three things in button code. Is the level defined by a pull-up or pull-down? Is the active level named and inverted in one place? Is the counted event produced after the debounce, once per press? A senior engineer may also ask where the debounce state lives, because a counter shared between an interrupt and the main loop needs the same care as any other shared variable (lesson 46).

Summary

  • gpio_get() reads the pad through the SIO GPIO_IN register at offset 0x004, and it returns the pin's present level, not the output register.
  • An input with no pull-up or pull-down floats. The RP2040 internal pull-up is 50 to 80 kΩ, enabled with gpio_pull_up().
  • A mechanical button bounces: one press makes several edges. Counting raw edges gives the wrong answer.
  • An integrator debounce climbs and falls between 0 and a fixed window, and changes state only at the ends of that range.
  • The window must be longer than the bounce and shorter than the fastest press you must catch.
  • Invert an active-low read once, in one place, and keep the counter and the stable state static.
