GPIO input and debouncing

A mechanical button does not make one clean edge. It makes a burst of them over a few milliseconds. If your code counts every edge, one press becomes ten. Debouncing turns the burst back into one event.

By the end of this lesson you can enable the internal pull-up from C, explain why a raw button count is wrong, and count presses correctly with an integrator debounce that you wrote yourself.

The idea

gpio_get() reads the pad level through the SIO input register GPIO_IN at 0x004 (RP2040 datasheet §2.3.1.7). It returns what the pin is at right now, not what your program last wrote. An input must always be at a defined level. A pull-up resistor gives it one when the button is open, so the RP2040's internal pull-up (50 to 80 kΩ) is the simplest choice (§2.19.4 and Table 625). Lesson 16 explains why a floating input is a bug. With the pull-up, the released button reads 1, and a press connects the pin to ground and reads 0. That is an active-low input. Its current is at most 3.3 V ÷ 50 kΩ = 66 µA, so pressing the button wins easily.

Why a button bounces

A tactile switch is a spring that closes a contact. When the contact meets, it does not stop cleanly. It hits, separates, and hits again for a short time. The Wokwi pushbutton models this on purpose, following Horowitz and Hill's description of contacts that separate and reconnect many times over about 1 ms. Its bounce attribute is on by default, and setting it to "0" turns the effect off (Wokwi pushbutton part).

Three ways to debounce

Wait after the edge is the simplest: on an edge, sleep_ms(20) and read again. It works, but it blocks the super-loop for 20 ms, and it is blind during the wait. That is why it does not fit a loop with other work (lesson 55 covers blocking).

An integrator keeps a small counter that climbs while the pin reads pressed and falls while it reads released. The counter is clamped to a range. The stable state changes only when the counter reaches an end of its range. A bounce is shorter than the window, so the counter never gets there. This is the method in this lesson, and the project uses it.

A timestamp records when the pin last changed, and accepts a new level only after it has been steady for a set time. It is the same idea on a clock, and lesson 55 uses time-based checks in the same loop. 

static bool debounce_press(bool raw_pressed) {
    static uint8_t integrator = 0;
    static bool stable_pressed = false;

    /* climb while pressed, fall while released, clamped to 0..DEBOUNCE_SAMPLES */
    if (raw_pressed) { if (integrator < DEBOUNCE_SAMPLES) integrator++; }
    else            { if (integrator > 0) integrator--; }

    if (!stable_pressed && integrator == DEBOUNCE_SAMPLES) {
        stable_pressed = true;      /* confirmed press: report it once, here */
        return true;
    }
    if (stable_pressed && integrator == 0) {
        stable_pressed = false;     /* confirmed release: re-arm */
    }
    return false;
}

The window is the choice you make. At one sample per millisecond, 10 samples is a 10 ms window. It must be longer than the bounce, and shorter than the fastest press you need to catch. Wokwi's bounce lasts about 1 ms, so 10 ms is generous in the simulator. A real switch's datasheet gives its own figure, and you should check it before you choose the window.

A plain edge detector on the raw pin is the most common bug in button code. It works on a bench with a good switch and fails on a cheap one. Always count presses after the debounce, and count raw edges only to show the bounce.

Try it in Wokwi

The project is projects/0052-gpio-input-debounce. One pushbutton sits between GP14 and GND, with bounce on. The starter counts raw edges and prints a line for each one. That is the wrong count, and you will see it.

  1. Open projects/0052-gpio-input-debounce/starter in VS Code (File → Open Folder).
  2. Build with Ctrl+Shift+B, then start the simulator with F1 → Wokwi: Start Simulator. Click the button once. The serial monitor prints several press lines for one click.
  3. Your task, in two places marked TODO(learner). First, configure GP14 as an input with the pull-up enabled, so the released button reads 1 and the starter's inverted read is correct. Second, replace the naive debounce_press() with the integrator above.
  4. You will know it works when the serial monitor prints DEBOUNCE OK at startup, and each click gives one press line. The raw-edge count may still climb, which is correct: it counts the bounce.
Hint for the pull-up

An input needs three calls, in this order: gpio_init() for the SIO function, gpio_set_dir() with GPIO_IN, then gpio_pull_up(). Without the pull-up, the released pin floats, and the count is random.

Hint for the integrator

Keep integrator and stable_pressed as static variables inside the function, so they survive between calls. Return true only on the step where the integrator reaches the top while the stable state is still released. The release branch must reset the stable state when the integrator returns to 0.

"A button counter sometimes counts two presses for one click. How do you find and fix it?" Answer out loud in 60 seconds, then compare.

Model answer

The usual cause is bounce, so I'd count raw edges first and see whether the count is much higher than the clicks. Then I'd check that the pin has a defined level, which means a pull-up or pull-down, and an intended input direction. The fix is to debounce in software: an integrator or a timestamp that accepts a level only after it is steady for a window longer than the bounce, then report the edge once. I'd test it with the bounce turned off and on in the simulator, and with a noisy real switch, because the two results should differ only in the raw count.
