GPIO input and debouncing

Reading pins and filtering contact bounce

By the end of this lesson you can enable the internal pull-up from C, explain why a raw button count is wrong, and count presses correctly with an integrator debounce that you wrote yourself.

Pins as inputs

In lesson 51 you drove pins as outputs, writing a level into the SIO output register for the pad to carry to an LED. This lesson goes the other way, a pin being an input when the chip reads the level on its pad, which is how a button, a limit switch, a rotary encoder or a door sensor arrives. Almost every product has at least one such input, and the code that reads them is where many field bugs live, such as the printer that skips a step, the coffee machine that starts twice or the alarm that fires on its own.

Lesson 16 gave the electrical reason an input needs a pull-up, and this lesson covers the software side of the same problem. A switch is a mechanical part whose state does not change cleanly, and since the pin reads whatever the switch does, bounce included, the code must decide which changes are real, a decision known as debouncing.

The GPIO_IN register

A GPIO pin is an input when its output enable bit is 0, and the chip still reads its pad through a separate register, which on the RP2040 is GPIO_IN at offset 0x004 in the SIO block, with one bit per pin (RP2040 datasheet §2.3.1.7, Table 16). The SDK function gpio_get() reads that register and tests the named pin's bit, returning the pad's level at the moment of the read rather than the value the program last wrote, which GPIO_OUT holds. Reading the output register instead would report a level the pin may not have if an external part pulls it the other way.

Each read is an ordinary load instruction on the Cortex-M0+, wrapped by the SDK in a small inline function, so the compiler turns gpio_get(14) into a load from the SIO address, a shift to form a mask and an AND. The SIO read takes one cycle, because it goes through the IOPORT rather than the system bus, which is why a polling loop can sample a pin every few microseconds without a bus stall (§2.3.1).

Floating inputs and pull-up resistors

A pin that is neither driven nor pulled has no defined level. The input buffer amplifies whatever small voltage or noise reaches it, so the reading can flip between 0 and 1 at random, and button code reading such a floating input sees presses that nobody made.

A pull-up resistor fixes this by connecting the pin to the supply through a high resistance. With the button open nothing else drives the pin, so the pull-up holds it at the supply level, which reads as 1, and when the button closes it connects the pin straight to ground and, because the pull-up is weak, the button wins and the pin reads 0. The RP2040 has a pull-up inside each pad, which the datasheet gives as 50 to 80 kΩ (§2.19.4 and Table 625), enabled by a bit in the pad control register, so a button needs no external part.

The resistance sets the current that flows while the button is pressed,

I = VDD ÷ Rpull-up(1)

where VDD is the 3.3 V supply and Rpull-up the pull-up resistance, giving at most 3.3 V ÷ 50 kΩ = 66 µA. That small current makes the internal pull-up fine for a button but not for a long wire or a heavy load, where an external pull-up of a few kΩ is the right choice. The pad is configured in the PADS_BANK0 block, where the pull-up enable is bit PUE (bit 3) of the GPIO0 pad register and the pull-down enable is PDE, and the two should not both be set unless a bus keeper is wanted (§2.19.4.1).

Contact bounce in mechanical switches

A tactile switch is a small metal spring that pushes two contacts together when pressed, and the contacts do not stop cleanly when they meet: the spring hits, separates a little and hits again several times before it settles. From the chip's side, the pin therefore changes level many times within a few milliseconds of a single press.

A pressed contact behaves like a ball dropped on the floor, which hits, bounces up, hits again and settles after a few smaller bounces, while the input sees every hit as a new press, so debouncing means waiting until the ball has stopped before saying where it is. The comparison simplifies the timing, though, because a real contact's bounces are irregular rather than steadily shrinking, so the code cannot predict when the last one comes.

The Wokwi pushbutton models this deliberately with its bounce attribute, which is on by default and turned off by setting it to "0". Its documentation cites Horowitz and Hill's description of real contacts separating and reconnecting many times over a period of about 1 ms (Wokwi pushbutton part, bounce attribute), but the simulator does not publish its own bounce duration, so 1 ms is not a fact about Wokwi. The figure for a real switch, from its datasheet, is the one that sets the window in your code.

Active-low button wiring

In this project the button connects GP14 to ground, so the pull-up holds GP14 high while the button is open and a press pulls it low, the pin reading 1 when released and 0 when pressed. Engineers call this active low, the active state being the 0 level, which the schematic shows as a switch to ground, and the code must invert the reading once, in one place. The starter does so with !gpio_get(BUTTON_PIN), letting the rest of the program use the word pressed with its usual meaning.

Mixing up the two levels is a common source of inverted logic. If the code tests gpio_get() == 1 to mean pressed, the program reports a press when the button is released and nothing when it is pressed, a symptom that looks like a bug in the press logic although its cause is the wiring convention.

Raw edge counting

The first code most people write is an edge detector that remembers the previous reading and counts when the current reading is pressed and the previous one was not. That is correct for a clean signal, but on a bouncing contact every bounce is a real edge on the pin, so one click gives several counts.

The starter keeps this naive detector deliberately, with two counters, raw_edges counting every edge and presses holding what the user should see. Comparing the two on the serial monitor shows the problem before it is fixed, which makes the reason for debouncing clear.

Debouncing methods

Three methods are common, and each answers the same question of how long a new level must last before the code believes it.

Waiting after the edge is the simplest: on an edge the code calls sleep_ms(20) and reads the pin again. It works, but the call blocks the whole loop for 20 ms, during which the program can neither sample other inputs nor do other work, and since lesson 55 explains why blocking calls break a super-loop, the method suits only a program with nothing else to do.

An integrator keeps a small counter that climbs while the raw pin reads pressed and falls while it reads released, clamped to the range from 0 to a fixed number of samples, and the stable state changes only when the counter reaches one end of its range. A bounce lasts less than the window, so the counter moves up and down without reaching the top and the stable state does not change, and this is the method used in this lesson.

A timestamp method records when the pin last changed and accepts a new level only after it has been steady for a set time. The idea is the same, measured on a clock instead of in samples, which fits well with a timer tick, as lesson 73 shows, and avoids the need for a fixed sampling rate.

The integrator debounce line by line

The function from the reference solution takes the raw pressed state, updates the counter and returns true exactly once for each confirmed press. 

static bool debounce_press(bool raw_pressed) {
    static uint8_t integrator = 0;
    static bool stable_pressed = false;

    /* climb while pressed, fall while released, clamped to 0..DEBOUNCE_SAMPLES */
    if (raw_pressed) { if (integrator < DEBOUNCE_SAMPLES) integrator++; }
    else            { if (integrator > 0) integrator--; }

    if (!stable_pressed && integrator == DEBOUNCE_SAMPLES) {
        stable_pressed = true;      /* confirmed press: report it once, here */
        return true;
    }
    if (stable_pressed && integrator == 0) {
        stable_pressed = false;     /* confirmed release: re-arm */
    }
    return false;
}

The two static variables keep their values between calls, whereas without static, integrator would be a fresh local starting from 0 on every call. A uint8_t is plenty for a window of 10 samples, and stable_pressed is the debounced state that the rest of the program is allowed to see.

The first if line moves the counter one step towards the raw reading, upwards only while it is below DEBOUNCE_SAMPLES and downwards only while it is above 0, and those two tests form the clamp. Without it a long hold would push the counter past the window, and a long release would drive it below 0 and wrap the uint8_t to 255, either way making the counter take far too long to change direction.

The next block reports the press, which happens only when the counter has reached the top while the stable state was released. The !stable_pressed test makes the report happen once, because while the button is held the counter stays at the top but the stable state is already true, so the function returns false on every later call.

The last block re-arms the detector: once the counter has fallen back to 0, the stable state becomes released and the next press can fire again, and in every other case the function returns false.

The starter's main loop wraps this function, reading the raw pin, counting raw edges for the comparison and calling the debounce, with a sleep of SAMPLE_MS, 1 ms, per step. The loop does not depend on exact timing, because the window is measured in samples.

Choosing the debounce window

The window is the number of consecutive samples that must agree before a change counts, so at one sample per millisecond, 10 samples make a 10 ms window. The window must be longer than the longest expected bounce, or the bounce will reach the top of the counter, and shorter than the fastest press the product must catch, so 500 ms would swallow a quick double tap while 1 ms would not stop the bounce.

The bounce length is a property of the switch, given as contact bounce in its datasheet or as a typical value in a manufacturer's application note, and the window should be a few times longer than that. The choice can also be tested in the simulator by changing DEBOUNCE_SAMPLES, rebuilding and checking that the count stays at one per click, and with a very short window the bounce starts to count again.

A plain edge detector on the raw pin is the most common bug in button code, because it works on the bench with a good switch and fails with a cheap one. Always count presses after the debounce, and count raw edges only to show the bounce.

The lab below runs the integrator from the reference solution on a bouncing button, so you can test a window choice before building it. Compare the naive count with the integrator's, then make the press shorter than the window, reduce the window to a single sample and add a noise spike.

Configuring the pull-up in code

The starter needs three calls, in order. gpio_init(BUTTON_PIN) routes the pin to the SIO function, function 5 for every GPIO (§2.19.2, Table 279), and also makes it an input with its output register driven low, gpio_set_dir(BUTTON_PIN, GPIO_IN) confirms the input direction by clearing the output-enable bit in GPIO_OE, and gpio_pull_up(BUTTON_PIN) sets the pull-up enable bit in the pad register. In the Pico SDK gpio_pull_up() calls gpio_set_pulls(gpio, true, false), turning the pull-up on and the pull-down off, and although calling it before the pin is an input is harmless, writing the calls in the order they take effect makes the intent clear.

Hint for the pull-up

An input needs three calls in this order: gpio_init() for the SIO function, gpio_set_dir() with GPIO_IN and then gpio_pull_up(). Without the pull-up the released pin floats and the count is random.

Hint for the integrator

Keep integrator and stable_pressed as static variables inside the function so that they survive between calls, and return true only on the step where the integrator reaches the top while the stable state is still released. The release branch must reset the stable state when the integrator returns to 0.

Common mistakes and how to spot them

No pull-up

The serial monitor prints presses while nobody touches the button, or the count changes on a released button, because without gpio_pull_up() the pin has no defined level. Enable the pull-up after gpio_set_dir() and confirm that the released pin reads 1.

Inverted logic

The program counts presses when the button is released and ignores the press itself, because the pin reads 0 when pressed and 1 when released, so a test for 1 means released. Invert the read once with !gpio_get() and use the word pressed everywhere after that.

An integrator that is not static

The debounced press count stays at 0 however often the button is clicked, because a local integrator starts from 0 on every call and never climbs to the top of the window. Mark the integrator and the stable state static, so that they keep their values between calls.

No clamp on the counter

After a long hold the button needs a long release before it counts again, because the counter kept climbing past the window. Clamp the counter at both ends, as the if lines in the integrator do.

A window that is too long

A fast double tap produces only one press, because the window is longer than the gap between the taps. Measure the switch's bounce and choose a window a few times longer, but no longer than that.

Input handling in production firmware

Professional firmware rarely debounces with sleep_ms(). It reads all inputs in one periodic function, often driven by a timer interrupt, and stores the debounced states in a struct that the rest of the program reads, so with a fixed read rate the window becomes a count of ticks. Hardware designers add an RC filter or a Schmitt-trigger input for long or noisy switch wiring, and the software debounce still runs, because a filter reduces the bounce without removing it.

A code reviewer checks that the level is defined by a pull-up or pull-down, that the active level is named and inverted in one place, and that the counted event comes after the debounce, once per press. A senior engineer may also ask where the debounce state lives, because a counter shared between an interrupt and the main loop needs the same care as any other shared variable (lesson 46).

Summary

  • gpio_get() reads the pad through the SIO GPIO_IN register at offset 0x004, returning the pin's present level rather than the output register's value.
  • An input without a pull-up or pull-down floats, and the RP2040's internal pull-up of 50 to 80 kΩ is enabled with gpio_pull_up().
  • A mechanical button bounces, one press making several edges, so counting raw edges gives the wrong answer.
  • An integrator debounce climbs and falls between 0 and a fixed window and changes state only at the ends of that range.
  • The window must be longer than the bounce and shorter than the fastest press the product must catch.
  • An active-low read is inverted once, in one place, and the counter and stable state are kept static.
