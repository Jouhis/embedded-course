Function pointers and callbacks

A callback lets a driver call your code without knowing your code. The same mechanism puts the reset handler and every interrupt handler into the vector table.

By the end of this lesson you can declare a function pointer type, register a callback in a table, dispatch an event safely with a NULL check, and explain the vector table as an array of function pointers.

Where we are and why it matters

Lesson 46 showed how a flag shared with an interrupt must be volatile, and lesson 47 used pointers to reach registers. This lesson uses pointers for a different purpose: storing the address of a function, so that one piece of code can call another piece it does not know about. Lesson 42 introduced the startup file, which contains a table of addresses that the core reads on reset.

The problem comes up in almost every firmware project. A UART driver receives a byte and must tell the application. A timer fires every 100 ms and must run a task. A button changes state and must wake a menu. The driver is written once, and the application changes. If the driver calls the application by name, every new application needs a change to the driver. A callback reverses the dependency: the application registers a function, and the driver calls it when the event happens. The project in lesson 46 already uses this design: it passes a callback to the SDK's repeating-timer call, which then calls it every 100 ms.

Concepts, one at a time

A function has an address

A function's code lives in memory, and the function has an address, just as a variable does. Calling a function is a branch to that address. A direct call names the function, and the compiler writes the branch with the address built in. An indirect call reads the address from a variable at run time and branches to it. On a Cortex-M the core loads the address into a register and branches through that register. The mechanism is one load and one branch, which is cheap.

A function pointer is a variable that holds such an address. Its declaration says what kind of function it points to. The declaration void (*handler)(int) reads from the inside out: handler is a pointer, and it points to a function that takes an int and returns void. The parentheses around *handler are required. Without them, void *handler(int) declares a function that returns a pointer.

A typedef gives the type a name, so the rest of the code can use it without repeating the pattern: 

typedef void (*Handler)(Event ev);     /* a type: pointer to a function taking Event, returning void */

static Handler handlers[EV_COUNT];       /* one slot per event; zero-initialised, so each slot is NULL */

void register_handler(Event ev, Handler h) {
    handlers[ev] = h;                       /* store the address; the function does not run yet */
}

void dispatch(Event ev) {
    handlers[ev](ev);                       /* call whatever address is stored for this event */
}

A callback is a function someone else calls

A callback is a function that you give to other code, which calls it later when an event occurs. The code that owns the event decides when to call. Your function decides what to do. In this lesson the event is a tick or a button press, and the owner is dispatch. The driver does not need to know what the handler does, and the application does not need to poll the driver for news.

The table is what makes it scale. Each event has one slot, and the slot holds a function pointer. Looking up the handler for event n is an index into an array of pointers, so adding an event means adding one enum entry and one slot. Nothing in dispatch has to change.

NULL: the address that is not a function

A null pointer is a pointer value that means "points to nothing". In C it is written NULL, and a static array of pointers is set to null automatically. C requires that objects with static storage duration are zero-initialised, so static Handler handlers[EV_COUNT]; starts with every slot null. Nobody has to write the zeros, and nobody can forget them.

A null function pointer is still a number, and that number is 0. Calling it branches to address 0. On the RP2040 that address is the start of the boot ROM, a region the chip uses at power-up and which is read-only. The code that runs there is not your code, so the call does something unpredictable. The only safe rule is to check the slot before the call.

A callback runs later than its registration, often from an interrupt. Do not pass a pointer to a local variable as the user data of a callback. The stack frame it points into is gone by the time the callback runs.

The vector table is a table of function pointers

When an interrupt or exception happens, the core does not search for a handler. It reads an array in memory, the vector table, at an index given by the exception number. The first word is the initial stack pointer. The second word is the address of the reset handler, and the next words are the addresses of NMI, HardFault and the peripheral interrupts. Each entry after the first is a function pointer in all but name.

The course's STM32 startup file shows the table directly. Its first entry is _estack, the top of the stack, which the linker defines. The second entry is Reset_Handler, and the next entries are NMI_Handler, HardFault_Handler and so on. Each handler name is declared as a weak alias of Default_Handler, which is a loop that never exits. A weak symbol is a default definition that another object file can replace with a strong one. If your code defines USART1_IRQHandler, the linker uses yours. If it does not, the table entry points at the default loop, and the device stops there. PM0056, STM32F10xxx Cortex-M3 programming manual Lesson 42 builds the startup file and the vector table in detail. The table is data in flash, placed at a fixed location that the core reads on reset and on each exception.

The vector table and your dispatcher are the same design. Your code registers an address in a table, and something later reads it and jumps there. The difference is that the hardware reads the vector table and has no NULL check. A missing entry therefore has to be filled with a safe default by the startup code, and the default in this file is the infinite loop. The loop is safe in one sense: it does nothing harmful. It is also silent, so a missing handler shows up as a device that stops, which is why the debugger is the first tool to reach for.

Worked example: a two-event dispatcher, step by step

Take a dispatcher with two events. The enum gives EV_TICK the value 0, EV_BUTTON the value 1, and EV_COUNT the value 2. The table therefore has two slots. On the RP2040 a pointer is 4 bytes, so the table is 8 bytes. The address of handlers[ev] is the base address of the table plus ev times 4, which the compiler computes from the element size.

Step 1: the application registers a handler. register_handler(EV_TICK, on_tick) stores the address of on_tick in slot 0. Suppose the linker placed on_tick at 0x10000A40. After the call, handlers[0] holds 0x10000A40, and handlers[1] still holds 0. Nothing has run yet, because a store does not call anything.

Step 2: an event arrives, and the code calls dispatch(EV_TICK). The index is 0. The dispatcher loads handlers[0], which is 0x10000A40, and branches to it. on_tick prints tick and returns. Control comes back to dispatch, and then to the caller.

Step 3: a button event arrives, and the code calls dispatch(EV_BUTTON). The index is 1. The dispatcher loads handlers[1], which is 0. The call branches to address 0. The program has left its own code, and nothing good can follow. This is the bug the starter contains.

Step 4: the fixed dispatcher checks the slot first. For dispatch(EV_BUTTON) the check finds 0, so the function increments the ignored count and returns, and the call never happens. The second dispatch(EV_TICK) finds the address again and calls on_tick. Counting the calls gives handled = 2 (both tick events) and ignored = 1 (the button). The summary line is DISPATCH OK handled=2 ignored=1.

The code, explained line by line

The solution in projects/0049-callback-dispatcher/solution is the program with the fix. Its key parts are below. 

typedef enum {
    EV_TICK,
    EV_BUTTON,
    EV_COUNT          /* number of events: keep last */
} Event;

typedef void (*Handler)(Event ev);

static Handler handlers[EV_COUNT];   /* zero-initialised: every entry starts as NULL */
static unsigned handled_count;
static unsigned ignored_count;

The enum gives each event a number, and EV_COUNT is the number of events. Because EV_COUNT comes last, it always equals the number of events, so the table is sized by the enum and cannot fall out of step with it. The typedef names the handler type once. The table is static, so it is visible only in this file, and as a static object it is zero-initialised by the C runtime, which makes every slot NULL. The two counters are static for the same reason, and they are zero at the start. 

static void register_handler(Event ev, Handler h) {
    if ((unsigned)ev < EV_COUNT) {   /* reject an out-of-range event before indexing */
        handlers[ev] = h;
    }
}

Registration stores the address and does nothing else. The range check guards the array. An event value of 5 would index past the end of a two-slot array, and the store would overwrite whatever memory follows. The cast to unsigned makes a negative value large, so one comparison catches both negative and too-large values. 

static void dispatch(Event ev) {
    if ((unsigned)ev >= EV_COUNT) {
        ignored_count++;
        return;
    }
    /* A NULL entry means nobody registered a handler. Calling it would jump to address 0,
     * so check first and count the event as ignored. */
    if (handlers[ev] == NULL) {
        ignored_count++;
        return;
    }
    handlers[ev](ev);
    handled_count++;
}

The first test rejects an event number outside the table, for the same reason as in registration. The second test is the important one. It compares the loaded pointer with NULL before the call, so the branch to address 0 cannot happen. The call handlers[ev](ev) loads the pointer, passes ev as the argument, and branches. The increment after the call counts an event only when its handler has returned.

The callback itself is an ordinary function with the matching signature: 

static void on_tick(Event ev) {
    (void)ev;             /* unused here: the event is always EV_TICK */
    printf("tick\n");
}

The signature void (Event) must match the typedef exactly. A mismatched function pointer is a constraint violation that a compiler may accept with only a warning, depending on the flags and the types involved. The mismatched call then passes the wrong argument, or none, and the bug shows up far from the registration. Compile with warnings enabled, and treat a pointer-type warning as an error. The line (void)ev; tells the compiler that the parameter is unused on purpose.

Common mistakes and how to spot them

  1. Calling a slot that nobody filled. The dispatcher calls handlers[ev] without the NULL check. The symptom is that the output stops after an event that has no handler, here after the first tick. On a device the symptom can be a reset or a hang, depending on what the chip holds at address 0. The fix is the check from the solution, with a counter so that unhandled events are visible.
  2. A handler with the wrong signature. A function declared void on_tick(void) is registered in a table of void (*)(Event). The symptom is a garbage value in the argument, or a crash, that changes from build to build. The fix is to use the typedef for every handler and to compile with -Wall, so a pointer-type mismatch is reported.
  3. Passing a pointer to a local as user data. A function sets up a callback with a pointer to a variable on its own stack, and returns. The callback runs later and reads memory that now holds other values. The symptom is a rare wrong value in the callback, often only when the system is busy. The fix is to use a static or global object for context, which lives as long as the callback.
  4. Doing slow work in an interrupt callback. A handler that runs from an ISR calls a blocking function, such as a long print or a delay. While it runs, other interrupts wait, and events are missed. The symptom is missing events and a device that responds late, but only under load. The fix is to set a flag in the callback, and do the work in main, as lesson 46 showed.
  5. An unhandled interrupt that hangs. The application enables a peripheral interrupt and never defines its handler. The vector entry points at Default_Handler, and the device stops inside its loop. The symptom is that the program freezes after the interrupt is enabled. The debugger shows the program counter inside Default_Handler. The fix is to define the handler with the exact name from the startup file.

In real projects

The Pico SDK uses callbacks throughout. The repeating-timer call takes a callback and a user-data pointer: its type repeating_timer_callback_t is a typedef for a pointer to a function that takes a repeating_timer_t * and returns bool. The return value tells the timer whether to keep firing. The interrupt API uses the same pattern. irq_set_exclusive_handler takes a handler pointer and installs it in the core's table, which is the vector-table idea applied at run time.

The STM32 HAL uses weak callbacks. Functions such as HAL_UART_RxCpltCallback are defined as __weak in the driver, with an empty body. The application defines a function with the same name, and the linker uses the application's version. This is the same weak-symbol mechanism that the startup file uses for interrupt handlers, and a reviewer expects it. A driver that calls a function by name with no override is a driver the team cannot customise.

Code review on callbacks checks four things. Every table is checked for NULL before a call. Every handler matches the typedef. Every callback that runs in an interrupt keeps its work short, and does not use blocking calls. And every context pointer outlives the registration. Reviewers also ask where the table lives, because a table in RAM can be corrupted, and one in flash cannot.

The interview question about the vector table is one of the most common in embedded hiring. The good answer describes the table as an array of addresses at a fixed location, explains that word 0 is the stack pointer, and says what happens when the table has no entry for an exception. The model answer at the end of this lesson does that in order.

Summary

  • A function pointer stores a function's address. Its declaration reads from the inside out, and a typedef gives the type a name.
  • A callback is a function you register with other code, which calls it when an event happens. A table of function pointers holds one callback per event.
  • Calling a NULL slot branches to address 0, which is not your code. Check every slot before the call, and count the events that have no handler.
  • Static objects are zero-initialised, so a file-scope handler table starts with every slot NULL.
  • The vector table is an array of addresses that the core reads on reset and on each exception. Word 0 is the initial stack pointer, and word 1 is the reset handler.
  • A missing vector entry points at Default_Handler, an infinite loop, through a weak alias. Define the handler with the exact name from the startup file.
  • Callbacks that run in an interrupt must keep their work short, and must not hold pointers to the stack.

"What is a vector table, and how does the CPU use it when an interrupt fires?" Answer out loud in 60 seconds, then compare.

Model answer

It is an array at a fixed address, with one word per exception. Word 0 is the initial stack pointer and the rest are handler addresses. When an exception is taken, the core reads the entry for that exception number and jumps to it, after saving registers on the stack. The table is data, so it can be relocated, and it is set up by the startup code. Unused entries must point at a safe default handler, because the hardware does not check for NULL.
