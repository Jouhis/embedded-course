Function pointers and callbacks

A callback lets a driver call your code without knowing your code. The same mechanism puts the reset handler and every interrupt handler into the vector table.

By the end of this lesson you can declare a function pointer type, register a callback in a table, dispatch an event safely with a NULL check, and explain the vector table as an array of function pointers.

The idea

A function has an address, and a function pointer stores that address. The declaration reads from the inside out: void (*handler)(int) is a pointer named handler to a function that takes an int and returns nothing. A typedef makes the type readable. Calling through a pointer is an indirect branch. The CPU loads an address from memory and jumps there. That is one more load than a direct call, and it is the reason a table of handlers is cheap. 

typedef void (*Handler)(Event ev);     /* a type: pointer to a function taking Event, returning void */

static Handler handlers[EV_COUNT];       /* one slot per event; zero-initialised, so each slot is NULL */

void register_handler(Event ev, Handler h) {
    handlers[ev] = h;                       /* store the address; the function does not run yet */
}

void dispatch(Event ev) {
    handlers[ev](ev);                       /* call whatever address is stored for this event */
}

This is a callback: the code that owns the event calls a function that someone else registered. The driver does not need to know what the handler does. The application does not need to poll the driver. Each event has a slot, so adding an event is one more entry, not one more if.

The NULL check

A slot that nobody registered holds NULL. Calling NULL does not do nothing: it jumps to address 0, which is not your code, and the result is a crash or worse. Check the slot before calling it. If the event has no handler, count it or ignore it, and say so in the design.

A callback runs later than its registration, often from an interrupt. Do not pass a pointer to a local variable as the user data of a callback. The stack frame it points into is gone by the time the callback runs.

The vector table is a table of function pointers

When an interrupt or exception happens, the core does not search for a handler. It reads an array in memory, the vector table, at an index given by the exception number. The first word is the initial stack pointer. The next words are the addresses of the reset handler, NMI, HardFault and the peripheral interrupts. Each entry is a function pointer in all but name. PM0056, STM32F10xxx Cortex-M3 programming manual Lesson 42 builds the startup file and the vector table itself. The table in the startup code is an array of addresses, placed at a fixed location the core reads on reset and on each exception.

That is why the dispatcher in this lesson and the vector table are the same design. Your code registers an address in a table, and something later reads it and jumps there. The difference is that the vector table is read by the hardware, which has no NULL check, so a missing entry must be filled with a safe default handler by the startup code.

You built a callback table, dispatched events through it, and guarded the one call that can jump to address 0. The same table idea is the vector table the core uses for every interrupt.

"What is a vector table, and how does the CPU use it when an interrupt fires?" Answer out loud in 60 seconds, then compare.

Model answer

It is an array at a fixed address, with one word per exception. Word 0 is the initial stack pointer and the rest are handler addresses. When an exception is taken, the core reads the entry for that exception number and jumps to it, after saving registers on the stack. The table is data, so it can be relocated, and it is set up by the startup code. Unused entries must point at a safe default handler, because the hardware does not check for NULL.
