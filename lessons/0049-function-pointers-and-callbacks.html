Function pointers and callbacks

Calling code through a stored function address

By the end of this lesson you can declare a function pointer type, register a callback in a table, dispatch an event safely with a NULL check, and explain the vector table as an array of function pointers.

Calling code that the caller does not know

Lesson 46 showed that a flag shared with an interrupt must be volatile, and lesson 47 used pointers to reach registers. This lesson uses pointers for another purpose, storing the address of a function so that one piece of code can call another it does not know about, the same idea behind the table of addresses that the core reads on reset in the startup file of lesson 42.

The need arises in most firmware projects. A UART driver receives a byte and must tell the application, a timer fires every 100 ms and must run a task, and a button changes state and must wake a menu. The driver is written once while the application changes, so if the driver called the application by name, every new application would need a driver change. A callback reverses the dependency, the application registering a function that the driver calls when the event happens, and the project in lesson 46 already works this way, passing a callback to the SDK's repeating-timer call, which then runs it every 100 ms.

Function addresses and indirect calls

A function's code lives in memory, so the function has an address just as a variable does, and calling it is a branch to that address. A direct call names the function and the compiler writes the branch with the address built in, whereas an indirect call reads the address from a variable at run time and branches to it. On a Cortex-M the core loads the address into a register and branches through that register, one load and one branch, which is cheap.

A function pointer is a variable holding such an address, and its declaration states what kind of function it points to. The declaration void (*handler)(int) reads from the inside out: handler is a pointer to a function that takes an int and returns void. The parentheses around *handler are required, because without them void *handler(int) declares a function returning a pointer.

A typedef names the type, so that the rest of the code can use it without repeating the pattern. 

typedef void (*Handler)(Event ev);     /* a type: pointer to a function taking Event, returning void */

static Handler handlers[EV_COUNT];       /* one slot per event; zero-initialised, so each slot is NULL */

void register_handler(Event ev, Handler h) {
    handlers[ev] = h;                       /* store the address; the function does not run yet */
}

void dispatch(Event ev) {
    handlers[ev](ev);                       /* call whatever address is stored for this event */
}

Callbacks and dispatch tables

A callback is a function given to other code, which calls it later when an event occurs, so the code that owns the event decides when to call and your function decides what to do. In this lesson the event is a tick or a button press and the owner is dispatch, so the driver needs no knowledge of what the handler does, and the application need not poll the driver for news.

A callback resembles leaving your phone number at a shop with a request to call when the part arrives, instead of standing at the counter asking every minute, which would be polling. The shop keeps the number, the function pointer, and calls it when the event happens, while leaving no number corresponds to the NULL pointer, which the shop must notice before dialling. The comparison fails at that point, though, because the CPU has no notion of a missing number and simply branches to address 0 unless the code checks first.

The table scales well, each event having one slot holding a function pointer. Finding the handler for event n is an index into an array of pointers, so adding an event means adding one enum entry and one slot, with no change to dispatch.

Null function pointers

A null pointer is a pointer value meaning that it points to nothing, written NULL in C. Because C requires objects with static storage duration to be zero-initialised, static Handler handlers[EV_COUNT]; starts with every slot null, without anyone writing the zeros or being able to forget them.

A null function pointer is still a number, and that number is 0, so calling it branches to address 0, which on the RP2040 is the start of the read-only boot ROM that the chip uses at power-up. The code there is not yours, and because a branch through a register to an address with bit 0 clear also clears the core's Thumb state, a Cortex-M takes a fault on the next instruction. The only safe rule is to check the slot before the call.

A callback runs later than its registration, often from an interrupt, so never pass a pointer to a local variable as a callback's user data, because the stack frame it points into is gone by the time the callback runs.

The vector table as a function pointer table

When an interrupt or exception happens, the core does not search for a handler but reads an array in memory, the vector table, at an index given by the exception number. The first word is the initial stack pointer, the second the address of the reset handler, and the following words the addresses of NMI, HardFault and the peripheral interrupts (PM0056 Rev 7, section 2.3.4 and Table 16), so every entry after the first is a function pointer in all but name.

The course's STM32 startup file shows the table directly. Its first entry is _estack, the top of the stack defined by the linker, its second Reset_Handler, and the next ones NMI_Handler, HardFault_Handler and so on, in the order of PM0056 Table 16, with NMI at offset 0x08 and Hard fault at 0x0C. Each handler name is declared as a weak alias of Default_Handler, a loop that never exits, a weak symbol being a default definition that a strong one in another object file can replace, so if your code defines USART1_IRQHandler the linker uses it, and otherwise the entry points at the default loop and the device stops there. PM0056, STM32F10xxx Cortex-M3 programming manual Lesson 42 covers the startup file and the vector table in detail. The table is data in flash at a fixed location that the core reads on reset and on every exception.

The vector table and the dispatcher share one design, in which code registers an address in a table and something later reads it and jumps there. The difference is that the hardware reads the vector table without any NULL check, so the startup code must fill every missing entry with a safe default, here the infinite loop. The loop does nothing harmful but is also silent, so a missing handler appears as a device that simply stops, which makes the debugger the first tool to reach for.

Worked example: a two-event dispatcher

We take a dispatcher with two events, whose enum gives EV_TICK the value 0, EV_BUTTON the value 1 and EV_COUNT the value 2, so the table has two slots. With 4-byte pointers on the RP2040 the table is 8 bytes, and the address of slot ev is

&handlers[ev] = base + 4 × ev(1)

where base is the table's start address and 4 the element size, which the compiler takes from the pointer type. Before following the steps, predict what the second dispatch does in a dispatcher without a check.

  1. Register a handler. register_handler(EV_TICK, on_tick) stores the address of on_tick in slot 0, so if the linker placed on_tick at 0x10000A40, then handlers[0] holds 0x10000A40 while handlers[1] still holds 0. Nothing has run yet, because a store calls nothing.
  2. Dispatch a tick. dispatch(EV_TICK) uses index 0, loads handlers[0], which is 0x10000A40, and branches to it, so on_tick prints tick and returns to dispatch and then to the caller.
  3. Dispatch a button press. dispatch(EV_BUTTON) uses index 1 and loads handlers[1], which is 0, so the call branches to address 0 and the program has left its own code, from which nothing good follows. This is the bug in the starter.
  4. Add the check. The fixed dispatcher finds 0 in the slot for dispatch(EV_BUTTON), increments the ignored count and returns without calling, while the second dispatch(EV_TICK) finds the address again and calls on_tick. The counts are handled = 2 for the two ticks and ignored = 1 for the button, giving the summary line DISPATCH OK handled=2 ignored=1.
  1. register_handler(EV_TICK, on_tick) stores the address of on_tick, say 0x10000A40, in slot 0. Storing an address calls nothing. Slot 1 still holds 0.
  2. dispatch(EV_TICK): the index is 0, so the dispatcher loads handlers[0] and branches to 0x10000A40. on_tick prints tick and returns.
  3. dispatch(EV_BUTTON): the index is 1. The slot address is the table base plus 1 × 4, and it holds 0, because nobody registered a button handler.
  4. The starter calls through the slot anyway. A call through a null pointer branches to address 0: the program has left its own code, and on a Cortex-M it ends in a fault.
  5. The fix is one check before the call: if the slot is NULL, count the event as ignored and return.
  6. The second tick is handled again. The totals are handled = 2 and ignored = 1, and the program prints DISPATCH OK.

The dispatcher code line by line

The solution in projects/0049-callback-dispatcher/solution is the program with the fix, and its key parts follow. 

typedef enum {
    EV_TICK,
    EV_BUTTON,
    EV_COUNT          /* number of events: keep last */
} Event;

typedef void (*Handler)(Event ev);

static Handler handlers[EV_COUNT];   /* zero-initialised: every entry starts as NULL */
static unsigned handled_count;
static unsigned ignored_count;

The enum numbers the events, and because EV_COUNT comes last, it always equals the number of events, so the table is sized by the enum and cannot fall out of step with it. The typedef names the handler type once, and the table is static, visible only in this file and zero-initialised by the C runtime as a static object, which makes every slot NULL, while the two counters are static for the same reason and start at zero. 

static void register_handler(Event ev, Handler h) {
    if ((unsigned)ev < EV_COUNT) {   /* reject an out-of-range event before indexing */
        handlers[ev] = h;
    }
}

Registration stores the address and does nothing else, apart from the range check that guards the array, since an event value of 5 would index past the end of a two-slot array and the store would overwrite whatever memory follows. The cast to unsigned turns a negative value into a large one, so a single comparison catches both negative and too-large values. 

static void dispatch(Event ev) {
    if ((unsigned)ev >= EV_COUNT) {
        ignored_count++;
        return;
    }
    /* A NULL entry means nobody registered a handler. Calling it would jump to address 0,
     * so check first and count the event as ignored. */
    if (handlers[ev] == NULL) {
        ignored_count++;
        return;
    }
    handlers[ev](ev);
    handled_count++;
}

The first test rejects an event number outside the table, as in registration, and the second is the important one, comparing the loaded pointer with NULL before the call so that the branch to address 0 cannot happen. The call handlers[ev](ev) loads the pointer, passes ev as the argument and branches, and the increment after it counts an event only once its handler has returned.

The callback itself is an ordinary function with the matching signature. 

static void on_tick(Event ev) {
    (void)ev;             /* unused here: the event is always EV_TICK */
    printf("tick\n");
}

Its signature void (Event) must match the typedef exactly, since a mismatched function pointer is a constraint violation. The Arm GCC 14.2 used in this course stops the build on it, because GCC 14 makes -Wincompatible-pointer-types an error for C, whereas older compilers may accept it with only a warning, after which the mismatched call passes the wrong argument or none and the bug surfaces far from the registration. Compile with warnings enabled and treat a pointer-type warning as an error, and note that (void)ev; tells the compiler that the parameter is deliberately unused.

Common mistakes and how to spot them

A call through an empty slot

The output stops after an event that has no handler, here after the first tick, and on a device the result can be a reset or a hang depending on what the chip holds at address 0, because the dispatcher calls handlers[ev] without a NULL check. Add the check from the solution, with a counter so that unhandled events remain visible.

A handler with the wrong signature

The argument holds garbage, or the program crashes, differently from build to build, because a function declared void on_tick(void) was registered in a table of void (*)(Event). Declare every handler through the typedef and compile with -Wall, so that a pointer-type mismatch is reported.

A pointer to a local passed as user data

The callback occasionally sees a wrong value, often only when the system is busy, because a function set up the callback with a pointer to a variable on its own stack and then returned, so the callback later reads memory that holds other values. Use a static or global object for context, which lives as long as the callback.

Slow work in an interrupt callback

Events go missing and the device responds late, but only under load, because a handler running from an ISR calls a blocking function such as a long print or a delay while other interrupts wait. Set a flag in the callback and do the work in main, as lesson 46 showed.

An unhandled interrupt that hangs

The program freezes once a peripheral interrupt is enabled, and the debugger shows the program counter inside Default_Handler, because the application never defined the handler and the vector entry still points at the default loop. Define the handler with the exact name from the startup file.

Callbacks in the Pico SDK and the STM32 HAL

The Pico SDK uses callbacks throughout. The repeating-timer call takes a callback and a user-data pointer, its type repeating_timer_callback_t being a typedef for a pointer to a function that takes a repeating_timer_t * and returns a bool telling the timer whether to keep firing. The interrupt API follows the same pattern, irq_set_exclusive_handler taking a handler pointer and installing it in the core's table, which applies the vector-table idea at run time.

The STM32 HAL uses weak callbacks instead. Functions such as HAL_UART_RxCpltCallback are defined __weak in the driver with an empty body, and when the application defines a function of the same name, the linker uses the application's version. This is the weak-symbol mechanism of the startup file's interrupt handlers, which reviewers expect, since a driver that calls a function by name with no way to override it cannot be customised by the team.

Code review of callbacks checks that every table is tested for NULL before a call, that every handler matches the typedef, that every callback running in an interrupt keeps its work short and avoids blocking calls, and that every context pointer outlives its registration. Reviewers also ask where the table lives, because a table in RAM can be corrupted whereas one in flash cannot.

Summary

  • A function pointer stores a function's address, its declaration reads from the inside out, and a typedef gives the type a name.
  • A callback is a function registered with other code, which calls it when an event happens, and a table of function pointers holds one callback per event.
  • Calling a NULL slot branches to address 0, which is not your code, so every slot must be checked before the call and events without a handler counted.
  • Static objects are zero-initialised, so a file-scope handler table starts with every slot NULL.
  • The vector table is an array of addresses that the core reads on reset and on every exception, with the initial stack pointer in word 0 and the reset handler in word 1.
  • A missing vector entry points through a weak alias at Default_Handler, an infinite loop, so a handler must use the exact name from the startup file.
  • Callbacks running in an interrupt must keep their work short and must not hold pointers to the stack.
