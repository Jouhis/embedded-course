The I2C protocol, decoded with a logic analyzer

I2C puts a whole conversation on two wires. A logic analyzer records both wires, and once you can read a START, an address and an ACK in the capture, you can debug any I2C sensor.

By the end of this lesson you can read a register from an I2C device with the Pico SDK (register pointer, repeated start, read), and decode the same transaction from a logic-analyzer capture: start, address with R/W, ACK and NACK, data and stop.

The idea

I2C has two wires. SDA carries data and SCL carries the clock, and both are open-drain: a device can only pull a line low, and a pull-up resistor takes it high when nobody pulls it down UM10204, section 3.1.1. Lesson 16 covers open-drain outputs and pull-ups in general. I2C depends on them, because two devices can drive the same wire without a short: neither can drive it high, so nothing fights.

The master starts every transaction and makes the clock. A START is SDA falling while SCL is high, and a STOP is SDA rising while SCL is high UM10204, section 3.1.4. The RP2040 reference manual describes the same START and STOP conditions for its I2C controller RP2040 datasheet, section 4.3.6.1. The data line may change only while the clock is low, except for START and STOP. That is what makes the sampling rule simple: the receiver reads SDA on the rising edge of SCL.

Bytes, addresses and ACK

Each byte is eight bits, most significant bit first. After the eighth clock, the receiver pulls SDA low for the ninth clock to acknowledge the byte (ACK), or leaves it high (NACK) UM10204, sections 3.1.5 and 3.1.6.

The first byte after a START carries the target address and the R/W bit. The address is 7 bits, and the eighth bit is 0 for a write and 1 for a read UM10204, section 3.1.10. So the 7-bit address 0x68 appears on the wire as 0xD0 for a write and 0xD1 for a read.

The address is 7 bits, so the wire byte is address × 2 + R/W. Forgetting the shift is the most common mistake in I2C code: the 8-bit value 0xD0 is not the device's address.

Reading a register

Most sensors have registers. To read one, the master writes the register number, then reads the value. The write and the read are one transaction, joined by a repeated START: the master does not send a STOP in between, so no other master can take the bus. 

/* 1. START, 0xD0 (write to 0x68), ACK, 0x75 (the register), ACK -- no STOP */
i2c_write_blocking(i2c0, 0x68, &reg, 1, true);   /* nostop = true */
/* 2. repeated START, 0xD1 (read from 0x68), ACK, one data byte, NACK, STOP */
i2c_read_blocking(i2c0, 0x68, &value, 1, false);  /* nostop = false: STOP at the end */

The SDK's nostop argument selects the join. With true, the write leaves the bus held, and the next call starts with a repeated START Pico SDK, hardware/i2c.h.

The MPU6050 is the device in this lesson. Its WHO_AM_I register is at address 0x75, and its default value is 0x68, which is the device's address with AD0 low InvenSense RM-MPU-6000A, register map, section 4.34. The device powers up in sleep mode, so the code first writes 0 to PWR_MGMT_1 (register 0x6B) to wake it RM-MPU-6000A, register 107.

Pull-ups and the rise time

The pull-up sets how fast the line rises after a device lets go. The rise time has a limit: 1000 ns for standard mode (100 kbit/s) UM10204, timing table for standard mode. For a bus of about 100 pF, a 4.7 kΩ pull-up rises in roughly 0.4 µs, which is inside the limit. A larger bus capacitance needs a smaller resistor. The RP2040's internal pull-ups are 50 to 80 kΩ, which is too weak to rely on for a bus, so the diagram adds 4.7 kΩ resistors to 3.3 V RP2040 datasheet, Table 625.

Try it in Wokwi

The project projects/0060-the-i2c-protocol wires a Wokwi MPU6050 to GP4 (SDA) and GP5 (SCL), with 4.7 kΩ pull-ups. A logic analyzer is connected to the same two wires, on channels D0 and D1. The program wakes the sensor, then reads WHO_AM_I once a second. When you stop the simulator, Wokwi writes wokwi.vcd to the project root.

  1. Open projects/0060-the-i2c-protocol/starter in VS Code (File → Open Folder).
  2. Build with Ctrl+Shift+B, and start the simulator with F1 → Wokwi: Start Simulator.
  3. Your task: wake the sensor with write_reg(REG_PWR_MGMT_1, 0x00), and print MPU6050 WHO_AM_I=0x68 when the read matches. Then change the pointer write in read_reg() to a repeated start (nostop = true), so the read does not follow a STOP. Stop the simulator, open wokwi.vcd in PulseView, and add the I2C decoder on the two channels.
  4. You will know it works when the serial monitor prints MPU6050 WHO_AM_I=0x68, and the decoder shows one START, the address 0x68 with the write bit, the register 0x75, a repeated START, the address with the read bit, the data 0x68, and one STOP.
Hint for reading the decode

PulseView shows the address byte as 7 bits plus R/W. A write frame reads 0x68 W, and a read frame reads 0x68 R. Find the ACK bits. Each byte should have an ACK after it, except the last read byte, which the master NACKs.

Hint for the repeated start

In the SDK, the write call's last argument is nostop. Set it to true for the register pointer write, and leave the read's nostop as false.

"Why does I2C need pull-up resistors, and why can two devices drive the same wire without damage?" Answer out loud in 60 seconds, then compare.

Model answer

I2C lines are open-drain. A device can pull a line low, but it cannot drive it high, so the pull-up is the only source of the high level. Two devices can drive the same wire because neither can connect it to the supply: pulling low is always safe. The pull-up value trades rise time against current, and the bus capacitance limits the usable resistor.

UM10204, I2C-bus specification and user manual (NXP): read section 3.1.4 for START and STOP, 3.1.5 and 3.1.6 for the byte format and ACK, 3.1.10 for the address and R/W bit, and section 7.1 for pull-up sizing.
