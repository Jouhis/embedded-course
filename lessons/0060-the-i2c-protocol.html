The I2C protocol

A two-wire addressed bus for sensors, read from a logic-analyser capture

By the end of this lesson you can read a register from an I2C device with the Pico SDK (register pointer, repeated start, read), and decode the same transaction from a logic-analyzer capture: start, address with R/W, ACK and NACK, data and stop.

Many sensors on two wires

Lesson 16 showed a pull-up resistor and an open-drain output, a pin that can only pull a line low with a resistor that lets it go high, lesson 53 showed UART, a link with one wire each way between one pair of devices and no shared clock, and lesson 58 read an analogue sensor directly into a pin. Real sensors usually work differently, because a gyroscope, a temperature sensor, an EEPROM and an OLED display can all sit on the same two wires and be addressed by number, which is what I2C provides.

I2C is the everyday bus of small sensors, spoken by many motion sensors, temperature sensors, EEPROMs and OLED displays. When one of them stops responding in a product, the fastest diagnosis is a logic-analyser capture, which can only be read with the protocol's rules in mind, so this lesson builds those rules from the wires up and then applies them to a simulated MPU6050 motion sensor.

Open-drain SDA and SCL lines

I2C rests on five ideas, the two open-drain wires, the START and STOP conditions, the byte with its acknowledge bit, the address with its read or write bit and the register read, each depending on the one before. I2C (Inter-Integrated Circuit) has two wires, SDA carrying data and SCL the clock, and both are open-drain, so a device can pull a line low but cannot drive it high, while a pull-up resistor on each line takes it high when nobody pulls it low. The NXP specification states that both lines are high when the bus is free and that the output stages must be open-drain so that devices can perform the wired-AND function UM10204, section 3.1.1.

The arrangement makes sharing safe. Two devices can drive the same wire without a short circuit, because neither can connect it to the supply, so if one pulls low while the other releases, the wire is low, which is a valid result.

START and STOP conditions

The master starts every transaction and generates every clock pulse. A START is SDA falling while SCL is high and a STOP is SDA rising while SCL is high UM10204, section 3.1.4, definitions the RP2040 I2C block shares RP2040 datasheet, section 4.3.6.1. The NXP specification calls the master a controller while the RP2040 datasheet calls it a master, the term this lesson uses. Apart from START and STOP, the data line may change only while the clock is low, which keeps the sampling rule simple: the receiver reads SDA while SCL is high.

Bit timing and clock stretching

A single bit takes one clock pulse, and the sequence within that pulse is the whole protocol at its lowest level. The master, which owns the clock, first pulls SCL low, the sender sets SDA to the next bit while SCL is low, and the master then releases SCL, which rises through the pull-up, after which SDA holds still while the receiver reads it, until SCL falls again and the cycle repeats. Eight such pulses make a byte, and a ninth carries the ACK.

The receiver therefore never has to guess when a bit starts, because the clock tells it, and the sender never changes a bit while the receiver is reading it. The master chooses the beat, which in standard mode is at most 100 kbit/s, so the speed is set by the master rather than the sensor.

A sensor that needs more time than the master's beat allows can hold SCL low after a byte, which the NXP specification calls clock stretching, and since the master cannot continue until the line is released, the transfer simply pauses UM10204, section 3.1.9. Many simple sensors never stretch the clock, and a logic analyser shows stretching as a long low period on SCL, a useful clue when a transfer is slow.

Bytes and the acknowledge bit

Every byte on the bus has eight bits, sent most significant bit first, and is followed by an acknowledge bit UM10204, section 3.1.5, the ninth clock after the eighth data bit belonging to the receiver. If the receiver pulls SDA low during that clock, it has taken the byte, an ACK, and if SDA stays high, the byte was not taken, a NACK. The NXP specification lists the reasons for a NACK, among them no device at the address and a receiver that cannot take more bytes UM10204, section 3.1.6.

The NACK has a second use, because a reading master ends the read by NACKing the last byte it receives and then sending a STOP. The NXP specification requires a controller-receiver to signal the end of the transfer UM10204, section 3.1.6, item 5, and its Device ID reading sequence ends by NACKing the last byte UM10204, section 3.1.17, so a NACK in a read is normal, whereas a NACK in a write means something is wrong.

Addresses and the R/W bit

The first byte after a START is the address, carrying a 7-bit device address in bits 7 to 1 and the R/W flag in the least significant bit, 0 meaning that the master writes and 1 that it reads UM10204, section 3.1.10, and the RP2040 datasheet draws the same byte in its figure of the 7-bit format RP2040 datasheet, section 4.3.6.2.1.

The address in the code has 7 bits while the wire carries 8, so address 0x68 appears on the wire as 0xD0 for a write, 0x68 shifted left by one plus a 0, and as 0xD1 for a read. The SDK performs the shift and the logic analyser shows the 8-bit byte, so 0x68 and 0xD0 describe the same device, and mixing them up is the commonest I2C mistake.

An I2C address works like a roll call in a classroom: the teacher calls one name and only that student raises a hand, the ACK, while if nobody of that name is present, no hand goes up and the teacher hears silence, the NACK. Every device hears every name, which is why two devices with the same address on one bus answer together and garble the reply. A roll call ends after each name, however, whereas on I2C the answering device then stays in the conversation for the bytes that follow.

Register reads with a repeated START

Most sensors have registers, and reading one takes two transfers: the master first writes the register number to the device, which sets the device's register pointer, and then reads the byte it points to. A repeated START joins the two transfers, the master sending no STOP between them and so keeping the bus, and the NXP specification states that a repeated START keeps the bus busy and is functionally identical to a START UM10204, section 3.1.4. 

/* 1. START, 0xD0 (write to 0x68), ACK, 0x75 (the register), ACK -- no STOP */
i2c_write_blocking(i2c0, 0x68, &reg, 1, true);   /* nostop = true */
/* 2. repeated START, 0xD1 (read from 0x68), ACK, one data byte, NACK, STOP */
i2c_read_blocking(i2c0, 0x68, &value, 1, false);  /* nostop = false: STOP at the end */

The SDK's nostop argument selects the join. According to the SDK header, with nostop true the master keeps control of the bus at the end of the transfer and the next transfer begins with a restart rather than a start Pico SDK, hardware/i2c.h, while with false the transfer ends with a STOP.

Register writes

A write needs no repeated start, because it has nothing to wait for. The wake-up write in this lesson sends the address, the register number and the value and then stops, its wire sequence being START, 0xD0 with W, ACK, 0x6B, ACK, 0x00, ACK, STOP, in which the sensor acknowledges each of the three bytes and the master's STOP frees the bus.

The read's first transfer is the same as the write without the value byte, followed by a repeated START instead of a STOP, so it belongs to the same transaction with the data direction reversed and the bus never released. With the two patterns side by side, most register-based devices can be read, because most of them follow one of these two shapes.

The write is also the first thing to check when a sensor does not respond. A wrong address gets no ACK on the first byte, ending the sequence there, while an acknowledged address followed by an unacknowledged byte cannot be explained by the bus itself, since whether a device acknowledges an unknown register is decided by its datasheet, which should be checked before blaming the wiring.

The MPU6050 motion sensor

The device in this lesson is the MPU6050, a motion sensor combining an accelerometer and a gyroscope, whose WHO_AM_I register at address 0x75 holds a default value of 0x68, the device's 7-bit address with the AD0 pin low InvenSense RM-MPU-6000A, register map, section 4.34, while connecting AD0 high changes the address to 0x69 Wokwi, MPU6050 part.

The sensor powers up in sleep mode, as the register description says RM-MPU-6000A, section 4, the SLEEP bit being bit 6 of PWR_MGMT_1, register 107 (0x6B), which puts the device to sleep when set RM-MPU-6000A, section 4.30. The code therefore writes 0 to PWR_MGMT_1 to clear the bit and wake the sensor before reading any measurement.

Worked example: one WHO_AM_I transaction

We trace one read of WHO_AM_I with the bytes in wire order, the master being the Pico and the target the MPU6050 at 0x68. Before reading the steps, predict who drives SDA during the data byte and who sends the final NACK.

  1. START. SDA falls while SCL is high, and the bus is now busy.
  2. Address byte, write. The master sends 0xD0, 0x68 shifted left plus 0 for write, as the bits 1 1 0 1 0 0 0 0 MSB first, and the sensor pulls SDA low on the ninth clock, acknowledging the byte.
  3. Register byte. The master sends 0x75, the WHO_AM_I register number, and the sensor's ACK leaves its register pointer at WHO_AM_I.
  4. Repeated START. Instead of a STOP the master sends a repeated START, keeping the bus.
  5. Address byte, read. The master sends 0xD1, 0x68 shifted left plus 1 for read, and the sensor ACKs.
  6. Data byte. The sensor sends 0x68 on SDA, one bit per clock, MSB first, while the master leaves SDA undriven.
  7. NACK and STOP. The master NACKs the data byte, ending the read, and sends a STOP, freeing the bus again.

The capture should show exactly that sequence: one START, the address 0x68 with W, the register 0x75, a repeated START, the address 0x68 with R, the data 0x68, a NACK and one STOP. A decode with a STOP between the register byte and the second START means the code is wrong, for the reason given in the mistakes section.

Decoding a logic-analyser capture

The logic analyser records two digital channels and its decoder turns them into bytes, inventing nothing, so every line of its table can be checked against the waveform beneath. Working through each capture in the same order catches the common faults quickly.

  1. Find the START. Look for SDA falling while SCL is high, which the decoder labels START, and if there is none, the master never began a transfer, so the code rather than the bus is at fault.
  2. Read the address byte. The decoder shows the 7-bit address and the R/W bit, so check that the address is the expected one and that the next bit is an ACK, which means a device answered, whereas a NACK here means no device at that address or a wrong address in the code.
  3. Read each data byte and its ACK. Each byte is followed by one ACK or NACK, the target acknowledging every byte of a write, while in a read the target sends the bytes and the master NACKs the last one.
  4. Check for a repeated START. Between the pointer write and the read there should be a START with no STOP before it, and a STOP there means the code released the bus, the second mistake below.
  5. Find the STOP. The transaction ends with a STOP, marked by the decoder, and if it is missing, the master still holds the bus and the next transfer will look odd.

Keep the capture and the code side by side: if the register number on the wire differs from the one in the code, the bug lies in the call's arguments, and if the value on the wire is right but the variable is wrong, the bug comes after the read.

Pull-up resistors and rise time

A pull-up sets how fast the line rises after a device lets go, and the rise time is limited, the NXP specification giving a maximum of 1 000 ns for standard mode at 100 kbit/s UM10204, Table 10. The pull-up and the bus capacitance form an RC circuit, and section 7.1 gives the rise time from 30 % to 70 % of VDD as

tr = 0.8473 × R × C(1)

where R is the pull-up resistance and C the bus capacitance UM10204, section 7.1. For the diagram's 4.7 kΩ resistors on a bus of about 100 pF the rise time is 0.8473 × 4 700 Ω × 100 pF = 0.40 µs, inside the 1 000 ns limit, and the largest resistor that still meets the limit is 1 000 ns ÷ (0.8473 × 100 pF) = 11.8 kΩ, so 4.7 kΩ has room to spare, while a longer bus with more capacitance needs a smaller resistor.

The RP2040's internal pull-ups are 50 to 80 kΩ according to its digital I/O table RP2040 datasheet, Table 625, so at 100 pF a 65 kΩ pull-up would take about 5 µs to rise, far beyond the limit. That is why the diagram adds external resistors and why the solution's comment calls the internal pull-up weak, and since a weak pull-up can still work on a short bench wire, the problem tends to hide.

The pins are GP4 for SDA and GP5 for SCL, which the RP2040's GPIO function table lists as I2C0's SDA and SCL, so the pair is valid for the I2C0 peripheral RP2040 datasheet, GPIO function table (Table 279). They are also the Pico board's default I2C pair, the SDK's board header boards/pico.h defining PICO_DEFAULT_I2C as 0, PICO_DEFAULT_I2C_SDA_PIN as 4 and PICO_DEFAULT_I2C_SCL_PIN as 5, but "default" only names the pair, and nothing connects the pins to the I2C block until the code sets their GPIO function to I2C with gpio_set_function().

The I2C driver code line by line

The solution's two helpers and its main loop show every rule of this lesson, starting with the write helper that the wake-up uses. 

/* Write one register. One transaction: START, address+W, register, data, STOP. */
static int write_reg(uint8_t reg, uint8_t value) {
    uint8_t buf[2] = {reg, value};
    int n = i2c_write_blocking(I2C_PORT, MPU_ADDR, buf, 2, false);  /* false = send STOP at the end */
    return n == 2 ? PICO_OK : PICO_ERROR_GENERIC;
}
  1. uint8_t buf[2] = {reg, value}; places the register number and the data in one array, the first byte after the address being the register pointer and the second the value, so one transfer writes both.
  2. i2c_write_blocking(I2C_PORT, MPU_ADDR, buf, 2, false) sends START, the address with the write bit, the two bytes and a STOP, the SDK adding the write bit to the 7-bit MPU_ADDR.
  3. false is nostop, so the SDK ends the transfer with a STOP, which is correct because nothing needs the bus after the write.
  4. The return value is the number of bytes the device acknowledged, or an error if the address was not acknowledged, so a missing device shows up here.
/* Read one register: a write of the register pointer, then a read. The two are joined by a */
/* repeated START (nostop = true), so the bus is never released between them. */
static int read_reg(uint8_t reg, uint8_t *value) {
    int n = i2c_write_blocking(I2C_PORT, MPU_ADDR, &reg, 1, true);   /* true = keep the bus, no STOP */
    if (n != 1) {
        return PICO_ERROR_GENERIC;   /* NACK on the address or the register byte */
    }
    n = i2c_read_blocking(I2C_PORT, MPU_ADDR, value, 1, false);       /* RESTART + address+R, then STOP */
    return n == 1 ? PICO_OK : PICO_ERROR_GENERIC;
}
  1. i2c_write_blocking(..., &reg, 1, true) sends the address with the write bit and then the register number, and with nostop true it leaves the bus held, so the SDK's next transfer starts with a repeated START.
  2. if (n != 1) catches a NACK on either byte, a return of 1 meaning the register number was acknowledged, while a failed address returns an error, which is not 1.
  3. i2c_read_blocking(..., value, 1, false) sends a repeated START and the address with the read bit and reads one byte, which the SDK NACKs before sending a STOP, because nostop is false.
  4. The function returns OK only when the read obtained exactly one byte, so the caller never sees partial results.
int main(void) {
    stdio_init_all();
    i2c_init(I2C_PORT, I2C_HZ);
    gpio_set_function(SDA_PIN, GPIO_FUNC_I2C);   /* route the pin to the I2C peripheral (not GPIO) */
    gpio_set_function(SCL_PIN, GPIO_FUNC_I2C);

    if (write_reg(REG_PWR_MGMT_1, 0x00) != PICO_OK) {   /* wake the sensor: clear SLEEP */
        printf("I2C FAIL: no ACK on the wake write\n");
    }
    while (true) {
        uint8_t id = 0;
        if (read_reg(REG_WHO_AM_I, &id) == PICO_OK && id == WHO_AM_I_VALUE) {
            printf("MPU6050 WHO_AM_I=0x%02X\n", id);   /* EXPECT: WHO_AM_I=0x68 */
        } else {
            printf("I2C FAIL: read 0x%02X\n", id);
        }
        sleep_ms(POLL_MS);
    }
}
  1. i2c_init(I2C_PORT, I2C_HZ) starts the I2C0 block at 100 kbit/s, standard mode, and returns the baud rate it achieved.
  2. gpio_set_function() on GP4 and GP5 connects the pins to the I2C block, without which they remain ordinary GPIO and the block sees nothing.
  3. The wake write sends register 0x6B with the value 0, clearing the SLEEP bit, and its failure message names the step, so the log shows which transfer went wrong.
  4. The loop reads WHO_AM_I once a second and reports success only for 0x68, while a mismatch prints the value read, which helps when the bus is wired to a different device.

Common mistakes and how to spot them

The address passed already shifted

The write returns an error and the solution prints I2C FAIL: read 0x00, because the read never received an address acknowledge, the usual cause being 0xD0 passed as the address, which the SDK then shifts again. Pass the 7-bit address 0x68, and compare with 0xD0 only in the analyser, which shows the 8-bit byte.

A STOP between the write and the read

The code works and prints WHO_AM_I=0x68, but the decoder shows two separate transactions, each with its own START and STOP, instead of one with a repeated START, which a single master on a quiet bus gets away with but a bus shared with another master does not. Pass nostop = true on the register write, as the solution does.

A pull-up that is too weak

Transfers work on the bench wire but some fail on a longer wire or at a higher speed, with slow, rounded edges in the decoder, because the internal 50 to 80 kΩ pull-up rises too slowly for a bus with real capacitance. Add external pull-ups of a few kilohms, as the diagram does, and check the rise time with equation (1).

The sensor left asleep

The device answers its address, but its measurements never change, because the SLEEP bit is set at power-up and the sensor does not measure until the wake write clears it. Write 0 to PWR_MGMT_1 before reading any measurement register, and note that the wake write in main() prints I2C FAIL if it is not acknowledged.

The wrong address for AD0

The write gets no acknowledge and the decoder shows a NACK straight after the address byte, because the board has AD0 high, which puts the device at 0x69 while the code asks for 0x68. Match the address to the AD0 pin, or find the device with an address scan.

Multi-master arbitration and bus debugging

This lesson has one master, the Pico, so the bus never has a conflict, but the protocol allows more. Two masters can start a transfer at the same moment and both drive SDA, and the NXP specification's rule is that each master checks, while SCL is high, that SDA matches what it sent. The first master to send a 1 and read back a 0 has lost arbitration, turns off its SDA driver and waits, and nothing is corrupted, because the winning bit is the one the other master had also sent, so the winner's data is intact UM10204, section 3.1.8.

That is why I2C can run several masters on one bus without a separate arbiter chip, and also why a second master on the bench can cause a problem that looks like a sensor fault: a bus that works with one master can fail intermittently once a second is added, the logic analyser showing the lost arbitration as a transfer that stops early. Clock stretching adds one more case, since a slow sensor holding SCL low can make a transfer the code expects to take 100 µs last longer, and a timeout in the driver, which the SDK's timeout functions provide, is the defence.

Professional I2C debugging therefore starts with the bus rather than the code, the first question being whether the device acknowledges its address, which one logic-analyser capture answers, and once the decode can be read, most bus faults turn out to be one of the five mistakes above.

Summary

  • I2C has two open-drain wires, SDA and SCL, whose high level comes from pull-ups, so several devices can share the bus safely.
  • A START is SDA falling while SCL is high, a STOP is SDA rising while SCL is high, and a repeated START keeps the bus.
  • Every byte has eight bits, MSB first, followed by an ACK or a NACK, and a master NACKs the last byte of a read.
  • The address is 7 bits on the wire plus a R/W bit, so 0x68 becomes 0xD0 for a write and 0xD1 for a read.
  • A register read is a write of the register pointer, a repeated START and a read, with nostop = true on the pointer write.
  • The rise time is 0.8473 × R × C with a standard-mode limit of 1 000 ns, so real buses need external pull-ups, the RP2040's internal ones being weak.
  • The MPU6050 powers up asleep, so the SLEEP bit in PWR_MGMT_1 (0x6B) must be cleared before its measurements are read.
UM10204, I2C-bus specification and user manual (NXP): read section 3.1.4 for START and STOP, 3.1.5 and 3.1.6 for the byte format and ACK, 3.1.10 for the address and R/W bit, Table 10 for the rise-time limit, and section 7.1 for pull-up sizing.
