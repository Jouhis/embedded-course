Capstone 6: Modbus RTU interface and the host master

A register map over a serial bus

By the end of this lesson you can explain a Modbus RTU frame byte by byte, decode a signed temperature from a holding register, say where the silent interval and the CRC sit in a frame, and drive the dryer from a host script that reads its status and writes its command register.

A dryer the outside world can talk to

Lessons 113 to 117 built the dryer's inside, lesson 113 writing the requirements and the state machine, lesson 114 the layered architecture and the task plan, lesson 115 the NTC driver and its host tests, lesson 116 the heater PWM, the buttons, the display and the safety checks and lesson 117 the RTOS threads and the PID loop. The inside works, but the dryer still has no way to tell the outside world what it is doing, so a factory line, a home server or a technician's laptop cannot ask it for its temperature, and nobody can start a drying cycle except by pressing the button on the case.

This stage solves the first of two problems every product in the field has, talking to the device over a wire, applying to a real product the framing rules lesson 101 taught for RS-485 and Modbus RTU, while the second problem, changing the firmware after the device has left the factory, is the subject of lesson 119. Both need care, because a wrong register map leaves the host reading nonsense and a framing mistake leaves the dryer silent.

Masters, slaves and holding registers

A bus is a wire, or a pair of wires, that several devices share, and Modbus is a protocol for a serial bus on which devices take turns sending short messages, one byte after another, usually with one master, which starts every conversation, and one or more slaves, which answer only when addressed. Here the master is a Python script on a PC, and the dryer is a slave with address 1.

Serial means that the bits of a byte travel one after another over a single data line, a job done on the chip by a UART (universal asynchronous receiver and transmitter), which shifts one byte out one bit at a time and collects the incoming bits into a byte, so the CPU never sees individual bits but reads a whole byte from the UART's data register when the receive interrupt fires and writes a whole byte to it when it has something to send, the protocol above the UART being built from these bytes.

The data the slave exposes is a list of holding registers, each a 16-bit number, two bytes, with an index (its address) starting at 0, the slave keeping the list in its own memory while the master reads and writes its entries. Such a register differs from the CPU and peripheral registers of earlier lessons, being a slot in a table the protocol defines, whose meaning the firmware decides.

The protocol therefore does not name the dryer's temperature or its state but moves 16-bit numbers in and out of a table, the meaning of each slot being an agreement between the firmware and the host, the register map, which is also why the same master script could talk to any device publishing a map like this one.

The protocol is simple, which is its strength, every request having the same shape, an address, a function code saying what to do, some fields and a checksum, and every reply being either the same kind of message with the answer in it or an exception, a short message saying why the request was refused. The physical layer, how the bits travel on the wire, is covered in lesson 101, a real RS-485 installation adding a transceiver chip that converts the signal levels, whereas the simulator and this build talk to the UART pins directly.

The register map

The map is the contract with the host, so it lives in one file, app/regmap.h, whose numbers the Python script copies, and the firmware publishes the read-only registers from the control state before each reply. Only two registers accept writes, a command and a material, everything else being read-only, so a write to it is refused.

A Modbus register map resembles a wall of numbered pigeonholes, the master never seeing the dryer's code but only asking what is in pigeonhole 3 or saying to put 1 in pigeonhole 10, the map being the agreement on what each number means, and once a product ships its numbers are not changed, because other people's programs depend on them. The comparison breaks for the read-only registers, though, because a pigeonhole holds whatever was last put in it, whereas the firmware overwrites those registers from its own state before every reply, so a value the master leaves there does not stay.

AddressNameAccessMeaning
0SETPOINT_CreadWhole degrees C of the selected material
1STATEread0 IDLE, 1 HEATING, 2 HOLDING, 3 COOLDOWN, 4 FAULT
2TEMP_X10readTemperature in tenths of a degree, signed (22.5 °C is 225)
3PWM_PCTreadHeater duty, 0 to 100 %
4FAULT_CODEread0 none, 1 over-temperature, 2 sensor, 3 runaway, 4 stale
5REMAINING_MINreadMinutes of drying left
6COMMANDwrite1 starts or stops the cycle, as the button does; reads 0
7MATERIALread and write0 PLA, 1 PETG, 2 ABS; a write is applied only while IDLE

Two rows need a comment, COMMAND being a trigger rather than a setting, because writing 1 does what the button does and the firmware clears the register straight after taking the command, so a read always returns 0, while MATERIAL is both a setting and a status, because the host can write it and then read it back. The firmware accepts a new material only while the dryer is IDLE, so a write during a cycle has no effect.

Signed temperatures in unsigned registers

A Modbus register is an unsigned 16-bit number holding 0 to 65535, whereas a chamber temperature can be below zero, so the register layout needs a way to carry −5.0 °C, which two's complement, the standard way binary hardware stores negative numbers, provides, the bits of a negative value being those that, added to the positive value, give zero in 16 bits. Before following the steps, predict the hexadecimal value that −50 tenths of a degree becomes.

  1. The positive value. 50 is 0x0032, 0000 0000 0011 0010 in binary.
  2. The inversion. Inverting every bit gives the one's complement, 0xFFCD, or 1111 1111 1100 1101.
  3. Adding 1. 0xFFCD + 1 = 0xFFCE, the value stored in the register.
  4. The check. The register holds 0xFFCE = 65486, and since 65536 − 65486 = 50, it reads as −50 when interpreted as a signed number.

The check in the last step shows the rule behind the whole scheme, a 16-bit register wrapping around at 65536, so 65486 sits 50 steps below zero, and the top half of the unsigned range, 32768 to 65535, being read as the negative numbers −32768 to −1, the bits staying the same while only the reading changes.

The firmware does this by casting, converting the signed value to int16_t, which the compiler stores as two's complement, and then to uint16_t, which keeps the same 16 bits, while the host does the reverse, reading the same 16 bits and interpreting them as signed. The mistake that catches people is reading the register as unsigned, which makes 0xFFCE 65486 tenths, 6548.6 °C, the bits being right and the reading absurd, so it is worth testing both directions.

The write check and the exceptions

The slave must not pretend to accept a write it will ignore, so modbus_slave_t has an optional check_write hook, which the dryer sets to regmap_check_write(), a write to a read-only register getting exception 02 (illegal data address) and an out-of-range command or material exception 03 (illegal data value), as the Modbus application protocol defines (lesson 101). With the hook left NULL the module behaves exactly like lesson 101's, so the change is backwards compatible, and a host test sends a real frame and checks the 0x86 0x02 reply.

The hook is short enough to read in full, the function below coming from the starter project, which the lesson does not ask you to change. 

uint8_t regmap_check_write(uint16_t reg, uint16_t value) {
    switch (reg) {
    case REG_COMMAND:
        return (value <= REGMAP_CMD_START_STOP) ? 0u : MODBUS_EXC_ILLEGAL_VALUE;
    case REG_MATERIAL:
        return (value < MATERIAL_COUNT) ? 0u : MODBUS_EXC_ILLEGAL_VALUE;
    default:
        return MODBUS_EXC_ILLEGAL_ADDRESS;   /* every other register is read-only */
    }
}
  • uint8_t regmap_check_write(uint16_t reg, uint16_t value) receives the register address and the value the master wants to write. Its return value is an exception code, and 0 means the write is accepted.
  • switch (reg) picks the rule for the register. Only two cases exist, and every other address falls through to default.
  • case REG_COMMAND accepts 0 and 1, because REGMAP_CMD_START_STOP is 1. Any larger value returns exception 03.
  • case REG_MATERIAL accepts 0 to 2, because there are MATERIAL_COUNT materials. A value of 3 or more returns exception 03.
  • default covers the read-only registers. Writing to them returns MODBUS_EXC_ILLEGAL_ADDRESS, which is exception 02, because the address does not accept writes at all.

The byte 0x86 is the function code 0x06 with its top bit set (0x06 + 0x80), that top bit being the exception flag and the byte after it the exception code, and the next section works one of these frames with real numbers.

Worked example: a frame byte by byte

A Modbus RTU frame is a sequence of bytes with nothing around it, no start byte and no end byte, its fields being the slave address, the function code, the data and a 16-bit CRC, a checksum computed from all the other bytes, so that the receiver can tell whether the bytes arrived intact. The Modbus CRC is CRC-16/MODBUS, which lesson 101 defines, and its check value for the ASCII text "123456789" is 0x4B37.

The example, which you can check with the master script, has the master reading register 2, the temperature, from slave 1. Before reading the table, predict how many bytes the request has.

StepBytes (hex)What each byte means
Request01 03 00 02 00 01 25 CA01 slave address; 03 read holding registers; 00 02 start address 2; 00 01 quantity 1; 25 CA the CRC, low byte first
Reply, reg 2 = 0xFFCE01 03 02 FF CE 78 2001 and 03 echo the request; 02 is the byte count of the data; FF CE is the register; 78 20 the CRC
Refused write01 86 02 C3 A186 is 0x06 with the exception flag 0x80 set; 02 is the exception code, illegal data address

Each of the three CRCs in this table can be checked with the CRC function in master_dryer.py, which computes the same CRC-16/MODBUS as the firmware, the CRC over the first six bytes of the request, 01 03 00 02 00 01, being 0xCA25, sent as 25 CA, the one over the first five bytes of the reply, 01 03 02 FF CE, 0x2078, sent as 78 20, and the one over 01 86 02 0xA1C3, sent as C3 A1.

The reply's data is the same two bytes as the register in the table above, so the host reads 0xFFCE and decodes it as −5.0 °C, as the plaintext block below writes out field by field. 

reply bytes:     01 03 02 FF CE 78 20
slave address:   01          slave 1 answers
function:        03          read holding registers
byte count:      02          two data bytes follow
register value:  FF CE       0xFFCE, read as big-endian (high byte first)
CRC:             78 20       0x2078, low byte first
signed reading:  65486 - 65536 = -50 tenths = -5.0 C

Two details of the byte order deserve notice, each 16-bit field being big-endian, its high byte first, so the start address 2 is sent as 00 02, whereas the CRC is the opposite, its low byte first (25 CA), and mixing up those two orders is a common bug in a first Modbus implementation. Endianness is the name for the order in which the bytes of a multi-byte number are sent or stored, which a protocol has to state for every field, and this one states it twice on purpose, because the two rules differ.

The frame lengths are fixed for the functions this slave supports, a read or a single write request being 8 bytes and a refused write reply 5 bytes (address, function with the flag, exception code and CRC), so a slave receiving a frame of any other length, or one whose CRC does not match, stays silent, silence being the protocol's way of saying that it did not understand and will not pretend to.

Silent intervals, the CRC and the receive interrupt

The RTU slave is the lesson 101 code reused as it is, modbus.c parsing a complete frame and crc16.c computing the CRC, so only the framing is new, framing meaning deciding where one frame ends and the next begins, for which an RTU frame has no marker. The rule is the silent interval, a frame ending when the line has been idle for a set time.

The Modbus serial-line specification defines the silence as 3.5 character times, and since this project's serial format is 8N1, a character is 10 bits on the wire (a start bit, eight data bits and a stop bit), so three and a half characters are 35 bit times, which at 115200 baud is 35 ÷ 115200 = 303.8 µs. The project does not use that computed value but a fixed 1.75 ms, which its own comment says 115200 baud needs and lesson 101 also gives, and since the specification could not be opened from this workspace, treat 1.75 ms as the project's value and check it in the document named in the Source box before relying on it.

The tasks tick at 1 ms, so the comms task measures silence in ticks, using a gap of 2 ms, which is safe, because it is longer than the required silence, and waiting up to 2 ms for the next byte, so if no byte comes, the frame collected so far is complete and the task passes it to modbus_process(). Bytes past the end of the buffer are dropped, so an overlong frame is cut short and fails its CRC, which means that it gets no reply.

The CRC is the second half of the protection, the sender computing the CRC-16 over the address, function and data bytes and appending it, and the receiver computing the same CRC over the bytes it received and comparing the result with the last two bytes, so any single-bit error changes the CRC and a corrupted frame is detected. The CRC does not say which byte was wrong, nor does it stop a deliberate forgery, saying only that the bytes that arrived are not the bytes that were sent.

Each received byte raises an interrupt, whose handler reads the status register and then the data register and puts the byte on a FreeRTOS queue (lesson 90), from which the comms task takes bytes at its own pace. The handler must not block, because an interrupt has no task to sleep, so it uses the non-blocking xQueueSendFromISR(), and since the interrupt is short, it never keeps the heater control waiting.

Reading the status register before the data register also clears the overrun flag, an overrun happening when a new byte arrives before the old one was read and stopping the receiver until the flag is cleared, so because the project's receive handler reads both registers in that order, one lost byte cannot stop the receiver for good, showing up instead as a bad frame that gets no reply.

One wire, one job. USART1 carries both the log and the Modbus frames. A status line printed between a request and its reply would corrupt the reply. So the build turns the once-a-second status line off with DRYER_LOG_STATUS 0, and the watchdog check-in in the logger task stays on. The lesson 117 build printed the line; this one reports the same state through the registers.

The frames of this lesson can be checked in the builder below by reading the dryer's registers with function 03, writing the command register with function 06 and comparing each CRC with the table, and typing 31 32 33 34 35 36 37 38 39, the text 123456789, under any bytes (hex) gives the check value 0x4B37.

The host master script

master_dryer.py is adapted from lesson 101's master, building the frames, checking the CRC with its own implementation and talking to the simulator through the RFC 2217 port in wokwi.toml, 4000 in this stage, RFC 2217 being a standard way to carry a serial port over a network connection, so that the script can talk to the simulated USART1 as if it were a real adapter. Its selftest command runs without a serial port, whereas the other commands need pyserial, which you install yourself, and you can run the selftest now. 

python master_dryer.py selftest
selftest OK: CRC-16/MODBUS 123456789 = 0x4B37, frames match, signed temperature decodes

The selftest checks the CRC against the standard check value, the request frames against the worked bytes above and the signed decoding, as well as checking that a corrupted frame fails the CRC test, and since the script's CRC is written separately from the C code, the two check each other, so if the C side and the Python side disagreed on a single byte, one of the two selftests would fail. The script has four commands, each mapping onto the register map.

  • status reads all eight registers in one request (function 03, start 0, quantity 8). It then decodes them: the state name, the temperature with its sign, the duty, the fault name and the minutes left. The decoding is where the signed reading from the earlier section happens.
  • material PETG writes register 7 with the value for the chosen material. The name must be PLA, PETG or ABS, and the script rejects anything else before it opens the port.
  • start writes 1 to register 6, the same command the button sends.
  • selftest runs the checks described above, with no serial port needed.

Each command builds its request with the CRC, sends it and reads the reply until the line has been silent for the same 1.75 ms the firmware uses, and since a correct slave echoes a write frame exactly, an echo means that the register accepted the value, while any other reply, or none, is printed as bytes so that you can see what came back.

Hint for the temperature register

The temperature is in hundredths of a degree. Divide by 10 to get tenths, and store it as an unsigned 16-bit value by casting through a signed 16-bit type. The test for −5.00 °C expects 0xFFCE, which is −50 in two's complement.

Common mistakes and how to spot them

Each of these has happened to someone building a Modbus device, and each entry gives the symptom first, so that you can recognise it before finding the cause.

A status line on the Modbus wire

The master reports a bad CRC or no reply, but only while the firmware runs with the status line enabled, a frame that works with the logger off failing with it on, because the log bytes land between the request and the reply, or inside the request, so the frame no longer matches its CRC. Keep DRYER_LOG_STATUS at 0 in this build, and send any debug text to a second serial port rather than USART1.

The temperature read as unsigned

A host script shows a chamber temperature of 6548.6 °C, or another large positive number, when the dryer is cold, although the register holds 0xFFCE and the bits are right, because the script reads the 16 bits as an unsigned number, so 65486 tenths becomes 6548.6 °C. Decode register 2 as signed (struct format <h in Python, int16_t in C), a path the selftest checks.

A write to a register the firmware owns

The master writes a new material with function 06, the reply echoes the write, and the next read shows the old material again, because the material is applied only while the dryer is IDLE and regmap_publish() copies the real material into the register on every reply, writes during a cycle being refused silently in the state machine. Stop the cycle first, write the material and read it back, since the firmware's behaviour is the design, so the fix belongs in the host rather than the register.

Register maps and host tools in products

Teams shipping a Modbus device publish the register map as a document or a shared header against which the host tool is written, the map being versioned like an API, so adding a register is safe, whereas moving or changing the meaning of one breaks every installed host. Reviewers ask for the map first and for a test proving that the firmware and the map agree, a job the host test in this capstone does, and lesson 120 shows how it runs in CI.

The master side is often a SCADA system or a PLC rather than a Python script, and the same rules apply there, the host having to use the same byte order, the same silent interval and the same CRC, so teams usually keep recorded frames with their correct replies and run them against any new host tool, a practice of which the selftest in this lesson is a small version.

Summary

  • Modbus RTU is a master and slaves on a shared serial line, holding registers being 16-bit slots whose meaning the firmware decides.
  • Signed values travel as two's complement in unsigned registers, −50 tenths being 0xFFCE, which read as unsigned gives a wrong temperature.
  • Each 16-bit field is big-endian while the CRC is sent low byte first, a frame ending at a silent interval with its integrity checked by the CRC, and bad frames get no reply.
  • Exception 02 means a bad address, here a write to a read-only register, exception 03 a bad value, and the flag 0x80 marks any exception reply.
  • The receive interrupt puts each byte on a queue with the non-blocking FromISR call, and a task assembles the frame.
  • Debug text stays off the Modbus wire, and the host script reads status and writes the command and material registers through the same map as the firmware.
