Zephyr setup

The west workspace, toolchain and first build

By the end of this lesson you can build a Zephyr application for the Pico with west build -b rpi_pico, change its blink period, and explain what west, the manifest and the project filter each do.

From FreeRTOS to Zephyr

Lessons 86 and 87 introduced the idea of an RTOS through FreeRTOS, a kernel with tasks, queues and a tick and nothing else, and lessons 88 to 93 built on it for the STM32. FreeRTOS gives you the scheduler and the synchronisation objects while leaving the rest to you, so you choose the drivers, decide how the board's pins are named in code and pick the build settings, choices that every project in a company then repeats.

Zephyr is the other common choice, a kernel with threads, a driver model, a hardware description, a configuration system and a build tool, all designed together. Nordic Semiconductor's SDK is built on Zephyr (see the resources list in the course), and a firm shipping several boards from several chip families often picks Zephyr so that one application and one set of tools can cover all of them. The next four lessons show how those parts fit together, this one covering the workspace and the build, lesson 95 the configuration, lesson 96 the hardware description and lesson 97 threads and kernel services.

The workspace has two parts that are easy to confuse, the Zephyr source tree, many git repositories fetched together, and your application, a small folder with a CMakeLists.txt, a prj.conf and some C files, and this lesson concerns the first part and how the second is built against it.

The parts of the Zephyr source tree

Zephyr is not one program but a source tree of many repositories, holding the kernel and its libraries, the board definitions, the drivers and the hardware abstraction layer (HAL) modules that vendors supply for their chips. A HAL is the vendor's code that talks to the registers of one chip family, so that the rest of Zephyr can use one API, the Pico's coming from Raspberry Pi and the Blue Pill's from ST, and although their internals do not matter yet, it does matter that they are separate repositories and that the workspace decides which ones to download.

Zephyr uses the word thread for what FreeRTOS calls a task, and since the glossary entry says to use the word thread inside Zephyr text, this course does so. A thread has its own stack, an entry function and a priority, just as a task does, except that a smaller number is more urgent, the opposite of FreeRTOS, a difference that commonly confuses anyone moving between the two and to which lesson 97 returns.

The west meta-tool and its manifest

West is the Zephyr meta-tool, which fetches the repositories, runs the build for a board and flashes the result. The first job is the one that makes a workspace, and it depends on a file called the west manifest, a list of projects each with a remote address, a revision and a path on disk, which for upstream Zephyr is zephyr/west.yml, listing every module the project knows about.

The manifest resembles a shopping list naming exactly which version of each Git repository to fetch, with west as the shop assistant who fetches them, so two people with the same list get the same workspace, which is why a team pins it. The comparison breaks because a shop may run out of an item, whereas a pinned revision in a git repository stays available for as long as the repository exists.

The workspace used by this course is at ~/zephyrproject, pinned to Zephyr v4.5.0, our copy of zephyr/west.yml listing the projects while the workspace's own settings in .west/config say which of them to keep, the relevant part being this. 

[manifest]
path = zephyr
file = west.yml
project-filter = -.*,+cmsis.*,+hal_rpi_pico,+hal_stm32

The path and file lines say where the manifest is, and the project-filter line is the one to understand, a list of patterns read from left to right, each either removing projects (with -) or keeping them (with +). The first pattern, -.*, removes every project, and the next four keep the projects whose names match, any name starting with cmsis and the two HAL modules for the Pico (hal_rpi_pico) and the Blue Pill (hal_stm32), so running west list in the workspace shows the Zephyr repository itself, always present because it holds the manifest, three CMSIS projects and the two HALs.

The filter saves disk space and download time, because the full Zephyr tree with every HAL and every module is several gigabytes, whereas a filter keeping only the Pico and the Blue Pill leaves a small fraction of that, which is why the course's setup script sets it.

Setting up the workspace

The course's setup script does the whole job when run from the workspace root as python tools/setup.py --zephyr, an optional step outside the core setup, because it downloads about 1 to 2 GB. The script creates a virtual environment in ~/zephyrproject/.venv, installs west into it, runs west init with the Zephyr v4.5.0 manifest, sets the project filter, runs west update and installs Zephyr's Python requirements, and if zephyr/west.yml and the west program already exist, it reports the workspace as present and does nothing else.

The steps behind the script are worth knowing, because each can fail on its own and the error message points at one step, and done by hand on Windows they run as follows.

  1. Create the virtual environment with python -m venv ~/zephyrproject/.venv, noting that on macOS and Linux the programs are in bin/ instead of Scripts/.
  2. Install west into it with ~/zephyrproject/.venv/Scripts/python -m pip install west.
  3. Create the workspace from the manifest with west init -m https://github.com/zephyrproject-rtos/zephyr --mr v4.5.0 ~/zephyrproject, the --mr option pinning the revision.
  4. Set the filter by running west config manifest.project-filter -- "-.*,+cmsis.*,+hal_rpi_pico,+hal_stm32" in the workspace, the -- being needed because the value starts with a minus sign, which west would otherwise read as an option.
  5. Download the projects with west update, the step that takes most of the time.
  6. Install the Python packages that Zephyr's build needs with python -m pip install -r zephyr/scripts/requirements-base.txt, run with the venv's Python.

Two commands check the result, west list showing six entries, the Zephyr repository and the five projects the filter keeps, and west manifest --path printing the path to zephyr/west.yml. The manifest command's flags are --resolve, --freeze, --validate, --path and --untracked, with --active-only as a modifier, whereas the name --active-path that some notes use does not exist in west v1.5.0, the version installed here.

The gnuarmemb toolchain variant

Zephyr needs a compiler and the tools around it, and although Zephyr's own SDK, bundling its own compilers and host tools, is the usual route for a new user, this course does not use it. Our workspace uses the gnuarmemb toolchain variant, meaning the Arm GNU Embedded toolchain already on this machine, chosen with two environment variables, ZEPHYR_TOOLCHAIN_VARIANT set to gnuarmemb and GNUARMEMB_TOOLCHAIN_PATH pointing at the folder containing arm-none-eabi-gcc, and the Zephyr CMake file for this variant checks that the path exists before going on (zephyr/cmake/toolchain/gnuarmemb/generic.cmake, lines 3 to 6).

The course's build script sets both variables when it finds the compiler, using the Arm GNU Toolchain 14.2 that the other lessons also use, so you need not set them by hand, although it helps to know where they come from, since a build failing with GNUARMEMB_TOOLCHAIN_PATH is not set means the variable did not reach the build. The SDK would give a known set of compilers for every board, whereas the gnuarmemb variant reuses the Arm toolchain that the Pico SDK and the STM32 lessons already need, leaving one compiler to maintain.

Building for a board

A Zephyr application is built for a board named with -b, the Pico's board definition lying in zephyr/boards/raspberrypi/rpi_pico/, whose main file, rpi_pico.dts, includes rpi_pico-common.dtsi, describing the chip's common peripherals, and ../common/rpi_pico-led.dtsi, describing the on-board LED. Lesson 96 looks at those files in detail, and for now the board name is the key, rpi_pico being the name that west and CMake look for. 

west build -p auto -b rpi_pico -d build /path/to/projects/0094-zephyr-setup/solution

The command runs from the workspace with the application folder as its last argument, the option -p auto cleaning the build folder when needed, so that a change in the board or the configuration leaves no stale files behind, and -d build setting the output folder, which the course's tools/build.py puts at build/ inside the application, because wokwi.toml looks for it there. The result is build/zephyr/zephyr.elf, the program that Wokwi runs.

The course's build script does the same thing, finding the application type from the files in the folder, choosing the board from the Wokwi diagram, where a wokwi-pi-pico part gives rpi_pico, and checking that the workspace's .venv contains west, and if west is missing, it prints Zephyr workspace not found and tells you to set it up in this lesson.

The blink code line by line

The solution's src/main.c is short, and every line is a Zephyr idea that the rest of the Zephyr lessons use, starting with the LED's description. 

static const struct gpio_dt_spec led = GPIO_DT_SPEC_GET(DT_ALIAS(led0), gpios);

This line creates a constant describing the LED, DT_ALIAS(led0) looking up the devicetree node that the alias led0 names, which the board defines to point at the LED on GP25, and GPIO_DT_SPEC_GET reading that node's gpios property and filling a struct with the GPIO controller, the pin number and the flags, so the C code never writes GP25 or the port name. Lesson 96 explains how the alias is defined, and the macro itself is in include/zephyr/drivers/gpio.h at line 376. 

if (!gpio_is_ready_dt(&led)) {
    printk("LED not ready\n");
    return 0;
}

gpio_is_ready_dt() asks whether the GPIO driver for this pin has started (gpio.h, line 982), because Zephyr starts drivers during boot and this check reveals one that failed, and since it is cheap and its message is the only clue in a failed run, the solution keeps it. The printk() call writes to the console, and return 0 ends main() rather than entering the blink loop with an unready pin. 

if (gpio_pin_configure_dt(&led, GPIO_OUTPUT_ACTIVE) < 0) {
    printk("LED configure failed\n");
    return 0;
}

This line sets the pin as an output and drives it to its active level, gpio_pin_configure_dt() taking the struct from GPIO_DT_SPEC_GET, so the board's flags, such as active-high, are already applied (gpio.h, line 1208), while GPIO_OUTPUT_ACTIVE requests an output that starts high and a negative return value means the configuration failed. 

printk("ZEPHYR SETUP OK\n");

uint32_t toggles = 0U;
while (1) {
    gpio_pin_toggle_dt(&led);
    toggles++;
    printk("toggle %u at %lld ms\n", toggles, k_uptime_get());
    k_msleep(BLINK_PERIOD_MS);
}

The first line prints the marker that the simulator run looks for, and the loop toggles the LED, flipping the pin from high to low or back (gpio.h, line 1924), while the counter counts toggles and k_uptime_get() returns the time since boot in milliseconds, as its header says, printed with the format %lld for that 64-bit value. Finally k_msleep() puts the thread to sleep for the period, during which the scheduler can run other threads, so the loop is not a busy wait. The period constant BLINK_PERIOD_MS is 250 in the solution, half a cycle, so the full period from high to high is 500 ms, a 2 Hz blink.

Try it in Wokwi

Zephyr runs on the Pico in Wokwi like any other firmware, and the first step is to see the blink work. In the starter the period is a named constant set to 500 ms, with three TODO(learner) comments in src/main.c, while the solution uses 250 ms and prints each toggle.

  1. Open projects/0094-zephyr-setup/starter in VS Code (File → Open Folder).
  2. Build with Ctrl+Shift+B, the task calling tools/build.py, which calls west build, so the build should finish without errors and create build/zephyr/zephyr.elf.
  3. Start the simulator with F1 → Wokwi: Start Simulator.
  4. Make the three changes, changing BLINK_PERIOD_MS from 500 to 250, printing the line ZEPHYR SETUP OK once before the loop and adding the toggle counter, incremented after gpio_pin_toggle_dt() with the message toggle N at X ms, where N is the counter and X is k_uptime_get().
  5. Build again and simulate, and the serial monitor should first show ZEPHYR SETUP OK and then lines of the form toggle 1 at ... ms, one every 250 ms, with the LED blinking twice as fast as before.
Hint

The three TODO(learner) comments are one line each: the period constant, a printk() before the while loop, and a counter increment with a printk() inside the loop. The toggle counter is a uint32_t, and it is printed with %u. The solution's src/main.c is the reference, and you should read it after you have tried.

The reference solution is in projects/0094-zephyr-setup/solution, to be compared after you have tried. Wokwi, a digital simulator, runs the Zephyr template through the same ELF file the build produces, but the simulator token is not set in this workspace, so the course could confirm the build, the ELF and the diagram lint, though not a live simulation run. If the serial monitor shows nothing, check that the build finished and that build/zephyr/zephyr.elf exists, then start the simulator again.

Common mistakes and how to spot them

The wrong board name

A configure error stops the build before any compiling with No board named 'pico' found. Did you mean:, followed by a short list and the advice to run west boards, because -b pico was typed instead of -b rpi_pico, an easy slip, since the chip and the board are both called Pico in conversation. Use the name that the board folder uses, rpi_pico, a behaviour we checked with the workspace's west and its CMake files.

A build run without the workspace

The course's build script stops with Zephyr workspace not found at ... (set up in lesson 94), or the shell cannot find west when it is called directly from another folder, because the workspace is missing or the virtual environment was never created, so the venv's scripts folder is not on the PATH. Run the setup in this lesson, or call west with the venv's full path, as the build script does.

A period edited without rebuilding

The LED keeps its old speed and the serial monitor shows the old interval, which looks like a bug in the simulator, because the simulator runs build/zephyr/zephyr.elf rather than your C file, and the change to BLINK_PERIOD_MS was never built. Build first with Ctrl+Shift+B, then start the simulator.

A HAL missing from the filter

A missing-module error appears during configure, because a board was added whose HAL is not in the filter, so west update never downloaded it, which west list, showing the projects present, confirms. Add the project to the filter with the same west config command and run west update again.

A west command that does not exist

The command west manifest --active-path, which notes from other sources sometimes use, fails, because the flag does not exist in west v1.5.0. Use west manifest --path, which prints the manifest file's path.

Pinned manifests and multi-board builds in product teams

A product team using Zephyr pins its manifest to exact commits rather than a branch, because a branch moves, so an unpinned build can change without any change in the team's code, which can make a field failure impossible to reproduce. The manifest is the single file saying which revision of each module the product uses, and reviewers read changes to it as carefully as changes to the code, while the filter does the same for the disk, writing the projects a build needs down in one place.

Teams also keep one application that builds for several boards, the board being a command-line choice while the hardware differences live in the board files, the overlays and the configuration, which lessons 95 and 96 cover. A continuous-integration job often builds the same application for each board in a list, so that a change breaking one board is found before it is merged.

Summary

  • Zephyr is a kernel plus drivers, a hardware description, a configuration system and a build tool, in which a task is called a thread and a smaller priority number is more urgent.
  • west reads the manifest in zephyr/west.yml, applies the project filter in .west/config and fetches only the projects the filter keeps.
  • The filter is read left to right, -.* removing everything and each + pattern then keeping the matching projects, as west list shows.
  • The gnuarmemb variant uses the Arm GNU toolchain already installed and needs ZEPHYR_TOOLCHAIN_VARIANT and GNUARMEMB_TOOLCHAIN_PATH, which the course's build script sets.
  • west build -p auto -b rpi_pico -d build builds for the Pico, the board name must be exact, and the output is build/zephyr/zephyr.elf.
  • The C code finds the LED through an alias with GPIO_DT_SPEC_GET(DT_ALIAS(led0), gpios), so no pin number is written in the code.
