Bench lab 4: Measure the bounce

Switch bounce measured and a debounce set from data

By the end of this lab you can capture a switch's bounce, measure its worst case over many presses, and choose a debounce lockout with a stated margin.

Simulated and real switch bounce

Lesson 52 picked a debounce time, and this lab measures how long a real button actually bounces, with the firmware and with a logic analyzer, so that the debounce is set from data. It is optional, needing a Pico 2, one or two pushbuttons (different kinds if you have them) and the logic analyzer, it does not count towards your progress, and it takes about 45 minutes.

A mechanical switch closes by bringing two metal contacts together, which hit, spring apart and hit again several times before they settle, each hit being an edge on the pin, the bounce that lesson 52 filtered with a lockout or an integrator sized by a rule of thumb.

Wokwi's pushbutton bounces too, but by a modelled amount, about 1 ms, which the attribute bounce: "0" can turn off (Wokwi docs: wokwi-pushbutton), whereas real switches vary by type, by age and from press to press, some cheap tactile switches bouncing for several milliseconds and a worn one longer, so a debounce tuned in the simulator can be far too short for the switch you actually fit.

The edge-timing firmware

The program in projects/bench04-measure-the-bounce enables a GPIO interrupt on both edges of GP14, the handler doing almost nothing, as lesson 57 recommends, storing time_us_32() in an array and, on a falling edge outside the lockout window, counting a press. The main loop waits until no edge has come for 50 ms and then reports the burst, how many edges it had and the time from the first to the last, one press making one burst and one release another. 

if ((events & GPIO_IRQ_EDGE_FALL) && (now - last_accept_us) >= DEBOUNCE_MS * 1000u) {
    last_accept_us = now;
    presses++;
}

The starter sets DEBOUNCE_MS to 1, about Wokwi's bounce, and the program prints a warning when one burst counted more than one press, so you see directly when the lockout is too short.

The interrupt has limits as a measuring tool, because edges closer together than the handler's run time can merge, so very fast bounce may be undercounted, whereas the logic analyzer has no such limit, which is why you measure with both.

Stage 1: in Wokwi

  1. Build and run the starter, and click the button about ten times.
  2. Each burst reports a few edges over a span below about 1 ms and the press count matches your clicks, so with a 1 ms lockout the simulator says that the debounce works.

Stage 2: on the board

Wire the button from GP14 to GND, and the analyzer's D0 to GP14 and its GND to GND, then flash the starter and open the serial port.

  1. Press and release the button 20 times, some slowly, some hard and some soft, watching for warning: one burst counted N presses.
  2. Write down the worst so far value for presses and releases, because releases often bounce differently from presses.
  3. Capture a press in PulseView at 24 MHz, zoom in on the first edge, count the edges and measure from the first to the last, then compare with the firmware's figure for the same press, more edges on the analyzer meaning that the interrupt missed some.
  4. If you have a second kind of switch, repeat with it, because a big arcade button and a small tactile switch rarely bounce alike.
  5. Choose DEBOUNCE_MS as the worst span you measured, doubled and rounded up to a whole millisecond, and at least 5 ms, fill in the table below, set the value and rebuild, after which 20 more presses should give no warnings.

The lockout is doubled because twenty presses are a small sample and the switch will age, a margin that costs little, since a 20 ms lockout still allows 50 presses a second, faster than anyone presses a button, the cost appearing only if the lockout grows long enough to eat genuine fast double presses, at around 100 ms.

Your debounce constant now has a measurement behind it rather than a guess, and you also have a small edge-timing tool you can reuse on any digital signal.

Common mistakes and how to spot them

Tuning on the simulator

A debounce that works in Wokwi counts double presses on the board, because Wokwi's bounce is a model setting rather than your switch. Measure the switch you ship.

Only presses measured

A release produces an extra press, because the release bounces too, and with a lockout only on presses, release bounce can look like a new press when it rings below the threshold. Measure both presses and releases.

The work done in the interrupt

Edges go missing and the measurement is distorted, because a handler that prints or debounces with delays is still running when the next edge arrives. Timestamp the edge and return.

Too few samples

A lockout set from one capture fails later, because bounce varies from press to press, so one capture tells you almost nothing about the worst case. Measure many presses before choosing the value.

Summary

  • Real switches bounce for longer, and more variably, than Wokwi's 1 ms model.
  • Edges are timestamped in a minimal interrupt handler and bursts reported from the main loop.
  • A logic analyzer sees edges an interrupt may merge, so it cross-checks the firmware's figures.
  • The lockout is sized from the measured worst case with a margin, and rechecked after the change.
