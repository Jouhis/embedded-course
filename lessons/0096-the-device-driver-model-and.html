The device driver model, and the GPIO and I2C APIs

Zephyr's drivers are found through the devicetree, and the application talks to them through generic APIs. You will read a real register from a sensor and handle a button with an interrupt, without naming a register or a pin in your C code.

By the end of this lesson you can read WHO_AM_I from the MYS-1 sensor at 0x48 with i2c_write_read_dt, and count button presses from a GPIO interrupt callback, with the sensor and the button both described in an overlay.

Where we are and why it matters

Lesson 94 showed where Zephyr keeps the hardware description: the chip's nodes, the board's nodes and your overlay, merged into one file at build time. It also introduced aliases, so the C code can ask for sw0 instead of a pin number. This lesson uses that tree for two kinds of device. A button is a GPIO input whose change you want to hear about straight away, which is the interrupt idea from lesson 57. A sensor is an I2C device, which you read by writing a register address and then reading the answer, as lesson 60 described on the wire.

The problem is portability. Suppose the same MYS-1 sensor sits on a Pico in one product and on another board in the next. If your C code contains i2c_write(i2c0, ...) and the GPIO number of the button, you rewrite it for each board. With the driver model, the C code names a node, and the overlay says which bus and address that node uses. The code stays the same and only the description changes. Engineers who maintain several boards depend on this every week.

The concepts, one at a time

A driver is a table of functions for one kind of device

A device driver is the code that knows how one kind of hardware works. In Zephyr it is written as a table of function pointers, called an ops table, plus the driver's private data. The GPIO driver has a table named struct gpio_driver_api (include/zephyr/drivers/gpio.h:934), whose entries are the operations any GPIO driver must provide. The chip-specific code fills in those entries.

A device is one instance of a driver: one GPIO port, or one I2C bus. Zephyr represents it as a struct device. The devicetree says which instances exist, and the build creates them at start-up. You get a pointer to one with DEVICE_DT_GET(node) (include/zephyr/device.h:323), and device_is_ready() (include/zephyr/device.h:906) tells you whether its driver started successfully. Your code never calls the chip's registers. It calls a generic function such as gpio_pin_get_dt(), which looks up the device's ops table and calls the right entry.

The indirection costs one function-pointer call per operation, and the program carries the code for every driver it links. In exchange, the same application code compiles against any board whose devicetree names a GPIO or an I2C bus. Lesson 49 introduced function pointers, and this is the same idea at the scale of a whole driver.

GPIO: logical levels, active low and pull-ups

A GPIO pin is one wire that software can read as a level or drive as a level. The button in this lesson is wired from GP14 to ground. When nothing presses it, a pull-up resistor inside the chip holds the pin at 1 (high). When you press it, the pin is connected to ground and reads 0 (low).

The overlay says GPIO_ACTIVE_LOW, which means the button is active when the physical level is low. Zephyr's GPIO API works with the logical level: gpio_pin_get_dt() returns 1 when the button is pressed, whichever way the wire is pulled. This is why the solution never tests for 0. The flag belongs to the hardware description, so if a later board wires the button to 3V3 instead, only the overlay changes. The logical-level idea is the same one that lesson 16 introduced for pull-ups.

Interrupts: a callback when the pin changes

Polling a pin means reading it on a timer. That is what the polled button of lesson 95 does, and it can miss a short press. An interrupt reverses the arrangement: the GPIO hardware notices the change, and the CPU runs an interrupt service routine (ISR). The GPIO driver's ISR then calls the functions you registered, which Zephyr calls callbacks. The driver fires them from its handler, for example in gpio_rpi_isr in drivers/gpio/gpio_rpi_pico.c:387, which calls gpio_fire_callbacks.

The trigger is chosen with a flag. GPIO_INT_EDGE_TO_ACTIVE is defined as an interrupt "on pin state change to logical level 1" (include/zephyr/drivers/gpio.h:210). Because the button is active low, the logical level 1 means pressed, so the callback fires once for each press and not for each release. An edge is a change from one level to the other, and this flag asks for one kind of edge only.

I2C: a bus of two wires and addresses

I2C connects many devices on two wires: SDA carries data, and SCL carries the clock. The master starts each transaction, sends a 7-bit address, and each device on the bus compares that address with its own. Lesson 60 covers the frame format. Here it matters that the address is seven bits, and the eighth bit says whether the master writes or reads. The MYS-1 datasheet gives its address as 0x48, the 7-bit form (section 2, the table of the I2C interface in projects/0063-mystery-sensor/MYSTERY-SENSOR-DATASHEET.html).

The sensor has a register pointer. The first byte the master writes after the address sets the pointer, and a read returns the register the pointer names. The datasheet's section 3.2 gives the sequence for reading one register: start, address with write, the register number, then a repeated start, address with read, one data byte and a stop. The repeated start is the second start condition in the same transaction. The master keeps the bus, and no other master can take it between the register write and the read.

Worked example: reading WHO_AM_I, byte by byte

The sensor's WHO_AM_I register is at address 0x0F, and the datasheet's table in section 3.1 gives its reset value as 0xA7. Read it step by step, as the bus carries it.

  1. Address byte for the write. The 7-bit address 0x48 shifts left by one bit, and the low bit is 0 for a write. In binary, 0x48 is 0100 1000. Shifted left, it is 1001 0000, which is 0x90. The bus carries 0x90, then waits for an acknowledge.
  2. Register byte. The master sends 0x0F. The MYS-1 acknowledges it and stores it as the register pointer.
  3. Repeated start and address byte for the read. The master sends a repeated start, then the address with the low bit set to 1 for a read. 0x48 shifted left gives 0x90, and setting the low bit gives 0x91.
  4. Data byte. The sensor sends the byte at the pointer, which is 0xA7. The master acknowledges nothing more, which is the standard way to end a read, and sends a stop.

The driver never shows these bytes. i2c_write_read_dt() builds the two messages for you. The write message has no stop flag, and the read message has I2C_MSG_RESTART, I2C_MSG_READ and I2C_MSG_STOP set (include/zephyr/drivers/i2c.h:1141 for the flags in the two-message form, and i2c.h:1662 for the helper). The repeated start is therefore part of the library call, not something your code must add.

The code, line by line

The solution is in projects/0096-device-driver-i2c/solution/src/main.c. Here is the sensor part, with each line explained.

static const struct i2c_dt_spec sensor = I2C_DT_SPEC_GET(DT_NODELABEL(mystery));

DT_NODELABEL(mystery) names the overlay node that has the label mystery. I2C_DT_SPEC_GET reads that node's parent bus and its reg property, and stores both in a struct (include/zephyr/drivers/i2c.h:180). The struct has a bus pointer, which is the struct device of i2c0, and an addr field, which is 0x48. The code never mentions the bus by name. 

#define MYS_REG_WHO_AM_I    0x0Fu
#define MYS_WHO_AM_I_VALUE  0xA7u

Both values are named constants. The first is the register address from the datasheet's section 3.1, and the second is the reset value of that register. Naming them lets a reviewer check each number against the datasheet, and it keeps the magic numbers out of the code path. 

static int read_who_am_i(uint8_t *id)
{
    uint8_t reg = MYS_REG_WHO_AM_I;
    return i2c_write_read_dt(&sensor, &reg, 1, id, 1);
}

The write part sends one byte from reg, and the read part fills one byte at id. Both lengths are passed explicitly, so the function never guesses how many bytes to move. The return value is 0 on success and a negative error code otherwise, which is why the caller checks rc before it looks at id. 

if (!i2c_is_ready_dt(&sensor)) {
    printk("I2C bus not ready\n");
    return 0;
}

i2c_is_ready_dt() asks whether the bus driver started (include/zephyr/drivers/i2c.h:630). If the subsystem is not compiled in, this check fails, and the message tells you so. The next section explains the Kconfig symbol that fixes it.

The button, from the pin to the counter

static volatile uint32_t presses;

static void button_pressed(const struct device *port, struct gpio_callback *cb, uint32_t pins)
{
    presses++;
}

The callback has the signature that gpio_callback_handler_t declares (include/zephyr/drivers/gpio.h:757): it receives the port, the callback record and the pin mask. This one ignores all three, because it only counts. presses is volatile, which tells the compiler the value can change outside the code it sees, namely in the ISR. The main thread reads it, and without volatile the compiler may keep a copy in a register. 

gpio_pin_interrupt_configure_dt(&button, GPIO_INT_EDGE_TO_ACTIVE);
gpio_init_callback(&button_cb, button_pressed, BIT(button.pin));
gpio_add_callback_dt(&button, &button_cb);

The three calls set up the interrupt in order. First, gpio_pin_interrupt_configure_dt enables the interrupt on the pin with the edge flag (gpio.h:1106). Second, gpio_init_callback stores the handler and a mask of the pins it cares about (gpio.h:1935). The mask is BIT(button.pin), so only this pin's events call the handler. Third, gpio_add_callback_dt links the callback record into the GPIO port's list (gpio.h:1992). Until the third call, nothing calls your function. 

while (1) {
    k_sleep(K_SECONDS(2));
    printk("button presses %u\n", presses);
}

The main thread sleeps, wakes every two seconds and prints the count. It reads presses without a lock. That is acceptable here because the read is a single 32-bit access, and the ISR is the only writer. A value that changes under the reader is a stale count, not a corrupt one. Lesson 95 used a mutex because its update was a read-modify-write across two threads, and this counter has only one writer.

Common mistakes and how to spot them

Leaving out CONFIG_I2C

The overlay describes the sensor, but the I2C driver is compiled only when CONFIG_I2C=y. The DesignWare driver that the Pico's i2c0 uses is declared inside the if I2C block of drivers/i2c/Kconfig, at line 163, and that block ends at line 320. Without the symbol, i2c_is_ready_dt() returns false and the console prints I2C bus not ready. The fix is the line in prj.conf, followed by a clean build so that the generated .config updates.

Wrong address in reg, or an 8-bit address

If the overlay says reg = <0x90>, because the 8-bit write address was copied from the bus trace, the driver addresses a device that is not there. The read then fails, and the solution's code prints MYSTERY no answer, error followed by the negative return code. The datasheet's table gives the 7-bit address, and the 8-bit form is only the bus byte with the R/W bit added. Check the overlay against section 2 of the datasheet, and check the wiring on the diagram: the sensor should sit on GP4 and GP5 with its pull-ups.

Counting on the wrong edge, or on a press without the active-low flag

Suppose the overlay drops GPIO_ACTIVE_LOW. The logical level 1 now means the pin is high, which is the released button. GPIO_INT_EDGE_TO_ACTIVE then fires when the button is let go, and the count rises by one per release. The symptom is a count that matches the presses but lags by a press, or a count that rises when your finger leaves the button. The fix is to put the active-low flag back in the overlay and not in the C code.

Setting up the callback but not the interrupt

The starter has the button configured as an input and nothing else. If you add gpio_init_callback and gpio_add_callback_dt but forget gpio_pin_interrupt_configure_dt, the pin never raises an interrupt, and the handler is never called. The printed line stays button presses 0 forever, while the sensor line prints normally. The fix is the first of the three calls above.

In real projects

Production code uses the driver model so that a board change is an overlay change. A reviewer checks three things in a driver-using change: that every device has its devicetree node and binding, that every call checks readiness before use, and that every interrupt callback does only what the ISR context allows. Lesson 95 explains why the last point matters.

Industry sensor drivers, such as those for a real MEMS accelerometer, follow the same pattern: a register map, a read helper that does the repeated start, and an interrupt line that tells the host when a sample is ready. The MYS-1 uses a polled DRDY flag instead of an interrupt, which the datasheet describes in section 4.2, so the course keeps the interrupt example on the button.

Summary

  • A driver is an ops table plus private data. A struct device is one instance, found through the devicetree with DEVICE_DT_GET.
  • GPIO_ACTIVE_LOW in the overlay makes gpio_pin_get_dt() return 1 when the button is pressed.
  • GPIO_INT_EDGE_TO_ACTIVE fires a callback on the change to logical 1, which for an active-low button is the press.
  • Set up an interrupt in three steps: configure the edge, initialise the callback with a pin mask, then add it.
  • The MYS-1 address is 0x48 in 7-bit form, which is 0x90 for a write and 0x91 for a read on the bus.
  • i2c_write_read_dt() sends the register pointer and the repeated start for you.
  • The I2C driver needs CONFIG_I2C=y, and the callback needs its interrupt configured.

Try it in Wokwi

The starter configures the button as an input. The MYS-1 node, the interrupt setup, the counter and the sensor read are left as TODO(learner) notes.

  1. Open projects/0096-device-driver-i2c/starter in VS Code, and press Ctrl+Shift+B to build.
  2. In boards/rpi_pico.overlay, add the mystery node under &i2c0 at 0x48, with the compatible vnd,mystery-sensor, as in the snippet above. The binding file dts/bindings/sensor/vnd,mystery-sensor.yaml is already in the folder.
  3. In prj.conf, add CONFIG_I2C=y.
  4. In src/main.c, add the sensor spec with I2C_DT_SPEC_GET, check i2c_is_ready_dt(), and read WHO_AM_I with i2c_write_read_dt(). Print MYSTERY WHO_AM_I 0x%02x when the value is 0xA7.
  5. Still in main.c, call gpio_pin_interrupt_configure_dt with GPIO_INT_EDGE_TO_ACTIVE, then gpio_init_callback and gpio_add_callback_dt. Finish the callback with the increment.
  6. Build, start the simulator, and read the serial monitor. You'll know it works when MYSTERY WHO_AM_I 0xa7 appears once near the start, and then button presses N appears every two seconds. Press the button (the b key in the diagram) and check that N rises.

Model answer

The application depends on a generic API, so the same code runs on another chip when the devicetree changes. The driver owns the registers, the timing and the errors, and the devicetree says which instance is which. The cost is one indirection and some code size, which the build report shows.
