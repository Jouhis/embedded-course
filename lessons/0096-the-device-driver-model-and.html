The device driver model, and the GPIO and I2C APIs

Zephyr's drivers are found through the devicetree, and the application talks to them through generic APIs. You will read a real register from a sensor and handle a button with an interrupt, without naming a register or a pin in your C code.

By the end of this lesson you can read WHO_AM_I from the MYS-1 sensor at 0x48 with i2c_write_read_dt, and count button presses from a GPIO interrupt callback, with the sensor and the button both described in an overlay.

The idea

A driver in Zephyr is a struct of function pointers, one per operation, plus its own private data. A struct device is one instance of a driver, and the devicetree says which instances exist. You get a pointer to a device with DEVICE_DT_GET(node) (include/zephyr/device.h:323), and you check it with device_is_ready(). This is the same idea as the HAL in Lab 4, built into the kernel: the application calls gpio_pin_get_dt and the GPIO driver for that chip does the register work. The same pattern appears in Linux (struct device and the driver model), and in the Arm CMSIS-Driver API. Learn it once and the names change less than you expect.

The MYS-1 sensor, from its datasheet

The mystery sensor is the chip from lesson 63. Its datasheet (projects/0063-mystery-sensor/MYSTERY-SENSOR-DATASHEET.html, section 3.1) says three things we need. Its 7-bit address is 0x48. Register 0x0F is WHO_AM_I, a read-only identity value that is 0xA7 after reset. And a read of one register is a write of the register pointer, a repeated start, then a read of one byte (section 3.2).

The repeated start matters. i2c_write_read_dt() does exactly that sequence in one call (include/zephyr/drivers/i2c.h:1662). The write phase sends the register number, and the read phase returns the byte, with no stop condition between them, so no other master can take the bus in the middle.

Describing the sensor in the overlay

The I2C bus i2c0 already exists on the Pico. The overlay adds one child node for the sensor, with its 7-bit address in reg:

&i2c0 {
    clock-frequency = <I2C_BITRATE_FAST>;
    status = "okay";
    mystery: mystery@48 {
        compatible = "vnd,mystery-sensor";
        reg = <0x48>;
        label = "MYS-1";
    };
};

The binding dts/bindings/sensor/vnd,mystery-sensor.yaml says include: i2c-device.yaml. That base binding requires reg and places the node on an I2C bus, and it has no compatible of its own (dts/bindings/i2c/i2c-device.yaml). So our binding only names the device and inherits the rest.

In C, one macro gathers the bus and the address from that node. I2C_DT_SPEC_GET(DT_NODELABEL(mystery)) gives a struct with the bus device and the 7-bit address (include/zephyr/drivers/i2c.h:180). The I2C subsystem must be on for this to link. Set CONFIG_I2C=y in prj.conf, because the Pico's DesignWare driver lives inside the if I2C block of drivers/i2c/Kconfig.

static const struct i2c_dt_spec sensor = I2C_DT_SPEC_GET(DT_NODELABEL(mystery));

uint8_t reg = 0x0F;     /* WHO_AM_I */
uint8_t id  = 0;
if (i2c_write_read_dt(&sensor, &reg, 1, &id, 1) == 0 && id == 0xA7) {
    printk("MYSTERY WHO_AM_I 0x%02x\n", id);
}

Buttons with an interrupt

Polling a button, as Lab 4 did, wastes time and can miss a short press. A GPIO interrupt calls your function when the pin changes. Three calls set it up: gpio_pin_interrupt_configure_dt(&button, GPIO_INT_EDGE_TO_ACTIVE) chooses the edge (include/zephyr/drivers/gpio.h:1106), gpio_init_callback stores your function and the pin mask, and gpio_add_callback_dt registers it (gpio.h:1935, 1992). GPIO_INT_EDGE_TO_ACTIVE is a logical edge, so it fires when the button becomes pressed, not when the pin changes level (gpio.h:210).

The callback runs in interrupt context. Keep it to an increment, and do the printing in a thread. The solution's callback is one line, presses++, and it is volatile because the main thread reads it.

Try it in Wokwi

The starter has the button set up and the sensor missing. You add the sensor node, then read WHO_AM_I.

  1. Open projects/0096-device-driver-i2c/starter in VS Code.
  2. In boards/rpi_pico.overlay, add the mystery node under &i2c0 at 0x48, as in the snippet above. The binding and the chip files are already in the folder.
  3. In prj.conf, add CONFIG_I2C=y.
  4. In src/main.c, write the sensor spec, the WHO_AM_I read, and the print. Finish the button callback with the increment.
  5. Build, start the simulator, and press the button a few times. You'll know it works when "MYSTERY WHO_AM_I 0xa7" appears once and "button presses" grows with each press.
Hint

If the bus is "not ready", the usual cause is CONFIG_I2C. Check build/zephyr/.config for CONFIG_I2C=y. If the read fails, check the address in reg and the wiring on the diagram: SDA is GP4 and SCL is GP5, with 4.7 kΩ pull-ups to 3V3.

"What does a device driver model buy you over calling registers directly?" Answer out loud in 60 seconds, then compare.

Model answer

The application depends on a generic API, so the same code runs on another chip when the devicetree changes. The driver owns the registers, the timing and the errors, and the devicetree says which instance is which. The cost is one indirection and some code size, which the build report shows.

Zephyr documentation: GPIO (the devicetree macros and the interrupt section), and Zephyr documentation: I2C (the i2c_write_read_dt helper). Read both, then compare with the sensor's section 3.2 in the datasheet.
