The preprocessor and multi-target builds

One code base can run on a Pico and on an STM32 if the build tells the code which board it is for. The preprocessor does the selection, and it also causes the bugs that interviewers like to ask about.

By the end of this lesson you can write a board header with an include guard and #if defined selection, choose a board with target_compile_definitions in CMake, and replace a dangerous function-like macro with a static inline function.

Where we are and why it matters

The course so far has built on two boards. The early lessons, starting with lesson 2, blink the Pico's on-board LED, and the STM32 lessons, such as lesson 42, use the Blue Pill, whose LED is on PC13. Lesson 45 showed how C evaluates arithmetic on the types you give it. This lesson is about the step before the compiler sees the code at all: the preprocessor, which edits the text of each file first.

The problem comes up when a product has more than one board. A company may build a sensor on a Pico for the prototype, and on an STM32 for the production cost. Two code bases that differ in one pin number are a maintenance trap, because a fix made in one is forgotten in the other. The usual answer is one code base, with the board chosen at build time. The preprocessor makes that choice, and it can also make the code hard to read if it is used carelessly. This lesson covers both.

Concepts, one at a time

The preprocessor edits text first

C compilation runs in phases. In the first phase the preprocessor reads each source file and performs the directives: #include pastes in another file, #define records a substitution, and the #if family keeps or removes blocks of text. The output of the preprocessor is ordinary C text, and that text is what the compiler reads. The compiler never sees the directives, and it never sees the macro names. It sees the results. The preprocessor does not know about types, scopes or values. It works on tokens: identifiers, numbers, operators and punctuation. That is why it can paste text together, and why it cannot check an argument's type.

Because the compiler reports errors on the expanded text, a message can point to a line that looks correct. When a message does not make sense, run the preprocessor by itself with -E, and read what the compiler actually received.

Object-like and function-like macros

An object-like macro is a name with a replacement list, such as #define LED_PIN 25u. Each use of LED_PIN is replaced by the text 25u. A function-like macro takes arguments. Each use is replaced by its replacement list, with the arguments substituted for the parameters, as text. The replacement is textual, so nothing is evaluated first. The argument 2 + 1 is pasted in as three tokens, and the operators inside the replacement decide how they group. cppreference, replacement of macros

The preprocessor offers two operators that work only inside macros. The # operator turns the argument into a string literal, so #name with name equal to OK becomes "OK". The ## operator joins two tokens into one, so EV_##name with name equal to OK becomes the single identifier EV_OK. Both are used in the X-macro pattern later in this lesson.

Conditional compilation

The #if, #ifdef, #elif, #else and #endif directives select which lines are compiled. The preprocessor evaluates each condition at build time, and a false branch is removed completely. A defined(NAME) test asks only whether the name has been defined, and it does not care about its value. The test #if defined(BOARD_PICO) is true for -DBOARD_PICO, and also for -DBOARD_PICO=0. That detail causes one of the mistakes below.

The #error directive stops the build and prints its message. It is a deliberate check: if no board was chosen, the build fails with a clear message, rather than compiling a pin that does not exist on the hardware.

Include guards

A header can be included more than once in one translation unit, through different paths. Each #include pastes the whole header in again, so a second copy of a typedef or a struct definition is a compile error. An include guard is a pattern that prevents this. The header wraps its contents in #ifndef NAME, defines NAME at the top, and ends with #endif. The second inclusion finds the name already defined and skips the body. Glossary: Include guard

Choosing a value at build time

The compiler's -D option defines a macro from the command line. In CMake the same thing is done with target_compile_definitions, which adds definitions to one target. The keyword PRIVATE applies the definitions to that target, and NAME=VALUE sets a value. The build, not the source file, decides which board the code is for. CMake documentation, target_compile_definitions

Worked example: SQUARE(2 + 1), step by step

A square is one of the most common things to write as a macro, and one of the easiest to get wrong. Here is the definition, with the lesson's test case: 

#define SQUARE(x) x * x

int a = SQUARE(2 + 1);

Step 1: the preprocessor finds SQUARE( and collects one argument, the tokens 2 + 1. It does not evaluate them.

Step 2: it substitutes the argument for x in the replacement list x * x. Each x becomes 2 + 1, so the text becomes 2 + 1 * 2 + 1. You can check this with arm-none-eabi-gcc -E, which prints exactly this line for the definition above.

Step 3: the compiler parses that text with the usual precedence. Multiplication binds tighter than addition, so 1 * 2 is computed first and gives 2. The expression is then 2 + 2 + 1, which is 5. The assignment stores 5 in a, not 9.

Now the function version, which the solution uses: 

static inline int square(int x) {
    return x * x;
}

int b = square(2 + 1);

Step 1: the compiler evaluates the argument 2 + 1 first, as a normal expression, and gets the value 3. The argument is a value, not text.

Step 2: the function receives 3 in its parameter x. Inside, x * x is 3 * 3, which is 9. The result is 9 in b. The function body is an ordinary expression, so the parameter is substituted once, by value.

The two results differ only because the macro pastes text and the function passes a value. Both forms run the same arithmetic. The difference is where the grouping happens.

Worked example: one line that selects the pin

The board header makes the same point for constants. With BOARD_PICO defined, the preprocessor keeps the Pico branch and removes the other one: 

#if defined(BOARD_PICO)
    #define LED_PIN  25u          /* kept: the Pico branch is compiled */
#elif defined(BOARD_BLUEPILL)
    #define LED_PIN  13u          /* removed: the preprocessor never sees it as code */
#endif

Every later use of LED_PIN becomes 25u. The line gpio_xor_mask(1u << LED_PIN) therefore becomes gpio_xor_mask(1u << 25u). The value is 1 shifted left 25 places, which is 33554432, a single bit in bit 25. A build with BOARD_BLUEPILL would produce 1u << 13u, which is 8192, a single bit in bit 13. The source line is the same in both builds, and only the text the compiler receives differs.

Dangerous macros, and the static inline alternative

The SQUARE macro fails because it has no parentheses. Adding them helps with that case, but not with the others. Suppose the argument has side effects: 

int i = 2;
int c = SQUARE(i++);     /* expands to i++ * i++ */

The expansion is i++ * i++. Both operands change i, and the standard does not sequence them. The result is undefined behaviour: the compiler may produce any value, and it may increment i twice or not at all. A function call such as square(i++) evaluates i++ once, before the call, and so has defined behaviour. Glossary: Undefined behaviour

Do not use a macro to hide a computation with side effects. SQUARE(i++) has undefined behaviour in C, because the argument is used twice without a sequence point between. Write a static inline function instead.

A static inline function fixes the problems at once. The argument is evaluated once, before the call. The parameter has a type, so the conversions follow the usual rules of C from lesson 45. The function has file-local linkage, so it does not clash with other files. And the compiler can still inline it, which removes the call overhead on the small functions where it matters. Glossary: Static inline function

Macros still have uses that a function cannot cover. A token-pasting list, a compile-time constant, or a stringized name must be a macro. Use them when the preprocessor's job is to write text, and use a function when the job is to compute a value.

X-macros: one list, many uses

An X-macro keeps one list of names in a macro. The list is written as a macro that takes another macro as its argument, and each use passes a different macro. Here is the pattern for event names: 

#define EVENT_LIST(X)  X(OK)  X(TIMEOUT)  X(BAD_CRC)
#define AS_ENUM(name)   EV_##name,          /* ## joins the prefix and the name */
#define AS_STRING(name) #name,              /* # turns the name into a string */

typedef enum { EVENT_LIST(AS_ENUM) EV_COUNT } Event;
static const char *const event_names[] = { EVENT_LIST(AS_STRING) };

Trace the enum. EVENT_LIST(AS_ENUM) expands to AS_ENUM(OK) AS_ENUM(TIMEOUT) AS_ENUM(BAD_CRC), and each of those becomes EV_OK,, EV_TIMEOUT, and EV_BAD_CRC,. The enum is therefore EV_OK = 0, EV_TIMEOUT = 1, EV_BAD_CRC = 2, EV_COUNT = 3. The number EV_TIMEOUT is 1 because it is the second entry.

Trace the string table. The same list with AS_STRING expands each name into a string literal, so the array is {"OK", "TIMEOUT", "BAD_CRC"}. The index of each string matches the enum value, because both come from the same list in the same order. Adding X(RETRY) to the list gives a new enum value and a new string in one edit. No two lists can drift apart.

The code, explained line by line

The starter and the solution share the board header, which is the core of the lesson. The header is short, and every line has a purpose: 

#ifndef BOARD_H
#define BOARD_H

#if defined(BOARD_PICO)
    #define BOARD_NAME "pico"
    #define LED_PIN    25u          /* on-board LED of the Raspberry Pi Pico */
#elif defined(BOARD_BLUEPILL)
    #define BOARD_NAME "bluepill"
    #define LED_PIN    13u          /* PC13 on the STM32 Blue Pill (active low) */
#else
    #error "Define BOARD_PICO or BOARD_BLUEPILL in CMakeLists.txt"
#endif

#endif /* BOARD_H */

The first two lines are the include guard. The name BOARD_H is defined on the second line, so a second inclusion finds it and skips the body. The #if defined chain chooses one set of definitions. The BOARD_NAME string is for the serial monitor, and LED_PIN is the number the rest of the code uses. Because every board sets the same two names, main.c never needs to know which board it is.

The #else branch is the safety net. It runs only when neither board was defined, and its #error stops the build. A build that forgets the board fails at once, instead of compiling a pin number that is wrong for the hardware.

The CMake line selects the board for this build. It is written in CMakeLists.txt, not in the source: 

target_compile_definitions(blink PRIVATE BOARD_PICO=1)

The line adds the definition BOARD_PICO=1 to the target blink. The PRIVATE keyword applies it to this target's compilation. The value 1 is not used by the header, which tests only whether the name is defined, so the value is a convention that reads clearly in the build file.

The STM32 template works the same way. The file templates/common/stm32f1.cmake calls add_compile_definitions(STM32F103xB), which defines the device macro for every target in that project. The umbrella header stm32f1xx.h tests that macro with #elif defined(STM32F103xB) to pick the device header for the chip.

The main file uses the X-macro, the function, and the board name: 

static inline int square(int x) {
    return x * x;
}

int main(void) {
    stdio_init_all();
    gpio_init(LED_PIN);
    gpio_set_dir(LED_PIN, GPIO_OUT);

    printf("MULTI-TARGET OK board=%s square=%d event=%s(%d)\n",
           BOARD_NAME, square(2 + 1), event_names[EV_TIMEOUT], (int)EV_TIMEOUT);

    while (true) {
        gpio_xor_mask(1u << LED_PIN);
        sleep_ms(500);
    }
}

The function square is the replacement for the macro, and it is called with 2 + 1, so the result is 9. The printf prints the board name from the header, the square, and the name of one enum value with its number. The format string uses %s for strings and %d for integers, and the cast (int)EV_TIMEOUT matches the %d with an int argument.

The loop calls gpio_xor_mask, which the SDK documents as toggling every GPIO that appears in its mask. The mask 1u << LED_PIN is the single bit for the LED, so the LED toggles every 500 ms. The loop does not mention a board. The board is entirely in the header, which is the point of the design.

Common mistakes and how to spot them

  1. A macro with side effects. A developer writes SQUARE(i++) or MAX(a++, b), and the variable changes twice, or the result is unpredictable. The symptom is a number that looks wrong on the serial monitor, and changes with the optimisation level. The fix is a static inline function, which evaluates its argument once.
  2. A constant macro without parentheses. A developer defines #define CLEAR_BIT 1 << 13, and then writes gpio &= ~CLEAR_BIT. The expansion is ~1 << 13, which is (~1) << 13, equal to 0xFFFFC000. That value clears bits 0 to 13, not only bit 13. The symptom is that other pins go low when one pin is cleared. The fix is to wrap the constant: #define CLEAR_BIT (1u << 13), and to test the value with a print.
  3. Testing a board name with a value. A build passes -DBOARD_PICO=0, meaning "not a Pico", but #if defined(BOARD_PICO) is true because the name is defined. The symptom is the Pico pin selected on a board that is not a Pico, and the serial monitor shows the wrong board name. The fix is to define only the chosen board, or to write the test as #if BOARD_PICO, which uses the value.
  4. A header without an include guard. A file includes board.h directly and also through another header. The build fails with a redefinition error, pointing at a line that looks fine. The symptom is an error that appears only when a new include is added. The fix is the guard at the top and the matching #endif at the bottom.
  5. Forgetting the board definition. A new build target is added to CMake without target_compile_definitions. Without the header's #error, the build would compile with no LED_PIN and fail somewhere confusing. With the safety net, the message says what to define. The symptom is a clear build error, and the fix is to add the line to the target.

In real projects

Teams use the preprocessor for three jobs: include guards, board or device selection, and compile-time constants that must be known before the code is compiled. They avoid it for computation. The HAL and CMSIS headers follow this split, with macros for device selection and register names, and small inline functions for everything that does arithmetic.

Code review on macros is strict in many teams, and some companies follow MISRA C, a coding standard that restricts macro use. A reviewer asks three questions of each macro. Does it have a function-like form that would be safer? Are its arguments parenthesised, and are they evaluated once? And is the board or device selection done in the build system, so the source does not hard-code a choice? A macro that fails any of these gets a comment in review.

The interview question about macros versus functions is common, and it tests whether you know both the preprocessor and the compiler. The strong answer names the textual nature of macros, gives the SQUARE(2 + 1) example with its result, and says when a macro is still the right tool. The model answer at the end of this lesson covers those points.

Summary

  • The preprocessor edits text before the compiler runs. A macro is a text substitution, and an #if removes code before it is compiled.
  • A function-like macro does not evaluate its argument first, so SQUARE(2 + 1) expands to 2 + 1 * 2 + 1, which is 5.
  • Use a static inline function for computation. Use a macro for token pasting, stringizing and compile-time constants.
  • Wrap every macro constant and every argument in parentheses, and never pass an expression with side effects to a macro.
  • Include guards stop a header being read twice in one translation unit.
  • Choose the board in the build with target_compile_definitions, and add an #error for the case where no board is chosen.
  • An X-macro keeps an enum and its names in one list, so they cannot drift apart.

"When would you write a macro, and when a static inline function? Give one example of each." Answer out loud in 60 seconds, then compare.

Model answer

Use a macro for things the compiler cannot express as a function: a token-pasting list such as an X-macro, a compile-time constant, or a stringizing name. Use a static inline function for any computation with arguments: it is typed, evaluates each argument once, and the compiler can still inline it. A macro such as SQUARE(x) x * x gives 5 for SQUARE(2 + 1), and a function gives 9.
