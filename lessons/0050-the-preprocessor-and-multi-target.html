The preprocessor and multi-target builds

One code base can run on a Pico and on an STM32 if the build tells the code which board it is for. The preprocessor does the selection, and it also causes the bugs that interviewers like to ask about.

By the end of this lesson you can write a board header with an include guard and #if defined selection, choose a board with target_compile_definitions in CMake, and replace a dangerous function-like macro with a static inline function.

The idea

The preprocessor runs before the compiler proper. It handles #include, #define and the #if family, and it replaces text. The compiler never sees the directives. So a #define is a substitution, not a variable, and a #if removes code before it is compiled. Preprocessor errors often appear far from their cause, because the compiler reports the expanded text. Run the preprocessor by hand with -E when a message does not make sense.

A function-like macro replaces each invocation with its replacement list, substituting the arguments for the parameters. The replacement is textual. cppreference, replacement of macros. That is the source of the most common macro bug.

Include guards and board selection

A header can be included more than once in one file, through different paths. An include guard makes the second inclusion do nothing. Board selection uses the same directives: the build defines a macro, and the header picks the matching pin. 

/* board.h */
#ifndef BOARD_H
#define BOARD_H

#if defined(BOARD_PICO)
    #define LED_PIN  25u          /* on-board LED of the Pico */
#elif defined(BOARD_BLUEPILL)
    #define LED_PIN  13u          /* PC13 on the Blue Pill */
#else
    #error "Define BOARD_PICO or BOARD_BLUEPILL"
#endif

#endif /* BOARD_H */

The #error line is a deliberate safety net. If someone builds without choosing a board, the build stops with a clear message, rather than compiling a pin that does not exist on their hardware.

The STM32 template already defines STM32F103xB for every target (templates/common/stm32f1.cmake), which is why CMSIS headers select the right device. You can use the same pattern: #if defined(STM32F103xB) for device code, and #if defined(BOARD_PICO) for the board.

Choosing the board in CMake

The build, not the source, decides which board the code is for. target_compile_definitions adds a definition to one target. PRIVATE keeps it to that target, and NAME=VALUE sets the value. CMake documentation, target_compile_definitions 

# CMakeLists.txt for the Pico
target_compile_definitions(blink PRIVATE BOARD_PICO=1)

# A Blue Pill folder would say instead:
# target_compile_definitions(blink PRIVATE BOARD_BLUEPILL=1)

Dangerous macros, and the static inline alternative

Consider a square written as a macro, with no parentheses: 

#define SQUARE(x) x * x

int a = SQUARE(2 + 1);    /* expands to 2 + 1 * 2 + 1, which is 5, not 9 */

Parentheses around the parameter, as in ((x) * (x)), fix this case, but the macro still has no types and no single evaluation. An argument with side effects, such as SQUARE(i++), is evaluated twice. A static inline function fixes all of these: the argument is evaluated once, it follows the usual conversion rules, and the compiler can still inline it.

Do not use a macro to hide a function call with side effects. SQUARE(i++) has undefined behaviour in C, because the argument is used twice without a sequence point between. Write a static inline function instead.

X-macros: one list, many uses

An X-macro keeps one list of names in a macro. You pass the list a different macro each time to generate the enum, the string table and anything else that must match. The list cannot drift out of step, because every use reads it. 

#define EVENT_LIST(X)  X(OK)  X(TIMEOUT)  X(BAD_CRC)
#define AS_ENUM(name)   EV_##name,          /* ## joins the prefix and the name */
#define AS_STRING(name) #name,              /* # turns the name into a string */

typedef enum { EVENT_LIST(AS_ENUM) EV_COUNT } Event;
static const char *const event_names[] = { EVENT_LIST(AS_STRING) };

  1. Open projects/0050-multi-target/starter in VS Code, build, and start the simulator.

  4. You will know it works when the serial monitor prints MULTI-TARGET OK board=pico square=9 event=TIMEOUT(1).

You chose the board in the build, not in the source, and replaced a macro that mis-evaluated its argument with a function that does not. You also wrote an X-macro list that keeps the enum and the names in step.

"When would you write a macro, and when a static inline function? Give one example of each." Answer out loud in 60 seconds, then compare.

Model answer

Use a macro for things the compiler cannot express as a function: a token-pasting list such as an X-macro, a compile-time constant, or a stringizing name. Use a static inline function for any computation with arguments: it is typed, evaluates each argument once, and the compiler can still inline it. A macro such as SQUARE(x) x * x gives 5 for SQUARE(2 + 1), and a function gives 9.
