Logging, tracing and field diagnostics

A device in the field cannot be debugged with a cable. Its logs and its reset reason are often the only evidence you get, so design them before the first crash.

By the end of this lesson you can keep the last few log lines in no-init RAM, read the reset reason from RCC_CSR, and print both after a software reset.

Where we are and why it matters

Lesson 84 ended with a fault that prints its own address. That output is useful only while the device is on your bench. The next question is harder. A device was reset last Tuesday, and nobody was watching. What did it do before the reset, and why did the reset happen? The answer has to be stored somewhere that survives the reset, and the reset itself has to leave a trace. This lesson is about those two things, and about the memory layout from lesson 78 that makes the first one possible.

A typical case is a support ticket. A customer reports that a controller restarted during the night. The support engineer has the device's log, a short text printed over a serial port in the lab, and the release number. Nothing else. If the firmware was designed for this, the log holds the last few lines before the restart, the reset reason says whether it was a watchdog, a software reset or a power loss, and the release's ELF file turns any address into a line of source. If it was not designed for this, the ticket is closed as "cannot reproduce". This lesson teaches the design.

The lesson has four parts. First, how logs are filtered and what they cost. Second, how a log stays in RAM across a reset. Third, how the reset reason is read from a register. Fourth, how the crash record and the trace tools fit together. The hands-on task puts the first three into one small program.

Log levels and what they cost

A log is a line of text the firmware writes to explain what it is doing. Logs have levels that say how important a line is: error, warning, info, debug and trace, from most to least important. A level is a threshold. A build keeps the lines at or above its threshold, and it drops the rest. A release build of a small device usually keeps errors, warnings and information, and drops debug and trace.

On a small chip, the important question is where the filter runs. A run-time filter is an if that checks the level when the program reaches the log call. The string and the call are still in the flash image, so they cost flash, and the check costs time on every call. A compile-time filter uses the preprocessor. A #if around a debug call removes the string and the call from the image before it is built, so the removed code costs no flash and no time. The example below uses that approach: 

#define LOG_LEVEL_ERROR  1
#define LOG_LEVEL_INFO   3
#define LOG_LEVEL        LOG_LEVEL_INFO   /* release build: info and above */

#if LOG_LEVEL >= 4                        /* debug and trace are compiled out below this */
#define LOG_DEBUG(msg) uart_puts(msg)
#else
#define LOG_DEBUG(msg) ((void)0)
#endif

With LOG_LEVEL set to info, the number is 3, the test LOG_LEVEL >= 4 is false, and LOG_DEBUG expands to ((void)0). The compiler sees a statement that does nothing, and removes it. The string never reaches the image. Change the level to 4 and the debug calls return, with their strings, in the next build.

Cost matters because the serial port is slow. A UART sends each byte as a frame: one start bit, eight data bits and one stop bit, which is ten bit times on the wire with the usual 8N1 format. At 115200 baud, that is 11520 bytes per second, or about 87 microseconds per byte. A 40-character line therefore takes about 3.5 milliseconds to leave the chip, even if the code that prints it is fast. That is the reason the serial port is a poor place for a log in a timing-critical path, and it is the reason the next warning matters.

A printf in an interrupt handler can take milliseconds at 115200 baud. Logs in a handler that has a deadline change the behaviour you are trying to observe. Log from the main loop, or into a buffer that the main loop prints.

Binary and deferred logging

Text logs are expensive in flash, because every line carries its format string. Binary logging sends a small numeric ID and the raw argument values. A host program turns them back into text using a table that the build creates. Systems in this family include defmt (Rust) and Trice (C). This course has not checked their current APIs, so read their own documentation before you adopt one.

A second idea is deferred logging. The handler or the critical code only copies a record into a buffer, and the main loop prints it later. The buffer costs RAM and the copy costs a little time, but the slow part, the UART, runs where its delay does not matter. The crash log in this lesson is a deferred log in its simplest form, because its contents are kept in memory and only printed after the reset.

A log that survives a reset

A crash is almost always at the end of a log. So the part worth keeping is the last few lines of the log. A ring buffer (glossary: ring buffer) is a fixed array with a write position that wraps back to the start when it reaches the end. It holds the newest lines and overwrites the oldest. Its size is fixed at build time, so its RAM cost is known.

A log in RAM that survives a reset is an aircraft's flight recorder. It keeps the last moments in a place the crash does not destroy, so the investigators can read them afterwards. Here the place is a RAM section that the startup code does not clear, and the investigator is the firmware after the reboot.

The ring must live in RAM that the startup code does not clear. Lesson 78 showed where that RAM sits among the static data, the heap and the stack. Lesson 42 showed what the startup code does before main. It copies .data from flash and clears .bss, the zero-initialised variables. The startup code's loop clears from the symbol _sbss up to _ebss, and the program's .bss lies in that range. A variable placed in a different section is not in that range, so it keeps its value across a reset. In GCC, the section is set with an attribute: 

static crash_log_t g_crash_log __attribute__((section(".noinit")));

The attribute puts the variable in a section named .noinit. The linker script in this project has no output section with that name. GCC then emits an orphan section, which is a section the linker script does not mention, and the linker places it after the sections it knows. In this build, the map file shows the result. The .noinit section starts at 0x200001bc, which is the same address as _ebss. The clear loop stops at _ebss, so the log is outside the range the loop clears. A production linker script would give the section its own output section, marked as not loaded, so its placement does not depend on the linker's orphan rules.

A power-on reset leaves RAM with random contents, so the log might look valid by chance. The sample stores a magic number and checks the ring indices before it trusts the contents. A checksum is stronger if the log must survive a brown-out, which is a dip in the supply voltage that does not fully reset the chip.

Reset reason: RCC_CSR on the STM32F1

The STM32F1 reports why it last reset in the RCC control and status register, RCC_CSR (glossary: reset reason). The reset sets a flag for its source. The flags stay set until software writes the RMVF bit, which clears them, so a reset can be read after it happens (RM0008 Rev 21, section 7.3.10). The reference manual RM0008 describes the register in section 7.3.10 of its RCC chapter. The bit positions below are read from the device header in third_party/cmsis-device-f1/Include/stm32f103xb.h, which the course build uses, and they match the register description in that section.

FlagBitMeaning
LPWRRSTF31Low-power management reset
WWDGRSTF30Window watchdog reset
IWDGRSTF29Independent watchdog reset
SFTRSTF28Software reset (NVIC_SystemReset)
PORRSTF27Power-on or power-down reset
PINRSTF26Reset pin (NRST)
RMVF24Write 1 to clear the flags above

The header defines each flag's mask as 0x1UL << RCC_CSR_..._Pos. The mask for SFTRSTF is 0x10000000, which is what a number quiz in this lesson asks for. The order of the flags matters for reading. Read the register once, at the start of main(), before anything else clears it. Then write RMVF, so the next boot shows only its own reset. A software reset is the one the crash log depends on, because NVIC_SystemReset() is the request that the handler and the assertion make. The chip resets, the SFTRSTF flag is set, and the log in RAM is still there to be read.

Crash dumps, trace and debug output

A crash dump is the state at the fault: the eight stacked words (lesson 84), the fault registers, and the last log lines. The device prints it or stores it, and the PC decode from lesson 84 turns it into source lines. The crash log in this lesson is a small dump, and it records the failing assertion's file and line in the same ring as the normal lines.

SWO and ITM (concept, not simulated in Wokwi) let the Cortex-M core send trace bytes over a single pin to the debugger, through the Instrumentation Trace Macrocell. You need a debug probe that supports SWO. Segger RTT (concept, not simulated in Wokwi) is a log buffer in RAM that the debugger reads over the debug link, without a UART. Both need hardware that this course does not have, so the hands-on uses the UART and a no-init buffer. On a real product the same ideas apply: the trace is for the bench, and the no-init record is for the field.

A worked example: the ring, with numbers

The ring in the sample holds 8 lines, and each line is up to 23 characters plus the terminating zero. The struct keeps a head, the index of the slot the next line goes into, and a count, the number of valid lines. Follow ten calls to crash_log_add, numbered 0 to 9, with a ring of 8 slots.

  1. Lines 0 to 7 fill slots 0 to 7. After each call the head moves on by one, so after line 7 the head is 0 again, and the count is 8.
  2. Line 8 goes into slot 0, which held line 0. The head moves to 1. Line 9 goes into slot 1, which held line 1. The head moves to 2. The count stays at 8, because the ring is full.
  3. Now find the oldest kept line. The formula in crash_log_line is (head + LINES - count) % LINES. With head 2, LINES 8 and count 8, the sum is 2 + 8 - 8 = 2, and 2 modulo 8 is 2. The oldest kept line is in slot 2, and that slot holds line 2.
  4. Line index i is in slot (oldest + i) % LINES. For i equal to 7, the slot is (2 + 7) % 8 = 1, which holds line 9, the newest. So the lines come out in order: 2, 3, 4, 5, 6, 7, 8, 9.

The formula has one job, which is to find where the oldest line lives when the ring has wrapped. A ring that has not wrapped has its oldest line in slot 0, and the same formula returns 0 in that case, because the count equals the head. The host tests check both cases. The starter's bug ignores the wrap and returns slot i directly. Its output on the ten-line test is the symptom: the test expects line 2 at index 0, and the starter returns the content of slot 0, which holds line 8. The real starter run prints that exact message. 

test_crash_log.c:50:test_ring_keeps_the_newest_lines:FAIL: Expected 'line 2' Was 'line 8'

The reset reason has a worked number too. When the software reset happens, the SFTRSTF flag is bit 28. One shifted left 28 places is 0x10000000, which is 268435456 in decimal. The host test passes the value 0x10000000 as the reset flags of a simulated second boot, and it reads the same value back from the log's reset_flags field. The test checks the number, not the name, because the RCC register is not on the PC.

Now the whole sequence in the sample. On the first boot, the magic number is random or missing, so crash_log_boot clears the log and returns false. The program prints tick 1, tick 2 and tick 3, and each tick is added to the ring. On the third tick, crash_assert_failed adds the line ASSERT main.c:125 to the ring, prints it, and calls NVIC_SystemReset(). On the second boot, the magic and the indices are valid, so the log is kept, the reset reason shows software-reset, and the program prints the four saved lines before it adds its own. Reading the code, that is the expected output. The simulator has not been observed to produce it, which the warning in the hands-on section explains.

  1. Ten calls to crash_log_add, lines 0 to 9, go into a ring of 8 slots. After the first eight, every slot is used, head has come back to 0 and count is 8.
  2. Line 8 goes into slot 0, replacing line 0, the oldest. head moves to 1.
  3. Line 9 replaces line 1 in slot 1. head is 2, and count stays 8 because the ring is full.
  4. Where is the oldest kept line now? (head + LINES − count) % LINES = (2 + 8 − 8) % 8 = 2. Slot 2, which holds line 2.
  5. Reading line i from slot (oldest + i) % 8 gives the lines in order: 2, 3, 4, 5, 6, 7, 8, 9. The starter read slot i directly, so its first line was line 8, which is what the failing test reports.

The code, line by line

The crash log is a struct, and the header defines it in a few lines. Each field has one purpose: 

typedef struct {
    uint32_t magic;                /* valid only when equal to CRASH_LOG_MAGIC */
    uint32_t boot_count;           /* boots since the log was last cleared */
    uint32_t reset_flags;          /* RCC_CSR reset flags seen at the latest boot */
    uint32_t head;                 /* index of the slot the next line goes into */
    uint32_t count;                /* how many lines are valid, at most CRASH_LOG_LINES */
    char lines[CRASH_LOG_LINES][CRASH_LOG_LINE_LEN];
} crash_log_t;

The magic number is the first check. It is a value unlikely to appear in random RAM by chance, here 0xC0DEFA11. The boot count and the reset flags are the record of each boot, and they are written at every start. The head and the count describe the ring, and the array holds the text. Because the struct is one object, one memset clears all of it, and one attribute places all of it in the no-init section. 

static bool looks_valid(const crash_log_t *log) {
    return log->magic == CRASH_LOG_MAGIC && log->head < CRASH_LOG_LINES && log->count <= CRASH_LOG_LINES;
}

The magic alone can match by chance, so the function also checks that the head and the count are inside the array. A head of 99 cannot come from a working program, and a count above 8 is impossible in an 8-slot ring. The test test_corrupt_indices_are_cleared sets the head to 99 and checks that the log is cleared. 

bool crash_log_boot(crash_log_t *log, uint32_t reset_flags) {
    bool valid = looks_valid(log);
    if (!valid) {
        memset(log, 0, sizeof *log);   /* power-on or corrupt RAM: start empty */
        log->magic = CRASH_LOG_MAGIC;
    }
    log->boot_count++;
    log->reset_flags = reset_flags;
    return valid;
}

crash_log_boot runs once per boot, before anything else logs. If the RAM is valid, it keeps the log. If not, it clears the whole struct and sets the magic, so the next boot will trust it. The boot count always goes up, because it counts boots whether or not the log survived. The function returns the validity, and main uses that result to choose the message it prints. 

void crash_log_add(crash_log_t *log, const char *text) {
    char *slot = log->lines[log->head];
    size_t n = strlen(text);
    if (n > CRASH_LOG_LINE_LEN - 1u) {
        n = CRASH_LOG_LINE_LEN - 1u;     /* cut long lines so the terminator fits */
    }
    memcpy(slot, text, n);
    slot[n] = '\0';

    log->head = (log->head + 1u) % CRASH_LOG_LINES;   /* wrap at the end of the array */
    if (log->count < CRASH_LOG_LINES) {
        log->count++;                          /* the ring fills, then stays full */
    }
}

The function copies the text into the slot under the head, cutting it to 23 characters and adding the terminating zero. The head then moves forward, and the modulo operation wraps it to 0 at the end of the array. The count goes up until the ring is full, and then it stays at 8. Because the count stops, the oldest line is overwritten, which is what a ring should do. 

const char *crash_log_line(const crash_log_t *log, uint32_t i) {
    if (i >= log->count) {
        return NULL;
    }
    uint32_t oldest = (log->head + CRASH_LOG_LINES - log->count) % CRASH_LOG_LINES;
    return log->lines[(oldest + i) % CRASH_LOG_LINES];
}

This is the formula from the worked example. The check at the top returns NULL past the last line, which lets the caller loop until it gets NULL. The + CRASH_LOG_LINES inside the first modulo keeps the subtraction from going negative, because the count can be as large as the array. Without that addition, an unsigned subtraction would wrap to a huge value and the modulo would return a meaningless slot. 

uint32_t flags = RCC->CSR & RESET_FLAGS_MASK;
RCC->CSR |= RCC_CSR_RMVF;

These two lines are the first two statements of main, after the clock setup. The first reads the register and keeps only the reset flags. The second writes 1 to RMVF, which clears the flags in the hardware. The order matters: the read has to come first. After the write, the register reads as zero until the next reset. The mask RESET_FLAGS_MASK combines the six flags the program reports, so the value passed to the log is exactly the reset reason. 

static crash_log_t g_crash_log __attribute__((section(".noinit")));

The declaration is the one shown in the explainer. The static keyword keeps the name inside the file, and the attribute moves the storage out of .bss. The sample's comment in main.c says that the map file must show _ebss before this variable. Check that after each build, because a change to the linker script can move the section.

Common mistakes and how to spot them

Mistake 1: a log in ordinary static memory. The developer writes static crash_log_t g_crash_log;, without the section attribute. The startup code zeroes .bss at every boot, so the magic is zero after every reset. The symptom is a second boot that prints no valid log in RAM, even after a crash. The fix is the .noinit section, and the check is the map file.

Mistake 2: clearing the reset flags before reading them. The developer writes RMVF at the top of main, and then reads the flags. The flags are already cleared, so every boot reports none recorded, which the print function shows when the value is zero. The symptom is that the reason is always missing. The fix is the order in the sample: read first, clear second.

Mistake 3: a ring that ignores the wrap. The developer returns lines[i] directly, as the starter does. The first line printed is then whatever is in slot 0, which is the newest line once the ring has wrapped. The symptom is the out-of-order output in the host test, Expected 'line 2' Was 'line 8'. The fix is the formula with the head and the count. The host test is the evidence, and it should run after every change to the ring.

Mistake 4: trusting the RAM without checks. The developer checks only the magic number, and a random value in the RAM passes by chance on a rare power-on. The symptom is a garbage line in the log, or a count that is larger than the array. The fix is the index check in looks_valid, and the test that writes a bad head and expects the log to be cleared.

Mistake 5: printing from the fault or the interrupt. The developer prints the crash record inside the handler, with printf, to see it faster. Each line takes milliseconds at 115200 baud, and the reset may come before the output is complete. The symptom is a partial report, or a device that reboots before the message ends. The fix is to store the record in the no-init buffer, which costs almost nothing, and to print it on the next boot.

Mistake 6: no build record. The team keeps the log, and throws away the ELF file after each release to save disk space. A field report then names a line that nobody can find in the release. The symptom is an address that decodes to nothing useful. The fix is to archive the ELF and the map for every release, as lesson 84 says.

In real projects

Field diagnostics in a product team are designed up front. The firmware writes the release identifier into the log at boot, so every report names its build. It keeps a boot counter, so a field engineer can see how often the device has restarted. It stores the reset reason, and a short ring of recent events, in no-init RAM. The on-device log is small on purpose: a few hundred bytes is enough to explain most resets. When the bench is available, the same firmware uses a richer trace, such as SWO or RTT, which the field build leaves out.

Reviewers look for the same things. They ask whether the record survives the reset, whether the reset reason is read before it is cleared, whether the ring handles the wrap, and whether the ELF is kept. They also ask what the device does when the record is invalid, because a crash log that is wrong is worse than none.

Summary

  • A compile-time log filter removes debug code from the image. A run-time check still stores the strings and costs time on every call.
  • A UART at 115200 baud sends about 87 microseconds per byte with 8N1 framing, so a log in a timing-critical path is a problem.
  • A ring buffer keeps the newest lines in a fixed array. The oldest line is at (head + LINES - count) % LINES.
  • The startup code clears only .bss, which runs from _sbss to _ebss. A variable in .noinit keeps its value across a reset.
  • RCC_CSR holds the reset flags. SFTRSTF is bit 28, with the mask 0x10000000. Read the flags first, then write RMVF to clear them.
  • Check the magic number and the indices before you trust the RAM, because power-on RAM is random.
  • Keep the ELF and the map file for every release, so that any field address can be decoded later.
