Logging, tracing and field diagnostics

A device in the field cannot be debugged with a cable. Its logs and its reset reason are often the only evidence you get, so design them before the first crash.

By the end of this lesson you can keep the last few log lines in no-init RAM, read the reset reason from RCC_CSR, and print both after a software reset.

Log levels and compile-time filtering

Logs have levels: error, warning, info, debug and trace. A level says how much to keep, and the filter decides what is compiled in. Compile-time filtering is the important part on a small chip. A #if around a debug call removes the string and the call from the image, so it costs no flash and no time, unlike a run-time check that still stores the string. 

#define LOG_LEVEL_ERROR  1
#define LOG_LEVEL_INFO   3
#define LOG_LEVEL        LOG_LEVEL_INFO   /* release build: info and above */

#if LOG_LEVEL >= 4                        /* debug and trace are compiled out below this */
#define LOG_DEBUG(msg) uart_puts(msg)
#else
#define LOG_DEBUG(msg) ((void)0)
#endif
A printf in an interrupt handler can take milliseconds at 115200 baud. Logs in a handler that has a deadline change the behaviour you are trying to observe. Log from the main loop, or into a buffer that the main loop prints.

Binary and deferred logging

Text logs are expensive: every line carries its format string. Binary logging sends a small numeric ID and the raw arguments, and a host program turns them back into text using a table built at compile time. Systems in this family include defmt (Rust) and Trice (C). This course has not checked their current APIs, so read their own documentation before you adopt one. The idea is what matters in an interview: the device sends bytes, the PC does the formatting, and the format strings never cost flash on the device.

A log that survives a reset

A ring of the last few lines is worth more than a long log, because a crash is almost always at the end. The ring must live in RAM that the startup code does not clear. Lesson 78 shows where that RAM sits among the static data, the heap and the stack. The startup clears only .bss (lesson 42), so a variable in a separate section keeps its value across a reset. In GCC that is an attribute: 

static crash_log_t g_crash_log __attribute__((section(".noinit")));

Our linker script has no .noinit output section. GCC emits an orphan .noinit section, and the linker places it after .bss. The build's map file in this project confirms it: .noinit starts at 0x200001bc, which is the same address as _ebss, so the clear loop (which stops at _ebss) does not touch it. A production linker script would give it an explicit NOLOAD output section, so the placement does not depend on the linker's orphan rules.

A power-on reset leaves RAM with random contents, and so the log might look valid by chance. The sample stores a magic number and checks the ring indices before trusting the contents. A checksum is stronger if the log must survive a brown-out.

Reset reason: RCC_CSR on the STM32F1

The STM32F1 reports why it last reset in the RCC control/status register, RCC_CSR (RM0008, the RCC chapter). The flags are set by the reset, and they stay set until you write the RMVF bit to clear them. Read the flags once, at the start of main(), before anything else. The bit names come from the device header (third_party/cmsis-device-f1/Include/stm32f103xb.h):

FlagBitMeaning
LPWRRSTF31Low-power management reset
WWDGRSTF30Window watchdog reset
IWDGRSTF29Independent watchdog reset
SFTRSTF28Software reset (NVIC_SystemReset)
PORRSTF27Power-on or power-down reset
PINRSTF26Reset pin (NRST)
RMVF24Write 1 to clear the flags above

The header defines each flag's mask as 0x1UL << RCC_CSR_..._Pos. The mask for SFTRSTF is 0x10000000, which is what a number quiz in this lesson asks for. Software reset is the reset you request with NVIC_SystemReset(). It is the one the crash log depends on.

Crash dumps, trace and debug output

A crash dump is the state at the fault: the eight stacked words (lesson 84), the fault registers, and the last log lines. The device prints it or stores it, and the PC decode from lesson 84 turns it into source lines.

SWO and ITM (concept, not simulated in Wokwi) let the Cortex-M core send trace bytes over a single pin to the debugger, through the Instrumentation Trace Macrocell. You need a debug probe that supports SWO. Segger RTT (concept, not simulated in Wokwi) is a log buffer in RAM that the debugger reads over the debug link, without a UART. Both need hardware that this course does not have, so the hands-on uses the UART and a no-init buffer.

"A customer reports that a device restarted on its own last week. How do you find out why?" Answer out loud in 60 seconds, then compare.

Model answer

First I ask the device for its reset reason: the RCC flags tell me software, watchdog, power-on or pin. A watchdog reset points at a hang, so I look for the last check-in and the task that did not report. A software reset points at an assertion or a fault handler, so I read the crash log that survived in no-init RAM: the file and line, the last log lines, and the HardFault dump if there is one. I decode any stacked PC with addr2line, using the .elf from exactly that release. If the logs are not enough, I ask for a reproduction with a debug build, and I make sure the next release logs more where the customer's device failed.
