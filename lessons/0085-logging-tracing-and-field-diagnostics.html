Logging, tracing, and field diagnostics

Evidence that survives a reset

By the end of this lesson you can keep the last few log lines in no-init RAM, read the reset reason from RCC_CSR, and print both after a software reset.

Evidence from a reset nobody watched

Lesson 84 ended with a fault that prints its own address, which helps only while the device is on your bench. The harder question concerns a device that reset last Tuesday with nobody watching, what it did before the reset and why the reset happened, which requires the answer to be stored somewhere that survives the reset and the reset itself to leave a trace. This lesson covers those two things together with the memory layout from lesson 78 that makes the first possible.

A typical case is a support ticket reporting that a controller restarted during the night, the support engineer having nothing but the device's log, a short text printed over a serial port in the lab, and the release number. Firmware designed for this keeps the last few lines before the restart in the log, a reset reason saying whether a watchdog, a software reset or a power loss caused it, and a release ELF file that turns any address into a line of source, whereas without that design the ticket is closed as "cannot reproduce".

The lesson covers how logs are filtered and what they cost, how a log stays in RAM across a reset, how the reset reason is read from a register, and how the crash record and the trace tools fit together, and the hands-on task puts the first three into one small program.

Log levels and compile-time filtering

A log is a line of text the firmware writes to explain what it is doing, and its level says how important it is, from error, warning and info down to debug and trace. A level acts as a threshold, a build keeping the lines at or above it and dropping the rest, so a release build of a small device usually keeps errors, warnings and information while dropping debug and trace.

On a small chip the important question is where the filter runs. A run-time filter is an if checking the level when the program reaches the log call, so the string and the call stay in the flash image, costing flash, and the check costs time on every call, whereas a compile-time filter uses the preprocessor, a #if around a debug call removing the string and the call from the image before it is built, so the removed code costs neither flash nor time. The example below takes that approach. 

#define LOG_LEVEL_ERROR  1
#define LOG_LEVEL_INFO   3
#define LOG_LEVEL        LOG_LEVEL_INFO   /* release build: info and above */

#if LOG_LEVEL >= 4                        /* debug and trace are compiled out below this */
#define LOG_DEBUG(msg) uart_puts(msg)
#else
#define LOG_DEBUG(msg) ((void)0)
#endif

With LOG_LEVEL set to info, the number is 3, so the test LOG_LEVEL >= 4 is false and LOG_DEBUG expands to ((void)0), a statement doing nothing that the compiler removes, so the string never reaches the image, while changing the level to 4 brings the debug calls and their strings back in the next build.

The time cost of a serial log line

Cost matters because the serial port is slow, a UART sending each byte as a frame of one start bit, eight data bits and one stop bit, ten bit times on the wire with the usual 8N1 format, so the byte rate is

bytes per second = baud rate ÷ bits per frame = 115 200 ÷ 10 = 11 520(1)

where the baud rate is the number of bits per second on the line and the frame has 10 bits, giving about 87 µs per byte. A 40-character line therefore takes about 3.5 ms to leave the chip however fast the printing code is, which makes the serial port a poor place for a log in a timing-critical path and explains the warning below.

A printf in an interrupt handler can take milliseconds at 115200 baud. Logs in a handler that has a deadline change the behaviour you are trying to observe. Log from the main loop, or into a buffer that the main loop prints.

Binary and deferred logging

Text logs are expensive in flash, because every line carries its format string, whereas binary logging sends a small numeric ID and the raw argument values, which a host program turns back into text using a table the build creates. Systems in this family include defmt (Rust) and Trice (C), whose current APIs this course has not checked, so their own documentation should be read before adopting one.

A second idea is deferred logging, in which the handler or critical code only copies a record into a buffer that the main loop prints later, so the buffer costs RAM and the copy a little time while the slow part, the UART, runs where its delay does not matter. The crash log of this lesson is a deferred log in its simplest form, its contents kept in memory and printed only after the reset.

A ring buffer in no-init RAM

A crash almost always lies at the end of a log, so the part worth keeping is its last few lines, which a ring buffer (glossary: ring buffer) holds, a fixed array with a write position wrapping back to the start at the end, keeping the newest lines and overwriting the oldest, with a size fixed at build time, so its RAM cost is known.

The ring must live in RAM that the startup code does not clear. Lesson 78 showed where that RAM sits among the static data, the heap and the stack, and lesson 42 what the startup code does before main, copying .data from flash and clearing .bss, the zero-initialised variables, in a loop running from the symbol _sbss up to _ebss, so a variable placed in a different section lies outside that range and keeps its value across a reset. In GCC the section is set with an attribute. 

static crash_log_t g_crash_log __attribute__((section(".noinit")));

The attribute puts the variable in a section named .noinit, which the project's linker script does not name, so GCC emits an orphan section, one the linker script does not mention, and the linker places it after the sections it knows. The map file of this build shows the .noinit section starting at 0x200001bc, the same address as _ebss, so the log lies outside the range the clear loop covers, whereas a production linker script would give the section its own output section, marked as not loaded, so that its placement does not depend on the linker's orphan rules.

A log in RAM that survives a reset resembles an aircraft's flight recorder, keeping the last moments in a place the crash does not destroy so that investigators can read them afterwards, the place here being a RAM section the startup code does not clear and the investigator the firmware after the reboot. The comparison breaks on power loss, though, because a flight recorder is built to survive any crash, whereas no-init RAM loses its contents when the supply fails, so a power cut leaves nothing to read.

Power-on RAM holds random contents, so a log could look valid by chance, which is why the sample stores a magic number and checks the ring indices before trusting the contents, and a checksum is stronger if the log must survive a brown-out, a dip in the supply voltage that does not fully reset the chip.

Reset flags in RCC_CSR on the STM32F1

The STM32F1 reports why it last reset in the RCC control and status register, RCC_CSR (glossary: reset reason), each reset setting a flag for its source, which stays set until software writes the RMVF bit to clear it, so a reset can be read after it happens (RM0008 Rev 21, section 7.3.10). The reference manual RM0008 describes the register in that section of its RCC chapter, and the bit positions below are read from the device header third_party/cmsis-device-f1/Include/stm32f103xb.h used by the course build, matching the register description.

FlagBitMeaning
LPWRRSTF31Low-power management reset
WWDGRSTF30Window watchdog reset
IWDGRSTF29Independent watchdog reset
SFTRSTF28Software reset (NVIC_SystemReset)
PORRSTF27Power-on or power-down reset
PINRSTF26Reset pin (NRST)
RMVF24Write 1 to clear the flags above

The header defines each flag's mask as 0x1UL << RCC_CSR_..._Pos. The mask for SFTRSTF is 0x10000000, which is what a number quiz in this lesson asks for. The order of operations matters, the register being read once at the start of main(), before anything else clears it, and RMVF written afterwards, so that the next boot shows only its own reset. A software reset is the one the crash log depends on, because NVIC_SystemReset() is the request the handler and the assertion make, after which the chip resets, the SFTRSTF flag is set and the log in RAM remains to be read.

Crash dumps, SWO, ITM and RTT

A crash dump is the state at the fault, the eight stacked words (lesson 84), the fault registers and the last log lines, which the device prints or stores and which the PC decode of lesson 84 turns into source lines. The crash log of this lesson is a small dump, recording the failing assertion's file and line in the same ring as the normal lines.

SWO and ITM (concept, not simulated in Wokwi) let the Cortex-M core send trace bytes over a single pin to the debugger through the Instrumentation Trace Macrocell, which needs a debug probe supporting SWO, while Segger RTT (concept, not simulated in Wokwi) is a log buffer in RAM that the debugger reads over the debug link without a UART. Both need hardware this course does not have, so the hands-on uses the UART and a no-init buffer, and on a real product the same ideas apply, the trace serving the bench and the no-init record the field.

Worked example: ten lines in an eight-slot ring

The ring in the sample holds 8 lines of up to 23 characters plus the terminating zero, its struct keeping a head, the index of the slot the next line goes into, and a count, the number of valid lines. We follow ten calls to crash_log_add, numbered 0 to 9, and before reading on, predict which line comes out first after the ring has wrapped.

  1. Fill the ring. Lines 0 to 7 fill slots 0 to 7, the head moving on by one after each call, so after line 7 the head is 0 again and the count is 8.
  2. Wrap. Line 8 goes into slot 0, overwriting line 0, and moves the head to 1, then line 9 goes into slot 1, overwriting line 1, and moves it to 2, while the count stays at 8, because the ring is full.
  3. Find the oldest line. The formula in crash_log_line is (head + LINES - count) % LINES, which with head 2, LINES 8 and count 8 gives 2 + 8 - 8 = 2 and 2 modulo 8 = 2, so the oldest kept line, line 2, is in slot 2.
  4. Read in order. Line index i lies in slot (oldest + i) % LINES, so for i = 7 the slot is (2 + 7) % 8 = 1, holding line 9, the newest, and the lines come out in the order 2, 3, 4, 5, 6, 7, 8, 9.

The formula's one job is to find the oldest line once the ring has wrapped, and for a ring that has not wrapped, whose oldest line is in slot 0, it returns 0, because the count equals the head, the host tests checking both cases. The starter's bug ignores the wrap and returns slot i directly, so on the ten-line test, which expects line 2 at index 0, it returns the content of slot 0, line 8, the exact message the real starter run prints. 

test_crash_log.c:50:test_ring_keeps_the_newest_lines:FAIL: Expected 'line 2' Was 'line 8'

The reset reason has a worked number too, the software-reset flag SFTRSTF being bit 28, so one shifted left 28 places gives 0x10000000, 268 435 456 in decimal. The host test passes 0x10000000 as the reset flags of a simulated second boot and reads the same value back from the log's reset_flags field, checking the number rather than the name, because the RCC register does not exist on the PC.

The whole sequence of the sample runs as follows. On the first boot the magic number is random or missing, so crash_log_boot clears the log and returns false, the program prints tick 1, tick 2 and tick 3, adding each to the ring, and on the third tick crash_assert_failed adds the line ASSERT main.c:125 to the ring, prints it and calls NVIC_SystemReset(). On the second boot the magic and the indices are valid, so the log is kept, the reset reason shows software-reset and the program prints the four saved lines before adding its own, which is the output expected from reading the code, though the simulator has not been observed to produce it, as the warning in the hands-on section explains.

  1. Ten calls to crash_log_add, lines 0 to 9, go into a ring of 8 slots. After the first eight, every slot is used, head has come back to 0 and count is 8.
  2. Line 8 goes into slot 0, replacing line 0, the oldest. head moves to 1.
  3. Line 9 replaces line 1 in slot 1. head is 2, and count stays 8 because the ring is full.
  4. Where is the oldest kept line now? (head + LINES − count) % LINES = (2 + 8 − 8) % 8 = 2. Slot 2, which holds line 2.
  5. Reading line i from slot (oldest + i) % 8 gives the lines in order: 2, 3, 4, 5, 6, 7, 8, 9. The starter read slot i directly, so its first line was line 8, which is what the failing test reports.

The crash log code line by line

The crash log is a struct that the header defines in a few lines, each field having one purpose. 

typedef struct {
    uint32_t magic;                /* valid only when equal to CRASH_LOG_MAGIC */
    uint32_t boot_count;           /* boots since the log was last cleared */
    uint32_t reset_flags;          /* RCC_CSR reset flags seen at the latest boot */
    uint32_t head;                 /* index of the slot the next line goes into */
    uint32_t count;                /* how many lines are valid, at most CRASH_LOG_LINES */
    char lines[CRASH_LOG_LINES][CRASH_LOG_LINE_LEN];
} crash_log_t;

The magic number, 0xC0DEFA11, is the first check, a value unlikely to appear in random RAM, the boot count and the reset flags record each boot and are written at every start, and the head and the count describe the ring whose array holds the text. Because the struct is one object, a single memset clears all of it and a single attribute places all of it in the no-init section. 

static bool looks_valid(const crash_log_t *log) {
    return log->magic == CRASH_LOG_MAGIC && log->head < CRASH_LOG_LINES && log->count <= CRASH_LOG_LINES;
}

The magic alone can match by chance, so the function also checks that the head and the count lie inside the array, since a head of 99 cannot come from a working program and a count above 8 is impossible in an 8-slot ring, and the test test_corrupt_indices_are_cleared sets the head to 99 and checks that the log is cleared. 

bool crash_log_boot(crash_log_t *log, uint32_t reset_flags) {
    bool valid = looks_valid(log);
    if (!valid) {
        memset(log, 0, sizeof *log);   /* power-on or corrupt RAM: start empty */
        log->magic = CRASH_LOG_MAGIC;
    }
    log->boot_count++;
    log->reset_flags = reset_flags;
    return valid;
}

crash_log_boot runs once per boot, before anything else logs, keeping the log if the RAM is valid and otherwise clearing the whole struct and setting the magic, so the next boot will trust it. The boot count always goes up, counting boots whether or not the log survived, and the function returns the validity, which main uses to choose the message it prints. 

void crash_log_add(crash_log_t *log, const char *text) {
    char *slot = log->lines[log->head];
    size_t n = strlen(text);
    if (n > CRASH_LOG_LINE_LEN - 1u) {
        n = CRASH_LOG_LINE_LEN - 1u;     /* cut long lines so the terminator fits */
    }
    memcpy(slot, text, n);
    slot[n] = '\0';

    log->head = (log->head + 1u) % CRASH_LOG_LINES;   /* wrap at the end of the array */
    if (log->count < CRASH_LOG_LINES) {
        log->count++;                          /* the ring fills, then stays full */
    }
}

The function copies the text into the slot under the head, cutting it to 23 characters and adding the terminating zero, then moves the head forward, the modulo wrapping it to 0 at the end of the array, while the count rises until the ring is full and then stays at 8, so the oldest line gets overwritten, as a ring should. 

const char *crash_log_line(const crash_log_t *log, uint32_t i) {
    if (i >= log->count) {
        return NULL;
    }
    uint32_t oldest = (log->head + CRASH_LOG_LINES - log->count) % CRASH_LOG_LINES;
    return log->lines[(oldest + i) % CRASH_LOG_LINES];
}

This is the formula of the worked example, the check at the top returning NULL past the last line, which lets the caller loop until it gets NULL. The + CRASH_LOG_LINES inside the first modulo keeps the subtraction from going negative, because the count can be as large as the array, and without it an unsigned subtraction would wrap to a huge value and the modulo would return a meaningless slot. 

uint32_t flags = RCC->CSR & RESET_FLAGS_MASK;
RCC->CSR |= RCC_CSR_RMVF;

These two lines are the first statements of main after the clock setup, the first reading the register and keeping only the reset flags and the second writing 1 to RMVF, which clears the flags in the hardware, so the read must come first, since after the write the register reads as zero until the next reset. The mask RESET_FLAGS_MASK combines the six flags the program reports, so the value passed to the log is exactly the reset reason. 

static crash_log_t g_crash_log __attribute__((section(".noinit")));

The declaration is the one shown earlier, the static keyword keeping the name inside the file while the attribute moves the storage out of .bss. The sample's comment in main.c says that the map file must show _ebss before this variable, which should be checked after each build, because a change to the linker script can move the section.

Common mistakes and how to spot them

A log in ordinary static memory

The second boot prints no valid log in RAM even after a crash, because the developer wrote static crash_log_t g_crash_log; without the section attribute, and the startup code zeroes .bss at every boot, so the magic is zero after every reset. Place the log in the .noinit section and confirm the placement in the map file.

Reset flags cleared before they are read

Every boot reports none recorded, which the print function shows for a zero value, because the developer writes RMVF at the top of main and reads the flags afterwards, when they are already cleared. Keep the order of the sample, reading first and clearing second.

A ring that ignores the wrap

The host test shows out-of-order output, Expected 'line 2' Was 'line 8', because the code returns lines[i] directly, as the starter does, so the first line printed is whatever slot 0 holds, the newest line once the ring has wrapped. Use the formula with the head and the count, and run the host test, the evidence, after every change to the ring.

RAM trusted without checks

A garbage line appears in the log, or a count larger than the array, because only the magic number was checked and a random RAM value matched it by chance on a rare power-on. Add the index check of looks_valid and the test that writes a bad head and expects the log to be cleared.

Printing from the fault or the interrupt

The report comes out partial, or the device reboots before the message ends, because the developer printed the crash record inside the handler with printf to see it sooner, and each line takes milliseconds at 115 200 baud. Store the record in the no-init buffer, which costs almost nothing, and print it on the next boot.

No build record kept

A field address decodes to nothing useful, because the team kept the logs but threw away the ELF file after each release to save disk space, so a reported line cannot be found in the release. Archive the ELF and the map of every release, as lesson 84 says.

Field diagnostics designed into products

Product teams design field diagnostics up front, the firmware writing the release identifier into the log at boot, so that every report names its build, keeping a boot counter, so that a field engineer can see how often the device has restarted, and storing the reset reason and a short ring of recent events in no-init RAM. The on-device log is small on purpose, a few hundred bytes explaining most resets, while on the bench the same firmware uses a richer trace such as SWO or RTT, which the field build leaves out.

Reviewers ask whether the record survives the reset, whether the reset reason is read before it is cleared, whether the ring handles the wrap and whether the ELF is kept, and also what the device does when the record is invalid, because a crash log that is wrong is worse than none.

Summary

  • A compile-time log filter removes debug code from the image, whereas a run-time check still stores the strings and costs time on every call.
  • A UART at 115 200 baud with 8N1 framing takes about 87 µs per byte, so a log in a timing-critical path is a problem.
  • A ring buffer keeps the newest lines in a fixed array, its oldest line lying at (head + LINES - count) % LINES.
  • The startup code clears only .bss, from _sbss to _ebss, so a variable in .noinit keeps its value across a reset.
  • RCC_CSR holds the reset flags, SFTRSTF being bit 28 with the mask 0x10000000, and the flags are read first and then cleared by writing RMVF.
  • The magic number and the indices are checked before the RAM is trusted, because power-on RAM is random.
  • The ELF and the map file of every release are kept, so that any field address can be decoded later.
