Mutexes, priority inversion and deadlock

A well-known RTOS bug was a spacecraft that kept resetting on Mars, caused by a high-priority task waiting for a low-priority one while a medium-priority task ran. The fix was a single setting on a mutex. This lesson shows the bug in the simulator, the fix on the Blue Pill, and how to avoid deadlock.

By the end of this lesson you can explain priority inversion with three tasks, show it in UART output, fix it by using a mutex with priority inheritance, and state a lock-ordering rule that prevents deadlock.

Where we are, and why it matters

Lesson 90 moved data and signals between tasks, and it used a mutex to keep log lines from mixing on the UART. It said that a mutex is not a binary semaphore, without saying why. This lesson explains the difference, and it covers the failure that the difference prevents. Lab 5 protects the I2C bus with a mutex, because the sensor task and the UI task both use it, and the same rule applies there.

This bug affects real devices. A shared bus or a shared log that two tasks touch with different priorities can make the most urgent task wait for the least urgent one. On a device that resets or misses a sample under that condition, the bug can look like a hardware fault, and it can pass every test that runs the tasks one at a time.

Concept 1: a mutex is a lock with an owner

A mutex is a lock: at most one task holds it at a time, and a task that tries to take it while it is held waits. A critical section is the code that must not run in two places at once, such as an update of a shared structure, and the mutex is how a task protects one.

FreeRTOS builds a mutex from the queue machinery. In queue.c at line 647, xQueueCreateMutex() calls xQueueGenericCreate() with a length of 1 and an item size of 0. The queue holds a token, not data: taking the mutex removes the token, and giving it back puts the token in. The difference from a binary semaphore is that the kernel also records the owner, the task that took the token, in the queue's xMutexHolder field. Only the owner is supposed to give the token back. That one extra field makes the next idea possible.

Concept 2: priority inheritance

Priority inheritance is the rule that while a high-priority task waits on a mutex, the owner runs at the waiter's priority. The owner is the only task the kernel can help, because the kernel knows who it is. In FreeRTOS, when a task blocks on a mutex, the queue code calls xTaskPriorityInherit() (queue.c line 1791 calls it, and it is defined in tasks.c at line 6639). The owner's priority is raised to the waiter's. When the owner gives the mutex back, xTaskPriorityDisinherit() (tasks.c line 6742) restores its original priority.

The effect is that no task of a middle priority can preempt the owner, because the owner now outranks them. A binary semaphore has no owner, so the kernel has no task to raise, and it cannot do this. That is the difference between the two objects, and the table below sets them side by side.

Concept 3: priority inversion

Priority inversion is the bug that inheritance prevents. A high-priority task H waits for a resource held by a low-priority task L. A medium-priority task M is ready and does not need the resource. Because M outranks L, L cannot run, so H waits for M, which has nothing to do with the resource. The higher task is in effect running at the lowest level. The glossary entry calls it a bounded but unjustified wait, which is a precise way to describe a delay that is not a deadlock and not starvation.

A junior worker holds the only key to the store room. The manager needs the key and waits. Meanwhile a mid-level colleague keeps the junior busy with other jobs, so the manager ends up waiting for the colleague, who has nothing to do with the store room. Priority inheritance gives the junior the manager's rank while they hold the key, so nobody below the manager can keep them busy.

The project projects/0091-priority-inversion reproduces this. Low (priority 1) takes the resource and holds it for 200 ms. Medium (priority 2) starts at 20 ms and runs for 300 ms. High (priority 3) starts at 50 ms and needs the resource for 10 ms. The controller, at priority 4, runs the two phases in turn. Phase 1 uses a binary semaphore as the lock. Phase 2 uses a mutex.

A worked example with real numbers

The project's timings are easiest to follow by stepping through each phase. The tasks do not sleep while they hold or wait. They busy-wait on the tick count, which keeps them Ready, so a higher-priority task can take the core from them. That detail changes the numbers, so read the steps with it in mind.

Phase 1, binary semaphore. At 0 ms, low takes the semaphore and starts a busy-wait for 200 ms. At 20 ms, medium becomes ready with a higher priority than low, so it takes the core. Low is preempted and stops. At 50 ms, high wakes and asks for the semaphore. It is held, so high blocks. The semaphore has no owner, so the kernel does not raise low's priority, and medium keeps running. Medium's 300 ms busy-wait started at 20 ms, so it ends at 320 ms. Only then does low get the core back. Its 200 ms busy-wait is measured in elapsed ticks since 0 ms, and 320 ms have passed, so low's critical section ends at once, and it releases the semaphore at 320 ms. High takes it at 320 ms. High waited 320 − 50 = 270 ms.

Phase 2, mutex. The sequence is the same until 50 ms. At 0 ms low takes the mutex, and it runs until 20 ms, when medium preempts it. At 50 ms high asks for the mutex and blocks. The kernel sees the owner and raises low's priority to 3, the same as high. Medium has priority 2, which is now lower than low, so medium cannot take the core back. Low runs from 50 ms, and its elapsed time reaches 200 ms at 200 ms. It releases the mutex. Its priority falls back to 1, high takes the mutex at 200 ms, and it has waited 200 − 50 = 150 ms.

The two results differ by a single line of code in the controller, and the difference is the length of time that medium holds the core, not any change to high. In phase 1 high waits for medium's whole run. In phase 2 high waits only for low's own hold time. The fix bounds the wait by the holding time of the resource, which is the best a design can do without changing the critical section.

Step through both phases on the timeline. The numbers are the project's: low holds the lock for 200 ms, medium runs for 300 ms, high needs it for 10 ms. Switch between the semaphore and the mutex and compare how long high waits, then change the times and predict the wait before you look.

The fix: a mutex

Phase 2 changes the constructor: xSemaphoreCreateMutex() in place of xSemaphoreCreateBinary(), and the give that makes the binary semaphore available is deleted, because a mutex is available when it is created. The take and give calls in the tasks are the same. The owner is recorded, so when high blocks, the kernel raises low's priority, and medium can no longer preempt it. The starter's phase 2 deliberately keeps the binary semaphore, so the output ends with PI NOT FIXED.

Do not use a mutex in an interrupt, and do not use a binary semaphore to protect shared data. A common mistake is "a semaphore is a lock too", which is true in the simplest sense and wrong for priority inversion.

Deadlock and lock ordering

Deadlock is a cycle of waiting. Task 1 holds lock A and waits for B. Task 2 holds B and waits for A. Neither can proceed, and no timeout is involved unless one is written. Four conditions must hold together, in the classic analysis of the problem: mutual exclusion, hold and wait, no preemption of a lock, and a circular wait. A design removes deadlock by breaking one of them. The simplest is the circular wait, with a lock ordering rule: every task takes locks in the same global order, for example always A before B. If every task obeys it, no cycle can form.

Two people need both the store-room key and the office key. One picks up the store-room key, the other the office key, and each waits for the other's. Neither ever moves. The rule that prevents it is simple: everyone picks up the keys in the same order.

  • Take locks in a fixed order, and document the order next to the locks.
  • Hold each lock for as short a time as possible; never call a blocking function inside a critical section.
  • Use timeouts on lock takes in code that might be stuck, and handle the timeout as an error, not as a retry loop.

A plain FreeRTOS mutex is not recursive. A task that takes a mutex it already holds waits for itself, and it never returns. If a function that needs the lock is called by another function that already holds it, the design needs a recursive mutex, which the kernel provides through xSemaphoreTakeRecursive() (the API is documented in semphr.h). Most code is better off with one lock and one path, so that the question does not come up.

Common mistakes and how to spot them

Mistake 1: a binary semaphore used as a lock. A developer protects the UART with a binary semaphore, because it looks the same in the code. The symptom is the phase-1 pattern: a high-priority task waits for a long time whenever a medium task runs. In this project that is 270 ms. The fix is xSemaphoreCreateMutex(), with the same take and give calls.

Mistake 2: taking a mutex from an interrupt. An ISR takes the UART mutex to print a fault. The symptom is an assertion or a hang, because the take may block and an interrupt cannot block. The fix is to set a flag or queue the event in the ISR, and let a task take the mutex and print.

Mistake 3: an early return that keeps the lock. A function takes the mutex, hits an error, returns, and never gives it back. The symptom is that the next task to take the mutex waits forever, often at portMAX_DELAY, and the system looks stuck. The fix is one exit path that always gives the mutex, or a timeout on each take so that the stuck task reports an error.

Mistake 4: two tasks taking two locks in opposite orders. Task 1 takes the sensor mutex and then the bus mutex, and task 2 takes the bus mutex and then the sensor mutex. The symptom is that the device stops at a random moment, and every task waiting on one of the two is blocked. The fix is a documented global order, such as always the sensor first.

Mistake 5: a mutex for data an interrupt also touches. A developer protects a counter with a mutex, and an ISR increments the same counter. The symptom is a count that is sometimes one short. A mutex cannot be taken in the ISR, so it does not protect the counter. The fix is a critical section, which masks interrupts for the short update, or a design where the ISR only sets a flag that the task reads.

A historical case: Mars Pathfinder

In July 1997 the Mars Pathfinder lander landed on Mars, and a few days into its mission it began to reset repeatedly, each reset losing data. Mike Jones, writing on 7 December 1997 about a keynote by David Wilner of Wind River Systems, described the cause in the RISKS Digest (volume 19, issue 49). The spacecraft ran VxWorks, a preemptive priority kernel. A high-priority bus management task shared a mutex with a low-priority meteorological task. A medium-priority communications task did not use the mutex, but it could preempt the low task while the low task held the mutex. The high task then waited for the medium task's run, which is the inversion this lesson shows.

Jones's account says that the mutex had been created with priority inheritance turned off. Had it been on, the low task would have inherited the high task's priority while it held the mutex, and the medium task could not have preempted it. The fix was to change the value that controlled that mutex. Jones reports that the JPL engineers used the VxWorks C interpreter, which had been left enabled on the spacecraft, to upload a short program that changed the flag from FALSE to TRUE. The resets stopped. Jones credits the three authors of the priority inheritance paper, L. Sha, R. Rajkumar and J. P. Lehoczky, with first describing the problem and its solution. A reply in the next issue, by Bob Rahe, dates that paper to 1990 and points out that an earlier mainframe operating system had a similar locking scheme. Read the original post for the details, and read it as one account of a talk, not as the team's own record.

The post is in the RISKS Digest, volume 19, issue 49. Its author reports a talk and the engineers' analysis as he understood it, so compare it with other accounts before you quote a detail.

In real projects

Teams keep a list of every mutex in the system, with its owner tasks and the order in which locks are taken, and they review any change that adds a lock. A common review question is what a function does while it holds the lock, because a call to a slow bus or a blocking queue inside the lock is a common source of long waits. In the Lab 5 design, the I2C mutex is held only across the bus transfer, never across a delay or a queue send, for exactly this reason.

Summary

  • A mutex is a lock with an owner, built from a length-1 queue of zero-byte items. Only the owner gives it back.
  • Priority inheritance raises the owner to the priority of the highest waiter while it holds the mutex, and restores it on give.
  • Priority inversion is a high-priority task waiting for a low-priority owner while a medium task runs. A binary semaphore cannot fix it, because it has no owner.
  • In the project, phase 1 gives high a wait of 270 ms, and phase 2 with a mutex gives 150 ms.
  • Deadlock needs a circular wait. A global lock order breaks it.
  • A plain mutex is not recursive, and a mutex cannot be taken from an interrupt.
