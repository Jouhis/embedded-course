Startup code and the vector table

Before your main() runs, a short piece of assembly prepares RAM, zeroes your globals and calls the clock setup. You can read every step of it in the files this course uses.

By the end of this lesson you can list what happens between reset and main() on an STM32F103 and an RP2040, and find the vector table entries and the copy and clear loops in the startup source.

The idea

On reset the core reads two words from the start of memory: the initial stack pointer and the address of the reset handler. The vector table is the array of such addresses, one per exception, and the core reads it at its base address. The table is just data at a fixed place, so the startup code and the linker script have to agree on where it is. The reset handler runs in Thread mode with the main stack, as the ST startup file's header says. The architecture course's exception model (lesson 34) explains why these two words are enough to start the core.

Nothing runs until the core jumps to the reset handler. Your C variables are then in an unknown state: .data is still in flash, and .bss still holds whatever was in RAM before. The startup code fixes both before it calls main().

The STM32F103 vector table

The startup file is third_party/cmsis-device-f1/Source/Templates/gcc/startup_stm32f103xb.s. Its table begins with two entries, then the handlers in numeric order: 

g_pfnVectors:
  .word _estack            /* word 0: initial stack pointer */
  .word Reset_Handler      /* word 1: first code to run */
  .word NMI_Handler
  .word HardFault_Handler
  .word MemManage_Handler
  .word BusFault_Handler
  .word UsageFault_Handler

The file is long because it lists every interrupt the part can take, and the unused entries are .word 0 or the default handler. The last entry is BootRAM, which the comment places at offset 0x108. The linker placed the table at 0x08000000 with a size of 0x10C bytes in the lab 2 build (blink.map), which is 67 words.

The dumped words in the same build confirm the layout. Word 0 is 0x20005000, the top of the 20 kB RAM. Word 1 is 0x080002F1, which is Reset_Handler at 0x080002F0 with the Thumb bit set. Other handler words point at Default_Handler, an infinite loop. The Thumb bit is why an address that is even in the map appears odd in the table: an instruction address in Thumb state has bit 0 set.

What Reset_Handler does

The reset handler in the same file does four things, in this order, before it calls the C library and your code:

  1. Call SystemInit. The clock setup from lesson 40 runs first, so the chip is at its final clock before any data is copied.
  2. Copy .data from flash to RAM. A loop copies from _sidata (the load address) to _sdata, until _edata. This is where the initial values of your initialised globals come from.
  3. Zero .bss. A loop writes 0 from _sbss up to _ebss, so every zero-initialised global starts at 0, as C requires.
  4. Call __libc_init_array, then main. The C library runs the static constructors, and then your program starts.

The symbols _sidata, _sdata, _edata, _sbss and _ebss come from the linker script. The startup file does not know the addresses. It reads them, and the linker script places them. That is the link between lesson 41 and this lesson.

If the copy loop used the wrong load address, every initialised global would start with garbage, and the bug would show before main() runs. This is why the startup file and the linker script must be written together, and why you check _sidata in the map file when a global has an odd starting value.

The RP2040 version

The RP2040 has the same job, done in the Pico SDK's crt0.S (pico-sdk 2.3.1, src/rp2_common/pico_crt0/crt0.S). Its vector table starts with __StackTop and _reset_handler. On the RP2040, the table's reserved slots for MemManage, BusFault and UsageFault are isr_invalid, because the M0+ has only HardFault. The reset handler copies the data sections from a table of source and destination addresses, zeroes __bss_start__ to __bss_end__, then calls runtime_init, main and exit.

One difference matters for interviews. The SDK's runtime_init does not call __libc_init_array. In the newlib interface it runs the preinit and init arrays itself, and the comment there says the full __libc_init_array also runs steps such as register_tm_clones, which earlier SDKs did not run. The STM32 startup calls __libc_init_array directly.

The RP2040 also boots through the bootrom and the second-stage bootloader before any of this. RP2040 datasheet, section 2.8.1 (Processor Controlled Boot Sequence) lists the steps the bootrom takes before it jumps into your image.

Try it in Wokwi

The project projects/0042-startup-code is a single demo. Its two globals are volatile, so the compiler cannot fold their values into constants. The demo prints what it finds at main(), and the linker symbols.

  1. Open projects/0042-startup-code in VS Code, build with Ctrl+Shift+B, and start the simulator with F5 to debug.
  2. Set a breakpoint on Reset_Handler, and continue. Step over SystemInit to see the data copy begin.
  3. Let the program run to main. The serial output should show g_copied at main(): 0x0000CAFE and g_cleared at main(): 0x00000000.
  4. Compare the linker symbol lines with the map file. _sidata should be 0x080004E0 in this build, _sdata is 0x20000000, and _ebss is 0x20000028.
Hint

If the breakpoint on Reset_Handler does not stop, look up its address with arm-none-eabi-nm -n build/blink | grep Reset_Handler. The debugger should stop at 0x080002F0.

"What happens between reset and main() on a Cortex-M microcontroller?" Answer out loud in 60 seconds, then compare.

Model answer

The core loads the initial stack pointer and the reset vector from the start of the vector table, then jumps to Reset_Handler. The handler calls SystemInit to set the clock, copies the initial values of the .data section from flash to RAM, zeroes .bss, and calls the C library's initialisers. Only then does it call main. The copy and clear use symbols from the linker script, so the startup code and the script must match.

RP2040 datasheet: read sections 2.7 (Boot Sequence) and 2.8.1 (Processor Controlled Boot Sequence). They list the steps before your code runs on the RP2040, which the Pico SDK's crt0.S then continues.
