Startup code and the vector table

Before your main() runs, a short piece of assembly prepares RAM, zeroes your globals and calls the clock setup. You can read every step of it in the files this course uses.

By the end of this lesson you can list what happens between reset and main() on an STM32F103 and an RP2040, and find the vector table entries and the copy and clear loops in the startup source.

Where we are and why it matters

Lesson 41 showed that the linker places .data in RAM while storing its starting values in flash, and that it defines symbols such as _sidata and _sdata for the start and end of that copy. Lesson 34 showed what the core does when an exception arrives. This lesson joins the two. Something must perform the copy, and something must tell the core where to begin. Both jobs belong to the startup code, and the vector table is the first thing it hands the core.

A startup problem often shows up first in a debugging session. A global counter starts with the value 7 in your code, but the variable reads 0x4F or some other junk when main() begins. The build looks correct, and the symptom appears only on the chip. The cause is almost always in the startup path: a copy loop that uses the wrong address, a clear loop that misses part of .bss, or a vector table that the core cannot find. Engineers who know this path can usually find such bugs quickly.

What the core does at reset

On reset the core reads two words from the start of its vector table. The first word is the initial stack pointer. The second word is the address of the reset handler, the first code to run. The table is an array of such addresses, one per exception. The STM32 startup file's own comment says the table must end up at physical address 0x00000000, which is where the chip's flash is aliased after reset. The linker places the table at the start of flash for that reason (lesson 41).

Nothing in your program has run yet at that point. Your C variables are in an unknown state: .data is still in flash, and .bss still holds whatever was in RAM before the reset. The reset handler fixes both before it calls main(). The startup file, the linker script and the vector table must agree on every address, because the code reads them through symbols.

The STM32F103 vector table

The startup file is third_party/cmsis-device-f1/Source/Templates/gcc/startup_stm32f103xb.s. Its table begins with two entries, then the core's handlers in order: 

g_pfnVectors:
  .word _estack            /* word 0: initial stack pointer */
  .word Reset_Handler      /* word 1: first code to run */
  .word NMI_Handler        /* word 2 */
  .word HardFault_Handler  /* word 3 */
  .word MemManage_Handler  /* word 4 */
  .word BusFault_Handler   /* word 5 */
  .word UsageFault_Handler /* word 6 */

The table keeps going. Words 7 to 10 are reserved and zero. Word 11 is SVC_Handler, then DebugMon_Handler, a zero, PendSV_Handler and SysTick_Handler. From word 16 on come the device's own interrupts, starting with WWDG_IRQHandler. The last entry is BootRAM, which the comment places at offset 0x108. That comment says the entry is for booting from RAM on medium-density devices. In this build the table is 268 bytes, which is 67 words. The map file gives the same size, and it places the table at 0x08000000 (lesson 41).

The dumped bytes confirm the layout. The first word, stored little-endian, is 0x20005000, the top of the 20 kB RAM. The second word is 0x080002F1. That is Reset_Handler at 0x080002F0 with bit 0 set. Bit 0 set marks the address as Thumb code, because the Cortex-M core runs only the Thumb instruction set. Every handler the file does not define points at Default_Handler, which is an infinite loop, and its entries read 0x08000339. So an address that appears even in the map file appears odd in the table.

What Reset_Handler does, in order

The reset handler in the same file does four things, in this order, before it calls the C library and your code:

  1. Call SystemInit. In this file, SystemInit is in system_stm32f1xx.c. Its body writes the vector table offset register only when the project defines USER_VECT_TAB_ADDRESS. It does not switch the clock. The clock is set by your code, as lesson 40 explained, and the variable SystemCoreClock starts at 8000000 until something updates it.
  2. Copy .data from flash to RAM. A loop copies from _sidata (the load address) to _sdata (the run address), until it reaches _edata. This is where the starting values of your initialised globals come from.
  3. Zero .bss. A second loop writes 0 from _sbss up to _ebss, so every zero-initialised global starts at 0, as C requires.
  4. Call __libc_init_array, then main. The C library runs its static constructors, and then your program starts.

The copy loop is the part that most bugs trace back to. Here is its code from the same file, with one comment per line: 

  ldr r0, =_sdata       /* r0: destination start, in RAM */
  ldr r1, =_edata       /* r1: destination end, in RAM */
  ldr r2, =_sidata      /* r2: source start, in flash */
  movs r3, #0           /* r3: byte offset, starts at 0 */
  b LoopCopyDataInit    /* test the loop condition first */
CopyDataInit:
  ldr r4, [r2, r3]      /* read a word from flash */
  str r4, [r0, r3]      /* write it to RAM at the same offset */
  adds r3, r3, #4       /* next word */
LoopCopyDataInit:
  adds r4, r0, r3       /* address of the next RAM word */
  cmp r4, r1            /* stop when it reaches _edata */
  bcc CopyDataInit      /* branch while it is below _edata */

Read the loop with an example. The demo's .data is 8 bytes: g_copied at 0x20000000 with the value 0xCAFE, then SystemCoreClock at 0x20000004 with the value 8000000. The stored bytes are at _sidata, which is 0x080004E0 in this build. On the first pass, r3 is 0, so the loop reads the word at 0x080004E0 and writes it to 0x20000000. Then r3 becomes 4, and the check computes 0x20000004, which is below _edata (0x20000008), so the loop runs again. It copies the second word to 0x20000004. Then r3 becomes 8, the check computes 0x20000008, which is not below _edata, and the loop stops. Two copies, eight bytes.

The clear loop does the same job with zeros. This build's .bss runs from 0x20000008 to 0x20000028, which is 32 bytes or 8 words. The loop writes zero to one word at a time, so it runs 8 times. The symbols _sbss, _ebss, _sidata, _sdata and _edata all come from the linker script. The startup file does not know the addresses. It reads them, and the linker script places them.

If the copy loop used the wrong load address, every initialised global would start with garbage, and the bug would appear before main() runs. This is why the startup file and the linker script must be written together. When a global has an odd starting value, check _sidata and the .data line in the map file before you look at your own code.

The RP2040 version

The RP2040 has the same job, done in the Pico SDK's crt0.S (pico-sdk 2.3.1, src/rp2_common/pico_crt0/crt0.S). Its vector table starts with __StackTop and _reset_handler, as the STM32's does. The table's four reserved slots after HardFault are isr_invalid, because the Cortex-M0+ has only HardFault in that range (lesson 39).

The reset handler is longer than the STM32's, for three reasons the source gives. First, it checks which core is running it. Core 1 normally sleeps in the bootrom, so a core other than core 0 is sent back to the bootrom instead of running the C startup. Second, it copies data from a table of source and destination ranges, not from one pair of symbols. The table includes .data, the scratch sections and, for some builds, code copied into RAM. Third, it zeroes .bss between __bss_start__ and __bss_end__. Then it calls runtime_init, main and exit.

One difference matters for interviews. The SDK's runtime_init does not call __libc_init_array. The newlib version of the function runs the preinit and init arrays itself, and it has a comment that explains why. Calling the full __libc_init_array would also run steps such as register_tm_clones, which earlier SDKs did not run, so the call is commented out. The STM32 startup calls __libc_init_array directly.

The RP2040 also boots through its bootrom and a second-stage bootloader before any of this. The datasheet lists the bootrom steps in section 2.8.1. Section 2.8.1.3 says that the second stage's only job is to configure the external flash interface, and that all other chip setup, such as the PLLs, is done later by platform initialisation code running over that interface.

Common mistakes

Each mistake below comes from a misunderstanding of the startup path. The symptom is what you see first, and the fix is the change that removes it.

Mistake 1: reading an initialised global before the copy

Symptom: a function that SystemInit calls reads a global with an initial value and gets whatever RAM held before the reset. The same read in main() is correct, because the copy has run by then. Fix: nothing that runs before the copy may depend on .data. Move that code after the copy, or make the value a const so it is read from flash directly.

Mistake 2: assuming SystemInit set the clock

Symptom: the timing is 8 MHz, not the 72 MHz you expected, so the delays are nine times too long and the UART baud rate is wrong. The code looks as if it configures the clock, because the header comment says so. Fix: read the function body. In this ST file, SystemInit does not switch the clock. Put the clock code in your own function, call it from main(), and call SystemCoreClockUpdate() after it.

Mistake 3: a handler name that does not match the vector table

Symptom: you write void USART1_Handler(void), the interrupt fires, and nothing you wrote runs. The debugger shows the core stopped in Default_Handler, the infinite loop. Fix: use the exact name in the startup file. The startup file declares each handler as a weak alias of Default_Handler. A function with the right name overrides the alias, and a function with the wrong name does not, so the table keeps pointing at the loop.

Mistake 4: a vector table that is not at the reset address

Symptom: the chip resets, runs a few instructions, and stops in a fault or a loop before main(). Nothing in your code has run. Fix: check the first two words of the table in the map file and the dump. Word 0 must be the top of RAM and word 1 must be Reset_Handler with bit 0 set. If the table is not at the address the core reads, the core takes garbage as its first instructions.

In real projects

Startup code in a production project is usually the vendor's file, with minor changes. The team's own changes are the heap and stack sizes in the linker script, the handler names for the interrupts they use, and any extra copy or clear steps for special memory, such as a block of RAM that must keep its value across resets. A reviewer checks those changes first. Each one changes the path described in this lesson, so each one needs a comment that explains why it is safe.

Interviewers ask about this path because it is the boundary between hardware and C. A candidate who can list the reset steps in order, and who can say which code runs before the globals exist, shows that they understand what the compiler assumes. That is the same reasoning that makes a volatile register access correct, and it is the reasoning needed to find many "works in the debugger, fails on reset" bugs.

Summary

  • On reset the core reads word 0 of the vector table as the stack pointer and word 1 as the reset handler, with bit 0 set for Thumb.
  • On the STM32F103, the table has _estack, Reset_Handler, then the core and device handlers. BootRAM sits at offset 0x108, and the table is 67 words.
  • Reset_Handler calls SystemInit, copies .data from _sidata to _sdata through _edata, zeroes .bss from _sbss to _ebss, then calls the C library's initialisers and main.
  • In the ST file, SystemInit does not switch the clock. Your code does, and SystemCoreClockUpdate() keeps the variable correct.
  • The RP2040's crt0 checks the core, copies data from a table of ranges, zeroes .bss, and calls runtime_init, which runs the preinit and init arrays itself.
  • A wrong handler name leaves the table pointing at Default_Handler, an infinite loop, so the bug looks like a hang.

  1. Open projects/0042-startup-code in VS Code, build with Ctrl+Shift+B, and start the simulator with F5 to debug.

If the breakpoint on Reset_Handler does not stop, look up its address with arm-none-eabi-nm -n build/blink.elf | grep Reset_Handler. The debugger should stop at 0x080002F0, and the vector table's word 1 holds that address with bit 0 set.

Model answer

The core loads the initial stack pointer and the reset vector from the start of the vector table, then jumps to Reset_Handler. The handler calls SystemInit, which on this ST file does not switch the clock, and then copies the initial values of the .data section from flash to RAM and zeroes .bss. It then calls the C library's initialisers and only then calls main. The copy and clear use symbols from the linker script, so the startup code and the script must match.

RP2040 datasheet: read sections 2.7 (Boot Sequence) and 2.8.1 (Processor Controlled Boot Sequence), including 2.8.1.3 (Flash Second Stage). They list the steps before your code runs on the RP2040, which the Pico SDK's crt0.S then continues. For the STM32, read startup_stm32f103xb.s from the first label to the end of the vector table.
