Startup code and the vector table

The code that runs between reset and main()

By the end of this lesson you can list what happens between reset and main() on an STM32F103 and an RP2040, and find the vector table entries and the copy and clear loops in the startup source.

From reset to main

Lesson 41 showed that the linker places .data in RAM while storing its starting values in flash, and that it defines symbols such as _sidata and _sdata to mark that copy, while lesson 34 showed what the core does when an exception arrives. This lesson joins the two. Something must perform the copy and something must tell the core where to begin, and both jobs belong to the startup code, whose vector table is the first thing the core receives.

A startup problem often surfaces first in a debugging session. A global counter is initialised to 7 in the code, yet it reads 0x4F or some other junk when main() begins, and although the build looks correct, the symptom appears only on the chip. The cause almost always lies in the startup path, in a copy loop with the wrong address, a clear loop that misses part of .bss or a vector table the core cannot find, and engineers who know this path usually find such bugs quickly.

The core at reset

On reset the core reads two words from the start of its vector table: the first is the initial stack pointer and the second the address of the reset handler, the first code to run. The table is an array of such addresses, one per exception, and the STM32 startup file's own comment says that it must end up at physical address 0x00000000, where the chip's flash is aliased after reset, which is why the linker places it at the start of flash (lesson 41).

At that moment nothing in the program has run, so the C variables are in an unknown state: .data is still in flash and .bss holds whatever RAM contained before the reset. The reset handler fixes both before calling main(), and because it reads the addresses through symbols, the startup file, the linker script and the vector table must agree on every one of them.

The STM32F103 vector table

The startup file is third_party/cmsis-device-f1/Source/Templates/gcc/startup_stm32f103xb.s, and its table begins with two entries followed by the core's handlers in order. 

g_pfnVectors:
  .word _estack            /* word 0: initial stack pointer */
  .word Reset_Handler      /* word 1: first code to run */
  .word NMI_Handler        /* word 2 */
  .word HardFault_Handler  /* word 3 */
  .word MemManage_Handler  /* word 4 */
  .word BusFault_Handler   /* word 5 */
  .word UsageFault_Handler /* word 6 */

The table continues with words 7 to 10 reserved and zero, then word 11, SVC_Handler, followed by DebugMon_Handler, a zero, PendSV_Handler and SysTick_Handler. From word 16 come the device's own interrupts, starting with WWDG_IRQHandler, and the last entry is BootRAM, which a comment places at offset 0x108 and describes as being for booting from RAM on medium-density devices. In this build the table is 268 bytes, or 67 words, matching the size in the map file, which places it at 0x08000000 (lesson 41).

The vector table resembles a list of speed-dial numbers. Entry 0 is not a number but the place to stand, the initial stack pointer, and each later entry is the address to call for one event, such as reset, a fault or a timer, so when an event happens the core looks up its entry and jumps there, and a wrong or missing entry calls the wrong handler or none. A phone would complain about an empty entry, however, whereas the core simply jumps to whatever address the word holds.

The dumped bytes confirm the layout. The first word, stored little-endian, is 0x20005000, the top of the 20 kB RAM, and the second is 0x080002F1, which is Reset_Handler at 0x080002F0 with bit 0 set to mark Thumb code, the only instruction set a Cortex-M core runs. Every handler the file does not define points at Default_Handler, an infinite loop, whose entries read 0x08000339, so an address that is even in the map file appears odd in the table.

The steps of Reset_Handler

The reset handler in the same file does four things, in this order, before handing over to the C library and the program.

  1. Call SystemInit. This function, in system_stm32f1xx.c, writes the vector table offset register only when the project defines USER_VECT_TAB_ADDRESS, and it does not switch the clock; your own code sets the clock, as lesson 40 explained, and SystemCoreClock stays at 8000000 until something updates it.
  2. Copy .data from flash to RAM. A loop copies from _sidata, the load address, to _sdata, the run address, until it reaches _edata, which is where the starting values of initialised globals come from.
  3. Zero .bss. A second loop writes 0 from _sbss up to _ebss, so every zero-initialised global starts at 0, as C requires.
  4. Call __libc_init_array, then main. The C library runs its static constructors, and then the program starts.

Reset_Handler acts like a stage crew before a show. It unpacks the props by copying .data from flash to RAM, clears the tables by zeroing .bss, sets the lights with SystemInit, and only then opens the curtain by calling main, so any code that runs before the crew has finished finds an empty stage, with globals holding whatever RAM held at power-up. The comparison exaggerates the lights, though, because in this ST file SystemInit leaves the clock as it was.

Most startup bugs trace back to the copy loop, whose code from the same file is shown below with one comment per line. 

  ldr r0, =_sdata       /* r0: destination start, in RAM */
  ldr r1, =_edata       /* r1: destination end, in RAM */
  ldr r2, =_sidata      /* r2: source start, in flash */
  movs r3, #0           /* r3: byte offset, starts at 0 */
  b LoopCopyDataInit    /* test the loop condition first */
CopyDataInit:
  ldr r4, [r2, r3]      /* read a word from flash */
  str r4, [r0, r3]      /* write it to RAM at the same offset */
  adds r3, r3, #4       /* next word */
LoopCopyDataInit:
  adds r4, r0, r3       /* address of the next RAM word */
  cmp r4, r1            /* stop when it reaches _edata */
  bcc CopyDataInit      /* branch while it is below _edata */

The demo's 8-byte .data makes a good test case: g_copied at 0x20000000 with the value 0xCAFE, then SystemCoreClock at 0x20000004 with the value 8000000, both stored at _sidata, 0x080004E0 in this build. On the first pass r3 is 0, so the loop reads the word at 0x080004E0 and writes it to 0x20000000. r3 then becomes 4 and the check computes 0x20000004, which is below _edata (0x20000008), so the loop copies the second word to 0x20000004. Finally r3 becomes 8, the check computes 0x20000008, which is not below _edata, and the loop stops after two copies of four bytes each.

The clear loop does the same with zeros. This build's .bss runs from 0x20000008 to 0x20000028, 32 bytes or 8 words, and since the loop writes one word per pass, it runs 8 times. The symbols _sbss, _ebss, _sidata, _sdata and _edata all come from the linker script, so the startup file does not know the addresses itself but reads the values the linker placed.

A copy loop with the wrong load address gives every initialised global a garbage starting value before main() runs, which is why the startup file and the linker script must be written together. When a global has an odd starting value, check _sidata and the .data line in the map file before looking at your own code.

RP2040 startup in crt0.S

The RP2040 does the same job in the Pico SDK's crt0.S (pico-sdk 2.3.1, src/rp2_common/pico_crt0/crt0.S), whose vector table starts with __StackTop and _reset_handler, as the STM32's does. The four reserved slots after HardFault are isr_invalid, because the Cortex-M0+ has only HardFault in that range (lesson 39).

Its reset handler is longer than the STM32's, for three reasons visible in the source. It first checks which core is running it, sending any core other than core 0 back to the bootrom, since core 1 normally sleeps there. It then copies data from a table of source and destination ranges rather than one pair of symbols, a table that includes .data, the scratch sections and, in some builds, code copied into RAM. Finally it zeroes .bss between __bss_start__ and __bss_end__ before calling runtime_init, main and exit.

Before any of this, the RP2040 boots through its bootrom and a second-stage bootloader. The datasheet lists the bootrom steps in section 2.8.1, and section 2.8.1.3 states that the second stage's only job is to configure the external flash interface, with all other chip setup, such as the PLLs, done later by platform initialisation code running over that interface.

Try it in Wokwi

  1. Open projects/0042-startup-code in VS Code, build with Ctrl+Shift+B, and start the simulator under the debugger with F5.
  2. Set a breakpoint on Reset_Handler and continue, step over SystemInit, then step into the copy loop, which repeats twice for .data while the destination address moves from 0x20000000 to 0x20000004.
  3. Let the program run to main. The serial output should show g_copied at main(): 0x0000CAFE and g_cleared at main(): 0x00000000.
  4. Compare the symbol lines with the map file. The output should show _sidata (flash):0x080004E0, _sdata (RAM): 0x20000000, _edata (RAM): 0x20000008 and _ebss: 0x20000028, matching the .data and .bss lines in build/blink.map.
Hint

If the breakpoint on Reset_Handler does not stop, look up its address with arm-none-eabi-nm -n build/blink.elf | grep Reset_Handler. The debugger should stop at 0x080002F0, and word 1 of the vector table holds that address with bit 0 set.

Common mistakes and how to spot them

An initialised global read before the copy

A function called from SystemInit reads an initialised global and gets whatever RAM held before the reset, while the same read in main() is correct because the copy has run by then. Nothing that runs before the copy may depend on .data, so move such code after it, or make the value const so that it is read directly from flash.

SystemInit assumed to set the clock

The timing corresponds to 8 MHz rather than the expected 72 MHz, so delays are nine times too long and the UART baud rate is wrong, although the header comment suggests the clock is configured. Read the function body: in this ST file SystemInit does not switch the clock, so put the clock code in your own function, call it from main() and follow it with SystemCoreClockUpdate().

A handler name that misses the vector table

An interrupt fires, nothing you wrote runs, and the debugger shows the core stuck in Default_Handler, the infinite loop, because the function was named USART1_Handler. The startup file declares each handler as a weak alias of Default_Handler, and only a function with exactly the right name overrides it, so copy the name from the startup file.

A vector table away from the reset address

The chip resets, runs a few instructions and stops in a fault or a loop before main(), with none of your code having run. Check the first two words of the table in the map file and the dump: word 0 must be the top of RAM and word 1 Reset_Handler with bit 0 set, because a table at the wrong address gives the core garbage as its first instructions.

Startup code in production projects

Startup code in a production project is usually the vendor's file with minor changes. The team's own changes are the heap and stack sizes in the linker script, the handler names for the interrupts it uses, and any extra copy or clear steps for special memory, such as a block of RAM that must keep its value across resets. A reviewer checks those changes first, because each alters the path described in this lesson, and each needs a comment explaining why it is safe.

Summary

  • On reset the core reads word 0 of the vector table as the stack pointer and word 1 as the reset handler, with bit 0 set for Thumb.
  • The STM32F103 table holds _estack, Reset_Handler and then the core and device handlers, with BootRAM at offset 0x108, 67 words in all.
  • Reset_Handler calls SystemInit, copies .data from _sidata to _sdata through _edata, zeroes .bss from _sbss to _ebss, and then calls the C library's initialisers and main.
  • In the ST file SystemInit does not switch the clock, so your code must, with SystemCoreClockUpdate() keeping the variable correct.
  • The RP2040's crt0 checks the core, copies data from a table of ranges, zeroes .bss and calls runtime_init, which runs the preinit and init arrays itself.
  • A wrong handler name leaves the table pointing at Default_Handler, an infinite loop, so the bug looks like a hang.
RP2040 datasheet: read sections 2.7 (Boot Sequence) and 2.8.1 (Processor Controlled Boot Sequence), including 2.8.1.3 (Flash Second Stage). They list the steps before your code runs on the RP2040, which the Pico SDK's crt0.S then continues. For the STM32, read startup_stm32f103xb.s from the first label to the end of the vector table.
