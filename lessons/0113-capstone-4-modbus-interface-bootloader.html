Capstone 4: Modbus interface, bootloader and CI

A dryer that only a button can drive is a demo. This last stage gives it a bus that a host can read and write, puts a bootloader in front of the application so the firmware can be updated, and runs every check on every commit. Then it takes stock of the whole capstone.

By the end of this lesson you can expose a register map over Modbus RTU and drive it from a host script, lay out a bootloader and an application in one image with a linker script and a version header, and read a CI workflow that builds, tests, analyses and simulates the firmware.

The idea: the product talks to the world

Industrial equipment is controlled by a host over a serial bus, usually Modbus (lesson 99). The protocol is simple, which is its strength: a request has an address, a function, two fields and a CRC, and a reply is the same length or an exception. The master (here, a Python script) asks for the status and writes a command. The dryer's job is to keep its register map true and to answer, without ever letting the bus stall the heater.

The register map

The map is the contract with the host, so it lives in one file, app/regmap.h, and the Python script copies the same numbers. Read-only registers are published from the control state before each reply. The two writable registers are a command and a material.

AddressNameAccessMeaning

Two details are worth discussing in an interview. Temperatures are signed, but Modbus registers are unsigned 16-bit values, so the code writes the two's complement and the host converts it back (the Python test checks −5.0 °C). And the slave must not pretend to accept a write it will ignore. modbus_slave_t has an optional check_write hook, and the dryer sets it to regmap_check_write(): a write to a read-only register gets exception 02 (illegal data address), and an out-of-range command or material gets exception 03 (illegal data value), as the Modbus application protocol defines (lesson 99). With the hook left NULL, the module behaves exactly like lesson 99's, so the change is backwards compatible. A host test sends a real frame and checks the 0x86 0x02 reply.

The RTU frame: silence, CRC and one interrupt per byte

The RTU slave is the lesson 99 code, reused as it is: modbus.c parses a complete frame and crc16.c computes the CRC. Only the framing is new. A frame ends after a silence of 3.5 characters, which is 1.75 ms at 115200 baud. The tasks tick at 1 ms, so the comms task uses a gap of 2 ms, which is safe because it is longer than the required silence.

Each received byte raises an interrupt, and the interrupt handler puts it on a FreeRTOS queue (lesson 89). A byte is never lost while the comms task is busy, and the interrupt is short. Reading the status register before the data register clears the overrun flag, so one lost byte cannot stop the receiver for good. A corrupted frame fails its CRC and gets no reply, which is the behaviour the specification asks for.

One wire, one job. USART1 carries both the log and the Modbus frames. A status line printed between a request and its reply would corrupt the reply. So the build turns the once-a-second status line off with DRYER_LOG_STATUS 0, and the watchdog check-in in the logger task stays on. The lesson 112 build printed the line; this one reports the same state through the registers.

The master: a host script

master_dryer.py is adapted from lesson 99's master. It builds the frames, checks the CRC with its own implementation, and talks to the simulator through the RFC 2217 port in wokwi.toml, which is 4000 in this stage. Its selftest command runs without a serial port, and the other commands need pyserial, which you install yourself. Run its selftest now: 

python master_dryer.py selftest
selftest OK: CRC-16/MODBUS 123456789 = 0x4B37, frames match, signed temperature decodes

The status command reads all eight registers in one request and prints them decoded: the state name, the temperature with its sign, the duty, the fault name and the minutes left. The material command writes register 7, and the start command writes register 6.

The bootloader and the image in one ELF

A product needs a way to update the firmware in the field. The usual design is a bootloader, a small program that runs first, checks the application image, and jumps to it (lesson 102). This build keeps both in one ELF and one hex, so it stays simple to simulate. The linker script splits the flash into two regions, as in lesson 102's boot.ld:

  • BOOT, 16 KB at 0x08000000: the startup code, the bootloader's main(), and the initial values of .data.
  • APP, 48 KB at 0x08004000: the image header (32 bytes), the application's vector table at +0x100, and everything else: FreeRTOS, the HAL, the drivers and the application.
  • RAM, 20 KB at 0x20000000: shared. The startup code initialises it once, so the jump does not copy anything again.

The header carries a magic number, the version as major and minor, the end of the image, and the offset of the vector table. The bootloader checks the magic, the vector offset, the image end, the initial stack pointer in RAM, and that the reset handler lies inside the image. Each check removes one way for a bad image to crash the boot. It does not check a CRC or a signature: the header has room for them, and lesson 103 covers why a signature is the real protection.

The version is not decorative. The application reads its own header from flash and draws FW 1.0 on the bottom line of the display. That is how a field technician checks which image is running, and how the host learns it too.

The jump gives up the bootloader. After __set_MSP() and the branch, the bootloader's code never runs again, and it cannot recover a hung application. A watchdog that resets the chip brings the bootloader back, which is why lesson 84's watchdog and this bootloader belong together.

Measured: does it fit?

The build reports the sizes below, from the solution's arm-none-eabi-size output and its map. Flash used by the bootloader and the application together is about 21 KB of the 64 KB part. The application slot holds about 19.6 KB of its 48 KB, so the design has room to grow. RAM use is about 10 KB of 20 KB, and that includes the 8 KB FreeRTOS heap that holds the task stacks. 

   text	   data	    bss	    dec	    hex	filename
  20802	    104	  10148	  31054	   794e	dryer.elf

The text section is the largest term. The HAL is linked for the I2C and the tick only, because the linker removes unused functions (--gc-sections), and the logic is compiled at -Og. If the image ever did not fit, the trims are, in order: use -Os for the release build, drop the font to the characters the status screen uses, and move the log strings out of the application. Each trade-off costs debuggability, which is why the course keeps the debug build for the simulator.

The CI workflow

CI runs the same checks on every commit, so a broken change is caught before it reaches a board. The workflow projects/0113-dryer-modbus-bootloader/.github/workflows/ci.yml is adapted from lesson 82, and it has four jobs:

  1. host-tests: builds the host project with CMake and Ninja and runs ctest. The ten test programs cover the conversion, the safety checks, the state machine, the controller, the closed loop, the Modbus frames and the register map.
  2. static-analysis: runs cppcheck with --error-exitcode=1 on the firmware sources, so a style finding fails the job.
  3. firmware: builds the bootloader and the application as one ELF with the Arm toolchain, prints the sizes and keeps the ELF, the hex and the map as artefacts. It needs the first two jobs to pass.
  4. simulate: runs the firmware in Wokwi and expects the banner DRYER RTOS OK on the serial monitor, within 10 seconds. The job reads the WOKWI_CLI_TOKEN secret through an environment variable and skips the step when the secret is absent, which is what a fork's pull request sees.

The local equivalents, which you can run now, give the results below.

python -I tools/build.py projects/0113-dryer-host-tests/solution --test
100% tests passed, 0 tests failed out of 10

cppcheck --enable=warning,style --std=c11 --quiet (firmware sources): no findings, exit code 0
The simulate job uses the official wokwi/wokwi-ci-action, the same action lesson 82 used, because the Wokwi CLI installation page was not reachable while this lesson was prepared. The action runs the same expected-text check as wokwi-cli --timeout --expect-text. No token was available here, so the simulation was not run for this stage; the lint of the diagram and the build passed.

Try it: the register that starts the dryer

  1. Open projects/0113-dryer-host-tests/starter and run python -I tools/build.py projects/0113-dryer-host-tests/starter --test from the workspace root. Exactly one of the ten test programs fails: regmap.
  2. Open projects/0113-dryer-modbus-bootloader/starter/app/regmap.c and find the TODO(learner) comment in regmap_publish(). Write the seven read-only registers from the table above. The fields come from the state, the output and the temperature arguments.
  3. Rerun the host tests. You know it works when all ten pass. Then build the firmware with python -I tools/build.py projects/0113-dryer-modbus-bootloader/starter.
  4. Optional, with pyserial installed: start the simulator on the solution, then run python master_dryer.py status. The eight values should match the banner's state. Compare them with your register map and fix any mismatch.
Hint for the temperature register

The temperature is in hundredths of a degree. Divide by 10 to get tenths, and store it as an unsigned 16-bit value by casting through a signed 16-bit type. The test for −5.00 °C expects 0xFFCE, which is −50 in two's complement.

Extensions: where to take it next

  • Real hardware. Build the heater stage on a board with a logic-level MOSFET, a fan with a flyback diode, and a bimetal thermal cutoff in series with the heater (lesson 106 for the board). Replace the LED with the heater and measure the real step response. Tune the PID on that data, not on the model.
  • A humidity sensor. An SHT31 or a BME280 on the same I2C bus would show the moisture the filament still holds. Each has its own I2C address and its own measurement sequence, and the datasheet gives both. Add it as a driver behind the same kind of interface as the NTC, and test its conversion on the PC with a fake.
  • Logging to flash. Keep the last fault and its time in the last flash page, so a field failure can be read after a reset. Writing flash needs an unlock, and erasing needs whole pages, so put the log in one page and wear-level it if you write often. Lesson 85 covers what a useful field log contains.
  • A signed image. Replace the header's reserved words with a CRC and then a signature, and check it in the bootloader before the jump. This is the step that makes the update path safe against a tampered image (lesson 103).

What to show an interviewer

Open the repository and show the requirements table from lesson 110, with each acceptance criterion pointing to a test. Run the host tests live, then show the closed-loop output and explain what the 80.4 s runaway means. Show the linker script and the header, and explain why the bootloader needs no copy of RAM. Finally show the CI workflow and the cppcheck line. Be honest about the limits: the sizes are the simulator's, the PID was not tuned on a real chamber, the presets are a compile-time table, and the display flush takes a large share of the CPU. A candidate who names those limits first is more credible than one who claims a perfect design.

You built a complete embedded product from requirements to CI: a Modbus slave on a register map, a bootloader and an application in one image with a version on the display, and a pipeline that builds, tests, analyses and simulates every commit. You can explain every part of it, and you can name its limits.

"How would you update the firmware of a device in the field, safely?" Answer out loud in 60 seconds, then compare.

Model answer

I'd keep a small bootloader that never changes, and an application slot with a header. The update writes the new image into a second slot, or into the same slot behind a flag, so a power loss mid-update leaves a bootable image. The bootloader checks the header, the length and a CRC, and then a signature from the vendor's key, and it jumps only if all three pass. If the check fails, it stays and reports, rather than running a bad image. A watchdog brings it back after a hang. For a safety product I'd also require a rollback to the last good image when the new one fails its first boot.

Modbus specifications (modbus.org): the Modbus over Serial Line specification, for the RTU frame and its silent interval, and the application protocol specification, for the function codes 03 and 06 and the exception responses. Read the serial line document first.
