Capstone 4: Modbus interface, bootloader and CI

A dryer that only a button can drive is a demo. This last stage gives it a bus that a host can read and write, puts a bootloader in front of the application so the firmware can be updated, and runs every check on every commit. Then it takes stock of the whole capstone.

By the end of this lesson you can expose a register map over Modbus RTU and drive it from a host script, lay out a bootloader and an application in one image with a linker script and a version header, and read a CI workflow that builds, tests, analyses and simulates the firmware.

Where we are and why it matters

Lessons 110 to 112 built the dryer's inside: its drivers, its state machine, its control loop and its tasks. The dryer still has no way to tell the outside world what it is doing. A factory line, a home server or a technician's laptop cannot ask it for its temperature, and nobody can start a drying cycle except by pressing the button on the case.

This stage solves two problems that every product in the field has. The first is talking to the device over a wire, which is what lesson 99 taught and this lesson applies to a real product. The second is changing the firmware after the device has left the factory, which is the job of a bootloader (lesson 102). Both need care, because a mistake in either one can make a working dryer unreachable.

What Modbus is, in plain words

A bus is a wire, or a pair of wires, that several devices share. Modbus is a protocol for a serial bus: devices take turns sending short messages, one byte after another. In the usual arrangement there is one master, which starts every conversation, and one or more slaves, which answer only when addressed. Here the master is a Python script on a PC, and the dryer is a slave with address 1.

The data the slave exposes is a list of holding registers. A holding register is a 16-bit number, which is two bytes, with an index (its address) starting at 0. The slave keeps the list in its own memory, and the master reads and writes entries of it. The register is not the same as a CPU register or a peripheral register from earlier lessons: it is a slot in a table that the protocol defines, and the firmware decides what each slot means.

The protocol is simple, which is its strength. Every request has the same shape: an address, a function code that says what to do, some fields, and a checksum. Every reply is either the same kind of message with the answer in it, or an exception, a short message that says why the request was refused. The physical layer, which is how the bits travel on the wire, is covered in lesson 99. A real RS-485 installation adds a transceiver chip that converts the signal levels; the simulator, and this build, talk to the UART pins directly.

The register map

The map is the contract with the host, so it lives in one file, app/regmap.h, and the Python script copies the same numbers. Read-only registers are published from the control state before each reply. The two writable registers are a command and a material.

Why the temperature needs a sign

A Modbus register is an unsigned 16-bit number, so it can hold 0 to 65535. A chamber temperature can be below zero, and the dryer's register layout needs a way to carry −5.0 °C. The answer is two's complement, the standard way that binary hardware stores negative numbers. The bits of a negative value are the bits that, added to the positive value, give zero in 16 bits.

Take −50 tenths of a degree (that is −5.0 °C). Work in 16 bits, step by step:

  1. Write 50 in binary: 50 is 0x0032, which is 0000 0000 0011 0010.
  2. Invert every bit (the one's complement): 0xFFCD, which is 1111 1111 1100 1101.
  3. Add 1: 0xFFCD + 1 = 0xFFCE. This is the value stored in the register.
  4. Check: the register holds 0xFFCE = 65486. Since 65536 − 65486 = 50, the register is −50 when read as a signed number.

The firmware does this by casting. It converts the signed value to int16_t, which the compiler stores as two's complement, and then to uint16_t, which keeps the same 16 bits. The host does the reverse: it reads the same 16 bits and interprets them as signed. The mistake that catches people is to read the register as unsigned. Then 0xFFCE is 65486 tenths, which is 6548.6 °C. The bits are right, and the reading is absurd, so it is worth testing both directions.

The write check and the exceptions

The slave must not pretend to accept a write it will ignore. modbus_slave_t has an optional check_write hook, and the dryer sets it to regmap_check_write(). A write to a read-only register gets exception 02 (illegal data address), and an out-of-range command or material gets exception 03 (illegal data value), as the Modbus application protocol defines (lesson 99). With the hook left NULL, the module behaves exactly like lesson 99's, so the change is backwards compatible. A host test sends a real frame and checks the 0x86 0x02 reply.

The byte 0x86 is the function code 0x06 with its top bit set (0x06 + 0x80). That top bit is the exception flag, and the byte after it is the exception code. The next section works one of these frames with real numbers.

A frame, byte by byte

A Modbus RTU frame is a sequence of bytes with nothing around it: no start byte and no end byte. The fields are the slave address, the function code, the data, and a 16-bit CRC. The CRC is a checksum: a short number computed from all the other bytes, so the receiver can tell whether the bytes arrived intact. The Modbus CRC is CRC-16/MODBUS, which lesson 99 defines, and its check value for the ASCII text "123456789" is 0x4B37.

Here is a worked example that you can check with the master script. The master wants to read register 2, the temperature, from slave 1.

StepBytes (hex)What each byte means
Request01 03 00 02 00 01 25 CA01 slave address; 03 read holding registers; 00 02 start address 2; 00 01 quantity 1; 25 CA the CRC, low byte first
Reply, reg 2 = 0xFFCE01 03 02 FF CE 78 2001 and 03 echo the request; 02 is the byte count of the data; FF CE is the register; 78 20 the CRC
Refused write01 86 02 C3 A186 is 0x06 with the exception flag 0x80 set; 02 is the exception code, illegal data address

The reply's data is the same two bytes as the register in the table above, so the host reads 0xFFCE and decodes it as −5.0 °C. Notice two details of the byte order. Each 16-bit field is big-endian, so its high byte comes first: the start address 2 is sent as 00 02. The CRC is the opposite, with its low byte first (25 CA). Mixing up those two orders is a common bug in a first Modbus implementation.

The frame lengths are fixed for the functions this slave supports: a read or a single write is 8 bytes (the request), and a refused write is 5 bytes (address, function with the flag, exception code, and CRC). A slave that receives a frame of any other length, or a frame whose CRC does not match, stays silent. Silence is the protocol's way of saying "I did not understand, and I will not pretend to".

The RTU frame: silence, CRC and one interrupt per byte

The RTU slave is the lesson 99 code, reused as it is: modbus.c parses a complete frame and crc16.c computes the CRC. Only the framing is new. Framing means deciding where one frame ends and the next begins, and an RTU frame has no marker for that. The rule is the silent interval: a frame ends when the line has been idle for a set time.

The Modbus serial-line specification defines the silence as 3.5 character times. A character is 11 bits on the wire (a start bit, eight data bits, a parity bit and a stop bit), so 3.5 characters at 115200 baud would be about 334 µs. The project does not use that computed value. It uses a fixed 1.75 ms, and its own comment says that is what 115200 baud needs. Lesson 99 gives the same figure. I could not open the specification from this workspace, so treat 1.75 ms as the project's value and check it in the document named in the Source box before you rely on it.

The tasks tick at 1 ms, so the comms task measures silence in ticks. It uses a gap of 2 ms, which is safe because it is longer than the required silence. The comms task waits up to 2 ms for the next byte. If no byte comes, the frame that has been collected so far is complete, and the task passes it to modbus_process(). Bytes past the end of the buffer are dropped, so an overlong frame is cut short and fails its CRC, which means it gets no reply.

Each received byte raises an interrupt. The interrupt handler reads the status register and then the data register, and it puts the byte on a FreeRTOS queue (lesson 89). The comms task takes bytes from the queue at its own pace. The interrupt is short, so it never keeps the heater control waiting. Reading the status register before the data register also clears the overrun flag. An overrun happens when a new byte arrives before the old one was read, and the overrun flag stops the receiver until it is cleared. The project's receive handler reads both registers in that order, so one lost byte cannot stop the receiver for good. The lost byte shows up as a bad frame, and the bad frame gets no reply.

One wire, one job. USART1 carries both the log and the Modbus frames. A status line printed between a request and its reply would corrupt the reply. So the build turns the once-a-second status line off with DRYER_LOG_STATUS 0, and the watchdog check-in in the logger task stays on. The lesson 112 build printed the line; this one reports the same state through the registers.

The master: a host script

master_dryer.py is adapted from lesson 99's master. It builds the frames, checks the CRC with its own implementation, and talks to the simulator through the RFC 2217 port in wokwi.toml, which is 4000 in this stage. RFC 2217 is a standard way to carry a serial port over a network connection, so the script can talk to the simulated USART1 as if it were a real adapter. Its selftest command runs without a serial port, and the other commands need pyserial, which you install yourself. Run its selftest now: 

python master_dryer.py selftest
selftest OK: CRC-16/MODBUS 123456789 = 0x4B37, frames match, signed temperature decodes

The selftest checks three things: the CRC against the standard check value, the request frames against the worked bytes above, and the signed decoding. The status command reads all eight registers in one request (function 03, start 0, quantity 8) and prints them decoded: the state name, the temperature with its sign, the duty, the fault name and the minutes left. The material command writes register 7, and the start command writes register 6.

The bootloader and the image in one ELF

A product needs a way to update the firmware in the field. The usual design is a bootloader, a small program that runs first, checks the application image, and jumps to it (lesson 102). The bootloader is the one part of the firmware that must never be updated by a faulty update, so it stays small and fixed.

This build keeps both in one ELF and one hex, so it stays simple to simulate. An ELF file is the standard output of the linker: it holds the code, the data and the addresses they must be loaded at. The hex file holds the same bytes as text, which is what a programmer tool writes to flash. The linker script decides which code goes to which address. This one splits the flash into two regions, as in lesson 102's boot.ld:

RegionAddress and sizeWhat is in it
BOOT0x08000000, 16 KBThe startup code, the bootloader's main(), and the initial values of .data.
APP0x08004000, 48 KBThe image header (32 bytes), the application's vector table at +0x100, and everything else: FreeRTOS, the HAL, the drivers and the application.
RAM0x20000000, 20 KBShared by both. The startup code initialises it once, so the jump does not copy anything again.

Flash is the chip's non-volatile memory: the program lives there and survives a power cut. RAM is the working memory, and its contents are lost at reset. Both regions of flash are read by the CPU at their addresses, which is why the header and the vector table must sit at fixed offsets.

The header, byte by byte

The application starts with a 32-byte header, which the bootloader reads before it trusts anything in the slot. The layout is a C structure (app_header_t) with a static assertion that its size is exactly 32 bytes, so the compiler refuses to build if the layout drifts.

OffsetFieldThis build's value
+0magic0x41505031, the ASCII letters "APP1", so a stray pattern of bytes is unlikely to match
+4version(major << 16) | minor, so 1.0 is 0x00010000
+8image_endThe address one past the last byte of the image, taken from the linker
+12vector_offset0x100, the offset of the vector table from the header
+16 to +31reserved[4]Zero here; room for a CRC and a signature (lesson 103)

The vector table is the list of addresses the CPU reads on reset and on each exception. Word 0 holds the initial stack pointer, which is the top of the stack, and word 1 holds the reset handler, the first code to run. The bootloader reads those two words from the application's table, sets the stack pointer to the first and jumps to the second. The application's table is at +0x100, so its first word is at 0x08004100.

The bootloader checks the magic, the vector offset, the image end, the initial stack pointer in RAM, and that the reset handler lies inside the image. Each check removes one way for a bad image to crash the boot. It does not check a CRC or a signature: the header has room for them, and lesson 103 covers why a signature is the real protection. An image that passes these checks can still be wrong in its contents, so the checks prevent crashes, not tampering.

The version is not decorative. The application reads its own header from flash and draws FW 1.0 on the bottom line of the display. That is how a field technician checks which image is running, and how the host learns it too.

The jump gives up the bootloader. After __set_MSP() and the branch, the bootloader's code never runs again, and it cannot recover a hung application. A watchdog that resets the chip brings the bootloader back, which is why lesson 84's watchdog and this bootloader belong together.

The jump, step by step

  1. The bootloader disables interrupts, so none runs in the middle of the hand-over.
  2. It points the vector table register (VTOR) at the application's table, so exceptions now use the application's handlers.
  3. It sets the main stack pointer (MSP) to the value in word 0 of that table.
  4. It calls the reset handler from word 1 as a function that never returns.

Each step depends on the one before. If step 2 is skipped, the first interrupt in the application would run a handler from the bootloader's table. If step 3 is skipped, the application starts on the stack pointer the bootloader left behind, not on the top of its own stack. The order is the reason the code is short, and it is also the reason a mistake here shows up as a crash that looks random.

The CI workflow

Continuous integration (CI) is a service that runs a fixed list of commands on every commit, so a broken change is caught before it reaches a board (lesson 82). The workflow projects/0113-dryer-modbus-bootloader/.github/workflows/ci.yml is adapted from lesson 82, and it has four jobs. The jobs run in a fixed order, shown by the needs lines in the file: a job with needs waits, and it is skipped when a job it needs fails.

  1. host-tests: builds the host project with CMake and Ninja and runs ctest. The ten test programs cover the conversion, the safety checks, the state machine, the controller, the closed loop, the Modbus frames and the register map.
  2. static-analysis: runs cppcheck with --error-exitcode=1 on the firmware sources, so a style finding fails the job. A static analyser reads the code without running it and reports patterns that are often bugs (lesson 83).
  3. firmware: builds the bootloader and the application as one ELF with the Arm toolchain, prints the sizes and keeps the ELF, the hex and the map as artefacts. It needs the first two jobs to pass.
  4. simulate: runs the firmware in Wokwi and expects the banner DRYER RTOS OK on the serial monitor, within 10 seconds. The job reads the WOKWI_CLI_TOKEN secret through an environment variable and skips the step when the secret is absent, which is what a fork's pull request sees.

The local equivalents, which you can run now, give the results below.

python -I tools/build.py projects/0113-dryer-host-tests/solution --test
100% tests passed out of 10

cppcheck --enable=warning,style --std=c11 --quiet (firmware sources): no findings, exit code 0
The simulate job uses the official wokwi/wokwi-ci-action, the same action lesson 82 used, because the Wokwi CLI installation page was not reachable while this lesson was prepared. The action runs the same expected-text check as wokwi-cli --timeout --expect-text. No token was available here, so the simulation was not run for this stage; the lint of the diagram and the build passed.

Hint for the temperature register

The temperature is in hundredths of a degree. Divide by 10 to get tenths, and store it as an unsigned 16-bit value by casting through a signed 16-bit type. The test for −5.00 °C expects 0xFFCE, which is −50 in two's complement.

Common mistakes and how to spot them

Every one of these has happened to someone building a Modbus device or a bootloader. Each entry gives the symptom first, so you can recognise it before you find the cause.

Mistake 1: a status line on the Modbus wire

Symptom: the master reports a bad CRC or no reply, but only while the firmware runs with the status line enabled. A frame that works with the logger off fails with it on. Cause: the log bytes land between the request and the reply, or inside the request, so the frame no longer matches its CRC. Fix: keep DRYER_LOG_STATUS at 0 in this build, and send any debug text to a second serial port, not to USART1.

Mistake 2: reading the temperature as unsigned

Symptom: a host script shows a chamber temperature of 6548.6 °C, or any large positive number, when the dryer is cold. The register holds 0xFFCE, and the bits are right. Cause: the script reads the 16 bits as an unsigned number, so 65486 tenths becomes 6548.6 °C. Fix: decode register 2 as signed (struct format <h in Python, int16_t in C). The selftest checks this path.

Mistake 3: changing a register that the firmware owns

Symptom: the master writes a new material with function 06, the reply echoes the write, and the next read shows the old material again. Cause: the material is applied only while the dryer is IDLE, and regmap_publish() copies the real material into the register on every reply. Writes during a cycle are refused silently in the state machine. Fix: stop the cycle first, write the material, and read it back. The firmware's behaviour is the design, so the fix is in the host, not in the register.

Mistake 4: a stale image on the board

Symptom: you change APP_VERSION to 1.1, rebuild, and the display still reads FW 1.0. Cause: the programmer flashed an old .hex file, often from an earlier build folder, so the header on the board is the old one. Fix: flash the file from the build you just made, check its time stamp, and read the version from the display or from the header in the flash. A version that is not checked on the device is only a guess.

In real projects

Teams that ship a Modbus device publish the register map as a document or a shared header, and the host tool is written against that same document. The map is versioned like an API: adding a register is safe, and moving or changing the meaning of one breaks every installed host. Reviewers ask for the map first, and for a test that proves the firmware and the map agree.

A production bootloader is rarely written from scratch. Teams usually start from an existing open bootloader, such as MCUboot (its design document is listed in RESOURCES.md), and adapt it to their own flash layout and keys. The bootloader is reviewed harder than any other code in the product, because a bug there can make a device unrecoverable in the field.

CI is judged by what it blocks. A pipeline that only reports is easy to ignore, while one that fails the merge gets fixed. The four jobs here follow that rule: a failing test stops the firmware build, and a finding from cppcheck fails the job. In an interview, the question is usually "what does your CI stop, and what does it only tell you", and this capstone has a clear answer.

Extensions: where to take it next

  • Real hardware. Build the heater stage on a board with a logic-level MOSFET, a fan with a flyback diode, and a bimetal thermal cutoff in series with the heater (lesson 106 for the board). Replace the LED with the heater and measure the real step response. Tune the PID on that data, not on the model.
  • A humidity sensor. An SHT31 or a BME280 on the same I2C bus would show the moisture the filament still holds. Each has its own I2C address and its own measurement sequence, and the datasheet gives both. Add it as a driver behind the same kind of interface as the NTC, and test its conversion on the PC with a fake.
  • Logging to flash. Keep the last fault and its time in the last flash page, so a field failure can be read after a reset. Writing flash needs an unlock, and erasing needs whole pages, so put the log in one page and wear-level it if you write often. Lesson 85 covers what a useful field log contains.
  • A signed image. Replace the header's reserved words with a CRC and then a signature, and check it in the bootloader before the jump. This is the step that makes the update path safe against a tampered image (lesson 103).

Summary

  • Modbus RTU is a master and slaves on a shared serial line. Holding registers are 16-bit slots, and the firmware decides what each one means.
  • Signed values travel as two's complement in unsigned registers. −50 tenths is 0xFFCE, and reading it as unsigned gives a wrong temperature.
  • A frame has no start or end marker. Its end is a silent interval, and its integrity is the CRC. Bad frames get no reply.
  • Exception 02 means a bad address (here, a write to a read-only register), and exception 03 means a bad value. The flag 0x80 marks any exception reply.
  • The bootloader checks a 32-byte header, sets VTOR and MSP, and jumps. It never returns, so a hung application needs a watchdog to bring it back.
  • Keep debug text off the Modbus wire, and flash the hex from the build you just made.
  • CI should stop a broken change, not only report it: tests, static analysis and the firmware build each gate the next job.

Model answer

I'd keep a small bootloader that never changes, and an application slot with a header. The update writes the new image into a second slot, or into the same slot behind a flag, so a power loss mid-update leaves a bootable image. The bootloader checks the header, the length and a CRC, and then a signature from the vendor's key, and it jumps only if all three pass. If the check fails, it stays and reports, rather than running a bad image. A watchdog brings it back after a hang. For a safety product I'd also require a rollback to the last good image when the new one fails its first boot.
