The device driver model and the GPIO and I2C APIs

Generic driver APIs found through the devicetree

By the end of this lesson you can read WHO_AM_I from the MYS-1 sensor at 0x48 with i2c_write_read_dt, and count button presses from a GPIO interrupt callback, with the sensor and the button both described in an overlay.

Portable device code across boards

Lesson 96 showed where Zephyr keeps the hardware description, the chip's nodes, the board's nodes and your overlay merged into one file at build time, and introduced aliases, so that the C code can ask for sw0 instead of a pin number. This lesson uses that tree for two kinds of device, a button, a GPIO input whose change should be heard at once, the interrupt idea of lesson 57, and a sensor, an I2C device read by writing a register address and then reading the answer, as lesson 60 described on the wire.

The problem is portability, because if the same MYS-1 sensor sits on a Pico in one product and on another board in the next, C code containing i2c_write(i2c0, ...) and the button's GPIO number must be rewritten for each board. With the driver model the C code names a node and the overlay says which bus and address that node uses, so the code stays the same while only the description changes, which teams maintaining several boards rely on.

Drivers as tables of functions

A device driver is the code that knows how one kind of hardware works, written in Zephyr as a table of function pointers, an ops table, plus the driver's private data. The GPIO driver's table is struct gpio_driver_api (include/zephyr/drivers/gpio.h:934), whose entries are the operations any GPIO driver must provide, filled in by the chip-specific code.

A device is one instance of a driver, one GPIO port or one I2C bus, represented as a struct device, the devicetree saying which instances exist and the build creating them at start-up. DEVICE_DT_GET(node) (include/zephyr/device.h:323) gives a pointer to one and device_is_ready() (include/zephyr/device.h:906) tells whether its driver started successfully, while your code never touches the chip's registers but calls a generic function such as gpio_pin_get_dt(), which looks up the device's ops table and calls the right entry.

A Zephyr driver resembles a universal remote whose buttons are the same for every television, the API such as gpio_pin_set_dt(), while behind each button the remote is programmed for one brand, the driver's table of functions, so your code presses buttons without learning which brand it talks to. The comparison breaks at the build, though, because a remote is reprogrammed at run time, whereas the devicetree fixes which driver sits behind each device when the firmware is compiled.

The indirection costs one function-pointer call per operation, and the program carries the code for every driver it links, in exchange for which the same application code compiles against any board whose devicetree names a GPIO or an I2C bus. Lesson 49 introduced function pointers, and this is the same idea at the scale of a whole driver.

Logical GPIO levels, active low and pull-ups

A GPIO pin is one wire that software can read or drive as a level, the button in this lesson being wired from GP14 to ground, so that with nothing pressing it an internal pull-up resistor holds the pin at 1 (high), while a press connects it to ground and it reads 0 (low).

The overlay says GPIO_ACTIVE_LOW, meaning the button is active when the physical level is low, and since Zephyr's GPIO API works with the logical level, gpio_pin_get_dt() returns 1 when the button is pressed whichever way the wire is pulled, which is why the solution never tests for 0. The flag belongs to the hardware description, so a later board wiring the button to 3V3 changes only the overlay, the logical-level idea being the one lesson 16 introduced for pull-ups.

GPIO interrupts and callbacks

Polling a pin means reading it on a timer, as the polled button of lesson 97 does, which can miss a short press, whereas an interrupt reverses the arrangement, the GPIO hardware noticing the change and the CPU running an interrupt service routine (ISR). The GPIO driver's ISR then calls the functions you registered, which Zephyr calls callbacks, firing them from its handler, for example in gpio_rpi_isr in drivers/gpio/gpio_rpi_pico.c:387, which calls gpio_fire_callbacks.

A flag chooses the trigger, GPIO_INT_EDGE_TO_ACTIVE being defined as an interrupt "on pin state change to logical level 1" (include/zephyr/drivers/gpio.h:210), and since the button is active low, logical 1 means pressed, so the callback fires once per press and not per release. An edge is a change from one level to the other, and this flag asks for one kind of edge only.

I2C addresses and the register pointer

I2C connects many devices on two wires, SDA carrying data and SCL the clock, the master starting each transaction by sending a 7-bit address that each device on the bus compares with its own. Lesson 60 covers the frame format, and what matters here is that the address has seven bits, the eighth saying whether the master writes or reads, the MYS-1 datasheet giving its address as 0x48, the 7-bit form (section 2, the table of the I2C interface in projects/0063-mystery-sensor/MYSTERY-SENSOR-DATASHEET.html).

The sensor has a register pointer, set by the first byte the master writes after the address, a read returning the register the pointer names, and the datasheet's section 3.2 gives the sequence for reading one register as start, address with write, the register number, a repeated start, address with read, one data byte and a stop. The repeated start is the second start condition in the same transaction, through which the master keeps the bus, so no other master can take it between the register write and the read.

Worked example: the WHO_AM_I read byte by byte

The sensor's WHO_AM_I register is at address 0x0F, its reset value being 0xA7 according to the datasheet's table in section 3.1, and the read can be followed step by step as the bus carries it. Before reading on, predict the two address bytes that appear on the bus.

  1. The address byte for the write. The 7-bit address 0x48, 0100 1000 in binary, shifts left by one bit to 1001 0000, with the low bit 0 for a write, giving 0x90, which the bus carries before waiting for an acknowledge.
  2. The register byte. The master sends 0x0F, which the MYS-1 acknowledges and stores as the register pointer.
  3. The repeated start and the read address. The master sends a repeated start, then the address with the low bit set to 1 for a read, 0x90 with the low bit set giving 0x91.
  4. The data byte. The sensor sends the byte at the pointer, 0xA7, and the master acknowledges nothing more, the standard way to end a read, before sending a stop.

The driver never shows these bytes, because i2c_write_read_dt() builds the two messages, the write message without a stop flag and the read message with I2C_MSG_RESTART, I2C_MSG_READ and I2C_MSG_STOP set (include/zephyr/drivers/i2c.h:1141 for the flags in the two-message form and i2c.h:1662 for the helper), so the library call includes the repeated start and your code adds nothing for it.

The sensor code line by line

The solution is in projects/0098-device-driver-i2c/solution/src/main.c, starting with the sensor part. 

static const struct i2c_dt_spec sensor = I2C_DT_SPEC_GET(DT_NODELABEL(mystery));

DT_NODELABEL(mystery) names the overlay node labelled mystery, and I2C_DT_SPEC_GET reads that node's parent bus and its reg property into a struct (include/zephyr/drivers/i2c.h:180) with a bus pointer, the struct device of i2c0, and an addr field, 0x48, so the code never mentions the bus by name. 

#define MYS_REG_WHO_AM_I    0x0Fu
#define MYS_WHO_AM_I_VALUE  0xA7u

Both values are named constants, the register address from the datasheet's section 3.1 and that register's reset value, so a reviewer can check each number against the datasheet and no magic numbers remain in the code path. 

static int read_who_am_i(uint8_t *id)
{
    uint8_t reg = MYS_REG_WHO_AM_I;
    return i2c_write_read_dt(&sensor, &reg, 1, id, 1);
}

The write part sends one byte from reg and the read part fills one byte at id, both lengths being passed explicitly, so the function never guesses how many bytes to move, and the return value is 0 on success and a negative error code otherwise, which is why the caller checks rc before looking at id. 

if (!i2c_is_ready_dt(&sensor)) {
    printk("I2C bus not ready\n");
    return 0;
}

i2c_is_ready_dt() asks whether the bus driver started (include/zephyr/drivers/i2c.h:630), a check that fails when the subsystem is not compiled in, the message saying so, and the mistakes section explains the Kconfig symbol that fixes it.

The button interrupt code

The button part counts presses in a callback. 

static volatile uint32_t presses;

static void button_pressed(const struct device *port, struct gpio_callback *cb, uint32_t pins)
{
    presses++;
}

The callback has the signature that gpio_callback_handler_t declares (include/zephyr/drivers/gpio.h:757), receiving the port, the callback record and the pin mask, all three ignored here, because it only counts. presses is volatile, telling the compiler that the value can change outside the code it sees, namely in the ISR, because without it the compiler may keep a copy in a register while the main thread reads it. 

gpio_pin_interrupt_configure_dt(&button, GPIO_INT_EDGE_TO_ACTIVE);
gpio_init_callback(&button_cb, button_pressed, BIT(button.pin));
gpio_add_callback_dt(&button, &button_cb);

The three calls set up the interrupt in order, gpio_pin_interrupt_configure_dt first enabling the interrupt on the pin with the edge flag (gpio.h:1106), gpio_init_callback then storing the handler and a mask of the pins it cares about (gpio.h:1935), BIT(button.pin), so that only this pin's events call the handler, and gpio_add_callback_dt finally linking the callback record into the GPIO port's list (gpio.h:1992), before which nothing calls your function. 

while (1) {
    k_sleep(K_SECONDS(2));
    printk("button presses %u\n", presses);
}

The main thread sleeps, wakes every two seconds and prints the count, reading presses without a lock, which is acceptable here because the read is a single 32-bit access and the ISR the only writer, so a value changing under the reader gives a stale count rather than a corrupt one. Lesson 97 used a mutex because its update was a read-modify-write across two threads, whereas this counter has only one writer.

Common mistakes and how to spot them

CONFIG_I2C left out

The console prints I2C bus not ready, because i2c_is_ready_dt() returns false when the I2C driver is not compiled, which happens without CONFIG_I2C=y, since the DesignWare driver that the Pico's i2c0 uses is declared inside the if I2C block of drivers/i2c/Kconfig, at line 163, a block ending at line 320. Add the line to prj.conf and do a clean build, so that the generated .config updates.

A wrong or 8-bit address in reg

The read fails and the solution's code prints MYSTERY no answer, error followed by the negative return code, because the overlay says reg = <0x90>, the 8-bit write address copied from a bus trace, so the driver addresses a device that is not there. The datasheet's table gives the 7-bit address, the 8-bit form being only the bus byte with the R/W bit added, so check the overlay against section 2 of the datasheet and the wiring on the diagram, where the sensor should sit on GP4 and GP5 with its pull-ups.

The active-low flag missing from the button

The count rises when your finger leaves the button rather than when it presses, lagging the presses by one, because the overlay dropped GPIO_ACTIVE_LOW, so logical 1 now means a high pin, the released button, and GPIO_INT_EDGE_TO_ACTIVE fires on release. Put the active-low flag back in the overlay rather than compensating in the C code.

A callback without the interrupt

The printed line stays button presses 0 forever while the sensor line prints normally, because gpio_init_callback and gpio_add_callback_dt were added but gpio_pin_interrupt_configure_dt was forgotten, so the pin never raises an interrupt and the handler is never called. Add the first of the three calls above.

Driver-based code in production firmware

Production code uses the driver model so that a board change is an overlay change, a reviewer checking in a driver-using change that every device has its devicetree node and binding, that every call checks readiness before use and that every interrupt callback does only what the ISR context allows, the last point being explained in lesson 97.

Industry sensor drivers, such as those for a real MEMS accelerometer, follow the same pattern of a register map, a read helper doing the repeated start and an interrupt line telling the host when a sample is ready, whereas the MYS-1 uses a polled DRDY flag instead of an interrupt, which the datasheet describes in section 4.2, so the course keeps the interrupt example on the button.

Summary

  • A driver is an ops table plus private data, and a struct device is one instance, found through the devicetree with DEVICE_DT_GET.
  • GPIO_ACTIVE_LOW in the overlay makes gpio_pin_get_dt() return 1 when the button is pressed.
  • GPIO_INT_EDGE_TO_ACTIVE fires a callback on the change to logical 1, which for an active-low button is the press.
  • An interrupt is set up in three steps, configuring the edge, initialising the callback with a pin mask and adding it.
  • The MYS-1 address is 0x48 in 7-bit form, which appears on the bus as 0x90 for a write and 0x91 for a read.
  • i2c_write_read_dt() sends the register pointer and the repeated start for you.
  • The I2C driver needs CONFIG_I2C=y, and the callback needs its interrupt configured.
