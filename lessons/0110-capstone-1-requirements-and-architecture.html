Capstone 1: requirements and architecture for a filament dryer

Your QIDI Q2 prints from spools that absorb water from the air. A dryer that holds a chamber at 45, 65 or 80 °C is a real product, and this capstone builds one. The first step is not code: it is the list of what the box must do and how it must fail.

By the end of this lesson you can write numbered requirements with acceptance criteria, draw a state machine with its transition table, sketch a layered architecture, justify RTOS task priorities with rate-monotonic reasoning, and build a skeleton that prints DRYER SKELETON OK.

Why a dryer. Nylon, PETG and PLA absorb moisture, and wet filament prints with bubbles and weak layers. Dedicated dryers hold a fixed temperature for hours. The controller is an ordinary embedded design: a sensor, a heater with a power switch, a display, buttons, and safety rules that must hold when a part fails. That is the job description of most firmware work.

The product is a filament dryer: a box that holds a chamber at a fixed temperature for hours, so that a spool of nylon, PETG or PLA gives up the water it has taken from the air. Wet filament prints with bubbles, stringing and weak layers, which is why makers and small print shops buy dryers. A dryer is a good firmware project because it has the parts most embedded products have: a temperature sensor, a heater switched by a power transistor, a display, buttons, and safety rules that must hold when a part fails. The problem this lesson solves is the first one any real project faces: deciding what the box must do, and how it must fail, before anyone writes C.

The idea: write the requirements before the code

A requirement says what the system must do, in a form that can be checked. A design says how. Interviewers and safety standards look for the same chain: every requirement has an acceptance criterion, and every criterion has a test. Functional safety standards such as IEC 61508 make this explicit (lesson 109), and a hiring manager reads a repository for it. You will build that chain in this capstone: the requirements here, the host tests in lessons 111 and 112, and the simulation and CI in lesson 113.

The dryer has two kinds of requirement. The functional ones say what it does for the user. The safety ones say what it does when something is broken, and they are the ones that make the design interesting. A third group, the non-functional ones, sets limits such as memory, timing and the way the code is checked.

Four words you will use all lesson

A requirement is one statement of what the system must do, written so that a reader can answer yes or no. An acceptance criterion is the measurable condition that makes the answer yes: a number with a unit, a state, a time, or a message on a screen. A test is the procedure that checks the criterion, and a design is the chosen way to meet the requirement. "The dryer must be safe" is not a requirement, because nobody can check it. "A reading of 90.00 °C latches FAULT and the heater command is 0" is one, because a test can supply the reading and look at both outputs.

The chain runs in one direction. Each requirement has at least one criterion, each criterion has a test, and the test runs against the same code that ships. When a reviewer asks "how do you know?", the answer is a row in the table and a test that passes or fails. A safety standard such as IEC 61508 asks for exactly this chain, and so does a good interview.

The state machine

A state machine is the cleanest way to describe a controller whose behaviour depends on what happened before. The dryer has five states: IDLE, HEATING (climbing to the setpoint), HOLDING (drying at the setpoint), COOLDOWN (cooling with the fan on), and FAULT (latched, heater off). Every transition has a cause, and the table below is the authoritative list. The diagram shows the main path.

States, events and transitions

A state is one of a fixed set of situations the machine can be in, such as "heating up". An event is something that happens: a button press, a new temperature reading, or the clock passing a deadline. A transition is the move from one state to another, caused by an event and sometimes guarded by a condition, such as "start pressed, and the sensor reads correctly". The table below lists every transition the design allows. Anything not in the table must not happen.

Why use a state machine instead of a few flags such as heating and fault? With flags, the combination of flags is the state, and some combinations are nonsense: heating and faulted at once, or holding with no setpoint. A state machine stores one variable with a fixed set of values, so each state can refuse the actions that are unsafe in it. In FAULT, the start button does nothing unless the cause is gone and the part is cool. A flag-based design has to remember that rule in every branch, and the first branch someone forgets is the bug.

Here is a trace through the machine, with the numbers from the requirements. The operator selects PLA and presses start at time 0, with a good sensor and the chamber at 22 °C. The machine moves from IDLE to HEATING (transition 1). The heater runs at full power until the chamber reaches 44 °C, one degree below the 45 °C setpoint. That moves it to HOLDING (transition 2), and the four-hour timer starts at that moment, not at time 0. When four hours of hold time have passed, it moves to COOLDOWN (transition 3). Now suppose the operator presses stop after one hour of holding instead. The stop is transition 4: HOLDING goes to COOLDOWN with the fan on, and the four-hour timer is abandoned. The machine returns to IDLE only when the chamber is at 40 °C or below (transition 5).

Two rules do most of the safety work. First, a stop is a cool-down, not a switch-off: a hot part that is cut off dead can stay hot for an hour in an enclosure. Second, a fault is latched in the state machine, not in the sensor reading, so a sensor that comes back does not restart the heater by itself.

The layered architecture

Layers separate what the product does from what the chip does. Each layer calls only the layer below it. This is the same idea as the HAL in lesson 76 and the driver model in lesson 96, applied to the whole product. The top layer is pure logic that you can test on a PC; the bottom layer is the only place with registers in it.

The HAL is an interface, not a vendor library. The application calls hal_heater_set_permille(), not a timer register, so the same logic runs in the simulator, on a Blue Pill, or on the PC with a fake HAL (lesson 81). The rule that matters in an interview is the dependency direction: nothing in the application may include a register header.

Calls go one way: a button, end to end

A HAL is the set of functions a layer exposes to the layer above it. A driver is the code that talks to one piece of hardware and turns it into plain values: an ADC code, a debounced button level, a duty cycle. The board file is the lowest layer, the only place that knows the register addresses of one chip on one board. Follow one button press down through the layers and back up. The Start button is wired from PB12 to ground, and the chip's internal pull-up holds the pin high while the button is open. The board file reads the pin register and returns 1 when the pin is low, which is what a press means. The button service samples that value through a debounce (lesson 52). When the debounced level changes from released to pressed, the service sets an event flag. The control code reads the flag once, and only then does the state change. Each layer calls the next one down, and nothing reaches up.

This is why the same state machine can run in the simulator, on the Blue Pill, and on the PC. The PC build replaces the board file with a fake that returns scripted values (lesson 81), and the rest of the code does not notice. In an interview, the rule to state is the dependency direction: no file in the application may include a register header.

Tasks and priorities with rate-monotonic reasoning

The product runs five jobs in parallel: the safety monitor, the control loop, the Modbus comms, the user interface, and the logger. In FreeRTOS each is a task with a priority (lesson 87). Rate-monotonic scheduling (lesson 91) gives the rule for periodic tasks: the shorter the period, the higher the priority. With that rule and the execution times, you can check that every deadline holds before you write any task code.

Words for scheduling

A task is a function that the RTOS runs as if it had its own processor, with its own stack. The scheduler decides which ready task runs. In FreeRTOS each task has a number priority, and the higher number wins: when a higher-priority task becomes ready, it preempts the running task, which means the CPU is taken away at once. A period is the time between two starts of a periodic task. The execution time is the CPU time one run needs, and a deadline is the time by which a run must finish. The utilisation of a task is its execution time divided by its period. The total utilisation is the sum over all periodic tasks. A utilisation of 0.5 means that half the processor is busy with that task, on average.

The rate-monotonic test is a sum. For n periodic tasks, the utilisation sum of execution time ÷ period stays below n(21/n − 1) if deadlines are guaranteed. For four tasks that bound is 0.757. Your estimates go into the sum. The display flush is the big term: a 1 KB frame at 100 kHz I2C takes about 90 ms, and the UI task spends it every 200 ms, so about 0.45 of the processor goes to drawing. That is high, and it is the first thing to measure on real hardware: lesson 112 has to schedule around it.

A worked example of the sum

Take estimates for the four periodic tasks and add them up step by step. These numbers are examples chosen for practice, not measurements from the project. The safety check takes 1 ms every 50 ms, giving 1 ÷ 50 = 0.02. The control cycle takes 5 ms every 100 ms, giving 5 ÷ 100 = 0.05. The UI task has two periods, so it contributes two terms: the button scan takes 0.5 ms every 20 ms, giving 0.025, and the redraw takes 90 ms every 200 ms, giving 0.45. The logger takes 1 ms every 100 ms, giving 0.01. The total is 0.02 + 0.05 + 0.025 + 0.45 + 0.01 = 0.555. That is below the bound of 0.757 for four tasks, so the rule says every deadline holds.

Treating the UI task as one task with two periods is a simplification. A stricter analysis splits it into two jobs, which makes five periodic jobs and a bound of 5 × (21/5 − 1) = 0.743. The total of 0.555 still passes. The design lesson is that the display flush, not the control loop, uses most of the headroom, so it is the first thing to measure and reduce. The bound is a sufficient test: a sum below it guarantees the deadlines, provided the estimates are right. A sum above it does not prove a miss; it only means the test cannot promise anything, and you must measure.

Estimates, not measurements. The execution times above are rough figures from reading the code, marked as estimates. A real design measures them with a GPIO toggle around each task, or a trace tool, and puts the measured numbers in the README.

What a pin does

A pin is a leg of the chip that connects a signal inside it to the outside world. Each general-purpose pin (a GPIO, for general-purpose input and output) can be an input, an output, or handed over to a built-in peripheral such as a timer or a serial port. That handover is the alternate function, and the table gives it for each pin. On the STM32F103, the setup of each pin is four bits in the port's configuration registers, CRL for pins 0 to 7 and CRH for pins 8 to 15: two bits choose the direction and speed, and two bits choose the kind of pin, such as push-pull output, open-drain output, or input with a pull-up. The skeleton's code writes those bits by hand, so that you can find them again in the reference manual.

An input with a pull-up is a pin that the chip holds high through a weak internal resistor. A button wired from the pin to ground pulls the pin low when it is pressed, so the pin reads 0 when pressed and 1 when released. This is active low: the active state is the low level. Active-low inputs are the normal case for buttons. The board file inverts the reading, so the rest of the code sees 1 for "pressed". Forgetting that inversion is one of the common mistakes below.

The OLED's I2C pins work differently. In open-drain mode a pin can only pull the line low, and a resistor on the board pulls it high. Lesson 61 explains why the bus is built that way. That is why the table says 4.7 kΩ external pull-ups on PB6 and PB7.

The real circuit behind the LED

In Wokwi the heater is a red LED, and the fan is a green one. On the real dryer, the microcontroller never drives a heater: it switches a power MOSFET. The gate is driven from PA6 through a series resistor of about 100 Ω, with a pull-down of about 10 kΩ so the heater stays off while the chip resets. The MOSFET's drain feeds the 24 V heater, and a logic-level N-channel part is chosen so its gate turns fully on at 3.3 V (lesson 12 and lesson 106 cover the parts and the layout). The fan is a motor, which is inductive, so it gets a flyback diode across its terminals (lesson 14).

A MOSFET (metal-oxide-semiconductor field-effect transistor) is a switch that the chip controls with voltage. Between its drain and source it either conducts well or almost not at all, and the gate voltage decides which. The part you choose must be specified to be fully on when its gate sees the 3.3 V that the pin produces. The gate resistor and pull-down values above are a starting point. Check them against the MOSFET's datasheet before you build anything.

The most important part is not on the MCU at all. A heater that the software can switch on must also have a hardware limit that does not depend on the software: a thermal fuse or a bimetal cutoff in series with the heater, rated above the setpoint and below the destruction temperature. Software safety is a second layer, not the only one. That sentence is worth repeating in an interview.

The same reasoning is behind Klipper's verify_heater on your printer: the firmware checks that the heater is actually heating, and it still does not replace a physical thermal protection.

The code, line by line

The skeleton's main.c is short, and it follows the architecture's rule: it calls only hal.h and the application modules. Read it as the start-up sequence of the product. These are the lines that matter. 

hal_init();                               /* board: clock, serial log, pins, timers, ADC, I2C */
dryer_init();                             /* application: the state machine starts in IDLE */
const material_t *m = materials_get(0);   /* the first preset: PLA */
(void)m;                                  /* linked in, not used yet */
hal_log("DRYER SKELETON OK");
for (;;) { }                              /* the RTOS tasks of lesson 112 do the work later */

hal_init() is the only call that touches registers, and it runs first, because everything after it assumes a configured clock and configured pins. dryer_init() puts the state machine in IDLE. materials_get(0) returns a pointer to the first row of a constant table, so the skeleton proves that the materials module is linked. The (void)m; line tells the compiler that the unused variable is deliberate, so it does not warn. hal_log() writes the banner. The final loop never ends, because a bare-metal program must not return from main(): returning would jump into whatever the start-up code left on the stack.

The serial log is the only real hardware in the skeleton, so it shows what a register write does. In hw/hal_bluepill.c, the line RCC->APB2ENR |= RCC_APB2ENR_IOPAEN | RCC_APB2ENR_USART1EN; switches on the clocks of port A and of USART1. Without a clock, a peripheral's registers do nothing. The line GPIOA->CRH = (GPIOA->CRH & ~(0xFU << 4)) | (0xBU << 4); clears the four configuration bits of PA9 and writes 0xB in their place: configuration 10 (alternate-function push-pull) and mode 11 (output at up to 50 MHz). The mask keeps the other seven pins of CRH unchanged, which is why the code reads the register, changes four bits, and writes it back, instead of assigning a whole value.

The baud rate comes from USART1->BRR = SystemCoreClock / LOG_BAUD;. The clock is the default 8 MHz internal oscillator, which the template's main.c states (lesson 67 explains that oscillator). The divider is 8 000 000 ÷ 115 200 = 69.4, and the register takes the whole number, 69. The baud rate that results is 8 000 000 ÷ 69 = 115 942, which is 0.6 % faster than 115 200. A UART tolerates a few per cent of error, so the log works, and you can check that number with a calculator. The last line of setup, USART1->CR1 = USART_CR1_TE | USART_CR1_UE;, turns on the transmitter and the peripheral. In hal_log(), each byte waits until the transmit-data-empty flag (TXE) is set before the next byte is written to the data register, so the loop never overwrites a byte that has not left yet.

Common mistakes and how to spot them

1. Requirements without numbers. Symptom: a review asks what "safe" means, and two engineers give two answers. Later, the first test is written with a value somebody guessed. Fix: write each requirement with a number, a unit and a condition, such as "90.00 °C measured at the sensor". If you cannot write a test for a row, the row is not finished.

2. Priorities chosen by importance instead of period. Symptom: the display looks right, but when the control loop slows, the temperature is sampled late and the overshoot grows. The serial log shows the control cycle at 130 ms instead of 100 ms. Fix: give the shortest period the highest priority, measure each task's execution time with a GPIO pin that you toggle around it, and add the utilisations again.

3. Active-low input read as active-high. Symptom: the Start button appears to start a cycle when it is released and does nothing when it is pressed. The debug view shows the raw pin at 1 while the button is held down. Fix: check the wiring (button to ground, pin with pull-up), then make the board file return 1 for a low pin, as hal_button_pressed() does. A unit test with a fake that returns 1 for "pressed" catches the inversion on the PC.

4. The serial log prints garbage or nothing. Symptom: the monitor shows no text, or random symbols. Cause: PA9 was left as an input (its CRH bits were not written), the port or USART clock was not enabled, or the baud divider is wrong. Fix: check IOPAEN and USART1EN in the clock register, then the 0xB nibble for PA9 in CRH, then the value of BRR.

In real projects

In a product team, the requirements table is the first document a safety assessor reads. Standards such as IEC 61508 (lesson 109) ask that each safety function is specified, verified and traced to tests. A small team keeps the table in the repository next to the code, and a change to a criterion comes with a change to its test. A reviewer checks two things: does every row have a number, and does every number have a test that fails when the number is wrong?

Physical protection matters as much as software. A heater that software can switch on must also have a hardware cutoff, such as a thermal fuse or a bimetal switch in series with the heater, that works without the microcontroller at all. The software checks are a second layer, not the only one. Klipper makes the same point on your printer: its verify_heater checks that a heater really heats, and the printer still needs its own physical protection.

In interviews, the question behind this lesson is "how do you know the product is safe?" A strong answer lists the requirements, names the test for each one, and says which layer is physical and which is software. Expect follow-up questions on the state machine, the layer rule and the scheduling sum, so know them from the tables in this lesson.

Summary

  • A requirement is a yes-or-no statement. Its acceptance criterion is the measurable condition, and a test checks the criterion.
  • Safety requirements describe what happens when a part fails, and they usually shape the architecture.
  • A state machine stores one state and lists every allowed transition, so unsafe actions are refused by state, not by flags scattered through the code.
  • Layers call only downward. Only the board file touches registers, so the logic also runs on a PC.
  • Each pin's configuration bits choose its function. An active-low input needs its reading inverted.
  • Rate-monotonic priorities give the shortest period the highest priority. A utilisation sum below n(21/n − 1) guarantees every deadline.
  • A hardware cutoff and software checks are two separate layers of protection.

"How do you choose the priorities of your RTOS tasks?" Answer out loud in 60 seconds, then compare.

Model answer

I list each task's period and worst-case execution time, then give the shortest period the highest priority, which is rate-monotonic scheduling. For periodic tasks, if the sum of execution time divided by period stays below n(21/n − 1), every deadline is met. Event-driven or human-paced tasks go lower, and the safety monitor goes highest because it must preempt anything that is running. I check the estimates with measurements, because a long blocking call, like a polled I2C transfer, changes the answer.
