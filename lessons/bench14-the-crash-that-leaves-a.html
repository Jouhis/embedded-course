Bench lab 14: The crash that leaves a note

A device in the field resets and nobody saw why. Make the firmware write a note as it dies, keep that note through the reset, and read it on the next boot, without ever mistaking power-on garbage for a crash.

This bench lab is optional. It needs only a Pico 2 and its USB cable. It doesn't count towards your progress. Time: about 50 minutes.
By the end of this lab you can record the cause and location of a crash in RAM that survives a reset, and validate that record with a magic number and a CRC so a power-on never reads as a crash.

What survives a reset

Lesson 84 added a watchdog and a HardFault handler. Together they turn a hang or a fault into a reset, which keeps the device running. They also destroy the evidence: after the reset, the firmware starts from scratch and nobody knows what went wrong. A post-mortem record fixes that. The dying firmware writes what it knows to a place that survives the reset, and the next boot reads it, logs it and clears it.

Two places on the RP2350 survive a watchdog reset:

  • The watchdog's scratch registers, eight 32-bit registers. A watchdog reset leaves them alone; a power-on or the RUN pin clears them (RP2350 datasheet, section 12.9.5). The SDK uses scratch 4 to 7 for its own reboot handling, so this lab uses scratch 0 only, for a run counter.
  • SRAM, as long as the start-up code doesn't clear it. The C start-up code zeroes every ordinary static variable (the .bss section) on every boot, reset or not. The SDK's __uninitialized_ram(name) places a variable in a section start-up leaves alone, a no-init region.

No-init RAM has a catch. After a power-on, nobody has written it, and SRAM powers up holding random bits. So the next boot must be able to tell "a crash note" from "garbage". This lab uses two checks: a magic number, a fixed 32-bit value that random data matches with a probability of one in four billion, and a CRC-32 over the note's fields, which also catches a note that was only half written when the reset hit.

The program

projects/bench14-crash-note crashes on purpose, twice, and counts runs in scratch 0:

  • Run 1: enables the watchdog with a 2 s timeout, then gets stuck in a loop that keeps writing its position into the note. The watchdog resets the chip.
  • Run 2: reads the note, then calls a callback pointer that was never set. Calling address 0 means branching to an address with bit 0 clear, which on a Cortex-M is a switch to ARM state the core doesn't support: it takes a fault, and with no UsageFault handler enabled, that becomes a HardFault. The handler finds the stacked registers, as in lesson 84, writes the stacked PC and LR into the note and resets with watchdog_reboot(0, 0, 0).
  • Run 3: reads the second note, prints BENCH14 both crashes recorded, and stops crashing.

Stage 1: in Wokwi

  1. Build and run the starter. Run 1 gets stuck and is reset; run 2 faults and is reset; run 3 finishes. But both runs 2 and 3 print no valid note.
  2. Task 1. The note is an ordinary static, which start-up zeroes on every boot. Declare it with __uninitialized_ram(note) instead. Run again: run 2 reports the stuck loop and run 3 the HardFault, with PC and LR.
  3. Look up the reported LR in the build's disassembly (arm-none-eabi-objdump -d build/blink.elf) or the map file. It's in main, right after the call to the NULL callback. The stacked PC is 0: the address the code tried to run.

In the simulator, the starter's weak check, note.cause != CAUSE_NONE, looks fine. That's because simulated RAM starts as zeros, so a fresh start never shows a note.

Stage 2: on the board

  1. Flash the version with Task 1 done but the weak check still in place. Open the serial port; it disconnects and reconnects at each reset (the board re-enumerates on USB), so reopen it if your terminal doesn't do so by itself. You get the same three runs.
  2. Now unplug the board for ten seconds and plug it back in, without BOOTSEL. Look at run 1's first lines. With the weak check you may see a "note" with a random cause, PC and uptime: power-on garbage, read as a crash.
  3. Task 2. Replace note_valid() with the real check: the magic number matches and the stored CRC matches a CRC computed over the other fields. Flash, repeat the power cycle: no valid note (power-on, or RAM held garbage), every time.
  4. Note that reset by watchdog: yes/no agrees: watchdog_caused_reboot() reads the chip's reset reason, a second, independent source of truth.

Whether you see garbage at step 2 depends on the chip and on how long it was off. Very short power cuts can leave SRAM almost intact, so an old, valid-looking note comes back. That's a second reason the program clears the note after reading it: a note must be reported once, not on every boot after it.

Common mistakes

  1. A note in ordinary static RAM. Start-up zeroes it, so it never survives. Use a no-init section.
  2. Trusting a single field. Random RAM often has a nonzero cause field. Use a magic number and a CRC.
  3. Not clearing the note after reading it. The same crash is reported on every later boot, and the crash statistics are wrong.
  4. Doing too much in the HardFault handler. printf there may fault again or never finish. Write a few words to RAM and reset; log on the next boot.
  5. Using the SDK's scratch registers. Scratch 4 to 7 belong to the SDK's reboot logic; writing them can change what happens on the next reset.

Summary

  • A post-mortem record keeps the cause of a reset: write it while dying, read and clear it on the next boot.
  • The watchdog scratch registers survive a watchdog reset; no-init RAM survives any reset that keeps power.
  • After power-on, SRAM is random; a magic number plus a CRC tells a real note from garbage, and catches half-written notes.
  • Calling a NULL function pointer on a Cortex-M faults because the target address has bit 0 clear; the stacked LR shows the caller.
  • Wokwi starts RAM at zero, so weak validity checks look fine in simulation and fail on a real power-up.
Your firmware now explains its own resets. In a product, this note plus a counter of resets by cause is often the first thing a support engineer asks for.
