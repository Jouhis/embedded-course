Embedded Linux

Application processors, kernels and hybrid designs

By the end of this lesson you can say whether a product needs an MCU, Linux on an application processor, or both; name what Linux adds and what it costs; and explain how Klipper splits its work between a Linux host and a microcontroller.

Beyond the single-program microcontroller

Until now the course has treated the microcontroller as the whole computer, your firmware starting at the reset vector, setting up the clock tree from lesson 40 and running one program directly from flash, with the startup code and vector table from lesson 42 as the only "operating system" in the project, a model that works very well for a thermostat, a motor controller or a sensor node.

It stops working when the product needs a web interface, a file system, a secure network stack and many programs that must not interfere with each other, at which point a product manager asks whether the team should move to Linux, a question that trades timing, power and cost against the work of keeping an operating system updated in the field. The 3D printer on your desk is already such a hybrid, a Linux computer running the interface and the planning while a small microcontroller fires the stepper pulses on time. This optional lesson is an overview of a large topic, needing no board, since its exercises are decision questions, and it gives you the vocabulary and the decision rules, starting from the constraints rather than the tools.

The microcontroller and physical addresses

A microcontroller (MCU) puts the processor core, the flash memory holding the program, the SRAM holding variables and peripherals such as timers, GPIO and UART on one chip, the core fetching each instruction from flash or SRAM, decoding it and executing it with no layer in between. When the chip is reset, the core reads the vector table and starts your code within microseconds, as lesson 42 showed in detail.

The key property is that the program sees physical addresses, so when your C code writes to 0x40020000, the bus carries that address to a peripheral without any translation, which makes timing predictable, because every access takes a known path, and the system cheap, because no translation hardware is needed. The cost is that nothing separates one part of the program from another, so a wild pointer in one task can overwrite another task's data.

A microcontroller resembles a pocket calculator, ready the moment you press a key, doing its one job the same way every time and running for months on a small battery, whereas a Linux board resembles a laptop, booting for a while, doing almost anything and needing updates and care, and many products carry both, each doing what it is good at. The comparison breaks for capability, though, because a calculator cannot be reprogrammed, whereas an MCU runs whatever firmware you write, so the real difference lies in timing, power and isolation rather than in what the chip can compute.

Application processors, the MMU and virtual memory

An application processor (AP) is a bigger class of chip, with a faster core, usually external DRAM rather than a few hundred kilobytes of SRAM, and a memory management unit (MMU), hardware that translates each address a program uses, a virtual address, into a physical address in memory. The translation uses tables that the operating system's kernel builds and maintains, each process getting its own set, an arrangement called virtual memory.

Virtual memory gives two things an MCU cannot easily provide, each process seeing its own address space, so that two programs can both use address 0x1000 without touching each other's data, and the kernel being able to leave parts of memory unmapped and catch the access, which is how a crash in one program is contained. The MPU that lesson 39 covered is different, the Cortex-M MPU having a small number of software-defined regions, each with access permissions, against which it checks accesses without translating addresses, so it cannot give each program its own view of memory, the RP2040 core having 8 MPU regions (see the MPU entry in the glossary).

The MMU is the reason Linux can run many programs safely and also the reason a Linux system is harder to make predictable, because a translation can miss the cache or require a table walk and the kernel can schedule other work between your instructions, effects that are small on average but change from run to run, which is what real-time engineers worry about.

The kernel, drivers and user space

The kernel is the part of Linux running with full access to the hardware, scheduling processes, handling interrupts, managing memory and talking to devices through drivers, whereas everything else, your Python script, a web server or a shell, runs in user space and asks the kernel for help through system calls, such as opening a file or sending a packet, which the kernel checks before acting.

The benefit of this split is reuse, because the kernel already contains drivers for USB, Wi-Fi, displays, storage and cameras as well as the TCP/IP stack, TLS and a file system such as ext4, each of which an MCU project needs a library for, ported and maintained. The price is that every service and every driver is code you must patch when a security fix arrives, the attack surface that lesson 106 discusses.

The Linux boot chain

A Linux product starts not with one program but with a chain, each loading the next, the boot ROM inside the chip running first and finding a bootloader on storage such as an SD card or eMMC, which loads the kernel and a device tree and hands over control. The kernel then mounts the root filesystem, holding the programs, libraries and configuration files, and starts the first user-space process.

Each step is a place where an update can break the product, and the chain is also why a Linux product takes seconds to boot, the bootloader, the kernel's own initialisation, the file system mount and every service that starts all adding time, whereas on an MCU the chain is one reset vector and your main. Lesson 104 covers the slot scheme that lets a field update fall back safely when one of those steps fails.

The device tree

An MCU project describes its pins and peripherals in code or a header file, whereas Linux, running the same kernel on many boards, reads that description from a device tree, a text file of nodes with properties describing the hardware on one board. The bootloader passes the compiled form to the kernel at boot, and the kernel matches each node to a driver by its compatible property. 

/ {
    uart0: serial@40000000 {          /* node name, label and address (invented here) */
        compatible = "example,uart";  /* the kernel looks for a driver with this string */
        reg = <0x40000000 0x1000>;   /* base address and size of the registers */
        status = "okay";              /* the node is enabled and should be probed */
    };
};

The serial@40000000 node name carries the unit address, and the label uart0: lets other nodes refer to it, while the compatible string is how the kernel picks a driver, so a typo there means that the driver never binds, and the reg property gives the register block the driver then maps. The address in this example is invented for illustration, a real board's address coming from its SoC datasheet, and lesson 96 shows the same idea in Zephyr's devicetree for the same reason, because the hardware description changes per board whereas the code that drives it should not.

Worked example: a boot budget and a power budget

The example compares an MCU and Linux on three budgets, boot time, battery life and timing. Before following the steps, predict roughly how many times longer the MCU design lasts on the same battery.

  1. The boot budget. A device must show a status screen within 50 ms of power-on, which Linux cannot do, because its boot chain alone takes seconds, whereas an MCU with a simple startup reaches main in microseconds and its display driver needs only a few milliseconds more, so the requirement rules out Linux before any other factor is considered.
  2. The MCU power budget. A coin-cell battery of 230 mAh (an illustrative size, not a product) powers a sensor node that sleeps at 10 µA and wakes for 5 ms every 10 minutes at 30 mA, the average current being the sleep current plus the active current weighted by its duty cycle, 5 ms divided by 600 s, or 0.0000083, so 30 mA times that is 0.25 µA, the average is 10.25 µA, and 230 mAh divided by 0.01025 mA gives about 22 400 hours, roughly 2.6 years.
  3. The Linux power budget. The same node running Linux draws about 300 mA all the time (an illustrative figure), so the same battery lasts 230 divided by 300, 0.77 hours or about 46 minutes, making the MCU design about 29 000 times better here.
  4. The timing budget. Linux's scheduler can run another task for a millisecond before your task gets the core, a latency that varies from run to run, and at 48 MHz one millisecond is 48 000 clock cycles, whereas a motor loop that must act within 10 µs has a budget of 480 cycles, so a single late scheduling event is one hundred times the budget.

The numbers are invented, but the method is the one you will use with real datasheet values, computing the average current rather than the peak and comparing it with the battery, and the timing step shows why a loop like that belongs on the MCU, whatever else the product does.

Hands-on: how Klipper splits the work

Many 3D printers run Klipper, which is a hybrid by design, the host being a Linux computer running the Python software that reads the printer's configuration, parses G-code and plans the motion, while the microcontroller runs firmware that generates the step pulses. The host computes when each step must happen and sends compressed queue_step commands ahead of time, the Klipper Code Overview saying that these commands are normally parsed and queued at least 100 ms before their first step Klipper Code Overview.

The MCU stores each queued move and fires the pulses itself, the Code Overview describing the step as scheduled on the MCU's hardware timer, with each step pulse rescheduling the next one, so because the host sends times well ahead of the pulses, a host late by a few milliseconds does not make any step late. The step times are stored as MCU clock values, so the MCU fires them on its own clock rather than the host's, which is the design, the timing-critical work running on the device with the deterministic clock and the heavy, flexible work on Linux.

The following sketch shows the idea in C, though it is not Klipper's code, the helper functions being hypothetical and the real firmware more involved. 

#include <stdint.h>

typedef struct {
    uint32_t next_clock;   /* MCU clock value at which the next step must fire */
    uint32_t interval;     /* clock ticks between steps in this queued move */
    uint32_t remaining;    /* steps left in the move */
} step_move_t;

static step_move_t move;

void step_timer_isr(void) {
    if (move.remaining == 0) {           /* nothing queued: leave the timer idle */
        return;
    }
    step_pin_pulse();                    /* hypothetical helper: pulse the driver's step pin */
    move.remaining--;
    move.next_clock += move.interval;    /* plan the next step on the MCU's own clock */
    timer_set_alarm(move.next_clock);    /* hypothetical helper: re-arm the hardware timer */
}

The struct holds the schedule the host sent in MCU clock ticks rather than seconds, so that it does not depend on the host's clock, and the if handles an empty queue, so that the timer does nothing until the host sends more work. The pulse happens inside the interrupt, which runs at a fixed moment, after which the code advances next_clock by a fixed interval, and the last line arms the timer for that clock value, so if the host is late, the queue is simply empty for a while, and the pulses already queued still arrive on time.

Open the Klipper Code Overview, find the paragraph about the queue and answer for yourself which part of the printer would notice a 5 ms host delay and which would not, the answer being the reason the split exists.

Common mistakes and how to spot them

Linux chosen because it is familiar

A battery prototype that works on the bench lasts a day in the field, because a team that has written Python for years reached for a Linux board by default and never calculated the power budget. Do the calculation from the worked example before choosing the architecture.

Linux timing treated as real-time

A 1 kHz control loop written as a Linux thread works in a one-minute test, but under load a few iterations come late by several milliseconds and the output jumps, intermittently and depending on what else is running, because the scheduler gives no hard deadline. Measure the worst-case latency under realistic load with a tool such as cyclictest, and move any hard deadline to an MCU, as Klipper does.

Only part of the software updated

A device boots but a driver is missing, or the kernel refuses to load its modules, because the team shipped a new application and left the kernel or the root filesystem on the old version, or updated the kernel and forgot that its modules were built for the old one. Release the bootloader, kernel, device tree and root filesystem as one versioned set with a rollback path, as lesson 104 describes.

The device tree of another board

One peripheral never appears, the boot log showing a missing device and no driver bound to its node, because the new board was brought up with the kernel and the device tree of the previous board. Check the compatible string and the status property of that node, and confirm the register address against the SoC datasheet.

The MCU memory model assumed to protect tasks

A variable in an unrelated task is corrupted and the fault appears far from its cause, because a developer used to Linux processes expected a crash in one task to be contained and built an MCU design with shared globals and no MPU regions. Give each task its own data and, where the design needs it, configure MPU regions for the stacks and shared buffers, as lesson 39 shows.

Build systems and reviews for Linux products

Teams building Linux products usually start from a generator, Buildroot describing itself as "a simple, efficient and easy-to-use tool to generate embedded Linux systems through cross-compilation" (Buildroot) and producing the toolchain, the root filesystem, the kernel and the bootloader from one configuration, which suits a small, fixed product. The Yocto Project is built from layers and recipes, which suits a company shipping many products from one base and maintaining them for years (The Yocto Project), and Bootlin's training covers both Bootlin embedded Linux training.

In a code review of a hybrid product, a senior engineer looks for where each deadline is enforced, asking which loop has a hard deadline, which device runs it and what happens to the product if the Linux side stops responding, a good answer naming the MCU watchdog and the safe state the MCU enters, which connects to the safety work in lesson 112.

Summary

  • An MCU runs one program from flash with physical addresses, which makes timing predictable and the system cheap.
  • An application processor with an MMU gives each process its own virtual address space, at the cost of a kernel, DRAM and a longer boot.
  • The MPU checks accesses against a few regions, whereas the MMU translates addresses, so they are different tools.
  • Linux boots through a chain of boot ROM, bootloader, kernel with device tree, root filesystem and then services.
  • The average power and the worst-case latency are calculated before choosing an architecture, boot time being a hard limit too.
  • Klipper's host plans the moves and sends them ahead of time, while the MCU fires each pulse on its own clock.
  • The bootloader, kernel, device tree and root filesystem are updated as one versioned set, with rollback.
