First blink in Wokwi

A first Pico program, built and run in a simulator

By the end of this lesson you can change a Pico blink to 5 Hz and wire a second LED that blinks in alternation with the on-board one, then see both work in the Wokwi simulator.

The edit, build and run loop

Lesson 1 installed the toolchain, and this lesson uses all of it for the first time. You will edit a C file, build it into blink.elf and watch that firmware run on a simulated Pico. Every later lesson repeats this loop with more demanding peripherals, so it is worth learning carefully now.

Blinking an LED is the traditional first program for a microcontroller, and it is still the first thing a firmware team tries on a new board. If the LED blinks, the clock runs, the program has loaded and the code reaches the pins, which is why engineers call it a bring-up test. A blink that misbehaves narrows the fault to a short list, which is far easier than a board that does nothing at all. The habit this lesson builds is to make one small change, check it, and read what changed.

A GPIO pin under program control

A Pico program is a C file, main.c, that the build turns into a firmware image, and the Pico SDK supplies the functions it calls. The on-board LED is wired to GPIO 25, where GPIO stands for general-purpose input/output, a pin the program can set to a digital level. Writing 1 makes the pin's voltage high, which lights the LED, and writing 0 makes it low, which turns the LED off. The high level is the chip's logic voltage, defined for this course in the logic level glossary entry; the exact values are in the Pico's datasheet and are not needed here. Wokwi's Pi Pico page confirms the GPIO 25 wiring and the GP pin names you will use.

It helps to know what actually happens when your code writes that pin. The CPU has no special instruction for pins. Instead it writes to an address that belongs to a peripheral register, a memory location wired to hardware rather than to RAM. Lesson 38 explains how the address map routes each access to the right block. For now, writing a pin is simply a memory write, much like writing an array element, except that the hardware acts on it. The Pico SDK's gpio_put does this with the chip's single-cycle I/O block (SIO), which lesson 38 introduces.

The main loop turns the LED on, waits, turns it off and waits again. sleep_ms() is blocking, which means the program does nothing else until the time has passed. That is acceptable for a blink and gives the simplest correct code. Lesson 55 replaces it with a loop that checks the time and keeps other work moving, since a real product can rarely afford to stop everything while it waits.

Pin direction: input and output

A GPIO pin can either drive the outside world as an output or read it as an input, depending on its direction setting. Two SDK calls set this up. gpio_init(pin) connects the pin to the chip's GPIO function, makes it an input and clears any output value. gpio_set_dir(pin, GPIO_OUT) then turns it into an output. GPIO_OUT is a constant equal to 1 and GPIO_IN is 0, and the SDK's header describes the argument as a boolean, true for out and false for in.

The order of the two calls matters. After gpio_init the pin is an input, so gpio_put stores the value without driving the LED. The starter code already calls both functions, but the second task asks you to do the same for a new pin, so it pays to understand the pair now.

Period, frequency and the blink rate

A blink is a repeating signal, and two numbers describe it. The period T is the time for one complete on-and-off cycle, and the frequency f is the number of complete cycles per second. The two are inverses of each other:

f = 1 ÷ T(1)

where f is in hertz (Hz, cycles per second) and T in seconds. A cycle of 100 ms on and 100 ms off lasts 200 ms, so Equation 1 gives 1 ÷ 0.2 s = 5 Hz.

The starter blinks at 1 Hz, with 500 ms on and 500 ms off for a 1 s period, and Task 1 changes it to 5 Hz by shortening both delays. A common slip is to count state changes rather than cycles. Since the LED changes state twice per cycle, counting changes gives 10 per second, which is double the true frequency.

The delay itself is a call to sleep_ms, declared in the SDK's pico/time.h as void sleep_ms(uint32_t ms). It takes a number of milliseconds and returns nothing. Because the parameter is an unsigned 32-bit integer, a negative time cannot be passed, which is the kind of small guarantee worth noticing when you read an API.

  1. gpio_put(LED_PIN, 1) becomes one store instruction. The CPU writes 0x02000000, a word with only bit 25 set, to the SIO's set register at 0xd0000014.
  2. The SIO sets bit 25 of the GPIO output, so pin 25 goes to 3.3 V. Current flows through the LED and its resistor to ground, and the LED lights.
  3. sleep_ms(500) makes the CPU wait for 500 ms. The pin needs nothing from the CPU in that time: the output register holds the level.
  4. gpio_put(LED_PIN, 0) writes the same bit to the clear register at 0xd0000018. The SIO clears bit 25, and the pin drops to 0 V.
  5. The second sleep_ms(500) keeps it low. One complete on-and-off cycle took 500 ms + 500 ms = 1 s: the period is 1 s, so the frequency is 1 Hz.
  6. while (true) jumps back to the first line, and the next period begins. Halve both delays and the period is 200 ms: 5 Hz, which is Task 1.

The LED and its series resistor

An LED is a diode that emits light when current flows through it in the forward direction. Unlike a resistor, a diode keeps its voltage roughly constant over a wide range of current once it reaches its forward voltage, and any further increase in voltage makes the current rise steeply. An LED connected straight to a pin would therefore draw more and more current until something fails. A current-limiting resistor in series prevents this, because its voltage drop grows with the current. The current is then

I = (Vpin − VF) ÷ R(2)

where Vpin is the pin voltage, VF the LED's forward voltage and R the resistor. With the pin at 3.3 V, a typical red LED at about 2.0 V and the 220 Ω resistor from the task, the resistor sees 3.3 V − 2.0 V = 1.3 V, and the current is 1.3 V ÷ 220 Ω = 0.0059 A, or about 5.9 mA. That is a sensible current for a small indicator LED. Forgetting the forward voltage and dividing 3.3 V by 220 Ω instead gives 15 mA, which overstates it, because the LED takes its share of the supply.

The current flows from the GP15 pin through the LED from its anode, the positive side and pin A on the Wokwi part, to its cathode, the negative side and pin C, and then through the resistor to GND. Since the LED lights only in that direction, the anode goes to the pin. Lesson 9 covers the diode in full.

Serial output over the UART

The starter also prints LED on and LED off to a serial monitor. The chip sends this text over a UART, a universal asynchronous receiver/transmitter, which sends one byte at a time as a series of voltage pulses at an agreed speed. The SDK's default speed is 115200 bits per second, defined as PICO_DEFAULT_UART_BAUD_RATE in hardware/uart.h. The details can wait; what matters now is which pins carry the signal.

The Pico's default UART uses GP0 for transmit and GP1 for receive, defined in the SDK's board header as PICO_DEFAULT_UART_TX_PIN 0 and PICO_DEFAULT_UART_RX_PIN 1. In diagram.json, the two connection lines wire GP0 to the serial monitor's RX input and GP1 to its TX output, so the chip's transmit pin feeds the monitor's receive input. In CMakeLists.txt, pico_enable_stdio_uart(blink 1) sends the SDK's printf output to that UART, and pico_enable_stdio_usb(blink 0) turns the USB serial path off.

A UART resembles two people tapping Morse code at a speed they agreed on beforehand. There is no shared clock between them, so the listener times each bit by counting from the start of the character. If one side taps at a different speed, the listener still hears taps but decodes nonsense, which is exactly how a wrong baud rate looks on a serial monitor: characters arrive, but they are garbage. The comparison stops at the framing, since a UART adds start and stop bits around each byte that Morse code has no equivalent for.

Building and starting the simulator

Every change goes through the same loop: edit main.c, build, then start the simulator. The simulator loads the newest ELF file, so it always runs the code you last built. If you start it before building, it runs the old file and shows the old behaviour, a mistake common enough to be the first item in the mistakes section below. Use F5 instead of starting the simulator when you want to pause and step. Debugging is lesson 54.

In VS Code, open the starter folder (File → Open Folder), then:

  • Build with Ctrl+Shift+B. The build writes build/blink.elf, and the terminal ends with a line saying the build finished without errors.
  • Start the simulator with F1 → Wokwi: Start Simulator. The board appears with the Pico and the serial monitor, the LED starts blinking and the serial monitor fills with lines.

The starter code, line by line

Here is the starter main.c without the comments that describe the tasks. Each group of lines is explained below it.

#include <stdio.h>
#include "pico/stdlib.h"

#define LED_PIN 25

int main(void) {
    stdio_init_all();
    gpio_init(LED_PIN);
    gpio_set_dir(LED_PIN, GPIO_OUT);

    while (true) {
        gpio_put(LED_PIN, 1);
        printf("LED on\n");
        sleep_ms(500);
        gpio_put(LED_PIN, 0);
        printf("LED off\n");
        sleep_ms(500);
    }
}
  • #include <stdio.h> brings in printf, the standard C output function, whose output the SDK sends to the UART.
  • #include "pico/stdlib.h" brings in the SDK's everyday header. It declares gpio_init, gpio_put, sleep_ms and the other functions used here, so the compiler can check each call.
  • #define LED_PIN 25 gives the pin a name. The number is the GPIO number, not the physical pin position on the board, and naming it means a moved LED changes one line rather than every call.
  • stdio_init_all() starts the standard input and output system so that printf works. It is called once, before any output.
  • gpio_init(LED_PIN) prepares pin 25 as described in the section on pin direction: GPIO function, input, cleared output.
  • gpio_set_dir(LED_PIN, GPIO_OUT) makes the pin an output so its level drives the LED. Without this line the LED never lights.
  • while (true) repeats forever. Firmware never returns from main, since there is nothing to return to, and stopping the chip means a reset.
  • gpio_put(LED_PIN, 1) drives pin 25 high. Inside the SDK it writes the pin's bit to the SIO set register, which is why it takes a single quick store.
  • printf("LED on\n") sends a line of text to the serial monitor. Since this takes time on the UART, a fast loop can fall behind its output.
  • sleep_ms(500) waits half a second while the LED stays on.
  • The next four lines do the same for the low level. gpio_put(LED_PIN, 0) writes the bit to the SIO clear register, and the program waits again.

The solution in projects/0002-first-blink/solution adds a second pin, EXT_LED_PIN set to 15, and a HALF_PERIOD_MS constant set to 100. In each phase it writes opposite levels to the two pins, and its comments explain why: the LEDs alternate only if the second pin always receives the opposite level of the first.

Try it in Wokwi

The starter runs the template blink unchanged, at 1 Hz with the on-board LED on for 500 ms and off for 500 ms. Its comments mark two tasks; look for the comments tagged (learner) in main.c.

  1. Task 1: make the blink 5 Hz. 5 Hz means 100 ms on and 100 ms off. Change the two sleep_ms delays in main.c from 500 to 100, build with Ctrl+Shift+B and start the simulator. Expected output: the on-board LED blinks five times per second, and the serial monitor prints LED on and LED off alternately, about ten lines per second. The lines scroll quickly, so judge the timing from the LED rather than the text.
  2. Task 2: add an external LED. Add a wokwi-led part and a wokwi-resistor part to diagram.json. Wire the LED's anode (pin A) to GP15, the LED's cathode (pin C) to resistor pin 1, and resistor pin 2 to GND.1. Set the resistor's value attribute to "220", meaning 220 Ω. Each connection is a line like ["pico:GP15", "led1:A", "green", []]. Save the file, then build and start the simulator again.
    Hint for the wiring

    Part types and pin names are on the Wokwi LED page and the Wokwi resistor page. If the simulator starts with the LED dark, check the anode and cathode first: the anode belongs on the pin side.

  3. Change the code for the external LED. Declare a constant EXT_LED_PIN with the value 15, and add gpio_init and gpio_set_dir(EXT_LED_PIN, GPIO_OUT) next to the existing pair. In the loop, write the opposite level to the external pin each time you write the on-board pin. Build again.
  4. Run and observe. Before you start the simulator, predict what the two LEDs should do. Expected output: they take turns five times per second each, so when one is lit the other is dark, and the serial monitor shows the blink lines. The reference solution prints Blink 5 Hz: on-board on, external off and Blink 5 Hz: on-board off, external on, which makes the phases easy to check.

Common mistakes and how to spot them

The simulator running an old build

You changed the delay to 100 ms and started the simulator, yet the LED still blinks at 1 Hz. The simulator was started without a build, so it loaded the previous build/blink.elf. Build with Ctrl+Shift+B, check the terminal for errors, and start the simulator again.

An output pin left as an input

The serial monitor prints its lines, but the external LED stays dark. The pin was never set as an output, and gpio_init alone leaves it as an input, so writing a level only stores the value. Add gpio_set_dir(EXT_LED_PIN, GPIO_OUT) after gpio_init.

An LED wired the wrong way round

The external LED stays dark even though the code is correct. In this case the anode and cathode are usually swapped, or the resistor sits on the pin side with the LED on the ground side in the wrong orientation. Since the LED conducts only from anode to cathode, check that A connects to GP15, C to the resistor, and the resistor's second pin to GND.1.

Both LEDs driven with the same level

The two LEDs blink in step rather than in alternation, because the second pin receives the same level as the first. Write the opposite level instead, with 1 and 0 swapped between the two pins in each phase, as the solution does.

Only one of the two delays changed

The LED is on for 100 ms but off for 500 ms, so the blink looks lopsided and the frequency is not 5 Hz. The on time and the off time are separate calls to sleep_ms, and one of them was missed. Change both, or better, define one constant for the half period and use it in both places, as the solution does.

Heartbeat LEDs in real products

Teams use a blink, or a steady heartbeat LED, as the first sign of life on a new board, and many production devices keep one so that a technician can see the firmware is running. The code is the same kind you wrote here, except that the pin number comes from a board header. Professional firmware defines each pin once, as you did with LED_PIN, so that a board revision changes a single line.

Code review looks for the same habits you practised. A reviewer checks that every pin is initialised and has its direction set before use, that time constants are named, and that comments explain why rather than what. A blocking sleep_ms in the main loop is a normal choice for a blink, but a warning sign in code that must also read sensors or respond to buttons, which is the trade-off lesson 55 deals with.

Summary

  • gpio_init prepares a pin and leaves it an input; gpio_set_dir(pin, GPIO_OUT) makes it drive its level.
  • gpio_put(pin, 1) sets a pin high by writing its bit to the SIO set register, and 0 uses the clear register.
  • sleep_ms blocks for the given number of milliseconds. A period is one on-and-off cycle, and f = 1 ÷ T.
  • 5 Hz is a 200 ms period, so 100 ms on and 100 ms off. Counting state changes gives twice the true frequency.
  • An LED needs a series resistor. With 3.3 V, a 2.0 V forward voltage and 220 Ω, the current is about 5.9 mA.
  • The anode goes to the pin and the cathode to the resistor, since the LED conducts only in that direction.
  • The Pico's default UART uses GP0 for transmit and GP1 for receive, and printf sends its output there.
  • Build before you simulate, because the simulator loads whatever blink.elf is on disk.
