First blink in Wokwi

You will build a Pico program, run it in a simulator, and change it the way firmware engineers do: small edits, rebuild, observe.

By the end of this lesson you can change a Pico blink to 5 Hz and wire a second LED that blinks in alternation with the on-board one, then see both work in the Wokwi simulator.

Where we are and why it matters

Lesson 1 installed the toolchain: the Arm compiler, the linker, CMake and the Pico SDK. This lesson uses all of them for the first time. You will edit a C file, build it into blink.elf, and watch that firmware run in a simulated Pico. Everything later in the course repeats this same loop with harder peripherals, so it is worth learning carefully now.

Blinking an LED is the traditional first program for a microcontroller, and it is still the first thing a firmware team tests on a new board. If the LED blinks, the clock runs, the program loads, and the code reaches the pins. That is why engineers call this kind of check a bring-up test. A blink that goes wrong narrows the problem to a short list, which is much easier than a board that does nothing. The skill here is the habit of making one small change, checking it, and reading what changed.

The idea: a pin the program controls

A Pico program is a C file, main.c, that the build turns into a firmware image. The Pico SDK supplies the functions it calls. The on-board LED is wired to GPIO 25. GPIO stands for general-purpose input/output: a pin the program can set to a digital level. Writing 1 to that pin makes its voltage high, which lights the LED. Writing 0 makes it low, which turns the LED off. The pin's high level is the chip's logic voltage, which the logic level entry in the glossary defines for this course. The exact voltages for the Pico are in its datasheet, and you do not need them for this lesson. Wokwi's Pi Pico page confirms the GPIO 25 wiring and the GP pin names you will use.

Here is what happens when your code writes that pin. The CPU does not have a special instruction for a pin. It writes to an address, and that address belongs to a peripheral register, a memory location that is wired to hardware instead of to RAM. Lesson 38 explains how the address map sends each access to the right block. For now, the important point is that writing a pin is a memory write, just like writing an array element, except that the hardware acts on it. The Pico SDK's gpio_put does this with the chip's single-cycle I/O block (SIO), which lesson 38 introduces.

The main loop turns the LED on, waits, turns it off and waits again. sleep_ms() is blocking: the program does nothing else until the time has passed. That is fine for a blink, and it is the simplest correct code. Lesson 55 replaces it with a loop that checks the time and keeps other work moving, because a real product cannot usually stop everything to wait.

Direction: a pin is an input until you say otherwise

A GPIO pin can drive the outside world (an output) or read it (an input). Which one it is depends on its direction setting. Two SDK calls set it up. gpio_init(pin) prepares the pin: it connects the pin to the chip's GPIO function, makes it an input, and clears any output value. gpio_set_dir(pin, GPIO_OUT) then makes it an output. GPIO_OUT is a constant equal to 1, and GPIO_IN is 0. The SDK's header calls the second argument a boolean: true for out, false for in.

The order matters. After gpio_init the pin is an input, so gpio_put stores the value but the pin does not drive the LED. The starter code calls both functions for you, but the second task asks you to do the same for a new pin, so understand the pair now.

Time: period, frequency and the blink rate

A blink is a repeating signal, and two numbers describe it. The period is the time for one complete on-and-off cycle. The frequency is how many complete cycles happen each second, and it is the inverse of the period: frequency = 1 ÷ period. A cycle of 100 ms on and 100 ms off lasts 200 ms, so its frequency is 1 ÷ 0.2 s = 5 Hz (hertz, cycles per second).

The starter blinks at 1 Hz: 500 ms on and 500 ms off, a 1 s period. Task 1 changes it to 5 Hz by halving both delays. A common mistake is to count the state changes rather than the cycles. The LED changes state twice per cycle, so counting changes gives 10 per second, which is double the true frequency.

The delay is a call to sleep_ms. Its signature in the SDK's pico/time.h is void sleep_ms(uint32_t ms): it takes a count of milliseconds and returns nothing. Its unsigned 32-bit parameter means you cannot pass a negative time, which is a small but useful check when you read an API.

The LED and its resistor

An LED is a diode that emits light when current flows through it in the forward direction. A diode does not behave like a resistor. Once the voltage across it reaches its forward voltage, its voltage stays roughly constant over a wide range of current, and the current rises steeply with any further increase in voltage. So connecting an LED straight to a pin would let the current climb until something fails. A current-limiting resistor in series fixes this, because the resistor's voltage drop rises with the current.

Here is a worked example with real numbers. Take the pin at 3.3 V, a typical red LED with a forward voltage of about 2.0 V, and the 220 Ω resistor from the task. The resistor sees the difference: 3.3 V − 2.0 V = 1.3 V. Ohm's law gives the current: I = V ÷ R = 1.3 V ÷ 220 Ω = 0.0059 A, which is about 5.9 mA. That is a sensible current for a small indicator LED. A tempting mistake is to forget the forward voltage and divide 3.3 V by 220 Ω, which gives 15 mA. The resistor does not see all of the supply, because the LED takes its share.

The current runs from the GP15 pin, through the LED from its anode (the positive side, pin A on the Wokwi part) to its cathode (the negative side, pin C), then through the resistor to GND. The LED lights only in that direction, so the anode goes to the pin. Lesson 9 covers the diode in full.

Serial output: text from the chip

The starter also prints LED on and LED off to a serial monitor. The chip sends the text over a UART, a universal asynchronous receiver/transmitter. A UART sends one byte at a time as a series of voltage pulses at an agreed speed. The SDK's default speed is 115200 bits per second, which it defines as PICO_DEFAULT_UART_BAUD_RATE in hardware/uart.h. You do not need the details yet. You need to know which pins carry it.

The Pico's default UART pins are GP0 for transmit and GP1 for receive. The SDK's board header defines them as PICO_DEFAULT_UART_TX_PIN 0 and PICO_DEFAULT_UART_RX_PIN 1. In diagram.json, the two connection lines wire GP0 to the serial monitor's RX input and GP1 to its TX input. Read from the chip's side, its transmit pin feeds the monitor's receive input, which is the same connection in the other direction. The CMakeLists.txt line pico_enable_stdio_uart(blink 1) makes the SDK's printf go to that UART, and pico_enable_stdio_usb(blink 0) turns the USB serial path off.

The loop: build, then simulate

Every change follows the same loop. Edit main.c, build, then start the simulator. The simulator loads the newest ELF file, so it always runs the code you just built. If you start the simulator before building, it runs the old file, and you will see the old behaviour. That mistake is so common that the first common-mistakes item below covers it. Use F5 instead of starting the simulator when you want to pause and step. Debugging is lesson 54.

In VS Code, open the starter folder (File → Open Folder), then:

  • Build with Ctrl+Shift+B. The build writes build/blink.elf. The terminal ends with a line that says the build finished without errors.
  • Start the simulator with F1 → Wokwi: Start Simulator. The board appears with the Pico and the serial monitor. The LED on the board starts blinking, and the serial monitor fills with lines.

The code, line by line

Here is the starter main.c, without the comments that describe the tasks. Each group of lines is explained below it.

#include <stdio.h>
#include "pico/stdlib.h"

#define LED_PIN 25

int main(void) {
    stdio_init_all();
    gpio_init(LED_PIN);
    gpio_set_dir(LED_PIN, GPIO_OUT);

    while (true) {
        gpio_put(LED_PIN, 1);
        printf("LED on\n");
        sleep_ms(500);
        gpio_put(LED_PIN, 0);
        printf("LED off\n");
        sleep_ms(500);
    }
}
  • #include <stdio.h> brings in printf, the standard C output function. The SDK sends its output to the UART, as described above.
  • #include "pico/stdlib.h" brings in the SDK's everyday header. It declares gpio_init, gpio_put, sleep_ms and the others you use here, so the compiler can check each call.
  • #define LED_PIN 25 gives the pin a name. The number is the GPIO number, not the physical pin position on the board. Using a name means you change one line, not every call, if the LED moves.
  • stdio_init_all() starts the standard input and output system, so printf works. Call it once, before any output.
  • gpio_init(LED_PIN) prepares pin 25 as described in the direction section: GPIO function, input, cleared output.
  • gpio_set_dir(LED_PIN, GPIO_OUT) turns the pin into an output, so its level drives the LED. Without this line the LED never lights.
  • while (true) repeats forever. A firmware program never returns from main, because nothing is left to return to. Stopping the chip is a reset, not a return.
  • gpio_put(LED_PIN, 1) drives pin 25 high. Inside the SDK this writes the pin's bit to the SIO set register, which is why it is a single quick store.
  • printf("LED on\n") sends a line of text to the serial monitor. It takes time on the UART, so a fast loop can fall behind the output.
  • sleep_ms(500) waits half a second, during which the LED stays on.
  • The next four lines do the same for the low level. gpio_put(LED_PIN, 0) clears the bit in the SIO clear register, and the program waits again.

The solution in projects/0002-first-blink/solution adds a second pin, EXT_LED_PIN set to 15, and a HALF_PERIOD_MS constant set to 100. It writes opposite levels to the two pins in each phase. Its comments explain why: the two LEDs alternate only if the second pin always gets the opposite level of the first.

Try it in Wokwi

The starter runs the template blink unchanged: 1 Hz, with the on-board LED on for 500 ms and off for 500 ms. Its comments mark two tasks. Look for the comments tagged (learner) in main.c.

  1. Task 1: make the blink 5 Hz. 5 Hz means 100 ms on and 100 ms off. Change the two sleep_ms delays in main.c from 500 to 100, build with Ctrl+Shift+B, and start the simulator. Expected output: the on-board LED blinks five times per second, and the serial monitor prints LED on and LED off alternately, about ten lines per second. The lines scroll quickly, so judge the timing from the LED, not from reading the text.
  2. Task 2: add an external LED. Add a wokwi-led part and a wokwi-resistor part to diagram.json. Wire the LED's anode (pin A) to GP15. Wire the LED's cathode (pin C) to resistor pin 1, and resistor pin 2 to GND.1. Set the resistor's value attribute to "220", meaning 220 Ω. Each connection is a line like ["pico:GP15", "led1:A", "green", []]. Save the file, then build and start the simulator again.
    Hint for the wiring

    Part types and pin names are on the Wokwi LED page and the Wokwi resistor page. If the simulator starts with the LED dark, check the anode and cathode first: the anode belongs on the pin side.

  3. Change the code for the external LED. Declare a constant EXT_LED_PIN with the value 15. Add gpio_init and gpio_set_dir(EXT_LED_PIN, GPIO_OUT) next to the existing pair. In the loop, write the opposite level to the external pin each time you write the on-board pin. Build again.
  4. Run and observe. Expected output: the on-board LED and the external LED take turns, five times per second each, so when one is lit the other is dark. The serial monitor shows the blink lines. If you prefer, the reference solution prints Blink 5 Hz: on-board on, external off and Blink 5 Hz: on-board off, external on, which lets you check the phases at a glance.

Common mistakes and how to spot them

  1. The simulator runs the old blink. Symptom: you changed the delay to 100 ms, started the simulator, and the LED still blinks at 1 Hz. Cause: you started the simulator without building, so it loaded the previous build/blink.elf. Fix: build with Ctrl+Shift+B, check the terminal for errors, then start the simulator again.
  2. The new LED never lights. Symptom: the serial monitor prints the lines, but the external LED stays dark. Cause: the pin was never set as an output. gpio_init alone leaves it as an input, so writing a level only stores the value. Fix: add gpio_set_dir(EXT_LED_PIN, GPIO_OUT) after gpio_init.
  3. The LED is wired backwards. Symptom: the external LED stays dark even though the code is right. Cause: the LED's anode and cathode are swapped, or the resistor is on the pin side and the LED on the ground side. The LED conducts only from anode to cathode. Fix: check that the anode (A) connects to GP15, the cathode (C) to the resistor, and the resistor's second pin to GND.1.
  4. Both LEDs turn on together. Symptom: the two LEDs blink in step, not in alternation. Cause: the second pin receives the same level as the first. Fix: write the opposite level, using 1 and 0 in the two phases, as in the solution.
  5. Only one of the two delays is changed. Symptom: the LED is on for 100 ms but off for 500 ms, so it looks lopsided and the frequency is not 5 Hz. Cause: the on time and off time are separate calls to sleep_ms, and one of them was missed. Fix: change both delays, or better, define one constant for the half period and use it in both places, as the solution does.
You changed the timing of a running firmware and added a second LED to the circuit, then saw both change in the simulator. That is the edit, build, observe loop you will use for the rest of the course.

In real projects

Teams use a blink, or a steady "heartbeat" LED, as the first sign of life on a new board, and many production products keep one so a technician can see that the firmware is alive. The code you wrote is the same kind of code, with the pin number taken from a board header rather than typed in. Professional firmware never hard-codes a pin number across the source. It defines it once, as you did with LED_PIN, so a board revision changes one line.

Code review looks for the same things you practised here. A reviewer checks that every pin is initialised and its direction set before use, that the time constants are named, and that the comments explain why, not just what. A blocking sleep_ms in a main loop is a normal choice for a blink, and a red flag in code that must also read sensors or respond to buttons. Lesson 55 deals with that trade-off.

In interviews, expect a question along the lines of how you would toggle a pin without the SDK. A strong answer names the register that the SDK writes, explains that a single write to a set or clear register changes one bit without disturbing the others, and says why this avoids a read-modify-write race with an interrupt. Lesson 47 covers writing registers through pointers, and lesson 57 covers the interrupt case.

Summary

  • gpio_init prepares a pin and leaves it an input; gpio_set_dir(pin, GPIO_OUT) makes it drive its level.
  • gpio_put(pin, 1) sets a pin high by writing its bit to the SIO set register; 0 uses the clear register.
  • sleep_ms blocks for the given milliseconds. A period is one on-and-off cycle; frequency is 1 ÷ period.
  • 5 Hz is a 200 ms period, so 100 ms on and 100 ms off. Counting state changes gives twice the true frequency.
  • An LED needs a series resistor. With 3.3 V, a 2.0 V forward voltage and 220 Ω, the current is about 5.9 mA.
  • The anode goes to the pin and the cathode to the resistor. The LED conducts only in that direction.
  • The Pico's default UART uses GP0 for transmit and GP1 for receive, and printf sends its output there.
  • Build before you simulate. The simulator loads whatever blink.elf is on disk.
