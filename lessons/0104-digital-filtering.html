Digital filtering: moving average and IIR

A potentiometer or thermistor reading jitters from sample to sample. Two short C functions smooth it, and one of them needs no loop at all. Knowing their step response tells you how much lag you are buying.

By the end of this lesson you can implement a moving average with a running sum and a first-order IIR (exponential moving average) in integer C, predict the step response of each from its equation, and say what a median filter removes that the others cannot.

Where we are, and why filtering matters

Lesson 58 showed how the ADC turns a voltage into an integer code. Lesson 21 showed how to hold fractions in integers, and lesson 80 showed how to test C on the PC before it runs on the Pico. This lesson uses all three. It also builds on lesson 8, because a thermistor is read through a voltage divider.

The problem is noise. A dryer's thermistor, read through a divider, gives a code that jitters by a few counts from one sample to the next, even when the air temperature is steady. If the heater controller of lesson 105 uses that jitter directly, it reacts to electrical hash rather than to the real temperature, and the heater switches on and off for no reason. A filter is a short program that turns the noisy stream into a smoother one before the control code sees it.

Real printer firmware does the same job. The Klipper configuration reference documents a smooth_time option in its heater sections, which averages temperature measurements over a time window to reduce the impact of measurement noise, and a pid_deriv_time option that does the same for the PID derivative term (Klipper Config Reference). The option names are the ones a Klipper user meets; the lesson's filters are the same idea in a few lines of C.

Concept 1: samples, sample rate and aliasing

The ADC gives you a number each time you ask for one. The number of samples per second is the sample rate. A filter sees only those samples. It never sees the analogue signal between them, and that has two consequences that every filter inherits.

The first consequence is the limit on what you can measure. A signal must change more slowly than half the sample rate, and that half is the Nyquist frequency. The second consequence is aliasing. A signal above the Nyquist frequency does not vanish when sampled. It folds down and appears as a slower signal that was never there. A 90 Hz hum sampled at 100 samples per second shows up as a 10 Hz wobble, because 100 − 90 = 10, and no filter can tell that wobble from a real 10 Hz change. Aliasing happens during sampling, before any filter runs. A digital filter cannot remove an alias afterwards. Sample fast enough, or filter the analogue signal first with an RC low-pass filter (lesson 13).

So a filter is for the noise that is inside the band you care about: jitter, spikes and hum that is slow compared with the sample rate. It cannot repair a signal that was undersampled.

Concept 2: FIR and IIR filters

A digital filter computes each output from past inputs, and sometimes from past outputs too. Its impulse response is the output you get when the input is a single sample of 1 followed by zeros. That response tells you how long an input keeps influencing the output, and it is the key to comparing filters.

There are two families. A FIR filter (finite impulse response) computes its output only from a finite window of past inputs. Once an input has left the window, it has no effect at all. A IIR filter (infinite impulse response) feeds its own previous output back in. An input's influence decays over time but never reaches exactly zero, so the memory has no end. The moving average is the FIR case. The exponential moving average is the simplest IIR case.

Moving average: a running sum, with a ring buffer

A moving average of N samples is the mean of the last N inputs. The naive code adds up the N values on every sample, so its work grows with N. The running-sum version keeps the total from the last update, and changes it by two numbers: it adds the newest sample and subtracts the one that just left the window.

To know which sample is leaving, the filter stores the last N inputs in a ring buffer. A ring buffer is an array with a write index that wraps back to zero at the end, so the slot the index points at always holds the oldest sample. Each update then costs the same whatever N is. Computer scientists write that cost as O(1), which means constant time, and it is the reason the running sum is worth the extra state. 

int32_t ma_update(moving_avg_t *m, int32_t x) {
    m->sum += x - m->buf[m->idx];          /* add the new sample, remove the oldest */
    m->buf[m->idx] = x;                    /* the oldest slot now holds the newest sample */
    m->idx = (uint8_t)((m->idx + 1u) % m->window);   /* advance and wrap: this is the ring */
    return m->sum / (int32_t)m->window;      /* the mean of the window */
}

Read the code line by line. Line 1 reads buf[idx], which is the oldest sample, and adds the new value and subtracts that old one in one statement. The order inside the statement is safe, but the order of the next two lines is not: line 2 overwrites the slot, so it must come after line 1 (the first common mistake below shows what goes wrong). Line 3 stores the newest sample in the slot the oldest one just vacated. Line 4 moves the index on, and the % wraps it from N − 1 back to 0. The cast keeps the index in the one byte the struct declares. Line 5 divides the sum by the window size. C integer division truncates toward zero, which is fine for ADC counts because they are never negative.

Worked example: a step through a window of four

Start with a window of N = 4, with every slot at zero, and feed in a step: the input jumps from 0 to 1000 and stays there. The table follows the sum and the output sample by sample. The number removed is the value the slot held before it was overwritten.

The output rises in four equal quarters and then holds. At sample 5 the first 1000 is removed and a new 1000 is added, so the sum does not change. The filter is exact, so the output lands on 250, 500, 750 and 1000 with no rounding. The lag of a moving average is about (N − 1) ÷ 2 samples. For N = 4 that is 1.5 samples: the output's centre of mass trails the input by that much. The falling step behaves the same way in reverse, with 750, 500, 250 and 0 as the four inputs of zero leave the window.

IIR: the exponential moving average

The first-order IIR filter, usually called the exponential moving average (EMA), feeds its own output back. Its equation is one line:

y += (x − y) × α

Here x is the new input, y is the stored output (the filter's state), and α, the smoothing factor, is a number between 0 and 1. Each new output moves a fraction α of the way from the old output towards the input. A small α smooths heavily and reacts slowly. A large α follows the input closely and passes more noise. When α is a power of one half, α = 1 ÷ 2k, the multiply becomes a shift: y += (x - y) >> k.

Take k = 3, so α = 1/8. After one sample, the output has moved 1/8 of the way. After n samples of a step from 0 to 1000, the output is 1000 × (1 − (7/8)n), because the gap to the input shrinks by 7/8 each time. The table gives the values, rounded to whole codes.

The response never reaches 1000 in a finite time. The time constant τ is the number of samples the output takes to cover 63 % of the step: τ = −1 ÷ ln(1 − α). For α = 1/8 that is 7.49 samples. The rule of thumb "about 2k samples", here 8, is close but not exact. The same numbers give a cutoff frequency, the frequency where the filter starts to attenuate, of about −fs ln(1 − α) ÷ 2π. At a sample rate of 100 Hz that is 2.1 Hz.

Figure 1 plots the two step responses on the same axes. The moving average reaches the input after four samples, and the EMA is still climbing after eight. Each one trades lag for smoothing in a different way, and the plot shows the trade directly.

Why the shift matters. The Cortex-M0+ core has no divide instruction, so a / in C becomes a call to a helper routine. The RP2040 adds an integer divider in its SIO block, and the Pico SDK maps the compiler's divide helper onto it (Pico SDK 2.3.1, pico_divider/divider_hardware.S). Lesson 21 explains that divider. Even so, a shift is the cheapest way to divide by a power of two, and a filter that runs every sample on a small core should use it.

Fixed point and the dead band

The Cortex-M0+ has no floating-point unit (lesson 21 compares the Arm cores), so a float EMA runs in software and costs many cycles per sample. Integer arithmetic is the normal choice. The integer EMA has one serious problem, though. Take y += (x - y) >> 3 with y = 0 and a steady input of 5. The difference is 5, and 5 ÷ 8 truncates to 0, so y never moves. The filter stalls at zero, five codes short of its input, and it stays there forever. The range of inputs that the update rounds to zero is a dead band.

The fix is to keep the state with extra fraction bits. The state holds y × 256, which is the same idea as the Q format of lesson 21, with eight fraction bits. A step of one unit in the state is then 1/256 of an output code, so the update can move the state even when the input is only a few codes away. The output is the state shifted back down by 8 bits, and that shift needs rounding. Adding 128 before the shift, which is half of 256, rounds to the nearest code.

Rounding matters for a steady input. The update stops moving once the gap 1280 − state is smaller than 8, so the state settles between 1273 and 1280. Truncation reads 4 for any state from 1273 to 1279, so a steady 5 would show as 4. Rounding reads 5 for the same states, which is what the host test test_ema_converges_to_a_small_steady_input checks.

Here is the fixed-point EMA with numbers. Prime the state at 0, as the host test does, and feed a steady input of 5. The target is 5 × 256 = 1280. The first update adds (1280 − 0) ÷ 8 = 160 to the state, and the output is (160 + 128) ÷ 256 = 1 after rounding. The second update adds (1280 − 160) ÷ 8 = 140, so the state is 300 and the output is still 1. The state keeps climbing, and the output first reaches 5 at sample 18, when the state passes 1152, which is 4.5 codes. The integer version, from the same start, never moves at all. 

/* state holds y * 256 (EMA_FRAC_BITS = 8) */
int32_t target = x * (1 << 8);                      /* scale the input into the state's units */
if (!e->primed) { e->state = target; e->primed = true; }
else  e->state += (target - e->state) >> e->k;   /* the IIR update, alpha = 1 / 2^k */
return (e->state + 128) >> 8;              /* round to nearest on the way out */

Line by line: the first line scales the input by 256, so it lives in the same units as the state. The if primes the state on the first call, so it starts at the first reading and not at zero (common mistake 3 explains why). The else applies the IIR equation with the shift. The last line adds half of 256 and shifts by 8, which divides by 256 with rounding. Notice that the state is never divided by 256 inside the loop. Only the output is, so the fraction bits survive from one sample to the next.

Right-shifting a negative signed value is implementation-defined in C, and gcc shifts arithmetically. Keep these filters on non-negative signals, or check the compiler's behaviour before you rely on it.

Median of three: removing spikes

A loose wire, a switching transient or a noise burst gives one wild sample. A moving average smears that spike over its whole window: an 8-sample average adds one-eighth of the spike to each of eight outputs. An EMA follows the spike at one-eighth of its size and then decays slowly. A median filter removes a lone spike completely, because the median of a set of values ignores the most extreme ones.

For a window of three samples, the median is the middle value once the three are sorted. The median of (10, 1000, 10) is 10, so the spike is gone. The cost is a delay of one sample on a real step, because the median needs the new value and the one before it. A worked sequence shows both effects. The inputs 10, 10, 10, 1000, 10 give the outputs 10, 10, 10, 10, 10. The inputs 10, 10, 10, 20, 20 give 10, 10, 10, 10, 20: the real edge arrives one sample late. Use the median first and the averaging second, so the spike never reaches the average. 

int32_t median3_update(median3_t *m, int32_t x) {
    m->hist[0] = m->hist[1];               /* shift the three-sample history */
    m->hist[1] = m->hist[2];
    m->hist[2] = x;
    if (m->count < 2u) { m->count++; return x; }   /* no full window yet */
    int32_t a = m->hist[0], b = m->hist[1], c = m->hist[2];
    return max32(min32(a, b), min32(max32(a, b), c));  /* median, without sorting */
}

Line by line: the first three assignments keep the last three inputs in a small history, oldest first. The if passes the input straight through for the first two calls, because there are not yet three samples to compare. The return line computes the median without sorting. min32(a, b) is the smaller of the two oldest values. max32(a, b) is the larger, and min32(max32(a, b), c) is the smaller of that larger value and the newest one. The outer max32 then picks the larger of the two results, which is the middle value of the three. Check it on (10, 1000, 10): the result is 10. On (2, 9, 5) it gives 5, the middle of the three.

Hint for the moving average

Subtract the oldest sample before you overwrite its slot. If you overwrite first, you subtract the new value from itself, the sum never changes, and the output stays at zero for any input.

Hint for the EMA

On the first call, set the state to the first sample rather than to 0. Otherwise the output ramps up from 0 and the step-response tests fail by the first few samples.

Common mistakes and how to spot them

These are the mistakes that a first implementation of these filters usually contains. Each one has a symptom you can see in the test output, the serial monitor or the spreadsheet.

Mistake 1: overwriting the slot before subtracting it

If the moving average stores the new sample first and then does sum += x - buf[idx], it subtracts the value it has just written. The sum stays at zero, and the output stays at zero for any input. The symptom is a flat zero in the ma8 column, while raw moves. The fix is the order in the running-sum code: add the new sample and subtract the old one before the write. The host test test_ma_step_response_rises_in_quarters fails with 0 instead of 250 on the first update.

Mistake 2: an integer EMA with no fraction bits

The integer update y += (x - y) >> 3 stalls once the gap to the input is smaller than 8 codes. With an input of 5 it stays at 0 forever. The symptom is an ema column that stops short of the raw column and never moves again. The host test test_integer_ema_without_fraction_stalls repeats the same integer equation and shows the stall in its assertion. The fix is the scaled state with rounding on the way out, as in the code above.

Mistake 3: starting the EMA at zero

If the state starts at zero, a steady reading of 1000 comes out as 125, 234, 330 and 414 in the first four samples, which is the step response of an empty filter. For a sensor that starts at room temperature, the first second of readings is wrong, and a controller that uses them will act on a temperature that does not exist. The symptom is a slow ramp at start-up that the reading does not have. The fix is to prime the state from the first sample, which the primed flag in the project does.

Mistake 4: averaging before removing spikes

If the moving average reads the raw signal and the median is computed afterwards, the spike is already spread across eight outputs. The spike of 600 codes appears as a rise of 600 ÷ 8 = 75 codes in the ma8 column for eight rows, and the median filter downstream cannot take it back. The symptom is a rectangular bump in the averaged column at every spike. The fix is the order the project uses: median first, then the averaging.

Mistake 5: a window of zero, or a window larger than the buffer

A window of zero makes the program divide by zero when it computes sum / window, and C leaves division by zero undefined. A window larger than the buffer writes past its end. Both are bugs in the configuration, not in the arithmetic, and the symptom is a crash or nonsense values that depend on the compiler. The fix is to clamp the window in the init function, as ma_init does, so the function cannot be given a bad size.

In real projects

Professional firmware filters sensor readings in the driver layer, close to the ADC, and documents each filter's time constant or cutoff next to the code. A reviewer asks two questions of every filter: what is the lag in samples or seconds, and what happens to the control loop's stability when that lag is added to the loop's own delay. A filter with a long time constant inside a fast PID loop can make a stable loop oscillate, so the filter and the loop are tuned together (lesson 105).

Reviewers also expect the filter to come with tests. The host tests in this lesson use the step response as the test, because a step response shows in one picture how fast a filter moves, how far it goes, and whether it lands exactly on the input. The same tests run on the PC in milliseconds, which is why the project does its arithmetic there first. Klipper's documented smooth_time and pid_deriv_time options are the same design choice made in a shipping product: a documented window, applied to the measurement before the control law uses it.

In interviews, the moving average without a loop is a common question, because it tests whether you know the running sum and the ring buffer. The answer below is the one to practise.

Summary

  • A filter sees samples, so it can remove noise inside the band of your signal, but it cannot undo aliasing from undersampling.
  • A moving average is FIR: a running sum and a ring buffer give constant cost per sample. Its lag is about (N − 1) ÷ 2 samples.
  • A first-order EMA is IIR: y += (x − y) × α, and with α = 1 ÷ 2k it is a shift. Its time constant is −1 ÷ ln(1 − α), about 7.5 samples for k = 3.
  • An integer EMA stalls in a dead band. Keep 8 fraction bits in the state, and round when you shift back down.
  • Prime the EMA from the first sample, so that it does not ramp up from zero.
  • A median of three removes a lone spike completely, at the cost of one sample of delay on a real edge. Run it before any averaging.
  • Subtract the old sample before you overwrite its slot, and clamp the window in the init function.
You wrote a moving average without a loop, an integer IIR with the rounding that keeps it out of the dead band, and a median that removes spikes. The host tests prove the step responses, and the same C runs on the Pico.

"Implement a moving average without a loop." Answer out loud in 60 seconds, then compare.

Model answer

Keep a ring buffer and a running sum. On each sample, add the new value, subtract the value that the write index is about to overwrite, store the new value in that slot, advance the index with wraparound, and divide the sum by the window size. Each update is one add and one subtract, so the cost is constant. Mention the start-up: the buffer begins as zeros, so the first outputs ramp up unless you count how many samples you have seen.
