Digital filtering: moving average and IIR

A potentiometer or thermistor reading jitters from sample to sample. Two short C functions smooth it, and one of them needs no loop at all. Knowing their step response tells you how much lag you are buying.

By the end of this lesson you can implement a moving average with a running sum and a first-order IIR (exponential moving average) in integer C, predict the step response of each from its equation, and say what a median filter removes that the others cannot.

The idea

The ADC gives you a number every time you ask, at a fixed rate. That rate is the sample rate, and the signal you care about must change more slowly than half of it. A sine wave at more than half the sample rate does not disappear; it folds down to a lower frequency and looks like a different signal. That fold is aliasing, and the limit of half the sample rate is the Nyquist frequency The Scientist and Engineer's Guide to DSP. Aliasing happens inside the sampling, before any filter runs. A digital filter cannot remove an alias, so sample fast enough, or filter the analogue signal before the ADC with an RC low-pass (lesson 13).

A digital filter is a short program that turns the sample stream into a smoother one. Two families cover most of the work in sensor code. A FIR (finite impulse response) filter averages a window of past inputs. An IIR (infinite impulse response) filter feeds its own previous output back in, so its memory never ends. The moving average is the FIR case, and the exponential moving average is the simplest IIR case.

Moving average: a running sum, O(1)

A moving average of N samples is the mean of the last N inputs. The naive version adds up N values on every sample, which costs work proportional to N. The running-sum version keeps the total and changes it by two numbers: add the newest sample, subtract the one that just left the window. The window itself is a ring buffer, an array with a write index that wraps around. Each update then costs the same whatever N is. 

int32_t ma_update(moving_avg_t *m, int32_t x) {
    m->sum += x - m->buf[m->idx];   /* add the new sample, remove the oldest */
    m->buf[m->idx] = x;             /* the oldest slot now holds the newest sample */
    m->idx = (m->idx + 1u) % m->window;   /* wrap around: this is the ring */
    return m->sum / (int32_t)m->window;
}

A step from 0 to 1000 into a window of 4 reads 250, 500, 750, 1000, one quarter of the way in each sample, and then holds. The output rises in N equal steps, and the lag is about (N − 1)/2 samples. The filter has an exact response, so you can check it with a test, which the Try it section does.

IIR: the exponential moving average

The first-order IIR filter feeds its own output back. Its equation is one line:

y += (x − y) × α, and with α = 1 / 2k, the code is y += (x - y) >> k.

Each new output moves a fraction α of the way from the old output to the input. With α = 1/8 (k = 3), the response to a unit step falls by 7/8 each sample, so the output after n samples is 1 − (7/8)n. The time constant τ, the number of samples to reach 63 % of a step, is −1 / ln(1 − α). For α = 1/8 that is 7.49 samples, close to but not equal to 2k = 8. The cutoff frequency at sample rate fs is about −fs ln(1 − α) / 2π. At 100 Hz that is 2.1 Hz.

A filter that multiplies by 1/8 with a shift needs no multiplier and no divider, which matters on a chip with no hardware divide. The Cortex-M0+ has no hardware divide, so each / costs a software routine (lesson 21 explains why). The moving average above has one divide per sample; a window of a power of two, with a shift in place of the divide, avoids it.

The fixed-point trap

The Cortex-M0+ has no FPU (lesson 26 and the Arm processor comparison table), so a float EMA runs in software and costs time on every sample. Integer arithmetic is the normal choice. The integer EMA has a problem, though. With y += (x - y) >> 3, if the input is 5 and the output is 0, then (5 − 0) >> 3 is 0, and the output never moves. The filter stalls 5 codes short, in a dead band.

The fix is to keep the state with extra fractional bits. Store y multiplied by 256, so one step is 1/256 of a code and small errors still move the state. Round when you shift back down, so a steady 5 reads 5 and not 4. The code in filters.c does both. 

/* state holds y * 256 (EMA_FRAC_BITS = 8) */
int32_t target = x * (1 << 8);
state += (target - state) >> k;
return (state + 128) >> 8;      /* round to nearest on the way out */
Right-shifting a negative signed value is implementation-defined in C (gcc shifts arithmetically). Keep these filters on non-negative signals, or check the compiler's behaviour before you rely on it.

Median of three: removing spikes

A loose wire or a noise burst gives one wild sample. A moving average smears it over N outputs; an EMA follows it at 1/8 of its size. A median of three samples removes a lone spike completely: the middle value of (10, 1000, 10) is 10. The cost is a one-sample delay on a real step, because the median needs the new value and the one before it. Use the median first and the averaging second, so the spike never reaches the average.

Hint for the moving average

Subtract the oldest sample before you overwrite its slot. If you overwrite first, you subtract the new value and the sum never changes.

Hint for the EMA

On the first call, set the state to the first sample rather than to 0. Otherwise the output ramps up from 0 and the step-response tests fail by the first few samples.

Model answer

Keep a ring buffer and a running sum. On each sample, add the new value, subtract the value that the write index is about to overwrite, store the new value in that slot, advance the index with wraparound, and divide the sum by the window size. Each update is one add and one subtract, so the cost is constant. Mention the start-up: the buffer begins as zeros, so the first outputs ramp up unless you count how many samples you have seen.
