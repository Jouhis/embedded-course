Von Neumann vs Harvard architecture

Shared and separate paths between the core and memory

By the end of this lesson you can say whether a Cortex-M core can fetch an instruction and load data in the same cycle, name the bus that proves it, and count the bus transfers in a short program.

The paths between the core and memory

Lessons 23 to 26 built the parts inside the CPU: gates, flip-flops, registers and the ALU. None of them does anything useful without a program and data, both of which live in memory that the CPU reaches over wires called a bus. This lesson is about those wires, because the way a core connects to memory decides how fast its instructions can run.

Many problems in this course come down to the bus. A timer interrupt that runs too long, a loop that misses its deadline or a function that speeds up after moving into RAM can all be traced to how many bus transfers the core makes and whether they can overlap. Lesson 36 adds caches and wait states to the picture, and lesson 37 shows the bus fabric, but the first thing to understand is the number of paths. Given a short program, you should be able to say how often the core uses the bus and which of those uses can happen at the same time.

Buses and transfers

A bus is a group of wires carrying an address, data and control signals between the CPU and a memory or peripheral. A transfer is one use of it, in which the CPU places an address on the wires, the target responds and a word of data moves. Every instruction needs at least one transfer, the fetch, which reads the instruction's bits from memory, and many instructions need a second, a load or a store, to read or write a value in memory.

With only one bus, only one transfer can happen at a time, so the fetch of the next instruction must wait for the current instruction's data transfer to finish, or the other way round. A design with one memory holding both program and data, reached over one path, is called a von Neumann architecture, after the computer pioneer whose name it carries. Its cost is that instructions and data take turns on the same wires.

Separate instruction and data paths

A Harvard design separates the two, fetching instructions from one memory over one path and data from another over a second path. The core can then fetch the next instruction and load data for the current one in the same cycle, because the two transfers do not share wires. The names come from early computer designs, and what matters in practice is the bus count.

Imagine a cook whose recipe book and pantry are in another room behind one narrow door. Each trip fetches either the next recipe line or an ingredient, never both, so the cook often waits at the door, which corresponds to a single shared bus. A Harvard kitchen has two doors, one to the recipe shelf and one to the pantry, and both trips can happen at the same moment. The comparison suggests two separate rooms, however, whereas a Cortex-M core reaches the same addresses through both doors, as the next paragraph explains.

One point is often misread: the names describe the paths, not the address map. A Cortex-M core has a single address space, in which a given address refers to one location whether it is read as an instruction or as data, and both designs share that map. The Harvard split concerns how many buses reach memory rather than whether the addresses are separate, as the glossary entry for Harvard architecture also states.

The four bus interfaces of the Cortex-M3

The Cortex-M3 is a Harvard design, which PM0056 Rev 7, section 1.3, calls a 3-stage pipeline Harvard architecture. Its Technical Reference Manual lists the feature as "Harvard processor architecture enabling simultaneous instruction fetch with data load/store" (Arm Cortex-M3 TRM DDI0337G, section 1.2.1), and the same section adds a three-stage pipeline and a prefetch unit, to which lesson 28 returns.

The bus interface chapter of the TRM, section 12.1, lists four interfaces, each with its own job:

  • ICode (section 12.3) is a 32-bit AHB-Lite bus for instruction fetches and vector fetches from the code memory space, 0x00000000 to 0x1FFFFFFF, which is where flash sits on most Cortex-M3 chips.
  • DCode (section 12.4) is also a 32-bit AHB-Lite bus, carrying data and debug accesses to the same code space. Compilers place constants called literal pools in the code space, so loading a constant uses this bus.
  • System (section 12.5) is a 32-bit AHB-Lite bus for the system space, 0x20000000 to 0xDFFFFFFF and 0xE0100000 to 0xFFFFFFFF, where SRAM and most peripherals sit. Instruction fetches as well as data and debug accesses can all use it.
  • External Private Peripheral Bus is an APB bus for the debug components at 0xE0040000 to 0xE00FFFFF, which normal code does not use.

The Harvard property lies in the first two buses. Because ICode and DCode are separate, the core can fetch the next instruction on ICode while loading a constant on DCode. The TRM recommends that external arbitration give DCode priority over ICode when the two share a memory, a detail that hints at how the memory system is built and that matters for the timing of real code.

One consequence surprises beginners. The TRM states that instruction fetches over the System bus are registered, costing an extra cycle, and that back-to-back instruction fetches from the System bus are not possible, whereas fetches over ICode are not registered, so its advice is that performance-critical code should run from the ICode interface. The same function can therefore run at different speeds depending on whether the linker placed it in flash or in SRAM, and lesson 38 covers the address ranges that decide which bus a fetch uses.

The single memory port of the Cortex-M0+

The Cortex-M0+ in the RP2040 is different. The Arm datasheet describes a single 32-bit AMBA-3 AHB-Lite system interface giving the core access to the whole system, lists the bus architecture as "AHB-Lite (Von Neumann bus architecture)", and states that instructions are fetched only through the AHB-Lite interface (Arm Cortex-M0+ processor datasheet, the features table and the interfaces section). The core thus has one port for both code and data.

The RP2040 chip, however, has many paths. Section 2.3 of its datasheet shows each of the two Cortex-M0+ cores with its own 32-bit AHB-Lite port for code fetches, loads and stores, and section 2.1 describes the bus fabric, a crossbar connecting four bus masters, the two cores and two DMA ports, to ten downstream ports, with up to four transfers possible in one cycle. Each core still has one memory port, so the chip is more parallel than the core.

The RP2040's GPIO block is a special case. The single-cycle IO block, SIO, sits on each core's IOPORT, a separate bus at addresses 0xD0000000 to 0xDFFFFFFF, and the datasheet explains that the SIO is not connected to the main system bus because of its timing requirements (RP2040 datasheet, section 2.3 and section 2.3.1). Setting a GPIO output from C uses that separate path.

Worked example: bus transfers in a store and reload

The simulator program in this lesson has five instructions: the first two load values into registers, the third stores a value to RAM, the fourth loads it back and the fifth halts. We count the transfers on one shared bus for the first four, as the simulator's left timeline does, and it is worth guessing the total before starting.

  1. Fetch MOV R2, #0x20000010. One transfer reads the instruction from memory. Running total: 1.
  2. Fetch MOV R0, #7. One transfer, and no data transfer is needed because the value is inside the instruction. Running total: 2.
  3. Fetch STR R0, [R2]. One transfer for the instruction. Running total: 3.
  4. Write the STR's data. The store writes the value 7 to the address in R2, 0x20000010, in one transfer. Running total: 4.
  5. Fetch LDR R1, [R2]. One transfer. Running total: 5.
  6. Read the LDR's data. The load reads the word at 0x20000010 back into R1 in one transfer. Running total: 6.

The total is six, and the beginner's error is to count only the four fetches. The data transfers are real, and on a shared bus each one blocks a fetch, whereas on a Harvard core the store's data write and the next fetch use different buses and can overlap. The number of transfers stays the same, but the time they occupy on the wires can shrink, which is the whole reason for the design.

A loop shows the effect more clearly. Suppose a loop body has four instructions, one of them a load: on one shared bus that is four fetches and one data read, five transfers per iteration. On an idealised Harvard core the data read can overlap a fetch, so the bus is busy for fewer cycles per iteration. Real numbers depend on wait states and caches, covered in lessons 36 and 37, but the bus count comes first, and it is why a loop with a load costs more than one without.

  1. Fetch MOV R2, #0x20000010: one transfer on either design. Its value is inside the instruction, so it needs no data transfer.
  2. Fetch MOV R0, #7: one more fetch.
  3. Fetch STR R0, [R2]: the third fetch.
  4. The STR writes 7 to 0x20000010. On one shared bus that write takes a slot of its own, and the next fetch waits. With separate buses, the write and the fetch of LDR happen in the same slot.
  5. Fetch LDR R1, [R2]. On the Harvard side, the LDR's data read overlaps the next fetch.
  6. The LDR reads 7 back: on the shared bus, its own slot again. Counting only the four fetches would give 4; the real total is 6.
  7. Both designs move the same six transfers. The shared bus needs six slots, and the idealised Harvard core five, because data and instructions travel on different wires.

Try it in the CPU simulator

The simulator in this lesson is a simplified teaching model that runs a small instruction subset on one memory map. Under the registers it draws two bus timelines for the same program side by side. On the left every transfer goes over one shared bus, as on a von Neumann core, and on the right an idealised Harvard core fetches on an instruction bus and loads and stores on a data bus, so the next instruction's fetch can share a slot with the previous instruction's data transfer. The program stores 7 into RAM and loads it back.

  1. Before pressing anything, count the transfers on one shared bus for the first four instructions, with one fetch per instruction and one extra transfer for each STR and each LDR. You should get six, so write the number down.
  2. Press Instruction once. The register row shows R2 = 0x20000010, and both timelines show one fetch in slot 1. Press it again, giving R0 = 7 with both timelines at slot 2; a MOV needs no data transfer, so the two designs are still level.
  3. Press it a third time, and the memory row shows the word at 0x20000010 holding 7, written by the STR. The shared bus places the write in slot 4, after the fetch in slot 3, while on the Harvard side the write is on the data bus in slot 4 and the instruction bus is free in that slot.
  4. Press it a fourth time, giving R1 = 7 as the LDR reads the value back. On the shared bus the LDR's fetch had to wait for the write, so it is in slot 5 and the read in slot 6, whereas on the Harvard side the fetch went into slot 4 beside the write and the read is in slot 5. Both sides count six transfers, but the shared bus needs six slots and the Harvard core five.
  5. The fifth instruction, B ., halts the program. Press Instruction once more and watch where its fetch lands, slot 7 on the shared bus and slot 5 on the Harvard side next to the read. After that, stop pressing Instruction: the simulator shows a branch to itself, which parks the program there and is not an error.
Hint

Each of the four instructions needs one fetch, the STR and the LDR each need one data transfer, and the two MOVs need none. Four fetches plus two data transfers make six.

The simulator has one memory map and no cache, and its slots are not clock cycles. Its Harvard side is idealised, with no wait states and every fetch able to overlap a data transfer. Real Cortex-M cores differ, the M3 being Harvard and the M0+ having one AHB-Lite port, and the RP2040's bus fabric has its own crossbar, so the real chips do not count transfers the same way. Use the slot counts to reason about the design rather than as a cycle prediction.

Common mistakes and how to spot them

Harvard taken to mean separate address maps

You assume that the address of a constant in flash cannot equal an address in RAM, and a debugger that shows one location through two views becomes confusing. Both designs share one address map, and the Harvard split concerns the buses that reach the same addresses. Lesson 38 covers the memory map and which ranges are flash and which RAM.

Code moved to RAM expected to run as fast

After moving a loop into SRAM to fix a timing problem, it takes longer rather than shorter. The cause is the System bus, whose instruction fetches are registered and cannot be back to back, as section 12.5.6 of the TRM states. Keep time-critical code in flash on the ICode bus, or measure the change before accepting it.

Only the fetches counted

An estimate of a loop's bus use comes out too low by the number of loads and stores, so the store and reload program seems to need four transfers instead of six. Count a transfer for every load and store in addition to every fetch.

One core's bus applied to every Cortex-M

You claim that an M0+ can overlap a fetch with a load, and a reviewer points out that the M0+ fetches only through its single AHB-Lite port. Check the core in your chip: the M3 is Harvard, while the RP2040's Cortex-M0+ has one memory port, with the chip's crossbar and IOPORT being separate matters. Base the bus count on the core you are targeting.

Code placement and bus timing in real projects

Linker scripts decide where code and data go, with code in flash on the ICode bus and variables in SRAM on the System bus, and the startup code that runs before main() is covered in lesson 42. A reviewer who sees a function placed in RAM asks why. The usual reason is speed, and the claim must be measured, because the System bus can be slower for fetches, as shown above.

Performance work starts with the bus count. A senior engineer reads a hot loop, counts its loads and stores, and asks whether they can overlap with fetches on this core, then checks the wait states and the memory the code runs from in the chip's reference manual rather than in a general description of the architecture. For an STM32F103, RM0008 Rev 21 covers the flash wait states in section 3.3.3.

Summary

  • A bus is a set of shared wires, a transfer is one use of it, and every instruction needs at least one fetch.
  • Von Neumann means one memory and one path, so fetches and data accesses take turns, while Harvard provides separate paths for instructions and data.
  • Both designs share one address map, so the split concerns buses rather than addresses.
  • The Cortex-M3 is Harvard, with ICode, DCode and System interfaces described in TRM section 12.1.
  • Instruction fetches over the System bus are registered and cannot be back to back, so code runs faster from flash on the ICode bus.
  • The Cortex-M0+ core has one AHB-Lite system port for code and data, and the RP2040 adds a crossbar and a separate IOPORT at chip level.
  • Count every fetch, load and store as a transfer when estimating a loop.
