Von Neumann vs Harvard architecture

Every instruction is fetched from memory and most of them also touch memory. How many paths the core has to memory decides what a loop costs.

By the end of this lesson you can say whether a Cortex-M core can fetch an instruction and load data in the same cycle, name the bus that proves it, and count the bus transfers in a short program.

Where we are and why it matters

Lessons 23 to 26 built the parts inside the CPU: gates, flip-flops, registers and the ALU. None of them does anything useful without a program and data to work on. Those live in memory, and the CPU reaches memory over wires called a bus. This lesson is about those wires, because the way a core connects to memory decides how fast its instructions can run.

Many of the problems in this course come down to the bus. A timer interrupt that runs too long, a loop that misses its deadline, or a function that runs faster after you move it into RAM all come down to how many bus transfers the core must make and whether they can overlap. Lesson 36 adds caches and wait states to the picture, and lesson 37 shows the bus fabric. The first thing to understand is the number of paths.

Given a short program, you should be able to say how many times the core must use the bus, and which of those uses could happen at the same time.

Concept 1: a bus is a set of shared wires

A bus is a group of wires that carry an address, data and control signals between the CPU and a memory or peripheral. A transfer is one use of the bus: the CPU puts an address on the wires, the target responds, and a word of data moves. Every instruction needs at least one transfer, the fetch, which reads the instruction's bits from memory. Many instructions need a second transfer, a load or a store, to read or write a value in memory.

If there is only one bus, only one transfer can happen at a time. The fetch of the next instruction must wait until the data transfer of the current one has finished, or the other way round. A design with one memory that holds both program and data, reached over one path, is called von Neumann architecture, after the computer pioneer whose name it carries. Its cost is that instructions and data take turns on the same wires.

Concept 2: Harvard gives instructions their own path

A Harvard design separates the two. Instructions come from one memory over one path, and data comes from another memory over another path. The core can then fetch the next instruction and load data for the current one in the same cycle, because the two transfers do not share wires. The names come from early computer designs, and for you the bus count is what matters.

One point is often misread. The names describe the paths, not the address map. A Cortex-M core has one address space: a given address refers to one location, whether you read it as an instruction or as data. Both designs share that map. The Harvard split is about how many buses reach the memory, not about whether addresses are separate. The glossary entry for Harvard architecture says the same thing: both designs share one address map.

Concept 3: the Cortex-M3 has four bus interfaces

The Cortex-M3 is a Harvard design (PM0056 Rev 7, section 1.3, calls it a 3-stage pipeline Harvard architecture). Its Technical Reference Manual lists the feature as "Harvard processor architecture enabling simultaneous instruction fetch with data load/store" (Arm Cortex-M3 TRM DDI0337G, section 1.2.1). The same section adds a three-stage pipeline and a prefetch unit, which we return to in lesson 28.

The TRM's bus interface chapter, section 12.1, lists four interfaces, and each one has a job:

  • ICode (section 12.3) is a 32-bit AHB-Lite bus for instruction fetches and vector fetches from the code memory space, 0x00000000 to 0x1FFFFFFF. This is where flash sits on most Cortex-M3 chips.
  • DCode (section 12.4) is also a 32-bit AHB-Lite bus. It carries data and debug accesses to the same code space, 0x00000000 to 0x1FFFFFFF. Compilers put constants called literal pools in the code space, so loading a constant uses this bus.
  • System (section 12.5) is a 32-bit AHB-Lite bus for the system space, 0x20000000 to 0xDFFFFFFF and 0xE0100000 to 0xFFFFFFFF. SRAM and most peripherals sit here. Instruction fetches, and data and debug accesses, can all use it.
  • External Private Peripheral Bus is an APB bus for the debug components, at 0xE0040000 to 0xE00FFFFF. It is not used by normal code.

The Harvard property is the first two buses. Because the ICode and DCode interfaces are separate, the core can fetch the next instruction on ICode while it loads a constant on DCode. The TRM recommends that the external arbitration give DCode priority over ICode when the two share a memory. That detail is a hint about how the memory system is built, and it matters for the timing of real code.

Here is a consequence that surprises beginners. The TRM says that instruction fetches over the System bus are registered, so they take an extra cycle, and that back-to-back instruction fetches from the System bus are not possible. Fetches over the ICode bus are not registered. The TRM's advice is that performance-critical code should run from the ICode interface. So the same function can run at different speeds, depending on whether the linker put it in flash or in SRAM. Lesson 38 covers the address ranges that decide which bus a fetch uses.

Concept 4: the Cortex-M0+ has one memory port

The Cortex-M0+ in the RP2040 is different. The Arm datasheet describes a single 32-bit AMBA-3 AHB-Lite system interface that gives the core access to the whole system. It lists the bus architecture as "AHB-Lite (Von Neumann bus architecture)", and it states that instructions are only fetched using the AHB-Lite interface (Arm Cortex-M0+ processor datasheet, the features table and the interfaces section). The core has one port for code and data.

The RP2040 chip, however, has many paths. The datasheet's section 2.3 shows each of its two Cortex-M0+ cores with its own 32-bit AHB-Lite port, used for code fetch, loads and stores. Section 2.1 describes the bus fabric, a crossbar that connects four bus masters, the two cores and two DMA ports, to ten downstream ports, and it says up to four transfers can take place in one cycle. Each core still has one memory port. The chip is more parallel than the core.

The RP2040's GPIO block is a special case. The single-cycle IO block, SIO, sits on each core's IOPORT, a separate bus at addresses 0xD0000000 to 0xDFFFFFFF. The datasheet says the SIO is not connected to the main system bus because of its timing requirements (RP2040 datasheet, section 2.3 and section 2.3.1). When you set a GPIO output from C, you are using that separate path.

Worked example: counting transfers in a store and reload

Take the simulator program in this lesson. It has five instructions. The first two load constants into registers, the third stores a value to RAM, the fourth loads it back, and the fifth halts. Count the transfers on one shared bus, as the simulator's model does, for the first four instructions.

  1. Fetch the MOV R2, #0x20000010. One transfer to read the instruction from memory. Running total: 1.
  2. Fetch the MOV R0, #7. One transfer. Running total: 2. The MOV needs no data transfer, because its value is in the instruction.
  3. Fetch the STR R0, [R2]. One transfer for the instruction. Running total: 3.
  4. Write the STR's data. The store writes the value 7 to the address in R2, which is 0x20000010. One transfer. Running total: 4.
  5. Fetch the LDR R1, [R2]. One transfer. Running total: 5.
  6. Read the LDR's data. The load reads the word at 0x20000010 back into R1. One transfer. Running total: 6.

The total is six. The beginner's error is to count only the four fetches and get four. The data transfers are real, and on a shared bus each one blocks a fetch. On a Harvard core the store's data write and the next fetch use different buses, so the two can overlap. The count of transfers stays the same, but the time they take on the wires can shrink, which is the reason for the design.

Now the loop case. Suppose a loop body has four instructions and one of them is a load. On one shared bus that is four fetches and one data read, five transfers per iteration. On an idealised Harvard core, the data read for this iteration can overlap a fetch, so the bus is busy for fewer cycles per loop. Real numbers depend on wait states and caches, which lessons 36 and 37 cover. The bus count is the first thing to understand, and it is the reason a loop with a load costs more than a loop without one.

Try it in the CPU simulator

The simulator in this lesson is a simplified teaching model. It runs a small instruction subset on one memory map and does not model separate buses, so it cannot show the overlap. What it does show is what each instruction reads and writes, which lets you count the transfers. The program stores 7 into RAM and loads it back.

  1. Before you press anything, count the transfers on one shared bus for the first four instructions. Count one fetch per instruction, and one extra transfer for each STR and each LDR. You should get six. Write the number down.
  2. Press Instruction once. The register row shows R2 = 0x20000010. Press it again: R0 = 7. Press it a third time: the memory row shows the word at 0x20000010 holding 7, because the STR wrote it. Press it a fourth time: R1 = 7, because the LDR read the value back.
  3. The fifth instruction is B ., which halts the program. Do not press Instruction again: the simulator shows it as a branch to itself, and the program is parked there. Do not treat that as an error.
Hint

Each of the four instructions needs one fetch. The STR and the LDR each need one data transfer, and the two MOVs need none. Add the fetches and the data transfers together: four plus two is six.

The simulator has one memory map, one bus and no cache. Real Cortex-M cores have several buses (Harvard on the M3, one AHB-Lite port on the M0+), and the bus fabric in the RP2040 has its own crossbar. The simulator's "one bus" count is a teaching shortcut. The real chips do not count transfers the same way, so use the count to reason about the design, not as a cycle prediction.

Common mistakes and how to spot them

Mistake 1: believing Harvard means separate address maps. Symptom: you assume that the address of a constant in flash cannot be the same as an address in RAM, and you are confused when a debugger shows two different things at one address. Fix: remember that both designs share one address map. The Harvard split is about the buses that reach the same addresses. Lesson 38 covers the memory map, which says which address ranges are flash and which are RAM.

Mistake 2: expecting a function to run at the same speed from RAM. Symptom: after you move a loop into SRAM, to fix a timing problem, the loop takes longer, not shorter. The cause is the System bus: its instruction fetches are registered and cannot be back to back, as section 12.5.6 of the TRM says. Fix: keep the time-critical code in flash on the ICode bus, or measure the change before you accept it.

Mistake 3: counting only the fetches. Symptom: your estimate of a loop's bus use is too low by the number of loads and stores. In the simulator, the store and reload program gives six transfers, not four. Fix: count a transfer for every load and store, in addition to every fetch.

Mistake 4: applying one core's bus to every Cortex-M. Symptom: you say an M0+ can overlap a fetch with a load, and a reviewer shows that the M0+ fetches only over its AHB-Lite port. Fix: check the core in your chip. The M3 is Harvard. The Cortex-M0+ in the RP2040 has one memory port for the core, and the chip's crossbar and IOPORT are separate things. Write the bus count for the core you are targeting.

In real projects

Linker scripts decide where code and data go. Code goes into flash, which is on the ICode bus, and variables go into SRAM, which is on the System bus. The startup code that runs before main() is covered in lesson 42. A reviewer who sees a function placed in RAM asks why: usually the reason is speed, and the answer must be measured, because the System bus can be slower for fetches, as shown above.

Performance work starts with the bus count. A senior engineer reads a hot loop, counts the loads and stores, and asks whether they can overlap with fetches on this core. They then check the wait states and the memory they run from in the reference manual for their chip, not in a general description of the architecture. For an STM32F103, RM0008 Rev 21 covers the flash wait states in section 3.3.3.

In an interview, the question "what is the difference between von Neumann and Harvard architecture, and which one does a Cortex-M3 use?" is common. A strong answer says that Harvard has separate instruction and data paths, that the M3 has separate ICode and DCode buses plus a System bus, and that both designs share one address map.

Summary

  • A bus is a set of shared wires. A transfer is one use of it, and every instruction needs at least one fetch.
  • Von Neumann means one memory and one path, so fetches and data accesses take turns. Harvard means separate paths for instructions and data.
  • Both designs share one address map. The split is about buses, not addresses.
  • The Cortex-M3 is Harvard. Its ICode, DCode and System interfaces are described in TRM section 12.1.
  • Instruction fetches over the System bus are registered and cannot be back to back, so code runs faster from flash on the ICode bus.
  • The Cortex-M0+ core has one AHB-Lite system port for code and data, and the RP2040 adds a crossbar and a separate IOPORT for the chip.
  • Count every fetch, load and store as a transfer when you estimate a loop.
You counted the bus transfers for a short program, and you can say why a Harvard core can overlap a fetch with a load while a von Neumann core cannot.
