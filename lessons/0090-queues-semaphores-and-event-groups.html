Queues, semaphores and event groups

Tasks need to hand data and signals to each other without sharing variables by hand. A queue carries data, a semaphore carries a signal, and an interrupt can use the FromISR versions of both. Picking the right one rules out several common concurrency bugs.

By the end of this lesson you can send data between tasks with a queue, signal a task from an interrupt with a binary semaphore, use the FromISR calls and portYIELD_FROM_ISR() correctly, and say when an event group is the better choice.

Where we are, and why it matters

Lesson 87 gave you tasks and priorities, and lesson 88 showed what a switch does to the registers. Neither says how two tasks should talk. In the Lab 5 monitor the button is an interrupt, the sensor is a task, and the screen is another task. The button handler must wake the UI task without waiting for it, and the sensor must pass its readings to the UI without writing into the UI's variables. Both needs are met by the kernel objects in this lesson.

The button case needs the most care. A press arrives as an interrupt from the EXTI controller, which lesson 70 introduced. The interrupt runs in the middle of whatever task was running, and it must finish quickly. It cannot wait for the UI task to become ready. It can only hand the press over, and the kernel's FromISR calls are how it does that.

Concept 1: a queue is a copying FIFO

A queue is a fixed-length first-in, first-out list of items. xQueueSend() copies an item in, and xQueueReceive() copies it out. The sender may reuse its variable as soon as the send returns, because the kernel has its own copy of the bytes. That is why a queue is safer than a pointer: passing a pointer to a local variable through a queue is a bug, because the local is gone by the time the receiver runs.

A queue has a fixed length, which is the number of items it can hold, and a fixed item size, which is the number of bytes in each item. The kernel allocates the storage when the queue is created, from the FreeRTOS heap. In queue.c line 529 the allocation is sizeof(Queue_t) plus the queue's storage in bytes, which is length times item size. A queue of length 4 with 4-byte items therefore holds 16 bytes of data, plus the kernel's bookkeeping.

A receiver that finds the queue empty blocks, so it uses no CPU while it waits. Both send and receive take a timeout. portMAX_DELAY means wait forever. On this port it is 0xffffffffUL (portmacro.h, the 32-bit tick case, which the template uses). A timeout of zero means try once and return.

Concept 2: a semaphore is a count, not data

A binary semaphore holds a count of 0 or 1. It means "this event happened, once". A counting semaphore counts events up to a limit you choose, such as the number of free buffers in a pool. A semaphore carries no data. The task that takes it learns that something happened, and nothing else.

A queue is a letterbox: each item is a copy of a letter, with content, and the reader takes the letters out in order. A semaphore is a ticket dispenser: it carries no content at all, only how many tickets are waiting. Use the letterbox when the receiver needs the data, and the dispenser when it only needs to know that something happened, and how often.

A binary semaphore created with xSemaphoreCreateBinary() starts empty. A task that takes it blocks until something gives it. A give while the count is already 1 changes nothing. Two presses before the task runs leave one give, so the task wakes once. A counting semaphore, or a queue of button events, keeps both. Lesson 91 covers the mutex, which is a semaphore with an owner.

The FreeRTOS macros make the semaphore a special queue. xSemaphoreCreateBinary() is xQueueGenericCreate with length 1, an item size of 0 and the binary type (semphr.h line 167), and xSemaphoreGive() sends into that queue with no data. The queue machinery is the same, so the semaphore has the same blocking and timeout behaviour.

Concept 3: an interrupt cannot block

An interrupt runs on the core in the middle of a task, and it must return quickly so the task can continue. If it blocked, the task it interrupted would be stuck behind it, and the interrupt itself has no task to sleep. So an ISR must use the non-blocking form of each call. FreeRTOS provides these as the FromISR versions: xQueueSendFromISR(), xSemaphoreGiveFromISR() and the rest. Each takes a pointer, pxHigherPriorityTaskWoken.

When a FromISR call makes a task ready and that task has a higher priority than the one the interrupt interrupted, the call sets the flag the pointer points to, to pdTRUE. The ISR passes that flag to portYIELD_FROM_ISR() at its end. The macro is defined in portmacro.h as portEND_SWITCHING_ISR (line 98), and line 111 maps portYIELD_FROM_ISR to it. If the flag is set, the port requests a switch when the interrupt returns, so the woken task runs immediately rather than after the next tick. The event-group documentation in event_groups.h shows the same pattern around line 603. 

void EXTI15_10_IRQHandler(void) {
    if ((EXTI->PR & EXTI_PR_PR12) != 0U) {
        EXTI->PR = EXTI_PR_PR12;              /* clear the flag, or the ISR runs again at once */
        BaseType_t woken = pdFALSE;
        xSemaphoreGiveFromISR(button_sem, &woken);
        portYIELD_FROM_ISR(woken);            /* switch now if the button task is more urgent */
    }
}

Read the handler line by line. EXTI->PR is the EXTI pending register, which holds one flag per line. EXTI_PR_PR12 is the bit for line 12, the button on PB12. The if checks that this line is the one that fired, because the same handler serves lines 10 to 15 and the others may be set too. The next line clears the flag by writing 1 to it. The project's comment says the flag is cleared by writing 1, and if it were not cleared, the interrupt would fire again as soon as the handler returned. The vendor reference manual, RM0008 Rev 21, describes the EXTI pending register in section 10.3.6. Each bit is set when the selected edge arrives on its line, and writing a 1 to the bit clears it.

BaseType_t woken = pdFALSE; declares the flag on the ISR's stack, initialised to false. xSemaphoreGiveFromISR(button_sem, &woken) gives the semaphore. In semphr.h line 640 this macro is xQueueGiveFromISR, which does not block and sets woken only if a higher-priority task was waiting on the semaphore. The last line passes that flag to the yield macro. With woken false the call does nothing, and the interrupt returns to the interrupted task.

An ISR that calls the plain xSemaphoreGive() or xQueueSend() is a bug. The plain calls are written for tasks and may block or change the kernel's lists in ways an interrupt cannot allow. The bug often appears to work at first and then fails intermittently. The ISR's NVIC priority must also be numerically equal to or higher than configMAX_SYSCALL_INTERRUPT_PRIORITY, which the template sets to 5 << 4 in FreeRTOSConfig.h line 30. The rule is explained in the next concept.

Concept 4: the interrupt priority limit

Lesson 72 taught that on the NVIC a lower number is more urgent. The FreeRTOS port uses that same number for interrupts, and it adds a limit. An interrupt that calls a FromISR function must have a priority at or below the limit, which means its number must be equal to or higher than the limit. The port's own comment says it directly: numerically low priority numbers are logically high priorities, so the interrupt's number must be equal to or numerically higher than configMAX_SYSCALL_INTERRUPT_PRIORITY. The check is vPortValidateInterruptPriority() in port.c line 766, and it runs from the send and give paths in queue.c.

The template defines the limit as (5 << 4), not as 5. The Cortex-M3 stores priorities in the top bits of an 8-bit field, and the STM32F1 implements only the top four bits, which is what __NVIC_PRIO_BITS at 4 in stm32f103xb.h line 51 says. The shift by 4 puts the priority 5 in those bits. The call NVIC_SetPriority(EXTI15_10_IRQn, 5) in the project does the same shift itself, so the number you pass to NVIC_SetPriority() is 5, not 80.

With four implemented bits there are 16 priority levels, numbered 0 to 15. Level 0 is the most urgent, and level 15 the least. The kernel's own interrupts, SysTick and PendSV, are given the lowest urgency: the port writes portMIN_INTERRUPT_PRIORITY, which is 255, into their priority fields (port.c line 55). The button interrupt at level 5 is therefore less urgent than levels 0 to 4, which are the ones that must not call FromISR functions, and more urgent than the rest.

The port also refuses the default. An interrupt left at priority 0 is the most urgent, and it is above the limit, so a FromISR call from it fails the check. The port's comment calls this out directly: an interrupt that uses the FreeRTOS API must not be left at its default priority of zero.

Concept 5: event groups

An event group is a word of flags. Several sources set bits with xEventGroupSetBits(), and a task waits with xEventGroupWaitBits() for a combination of them, either all of the bits or any of them. The bits are not counted. Setting a bit that is already set changes nothing, and that is the difference from a counting semaphore.

Take a task that acts only when a sensor is ready and the button has been pressed. Give the sensor bit the value 0x01 and the button bit 0x02. The waiter asks for both bits, so the mask is 0x03, and it waits for all of them. The sensor sets 0x01 when a reading is ready, the button sets 0x02 when it is pressed, and the waiter wakes when the value has both. If the button is pressed twice before the sensor reads, the bit is still set once, which is the right answer for a condition.

An ISR may set event bits too, with xEventGroupSetBitsFromISR(), which is defined in event_groups.c. It follows the same pattern: the call reports whether a switch is needed, and the ISR passes that to portYIELD_FROM_ISR(). Use a queue when the data matters, a semaphore when a single event is enough, and an event group when the task waits for a combination of conditions.

Feed a task from a button ISR with each kernel object. Press five times fast and then let the task take: the queue keeps every press and which one it was, the counting semaphore keeps the number, and the binary semaphore keeps only that something happened.

Common mistakes and how to spot them

Mistake 1: calling the plain give from an ISR. The button handler calls xSemaphoreGive(), which is written for tasks. The symptom is intermittent: the button task sometimes wakes late, sometimes not at all, and the log shows lines in the wrong order. The fix is xSemaphoreGiveFromISR() with a woken flag, followed by portYIELD_FROM_ISR(woken).

Mistake 2: the EXTI flag left set. The handler forgets the line that clears the pending bit. The symptom is the BUTTON line printed without end, or the system seems stuck inside the interrupt, because the interrupt fires again the moment it returns. The fix is to clear the flag at the start of the handler, as the project does, and to check the pending register with the debugger when a handler runs forever.

Mistake 3: an ISR priority above the limit. A developer gives the button interrupt priority 0 for "the most responsive button". The symptom is an assertion in vPortValidateInterruptPriority(). With the template's configASSERT, the device stops with interrupts disabled at the first FromISR call, which is the behaviour the template chose on purpose. The fix is to give the interrupt a priority numerically equal to or higher than 5.

Mistake 4: a binary semaphore counting presses. A developer expects each of three quick presses to print a line, and sees only one. The symptom is that the printed count is lower than the number of presses. The binary semaphore remembers at most one give. The fix is a counting semaphore, or a queue of press events, when every event matters.

Mistake 5: a pointer to a local through a queue. A producer declares the queue item as a pointer, int *, and sends the address of a local, value, from a loop. The queue copies the pointer, not the number it points to. The symptom is that the consumer prints garbage, because the local has changed or gone out of scope by the time it is read through the pointer. The fix is to queue the value itself, so the queue copies the number, or to point at storage that outlives the send. The project's xQueueSend(work_queue, &i, ...) is safe because the item is a uint32_t, so the queue copies the value of i at the send.

In real projects

Firmware teams use the FromISR rule as a review item. A reviewer checks each interrupt handler for any call that is not in the ISR-safe list, and for the priority of the interrupt against the kernel's limit. The common practice is to keep handlers short: clear the flag, move the data into a queue or set a bit, and yield. Everything slow happens in a task that the handler wakes.

Queues are also the standard way to hand commands between tasks in a product. A display task receives events from a button task and a sensor task on one queue, and it never reads their variables. The design is easier to test, because the queue is the interface, and a test can feed it events directly.

Summary

  • A queue copies fixed-size items in FIFO order, and a receiver blocks while it is empty. Its storage is allocated from the heap.
  • A binary semaphore holds 0 or 1, so repeated gives before a take count once. A counting semaphore keeps the count up to its limit.
  • An ISR must call the FromISR versions, which never block, and pass woken to portYIELD_FROM_ISR() to switch at once.
  • An ISR that calls FromISR functions must have a priority numerically equal to or higher than configMAX_SYSCALL_INTERRUPT_PRIORITY, which is 5 << 4 in the template.
  • The EXTI pending flag must be cleared in the handler, or the interrupt fires again at once.
  • An event group is a set of bits that a task waits on for all or any, and a repeated set counts once.
