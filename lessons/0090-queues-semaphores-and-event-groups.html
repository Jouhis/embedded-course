Queues, semaphores, and event groups

Passing data and signals between tasks

By the end of this lesson you can send data between tasks with a queue, signal a task from an interrupt with a binary semaphore, use the FromISR calls and portYIELD_FROM_ISR() correctly, and say when an event group is the better choice.

Communication between tasks and interrupts

Lesson 87 gave you tasks and priorities and lesson 88 showed what a switch does to the registers, but neither says how two tasks should talk. In the Lab 5 monitor the button is an interrupt, the sensor a task and the screen another task, so the button handler must wake the UI task without waiting for it, and the sensor must pass its readings to the UI without writing into the UI's variables, both needs being met by the kernel objects of this lesson.

The button case needs the most care. A press arrives as an interrupt from the EXTI controller introduced in lesson 70, running in the middle of whatever task was running and needing to finish quickly, so it cannot wait for the UI task to become ready but can only hand the press over, which the kernel's FromISR calls let it do.

Queues as copying FIFOs

A queue is a fixed-length first-in, first-out list of items, xQueueSend() copying an item in and xQueueReceive() copying it out. The sender may reuse its variable as soon as the send returns, because the kernel keeps its own copy of the bytes, which makes a queue safer than a pointer, since passing a pointer to a local variable through a queue is a bug, the local being gone by the time the receiver runs.

A queue has a fixed length, the number of items it can hold, and a fixed item size, the bytes per item, its storage being allocated from the FreeRTOS heap when the queue is created. In queue.c line 529 the allocation is sizeof(Queue_t) plus the queue's storage in bytes,

storage = length × item size(1)

where the length is the number of items and the item size is in bytes, so a queue of length 4 with 4-byte items holds 16 bytes of data plus the kernel's bookkeeping.

A receiver that finds the queue empty blocks, using no CPU while it waits, and both send and receive take a timeout, portMAX_DELAY meaning wait forever, which on this port is 0xffffffffUL (portmacro.h, the 32-bit tick case the template uses), while a timeout of zero means try once and return.

Binary and counting semaphores

A binary semaphore holds a count of 0 or 1, meaning "this event happened, once", while a counting semaphore counts events up to a chosen limit, such as the number of free buffers in a pool. A semaphore carries no data, so the task that takes it learns that something happened and nothing else.

A binary semaphore created with xSemaphoreCreateBinary() starts empty, a task taking it blocking until something gives it, and a give while the count is already 1 changes nothing, so two presses before the task runs leave one give and the task wakes once, whereas a counting semaphore, or a queue of button events, keeps both. Lesson 91 covers the mutex, a semaphore with an owner.

The FreeRTOS macros make the semaphore a special queue, xSemaphoreCreateBinary() being xQueueGenericCreate with length 1, an item size of 0 and the binary type (semphr.h line 167), and xSemaphoreGive() sending into that queue without data, so the semaphore shares the queue machinery and therefore its blocking and timeout behaviour.

A queue resembles a letterbox, each item being a copy of a letter with content that the reader takes out in order, while a semaphore resembles a ticket dispenser carrying no content at all, only how many tickets are waiting, so the letterbox suits a receiver that needs the data and the dispenser one that only needs to know that something happened, and how often. The comparison breaks for the binary semaphore, though, because a dispenser counts every ticket, whereas a binary semaphore remembers at most one.

Interrupts and the FromISR calls

An interrupt runs on the core in the middle of a task and must return quickly so that the task can continue, since a blocked interrupt would leave the interrupted task stuck behind it while having no task of its own to sleep in. An ISR must therefore use the non-blocking form of each call, which FreeRTOS provides as the FromISR versions, xQueueSendFromISR(), xSemaphoreGiveFromISR() and the rest, each taking a pointer, pxHigherPriorityTaskWoken.

When a FromISR call makes ready a task of higher priority than the interrupted one, it sets the flag the pointer points to, to pdTRUE, and the ISR passes that flag to portYIELD_FROM_ISR() at its end, a macro defined in portmacro.h as portEND_SWITCHING_ISR (line 98), to which line 111 maps portYIELD_FROM_ISR. With the flag set, the port requests a switch when the interrupt returns, so the woken task runs at once rather than after the next tick, the pattern that the event-group documentation in event_groups.h also shows around line 603. 

void EXTI15_10_IRQHandler(void) {
    if ((EXTI->PR & EXTI_PR_PR12) != 0U) {
        EXTI->PR = EXTI_PR_PR12;              /* clear the flag, or the ISR runs again at once */
        BaseType_t woken = pdFALSE;
        xSemaphoreGiveFromISR(button_sem, &woken);
        portYIELD_FROM_ISR(woken);            /* switch now if the button task is more urgent */
    }
}

EXTI->PR is the EXTI pending register, holding one flag per line, and EXTI_PR_PR12 the bit for line 12, the button on PB12, the if checking that this line fired, because the same handler serves lines 10 to 15 and the others may be set too. The next line clears the flag by writing 1 to it, as the project's comment says, since an uncleared flag would make the interrupt fire again as soon as the handler returned, and the vendor reference manual, RM0008 Rev 21, describes the EXTI pending register in section 10.3.6, each bit being set when the selected edge arrives on its line and cleared by writing a 1.

BaseType_t woken = pdFALSE; declares the flag on the ISR's stack, initialised to false, and xSemaphoreGiveFromISR(button_sem, &woken) gives the semaphore, the macro being xQueueGiveFromISR in semphr.h line 640, which does not block and sets woken only if a higher-priority task was waiting on the semaphore. The last line passes that flag to the yield macro, which does nothing when woken is false, so the interrupt then returns to the interrupted task.

An ISR that calls the plain xSemaphoreGive() or xQueueSend() is a bug. The plain calls are written for tasks and may block or change the kernel's lists in ways an interrupt cannot allow. The bug often appears to work at first and then fails intermittently. The ISR's NVIC priority must also be numerically equal to or higher than configMAX_SYSCALL_INTERRUPT_PRIORITY, which the template sets to 5 << 4 in FreeRTOSConfig.h line 30. The rule is explained in the next concept.

The kernel's interrupt priority limit

Lesson 72 taught that on the NVIC a lower number is more urgent, and the FreeRTOS port uses the same number for interrupts while adding a limit, an interrupt calling a FromISR function needing a priority at or below the limit, which means a number equal to or higher than it. The port's own comment states it directly, numerically low priority numbers being logically high priorities, so the interrupt's number must be equal to or numerically higher than configMAX_SYSCALL_INTERRUPT_PRIORITY, and the check is vPortValidateInterruptPriority() in port.c line 766, called from the send and give paths in queue.c.

The template defines the limit as (5 << 4) rather than 5, because the Cortex-M3 stores priorities in the top bits of an 8-bit field and the STM32F1 implements only the top four, as __NVIC_PRIO_BITS at 4 in stm32f103xb.h line 51 says, so the shift by 4 puts the priority 5 into those bits. The project's call NVIC_SetPriority(EXTI15_10_IRQn, 5) does the same shift itself, so the number passed to NVIC_SetPriority() is 5, not 80.

Four implemented bits give 16 priority levels, numbered 0 to 15, level 0 being the most urgent and level 15 the least, and the kernel's own interrupts, SysTick and PendSV, receive the lowest urgency, the port writing portMIN_INTERRUPT_PRIORITY, which is 255, into their priority fields (port.c line 55). The button interrupt at level 5 is therefore less urgent than levels 0 to 4, the ones that must not call FromISR functions, and more urgent than the rest.

The port also refuses the default, since an interrupt left at priority 0 is the most urgent and lies above the limit, so a FromISR call from it fails the check, and the port's comment says directly that an interrupt using the FreeRTOS API must not be left at its default priority of zero.

Event groups for combined conditions

An event group is a word of flags that several sources set with xEventGroupSetBits() while a task waits with xEventGroupWaitBits() for a combination of them, either all the bits or any of them. The bits are not counted, so setting a bit that is already set changes nothing, which is the difference from a counting semaphore.

Take a task that acts only when a sensor is ready and the button has been pressed, the sensor bit having the value 0x01 and the button bit 0x02, so the waiter asks for both with the mask 0x03 and waits for all of them. The sensor sets 0x01 when a reading is ready and the button 0x02 when pressed, and the waiter wakes when the value holds both, while two presses before the sensor reads still leave the bit set once, the right answer for a condition.

An ISR may set event bits too, with xEventGroupSetBitsFromISR(), defined in event_groups.c, following the same pattern of reporting whether a switch is needed and passing that to portYIELD_FROM_ISR(). A queue suits data that matters, a semaphore a single event and an event group a task waiting for a combination of conditions.

Common mistakes and how to spot them

The plain give called from an ISR

The button task sometimes wakes late, sometimes not at all, and the log shows lines in the wrong order, because the button handler calls xSemaphoreGive(), which is written for tasks. Use xSemaphoreGiveFromISR() with a woken flag, followed by portYIELD_FROM_ISR(woken).

The EXTI flag left set

The BUTTON line prints without end, or the system seems stuck inside the interrupt, because the handler forgot the line clearing the pending bit, so the interrupt fires again the moment it returns. Clear the flag at the start of the handler, as the project does, and check the pending register with the debugger whenever a handler runs forever.

An ISR priority above the limit

An assertion fires in vPortValidateInterruptPriority(), the template's configASSERT stopping the device with interrupts disabled at the first FromISR call, a behaviour the template chose on purpose, because a developer gave the button interrupt priority 0 for "the most responsive button". Give the interrupt a priority numerically equal to or higher than 5.

A binary semaphore expected to count presses

Three quick presses print one line, a count lower than the number of presses, because a binary semaphore remembers at most one give. Use a counting semaphore, or a queue of press events, when every event matters.

A pointer to a local sent through a queue

The consumer prints garbage, because a producer declared the queue item as a pointer, int *, and sent the address of a local, value, from a loop, so the queue copied the pointer rather than the number and the local had changed or gone out of scope by the time it was read. Queue the value itself, so that the queue copies the number, or point at storage that outlives the send, the project's xQueueSend(work_queue, &i, ...) being safe because the item is a uint32_t and the queue copies the value of i at the send.

Interrupt handlers and queues in product firmware

Firmware teams make the FromISR rule a review item, a reviewer checking each interrupt handler for any call outside the ISR-safe list and comparing the interrupt's priority with the kernel's limit. The common practice keeps handlers short, clearing the flag, moving the data into a queue or setting a bit and yielding, while everything slow happens in a task the handler wakes.

Queues are also the standard way to hand commands between tasks in a product, a display task receiving events from a button task and a sensor task on one queue without ever reading their variables, a design that is easier to test, because the queue is the interface and a test can feed it events directly.

Summary

  • A queue copies fixed-size items in FIFO order, a receiver blocking while it is empty, and its storage comes from the heap.
  • A binary semaphore holds 0 or 1, so repeated gives before a take count once, while a counting semaphore keeps the count up to its limit.
  • An ISR calls the FromISR versions, which never block, and passes woken to portYIELD_FROM_ISR() to switch at once.
  • An ISR calling FromISR functions needs a priority numerically equal to or higher than configMAX_SYSCALL_INTERRUPT_PRIORITY, which is 5 << 4 in the template.
  • The EXTI pending flag is cleared in the handler, or the interrupt fires again at once.
  • An event group is a set of bits that a task waits on for all or any, a repeated set counting once.
