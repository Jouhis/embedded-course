Lab 3: Environment monitor

A sensor, an OLED, buttons and a log in one super-loop

By the end of this lab you can build a super-loop that reads a sensor, draws a menu on an OLED, reacts to two interrupt-driven buttons, and logs the state over UART, with no call that blocks the loop.

The device and its loop

This lab puts Part 4 together in one device, a temperature sensor on I2C, an OLED screen, two debounced buttons with interrupts, a menu state machine, non-blocking timing and a UART log. Each piece is a lesson you have done, and this is the first time they run at the same time.

The device has one loop, which never waits without a bound but checks three deadlines, taking a sensor sample every 200 ms, redrawing the screen every 500 ms and printing a log line every second. The buttons work differently, because their interrupts only record a press and the loop acts on the record, a split that keeps the loop short, following the rule from lesson 57 and the timing rule from lesson 55.

The sensor and the OLED share one I2C bus, I2C0 on GP4 and GP5, which is normal in industry, because each device has its own address and the bus has only one set of pull-ups. The bus is covered in lesson 60, and the OLED driver is lesson 61's, which this lab reuses unchanged except for six extra glyphs, while lesson 62 shows the same kind of panel on SPI for comparison with this I2C version.

One loop, three deadlines

A super-loop is a while (true) loop that calls a short function for each job, over and over, with no operating system, the simplest firmware structure that handles several jobs at once. Lesson 55 introduced it, and this lab uses one loop for four jobs, the sensor, the screen, the buttons and the log.

Each job has a deadline, a stored time at which the job should run next, and the loop reads the clock on every pass and runs a job only when its deadline has passed. A job that is not due costs one comparison, so the loop goes round in a few microseconds when nothing is due. The clock comes from the SDK's to_ms_since_boot(get_absolute_time()), a 32-bit count of milliseconds that the chip keeps since power-up.

The comparison has to survive the counter wrapping to zero, because a 32-bit millisecond count wraps after 232 ms, about 49.7 days. The loop therefore tests

(int32_t)(now − deadline) ≥ 0(1)

where the subtraction is done in unsigned arithmetic, so it gives the right answer across the wrap, and the signed cast reads the result as a small positive or negative number. This is a wrap-safe timeout, and lesson 55 explained why a plain now >= deadline is wrong.

A worked case shows the arithmetic. Say the deadline is 0xFFFFFFF0, which is 4294967280 ms, and the clock has just wrapped, so now is 0x00000005, which is 5 ms. In unsigned arithmetic 5 − 4294967280 wraps to 21, and the cast gives +21, which is not negative, so the job is due, whereas had now been 0xFFFFFFE0, the difference would be −16 and the job would not be due yet. The rule works in both cases, as long as the two times are less than about 24.8 days apart.

Two devices on one I2C bus

The sensor and the OLED are both I2C devices, and I2C lets many devices share two wires, SDA carrying the data and SCL the clock. Each device answers to a 7-bit address, which the master sends first in each transaction, the sensor being at 0x48, as its datasheet says, and the OLED at 0x3C, as lesson 61 explains, so each device answers only its own transactions.

Each byte on the bus is followed by an acknowledge bit, the receiver pulling SDA low for one clock to say ACK and leaving it high to say NACK, which means that no device is there or that the byte was not accepted. The SDK reports this to your code, because i2c_write_blocking() returns the number of bytes written, or PICO_ERROR_GENERIC if the address is not acknowledged (Pico SDK, hardware_i2c), and that return value is how the lab notices a sensor that has gone missing. The OLED driver from lesson 61 does not check it, so a missing display does not stop the rest of the device.

The bus has one pair of pull-up resistors, RSDA and RSCL in the diagram, which both devices share, a pull-up being a resistor from the line to the supply, so that the line is high when no device pulls it low (lesson 16). The Pico's internal pulls are too weak for a real bus, which is why the diagram has 4.7 kΩ resistors, and the solution's gpio_pull_up() calls also enable the chip's own weak pulls, which is harmless next to the external resistors.

The bus runs at 400 kHz, at which each byte takes nine clock pulses, eight data bits and one ACK, so 22.5 µs, a number the timing of the display flush depends on.

Reading the sensor without waiting

The MYS-1 makes a new temperature sample every 500 ms and sets a data-ready flag (DRDY) in bit 0 of its STATUS register at address 0x27, which reading the high byte of the temperature clears. The datasheet says that the sensor does not queue samples, so an older value is lost if you do not read it before the next one arrives (MYS-1 datasheet, section 4.2), and lesson 63 built the driver with a loop that waits for DRDY, with a timeout.

This lab cannot wait, because a driver that waits for DRDY blocks the super-loop for up to 500 ms, and the buttons, the screen and the log all stop with it. sensor_poll() therefore reads STATUS once, returning SENSOR_IDLE if DRDY is clear so that the loop goes on, and reading TEMP_L and TEMP_H in one burst if DRDY is set, returning the new sample. The burst matters, because reading TEMP_L latches the sample, so both bytes come from the same reading.

The poll rate of 5 per second, faster than the sensor's 2 per second, is deliberate. The loop checks often enough to see every sample soon after it arrives, and a poll that finds DRDY clear costs one short transaction, while polling faster than the sensor cannot show a newer sample, because there is none, so the sample rate is the sensor's rather than the loop's.

The read itself is a repeated start, in which the driver writes the register number with nostop = true, so that the bus stays claimed, and then reads the bytes, for the reason lesson 63 explained: a STOP between the two would let another master take the bus in between, which the datasheet warns about.

Buttons, bounce and interrupts

Each button connects a pin to ground when it is pressed, and with a pull-up on the pin it reads high when the button is up and low when it is down. The lab wires the buttons as active low, so a press is a falling edge, the pin going from high to low, the wiring lesson 52 covered.

A mechanical switch does not change cleanly, because for a few milliseconds the contacts make and break many times, which is bounce, so one click can produce several falling edges. The lab removes the extra edges with a debounce window, ignoring any edge on the same button within 30 ms after an edge is accepted. Lesson 52 described other debouncing methods, and a time window is the simplest one that works for a button that is not pressed rapidly.

The button is connected to an interrupt, the RP2040 sending GPIO events to the core through interrupt lines, one per bank of pins, with both buttons in bank 0 (RP2040 datasheet, section 2.3.2, Table 80, IRQ 13 IO_IRQ_BANK0). The SDK's gpio_set_irq_enabled_with_callback() installs one callback for the bank, which receives the pin number and the event mask, and the lab checks GPIO_IRQ_EDGE_FALL in the mask, so that a rising edge (a release) does nothing. Both buttons share the callback, which is why the handler compares the pin number.

The record-only interrupt handler

An interrupt service routine (ISR) runs in the middle of the loop, when the press happens rather than when the loop is ready, and since the loop is paused while it runs, it must be short. The lab's handler does three things, checking the edge, applying the debounce window and setting one bit in pending_events, and nothing else, so it neither draws, prints nor changes the menu state, which the loop does at a time it chooses.

The handler reads the time with to_ms_since_boot(), which only reads the hardware timer and does not wait, and compares it with the last accepted press on the same button, keeping one timestamp for each button. A press that comes less than 30 ms after the last accepted one is treated as bounce and dropped, following the rules lesson 57 gave.

The flag itself is shared between the handler and the loop, so it is declared volatile, because, as lesson 46 explained, the compiler must not keep the value in a register between reads. The lab goes one step further, the main loop reading the flag and clearing it with interrupts off, using save_and_disable_interrupts() and restore_interrupts(), since otherwise a press that arrives between the read and the clear would be lost. The disabled section is a few instructions long, so the interrupt is delayed by very little.

The critical section in ui_poll_buttons() protects the flag from one interrupt on one core. It is not a lock between cores. Lesson 64 explained why a second core would need a spinlock instead.

The menu state machine

A state machine is code that is always in one of a fixed set of states and moves between them on events. This menu has three screens, LIVE, MINMAX and SETPOINT, button A being the event that moves to the next screen and button B an event whose meaning depends on the state, resetting the range on MINMAX, raising the alarm threshold on SETPOINT and doing nothing on LIVE.

The screen change is one line, screen = (screen + 1) % UI_SCREEN_COUNT, and with a count of three, LIVE becomes MINMAX, MINMAX becomes SETPOINT and SETPOINT wraps back to LIVE. The modulo keeps the rule in one place, so a fourth screen needs only a change to the enum and the wrap follows. Separating the state from the events is what makes this easy to test, because each event changes the state in one function and the drawing code only reads the state.

The alarm is not a state but a value the state machine computes from the newest reading and the threshold each time a sample arrives, on when the reading is above the threshold, and it appears on the LIVE screen. Keeping it as a value rather than a screen means it can be shown on any screen without changing the state.

Drawing and logging

The OLED driver keeps a framebuffer in RAM, one byte per eight vertical pixels in each column. The UI draws into that buffer with display_clear() and display_text(), which touch only RAM, and then display_flush() sends the whole buffer over I2C, the split lesson 61 described.

The flush is the one place where the loop waits for hardware. It sends about 1 080 bytes, counting the commands for each page, and at 400 kHz each byte takes 22.5 µs, so a flush takes about 24 ms before the start and stop conditions are counted. That is a bounded wait, but it means the loop can be late by up to about 25 ms on a draw pass, the sample and button deadlines still running, only a little late. The lab accepts that delay, and drawing only every 500 ms keeps the screen busy for about 5 % of the time.

The log uses printf(). The SDK's default UART is UART0 on GP0 and GP1 for the Pico, and stdio_init_all() routes printf() to it (Pico SDK defaults for the Pico board). The log prints a snapshot of the state once a second, the newest temperature, the minimum and maximum, the alarm flag, the threshold and the screen name, taken with ui_status(), so that the log always shows one consistent state.

Worked example: one button press, step by step

We follow one press of button A through the code, with real times, the sensor and the display keeping their own deadlines, which do not matter for this trace. Before reading on, predict how many times the screen changes for a press that bounces three times, and when the new screen appears.

  1. t = 5000.0 ms. The button bounces. The first falling edge reaches the ISR. The debounce check compares 5000 with the last accepted press on button A, which was long ago, so the press is accepted. The handler stores 5000 as the last accepted time and sets EVT_A in pending_events. The ISR returns.
  2. t = 5000.8, 5002.1 and 5004.5 ms. The contact bounces three more times. Each edge reaches the ISR. Each is less than 30 ms after 5000, the last accepted press, so each is dropped. Nothing is recorded.
  3. The next loop pass. The loop calls ui_poll_buttons(). It disables interrupts, copies pending_events (which holds EVT_A), clears it and restores interrupts. Then it sees EVT_A, and screen changes from LIVE to MINMAX. The function returns, and the loop goes on.
  4. The next draw deadline. The draw deadline comes every 500 ms. The screen state is already MINMAX, but the OLED still shows LIVE until the next draw. That draw renders MINMAX into the framebuffer and flushes it, which takes about 24 ms. The new screen therefore appears between 0 and 500 ms after the press, plus the flush time, depending on where the press falls in the draw cycle.

The trace shows that the ISR did almost no work, that the bounce was removed by a time rule rather than by waiting, and that the state changed one loop pass after the press, because the loop picks up the flag and does the work at its own pace. The display is a separate step with its own deadline, which is why the OLED lags the state.

Worked example: deadlines without drift

The log's deadline starts at 1000 ms after boot, and it should print every 1000 ms. Suppose the loop was busy with a flush and reaches the log deadline at 1007 ms, 7 ms late, and predict which of the two ways of setting the next deadline keeps the log on the one-second grid.

RuleCalculationNext deadline
Add the period to the deadline (the lab's rule)1000 + 10002000 ms
Add the period to now (wrong)1007 + 10002007 ms

With the lab's rule the 7 ms lateness is spent once, and the next print comes at 2000 ms, whereas with the wrong rule every late pass adds its lateness to the schedule, so the log drifts away from the one-second grid, and after a few minutes it runs visibly off the sensor's 500 ms samples. The lab's Hint 5 gives this rule.

Design choices

Each choice in the lab is a trade-off a reviewer will ask about, the four main ones being these.

  • One super-loop, not an RTOS. Four jobs with simple deadlines fit in one loop, and the loop's behaviour is easy to read. Lab 4 ports this device to the STM32, and lab 5 moves it onto FreeRTOS, where each job has its own task. The comparison will make sense once you have built the loop by hand.
  • The sensor is polled once per pass. A blocking poll would be simpler to write, and it would make the whole device wait on a sensor that may never answer. The cost of a non-blocking poll is a little more code, and the benefit is that the screen and the buttons never stop.
  • Debounce by time, not by counting. A 30 ms lockout is one line. The alternative, an integrator that counts stable samples, handles noisy inputs better but needs a timer tick. This lab's buttons are clean enough for the lockout.
  • The ISR only records. The alternative is to draw in the handler, which would make the screen update the moment the button is pressed. It would also make the loop's timing depend on the display, and a drawing bug would show up as a missed press.

Requirements

  1. Read the sensor every 200 ms. Each read must return at once: if no new sample is ready, the loop goes on.
  2. Redraw the OLED every 500 ms. The LIVE screen shows the current temperature. The screen says NO DATA until the first sample, and SENSOR ERR if the sensor stops answering.
  3. Button A (GP14) moves to the next screen, in the order LIVE, MINMAX, SETPOINT, then back to LIVE.
  4. On MINMAX, button B resets the minimum and maximum. The screen shows both values since the last reset.
  5. On SETPOINT, button B raises the alarm threshold by 1 °C. It wraps from 35 back to 20. The threshold starts at 28 °C.
  6. The alarm is on when the newest reading is above the threshold. The LIVE screen then shows ALARM, and the log prints ALARM=1.
  7. Both buttons are interrupt-driven. The interrupt handler records a press and nothing more. Presses closer than 30 ms apart on the same button count as one press (debounce).
  8. Print one log line every second over UART: LAB3 T=22.50 MIN=21.90 MAX=23.10 ALARM=0 SET=28 SCREEN=LIVE. Print LAB3 T=none ... before the first sample.
  9. After sensor, display and buttons have all initialised, print LAB3 OK once.

Acceptance criteria

  • The log shows LAB3 OK once, after startup, and the temperature changes slowly over the next few seconds.
  • The OLED shows the temperature on LIVE, and the same value appears in the log within one second.
  • Pressing button A three times returns the screen to LIVE, and the log shows each screen name in turn.
  • On MINMAX, the minimum is less than or equal to the maximum, and button B resets both (the screen shows NO DATA until the next sample).
  • On SETPOINT, pressing B repeatedly takes the threshold from 28 to 35, then to 20. Set it to 22: the log shows ALARM=1, and the LIVE screen shows ALARM.
  • A single click on a button produces one screen change, not two. Pressing a button a second time within 30 ms counts as the same press.
  • Remove the sensor's SDA wire in the diagram. Within about 1 s the LIVE screen shows SENSOR ERR, and the buttons and the log keep working.

Milestones

  1. M1: sensor and log. Implement sensor_init, sensor_poll and ui_on_sample, after which the log shows T= values.
  2. M2: display. Implement display_init, display_flush and ui_draw for LIVE, after which the OLED shows the temperature.
  3. M3: buttons. Implement ui_init, the interrupt handler and ui_poll_buttons, after which button A changes the screen.
  4. M4: min, max and alarm. Finish MINMAX and SETPOINT, including button B, the alarm and the wrap.
  5. M5: the whole device. Check every acceptance criterion, then the error case.

Hint 1: the sensor poll (M1)

Lesson 63's driver waited for data-ready. This lab's sensor_poll checks once. Read STATUS, and if bit 0 is clear, return SENSOR_IDLE. If it is set, read TEMP_L and TEMP_H in one burst, and convert them the way lesson 63 did.

Hint 2: the display init and flush (M2)

The OLED driver is the lesson 61 code, copied into this folder as ssd1306.c and font.c. Your display_init calls ssd1306_init with the I2C0 bus, and your display_flush calls ssd1306_flush. Both are one line. Check the lesson 61 explanation of the control bytes if the screen does not change.

Hint 3: the interrupt handler (M3)

The handler runs with the press. Read the pin's edge from the events argument, and check that it is GPIO_IRQ_EDGE_FALL. Keep the time of the last accepted press for each button. A press that comes less than 30 ms after that is a bounce. Set a bit in pending_events, and nothing else.

Hint 4: the events in the main loop (M3)

Take the events with interrupts off, then clear them, then restore the interrupts. That ordering keeps a press that arrives during the clear. Button A advances the screen with (screen + 1) % UI_SCREEN_COUNT.

Hint 5: the deadlines (main loop)

Compare with (int32_t)(now - deadline) >= 0, and add the period to the deadline, not to now. Adding to now drifts, and the drift grows with every late iteration.

Common mistakes and how to spot them

Waiting for DRDY inside the sensor poll

The log stops printing for half a second at a time and a button press seems to lag, and with the sensor unplugged the whole device freezes and no screen changes, because a while loop around the STATUS read stops the super-loop for up to 500 ms. Read STATUS once and return SENSOR_IDLE if DRDY is clear.

Drawing or printing inside the handler

One of two quick presses is lost, or the device stops responding for a moment, because the handler calls display_text() or printf(). Record the press in pending_events and act on it in ui_poll_buttons().

The period added to now

The log's one-second rhythm drifts relative to the sensor over minutes, as the worked example shows, because the next deadline is now + PERIOD instead of deadline + PERIOD. Add the period to the deadline.

No pull-up on a button pin

The screen changes by itself, or a press is missed, and the behaviour changes with the position of your hand near the wires, because the pin floats when the button is up. Call gpio_pull_up(), and check the level with gpio_get() printed to the log.

Both edges enabled

Every click moves the menu two screens, because the callback fires on the press and on the release. Enable GPIO_IRQ_EDGE_FALL only, and check the mask in the callback.

A shared flag without volatile or the critical section

An optimised build never sees the press, or a press is lost very rarely, because the loop may keep the flag in a register, or a press may arrive between the read and the clear. Declare the flag volatile, and copy and clear it with interrupts disabled.

Super-loops in small products

Many small embedded products use a super-loop with flags from interrupts, among them thermostats, meters, remote controls and sensor nodes, because it is simple to reason about, its timing is visible in the code and it needs no operating system. Its weakness is that one slow job delays all the others, so a job is added only after checking the time it can take, a flush of 24 ms being acceptable here, whereas one of 200 ms would need a different design.

A reviewer of this kind of code looks for four things: every blocking call in the loop has a known bound, every flag shared with an interrupt is volatile and protected on every read-and-clear, every deadline adds the period to the deadline, and the interrupt handler is short. Those four checks catch most of the mistakes above.

Summary

  • A super-loop runs several jobs from one while (true), each job having a deadline and running only when the deadline has passed.
  • Deadlines are compared with (int32_t)(now - deadline) >= 0, which survives the 32-bit wrap, and the period is added to the deadline rather than to now.
  • Two I2C devices share SDA and SCL, each with its own address, and a missing device shows up as a NACK, for which i2c_write_blocking() returns PICO_ERROR_GENERIC.
  • The sensor's data-ready flag is read once per poll without waiting, and reading TEMP_L and TEMP_H in one burst keeps the two bytes from one sample.
  • A switch bounces for a few milliseconds, and a 30 ms lockout after each accepted falling edge removes the extra edges.
  • An interrupt handler records a press in a volatile flag, which the loop copies and clears with interrupts off before acting on it.
  • The state machine changes state on events, while the alarm is a value computed from the newest sample.
  • A flush of the OLED takes about 24 ms at 400 kHz, the longest wait in the loop.
