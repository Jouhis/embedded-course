Interrupts in practice

An interrupt lets a button press reach the CPU without a polling loop. The handler must finish fast, and the data it shares with main must be read in a way that cannot be interrupted halfway.

By the end of this lesson you can register a GPIO falling-edge callback on the Pico SDK, keep an interrupt service routine (ISR) short and free of printf, and read and clear a shared counter in main inside a critical section.

Where we are and why it matters

Lesson 34 showed what the core does when an exception happens: it saves a few registers on the stack, jumps to a handler, and returns when the handler finishes. Lesson 55 built a super-loop that never blocks, and it checks its inputs by polling them on every pass. Polling has a cost. If the loop takes 100 ms for one pass, a button press that lasts 20 ms can be missed, or noticed 100 ms late. An interrupt removes that delay, because the hardware calls the handler the moment the pin changes.

Interrupts are how a real product notices a bit of hardware without spending its time asking. A printer's motor controller counts encoder edges in an interrupt, a Bluetooth radio raises a flag when a packet arrives, and a battery charger reacts to a fault pin. The price is that the handler runs at a moment the main program does not choose, which changes how you write both the handler and the main code. This lesson covers those rules, using a GPIO button on the Pico.

The concepts, one at a time

Four ideas explain how the RP2040 turns a pin change into a call to your code. The first is the interrupt controller, the second is the shared GPIO line, the third is priority, and the fourth is the shared-data problem that makes the handler hard to get right.

The interrupt controller

An interrupt is a hardware event that makes the core stop what it is doing and run a handler. The part of the CPU that accepts those events is the Nested Vectored Interrupt Controller (NVIC), which has one input per interrupt source and decides which pending interrupt runs next. Each RP2040 core has its own NVIC with 32 inputs. The datasheet says that only the lower 26 signals are connected to anything, and that IRQs 26 to 31 are tied to zero, so they never fire RP2040 datasheet, section 2.3.2. That leaves 26 real sources, and each one has a fixed number in a table in the same section. The M0+ core has its own exception vector table. Lesson 42 covers how that table gets its addresses from the startup code.

The number matters because the handler's address is stored in a table indexed by that number. The core looks up the entry for the interrupt, jumps there, and runs the code. When you write a handler in C, the table entry is filled in by the vector table that the linker built. You do not look the entry up yourself.

One line for every GPIO bank

The 30 GPIO pins on the RP2040 are grouped into banks. Bank 0 holds GPIO 0 to 29, and each pin in it can raise an interrupt on its own edge events. The hardware does not give each pin its own NVIC input. All the pins in bank 0 share one line, IO_IRQ_BANK0, which is IRQ 13 in the datasheet's table of interrupt sources RP2040 datasheet, section 2.3.2, Table 80. The datasheet also says there is one GPIO interrupt per bank per core, so each core can receive its own GPIO events RP2040 datasheet, section 2.3.2.

So one handler serves every pin in the bank. It has to find out which pin changed, and the SDK does that for you. Its default GPIO handler loops over the pins in bank 0, reads the event bits for each, acknowledges each event so it does not fire again, and calls your callback once per pin with the pin number and the events Pico SDK, GPIO reference. The callback has the type void (*)(uint gpio, uint32_t event_mask), so it receives both the pin and the kind of edge.

The call that connects your function is gpio_set_irq_enabled_with_callback(). It enables one edge event on one pin and installs the callback on the calling core Pico SDK, GPIO reference. You never write to the NVIC yourself for a GPIO interrupt. The SDK does it the first time you enable an event.

Priority: who runs first

Several interrupts can be pending at once, so the NVIC needs a rule. The Cortex-M0+ in the RP2040 implements the two most significant bits of each 8-bit priority field, which gives four levels, and level 0 is the highest. When two interrupts have the same level, the one with the lower IRQ number runs first. The datasheet also says that nested interrupts are supported in hardware, so a higher-priority interrupt can interrupt a running lower-priority handler RP2040 datasheet, section 2.3.2.

The default levels are fine for a first project. In a real product you set the priority of the interrupt that must react fastest, such as a motor-stop input, to the highest level, and you leave slow sources at the default. Priority changes how long a handler can wait, which is why the rule for ISR length exists.

Rules for an ISR

Three rules follow from the fact that the ISR interrupts main at an arbitrary instruction. You cannot predict where main is when the button is pressed, so the handler must be written to work from any point.

  1. Keep it short. While the ISR runs, the interrupt that called it is held off, and so are any others at the same or lower priority. A long handler delays the other sources. Set a flag or add to a counter, then return.
  2. Do not block and do not call printf. printf writes to a UART that may be full, so it can wait. It is also not safe to call from two places at once: if main was inside printf when the ISR runs, the two calls can corrupt each other's buffer.
  3. Share data with volatile, and make multi-step updates atomic. volatile stops the compiler from caching the flag in a register (lesson 46). It does not stop an interrupt from landing between a read and a clear, which is a separate problem.

The shared-data problem

The third rule is the one beginners miss most often, so it is worth one worked example. Suppose the ISR does press_count++ and press_pending = true, and main wants to report the count and clear the flag. In C that is three operations: read the flag, read the count, write the flag. The compiler turns each into one or more instructions, and the interrupt can run between any two of them.

Here is a trace with real values. Before the trace, the count is 1 and the flag is true, because press 1 has happened and has not been reported yet.

  1. main, step 1. It reads press_pending and gets true. It has decided to report.
  2. main, step 2. It reads press_count and gets 1.
  3. The second press. The button goes down, and the ISR runs. It sets press_count to 2 and sets press_pending to true, which it already was.
  4. main, step 3. It writes press_pending = false and prints presses=1.

The second press happened, but the program reports only one, and the flag is clear, so nothing will report press 2 until a third press sets the flag again. The count in memory is right, but the report is stale. The fix is to make steps 1 to 3 one unit that the ISR cannot interrupt. That is the critical section below.

Critical sections

A critical section is a short stretch of code that runs with interrupts disabled, so that a multi-step update of shared data cannot be interrupted. The SDK provides save_and_disable_interrupts(), which returns the old interrupt state, and restore_interrupts(), which puts it back Pico SDK, hardware/sync.h. On this core, the save reads the PRIMASK register and then executes cpsid i, which masks all configurable interrupts Pico SDK, hardware/sync.h. Use the save-and-restore pair, not a plain disable. Code that is already inside a critical section should not turn interrupts back on when it finishes. 

/* main loop: read and clear the flag and count as one step */
uint32_t saved = save_and_disable_interrupts();
bool pending = press_pending;     /* 1. read the flag */
uint32_t total = press_count;     /* 2. read the count */
press_pending = false;             /* 3. clear the flag */
restore_interrupts(saved);

Walk through the code line by line. save_and_disable_interrupts() returns the current interrupt state, which is saved in saved, and then masks interrupts, so no ISR can start until the restore. Lines 1 to 3 are the three steps from the trace, and now they cannot be split. restore_interrupts(saved) puts back the state the caller had before, so if this code had been called from inside another critical section, the interrupts would stay off until that outer section ended.

The critical section is short on purpose. It must not contain a printf, a delay or a long calculation, because while interrupts are masked, nothing else on this core runs. The printing happens after the restore, with the copies in pending and total.

volatile is not a lock. It stops the compiler from caching a variable, and nothing more. A count++ in the ISR and a read-and-clear in main still need the critical section above.

Replay the trace above, and choose the moment of the second press yourself. Press between step 2 and step 3 and the count is right while the report is stale. Then turn on the critical section and press at the same moment.

Worked example: following one press

Put the pieces together with the solution's numbers. The project wires a pushbutton to GP14 with the internal pull-up on, as in lesson 16. The pin is high when released and low when pressed, so the press is a falling edge, and the callback is registered for GPIO_IRQ_EDGE_FALL.

  1. Setup. main calls gpio_set_irq_enabled_with_callback(14, GPIO_IRQ_EDGE_FALL, true, &on_button). The SDK enables the falling-edge event for GP14 in bank 0 and installs on_button as the callback for this core. The loop then sleeps for 100 ms per pass.
  2. The press. The pin goes from high to low. The hardware sets the event bit for GP14 and raises IRQ 13 to the NVIC. The core stops main between two instructions and jumps to the bank 0 handler.
  3. The handler. The SDK handler finds the event bit for GP14, clears it, and calls on_button(14, GPIO_IRQ_EDGE_FALL). The callback increments press_count to 1 and sets press_pending to true. It returns, and the core restores the registers saved at entry.
  4. Main reports. Within 100 ms, the loop enters the critical section, copies the flag and the count (1), clears the flag, and restores the interrupts. Since the flag was set, it prints presses=1.
  5. The next press. The second press behaves the same way. The count becomes 2 and the flag is set again, so the next report prints presses=2.

That sequence is the expected serial output: one presses=N line for each press, with N counting up. The solution prints interrupts ready once at startup, and the starter's extra pressed line from the ISR is the wrong behaviour you are asked to remove.

The code, line by line

The solution's handler and main loop are short, and every line supports one of the rules above. Read the handler first. 

/* Shared with the ISR. volatile stops the compiler caching them in main (lesson 46). */
static volatile uint32_t press_count = 0;
static volatile bool press_pending = false;

/* ISR: short, no printf, no blocking. It only records that something happened. */
static void on_button(uint gpio, uint32_t events) {
    (void)gpio;
    (void)events;
    press_count++;          /* written only here, so the ISR never races with itself */
    press_pending = true;   /* main clears this after reporting */
}
  1. static volatile uint32_t press_count is a counter in RAM. static keeps it private to this file, and volatile makes every read and write happen, so main never reads a copy it kept in a register from before the press.
  2. static volatile bool press_pending is the flag. It is bool because it only needs two states. Like the counter, it must be volatile, because the ISR writes it and main reads it.
  3. (void)gpio; and (void)events; silence the unused-argument warnings. The callback has to accept both arguments, because the SDK passes them, even though this handler does not need them.
  4. press_count++; is written only in the ISR, so the counter has a single writer. That is why it does not need a critical section in the handler itself. The race is in main, which reads it.
  5. press_pending = true; sets the flag for main. The handler does nothing slower than these two writes, which is why it can be this short.
int main(void) {
    stdio_init_all();
    gpio_init(BUTTON_PIN);
    gpio_set_dir(BUTTON_PIN, GPIO_IN);
    gpio_pull_up(BUTTON_PIN);   /* released = 1, pressed = 0, so the falling edge is a press */

    /* Installs the shared GPIO callback on this core and enables the falling-edge event. */
    gpio_set_irq_enabled_with_callback(BUTTON_PIN, GPIO_IRQ_EDGE_FALL, true, &on_button);
    printf("interrupts ready\n");

    while (true) {
        /* Read-and-clear is three memory operations. Disable interrupts so the ISR */
        /* cannot run between them and set a new press that we then clear unreported. */
        uint32_t saved = save_and_disable_interrupts();
        bool pending = press_pending;
        uint32_t total = press_count;
        press_pending = false;
        restore_interrupts(saved);

        if (pending) {
            printf("presses=%lu\n", (unsigned long)total);   /* EXPECT: presses=1 */
        }
        sleep_ms(LOOP_MS);
    }
}
  1. gpio_init, gpio_set_dir and gpio_pull_up set up the pin as an input with a pull-up. The comment states the logic: released reads 1, pressed reads 0, so the press is the falling edge. Lesson 16 covers why a pull-up is needed.
  2. gpio_set_irq_enabled_with_callback does three things at once: it enables the falling-edge event on GP14, it installs the shared bank 0 handler if this is the first event, and it records on_button as the callback. The true means enable.
  3. The critical section is the four-line block from the previous section. The copy into pending and total happens inside it, and the printing does not.
  4. if (pending) prints only when a press was pending, so the serial log shows one line per press and nothing while the button is idle.
  5. sleep_ms(LOOP_MS) makes the loop wait 100 ms. That is fine here, because the press is already recorded by the ISR, so the delay only changes when the report appears, not whether it appears.

Common mistakes and how to spot them

Mistake 1: printf in the handler. Symptom: the serial monitor shows a pressed line from the ISR on every press, and on hardware with a busy UART the handler can wait for the buffer to drain, so the other interrupts are delayed. The starter has this on purpose. Fix: delete the call, set a flag or a counter, and let main print.

Mistake 2: no volatile on the shared flag. Symptom: main never reports, even though the counter in the debugger rises when you press the button. The compiler may read press_pending once into a register and never look at the memory again, so the loop does not see the ISR's write. Fix: declare both shared variables volatile. The debugger is the quickest way to see the difference: the variable's value in memory is right, but the code never reads it.

Mistake 3: read-and-clear without the critical section. Symptom: the report is sometimes one press behind, and a press is missing from the log even though the count in the debugger is correct. The worked example above shows the interleaving. Fix: wrap the three steps in save_and_disable_interrupts() and restore_interrupts(), as the solution does.

Mistake 4: callback never enabled. Symptom: pressing the button prints nothing at all, and the count in the debugger does not move. The handler is installed, but the event was never enabled, so the NVIC never gets the request. Fix: check the third argument of gpio_set_irq_enabled_with_callback(), which must be true, and check that the event mask is GPIO_IRQ_EDGE_FALL for a press with a pull-up.

Mistake 5: one press counted as several. Symptom: on real hardware, one push of a mechanical button prints two or three presses lines, because the contact bounces and the pin falls several times. The simulator does not show this. The starter's diagram sets the button's bounce attribute to 0, so one press makes one edge. Fix: debounce the events, as lesson 52 does, either in the handler with a timestamp check or in main with an integrator.

In real projects

Professional firmware uses this pattern widely. The ISR does the minimum: it reads the hardware event, records it in a buffer or a flag, and returns. The main loop or a task does the rest. Code review checks three things in every handler: no blocking calls, no logging, and every shared variable is either volatile, protected by a critical section, or written from one place only. A reviewer who sees a printf inside an ISR asks for it to be moved out.

The same design shows up on bigger systems. A real-time operating system's ISR hands data to a queue and wakes a task, instead of doing the work itself. Lesson 87 introduces FreeRTOS tasks, and the same rule applies there. Priority decides which handler runs first when two events arrive together, so a safety input is given a higher priority than a status LED.

Summary

  • An interrupt makes the core stop main and run a handler. On the RP2040 the NVIC has 26 connected sources, and each core has its own.
  • All GPIO pins in bank 0 share IRQ 13. The SDK's handler finds the pin, acknowledges the event, and calls your callback with the pin and the event mask.
  • Register the callback with gpio_set_irq_enabled_with_callback(), using GPIO_IRQ_EDGE_FALL and true for a press on a pull-up.
  • Priority decides which pending interrupt runs first. At equal priority, the lower IRQ number runs first.
  • Keep the ISR short. Set a flag or add to a counter, and never call printf or block.
  • Declare shared variables volatile. That stops caching, and nothing more.
  • A read-and-clear of shared data needs save_and_disable_interrupts() and restore_interrupts(), because an ISR can run between any two of its steps.
  • Real buttons bounce, so one press can raise several edges. Debounce the events before counting them.
