Interrupts in practice

Hardware-triggered handlers and data shared with main

By the end of this lesson you can register a GPIO falling-edge callback on the Pico SDK, keep an interrupt service routine (ISR) short and free of printf, and read and clear a shared counter in main inside a critical section.

From polling to interrupts

Lesson 34 showed what the core does when an exception happens, saving a few registers on the stack, jumping to a handler and returning when it finishes, and lesson 55 built a super-loop that never blocks and polls its inputs on every pass. Polling has a cost, because if one pass of the loop takes 100 ms, a 20 ms button press can be missed or noticed 100 ms late, whereas an interrupt removes the delay by having the hardware call the handler the moment the pin changes.

Interrupts let a real product notice hardware without spending its time asking: a printer's motor controller counts encoder edges in an interrupt, a Bluetooth radio raises a flag when a packet arrives and a battery charger reacts to a fault pin. The price is that the handler runs at a moment the main program does not choose, which changes how both the handler and the main code must be written, and this lesson covers those rules with a GPIO button on the Pico.

The NVIC interrupt controller

Four ideas explain how the RP2040 turns a pin change into a call to your code: the interrupt controller, the shared GPIO line, priority and the shared-data problem that makes handlers hard to get right. An interrupt is a hardware event that makes the core stop what it is doing and run a handler, and the part of the CPU that accepts those events is the Nested Vectored Interrupt Controller (NVIC), which has one input per interrupt source and decides which pending interrupt runs next. Each RP2040 core has its own NVIC with 32 inputs, of which, as the datasheet states, only the lower 26 are connected, IRQs 26 to 31 being tied to zero so that they never fire RP2040 datasheet, section 2.3.2, which leaves 26 real sources, each with a fixed number in a table in the same section. The M0+ core has its own exception vector table, and lesson 42 covers how that table gets its addresses from the startup code.

The number matters because the handler's address is stored in a table indexed by it, the core looking up the interrupt's entry and jumping there. For a handler written in C, the entry is filled in by the vector table the linker built, so the code never looks it up itself.

The shared GPIO interrupt line

The 30 GPIO pins of the RP2040 are grouped into banks, bank 0 holding GPIO 0 to 29, each of which can raise an interrupt on its own edge events. The hardware does not give each pin its own NVIC input, however, but has all the pins of bank 0 share one line, IO_IRQ_BANK0, which is IRQ 13 in the datasheet's table of interrupt sources RP2040 datasheet, section 2.3.2, Table 80, and the datasheet adds that there is one GPIO interrupt per bank per core, so each core can receive its own GPIO events RP2040 datasheet, section 2.3.2.

One handler therefore serves every pin in the bank and must find out which pin changed, which the SDK does: its default GPIO handler loops over the pins of bank 0, reads each pin's event bits, acknowledges each event so that it does not fire again and calls your callback once per pin with the pin number and the events Pico SDK, GPIO reference. The callback has the type void (*)(uint gpio, uint32_t event_mask), so it receives both the pin and the kind of edge.

The call that connects the function is gpio_set_irq_enabled_with_callback(), which enables one edge event on one pin and installs the callback on the calling core Pico SDK, GPIO reference. A GPIO interrupt never requires writing to the NVIC directly, because the SDK does so the first time an event is enabled.

Interrupt priority

Several interrupts can be pending at once, so the NVIC needs a rule. The Cortex-M0+ in the RP2040 implements the two most significant bits of each 8-bit priority field, giving four levels with level 0 the highest, and when two interrupts share a level, the one with the lower IRQ number runs first. The datasheet adds that nested interrupts are supported in hardware, so a higher-priority interrupt can interrupt a running lower-priority handler RP2040 datasheet, section 2.3.2.

The default levels suit a first project, while a real product gives the interrupt that must react fastest, such as a motor-stop input, the highest level and leaves slow sources at the default. Priority determines how long a handler can be kept waiting, which is the reason for the rule about ISR length.

Rules for interrupt service routines

Three rules follow from the fact that the ISR interrupts main at an arbitrary instruction: since nobody can predict where main is when the button is pressed, the handler must work from any point.

  1. Keep it short. While the ISR runs, the interrupt that called it is held off, together with any others at the same or lower priority, so a long handler delays the other sources. Set a flag or add to a counter, then return.
  2. Neither block nor call printf. printf writes to a UART that may be full, so it can wait, and it is not safe to call from two places at once, because if main was inside printf when the ISR ran, the two calls could corrupt each other's buffer.
  3. Share data through volatile and make multi-step updates atomic. volatile stops the compiler from caching the flag in a register (lesson 46), but it does not stop an interrupt from landing between a read and a clear, which is a separate problem.

The shared-data problem

The third rule is the one beginners miss most often, so it deserves a worked trace. Suppose the ISR does press_count++ and press_pending = true, while main wants to report the count and clear the flag. In C that is three operations, reading the flag, reading the count and writing the flag, each compiled into one or more instructions, and the interrupt can run between any two of them. Before the trace the count is 1 and the flag is true, because press 1 has happened and not yet been reported; predict what main prints if a second press arrives in the middle.

  1. main, step 1. It reads press_pending, gets true and decides to report.
  2. main, step 2. It reads press_count and gets 1.
  3. The second press. The button goes down and the ISR runs, setting press_count to 2 and press_pending to true, which it already was.
  4. main, step 3. It writes press_pending = false and prints presses=1.

The second press happened, yet the program reports only one, and with the flag now clear nothing will report press 2 until a third press sets the flag again, so the count in memory is right while the report is stale. The fix is to make steps 1 to 3 a single unit that the ISR cannot interrupt, which is the critical section described next.

Critical sections

A critical section is a short stretch of code that runs with interrupts disabled, so that a multi-step update of shared data cannot be interrupted. The SDK provides save_and_disable_interrupts(), which returns the old interrupt state, and restore_interrupts(), which puts it back Pico SDK, hardware/sync.h, and on this core the save reads the PRIMASK register and then executes cpsid i, masking all configurable interrupts Pico SDK, hardware/sync.h. Use the save-and-restore pair rather than a plain disable, so that code already inside a critical section does not turn interrupts back on when it finishes. 

/* main loop: read and clear the flag and count as one step */
uint32_t saved = save_and_disable_interrupts();
bool pending = press_pending;     /* 1. read the flag */
uint32_t total = press_count;     /* 2. read the count */
press_pending = false;             /* 3. clear the flag */
restore_interrupts(saved);

save_and_disable_interrupts() returns the current interrupt state, kept in saved, and masks interrupts, so no ISR can start until the restore, and lines 1 to 3, the three steps of the trace, can no longer be split. restore_interrupts(saved) restores the caller's previous state, so if this code had run inside another critical section, the interrupts would stay off until that outer section ended.

A critical section resembles a "do not disturb" sign on a door: while it hangs there nobody comes in, so a job that must not be interrupted can be finished, and everyone else waits outside, including the urgent visitors, the interrupts. That is why the sign hangs for a few lines of code and never for a loop or a printf. Unlike visitors, though, an interrupt that arrives while the sign is up is not turned away but held pending, and it runs the moment the sign comes down.

The critical section is short on purpose and must not contain a printf, a delay or a long calculation, because while interrupts are masked nothing else runs on this core, so the printing happens after the restore, using the copies in pending and total.

volatile is not a lock: it stops the compiler from caching a variable and nothing more, so a count++ in the ISR and a read-and-clear in main still need the critical section above.

Worked example: one button press

We now combine the pieces with the solution's numbers. The project wires a pushbutton to GP14 with the internal pull-up on, as in lesson 16, so the pin is high when released and low when pressed, which makes the press a falling edge, and the callback is registered for GPIO_IRQ_EDGE_FALL.

  1. Setup. main calls gpio_set_irq_enabled_with_callback(14, GPIO_IRQ_EDGE_FALL, true, &on_button), and the SDK enables the falling-edge event for GP14 in bank 0 and installs on_button as this core's callback, after which the loop sleeps for 100 ms per pass.
  2. The press. The pin goes from high to low, the hardware sets GP14's event bit and raises IRQ 13 at the NVIC, and the core stops main between two instructions and jumps to the bank 0 handler.
  3. The handler. The SDK handler finds GP14's event bit, clears it and calls on_button(14, GPIO_IRQ_EDGE_FALL), which increments press_count to 1 and sets press_pending to true before returning, after which the core restores the registers saved at entry.
  4. Main reports. Within 100 ms the loop enters the critical section, copies the flag and the count of 1, clears the flag and restores the interrupts, and because the flag was set, it prints presses=1.
  5. The next press. The second press repeats the sequence, the count becoming 2 and the flag being set again, so the next report prints presses=2.

The expected serial output is therefore one presses=N line per press with N counting up. The solution prints interrupts ready once at startup, while the starter's extra pressed line from the ISR is the wrong behaviour the task asks you to remove.

The handler and main loop line by line

The solution's handler and main loop are short, and every line supports one of the rules above, starting with the handler. 

/* Shared with the ISR. volatile stops the compiler caching them in main (lesson 46). */
static volatile uint32_t press_count = 0;
static volatile bool press_pending = false;

/* ISR: short, no printf, no blocking. It only records that something happened. */
static void on_button(uint gpio, uint32_t events) {
    (void)gpio;
    (void)events;
    press_count++;          /* written only here, so the ISR never races with itself */
    press_pending = true;   /* main clears this after reporting */
}
  1. static volatile uint32_t press_count is a counter in RAM, made private to the file by static, while volatile makes every read and write happen, so main never reads a copy kept in a register from before the press.
  2. static volatile bool press_pending is the flag, a bool because it needs only two states, and like the counter it must be volatile, since the ISR writes it and main reads it.
  3. (void)gpio; and (void)events; silence the unused-argument warnings, because the callback must accept both arguments that the SDK passes even though this handler does not need them.
  4. press_count++; appears only in the ISR, so the counter has a single writer and needs no critical section in the handler itself, the race being in main, which reads it.
  5. press_pending = true; sets the flag for main, and since the handler does nothing slower than these two writes, it can be this short.
int main(void) {
    stdio_init_all();
    gpio_init(BUTTON_PIN);
    gpio_set_dir(BUTTON_PIN, GPIO_IN);
    gpio_pull_up(BUTTON_PIN);   /* released = 1, pressed = 0, so the falling edge is a press */

    /* Installs the shared GPIO callback on this core and enables the falling-edge event. */
    gpio_set_irq_enabled_with_callback(BUTTON_PIN, GPIO_IRQ_EDGE_FALL, true, &on_button);
    printf("interrupts ready\n");

    while (true) {
        /* Read-and-clear is three memory operations. Disable interrupts so the ISR */
        /* cannot run between them and set a new press that we then clear unreported. */
        uint32_t saved = save_and_disable_interrupts();
        bool pending = press_pending;
        uint32_t total = press_count;
        press_pending = false;
        restore_interrupts(saved);

        if (pending) {
            printf("presses=%lu\n", (unsigned long)total);   /* EXPECT: presses=1 */
        }
        sleep_ms(LOOP_MS);
    }
}
  1. gpio_init, gpio_set_dir and gpio_pull_up make the pin an input with a pull-up, and the comment states the logic, released reading 1 and pressed reading 0, so the press is the falling edge; lesson 16 explains why a pull-up is needed.
  2. gpio_set_irq_enabled_with_callback does three things at once, enabling the falling-edge event on GP14, installing the shared bank 0 handler if this is the first event and recording on_button as the callback, the true meaning enable.
  3. The critical section is the block from the previous section, with the copies into pending and total made inside it and the printing outside.
  4. if (pending) prints only when a press was pending, so the serial log shows one line per press and nothing while the button is idle.
  5. sleep_ms(LOOP_MS) makes the loop wait 100 ms, which is acceptable here because the ISR has already recorded the press, so the delay changes only when the report appears and not whether it appears.

Hint for the callback

The callback signature is void f(uint gpio, uint32_t events). Pass GPIO_IRQ_EDGE_FALL for the event and true to enable it; the SDK calls your function, so there is nothing to register with the NVIC yourself.

Hint for the volatile qualifier

Look at the declarations: the flag and the count are written in the ISR and read in main, which lesson 46 explains requires volatile.

Common mistakes and how to spot them

printf in the handler

The serial monitor shows a pressed line from the ISR on every press, and on hardware with a busy UART the handler can wait for the buffer to drain while the other interrupts are delayed, a fault the starter contains on purpose. Delete the call, set a flag or a counter and let main print.

No volatile on the shared flag

main never reports, although the counter shown in the debugger rises with each press, because the compiler may read press_pending once into a register and never look at memory again, so the loop does not see the ISR's write. Declare both shared variables volatile; the debugger shows the difference quickest, the value in memory being right while the code never reads it.

Read-and-clear without a critical section

The report is sometimes one press behind and a press is missing from the log, although the count in the debugger is correct, because of the interleaving shown in the trace above. Wrap the three steps in save_and_disable_interrupts() and restore_interrupts(), as the solution does.

A callback that is never enabled

Pressing the button prints nothing and the count in the debugger does not move, because the handler is installed but the event was never enabled, so the NVIC never receives the request. Check that the third argument of gpio_set_irq_enabled_with_callback() is true and that the event mask is GPIO_IRQ_EDGE_FALL for a press with a pull-up.

One press counted as several

On real hardware one push of a mechanical button prints two or three presses lines, because the contact bounces and the pin falls several times, which the simulator does not show, since the starter's diagram sets the button's bounce attribute to 0 so that one press makes one edge. Debounce the events as lesson 52 does, either in the handler with a timestamp check or in main with an integrator.

Interrupt design in production firmware

Professional firmware uses this pattern widely, the ISR doing the minimum of reading the hardware event, recording it in a buffer or a flag and returning, while the main loop or a task does the rest. Code review checks every handler for blocking calls and logging and every shared variable for being volatile, protected by a critical section or written from one place only, and a reviewer who finds a printf inside an ISR asks for it to be moved out.

The same design appears on bigger systems, where a real-time operating system's ISR hands data to a queue and wakes a task instead of doing the work itself, as the FreeRTOS tasks of lesson 87 show under the same rule. Priority decides which handler runs first when two events arrive together, so a safety input is given a higher priority than a status LED.

Summary

  • An interrupt makes the core stop main and run a handler, and on the RP2040 each core has its own NVIC with 26 connected sources.
  • All GPIO pins in bank 0 share IRQ 13, and the SDK's handler finds the pin, acknowledges the event and calls your callback with the pin and the event mask.
  • The callback is registered with gpio_set_irq_enabled_with_callback(), using GPIO_IRQ_EDGE_FALL and true for a press on a pull-up.
  • Priority decides which pending interrupt runs first, and at equal priority the lower IRQ number wins.
  • An ISR stays short, setting a flag or adding to a counter, and never calls printf or blocks.
  • Shared variables are declared volatile, which stops caching and nothing more.
  • A read-and-clear of shared data needs save_and_disable_interrupts() and restore_interrupts(), because an ISR can run between any two of its steps.
  • Real buttons bounce, so one press can raise several edges, and the events must be debounced before they are counted.
