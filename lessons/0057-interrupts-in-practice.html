Interrupts in practice

An interrupt lets a button press reach the CPU without a polling loop. The handler must finish fast, and the data it shares with main must be read in a way that cannot be interrupted halfway.

By the end of this lesson you can register a GPIO falling-edge callback on the Pico SDK, keep an interrupt service routine (ISR) short and free of printf, and read and clear a shared counter in main inside a critical section.

The idea

An interrupt is a hardware event that makes the core stop what it is doing, save a few registers on the stack and run a handler (lesson 34). On the RP2040 the event goes through the NVIC, which has 32 interrupt inputs. Only the lower 26 are connected to anything, and inputs 26 to 31 are tied to zero, so they never fire RP2040 datasheet, section 2.3.2. The M0+ core has its own exception vector table. Lesson 42 covers how that table gets its addresses from the startup code.

All GPIO pins share one interrupt line per bank. The GPIO bank 0 interrupt is IRQ 13 (RP2040 datasheet, Table 80). When a pin event happens, the single handler for bank 0 checks which pins had events, then calls the callback you registered. The SDK's gpio_set_irq_enabled_with_callback() installs that callback and enables one edge event on one pin Pico SDK, GPIO reference.

Rules for an ISR

Three rules follow from the fact that the ISR preempts main at an arbitrary instruction:

  1. Keep it short. While the ISR runs, the interrupt that calls it is held off, and so are any others at the same or lower priority. Set a flag and return.
  2. Do not block and do not call printf. printf writes to a UART that may be full, and it is not reentrant: if main was inside printf when the ISR runs, the two calls can corrupt each other's buffer.
  3. Share data with volatile, and make multi-step updates atomic. volatile stops the compiler from caching the flag (lesson 46). It does not stop an interrupt from landing between a read and a clear.

Critical sections

A critical section is a short stretch of code that runs with interrupts disabled. The SDK provides save_and_disable_interrupts(), which returns the old interrupt state, and restore_interrupts(), which puts it back Pico SDK, hardware/sync.h. On the Cortex-M0+ the disable is a write to PRIMASK, one bit that masks all configurable interrupts. Use the save-and-restore pair, not a plain disable. Code that is already inside a critical section should not turn interrupts back on when it finishes. 

/* main loop: read and clear the flag and count as one step */
uint32_t saved = save_and_disable_interrupts();
bool pending = press_pending;     /* 1. read the flag */
uint32_t total = press_count;     /* 2. read the count */
press_pending = false;             /* 3. clear the flag */
restore_interrupts(saved);

Without the critical section, an ISR could run between steps 2 and 3. It would increment the count and set the flag, and then main would clear the flag and report a count that misses the new press. Each single 32-bit load or store is atomic on this core, but three of them in a row are not.

volatile is not a lock. It stops the compiler from caching a variable, and nothing more. A count++ in the ISR and a read-and-clear in main still need the critical section above.

Hint for the callback

The callback signature is void f(uint gpio, uint32_t events). Pass GPIO_IRQ_EDGE_FALL for the event and true to enable it. The SDK calls your function, so you do not register it with the NVIC yourself.

Hint for the volatile qualifier

Look at the declarations: the flag and the count are written in the ISR and read in main. Lesson 46 explains why that needs volatile.

You registered a hardware callback, kept the handler to one flag and one counter, and read the shared state in a critical section. That is the pattern behind most interrupt-driven firmware.

"Why must an ISR be short, and what goes wrong if you call printf from one?" Answer out loud in 60 seconds, then compare.

Model answer

While the ISR runs, the interrupt that called it and any at the same or lower priority wait, so a long ISR adds latency to everything else. printf can block on a full UART and is not reentrant, so calling it from an ISR can deadlock or corrupt output that main was writing. The usual pattern is to set a flag or push data to a buffer in the ISR and do the slow work in main.

RP2040 datasheet, section 2.3.2 (Interrupts) and Table 80: read which IRQ numbers are connected, and where IO_IRQ_BANK0 sits. Then read the GPIO section of the Pico SDK GPIO reference for gpio_set_irq_enabled_with_callback.
