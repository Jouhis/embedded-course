"Your sensor is on I2C and your buttons use interrupts. The main loop must never block. Walk me through the design, and say where each blocking risk is." Explain out loud for 90 seconds, then compare.

Model answer

A super-loop with deadlines. Each sensor read is a single short I2C transaction that returns at once, so the loop never waits for a sample. The buttons' interrupts only set flags, and the loop reads and clears those flags with interrupts briefly disabled, so no press is lost. The blocking risks are the bus transactions themselves, which are bounded by the I2C speed, and any wait loop someone adds later, such as polling a flag with no timeout. Name each one and bound it.

"Two cores share a buffer, and an interrupt also touches it. What protects it, and why is volatile not enough?" Explain out loud for 60 seconds, then compare.

Model answer

A spinlock protects the buffer between the two cores, and disabling interrupts on the holding core protects it from the interrupt on that core. volatile only forces the compiler to reload the value, so it does not stop two read-modify-writes from interleaving, and it gives no ordering between cores. Hand-off through an inter-core FIFO is the other option, when one core owns the data at a time.

"When would you use PIO and DMA instead of a timer and an interrupt?" Explain out loud for 60 seconds, then compare.

Model answer

When the timing is too tight or too regular for the CPU to meet with interrupts, such as a fixed bit-level protocol or a fast LED strip. PIO runs the bit timing in its own state machine, and DMA moves the data with pacing from the PIO's data request, so the CPU is not in the timing path. The cost is a more complex design, and a program that is harder to change, so use the simpler tools when they meet the timing.
