The build pipeline: compile, link, and the linker script

A build is four tools in a row. The last one, the linker, decides where every byte of your program lives, and the linker script is where you can read that decision.

By the end of this lesson you can name the four build stages, read the sections of an ELF file with arm-none-eabi-size, and explain how the linker script places .data in RAM while storing its initial values in flash.

The idea

Your main.c goes through four stages. The preprocessor expands #include and macros such as GPIO_BSRR_BR13 into plain C. The compiler turns that C into assembly text for the target. The assembler turns the assembly into an object file (.o) of machine code, with symbols that still have no final address. The linker joins all the object files and the libraries, places every section at an address, and writes the final ELF file. Lab 2 uses the first stage: you will run the preprocessor by hand and see GPIO_BSRR_BR13 become (0x1UL << 29).

The CMake build for the STM32 template passes the same flags to every stage: -mcpu=cortex-m3 -mthumb, plus -ffunction-sections -fdata-sections, which give each function and variable its own section so the linker can drop what is unused (templates/common/stm32f1.cmake). The Cortex-M3 target flags are set once, so every object agrees on the instruction set.

Reading a real ELF file

The demo project for this lesson is built with the same flags. Its sections, from arm-none-eabi-size -A build/blink, look like this:

SectionSize (bytes)AddressWhat it holds
.isr_vector2680x08000000The vector table, from the startup file (lesson 42)
.text7520x08000000 + 268Code, in flash
.rodata180in flashRead-only data, such as const tables
.data80x20000000 (RAM)Initialised globals. Their starting values are stored in flash.
.bss32in RAM, after .dataZero-initialised globals, cleared at startup
._user_heap_stack1536in RAMReserved space for heap and stack, not code. size counts it as .bss in its totals.

The .text, .rodata and .data rows are the sections most textbooks name. .bss and ._user_heap_stack are the RAM-only sections. The .data section in the table is 8 bytes because the demo has one initialised global of 4 bytes and SystemCoreClock, another 4 bytes, which the ST system file initialises to 8000000.

The linker script, from the template

The linker script is templates/common/stm32f103c8.ld. Its first job is the memory map. It names two regions and their sizes: 

MEMORY
{
  FLASH (rx)  : ORIGIN = 0x08000000, LENGTH = 64K
  RAM   (rwx) : ORIGIN = 0x20000000, LENGTH = 20K
}

Its second job is the sections. The part that matters most is .data, which uses two addresses at once: 

_sidata = LOADADDR(.data);       /* where the initial values live: flash */
.data :
{
  _sdata = .;
  *(.data) *(.data*)
  _edata = .;
} > RAM AT> FLASH             /* runs in RAM, is stored in FLASH */

> RAM is the virtual address, where the variable lives while the program runs. AT> FLASH is the load address, where the initial bytes sit in the image. The startup code copies from the load address to the virtual address before main(). Lesson 42 walks through that copy.

The .bss section has only a virtual address, > RAM, because there is nothing to store: the startup code writes zeros. The last section, ._user_heap_stack, reserves space for the stack from the top of RAM downward, which is why _estack is set to ORIGIN(RAM) + LENGTH(RAM).

Keep the linker's own rules straight: a section that is written to at run time must have a RAM address. A const object in flash is fine because nothing writes to it. Putting a writable variable in a flash-only section would link cleanly and then fail at run time.

The map file

The linker also writes a map file, blink.map, because the template passes -Wl,-Map=blink.map (stm32f1.cmake). It shows where each symbol landed. In the lab 2 build it contains lines like these: 

.isr_vector     0x08000000      0x10c
                0x08000000                        g_pfnVectors
                0x08000244                        main
.data           0x20000000        0x4 load address 0x08000414
                0x08000414                        _sidata = LOADADDR (.data)

The load address on the .data line is the flash address where the initial values are stored. Lesson 43 shows how to find a symbol in the map and read its address.

File formats: ELF, HEX, and UF2

The ELF file is the full result, with symbols and debug information, so Wokwi and GDB can use it. The STM32 template also converts it to Intel HEX with objcopy -O ihex (stm32f1.cmake), a text format that many programmers and tools accept. The RP2040's bootrom accepts UF2 files over USB: the chip appears as a mass-storage drive, and you copy a UF2 file onto it. RP2040 datasheet, section 2.8.4 (USB Mass Storage Interface). The Pico SDK's linker script is different from the STM32 one. It is built from fragments: the default memory map is src/rp2040/pico_platform/memmap_default.ld in pico-sdk 2.3.1, which includes the RAM and flash definitions from the other fragments.

Try it in Wokwi and the terminal

Open projects/0041-build-pipeline in VS Code. Build it with Ctrl+Shift+B. Then open the terminal in that folder and run the size tool. The demo has one initialised global and one zero-initialised global, and a const table.

  1. Run arm-none-eabi-size -A build/blink. Note the .data and .bss sizes.
  2. Open main.c and change uint32_t g_initialised = 0x1234ABCDU; to uint32_t g_initialised;. This removes the initial value.
  3. Before you rebuild, predict the new .data and .bss sizes. Then rebuild and run the size tool again.
  4. Find g_initialised in build/blink.map. It should be in .bss now, not .data.
Hint

A 4-byte uint32_t moves from .data to .bss. Count the change: .data shrinks by 4 bytes, and .bss grows by 4 bytes. Revert the change afterwards, or copy the file back from the solution folder.

Put the file back when you finish. The lab and the next lesson assume the demo still prints g_initialised with the value 0x1234ABCD.

Model answer

The preprocessor, compiler and assembler turn each source file into an object file. The linker joins them with the libraries and the linker script, which assigns each section an address and writes an ELF file. A global with no initial value is in .bss, and one with an initial value is in .data: its variable lives in RAM, and its starting value is stored in flash at the load address. Startup code copies .data from flash to RAM and clears .bss before main() runs. A const global stays in flash in .rodata.

RP2040 datasheet: section 2.8 (Bootrom) and 2.8.4 (USB Mass Storage Interface, UF2). It explains how a UF2 file reaches flash. Read the linker script in templates/common/stm32f103c8.ld alongside it.
