The build pipeline: compile, link, and the linker script

A build is four tools in a row. The last one, the linker, decides where every byte of your program lives, and the linker script is where you can read that decision.

By the end of this lesson you can name the four build stages, read the sections of an ELF file with arm-none-eabi-size, and explain how the linker script places .data in RAM while storing its initial values in flash.

Where we are and why it matters

So far every lesson has built a project with the Ctrl+Shift+B task and never looked inside the result. Lesson 38 used the vendor header to get a register address, and lesson 40 used the clock values from that header. At build time, those names become numbers. The preprocessor puts the header's macros into your code, the compiler and assembler produce machine code, and the linker assigns every function and variable an address in flash or RAM.

This lesson is about the case where a build succeeds but the chip misbehaves. A global variable has the wrong value at start-up, the program is too large for the flash, or a new variable silently pushes the stack into data. Each of these is a question about where the linker put things. In industry the firmware team reads the map file and the section sizes after every change, and a reviewer may ask why the RAM use went up by 200 bytes. The rest of this lesson shows how to answer such questions.

The four stages

Your main.c goes through four stages. Each one is a separate tool, and the output of one is the input of the next.

  1. The preprocessor expands #include lines and macros into plain C text. It does not know about types or registers. It only substitutes text. The output is still C.
  2. The compiler turns that C into assembly text for the target processor. Here the target is the Cortex-M3, selected by the -mcpu=cortex-m3 -mthumb flags.
  3. The assembler turns the assembly into an object file, .o. The object file holds machine code and data, but the addresses are not final, and symbols that point to other files are still unresolved.
  4. The linker joins all the object files and the libraries, places every section at an address, resolves every symbol, and writes the final ELF file. It is the only stage that reads the linker script.

Lab 2 runs the first stage by hand. It shows GPIO_BSRR_BR13 becoming (0x1UL << (29U)), so you can watch the macro expand. The CMake build for the STM32 template passes the same flags to every stage. The template adds -ffunction-sections -fdata-sections, which give each function and each variable its own section, so the linker can drop what is not used. The --gc-sections link flag does the dropping (templates/common/stm32f1.cmake).

Sections: the units the linker places

The compiler does not emit one block of code and data. It emits named sections, each a group of bytes with a name and a purpose. The linker places each section as a unit. The names you will see are .text for code, .rodata for read-only data, .data for initialised variables that can change, and .bss for variables that start at zero. The vector table has its own section, .isr_vector, so the linker can put it at the start of flash, where the core looks for it (lesson 42).

Each section has two addresses. The load address is where its bytes are stored in the image that gets programmed into flash. The run address, which the linker calls the virtual address, is where the core reads and writes the section while the program runs. For most sections the two are the same. The exception is .data, and that exception is what the rest of this lesson explains.

Reading a real ELF file

The size tool also prints a summary in its default format, with text, data and bss totals. Those totals group the sections in a fixed way, and the table lets you check them. In this build, the default output reads text 1200, data 16 and bss 1568. The text total is .isr_vector, .text and .rodata together (268 + 752 + 180 = 1200). The data total is .data plus the two arrays (8 + 4 + 4 = 16). The bss total is .bss plus the reserved block (32 + 1536 = 1568), so the reserved heap and stack count as bss in the summary, even though they are not zero-initialised data.

The .data section has 8 bytes because the demo has two initialised globals of 4 bytes each: g_initialised and SystemCoreClock. The ST system file gives SystemCoreClock the starting value 8000000, so it is initialised too.

A worked example: where the bytes go

Take the addresses from the map file and trace the bytes of this build. The flash is written first, from address 0x08000000 upwards.

  1. The vector table is 268 bytes, or 0x10C, at 0x08000000. It ends at 0x0800010C, where .text begins.
  2. .text is 752 bytes, or 0x2F0. It ends at 0x080003FC, where .rodata begins. main is at 0x08000270, inside .text.
  3. .rodata is 180 bytes, or 0xB4. It ends at 0x080004B0. The kLookup table in the demo sits at 0x08000480, inside it.
  4. The two arrays take 4 bytes each, at 0x080004B0 and 0x080004B4. The initial values of .data start at 0x080004B8. That address is _sidata, the symbol the startup code reads.
  5. The .data bytes, 8 of them, are stored at 0x080004B8 to 0x080004BF. The run address of the same bytes is 0x20000000, in RAM.
  6. The .bss section starts at 0x20000008, and it is 32 bytes. It has no bytes in flash. Its load address in the map file is 0x080004C0, but that is only a placeholder: the ELF section flags say ALLOC, with no CONTENTS.

The RAM budget follows from the same numbers. The reserved block runs from 0x20000028 to 0x20000628. The stack starts at the top of RAM, 0x20005000, and grows downward. The room between the end of the reserved block and the stack top is 0x20005000 minus 0x20000628, which is 0x49D8, or 18,904 bytes. That space is shared by the stack and anything else you add, so a new array of 1000 bytes in .bss reduces it by 1000 bytes.

The linker script, from the template

The linker script for the Blue Pill is templates/common/stm32f103c8.ld. Its first job is the memory map. It names two regions and their sizes: 

MEMORY
{
  FLASH (rx)  : ORIGIN = 0x08000000, LENGTH = 64K
  RAM   (rwx) : ORIGIN = 0x20000000, LENGTH = 20K
}

The line before it sets the top of the stack: _estack = ORIGIN(RAM) + LENGTH(RAM);. That is 0x20000000 plus 20 × 1024, which is 0x20005000. The stack pointer starts there, and the first push moves it downward. The first word of the vector table holds the same value, and the core reads that word as the initial stack pointer at reset (lesson 42 covers the table).

The second job of the script is the sections. The part that matters most is .data, which uses two addresses at once: 

_sidata = LOADADDR(.data);       /* where the initial values live: flash */
.data :
{
  . = ALIGN(4);
  _sdata = .;
  *(.data) *(.data*)
  . = ALIGN(4);
  _edata = .;
} > RAM AT> FLASH             /* runs in RAM, is stored in FLASH */

The first line asks the linker for the load address of .data and stores it in _sidata. The block that follows collects every .data input section and records its start and end as _sdata and _edata. The final line has two parts. > RAM is the run address, where the variable lives while the program runs. AT> FLASH is the load address, where the initial bytes sit in the image. The startup code copies from the load address to the run address before main(). Lesson 42 walks through that copy.

The .bss block has only > RAM. There is no AT clause because there is nothing to store. The startup code writes zeros over that RAM. The last block, ._user_heap_stack, is different from what its name suggests. It does not reserve the stack. It adds _Min_Heap_Size (0x200) and _Min_Stack_Size (0x400) to the location counter, so that the linker fails if the minimum heap and stack do not fit in RAM. The stack itself starts at _estack and grows down.

Keep the linker's rules straight: a section that is written at run time must have a RAM run address. A const object in flash is fine because nothing writes to it. If you place a writable variable in a section that only has a flash address, the link can succeed, and the program fails at run time when it first writes that variable.

The map file

The linker also writes a map file, blink.map, because the template passes -Wl,-Map=blink.map (stm32f1.cmake). It lists every section and symbol with its address. These lines are from the build in this lesson: 

.isr_vector    0x08000000      0x10c
               0x08000000                g_pfnVectors
.text          0x0800010c      0x2f0
               0x08000270                main
               0x080004b8                _sidata = LOADADDR (.data)
.data          0x20000000        0x8 load address 0x080004b8
               0x20000000                g_initialised
               0x20000004                SystemCoreClock

The load address on the .data line is the flash address where the initial values are stored, and it matches the _sidata line above it. Every symbol that the code uses has its own line, so you can check that a variable really landed where you expect. Lab 2 has you read the map file for specific symbols.

File formats: ELF, HEX, and UF2

The ELF file is the full result, with symbols and debug information, so Wokwi and GDB can use it. The STM32 template also converts it to Intel HEX with objcopy -O ihex (stm32f1.cmake). Intel HEX is a text format that records each byte with its address, so tools can program a chip from it without understanding the ELF layout.

The RP2040's bootrom accepts UF2 files over USB. The chip appears as a mass-storage drive, and you copy a UF2 file onto it. Each UF2 block carries its own target address and a family ID, and the bootrom writes the blocks to flash or RAM and reboots (RP2040 datasheet, section 2.8.4 (USB Mass Storage Interface)). The Pico SDK's linker script is built from fragments. The default memory map is src/rp2040/pico_platform/memmap_default.ld in pico-sdk 2.3.1, and it includes the memory and section fragments from the other folders.

Try it in Wokwi and the terminal

Open projects/0041-build-pipeline in VS Code. Build it with Ctrl+Shift+B. Then open a terminal in that folder, and run the size tool. The demo has one initialised global, one zero-initialised global and a const table. The toolchain must be on your path, which the VS Code build task arranges.

  1. Run arm-none-eabi-size -A build/blink.elf. Find the .data line, which should read 8 bytes, and the .bss line, which should read 32 bytes.
  2. Open main.c and change uint32_t g_initialised = 0x1234ABCDU; to uint32_t g_initialised;. This removes the initial value.
  3. Before you rebuild, predict the new .data and .bss sizes. Then rebuild and run the size tool again. You should see .data at 4 bytes and .bss at 36 bytes.
  4. Find g_initialised in build/blink.map. It should be in .bss now, not .data, and it should have no load address of its own.
  5. Run the simulator. The serial line g_initialised value: 0x00000000 should now print, because a zero-initialised global starts at zero.
Hint

A 4-byte uint32_t moves from .data to .bss. Count the change: .data shrinks by 4 bytes, and .bss grows by 4 bytes. Revert the change afterwards, or copy the file back from the solution folder.

Put the file back when you finish. The lab and the next lesson assume the demo still prints g_initialised with the value 0x1234ABCD.

Common mistakes

Mistake 1: reading the map file's load address for .bss as data in flash

Symptom: the map file shows a load address for .bss, and you think a table of zeros is stored in flash, so you search the flash for it. Fix: check the ELF flags with arm-none-eabi-objdump -h. The .bss section is ALLOC only, with no CONTENTS, so nothing is stored. The startup code writes the zeros.

Mistake 2: a writable variable in a const-like declaration

Symptom: you declare a lookup table as const, then try to change one entry at run time. A direct assignment is a compile error. If you cast the const away, the write targets flash, which the program cannot change, so the table does not change. Fix: remove const if the table must change, which moves it to .data (initialised) or .bss (zero). Then the section has a RAM run address, and the write goes to RAM.

Mistake 3: forgetting that globals cost RAM at every boot

Symptom: a new 2 KB buffer works in the simulator, and then the stack collides with it under load, and the program corrupts variables without any error. Fix: check the .bss and .data totals after every change. Subtract them from the 20 KB RAM, and keep the stack room in mind. In this build, 18,904 bytes sit between the reserved block and the stack top, and every global reduces that margin.

Mistake 4: editing the linker script to hide a size error

Symptom: the link fails with a region overflow, and someone raises the length of RAM in the script to make the error go away. The chip does not have that RAM, so the program runs until the extra range is touched. Fix: change the memory map only when the chip really has the memory. Reduce the globals, or check the datasheet for the true size.

In real projects

Teams check the size tool output on every merge. Many keep a small script that prints the flash and RAM totals and fails the build if either crosses a limit. Code review asks whether a new global belongs in .bss, whether a large table should be const so it stays in flash, and whether a new dependency pulled in a large library. The linker script for a new board is part of the board support code, and it is reviewed with the same care as the register setup.

In interviews, the question "where does a global variable live?" is common, and it has a precise answer. A global with no initial value lives in .bss, and one with an initial value lives in .data: its run address is in RAM, and its starting bytes are stored in flash at the load address. A const global stays in flash in .rodata. Naming all three cases, and the copy that startup code makes, is a complete answer.

Summary

  • The four stages are preprocessing, compiling, assembling and linking. Only the linker reads the linker script.
  • The compiler emits named sections, and the linker places each one. The vector table is .isr_vector.
  • A .data section has a RAM run address, a flash load address, and the startup code copies it between them.
  • .bss has a run address only, and nothing is stored for it. const data stays in flash.
  • The map file lists each section and symbol with its address, and the size tool gives section totals.
  • The STM32 template makes an ELF file, and objcopy turns it into Intel HEX. The RP2040 bootrom accepts UF2.

Model answer

The preprocessor, compiler and assembler turn each source file into an object file. The linker joins them with the libraries and the linker script, which assigns each section an address and writes an ELF file. A global with no initial value is in .bss, which is cleared at startup and has no bytes stored in flash. A global with an initial value is in .data: its variable lives in RAM, and its starting value is stored in flash at the load address. Startup code copies .data from flash to RAM and clears .bss before main() runs. A const global stays in flash in .rodata.
