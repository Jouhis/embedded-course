The build pipeline: compile, link, and the linker script

The tools that turn C source into a placed firmware image

By the end of this lesson you can name the four build stages, read the sections of an ELF file with arm-none-eabi-size, and explain how the linker script places .data in RAM while storing its initial values in flash.

Inside a successful build

Every lesson so far has built a project with the Ctrl+Shift+B task without looking inside the result. Lesson 38 took a register address from the vendor header and lesson 40 the clock values, and at build time those names become numbers: the preprocessor inserts the header's macros into the code, the compiler and assembler produce machine code, and the linker assigns every function and variable an address in flash or RAM.

This lesson concerns the case in which a build succeeds but the chip misbehaves: a global variable has the wrong value at start-up, the program no longer fits in flash, or a new variable silently pushes the stack into data. Each is a question about where the linker put things. In industry the firmware team reads the map file and the section sizes after every change, and a reviewer may well ask why RAM use rose by 200 bytes, so the rest of this lesson shows how to answer such questions.

The four build stages

main.c passes through four stages, each a separate tool whose output feeds the next.

  1. The preprocessor expands #include lines and macros into plain C text. It knows nothing of types or registers and only substitutes text, so its output is still C.
  2. The compiler turns that C into assembly text for the target processor, here the Cortex-M3 selected by the -mcpu=cortex-m3 -mthumb flags.
  3. The assembler turns the assembly into an object file, .o, holding machine code and data whose addresses are not yet final and whose references to other files are still unresolved.
  4. The linker joins all the object files and libraries, places every section at an address, resolves every symbol and writes the final ELF file. It is the only stage that reads the linker script.

Lab 2 runs the first stage by hand and shows GPIO_BSRR_BR13 becoming (0x1UL << (29U)), so the macro expansion can be watched directly. The CMake build for the STM32 template passes the same flags to every stage and adds -ffunction-sections -fdata-sections, which give each function and variable its own section so that the linker can drop unused ones, a job done by the --gc-sections link flag (templates/common/stm32f1.cmake).

Sections, load addresses and run addresses

The compiler does not emit one block of code and data but named sections, each a group of bytes with a name and a purpose, which the linker places as units. The names met most often are .text for code, .rodata for read-only data, .data for initialised variables that can change and .bss for variables that start at zero, while the vector table has its own section, .isr_vector, so that the linker can put it at the start of flash, where the core looks for it (lesson 42).

Each section has two addresses. The load address is where its bytes are stored in the image programmed into flash, and the run address, which the linker calls the virtual address, is where the core reads and writes the section while the program runs. For most sections the two coincide, and the exception, .data, is what the rest of this lesson explains.

The text total combines .isr_vector, .text and .rodata (268 + 752 + 180 = 1200), the data total is .data plus the two arrays (8 + 4 + 4 = 16), and the bss total is .bss plus the reserved block (32 + 1536 = 1568), so the summary counts the reserved heap and stack as bss even though they are not zero-initialised data.

.data holds 8 bytes because the demo has two initialised 4-byte globals, g_initialised and SystemCoreClock, the latter given the starting value 8000000 by the ST system file.

Worked example: where the bytes of the build go

Using the addresses from the map file, we trace the bytes of this build through flash, which is written from address 0x08000000 upwards. Before following the steps, guess where the initial values of .data end up.

  1. The vector table, 268 bytes or 0x10C, sits at 0x08000000 and ends at 0x0800010C, where .text begins.
  2. .text, 752 bytes or 0x2F0, ends at 0x080003FC, where .rodata begins, and contains main at 0x08000270.
  3. .rodata, 180 bytes or 0xB4, ends at 0x080004B0 and contains the demo's kLookup table at 0x08000480.
  4. The two arrays take 4 bytes each, at 0x080004B0 and 0x080004B4, after which the initial values of .data start at 0x080004B8, the address of _sidata, the symbol the startup code reads.
  5. The 8 bytes of .data are stored at 0x080004B8 to 0x080004BF, while the run address of the same bytes is 0x20000000 in RAM.
  6. .bss starts at 0x20000008 and is 32 bytes long, with no bytes in flash. Its load address in the map file, 0x080004C0, is only a placeholder, since the ELF section flags show ALLOC without CONTENTS.

The RAM budget follows from the same numbers. The reserved block runs from 0x20000028 to 0x20000628, and the stack starts at the top of RAM, 0x20005000, and grows downwards, so the room between the end of the reserved block and the stack top is

free = 0x20005000 − 0x20000628 = 0x49D8 = 18 904 bytes(1)

where the first address is the stack top and the second the end of the reserved block. This space is shared by the stack and anything else added later, so a new 1 000-byte array in .bss reduces it by 1 000 bytes.

The memory regions in the linker script

The Blue Pill's linker script is templates/common/stm32f103c8.ld, and its first job is the memory map, naming two regions and their sizes. 

MEMORY
{
  FLASH (rx)  : ORIGIN = 0x08000000, LENGTH = 64K
  RAM   (rwx) : ORIGIN = 0x20000000, LENGTH = 20K
}

The line before it sets the top of the stack, _estack = ORIGIN(RAM) + LENGTH(RAM);, which is 0x20000000 plus 20 × 1024, or 0x20005000. The stack pointer starts there and the first push moves it downwards, and the first word of the vector table holds the same value, which the core reads as the initial stack pointer at reset (lesson 42 covers the table).

Initialised data travels like clothes in a suitcase. At build time the linker packs the starting values of .data into flash, the suitcase, and books them a room in RAM, where the program will use them, and at reset the startup code unpacks the suitcase into the room. That is why .data has two addresses in the map file, where it is packed and where it lives. Unlike a suitcase, though, the flash copy is never emptied, so after a reset the same values are unpacked again.

The .data, .bss and heap-stack blocks

The script's second job is the sections, and the part that matters most is .data, which uses two addresses at once. 

_sidata = LOADADDR(.data);       /* where the initial values live: flash */
.data :
{
  . = ALIGN(4);
  _sdata = .;
  *(.data) *(.data*)
  . = ALIGN(4);
  _edata = .;
} > RAM AT> FLASH             /* runs in RAM, is stored in FLASH */

The first line asks the linker for the load address of .data and stores it in _sidata. The following block collects every .data input section and records its start and end as _sdata and _edata, and its final line has two parts: > RAM gives the run address, where the variable lives while the program runs, and AT> FLASH the load address, where the initial bytes sit in the image. The startup code copies from the load address to the run address before main(), as lesson 42 shows.

The .bss block has only > RAM, with no AT clause, because there is nothing to store, and the startup code writes zeros over that RAM. The last block, ._user_heap_stack, does less than its name suggests: rather than reserving the stack, it adds _Min_Heap_Size (0x200) and _Min_Stack_Size (0x400) to the location counter, so that the link fails if the minimum heap and stack do not fit in RAM, while the stack itself still starts at _estack and grows down.

A section written at run time must have a RAM run address. A const object in flash is fine because nothing writes to it, but a writable variable placed in a section with only a flash address can link successfully and then fail at run time the first time it is written.

The map file

The linker also writes a map file, blink.map, because the template passes -Wl,-Map=blink.map (stm32f1.cmake), and it lists every section and symbol with its address. These lines come from the build in this lesson. 

.isr_vector    0x08000000      0x10c
               0x08000000                g_pfnVectors
.text          0x0800010c      0x2f0
               0x08000270                main
               0x080004b8                _sidata = LOADADDR (.data)
.data          0x20000000        0x8 load address 0x080004b8
               0x20000000                g_initialised
               0x20000004                SystemCoreClock

The load address on the .data line is the flash address of the initial values, matching the _sidata line above it, and since every symbol the code uses has its own line, you can check that a variable really landed where you expected. Lab 2 has you read the map file for specific symbols.

ELF, Intel HEX and UF2 files

The ELF file is the complete result, with symbols and debug information that Wokwi and GDB use. The STM32 template also converts it to Intel HEX with objcopy -O ihex (stm32f1.cmake), a text format recording each byte with its address, so that tools can program a chip from it without understanding the ELF layout.

The RP2040's bootrom accepts UF2 files over USB, with the chip appearing as a mass-storage drive onto which the file is copied. Each UF2 block carries its own target address and a family ID, and the bootrom writes the blocks to flash or RAM and reboots (RP2040 datasheet, section 2.8.4 (USB Mass Storage Interface)). The Pico SDK's linker script is assembled from fragments, with the default memory map in src/rp2040/pico_platform/memmap_default.ld in pico-sdk 2.3.1 including the memory and section fragments from the other folders.

Try it in Wokwi and the terminal

Open projects/0041-build-pipeline in VS Code and build it with Ctrl+Shift+B, then open a terminal in that folder to run the size tool, which the VS Code build task puts on the path. The demo has one initialised global, one zero-initialised global and a const table.

  1. Run arm-none-eabi-size -A build/blink.elf and find the .data line, which should read 8 bytes, and the .bss line, which should read 32 bytes.
  2. Open main.c and change uint32_t g_initialised = 0x1234ABCDU; to uint32_t g_initialised;, removing the initial value.
  3. Predict the new .data and .bss sizes before rebuilding, then rebuild and run the size tool again; .data should now be 4 bytes and .bss 36 bytes.
  4. Find g_initialised in build/blink.map, where it should now be in .bss rather than .data, with no load address of its own.
  5. Run the simulator, which should now print g_initialised value: 0x00000000, because a zero-initialised global starts at zero.
Hint

A 4-byte uint32_t moves from .data to .bss, so .data shrinks by 4 bytes and .bss grows by 4. Revert the change afterwards, or copy the file back from the solution folder.

Restore the file when you finish, because the lab and the next lesson assume that the demo still prints g_initialised with the value 0x1234ABCD.

Common mistakes and how to spot them

The .bss load address read as data in flash

The map file shows a load address for .bss, and a search of flash for the table of zeros finds nothing. Check the ELF flags with arm-none-eabi-objdump -h: .bss is ALLOC only, without CONTENTS, so nothing is stored, and the startup code writes the zeros.

A table that must change declared const

A lookup table declared const refuses to change at run time: a direct assignment is a compile error, and casting the const away aims the write at flash, which the program cannot change. Remove const if the table must change, which moves it to .data if initialised or .bss if zero, so that the section has a RAM run address and the write reaches RAM.

The RAM cost of globals forgotten

A new 2 kB buffer works in the simulator, then under load the stack collides with it and variables are corrupted without any error. Check the .bss and .data totals after every change, subtract them from the 20 kB of RAM and keep the stack room in mind; in this build 18 904 bytes separate the reserved block from the stack top, and every global reduces that margin.

The linker script edited to hide a size error

The link fails with a region overflow, someone raises the RAM length in the script to silence it, and the program then runs until it touches the range the chip does not have. Change the memory map only when the chip really has the memory, and otherwise reduce the globals or check the datasheet for the true size.

Size checks and linker scripts in real projects

Teams check the size tool output on every merge, and many keep a small script that prints the flash and RAM totals and fails the build when either crosses a limit. Code review asks whether a new global belongs in .bss, whether a large table should be const so that it stays in flash, and whether a new dependency pulled in a large library. The linker script of a new board belongs to the board support code and is reviewed with the same care as the register setup.

Summary

  • The four stages are preprocessing, compiling, assembling and linking, and only the linker reads the linker script.
  • The compiler emits named sections that the linker places as units, with the vector table in .isr_vector.
  • .data has a RAM run address and a flash load address, and the startup code copies it between them.
  • .bss has only a run address with nothing stored for it, while const data stays in flash.
  • The map file lists each section and symbol with its address, and the size tool gives section totals.
  • The STM32 template produces an ELF file that objcopy converts to Intel HEX, and the RP2040 bootrom accepts UF2.
RP2040 datasheet: section 2.8 (Bootrom) and 2.8.4 (USB Mass Storage Interface, UF2). It explains how a UF2 file reaches flash. Read the linker script in templates/common/stm32f103c8.ld alongside it, and compare its sections with the table above.
