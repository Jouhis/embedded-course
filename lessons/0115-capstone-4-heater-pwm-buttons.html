Capstone 4: heater PWM, buttons, display, and safety checks

The dryer can now read its sensor and turn a temperature into a number. This lesson makes it act: a timer sets the heater power, a debounced button gives one event per press, the OLED shows the state, and the safety checks decide when the heater must be cut.

By the end of this lesson you can work out a timer's PWM period and duty from its prescaler, auto-reload and compare values, explain why a debounced button gives one event per press, and write a safety check that passes one host test per rule.

Where we are and why it matters

Lesson 114 turned the ADC code into hundredths of a degree and tested the conversion on the PC. This lesson adds the parts that act on the number. The heater is switched by a timer output, the start and material buttons become events, the OLED shows four lines of text, and the safety checks decide whether the heater must be cut. Requirements 1.3 and 1.4 in the Capstone 1 table ask for the button and the display, and requirements 2.1 to 2.4 are the four safety rules.

Each part can fail in a way that looks correct on the screen. A button read as a raw level advances a preset several times per press. A safety rule with a wrong boundary lets a fault through by one count. The hardware ideas come from lesson 59 (PWM), lesson 71 (timers), lesson 52 (debounce), lesson 61 (the I2C OLED) and lesson 56 (state machines).

The heater: from on-off control to duty cycle

The heater controller in app/control.c is a bang-bang controller with hysteresis. A bang-bang controller has two outputs: full power or none. With hysteresis, it switches the heater fully on when the chamber is more than a band below the setpoint, and fully off when the chamber is more than the band above it. Inside the band it keeps its previous state. The band is set by CONTROL_HYST_CENTI, which is 100, or 1.00 °C. The dead band stops the output from chattering on and off each time the temperature crosses the setpoint. The hysteresis idea is the same one that keeps a thermostat from clicking.

Bang-bang is easy to test, but it overshoots: the heater runs at full power until the chamber is already past the setpoint. Lesson 116 replaces it with a PID controller, which lowers the power before the setpoint is reached. Either controller still needs a way to set the power, and that way is pulse-width modulation.

Pulse-width modulation (PWM) switches the output on and off with a fixed period. The fraction of each period that the output is high is the duty cycle. A 70 % duty gives 70 % of the average power, because the heater's temperature responds to the average and not to each switch. The heater's temperature changes over tens of seconds, so a switching rate of 1 kHz is far faster than the chamber can respond, and it leaves a wide margin for the controller's sample rate.

The timer: a counter that compares itself

A timer is a counter that counts clock ticks and compares its count with registers. Three registers set the PWM output on the Blue Pill's TIM3, channel 1, which is pin PA6:

  • The prescaler (PSC) divides the timer clock. The counter moves once every PSC + 1 input ticks.
  • The auto-reload value (ARR) is the top of the count. The counter runs from 0 up to ARR and then starts again at 0, so one period has ARR + 1 steps.
  • The compare register (CCR) sets where the output changes. In PWM mode 1, the output is high while the counter is below the compare value, and low from then until the period ends.

The board file assumes an 8 MHz timer clock. After reset the Blue Pill runs from its internal 8 MHz oscillator, which lesson 67 introduced, and the board file does not change that clock. The arithmetic is worth doing once by hand. A prescaler of 7 divides the 8 MHz clock by 8, giving a counter clock of 1 MHz. An auto-reload of 999 counts 1000 steps, so the period is 1000 ÷ 1 MHz = 1 ms, which is 1 kHz. The output is high while the count is below CCR. A compare value of 0 is always low, and a value of 1000 is always high, because the counter never reaches 1000. Those two endpoints need no special case, so the driver can accept any duty from 0 to 1000 and pass it straight to the register. The unit is permille, which is 0.1 % per step.

One period, step by step

Take a duty of 250 permille, which is 25 %. The driver writes 250 to the compare register. Each period has 1000 counter steps, numbered 0 to 999, and each step lasts 1 µs, because the counter clock is 1 MHz. For steps 0 to 249 the counter is below 250, so the output is high for 250 µs. For steps 250 to 999 the output is low for 750 µs. The period is 1 ms, and the high time is 0.25 ms, so the duty is 0.25 ms ÷ 1 ms = 25 %. Writing 500 would give 50 %, and writing 1000 would keep the output high for every step.

The same method gives the value for any other frequency. A fan driver on the same 1 MHz counter clock needs 1 MHz ÷ 25 kHz = 40 ticks per period, and so an auto-reload of 39. You can check that on the quiz below.

The board file, line by line

The board file sets up the timer with a few register writes. These lines are from hw/hal_bluepill.c, in the order the file writes them: 

TIM3->PSC = PWM_PSC;                 /* 7: divide the 8 MHz clock by 8 */
TIM3->ARR = PWM_ARR;                 /* 999: the counter runs from 0 to 999 */
TIM3->CCMR1 = (6U << 4) | TIM_CCMR1_OC1PE;   /* OC1M = 110 (PWM mode 1), preload on */
TIM3->CCER = TIM_CCER_CC1E;          /* let channel 1 drive its output pin */
TIM3->CCR1 = 0U;                     /* start with the heater off */
TIM3->CR1 = TIM_CR1_ARPE;            /* buffer ARR until the next period */
TIM3->EGR = TIM_EGR_UG;              /* load the buffered values now */
TIM3->CR1 |= TIM_CR1_CEN;            /* start counting */

The first two lines are the arithmetic above. PWM_PSC is 7, and the counter clock becomes 1 MHz. PWM_ARR is 999, and the period becomes 1 kHz. The third line selects the output mode. The OC1M field, shifted into place with << 4, holds 110, which is PWM mode 1. The preload bit OC1PE makes a new compare value take effect at the start of the next period instead of in the middle of one. That prevents a short or long pulse when the duty changes.

The fourth line connects channel 1 to its pin. The fifth sets the compare value to 0, so the heater is off at reset. ARPE buffers the auto-reload value the same way the preload bit buffers the compare value. The update event written to EGR copies the buffered values into the working registers at once, so the first period starts with the values written. Only then does CEN start the counter. The order is the lesson: the values are loaded first, and the counter starts last. Starting it earlier can run a first period with values that are not yet in place.

The driver function that sets the power is short. It clamps the duty to 1000 and writes the compare register: 

void hal_heater_set_permille(uint16_t permille) {
    if (permille > 1000U) {
        permille = 1000U;
    }
    /* CCR above ARR keeps the output high for the whole period, so 1000 is a constant full power. */
    TIM3->CCR1 = permille;
}

The clamp protects the duty cycle from a caller that asks for more than 100 %. The write needs no other special case at the ends.

The heater's timer is the one from lesson 71, so the configurator starts at PSC 7 and ARR 999: 1 kHz. Set CCR1 for the duty you want, then load the fan preset and check the 40-tick period.

The buttons: one press, one event

A mechanical button bounces for a few milliseconds when it closes and when it opens. A raw read in a loop therefore sees several presses for one push. The fix is an integrator debounce (lesson 52). It counts up while the raw level reads pressed and down while it reads released. The output changes only when the count reaches its limit, which is 3 here for pressed, and returns to 0 for released. A bounce that is shorter than the window never reaches the output. The module lives in app/debounce.c, and it has its own host test in test/test_debounce.c.

The buttons go to ground through an internal pull-up, so the pin reads 1 when the button is open and 0 when it is pressed. This is an active-low input, and the board file inverts it, so hal_button_pressed() returns 1 for a press.

Watching the integrator

The button is sampled every 20 ms in the superloop, which is the BUTTON_PERIOD_MS value in main.c. Take the raw samples from the bounce test in test/test_drivers.c: 1, 0, 1, 0, 1, 0. That is a bouncing press. The count goes 1, 0, 1, 0, 1, 0. It never reaches 3, so the output stays released, and no event is raised.

Now a clean press with samples 1, 1, 1, 1, taken at 0, 20, 40 and 60 ms. The count goes 1, 2, 3, and on the third sample, at 40 ms, the output becomes pressed. That is one event. The fourth sample adds nothing, because the count saturates at 3. Holding the button for ten seconds still gives one event, because the event follows the change, not the level.

The event code, line by line

The button driver turns the debounced level into an event. These are the lines of buttons_sample() that do it: 

void buttons_sample(buttons_t *b) {
    uint8_t start_before = b->start.stable;
    uint8_t material_before = b->material.stable;
    uint8_t start_now = debounce_update(&b->start, hal_button_pressed(HAL_BUTTON_START));
    uint8_t material_now = debounce_update(&b->material, hal_button_pressed(HAL_BUTTON_MATERIAL));
    if (start_now && !start_before) {
        b->start_event = true;
    }
    if (material_now && !material_before) {
        b->material_event = true;
    }
}

The first two lines save the debounced level from before this sample, and the next two feed the raw level into the integrator. The order matters, because the old level must be saved before the update. The two if statements raise an event only when the new level is 1 and the old level was 0, which is the edge from released to pressed. A held button keeps the level at 1, so no further event is raised.

The control step reads the flag through buttons_take_start(), which returns it and clears it. Two presses between two control steps collapse into one flag. The material button has its own flag, so pressing one never consumes the other.

The display: the driver from Labs 3 to 5

The SSD1306 driver and its 5 × 7 font come from the Lab 5 code. The font table is the one from that lab, extended with the F, G, H, W, Y and percent glyphs that the status screen needs. The new glyphs use the same format as the others: one byte per column, with bit 0 as the top row. The driver draws into a 1 KB framebuffer in RAM and sends the whole buffer over I2C with display_flush().

Drawing changes only the framebuffer, which is in RAM and is fast. The flush is the slow part. The framebuffer is 128 × 64 ÷ 8 = 1024 bytes, because each pixel is one bit. On I2C each byte takes nine bit times, eight data bits and one acknowledge bit. At 100 kHz, 1024 × 9 ÷ 100 000 = 0.092 s, so the data alone takes about 92 ms. Lesson 116 has to schedule around that figure.

Text is drawn with a 5 × 7 glyph and one blank column, which makes 6 pixels per character. The line is 128 pixels wide, so 128 ÷ 6 = 21.3, and 21 whole characters fit. That is why the text builder fills lines of 21 characters. The array UI_LINE_CHARS is 22, which is 21 characters plus the terminating NUL byte, and the NUL is not drawn.

The text itself is built by ui_compose(), a pure function that takes the dryer state and the temperature and fills four strings. It has no display call in it, so the host test test/test_ui.c can check every line exactly, which matters because the learner reads those strings on the screen. The test checks that the longest line fits in 21 characters.

The superloop calls the draw function every 200 ms. The function below is from main.c: 

static void draw(void) {
    char lines[UI_LINES][UI_LINE_CHARS];
    dryer_out_t out;
    dryer_in_t none = { 0 };
    dryer_step(&dryer, &none, &out);     /* a refresh with no press: the state does not change */
    ui_compose(&dryer, &out, last_temp, last_sensor_ok, lines);
    display_clear();
    for (uint8_t i = 0; i < UI_LINES; i++) {
        display_text((uint8_t)(i * 2u), 0u, lines[i]);
    }
    (void)display_flush();
}

The dryer_step() call passes an empty input, so the state machine recomputes its outputs without changing state. The comment says so, because a draw that calls into the state machine is easy to misread. ui_compose() builds the four lines, and the loop writes them at pages 0, 2, 4 and 6. A page is 8 pixels high, so a text row on every second page leaves a blank page between lines. The flush sends the 1 KB buffer to the panel.

The superloop itself is short. It runs three jobs at their own periods, using the millisecond clock: 

uint32_t now = hal_millis();
if ((int32_t)(now - next_btn) >= 0) {
    next_btn += BUTTON_PERIOD_MS;
    buttons_sample(&buttons);
}

Each job keeps its own next deadline and moves it forward by its period when it runs. The clock wraps after about 49.7 days (the comment in hal.h). The unsigned subtraction is still correct after a wrap, and the signed cast makes it negative while the deadline is in the future. The runaway timer uses the same rule.

The safety checks: pure logic with a test per rule

safety_check() returns the first fault it finds, checking the rules in a fixed order: the sensor, the over-temperature cutoff, the stale sample, and then the heater runaway. The check takes its inputs as a struct, so a test can supply any temperature, age or heater state without a heater or a clock. The state machine in dryer.c latches whatever the check returns into the FAULT state, and the heater is cut in the same control step.

The runaway rule follows the idea of Klipper's verify_heater option. Klipper's configuration reference gives the default heating gain as 2, the check time as 20 seconds for extruders and 60 seconds for the heater bed, and the hysteresis as 5 (klipper3d.org Config_Reference, [verify_heater]). The dryer uses a 2 °C gain, a 60 s window and a 5 °C band, which fits a chamber with more thermal mass than a nozzle. The rule is simple to state: while the heater is at full power and well below the setpoint, the temperature must rise by 2 °C within the window. A rise restarts the window. A heater that does not rise trips the fault.

Here is the code, from the reference app/safety.c. The top-level function calls the checks in order: 

fault_t safety_check(const safety_in_t *in, runaway_t *r) {
    if (!in->sensor_ok) {
        return FAULT_SENSOR;
    }
    if (in->temp_centi >= SAFETY_CUTOFF_CENTI) {
        return FAULT_OVERTEMP;
    }
    if (in->sample_age_ms > SAFETY_STALE_MS) {
        return FAULT_STALE;
    }
    return runaway_check(in, r);
}

The order is deliberate. A bad sensor makes the temperature meaningless, so it goes first, and the runaway rule goes last because it needs the others to be clean. Each if returns at once, so the first fault wins. The cutoff uses >=, so a reading of exactly 90.00 °C is a fault, as requirement 2.1 says.

The runaway check has state, so it takes the window record r as well as the inputs: 

static fault_t runaway_check(const safety_in_t *in, runaway_t *r) {
    bool far_below = in->temp_centi < in->setpoint_centi - SAFETY_RUNAWAY_BAND_CENTI;
    if (!in->heater_enabled || !in->heater_full || !far_below) {
        runaway_reset(r);
        return FAULT_NONE;
    }
    if (!r->armed) {
        r->armed = true;
        r->ref_ms = in->now_ms;
        r->ref_centi = in->temp_centi;
        return FAULT_NONE;
    }
    if (in->temp_centi >= r->ref_centi + SAFETY_RUNAWAY_GAIN_CENTI) {
        r->ref_ms = in->now_ms;
        r->ref_centi = in->temp_centi;
        return FAULT_NONE;
    }
    if (in->now_ms - r->ref_ms >= SAFETY_RUNAWAY_MS) {
        return FAULT_RUNAWAY;
    }
    return FAULT_NONE;
}

The first if asks whether the rule applies at all. It applies only while the state machine wants heat, the heater is at full power and the chamber is more than 5 °C below the setpoint. Any other case resets the window and returns no fault, because a heater that is not at full power is not being tested. The first sample that does apply arms the window and records the time and the temperature. Each later sample is compared with that reference: a rise of 2 °C restarts the window from the current time and temperature. If neither happened and the window has run for 60 s, the function returns FAULT_RUNAWAY. The subtraction now_ms − ref_ms is unsigned, so it stays correct across the 32-bit wrap of the clock.

Two rules, worked through

Stale sample. The control step produces a sample every 100 ms, and the check receives the age of the newest sample. With a limit of 500 ms, an age of 480 ms is fine and an age of 510 ms is a fault. The check is a plain comparison, so a test can supply any age.

Heater runaway. Suppose the setpoint is 65.00 °C, the chamber reads 25.00 °C, and the heater is at full power. The check opens a window at time 0 with a reference of 25.00 °C. At 30 s the chamber reads 26.00 °C, which is short of the 2.00 °C rise, so the window stays open. At 35 s the chamber reads 27.10 °C, which is 2.10 °C above the reference. The window restarts at 35 s with a reference of 27.10 °C. If the chamber then stays at 27.20 °C, the new window expires 60 s later, at 95 s, and the check returns FAULT_RUNAWAY. A slow but healthy heater that gains 2 °C every minute never trips, and a dead heater trips 60 s after its window opened.

Whether that gap matters is a requirements question, and the Capstone 1 table would need a new row with its own test before the code changes.

Common mistakes and how to spot them

1. A held button counts as several presses. Symptom: in the simulator, one press of the material button advances the preset two or three times. Fix: raise the event only on the change from released to pressed, and keep the integrator's saturation. The test test_a_held_press_is_one_event in test_drivers.c catches this on the PC.

2. The state machine reads the raw level. Symptom: while the material button is held, the preset advances on every control step, about ten times a second, and the display changes faster than a person presses. Cause: the control step called hal_button_pressed() directly instead of taking the event. Fix: read the button only through the event functions, so each press reaches the state machine once.

3. The runaway window never restarts. Symptom: a healthy heater trips RUNAWAY about a minute after it starts, even though the chamber is rising. Fix: check the restart branch, which must reset the reference to the current time and temperature. Then write a test that feeds a steady 2 °C rise every minute and expects no fault, as the restart test does.

4. The cutoff uses the wrong comparison. Symptom: test_cutoff_at_90_degrees fails with Expected 1 Was 0. The code was written with >, so a reading of exactly 90.00 °C passed. Fix: use >= for a limit that means "reached", and keep the boundary test next to it, so a future edit that moves the limit fails at once.

5. The display text counts the NUL. Symptom: a line built with 22 visible characters fails test_longest_line_fits_the_display, and on the OLED the last character is cut off or wraps. Cause: the length of the buffer, 22, was used as the length of the text. Fix: build text up to 21 characters, and keep the 22-byte buffer only for the terminating NUL.

In real projects

Production firmware debounces buttons in hardware, with a resistor-capacitor filter and a Schmitt-trigger input, or in software, as here. A software integrator costs no parts but adds latency, and its sample period must be longer than the bounce. A reviewer will ask how long the bounce is and where the limit came from.

A PWM frequency should have a stated reason. The heater's 1 kHz is well above what the chamber can follow, and a fan at 25 kHz is chosen to be above the range most people can hear. Safety rules are tested as pure functions with one test per rule and boundary, which gives the trace that a standard such as IEC 61508 asks for (lesson 111). Lesson 116 adds a supervisor that makes sure the check runs.

Summary

  • A bang-bang controller with hysteresis switches the heater fully on or off inside a dead band, and it overshoots. PWM sets the average power by a duty cycle.
  • In PWM mode 1, the output is high while the counter is below the compare value. The period is (PSC + 1) ÷ clock × (ARR + 1), and a compare value from 0 to 1000 is a duty in permille.
  • Load the PWM values first, then start the counter. The preload and update event make the first period use the values written.
  • A button integrator changes its output only when the count reaches its limit. An event is the edge from released to pressed, so a held button gives one event.
  • The display text is built by a pure function and tested line by line. The flush of 1 KB over I2C takes about 92 ms at 100 kHz, which the schedule must allow for.
  • Safety checks run in a fixed order and return the first fault. The runaway window restarts on each real rise, and the rule applies only at full power and far below the setpoint.
  • Each safety rule and each boundary has its own host test. Gaps in the rules, such as a cold reading with the heater off, belong in the requirements.

Try it: write the safety checks

The starter in projects/0115-dryer-drivers/starter is the whole dryer, and it has one stub left: safety_check() returns FAULT_NONE for every input. The PWM, the buttons and the display are already written, and the safety tests in projects/0114-dryer-host-tests check your version. Your task is to make all eight host test programs pass and the firmware build.

  1. Open projects/0115-dryer-drivers/starter/app/safety.c. Read the TODO(learner) comment. It lists the four checks in order: sensor, over-temperature, stale sample, and runaway.
  2. Implement the first three checks as plain comparisons. Use SAFETY_CUTOFF_CENTI with >= for the cutoff, and SAFETY_STALE_MS with > for the stale rule.
  3. Implement the runaway check as the comment describes. Call runaway_reset() whenever the rule does not apply, open the window on the first applicable sample, and restart it after a 2 °C rise. Return FAULT_RUNAWAY when 60 s pass without a rise.
  4. Run the host tests from the workspace root: python -I tools/build.py projects/0114-dryer-host-tests/starter --test. Expect 100% tests passed out of 8. If CMake reports a CMakeCache.txt from a different folder, add --clean. The copied folders carry stale build directories, and --clean deletes them first.
  5. Build the firmware: python -I tools/build.py projects/0115-dryer-drivers/starter --clean. The build should finish with no errors. Open hw/hal_bluepill.c and find the PWM register lines from this lesson. Compare them with the solution in projects/0115-dryer-drivers/solution.
  6. Optional: open test/test_safety.c and read test_no_runaway_near_the_setpoint. Explain in one sentence why the check must be off near the setpoint, and then compare your answer with the table above.
Hint for the order

Return the first fault you find, and do the cheap checks first. A sensor check that comes after the runaway check would let a bad sensor reach the window logic. The runaway check is the only one with state, so the other three must not touch the window.

Hint for the runaway window

The window needs three things: whether it is open, the time it opened, and the temperature at that moment. A rise is measured against the stored temperature, not the previous sample. A test that sets the time 60 s after the window opened tells you whether the expiry is right.
