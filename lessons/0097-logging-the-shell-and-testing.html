Logging, the shell, and testing with ztest and Twister

Three tools make firmware easier to live with: a logger that tells you what happened, a shell that lets you poke the device by hand, and unit tests that run without the hardware. Zephyr ships all three, and this lesson uses each one.

By the end of this lesson you can register a shell command that drives the LED, write a ztest case for a conversion function, and explain what Twister needs to run it, including why it cannot run on Windows.

Where we are and why it matters

Lesson 53 printed text from the Pico over its UART, one call at a time. Lesson 85 explained why a deployed device needs logs it can send back, and lesson 80 introduced unit tests that run on a PC. Lesson 93 taught Kconfig, the switches that turn each of these features on or off, and lesson 94 showed how the board describes its UART. This lesson puts those pieces to work in Zephyr.

The problem is practical. When a board sits on your desk, a shell lets you type led on and see the result, which saves a rebuild for each test. When a board is in a cabinet at a customer's site, the same log lines and the same command set tell you what it did. When no board is available at all, which is the normal state of a CI server, a unit test can check the logic that the firmware depends on. Each tool solves a different part of the same problem, and each one is in daily use at firms that ship embedded products.

The concepts, one at a time

A log message has a level and a module

A log message is a line of text that the firmware emits on purpose. Each message has a level, which says how serious it is. Zephyr defines four: LOG_LEVEL_ERR is 1, LOG_LEVEL_WRN is 2, LOG_LEVEL_INF is 3 and LOG_LEVEL_DBG is 4 (include/zephyr/logging/log_core.h:40-46). A lower number is more serious, and a higher number is more detail.

Each source file that logs is a module. LOG_MODULE_REGISTER(app, LOG_LEVEL_INF) names this file's module app and gives it a level. A message prints when its level is at most the module's level (include/zephyr/logging/log_core.h:201). So a module at level INF prints errors, warnings and info, and it drops debug messages. The macros LOG_ERR, LOG_WRN, LOG_INF and LOG_DBG each carry one level (include/zephyr/logging/log.h).

The global switch is CONFIG_LOG. With it off, every log macro compiles to nothing, so the calls cost no flash and no time. The default level for modules that do not name one is CONFIG_LOG_DEFAULT_LEVEL, which the solution sets to 3. A level in code is a decision about one file, and a level in Kconfig is a decision about the whole build.

Log backends decide where the text goes

A backend is the output that a log message reaches. Zephyr has a UART backend, which writes straight to a serial port, and a shell backend, which sends messages through the shell's output. Both cannot write to the same port without mixing their text. The UART backend has the symbol LOG_BACKEND_UART, and its default is set in subsys/logging/backends/Kconfig.uart: it is on by default only when the serial shell is not, as the line default y if !SHELL_BACKEND_SERIAL says.

The lesson's project turns on the shell, so the logs must go through the shell's backend. That is the reason for CONFIG_SHELL_LOG_BACKEND=y in prj.conf. It is defined in subsys/shell/Kconfig at line 288. A learner who turns on the logger but forgets this line sees nothing, because the UART backend is off and the shell backend is not selected.

The shell is a command line inside the firmware

A shell reads text from a serial port, splits it into a command and its arguments, and calls a function you wrote for that command. The shell runs in its own thread, which the kernel starts for you, so main() can return. Its prompt is uart:~$ (the default in subsys/shell/backends/Kconfig.backends). The serial backend uses the UART that the board names with zephyr,shell-uart, which is &uart0 on the Pico (boards/raspberrypi/rpi_pico/rpi_pico-common.dtsi:21).

A command is a function of the form int handler(const struct shell *sh, size_t argc, char **argv), the type that shell_cmd_handler declares (include/zephyr/shell/shell.h:267). argv[0] is the command name and argc counts it too. You register it with SHELL_CMD_REGISTER (shell.h:465) for a plain command, or with SHELL_CMD_ARG_REGISTER when you want the shell to check the argument count. A command with subcommands, such as led on, is built with SHELL_STATIC_SUBCMD_SET_CREATE (shell.h:502).

Unit tests run where there is no board

A unit test checks one function with chosen inputs and compares the result with an expected value. The firmware is useful to test only if the logic is separate from the hardware. The MYS-1 conversion is a good example: it takes a number and returns a number, and it touches no register. Lesson 80 made the same argument for the host, and ztest is Zephyr's framework for the same job.

ZTEST_SUITE groups tests under one name, and ZTEST defines one test case (subsys/testsuite/ztest/include/zephyr/ztest_test.h:289 and :789). zassert_equal(a, b, message) compares two values, and it is one of the assertion macros in ztest_assert.h (:346). The ztest documentation says that these macros "will instantly fail the test if the related assertion fails", which means the test case stops at that line, the failure is reported with its file and line, and the next test runs.

Twister runs the tests

Twister is Zephyr's test runner. It reads a description file in each test folder, builds the test for each platform the description names, and runs each one with the harness it names. The description file is testcase.yaml in this project. Zephyr's 4.5 documentation names tests.yaml as the file and calls testcase.yaml deprecated, but Twister still scans for both names (scripts/pylib/twister/twisterlib/testplan.py:167). The project uses the older name, and it still works.

The platform that runs on a PC is native_sim. It compiles the code into a Linux process, so the test runs at PC speed. The ztest documentation says that unit tests run as native applications and are "therefore only supported for Linux", and arch/posix/CMakeLists.txt stops the configure step on other hosts with the message The POSIX architecture only works on Linux (lines 4 and 5). -p (--platform) on the Twister command line selects the platform (doc/develop/twister/index.rst).

Worked example: 1440 counts becomes 22.50 degrees

The MYS-1 reports temperature in units of 1/64 degree, as a signed 16-bit number (datasheet section 4.1, projects/0063-mystery-sensor/MYSTERY-SENSOR-DATASHEET.html). The conversion has to produce hundredths of a degree, so that the shell can print two decimal places without floating point. Take the raw value 1440 and follow the arithmetic.

  1. Raw count. The sensor says 1440. The integer is raw = 1440.
  2. Scale to hundredths. Multiply by 100 first: 1440 × 100 = 144000.
  3. Divide by 64. 144000 / 64 = 2250 exactly, so the result is 2250 hundredths, which is 22.50 degrees. Check it another way: 1440 / 64 = 22.5.
  4. Print. The shell takes the magnitude, 2250, and prints 2250 / 100 = 22 and 2250 % 100 = 50, giving 22.50 C.

Now do it the wrong way. Divide first: 1440 / 64 = 22 in integer arithmetic, because the fraction .5 is dropped. Then 22 × 100 = 2200, and the monitor prints 22.00 C. The error is half a degree, and it comes from the order of two operations, not from the sensor. This is why the solution's comment says to multiply first.

The negative case shows the signed type at work. The count -64 is -1.00 C. If the raw value is read as an unsigned 16-bit number, the same bits are 65472, which is 0xFFC0, and 65472 × 100 / 64 gives 102300, which prints as 1023.00 C. The datasheet gives the same warning in section 4.1.

The code, line by line

The solution is in projects/0097-logging-shell-ztest/solution. The conversion lives in src/temp_format.c, and the application in src/main.c only parses and prints.

LOG_MODULE_REGISTER(app, LOG_LEVEL_INF);
static const struct gpio_dt_spec led = GPIO_DT_SPEC_GET(DT_ALIAS(led0), gpios);

LOG_MODULE_REGISTER makes this file's module app at level INF, so the file's LOG_INF prints and its LOG_DBG does not. The LED is found through the led0 alias, as in lesson 94, so the code names no pin. 

static int cmd_led_on(const struct shell *sh, size_t argc, char **argv)
{
    ARG_UNUSED(argc);
    ARG_UNUSED(argv);
    gpio_pin_set_dt(&led, 1);
    shell_print(sh, "LED on");
    return 0;
}

This is a shell handler with the signature from above. ARG_UNUSED marks the two arguments that this command does not read, so the compiler does not warn. gpio_pin_set_dt(&led, 1) sets the logical level 1, and the overlay's active-high flag turns that into a driven high pin. shell_print writes to the same session that sent the command, which is why the reply appears in the monitor and not on a different port. 

SHELL_STATIC_SUBCMD_SET_CREATE(sub_led,
    SHELL_CMD(on, NULL, "Turn the LED on", cmd_led_on),
    SHELL_CMD(off, NULL, "Turn the LED off", cmd_led_off),
    SHELL_CMD(toggle, NULL, "Toggle the LED", cmd_led_toggle),
    SHELL_SUBCMD_SET_END
);
SHELL_CMD_REGISTER(led, &sub_led, "Control the LED", NULL);

The subcommand set is a list of three children, on, off and toggle. The NULL in each entry means that a child has no children of its own. SHELL_CMD_REGISTER adds the parent, led, to the root of the shell, and the last argument is NULL because the parent has no handler, only the subcommands. Typing led on selects the first child, and typing led alone prints the list. 

static int cmd_temp(const struct shell *sh, size_t argc, char **argv)
{
    if (argc != 2) {
        shell_error(sh, "usage: temp <raw count>");
        return -EINVAL;
    }
    long raw = strtol(argv[1], NULL, 0);
    if (raw < INT16_MIN || raw > INT16_MAX) {
        shell_error(sh, "raw count must fit in 16 bits");
        return -ERANGE;
    }

The first check counts the command name, so argc == 2 means one argument. strtol(argv[1], NULL, 0) converts the text to a number, and base 0 accepts both decimal (1440) and hexadecimal (0x5a0). The range check comes before the cast, because a value outside the 16-bit range would be cut to the wrong number. The shell error function prints a message and returns a negative code, which the shell reports back. 

    int32_t centi = mys_raw_to_centi_c((int16_t)raw);
    int32_t mag = centi < 0 ? -centi : centi;
    LOG_DBG("raw %ld -> %d centi-C", raw, (int)centi);
    shell_print(sh, "%s%ld.%02ld C", centi < 0 ? "-" : "",
                (long)(mag / 100), (long)(mag % 100));
    return 0;
}
SHELL_CMD_ARG_REGISTER(temp, NULL, "Convert a MYS-1 raw count to degrees C", cmd_temp, 2, 0);

The conversion runs on the value cast to int16_t, so the sign is kept. The magnitude is printed with %02ld, so a value of 50 prints as 50 and a value of 5 would print as 05. That is why the sign is handled separately: printing a negative number's integer and fraction parts directly would give the wrong fraction. The LOG_DBG line is silent at level INF, and it costs nothing in the release build if you turn logging off. SHELL_CMD_ARG_REGISTER takes the minimum argument count, 2, which includes the command name, and the maximum optional count, 0. 

int32_t mys_raw_to_centi_c(int16_t raw)
{
    return ((int32_t)raw * CENTI_PER_DEGREE) / COUNTS_PER_DEGREE;
}

This is src/temp_format.c, and it is the function that the test calls. The cast to int32_t happens before the multiply, so the product of the 16-bit input and 100 fits in 32 bits. The multiply comes before the divide, as in the worked example. The function contains no hardware call, which is what makes it testable on a PC. 

ZTEST_SUITE(temp_format, NULL, NULL, NULL, NULL, NULL);

ZTEST(temp_format, test_room_temperature)
{
    zassert_equal(mys_raw_to_centi_c(1440), 2250, "1440 counts should be 22.50 C");
}

ZTEST_SUITE declares the suite and gives it no setup or teardown, because the conversion keeps no state. ZTEST defines the test case, and the test body calls zassert_equal. The third argument is the message printed on failure. The solution also has a negative case, -64 → -100, and a range case that checks 32767 → 51198 (the exact value 51198.4375 rounded toward zero) and -32768 → -51200. Each of these was chosen to test an edge of the arithmetic.

Common mistakes and how to spot them

Shell enabled, but the shell symbols missing

shell_print is a macro that expands to a call to shell_fprintf_impl (include/zephyr/shell/shell.h:1287 and :1393). That function exists only when CONFIG_SHELL is on. If the code calls shell_print and the symbol is off, the link fails with undefined reference to shell_fprintf_impl. The message looks like a code bug, but the cause is a missing Kconfig line, and the fix is CONFIG_SHELL=y in prj.conf. The starter's comment describes this failure, and the solution's prj.conf has the line.

Logs missing from the monitor

The symptom is a LOG_INF line that never appears, while the shell works. The serial shell turns the UART log backend off by default, so the log messages go nowhere unless the shell log backend is selected. The fix is CONFIG_SHELL_LOG_BACKEND=y. A quick check is to type help: if the shell replies, the port works, and only the backend selection is wrong.

Dividing before multiplying

If the conversion is written as raw / 64 * 100, the monitor prints 22.00 C for temp 1440, not 22.50 C. The test test_room_temperature fails and prints its own message, which names the expected value, so the failing line is the fastest way to see the mistake. The fix is the expression in the solution: multiply first, divide last.

Reading the count as unsigned

If the parameter is declared uint16_t, the value -64 arrives as 65472, and the output is 1023.00 C. The negative-temperature test fails, and it says what it expected. Keep the raw type signed, as the datasheet says, and check the negative case every time the conversion changes.

Running native_sim on Windows

A learner who runs the test on the Windows PC sees the configure step stop with The POSIX architecture only works on Linux. The message is correct: native_sim is a Linux process. Run the test on Linux, or in WSL, which is a Linux environment inside Windows. The Pico build still works on Windows, which is why the test folder also lists rpi_pico.

In real projects

Production teams keep the logger at a level that matches the release. Debug messages are cut at build time, and the error and warning messages stay on, so a field report contains the lines that matter. The shell is often kept in a development image, or behind a build flag, because an open command line is a security risk in the field. Lesson 103 covers security in general.

Unit tests in CI are the usual form of this lesson's test. A server builds each test for a Linux host, runs it, and reports the result. Lesson 82 describes that pipeline. The test folder is small, and its value grows with each bug it catches. Reviewers ask for a test with each change to conversion or parsing logic, and they look first at the edge cases.

Summary

  • A log message has a level: ERR is 1, WRN is 2, INF is 3 and DBG is 4. A module at level INF prints the first three.
  • With CONFIG_LOG off, the log macros compile to nothing. The UART log backend is off by default when the serial shell is on, so select CONFIG_SHELL_LOG_BACKEND.
  • A shell command is a handler with (sh, argc, argv). argc counts the command name, and SHELL_CMD_ARG_REGISTER checks the count.
  • Do the arithmetic in the order that keeps the fraction: multiply by 100, then divide by 64.
  • ZTEST defines a test case, and a failed zassert stops that test at once.
  • Twister runs tests from a description file, and native_sim needs a Linux host.
  • Keep the hardware-free logic separate, so the same function runs in the shell, on the board and in a host test.

Try it in Wokwi

The starter has the shell on and several TODO(learner) notes. You turn on the logger, write the LED commands and the temperature command, and fill in the formula and one test.

  1. Open projects/0097-logging-shell-ztest/starter in VS Code. In prj.conf, uncomment or add CONFIG_LOG=y, CONFIG_LOG_DEFAULT_LEVEL=3 and CONFIG_SHELL_LOG_BACKEND=y, from the TODO(learner) note.
  2. In src/main.c, replace the two placeholder bodies in cmd_led_on and cmd_led_off with gpio_pin_set_dt and the correct messages, LED on and LED off.
  3. Add the toggle entry to the subcommand set, calling gpio_pin_toggle_dt.
  4. In cmd_temp, check argc, parse argv[1] with strtol(argv[1], NULL, 0), convert it with mys_raw_to_centi_c, and print the degrees with the sign and the two decimals.
  5. In main(), replace the TODO(learner) note with LOG_INF("shell ready"), so the log line appears before the prompt.
  6. In src/temp_format.c, return raw * 100 / 64, multiplying first. In tests/temp_format/src/test_temp_format.c, add the negative test from the TODO(learner) note.
  7. Build with Ctrl+Shift+B, start the simulator, and type help, then led on and temp 1440. You'll know it works when led appears in the help list, the LED turns on after led on, and the monitor prints 22.50 C. The solution also prints shell ready at start, and that line is your check for step 5.
Hint

The shell only sees commands it was given. If help does not list led, check that the SHELL_CMD_REGISTER line is still in the file. For the formula, multiply first and divide last: raw * 100 / 64. For the negative test, the expected value for -64 is -100.

Model answer

Separate the logic from the hardware, so the logic is plain C that takes numbers and returns numbers. Write unit tests for it with a framework such as ztest, and run them on a host or a simulator in CI, using Twister or another runner. Keep the hardware-dependent code thin and test it on the bench or in the simulator.
