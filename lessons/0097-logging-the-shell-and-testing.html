Logging, the shell, and testing with ztest and Twister

Three tools make firmware easier to live with: a logger that tells you what happened, a shell that lets you poke the device by hand, and unit tests that run without the hardware. Zephyr ships all three, and this lesson uses each one.

By the end of this lesson you can register a shell command that drives the LED, write a ztest case for a conversion function, and explain what Twister needs to run it, including why it cannot run on Windows.

The idea

The logger is a module with a name and a level. LOG_MODULE_REGISTER(app, LOG_LEVEL_INF) names this file's module and sets its level, and LOG_INF, LOG_DBG and the others print when the level allows (include/zephyr/logging/log.h:845). The global switch is CONFIG_LOG. With it off, every log call compiles to nothing. The shell is the other half of debugging. It runs in its own thread, reads commands from the UART, and calls your functions, which is how many teams test a board on the bench.

The shell is on with CONFIG_SHELL=y, and its serial backend uses the UART named by the board's zephyr,shell-uart node (uart0 on the Pico). A command is one SHELL_CMD_REGISTER line, and a subcommand tree is a SHELL_STATIC_SUBCMD_SET_CREATE block (include/zephyr/shell/shell.h:465, 502).

With the shell on, the UART log backend is off by default (subsys/logging/backends/Kconfig.uart: default y if !SHELL_BACKEND_SERIAL). The logs go through the shell's log backend instead, so set CONFIG_SHELL_LOG_BACKEND=y. Our starter forgot the shell, and the linker reported undefined reference to shell_fprintf_impl. That is a missing Kconfig symbol, not a code bug.

The conversion function, and its tests

The MYS-1 reports 1/64 °C per count, as a signed 16-bit number (datasheet section 4.1). The conversion function mys_raw_to_centi_c has no hardware in it: it takes a number and returns hundredths of a degree. That makes it testable on any machine. In the solution it is (int32_t)raw * 100 / 64. The code multiplies first, so the division keeps the fraction, and the product fits in 32 bits. 

ZTEST_SUITE(temp_format, NULL, NULL, NULL, NULL, NULL);

ZTEST(temp_format, test_room_temperature)
{
    zassert_equal(mys_raw_to_centi_c(1440), 2250, "1440 counts should be 22.50 C");
}

ZTEST_SUITE groups the tests, and ZTEST defines one test case (subsys/testsuite/ztest/include/zephyr/ztest_test.h:289, 789). zassert_equal reports the message and goes on to the next test (ztest_assert.h:346). The tests live in tests/temp_format/ with their own prj.conf, CMakeLists.txt and testcase.yaml. The test build compiles the same temp_format.c that the application uses, so the test checks the shipped code.

Twister, and what it needs

Twister is Zephyr's test runner. It reads testcase.yaml, builds each test for the platforms it names, and runs them where it can (Zephyr testing). The simulated board that CI uses is native_sim, which compiles the code into a Linux process. That needs Linux, and the docs say so: unit tests run as native applications, so they are "only supported for Linux" (ztest docs). The CMake guard says the same: arch/posix/CMakeLists.txt stops configuration unless the host is Linux.

What we checked on this Windows machine: the ztest suite builds for the Pico (python -I tools/build.py projects/0097-logging-shell-ztest/solution/tests/temp_format), and a native_sim configure stops with the POSIX message even with a MinGW gcc on the PATH. Twister could not run here: its Python modules need natsort, which is not installed, and this course does not install packages. On Linux or WSL you would install the Zephyr requirements and run west twister -T projects/0097-logging-shell-ztest/solution/tests/temp_format -p native_sim. We did not run that.

Try it in Wokwi

The starter has the shell on, with three TODO(learner) handlers. You write the LED commands and the temperature command, and you turn on the logger.

  1. Open projects/0097-logging-shell-ztest/starter in VS Code. In prj.conf, turn on CONFIG_LOG and CONFIG_SHELL_LOG_BACKEND from the TODO(learner) note.
  2. In src/main.c, write cmd_led_on and cmd_led_off with gpio_pin_set_dt. Then write cmd_temp: parse the argument with strtol, convert it with mys_raw_to_centi_c, and print the degrees.
  3. In src/temp_format.c, fill in the formula, then build the test folder and check it compiles.
  4. Build, start the simulator, and type led on and temp 1440 in the serial monitor. You'll know it works when the LED turns on and the monitor prints 22.50 C.
Hint

The shell only sees commands it was given. If help does not list led, check that the SHELL_CMD_REGISTER line is still in the file. For the formula, multiply first and divide last: raw * 100 / 64.

The reference solution is in projects/0097-logging-shell-ztest/solution. Try first, compare after.

Typing into the simulator's serial monitor depends on how Wokwi routes input to the Pico's UART, which we did not verify here (no simulator token). If your shell does not respond, check the serial monitor's input box and the RX/TX wiring in diagram.json first.

"How would you test firmware logic when you have no board on your desk?" Answer out loud in 60 seconds, then compare.

Model answer

Separate the logic from the hardware, so the logic is plain C that takes numbers and returns numbers. Write unit tests for it with a framework such as ztest, and run them on a host or a simulator in CI, using Twister or another runner. Keep the hardware-dependent code thin and test it on the bench or in the simulator.

Zephyr documentation: ztest: read "Writing a test suite" and the note on the Linux-only native host. Then open samples/subsys/testsuite/integration in the Zephyr tree for a complete example.
