Privilege modes

A Cortex-M runs code in one of two modes, and it can have two stacks. Those choices are why an RTOS can give each task its own stack without giving tasks the power to break the kernel.

By the end of this lesson you can say which mode a handler runs in, which stack pointer exceptions use, what privileged and unprivileged code can and cannot do, and why an RTOS switches tasks to the process stack.

The idea

The core has two modes. Thread mode runs your main program and the RTOS tasks. Handler mode runs exception handlers, including interrupt service routines. Arm's TRM says thread mode "is entered on reset, and can be entered as a result of an exception return", and handler mode "is entered as a result of an exception" (Arm Cortex-M3 TRM DDI0337G, §2.1.1).

Separately from the mode, code is either privileged or unprivileged. The TRM says that "unprivileged execution limits or excludes access to some resources", and that "privileged execution has access to all resources". Handler mode is always privileged. Thread mode can be either, and is privileged out of reset (§2.2). So an interrupt handler can always touch the system registers, while a task can be restricted if the software arranges it. Which CONTROL bit makes thread mode unprivileged is in the TRM's register description. We did not check that for this lesson, so read it before you rely on it.

Two stack pointers

The core has two stack pointers, SP_main and SP_process, and SP (R13) is the one currently selected. The TRM states that out of reset all code uses the main stack, and that all exceptions continue to use the main stack (§2.2.1). Thread mode can use either stack, chosen by bit 1 of the CONTROL register, which the TRM says you can change with an MSR instruction in thread mode. An exception return can also change the choice, through the EXC_RETURN value that the handler exits with (§2.2.1).

That is the reason an RTOS works the way it does. Each task has its own stack, and the task runs in thread mode with the process stack selected. When an interrupt arrives, the core stacks the frame on the main stack, so the kernel's handler work never lands on a task's stack. Lesson 88 shows this in full, when the RTOS switches the process stack pointer between tasks.

The simulator models both stack pointers, the CONTROL register (SPSEL in bit 1, nPRIV in bit 0), MRS/MSR and SVC. Two simplifications: nested exceptions are not modelled, and the first exercise below uses the main stack only. The second exercise switches to the process stack.

Try it in the CPU simulator

The program counts up in thread mode. Its handler is a single instruction and a return. Watch the mode label in the register panel, which reads "Thread mode" or "Handler mode", and the stack pointer.

  1. Press Run, then Pause. The register panel shows "Thread mode". Note the SP.
  2. Press IRQ ⚡, then Step until the interrupt is taken. Predict the SP value: an eight-word frame is 32 bytes. Check the mode label.
  3. Press Instruction until the handler returns. Check that the mode is back to "Thread mode" and the SP is back to its starting value.
Hint

The starting SP is 0x20000100. An eight-word frame is 32 bytes. After the return, the stacked frame is removed and the SP returns to 0x20000100. R1 reads 0 again afterwards, not 1: the handler's write is undone when the frame restores R1, the same effect as in lesson 34.

Try it: two stacks and unprivileged code

This program gives thread mode its own process stack, drops privilege, and then makes a supervisor call, which is how unprivileged code asks the kernel for something. Turn on the System registers panel (it is shown below) and watch MSP, PSP, CONTROL and IPSR.

  1. Press Instruction four times. Before each press, predict which register changes. After the fourth, CONTROL is 2 and Active SP reads PSP: thread mode now runs on the process stack at 0x20000080.
  2. Two more presses set CONTROL to 3 (unprivileged). Then the MSR CONTROL, R0 that tries to set it back to 0 is ignored: read the message. Unprivileged code cannot promote itself.
  3. Step over SVC #0. Predict first: on which stack is the frame pushed, and what will LR hold? Then check: the frame lands on the PSP (PSP drops by 32), the handler runs on the MSP, IPSR is 11 (SVCall) and LR is 0xFFFFFFFD, meaning "return to thread mode, process stack".
  4. The handler, which is privileged, clears nPRIV, then returns. The thread is privileged again and still on the PSP.

This is the skeleton of an RTOS: tasks on PSP, kernel on MSP, and SVC as the gate between them. Lesson 88 adds the missing piece, swapping the PSP between tasks.

You watched the core switch from thread mode to handler mode and back, predicted an exception frame, and moved thread mode onto its own stack with reduced privilege, the exact arrangement an RTOS uses.

"Why does an RTOS use the process stack for tasks and the main stack for interrupts?" Answer out loud in 60 seconds, then compare.

Model answer

Each task needs its own stack, so a task's frame cannot be overwritten by another task or by the kernel. On the Cortex-M, thread mode can select the process stack, while exceptions always stack on the main stack. The kernel's handler work and the interrupt frames therefore sit on the main stack, and a context switch changes only the process stack pointer. Lesson 88 covers the switch itself.

Arm Cortex-M3 TRM DDI0337G: §2.1.1 (thread and handler modes), §2.2 (privileged and unprivileged access) and §2.2.1 (the main and process stacks and CONTROL[1]). Read §2.2.1 twice: it is the basis of the RTOS design you will meet in Part 7.
