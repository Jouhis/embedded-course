Privilege modes

A Cortex-M runs code in one of two modes, and it can have two stacks. Those choices are why an RTOS can give each task its own stack without giving tasks the power to break the kernel.

By the end of this lesson you can say which mode a handler runs in, which stack pointer exceptions use, what privileged and unprivileged code can and cannot do, and why an RTOS switches tasks to the process stack.

Where we are and why it matters

This lesson builds on three earlier ones. Lesson 31 introduced the registers, including the stack pointer SP and the status register xPSR. Lesson 33 explained the stack and the calling convention. Lesson 34 showed that an interrupt pushes an eight-word frame and returns through EXC_RETURN. Each of those topics touches the stack, and this lesson shows that the core has more than one stack.

The reason is a product problem. Consider the firmware of a 3D printer. It runs a motion task, a temperature task, a display task and a communication task, and each one needs its own stack. Now suppose the display task has a bug that writes to a timer register, or that overruns its stack into the motion task's data. The printer then misbehaves in a way that is hard to trace, because the fault is far from its cause. A multitasking system needs two things from the hardware. Each task needs a stack of its own. And some code, the kernel, must be able to stop a task from touching the system registers. The Cortex-M gives you both, through its modes, its privilege level and its two stack pointers.

The concepts, one at a time

Thread mode and handler mode

The core has two modes, thread mode and handler mode. Thread mode runs your main program and the RTOS tasks. Handler mode runs exception handlers, including interrupt service routines. Arm's TRM says that thread mode "is entered on reset, and can be entered as a result of an exception return", and that handler mode "is entered as a result of an exception" (Arm Cortex-M3 TRM DDI0337G, §2.1.1). So the mode is not chosen by your code. It changes when the core takes an exception and when it returns from one.

Privileged and unprivileged code

Mode and privilege are different things. Mode says which kind of code is running. Privilege says what that code is allowed to touch. The TRM says that "unprivileged execution limits or excludes access to some resources", and that "privileged execution has access to all resources" (§2.2). The TRM also says that privilege "is decoupled from all other concepts in ARMv7-M" (§5.4.2), so the two ideas are separate.

The rules are short. Handler mode is always privileged. Thread mode can be either, and it starts privileged after reset (§2.2). The TRM lists what unprivileged code cannot do: use some instructions such as CPS, which changes the interrupt mask, and access most of the system control space (SCS) registers (§2.2). The SCS holds the system registers of the core itself, not the peripheral registers of the chip. Access to the chip's peripherals depends on the design of the system, and a memory protection unit can restrict it further, which lesson 39 covers.

Only a handler can give thread mode back its privilege. The TRM says that once thread mode has been changed from privileged to user, "it cannot change itself back to privileged. Only a Handler can change the privilege of Thread mode" (§2.2). That rule is what lets a kernel run tasks safely, and it is the reason the SVC instruction exists, as you will see below.

Two stack pointers

The core has two stack pointers, which the TRM calls SP_main and SP_process. SP is register R13, and it is banked: only one of the two is visible at a time. The TRM says that "out of reset, all code uses the main stack", and that "all exceptions continue to use the main stack" (§2.2.1). Thread mode can switch to the process stack, and it does so through bit 1 of the CONTROL register, CONTROL[1], which the TRM names and this course calls SPSEL. Writing that bit with MSR selects the process stack in thread mode (§2.2.1). An exception return can also select it, through the EXC_RETURN value (Table 5-6 in lesson 34).

The CONTROL register has two bits that matter here. Bit 0 is the privilege bit: setting CONTROL[0] makes thread mode unprivileged (§2.2). Bit 1 is the stack select. The two bits are independent, so a task can run unprivileged on the process stack, which is the setting an RTOS uses for a protected task.

Where does an interrupt's frame go? The TRM answers this directly. "An exception that pre-empts a user thread saves the context of the user thread on the stack that the Thread mode is using" (§5.4). So the eight-word frame from lesson 34 goes on the task's process stack, not on the main stack. After that first push, the handler runs on the main stack, and "all subsequent interrupt pre-emptions use the main stack" (§5.4). The main stack is used for the handler's own work, and the process stack holds the task's frame.

That layout is the reason an RTOS works the way it does. The TRM spells out the reason in one paragraph. A task switch needs the kernel to save the state of the task it is leaving, and the frame that the hardware already pushed onto the task's stack is part of that state. The TRM says that "to reschedule, the kernel only requires to save the eight registers not pushed by hardware, r4-r11, and to copy SP_process into the Thread Control Block (TCB). If the processor saved the context on the main stack, the kernel would have to copy the 16 registers to the TCB" (§5.4). The hardware saved half the context on the task's own stack, so the kernel saves only the other half.

Getting into the kernel with SVC

Unprivileged code cannot change its own privilege, and it cannot touch the system registers. So when a task needs a kernel service, it asks for one with the SVC instruction, the supervisor call. The instruction raises the SVCall exception, which is exception number 11 in the TRM's table (Table 5-1). The SVCall handler runs in handler mode, which is privileged, so it can do the work the task asked for. When it returns, the task continues. The SVC call is the gate between the two. The task gets the service a privileged handler performs for it, and never the privilege itself.

Picture a hotel. Guests, the unprivileged code, have key cards that open their own room and nothing else. Staff, the privileged code, carry master keys. A guest who needs something from a locked store room does not pick the lock: they call the front desk, which checks the request and fetches it. SVC is that call, and the kernel's SVC handler is the front desk.

A worked example with real numbers

The second exercise below sets up a process stack at 0x20000080, drops privilege, and makes an SVC call. Here is the whole sequence, with the stack pointer values, so you can check each step against the simulator.

Step 5 is the one to check carefully. The frame is 32 bytes, which is 0x20. Subtract it from 0x20000080 and you get 0x20000060. The frame sits at 0x20000060 to 0x2000007F, in the process stack. The handler then reads PSP with MRS and gets 0x20000060, the address of its own caller's frame. That value is how the kernel finds the frame of the task that asked for the service.

Step 6 shows why the return value matters. The handler returns with 0xFFFFFFFD in LR. Table 5-6 lists this as a return to thread mode that gets its state from the process stack. If the handler had left LR as 0xFFFFFFF9, the core would have unstacked from the main stack, and the task would have resumed with the wrong stack pointer and the wrong frame. The value in LR is part of the state, and the handler must leave it alone.

Try it in the CPU simulator

The program counts up in thread mode. Its handler is a single instruction and a return. Watch the mode label in the register panel, which reads "Thread mode" or "Handler mode", and the stack pointer.

  1. Press Run, then Pause. The register panel shows "Thread mode". Note the SP.
  2. Press IRQ ⚡, then Step until the interrupt is taken. Predict the SP value: an eight-word frame is 32 bytes, so SP reads 0x200000E0 if it started at 0x20000100. Check the mode label.
  3. Press Instruction until the handler returns. Check that the mode is back to "Thread mode" and the SP is back to its starting value.
Hint

The starting SP is 0x20000100. An eight-word frame is 32 bytes. After the return, the stacked frame is removed and the SP returns to 0x20000100. R1 reads 0 again afterwards, not 1: the handler's write is undone when the frame restores R1, the same effect as in lesson 34.

Try it: two stacks and unprivileged code

This program gives thread mode its own process stack, drops privilege, and then makes a supervisor call, which is how unprivileged code asks the kernel for something. Turn on the System registers panel (it is shown below) and watch MSP, PSP, CONTROL and IPSR.

  1. Press Instruction four times. Before each press, predict which register changes. After the fourth, CONTROL is 2 and Active SP reads PSP: thread mode now runs on the process stack at 0x20000080.
  2. Two more presses set CONTROL to 3, which makes thread mode unprivileged. The next two presses load 2 into R0 and try to write it to CONTROL. The write is ignored, and the simulator says so. Writing 2 would clear the privilege bit, so the ignored write is the rule from the TRM at work: unprivileged code cannot promote itself.
  3. Step over SVC #0. Predict first: on which stack is the frame pushed, and what will LR hold? Then check: the frame lands on the PSP (PSP drops by 32, to 0x20000060), the handler runs on the MSP, IPSR is 11 (SVCall) and LR is 0xFFFFFFFD, meaning "return to thread mode, process stack".
  4. The handler, which is privileged, clears nPRIV, then returns. The thread is privileged again and still on the PSP. Check that PSP is back at 0x20000080 and that the final MRS R2, CONTROL reads 2.

This is the skeleton of an RTOS: tasks on PSP, kernel on MSP, and SVC as the gate between them. Lesson 88 adds the missing piece, swapping the PSP between tasks.

Line by line

The first four lines give thread mode its own stack. LDR R0, =0x20000080 loads the address into R0. The assembler places the constant in a literal pool near the code and loads it from there, which is why the line uses the = form. MSR PSP, R0 writes R0 into the process stack pointer. It comes before the next step on purpose. Once SPSEL selects PSP, every push and pop uses whatever PSP holds, so PSP must be valid first.

The next two lines select the process stack and drop privilege. MOV R0, #2 sets bit 1 of the value, which is SPSEL, and MSR CONTROL, R0 writes it. From this point thread mode uses PSP. MOV R0, #3 sets both bits, SPSEL and nPRIV, and the write makes thread mode unprivileged. The program is still in thread mode, and the core keeps its stack choice.

MOV R0, #2 followed by MSR CONTROL, R0 is the attempt to restore privilege. It is ignored, because the core is in thread mode and thread mode cannot raise its own privilege. SVC #0 then asks the kernel for help. It pushes the eight-word frame on PSP and switches to the handler.

The handler has three instructions. MRS R1, PSP reads the process stack pointer, which now points at the frame, so R1 holds the caller's stack pointer for the kernel to use. MOV R0, #2 and MSR CONTROL, R0 clear nPRIV for the caller. This write is allowed because the code is in handler mode, which is privileged. BX LR returns with 0xFFFFFFFD, which unstacks the frame from PSP and resumes the thread on the process stack. The final MRS R2, CONTROL reads 2, which shows that the thread is privileged again.

You watched the core switch from thread mode to handler mode and back, predicted an exception frame, and moved thread mode onto its own stack with reduced privilege, the exact arrangement an RTOS uses.

Common mistakes and how to spot them

1. Expecting unprivileged code to raise its own privilege

A task that writes 2 to CONTROL to drop its privilege back has no effect, because the TRM does not let thread mode restore privilege. The simulator reports the write as ignored, and the next MRS shows the old value. The symptom is code that works on paper and then behaves differently when it runs unprivileged. The fix is to ask the kernel for the change through an SVC, and to let the privileged handler write CONTROL.

2. Selecting PSP before loading it

Setting SPSEL to 1 switches the stack at once. If PSP has never been set, the next push or pop uses whatever value PSP holds, which may point into a peripheral register or an unused part of memory. The symptom is a fault or memory corruption that appears far from the cause. The fix is the order the program above uses: write PSP first, then set SPSEL. A good habit is to check that PSP lies inside RAM before the switch.

3. Giving a task a stack with no room for the frame

The first frame of an interrupt taken in a task goes on the task's process stack (§5.4). That is 32 bytes on top of whatever the task uses. A task whose stack is sized exactly for its own variables will overflow the first time an interrupt fires, even though its code never overflowed before. The symptom is a crash or corrupted data that appears only once interrupts are enabled. The fix is to budget for the frame, and to remember that the second and later pre-emptions use the main stack, so a task needs room for only one frame of this kind.

4. Changing LR before the return

The handler's return depends on the EXC_RETURN value the hardware put in LR. If that value is overwritten, the return picks the wrong stack. A handler that leaves LR as 0xFFFFFFF9 returns to thread mode on the main stack, and the task resumes with the wrong frame. The symptom is a task whose local variables look like garbage after a service call, and an SP that reads the main stack value instead of the process stack value. The fix is to leave LR alone between entry and return. In C the compiler handles this. In assembly, return with BX LR and nothing that writes LR in between.

In real projects

In a production RTOS port, the kernel's exception handlers run in handler mode on the main stack, and each task runs in thread mode on its own process stack. The context switch saves the registers that the hardware did not save and swaps the process stack pointer. Lesson 88 builds that switch. When a memory protection unit is fitted, it can also restrict which memory an unprivileged task may write, so a bug in one task has less room to overwrite another task's stack. Lesson 39 covers the protection unit.

A code reviewer looks for three things in this area. Task code should never write CONTROL or change the stack pointer, because that belongs to the port. System calls should go through an SVC, not through a direct call into kernel data. And every task's stack should be sized with the frame in mind, not only the task's own locals. Reviewers also check that a handler that switches stacks leaves LR alone, because a change there sends the task back to the wrong stack.

Summary

  • Thread mode runs the main program and tasks. Handler mode runs exception handlers and is always privileged.
  • Privilege is separate from mode. Unprivileged code cannot change system registers, and thread mode cannot restore its own privilege.
  • Only a handler can make thread mode privileged again. The SVC instruction is how unprivileged code asks for that service.
  • There are two stack pointers, MSP and PSP. Out of reset, and for all handlers, the main stack is used. Thread mode can use PSP, selected by CONTROL[1].
  • The first interrupt frame of a task goes on the task's process stack, so a task must have room for 32 bytes beyond its own use.
  • On a context switch, the kernel saves only R4 to R11 and the process stack pointer, because the hardware already saved the rest.
  • The return value in LR, EXC_RETURN, chooses the stack and the mode after return. Leave LR alone.
