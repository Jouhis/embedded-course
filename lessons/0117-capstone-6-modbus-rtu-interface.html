Capstone 6: Modbus RTU interface and the host master

A dryer that only a button can drive is a demo. This stage gives it a bus that a PC can read and write, so a factory line or a technician can see its state and start a drying cycle.

By the end of this lesson you can explain a Modbus RTU frame byte by byte, decode a signed temperature from a holding register, say where the silent interval and the CRC sit in a frame, and drive the dryer from a host script that reads its status and writes its command register.

Where we are and why it matters

Lessons 112 to 116 built the dryer's inside. Lesson 112 wrote the requirements and the state machine, lesson 113 the layered architecture and the task plan, lesson 114 the NTC driver and its host tests, lesson 115 the heater PWM, the buttons, the display and the safety checks, and lesson 116 the RTOS threads and the PID loop. The inside works, but the dryer still has no way to tell the outside world what it is doing. A factory line, a home server or a technician's laptop cannot ask it for its temperature, and nobody can start a drying cycle except by pressing the button on the case.

This stage solves the first of two problems that every product in the field has: talking to the device over a wire. The framing rules are the ones lesson 101 taught for RS-485 and Modbus RTU, and this lesson applies them to a real product. The second problem, changing the firmware after the device has left the factory, is the subject of lesson 118. Both need care. A wrong register map leaves the host reading nonsense, and a framing mistake leaves the dryer silent.

What Modbus is, in plain words

A bus is a wire, or a pair of wires, that several devices share. Modbus is a protocol for a serial bus: devices take turns sending short messages, one byte after another. In the usual arrangement there is one master, which starts every conversation, and one or more slaves, which answer only when addressed. Here the master is a Python script on a PC, and the dryer is a slave with address 1.

Serial means that the bits of a byte travel one after another over a single data line. On the chip, a UART (universal asynchronous receiver and transmitter) does this work. It shifts one byte out one bit at a time, and it collects the incoming bits into a byte. The CPU never sees individual bits. It reads a whole byte from the UART's data register when the receive interrupt fires, and it writes a whole byte to the data register when it has something to send. The protocol above the UART is built from these bytes.

The data the slave exposes is a list of holding registers. A holding register is a 16-bit number, which is two bytes, with an index (its address) starting at 0. The slave keeps the list in its own memory, and the master reads and writes entries of it. The register is not the same as a CPU register or a peripheral register from earlier lessons: it is a slot in a table that the protocol defines, and the firmware decides what each slot means.

The protocol does not name the dryer's temperature or its state. It moves 16-bit numbers in and out of a table, and the meaning of each slot is an agreement between the firmware and the host. That agreement is the register map. It is also why the same master script could talk to any device that publishes a map like this one.

The protocol is simple, which is its strength. Every request has the same shape: an address, a function code that says what to do, some fields, and a checksum. Every reply is either the same kind of message with the answer in it, or an exception, a short message that says why the request was refused. The physical layer, which is how the bits travel on the wire, is covered in lesson 101. A real RS-485 installation adds a transceiver chip that converts the signal levels. The simulator, and this build, talk to the UART pins directly.

The register map

The map is the contract with the host, so it lives in one file, app/regmap.h, and the Python script copies the same numbers. The firmware publishes the read-only registers from the control state before each reply. Only two registers accept writes: a command and a material. Everything else is read-only, and a write to it is refused.

AddressNameAccessMeaning
0SETPOINT_CreadWhole degrees C of the selected material
1STATEread0 IDLE, 1 HEATING, 2 HOLDING, 3 COOLDOWN, 4 FAULT
2TEMP_X10readTemperature in tenths of a degree, signed (22.5 °C is 225)
3PWM_PCTreadHeater duty, 0 to 100 %
4FAULT_CODEread0 none, 1 over-temperature, 2 sensor, 3 runaway, 4 stale
5REMAINING_MINreadMinutes of drying left
6COMMANDwrite1 starts or stops the cycle, as the button does; reads 0
7MATERIALread and write0 PLA, 1 PETG, 2 ABS; a write is applied only while IDLE

Two rows need a comment. COMMAND is a trigger, not a setting: writing 1 does what the button does, and the firmware clears the register straight after it takes the command, so a read always returns 0. MATERIAL is both a setting and a status, because the host can write it and then read it back. The firmware accepts a new material only while the dryer is IDLE, so a write during a cycle has no effect.

Why the temperature needs a sign

A Modbus register is an unsigned 16-bit number, so it can hold 0 to 65535. A chamber temperature can be below zero, and the register layout needs a way to carry −5.0 °C. The answer is two's complement, the standard way that binary hardware stores negative numbers. The bits of a negative value are the bits that, added to the positive value, give zero in 16 bits.

Take −50 tenths of a degree (that is −5.0 °C). Work in 16 bits, step by step:

  1. Write 50 in binary: 50 is 0x0032, which is 0000 0000 0011 0010.
  2. Invert every bit (the one's complement): 0xFFCD, which is 1111 1111 1100 1101.
  3. Add 1: 0xFFCD + 1 = 0xFFCE. This is the value stored in the register.
  4. Check: the register holds 0xFFCE = 65486. Since 65536 − 65486 = 50, the register is −50 when read as a signed number.

The check in the last step shows the rule behind the whole scheme. A 16-bit register wraps around at 65536, so the value 65486 sits 50 steps below zero. The top half of the unsigned range, 32768 to 65535, is read as the negative numbers −32768 to −1. The bits do not change; only the reading does.

The firmware does this by casting. It converts the signed value to int16_t, which the compiler stores as two's complement, and then to uint16_t, which keeps the same 16 bits. The host does the reverse: it reads the same 16 bits and interprets them as signed. The mistake that catches people is to read the register as unsigned. Then 0xFFCE is 65486 tenths, which is 6548.6 °C. The bits are right and the reading is absurd, so it is worth testing both directions.

The write check and the exceptions

The slave must not pretend to accept a write it will ignore. modbus_slave_t has an optional check_write hook, and the dryer sets it to regmap_check_write(). A write to a read-only register gets exception 02 (illegal data address), and an out-of-range command or material gets exception 03 (illegal data value), as the Modbus application protocol defines (lesson 101). With the hook left NULL, the module behaves exactly like lesson 101's, so the change is backwards compatible. A host test sends a real frame and checks the 0x86 0x02 reply.

The hook is short enough to read in full. This is the function from the starter project, which the lesson does not ask you to change: 

uint8_t regmap_check_write(uint16_t reg, uint16_t value) {
    switch (reg) {
    case REG_COMMAND:
        return (value <= REGMAP_CMD_START_STOP) ? 0u : MODBUS_EXC_ILLEGAL_VALUE;
    case REG_MATERIAL:
        return (value < MATERIAL_COUNT) ? 0u : MODBUS_EXC_ILLEGAL_VALUE;
    default:
        return MODBUS_EXC_ILLEGAL_ADDRESS;   /* every other register is read-only */
    }
}
  • uint8_t regmap_check_write(uint16_t reg, uint16_t value) receives the register address and the value the master wants to write. Its return value is an exception code, and 0 means the write is accepted.
  • switch (reg) picks the rule for the register. Only two cases exist, and every other address falls through to default.
  • case REG_COMMAND accepts 0 and 1, because REGMAP_CMD_START_STOP is 1. Any larger value returns exception 03.
  • case REG_MATERIAL accepts 0 to 2, because there are MATERIAL_COUNT materials. A value of 3 or more returns exception 03.
  • default covers the read-only registers. Writing to them returns MODBUS_EXC_ILLEGAL_ADDRESS, which is exception 02, because the address does not accept writes at all.

The byte 0x86 is the function code 0x06 with its top bit set (0x06 + 0x80). That top bit is the exception flag, and the byte after it is the exception code. The next section works one of these frames with real numbers.

A frame, byte by byte

A Modbus RTU frame is a sequence of bytes with nothing around it: no start byte and no end byte. The fields are the slave address, the function code, the data, and a 16-bit CRC. The CRC is a checksum: a short number computed from all the other bytes, so the receiver can tell whether the bytes arrived intact. The Modbus CRC is CRC-16/MODBUS, which lesson 101 defines, and its check value for the ASCII text "123456789" is 0x4B37.

Here is a worked example that you can check with the master script. The master wants to read register 2, the temperature, from slave 1.

StepBytes (hex)What each byte means
Request01 03 00 02 00 01 25 CA01 slave address; 03 read holding registers; 00 02 start address 2; 00 01 quantity 1; 25 CA the CRC, low byte first
Reply, reg 2 = 0xFFCE01 03 02 FF CE 78 2001 and 03 echo the request; 02 is the byte count of the data; FF CE is the register; 78 20 the CRC
Refused write01 86 02 C3 A186 is 0x06 with the exception flag 0x80 set; 02 is the exception code, illegal data address

Each of the three CRCs in this table can be checked with the CRC function in master_dryer.py, which computes the same CRC-16/MODBUS as the firmware. Over the first six bytes of the request, 01 03 00 02 00 01, the CRC is 0xCA25, sent as 25 CA. Over the first five bytes of the reply, 01 03 02 FF CE, it is 0x2078, sent as 78 20. Over 01 86 02 it is 0xA1C3, sent as C3 A1.

The reply's data is the same two bytes as the register in the table above, so the host reads 0xFFCE and decodes it as −5.0 °C. The plaintext block below writes the decoding out, field by field: 

reply bytes:     01 03 02 FF CE 78 20
slave address:   01          slave 1 answers
function:        03          read holding registers
byte count:      02          two data bytes follow
register value:  FF CE       0xFFCE, read as big-endian (high byte first)
CRC:             78 20       0x2078, low byte first
signed reading:  65486 - 65536 = -50 tenths = -5.0 C

Notice two details of the byte order. Each 16-bit field is big-endian, so its high byte comes first: the start address 2 is sent as 00 02. The CRC is the opposite, with its low byte first (25 CA). Mixing up those two orders is a common bug in a first Modbus implementation. Endianness is the name for the order in which the bytes of a multi-byte number are sent or stored, and a protocol has to state it for every field. This one states it twice, on purpose, because the two rules differ.

The frame lengths are fixed for the functions this slave supports: a read or a single write is 8 bytes (the request), and a refused write is 5 bytes (address, function with the flag, exception code, and CRC). A slave that receives a frame of any other length, or a frame whose CRC does not match, stays silent. Silence is the protocol's way of saying "I did not understand, and I will not pretend to".

The RTU frame: silence, CRC and one interrupt per byte

The RTU slave is the lesson 101 code, reused as it is: modbus.c parses a complete frame and crc16.c computes the CRC. Only the framing is new. Framing means deciding where one frame ends and the next begins, and an RTU frame has no marker for that. The rule is the silent interval: a frame ends when the line has been idle for a set time.

The Modbus serial-line specification defines the silence as 3.5 character times. This project's serial format is 8N1, so a character is 10 bits on the wire (a start bit, eight data bits and a stop bit). Three and a half characters are 35 bit times, and at 115200 baud that is 35 ÷ 115200 = 303.8 µs. The project does not use that computed value. It uses a fixed 1.75 ms, and its own comment says that is what 115200 baud needs. Lesson 101 gives the same figure. I could not open the specification from this workspace, so treat 1.75 ms as the project's value and check it in the document named in the Source box before you rely on it.

The tasks tick at 1 ms, so the comms task measures silence in ticks. It uses a gap of 2 ms, which is safe because it is longer than the required silence. The comms task waits up to 2 ms for the next byte. If no byte comes, the frame that has been collected so far is complete, and the task passes it to modbus_process(). Bytes past the end of the buffer are dropped, so an overlong frame is cut short and fails its CRC, which means it gets no reply.

The CRC is the second half of the protection. The sender computes the CRC-16 over the address, function and data bytes, and appends it. The receiver computes the same CRC over the bytes it received and compares the result with the last two bytes. Any single-bit error changes the CRC, so a corrupted frame is detected. The CRC does not say which byte was wrong, and it does not stop a deliberate forgery. It only says that the bytes that arrived are not the bytes that were sent.

Each received byte raises an interrupt. The interrupt handler reads the status register and then the data register, and it puts the byte on a FreeRTOS queue (lesson 90). The comms task takes bytes from the queue at its own pace. The handler must not block, because an interrupt has no task to sleep, so it uses the non-blocking xQueueSendFromISR(). The interrupt is short, so it never keeps the heater control waiting.

Reading the status register before the data register also clears the overrun flag. An overrun happens when a new byte arrives before the old one was read, and the overrun flag stops the receiver until it is cleared. The project's receive handler reads both registers in that order, so one lost byte cannot stop the receiver for good. The lost byte shows up as a bad frame, and the bad frame gets no reply.

One wire, one job. USART1 carries both the log and the Modbus frames. A status line printed between a request and its reply would corrupt the reply. So the build turns the once-a-second status line off with DRYER_LOG_STATUS 0, and the watchdog check-in in the logger task stays on. The lesson 116 build printed the line; this one reports the same state through the registers.

Check the frames of this lesson in the builder. Read the dryer's registers with function 03, write the command register with function 06, and compare each CRC with the table. Under any bytes (hex), type 31 32 33 34 35 36 37 38 39, the text 123456789, to get the check value 0x4B37.

The master: a host script

master_dryer.py is adapted from lesson 101's master. It builds the frames, checks the CRC with its own implementation, and talks to the simulator through the RFC 2217 port in wokwi.toml, which is 4000 in this stage. RFC 2217 is a standard way to carry a serial port over a network connection, so the script can talk to the simulated USART1 as if it were a real adapter. Its selftest command runs without a serial port, and the other commands need pyserial, which you install yourself. Run its selftest now: 

python master_dryer.py selftest
selftest OK: CRC-16/MODBUS 123456789 = 0x4B37, frames match, signed temperature decodes

The selftest checks three things: the CRC against the standard check value, the request frames against the worked bytes above, and the signed decoding. It also checks that a corrupted frame fails the CRC test. The script's CRC is written separately from the C code, so the two check each other. If the C side and the Python side disagreed on a single byte, one of the two selftests would fail.

The script has four commands, and each one maps onto the register map:

  • status reads all eight registers in one request (function 03, start 0, quantity 8). It then decodes them: the state name, the temperature with its sign, the duty, the fault name and the minutes left. The decoding is where the signed reading from the earlier section happens.
  • material PETG writes register 7 with the value for the chosen material. The name must be PLA, PETG or ABS, and the script rejects anything else before it opens the port.
  • start writes 1 to register 6, the same command the button sends.
  • selftest runs the checks described above, with no serial port needed.

Each command builds its request with the CRC, sends it, and reads the reply until the line has been silent for the same 1.75 ms the firmware uses. A correct slave echoes a write frame exactly, so an echo means the register accepted the value. Any other reply, or none, is printed as bytes so you can see what came back.

Hint for the temperature register

The temperature is in hundredths of a degree. Divide by 10 to get tenths, and store it as an unsigned 16-bit value by casting through a signed 16-bit type. The test for −5.00 °C expects 0xFFCE, which is −50 in two's complement.

Common mistakes and how to spot them

Every one of these has happened to someone building a Modbus device. Each entry gives the symptom first, so you can recognise it before you find the cause.

Mistake 1: a status line on the Modbus wire

Symptom: the master reports a bad CRC or no reply, but only while the firmware runs with the status line enabled. A frame that works with the logger off fails with it on. Cause: the log bytes land between the request and the reply, or inside the request, so the frame no longer matches its CRC. Fix: keep DRYER_LOG_STATUS at 0 in this build, and send any debug text to a second serial port, not to USART1.

Mistake 2: reading the temperature as unsigned

Symptom: a host script shows a chamber temperature of 6548.6 °C, or any large positive number, when the dryer is cold. The register holds 0xFFCE, and the bits are right. Cause: the script reads the 16 bits as an unsigned number, so 65486 tenths becomes 6548.6 °C. Fix: decode register 2 as signed (struct format <h in Python, int16_t in C). The selftest checks this path.

Mistake 3: changing a register that the firmware owns

Symptom: the master writes a new material with function 06, the reply echoes the write, and the next read shows the old material again. Cause: the material is applied only while the dryer is IDLE, and regmap_publish() copies the real material into the register on every reply. Writes during a cycle are refused silently in the state machine. Fix: stop the cycle first, write the material, and read it back. The firmware's behaviour is the design, so the fix is in the host, not in the register.

In real projects

Teams that ship a Modbus device publish the register map as a document or a shared header, and the host tool is written against that same document. The map is versioned like an API: adding a register is safe, and moving or changing the meaning of one breaks every installed host. Reviewers ask for the map first, and for a test that proves the firmware and the map agree. The host test in this capstone does that job, and lesson 119 shows how it runs in CI.

The master side is often a SCADA system or a PLC rather than a Python script, and the same rules apply there. The host has to use the same byte order, the same silent interval and the same CRC. Teams usually keep recorded frames with their correct replies and run them against any new host tool. The selftest in this lesson is a small version of that practice.

Summary

  • Modbus RTU is a master and slaves on a shared serial line. Holding registers are 16-bit slots, and the firmware decides what each one means.
  • Signed values travel as two's complement in unsigned registers. −50 tenths is 0xFFCE, and reading it as unsigned gives a wrong temperature.
  • Each 16-bit field is big-endian, but the CRC is sent low byte first. A frame has no start or end marker: its end is a silent interval, and its integrity is the CRC. Bad frames get no reply.
  • Exception 02 means a bad address (here, a write to a read-only register), and exception 03 means a bad value. The flag 0x80 marks any exception reply.
  • The receive interrupt puts each byte on a queue with the non-blocking FromISR call, and a task assembles the frame.
  • Keep debug text off the Modbus wire. The host script reads status and writes the command and material registers through the same map as the firmware.
