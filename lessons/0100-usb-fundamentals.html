USB fundamentals

A USB device has no voice of its own: the host asks and the device answers. Everything a device can do, from a keyboard to a serial port, is described in descriptors that the host reads at connection time. This lesson covers that model, and it builds a USB serial demo for the Pico that you can run on real hardware.

By the end of this lesson you can describe the order of USB enumeration, name the four transfer types and the device classes, and explain why the CDC demo needs a real Pico to show its port.
Why this lesson has no simulator task. Wokwi's USB support is partial (NOTES.md), so it cannot enumerate a device. The lesson is concept-first, and it ends with a demo that builds here and runs on a real board.

The idea: the host is in charge

A USB network has one host, normally the PC, and devices hang off it through hubs. The host starts every transfer. A device never sends data unsolicited: it answers when the host asks, or it has an interrupt endpoint that the host polls on a schedule. The host also decides when a device gets power, which address it uses and which driver serves it. This is the opposite of a serial line, where either side may start. It is also why a USB keyboard has a fixed polling interval, and why a USB device that hangs stops only itself, not the host.

The classic primer that explains the host-and-device model, endpoints, descriptors and enumeration in full is USB in a NutShell. This lesson did not open its sections, so read them before you rely on any detail here.

Endpoints and transfer types

An endpoint is one source or sink of data on a device, identified by a number and a direction (IN to the host, or OUT from it). Every device has endpoint 0, the control endpoint, used for configuration and requests. Other endpoints use one of four transfer types, each chosen for a purpose.

Transfer typeTypical useGuarantee
ControlEnumeration, configuration, class requestsDelivered and checked; used on endpoint 0
InterruptKeyboards, mice, small status messagesPolled at a set interval, small payload, with a delivery check
BulkSerial data, disk blocks, large transfersDelivered and checked, with no timing promise
IsochronousAudio and video streamsA reserved bandwidth and timing, but no retry of bad data

Descriptors: the device describes itself

A device does not have a fixed identity. It stores descriptors, which are small structures the host reads: the device descriptor (vendor and product IDs, the default class), one or more configuration descriptors, the interface descriptors inside each configuration (each interface is one function with a class), and the endpoint descriptors inside each interface (number, direction, transfer type and maximum packet size). String descriptors give the names a user sees.

Enumeration: how the host meets a new device

When a device is attached, the host sees it and resets the bus. The device then answers at the default address 0. The host reads the device descriptor first, then assigns a unique address with SET_ADDRESS. It reads the configuration descriptors, selects one with SET_CONFIGURATION, and loads a driver for each interface's class. Only then does data move. This sequence is why a device that fails enumeration shows up as an unknown device on the PC, with no port.

Device classes: one protocol, many devices

A class defines how an interface behaves, so the host can use a standard driver without knowing the vendor. Three classes matter here:

  • CDC, the communications device class, which gives a virtual serial port (a COM port on Windows). The Pico's stdio over USB uses it.
  • HID, the human interface device class, for keyboards, mice and generic input and output reports.
  • MSC, the mass storage class, which makes the device look like a disk.

TinyUSB, the open-source USB stack that the Pico SDK uses, supports all three as device classes, along with others (TinyUSB documentation). Its device stack is what the demo below runs on the RP2040.

TinyUSB in the Pico SDK

The Pico SDK wires TinyUSB into the standard I/O library. Setting pico_enable_stdio_usb(target 1) in CMake makes printf go to a USB CDC port. Setting pico_enable_stdio_uart(target 0) stops it from using UART0 at the same time. The SDK in this workspace (2.3.1) includes TinyUSB under lib/tinyusb, and the demo builds with it.

Try it: build the USB CDC demo

The project is projects/0100-usb-cdc-demo. It prints a line each half-second over USB, and it waits up to three seconds for a terminal to open first. You cannot see the port in Wokwi, so you build it and check the build output.

  1. From the workspace root, run python -I tools/build.py projects/0100-usb-cdc-demo. It ends with the link step, and it produces build/usb_cdc_demo.elf.
  2. Read main.c. Find the call that enables the USB stdio in CMakeLists.txt, and the line that turns UART stdio off.
  3. On a real Pico, you need a way to load the program. The templates turn picotool off (PICO_NO_PICOTOOL), so the build makes an ELF, not a UF2. Load it with a debug probe, or turn picotool on and build a UF2. Then plug the board in, and open the new serial port in a terminal at any baud rate. You will know it works when the port lists CDC demo: connected=1 and then a tick line every second.
Do not expect the Wokwi simulator to show this port. The serial monitor is UART-based, and the USB device is not simulated for the Pico in this course.

"How does a USB device get an address and tell the host what it is?" Answer out loud in 60 seconds, then compare.

Model answer

The host detects the attach and resets the bus, so the device answers at address 0. The host reads the device descriptor, then sends SET_ADDRESS to give the device a unique address. It reads the configuration and interface descriptors, which list the classes and the endpoints, selects a configuration, and loads a driver for each class. The device never announces itself: the host learns everything from its descriptors.
