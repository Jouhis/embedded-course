Interview preparation: a practice quiz

An embedded interview tests recall under pressure, so this lesson drills the whole course in one sitting: C traps, hardware, RTOS and debugging, plus five coding routines you should be able to write without notes.

By the end of this lesson you can answer 30 mixed questions from across the course and write five classic C routines (bit reversal, popcount, a ring buffer, a byte swap, and macro pitfalls) from memory, then explain a design out loud.

This lesson is concept-only. There is no Wokwi project: the practice is in your head and on paper. The coding drills were compiled and run with the host GCC (MinGW) using -std=c11 -Wall -Wextra -Werror, so the reference answers are checked, not just written. The drills use the same host-test approach as lesson 80.

Integer promotion and wraparound

C computes arithmetic on small integers in a larger type. This rule is called integer promotion: any integer type narrower than int is converted to int before an operation (cppreference, "Conversions", in RESOURCES.md). The value only becomes an 8-bit number again when it is stored back into an 8-bit variable.

Take uint8_t a = 200 and uint8_t b = 100, then work out (uint8_t)(a + b) step by step:

  1. Promote both operands to int: 200 and 100, which fit in an int.
  2. Add them in int: 300. Nothing has wrapped yet.
  3. Convert to uint8_t. An unsigned conversion keeps the value modulo 28, which is 256 for 8 bits, so 300 becomes 300 − 256 = 44.

The reason the language works this way is that the CPU has no 8-bit add for a value you have not yet stored. The compiler computes in a register that is at least 32 bits wide, and it truncates only when the result must fit a smaller variable. The other rule to remember is about signed types. A signed overflow, such as adding past INT_MAX, is undefined behaviour, which means the compiler may assume it never happens (cppreference, "Arithmetic operators, overflows"). Unsigned arithmetic always wraps modulo 2N, so the same sum is safe on an unsigned type and dangerous on a signed one.

Two's complement and signed values

An 8-bit signed variable stores its 256 bit patterns as −128 to 127. In two's complement, the top bit has weight −128 instead of +128, and the other bits add up as usual. So the pattern 0x80 (binary 1000 0000) is −128, and 0xFF is −1: adding 1 to 0xFF gives 0x100, which wraps to 0x00. You can check any negative value the same way: write the positive value, invert the bits, add one. That is how the register value in lesson 113 was built, and it is the rule behind the ADC and temperature questions too.

Volatile and the value the compiler does not see

The compiler optimises on the assumption that the code it can see is the only code that changes a variable. An interrupt handler is code the main loop cannot see in its own body, so a flag set there can look constant to the main loop. Consider a loop that waits for done, where done is set in an ISR. Without volatile, the compiler may read done once, keep it in a register, and loop forever, because nothing in the loop writes it.

Declaring the variable volatile tells the compiler that every read and write of it is an observable side effect, which it may not skip, merge or reorder against other visible side effects in the same thread (cppreference, "volatile", in RESOURCES.md). It does not make an access atomic, and it gives no synchronisation between threads. The same page says that threads should use _Atomic types from C11 for that job, and the mutex and critical section ideas below cover the rest.

Setting one bit without touching the others

A register is a number, and a bit is one of its 32 positions. To change one bit, you combine the register with a mask, a number that is 1 only at the positions you want to affect. Work through an example with REG = 0x05 (binary 0000 0101) and bit 3:

  1. The mask for bit 3 is 1u << 3, which is 0x08 (0000 1000).
  2. OR the register with the mask: 0000 0101 | 0000 1000 = 0000 1101, which is 0x0D. Bit 3 is set, and bits 0 and 2 are unchanged.
  3. AND with the inverted mask clears the bit: 0000 1101 & 1111 0111 = 0000 0101, which is back to 0x05.

OR sets, AND clears, and XOR toggles. The read-modify-write pattern (lesson 20) works because the other bits pass through unchanged. It also explains a common bug: writing REG = (1u << 3) sets bit 3 and clears every other bit, which is wrong for a register that other code relies on.

Interrupts, critical sections and latency

An interrupt is a hardware signal that makes the CPU stop the current code, save its state and run a handler (lesson 34). A critical section is a short piece of code that runs with interrupts masked, so no handler can change the shared data in the middle of it. The cost is latency: while interrupts are masked, a pending interrupt waits. If a critical section runs for 2 µs, a timer interrupt that fires during it starts 2 µs late, however high its priority. The priority only chooses the winner after the mask is lifted.

Mutexes, priority inversion and the ring buffer

A mutex is a lock that one task holds at a time, and it has an owner. Priority inversion happens when a high-priority task waits for a mutex that a low-priority task holds, while a medium-priority task keeps the low one from running. The fix is priority inheritance, where the holder temporarily runs at the waiter's priority (lesson 90). Interview answers that name the lock and the timeline score well, because the cause is easy to draw.

A ring buffer stores bytes in a fixed array and moves two indices around it. The drill below uses free-running 32-bit counters: the head and tail count up forever, and the slot is the counter masked to the array size. The buffer is full when head minus tail equals the size. Because the counters never reset, all 16 slots can hold data, and the subtraction still works after the counters wrap at 232, since the size divides 232.

Timing numbers you should be able to compute

Many questions reduce to a few numbers. A UART byte with a start bit, eight data bits and a stop bit takes 10 bit times, so at 115200 baud it takes 10 ÷ 115200 s, which is 86.8 µs (lesson 53). An I2C byte with its acknowledge takes nine clock pulses, so at 100 kHz it takes 90 µs (lesson 60). A PWM period at 1 kHz from a 1 MHz clock has 1000 ticks, so the auto-reload value is 999 (lesson 59). Write the formula before you write the number, and say the unit out loud.

Explain out loud

Interviewers often ask you to talk through a design on a whiteboard. Set a two-minute timer, speak the answer, and only then open the outline.

"Design a button debouncer for a firmware with a main loop and a 1 ms tick." Speak for two minutes, then compare.

Model answer outline
  1. State the goal: report one press per physical press, with no blocking delay.
  2. Sample the pin in the 1 ms tick (or a 5 ms slot) and store the last raw reading.
  3. Count consecutive equal samples. Accept a new level only after N equal samples, for example N = 5 at 5 ms, and measure the switch's real bounce time with a logic analyzer before choosing N (lesson 52).
  4. Report the edge once, on the change of the accepted level. Never call a delay.
  5. Test it on the host: feed a scripted sequence of bouncing samples and check the output (lesson 80).
  6. Say what you would change for a wake-up pin in a low-power design (lesson 75).

"Structure the firmware for a battery-powered sensor node with a radio, a display and a button." Speak for two minutes, then compare.

Model answer outline
  1. Split the layers: drivers that touch registers (sensor, display, radio), a hardware abstraction layer with an interface per device, and pure logic modules for the measurement and the display state (lessons 76 and 77).
  2. Put each piece behind an interface so the logic can be tested on a PC with fakes (lessons 80 and 81).
  3. Choose the scheduler: a super-loop with a timer tick is enough for one sensor; an RTOS when radio and display need their own timing (lessons 86 and 87).
  4. Plan the low-power loop: sleep between samples and wake on a timer or the button pin (lesson 75).
  5. Add a watchdog, a logging path, and a bootloader slot for updates (lessons 84, 85 and 102).

"Explain priority inversion on a whiteboard, with a timeline." Speak for two minutes, then compare.

Model answer outline
  1. Draw three tasks: low (L), medium (M), high (H). Mark when L takes a mutex.
  2. H becomes ready and blocks on the mutex that L holds.
  3. M becomes ready. M has higher priority than L, so it runs, and L cannot finish and release the mutex. H waits for M, which has nothing to do with the mutex.
  4. The fix is priority inheritance: L runs at H's priority while it holds the mutex, so M cannot preempt it (lesson 90).
  5. Mention the Mars Pathfinder story as the real case where the mutex lacked inheritance (RISKS Digest, in the resources).

Coding drills

Write each routine from memory, then compile it with gcc -std=c11 -pedantic -Wall -Wextra -Werror and add a small main with assert checks. Each solution below compiled and passed its tests on the host GCC used in this course. Open a solution only after you have tried.

Drill 1: reverse the bits of a 32-bit value

Return the value whose bit 0 is bit 31 of the input, and so on. Test with 0x00000001 and 0x0000000F.

Solution 
/* Reverse the order of the 32 bits: bit 0 becomes bit 31, and so on. */
uint32_t reverse_bits32(uint32_t x)
{
    uint32_t r = 0u;
    for (unsigned i = 0u; i < 32u; i++) {
        r = (r << 1) | (x & 1u);   /* append the lowest bit of x to r */
        x >>= 1;                   /* move to the next bit of x */
    }
    return r;
}

The loop appends one input bit to the result on each pass. It runs 32 times, so the result has the input bits in reverse order.

Drill 2: count the set bits

Return the number of 1 bits in a 32-bit value, without a loop over all 32 positions.

Solution 
/* Count the set bits. x &= x - 1 clears the lowest set bit, so the loop runs once per 1. */
unsigned popcount32(uint32_t x)
{
    unsigned n = 0u;
    while (x != 0u) {
        x &= x - 1u;
        n++;
    }
    return n;
}

Each pass clears the lowest set bit, so the loop runs once per set bit. This version is portable C, so it runs on any core, including the Cortex-M0+ with no popcount instruction.

Drill 3: a ring buffer

Write a FIFO of 16 bytes with push and pop. It must report full and empty without a wasted slot, and it must keep working when the indices wrap. Explain why head and tail are volatile.

Solution 
#define RB_SIZE 16u                 /* must be a power of two */
#define RB_MASK (RB_SIZE - 1u)

/* head and tail count up forever (they wrap at 2^32). The index is
   head & RB_MASK. Because RB_SIZE divides 2^32, the wrap is harmless.
   volatile: an ISR may change head or tail, so the compiler must reload them. */
typedef struct {
    uint8_t buf[RB_SIZE];
    volatile uint32_t head;         /* written only by the producer */
    volatile uint32_t tail;         /* written only by the consumer */
} ring_t;

static bool rb_push(ring_t *rb, uint8_t v)
{
    if (rb->head - rb->tail == RB_SIZE) {
        return false;               /* full: all 16 slots in use */
    }
    rb->buf[rb->head & RB_MASK] = v;
    rb->head = rb->head + 1u;
    return true;
}

static bool rb_pop(ring_t *rb, uint8_t *v)
{
    if (rb->head == rb->tail) {
        return false;               /* empty */
    }
    *v = rb->buf[rb->tail & RB_MASK];
    rb->tail = rb->tail + 1u;
    return true;
}

static uint32_t rb_count(const ring_t *rb)
{
    return rb->head - rb->tail;
}

The indices count up forever and wrap at 232. Because the size divides 232, the unsigned subtraction still gives the fill level. An interrupt may change one index, so both are volatile. For a producer in an ISR and a consumer in main, this is the usual single-producer single-consumer pattern (lesson 70). It is safe for exactly one writer per index.

Drill 4: swap the bytes of a 32-bit value, and read big-endian

Write a byte swap for uint32_t, and a function that reads a big-endian 16-bit value from a byte buffer without casting the buffer.

Solution 
/* Swap the byte order of a 32-bit value. */
uint32_t bswap32(uint32_t x)
{
    return ((x & 0x000000FFu) << 24) |
           ((x & 0x0000FF00u) << 8)  |
           ((x & 0x00FF0000u) >> 8)  |
           ((x & 0xFF000000u) >> 24);
}

/* Read a big-endian 16-bit value from a byte buffer. Byte-by-byte access
   works on any CPU and avoids unaligned or type-punned reads. */
uint16_t be16_read(const uint8_t *p)
{
    return (uint16_t)(((uint16_t)p[0] << 8) | p[1]);
}

Byte-by-byte access works on any CPU and avoids unaligned reads and strict-aliasing problems (lessons 45 and 48). Cortex-M cores have a byte-reverse instruction (REV), and the compiler may use it for this pattern, but the portable form is the one to write.

Drill 5: the macro pitfalls

Show why SQUARE(1 + 2) is wrong with a naive macro, how to fix it, why an inline function avoids double evaluation, and why a do { } while (0) wrapper is needed for a macro that is a statement.

Solution 
#define SQUARE_BAD(x) x * x            /* no parentheses: wrong for expressions */
#define SQUARE(x) ((x) * (x))          /* parenthesise every use of the argument */

/* An inline function evaluates its arguments exactly once. */
static inline int min_int(int a, int b)
{
    return (a < b) ? a : b;
}

/* A do-while(0) makes the macro one statement, so it works after if/else. */
#define SET_BITS(reg, mask) do { (reg) |= (mask); } while (0)

The naive macro expands SQUARE_BAD(1 + 2) to 1 + 2 * 1 + 2, which is 5. Parentheses around every use of the argument fix it. The inline function evaluates i++ once. The do-while wrapper makes the macro one statement, so an if without braces still works (lesson 50).

Behavioural questions and the STAR method

Behavioural questions ("Tell me about a time when...") test judgement. Answer with STAR: Situation (one or two sentences of context), Task (what you had to achieve), Action (what you did, in order), and Result (a measurable outcome and what you would do differently). Most candidates spend too long on the situation. Give it a third of your time at most. Use STAR as a checklist, not a script.

PartLengthEmbedded example
Situationone sentenceA sensor board gave wrong readings on some units but not all.
Taskone sentenceFind the cause within the sprint and make the readings reliable.
Actionthree stepsI captured the I2C lines with a logic analyzer, found slow rise times on SDA, and tested a lower pull-up value. I checked the datasheet's timing limits before changing it (lesson 60).
ResultmeasuredZero failed reads in 1000 cycles on five boards, and I added a rise-time check to the bring-up checklist.

Replace the example with a real story from your own work. The learner's own project is the best source: a bug in the capstone, a timing fault in a lab, or a review that changed a design.

"Tell me about a bug that took you the longest to find." Use STAR. Keep the answer under two minutes.

Model answer

S: Readings from a sensor were wrong on only some boards. T: Find the cause before the demo on Friday. A: I first ruled out the software by reading the raw bytes, then used the logic analyzer on the I2C lines and saw SDA rising slowly, which I traced to an oversized pull-up. I measured the rise time against the bus specification and lowered the value. R: The failures stopped in 1000 cycles on five boards, and I added the rise-time measurement to the bring-up checklist, so the next board is checked before it is shipped.

Common mistakes and how to spot them

Most lost interview marks come from how a candidate answers, not from what they know. Each entry below gives the symptom, so you can notice it while you practise.

Mistake 1: answering from recognition

Symptom: you read a question, feel that you know it, and say "volatile, yes" without a reason. In the interview the follow-up question ("so what does the compiler do without it?") exposes the gap. Cause: the words feel familiar, and familiarity is not recall. Fix: answer on paper first, in one sentence with a reason, and only then open the "Why" text. The "Why" is a check, not a source of the answer.

Mistake 2: reading the tempting answer as the right one

Symptom: you miss the same kind of question again and again, always choosing the answer that sounds like the textbook. Cause: the wrong options in these quizzes are chosen because they sound plausible, such as "const" for "volatile" or "128" for a signed 0x80. Fix: for each miss, write down which rule the tempting answer broke. A pattern of the same broken rule points to one lesson to reread.

Mistake 3: copying a drill solution

Symptom: the drill looks easy after you have read its solution, and you cannot write it on a blank page the next day. Cause: reading a solution gives recognition, not recall, which is the skill that interviews test. Fix: close the solution, write the function from memory, compile it with -Wall -Wextra -Werror, and check it with the asserts. Only then compare. A drill you can write three days later counts as learned.

Mistake 4: a model answer with no number

Symptom: the answer says "the timing is fine" or "the code is efficient", and the interviewer asks for the figure. Cause: the candidate has a conclusion but no measurement or calculation behind it. Fix: attach one number to each claim: the bit time, the utilisation, the cycle count or the measured rise time. The timing and calculation answers in this lesson each carry one.

In real projects and interviews

Interviewers at small embedded teams usually ask you to reason out loud about a small design, and they care more about the path than the final answer. They listen for three things: that you state the problem before the solution, that you name the trade-off you accepted, and that you know how you would test the result. The explain-out-loud prompts in this lesson are written in that order for that reason.

On the job, the same ideas appear in code review. A reviewer who sees a flag shared with an interrupt and no volatile, a mask written as a plain assignment, or a blocking call inside an ISR will ask about it in review, usually with a question of the same shape as the quiz. A candidate who can answer that question in review is the one who gets the offer, and the one who can explain why a rule exists is the one who keeps the job.

Summary

  • Integer promotion happens before arithmetic. The result wraps only when it is stored in a smaller type, and an unsigned conversion keeps the value modulo 2N.
  • Signed overflow is undefined, so keep arithmetic that can overflow in unsigned types when the wrap is wanted.
  • In two's complement, the top bit has weight −128 for 8 bits. Build a negative value by inverting the bits and adding one.
  • volatile stops the compiler keeping a value in a register across code it cannot see. It does not give atomicity or thread safety.
  • OR sets a bit, AND with the inverted mask clears it, and XOR toggles it. Plain assignment overwrites the whole register.
  • Priority inversion needs a lock, a low task that holds it, and a medium task that keeps the low task from finishing. Priority inheritance fixes it.
  • Write the formula before the number, and say the unit out loud.
