Timers

Hardware counters for PWM, input capture and encoders

By the end of this lesson you can compute a timer's prescaler and reload value for a target frequency, configure PWM output and input capture on the Blue Pill's TIM2 to TIM4 through CMSIS registers, and read a rotary encoder in encoder mode.

Counting in hardware beside the CPU

Lesson 40 set up the clock tree from which this lesson's timer runs, lesson 47 showed how a C struct can be laid over a block of registers, which is how TIM2->ARR and the other timer names work, and lesson 70 used the USART and the EXTI interrupt. This lesson adds the last common peripheral block met on the way to real hardware, the timer.

A timer solves three recurring problems: a motor driver or a heater needs a square wave with an adjustable on-time, which is PWM, a servo needs a pulse of an exact width, which means measuring time, and a rotary knob needs its rotation counted without a missed step, which is an encoder. A delay loop does none of these reliably, because the CPU is busy during every instruction it runs, whereas the timer counts in hardware and leaves the CPU free between events.

The timer counter and the update event

A counter is a register whose next value is its current value plus one on each tick of a clock, and a timer is a counter plus logic that does something useful with its value, driving a pin, recording the time of an edge on a pin or raising an interrupt when the count reaches a limit.

The count lives in a register, CNT, in the peripheral's address block, which the CPU reads with an ordinary load while the hardware increments it on its own clock without the CPU taking part. A timer therefore times events more precisely than a loop can, because the loop's speed depends on what the CPU is doing and the counter's only on its clock.

The counter counts from zero up to a limit held in the auto-reload register ARR, then wraps back to zero and raises an update event, the hardware's signal that the period has ended. The clock driving the counter is not the raw system clock either, because it first passes a prescaler, PSC, a divider the hardware applies before counting.

Prescaler, reload and the plus-one rule

The counter ticks at fclk ÷ (PSC + 1) and a period lasts ARR + 1 ticks, because the counter goes from zero up to ARR inclusive, so the update rate is

f = fclk ÷ ((PSC + 1) × (ARR + 1))(1)

where fclk is the timer's input clock. The two + 1 terms are the most common source of off-by-one errors in this lesson, and both have the same cause, a register that stores a count minus one.

A prescaler of 0 makes the counter tick at the full clock and a prescaler of 7 once every eight clock cycles, because the register stores the divider minus one, so writing 7 gives a divide-by-8. The reload follows the same convention: ARR = 999 does not mean counting to 999 and stopping, but counting 0, 1, 2 and so on up to 999, which is 1 000 values, before wrapping, so the period is 1 000 ticks, a pattern that every timer shares, including the SysTick timer of lesson 73.

In these projects the Blue Pill runs from the 8 MHz HSI oscillator (lesson 40) without the PLL, so with PSC = 7 the counter ticks at 8 MHz ÷ 8 = 1 MHz, one count per microsecond, and every number in this lesson is a count of microseconds, which keeps the arithmetic easy to check on paper.

Output compare and PWM

The timer can also drive a pin. Each channel has a capture/compare register, CCRx, which the hardware compares with CNT continuously, changing the channel's output pin when the two are equal or the count crosses the value, a mode called output compare, in which the OCxM bits of CCMRx decide exactly how the pin reacts.

The most useful output compare mode is PWM, a square wave whose high time is a chosen fraction of each period. In PWM mode 1 the pin is active while CNT < CCR, so the high time is CCR ticks, the period ARR + 1 ticks and the duty cycle

D = CCR ÷ (ARR + 1)(2)

where CCR is the channel's compare value, so for the LED in this lesson ARR = 999 and CCR = 250 give a 1 kHz signal at 25 % duty (RM0008 Rev 21, section 15.3.9, PWM mode).

The bit pattern for PWM mode 1 is OC1M = 110 in binary (RM0008 Rev 21, section 15.4.7). The CMSIS header names the two set bits TIM_CCMR1_OC1M_1 and TIM_CCMR1_OC1M_2, and the HAL names the whole mode TIM_OCMODE_PWM1, the two bits together (stm32f1xx_hal_tim.h), so writing the pattern with both names in one expression reads more clearly than a raw hex number.

A hobby servo expects a frame of about 20 ms containing a pulse of about 1 to 2 ms that sets its position, the centre lying near 1.5 ms. This is the usual convention for hobby servos rather than a figure from this course's sources, so the servo's datasheet should be checked before relying on the end points. With PSC = 7 and ARR = 19999 the frame is 20 000 µs, so the frequency is 50 Hz, and CCR = 1500 gives a high time of 1.5 ms.

Setting the preload bit (OC1PE) and the auto-reload preload bit (ARPE) makes a new ARR or CCR take effect at the next update event. Without them, a write during a period can give one short or long cycle. Always set the preload bits before you start the counter (RM0008 Rev 21, sections 15.3.1, 15.3.9 and 15.4.7).

Input capture of edge times

A timer can also work the other way round, an input capture channel watching a pin and copying the current value of CNT into its CCRx register when an edge arrives. The copy happens in hardware at the moment of the edge, so the value is accurate even while the CPU is busy elsewhere, and the CPU reads it later.

A bicycle computer measures speed this way. A magnet on the wheel passes a sensor once per turn, and the timer captures the count at each pulse. The difference between two captures is the time for one turn, and the wheel's circumference divided by that time is the speed. The CPU only reads two numbers; the timer did the timing in hardware.

One capture gives the time of one edge, while two captures, one on the rising edge and one on the falling edge, give the width of the pulse between them through a subtraction done in the counter's width. With a 16-bit counter, (uint16_t)(fall - rise) is correct even if the counter wrapped between the edges, because the unsigned 16-bit result is taken modulo 65 536, the rule for unsigned types explained in lesson 45.

Channels 3 and 4 of a timer can both capture the same input, one on the rising and one on the falling edge, and the solution does this on TIM3, CH3 taking the rising edge and CH4 the falling edge of the signal on PB0. The same timer's CH1 already drives the servo output, so using CH1 for the input would conflict with it.

Encoder mode for quadrature signals

A quadrature encoder has two outputs, A and B, 90 degrees out of phase, so when the shaft turns one way A changes before B, and when it turns the other way B changes before A. The order of the edges therefore gives the direction and their number the distance.

A quadrature encoder resembles two people clapping the same rhythm, one a quarter beat behind the other: if A claps first the shaft turns one way, if B claps first it turns the other, and counting the claps gives the distance. Real clappers can drift apart, however, whereas the encoder's two signals are fixed by the disc's geometry, so a change in their order always means a change in direction rather than a timing error.

Encoder mode makes the counter do this work itself, the slave mode select bits SMS in SMCR setting the mode. The HAL names the value TIM_ENCODERMODE_TI12, which is SMS = 011 (RM0008 Rev 21, section 15.3.12), and its comment calls it "quadrature encoder mode 3, x4 mode, counts up/down on both TI1FP1 and TI2FP2 edges" (stm32f1xx_hal_tim.h), so mode 3 counts every edge of both signals, four counts per full cycle, and the CPU reads only CNT without watching the pins.

The Wokwi wokwi-ky-040 part has pins CLK (A), DT (B), SW (push button) and the supply pins VCC and GND, and its docs say that the module has 20 steps per revolution, each producing a LOW signal on both DT and CLK, CLK going low first for clockwise rotation and DT first for counter-clockwise, so the first pin to fall sets the direction (Wokwi part: KY-040 rotary encoder).

If each of the 20 steps gives one full cycle, mode 3 counts four per step, 80 counts per revolution, but since the solution does not print a full revolution, the count should be checked with the encoder in use before relying on that figure.

Timer channels and their pins

Each timer channel has a fixed pin in the default mapping, the only mapping this lesson uses: TIM2 CH1 on PA0, TIM3 CH1 on PA6, TIM3 CH3 on PB0 and TIM4 CH1 and CH2 on PB6 and PB7. Remapping through the alternate-function block (AFIO) would move them, and the course does not remap (STM32F103x8/xB datasheet, "Pinouts and pin description" table, alternate-function column).

Verification note: the pin table above is taken from the course's source list, and the datasheet itself could not be opened when this lesson was revised. Check each pin in the table against your copy of the datasheet before you wire a real board.

Wokwi simulates TIM1 to TIM4 on the Blue Pill, but only partly. PWM output works. Input capture and encoder mode do not: in the simulator CCR3 and CCR4 stay 0, and TIM4 counts up on its own whatever SMCR says, so the ENC count value is meaningless there. The register setup in the solution is the reference for a real board; test the capture and the encoder on hardware when you can.

Worked example: a 1 kHz LED at 25 % duty

The target is a 1 kHz PWM at 25 % duty from an 8 MHz clock, and the steps below are the arithmetic the solution uses, written out so that it can be repeated for any target. Before starting, predict the reload value for a 1 µs tick.

  1. Choose the prescaler. A convenient tick comes from PSC = 7, giving 8 000 000 ÷ 8 = 1 000 000 Hz, one tick per microsecond.
  2. Find the period in ticks. A 1 kHz frequency has a 1 ms period, which is 1 000 ticks of 1 µs.
  3. Set the reload. The period is ARR + 1 ticks, so ARR = 1 000 − 1 = 999, and equation (1) confirms 1 000 000 ÷ (999 + 1) = 1 000 Hz.
  4. Set the duty. 25 % of 1 000 ticks is 250 ticks, so CCR1 = 250, and equation (2) gives 250 ÷ 1 000 = 25 %.

The steps show why the plus-one rule matters, because ARR = 1000 would make the period 1 001 ticks and the frequency 999.0 Hz, an error a scope would show and the LED would not, and the duty would drift as well, since 250 of 1 001 is not exactly 25 %.

The configurator below confirms this worked example. Then load the plus-one bug and compare the frequencies, and type a target frequency and duty to find the register values.

Worked example: a servo pulse measured by capture

The servo signal is generated on TIM3 CH1 and fed back into TIM3 CH3 and CH4 through a wire from PA6 to PB0, with the same arithmetic over a longer period. Before reading the steps, predict what the two capture registers hold for a 1.5 ms pulse whose rising edge lands at count 1 000.

  1. Keep the tick. The clock and prescaler are as before, 1 MHz or one tick per microsecond.
  2. Set the frame. A 20 ms frame is 20 000 ticks, so ARR = 19 999, and the frequency is 1 000 000 ÷ 20 000 = 50 Hz.
  3. Set the pulse. The pulse is 1 500 ticks, so CCR1 = 1500 and the high time is 1.5 ms.
  4. Capture the edges. If the rising edge is captured at CCR3 = 1000, the falling edge comes 1 500 ticks later, at CCR4 = 2500.
  5. Subtract. The width is 2 500 − 1 000 = 1 500 µs, which matches the output, so the wiring and the registers are both right.

If the counter wraps during the pulse, for example with the rising edge captured at 65 000 and the falling edge at 500 after the 16-bit counter passed 65 535 and restarted at zero, the plain subtraction 500 − 65 000 is negative, while the unsigned 16-bit form (uint16_t)(500 − 65 000) gives 1 036, the correct width of 500 + (65 536 − 65 000). The wrap cancels out as long as the pulse is shorter than the counter's full range.

The timer setup code line by line

The solution is in projects/0071-timers/solution/main.c, and its three functions set up the three uses of the timer. Each starts by setting pin modes, the port's configuration registers being CRL (pins 0 to 7) and CRH (pins 8 to 15), with a 4-bit field per pin made of a 2-bit CNF and a 2-bit MODE. The helper gpio_set_pin() picks the right register, clears the field with a mask and writes the new value, 0xB meaning CNF=10 and MODE=11, an alternate-function push-pull output at 50 MHz, since the timer drives the pin and the pin must therefore be in alternate-function mode rather than plain output mode. 

/* PA0 is TIM2 CH1: the LED output. */
RCC->APB1ENR |= RCC_APB1ENR_TIM2EN;
gpio_set_pin(GPIOA, 0U, CFG_AF_PUSHPULL_50);

TIM2->PSC = TIM_PSC;            /* divide 8 MHz by 8: 1 MHz tick */
TIM2->ARR = LED_PWM_ARR;       /* period = 1000 ticks: 1 kHz */
TIM2->CCMR1 = TIM_CCMR1_OC1M_1 | TIM_CCMR1_OC1M_2 | TIM_CCMR1_OC1PE;
TIM2->CCR1  = LED_DUTY_CCR;    /* high for 250 of 1000 ticks */
TIM2->CCER  = TIM_CCER_CC1E;   /* turn the channel 1 output on */
TIM2->CR1   = TIM_CR1_ARPE;    /* preload ARR at each update */
TIM2->EGR   = TIM_EGR_UG;      /* load PSC and ARR now */
TIM2->CR1  |= TIM_CR1_CEN;     /* start the counter */

The first line turns on the clock to TIM2 in the RCC, because a peripheral without a clock ignores its register writes, and the second makes PA0 an alternate-function output so that the timer drives it. PSC and ARR set the 1 kHz period, CCMR1 sets channel 1 to PWM mode 1 with the preload bit, CCR1 sets the high time and CCER turns the channel's output on. ARPE in CR1 preloads the period register, so a later change takes effect at the next update event, and UG in EGR forces an update now, copying the prescaler and reload into the active registers (RM0008 Rev 21, sections 15.3.1 and 15.4.6), without which the first period would use the reset values. The last line sets the counter enable bit and starts the timer. 

/* Input capture on TIM3: CH3 at the rising edge, CH4 at the falling edge of TI3. */
TIM3->CCMR2 = TIM_CCMR2_CC3S_0 | TIM_CCMR2_CC4S_1;
TIM3->CCER  = TIM_CCER_CC1E | TIM_CCER_CC3E | TIM_CCER_CC4E | TIM_CCER_CC4P;

static uint32_t capture_pulse_us(void) {
    uint16_t rise = (uint16_t)TIM3->CCR3;
    uint16_t fall = (uint16_t)TIM3->CCR4;
    return (uint16_t)(fall - rise);   /* wrap-safe, see worked example 2 */
}

CC3S_0 sets the channel 3 input to TI3, the direct input, so CH3 captures the edge on PB0, while CC4S_1 sets the channel 4 input to TI3 from the other side, the value 10 in the field selecting the signal of the other channel in the pair, so both channels see the same pin. CC4P in CCER makes channel 4 capture on the falling edge, so CCR4 holds the fall time and CCR3 the rise time (RM0008 Rev 21, sections 15.4.8 and 15.4.9), and the function reads both as 16-bit numbers and subtracts them as 16-bit unsigned values, as in the worked example. 

/* Encoder mode on TIM4: CH1 is CLK on PB6, CH2 is DT on PB7. */
TIM4->CCMR1 = TIM_CCMR1_CC1S_0 | TIM_CCMR1_CC2S_0;
TIM4->SMCR  = TIM_SMCR_SMS_0 | TIM_SMCR_SMS_1;   /* SMS = 011: encoder mode 3 */
TIM4->ARR   = 0xFFFFU;                         /* full 16-bit range */
TIM4->CR1   = TIM_CR1_CEN;

static int32_t encoder_count(void) {
    return (int16_t)TIM4->CNT;     /* signed, so a backward turn reads -1 */
}

CC1S_0 and CC2S_0 map channels 1 and 2 to their own input pins, TI1 and TI2 (RM0008 Rev 21, section 15.4.7), and the SMS field is set to three, SMS_0 and SMS_1 together, selecting encoder mode 3 as the HAL comment describes. The reload spans the full 16 bits, so the count wraps at 65 536 rather than at a small number that would clip a long run, and the read function casts the 16-bit CNT to int16_t, so that a backward turn, which takes the unsigned count from 0 to 65 535, reads as −1, as a person expects.

Common mistakes and how to spot them

The plus-one rule forgotten

The frequency comes out close to the target but not equal to it, a scope showing a 1 001 µs period for a 1 kHz target or the servo jittering because its frame is 20.001 ms, because the reload was written as the tick count rather than the count minus one. Compute ARR = (f_clk ÷ ((PSC + 1) × f)) − 1, and check the answer by recomputing the frequency with equation (1).

No update event after changing PSC or ARR

The first cycle is too long or too short and the timing is correct afterwards, because the written value sits in the preload buffer and the first period still uses the old one. Write UG to EGR right after the timer setup and before CEN, as the solution does.

The capture on the wrong channel

A capture register stays at zero, or the reading does not change when the pulse changes, because a pin driven by an output channel cannot also be read as an input on the same channel, and in this lesson TIM3 CH1 is the servo output, so the capture must use CH3 and CH4. Check the channel and the pin in the datasheet table, and confirm that the output channel is not the one being read.

Captures subtracted in the wrong type

The pulse width reads around −64 500 µs, or a huge positive number once the sign is lost, because int32_t width = fall − rise with 16-bit values goes negative across a wrap. Use the 16-bit unsigned form of capture_pulse_us().

The encoder count read as unsigned

The count jumps to about 65 000 when the knob turns the other way, because a backward turn takes CNT from 0 to 65 535 and a plain read shows that large number. Read it through the signed cast (int16_t)TIM4->CNT, which turns the same bit pattern into −1.

Timers in products and code review

In a product the timer is often the first peripheral a team configures after the clock. PWM sets the brightness of an LED and, through a driver, the speed of a motor, and it is the usual way a microcontroller controls the average power of a heater, while input capture measures the period of a sensor pulse, such as a radio-control receiver or a tachometer, and encoder mode reads a rotary control, such as a knob, a jog wheel or a motor shaft. Each use depends on the arithmetic of this lesson.

A senior engineer reviewing timer code expects the prescaler and reload as named constants with a comment on the resulting frequency, so that a clock change stays visible, a stated reason after every write to a preloaded register, usually the update event, and counter reads made in the counter's width, with the code saying so.

Summary

  • A timer is a counter that the hardware advances, so the CPU sets the registers once and reads the result later.
  • The counter ticks at fclk ÷ (PSC + 1) and a period lasts ARR + 1 ticks, both terms carrying a plus one.
  • PWM mode 1 (OC1M = 110) is high while CNT < CCR, giving a duty of CCR ÷ (ARR + 1).
  • Input capture copies CNT into a CCRx register at an edge, and the difference of two captures, computed in the counter's unsigned width, is the pulse width.
  • Encoder mode 3 (SMS = 011) counts every edge of both channels, so the CPU reads only CNT.
  • An update event (EGR UG) after changes to the preloaded registers makes the first period use the new values.
  • In Wokwi, PWM and the polled pulse measurement work while input capture and encoder mode are not simulated, so those are checked against the arithmetic here and tested on a real board.
