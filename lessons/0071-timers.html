Timers: PWM, input capture, encoder mode

A timer is a counter that the hardware advances for you. The CPU sets a few registers once, and then the counter times pulses, measures edges and counts rotation while your code does other work.

By the end of this lesson you can compute a timer's prescaler and reload value for a target frequency, configure PWM output and input capture on the Blue Pill's TIM2 to TIM4 through CMSIS registers, and read a rotary encoder in encoder mode.

Where we are and why it matters

Lesson 40 set up the clock tree, and the timer in this lesson runs from that clock. Lesson 47 showed how a C struct can be laid over a block of registers, which is how TIM2->ARR and the other timer names work in this lesson. Lesson 70 used the USART and the EXTI interrupt, and this lesson adds the last common peripheral block that a beginner meets on the way to real hardware: the timer.

A timer solves three problems that come up again and again. A motor driver or a heater needs a square wave whose on-time can be changed, which is PWM. A servo needs a pulse of an exact width, which means measuring a time. A rotary knob needs its rotation counted without missing a step, which is an encoder. A delay loop can do none of these reliably, because the CPU is busy during every instruction it runs. The timer does the counting in hardware, so the CPU is free to do other work between the events.

Concept 1: a counter that runs next to the CPU

A counter is a register whose next value is its current value plus one, on each tick of a clock. A timer is a counter plus the logic that does something useful with its value: it can drive a pin, record the time of an edge on a pin, or raise an interrupt when the count reaches a limit.

The timer's count is stored in a register, CNT, in the peripheral's block of addresses. The CPU reads it with an ordinary load, and the hardware increments it on its own clock. The CPU is not involved in each increment. This is why a timer times events more precisely than a loop can. The loop's speed depends on what the CPU is doing, while the counter's speed depends only on its clock.

The counter is not infinite. It counts from zero up to a limit, then wraps back to zero and raises an update event, which is the hardware's word for "the period has ended". The limit is held in the auto-reload register ARR. The clock that drives the counter is not the raw system clock either. It goes through a prescaler PSC, a divider that the hardware applies first.

Concept 2: prescaler and reload, and the plus-one rule

The counter ticks at f_clk ÷ (PSC + 1). The period is ARR + 1 ticks, because the counter goes from zero up to ARR inclusive. The update rate is therefore f = f_clk ÷ ((PSC + 1)(ARR + 1)). The two + 1 terms are the most common source of off-by-one errors in this lesson, and the next section shows why both are there.

Think of the prescaler as a slow hand on a clock face. A prescaler of 0 means the counter ticks at the full clock. A prescaler of 7 means it ticks once every eight clock cycles. The register stores the divider minus one, so writing 7 gives a divide-by-8. That is why the formula has PSC + 1.

The reload has the same convention. Writing ARR = 999 does not mean "count to 999 and stop". It means "count 0, 1, 2, up to 999, that is 1000 values, then wrap". So the period is 1000 ticks. The same pattern appears in every timer, and in the SysTick timer in lesson 73.

The Blue Pill runs from the 8 MHz HSI oscillator in these projects (lesson 40), with no PLL. With PSC = 7 the counter ticks at 8 MHz ÷ 8 = 1 MHz, so one count is one microsecond. Every number in this lesson is a count of microseconds, which keeps the arithmetic easy to check on paper.

Concept 3: output compare and PWM

The timer can also drive a pin. Each channel has a capture/compare register, CCRx, and the hardware compares it with CNT all the time. When the two are equal, or when the count crosses the value, the channel changes its output pin. This mode is called output compare. Setting the mode in the OCxM bits of CCMRx decides exactly how the pin reacts.

The most useful output compare mode is PWM, a square wave whose high time is a chosen fraction of each period. In PWM mode 1 the pin is active while CNT < CCR. The high time is CCR ticks, the period is ARR + 1 ticks, and the duty cycle is CCR ÷ (ARR + 1). For the LED in this lesson, ARR = 999 and CCR = 250 give a 1 kHz signal at 25 % duty. RM0008 Rev 21, section 15.3.9, PWM mode

The bit pattern for PWM mode 1 is OC1M = 110 (binary) (RM0008 Rev 21, section 15.4.7). The CMSIS header names the two bits TIM_CCMR1_OC1M_1 and TIM_CCMR1_OC1M_2, and the HAL names the whole mode TIM_OCMODE_PWM1, which is those two bits together (stm32f1xx_hal_tim.h). Writing the pattern with both names in one expression is clearer than writing a raw hex number.

A hobby servo expects a frame of about 20 ms, with a pulse of about 1 to 2 ms that sets its position. The centre position is near 1.5 ms. This is the usual convention for hobby servos, not a figure from this course's sources: check your servo's datasheet before you rely on the end points. With PSC = 7 and ARR = 19999 the frame is 20 000 microseconds, so the frequency is 50 Hz. With CCR = 1500 the high time is 1.5 ms.

Setting the preload bit (OC1PE) and the auto-reload preload bit (ARPE) makes a new ARR or CCR take effect at the next update event. Without them, a write during a period can give one short or long cycle. Always set the preload bits before you start the counter (RM0008 Rev 21, sections 15.3.1, 15.3.9 and 15.4.7).

Concept 4: input capture, timing the edges

The timer can also work the other way round. An input capture channel watches a pin, and when an edge arrives it copies the current value of CNT into the channel's CCRx register. The copy happens in hardware at the moment of the edge, so the value is accurate even if the CPU is busy elsewhere. The CPU reads the saved value later.

One capture gives the time of one edge. Two captures, one on the rising edge and one on the falling edge, give the width of the pulse between them, and the subtraction does the timing. The subtraction must use the counter's width. With a 16-bit counter, (uint16_t)(fall - rise) is correct even if the counter wrapped between the two edges, because the unsigned 16-bit result is taken modulo 65 536. Lesson 45 explains the modulo rule for unsigned types.

Channels 3 and 4 of a timer can both capture the same input, one at the rising edge and one at the falling edge. The solution uses this on TIM3, with CH3 on the rising edge and CH4 on the falling edge of the signal on PB0. The same timer's CH1 is already the servo output, so using CH1 for the input would conflict with the output.

Concept 5: encoder mode, counting rotation

A quadrature encoder has two outputs, A and B, that are 90 degrees out of phase. When the shaft turns one way, A changes before B. When it turns the other way, B changes before A. The order of the edges therefore gives the direction, and the number of edges gives the distance.

Encoder mode makes the counter do this work itself. The slave mode select bits SMS in SMCR set the mode. The HAL names the value TIM_ENCODERMODE_TI12, which is SMS = 011 (RM0008 Rev 21, section 15.3.12), and the HAL comment calls it "quadrature encoder mode 3, x4 mode, counts up/down on both TI1FP1 and TI2FP2 edges" (stm32f1xx_hal_tim.h). So mode 3 counts every edge of both signals, four counts for each full cycle. The CPU then reads only CNT, and it does not need to watch the pins.

The Wokwi wokwi-ky-040 part has pins CLK (A), DT (B), SW (push button) and the supply pins VCC and GND. Its docs say the module has 20 steps per revolution, and that each step produces a LOW signal on both DT and CLK. Clockwise, CLK goes low first; counter-clockwise, DT goes low first. The first pin to fall sets the direction. Wokwi part: KY-040 rotary encoder

If each of the 20 steps gives one full cycle, mode 3 counts four per step, which is 80 counts per revolution. The solution does not print a full revolution, so check the count with your own encoder before you rely on the figure.

Worked example 1: the 1 kHz LED, step by step

Start with the target: a 1 kHz PWM at 25 % duty, from an 8 MHz clock. The steps below are the arithmetic the solution uses, written out in full so you can repeat them for any other target.

  1. Choose the prescaler. We want a counter that ticks at a convenient rate. With PSC = 7 the tick is 8 000 000 ÷ 8 = 1 000 000 Hz, which is one tick per microsecond.
  2. Work out the period in ticks. A 1 kHz frequency has a period of 1 ms, which is 1000 microsecond ticks.
  3. Set the reload. The period is ARR + 1 ticks, so ARR = 1000 − 1 = 999. Check: 1 000 000 ÷ (999 + 1) = 1000 Hz.
  4. Set the duty. 25 % of 1000 ticks is 250 ticks, so CCR1 = 250. The output is high for 250 of the 1000 ticks.

The steps show why the plus-one rule matters. If you forgot it and wrote ARR = 1000, the period would be 1001 ticks and the frequency would be 999.0 Hz. A scope would show the error, and the LED would not. The duty would also drift, because 250 of 1001 is not exactly 25 %.

Worked example 2: the servo pulse, measured by capture

The servo signal is generated on TIM3 CH1 and fed back into TIM3 CH3 and CH4 through a wire from PA6 to PB0. The arithmetic is the same, with a longer period.

  1. The clock and the prescaler are as before: 1 MHz, one tick per microsecond.
  2. The frame is 20 ms, which is 20 000 ticks, so ARR = 19 999. The frequency is 1 000 000 ÷ 20 000 = 50 Hz.
  3. The pulse is 1500 ticks, so CCR1 = 1500. The high time is 1.5 ms.
  4. The capture sees the rising edge at some time, say CCR3 = 1000. The falling edge comes 1500 ticks later, so CCR4 = 2500.
  5. The width is 2500 − 1000 = 1500 µs. The answer agrees with the output, so the wiring and the registers are both right.

Consider what happens if the counter wraps during the pulse. Suppose the rising edge captures 65 000 and the falling edge captures 500, because the 16-bit counter went past 65 535 and started again at zero. The plain subtraction 500 − 65 000 is negative. The unsigned 16-bit form gives (uint16_t)(500 − 65 000), which is 1036, the correct width: 500 + (65 536 − 65 000) = 1036. The wrap cancels out, as long as the pulse is shorter than the counter's full range.

The code, line by line

The solution is in projects/0071-timers/solution/main.c. The three functions below set up the three uses of the timer. Each line is shown with its meaning, so you can match the code to the concepts above.

Setting a pin's mode. The port's configuration registers are CRL (pins 0 to 7) and CRH (pins 8 to 15). Each pin has a 4-bit field, made from a 2-bit CNF and a 2-bit MODE. The helper gpio_set_pin() picks the right register, clears the field with a mask, and writes the new value. The value 0xB means CNF=10 and MODE=11, which is an alternate-function push-pull output at 50 MHz. The timer drives the pin, so the pin must be in the alternate-function mode and not in the plain output mode. 

/* PA0 is TIM2 CH1: the LED output. */
RCC->APB1ENR |= RCC_APB1ENR_TIM2EN;
gpio_set_pin(GPIOA, 0U, CFG_AF_PUSHPULL_50);

TIM2->PSC = TIM_PSC;            /* divide 8 MHz by 8: 1 MHz tick */
TIM2->ARR = LED_PWM_ARR;       /* period = 1000 ticks: 1 kHz */
TIM2->CCMR1 = TIM_CCMR1_OC1M_1 | TIM_CCMR1_OC1M_2 | TIM_CCMR1_OC1PE;
TIM2->CCR1  = LED_DUTY_CCR;    /* high for 250 of 1000 ticks */
TIM2->CCER  = TIM_CCER_CC1E;   /* turn the channel 1 output on */
TIM2->CR1   = TIM_CR1_ARPE;    /* preload ARR at each update */
TIM2->EGR   = TIM_EGR_UG;      /* load PSC and ARR now */
TIM2->CR1  |= TIM_CR1_CEN;     /* start the counter */

Read the block from top to bottom. The first line turns on the clock to TIM2 in the RCC, because a peripheral with no clock does not respond to its register writes. The second line makes PA0 the alternate-function output, so the timer drives it. The next lines set the timing: PSC and ARR give the 1 kHz period. CCMR1 sets the channel 1 mode to PWM mode 1 with the preload bit, and CCR1 sets the high time. CCER turns the channel's output on. CR1 with ARPE makes the period register preloaded, so a later change takes effect at the next update event. EGR with UG forces an update now, which copies the prescaler and reload into the active registers (RM0008 Rev 21, sections 15.3.1 and 15.4.6). Without that line, the first period would use the reset values. The last line sets the counter enable bit and starts the timer. 

/* Input capture on TIM3: CH3 at the rising edge, CH4 at the falling edge of TI3. */
TIM3->CCMR2 = TIM_CCMR2_CC3S_0 | TIM_CCMR2_CC4S_1;
TIM3->CCER  = TIM_CCER_CC1E | TIM_CCER_CC3E | TIM_CCER_CC4E | TIM_CCER_CC4P;

static uint32_t capture_pulse_us(void) {
    uint16_t rise = (uint16_t)TIM3->CCR3;
    uint16_t fall = (uint16_t)TIM3->CCR4;
    return (uint16_t)(fall - rise);   /* wrap-safe, see worked example 2 */
}

CC3S_0 sets the channel 3 input to TI3, the direct input, so CH3 captures the edge on PB0. CC4S_1 sets the channel 4 input to TI3 as well, but from the other side: the value 10 in the field selects the signal from the other channel of the pair. The point is that both channels see the same pin. CC4P in CCER makes channel 4 capture on the falling edge, so CCR4 holds the fall time and CCR3 holds the rise time (RM0008 Rev 21, sections 15.4.8 and 15.4.9). The function reads both values as 16-bit numbers and subtracts them as 16-bit unsigned, as worked example 2 showed. 

/* Encoder mode on TIM4: CH1 is CLK on PB6, CH2 is DT on PB7. */
TIM4->CCMR1 = TIM_CCMR1_CC1S_0 | TIM_CCMR1_CC2S_0;
TIM4->SMCR  = TIM_SMCR_SMS_0 | TIM_SMCR_SMS_1;   /* SMS = 011: encoder mode 3 */
TIM4->ARR   = 0xFFFFU;                         /* full 16-bit range */
TIM4->CR1   = TIM_CR1_CEN;

static int32_t encoder_count(void) {
    return (int16_t)TIM4->CNT;     /* signed, so a backward turn reads -1 */
}

CC1S_0 and CC2S_0 map channels 1 and 2 to their own input pins, TI1 and TI2 (RM0008 Rev 21, section 15.4.7). The SMS field is set to three, which is SMS_0 and SMS_1 together, and that selects encoder mode 3 as the HAL comment describes. The reload is set to the full 16 bits, so the count wraps at 65 536 rather than at a small number that would clip a long run. The read function casts the 16-bit CNT to int16_t. A backward turn takes the count from 0 to 65 535 when read unsigned, and the signed cast makes that −1, which is what a person expects.

Common mistakes and how to spot them

The first mistake is the plus-one rule. The frequency is close to the target, but not equal to it. The symptom on a scope is a period of 1001 µs for a 1 kHz target, or the servo jitters because its frame is 20.001 ms. The fix is the formula: write ARR = (f_clk ÷ ((PSC + 1) × f)) − 1, and check the answer by recomputing the frequency from it.

The second mistake is forgetting the update event after you change the prescaler or the reload. The register you wrote is the preload buffer, and the first period still uses the old value. The symptom is a first cycle that is too long or too short, and then the correct timing. The fix is the EGR write with UG, as the solution does, right after the timer setup and before CEN.

The third mistake is using the wrong channel for the capture. A pin driven by an output channel cannot also be read as an input on the same channel. In this lesson, CH1 on TIM3 is the servo output, so the capture uses CH3 and CH4. The symptom of a bad choice is a capture register that stays at zero, or a reading that does not change when the pulse changes. The fix is to check the channel and the pin in the datasheet table, and to confirm that the output channel is not the one you are reading.

The fourth mistake is subtracting the captures in the wrong type. If you write int32_t width = fall − rise with 16-bit values, a wrap gives a negative number. The symptom is a pulse width that looks like −64 500 µs, or a huge positive number after the sign is lost. The fix is the 16-bit unsigned form, as in capture_pulse_us().

The fifth mistake is reading the encoder count as unsigned. Turning the knob backwards makes CNT go from 0 to 65 535, so a plain read shows a large number that appears to jump. The symptom is a count that jumps to about 65 000 when you turn the knob the other way. The fix is the signed cast, (int16_t)TIM4->CNT, which turns the same bit pattern into −1.

In real projects

In a product, the timer is often the first peripheral a team configures after the clock. PWM sets the brightness of an LED and the speed of a motor through a driver, and it is the usual way a microcontroller controls the average power in a heater. Input capture measures the period of a sensor pulse, such as a radio-control receiver or a tachometer. Encoder mode reads a rotary control, such as a knob, a jog wheel or a motor shaft. Each use depends on the same arithmetic you did above.

A senior engineer reviewing timer code looks for three things. The prescaler and the reload should be named constants, with a comment on the resulting frequency, so that a change to the clock is visible. Every write to a preloaded register should be followed by a reason, usually the update event. Counter reads should use the width of the counter, and the code should say so.

Summary

  • A timer is a counter that the hardware advances. The CPU sets the registers once and reads the result later.
  • The counter ticks at f_clk ÷ (PSC + 1), and the period is ARR + 1 ticks. Both terms carry a plus one.
  • PWM mode 1 (OC1M = 110) is high while CNT < CCR. The duty is CCR ÷ (ARR + 1).
  • Input capture copies CNT into a CCRx register at the edge. The difference of two captures is the width, computed in the counter's unsigned width.
  • Encoder mode 3 (SMS = 011) counts every edge of both channels, so the CPU reads only CNT.
  • Write the update event (EGR UG) after you change the preloaded registers, so the first period uses the new values.
