PIO and DMA

Some timing is too tight for the CPU, even at 125 MHz. The RP2040 has programmable I/O state machines that run a few instructions per bit, and a DMA engine that keeps them fed. Together they move data without the core in the loop.

Optional. You do not need this lesson for Lab 3 or the capstone. Read it when you meet a protocol with exact timing, such as an LED strip, a custom serial format or a fast parallel bus.
By the end of this lesson you can name the nine PIO instructions, decode a 16-bit PIO instruction, and explain how a DMA channel is paced by a PIO data request (DREQ).

Where we are and why it matters

Lesson 64 put a second core on the chip and showed how the two cores share data safely. Before that, lesson 55 showed that a super-loop must never wait, and lesson 57 showed that an interrupt arrives when it likes, so the CPU's timing has a little jitter. For most work, a little jitter does not matter. For some protocols it does. Many LED strips, for example, read each bit from the length of one pulse, so a pulse that is too long is read as a different bit.

The usual answers are to bit-bang the pin in a tight loop with interrupts off, or to use a peripheral. Bit-banging ties up the CPU for the whole transfer, and the code must stay in step with the clock. A peripheral such as a UART or SPI block is fixed in its function, so it cannot do a protocol it was not built for. The RP2040's PIO is the middle path: a small programmable engine that does exactly one job per instruction, with no interrupts to be late, and a DMA channel that moves the data while the CPU does other work.

The clock and the cycle

A clock cycle is one tick of the chip's clock. The Pico SDK runs the system clock at 125 MHz by default, which is the value of SYS_CLK_HZ in the SDK's RP2040 platform definitions (RP2040 datasheet, section 2.15, Clocks). One cycle is therefore 1 ÷ 125,000,000 seconds, which is 8 ns. A CPU instruction takes one or more cycles, so the CPU can change a pin only at discrete times, and any interrupt that arrives between two of its instructions moves the next change later.

A PIO state machine works on the same clock, but its instructions are simple and its program is fixed. The datasheet says that every PIO instruction executes in one clock cycle (RP2040 datasheet, section 3.4.1). So the time between two pin changes is the sum of the cycles in the program between them, and nothing else can add to it. That determinism is the reason PIO exists.

The idea: what a state machine is

The RP2040 has two PIO blocks, and each has four state machines. Every state machine is a very small processor. It has a program counter, two 32-bit shift registers, two 32-bit scratch registers, FIFOs that connect it to the CPU and the DMA, and a clock divider. It runs a short program from an instruction memory that the four state machines of one block share. It shifts data in and out of GPIO pins. It does not take interrupts, but it can set IRQ flags that the CPU can see (RP2040 datasheet, section 3.1).

It has no data memory of its own. The two scratch registers are its only general storage, and the shift registers hold the bits in transit. A PIO state machine is therefore closer to a sequencer than to a CPU: it is built to move bits between a FIFO and a pin, on a clock you choose, and to wait at the right moments. The instruction memory holds 32 instructions per block, and each instruction is 16 bits wide (RP2040 datasheet, sections 3.1 and 3.4.1).

The FIFO is a first-in, first-out buffer. Each state machine has four 32-bit words of buffer in each direction, the TX FIFO for data going out from the CPU or DMA and the RX FIFO for data coming in. The TX FIFO is the one this lesson uses.

The nine instructions

The instruction set has nine instructions, and each one is 16 bits. The top three bits select the instruction. The remaining bits hold the operands: the destination, the bit count, the condition and so on. The table is the datasheet's encoding table, Table 366 in section 3.4.1.

Bits 15:13InstructionWhat it does
000JMPJump, optionally on a condition
001WAITStall until a pin or flag has a value
010INShift bits from pins into the input shift register
011OUTShift bits out of the output shift register to a destination
100PUSH / PULLMove a word between a FIFO and a shift register
101MOVCopy a value between registers, with an optional operation
110IRQSet or clear an interrupt flag
111SETWrite a 5-bit constant to pins, pin directions or scratch registers

Every instruction also has a 5-bit delay field, at bits 12 to 8 in this layout. The field counts idle cycles that the state machine spends after the instruction before it moves on. With the maximum value of 31, one instruction holds its pins for 32 cycles in total: one cycle for the instruction and 31 idle cycles. This is how a fast clock makes a slow pattern. The datasheet calls this the delay, and says that the field can also hold side-set bits when the program asks for them, which this lesson does not use (RP2040 datasheet, section 3.4.1).

Decode one instruction, bit by bit

Here is the program in this lesson's project. It has two instructions, and you can decode both with only the table above: 

0x80A0   1000 0000 1010 0000   PULL, no delay, block until the TX FIFO has a word
0x7F04   0111 1111 0000 0100   OUT PINS, 4 [31]: shift 4 bits to the pins, then wait 31 cycles

Start with 0x80A0. Write it in binary, four bits per hex digit: 1000 0000 1010 0000. The top three bits, 100, select PULL. Bit 7 is fixed at 1 for PULL, which is how the decoder tells PULL from PUSH. Bit 6 is the IfEmpty flag, which is 0 here, so the pull happens whether or not the output shift register is empty. Bit 5 is the Block flag, which is 1 here. Blocking means the state machine stalls until the FIFO has a word. The delay field, bits 12 to 8, is 00000, so the PULL has no delay. The remaining bits are zero.

Now 0x7F04, which is 0111 1111 0000 0100. The top bits, 011, select OUT. The delay field, bits 12 to 8, is 11111, which is 31. Bits 7 to 5 are the destination: 000 means PINS. Bits 4 to 0 are the bit count, 00100, which is 4. So this instruction shifts 4 bits out of the output shift register onto the pins, then idles for 31 cycles. A bit count of 1 to 31 is written as is, and a count of 32 is written as 00000. The destination codes are in section 3.4.5 of the datasheet.

The bit count and the shift direction decide which four bits go out. The project configures the shift to the right, so OUT takes the least significant bits of the 32-bit word first, and pin GP10 gets bit 0. Take the value 4, which is 0100 in the low four bits. Bit 2 is the only one set, so OUT drives GP12 high and the other three pins low. That is the third LED in the pattern.

Worked example: how long is one step?

The project's program has two instructions in a loop. The .wrap_target and .wrap directives mark the start and end of the loop. The last instruction jumps back to the first, and the datasheet says that this wrap is a free, zero-cycle jump, where a plain JMP would cost one cycle (RP2040 datasheet, section 3.5.2). So a step is the cycles of the two instructions and nothing more.

  1. The PULL takes 1 cycle when the FIFO has a word. Its delay is 0.
  2. The OUT takes 1 cycle, plus its delay of 31 idle cycles, so 32 cycles in total.
  3. One pass through the loop is therefore 1 + 32 = 33 cycles. The pins hold the pattern for those 33 cycles, from one OUT to the next.
  4. The PIO clock is the system clock divided by the clock divider. The divider is 60000 with no fraction: 125,000,000 ÷ 60000 ≈ 2083 Hz. One PIO cycle is therefore 1 ÷ 2083 ≈ 0.48 ms.
  5. One step is 33 × 0.48 ms = 15.84 ms. Six steps take about 95 ms.

The divider formula is in the register description: the frequency is the clock divided by (CLKDIV_INT + CLKDIV_FRAC ÷ 256), and the divisor can be from 1 to 65536 (RP2040 datasheet, section 3.5.5 and the SM0_CLKDIV register). The fraction exists so that a PIO program can match a rate that is not a whole number of cycles. This project does not need it.

The comment in the solution's main.c says one step is 32 PIO cycles, about 15 ms. It counts the OUT but forgets the PULL. The arithmetic above gives 33 cycles, 15.84 ms. The lesson uses the arithmetic, and the difference is the cycle that you would miss if you timed the pattern by eye.

How pioasm fits in

In a normal Pico SDK project you do not type the words by hand. You write a .pio file with labels, like this, and the build runs pioasm, the PIO assembler. It produces a header with a pio_program_t that your C code links to: 

.program pattern
.wrap_target
    pull block          ; wait for a word from DMA
    out pins, 4 [31]    ; show its low four bits for 32 cycles
.wrap

The .program directive starts a program and names it. .wrap_target and .wrap are essentially labels: they mark the first and last instructions of the loop, and pioasm exports them as constants that the SDK uses to set the hardware wrap. The square brackets, as in [31], give the delay. Each line after the semicolon is a comment for the reader (RP2040 datasheet, section 3.3.1).

The project does exactly that: pattern.pio sits next to main.c, and one line in CMakeLists.txt, pico_generate_pio_header(blink ${CMAKE_CURRENT_LIST_DIR}/pattern.pio), makes the build run pioasm and write build/pattern.pio.h. The first build of a PIO project takes longer, because the SDK compiles pioasm itself with the host compiler. That is MinGW gcc, the host compiler that lesson 1 introduced.

main.c still holds the two words decoded by hand from the datasheet, in hand_decoded_words. At startup the program compares them with pioasm's output and prints PIO WORDS MATCH. Open build/pattern.pio.h after a build and check the words yourself: pioasm writes 0x80a0 and 0x7f04, with the disassembly as comments.

Decoding a few words by hand, once, is how you learn to read the encoding table. In real work you always let pioasm do it, and read its header when you need to check.

DMA: a channel that paces itself

A DMA (direct memory access) channel copies data from one address to another without the CPU. The CPU sets up the source, the destination, the number of transfers and the size of each transfer, and then starts the channel. The channel does the copying, one transfer at a time, while the CPU runs other code. Each transfer is one read and one write on the bus.

The question is when to copy. If the DMA copied as fast as the bus allowed, it would overrun a peripheral that is slower than the bus. So a peripheral that can use DMA raises a data request (DREQ) when it can accept or supply one word. The DMA channel waits for that request, so the peripheral sets the pace. The DREQ for PIO0 state machine 0's TX FIFO is DREQ_PIO0_TX0, which is number 0 in the global DREQ table (RP2040 datasheet, section 2.5.3.1, Table 119).

The RP2040's DMA uses a credit scheme. Each DREQ pulse adds one credit to the channel, and the DMA issues a transfer when it has a credit. The datasheet says this keeps as many transfers in flight as the peripheral has room for, so an 8-deep FIFO can take one word per clock without overflow or underflow (RP2040 datasheet, section 2.5.3.2). In practice the TX FIFO of this state machine has four words of room, and the DMA fills it, then waits until the PIO pulls a word out. 

/* DMA: write one word to the PIO TX FIFO each time the FIFO asks for one */
channel_config_set_transfer_data_size(&dc, DMA_SIZE_32);
channel_config_set_read_increment(&dc, true);     /* walk through steps[] */
channel_config_set_write_increment(&dc, false);   /* always the same FIFO register */
channel_config_set_dreq(&dc, pio_get_dreq(PIO0, 0, true));

Line by line. channel_config_set_transfer_data_size(&dc, DMA_SIZE_32) makes each transfer 32 bits wide, which matches the width of the FIFO word. channel_config_set_read_increment(&dc, true) moves the source address forward by one word after each transfer, so the DMA walks through the steps[] array. channel_config_set_write_increment(&dc, false) keeps the destination fixed at the same FIFO register, so every word goes to the same place. channel_config_set_dreq(&dc, pio_get_dreq(PIO0, 0, true)) is the pacing. pio_get_dreq(pio, sm, is_tx) returns the DREQ number for a state machine's FIFO. The last argument is true for the TX FIFO, which the DMA writes. The SDK's dma_channel_configure then applies the whole configuration to the channel, and the DMA waits on the DREQ for each word.

The project's steps[] array holds six patterns: 1, 2, 4, 8, 4, 2. Each is a 32-bit word whose low four bits are the LED pattern. The pattern runs back and forth across four LEDs on GP10 to GP13.

In real projects

The datasheet lists what PIO is used for: parallel buses such as the 8080 and 6800 families, I2C, I2S, SDIO, SPI and QSPI, UART, and DPI or VGA video output through a resistor network (RP2040 datasheet, section 3.1). Real products use it for custom interfaces that no fixed peripheral covers, and for a second UART or SPI when the main ones are busy. A typical design gives a PIO program a clear job, feeds it from DMA, and keeps the CPU free for the rest of the firmware.

A senior engineer expects three things from a PIO change. The first is a comment on every instruction in the .pio file that says what it does and how many cycles it takes, because the timing lives in those comments. The second is a check of the generated header against a hand decode, as this project does, so a later edit cannot silently change the words. The third is a measurement on real hardware with a logic analyzer, since the cycle count is only a model until a probe confirms it. The glossary's logic analyzer entry explains what to look for.

Common mistakes and how to spot them

Each mistake below has a symptom you can see on the serial monitor or on the LEDs, and a fix.

  1. Asking for the RX DREQ on a transmit FIFO. Writing pio_get_dreq(PIO0, 0, false) makes the DMA wait for a word in the RX FIFO. This program never pushes one, so the request never arrives. Symptom: the serial monitor prints PIO DMA OK, but the LEDs never move and the restart loop never runs. Fix: pass true, because the DMA writes to the TX FIFO.
  2. Enabling the state machine after the DMA has run. The DMA fills the four TX FIFO words and then stops, waiting for the state machine to pull. With the state machine disabled, nothing is pulled. Symptom: the LEDs stay off, and the DMA appears stuck after the first few words. Fix: call pio_sm_set_enabled(PATTERN_PIO, PATTERN_SM, true) before the DMA starts, as the solution does.
  3. Setting the clock divider for a faster state machine. A divider of 1 runs the PIO at the full 125 MHz. One step then takes 33 cycles of 8 ns, which is about 0.26 µs. Symptom: the four LEDs look dim and steady rather than stepping. Fix: keep the divider that gives the rate you need, and check the arithmetic in the worked example before you change it.
  4. Mixing up the bit order. If the shift is set to the left, OUT takes the most significant bits of the word first. Your steps[] values then show the wrong LEDs. Symptom: the pattern steps in the right order, but the wrong LED lights, or two LEDs light together. Fix: check sm_config_set_out_shift(&c, true, false, 32). The first argument, true, selects right shift, which is what the solution uses.

Summary

  • A PIO state machine is a small sequencer with two shift registers, two scratch registers, FIFOs and a clock divider. Each instruction takes one PIO cycle, plus its delay.
  • Each PIO instruction is 16 bits. The top three bits select the instruction, and the table in section 3.4.1 gives the rest.
  • PULL moves a word from the TX FIFO to the output shift register. OUT shifts bits from there to a destination such as the pins.
  • The clock divider sets the PIO clock: the system clock divided by the integer and fractional divisor.
  • A step's length is the sum of the cycles in the loop, and a wrap costs no cycle. In this project, 33 cycles, about 15.84 ms.
  • A DMA channel copies words into the TX FIFO, and waits for the DREQ that the PIO raises when the FIFO has room.
  • Common mistakes: the wrong DREQ direction, an unenabled state machine, a wrong clock divider and a reversed shift direction.
