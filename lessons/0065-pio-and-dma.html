PIO and DMA

Some timing is too tight for the CPU, even at 125 MHz. The RP2040 has programmable I/O state machines that run a few instructions per bit, and a DMA engine that keeps them fed. Together they move data without the core in the loop.

Optional (⭐). You do not need this lesson for Lab 3 or the capstone. Read it when you meet a protocol with exact timing, such as an LED strip, a custom serial format or a fast parallel bus.
By the end of this lesson you can name the nine PIO instructions, decode a 16-bit PIO instruction, and explain how a DMA channel is paced by a PIO data request (DREQ).

The idea

The RP2040 has two PIO blocks, and each has four state machines. A PIO state machine is a very small processor: it runs a short program from its own instruction memory, shifts data in and out of pins, and does one instruction per clock cycle, with no interrupts and no cache. It is built for precise timing, not for general work (RP2040 datasheet, section 3.1). A PIO state machine is the same idea as a CPU with a tiny instruction set, but it has no data memory and no call stack. Its job is to take bits from a FIFO and put them on pins, on a clock you choose.

The instruction set has nine instructions, and each one is 16 bits. The top three bits select the instruction:

Bits 15:13InstructionWhat it does
000JMPJump, optionally on a condition
001WAITStall until a pin or flag has a value
010INShift bits from pins into the input shift register
011OUTShift bits out of the output shift register to a destination
100PUSH / PULLMove a word between a FIFO and a shift register
101MOVCopy a value between registers, with an optional operation
110IRQSet or clear an interrupt flag
111SETWrite a 5-bit constant to pins, pin directions or scratch registers

The table is from the datasheet's encoding table, which is Table 366 in section 3.4.1. Every instruction also has a 5-bit delay field, so one instruction can hold its pins for up to 31 extra cycles. That is how this course's program makes a slow pattern out of a fast clock.

Decode one instruction

Here is the program in this lesson's project. It has two instructions: 

0x80A0   1000 0000 1010 0000   PULL, no delay, block until the TX FIFO has a word
0x7F04   0111 1111 0000 0100   OUT PINS, 4 [31]: shift 4 bits to the pins, then wait 31 cycles

In 0x80A0, the top three bits 100 select PULL. Bit 7 is fixed at 1 for PULL, bit 6 selects "if empty" (0 here), and bit 5 selects "block" (1 here). Blocking means the state machine stalls until the FIFO has a word. In 0x7F04, the top bits 011 select OUT, the delay field 11111 is 31, the destination 000 is PINS, and the bit count 00100 is 4. Bit counts of 1 to 32 are written as is, except that 32 is written as 00000. The destination codes are in section 3.4.5 of the datasheet.

How pioasm normally fits in

In a normal Pico SDK project you do not type the words by hand. You write a .pio file with labels, like this, and the build runs pioasm, which generates a header with a pio_program_t that you link to: 

.program pattern
.wrap_target
    pull block          ; wait for a word from DMA
    out pins, 4 [31]    ; show its low four bits for 32 cycles
.wrap

The project does exactly that: pattern.pio sits next to main.c, and one line in CMakeLists.txt, pico_generate_pio_header(blink ${CMAKE_CURRENT_LIST_DIR}/pattern.pio), makes the build run pioasm and write build/pattern.pio.h. The first build of a PIO project takes longer, because the SDK compiles pioasm itself with the host compiler (MinGW gcc, installed in lesson 1's tool check).

main.c still holds the two words decoded by hand from the datasheet, in hand_decoded_words. At startup the program compares them with pioasm's output and prints PIO WORDS MATCH. Open build/pattern.pio.h after a build and check the words yourself: pioasm writes 0x80a0 and 0x7f04, with the disassembly as comments.

Decoding a few words by hand, once, is how you learn to read the encoding table. In real work you always let pioasm do it, and read its header when you need to check.

DMA paced by PIO

A DMA channel copies data from memory to a peripheral without the CPU. The question is when to copy. Each peripheral that can use DMA raises a data request, called a DREQ, when it can take or give one word. The DMA channel waits for that request, so the peripheral sets the pace. The DREQ for PIO0 state machine 0's TX FIFO is DREQ_PIO0_TX0, with the number 0 in the global DREQ table (RP2040 datasheet, section 2.5.3, Table 119). The pacing is the point. The CPU never checks whether the FIFO has room. The DREQ tells the DMA when to move the next word, and the PIO's pull block tells the state machine when to proceed.

This project does three things. The PIO program pulls one word, shows its low four bits on four pins for 32 PIO cycles, and then pulls the next word. A DMA channel walks through an array of six patterns, one word at a time, paced by the DREQ. The CPU starts the DMA and restarts it when it finishes. 

/* DMA: write one word to the PIO TX FIFO each time the FIFO asks for one */
channel_config_set_transfer_data_size(&dc, DMA_SIZE_32);
channel_config_set_read_increment(&dc, true);     /* walk through steps[] */
channel_config_set_write_increment(&dc, false);   /* always the same FIFO register */
channel_config_set_dreq(&dc, pio_get_dreq(PIO0, 0, true));

Try it in Wokwi

Wokwi simulates PIO and can show its state machines in the PIO debugger, and it supports DMA only in combination with PIO, which this project uses. The four LEDs on GP10 to GP13 form a pattern that runs back and forth.

  1. Open projects/0065-pio-and-dma/starter in VS Code (File → Open Folder).
  2. Build: Ctrl+Shift+B.
  3. Start the simulator: F1 → Wokwi: Start Simulator. The serial monitor prints PIO ready, DMA not set up and the LEDs stay off.
  4. Your task: replace the TODO(learner) comment with the DMA setup. Claim a channel, configure it to move 32-bit words from steps[] to the PIO TX FIFO, set the DREQ, enable the state machine, and restart the DMA in a loop when it finishes.
  5. You will know it works when the serial monitor prints PIO DMA OK steps=6 and the four LEDs step through the pattern about every 15 ms.
Hint for the DREQ

Use pio_get_dreq(PATTERN_PIO, PATTERN_SM, true). The last argument is true because the DMA writes to the TX FIFO. The state machine must be enabled before the first word matters.

Hint for the restart

The SDK has dma_channel_wait_for_finish_blocking() and dma_channel_transfer_from_buffer_now(). Call the first, then the second, inside the while loop.

"You need to drive an LED strip with an exact bit timing while the CPU runs an RTOS. How do you do it, and what do you do with the CPU?" Answer out loud in 60 seconds, then compare.

Model answer

Use a PIO state machine. Its program produces the bit timing in cycles, with no interrupts to be late, and a DMA channel paced by the state machine's DREQ feeds it the pixel data from a buffer. The CPU only prepares the buffer and starts the transfer, so the RTOS tasks are not in the timing path. The trade-off is that the PIO program is hard to change and has limited memory, so it suits a fixed protocol. Check the timing against the datasheet and the LED strip's own timing table.

RP2040 datasheet, section 3.4 (Instruction Set, Table 366) and section 2.5.3 (DMA data request): read the encoding table, then the PULL and OUT pages, then the DREQ table. The Pico SDK book has a PIO chapter with worked examples: Raspberry Pi Pico C/C++ SDK.
