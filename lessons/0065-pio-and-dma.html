PIO and DMA

Programmable I/O state machines fed by DMA

Optional. You do not need this lesson for Lab 3 or the capstone. Read it when you meet a protocol with exact timing, such as an LED strip, a custom serial format or a fast parallel bus.
By the end of this lesson you can name the nine PIO instructions, decode a 16-bit PIO instruction, and explain how a DMA channel is paced by a PIO data request (DREQ).

Timing too tight for the CPU

Lesson 64 put a second core to work and showed how the two cores share data safely, while earlier, lesson 55 showed that a super-loop must never wait and lesson 57 that an interrupt arrives when it likes, giving the CPU's timing a little jitter. For most work that jitter does not matter, but for some protocols it does, many LED strips reading each bit from the length of one pulse, so that a pulse that runs too long is read as a different bit.

The usual answers are to bit-bang the pin in a tight loop with interrupts off or to use a peripheral. Bit-banging ties up the CPU for the whole transfer and keeps the code in step with the clock, while a peripheral such as a UART or SPI block has a fixed function and cannot run a protocol it was not built for. The RP2040's PIO is the middle path, a small programmable engine that does exactly one job per instruction with no interrupts to make it late, together with a DMA channel that moves the data while the CPU does other work.

Clock cycles and deterministic timing

A clock cycle is one tick of the chip's clock, and the Pico SDK runs the system clock at 125 MHz by default, the value of SYS_CLK_HZ in the SDK's RP2040 platform definitions (RP2040 datasheet, section 2.15, Clocks), so one cycle lasts 1 ÷ 125 000 000 s, or 8 ns. A CPU instruction takes one or more cycles, so the CPU can change a pin only at discrete times, and any interrupt arriving between two of its instructions delays the next change.

A PIO state machine runs on the same clock, but its instructions are simple and its program is fixed, the datasheet stating that every PIO instruction executes in one clock cycle (RP2040 datasheet, section 3.4.1). The time between two pin changes is therefore the sum of the cycles in the program between them and nothing else can add to it, and that determinism is the reason PIO exists.

The PIO state machine

The RP2040 has two PIO blocks with four state machines each, every state machine being a very small processor with a program counter, two 32-bit shift registers, two 32-bit scratch registers, FIFOs connecting it to the CPU and the DMA, and a clock divider. It runs a short program from an instruction memory shared by the four state machines of its block and shifts data in and out of GPIO pins, and although it takes no interrupts, it can set IRQ flags that the CPU sees (RP2040 datasheet, section 3.1).

A PIO state machine resembles a tiny assistant with a to-do list of at most 32 lines taped to the wall, who does nothing but work through it one line per clock cycle, changing and reading pins at exactly the moments the list says. The CPU hands it data and walks away, so the timing no longer depends on what the CPU is doing. An assistant could improvise when something unexpected happened, however, whereas the state machine can only follow its list, so every case it must handle has to be written into the program.

It has no data memory of its own, the two scratch registers being its only general storage and the shift registers holding the bits in transit, so a PIO state machine is closer to a sequencer than to a CPU, built to move bits between a FIFO and a pin on a chosen clock and to wait at the right moments. The instruction memory holds 32 instructions per block, each 16 bits wide (RP2040 datasheet, sections 3.1 and 3.4.1).

The FIFO is a first-in, first-out buffer, each state machine having four 32-bit words of it in each direction, the TX FIFO for data going out from the CPU or DMA and the RX FIFO for data coming in, and this lesson uses the TX FIFO.

The nine PIO instructions

The instruction set has nine instructions of 16 bits each, the top three bits selecting the instruction and the remaining bits holding the operands, such as the destination, the bit count and the condition. The table follows the datasheet's encoding table, Table 366 in section 3.4.1.

Bits 15:13InstructionWhat it does
000JMPJump, optionally on a condition
001WAITStall until a pin or flag has a value
010INShift bits from pins into the input shift register
011OUTShift bits out of the output shift register to a destination
100PUSH / PULLMove a word between a FIFO and a shift register
101MOVCopy a value between registers, with an optional operation
110IRQSet or clear an interrupt flag
111SETWrite a 5-bit constant to pins, pin directions or scratch registers

Every instruction also has a 5-bit delay field, at bits 12 to 8 in this layout, counting the idle cycles the state machine spends after the instruction before moving on, so with the maximum value of 31 one instruction holds its pins for 32 cycles in total, one for the instruction and 31 idle. This is how a fast clock makes a slow pattern, and the datasheet adds that the field can also hold side-set bits when a program asks for them, which this lesson does not use (RP2040 datasheet, section 3.4.1).

Decoding a PIO instruction bit by bit

The project's program has two instructions, both of which can be decoded with the table above alone. Before reading the decode, find the top three bits of each word and name the instruction they select. 

0x80A0   1000 0000 1010 0000   PULL, no delay, block until the TX FIFO has a word
0x7F04   0111 1111 0000 0100   OUT PINS, 4 [31]: shift 4 bits to the pins, then wait 31 cycles

0x80A0 in binary, four bits per hex digit, is 1000 0000 1010 0000, whose top three bits, 100, select PULL. Bit 7 is fixed at 1 for PULL, which is how the decoder tells PULL from PUSH, bit 6 is the IfEmpty flag, 0 here, so the pull happens whether or not the output shift register is empty, and bit 5 is the Block flag, 1 here, so the state machine stalls until the FIFO has a word. The delay field, bits 12 to 8, is 00000, so the PULL has no delay, and the remaining bits are zero.

0x7F04 is 0111 1111 0000 0100, whose top bits, 011, select OUT, with the delay field at bits 12 to 8 reading 11111, or 31, the destination at bits 7 to 5 reading 000, which means PINS, and the bit count at bits 4 to 0 reading 00100, or 4. The instruction therefore shifts 4 bits from the output shift register onto the pins and then idles for 31 cycles. A bit count of 1 to 31 is written as is, and a count of 32 is written as 00000. The destination codes are in section 3.4.5 of the datasheet.

The bit count and the shift direction decide which four bits go out. The project shifts to the right, so OUT takes the least significant bits of the 32-bit word first and pin GP10 receives bit 0, and for the value 4, 0100 in the low four bits, only bit 2 is set, so OUT drives GP12 high and the other three pins low, lighting the third LED of the pattern.

Worked example: the length of one step

The project's two instructions run in a loop whose start and end the .wrap_target and .wrap directives mark, the last instruction jumping back to the first through a wrap, which the datasheet describes as a free, zero-cycle jump, whereas a plain JMP would cost one cycle (RP2040 datasheet, section 3.5.2). A step thus consists of the cycles of the two instructions and nothing more, so before working through it, predict how many cycles one pass takes.

  1. Count the PULL. It takes 1 cycle when the FIFO has a word, with a delay of 0.
  2. Count the OUT. It takes 1 cycle plus its delay of 31 idle cycles, 32 cycles in total.
  3. Add the loop. One pass is 1 + 32 = 33 cycles, the pins holding the pattern for those 33 cycles from one OUT to the next.
  4. Find the PIO clock. With a divider of 60 000 and no fraction, the PIO runs at 125 000 000 ÷ 60 000 ≈ 2 083 Hz, so one PIO cycle lasts 1 ÷ 2 083 ≈ 0.48 ms.
  5. Find the step. One step lasts 33 × 0.48 ms = 15.84 ms, and six steps take about 95 ms.

The divider formula is in the register description, the PIO clock being

fPIO = fsys ÷ (CLKDIV_INT + CLKDIV_FRAC ÷ 256)(1)

where fsys is the system clock and the divisor can range from 1 to 65 536 (RP2040 datasheet, section 3.5.5 and the SM0_CLKDIV register). The fraction lets a PIO program match a rate that is not a whole number of cycles, which this project does not need.

The comment in the solution's main.c says one step is 32 PIO cycles, about 15 ms. It counts the OUT but forgets the PULL. The arithmetic above gives 33 cycles, 15.84 ms. The lesson uses the arithmetic, and the difference is the cycle that you would miss if you timed the pattern by eye.

The pioasm assembler in the build

In a normal Pico SDK project the words are not typed by hand. A .pio file with labels, like the one below, is assembled during the build by pioasm, the PIO assembler, which produces a header holding a pio_program_t that the C code links to. 

.program pattern
.wrap_target
    pull block          ; wait for a word from DMA
    out pins, 4 [31]    ; show its low four bits for 32 cycles
.wrap

The .program directive starts and names a program, while .wrap_target and .wrap are essentially labels marking the first and last instructions of the loop, which pioasm exports as constants that the SDK uses to set the hardware wrap. Square brackets, as in [31], give the delay, and the text after each semicolon is a comment for the reader (RP2040 datasheet, section 3.3.1).

The project does exactly that, pattern.pio sitting next to main.c and one line in CMakeLists.txt, pico_generate_pio_header(blink ${CMAKE_CURRENT_LIST_DIR}/pattern.pio), making the build run pioasm and write build/pattern.pio.h. The first build of a PIO project takes longer, because the SDK compiles pioasm itself with the host compiler, the MinGW gcc that lesson 1 introduced.

main.c still holds the two words decoded by hand from the datasheet in hand_decoded_words, and at startup the program compares them with pioasm's output and prints PIO WORDS MATCH. After a build, open build/pattern.pio.h and check the words yourself, pioasm writing 0x80a0 and 0x7f04 with the disassembly as comments.

Decoding a few words by hand, once, is how you learn to read the encoding table. In real work you always let pioasm do it, and read its header when you need to check.

DMA channels paced by a data request

A DMA (direct memory access) channel copies data from one address to another without the CPU, which sets up the source, the destination, the number of transfers and the size of each and then starts the channel. The channel does the copying one transfer at a time, each transfer being one read and one write on the bus, while the CPU runs other code.

A DMA channel acts as a courier, told where to pick up, where to deliver, how many parcels to carry and whom to wait for between parcels, the DREQ signal, after which it works alone while the CPU does something else and rings the bell, an interrupt, when the last parcel is delivered. A courier can decide that a parcel looks damaged, though, whereas the channel copies whatever bits it finds without checking them.

The question is when to copy, because a DMA copying as fast as the bus allowed would overrun a peripheral slower than the bus. A peripheral that can use DMA therefore raises a data request (DREQ) when it can accept or supply one word, and the DMA channel waits for that request, so the peripheral sets the pace. The DREQ for the TX FIFO of PIO0 state machine 0 is DREQ_PIO0_TX0, number 0 in the global DREQ table (RP2040 datasheet, section 2.5.3.1, Table 119).

The RP2040's DMA uses a credit scheme in which each DREQ pulse adds one credit to the channel and the DMA issues a transfer whenever it holds a credit. According to the datasheet, this keeps as many transfers in flight as the peripheral has room for, so an 8-deep FIFO can take one word per clock without overflow or underflow (RP2040 datasheet, section 2.5.3.2). In practice the TX FIFO of this state machine has four words of room, which the DMA fills before waiting until the PIO pulls a word out. 

/* DMA: write one word to the PIO TX FIFO each time the FIFO asks for one */
channel_config_set_transfer_data_size(&dc, DMA_SIZE_32);
channel_config_set_read_increment(&dc, true);     /* walk through steps[] */
channel_config_set_write_increment(&dc, false);   /* always the same FIFO register */
channel_config_set_dreq(&dc, pio_get_dreq(PIO0, 0, true));

channel_config_set_transfer_data_size(&dc, DMA_SIZE_32) makes each transfer 32 bits wide, matching the FIFO word, and channel_config_set_read_increment(&dc, true) advances the source address by one word after each transfer, so the DMA walks through the steps[] array, while channel_config_set_write_increment(&dc, false) keeps the destination fixed at the FIFO register, so every word goes to the same place. channel_config_set_dreq(&dc, pio_get_dreq(PIO0, 0, true)) sets the pacing, pio_get_dreq(pio, sm, is_tx) returning the DREQ number for a state machine's FIFO, with the last argument true for the TX FIFO that the DMA writes. The SDK's dma_channel_configure then applies the whole configuration, and the DMA waits on the DREQ for each word.

The project's steps[] array holds six patterns, 1, 2, 4, 8, 4 and 2, each a 32-bit word whose low four bits form the LED pattern, which runs back and forth across four LEDs on GP10 to GP13.

Common mistakes and how to spot them

Each mistake below has a symptom visible on the serial monitor or the LEDs, and a fix.

The RX DREQ requested for a transmit FIFO

The serial monitor prints PIO DMA OK, but the LEDs never move and the restart loop never runs, because pio_get_dreq(PIO0, 0, false) makes the DMA wait for a word in the RX FIFO, which this program never pushes, so the request never arrives. Pass true, because the DMA writes to the TX FIFO.

The state machine enabled after the DMA has run

The LEDs stay off and the DMA appears stuck after the first few words, because it fills the four TX FIFO words and then waits for the state machine to pull, which a disabled state machine never does. Call pio_sm_set_enabled(PATTERN_PIO, PATTERN_SM, true) before the DMA starts, as the solution does.

A clock divider set for a faster state machine

The four LEDs look dim and steady instead of stepping, because a divider of 1 runs the PIO at the full 125 MHz, so a step of 33 cycles of 8 ns lasts about 0.26 µs. Keep the divider that gives the required rate, and check the arithmetic of the worked example before changing it.

The bit order reversed

The pattern steps in the right order but the wrong LED lights, or two light together, because with the shift set to the left OUT takes the most significant bits of the word first, so the steps[] values reach the wrong pins. Check sm_config_set_out_shift(&c, true, false, 32), whose first argument, true, selects the right shift the solution uses.

PIO applications and review practice

The datasheet lists the uses of PIO, among them parallel buses such as the 8080 and 6800 families, I2C, I2S, SDIO, SPI and QSPI, UART, and DPI or VGA video output through a resistor network (RP2040 datasheet, section 3.1). Real products use it for custom interfaces that no fixed peripheral covers and for an extra UART or SPI when the main ones are busy, a typical design giving a PIO program one clear job, feeding it from DMA and leaving the CPU free for the rest of the firmware.

A senior engineer expects three things from a PIO change: a comment on every instruction in the .pio file stating what it does and how many cycles it takes, since the timing lives in those comments, a check of the generated header against a hand decode, as this project makes, so that a later edit cannot silently change the words, and a measurement on real hardware with a logic analyser, because the cycle count is only a model until a probe confirms it. The glossary entry on the logic analyzer explains what to look for.

Summary

  • A PIO state machine is a small sequencer with two shift registers, two scratch registers, FIFOs and a clock divider, each instruction taking one PIO cycle plus its delay.
  • Each PIO instruction has 16 bits, the top three selecting the instruction and the table in section 3.4.1 giving the rest.
  • PULL moves a word from the TX FIFO to the output shift register, and OUT shifts bits from there to a destination such as the pins.
  • The clock divider sets the PIO clock as the system clock divided by the integer and fractional divisor.
  • A step lasts the sum of the cycles in the loop, a wrap costing no cycle, which in this project gives 33 cycles, about 15.84 ms.
  • A DMA channel copies words into the TX FIFO, waiting for the DREQ that the PIO raises whenever the FIFO has room.
  • The common mistakes are the wrong DREQ direction, a state machine left disabled, a wrong clock divider and a reversed shift direction.
