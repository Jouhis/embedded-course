Threads and kernel services

Zephyr's kernel has the same building blocks as FreeRTOS: threads, message queues, semaphores, mutexes and deferred work. The names differ, and the priority numbers run the other way. This lesson builds all five on the Pico and maps each one to its FreeRTOS counterpart.

By the end of this lesson you can define a thread with K_THREAD_DEFINE, pass events with a message queue, guard a counter with a mutex, and explain how a Zephyr priority compares with a FreeRTOS one.

Where we are and why it matters

Lessons 87 to 91 taught a real-time operating system (RTOS) on FreeRTOS. You created tasks, passed data through queues and semaphores, protected a shared variable with a mutex, and watched the stack. Those ideas do not change in Zephyr. What changes is the API, the names and the way the priority numbers are read. Lesson 96 then showed where Zephyr keeps the pin numbers, so the code in this lesson names no pin.

The problem this lesson solves is common in a product. A button must be read without losing presses, a counter must be shown without losing updates, a blink must keep its rhythm while the rest of the firmware is busy, and a slow print must never delay a button. Each job needs its own thread of control, and the kernel's objects let the jobs talk without stepping on each other.

The concepts, one at a time

A thread is a function with its own stack

A thread is a function that the kernel can run, pause and resume. Each thread has a stack, a region of RAM where its local variables and return addresses live while it runs. Every thread also has a small record in RAM, the thread control block, which holds its priority, its state and a pointer to its saved stack position. The stack and the record are the thread's entire memory of where it was.

A CPU core has one set of registers. When two threads both want to run, the kernel must save the running thread's registers into that thread's stack, load the registers of another thread from its stack, and jump to where that thread stopped. This is a context switch, and it is the reason each thread needs its own stack. It is the same mechanism you read about in lesson 88, now managed by Zephyr's scheduler.

A thread is either ready (it could run now), running (it has the CPU), or blocked (it waits for something, such as a message or a time). Waiting costs no CPU time: a blocked thread is simply not chosen by the scheduler until its wait ends. Most of the bugs in this lesson come from a thread that waits in the wrong place.

Priorities come in two classes

The scheduler picks the most urgent ready thread. Zephyr measures urgency with a number, and it has one rule that surprises FreeRTOS users: a smaller number is more urgent. The macro K_PRIO_PREEMPT(x) gives a preemptible priority equal to x, so K_PRIO_PREEMPT(0) is the most urgent preemptible priority (include/zephyr/kernel.h:90). A preemptible thread can be interrupted at any moment by a ready thread of higher or equal urgency.

Zephyr also has cooperative priorities, made with K_PRIO_COOP(x), which are negative (include/zephyr/kernel.h:78). The Zephyr threads documentation says that a cooperative thread "has a negative priority value", and that once it is running it stays running until it does something that makes it unready. A preemptible thread can never take the CPU from it. The lesson's project uses only preemptible priorities. The numbers run the opposite way to FreeRTOS. In FreeRTOS a larger number is more urgent. In Zephyr a smaller number is more urgent. Check that before you copy a priority from a FreeRTOS project.

Message queues copy fixed-size messages

A message queue passes data from one thread to another without sharing memory. The sender copies a message into the queue, and the receiver copies it out. Every message has the same size, which you set when you define the queue. K_MSGQ_DEFINE(q_name, q_msg_size, q_max_msgs, q_align) reserves the buffer at build time (include/zephyr/kernel.h:5351), so the queue can never run out of memory at run time.

The copy has a price, so messages should be small. A button event with one 32-bit timestamp is cheap. A whole display frame is not.

A queue also has a fixed depth, so a put can fail. The timeout argument decides what happens then. K_NO_WAIT returns at once with an error, K_FOREVER blocks until there is room, and a time in milliseconds blocks for at most that long. With K_NO_WAIT and a full queue, k_msgq_put returns -ENOMSG (kernel/msg_q.c:237), and the caller decides what to do.

Semaphores count things

A semaphore is a counter with two operations. k_sem_give adds one, and k_sem_take subtracts one, waiting first if the count is zero. A binary semaphore is the special case with a limit of one. Zephyr defines one with K_SEM_DEFINE(name, initial_count, count_limit) (include/zephyr/kernel.h:3874), so you choose both the starting count and the most the count can reach.

A semaphore carries a signal, not data: giving it says "one more event happened". The Zephyr semaphore documentation says that a thread or an interrupt may give a semaphore, which makes it the right tool to wake a thread from an interrupt. An interrupt may take one only without waiting.

Mutexes guard shared data

A mutex is a lock with an owner. Only the thread that locked it may unlock it, and another thread that tries to lock it waits. Use a mutex when several threads read and write the same variable. The classic bug is the read-modify-write in total_presses++: the CPU reads the number, adds one and writes it back, in separate steps. If a higher-priority thread preempts between the read and the write, and it also increments the number, one of the two increments is lost, which is a lost update. The mutex makes those steps one unit to every other thread that asks for the lock.

Zephyr mutexes do two things a plain lock does not. They are reentrant, so the owner can lock them again without deadlocking itself. They also implement priority inheritance. If a high-priority thread waits for a mutex held by a low-priority thread, the owner's priority is raised while the high-priority thread waits, so a middle-priority thread cannot keep the owner from finishing (the algorithm is described in the comment at the top of kernel/mutex.c). Lesson 91 explains the failure that this prevents.

A mutex has one hard rule. An interrupt handler must never lock it, because the handler cannot wait and the thread that holds the lock may be the one the interrupt interrupted. The kernel checks this with an assertion, mutexes cannot be used inside ISRs (kernel/mutex.c:209). Assertions can be compiled out by configuration, so keep them on while you develop.

Timers and deferred work

A kernel timer runs a function after a delay and then, optionally, again at a fixed period. The function you give it is its expiry function. The timer documentation says that the expiry function runs in interrupt context, and that it must be kept short and non-blocking. An interrupt service routine (ISR) is code that the hardware calls directly, and interrupt context is the state the CPU is in while an ISR runs. An ISR cannot sleep or wait for a lock.

The usual answer is deferred work. The expiry function does the minimum that must happen at the exact moment, and then hands the rest to a thread. Zephyr's system workqueue is a thread that runs work items in order. The documentation says that a work item may be submitted by an interrupt or by a thread, and the system workqueue is the thread that runs it. Deferred work lets the interrupt stay short and the slow code run where waiting is allowed.

Worked example: one press, from the pin to the screen

Take the solution in projects/0097-threads-and-kernel/solution, and follow one button press. The numbers below are chosen for the example, not measured, so that the arithmetic is easy to check. The button is on GP14 and is active low, so the pin reads 0 when pressed. The button thread runs every BUTTON_POLL_MS, which is 10 ms, and it looks at the pin each time.

  1. t = 1000 ms. The user presses the button. The pin falls to 0. Nothing in the firmware runs yet.
  2. t = 1010 ms. The button thread wakes from its 10 ms sleep. It calls gpio_pin_get_dt(&button), which returns 1 because the logical level is pressed. Its variable was_pressed is false, so this is a new press.
  3. t = 1010 ms, still. The thread builds an event with uptime_ms = k_uptime_get_32(), which is 1010, and calls k_msgq_put(&button_q, &ev, K_NO_WAIT). The queue copies the event. The UI thread was blocked in k_msgq_get, so it now becomes ready. It has priority 5, and the button thread has priority 2, so the button thread keeps the CPU.
  4. t = 1020 ms. The button thread sleeps for 10 ms. The scheduler now picks the most urgent ready thread, which is the UI thread. It takes the event, locks stats_lock, increments total_presses from 0 to 1, unlocks, and prints press 1 at 1010 ms.
  5. t = 2000 ms. The timer expires. Its expiry function runs in interrupt context. It gives tick_sem and submits report_work. Both actions are short and never wait.
  6. t = 2000 ms, after the interrupt. The blink thread (priority 7) was waiting on the semaphore, and it is now ready. The system workqueue thread also has work to do. The scheduler runs them in priority order. The blink thread toggles the LED, and the work handler locks the mutex, reads total_presses as 1, unlocks, and prints total presses 1.

Each object does one job here. The queue carried the event to the UI thread, the mutex made the increment and the read a safe pair, and the semaphore and the workqueue carried the tick out of the interrupt. The mutex was held only for one increment.

The example also hides a limit. The button was polled, so a press shorter than 10 ms could come and go between two looks at the pin. That trade is deliberate in this project, and the common-mistakes section returns to it.

The code, line by line

The solution has three threads, one timer and one work item. Each piece is short, and each line below is named as it appears in src/main.c.

#define BUTTON_PRIO   K_PRIO_PREEMPT(2)
#define UI_PRIO       K_PRIO_PREEMPT(5)
#define BLINK_PRIO    K_PRIO_PREEMPT(7)
#define THREAD_STACK  1024

The three priorities are written as macros, so a reader can see the order at a glance. Button is 2, UI is 5 and blink is 7, and a smaller number runs first. THREAD_STACK gives each thread 1024 bytes of stack. Those bytes are reserved at build time, so a thread that uses more stack than it was given overwrites memory that belongs to another thread. Lesson 92 shows how to measure the real use. 

K_MSGQ_DEFINE(button_q, sizeof(struct button_event), QUEUE_DEPTH, 4);
K_SEM_DEFINE(tick_sem, 0, 1);
K_MUTEX_DEFINE(stats_lock);
static uint32_t total_presses;

The queue holds up to QUEUE_DEPTH (8) events, each the size of one struct button_event. The semaphore starts at 0, so the blink thread must wait for the first tick, and its limit is 1, so ticks cannot pile up if nobody takes them. The mutex protects total_presses, which is an ordinary static variable with file scope, so only code in this file can reach it. The last argument of K_MSGQ_DEFINE is the alignment, which the kernel needs for the buffer. 

static const struct gpio_dt_spec button = GPIO_DT_SPEC_GET(DT_ALIAS(sw0), gpios);

This line is the one that connects the code to the hardware. DT_ALIAS(sw0) names the node that the overlay labels sw0, and GPIO_DT_SPEC_GET reads its gpios property into a struct with the port, the pin and the flags (include/zephyr/drivers/gpio.h:376). The flags include GPIO_ACTIVE_LOW, which gpio_pin_get_dt already applies, so the value 1 means pressed (include/zephyr/drivers/gpio.h:1796). 

static void tick_expired(struct k_timer *timer)
{
    k_sem_give(&tick_sem);
    k_work_submit(&report_work);
}

This is the expiry function, so it runs in interrupt context. k_sem_give is allowed there, and k_work_submit is allowed there too, because it only adds the work item to the queue. The function contains no lock and no print. That is the discipline the timer documentation asks for, and the function is short enough to check by eye. 

static void report_handler(struct k_work *work)
{
    k_mutex_lock(&stats_lock, K_FOREVER);
    uint32_t n = total_presses;
    k_mutex_unlock(&stats_lock);
    printk("total presses %u\n", n);
}
K_WORK_DEFINE(report_work, report_handler);

The work handler runs in a thread, so it may lock a mutex and wait for it. It copies the shared counter into a local variable while it holds the lock, and then releases the lock before it prints. Printing can be slow, and holding a lock during a slow call would stall the UI thread for as long as the print takes. K_WORK_DEFINE creates the work item, and the work item knows which function to call. 

static void button_thread(void *p1, void *p2, void *p3)
{
    bool was_pressed = false;
    while (1) {
        bool pressed = gpio_pin_get_dt(&button) == 1;
        if (pressed && !was_pressed) {
            struct button_event ev = { .uptime_ms = k_uptime_get_32() };
            if (k_msgq_put(&button_q, &ev, K_NO_WAIT) != 0) {
                printk("button queue full, press dropped\n");
            }
        }
        was_pressed = pressed;
        k_msleep(BUTTON_POLL_MS);
    }
}
K_THREAD_DEFINE(button_tid, THREAD_STACK, button_thread, NULL, NULL, NULL,
                BUTTON_PRIO, 0, 0);

The was_pressed variable turns a level into an event. The pin stays at 1 for as long as the button is held, so the code posts an event only on the step from not pressed to pressed. The K_NO_WAIT argument means that a full queue returns at once, and the thread prints a warning and carries on polling. The thread never waits on the queue, because a stalled button thread would miss the next press. K_THREAD_DEFINE reserves the stack and the thread record at build time, and starts the thread with priority 2 after a delay of 0 ms (include/zephyr/kernel.h:1029). 

static void ui_thread(void *p1, void *p2, void *p3)
{
    while (1) {
        struct button_event ev;
        k_msgq_get(&button_q, &ev, K_FOREVER);
        k_mutex_lock(&stats_lock, K_FOREVER);
        total_presses++;
        uint32_t n = total_presses;
        k_mutex_unlock(&stats_lock);
        printk("press %u at %u ms\n", n, ev.uptime_ms);
    }
}

K_FOREVER on the get means the thread sleeps until a message arrives and uses no CPU while it waits. The increment and the copy of the count happen under the mutex, so a reader in the work handler can never see the variable half-updated. The print comes after the unlock, for the same reason as in the work handler. 

static void blink_thread(void *p1, void *p2, void *p3)
{
    while (1) {
        k_sem_take(&tick_sem, K_FOREVER);
        gpio_pin_toggle_dt(&led0);
    }
}

The blink thread waits on the semaphore once per tick. Each give from the timer adds one, and each take removes one, so the LED toggles once a second, and it blinks at a steady rhythm even when the UI is busy. If the thread were slow, the count would stay at its limit of 1 and the extra ticks would be lost, which is the reason the limit is set. 

k_timer_start(&tick_timer, K_SECONDS(1), K_SECONDS(1));

k_timer_start takes the timer, the delay before the first expiry, and the period (include/zephyr/kernel.h:2013). Both are one second, so the first expiry is at 1 s and then every second after. The call is in main(), after the LED and the button are configured, so the LED is already an output when the first tick toggles it.

FreeRTOS has no equivalent to K_NO_WAIT as a named constant, and it has no negative cooperative priority. Both exist in Zephyr. The priority difference is the one that causes the most bugs when people move code.

Common mistakes and how to spot them

Copying a FreeRTOS priority number

Suppose a FreeRTOS project has a task at priority 6, the most urgent task in the project, and you copy the number as K_PRIO_PREEMPT(6) into Zephyr. In Zephyr every thread numbered 0 to 5 now runs before it, so the most urgent task has become one of the least urgent. The symptom is a UI that updates late, or a button that seems to lose presses while a background thread is busy. The fix is to decide the order you want, then write the Zephyr number for that order. The table above is the place to check.

Taking a mutex, or printing for long, inside the timer

If you put k_mutex_lock(&stats_lock, K_FOREVER) inside tick_expired, the kernel's check for this (kernel/mutex.c:209) fails, and with assertions enabled the console reports mutexes cannot be used inside ISRs. The check is a safety net. The fix is the one in the solution: give the semaphore and submit work, and let the work handler lock the mutex.

Using K_FOREVER where the thread must keep polling

In the button thread, k_msgq_put(&button_q, &ev, K_FOREVER) looks harmless, because the queue has room most of the time. When the UI is slow and the queue fills, the put blocks inside the thread, the button thread stops sampling the pin, and any press that starts and ends during the wait is lost. The symptom is a count that falls behind the presses you made, while the blink thread keeps its one-second rhythm. The fix is K_NO_WAIT plus a warning, so the thread keeps sampling and reports the drop.

Forgetting that a poll can miss a short press

The button thread samples the pin every 10 ms. A press that lasts 3 ms, and that starts and ends between two samples, is never seen. A student who expects "one press, one line" will see fewer lines than button presses when tapping quickly. The fix depends on the requirement: poll faster, or use a GPIO interrupt, as lesson 57 and lesson 98 do.

In real projects

Production firmware has a few threads with clear jobs, such as input, control, communication and logging, and the objects in this lesson connect them. A senior engineer reviewing a Zephyr change asks three questions: which context each function runs in, whether any ISR or expiry function can block, and which mutex protects each shared variable.

Zephyr supports many boards. The same thread, queue and mutex code runs on each of them, and only the devicetree and the drivers change. That is why this lesson uses the generic APIs and the overlay from lesson 96. The priority numbers are the one part that follows the product rather than the board, so a team writes them down in one header and reviews any change to them.

Summary

  • A thread has its own stack and a control block. The scheduler runs the most urgent ready thread, and a context switch saves and restores registers.
  • In Zephyr a smaller priority number is more urgent. K_PRIO_PREEMPT(x) is preemptible; K_PRIO_COOP(x) is negative and is never preempted by a preemptible thread.
  • A message queue copies fixed-size messages. K_NO_WAIT returns -ENOMSG when the queue is full, and K_FOREVER blocks.
  • A semaphore counts events. Its limit set at definition stops ticks from piling up.
  • A mutex is an owned, reentrant lock with priority inheritance. It is never taken inside an interrupt.
  • A timer expiry runs in interrupt context. Keep it to a give and a work submit, and let a thread do the rest.
  • Watch the priority numbers when you move code from FreeRTOS, because the order is reversed.
