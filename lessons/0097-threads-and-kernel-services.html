Threads and kernel services

Zephyr's threads, queues, semaphores, mutexes and work

By the end of this lesson you can define a thread with K_THREAD_DEFINE, pass events with a message queue, guard a counter with a mutex, and explain how a Zephyr priority compares with a FreeRTOS one.

The FreeRTOS objects in Zephyr

Lessons 87 to 91 taught a real-time operating system (RTOS) on FreeRTOS, creating tasks, passing data through queues and semaphores, protecting a shared variable with a mutex and watching the stack, ideas that do not change in Zephyr, whereas the API, the names and the reading of the priority numbers do. Lesson 96 then showed where Zephyr keeps the pin numbers, so the code in this lesson names no pin.

The problem this lesson solves is common in a product, where a button must be read without losing presses, a counter shown without losing updates, a blink kept in rhythm while the rest of the firmware is busy and a slow print prevented from ever delaying a button. Each job needs its own thread of control, and the kernel's objects let the jobs talk without stepping on each other.

Threads and their stacks

A thread is a function that the kernel can run, pause and resume, each thread having a stack, a region of RAM where its local variables and return addresses live while it runs, and a small record in RAM, the thread control block, holding its priority, its state and a pointer to its saved stack position, the stack and the record together being the thread's entire memory of where it was.

A CPU core has one set of registers, so when two threads both want to run, the kernel must save the running thread's registers on that thread's stack, load another thread's registers from its stack and jump to where that thread stopped. This is a context switch, the reason each thread needs its own stack, and the same mechanism lesson 88 described, now managed by Zephyr's scheduler.

A thread is either ready, able to run now, running, holding the CPU, or blocked, waiting for something such as a message or a time, and since a blocked thread is simply not chosen by the scheduler until its wait ends, waiting costs no CPU time. Most of the bugs in this lesson come from a thread that waits in the wrong place.

Preemptible and cooperative priorities

The scheduler picks the most urgent ready thread, measuring urgency with a number under a rule that surprises FreeRTOS users, a smaller number is more urgent. The macro K_PRIO_PREEMPT(x) gives a preemptible priority equal to x, so K_PRIO_PREEMPT(0) is the most urgent preemptible priority (include/zephyr/kernel.h:90), and a preemptible thread can be interrupted at any moment by a ready thread of higher or equal urgency.

Zephyr also has cooperative priorities, made with K_PRIO_COOP(x), which are negative (include/zephyr/kernel.h:78), the Zephyr threads documentation saying that a cooperative thread "has a negative priority value" and that once running it stays running until it does something that makes it unready, so a preemptible thread can never take the CPU from it. The lesson's project uses only preemptible priorities. The numbers run the opposite way to FreeRTOS. In FreeRTOS a larger number is more urgent. In Zephyr a smaller number is more urgent. Check that before you copy a priority from a FreeRTOS project.

A cooperative thread resembles a speaker who keeps the microphone until handing it over, so that nobody can cut in and the speaker must not talk for too long, while a preemptive thread resembles a speaker in a meeting whose chair may interrupt when someone more urgent raises a hand, Zephyr's negative priorities being the first kind and zero and above the second. The comparison breaks for interrupts, though, because even a cooperative thread is interrupted by hardware interrupts, which the speaker's rule would forbid.

Message queues

A message queue passes data from one thread to another without sharing memory, the sender copying a message into the queue and the receiver copying it out, every message having the size set when the queue is defined. K_MSGQ_DEFINE(q_name, q_msg_size, q_max_msgs, q_align) reserves the buffer at build time (include/zephyr/kernel.h:5351), so the queue can never run out of memory at run time.

The copy has a price, so messages should be small, a button event with one 32-bit timestamp being cheap and a whole display frame not.

A queue also has a fixed depth, so a put can fail, the timeout argument deciding what happens then, K_NO_WAIT returning at once with an error, K_FOREVER blocking until there is room and a time in milliseconds blocking for at most that long. With K_NO_WAIT and a full queue k_msgq_put returns -ENOMSG (kernel/msg_q.c:237), leaving the caller to decide what to do.

Semaphores

A semaphore is a counter with two operations, k_sem_give adding one and k_sem_take subtracting one, after waiting if the count is zero, and a binary semaphore is the special case with a limit of one. Zephyr defines one with K_SEM_DEFINE(name, initial_count, count_limit) (include/zephyr/kernel.h:3874), so both the starting count and the highest count are chosen.

A semaphore carries a signal rather than data, a give saying that one more event happened, and since the Zephyr semaphore documentation says that a thread or an interrupt may give a semaphore, it is the right tool to wake a thread from an interrupt, although an interrupt may take one only without waiting.

Mutexes

A mutex is a lock with an owner, only the thread that locked it being allowed to unlock it while another thread trying to lock it waits, and it belongs wherever several threads read and write the same variable. The classic bug is the read-modify-write in total_presses++, where the CPU reads the number, adds one and writes it back in separate steps, so if a higher-priority thread that also increments the number preempts between the read and the write, one of the two increments is lost, a lost update, which the mutex prevents by making those steps one unit to every other thread that asks for the lock.

Zephyr mutexes do two things a plain lock does not, being reentrant, so the owner can lock them again without deadlocking itself, and implementing priority inheritance, which raises the priority of a low-priority owner while a high-priority thread waits for its mutex, so that a middle-priority thread cannot keep the owner from finishing (the algorithm is described in the comment at the top of kernel/mutex.c). Lesson 91 explains the failure this prevents.

A mutex has one hard rule, that an interrupt handler must never lock it, because the handler cannot wait and the thread holding the lock may be the one the interrupt interrupted, which the kernel checks with an assertion, mutexes cannot be used inside ISRs (kernel/mutex.c:209), and since configuration can compile assertions out, keep them on during development.

Kernel timers and deferred work

A kernel timer runs a function, its expiry function, after a delay and then, optionally, again at a fixed period, the timer documentation saying that the expiry function runs in interrupt context and must be kept short and non-blocking. An interrupt service routine (ISR) is code that the hardware calls directly, interrupt context being the state of the CPU while an ISR runs, and an ISR cannot sleep or wait for a lock.

The usual answer is deferred work, in which the expiry function does the minimum that must happen at the exact moment and hands the rest to a thread. Zephyr's system workqueue is a thread that runs work items in order, the documentation saying that a work item may be submitted by an interrupt or by a thread, so the interrupt stays short while the slow code runs where waiting is allowed.

Worked example: one press from the pin to the screen

One button press can be followed through the solution in projects/0097-threads-and-kernel/solution, with numbers chosen for the example rather than measured, so that the arithmetic is easy to check. The button is on GP14 and active low, reading 0 when pressed, and the button thread looks at the pin every BUTTON_POLL_MS, 10 ms. Before reading the steps, predict which thread prints first after the press, and why.

  1. t = 1000 ms. The user presses the button and the pin falls to 0, while nothing in the firmware runs yet.
  2. t = 1010 ms. The button thread wakes from its 10 ms sleep and calls gpio_pin_get_dt(&button), which returns 1, the logical pressed level, and since its variable was_pressed is false, this is a new press.
  3. t = 1010 ms, the put. The thread builds an event with uptime_ms = k_uptime_get_32(), 1010, and calls k_msgq_put(&button_q, &ev, K_NO_WAIT), the queue copying the event, so the UI thread, blocked in k_msgq_get, becomes ready, although with priority 5 against the button thread's 2 it does not take the CPU yet.
  4. t = 1010 ms, the UI thread. The button thread goes to sleep for 10 ms, so the scheduler picks the most urgent ready thread, the UI thread, which takes the event, locks stats_lock, increments total_presses from 0 to 1, unlocks and prints press 1 at 1010 ms.
  5. t = 2000 ms. The timer expires, its expiry function running in interrupt context, giving tick_sem and submitting report_work, two short actions that never wait.
  6. t = 2000 ms, after the interrupt. The blink thread (priority 7), which was waiting on the semaphore, is now ready and the system workqueue thread has work to do, so the scheduler runs them in priority order, the blink thread toggling the LED and the work handler locking the mutex, reading total_presses as 1, unlocking and printing total presses 1.

Each object does one job here, the queue carrying the event to the UI thread, the mutex making the increment and the read a safe pair and the semaphore and the workqueue carrying the tick out of the interrupt, while the mutex was held for only one increment.

The example also hides a limit, because the button was polled, so a press shorter than 10 ms could come and go between two looks at the pin, a deliberate trade in this project to which the mistakes section returns.

The project code line by line

The solution has three threads, one timer and one work item, each piece short and each line named below as it appears in src/main.c. 

#define BUTTON_PRIO   K_PRIO_PREEMPT(2)
#define UI_PRIO       K_PRIO_PREEMPT(5)
#define BLINK_PRIO    K_PRIO_PREEMPT(7)
#define THREAD_STACK  1024

The three priorities are written as macros, so that a reader sees the order at a glance, button 2, UI 5 and blink 7, a smaller number running first, and THREAD_STACK gives each thread 1024 bytes of stack, reserved at build time, so a thread using more stack than it was given overwrites memory belonging to another thread. Lesson 92 shows how to measure the real use. 

K_MSGQ_DEFINE(button_q, sizeof(struct button_event), QUEUE_DEPTH, 4);
K_SEM_DEFINE(tick_sem, 0, 1);
K_MUTEX_DEFINE(stats_lock);
static uint32_t total_presses;

The queue holds up to QUEUE_DEPTH (8) events, each the size of one struct button_event, and the last argument of K_MSGQ_DEFINE is the alignment the kernel needs for the buffer. The semaphore starts at 0, so the blink thread must wait for the first tick, and its limit is 1, so ticks cannot pile up if nobody takes them, while the mutex protects total_presses, an ordinary static variable with file scope that only code in this file can reach. 

static const struct gpio_dt_spec button = GPIO_DT_SPEC_GET(DT_ALIAS(sw0), gpios);

This line connects the code to the hardware, DT_ALIAS(sw0) naming the node the overlay labels sw0 and GPIO_DT_SPEC_GET reading its gpios property into a struct with the port, the pin and the flags (include/zephyr/drivers/gpio.h:376), among them GPIO_ACTIVE_LOW, which gpio_pin_get_dt already applies, so the value 1 means pressed (include/zephyr/drivers/gpio.h:1796). 

static void tick_expired(struct k_timer *timer)
{
    k_sem_give(&tick_sem);
    k_work_submit(&report_work);
}

This is the expiry function, so it runs in interrupt context, where k_sem_give is allowed, and so is k_work_submit, because it only adds the work item to the queue. The function contains no lock and no print, the discipline the timer documentation asks for, and is short enough to check by eye. 

static void report_handler(struct k_work *work)
{
    k_mutex_lock(&stats_lock, K_FOREVER);
    uint32_t n = total_presses;
    k_mutex_unlock(&stats_lock);
    printk("total presses %u\n", n);
}
K_WORK_DEFINE(report_work, report_handler);

The work handler runs in a thread, so it may lock a mutex and wait for it, copying the shared counter into a local variable while it holds the lock and releasing the lock before it prints, because printing can be slow and holding a lock during a slow call would stall the UI thread for as long as the print takes. K_WORK_DEFINE creates the work item, which knows which function to call. 

static void button_thread(void *p1, void *p2, void *p3)
{
    bool was_pressed = false;
    while (1) {
        bool pressed = gpio_pin_get_dt(&button) == 1;
        if (pressed && !was_pressed) {
            struct button_event ev = { .uptime_ms = k_uptime_get_32() };
            if (k_msgq_put(&button_q, &ev, K_NO_WAIT) != 0) {
                printk("button queue full, press dropped\n");
            }
        }
        was_pressed = pressed;
        k_msleep(BUTTON_POLL_MS);
    }
}
K_THREAD_DEFINE(button_tid, THREAD_STACK, button_thread, NULL, NULL, NULL,
                BUTTON_PRIO, 0, 0);

The was_pressed variable turns a level into an event, because the pin stays at 1 for as long as the button is held, so the code posts an event only on the step from not pressed to pressed. With K_NO_WAIT a full queue returns at once and the thread prints a warning and carries on polling, never waiting on the queue, since a stalled button thread would miss the next press, and K_THREAD_DEFINE reserves the stack and the thread record at build time and starts the thread with priority 2 after a delay of 0 ms (include/zephyr/kernel.h:1029). 

static void ui_thread(void *p1, void *p2, void *p3)
{
    while (1) {
        struct button_event ev;
        k_msgq_get(&button_q, &ev, K_FOREVER);
        k_mutex_lock(&stats_lock, K_FOREVER);
        total_presses++;
        uint32_t n = total_presses;
        k_mutex_unlock(&stats_lock);
        printk("press %u at %u ms\n", n, ev.uptime_ms);
    }
}

K_FOREVER on the get means that the thread sleeps until a message arrives, using no CPU while it waits, and the increment and the copy of the count happen under the mutex, so a reader in the work handler can never see the variable half-updated, while the print comes after the unlock, for the same reason as in the work handler. 

static void blink_thread(void *p1, void *p2, void *p3)
{
    while (1) {
        k_sem_take(&tick_sem, K_FOREVER);
        gpio_pin_toggle_dt(&led0);
    }
}

The blink thread waits on the semaphore once per tick, each give from the timer adding one and each take removing one, so the LED toggles once a second at a steady rhythm even while the UI is busy, and if the thread were slow, the count would stay at its limit of 1 and the extra ticks would be lost, which is why the limit is set. 

k_timer_start(&tick_timer, K_SECONDS(1), K_SECONDS(1));

k_timer_start takes the timer, the delay before the first expiry and the period (include/zephyr/kernel.h:2013), both one second here, so the first expiry is at 1 s and the rest follow every second, and the call sits in main() after the LED and the button are configured, so the LED is already an output when the first tick toggles it.

Common mistakes and how to spot them

A FreeRTOS priority number copied over

The UI updates late, or a button seems to lose presses while a background thread is busy, because a FreeRTOS task at priority 6, the most urgent in its project, was copied as K_PRIO_PREEMPT(6), so every Zephyr thread numbered 0 to 5 now runs before it and the most urgent task has become one of the least urgent. Decide the order you want, then write the Zephyr number for that order, checking it against the table in the FreeRTOS mapping section below.

A mutex taken inside the timer

With assertions enabled the console reports mutexes cannot be used inside ISRs, because k_mutex_lock(&stats_lock, K_FOREVER) was put inside tick_expired, which fails the kernel's check (kernel/mutex.c:209), a safety net rather than a guarantee. Do as the solution does, giving the semaphore and submitting work in the expiry function and letting the work handler lock the mutex.

K_FOREVER where the thread must keep polling

The count falls behind the presses made while the blink thread keeps its one-second rhythm, because k_msgq_put(&button_q, &ev, K_FOREVER) in the button thread, harmless while the queue has room, blocks once a slow UI lets the queue fill, so the button thread stops sampling the pin and any press that starts and ends during the wait is lost. Use K_NO_WAIT with a warning, so that the thread keeps sampling and reports the drop.

A short press missed by the poll

Quick taps produce fewer lines than presses, because the button thread samples the pin every 10 ms, so a 3 ms press that starts and ends between two samples is never seen. Depending on the requirement, poll faster or use a GPIO interrupt, as lesson 57 and lesson 98 do.

The table lines up the Zephyr objects with those of lessons 87 to 91, which use FreeRTOS, so check the FreeRTOS column against those lessons before relying on it.

FreeRTOS has no named constant equivalent to K_NO_WAIT and no negative cooperative priority, both of which exist in Zephyr, and the priority difference is the one that causes the most bugs when people move code.

Thread design reviews in Zephyr products

Production firmware has a few threads with clear jobs, such as input, control, communication and logging, connected by the objects in this lesson, and a senior engineer reviewing a Zephyr change asks which context each function runs in, whether any ISR or expiry function can block and which mutex protects each shared variable.

Zephyr supports many boards, the same thread, queue and mutex code running on each of them while only the devicetree and the drivers change, which is why this lesson uses the generic APIs and the overlay from lesson 96. The priority numbers are the one part that follows the product rather than the board, so a team writes them down in one header and reviews any change to them.

Summary

  • A thread has its own stack and a control block, the scheduler running the most urgent ready thread and a context switch saving and restoring registers.
  • In Zephyr a smaller priority number is more urgent, K_PRIO_PREEMPT(x) giving a preemptible priority and K_PRIO_COOP(x) a negative one never preempted by a preemptible thread.
  • A message queue copies fixed-size messages, K_NO_WAIT returning -ENOMSG when the queue is full and K_FOREVER blocking.
  • A semaphore counts events, and the limit set at its definition stops ticks from piling up.
  • A mutex is an owned, reentrant lock with priority inheritance that is never taken inside an interrupt.
  • A timer expiry runs in interrupt context, so it is kept to a give and a work submit while a thread does the rest.
  • Priority numbers need checking when code moves from FreeRTOS, because the order is reversed.
