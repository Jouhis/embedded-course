Designing a serial protocol: framing, checksums, CRC

A UART gives you a stream of bytes with no beginnings and no ends. A protocol turns that stream into messages that a receiver can find, check and, when a message is lost, ask again for. You will implement COBS byte stuffing and CRC-16/CCITT-FALSE, test them on the PC, and frame sensor readings on the Pico.

By the end of this lesson you can implement COBS encoding and decoding and a CRC-16/CCITT-FALSE, check the CRC against its standard value, and frame a sensor reading so that a receiver can find it and verify it.

The idea: a stream needs framing

A receiver that reads a UART byte by byte cannot tell where one message stops and the next starts, and line noise can add or drop bytes. A protocol has to solve two problems: framing, which marks where each message begins and ends, and error detection, which tells the receiver whether the bytes are intact. Three common framing styles solve the first one:

  • Length prefix. The first byte gives the length. It is simple, but one corrupted length byte loses synchronisation for every message after it.
  • Delimiter with escaping. A special byte ends each frame, and the body is rewritten so the delimiter never appears inside it. SLIP does this by escaping the end byte (RFC 1055, not opened for this lesson). In the worst case it can double the length of a frame.
  • COBS. Consistent Overhead Byte Stuffing rewrites the body so it contains no zero at all, and then 0x00 is free to mark every frame end. Its overhead is bounded, and a receiver can resynchronise after any noise: the next zero is the next frame.

Cheshire and Baker's paper defines COBS and proves its bound: the stuffing adds no more than one byte in 254 to any packet (Cheshire and Baker, "Consistent Overhead Byte Stuffing", IEEE/ACM Transactions on Networking, 1999). That makes COBS the usual choice for a binary stream that must resynchronise after noise. The paper's publisher identifier is S 1063-6692(99)03826-1. COBS: the rule in one example

COBS splits the data at its zeros. Each block starts with a code byte that gives the distance to the next zero, counting the code byte itself, and the data bytes of the block follow. Take 11 22 00 33. The first block holds 11 22, and its code is 3 (two data bytes plus one). The zero is replaced by the code. The last block holds 33, with code 2. The encoding is 03 11 22 02 33, which has no zero in it. Decoding reverses it: read a code, copy the block, and put back the zero that the code stood for.

Checksums and CRC: what they can catch

A checksum adds the bytes together, and it catches a single flipped bit. It misses a reordering of bytes, and it misses many pairs of errors that cancel. A cyclic redundancy check (CRC) treats the message as a long binary number and takes its remainder when divided by a fixed polynomial. Its detection power depends on the polynomial, and it catches all burst errors up to its width. Choosing a polynomial is a research problem: Philip Koopman's tables list the best polynomials for each size and Hamming distance (Koopman, "Best CRC Polynomials", Carnegie Mellon University).

The bitwise version works one bit at a time: eight shifts per byte, and no table. A table-driven version looks up 256 precomputed values, one per byte, which is faster but costs 512 bytes of flash. On a small microcontroller, the bitwise form is often the right trade. The check value is the test you run first: if your CRC gives 0x29B1 for "123456789", the polynomial, the init value and the bit order are all right. Append the CRC big-endian to a frame and the CRC of the whole frame becomes zero, which lets the receiver check a frame in one call.

Sequence numbers and retries

A CRC tells the receiver that a frame is damaged, but it cannot tell it that a frame is missing. Add a sequence number to each frame. The receiver answers with an ACK for a good frame or a NACK for a bad one, and the sender retries after a timeout. The sequence number also lets the receiver drop a duplicate when an ACK was lost. Stop-and-wait, one frame in flight at a time, is the simplest scheme that works. Lesson 99's Modbus avoids the problem by making every request a question that gets an answer.

Hint for the encoder

Keep two indexes: code_at, where the current code byte goes, and w, the next free output byte. At each zero, write the code into code_at and reserve the next code byte. At 254 data bytes, close the block the same way, without a zero.

Hint for the decoder

Read a code c, reject a zero code, and copy c - 1 bytes. After any block except one whose code is 0xFF, put back a zero, unless the input has ended.

Try it on the Pico: a framed sensor stream

The Pico project is projects/0101-framed-sensor-stream. Each frame carries a sequence number, a sensor ID, a 16-bit reading and a CRC, all COBS-encoded and ended by a zero. The firmware decodes each frame back, then checks that a corrupted frame is rejected, and it prints ROUNDTRIP OK at the end.

  1. Open projects/0101-framed-sensor-stream/starter in VS Code. The starter prints frames with no bytes, and ROUNDTRIP FAILED at the end.
  2. In main.c, fill in frame_encode(), following the comment: body, CRC, COBS, then the delimiter. Then fill in frame_decode(): COBS-decode, check the body length, check that the CRC of all six bytes is zero, and read the fields back.
  3. Build, then start the simulator with F1 → Wokwi: Start Simulator. You will know it works when the serial monitor shows five FRAME lines, each followed by decoded, then corrupted frame rejected: yes, and then ROUNDTRIP OK.

"How would you frame a binary byte stream on a UART, and how would the receiver know a frame is corrupted?" Answer out loud in 60 seconds, then compare.

Model answer

I would use COBS, so the body contains no zero, and end each frame with 0x00. A receiver that loses sync just waits for the next zero. Each frame carries a sequence number and a CRC-16 over its contents. A nonzero CRC over the frame, with its CRC appended, means damage, and the receiver answers NACK so the sender retries. The sequence number catches a lost frame or a duplicate. The check value of the CRC is the first test I run.
