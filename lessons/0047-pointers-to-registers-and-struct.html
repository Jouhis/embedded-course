Pointers to registers and struct overlays

A peripheral register is a fixed address on the bus. In C you reach it with a pointer, and a struct lets you name its fields. Vendor headers do exactly this, and you can write the same thing yourself.

By the end of this lesson you can write a register struct for the STM32F1 GPIO port, turn a fixed address into a pointer to it, and set PC13 with a single atomic BSRR write instead of a read-modify-write.

The idea

The CPU reaches a peripheral the same way it reaches RAM: a load or a store to an address. Lesson 38 explains the memory map that gives each peripheral its address. In C you write the address as an integer and turn it into a pointer with a cast. The volatile qualifier, from lesson 46, stops the compiler from caching or dropping the access. The cast does not create memory. It tells the compiler that a store to this address is a real hardware action, not a write to a variable it may reorder. 

/* The GPIOC BSRR register is at 0x40011000 + 0x10 (RM0008 memory map and GPIO registers). */
#define GPIOC_BSRR  (*(volatile uint32_t *)0x40011010u)

GPIOC_BSRR = 1u << 13;      /* one store to the register: sets bit 13 */

The left side of (*(volatile uint32_t *)0x40011010u) is a dereference, so it names the register itself. Read it, and you read the hardware. Write it, and you drive the bus.

A struct overlays the register block

A GPIO port is not one register. It is a block of seven 32-bit registers at consecutive offsets. A struct with the same field order maps onto that block: the first field sits at offset 0, the next at offset 4, and so on. CMSIS does this in stm32f103xb.h, so the code reads GPIOC->ODR rather than an address with an offset. CMSIS documentation 

typedef struct {
  __IO uint32_t CRL;    /* 0x00: configuration, pins 0 to 7 */
  __IO uint32_t CRH;    /* 0x04: configuration, pins 8 to 15 */
  __IO uint32_t IDR;    /* 0x08: input data */
  __IO uint32_t ODR;    /* 0x0C: output data */
  __IO uint32_t BSRR;   /* 0x10: bit set and reset, one write per pin */
  __IO uint32_t BRR;    /* 0x14: bit reset only */
  __IO uint32_t LCKR;   /* 0x18: configuration lock */
} GPIO_TypeDef;

#define GPIOC  ((GPIO_TypeDef *)GPIOC_BASE)   /* GPIOC_BASE is 0x40011000 */

GPIOC->BSRR = 1u << 13;   /* the same store as above, now named */

The vendor header defines __IO as volatile: the file core_cm3.h sets #define __IO volatile. So every register field carries the qualifier from lesson 46 without you writing it each time. A struct works as an overlay only if the compiler lays out its fields in order with no padding between 32-bit registers. Every field here is 4 bytes, so the offsets come out as the reference manual lists them. Lesson 48 covers why this is safe for registers and why bit-fields are not.

Read-modify-write vs the atomic BSRR

To set one pin in the output data register, you could write GPIOC->ODR |= 1u << 13;. That is three steps: load ODR, OR in the bit, and store the result back. If an interrupt changes another pin between the load and the store, the store writes back the old value of that other pin, and the change is lost.

BSRR avoids the read. Writing a 1 to bit n sets pin n. Writing a 1 to bit n + 16 resets it. A 0 does nothing. So a single store changes only the pins you name, and the hardware never reads the old state first. BSRR is the reason the Blue Pill template writes GPIO_BSRR_BR13 to turn the LED on. That constant is bit 13 + 16 = 29, the reset half.

The read-modify-write is fine during setup, when no interrupt is touching the port. For a pin that an ISR or another task may change, use BSRR. The RM0008 reference manual describes the set and reset bits in its GPIO register section, and the CMSIS header defines the same bit names. RM0008, GPIO registers

Try it in Wokwi

The project projects/0047-register-pointers is a Blue Pill. The starter gives you the register struct and the base addresses, but it has two mistakes in them. The CMSIS GPIO definitions are not used here: RCC, SysTick and USART1 still come from CMSIS, and the GPIO port is yours.

  1. Open projects/0047-register-pointers/starter in VS Code, build with Ctrl+Shift+B, then start the simulator with F1 → Wokwi: Start Simulator.
  2. Your task: correct the base address for GPIOC, and put the struct fields in the offset order from RM0008. Then write the PC13 configuration and the BSRR toggling. The comments marked for you in the starter say where.
  3. You will know it works when the serial monitor prints OWN STRUCT OK, followed by LED on and LED off lines every 500 ms, and the on-board LED blinks.
Hint for the base address and offsets

GPIOA and GPIOC are different ports, so their base addresses differ by 0x800 (RM0008 memory map, APB2 peripherals). Check the field order against the offset comments in the struct: each field is 4 bytes, so the struct order sets the offsets.

Hint for BSRR

PC13 is pin 13. Its set bit is 13, and its reset bit is 13 + 16. The LED is wired active low, so the LED is on when PC13 is low.

You turned a fixed address into a typed register block, wrote the struct for the GPIO port yourself, and drove PC13 with single BSRR writes. That is what the vendor headers do underneath every GPIOC-> you have seen.

"How do you access a memory-mapped register from C, and why does the pointer need volatile?" Answer out loud in 60 seconds, then compare.

Model answer

Define the register's address as a constant, cast it to a pointer to a volatile fixed-width type, and dereference it. Or define a struct whose fields follow the register offsets and point it at the base address. Volatile is required because the hardware can change the value, and reads can have side effects. Without it the compiler may cache the value or drop an access. For a pin that other code also changes, write BSRR rather than doing a read-modify-write on ODR.

RM0008, STM32F101/102/103 reference manual: read the memory map (section 3), and the GPIO register descriptions, including the BSRR and BRR bits. Then compare them with the CMSIS struct in third_party/cmsis-device-f1/Include/stm32f103xb.h.
