Pointers to registers and struct overlays

Typed C access to peripheral registers at fixed addresses

By the end of this lesson you can write a register struct for the STM32F1 GPIO port, turn a fixed address into a pointer to it, and set PC13 with a single atomic BSRR write instead of a read-modify-write.

From addresses to named registers

Lesson 38 explained the memory map, in which the chip places flash, SRAM and the peripherals at fixed addresses that the CPU reaches with ordinary loads and stores, and lesson 46 showed that a value the hardware can change must be accessed through volatile so that the compiler does not cache it. Lesson 2 blinked the on-board LED by writing to a GPIO pin, and this lesson shows what those writes actually are.

Every driver deals with this. A firmware engineer must configure a pin as an output and drive it high or low, safely, while an interrupt may be running, and the vendor header hides the detail behind names such as GPIOC->BSRR. When a bug appears in that code, a developer who does not know what the names stand for can only guess, whereas once you can write the struct yourself, the vendor code stops being opaque and can be checked against the reference manual.

Registers as fixed addresses

The CPU reaches a peripheral the same way it reaches RAM, a load instruction reading an address and a store writing one, while the bus carries the address and data and the peripheral at that address decides what the access means. A peripheral register is a location of this kind that configures a peripheral or reflects its state, so reading or writing its address talks to the hardware, and no memory cell stores the value in the usual sense.

In C the address is written as an integer constant. A pointer is a variable that holds an address and remembers the type of the object there, so casting an integer to a pointer type tells the compiler that the integer is an address of that type. The expression (*(volatile uint32_t *)0x40011010u) casts the number to a pointer to a volatile uint32_t and dereferences it, naming the register itself, so reading it performs a load from that address and writing it a store. 

/* The GPIOC BSRR register sits at 0x40011000 + 0x10. */
#define GPIOC_BSRR  (*(volatile uint32_t *)0x40011010u)

GPIOC_BSRR = 1u << 13;      /* one store to the register: sets bit 13 */

The cast creates no memory and runs no code, but tells the compiler two facts: that the access goes to a fixed address, and that every access is a real event rather than a value it may reuse. The volatile qualifier supplies the second fact, as lesson 46 explained, and without it the compiler might merge two stores or drop one it believes has no effect.

Structs as lists of offsets

A GPIO port is not one register but a block of seven 32-bit registers at consecutive addresses, and a struct is the C way to describe such a block. A struct lays out its members in declaration order, each at an offset from its start, so when every member is a 32-bit value each offset lies 4 bytes after the previous one, and the member at offset 0x10 is the fifth, with four members before it, since 4 × 4 = 16 = 0x10. A struct's members are placed in declaration order, with padding only where alignment requires it. Here every member is a 4-byte value at 4-byte alignment, so no padding appears and the offsets equal the register offsets.

If a pointer points at the start of the port, then port->ODR is the member at ODR's offset, which the compiler adds to the base address when it builds the access. You write a name and the compiler produces the same load or store as the explicit address form, so the struct is purely a naming device that adds nothing to the hardware. 

typedef struct {
  __IO uint32_t CRL;    /* offset 0x00: configuration, pins 0 to 7 */
  __IO uint32_t CRH;    /* offset 0x04: configuration, pins 8 to 15 */
  __IO uint32_t IDR;    /* offset 0x08: input data */
  __IO uint32_t ODR;    /* offset 0x0C: output data */
  __IO uint32_t BSRR;   /* offset 0x10: bit set and reset, one write per pin */
  __IO uint32_t BRR;    /* offset 0x14: bit reset only */
  __IO uint32_t LCKR;   /* offset 0x18: configuration lock */
} GPIO_TypeDef;

#define GPIOC  ((GPIO_TypeDef *)GPIOC_BASE)   /* GPIOC_BASE is 0x40011000 */

GPIOC->BSRR = 1u << 13;   /* the same store as above, now named */

The vendor header contains a real example of this struct. In third_party/cmsis-device-f1/Include/stm32f103xb.h the GPIO structure has the same seven members in the same order, and the base addresses GPIOA_BASE and GPIOC_BASE are computed from the APB2 peripheral base of 0x40010000 plus 0x800 for port A and 0x1000 for port C, giving 0x40010800 and 0x40011000 (RM0008 Rev 21, Table 3 in section 3.3).

A struct overlay resembles a transparent template laid over a paper form, with a label at each box: CRL here, ODR there, BSRR further down. On its own the template is only labels at offsets, but laid at the right corner, the peripheral's base address, each label sits on the real register, and laid at the wrong base, every label is wrong in the same way. Unlike a paper form, though, reading some of these boxes changes them, which is why the template needs volatile.

The __IO macro

The members of the vendor struct are written as __IO uint32_t rather than plain uint32_t, and the macro __IO is defined in the Arm CMSIS core header core_cm3.h as volatile. Every register field therefore carries the qualifier from lesson 46 without it being written at each use, the macro being a naming convention and the qualifier doing the work. CMSIS documentation

A struct overlay works only when the compiler lays out the fields exactly as the reference manual lists them. Here every field is a 4-byte register and the struct has no padding, so the offsets come out right, and lesson 48 covers when this breaks and why bit-fields are no safe substitute for a register map.

Read-modify-write and the BSRR register

A read-modify-write changes one bit of a register in three steps, loading the whole register, changing the bit in the copy and storing the copy back, which is exactly what GPIOC->ODR |= 1u << 13; does. The store writes back every bit of the register, including bits that other code may have changed meanwhile, so if an interrupt runs between the load and the store, its change is lost.

The BSRR register, whose name stands for bit set and reset, avoids the load. Writing a 1 to bit n, for n from 0 to 15, sets pin n high, writing a 1 to bit n + 16 resets pin n and drives it low (RM0008 Rev 21, section 9.2.5), and a 0 in any bit leaves that pin alone. One store therefore changes only the named pins, and the hardware never needs the old state. The CMSIS header defines the same layout, with GPIO_BSRR_BS13 as bit 13 and GPIO_BSRR_BR13 as bit 29, which is 13 plus 16.

Worked example: one BSRR write

Suppose the program wants PC13 driven low, which turns the active-low LED on. We follow both ways of doing it with real numbers to see where they differ, starting with BSRR.

  1. Find the address. The base of port C is 0x40011000 and BSRR is the fifth member, at offset 0x10, so the store goes to 0x40011000 + 0x10 = 0x40011010.
  2. Build the value. Driving PC13 low uses the reset half of BSRR, bit 13 + 16 = 29, so the value is 1u << 29, which is 0x20000000, a single 1 in bit 29, while bit 13 is 0 and the set half does nothing.
  3. Perform the store. The CPU stores 0x20000000 to 0x40011010, and the hardware resets PC13 and leaves the other 31 bits alone. The write needed no read and cannot lose a change made by an interrupt, because the hardware never reads the old state of the port.

The read-modify-write version is shown setting PC13 high instead. Suppose ODR holds 0x00000000 and the program wants bit 13 set, which is 0x00002000; before reading the steps, predict what happens to PC5 if an interrupt sets it midway. 

1. load  ODR  from 0x4001100C       -> 0x00000000   (main reads the old value)
2. ISR runs: it sets PC5 by writing ODR -> 0x00000020
3. main ORs bit 13 into its copy: 0x00000000 | 0x00002000 = 0x00002000
4. main stores the copy to ODR      -> 0x00002000   (PC5 is now low again)

The interrupt's change to PC5 is lost without any report, and since the same code is correct when no interrupt touches the port, the bug appears only sometimes. The BSRR version has no load and no full-register store that could overwrite another bit, its single store of 0x00002000 to BSRR setting PC13 and leaving PC5 alone. Setup code may use read-modify-write, because it runs before any interrupt is enabled, but code that changes a pin at run time should use BSRR.

The register-pointers project line by line

The starter in projects/0047-register-pointers asks you to finish a short program that uses your own struct for port C, and the key lines of the finished solution are below. The file keeps the CMSIS header for the rest of the chip, so only the GPIO port is written by hand. 

/* GPIOA is at 0x40010800 and GPIOC at 0x40011000 (CMSIS header: APB2 base plus 0x800 and 0x1000). */
#define MY_GPIOA_BASE  0x40010800UL
#define MY_GPIOC_BASE  0x40011000UL

typedef struct {
    volatile uint32_t CRL;    /* 0x00 */
    volatile uint32_t CRH;    /* 0x04 */
    volatile uint32_t IDR;    /* 0x08 */
    volatile uint32_t ODR;    /* 0x0C */
    volatile uint32_t BSRR;   /* 0x10 */
    volatile uint32_t BRR;    /* 0x14 */
    volatile uint32_t LCKR;   /* 0x18 */
} MyGpio;

#define MY_GPIOC  ((MyGpio *)MY_GPIOC_BASE)

The first two defines are the base addresses. The ports lie in order inside the APB2 region, 0x400 bytes apart, so port A is at offset 0x800, port B at 0xC00 and port C at 0x1000, and a slip from one port to another still gives a valid address, which the compiler and linker accept without any warning.

The struct declares each member as volatile uint32_t, so every access is a real load or store, and the member order matches the offsets in the comments. With 4 bytes per member the struct is 7 × 4 = 28 bytes, or 0x1C, with the last member LCKR at 0x18, and the comments serve the review, letting a reader check each name against the reference manual's table (RM0008 Rev 21, section 9.2 and Table 59).

The last define casts the base address to a pointer to the struct, and because the macro is a constant expression, MY_GPIOC->BSRR compiles to a store at 0x40011010. This cast from integer to pointer is the step that turns an address into a typed view of the hardware. 

RCC->APB2ENR |= RCC_APB2ENR_IOPCEN;   /* clock the GPIOC block first */

/* PC13 is in CRH, so its 4-bit field starts at bit (13 - 8) * 4 = 20. */
MY_GPIOC->CRH = (MY_GPIOC->CRH & ~(0xFU << 20)) | (0x2U << 20);

/* BSRR: bit n sets pin n, bit n + 16 resets it. A single write changes only the named pin. */
MY_GPIOC->BSRR = 1U << (LED_PIN_BIT + 16U);   /* PC13 low: LED on */
MY_GPIOC->BSRR = 1U << LED_PIN_BIT;           /* PC13 high: LED off */

The clock line comes first. The RCC block, the reset and clock controller, has an enable bit for each peripheral, and the GPIOC block ignores accesses until its clock is on, so the enable bit must be written before the port. The vendor headers name the bit RCC_APB2ENR_IOPCEN, bit 4 of RCC_APB2ENR (RM0008 Rev 21, section 7.3.7).

The CRH line is the configuration step and deliberately a read-modify-write, clearing the 4-bit field for pin 13 and setting a new value. The field starts at bit 20, which the vendor header gives as GPIO_CRH_MODE13_Pos, with the configuration bits CNF13 from bit 22, given as GPIO_CRH_CNF13_Pos, so the mask 0xFU << 20 covers bits 23 to 20 and its inverse clears them. The new value 0x2U << 20 sets MODE13 to 10, an output at 2 MHz, and leaves CNF13 at 00, general-purpose push-pull, as the port configuration table of RM0008 Rev 21 defines (Table 20 in section 9.1, and Table 21 for the MODE bits), with the field layout in section 9.2.2, where MODE13 is bits 21:20 and CNF13 bits 23:22. Setup runs before any interrupt, so the read-modify-write is safe here.

The BSRR lines are the run-time step. 1U << (LED_PIN_BIT + 16U) is 1U << 29, which resets PC13 and drives it low, while the second line sets bit 13 and drives PC13 high. Each is a single store, so an interrupt using another pin cannot disturb PC13, and PC13 cannot disturb another pin.

Hint for the base address and offsets

GPIOA and GPIOC are different ports whose base addresses differ by 0x800, since the CMSIS header gives GPIOA_BASE and GPIOC_BASE as the APB2 base plus 0x800 and 0x1000. Check the field order against the offset comments in the struct, remembering that each field is 4 bytes, so the declaration order sets the offsets.

Hint for BSRR

PC13 is pin 13, with set bit 13 and reset bit 13 + 16 = 29. The LED is wired active low, so it is on when PC13 is low, which means the reset bit turns it on and the set bit turns it off.

The reference solution is in projects/0047-register-pointers/solution, so try first and compare afterwards.

Common mistakes and how to spot them

A wrong base address that is still valid

The LED never blinks while the serial monitor shows the expected lines, because the code uses GPIOA's base for port C, which the compiler and linker accept and the program runs with. Compare each base address with the CMSIS header, where GPIOC_BASE is 0x40011000, or print the pointer value on the serial monitor as a quick check.

Struct members in the wrong order

The pin that changes is not the pin you configured, and the output is wrong in a way that is hard to see, because with CRL and CRH swapped, the configuration meant for pins 8 to 15 lands in the register for pins 0 to 7, and a dropped or doubled member would shift every later member by one slot. Check each member against its offset comment, and add static_assert checks such as offsetof(MyGpio, CRH) == 0x04 and offsetof(MyGpio, ODR) == 0x0C to catch the error at compile time.

A read-modify-write on a pin an interrupt also changes

A second output pin occasionally drops back to its old value with no error, because GPIOC->ODR |= bit, which looks correct and works most of the time, overwrote an interrupt's change. Use BSRR for every pin that run-time code changes.

The clock enable forgotten

A pin never changes state, although the code believes it wrote the configuration, because the port's registers ignore accesses until its clock is on. Set the enable bit in RCC first, and check it before debugging the port.

A zero written to BSRR

A pin stays where it was after a "turn off" write, because GPIOC->BSRR = 0 leaves every pin unchanged, a 0 in a BSRR bit doing nothing. Write the 1 into the half that does the job, the set half to drive high and the reset half to drive low.

Register access in vendor headers and reviews

Most STM32 projects reach their registers through the vendor header, and many drivers use the pattern of this lesson, the HAL and the low-layer functions writing to these structs and using BSRR for pins that change at run time. A driver that writes raw addresses is unusual, and a reviewer will ask why.

A code review of a register access checks four things: that the address comes from the header or the reference manual's memory map rather than a hand-typed number, that the struct members match the offsets, which a compile-time check can verify, that any pin an interrupt or another task can change uses BSRR or a critical section rather than a read-modify-write, and that the peripheral clock is on before the first access. A raw address without a comment prompts a request for its source.

Summary

  • A peripheral register is a fixed address whose loads and stores talk to the hardware, so every access must be volatile.
  • A struct of 4-byte members in the reference manual's order overlays the port, each member sitting at its register offset.
  • The GPIO port C block starts at 0x40011000, with ODR at 0x4001100C and BSRR at 0x40011010.
  • BSRR sets a pin with bit n and resets it with bit n + 16, and a 0 does nothing, so one store touches only the named pin.
  • A read-modify-write on ODR can lose a change an interrupt made between its load and store, so pins that change at run time should use BSRR.
  • The port's clock must be enabled in RCC before the first access, and the pin's configuration field is set with a read-modify-write during setup.
  • In the vendor header __IO is volatile, so the struct members are volatile without extra typing.

Then compare them with the CMSIS struct in third_party/cmsis-device-f1/Include/stm32f103xb.h, where the same offsets and bit names are defined.
