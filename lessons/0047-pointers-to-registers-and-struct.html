Pointers to registers and struct overlays

A peripheral register is a fixed address on the bus. In C you reach it with a pointer, and a struct lets you name its fields. Vendor headers do exactly this, and you can write the same thing yourself.

By the end of this lesson you can write a register struct for the STM32F1 GPIO port, turn a fixed address into a pointer to it, and set PC13 with a single atomic BSRR write instead of a read-modify-write.

Where we are and why it matters

Lesson 38 explained the memory map: the chip places flash, SRAM and the peripherals at fixed addresses, and the CPU reaches all of them with ordinary loads and stores. Lesson 46 showed that a value the hardware can change must be read and written with volatile, so the compiler does not cache it. Lesson 2 blinked the on-board LED by writing to a GPIO pin, and this lesson shows what those writes actually are.

Every driver deals with this. A firmware engineer must configure a pin as an output, drive it high or low, and do that safely while an interrupt may be running. The vendor header hides the detail behind names such as GPIOC->BSRR. When a bug happens in that code, a developer who does not know what the names stand for can only guess. Once you can write the struct yourself, the vendor code stops being magic, and you can check it against the reference manual.

Concepts, one at a time

A register is a fixed address

The CPU reaches a peripheral the same way it reaches RAM: a load instruction reads an address, and a store instruction writes one. The bus carries the address and the data, and the peripheral at that address decides what the access means. A peripheral register is a memory location of this kind. It configures a peripheral, or it reflects the state of one. Reading or writing its address talks to the hardware, and no memory cell stores the value in the usual sense.

In C, the address is written as an integer constant. A pointer is a variable that holds an address and remembers the type of the object at that address. Casting an integer to a pointer type tells the compiler that the integer is an address of that type. The expression (*(volatile uint32_t *)0x40011010u) casts the number to a pointer to a volatile uint32_t and then dereferences it. The dereference names the register itself. Reading it performs a load from that address, and writing it performs a store. 

/* The GPIOC BSRR register sits at 0x40011000 + 0x10. */
#define GPIOC_BSRR  (*(volatile uint32_t *)0x40011010u)

GPIOC_BSRR = 1u << 13;      /* one store to the register: sets bit 13 */

The cast does not create memory, and it does not run any code. It tells the compiler two facts. The access goes to a fixed address, and every access is a real event, not a value the compiler may reuse. The volatile qualifier supplies the second fact, as lesson 46 explained. Without it, the compiler might merge two stores or drop one that it thinks has no effect.

A struct is a list of offsets

A GPIO port is not one register. It is a block of seven 32-bit registers at consecutive addresses. The struct is the C way to describe such a block. A struct lays its members out in the order they are declared, and each member sits at an offset from the start of the struct. When every member is a 32-bit value, each offset is 4 bytes after the previous one. A member at offset 0x10 is the fifth member, because 4 members come before it, and 4 × 4 = 16 = 0x10. A struct's members are placed in declaration order, with padding only where alignment requires it. All members here are 4-byte values at 4-byte alignment, so no padding appears and the offsets are exactly the register offsets.

If a pointer points at the start of the port, then port->ODR is the member at the offset of ODR. The compiler adds the offset to the base address when it builds the access. You write a name and the compiler produces the same load or store as the explicit address form. The struct is only a naming device. It does not add anything to the hardware. 

typedef struct {
  __IO uint32_t CRL;    /* offset 0x00: configuration, pins 0 to 7 */
  __IO uint32_t CRH;    /* offset 0x04: configuration, pins 8 to 15 */
  __IO uint32_t IDR;    /* offset 0x08: input data */
  __IO uint32_t ODR;    /* offset 0x0C: output data */
  __IO uint32_t BSRR;   /* offset 0x10: bit set and reset, one write per pin */
  __IO uint32_t BRR;    /* offset 0x14: bit reset only */
  __IO uint32_t LCKR;   /* offset 0x18: configuration lock */
} GPIO_TypeDef;

#define GPIOC  ((GPIO_TypeDef *)GPIOC_BASE)   /* GPIOC_BASE is 0x40011000 */

GPIOC->BSRR = 1u << 13;   /* the same store as above, now named */

The vendor header is a real example of this struct. In third_party/cmsis-device-f1/Include/stm32f103xb.h the GPIO structure has the same seven members in the same order, and the base addresses are defined as GPIOA_BASE and GPIOC_BASE. The header computes them from the APB2 peripheral base, which is 0x40010000, plus an offset of 0x800 for port A and 0x1000 for port C. Those two numbers give 0x40010800 and 0x40011000 (RM0008 Rev 21, Table 3 in section 3.3).

A struct overlay is a transparent template laid over a paper form. The template has a label at each box: CRL here, ODR there, BSRR further down. On its own it is just labels at offsets. Lay it down at the right corner, the peripheral's base address, and every label sits on the real register. Lay it at the wrong base and every label is wrong in the same way.

__IO means volatile

The members in the vendor struct are not written as plain uint32_t. They are written as __IO uint32_t. The macro __IO is defined in the Arm CMSIS core header core_cm3.h as volatile. So every register field carries the qualifier from lesson 46, and you do not write it at each use. The macro is a naming convention, and the qualifier is what does the work. CMSIS documentation

A struct overlay works only when the compiler lays out the fields exactly as the reference manual lists them. Every field here is a 4-byte register, and the struct has no padding, so the offsets come out right. Lesson 48 covers when this breaks, and why bit-fields are not a safe substitute for a register map.

Read-modify-write, and why BSRR avoids it

A read-modify-write changes one bit of a register in three steps: load the whole register, change the bit in the copy, and store the copy back. The code GPIOC->ODR |= 1u << 13; does exactly this. The problem is that the store writes back every bit of the register, including the bits that other code might have changed in the meantime. If an interrupt runs between the load and the store, its change is lost.

The BSRR register avoids the load. Its name stands for bit set and reset. Writing a 1 to bit n from 0 to 15 sets pin n high. Writing a 1 to bit n + 16 resets pin n, which drives it low (RM0008 Rev 21, section 9.2.5). A 0 in any bit does nothing to that pin. So one store changes only the pins you name, and the hardware never needs the old state. The CMSIS header defines the same layout: GPIO_BSRR_BS13 is bit 13 and GPIO_BSRR_BR13 is bit 29, which is 13 plus 16.

Worked example: what one BSRR write does

Suppose the program wants PC13 driven low, which turns the active-low LED on. We will follow the two ways to do it, with real numbers, and see where they differ.

Step 1: find the address. The base of port C is 0x40011000. BSRR is the fifth member, at offset 0x10. The sum is 0x40011000 + 0x10 = 0x40011010. That is the address of the store.

Step 2: build the value. Driving PC13 low is the reset half of BSRR, which is bit 13 + 16 = 29. The value is 1u << 29. In hexadecimal, 29 is 0x1D, and 1 << 29 is 0x20000000, a single 1 in bit 29. Bit 13 is 0, so the set half does nothing.

Step 3: perform the store. The CPU stores 0x20000000 to 0x40011010. The hardware resets PC13 and leaves the other 31 bits alone. The write needed no read, and it cannot lose a change made by an interrupt, because the hardware never reads the old state of the port.

Now the read-modify-write version, to set PC13 high instead. Suppose ODR currently holds 0x00000000, and the program wants bit 13 set, which is 0x00002000. The steps run as follows: 

1. load  ODR  from 0x4001100C       -> 0x00000000   (main reads the old value)
2. ISR runs: it sets PC5 by writing ODR -> 0x00000020
3. main ORs bit 13 into its copy: 0x00000000 | 0x00002000 = 0x00002000
4. main stores the copy to ODR      -> 0x00002000   (PC5 is now low again)

The interrupt's change to PC5 is lost, and nothing reports it. The same code is correct when no interrupt touches the port, which is why the bug appears only sometimes. The BSRR version has no step 1 and no step 4 that could overwrite another bit. Its single store writes 0x00002000 to BSRR, which sets PC13 and leaves PC5 alone. Setup code can use read-modify-write, because it runs before any interrupt is enabled. Code that changes a pin at run time should use BSRR.

Step the worked example yourself. You decide when the interrupt fires. Fire it between main's load and its store and watch PC5 disappear, then switch to BSRR and try to break it again.

The code, explained line by line

The starter in projects/0047-register-pointers asks you to finish a short program that uses your own struct for port C. The solution shows the finished version, and its key lines are below. The file keeps the CMSIS header for the rest of the chip, so only the GPIO port is written by hand. 

/* GPIOA is at 0x40010800 and GPIOC at 0x40011000 (CMSIS header: APB2 base plus 0x800 and 0x1000). */
#define MY_GPIOA_BASE  0x40010800UL
#define MY_GPIOC_BASE  0x40011000UL

typedef struct {
    volatile uint32_t CRL;    /* 0x00 */
    volatile uint32_t CRH;    /* 0x04 */
    volatile uint32_t IDR;    /* 0x08 */
    volatile uint32_t ODR;    /* 0x0C */
    volatile uint32_t BSRR;   /* 0x10 */
    volatile uint32_t BRR;    /* 0x14 */
    volatile uint32_t LCKR;   /* 0x18 */
} MyGpio;

#define MY_GPIOC  ((MyGpio *)MY_GPIOC_BASE)

The first two defines are the base addresses. The ports are placed in order inside the APB2 region, 0x400 bytes apart, so port A is at offset 0x800, port B at 0xC00 and port C at 0x1000. A typo of one port for the other gives an address that is valid, so the compiler and linker accept it. Nothing warns you.

The struct declares each member as volatile uint32_t, so every access is a real load or store. The member order matches the offsets in the comments. Because each member is 4 bytes, the struct's size is 7 × 4 = 28 bytes, which is 0x1C, and the last member LCKR sits at 0x18. The comments are there for review: a reader can check each name against the reference manual's table (RM0008 Rev 21, section 9.2 and Table 59).

The last define casts the base address to a pointer to the struct. The macro is a constant expression, so MY_GPIOC->BSRR compiles to a store at 0x40011010. The cast from integer to pointer is the step that turns an address into a typed view of the hardware. 

RCC->APB2ENR |= RCC_APB2ENR_IOPCEN;   /* clock the GPIOC block first */

/* PC13 is in CRH, so its 4-bit field starts at bit (13 - 8) * 4 = 20. */
MY_GPIOC->CRH = (MY_GPIOC->CRH & ~(0xFU << 20)) | (0x2U << 20);

/* BSRR: bit n sets pin n, bit n + 16 resets it. A single write changes only the named pin. */
MY_GPIOC->BSRR = 1U << (LED_PIN_BIT + 16U);   /* PC13 low: LED on */
MY_GPIOC->BSRR = 1U << LED_PIN_BIT;           /* PC13 high: LED off */

The clock line comes first. The RCC block, which is the reset and clock controller, has an enable bit for each peripheral. The GPIOC block does not respond to accesses until its clock is on, so the write to the enable bit must come before any write to the port. The vendor headers name the bit RCC_APB2ENR_IOPCEN, which is bit 4 of RCC_APB2ENR (RM0008 Rev 21, section 7.3.7).

The CRH line is the configuration step, and it is a read-modify-write on purpose. It clears the 4-bit field for pin 13 and sets it to a new value. The field for pin 13 starts at bit 20, which is the value the vendor header gives as GPIO_CRH_MODE13_Pos, and the configuration bits CNF13 start at bit 22, from GPIO_CRH_CNF13_Pos. The mask 0xFU << 20 covers bits 23 to 20, and the inverted mask clears them. The new value 0x2U << 20 sets MODE13 to 10, an output at 2 MHz, and leaves CNF13 at 00, general-purpose push-pull. The meaning of the value 0x2 in this field is in the port configuration table of RM0008 Rev 21 (Table 20 in section 9.1, and Table 21 for the MODE bits), and the field layout is in section 9.2.2, where MODE13 is bits 21:20 and CNF13 is bits 23:22. Setup runs before any interrupt, so the read-modify-write is safe here.

The BSRR lines are the run-time step. 1U << (LED_PIN_BIT + 16U) is 1U << 29, which resets PC13 and drives it low. The second line sets bit 13 and drives PC13 high. Each line is a single store, so an interrupt that uses another pin cannot disturb PC13, and PC13 cannot disturb another pin.

Hint for the base address and offsets

GPIOA and GPIOC are different ports, so their base addresses differ by 0x800 (the CMSIS header gives GPIOA_BASE and GPIOC_BASE as APB2 base plus 0x800 and 0x1000). Check the field order against the offset comments in the struct: each field is 4 bytes, so the declaration order sets the offsets.

Hint for BSRR

PC13 is pin 13. Its set bit is 13, and its reset bit is 13 + 16 = 29. The LED is wired active low, so the LED is on when PC13 is low. Use the reset bit to turn it on, and the set bit to turn it off.

Common mistakes and how to spot them

  1. A wrong base address that is still a valid address. The code uses GPIOA's base for port C. The compiler and linker accept it, and the program runs. The symptom is that the LED never blinks, while the serial monitor shows the expected lines. The fix is to compare each base address with the CMSIS header, where GPIOC_BASE is 0x40011000. A quick check is to print the pointer value on the serial monitor.
  2. Struct members in the wrong order. Swapping CRL and CRH moves every later member by one slot, so ODR is read and written at the offset of IDR. The symptom is that the pin you configured is not the pin that changes, and the output is wrong in a way that is hard to see. The fix is to check each member against its offset comment. A static_assert on offsetof(MyGpio, ODR) == 0x0C would catch it at compile time.
  3. A read-modify-write on a pin that an interrupt also changes. GPIOC->ODR |= bit looks correct and works most of the time. The symptom is a rare lost change: a second output pin drops to its old value, with no error. The fix is to use BSRR for any pin that run-time code changes.
  4. Forgetting the clock enable. The port's registers do not respond until its clock is on, so the configuration write does nothing. The symptom is a pin that never changes state, while the code reads back the value it wrote. The fix is to set the enable bit in RCC first, and to check it before debugging the port.
  5. Writing 0 to BSRR and expecting a change. A 0 in a BSRR bit does nothing, so GPIOC->BSRR = 0 leaves every pin as it was. The symptom is a pin that stays where it was after a "turn off" write. The fix is to write the 1 in the half that does the job: the set half to drive high, the reset half to drive low.

In real projects

Most STM32 projects reach their registers through the vendor header, and many drivers use the same pattern as this lesson. The HAL and the low-layer functions write to these structs, and they use BSRR for pins that change at run time. A driver that writes raw addresses is unusual, and a reviewer asks why.

A code review of a register access checks four things. The address must come from the header or the reference manual's memory map, not from a number typed by hand. The struct members must match the offsets, which a compile-time check can verify. Any pin that an interrupt or another task can change must use BSRR or a critical section, not a read-modify-write. And the peripheral clock must be on before the first access. A reviewer who finds a raw address with no comment will ask for the source.

Summary

  • A peripheral register is a fixed address. A load or store to it talks to the hardware, so the access must be volatile.
  • A struct whose members are 4-byte registers, in the reference manual's order, overlays the port: each member sits at its register offset.
  • The GPIO port C block starts at 0x40011000, and its ODR is at 0x4001100C and its BSRR at 0x40011010.
  • BSRR sets a pin with bit n and resets it with bit n + 16. A 0 in any bit does nothing, so one store touches only the named pin.
  • A read-modify-write on ODR can lose a change made by an interrupt between its load and its store. Use BSRR for pins that change at run time.
  • Enable the port's clock in RCC before the first access, and set the configuration field of the pin with a read-modify-write during setup.
  • In the vendor header, __IO is volatile, so the struct members are volatile without extra typing.

Then compare them with the CMSIS struct in third_party/cmsis-device-f1/Include/stm32f103xb.h, where the same offsets and bit names are defined.
