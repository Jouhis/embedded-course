An I2C OLED display and a small UI framework

A 128 by 64 OLED panel has 1024 pixels, and the controller takes them as bytes over I2C. You will write the driver in about a hundred lines, then build a menu on top of it that two buttons can drive.

By the end of this lesson you can explain the SSD1306's control byte and page addressing, write pixels into a framebuffer and flush it page by page over I2C, and drive a cursor-based menu from two buttons using callbacks.

The idea

The SSD1306 is a monochrome OLED controller. It has its own display RAM, 128 columns by 8 pages, and each RAM byte holds the state of eight vertical pixels in one column SSD1306 datasheet, section 8.7. Your code keeps a copy of that RAM in the Pico's memory, called the framebuffer, and sends it over I2C each time the picture changes. The panel's address is 0x3C, which is 0111100 with the SA0 bit low SSD1306 datasheet, section 8.1.5. The framebuffer is 128 × 8 = 1024 bytes. On an RP2040 with 264 KB of RAM, that is a small fraction, and the cost is paid once.

The control byte

Every I2C write to the SSD1306 starts with a control byte. Its top bit, Co, says whether more control bytes follow. Its next bit, D/C#, says whether the bytes that follow are commands or display data SSD1306 datasheet, section 8.1.5.1. So a single command is sent as 0x80 followed by the command byte, and a stream of pixels is sent as 0x40 followed by the bytes. 

/* one command: control 0x80 (Co = 1, D/C# = 0), then the command */
uint8_t buf[2] = {0x80, cmd};
i2c_write_blocking(bus, 0x3C, buf, 2, false);

/* a page of pixels: control 0x40 (Co = 0, D/C# = 1), then 128 data bytes */
frame[0] = 0x40;
i2c_write_blocking(bus, 0x3C, frame, 129, false);

Page addressing

The controller can move its write pointer three ways. Page addressing, selected by the command 0x20 0x02, writes one page of 128 columns, then the pointer wraps back to the start column of the same page. You set the page and the column for each page with three commands: page start 0xB0 to 0xB7, and the column's low nibble (0x00 to 0x0F) and high nibble (0x10 to 0x1F) SSD1306 datasheet, sections 10.1.3, 10.1.13, 10.1.1 and 10.1.2.

The driver below sends 129 bytes per page, eight times. That is about 1 KB over I2C per frame. At 400 kbit/s, the wire time is roughly 25 ms, so the menu redraws only when a button changes something.

The init sequence is the one in the pico-examples i2c/ssd1306_i2c driver, published under the BSD-3-Clause licence by Raspberry Pi. It is checked against the SSD1306 datasheet. The example uses 128 by 32 settings in some places, so the 128 by 64 values here use the multiplex ratio 0x3F and the COM pin layout 0x12.

A 5 by 7 font

A character is a 5 by 7 bitmap, stored as five column bytes. Bit 0 of each column is the top row, and bit 6 is the bottom row. The capital L is {0x7F, 0x40, 0x40, 0x40, 0x40}: the first column is the full stem, and the bottom bar is bit 6 in each of the last four columns. A blank column between characters makes a six-pixel advance per character.

A complete font for 95 characters is too big for a lesson. The font here defines only the characters the menu uses: digits, a few capitals, a space, : and >. Adding a letter means adding one 5-byte entry.

A menu with a cursor and callbacks

A menu is an array of items, each with a label and an action, plus a cursor index. The action is a function pointer, the same callback mechanism as lesson 49. The menu does not know what an item does: it calls the pointer. Two buttons drive it. One moves the cursor down with wrap-around, and one runs the selected action. The buttons are read by polling for the falling edge, so one press is one step, however long the button is held.

Try it in Wokwi

The project projects/0061-an-i2c-oled-display-and wires a board-ssd1306 display to GP4 (SDA) and GP5 (SCL), with 4.7 kΩ pull-ups as in lesson 60, and two pushbuttons: DOWN on GP14 and SELECT on GP15. Wokwi's SSD1306 board part is the one to use, because the older wokwi-ssd1306 part is deprecated Wokwi, board-ssd1306 part. The display's address is 0x3C.

  1. Open projects/0061-an-i2c-oled-display-and/starter in VS Code (File → Open Folder).
  2. Build with Ctrl+Shift+B, and start the simulator with F1 → Wokwi: Start Simulator. The init and flush code is given. The screen stays blank until you finish the drawing code.
  3. Your task: write ssd1306_draw_char() (copy the five column bytes from font_glyph(), and leave one blank column), and ssd1306_draw_text() (advance by six). Then fix the cursor in menu_next(): the starter does a plain increment, which runs off the end of the item list. Finally draw the status line, print MENU OK once, and check that DOWN moves the cursor and SELECT counts a press.
Hint for the glyph copy

The glyph has five columns. Copy them into s_fb[page][x + i], and leave x + 5 at zero. Check the page and x against the framebuffer's size first.

Hint for the cursor

A modulo by the item count keeps the cursor in range, and it wraps by itself after the last item.

You drew text on an OLED you wrote the driver for, with the control byte, page addressing and a framebuffer, and you drove a menu from two buttons with callbacks. The same framebuffer and flush pattern works for the other SSD1306 and SH1106 panels.

"How would you drive a 128 by 64 OLED over I2C, and why is the framebuffer usually kept in RAM?" Answer out loud in 60 seconds, then compare.

Model answer

Keep a 1 KB framebuffer in RAM, draw into it, and send it to the panel with page addressing: set the page and column for each of the eight pages, then burst 128 data bytes after a 0x40 control byte. The RAM copy lets you draw in any order and makes partial updates cheap. The I2C wire time, about 25 ms at 400 kbit/s, limits the frame rate, so redraw only when the picture changes.

SSD1306 datasheet (Solomon Systech): read section 8.1.5 for the I2C address and the control byte, 8.7 for the display RAM, and 10.1.3 for addressing modes. Then compare with the pico-examples SSD1306 driver, which is BSD-3-Clause.
