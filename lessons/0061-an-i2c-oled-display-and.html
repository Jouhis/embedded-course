An I2C OLED display and a small UI framework

A 128 by 64 OLED has 8,192 pixels, and its controller takes them as 1,024 bytes over I2C. You will write the display driver in about a hundred lines, then build a menu on top of it that two buttons can drive.

By the end of this lesson you can explain the SSD1306's control byte and page addressing, write pixels into a framebuffer and flush it page by page over I2C, and drive a cursor-based menu from two buttons using callbacks.

Where we are and why it matters

Lesson 60 decoded one I2C register read in a logic-analyzer capture. You saw a device answer at a 7-bit address, a master send a register pointer and then read, and pull-up resistors hold both lines high when nobody drives them. This lesson uses the same two wires for something a user can see: a picture on a small screen.

Small status screens are common in products. A bench meter, a heater controller or a 3D printer's front panel each shows a few lines of text and lets the user step through a menu with two or three buttons. The usual job is to write a small display driver in plain C, keep it separate from the menu logic, and test the parts on their own. The menu uses function pointers, the callback mechanism from lesson 49.

Concept 1: a panel is a grid of pixels, and a controller holds its memory

An OLED (organic light-emitting diode) panel is a sheet of tiny light sources, one per pixel. Each pixel lights when current flows through it, so the panel needs no backlight. The glass alone cannot show anything. It needs a controller chip that turns bytes from the microcontroller into the voltages that switch each row and column on and off. This panel's controller is the SSD1306, made by Solomon Systech.

The SSD1306 has its own memory, called display RAM or GDDRAM. The datasheet says it is a bit-mapped static RAM of 128 × 64 bits, split into eight pages of 128 columns each SSD1306 datasheet, section 8.7. Each byte is one column of one page, and its eight bits are eight vertical pixels. The controller reads this RAM to drive the panel, so the picture stays on the glass without help from the microcontroller. The microcontroller only has to change the RAM when the picture changes.

Your code keeps a copy of that RAM in the Pico's own memory. That copy is called the framebuffer. For 128 columns and 8 pages it is 8 × 128 = 1,024 bytes. Drawing happens in the framebuffer, which is ordinary RAM and is fast to write, and a separate step copies it to the panel. This split between "draw" and "flush" is the main idea of the driver.

Concept 2: the address, and the control byte that says what follows

The SSD1306 answers on I2C at the 7-bit address 0x3C, which is the bit pattern 0111100 with the SA0 pin low SSD1306 datasheet, section 8.1.5. Lesson 60 showed that the master sends the 7 address bits followed by one read/write bit. For a write, that byte is 0111100 followed by 0, which is 0x78 on the wire. The SDK takes the 7-bit address and adds the bit for you, so your code passes 0x3C.

The SSD1306 is not a register device like the sensors in lesson 60. Instead, each write starts with a control byte, and the control byte tells the chip how to read the bytes that follow. Its top bit, Co, is the continuation bit. Co = 0 means the rest of the transfer is data only. Co = 1 means another control byte follows. The next bit, D/C#, says whether the byte after the control byte is a command (0) or a byte of display data (1). Data bytes go into the display RAM, and the column pointer moves on by one after each one SSD1306 datasheet, section 8.1.5.1.

That gives two control bytes you will use. A single command is sent as 0x80 (Co = 1, D/C# = 0) followed by the command. A stream of pixels is sent as 0x40 (Co = 0, D/C# = 1) followed by the bytes. The driver below never mixes the two in one transfer, which keeps each frame easy to read on a logic analyzer.

Concept 3: page addressing, and how the pointer moves

The controller has three ways to move its write pointer through the RAM: horizontal, vertical and page addressing. The mode is set by the command 0x20 followed by a byte whose two low bits, A[1:0], choose the mode. The value 10b selects page addressing, and the datasheet lists it as the reset default SSD1306 datasheet, section 10.1.3. The driver sends 0x20 0x02 anyway, so the code does not depend on the reset value.

In page addressing, the column pointer goes up by one after each data byte. When it reaches the last column, it returns to the start column of the same page, and the page pointer does not change. The datasheet states this rule in section 10.1.3. To move to the next page, you must set the page and the column again. That is why the flush code below sends three positioning commands before each row of data.

The three positioning commands are these. Page start 0xB0 to 0xB7 selects the page (section 10.1.13). The low nibble of the column, 0x00 to 0x0F, is one command (section 10.1.1). The high nibble, 0x10 to 0x1F, is the other (section 10.1.2). Column 0 is therefore 0x00 and 0x10. Each command is one control byte plus one command byte, so each positioning step costs two bytes.

Worked example: how long a frame takes on the wire

Suppose you want to know whether a full redraw is affordable at 400 kbit/s, the fast mode the SSD1306 accepts. Count the bytes for one frame. For each page there are three commands. Each command is an address byte, a control byte and a command byte, so it costs three bytes, and three commands cost nine. The data for the page is an address byte, a 0x40 control byte and 128 pixel bytes, which is 130 bytes. One page is therefore 9 + 130 = 139 bytes.

For eight pages the total is 8 × 139 = 1,112 bytes. Each byte on I2C takes nine clock pulses, eight for the data bits and one for the acknowledge bit (lesson 60). So the frame needs 1,112 × 9 = 10,008 clock pulses. At 400,000 pulses per second, that takes 10,008 ÷ 400,000 = 0.025 s, or about 25 ms. That is about 40 frames per second if you sent them back to back, which is far more than a menu needs. The sensible rule is to redraw only when a button changes something.

The init sequence is the one in the pico-examples i2c/ssd1306_i2c driver, published under the BSD-3-Clause licence by Raspberry Pi. That example defaults to a 128 by 32 panel, so its multiplex and COM pin values are the 32-row ones. For a 128 by 64 panel the mux ratio is 0x3F (64 rows minus one), and the COM pin layout is 0x12. The example also uses horizontal addressing (0x20 0x00) and sends the whole buffer in one go. This driver uses page addressing so that each row can be sent on its own.

Concept 4: a 5 by 7 font is five column bytes

A character on this display is a glyph, a bitmap. The menu uses a 5 by 7 font: seven rows high and five columns wide. Each column is one byte, and bit 0 of each column is the top row. The capital L is therefore {0x7F, 0x40, 0x40, 0x40, 0x40}. In binary, 0x7F is 0111 1111, so the first column has all seven rows lit, which is the vertical stem. 0x40 is 0100 0000, which lights only bit 6, the bottom row. Each of the last four columns lights that bottom row, which makes the foot of the L.

Characters are drawn left to right with one blank column between them. Five columns plus the blank make a six-column advance, so the text "PRESSES" takes 7 × 6 = 42 columns. The font in this project defines only the characters the menu needs: the digits, the capitals in the menu words, a space, :, . and >. A character it does not know is drawn as a space. That is a deliberate choice, because it never reads past the table, but it also means a missing letter shows as a gap rather than an error.

Draw a character and read its column bytes, then place it on the panel and read the commands that put it there. The last line repeats the frame-time arithmetic for the text you type.

Concept 5: buttons, edges and a menu with callbacks

Each button is wired between a GPIO pin and ground, and the pin has its internal pull-up enabled pull-up resistor. The pin reads 1 when the button is released and 0 when it is pressed. The helper pressed() returns the inverse of the pin, so it is true while the button is held down.

A button stays down for a long time, but a menu should move one step per press. The code therefore reacts to the edge, the moment the state changes from released to pressed. It keeps the previous sample of each button and acts only when the current sample is pressed and the previous one was not. A held button then causes one step, however long it is held. Real switches also bounce for a few milliseconds when they close, which needs its own handling, covered in lesson 52. The buttons in this project have bounce set to 0.

The menu itself is a plain struct. It holds an array of items, the number of items, and a cursor index. Each item has a label and a callback, which is a function pointer of type menu_action_t. When the user selects an item, the menu calls the pointer. The menu does not need to know what an action does. Adding an item means adding one line to the array and one function. Lesson 49 covers how the call works.

The cursor must stay inside the array. Moving it down by one step is (cursor + 1) % count, which goes from 0 to 1 to 2 and then back to 0 for three items. A plain increment would reach 3, one past the end, and selecting that item would call a pointer read from memory outside the array. The starter project contains exactly that bug on purpose.

Worked example: one press of DOWN, step by step

Start with three items and the cursor at 0, which is BLINK. The main loop samples the buttons every 20 ms. The table shows what the code does on each sample, with down_prev as the value from the previous sample.

Then ssd1306_flush() sends the 1,024 bytes to the panel. The screen updates within about 45 ms of the press: up to 20 ms of polling, then the 25 ms transfer. If you press DOWN again on sample 5, the cursor moves to 2, and one more press gives (2 + 1) % 3 = 0, so the cursor wraps back to BLINK.

The code, explained line by line

The driver is three small files: ssd1306.c for the display, menu.c for the menu, and main.c for the buttons and the loop. The excerpts below are from the reference solution. Start with the one-command helper, which is the smallest unit of the protocol. 

static void send_cmd(uint8_t cmd) {
    uint8_t buf[2] = {CTRL_CMD, cmd};          /* 0x80: Co = 1, D/C# = 0 */
    i2c_write_blocking(s_bus, SSD1306_ADDR, buf, 2, false);
}

CTRL_CMD is 0x80, the control byte for one command. The buffer holds the control byte and the command, and i2c_write_blocking() sends them as one write. The last argument, false, means "send a STOP at the end". Each command is therefore its own complete transfer, which is simple and easy to see on a logic analyzer. The helper is static because nothing outside this file should send raw commands. 

static const uint8_t init[] = {
    0xAE,              /* display off while configuring */
    0xD5, 0x80,        /* clock divide ratio 1, default oscillator */
    0xA8, 0x3F,        /* multiplex ratio 64 (rows - 1) */
    0x20, 0x02,        /* memory addressing mode: page */
    0xA1,              /* segment remap: column 127 on SEG0 */
    0xC8,              /* COM scan from COM[N-1] down to COM0 */
    0xDA, 0x12,        /* COM pin layout for 128x64 */
    0xAF,              /* display on */
};

The init table is a list of command bytes, and each pair in it is a command with its argument. 0xAE turns the panel off while it is configured, and 0xAF turns it on at the end. 0xD5 0x80 sets the clock divide ratio to one. 0xA8 0x3F sets the multiplex ratio: the controller scans 64 rows, and the datasheet stores that as 63, which is 0x3F. 0x20 0x02 chooses page addressing, as described above. 0xA1 maps column 127 to segment 0, so that the picture is not mirrored on the panel. 0xC8 sets the scan direction, and 0xDA 0x12 selects the COM pin layout for this 128 by 64 panel (datasheet section 10.1.18). The table omits a few values that set contrast and timing, which the full file in the project includes. Each value is the one the reference driver uses, and the project's comments name the matching sections. 

void ssd1306_draw_char(uint8_t page, uint8_t x, char c) {
    if (page >= SSD1306_PAGES || x + CHAR_ADVANCE > SSD1306_WIDTH) {
        return;                       /* off the panel: drop it */
    }
    const uint8_t *cols = font_glyph(c);
    for (uint8_t i = 0; i < GLYPH_WIDTH; i++) {
        s_fb[page][x + i] = cols[i];        /* one column byte per RAM byte */
    }
    s_fb[page][x + GLYPH_WIDTH] = 0x00;     /* the blank column after the glyph */
}

The first if is the bounds check. s_fb is a fixed array of 8 pages by 128 columns, so a page or column outside it would write into some other variable's memory. The check uses CHAR_ADVANCE, which is six, so a character that would end past the right edge is dropped as a whole. The line font_glyph(c) returns a pointer to the five column bytes of the character. The loop copies them into the framebuffer, one byte per column. Each column byte goes to one RAM byte, which is why a glyph's bit 0 becomes the top pixel of the page. The last line writes the blank column that separates this character from the next one. 

void ssd1306_flush(void) {
    static uint8_t frame[1 + SSD1306_WIDTH];   /* the control byte, then one page */
    for (uint8_t page = 0; page < SSD1306_PAGES; page++) {
        send_cmd(CMD_PAGE_START | page);     /* 0xB0 | page */
        send_cmd(CMD_COL_LOW);               /* column 0, low nibble */
        send_cmd(CMD_COL_HIGH);              /* column 0, high nibble */
        frame[0] = CTRL_DATA;                /* 0x40: Co = 0, D/C# = 1 */
        memcpy(&frame[1], s_fb[page], SSD1306_WIDTH);
        i2c_write_blocking(s_bus, SSD1306_ADDR, frame, sizeof frame, false);
    }
}

Flush is the only function that moves pixels to the panel. For each of the eight pages it sends the three positioning commands, then one write holding the control byte and the 128 bytes of that page. The frame array is static so that the 129-byte buffer is not rebuilt on the stack each call. The memcpy() copies one page of the framebuffer into the frame, after the control byte. Because the control byte is 0x40, the panel reads every byte after it as pixels. Without that byte, the first pixel value would be read as a command. 

void menu_next(menu_t *m) {
    m->cursor = (uint8_t)((m->cursor + 1) % m->count);
}

This is the whole cursor logic. The modulo by count keeps the result between 0 and count - 1. The cast back to uint8_t keeps the type the struct uses. The menu does not check which item is selected. The action table is the only thing that decides what a selection does. 

bool down_now = pressed(BTN_DOWN);
if (down_now && !down_prev) {        /* falling edge: a new press only */
    menu_next(&s_menu);
    dirty = true;                  /* redraw after this iteration */
}
down_prev = down_now;

The loop copies the current sample into down_prev at the end of each pass, so the next pass can compare. The condition runs the step only on the pass where the button goes from released to pressed. The dirty flag separates input from output: the buttons set it, and the drawing code runs once per pass if it is set. That keeps the I2C bus idle when nothing has changed.

Try it in Wokwi

The project projects/0061-an-i2c-oled-display-and wires a board-ssd1306 display to GP4 (SDA) and GP5 (SCL), with 4.7 kΩ pull-ups as in lesson 60, and two pushbuttons: DOWN on GP14 and SELECT on GP15.   2. Build with Ctrl+Shift+B, then start the simulator with F1 → Wokwi: Start Simulator. The init and flush code is given, so the panel is powered and configured, but it stays blank: nothing has been drawn into the framebuffer yet.

  4. Write ssd1306_draw_text(). It calls ssd1306_draw_char() for each character and advances x by six. Stop at the end of the string or when the next character would not fit.
  5. Fix menu_next() in menu.c. The starter does a plain m->cursor++. Replace it with a modulo by m->count, and write a comment that says why the modulo keeps the cursor in range.

Hint for the glyph copy

The glyph has five columns. Copy them into s_fb[page][x + i], and leave x + 5 at zero. Check the page and x against the framebuffer's size first. The function already has a bounds check at the top, so you only need the copy.

Hint for the cursor

A modulo by the item count keeps the cursor in range, and it wraps by itself after the last item. Write m->cursor = (m->cursor + 1) % m->count; and check that the cast to uint8_t still fits.

Common mistakes and how to spot them

Most display bugs look like a blank or wrong screen, which tells you little on its own. The fastest route is to match the symptom to one of the cases below, then check the bus on a logic analyzer if the code does not explain it.

Mistake 1: sending pixels without the 0x40 control byte

Symptom: the screen stays blank, or it shows a scrambled pattern while the serial monitor says everything is fine. Cause: the first pixel byte is read as a command, because the panel expects a control byte before every write. Fix: keep frame[0] = CTRL_DATA in the flush loop, and check on the analyzer that every data write starts with 0x40.

Mistake 2: drawing into the framebuffer and never flushing

Symptom: the text exists in the framebuffer, but the screen shows the old picture or nothing. The logic analyzer shows the init commands and then no transfers at all. Cause: ssd1306_flush() was never called, or it was called only when dirty is set, and nothing set it. Fix: flush once per pass after the drawing, and set dirty = true in every branch that changes the menu.

Mistake 3: the segment remap is missing

Symptom: the picture comes out mirrored left to right, so text reads backwards. Cause: without 0xA1 the datasheet maps column 0 to SEG0, and the reference picture expects column 127 there (section 10.1.8). Fix: keep the remap in the init table, and do not change it without a reason. If you change the scan direction with 0xC8, check the remap as well.

Mistake 4: the cursor is incremented without a wrap

Symptom: after the last item, no row shows the > cursor, because menu_draw() only draws it on the row whose index equals the cursor, and the cursor is now past the last row. Pressing SELECT then calls whatever pointer sits past the array. Cause: the plain m->cursor++ from the starter. Fix: wrap with the item count, as in menu_next() above.

Mistake 5: reacting to the held level instead of the edge

Symptom: one press moves the cursor two or three items. Cause: the code tests if (down_now), which is true on every poll while the button is held. The poll runs every 20 ms, so a 100 ms press counts five times. Fix: keep the previous sample and act only when the current one is pressed and the previous one was not.

Mistake 6: a character missing from the font

Symptom: a letter does not appear, and the gap is exactly one character wide. Cause: font_glyph() returns the space glyph for any character it does not have, so nothing is drawn and nothing fails. Fix: add one five-byte entry to GLYPHS for the character, and check the bitmap bit by bit before you trust it.

In real projects

Professional display code has three layers. The controller driver does the init table, the flush and the primitives that write into the framebuffer. A graphics layer draws text, lines and fonts on top of it. The application layer holds the screens and the menu state. The menu in this lesson is in the third layer, and it never calls the I2C functions. That separation is what lets a reviewer test the cursor logic on a PC, with no display attached. From lesson 80 onward the course does exactly that with Unity and FFF.

A code reviewer of a display driver usually checks four things. Every write into the framebuffer has a bounds check, and the check is at the top of the function. Drawing never touches I2C directly, so the flush is the only place the bus is used. The init table matches the panel's datasheet and the module's COM layout, because many inexpensive modules differ in that one value. The redraw is driven by a dirty flag, so an idle screen costs no bus time.

The framebuffer costs 1 KB here, which is small against the RP2040's 264 kB of SRAM. A smaller microcontroller may not have that room, and then the driver must draw each page directly from a smaller buffer, or send one row at a time. The same datasheet also describes 4-wire SPI for the same controller (section 8.1.3). Lesson 62 covers that bus, and the framebuffer and flush pattern you wrote here carries over unchanged.

Summary

  • The SSD1306 keeps the picture in display RAM: 8 pages of 128 columns, one byte per column per page, with bit 0 at the top of each page.
  • The address is 0x3C, which is 0x78 on the wire for a write. The control byte is 0x80 before a command and 0x40 before pixel data.
  • Page addressing (0x20 0x02) needs a page start (0xB0 plus the page), and a column low and high nibble, for each page. The column pointer wraps within the page.
  • Draw into a 1 KB framebuffer, then flush page by page. A full flush is about 1,112 bytes on the wire, about 25 ms at 400 kbit/s.
  • A 5 by 7 glyph is five column bytes, with bit 0 at the top. A character missing from the font draws as a space.
  • A menu holds items with function-pointer actions. Wrap the cursor with a modulo by the item count, and act on the falling edge of a button.
You drew text on an OLED you wrote the driver for, with the control byte, page addressing and a framebuffer, and you drove a menu from two buttons with callbacks. The same framebuffer and flush pattern works for other SSD1306 and SH1106 panels, with the init table adjusted to the panel.
