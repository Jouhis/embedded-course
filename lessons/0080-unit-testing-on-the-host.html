Unit testing on the host with Unity; TDD for firmware

Flashing a board to check one line of logic takes minutes. A unit test on your PC takes a fraction of a second, and it runs the same code every time. This lesson shows how to split logic from hardware so that it can be tested, and how to write the test first.

By the end of this lesson you can write a failing Unity test for a small module, make it pass with the simplest code, and run the whole suite on the PC with one command.

The idea: logic without hardware

Most firmware bugs are in logic: a debounce that counts wrong, a state machine that misses a transition, a conversion that overflows. Logic that touches a pin is hard to test, because the test needs the board. The fix is to separate the two. A module takes numbers in and returns numbers out, and the code that reads the pin is a thin layer above it. The debounce in this lesson takes a raw level and returns a stable level, and it never reads a pin.

That separation makes the logic run on any target. The same .c file compiles with the PC's gcc for the tests and with the ARM toolchain for the board. The term for this is dual targeting (see the glossary), and James Grenning's book on test-driven development for embedded C is the reference for the practice (Grenning, Test-Driven Development for Embedded C, Pragmatic).

Unity: asserts and fixtures

Unity is a unit-test framework written in plain C, so it compiles with the PC's gcc and with the ARM compiler alike (Unity, Throw The Switch). A test is a function. It checks results with an assert, and Unity reports the first failure with its file and line. Unity has typed assert macros, such as TEST_ASSERT_EQUAL_INT for an int and TEST_ASSERT_EQUAL_UINT8 for a byte, so the comparison has the right width.

Two functions run around each test. setUp() runs before every test, so each test starts from a known state, and tearDown() runs after it. main() lists the tests with RUN_TEST between UNITY_BEGIN() and UNITY_END(). 

static debounce_t d;
void setUp(void) { debounce_init(&d); }    /* a fresh state before every test */
void tearDown(void) { }

static void test_three_presses_confirm(void) {
    debounce_update(&d, 1);
    debounce_update(&d, 1);
    TEST_ASSERT_EQUAL_UINT8(1, debounce_update(&d, 1));  /* the third sample confirms */
}

Red, green, refactor

Test-driven development repeats three steps. Red: write a test for one behaviour, and run it to see it fail. Green: write the simplest code that makes it pass, even if the code is ugly. Refactor: clean the code while the tests stay green. The failing test is the proof that the test can fail, and a test that was never red may pass for the wrong reason.

Start with the behaviour you want, not with the data structure. The test "three presses confirm" says what the debounce is for. The integrator is an implementation choice that the test does not need to know about.

Host and target together

The host run checks the logic, and the board run checks the pins, the clocks and the timing. Neither replaces the other. Host tests run in a fraction of a second, so you run them after every change. Lesson 81 adds fakes, which replace a hardware function with a function the test controls, and lesson 82 runs these tests in continuous integration. CMock is the other common tool for generating fakes. It needs Ruby, which is not installed on the workspace PC, so this course uses FFF for the hands-on mocks in lesson 81.

What a unit test is, and why it helps beginners

A unit test runs one small piece of code with chosen inputs and checks the output against an expected value. For a beginner, the useful part is the feedback loop. A change to the debounce takes a second to check on the PC. The same change on the Blue Pill means editing main.c, building, flashing, pressing the button, and reading the serial monitor, which can take minutes and depends on the wiring. A fast loop lets you try ten ideas in the time one board run takes.

The other benefit is that a test records a behaviour. Once "three presses confirm the press" is a test, nobody can break it without seeing a red line, even years later.

The concepts, one at a time

Assert

An assert in a test is a check that stops the test with a message when a value is wrong. Unity provides a family of them. TEST_ASSERT_EQUAL_UINT8(expected, actual) compares two 8-bit values. The macro is written for one width on purpose: a comparison of a uint8_t with an int can hide a truncation, and the typed form makes the width part of the test. The macros are defined in third_party/Unity/src/unity.h, which is where you look when you want to know exactly what an assert does.

Test fixture: setUp and tearDown

A fixture is the state that a test needs before it runs. Unity calls setUp() before each test, and tearDown() after it. The debounce test puts a debounce_t in a static variable and resets it in setUp(). Without the reset, the test that runs second would start with the count left over from the first, and a failure would depend on the order of the tests. The rule is that each test starts from the same state, which the fixture guarantees.

Red, green, refactor

Test-driven development (TDD) orders the work as three steps. In the red step you write a test that fails, and you watch it fail, because a test that has never failed may not test anything. In the green step you write the simplest code that passes, even if it is ugly. In the refactor step you clean the code and keep the tests green. The starter project is at the red step, and the hands-on task is the green step, with the refactor at the end.

Dual targeting

Dual targeting means that the same source file builds for two targets: the PC, for tests, and the board, for the product. The debounce module in src/debounce.c includes only its own header debounce.h, which includes stdint.h. It never names a register or an SDK function, so the PC compiler accepts it without change. The pin code lives in a separate file that only the board build links.

A worked example: the red step, with the real output

Run the starter's tests and look at the three failures. They come from the lines of the debounce function that the starter leaves empty. The output from the starter, which is produced by the commands in the hands-on task, shows the first failure as test_three_presses_confirm_the_press:FAIL: Expected 1 Was 0. Read the test to see why. It calls debounce_update() three times with a high input, and then asserts that the third call returns 1. The starter returns 0 from every call, so the third assert sees 0. The message names the file, the line, the test, the expected value and the actual value. You do not need a debugger to see what went wrong.

Now trace the solution's rule for the same three calls, with the numbers. The count starts at 0 and stable at 0. The first high input raises the count to 1, which is below DEBOUNCE_MAX, so the output stays 0. The second raises it to 2, still 0. The third raises it to 3, which equals DEBOUNCE_MAX, so stable becomes 1 and the function returns 1. The assert passes. The value 3 is the only thing the test depends on, through the constant. That is why the test uses the name, not the literal 3.

The suite then runs seven tests, and the summary line says 7 Tests 0 Failures 0 Ignored. The starter's run ends with 7 Tests 3 Failures 0 Ignored. The three failures are the three tests that expect a press or a release to be confirmed, which is what the starter cannot yet do.

The code, line by line

The test file has one pattern in every test, and the first test shows it.

  1. static void test_starts_released(void) declares a test as a static function. A test is not called by any code except main(), so static keeps its name out of the rest of the program.
  2. TEST_ASSERT_EQUAL_UINT8(0, debounce_update(&d, 0)); calls the function under test once, with a low input, and asserts that the result is 0. The call is inside the assert, so the value is checked as soon as it is returned.
  3. RUN_TEST(test_starts_released); in main() runs the function, catches the first failed assert, prints the result and counts it. Unity's UNITY_END() returns the number of failures, and main() returns it, so CTest sees a failing exit code.

The debounce function itself is short, and the test file is where most of the thinking goes. A learner who writes the test first has already decided what the function must do, which is the point of the discipline.

Common mistakes and how to spot them

  1. The test never fails. A test is written after the code and passes at once. The symptom is a green suite that has never been red, and a test that still passes after the code is deleted. The fix is to run the test before writing the code and see it fail, or to break the code on purpose and check that the test notices.
  2. The tests share state. A test relies on the count left by the one before it, which happens when setUp() is empty. The symptom is that the suite passes in one order and fails when a test is moved. The fix is to reset every static in setUp(), as the debounce test does with debounce_init().
  3. The test asserts the implementation. A test checks that the integrator equals 3 after three presses, using a field name, so every refactor breaks it. The symptom is a red suite after a rename, with no change in behaviour. The fix is to assert the output of the function, which is the behaviour the rest of the program depends on.
  4. The unit reads a pin. A developer adds gpio_get() to the module to make the test simpler. The PC build fails with a missing header, which is the early warning. The fix is to pass the raw level in as an argument, as the module does now.

In real projects

Test suites are the first thing a firmware team checks in a continuous integration run, and the lesson on CI (lesson 82) runs the host tests on every commit. Teams separate the logic from the hardware so that the logic is testable, and they keep the hardware layer thin and check it on the board. An interviewer who asks how you test hardware code is listening for that split. The strongest answer names the seam: the module takes values in and returns values out, the fake replaces the hardware call in the test, and the board run checks the timing that only the board has.

Summary

  • A unit test runs one piece of logic on the PC in a fraction of a second, and it records a behaviour.
  • Use typed asserts such as TEST_ASSERT_EQUAL_UINT8, and read their definitions in unity.h when in doubt.
  • setUp() resets the fixture before every test, so tests do not depend on each other.
  • Red, green, refactor: see the test fail, make it pass with the simplest code, then clean up with the tests green.
  • Dual targeting: the logic has no hardware in it, so the same file builds for the PC and the board.
  • Read the Unity summary line and the CTest result. Zero failures and OK mean the suite passed.

Try it on the PC

The project is projects/0080-debounce-tdd. It is a host-test project: no Wokwi and no board, only the PC's gcc, Unity, and CTest. The starter has the debounce header, an empty debounce_update() marked TODO(learner), and seven tests. Three of the tests fail on the starter, by design.

  1. From the workspace root, run the starter's tests: python -I tools/build.py projects/0080-debounce-tdd/starter --test. Three tests fail. The output names them, and ends with 0% tests passed, 1 tests failed out of 1.
  2. Read the three failing tests in test/test_debounce.c. Each names a behaviour: a press needs three samples, a release needs three lows, and a bounce during a press keeps it pressed.
  3. Your task: in src/debounce.c, implement debounce_update(). Keep the integrator in d->count. Count up on a high sample and down on a low one, stop at DEBOUNCE_MAX and at 0, and set d->stable only at those two ends. Return d->stable.
  4. Run the tests again with the same command. You will know it works when the output ends with 100% tests passed out of 1, and the Unity summary above it reads 7 Tests 0 Failures 0 Ignored followed by OK.
  5. Refactor: rename the variables if the names are unclear, and keep the tests green after each change. Then run the command once more.
Hint for the two ends of the integrator

The stable level must change only when the count reaches DEBOUNCE_MAX (becomes 1) or 0 (becomes 0). Between the two ends, the output keeps its old value. Test that rule with the bounce test before you change anything else.

Hint if the release test fails

Check the release with the counter at the top. After three presses the count is DEBOUNCE_MAX, so the stable level stays 1 until the count falls to 0. Count the lows by hand: the first two keep the press, and the third releases it.

The reference solution is in projects/0080-debounce-tdd/solution. Its tests pass, and it prints 7 Tests 0 Failures 0 Ignored and OK. Try first, compare after.

Model answer

I keep the logic in plain C modules that take values in and return values out, with no register or SDK call inside them. Those modules compile on the PC with a unit-test framework, so I can write a failing test first and run the whole suite in a fraction of a second. Where the logic has to call hardware, the test replaces that call with a fake that records the call and returns a value I choose. The board-side layer is thin, and I test it on the target with a small set of tests, because the clock, the timing and the electrical behaviour exist only there.
