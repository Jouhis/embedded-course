Unit testing on the host with Unity; TDD for firmware

Firmware logic tested on the PC

By the end of this lesson you can write a failing Unity test for a small module, make it pass with the simplest code, and run the whole suite on the PC with one command.

Unit tests and a fast feedback loop

A unit test runs one small piece of code with chosen inputs and checks the output against an expected value, and its most useful part is the feedback loop. A change to the debounce takes a second to check on the PC, whereas on the Blue Pill the same change means editing main.c, building, flashing, pressing the button and reading the serial monitor, which can take minutes and depends on the wiring, so the fast loop lets you try ten ideas in the time one board run takes.

A test also records a behaviour, so that once "three presses confirm the press" is a test, nobody can break it without seeing a red line, even years later.

Typed asserts in Unity

An assert in a test is a check that stops the test with a message when a value is wrong, and Unity provides a family of them, TEST_ASSERT_EQUAL_UINT8(expected, actual), for example, comparing two 8-bit values. The macro is written for one width on purpose, because comparing a uint8_t with an int can hide a truncation, whereas the typed form makes the width part of the test, and the macros are defined in third_party/Unity/src/unity.h, which shows exactly what each assert does.

Test fixtures with setUp and tearDown

A fixture is the state a test needs before it runs, Unity calling setUp() before each test and tearDown() after it. The debounce test keeps a debounce_t in a static variable and resets it in setUp(), without which the second test would start with the count left over from the first and a failure would depend on the order of the tests, so the fixture guarantees that each test starts from the same state.

Red, green and refactor in test-driven development

Test-driven development (TDD) orders the work in three steps. In the red step you write a test that fails and watch it fail, because a test that has never failed may not test anything, in the green step you write the simplest code that passes, however ugly, and in the refactor step you clean the code while keeping the tests green. The starter project stands at the red step, the hands-on task is the green step and the refactor comes at the end.

The work starts from the behaviour wanted, the test "three presses confirm" saying what the debounce is for, while the integrator is an implementation choice that the test does not need to know about.

Dual targeting of plain C modules

Dual targeting means that the same source file builds for two targets, the PC for tests and the board for the product. The debounce module in src/debounce.c includes only its own header debounce.h, which includes stdint.h, and never names a register or an SDK function, so the PC compiler accepts it unchanged, while the pin code lives in a separate file that only the board build links.

Separating logic from hardware

Most firmware bugs lie in logic, a debounce that counts wrong, a state machine that misses a transition or a conversion that overflows, and logic that touches a pin is hard to test, because the test needs the board. The fix separates the two, a module taking numbers in and returning numbers out while a thin layer above it reads the pin, so the debounce in this lesson takes a raw level and returns a stable level without ever reading a pin.

That separation lets the logic run on any target, the same .c file compiling with the PC's gcc for the tests and with the ARM toolchain for the board, which is the practice of dual targeting (see the glossary), for which James Grenning's book on test-driven development for embedded C is a standard reference (Grenning, Test-Driven Development for Embedded C, Pragmatic).

A host test resembles a flight simulator, in which the pilot, your logic, practises every emergency safely and in seconds without an aircraft. The comparison breaks because a simulator cannot show everything, such as how the real board behaves with noise on a pin, so the test flight on the board still happens, only with far fewer surprises.

The Unity test framework

Unity is a unit-test framework written in plain C, so it compiles with the PC's gcc and the ARM compiler alike (Unity, Throw The Switch). A test is a function that checks results with asserts, Unity reporting the first failure with its file and line, and the typed assert macros, such as TEST_ASSERT_EQUAL_INT for an int and TEST_ASSERT_EQUAL_UINT8 for a byte, give each comparison the right width.

Two functions run around each test, setUp() before every test, so that each starts from a known state, and tearDown() after it, while main() lists the tests with RUN_TEST between UNITY_BEGIN() and UNITY_END(). 

static debounce_t d;
void setUp(void) { debounce_init(&d); }    /* a fresh state before every test */
void tearDown(void) { }

static void test_three_presses_confirm(void) {
    debounce_update(&d, 1);
    debounce_update(&d, 1);
    TEST_ASSERT_EQUAL_UINT8(1, debounce_update(&d, 1));  /* the third sample confirms */
}

Host runs and target runs together

The host run checks the logic and the board run the pins, the clocks and the timing, neither replacing the other, and since host tests take a fraction of a second, they run after every change. Lesson 81 adds fakes, which replace a hardware function with one the test controls, and lesson 82 runs these tests in continuous integration. CMock is the other common tool for generating fakes. It needs Ruby, which is not installed on the workspace PC, so this course uses FFF for the hands-on mocks in lesson 81.

Worked example: the red step and its output

Running the starter's tests produces three failures, coming from the lines of the debounce function that the starter leaves empty. The first, from the commands of the hands-on task, reads test_three_presses_confirm_the_press:FAIL: Expected 1 Was 0, and before reading the test, predict which value the starter's debounce_update() returned on the third call.

The test calls debounce_update() three times with a high input and asserts that the third call returns 1, while the starter returns 0 from every call, so the third assert sees 0. The message names the file, the line, the test, the expected value and the actual value, so no debugger is needed to see what went wrong.

  1. Start. In the solution's rule the count starts at 0 and stable at 0.
  2. First high input. The count rises to 1, below DEBOUNCE_MAX, so the output stays 0.
  3. Second high input. The count rises to 2, and the output is still 0.
  4. Third high input. The count rises to 3, equal to DEBOUNCE_MAX, so stable becomes 1, the function returns 1 and the assert passes.

The value 3 is the only thing the test depends on, through the constant, which is why the test uses the name rather than the literal 3. The suite runs seven tests, the solution's summary line reading 7 Tests 0 Failures 0 Ignored and the starter's ending with 7 Tests 3 Failures 0 Ignored, the three failures being the tests that expect a press or a release to be confirmed, which the starter cannot yet do.

The test file line by line

Every test in the file follows one pattern, which the first test shows.

  1. static void test_starts_released(void) declares a test as a static function, since no code but main() calls it, so static keeps its name out of the rest of the program.
  2. TEST_ASSERT_EQUAL_UINT8(0, debounce_update(&d, 0)); calls the function under test once with a low input and asserts that the result is 0, the call sitting inside the assert so that the value is checked as soon as it is returned.
  3. RUN_TEST(test_starts_released); in main() runs the function, catches the first failed assert, prints the result and counts it, and since Unity's UNITY_END() returns the number of failures, which main() returns in turn, CTest sees a failing exit code.

The debounce function itself is short, and most of the thinking goes into the test file, because a learner who writes the test first has already decided what the function must do, which is the point of the discipline.

Try it on the PC

The project is projects/0080-debounce-tdd, a host-test project with no Wokwi and no board, only the PC's gcc, Unity and CTest. The starter has the debounce header, an empty debounce_update() marked TODO(learner) and seven tests, three of which fail on the starter by design.

  1. From the workspace root, run the starter's tests with python -I tools/build.py projects/0080-debounce-tdd/starter --test, and three tests fail, the output naming them and ending with 0% tests passed, 1 tests failed out of 1.
  2. Read the three failing tests in test/test_debounce.c, each naming a behaviour, a press needing three samples, a release three lows and a bounce during a press keeping it pressed.
  3. In src/debounce.c, implement debounce_update(), keeping the integrator in d->count, counting up on a high sample and down on a low one, stopping at DEBOUNCE_MAX and at 0, setting d->stable only at those two ends and returning d->stable.
  4. Run the tests again with the same command, and the implementation works when the output ends with 100% tests passed out of 1 and the Unity summary above it reads 7 Tests 0 Failures 0 Ignored followed by OK.
  5. Refactor by renaming any unclear variables while keeping the tests green after each change, then run the command once more.
Hint for the two ends of the integrator

The stable level must change only when the count reaches DEBOUNCE_MAX (becoming 1) or 0 (becoming 0), the output keeping its old value between the two ends, and the bounce test checks that rule before anything else changes.

Hint if the release test fails

Check the release with the counter at the top, since after three presses the count is DEBOUNCE_MAX and the stable level stays 1 until the count falls to 0. Counting the lows by hand, the first two keep the press and the third releases it.

The reference solution is in projects/0080-debounce-tdd/solution, whose tests pass with 7 Tests 0 Failures 0 Ignored and OK, so try first and compare afterwards.

You wrote a unit test that failed first, made it pass and ran the whole suite on the PC with one command, without a board.

Common mistakes and how to spot them

A test that never fails

The suite has never been red and a test still passes after the code is deleted, because the test was written after the code and passed at once. Run the test before writing the code and watch it fail, or break the code on purpose and check that the test notices.

Tests that share state

The suite passes in one order and fails when a test is moved, because a test relies on the count left by the one before it, as happens when setUp() is empty. Reset every static in setUp(), as the debounce test does with debounce_init().

A test that asserts the implementation

The suite turns red after a rename with no change in behaviour, because a test checks through a field name that the integrator equals 3 after three presses, so every refactor breaks it. Assert the function's output, the behaviour the rest of the program depends on.

A unit that reads a pin

The PC build fails with a missing header, an early warning that a developer added gpio_get() to the module to simplify the test. Pass the raw level in as an argument, as the module does now.

Host test suites in firmware teams

Test suites are the first thing a firmware team checks in a continuous integration run, and the CI lesson (lesson 82) runs the host tests on every commit. Teams separate the logic from the hardware so that the logic is testable, keeping the hardware layer thin and checking it on the board, and the split rests on a seam, the module taking values in and returning values out while a fake replaces the hardware call in the test and the board run checks the timing that only the board has.

Summary

  • A unit test runs one piece of logic on the PC in a fraction of a second and records a behaviour.
  • Typed asserts such as TEST_ASSERT_EQUAL_UINT8 check the width, and their definitions in unity.h settle any doubt.
  • setUp() resets the fixture before every test, so tests do not depend on each other.
  • In red, green and refactor the test fails first, the simplest code makes it pass, and the clean-up keeps the tests green.
  • In dual targeting the logic contains no hardware, so the same file builds for the PC and the board.
  • Zero failures with OK in the Unity summary line and a passing CTest result mean the suite passed.
