Capstone 4: heater PWM, buttons, display, and safety checks

Outputs, inputs and tested safety rules

By the end of this lesson you can work out a timer's PWM period and duty from its prescaler, auto-reload and compare values, explain why a debounced button gives one event per press, and write a safety check that passes one host test per rule.

Acting on the temperature

Lesson 115 turned the ADC code into hundredths of a degree and tested the conversion on the PC, and this lesson adds the parts that act on the number, a timer output switching the heater, the start and material buttons becoming events, the OLED showing four lines of text and the safety checks deciding whether the heater must be cut. Requirements 1.3 and 1.4 in the Capstone 1 table ask for the button and the display, and requirements 2.1 to 2.4 are the four safety rules.

Each part can fail in a way that looks correct on the screen, a button read as a raw level advancing a preset several times per press and a safety rule with a wrong boundary letting a fault through by one count. The hardware ideas come from lesson 59 (PWM), lesson 71 (timers), lesson 52 (debounce), lesson 61 (the I2C OLED) and lesson 56 (state machines).

Bang-bang control and the duty cycle

The heater controller in app/control.c is a bang-bang controller with hysteresis, a bang-bang controller having two outputs, full power or none, and with hysteresis it switches the heater fully on when the chamber is more than a band below the setpoint and fully off when it is more than the band above it, keeping its previous state inside the band. The band is set by CONTROL_HYST_CENTI, which is 100, or 1.00 °C, and this dead band stops the output from chattering on and off each time the temperature crosses the setpoint, the same hysteresis idea that keeps a thermostat from clicking.

Bang-bang is easy to test but overshoots, because the heater runs at full power until the chamber is already past the setpoint, so lesson 117 replaces it with a PID controller, which lowers the power before the setpoint is reached, although either controller still needs a way to set the power, which is pulse-width modulation.

Pulse-width modulation (PWM) switches the output on and off with a fixed period, the fraction of each period that the output is high being the duty cycle, so a 70 % duty gives 70 % of the average power, because the heater's temperature responds to the average rather than to each switch. The heater's temperature changes over tens of seconds, so a switching rate of 1 kHz is far faster than the chamber can respond and leaves a wide margin for the controller's sample rate.

The timer and its compare register

A timer is a counter that counts clock ticks and compares its count with registers, three of which set the PWM output on the Blue Pill's TIM3, channel 1, pin PA6.

  • The prescaler (PSC) divides the timer clock. The counter moves once every PSC + 1 input ticks.
  • The auto-reload value (ARR) is the top of the count. The counter runs from 0 up to ARR and then starts again at 0, so one period has ARR + 1 steps.
  • The compare register (CCR) sets where the output changes. In PWM mode 1, the output is high while the counter is below the compare value, and low from then until the period ends.

The board file assumes an 8 MHz timer clock, the Blue Pill running after reset from its internal 8 MHz oscillator, which lesson 67 introduced and which the board file does not change, and the period follows as

TPWM = (PSC + 1) × (ARR + 1) ÷ fclk(1)

where fclk is the timer clock, so a prescaler of 7 divides the 8 MHz clock by 8, giving a counter clock of 1 MHz, and an auto-reload of 999 counts 1000 steps, making the period 1000 ÷ 1 MHz = 1 ms, which is 1 kHz. The output is high while the count is below CCR, so a compare value of 0 is always low and one of 1000 always high, because the counter never reaches 1000, endpoints that need no special case, so the driver can accept any duty from 0 to 1000 and pass it straight to the register, in permille, 0.1 % per step.

Worked example: one PWM period

A duty of 250 permille, 25 %, shows how the compare value shapes one period. Before following the steps, predict how long the output stays high.

  1. The compare value. The driver writes 250 to the compare register, and each period has 1000 counter steps, numbered 0 to 999, each lasting 1 µs, because the counter clock is 1 MHz.
  2. The high part. For steps 0 to 249 the counter is below 250, so the output is high for 250 µs.
  3. The low part. For steps 250 to 999 the output is low for 750 µs.
  4. The duty. The period is 1 ms and the high time 0.25 ms, so the duty is 0.25 ms ÷ 1 ms = 25 %, while writing 500 would give 50 % and writing 1000 would keep the output high for every step.

The same method gives the value for any other frequency, a fan driver on the same 1 MHz counter clock needing 1 MHz ÷ 25 kHz = 40 ticks per period and so an auto-reload of 39, which you can check in the quiz below.

The PWM setup in the board file

The board file sets up the timer with a few register writes, these lines from hw/hal_bluepill.c appearing in the order the file writes them. 

TIM3->PSC = PWM_PSC;                 /* 7: divide the 8 MHz clock by 8 */
TIM3->ARR = PWM_ARR;                 /* 999: the counter runs from 0 to 999 */
TIM3->CCMR1 = (6U << 4) | TIM_CCMR1_OC1PE;   /* OC1M = 110 (PWM mode 1), preload on */
TIM3->CCER = TIM_CCER_CC1E;          /* let channel 1 drive its output pin */
TIM3->CCR1 = 0U;                     /* start with the heater off */
TIM3->CR1 = TIM_CR1_ARPE;            /* buffer ARR until the next period */
TIM3->EGR = TIM_EGR_UG;              /* load the buffered values now */
TIM3->CR1 |= TIM_CR1_CEN;            /* start counting */

The first two lines are the arithmetic above, PWM_PSC being 7, which makes the counter clock 1 MHz, and PWM_ARR 999, which makes the period 1 kHz, while the third line selects the output mode, the OC1M field, shifted into place with << 4, holding 110, PWM mode 1. The preload bit OC1PE makes a new compare value take effect at the start of the next period instead of in the middle of one, which prevents a short or long pulse when the duty changes.

The fourth line connects channel 1 to its pin and the fifth sets the compare value to 0, so that the heater is off at reset, while ARPE buffers the auto-reload value as the preload bit buffers the compare value, and the update event written to EGR copies the buffered values into the working registers at once, so that the first period starts with the values written. Only then does CEN start the counter, the values being loaded first and the counter started last, because starting it earlier can run a first period with values not yet in place.

The driver function setting the power is short, clamping the duty to 1000 and writing the compare register. 

void hal_heater_set_permille(uint16_t permille) {
    if (permille > 1000U) {
        permille = 1000U;
    }
    /* CCR above ARR keeps the output high for the whole period, so 1000 is a constant full power. */
    TIM3->CCR1 = permille;
}

The clamp protects the duty cycle from a caller asking for more than 100 %, and the write needs no other special case at the ends. The heater's timer is the one from lesson 71, so the configurator below starts at PSC 7 and ARR 999, 1 kHz, and you can set CCR1 for the duty you want, then load the fan preset and check the 40-tick period.

Debounced buttons and press events

A mechanical button bounces for a few milliseconds when it closes and when it opens, so a raw read in a loop sees several presses for one push, which an integrator debounce (lesson 52) fixes by counting up while the raw level reads pressed and down while it reads released, the output changing only when the count reaches its limit, here 3 for pressed, and returning to 0 for released. A bounce shorter than the window therefore never reaches the output, and the module lives in app/debounce.c, with its own host test in test/test_debounce.c.

The buttons go to ground through an internal pull-up, so the pin reads 1 when the button is open and 0 when it is pressed, an active-low input that the board file inverts, so that hal_button_pressed() returns 1 for a press.

The integrator on bouncing and clean presses

The button is sampled every 20 ms in the superloop, the BUTTON_PERIOD_MS value in main.c, and the raw samples from the bounce test in test/test_drivers.c, 1, 0, 1, 0, 1, 0, make a bouncing press whose count goes 1, 0, 1, 0, 1, 0, never reaching 3, so the output stays released and no event is raised.

A clean press with samples 1, 1, 1, 1, taken at 0, 20, 40 and 60 ms, makes the count go 1, 2, 3, the output becoming pressed on the third sample, at 40 ms, which is one event, while the fourth sample adds nothing, because the count saturates at 3. Holding the button for ten seconds still gives one event, because the event follows the change rather than the level.

The press-event code

The button driver turns the debounced level into an event, in these lines of buttons_sample(). 

void buttons_sample(buttons_t *b) {
    uint8_t start_before = b->start.stable;
    uint8_t material_before = b->material.stable;
    uint8_t start_now = debounce_update(&b->start, hal_button_pressed(HAL_BUTTON_START));
    uint8_t material_now = debounce_update(&b->material, hal_button_pressed(HAL_BUTTON_MATERIAL));
    if (start_now && !start_before) {
        b->start_event = true;
    }
    if (material_now && !material_before) {
        b->material_event = true;
    }
}

The first two lines save the debounced level from before this sample and the next two feed the raw level into the integrator, an order that matters, because the old level must be saved before the update, while the two if statements raise an event only when the new level is 1 and the old level was 0, the edge from released to pressed, so a held button, keeping the level at 1, raises no further event.

The control step reads the flag through buttons_take_start(), which returns and clears it, so two presses between two control steps collapse into one flag, and the material button has its own flag, so pressing one never consumes the other.

The SSD1306 display driver

The SSD1306 driver and its 5 × 7 font come from the Lab 5 code, the font table being the one from that lab extended with the F, G, H, W, Y and percent glyphs the status screen needs, in the same format as the others, one byte per column with bit 0 as the top row. The driver draws into a 1 KB framebuffer in RAM and sends the whole buffer over I2C with display_flush().

Drawing changes only the framebuffer, which is in RAM and fast, whereas the flush is the slow part, the framebuffer being 128 × 64 ÷ 8 = 1024 bytes, because each pixel is one bit, and on I2C each byte taking nine bit times, eight data bits and one acknowledge bit, so at 100 kHz 1024 × 9 ÷ 100 000 = 0.092 s and the data alone takes about 92 ms, a figure lesson 117 has to schedule around.

Text is drawn with a 5 × 7 glyph and one blank column, 6 pixels per character, so on a line 128 pixels wide 128 ÷ 6 = 21.3 and 21 whole characters fit, which is why the text builder fills lines of 21 characters, the array UI_LINE_CHARS being 22, 21 characters plus the terminating NUL byte, which is not drawn.

The text itself is built by ui_compose(), a pure function taking the dryer state and the temperature and filling four strings without any display call, so that the host test test/test_ui.c can check every line exactly, which matters because the learner reads those strings on the screen, the test also checking that the longest line fits in 21 characters. The superloop calls the draw function below, from main.c, every 200 ms. 

static void draw(void) {
    char lines[UI_LINES][UI_LINE_CHARS];
    dryer_out_t out;
    dryer_in_t none = { 0 };
    dryer_step(&dryer, &none, &out);     /* a refresh with no press: the state does not change */
    ui_compose(&dryer, &out, last_temp, last_sensor_ok, lines);
    display_clear();
    for (uint8_t i = 0; i < UI_LINES; i++) {
        display_text((uint8_t)(i * 2u), 0u, lines[i]);
    }
    (void)display_flush();
}

The dryer_step() call passes an empty input, so the state machine recomputes its outputs without changing state, as the comment says, because a draw that calls into the state machine is easy to misread, and ui_compose() builds the four lines, which the loop writes at pages 0, 2, 4 and 6. A page is 8 pixels high, so a text row on every second page leaves a blank page between lines, and the flush sends the 1 KB buffer to the panel.

The superloop itself is short, running three jobs at their own periods with the millisecond clock. 

uint32_t now = hal_millis();
if ((int32_t)(now - next_btn) >= 0) {
    next_btn += BUTTON_PERIOD_MS;
    buttons_sample(&buttons);
}

Each job keeps its own next deadline and moves it forward by its period when it runs, and although the clock wraps after about 49.7 days (the comment in hal.h), the unsigned subtraction stays correct after a wrap, the signed cast making it negative while the deadline is in the future, the same rule the runaway timer uses.

Safety checks as tested pure logic

safety_check() returns the first fault it finds, checking the rules in a fixed order, the sensor, the over-temperature cutoff, the stale sample and then the heater runaway, and it takes its inputs as a struct, so that a test can supply any temperature, age or heater state without a heater or a clock. The state machine in dryer.c latches whatever the check returns into the FAULT state, and the heater is cut in the same control step.

The runaway rule follows the idea of Klipper's verify_heater option, whose configuration reference gives the default heating gain as 2, the check time as 20 seconds for extruders and 60 seconds for the heater bed and the hysteresis as 5 (klipper3d.org Config_Reference, [verify_heater]), while the dryer uses a 2 °C gain, a 60 s window and a 5 °C band, which fits a chamber with more thermal mass than a nozzle. The rule is that while the heater is at full power and well below the setpoint, the temperature must rise by 2 °C within the window, a rise restarting the window, so a heater that does not rise trips the fault.

The top-level function of the reference app/safety.c calls the checks in order. 

fault_t safety_check(const safety_in_t *in, runaway_t *r) {
    if (!in->sensor_ok) {
        return FAULT_SENSOR;
    }
    if (in->temp_centi >= SAFETY_CUTOFF_CENTI) {
        return FAULT_OVERTEMP;
    }
    if (in->sample_age_ms > SAFETY_STALE_MS) {
        return FAULT_STALE;
    }
    return runaway_check(in, r);
}

The order is deliberate, a bad sensor making the temperature meaningless, so it goes first, while the runaway rule goes last, because it needs the others to be clean, and since each if returns at once, the first fault wins. The cutoff uses >=, so a reading of exactly 90.00 °C is a fault, as requirement 2.1 says. The runaway check has state, so it takes the window record r as well as the inputs. 

static fault_t runaway_check(const safety_in_t *in, runaway_t *r) {
    bool far_below = in->temp_centi < in->setpoint_centi - SAFETY_RUNAWAY_BAND_CENTI;
    if (!in->heater_enabled || !in->heater_full || !far_below) {
        runaway_reset(r);
        return FAULT_NONE;
    }
    if (!r->armed) {
        r->armed = true;
        r->ref_ms = in->now_ms;
        r->ref_centi = in->temp_centi;
        return FAULT_NONE;
    }
    if (in->temp_centi >= r->ref_centi + SAFETY_RUNAWAY_GAIN_CENTI) {
        r->ref_ms = in->now_ms;
        r->ref_centi = in->temp_centi;
        return FAULT_NONE;
    }
    if (in->now_ms - r->ref_ms >= SAFETY_RUNAWAY_MS) {
        return FAULT_RUNAWAY;
    }
    return FAULT_NONE;
}

The first if asks whether the rule applies at all, which it does only while the state machine wants heat, the heater is at full power and the chamber is more than 5 °C below the setpoint, any other case resetting the window and returning no fault, because a heater not at full power is not being tested. The first applicable sample arms the window and records the time and the temperature, and each later sample is compared with that reference, a rise of 2 °C restarting the window from the current time and temperature, while if neither happened and the window has run for 60 s, the function returns FAULT_RUNAWAY, the unsigned subtraction now_ms − ref_ms staying correct across the 32-bit wrap of the clock.

Worked example: the stale and runaway rules

The two rules with timing are easiest to check with numbers. Before following the steps, predict when a heater stuck at 27.20 °C trips the runaway fault.

  1. A stale sample. The control step produces a sample every 100 ms and the check receives the age of the newest one, so with a limit of 500 ms an age of 480 ms is fine and an age of 510 ms a fault, a plain comparison for which a test can supply any age.
  2. The window opens. With the setpoint at 65.00 °C, the chamber at 25.00 °C and the heater at full power, the check opens a window at time 0 with a reference of 25.00 °C.
  3. A small rise. At 30 s the chamber reads 26.00 °C, short of the 2.00 °C rise, so the window stays open.
  4. A real rise. At 35 s the chamber reads 27.10 °C, 2.10 °C above the reference, so the window restarts at 35 s with a reference of 27.10 °C.
  5. The expiry. If the chamber then stays at 27.20 °C, the new window expires 60 s later, at 95 s, and the check returns FAULT_RUNAWAY.

A slow but healthy heater gaining 2 °C every minute therefore never trips, whereas a dead heater trips 60 s after its window opened.

Try it: write the safety checks

The starter in projects/0116-dryer-drivers/starter is the whole dryer with one stub left, safety_check(), which returns FAULT_NONE for every input, the PWM, the buttons and the display being already written and the safety tests in projects/0115-dryer-host-tests checking your version, and your task is to make all eight host test programs pass and the firmware build.

  1. Open projects/0116-dryer-drivers/starter/app/safety.c and read the TODO(learner) comment, which lists the four checks in order, sensor, over-temperature, stale sample and runaway.
  2. Implement the first three checks as plain comparisons, using SAFETY_CUTOFF_CENTI with >= for the cutoff and SAFETY_STALE_MS with > for the stale rule.
  3. Implement the runaway check as the comment describes, calling runaway_reset() whenever the rule does not apply, opening the window on the first applicable sample, restarting it after a 2 °C rise and returning FAULT_RUNAWAY when 60 s pass without a rise.
  4. Run the host tests from the workspace root with python -I tools/build.py projects/0115-dryer-host-tests/starter --test, expecting 100% tests passed out of 8, and if CMake reports a CMakeCache.txt from a different folder, add --clean, because the copied folders carry stale build directories, which --clean deletes first.
  5. Build the firmware with python -I tools/build.py projects/0116-dryer-drivers/starter --clean, which should finish with no errors, then open hw/hal_bluepill.c, find the PWM register lines from this lesson and compare them with the solution in projects/0116-dryer-drivers/solution.
  6. Optionally, open test/test_safety.c, read test_no_runaway_near_the_setpoint, explain in one sentence why the check must be off near the setpoint and compare your answer with the table above.
Hint for the order

Return the first fault you find, and do the cheap checks first. A sensor check that comes after the runaway check would let a bad sensor reach the window logic. The runaway check is the only one with state, so the other three must not touch the window.

Hint for the runaway window

The window needs three things: whether it is open, the time it opened, and the temperature at that moment. A rise is measured against the stored temperature, not the previous sample. A test that sets the time 60 s after the window opened tells you whether the expiry is right.

Common mistakes and how to spot them

A held button counted as several presses

One press of the material button advances the preset two or three times in the simulator, because the event follows the level rather than the change. Raise the event only on the change from released to pressed and keep the integrator's saturation, the test test_a_held_press_is_one_event in test_drivers.c catching this on the PC.

The state machine reading the raw level

While the material button is held, the preset advances on every control step, about ten times a second, and the display changes faster than a person presses, because the control step called hal_button_pressed() directly instead of taking the event. Read the button only through the event functions, so that each press reaches the state machine once.

A runaway window that never restarts

A healthy heater trips RUNAWAY about a minute after it starts, even though the chamber is rising, because the restart branch does not reset the reference. Check that branch, which must reset the reference to the current time and temperature, then write a test that feeds a steady 2 °C rise every minute and expects no fault, as the restart test does.

The wrong comparison for the cutoff

test_cutoff_at_90_degrees fails with Expected 1 Was 0, because the code was written with >, so a reading of exactly 90.00 °C passed. Use >= for a limit that means reached, and keep the boundary test next to it, so that a future edit moving the limit fails at once.

Display text that counts the NUL

A line built with 22 visible characters fails test_longest_line_fits_the_display, and on the OLED the last character is cut off or wraps, because the length of the buffer, 22, was used as the length of the text. Build text up to 21 characters, keeping the 22-byte buffer only for the terminating NUL.

Debounce, PWM frequency and safety tests in products

Production firmware debounces buttons either in hardware, with a resistor-capacitor filter and a Schmitt-trigger input, or in software, as here, a software integrator costing no parts but adding latency and needing a sample period longer than the bounce, so a reviewer will ask how long the bounce is and where the limit came from.

A PWM frequency should have a stated reason, the heater's 1 kHz being well above what the chamber can follow and a fan at 25 kHz being chosen to lie above the range most people can hear. Safety rules are tested as pure functions with one test per rule and boundary, which gives the trace a standard such as IEC 61508 asks for (lesson 112), and lesson 117 adds a supervisor that makes sure the check runs.

Summary

  • A bang-bang controller with hysteresis switches the heater fully on or off around a dead band and overshoots, while PWM sets the average power by a duty cycle.
  • In PWM mode 1 the output is high while the counter is below the compare value, the period being (PSC + 1) × (ARR + 1) ÷ clock, and a compare value from 0 to 1000 is a duty in permille.
  • The PWM values are loaded first and the counter started last, the preload and update event making the first period use the values written.
  • A button integrator changes its output only when the count reaches its limit, and an event is the edge from released to pressed, so a held button gives one event.
  • The display text is built by a pure function and tested line by line, while the flush of 1 KB over I2C takes about 92 ms at 100 kHz, which the schedule must allow for.
  • Safety checks run in a fixed order and return the first fault, the runaway window restarting on each real rise and applying only at full power far below the setpoint.
  • Each safety rule and boundary has its own host test, and gaps in the rules, such as a cold reading with the heater off, belong in the requirements.
