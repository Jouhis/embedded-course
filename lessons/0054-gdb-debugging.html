GDB debugging: breakpoints, watchpoints, and memory

When a value is wrong, printf tells you what it is. A watchpoint tells you which instruction changed it, and that is usually the answer you need. GDB gives you both, and it works with the simulator the same way it works with a probe on a real board.

By the end of this lesson you can stop the Pico simulator on a memory write with a watchpoint, examine memory with x, and find the statement that corrupts a neighbouring variable.

The idea

GDB runs on your PC and talks to a GDB server. In Wokwi, the server is inside the simulator, and gdbServerPort = 3333 in wokwi.toml is the port it listens on (Wokwi debugging docs). The debugger reads and writes registers and memory through that port. The chip does not know it is being debugged: a breakpoint is the core running a BKPT instruction or a hardware comparator, and a watchpoint is the core's own comparator on a data address. This is the same protocol a probe such as an SWD debugger uses on a real board. Lesson 32 used GDB to step through compiled C, and this lesson uses it to find a bug.

The Cortex-M0+ in the RP2040 has four hardware breakpoint comparators and two watchpoint comparators. Software breakpoints (the BKPT instruction) are not limited (§2.4.2.4). Two watchpoints are enough for one bug at a time, but they are a hard limit: a third watch needs you to delete one.

Start a session

  1. Build the project with Ctrl+Shift+B. The course builds in Debug mode: debug symbols (-g) and light optimisation (-Og), so stepping follows your source closely. A release build (python tools/build.py <project> --release) optimises harder, and the stepping order can then jump around.
  2. Start the simulator first: F1 → Wokwi: Start Simulator. Starting the debugger first makes it fail to connect. The Wokwi docs also offer Wokwi: Start Simulator and Wait for Debugger, which pauses before the first instruction until GDB attaches.
  3. Press F5. The project's .vscode/launch.json connects to localhost:3333, and the debugger stops at the start of the program.

The commands you need

The VS Code debug toolbar covers stepping. The debug console accepts GDB commands directly if you prefix them with -exec, for example -exec x/8xb &frame. Here are the commands for this lesson. The full list is in the reference sheet.

CommandWhat it does
break main, break file.c:42Stop when execution reaches a function or line.
continue (c)Run until the next stop.
next (n) and step (s)Run one source line, stepping over or into calls.
finishRun until the current function returns, and print its return value.
btPrint the call stack, from the current function up to main.
info registersShow r0 to r12, sp, lr, pc and xPSR. Lesson 31 explains each one.
print frame, print/x frame.sentinelShow a variable, optionally in hex.
x/8xb &frameExamine memory: eight bytes in hex, starting at the address of frame.
set var seed = 0x20Change a variable while the program is stopped.
watch frame.sentinelStop when the value of that object changes.
info breakpoints, delete 2List the breakpoints and watchpoints, or remove one.

The x command has the form x/NFU address. N is a count, F is a format (x for hex, d for decimal, s for a string) and U is the unit size (b for byte, h for halfword, w for word). x/8xb &frame therefore prints eight bytes in hex, which is the whole data[] array in the struct you will meet in the task.

A watchpoint on a variable stops the program when the variable's bytes change. It does not stop on the line that assigns it, but on the store that changed the bytes. That is the line you want: it is the one that corrupted the value, even when the name in the statement is a different variable.

A watchpoint on a neighbour

Here is the shape of the bug in the task. A struct holds a fixed-length array, and a byte right after the array is a sentinel. An off-by-one loop writes one element past the end. The write lands on the sentinel, which is adjacent in memory. From the struct's point of view it is a valid assignment, so the compiler does not complain. 

typedef struct {
    uint8_t data[FRAME_LEN];   /* bytes 0 to 7 */
    uint8_t sentinel;           /* byte 8: one past data[] */
} frame_t;

for (uint32_t i = 0; i <= FRAME_LEN; i++) {
    f->data[i] = (uint8_t)(seed + i);   /* i == 8 writes the sentinel */
}

The debugging method is the one to remember. Confirm the symptom with a print, then set a watchpoint on the value that should not change. continue runs until the watchpoint fires, and GDB prints the old value, the new value, and the line where the store happened. Then bt shows how you got there, and x shows the memory around the address.

Watchpoints are a feature of the core's debug unit, and the simulator must implement them. The Wokwi docs do not list watchpoints, so confirm that the watch stops in the simulator before you rely on it. If it does not, use the fallback below, which uses only breakpoints.

Try it in Wokwi

The project is projects/0054-gdb-watchpoint. The starter prints a line every second, and the line says the sentinel is corrupted. Your job is to find the write that corrupts it, and fix that statement. The sentinel is a global, so it has a fixed address that GDB can watch.

  1. Open projects/0054-gdb-watchpoint/starter in VS Code (File → Open Folder). Build, start the simulator, then press F5.
  2. Your task: set a watchpoint on frame.sentinel, with watch frame.sentinel in the debug console. Continue with c until GDB stops. Read the old and new values. Use bt to see the call, and x/9xb &frame to see the eight data bytes and the sentinel together.
  3. The stop shows the line that wrote the byte. Fix that line so the loop does not write past data[]. Stop the debugger, rebuild, start the simulator again, and press F5.
  4. You will know it works when the serial monitor prints GDB WATCH OK every second, with the sentinel intact at 0xa5.
Fallback if the watchpoint never stops

Use breakpoints, which the core has in hardware. Set break build_frame, continue, then use next through the loop and print frame.sentinel with print/x frame.sentinel on each pass. The first pass where the value changes is the one that writes past the array. This is slower than a watchpoint, but it finds the same line.

Hint for the bound

Count the elements. data[] has FRAME_LEN elements, indexed 0 to FRAME_LEN − 1. A loop that stops when i is less than FRAME_LEN never reaches the sentinel.

The reference solution is in projects/0054-gdb-watchpoint/solution. Try first, compare after. Its comment on build_frame() names the bug and the fix.

You stopped the simulated Pico on the instruction that wrote a byte it should not, read the value with x, and fixed the bound. That is the method for any memory corruption: a watchpoint on the value, then the backtrace of the write.

"A global variable gets a wrong value, and no code in your file obviously writes it. How do you find the writer?" Answer out loud in 60 seconds, then compare.

Model answer

I'd confirm the wrong value is real with a print or a read of memory, then find its address and set a watchpoint on it, so the debugger stops at the first write that changes it. The backtrace shows which function did the write. If the watchpoint is unavailable, I'd break at the suspect function and step through it, checking the value on each pass. The usual causes are an out-of-bounds write into a neighbour, a DMA or ISR writing the wrong buffer, or a pointer that aims at the wrong struct. I'd also check the map file to see what sits next to the variable.
