GDB debugging

Breakpoints, watchpoints and memory inspection on a running target

By the end of this lesson you can stop the Pico simulator on a memory write with a watchpoint, examine memory with x, and find the statement that corrupts a neighbouring variable.

Finding the instruction that wrote a value

Lesson 32 showed how the compiler turns C into Arm instructions and how to step through them in GDB, lesson 31 explained the registers a stopped program exposes, lesson 46 introduced volatile for memory that can change behind the compiler's back, and lesson 47 turned a struct into a view of memory with fixed offsets. This lesson uses all of that to answer one question: when a value in memory is wrong, which instruction wrote it?

Memory corruption is among the hardest firmware bugs, because a variable changes, nothing in the file under study obviously changes it, and the symptom appears far away, often as a crash or a sensor value that is simply wrong, while in a product the same bug may appear once a week on one unit in a thousand. A print in the suspect function can show the wrong value but not the write that caused it, and extra prints can shift the timing enough to hide the bug, whereas a debugger with a watchpoint answers the question directly without changing the program's code.

Debuggers, GDB servers and ELF files

The GNU Debugger, GDB, runs on the PC and controls the target chip through a link, which on a real board is a probe speaking the Serial Wire Debug protocol and in Wokwi a GDB server inside the simulator, listening on the TCP port set by gdbServerPort = 3333 in wokwi.toml (Wokwi debugging docs). Through that port the debugger reads and writes registers and memory and stops and resumes the core, while the program itself does not know it is being debugged.

GDB also needs the ELF file the build produces, a container for the machine code that also stores symbols and debug information. The debug information, written by the compiler when given -g, records which address holds each variable, which source line each instruction came from and what the types look like, which is how GDB can print frame.sentinel by name rather than by address. The course builds in Debug mode with -Og -g, so the symbols are present and the stepping order stays close to the source. The GDB server never sees the C source, only memory and registers, which GDB turns into names by reading the ELF debug information. A release build without -g still runs, but GDB can then show only raw addresses.

Hardware breakpoints and watchpoints

A breakpoint stops the core at a code address, and a watchpoint stops it when a data address is accessed or, in GDB's default form, when the value there changes. The core supports both in hardware: the Cortex-M0+ in the RP2040 has a breakpoint unit with four hardware breakpoints and a watchpoint unit with two watchpoints, while software breakpoints, which use the BKPT instruction, are unlimited, so the limit of four applies only to breakpoints placed in hardware (§2.4.2.4).

The watchpoint limit is the one that matters here, and it is a hard limit, since each hardware watchpoint is a comparator on one address range that halts the core when a store hits the range. Two watchpoints suffice for one bug at a time, but a third requires deleting one first, and GDB should be expected to report an error when it tries to arm a third.

A watch on a value does more than watch an address: GDB reads the old value, arms the comparator on the address, and on each halt compares the old and new values, resuming silently if they are equal. A store that writes the same value as before therefore does not stop the program, which is exactly the behaviour wanted for a value that should never change.

A breakpoint resembles a tripwire across a path, stopping the program when execution reaches a line of code, whereas a watchpoint resembles an alarm on a drawer, going off when any code opens that piece of memory, so when a variable is corrupted by an unknown writer, the drawer alarm is the right tool. The comparison is generous, though, because the hardware has only two such alarms, and each covers only a small range of addresses.

Starting a debug session

A session needs the build, the simulator and the debugger, started in that order.

  1. Build the project with Ctrl+Shift+B. The course builds in Debug mode, with debug symbols (-g) and light optimisation (-Og), so stepping follows the source closely, whereas a release build (python tools/build.py <project> --release) optimises harder and the stepping order can jump around.
  2. Start the simulator first with F1 → Wokwi: Start Simulator, because, as the Wokwi docs explain, the debugger connects to the server the simulator runs. The docs also offer Wokwi: Start Simulator and Wait for Debugger, which holds the program until the debugger attaches.
  3. Press F5. The project's .vscode/launch.json connects to localhost:3333 with stopAtConnect set, so the debugger stops at the start of the program.

GDB commands for this lesson

The VS Code debug toolbar covers stepping, and the debug console accepts GDB commands directly with the prefix -exec, as in -exec x/8xb &frame. The table lists the commands this lesson needs, and the full list is in the reference sheet.

CommandWhat it does
break main, break file.c:42Stop when execution reaches a function or line.
continue (c)Run until the next stop.
next (n) and step (s)Run one source line, stepping over or into calls.
finishRun until the current function returns, and print its return value.
btPrint the call stack, from the current function up to main.
info registersShow r0 to r12, sp, lr, pc and xPSR. Lesson 31 explains each one.
print frame, print/x frame.sentinelShow a variable, optionally in hex.
x/8xb &frameExamine memory: eight bytes in hex, starting at the address of frame.
set var (for example set var seed = 0x20)Change a variable while the program is stopped. seed is a parameter of build_frame(), so set it while the stop is inside that function.
watch frame.sentinelStop when the value of that object changes.
info breakpoints, delete 2List the breakpoints and watchpoints, or remove one.

The x command has the form x/NFU address, where N is a count, F a format (x for hex, d for decimal, s for a string) and U the unit size (b for byte, h for halfword, w for word). x/8xb &frame therefore prints eight bytes in hex, the whole data[] array of the struct in the task.

A watchpoint on a variable stops the program when the variable's bytes change, not on the line that assigns it but on the store that changed the bytes. That is the line wanted, because it is the one that corrupted the value, even when the statement names a different variable.

Struct layout byte by byte

Finding a corrupted byte requires knowing where each byte lives. The struct in this lesson holds an array of eight uint8_t values followed by one more uint8_t, and C lays out struct members in declaration order, each at an offset from the start. A uint8_t takes one byte and needs no alignment, so no padding separates the array from the sentinel: data[0] is at offset 0, data[7] at offset 7 and sentinel at offset 8, so the struct is nine bytes long and sizeof(frame_t) is 9.

That layout makes the bug possible, because the array has no guard. Writing data[8] does not fail, since the compiler sees an index of type uint32_t and has no bounds check to make, so the store lands at offset 8, on the sentinel: C does not stop a write past the end of an array, and in a struct the byte after the array is simply another member. 

typedef struct {
    uint8_t data[FRAME_LEN];   /* bytes 0 to 7 */
    uint8_t sentinel;           /* byte 8: one past data[] */
} frame_t;

for (uint32_t i = 0; i <= FRAME_LEN; i++) {
    f->data[i] = (uint8_t)(seed + i);   /* i == 8 writes the sentinel */
}

The first member, uint8_t data[FRAME_LEN], is an array of eight bytes, FRAME_LEN being the named constant 8, and the second, uint8_t sentinel, is one byte that the program uses as a marker that the frame is intact. The typedef names the struct frame_t, so the rest of the code can write frame_t frame;.

The loop contains the bug. Its condition i <= FRAME_LEN runs the body for i from 0 up to 8 inclusive, and since the body writes f->data[i], the last write is data[8], outside the array. The value written is seed + i, whose cast to uint8_t keeps only the low eight bits.

Worked example: watching the sentinel

We follow the starter's numbers. The main loop sets the sentinel to 0xA5 and the seed is 0x10, so the buggy loop writes 0x10 into data[0] for i equal to 0, 0x11 into data[1] for 1 and so on, each value one more than the last, until the last ordinary write, at i equal to 7, puts 0x17 into data[7]. Before reading on, predict the value the sentinel holds after the loop.

When i reaches 8, the expression seed + i is 0x10 + 8, or 0x18, and the store goes to data[8], the sentinel byte, which changes from 0xA5 to 0x18. The main loop then compares the sentinel with 0xA5, finds the mismatch and prints the corruption message.

The trace is therefore the sentinel at 0xA5, the writes 0x10 to 0x17 into the array with the sentinel untouched, and finally the write of 0x18 that replaces it. A dump with x/9xb &frame just before the bad write shows 0x10 to 0x17 with 0xa5 in the last position, and just after it the last byte reads 0x18. The addresses on the left of the dump depend on the build, so read the first address the command prints and count from there, the sentinel being at that address plus 8.

The watchpoint makes this trace automatic. With watch frame.sentinel set while the program is stopped, the next store that changes the sentinel halts the core, GDB prints the old value 0xa5 and the new value 0x18, and the stopped line is the store inside build_frame() with i equal to 8.

  1. The frame holds eight data bytes, and right after them a sentinel byte that main sets to 0xA5. The loop is meant to fill data[0] to data[7] with seed + i, seed = 0x10.
  2. i = 0: data[0] = 0x10.
  3. i = 1: data[1] = 0x11.
  4. i = 2: data[2] = 0x12.
  5. i = 3: data[3] = 0x13.
  6. i = 4: data[4] = 0x14.
  7. i = 5: data[5] = 0x15.
  8. i = 6: data[6] = 0x16.
  9. i = 7: data[7] = 0x17, the last element. The sentinel is untouched, and an x/9xb &frame dump shows 10 11 12 13 14 15 16 17 a5.
  10. The test is i <= FRAME_LEN, so the loop runs once more with i = 8. data[8] is one past the array: the store lands on the sentinel, which becomes 0x18.
  11. Finding this by hand means stepping until the byte changes. A watchpoint does it for you: watch frame.sentinel halts the core on the store itself and prints the old and new values and the line, with i = 8.

Try it in Wokwi

The project is projects/0054-gdb-watchpoint, whose starter prints a line every second reporting that the sentinel is corrupted. The task is to find the write that corrupts it and fix that statement, and because the sentinel is a global, it has a fixed address that GDB can watch.

  1. Open projects/0054-gdb-watchpoint/starter in VS Code (File → Open Folder), build, start the simulator and press F5.
  2. Set a watchpoint on frame.sentinel by typing watch frame.sentinel in the debug console and continue with c until GDB stops. Read the old and new values, which should be 0xa5 and 0x18, then use bt to see the call and x/9xb &frame to see the eight data bytes and the sentinel together.
  3. The stop shows the line that wrote the byte, so fix that line so that the loop no longer writes past data[], then stop the debugger, rebuild, start the simulator again and press F5.
  4. The fix works when the serial monitor prints GDB WATCH OK every second, with the sentinel intact at 0xa5.
Fallback if the watchpoint never stops

Use breakpoints, which the core also has in hardware: set break build_frame, continue, then step through the loop with next, printing the sentinel with print/x frame.sentinel on each pass. The first pass on which the value changes is the one that writes past the array, which is slower to find than with a watchpoint but leads to the same line.

Hint for the bound

Count the elements: data[] has FRAME_LEN elements, indexed 0 to FRAME_LEN − 1, so a loop that runs only while i is less than FRAME_LEN never reaches the sentinel.

The reference solution is in projects/0054-gdb-watchpoint/solution, whose comment on build_frame() names the bug and the fix, so try first and compare afterwards.

You stopped the simulated Pico on the instruction that wrote a byte it should not have, read the memory with x and fixed the bound, the method for any memory corruption: a watchpoint on the value, then the backtrace of the write.

Common mistakes and how to spot them

A watchpoint on a local variable

GDB reports that the watchpoint's scope has ended, or the watch never fires again after the function returns, because a local lives in the stack frame, which disappears on return. Watch a global, or a field of a struct that outlives the function, which is why the sentinel is a global.

The debugger started before the simulator

The debugger reports that it cannot connect to localhost:3333, because F5 was pressed with no simulator running. Start the simulator with F1 first and then press F5.

A release build under the debugger

The program runs past a line without stopping, or a variable prints as <optimized out>, because a build with --release let the compiler move or remove the code. Rebuild in Debug mode, the course's default, and set the breakpoint again.

A watchpoint that stops too often

Every continue returns to the prompt almost at once and the program seems to crawl, because the watched counter changes every millisecond. Add a condition, as in watch frame.sentinel if frame.sentinel != 0xa5, or use a breakpoint on the function that makes the change.

The symptom fixed instead of the write

The message changes to OK, yet the array still writes past its end, because the sentinel is simply reset after each frame, so the next field placed after it will be corrupted instead. Find the store with the watchpoint and correct the bound, as the task asks.

Debugging memory corruption on real hardware

Engineers use a debugger on real boards every day but also apply the same ideas without one. On a microcontroller the memory protection unit (MPU) can make a guard region fault on a bad write, whose fault handler then reports the address of the store, as lesson 39 describes, but once the corrupted variable is known, a watchpoint remains the fastest tool.

A code reviewer looks for bounded loops, expecting any loop that writes into an array to compare the index with the array length using < rather than <=, with the length taken from one named constant. A senior engineer also asks what follows an array in a struct, because the byte after an array is always a candidate for corruption, and some teams place a canary, a known pattern, in a guard field to catch exactly this, checking it in the main loop.

Summary

  • GDB talks to the target through a link, a probe on hardware or the GDB server on port 3333 in Wokwi.
  • The ELF file's debug information turns addresses into names, so the build must include -g.
  • The Cortex-M0+ has 4 hardware breakpoints and 2 hardware watchpoints, so a third watchpoint requires deleting one first.
  • A watchpoint halts the core on the store that changes the value, so the stop shows the line that corrupted it.
  • A struct lays out its members in order, so a uint8_t array of 8 followed by a uint8_t puts the marker at offset 8.
  • C does not bounds-check array writes, so a loop that uses <= writes one element past the end.
