GDB debugging: breakpoints, watchpoints, and memory

When a value is wrong, printf tells you what it is. A watchpoint tells you which instruction changed it, and that is usually the answer you need. GDB gives you both, and it works with the simulator the same way it works with a probe on a real board.

By the end of this lesson you can stop the Pico simulator on a memory write with a watchpoint, examine memory with x, and find the statement that corrupts a neighbouring variable.

Where we are and why it matters

Lesson 32 showed you how the compiler turns C into Arm instructions, and how to step through them in GDB. Lesson 31 explained the registers that a stopped program exposes. Lesson 46 introduced volatile, which tells the compiler that a memory location can change behind its back. Lesson 47 turned a struct into a view of memory with fixed offsets. This lesson uses all of that to answer one question: when a value in memory is wrong, which instruction wrote it?

Memory corruption is one of the hardest bugs in firmware. A variable changes, nothing in the file you are reading obviously changes it, and the symptom appears far away, often as a crash or a sensor value that is simply wrong. In a product, the same bug can appear once a week on one unit in a thousand. A print in the suspicious function can show you the wrong value, but it cannot show you the write that caused it, and adding prints can move the timing enough to hide the bug. A debugger with a watchpoint answers the question directly, and it does not change the program's code to do it.

What a debugger does

The GNU Debugger, GDB, is a program that runs on your PC. It controls the target chip through a link. On a real board, the link is a probe that speaks the Serial Wire Debug protocol. In Wokwi, the link is a GDB server that runs inside the simulator, and gdbServerPort = 3333 in wokwi.toml is the TCP port it listens on (Wokwi debugging docs). The debugger reads and writes registers and memory through that port, and it can stop and resume the core. The program itself does not know it is being debugged.

GDB needs one more thing: the ELF file. The build produces an ELF file, which is a container for the machine code, and it also stores symbols and debug information. The debug information, which the compiler writes when you pass -g, records which address holds each variable, which line each instruction came from, and what the types look like. That is how GDB can print frame.sentinel by name and not by address. The course builds in Debug mode with -Og -g, so the symbols are there and the stepping order is close to your source.

The GDB server does not reach into your C source. It sees only memory and registers, and GDB turns those into names by reading the ELF debug information. A release build without -g still runs, but GDB can only show raw addresses.

Breakpoints and watchpoints in hardware

A breakpoint stops the core at a code address. A watchpoint stops it when a data address is accessed or, in GDB's default form, when the value there changes. The core has hardware support for both. The Cortex-M0+ in the RP2040 has a breakpoint unit with four hardware breakpoints and a watchpoint unit with two watchpoints. The Cortex-M0+ has unlimited software breakpoints, which use the BKPT instruction, so the limit of four applies only to breakpoints placed in hardware (§2.4.2.4).

The watchpoint limit is the one that matters for this lesson, and it is a hard limit. Each hardware watchpoint is a comparator that watches one address range. When a store hits that range, the core halts. Two watchpoints are enough for one bug at a time. A third watch needs you to delete one first. If you set more than two, expect GDB to report an error when it tries to arm the third one.

A watch on a value is more than a watch on an address. GDB reads the old value, arms the comparator on the address, and when the core halts, GDB compares the old and new values. If they are equal, GDB resumes silently. So a store that writes the same value as before does not stop the program, which is exactly what you want for a value that should never change.

Start a session

  1. Build the project with Ctrl+Shift+B. The course builds in Debug mode: debug symbols (-g) and light optimisation (-Og), so stepping follows your source closely. A release build (python tools/build.py <project> --release) optimises harder, and the stepping order can then jump around.
  2. Start the simulator first: F1 → Wokwi: Start Simulator. The Wokwi docs say to start the simulator before the debugger, because the debugger connects to the server the simulator runs. They also offer Wokwi: Start Simulator and Wait for Debugger, which waits for the debugger to attach before the program runs.
  3. Press F5. The project's .vscode/launch.json connects to localhost:3333, and stopAtConnect is set, so the debugger stops at the start of the program.

The commands you need

The VS Code debug toolbar covers stepping. The debug console accepts GDB commands directly if you prefix them with -exec, for example -exec x/8xb &frame. Here are the commands for this lesson. The full list is in the reference sheet.

CommandWhat it does
break main, break file.c:42Stop when execution reaches a function or line.
continue (c)Run until the next stop.
next (n) and step (s)Run one source line, stepping over or into calls.
finishRun until the current function returns, and print its return value.
btPrint the call stack, from the current function up to main.
info registersShow r0 to r12, sp, lr, pc and xPSR. Lesson 31 explains each one.
print frame, print/x frame.sentinelShow a variable, optionally in hex.
x/8xb &frameExamine memory: eight bytes in hex, starting at the address of frame.
set var (for example set var seed = 0x20)Change a variable while the program is stopped. seed is a parameter of build_frame(), so set it while the stop is inside that function.
watch frame.sentinelStop when the value of that object changes.
info breakpoints, delete 2List the breakpoints and watchpoints, or remove one.

The x command has the form x/NFU address. N is a count, F is a format (x for hex, d for decimal, s for a string) and U is the unit size (b for byte, h for halfword, w for word). x/8xb &frame therefore prints eight bytes in hex, which is the whole data[] array in the struct you will meet in the task.

A watchpoint on a variable stops the program when the variable's bytes change. It does not stop on the line that assigns it, but on the store that changed the bytes. That is the line you want: it is the one that corrupted the value, even when the name in the statement is a different variable.

A struct, byte by byte

Before you can find a corrupted byte, you need to know where each byte lives. The struct in this lesson has an array of eight uint8_t values and one more uint8_t after it. C lays struct members out in memory in declaration order, each at an offset from the start of the struct. Each uint8_t takes one byte and needs no alignment, so there is no padding between the array and the sentinel. data[0] is at offset 0, data[7] is at offset 7, and sentinel is at offset 8. The whole struct is nine bytes long, and sizeof(frame_t) is 9.

That layout is what makes the bug possible. The array has no guard. Writing data[8] does not fail, because the compiler sees an index of type uint32_t, and it has no bounds check to make. The store lands at offset 8, which is the sentinel. C does not stop you from writing past the end of an array, and in a struct the byte after the array is simply another member. 

typedef struct {
    uint8_t data[FRAME_LEN];   /* bytes 0 to 7 */
    uint8_t sentinel;           /* byte 8: one past data[] */
} frame_t;

for (uint32_t i = 0; i <= FRAME_LEN; i++) {
    f->data[i] = (uint8_t)(seed + i);   /* i == 8 writes the sentinel */
}

Read the struct line by line. The first member is uint8_t data[FRAME_LEN]. It is an array of eight bytes, and FRAME_LEN is the named constant 8. The second member is uint8_t sentinel, one byte that the program uses as a marker that the frame is intact. The typedef gives the struct the name frame_t so that the rest of the code can write frame_t frame;.

The loop is the bug. The condition i <= FRAME_LEN runs the body for i equal to 0, 1, up to 8 inclusive. The body writes f->data[i], so the last write is data[8], which is outside the array. The value written is seed + i, and the cast to uint8_t keeps only the low eight bits.

A worked example: watching the sentinel

Take the starter's numbers. The sentinel is set to 0xA5 by the main loop. The seed is 0x10, so the buggy loop writes these values: for i equal to 0 it writes 0x10 into data[0], for 1 it writes 0x11 into data[1], and so on. The pattern is one more than the previous value, so the last ordinary write, at i equal to 7, puts 0x17 into data[7].

Now the bad iteration. When i is 8, the expression seed + i is 0x10 + 8, which is 0x18. The store goes to data[8], the sentinel byte, and the sentinel changes from 0xA5 to 0x18. The main loop then compares the sentinel with 0xA5, finds a mismatch, and prints the corruption message.

So the trace is: sentinel 0xA5, then writes 0x10 through 0x17 into the array with the sentinel untouched, then the write 0x18 that replaces the sentinel. The memory dump with x/9xb &frame just before the bad write shows 0x10 through 0x17 and 0xa5 in the last position. Right after it, the last byte reads 0x18. The addresses on the left of the dump depend on your build, so read the first address the command prints and count from there. The byte at that address plus 8 is the sentinel.

The watchpoint makes this trace automatic. Set watch frame.sentinel while the program is stopped. The next store that changes the sentinel halts the core, and GDB prints the old value 0xa5 and the new value 0x18. The stopped line is the store inside build_frame(), with i equal to 8. You did not have to guess where to look.

Try it in Wokwi

The project is projects/0054-gdb-watchpoint. The starter prints a line every second, and the line says the sentinel is corrupted. Your job is to find the write that corrupts it, and fix that statement. The sentinel is a global, so it has a fixed address that GDB can watch.

  1. Open projects/0054-gdb-watchpoint/starter in VS Code (File → Open Folder). Build, start the simulator, then press F5.
  2. Your task: set a watchpoint on frame.sentinel, with watch frame.sentinel in the debug console. Continue with c until GDB stops. Read the old and new values. Use bt to see the call, and x/9xb &frame to see the eight data bytes and the sentinel together. You should see the old value 0xa5 and a new value 0x18.
  3. The stop shows the line that wrote the byte. Fix that line so the loop does not write past data[]. Stop the debugger, rebuild, start the simulator again, and press F5.
  4. You will know it works when the serial monitor prints GDB WATCH OK every second, with the sentinel intact at 0xa5.
Fallback if the watchpoint never stops

Use breakpoints, which the core has in hardware. Set break build_frame, continue, then use next through the loop and print frame.sentinel with print/x frame.sentinel on each pass. The first pass where the value changes is the one that writes past the array. This is slower than a watchpoint, but it finds the same line.

Hint for the bound

Count the elements. data[] has FRAME_LEN elements, indexed 0 to FRAME_LEN − 1. A loop that stops when i is less than FRAME_LEN never reaches the sentinel.

The reference solution is in projects/0054-gdb-watchpoint/solution. Try first, compare after. Its comment on build_frame() names the bug and the fix.

Common mistakes and how to spot them

Mistake 1: a watchpoint on a local variable. You watch a local in a function, the function returns, and the watch is cleared or stops firing. Symptom: GDB reports that the watchpoint's scope has ended, or it never stops again. A local lives in the stack frame, and the frame is gone after the return. Fix: watch a global, or a field of a struct that lives longer than the function. The sentinel is a global for that reason.

Mistake 2: starting the debugger before the simulator. You press F5 with no simulator running. Symptom: the debugger reports that it cannot connect to localhost:3333. Fix: start the simulator with F1, then press F5.

Mistake 3: debugging a release build. You build with --release, and your breakpoint on a line is never hit, because the compiler moved or removed the code. Symptom: the program runs past the line with no stop, or a variable prints as <optimized out>. Fix: rebuild in Debug mode, which the course's default build uses, and set the breakpoint again.

Mistake 4: a watchpoint that stops too often. You watch a counter that changes every millisecond, and the debugger stops on each change, so the program seems to crawl. Symptom: continue returns to the prompt again and again. Fix: add a condition with watch frame.sentinel if frame.sentinel != 0xa5, or use a breakpoint on the function that makes the change.

Mistake 5: fixing the symptom, not the write. You see the sentinel is wrong and reset it after each frame. Symptom: the message changes to OK, and the array still writes past its end. The next field placed after the sentinel is then corrupted. Fix: find the store with the watchpoint and correct the bound, as the task asks.

In real projects

Engineers use a debugger on real boards every day, but they also use the same ideas without one. On a microcontroller, the memory protection unit (MPU) can make a guard region fault on a bad write, and the fault handler can then report the address of the store. Lesson 39 covers the MPU and faults. A watchpoint is still the fastest tool once you know which variable is wrong.

A code reviewer looks for bounded loops. Any loop that writes into an array should compare the index with the array length, using < and not <=, and the length should come from one named constant. A senior engineer will also ask whether the struct has anything after an array, because a byte that follows the array is always a candidate for a corruption bug. Some teams place a canary, a known pattern, in a guard field to catch exactly this, and they check it in the main loop.

Debugging questions come up in interviews because they test a method. The interviewer wants to hear that you confirm the symptom, find the address, watch the value, and read the backtrace. A good answer names the tool and the sequence, and it does not depend on guessing the cause.

You stopped the simulated Pico on the instruction that wrote a byte it should not, read the value with x, and fixed the bound. That is the method for any memory corruption: a watchpoint on the value, then the backtrace of the write.

Summary

  • GDB talks to the target through a link: a probe on hardware, or the GDB server on port 3333 in Wokwi.
  • The ELF file's debug information turns addresses into names, so the build must include -g.
  • The Cortex-M0+ has 4 hardware breakpoints and 2 hardware watchpoints. A third watchpoint needs one deleted first.
  • A watchpoint halts the core on the store that changes the value, so the stop shows the line that corrupted it.
  • A struct lays out members in order, and a uint8_t array of 8 followed by a uint8_t has the marker at offset 8.
  • C does not bounds-check array writes. A loop that uses <= writes one element past the end.

"A global variable gets a wrong value, and no code in your file obviously writes it. How do you find the writer?" Answer out loud in 60 seconds, then compare.

Model answer

I'd confirm the wrong value is real with a print or a read of memory, then find its address and set a watchpoint on it, so the debugger stops at the first write that changes it. The backtrace shows which function did the write. If the watchpoint is unavailable, I'd break at the suspect function and step through it, checking the value on each pass. The usual causes are an out-of-bounds write into a neighbour, a DMA or ISR writing the wrong buffer, or a pointer that aims at the wrong struct. I'd also check the map file to see what sits next to the variable.
