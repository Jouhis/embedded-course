Timing and non-blocking super-loops

Deadline-driven loops that never wait

By the end of this lesson you can run three LEDs at 1, 2 and 4 Hz from one loop with no sleep_ms(), and write a deadline comparison that stays correct when the 32-bit microsecond counter wraps.

Several jobs in one loop

Lesson 51 showed how to set a pin and lesson 52 how to read one, both quick operations, but real firmware does much more between them: it blinks a status LED, reads a button, parses bytes from a UART (lesson 53) and talks to a sensor over a slow bus. If each step waits in its own sleep_ms(), the others stop, a problem the debounce of lesson 52 already met, since its sampling loop could not wait 20 ms without missing changes on the button.

Many small embedded products are built this way. A kitchen timer, a thermostat, a 3D printer controller and a battery charger all run a loop that checks several things one after another many times a second, a structure called a super-loop. Making it work requires a clock, a way of comparing times that stays correct and the discipline never to wait, and lesson 56 builds on this structure to hold each task's state explicitly.

The RP2040 system timer

A clock in firmware is a counter, read from a register, that increases at a known rate. The RP2040's system timer is a single 64-bit counter that increments once per microsecond and, as the datasheet says, cannot overflow in practice, clocked from a one-microsecond reference derived from the crystal oscillator so that its rate does not drift with the CPU clock (RP2040 datasheet §4.6.1). The timer block sits at address 0x40054000 (§4.6, TIMER_BASE).

The bus is 32 bits wide while the counter has 64, so the CPU cannot read it in one access, and the timer uses a register pair instead: reading TIMELR, the low word, latches the high word into TIMEHR until it is read, so the datasheet's rule is to read TIMELR first and then TIMEHR (§4.6.2, Table 527). Without the latch the low word could roll over between the two reads and the combined value would be off by about 4 295 s. The SDK's time_us_64() avoids the latch altogether, reading the raw high and low words TIMERAWH and TIMERAWL, reading the high word again and retrying if it changed (pico-sdk 2.3.1, timer.c), so the SDK function is preferable to a hand-written two-register read. The datasheet warns about two readers of TIMELR at once, for example an interrupt and the main loop: if one reads TIMELR and the other reads it before the first has read TIMEHR, the high word may not match the low word. Use the SDK function in both places.

For most timing the 32-bit time_us_32() suffices, returning the low 32 bits of the same counter, which wrap every 232 µs, about 4 295 s or 71.6 minutes. The SDK also offers absolute_time_t, an opaque timestamp in microseconds since boot, obtained with get_absolute_time() and used with make_timeout_time_ms() to form a deadline, absolute_time_diff_us() to compare and sleep_until() to wait (pico-sdk 2.3.1, pico/time.h). Those helpers are the right tool for a delay, but inside a super-loop with several deadlines a plain 32-bit integer is smaller and faster to compare, so the code below uses one.

Blocking waits and deadline checks

sleep_ms(500) does not return until 500 ms have passed, during which the CPU does nothing else and any LED, button or UART byte due in that time must wait, which is what blocking means. A non-blocking loop instead asks whether the deadline has been reached yet, and if not, it moves on and the loop keeps running.

A blocking program resembles a cook with three pots who stands over the first for ten minutes while the other two burn, whereas a good cook glances at the clock, stirs whichever pot is due and moves on, so sleep_ms() is standing over one pot and the deadline pattern is the glance at the clock. A cook can at least smell a pot burning, though, while a loop notices a missed deadline only when it next checks the time.

A timeline makes the difference concrete. If a button press arrives 100 ms after a sleep_ms(500) starts, it is not read until the 500 ms have passed, so the program responds 400 ms late, still correctly but with a delay the user can see. A loop that checks a deadline reads the same press on its next pass, typically a few microseconds after it arrives, because the work per pass is small, so the response time depends on the loop's period rather than on any single delay.

The loop's period matters as well. A super-loop doing 50 µs of work per pass checks its deadlines about 20 000 times a second and catches each within 50 µs of its exact time, which is usually fine for a blink, whereas a loop that stalls for several milliseconds in a printf, as lesson 53 showed, delays every deadline by as much, so the timing is only as good as the slowest path through the loop.

At 500 ms and at every whole second all three deadlines coincide, so one pass must service all three, which the loop does because it calls blink_service() for each blink on every pass and each call checks only its own deadline, while at 125 ms, 375 ms and every other odd multiple of 125 ms only the 4 Hz blink is due. Over one second the 4 Hz LED toggles eight times, four full blinks, the 2 Hz LED four times and the 1 Hz LED twice.

Consider now the timing error. If a pass arrives at 503 ms, the 500 ms deadline is 3 ms late and the toggle happens at 503 ms, but the code adds the half period to the old deadline of 500 ms, so the next deadline is 1 000 ms rather than 1 003 ms and the next toggle lands on time. That is why the deadline advances from its old value, because adding the half period to the current time would push the whole blink later on every late pass, and the error would grow over time.

  1. Three LEDs toggle at 1, 2 and 4 Hz, so their half periods are 500, 250 and 125 ms. Each blink keeps its own next deadline. The loop spins, checking the time; it never sleeps.
  2. 125 ms: the 4 Hz deadline is due. Its LED toggles and its deadline moves to 250 ms. The other two checks find nothing to do.
  3. 250 ms: two deadlines fall due. The same pass services both, because each blink_service() call checks only its own deadline.
  4. 375 ms: only the 4 Hz LED again.
  5. 500 ms: all three deadlines meet. One pass of the loop toggles all three LEDs.
  6. 625 ms: 4 Hz only.
  7. 750 ms: 2 Hz and 4 Hz.
  8. 875 ms: 4 Hz only.
  9. 1000 ms: all three again. A blocking sleep_ms() for one LED would have stalled the other two; checking deadlines keeps all three on time.

The deadline pattern in code

A blink is a deadline and a toggle: the code stores the time of the next toggle and on each pass asks whether it has arrived, and if so toggles and adds the half period to the stored deadline, the old deadline rather than the current time, so that a late pass does not slow the blink over time. 

static bool is_due(uint32_t now_us, uint32_t deadline_us) {
    return (int32_t)(now_us - deadline_us) >= 0;   /* wraparound-safe */
}

static void blink_service(blink_t *b, uint32_t now_us) {
    if (is_due(now_us, b->next_us)) {
        gpio_xor_mask(b->mask);            /* one atomic toggle (lesson 51) */
        b->next_us += b->half_us;       /* from the old deadline, not from now */
    }
}

is_due() returns true when now_us is at or after deadline_us. The subtraction is done in uint32_t and wraps modulo 232, and the cast to int32_t reads the result as a signed distance, which the next section explains. For values out of range the C standard leaves that cast to the implementation, but the Arm compiler keeps the bit pattern, which is the behaviour this code relies on.

blink_service() takes a pointer to the blink's state and, once the deadline has come, calls gpio_xor_mask(b->mask), the SIO's GPIO_OUT_XOR alias from lesson 51, a single store that flips only the pins in the mask and leaves the other two LEDs untouched. Then b->next_us += b->half_us moves the deadline on by one half period from the last deadline rather than from the current time, which keeps the rate exact.

The main loop calls blink_service() for each LED and does nothing else that waits, and since it runs many times per millisecond, the toggles land within a few microseconds of their deadlines.

Counter wraparound and signed distance

The counter wraps from 0xFFFFFFFF back to 0x00000000, which breaks a test such as now >= deadline: a deadline just below the wrap, 0xFFFFFFF0, and a time just after it, 0x00000008, give 8 >= 0xFFFFFFF0, which is false, so the LED would stop blinking for about 71 minutes.

The remedy is to subtract first. In unsigned arithmetic now − deadline is the true distance between the two times modulo 232, and read as a signed value it is positive when now is at or after the deadline and negative before it. With the numbers above, 0x00000008 − 0xFFFFFFF0 = 0x00000018 = +24, so the deadline has passed, whereas 0xFFFFFFE0 − 0xFFFFFFF0 = 0xFFFFFFF0 = −16, so it has not.

We work through the first case by hand. The deadline is 16 µs below the wrap, 232 − 16, and the time 8 µs after it, so the true distance from deadline to now is 16 + 8 = 24 µs. The unsigned subtraction 8 − (232 − 16) equals 24 − 232, which is 24 modulo 232, the bit pattern 0x00000018, whose top bit is 0, so the signed reading is +24 and the test says due.

The second case shows the other direction. The time 0xFFFFFFE0 lies 16 µs before the deadline's bit pattern, and the subtraction gives 0xFFFFFFF0, whose top bit is 1, so the signed reading is −16 and the test says not yet. The method works for any two times whose true distance is less than half the counter's range.

The subtraction is correct only for times less than 231 µs apart, about 35.8 minutes. A deadline further away is a different problem, needing a 64-bit time or a rule that the deadline is rescheduled before it gets that far.

The trick rests on the property of unsigned arithmetic covered in lesson 45, that a modulo-232 subtraction gives the correct distance even when the operands have wrapped. Common mistakes and how to spot them

A sleep left in the loop

The 4 Hz LED blinks in bursts and the uptime line comes out late, because one sleep_ms() stayed in the loop while the blinks were added. Remove every wait from the loop, and if proof is needed, measure the loop on a spare GPIO with a logic analyser.

A test for equality instead of at-or-after

A blink stops after a few seconds and never restarts, because with if (now == b->next_us) the loop, sampling the time about every 50 µs, may never see the exact microsecond of the deadline, and once it is missed the test stays false forever since the deadline never moves. Use is_due(), which catches any time at or after the deadline.

The half period added to now

All three LEDs run slightly slower than they should, with an error that grows over minutes, because b->next_us = now + b->half_us lets every late pass push the deadline later and the errors add up. Advance the stored deadline from its old value, as the code does.

A plain comparison at the wrap

All LEDs stop together about 71 minutes after boot and stay stopped until the counter wraps again, because now >= b->next_us fails across the wrap. Use the signed distance in is_due().

A deadline more than half the range away

A one-hour timeout built on time_us_32() fires early or is reported as already past, because the signed distance is valid only for times less than 231 µs apart. Use a 64-bit time for long intervals, or reschedule the deadline before it gets that far.

Periodic scheduling in larger systems

Super-loops are common in small products, and the deadline pattern appears in larger systems too. A typical design keeps a list of periodic tasks, each with a period and a next deadline, and a scheduler runs every task whose deadline has arrived, which is also what an RTOS does with its own tick, as the FreeRTOS tasks of lesson 87 show. The wraparound rule applies there as well, so RTOS code compares tick counts with the same subtraction.

Professional firmware often moves timing from polling to interrupts, the timer raising an alarm interrupt at the deadline and the handler setting a flag or running a short action, so the main loop no longer checks the time on every pass. The RP2040 timer has four alarms, each raising an interrupt on a match with the low 32 bits of the counter (§4.6.3), at the cost that an interrupt handler must stay short, as lesson 57 covers.

A reviewer checks timing code for any wait in the loop, for wraparound handling in every comparison and for deadlines that advance from their old values. A senior engineer also asks how the timing was measured, because a toggle that looks right on screen can still be milliseconds late, which only a logic analyser on a spare pin reveals reliably.

Summary

  • The RP2040 timer is a 64-bit microsecond counter, read with time_us_64(), or with time_us_32() for short intervals.
  • The 32-bit counter wraps every 232 µs, about 71.6 minutes.
  • A blink is a deadline and a toggle, and its deadline advances from the old value rather than from the current time.
  • A deadline is tested as at-or-after with a signed distance, which stays correct across the wrap.
  • The distance method is valid only for times less than 231 µs apart, about 35.8 minutes.
  • A super-loop must never wait, and its timing is set by the slowest path through the loop.
RP2040 datasheet, section 4.6 (Timer): read 4.6.1 for the 64-bit counter and its 1 µs reference, 4.6.2 (Counter) for the TIMELR and TIMEHR latch and the note about two cores, and 4.6.3 (Alarms) for the 32-bit alarm match. The register table shows the TIMER base at 0x40054000.
