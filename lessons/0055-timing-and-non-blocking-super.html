Timing and non-blocking super-loops

sleep_ms() is fine until a program needs two things at once. A blink, a button and a sensor cannot all wait in the same place. The fix is to store a deadline, check it on every pass, and never wait.

By the end of this lesson you can run three LEDs at 1, 2 and 4 Hz from one loop with no sleep_ms(), and write a deadline comparison that stays correct when the 32-bit microsecond counter wraps.

Where we are and why it matters

Lesson 51 showed how to set a pin, and lesson 52 showed how to read one. Both were quick operations. Real firmware does a lot of work between them: it blinks a status LED, reads a button, parses bytes from a UART (lesson 53), and talks to a sensor over a slow bus. If each of those steps waits in its own sleep_ms(), the others stop. The debounce in lesson 52 already ran into this. Its sampling loop could not wait for 20 ms without blinding itself to the button.

Almost every small embedded product is built this way. A kitchen timer, a thermostat, a 3D printer controller and a battery charger all run a loop that checks several things, one after another, many times a second. That structure is called a super-loop. Making it work requires a clock, a way to compare times that stays correct, and the discipline to never wait. Lesson 56 builds on this structure to hold each task's state explicitly.

What a clock gives the program

A clock in firmware is a counter that goes up at a known rate, read from a register. The RP2040 has a system timer that counts microseconds. It is a single 64-bit counter that increments once per microsecond, and the datasheet says it cannot overflow in practice. The counter is clocked from a one-microsecond reference derived from the crystal oscillator, so its rate does not drift with the CPU clock (RP2040 datasheet §4.6.1). The timer block sits at address 0x40054000 (§4.6, TIMER_BASE).

The bus is 32 bits wide, and the counter is 64 bits, so the CPU cannot read it in one access. The timer uses a pair of registers. Reading TIMELR, the low word, latches the high word into TIMEHR, so the high word stops changing until it is read. The datasheet's rule is to read TIMELR first, then TIMEHR (§4.6.2, Table 527). Without the latch, the low word could roll over between the two reads, and the combined value would be off by about 4 295 seconds. The SDK's time_us_64() avoids the latch: it reads the raw high and low words, TIMERAWH and TIMERAWL, reads the high word again, and retries if it has changed (pico-sdk 2.3.1, timer.c). Use the SDK function rather than writing your own two-register read.

The datasheet warns about two cores reading TIMELR at the same time, for example in an interrupt and in the main loop. If one core reads TIMELR and the other core reads it before the first has read TIMEHR, the high word may not match the low word. Use the SDK function in both places.

For most timing, the 32-bit time_us_32() is enough. It returns the low 32 bits of the same counter. It wraps every 232 µs, which is about 4 295 seconds, or 71.6 minutes. The SDK also has absolute_time_t, an opaque timestamp in microseconds since boot. You get one with get_absolute_time(), make a deadline with make_timeout_time_ms(), compare with absolute_time_diff_us(), and wait with sleep_until() (pico-sdk 2.3.1, pico/time.h). Those helpers are the right tool when you write a delay. Inside a super-loop with several deadlines, a plain 32-bit integer is smaller and faster to compare, and the code below uses one.

Blocking vs checking the time

sleep_ms(500) does not return until 500 ms have passed. The CPU does nothing else during that time, and any LED, button or UART byte that should be handled in those 500 ms waits. That is blocking. A non-blocking loop asks instead: is the deadline reached yet? If not, it moves on, and the loop keeps running.

Compare the two with a timeline. Suppose a button press arrives 100 ms after a sleep_ms(500) starts. The press is not read until 500 ms have passed, so the program responds 400 ms late. The button is still pressed, and the code is still correct, but the delay is visible to the user. In a loop that checks a deadline, the same press is read on the next pass, which is typically a few microseconds after it arrives. The work done per pass is small, so the response time depends on the loop's period and not on any single delay.

The loop's period matters too. A super-loop that does 50 µs of work per pass checks its deadlines about 20 000 times a second. A deadline is then caught within 50 µs of its exact time, and that is usually fine for a blink. A loop that stalls in a 20 ms printf, as lesson 53 showed, delays every deadline by that much. The timing is only as good as the slowest path through the loop.

A worked example: three blinks on one timeline

The project's three LEDs toggle at 1, 2 and 4 Hz. A 1 Hz blink has a period of one second, and its LED is on for half of it, so it toggles every 500 000 µs. A 2 Hz blink toggles every 250 000 µs, and a 4 Hz blink every 125 000 µs. Each deadline is the start time plus a multiple of its half period. Take the start as time 0, which is the value time_us_32() returned once before the loop.

Read the table to see what the loop must do. At 500 ms and at every whole second, all three deadlines fall on the same instant, so one pass of the loop must service all three. The loop does that, because blink_service() is called for each blink on every pass, and each call checks only its own deadline. At 125 ms, 375 ms and every other odd multiple of 125 ms, only the 4 Hz blink is due. Over one second the 4 Hz LED toggles eight times, which is four full blinks, the 2 Hz LED toggles four times, and the 1 Hz LED toggles twice.

Now the timing error. If a pass arrives at 503 ms, the 500 ms deadline is 3 ms late, and the toggle happens at 503 ms. The code then adds the half period to the old deadline, 500 ms, and gets 1000 ms as the next deadline, not 1003 ms. The next toggle still lands on time. This is the reason the deadline is advanced from the old value. If the code added the half period to the current time, every late pass would push the whole blink later, and the error would grow over time.

The deadline pattern

A blink is a deadline and a toggle. Store the time of the next toggle, and on each pass ask whether it has arrived. If it has, toggle, and add the half period to the stored deadline. Add to the old deadline, not to the current time, so a late pass does not make the blink slower over time. 

static bool is_due(uint32_t now_us, uint32_t deadline_us) {
    return (int32_t)(now_us - deadline_us) >= 0;   /* wraparound-safe */
}

static void blink_service(blink_t *b, uint32_t now_us) {
    if (is_due(now_us, b->next_us)) {
        gpio_xor_mask(b->mask);            /* one atomic toggle (lesson 51) */
        b->next_us += b->half_us;       /* from the old deadline, not from now */
    }
}

Line by line. is_due() returns true when now_us is at or after deadline_us. The subtraction is done in uint32_t, so it wraps modulo 232, and the cast to int32_t reads the result as a signed distance. The next section explains why that works. The cast is an implementation detail that the C standard leaves to the compiler for values out of range, but on the Arm compiler the cast keeps the bit pattern, which is the behaviour this code relies on.

blink_service() takes a pointer to the blink's state. When the deadline has come, it calls gpio_xor_mask(b->mask). That is the SIO's GPIO_OUT_XOR alias from lesson 51: one store that flips only the pins named in the mask, so the other two LEDs are untouched. Then b->next_us += b->half_us moves the deadline on by one half period. The stored value is the one from the last deadline, not the current time, which is what keeps the rate exact.

The main loop calls blink_service() for each LED and does nothing else that waits. The loop runs many times per millisecond, so the toggles land within a few microseconds of their deadlines.

Wraparound: why subtract first

The counter wraps from 0xFFFFFFFF back to 0x00000000. A test such as now >= deadline is wrong across that wrap. A deadline just below the wrap, 0xFFFFFFF0, and a time just after it, 0x00000008, give 8 >= 0xFFFFFFF0, which is false. The LED would stop blinking for about 71 minutes.

Subtract instead. In unsigned arithmetic, now − deadline is the true distance between the two times, modulo 232. Reading that result as a signed value gives a positive number when now is at or after the deadline, and a negative one when it is before. Here is the check with the numbers above: 0x00000008 − 0xFFFFFFF0 = 0x00000018 = +24, so the deadline has passed. 0xFFFFFFE0 − 0xFFFFFFF0 = 0xFFFFFFF0 = −16, so it has not.

Work through the first case by hand. The deadline is 16 µs below the wrap, so 232 − 16. The time is 8 µs after the wrap. The true distance from the deadline to now is 16 + 8 = 24 µs. The unsigned subtraction 8 − (232 − 16) equals 24 − 232, which is 24 modulo 232. The bit pattern is 0x00000018. Its top bit is 0, so the signed reading is +24, and the test says due.

The second case shows the other direction. The time is 0xFFFFFFE0, which is 16 µs before the deadline's bit pattern. The subtraction gives 0xFFFFFFF0, whose top bit is 1, so the signed reading is −16, and the test says not yet. The trick works for any two times whose true distance is less than half the counter's range.

The subtraction is right only if the two times are less than 231 µs apart, which is about 35.8 minutes. A deadline further away than that is a different problem: it needs a 64-bit time, or a check that you reschedule the deadline before it gets that far.
The trick is the same as the one you know from unsigned arithmetic: the result of a modulo-232 subtraction is correct even when the operands have wrapped. Lesson 45 covers unsigned wraparound.

Common mistakes and how to spot them

Mistake 1: a sleep left in the loop. You leave one sleep_ms() in the loop while you add the blinks. Symptom: the 4 Hz LED blinks in bursts, and the uptime line comes out late. Fix: remove every wait from the loop, and measure the loop with a spare GPIO on a logic analyzer if you need proof.

Mistake 2: testing equality instead of at-or-after. You write if (now == b->next_us). Symptom: a blink stops after a few seconds, and never restarts. The loop samples the time about every 50 µs, so the exact microsecond of the deadline may never be seen. Once the deadline is missed, the test is false forever, because the deadline never moves. Fix: use is_due(), which catches any time at or after the deadline.

Mistake 3: adding the half period to now. You write b->next_us = now + b->half_us. Symptom: all three LEDs run a little slower than they should, and the error grows over minutes. Each late pass pushes the deadline later, and the errors add up. Fix: advance the stored deadline from its old value, as the code does.

Mistake 4: a plain greater-than at the wrap. You write now >= b->next_us. Symptom: all LEDs stop together about 71 minutes after boot, and they stay stopped until the next wrap at the same point. Fix: use the signed distance in is_due().

Mistake 5: a deadline more than half the range away. You set a timeout of an hour with time_us_32(). Symptom: the timeout fires early, or the check reports it as already past. The signed distance is only valid for times less than 231 µs apart. Fix: use a 64-bit time for long intervals, or reschedule the deadline before it gets that far.

In real projects

Super-loops are common in small products, and the same deadline pattern appears in larger systems. A typical design keeps a list of periodic tasks, each with a period and a next deadline, and the scheduler runs every task whose deadline has arrived. An RTOS does the same job with its own tick, and lesson 87 introduces FreeRTOS tasks. In both cases the wraparound rule still applies, so the RTOS code compares tick counts with the same subtraction trick.

Professional firmware often moves the timing from polling to interrupts. The timer raises an alarm interrupt at the deadline, and the handler sets a flag or runs a short action. The main loop then does not check the time on every pass. The RP2040 timer has four alarms that each raise an interrupt on a match of the low 32 bits of the counter (§4.6.3). The trade-off is that an interrupt handler must stay short, which lesson 57 covers.

A reviewer checks timing code for three things. Is there a wait anywhere in the loop? Does each comparison handle wraparound? Does each deadline advance from its old value? A senior engineer also asks how the timing was measured. A toggle that looks right on the screen can still be late by milliseconds, so a logic analyzer on a spare pin is the honest test.

Interviewers ask about this because the answer shows that you understand time as a number that wraps. A question about a timer that stops working after a long run is a test of exactly this knowledge.

You replaced a blocking wait with deadlines that a single loop checks, and you wrote a comparison that stays right across the 32-bit wrap. That is the core structure of a firmware super-loop.

Summary

  • The RP2040 timer is a 64-bit microsecond counter. Read it with time_us_64(), or use time_us_32() for short intervals.
  • The 32-bit counter wraps every 232 µs, which is about 71.6 minutes.
  • A blink is a deadline and a toggle. Advance the deadline from its old value, not from now.
  • Test a deadline with at-or-after, using a signed distance, so the test stays right across the wrap.
  • The distance trick is valid only for times less than 231 µs apart, about 35.8 minutes.
  • A super-loop must never wait. Its timing is set by the slowest path through the loop.

"A timer counter wraps. How do you check whether a deadline has passed, and what breaks if you compare with a plain greater-than?" Answer out loud in 60 seconds, then compare.

Model answer

I subtract the deadline from the current time in unsigned arithmetic, and test the sign of the result by casting it to a signed integer. That gives the correct distance modulo the counter width, so it stays right across the wrap, as long as the two times are less than half the range apart. A plain greater-than fails at the wrap: a deadline just before the wrap looks larger than a time just after it, so the event is missed for a whole counter period. I'd also say how long the counter takes to wrap, since that sets the largest interval the check can handle, and use a 64-bit counter if the interval can be longer.

RP2040 datasheet, section 4.6 (Timer): read 4.6.1 for the 64-bit counter and its 1 µs reference, 4.6.2 (Counter) for the TIMELR and TIMEHR latch and the note about two cores, and 4.6.3 (Alarms) for the 32-bit alarm match. The register table shows the TIMER base at 0x40054000.
