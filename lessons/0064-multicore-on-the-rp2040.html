Multicore on the RP2040

Two cores sharing memory through FIFOs and spinlocks

Concept lesson, optional for the Wokwi path. Wokwi simulates only one Pico core (see NOTES.md), so there is no multicore project to run. You will learn the mechanisms from the datasheet, predict races on paper, and review code for the bugs they cause. To run the code for real, use any Raspberry Pi Pico board with the Pico SDK; the same reasoning applies there, where both cores run at the same time.

By the end of this lesson you can launch core 1 with the Pico SDK, pass a value between the cores through the SIO FIFO, protect a shared counter with a hardware spinlock, and spot a shared-data race in a code review.

A second processor on the chip

Lesson 63 ended with a driver talking to one sensor from one core, lesson 61 put a display on the same I2C bus, and lesson 57 showed the only way code on a single core can run in the middle of other code, an interrupt. This lesson adds a second processor, because the RP2040 on the Pico has two Arm Cortex-M0+ cores, both able to run C code at the same time.

The reason to use both is timing. A common product layout puts the user interface, the display and the logging on one core and a time-critical job, such as sampling a sensor at a fixed rate or driving a motor, on the other, so that the slow core can take as long as it needs without making the fast core late. The price is that the cores must share data, such as the newest sensor reading or a buffer of samples, and since almost every multicore bug comes from that shared data, reviewers examine each shared variable with care.

Two cores sharing one memory

A CPU core is one processor with its own registers and stack pointer, repeating one cycle of fetching an instruction from memory, decoding and executing it and moving to the next, the cycle that lesson 28 described for one CPU. A dual-core chip runs two of those cycles side by side, each with its own program counter.

Both cores reach the same SRAM (the on-chip read-write memory holding variables and stacks), the same peripherals and the same GPIO pins through the chip's bus fabric, the set of wires and switches that carries each access from a core to its target. When both cores want the bus in the same cycle, they compete for it and one waits, and the RP2040 datasheet describes this shared bus in section 2.1, noting that multiple masters may compete for bus access (RP2040 datasheet, sections 2.1 and 2.5.3.2).

Each core has its own stack, so local variables are safe, but a global variable has one address in SRAM that both cores can read and write. Nothing in the hardware groups C statements so that one core finishes them before the other starts, so between any two statements of one core a statement of the other can land, which is called interleaving and is the root of every race in this lesson.

Interrupt masking on one core and on two

On a single core, interleaving happens in only one way, an interrupt running in the middle of foreground code, and it can be stopped, as lesson 57 did by switching interrupts off for a few instructions so that the update is safe. On two cores that trick is only half a fix, because switching interrupts off on core 0 does nothing to core 1, which keeps running its own instructions, so a lock is needed that both cores see and that the hardware makes indivisible.

The RP2040 provides that lock and a message channel as well, both in the SIO, the single-cycle I/O block sitting directly on each core's I/O port, where a read or write takes one cycle while a normal bus access takes two or more (RP2040 datasheet, section 2.3.1). The SIO holds the inter-core FIFOs, the 32 hardware spinlocks and the GPIO registers that both cores can share.

A lost update in count++

In C, count++ is three steps, loading the value from memory into a register, adding one and storing the register back, and the compiler usually emits one instruction for each, so the other core can run its own steps in between. With a counter starting at 5, core 0 loads 5 and core 1 loads 5 before core 0 has stored anything, both add one and both store 6, so two increments raise the counter by only one.

At scale the loss adds up: if core 0 and core 1 each run shared++ 100 000 times without a lock, the true total is 200 000 and the result can be any lower number. Each lost update is rare on any one step, so a test may pass a hundred times and fail on the hundred-and-first run, which is why multicore races are found by review and by design rather than by testing alone.

volatile does not fix this. Lesson 46 showed that volatile forces a reload on each access, but it gives no atomicity and no ordering between the two cores. The cppreference page on volatile says exactly that (cppreference: volatile).

Launching core 1

After reset, core 0 runs the boot sequence while core 1 runs no user code, the datasheet stating that core 1 enters a deep sleep state and stays there until user code wakes it through the mailbox, the inter-core FIFO described below (RP2040 datasheet, sections 2.3.1.1 and 2.8.2). Before it can run, core 1 needs a stack pointer, an entry point and a vector table, the table of handler addresses the core jumps to on an exception (lesson 42).

The datasheet gives a six-word handshake for this, with both cores moving through a small state machine together (section 2.8.2), but it is never written by hand, because the Pico SDK wraps it in one call. 

#include "pico/multicore.h"

static void core1_entry(void) {
    /* runs on core 1, with its own stack */
    while (true) {
        /* core 1 work goes here */
    }
}

int main(void) {
    multicore_launch_core1(core1_entry);   /* wakes core 1 and starts it at core1_entry */
    /* core 0 carries on with its own work */
}

The #include brings in the SDK's multicore API, and core1_entry is an ordinary function that the SDK calls on core 1, so it takes no arguments and returns nothing, its while (true) loop keeping core 1 busy as a real program would. In main, multicore_launch_core1 takes the function pointer, wakes core 1 through the handshake and returns on core 0 once core 1 has started, after which core 0 carries on. The SDK's default stack for core 1 sits below core 0's stack, while multicore_launch_core1_with_stack gives core 1 a stack of its own, the better choice when the two stacks must be sized separately.

The inter-core FIFOs

A FIFO (first in, first out) is a queue whose items come out in the order they went in. The SIO has two hardware FIFOs, each 32 bits wide and eight entries deep, one carrying words from core 0 to core 1 and the other from core 1 to core 0, so each core writes to its outgoing FIFO and reads from its incoming one, while a status register, FIFO_ST, reports whether the incoming FIFO has data (the VLD bit) and whether the outgoing one has room (the RDY bit) (RP2040 datasheet, section 2.3.1.4).

Writing to a full FIFO or reading an empty one leaves the contents intact but sets a sticky error flag (WOF or ROE), a sign of a bug in the protocol, so the SDK's blocking calls check the status first, multicore_fifo_push_blocking() waiting until there is room and multicore_fifo_pop_blocking() until a word arrives. The pop sleeps with the WFE (wait for event) instruction between checks and the push sends an event with SEV (send event) after each word, so the waiting core is woken without busy looping, and multicore_fifo_pop_timeout_us() provides a bounded wait (Pico SDK, pico_multicore).

The FIFO is also the right tool for handing over ownership of data. Suppose core 1 fills slot 3 of a four-slot sample buffer for core 0 to process: core 1 pushes the number 3 into the FIFO and stops touching slot 3, and core 0 pops the 3, reads slot 3 and only then gives the slot back. Each slot thus has one owner at any moment, the message being the hand-over, so no core spins and no lock is held while the sample is processed.

The FIFO can also raise an interrupt, the datasheet listing the FIFO IRQ outputs as system interrupts 15 (SIO_IRQ_PROC0) and 16 (SIO_IRQ_PROC1), with core 0 typically using 15 and core 1 using 16 (RP2040 datasheet, sections 2.3.1.4 and 2.3.2, Table 80), so a handler on core 1 can wake when a word arrives instead of waiting in a pop.

The FIFOs work like two pneumatic tubes between two offices, one in each direction, each office dropping capsules into its outgoing tube and taking them from its incoming one in order. Nobody shares a desk, so nobody fights over one, and a full tube makes the sender wait while an empty one makes the receiver wait. Real tubes carry any parcel, however, whereas each FIFO entry is a single 32-bit word, so larger data travels as an index or a pointer to memory that the receiver then owns.

Hardware spinlocks

A spinlock is a lock held by spinning, a core repeating a check until it succeeds. The SIO provides 32 of them, each one bit in a register at addresses SPINLOCK0 to SPINLOCK31 (RP2040 datasheet, section 2.3.1.3), with two operations: a read tries to claim the lock, returning nonzero if the claim worked and zero if someone already holds it, and a write of any value releases it. If both cores try to claim the same lock in the same clock cycle, core 0 succeeds.

The hardware makes the claim indivisible, which a software lock cannot achieve alone, because two cores could each read a flag as free and each set it, so a lock that works across cores needs an operation that reads and claims in one step, and the spinlock provides it. The datasheet intends spinlocks for short critical sections, the stretches of code that must not be interleaved with the other core, because a core that loses a race spins and does no other work, so a long hold wastes the other core's time.

A spinlock resembles the key to a single-occupancy room hanging on a hook: whoever takes the key goes in, and anyone else arriving keeps checking the hook until the key returns. The hardware makes looking at the hook and taking the key a single step, so two people can never both take it. A person waiting for a key would sit down, though, whereas a spinning core keeps checking at full speed, which is why the time inside must be short.

The SDK wraps the hardware in a small API, and the complete example below is explained line by line after it. 

static spin_lock_t *counter_lock;      /* made once, in main(), with spin_lock_init() */
static volatile uint32_t shared_count;

void bump_shared(void) {
    uint32_t saved = spin_lock_blocking(counter_lock);  /* claim, and disable interrupts */
    shared_count++;                                    /* only one core is in here */
    spin_unlock(counter_lock, saved);                  /* release, and restore interrupts */
}

counter_lock is a pointer to the lock rather than the lock itself, set up once in main() with counter_lock = spin_lock_init((uint)spin_lock_claim_unused(true));, where spin_lock_claim_unused(true) returns the number of a free lock that nothing else in the program has claimed. On the RP2040 the SDK reserves locks 0 to 13 for itself, 14 and 15 for an operating system and 16 to 23 for shared striped use, so claimed locks come from the range 24 to 31, and the call panics if none is free (Pico SDK, hardware_sync), whereas a number picked by hand risks colliding with a library that already uses it.

Inside bump_shared, the first line calls spin_lock_blocking, the form that also disables interrupts on the calling core before spinning, using save_and_disable_interrupts, which returns the old interrupt state kept in saved, and then claiming the lock. This prevents a deadlock on one core, since an interrupt handler on core 0 trying to take the same lock while the foreground code held it would spin forever. The second line does the protected work, and the third, spin_unlock, releases the lock and restores the interrupt state from saved, which must therefore stay unchanged in between.

The volatile on shared_count is not what protects it, because the lock does, and the keyword only makes the compiler reload the value inside the lock, which is still needed, since the other core may have changed it while this core waited.

The lock protects the data, not the code. Every access to shared_count on both cores must take the same lock. One unlocked read or write in one place is enough to break it.

Choosing between FIFOs, spinlocks and atomic GPIO

The tool follows from the shape of the sharing rather than from habit, and each rule below gives the tool and the reason.

  1. Passing a message or handing over a buffer: use a FIFO, sending an index or a pointer and letting the receiving core own the data after the pop, so the hand-over happens once and the data is never shared while both cores can touch it.
  2. Sharing a counter or small structure that both cores read and write: use a spinlock around every access, keeping the critical section to a few lines so that the other core spins only briefly.
  3. Setting or clearing one GPIO bit from both cores: use the SIO's atomic GPIO registers, the SET, CLR and XOR aliases, rather than a read-modify-write on the output register. The datasheet says both cores can write these registers with the result as though core 0 wrote first and core 1 immediately afterward (RP2040 datasheet, section 2.3.1.2), whereas a read-modify-write on the OUT register can lose the other core's change.

The cost is the same in every case, a lock or a FIFO wait being time the other core might have spent working, so the shared part should be as short as possible, and moving work out of the critical section is usually the best speed-up and the first change a reviewer asks for.

Common mistakes and how to spot them

The mistakes below appear in real reviews, each with its symptom and fix, so that it can be recognised in a log or in a code review.

An unlocked read-modify-write

The total comes out low, by a different amount on every run, because code such as shared_count++ is called from both cores without a lock. Take the lock around every access on both cores, or move the update to one core and send the new value through a FIFO.

A lock left held by an early return

The other core stops making progress, a debugger showing it stuck inside spin_lock_blocking and the serial log ending after an error, because a function took the lock, hit the error and returned before spin_unlock. Give the function one exit path, storing the result in a variable, letting every branch fall through to spin_unlock and returning the variable at the end.

A flag published before the data

The first few samples are occasionally wrong on some runs, because core 0 sets ready = 1 before filling the buffer and core 1 sees the flag and reads the buffer too early. Fill the data first and hand it over with a FIFO push, or, if a shared flag is unavoidable, place a memory barrier (__dmb(), which the SDK provides) between the data write and the flag write and another between seeing the flag and reading the data, remembering that volatile is not a barrier.

A blocking wait while holding the lock

Both cores stop and neither makes progress, because core 0 takes the lock and calls multicore_fifo_pop_blocking() to wait for core 1, while core 1 needs the same lock before it can send the message and spins, each core waiting for the other in a deadlock. Finish the wait before taking the lock, or send the message before taking it.

The same lock taken twice

The core hangs forever at the second spin_lock_blocking while the other core carries on, because a helper that takes the lock is called from a function already holding it, and as the SDK comments state, a hardware spinlock may not be acquired re-entrantly. Split the code into an outer function that takes the lock and an inner one that assumes it is held.

volatile trusted as protection

The same lost updates as with an unlocked read-modify-write appear, because the author assumed that marking the data volatile made it safe. Treat the lock as the protection and use volatile only to stop the compiler caching the value inside the lock.

Each mistake yields to the same three questions, which core can see the data, which lock or FIFO covers it, and whether any path leaves the lock held or waits for the other core while holding it, and those questions find most multicore bugs.

Multicore design and review in products

Multicore firmware appears where one part of a product must never wait for another, a motor loop beside a user interface, a sensor sampler beside a network stack or a fast protocol engine beside slow logging. The usual split gives each core one job and each piece of data one owner, with the FIFO carrying data between the two jobs and a spinlock appearing only where data really is shared, guarding a short list of variables.

A senior engineer reviewing such code asks for a comment beside each lock naming the data it protects, so that the next reader knows what must be locked, a check that no path leaves a lock held and no blocking call sits inside a critical section, and a clear reason for every shared variable explaining why it cannot be a FIFO message instead. Those checks are short, and they catch the mistakes above before they reach a board.

The SDK builds higher-level tools on the same hardware, its critical_section API being a spinlock with a name and its mutex and queue types resting on the same ideas, and these are the ones to use when they fit.

Summary

  • Two cores share one SRAM and one set of peripherals, so either core can change a shared variable between two of the other core's steps.
  • Disabling interrupts protects only the core that disables them, so shared data needs a lock that both cores see.
  • count++ is a load, an add and a store, so two cores can lose an update, which volatile does not prevent.
  • Core 1 sleeps after reset until multicore_launch_core1() wakes it through the SDK's handshake on the inter-core FIFO.
  • Each inter-core FIFO is 32 bits wide and eight entries deep and serves to pass messages and hand over ownership of data.
  • The SIO has 32 hardware spinlocks, a read claiming one and a write releasing it, and spin_lock_blocking() also disables interrupts on the calling core.
  • GPIO bits that both cores touch are changed through the SIO's SET, CLR and XOR aliases rather than a read-modify-write.
  • The common mistakes are an unlocked update, an early return that keeps a lock, a flag set before its data, a blocking wait inside a lock and taking the same lock twice.
