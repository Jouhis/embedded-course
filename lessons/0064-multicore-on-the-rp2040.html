Multicore on the RP2040: FIFOs and spinlocks

The RP2040 has two cores that share one memory. Two cores running at once make a race that one core can never have, and the chip gives you two tools to stop it: a FIFO to pass messages and a spinlock to take turns.

Concept lesson, optional for the Wokwi path. Wokwi simulates only one Pico core (see NOTES.md), so there is no multicore project to run. You will learn the mechanisms from the datasheet, predict races on paper, and review code for the bugs they cause. To run the code for real, use any Raspberry Pi Pico board with the Pico SDK; the same reasoning applies there, where both cores run at the same time.

By the end of this lesson you can launch core 1 with the Pico SDK, pass a value between the cores through the SIO FIFO, protect a shared counter with a hardware spinlock, and spot a shared-data race in a code review.

Where we are and why it matters

Lesson 63 ended with a driver that talks to one sensor from one core. Lesson 61 put a display on the same I2C bus, and lesson 57 showed the only way code on a single core can run in the middle of other code: an interrupt. This lesson adds a second processor. The RP2040 on the Pico has two Arm Cortex-M0+ cores, and both can run your C code at the same time.

The reason to do this is timing. A common product layout puts the user interface, the display and the logging on one core, and a time-critical job such as sampling a sensor at a fixed rate or driving a motor on the other. The slow core can then take as long as it needs without making the fast core late. The price is that the two cores have to share data, such as the newest sensor reading or a buffer of samples. Almost every multicore bug comes from that shared data, and reviewers look at each shared variable with care.

Two cores, one memory

A CPU core is one processor. It has its own registers and its own stack pointer, and it repeats one cycle: fetch an instruction from memory, decode it, execute it, and move to the next. Lesson 28 described that cycle for one CPU. A dual-core chip is two of those cycles running side by side, each with its own program counter.

The two cores are not separate computers. Both reach the same SRAM (the on-chip read-write memory that holds your variables and stacks), the same peripherals and the same GPIO pins, through the chip's bus fabric. The bus is the set of wires and switches that carries each access from a core to its target. When both cores want the bus in the same cycle, they compete for it, and one of them waits. The RP2040 datasheet describes this shared bus in section 2.1, and it notes that multiple masters may compete for bus access (RP2040 datasheet, sections 2.1 and 2.5.3.2).

Each core has its own stack, so local variables are safe. A global variable has one address in SRAM, and both cores can read and write it. Nothing in the hardware groups your C statements so that one core finishes them before the other starts. For any two statements, one core's statement can land between two of the other core's statements. Programmers call this interleaving, and it is the root of every race in this lesson.

Why one core is different

On a single core, interleaving happens in only one way: an interrupt runs in the middle of foreground code. You can stop that. Lesson 57 used this: the foreground code switches interrupts off for a few instructions, the interrupt cannot run, and the update is safe. That trick is only half a fix on two cores. Switching interrupts off on core 0 does nothing to core 1, which keeps running its own instructions. You need a lock that both cores see, and that the hardware makes indivisible.

The RP2040 gives you that lock, and a message channel too. Both live in the SIO block, the single-cycle I/O block that sits directly on each core's I/O port. A read or write to the SIO takes one cycle, while a normal bus access takes two or more (RP2040 datasheet, section 2.3.1). The SIO holds the inter-core FIFOs, the 32 hardware spinlocks, and the GPIO registers that both cores can share.

The race in one line

In C, count++ is three steps: load the value from memory into a register, add one, and store the register back. The compiler usually emits one instruction for each step, and the other core can run its own steps between yours. Take a counter that starts at 5. Core 0 loads 5. Core 1 loads 5 before core 0 has stored anything. Both add one and both store 6. Two increments happened, and the counter went up by one.

Run it at scale and the loss adds up. If core 0 and core 1 each run shared++ 100000 times with no lock, the true total is 200000, and the result can be any lower number. Each lost update is rare on any one step, so a test may pass a hundred times and fail on the hundred-and-first run. That is why multicore races are found by review and by design, not only by testing.

volatile does not fix this. Lesson 46 showed that volatile forces a reload on each access, but it gives no atomicity and no ordering between the two cores. The cppreference page on volatile says exactly that (cppreference: volatile).

Starting core 1

After reset, core 0 runs the boot sequence. Core 1 does not run your code. The datasheet says that core 1 goes into a deep sleep state and stays there until user code wakes it through the mailbox, which is the inter-core FIFO described below (RP2040 datasheet, sections 2.3.1.1 and 2.8.2). Core 1 needs three things before it can run: a stack pointer, an entry point and a vector table, which is the table of handler addresses the core jumps to on an exception (lesson 42).

The datasheet gives a six-word handshake for this, with both cores moving through a small state machine together (section 2.8.2). You never write it yourself. The Pico SDK wraps it in one call: 

#include "pico/multicore.h"

static void core1_entry(void) {
    /* runs on core 1, with its own stack */
    while (true) {
        /* core 1 work goes here */
    }
}

int main(void) {
    multicore_launch_core1(core1_entry);   /* wakes core 1 and starts it at core1_entry */
    /* core 0 carries on with its own work */
}

Line by line: the #include brings in the SDK's multicore API. core1_entry is an ordinary function, but the SDK calls it on core 1, so it has no arguments and no return value to send back. Its while (true) loop keeps core 1 busy, as a real program would. In main, multicore_launch_core1 takes the function pointer, wakes core 1 through the handshake, and returns on core 0 once core 1 has started. Core 0 then carries on. The SDK's default stack for core 1 sits below core 0's stack; multicore_launch_core1_with_stack lets you give core 1 a stack of your own, which is the better choice when the two stacks must be sized separately.

Tool 1: the inter-core FIFOs

A FIFO (first in, first out) is a queue: items come out in the order they went in. The SIO has two hardware FIFOs. Each is 32 bits wide and eight entries deep. One carries words from core 0 to core 1, and the other carries words from core 1 to core 0. Each core writes to its outgoing FIFO and reads from its incoming one. A status register, FIFO_ST, reports whether the incoming FIFO has data (the VLD bit) and whether the outgoing FIFO has room (the RDY bit) (RP2040 datasheet, section 2.3.1.4).

If you write to a full FIFO or read an empty one, the FIFO keeps its contents, but a sticky error flag is set (WOF or ROE). That is a sign of a bug in your protocol, so the SDK's blocking calls check the status for you. multicore_fifo_push_blocking() waits until there is room, and multicore_fifo_pop_blocking() waits until a word arrives. The pop sleeps with the WFE (wait for event) instruction between checks, and the push sends an event with SEV (send event) after each word, so the waiting core is woken without busy looping. The SDK also has multicore_fifo_pop_timeout_us() for a bounded wait (Pico SDK, pico_multicore).

The FIFO is also the right tool to hand over ownership of data. Suppose core 1 fills slot 3 of a four-slot sample buffer, and core 0 should process it. Core 1 pushes the number 3 into the FIFO and then stops touching slot 3. Core 0 pops the 3, reads slot 3, and only then gives the slot back. At any moment, one core owns each slot, and the message is the hand-over. No core spins, and no lock is held while the sample is processed.

The FIFO can also raise an interrupt. The datasheet lists the FIFO IRQ outputs as system interrupts 15 (SIO_IRQ_PROC0) and 16 (SIO_IRQ_PROC1), and says that core 0 typically uses 15 and core 1 uses 16 (RP2040 datasheet, sections 2.3.1.4 and 2.3.2, Table 80). A handler on core 1 can therefore wake when a word arrives, instead of waiting in a pop.

Tool 2: hardware spinlocks

A spinlock is a lock that is held by spinning: a core repeats a check until the check succeeds. The SIO provides 32 of them, each one bit in a register, at addresses SPINLOCK0 to SPINLOCK31 (RP2040 datasheet, section 2.3.1.3). Each lock has two operations. A read tries to claim it: the read returns nonzero if the claim worked, and zero if someone already holds it. A write of any value releases it. If both cores try to claim the same lock in the same clock cycle, core 0 succeeds.

The hardware makes the claim indivisible. That is the part a software lock cannot do alone, because two cores can each read a flag as free and each set it. A lock that works across cores needs an operation that reads and claims in one step, and the spinlock is that operation. The datasheet says spinlocks are for short critical sections, the stretches of code that must not be interleaved with other cores. A core that loses a race spins and does no other work, so a long hold wastes the other core's time.

The SDK wraps the hardware in a small API. This is a complete example, and each line is explained below it: 

static spin_lock_t *counter_lock;      /* made once, in main(), with spin_lock_init() */
static volatile uint32_t shared_count;

void bump_shared(void) {
    uint32_t saved = spin_lock_blocking(counter_lock);  /* claim, and disable interrupts */
    shared_count++;                                    /* only one core is in here */
    spin_unlock(counter_lock, saved);                  /* release, and restore interrupts */
}

Line by line. counter_lock is a pointer to the lock, not the lock itself. It is set up once, in main(), with counter_lock = spin_lock_init((uint)spin_lock_claim_unused(true));. spin_lock_claim_unused(true) returns the number of a free lock that nobody else in the program has claimed. On the RP2040 the SDK reserves locks 0 to 13 for itself, 14 and 15 for an operating system and 16 to 23 for shared striped use, so claimed locks come from the range 24 to 31, and the call panics if none is free (Pico SDK, hardware_sync). Picking a number by hand risks colliding with a library that already uses it.

Inside bump_shared, the first line calls spin_lock_blocking. Its name matters: it is the form that also disables interrupts on the calling core before it spins. The SDK does this with save_and_disable_interrupts, which returns the old interrupt state, and then claims the lock. The return value is kept in saved. This prevents a deadlock on one core: if an interrupt handler on core 0 tried to take the same lock while the foreground code held it, the handler would spin forever. The second line does the protected work. The third line is spin_unlock, which releases the lock and then restores the interrupt state from saved. The state must be passed back, so the function must not change it in between.

The volatile on shared_count is not what protects it. The lock does. The keyword only makes the compiler reload the value inside the lock, which is still needed, because the other core may have changed it while this core was waiting.

The lock protects the data, not the code. Every access to shared_count on both cores must take the same lock. One unlocked read or write in one place is enough to break it.

Which tool for which job

Choose the tool by the shape of the sharing, not by habit. Each rule below gives the tool to use and the reason.

  1. Passing a message, or handing over ownership of a buffer: use a FIFO. Send an index or a pointer, and let the receiving core own the data after the pop. The hand-over happens once, and the data is never shared while both cores can touch it.
  2. Sharing a counter or a small structure that both cores read and write: use a spinlock around every access. Keep the critical section to a few lines, so the other core spins for only a short time.
  3. Setting or clearing one GPIO bit from both cores: use the SIO's atomic GPIO registers, the SET, CLR and XOR aliases, not a read-modify-write on the output register. The datasheet says both cores can write these registers, and that the result is as though core 0 wrote first and core 1 wrote immediately afterward (RP2040 datasheet, section 2.3.1.2). A read-modify-write on the OUT register can lose the other core's change.

The cost is the same in every case. A lock or a FIFO wait is time that the other core might have spent on work, so keep the shared part as short as you can. Moving work out of the critical section is usually the best speed-up, and it is the change a reviewer asks for first.

Common mistakes and how to spot them

The mistakes below are the ones that show up in real reviews. Each one comes with its symptom and its fix, so you can recognise it in a log or in a code review.

  1. An unlocked read-modify-write. Code such as shared_count++ with no lock, called from both cores. Symptom: the total is low, and the low value changes from run to run. Fix: take the lock around every access on both cores, or move the update to one core and send the new value through a FIFO.
  2. A lock left held by an early return. A function takes the lock, hits an error and returns before spin_unlock. Symptom: the other core stops making progress. A debugger shows it stuck inside spin_lock_blocking, and the serial log stops after the error. Fix: have one exit path, so the unlock always runs. Store the result in a variable, let every branch fall through to spin_unlock, and return the variable at the end.
  3. A flag published before the data. Core 0 sets ready = 1 and then fills the buffer. Core 1 sees the flag and reads the buffer too early. Symptom: the first few samples are wrong, rarely, and only on some runs. Fix: fill the data first, then hand over with a FIFO push. If you must use a shared flag, put a memory barrier (__dmb(), which the SDK provides) between the data write and the flag write, and another between seeing the flag and reading the data. volatile is not a barrier.
  4. A blocking wait while holding the lock. Core 0 takes the lock, then calls multicore_fifo_pop_blocking() to wait for core 1. Core 1 needs the same lock before it can send the message, so it spins. Symptom: both cores stop, and neither makes progress. This is a deadlock: each core waits for the other. Fix: finish the wait before taking the lock, or send the message before taking it.
  5. Taking the same lock twice. A helper that takes the lock is called from a function that already holds it. Symptom: the core hangs at the second spin_lock_blocking forever, and the other core carries on. The SDK comments say that a hardware spinlock may not be acquired re-entrantly. Fix: split the code into an outer function that takes the lock and an inner function that assumes it is held.
  6. Trusting volatile as protection. The code is marked volatile, so the author assumes it is safe. Symptom: the same lost updates as the first mistake. Fix: read the lock as the protection, and use volatile only to stop the compiler caching the value inside the lock.

Look at each mistake from the same angle. Ask which core can see the data, which lock or FIFO covers it, and whether any path leaves the lock held or waits for the other core while holding it. Those three questions find most multicore bugs.

In real projects

Multicore firmware shows up where one part of a product must never wait for another: a motor loop beside a user interface, a sensor sampler beside a network stack, or a fast protocol engine beside slow logging. The usual split is to give each core one job and one owner for each piece of data. The FIFO carries the data between the two jobs. A spinlock appears only where the data really is shared, and it guards a short list of variables.

A senior engineer reviewing this code asks for three things. First, a comment next to each lock that names the data it protects, so the next reader knows what must be locked. Second, a check that no path leaves the lock held, and that no blocking call sits inside a critical section. Third, a clear reason for every shared variable: why it cannot be a FIFO message instead. Those three checks are short, and they catch the mistakes above before they reach a board.

The SDK builds higher-level tools on the same hardware. Its critical_section API is a spinlock with a name, and its mutex and queue types are built on the same ideas. Use those when they fit. In an interview, the question is usually about the reasoning behind them, so be ready to explain why a lock is needed on two cores when a single core needed only an interrupt switch.

Summary

  • Two cores share one SRAM and one set of peripherals, so any shared variable can be changed by either core between two of the other core's steps.
  • Disabling interrupts protects only the core that disables them. A lock that both cores see is needed for shared data.
  • count++ is a load, an add and a store, so two cores can lose an update. volatile does not prevent this.
  • Core 1 sleeps after reset. multicore_launch_core1() wakes it through the SDK's handshake on the inter-core FIFO.
  • Each inter-core FIFO is 32 bits wide and eight entries deep. Use it to pass messages and hand over ownership of data.
  • The SIO has 32 hardware spinlocks. A read claims one, a write releases it, and spin_lock_blocking() also disables interrupts on the calling core.
  • Use the SIO's SET, CLR and XOR aliases for GPIO bits that both cores touch, rather than a read-modify-write.
  • The common mistakes are an unlocked update, an early return that keeps a lock, a flag set before its data, a blocking wait inside a lock, and taking the same lock twice.

"Two cores share a sensor buffer. How do you protect it, and what does the protection cost?" Answer out loud in 60 seconds, then compare.

Model answer

Decide who owns the data at each moment. If one core fills the buffer and the other drains it, pass the buffer index or pointer through an inter-core FIFO, so only one core touches it at a time. If both cores touch the same structure, take a hardware spinlock around every access, keep the critical section short, and use the save and restore form so interrupts are handled. The cost is that the waiting core spins or waits, and a long critical section adds latency to both cores. Never set a flag and then fill the data: the other core can see the flag first. Never wait for the other core while holding the lock, because that deadlocks.
