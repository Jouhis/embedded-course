Multicore on the RP2040: FIFOs and spinlocks

The RP2040 has two cores that share one memory. Two cores running at once make a race that one core can never have, and the chip gives you two tools to stop it: a FIFO to pass messages and a spinlock to take turns.

Concept lesson, optional for the Wokwi path. Wokwi simulates only one Pico core (see NOTES.md), so there is no multicore project to run. You will learn the mechanisms from the datasheet, predict races on paper, and review code for the bugs they cause. The same reasoning applies on a real Pico, where both cores run at the same time.

By the end of this lesson you can launch core 1 with the Pico SDK, pass a value between the cores through the SIO FIFO, protect a shared counter with a hardware spinlock, and spot a shared-data race in a code review.

The idea

The RP2040 has two Arm Cortex-M0+ cores, and both see the same SRAM, the same peripherals and the same GPIO. Each core runs its own instruction stream, so for any two statements, one core's statement can land between two of the other core's statements. Nothing in the hardware orders them for you. RP2040 datasheet, section 2.3 On a single core, an interrupt is the only way two pieces of code interleave, and you can switch it off. A second core cannot be switched off by the first, so you need a lock that works across cores.

Core 1 is not running at reset. It sits in a deep sleep until core 0 wakes it, and the bootrom uses the inter-core FIFO and the event signal to hand it a stack pointer, an entry point and a vector table (RP2040 datasheet, sections 2.3.1.1 and 2.3.1.4). The Pico SDK wraps that for you: 

#include "pico/multicore.h"

static void core1_entry(void) {
    /* runs on core 1, with its own stack */
    while (true) {
        /* core 1 work goes here */
    }
}

int main(void) {
    multicore_launch_core1(core1_entry);   /* wakes core 1 and starts it at core1_entry */
    /* core 0 carries on with its own work */
}

Each core has its own stack, but there is only one SRAM. A global variable is visible to both cores, and any access to it can interleave with the other core's access.

The race in one line

In C, count++ is three steps: load the value, add one, and store it back. On the Cortex-M0+ each step is a separate instruction, and the other core can run its own steps between yours. If both cores do the three steps at the same time, both can load the same old value and both store the same new one. One increment is lost.

volatile does not fix this. Lesson 46 showed that volatile forces a reload on each access, but it gives no atomicity and no ordering between the two cores. The cppreference page on volatile says exactly that (cppreference: volatile).

Tool 1: the inter-core FIFOs

The SIO has two hardware FIFOs. One carries messages from core 0 to core 1, and the other carries messages from core 1 to core 0. Each is 32 bits wide and eight entries deep. Each core writes to its outgoing FIFO and reads from its incoming one, and a status register tells it whether the FIFO has data or room (RP2040 datasheet, section 2.3.1.4). A FIFO hand-off is also a synchronisation point. The reader cannot see the message until the writer has written it, so the order is fixed by the hardware. This is the main reason to prefer a FIFO over a shared flag.

The SDK API is short. Use multicore_fifo_push_blocking() on the sending core and multicore_fifo_pop_blocking() on the receiving core. The blocking pop waits until data arrives. Pico SDK, pico_multicore lists the other forms, including the timeout version.

Tool 2: hardware spinlocks

The SIO has 32 hardware spinlocks. A spinlock is one bit with two operations. A read tries to claim it: the read returns nonzero if the claim worked, and zero if someone already holds it. A write of any value releases it. If both cores try to claim the same lock in the same clock cycle, core 0 wins (RP2040 datasheet, section 2.3.1.3).

A spinlock is only safe for short critical sections, because the losing core spins and does no other work. The SDK's spin_lock_blocking() also disables interrupts on the holding core, which stops an interrupt from taking the lock and then waiting for it on the same core. Its matching release is spin_unlock(), which takes the saved interrupt state back. 

static spin_lock_t *counter_lock;      /* made once, in main(), with spin_lock_init() */
static volatile uint32_t shared_count;

void bump_shared(void) {
    uint32_t saved = spin_lock_blocking(counter_lock);  /* claim, and disable interrupts */
    shared_count++;                                    /* only one core is in here */
    spin_unlock(counter_lock, saved);                  /* release, and restore interrupts */
}
The lock protects the data, not the code. Every access to shared_count on both cores must take the same lock. One unlocked read or write in one place is enough to break it.

Which tool for which job

  1. Passing a message or ownership of a buffer: use a FIFO. Send a pointer or an index, and let the receiver own the data after the pop.
  2. Sharing a counter or a small structure that both cores read and write: use a spinlock around every access.
  3. Setting or clearing one GPIO bit from both cores: use the SIO's atomic GPIO registers (the set, clear and xor aliases), not a read-modify-write on the output register.

The cost is the same in every case. A lock or a FIFO wait is time that the other core might have spent on work, so keep the shared part as short as you can.

Model answer

Decide who owns the data at each moment. If one core fills the buffer and the other drains it, pass the buffer index or pointer through an inter-core FIFO, so only one core touches it at a time. If both cores touch the same structure, take a hardware spinlock around every access, keep the critical section short, and use the save and restore form so interrupts are handled. The cost is that the waiting core spins or waits, and a long critical section adds latency to both cores. Never set a flag and then fill the data: the other core can see the flag first.
