Bootloaders and firmware updates

A device in the field must be updated without a debugger, and it must survive an update that goes wrong. A bootloader owns the reset vector, checks the image it is about to run, and keeps a way back to the last good one. You will build a small bootloader and an application slot, and boot the application from the bootloader.

By the end of this lesson you can validate an application image header, hand over to the application by setting VTOR and MSP and branching to its reset handler, and explain how a test-then-confirm rollback recovers from a failed update.

The idea: the bootloader runs first

After reset the core reads the vector table at address 0 and starts whatever image sits there (lesson 42). A bootloader makes that image small and fixed: it decides which application runs, and it can replace the application with a new one. The application is a separate image in its own flash slot. The bootloader validates it, and the boot only proceeds if the image passes. Over-the-air (OTA) updates use the same mechanism. The device downloads a new image into the spare slot, and the bootloader then decides whether to switch to it. The download is a transport problem; the switch is the bootloader's job.

The flash layout: slots and metadata

MCUboot, the bootloader Zephyr ships, calls the two application slots the primary and the secondary. It normally runs only the image in the primary slot. To run a new image from the secondary, it first moves the contents into the primary, by swapping or by overwriting, and it keeps the old image in the secondary so it can swap back (MCUboot design: image slots).

The image header: is this really an application?

Before the bootloader trusts a slot, it reads a header at the slot's start. MCUboot's header is 32 bytes, with a magic value (0x96f3b83d), a load address, the header size, the size of the protected TLVs, the image size and a version (MCUboot design: image format). Each field answers one question: is this an image at all, how big is it, which version is it, and where does it end?

The header in this lesson follows that idea in a smaller form (projects/0102-bootloader-and-app/solution/app_image.h): a magic word APP1, a version, the address one past the end of the image, the vector table's offset from the header, and four reserved words. The reserved words are where a CRC or a signature would go. A real image needs one of them, because a magic word alone cannot tell an interrupted download from a complete one. This build leaves them zero, for a reason the next section explains.

Boot decision and rollback

An update that works must still be confirmed, because a new image can boot and then crash later. A common scheme keeps a trial counter in the metadata. After an update, the bootloader runs the new image in test mode and decrements the counter at each boot. If the application confirms itself (it sets a confirm flag once it has run correctly for a while), the bootloader keeps it. If the counter runs out without a confirm, the bootloader swaps back to the old image. MCUboot names these steps the test swap, the confirm (image OK) and the revert (MCUboot design: boot swap types).

The course build does not implement the counter, because it has one slot and no metadata area. The concept is the important part: the device must know when an image has proven itself, and it must have a way back before it erases the old one.

Jumping to the application

The hand-over is three register writes and a branch, and each one has a reason. The application's vector table is at 0x08004100, and its word 0 is the initial stack pointer, word 1 the reset handler (lesson 42). The bootloader:

  1. disables interrupts, so no bootloader interrupt runs half-way through the hand-over;
  2. writes the application's table address into SCB->VTOR, so that exceptions now use the application's table (Arm PM0056, the SCB section, in RESOURCES.md as the STM32F1 Cortex-M3 programming manual);
  3. loads the main stack pointer from word 0 with __set_MSP();
  4. branches to the reset handler in word 1. The branch never returns.
/* from the solution's main.c: the hand-over, in order */
__disable_irq();
SCB->VTOR = APP_BASE_ADDR + APP_VECTOR_OFFSET;   /* exceptions use the app's table */
__set_MSP(sp);                                     /* the app's stack starts at its top */
((void (*)(void))(uintptr_t)reset)();              /* branch to the app's Reset_Handler */
Setting VTOR is not optional. If it still points at the bootloader's table, the application's first interrupt would enter the bootloader's handler. And if you forget to set MSP, the application starts with the bootloader's stack pointer, which may be in the middle of the bootloader's data.

The combined image: one link, two regions

A real product builds the bootloader and the application as two separate programs, and a flash tool joins them. Two options work for that: a tool such as srec_cat merges the two Intel HEX files, or MCUboot's imgtool signs the application and prepends its header. The Wokwi simulator loads one file (the wokwi.toml firmware key), and arm-none-eabi-objcopy cannot merge two inputs into one file.

This project takes a simpler route that gives the same flash image: one link, two regions. The linker script boot.ld defines a BOOT region at 0x08000000, 16 KiB, and an APP region at 0x08004000, 48 KiB. The bootloader's code goes in the first region, and the application's header, vector table and code go in the second, with ASSERTs that check the header is first in its slot. The linker reports an error if the bootloader grows past 16 KiB. The result is one ELF and one .hex, and wokwi.toml loads that .hex. You can see the layout yourself: arm-none-eabi-objdump -h build/boot_and_app.elf lists .app_header at 08004000 and .app_vectors at 08004100.

The trade-off: in one link the application can call the bootloader's functions, such as uart_puts, and the two cannot be updated separately. A product that updates the application in the field keeps them as separate images, and the lesson's layout is the same picture with the join done by a tool.

Try it: validate the slot, then jump

The project is projects/0102-bootloader-and-app. The application prints BOOT -> APP OK. The starter has the two functions that do the work, marked TODO(learner): slot_is_valid() and jump_to_app().

  1. Open projects/0102-bootloader-and-app/starter in VS Code, then build with Ctrl+Shift+B. The starter builds, and it prints BOOT: no valid image.
  2. In main.c, write slot_is_valid() with the five checks in the comment: the magic, the vector offset, the image end, the stack pointer in SRAM, and the reset handler's Thumb bit and address.
  3. Write jump_to_app() in the order given in its comment: disable interrupts, set VTOR, set MSP, then call the reset handler through a function pointer.
  4. Start the simulator with F1 → Wokwi: Start Simulator. You will know it works when the serial monitor shows BOOT: image valid, jumping and then BOOT -> APP OK.
Hint for the checks

The vector table is at APP_BASE_ADDR + APP_VECTOR_OFFSET. Word 0 is vectors[0], and word 1 is vectors[1]. A reset handler address has bit 0 set, so test it with & 1u.

Hint if the app does not start

Check the vector table with objdump -s -j .app_vectors build/boot_and_app.elf. The first word should be an address in SRAM, near 0x20005000, and the second a Thumb address in the slot, ending in 1.

"How does a bootloader hand over to an application safely, and how do you recover from a bad update?" Answer out loud in 60 seconds, then compare.

Model answer

The bootloader validates the image first: a magic value, the size, a CRC or signature, and the vector table's stack pointer and reset address. To hand over, it disables interrupts, sets VTOR to the application's table, loads the stack pointer from word 0 and branches to the reset handler. For a bad update, the new image runs in test mode with a trial counter. If it does not confirm itself before the counter runs out, the bootloader reverts to the old image, so the device stays usable.

MCUboot design (docs.mcuboot.com): read the sections on the image format (the 32-byte header and its magic), image slots, and the boot swap types (test, confirm and revert). It is the reference that the Zephyr project uses for its own bootloader.
