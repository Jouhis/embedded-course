Embedded security

Trusted boot, locked debug and exposed interfaces

By the end of this lesson you can classify threats with STRIDE, explain a chain of trust built from signed images, and say what debug lockdown and readout protection do and do not stop.

Deliberate changes rather than damage

Lesson 104 built a bootloader that checks an image header before jumping to an application and lesson 103 used a CRC to detect damaged frames, both checks asking whether the bytes got corrupted, whereas security asks the harder question of whether a hostile party changed them on purpose. Lesson 101 showed a Modbus slave on a shared bus, where anyone with a cable can send a request, and lesson 84 how a watchdog and a fault handler keep a device running, yet none of these ideas stop a determined attacker from writing their own firmware.

The problem shows up in many connected products, a smart meter, a medical pump, a car's engine controller and a factory robot each being reachable over a network or a service port and each running firmware that someone else could replace, which regulators now treat as a product requirement. This lesson gives you the vocabulary and the reasoning a firmware engineer uses before writing any security code.

The lesson has no simulator task, because security depends on the hardware and on keys a simulator does not have, and Wokwi has no secure boot, so it is a concept lesson with an interactive threat-model exercise, while lesson 104's bootloader is the place where the signature check would go.

Threat models and the STRIDE categories

A threat model lists what you protect, who might attack it and how, starting from three questions, what the assets are, such as the firmware, the keys, the calibration data and the user's settings, where the entry points are, such as the debug port, the update path, each serial or radio message and each command parser, and where the trust boundaries lie, the places where data crosses from something you trust into something you do not. The model is useful even before any code is written, because it shows which parts of the design must be defended first.

STRIDE is a common way to sort threats into six kinds, Spoofing (pretending to be someone else), Tampering (changing data), Repudiation (denying an action with no way to prove it), Information disclosure (leaking secrets), Denial of service (stopping the device) and Elevation of privilege (gaining rights you should not have). STRIDE comes from Microsoft's threat-modelling work, and since this lesson did not open a primary source for it, use the six names as a checklist rather than a standard.

The categories matter because each has a different defence, tampering being answered by integrity checks such as signatures, information disclosure by keeping secrets out of reach, as readout protection does, and spoofing by authentication, while repudiation is answered by an audit log the attacker cannot quietly edit, denial of service by input checks and a watchdog and elevation of privilege by checking authorisation on every privileged command. A threat that cannot be placed in a category is probably not yet understood.

The exercise below gives six threats for a connected controller, and you pick the STRIDE category for each.

ThreatSTRIDE category
1. An attacker writes a modified application image to flash.
2. A technician reads the firmware out over the debug port and copies it.
3. A calibration change has no record of which operator made it.
4. A malformed frame on the bus makes the controller reset in a loop.
5. A normal user sends a command that unlocks the admin menu.
6. A forged message claims to come from the cloud server.

Worked example: a threat model for one device

The Modbus slave on an RS-485 bus from lesson 101 makes a concrete case to model. Before reading the steps, predict which STRIDE categories a write of an unsafe setpoint from another bus node falls into.

  1. The assets. The assets are the holding registers, the setpoints the master writes, the firmware image in flash and the calibration constants.
  2. The entry points and the boundary. The entry points are the RS-485 transceiver, the debug port and the bootloader's update path from lesson 104, and the trust boundary sits at the transceiver, everything arriving on the bus being untrusted, because any node with a cable can talk to it.
  3. The unsafe write. A node on the bus writes setpoint 1 with a value of 250 degrees to the heater, above a safe limit of 220 degrees, and the device accepts the write, because Modbus has no concept of who may write, which makes it elevation of privilege if the node should not be allowed to set that value and tampering with the setpoint data.
  4. The defence. The defence is an authorisation check on the write, a software rule in the slave, plus a range check on the value itself, whereas authenticating the sender, which would fix spoofing, needs a key and a MAC on every frame, which Modbus RTU does not carry, a gap that the model makes visible, which is its job.
  5. A second threat. A technician plugs a debugger into the device and reads the firmware back, which is information disclosure, because the firmware, perhaps holding a proprietary algorithm, has left the device, the defence being readout protection and a closed debug port, which the rest of this lesson shows to be necessary but not sufficient.

Integrity, authenticity and secrecy

Three words get confused in security work, each a separate promise, integrity meaning that the bytes have not changed, which a CRC gives in a weak form against random errors, authenticity that the bytes came from someone holding a secret, which a MAC or a signature gives, and secrecy that nobody without a key can read the bytes, which encryption gives. A design must state which of these it needs, a firmware update usually needing authenticity and integrity but not always secrecy, because the firmware is often public.

The three promises resemble those of a parcel, a tamper-evident seal promising integrity, since you can tell whether someone opened it, a signature on the label authenticity, since you know who sent it, and a locked box secrecy, since nobody on the way can see inside, while a seal without a signature can be resealed by anyone, which is why a CRC alone does not stop an attacker. The comparison breaks for copying, though, because a parcel exists once, whereas firmware can be copied without limit, so a secret placed inside it is shared with everyone who obtains a copy.

The difference between a checksum and a signature comes down to the secret, because a CRC is computed by a public formula over the data, so anyone can run the same formula after changing the data and produce a matching check, whereas a MAC is a keyed hash needing a secret key to compute, so a forger without the key cannot produce one. A signature goes a step further, using a private key to sign and a public key to verify, so the verifier holds no secret that a forger could copy from the device, and the rest of this lesson uses signatures, because a device in the field holds only the public half.

A chain of trust from the boot ROM

Secure boot starts from something the attacker cannot change, each stage checking the next before it runs, and on the RP2350 the bootrom, fixed at design time, is that root of trust, checking a signature on the image before running it and refusing an image whose signature does not verify (RP2350 datasheet, section 10.1.1, Secure boot, p. 734).

The check works in four steps, hashing the image with SHA-256, verifying the signature over the image's public key, comparing the signed hash with the computed one and comparing the public key with a fingerprint stored in one-time-programmable memory, because a signature proves something only if the key is genuine, which is why the fingerprint sits in OTP and cannot be changed afterwards. The datasheet also describes an anti-rollback version number held in an OTP counter, which stops an attacker from installing an older image with a known flaw.

A chain of trust resembles a relay of runners carrying sealed envelopes, each runner checking the seal of the next envelope before handing over, and since the first runner, the boot ROM, cannot be replaced, a forged envelope is stopped at the first hand-over it reaches as long as every runner checks the next one. The comparison breaks at the end of the chain, because the last runner's checks cover only what is in the envelope, whereas an attacker with a debug port can bypass the relay entirely and write to the flash directly.

The image is hashed first because a signature algorithm is slow and works on a fixed-size number, so the image is compressed to a fixed-size digest with a cryptographic hash and the signature covers the digest, a change to any byte of the image changing the digest and making the signature fail. The hash must be collision-resistant, so that an attacker cannot craft a second image with the same digest, which is why a weak hash such as a CRC is not used here.

The RP2350 datasheet uses secp256k1 ECDSA over a SHA-256 hash for these signatures. Other designs use Ed25519 or ECDSA on a different curve. Check which algorithm your bootloader supports before you design a key scheme. Do not write your own cryptography: use a library that is reviewed.

A CRC, which lesson 103 used for damage, is therefore not enough, because anyone can recompute it after changing the data, since it has no secret, whereas a signature needs the private key, which is what an attacker cannot make.

Debug lockdown and readout protection

Debug access is a path around the software, a debug port such as SWD on an ARM chip (lesson 54 used GDB through a probe) letting a host halt the core and read and write memory, so anything the bootloader checks is irrelevant if the debugger can write the flash directly. A secure design therefore closes the debug port in production, which is why the RP2350 datasheet says that a debugger can skip the bootrom entirely and that disabling debug is part of the secure boot enable procedure (RP2350 datasheet, section 10.1.1, and section 10.5 for the enable procedure).

Readout protection applies the same idea to the flash contents, the chip refusing to let a debugger read the code back, so that a copy of the firmware cannot be extracted through the debug port, and the STM32F103 has an option-byte status bit for this, FLASH_OBR_RDPRT, bit 1 of FLASH_OBR, named "Read protection" in third_party/cmsis-device-f1/Include/stm32f103xb.h. RM0008 Rev 21 lists read and write protection among the features of the flash interface (section 3.3.3) and refers the complete flash register configuration to the STM32F10xxx Flash programming manual, PM0075, but since RM0008 does not give the levels and PM0075 is not in this course's workspace, check the levels there, remembering that a level you set may be permanent.

Readout protection stops casual copying. It does not encrypt the flash, and it does not stop an attacker with time and equipment to attack the chip itself. Treat it as one layer, not as the defence.

The RP2040 and the RP2350 compared

The RP2350 datasheet describes secure boot as a feature of the RP2350 bootrom, with the glitch detectors, the redundancy coprocessor and the OTP keys around it, whereas the RP2040 is the earlier chip in this course, whose datasheet this lesson did not open, so check its bootrom section before concluding that the RP2040 has no secure boot. The RP2350 is the chip to use for a product that needs a signed image.

The comparison matters for a real project, because a product's bill of materials, its update process and its certification plan all depend on which chip gives a root of trust in hardware, a chip with a secure bootrom letting the team move the trust into silicon, whereas a chip without one forces the team to build the whole chain in software and accept what that cannot defend.

The attack surface of a device

Every interface is an attack surface, the debug port, the bootloader's update path, every serial or CAN message and every command parser, and the surface is reduced before it is defended, by turning off what is unused, checking every length field before copying and authenticating the commands that change state. Lesson 84 showed the watchdog and the fault handler, which turn a crash into a recovery and keep a device usable under attack.

A length field is a common entry point, because a frame claiming to carry 200 bytes for a buffer holding 64 overwrites the stack if the parser copies without a check, and the COBS decoder in the lesson 103 project (projects/0103-serial-framing-tests), which rejects a block running past the end of its input, applies exactly this kind of defence. Each such check is small, while forgetting one can be expensive.

Common mistakes and how to spot them

A CRC used as a security check

A test that changes one byte of the update image and recomputes the CRC is accepted by the bootloader, because the team added a CRC to the image and believed it protected, although a CRC has no secret. Replace the CRC with a signature check, keeping the CRC only for damage detection in the transport.

The debug port open in production

A probe connected to the board reads or rewrites the firmware and the secure boot check never runs, because the bootloader is correct but the debug port still writes flash. Close the debug port and set readout protection as part of the production procedure, and test that a probe can no longer connect.

A key stored where the attacker can read it

Anyone who dumps the firmware, from a debug port or a leaked build, holds the key and can sign their own images, because the team put a symmetric key in the firmware so that the device could verify the update. Keep the private key on the build server, put only the public key on the device and keep the device's trust anchor in OTP or the bootrom where the design allows.

A secret that is really a constant

A password works on every device the team has ever shipped once someone has found it in a dump, because a hard-coded password for the service menu, or a serial number used as a key, looks secret but is the same on every unit and can be read from the flash. Derive secrets per device from a value that is unique and protected, and never ship the same password on every unit.

Side channels and fault injection

A signature check in software can be attacked by a glitch, a short fault in the power or clock that makes a comparison succeed when it should fail, and the RP2350 datasheet says exactly this, that a pure-software secure boot is susceptible to fault injection, which the glitch detector and the redundancy coprocessor exist to stop (section 10.1.1). A glitch might skip one instruction, such as the branch that rejects a bad signature, so the defence is to make the decision hard to skip with a redundant comparison, a value checked twice or a hardware detector that resets the chip when the supply dips.

Side-channel attacks read secrets from timing or power use, a key comparison exiting at the first mismatched byte taking slightly longer when more bytes match, so an attacker measuring many runs can recover the key one byte at a time, the software defence being a comparison that always takes the same time and the hardware defence shielding and filtering. Both are physical attacks that matter when the attacker holds the device, and their defence lies in the hardware and the algorithm, not in a single line a firmware author can add.

A redundant check against a glitch

A bootloader that computes the digest, calls verify_signature() and branches to the application if the result is 1 lets an attacker run any code with one glitch landing during the call that makes the function return 1 for a bad signature. A harder target stores 0xA5 in a variable, calls the verifier and checks for 0xA5 again only after a second independent verification, so two glitches in the right two places are needed and the second check's value is hard to guess, which does not prove the decision right but raises the cost of the attack, the realistic goal.

Security processes and regulation

Professional teams treat security as a process as much as a design, keeping a threat model under version control, reviewing it when the interfaces change and tying each threat to a test, so a firmware update path is tested with a tampered image, a truncated image and a replay of an old, valid image, the replay being the one the anti-rollback counter exists to stop. Keys live in an HSM or a signing server, the device holding only the public key, and security patches are part of the release plan.

Regulation is now part of the job, the EU Cyber Resilience Act, Regulation (EU) 2024/2847, setting cybersecurity requirements for products with digital elements sold in the EU and asking manufacturers for secure-by-default design, security updates over the product's life and a vulnerability reporting duty, its official text being on EUR-Lex. Secondary sites give the application dates and disagree on some of them, and since this build could not open the official text to confirm them, check the dates in the regulation itself before quoting one.

Summary

  • A threat model names the assets, the entry points and the trust boundaries and then sorts each threat by STRIDE.
  • Integrity, authenticity and secrecy are three separate promises, each needing its own mechanism.
  • A CRC detects damage but has no secret, so it cannot stop a forger, whereas a signature needs a private key that the device never holds.
  • Secure boot is a chain in which a root of trust fixed in silicon checks the first image and each stage checks the next.
  • On the RP2350 the bootrom is the root of trust, and the datasheet describes the OTP fingerprint and the anti-rollback counter (section 10.1.1).
  • Debug lockdown and readout protection stop the easy extraction paths, though neither stops a determined physical attacker.
  • Fault injection can skip one check, so critical decisions need redundancy or a hardware detector.
  • Every length field and every command that changes state is checked, since each unchecked entry point is part of the attack surface.
