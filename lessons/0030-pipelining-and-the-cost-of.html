Pipelining and the cost of branches

Overlapped instruction stages and the flush after a taken branch

By the end of this lesson you can count the cycles a taken branch costs in the simulator's 3-stage model, and explain why a loop with a conditional branch slows down each time the branch is taken.

Cycle counts and timing

Lesson 28 showed the core running one instruction at a time through fetch, decode and execute, and lesson 29 what the instruction bits mean, but neither said how long each phase takes, which is what decides how fast code runs. A motor step loop that must finish in 50 µs, a bit-banged protocol that must keep its edges on time and an interrupt handler that must finish before the next interrupt all depend on counting cycles correctly.

The cost of a branch is the part of that count most often guessed wrong. Every if, every loop and every function call is a branch, so the cost is paid throughout a real program. This lesson explains where it comes from using the simulator's simple model, then checks the model against Arm's timing table for a real Cortex-M3.

Clock cycles, pipelines and throughput

A clock cycle is one tick of the core's clock, the unit in which the core's work is measured; the Pico runs its core at 125 MHz, which is 8 ns per cycle. A pipeline splits the fetch, decode and execute work into stages that run at the same time, so while one instruction is in the execute stage, the next is being decoded and the one after that fetched from memory.

The benefit of a pipeline is throughput, the number of instructions finished per cycle, and its cost is latency, the time one instruction takes from fetch to completion. Pipelining makes latency slightly longer and throughput much higher. Without a pipeline, a 3-stage core would finish one instruction every three cycles, leaving two of its three stages idle at any moment, whereas with a pipeline one instruction finishes every cycle once the first is through. A pipeline is only as good as its guess about what comes next. Straight-line code keeps every stage busy, and a branch is the exception, because the instructions fetched after it may be the wrong ones.

The Cortex-M3 has a three-stage pipeline of fetch, decode and execute, whose stages Arm's TRM names in its section on the execution pipeline (Arm Cortex-M3 TRM DDI0337G, §1.3). The Cortex-M0+ has a two-stage pipeline and implements Armv6-M (Arm Cortex-M0+ datasheet). A shorter pipeline has less work in flight to discard, but it also overlaps less.

Branches in a pipeline

Because a pipeline keeps several instructions in flight, the core must decide what to fetch next before the current instruction has finished. For straight-line code the answer is simply the next address in memory, but for a branch it depends on the outcome, which the core learns only when the branch reaches execute. A conditional branch such as BNE is taken only when a flag test passes, so at the fetch stage the core cannot know whether to fetch the next instruction in memory or the branch target.

A pipeline works like laundry with a washer and a dryer: while load 1 dries, load 2 is already washing, so both machines stay busy. A taken branch is discovering, after load 2 has started, that a different load was needed, so you pull it out wet and start the right one while the dryer stands idle, and those idle cycles are the cost of the branch. The picture exaggerates the damage, though, because a flushed instruction has changed nothing, whereas a wet load still has to be dealt with.

The core therefore makes a guess. The TRM states that for conditional branches "the address is speculatively presented", and that the forwarded result then decides "if the branch path flushes the fetch queue or is preserved" (DDI0337G, §1.4). If the branch is not taken, the guess was right and nothing is lost. If it is taken, the fetched instructions are on the wrong path and the core discards them, a step called a pipeline flush. The discarded instructions are never executed, but the fetch cycles that brought them in are gone, and the core must start fetching from the target before it can do useful work again.

The TRM also describes branch target forwarding (§1.5), in which for some branch types the core presents the branch's memory access "at least a cycle earlier than when the opcode reaches execute". This shortens the wait for the target without reducing the cost to zero, and conditional branches are still speculated, so read the section before assuming a branch is free.

Worked example: the cycle count of a loop on a Cortex-M3

The TRM gives timings for every Thumb instruction in its instruction timing chapter (Chapter 18, Table 18-1), and we use three rows of that table to check the simulator. In the table's own terms, those rows state the following.

  • Data operations such as ADD, MOV and CMP take 1 cycle in the 16-bit form.
  • Branches take 1 cycle plus any fetch stalls, which we ignore here.
  • For a taken branch, "pipeline reloads (two cycles are added)", so a taken B, BNE or BL takes 1 + 2 = 3 cycles.

Table 18-1 applies to the Cortex-M3, and its text adds that "additional cycles can be taken because of fetch stalls", which occur when the memory cannot supply an instruction in time. We assume the memory keeps up, so the numbers below are the best case, and real code on a real board can be slower. The cycle count of one loop pass is then

cycles per pass = ndata + 1 + 2·t(1)

where ndata is the number of 1-cycle data operations in the pass, the 1 is the branch's base cycle, and t is 1 when the branch is taken and 0 when it falls through.

The loop in the simulator example below starts with MOV R0, #0 and then runs an ADD, a CMP and a BNE four times, with the BNE taken on the first three passes and falling through on the fourth. Before working through it, estimate the total, then count pass by pass.

  1. Before the loop: MOV R0, #0 takes 1 cycle. Total so far: 1.
  2. Pass 1: ADD and CMP take 1 cycle each, and the taken BNE takes 3, so by Equation 1 the pass costs 2 + 1 + 2 = 5 cycles. Total: 6.
  3. Pass 2: the same as pass 1, 5 cycles. Total: 11.
  4. Pass 3: the same again, 5 cycles. Total: 16.
  5. Pass 4: ADD and CMP take 1 cycle each, and the BNE falls through in 1, so the pass costs 3 cycles. Total: 19.

The loop thus runs for 19 cycles including the MOV. Each of the three taken branches costs 2 cycles more than an untaken one, so 6 of the 19 cycles are branch penalty, and the remaining 13 are the work itself: four adds, four compares, the four branches' base cycles and the initial move. That 6-cycle figure is what the simulator reports as "cycles lost to branch flushes" for this loop, with the halt added on top.

The same penalty applies to calls and returns. Table 18-1 places B, BL and BX in one row of 16-bit branches with the same "two cycles are added" rule when taken, so a call costs the same flush as a loop's back-edge, and a function called inside a hot loop pays it twice per pass, once for the call and once for the return.

  1. Cycle 1: the loop's ADD is fetched. Fetch, decode and execute are separate stages, so up to three instructions are in flight.
  2. Cycle 2: CMP is fetched while ADD is decoded.
  3. Cycle 3: BNE is fetched, CMP decoded, and ADD executes. From now on one instruction finishes every cycle.
  4. Cycle 4: the core does not yet know whether BNE will branch, so it keeps fetching in a straight line: the instruction after BNE.
  5. Cycle 5: BNE executes and is taken. The two instructions fetched behind it are the wrong ones, so the pipeline throws them away.
  6. Cycle 6: fetching restarts at the branch target, the ADD. Nothing reaches execute this cycle: a bubble.
  7. Cycle 7: a second bubble while the refilled pipeline catches up. These are the two cycles the TRM adds for a taken branch.
  8. Cycle 8: ADD executes again. A taken BNE cost 1 + 2 = 3 cycles; one that falls through costs 1. Over the lesson's loop, 6 of the 19 cycles are this penalty.

The simulator's pipeline model

The simulator is a teaching model rather than a Cortex-M3. It has a 3-stage pipeline in which each taken branch flushes the two instructions behind it and so loses 2 cycles, while an untaken branch loses nothing. This matches the TRM's "two cycles are added" for a taken branch, which is why the penalty is 2 rather than 1. Real cores differ in detail: the Cortex-M0+ has a two-stage pipeline, so its numbers are different, and its branch cycle counts were not checked for this lesson, so use the datasheet and the TRM of the chip you are building for.

The simulator's pipeline view draws the three stages and marks flushed instructions with a cross, as a picture of the model rather than a trace of real hardware. The count it prints is the number of taken branches times 2, and it includes the halt at the end of the program, which the warning below explains.

The simulator's halt, B ., counts as a taken branch too, because it jumps to itself. When counting flushes in the program below, leave out the final halt: the pipeline view adds it to the total, so the on-screen total is one branch higher than the loop's real cost.

Common mistakes and how to spot them

The untaken branch charged the full penalty

A predicted cycle count comes out two cycles too high for every loop exit, because 2 cycles were added for every branch, including the one that falls through. Charge the penalty only when the branch is taken, and the base cycle to every branch.

The halt forgotten as a taken branch

Your prediction matches the loop's cost but not the number on screen, because the pipeline view counts B . and its total is one branch higher. Subtract the halt, as the warning above says.

A flush confused with a wait state

A loop is slow although its code is short, and the blame falls on the flash when the real cause is taken branches. Flash wait states are a separate effect, in which a memory slower than the core makes the core wait, whereas a flush discards work already done. Count taken branches first, then check the wait states in the datasheet and the clock setup.

One core's numbers used for another

A timing estimate is right on one board and wrong on the Pico, because the 2-cycle penalty comes from the Cortex-M3 pipeline and a Cortex-M0+ has a shorter pipeline with different numbers. Check the timing source for the core in your project.

Cycle counting in real firmware

Professional firmware engineers rarely count cycles by hand for a whole program, only where timing matters: an interrupt handler, a bit-banged waveform or the body of a loop that runs at a fixed rate. For interrupts the TRM gives a fixed figure, "a 12-cycle latency from asserting the interrupt to the first instruction of the ISR executing" (DDI0337G, §5.5.1, Figure 5-2), which a reviewer can check. The rest of the timing is measured on the board with a timer or the debugger, because caches, flash wait states and bus contention all change the result.

A code review of a hot loop often asks whether a branch inside the loop could be removed and whether the back-edge jumps a short distance, and both questions concern the same cost.

Summary

  • A pipeline overlaps the fetch, decode and execute stages, so in steady state one instruction finishes per cycle.
  • The Cortex-M3 has three pipeline stages (TRM §1.3), and the Cortex-M0+ two.
  • A conditional branch is speculated, with the core fetching the next instructions in memory until it knows the outcome (TRM §1.4).
  • A taken branch flushes the instructions behind it, and in Arm's timing table it costs 3 cycles against 1 for an untaken one (Table 18-1).
  • The simulator charges 2 cycles per taken branch and includes the halt in its on-screen total.
  • A loop with a taken back-edge pays the penalty on every pass except the last.
  • Flash wait states and flushes are different effects, and a real loop's cycle count needs both checked.

Read Table 18-1 before you quote a branch cost for a real chip, and check the M0+ numbers in its own datasheet.
