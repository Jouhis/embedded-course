Pipelining and the cost of branches

A pipeline lets the core work on three instructions at once. A branch throws away the work it started on the wrong path, and that is where a loop pays its price.

By the end of this lesson you can count the cycles a taken branch costs in the simulator's 3-stage model, and explain why a loop with a conditional branch slows down each time the branch is taken.

The idea

A pipeline splits the fetch-decode-execute loop from lesson 28 into stages that run at the same time. With three stages, while one instruction is executing, the next is being decoded and the one after is being fetched. Each instruction still takes the same number of steps, but the core finishes about one instruction per cycle in steady state. A pipeline is only as good as its guess about what comes next. Straight-line code keeps every stage busy. A branch is the exception, because the instructions fetched after it may be the wrong ones.

The Cortex-M3 has a three-stage pipeline: fetch, decode and execute (Arm Cortex-M3 TRM DDI0337G, §1.1 and §1.3). The TRM also describes branch target forwarding (§1.5), a hardware feature that reduces the cost of some branches. The Cortex-M0+ has a two-stage pipeline and implements Armv6-M (Arm Cortex-M0+ datasheet). A shorter pipeline has less work in flight to throw away, but it also overlaps less.

What a taken branch costs

When a branch is taken, the next instruction is not the one that followed it in memory. The core has already fetched the instructions behind the branch, and they are on the wrong path. Those instructions are flushed: thrown away without any effect. The cycles spent on them are lost.

The simulator uses the simplest model of this. It has a 3-stage pipeline, and each taken branch flushes the two instructions that follow it, so it loses 2 cycles. An untaken branch loses nothing, because the next instruction in memory is the right one. Real Cortex-M cores differ in detail: the exact cost depends on the instruction, the core and the memory, and the TRM's instruction timing chapter (Chapter 18) gives the figures. We did not check those figures for this lesson, so use the TRM before you quote a number.

The simulator's halt, B ., counts as a taken branch too, because it jumps to itself. When you count flushes in the program below, do not count the final halt. The pipeline view adds it to the total, so the total on screen is one branch higher than the loop's real cost.

"Why do branches cost so much in a pipelined core, and what does a shorter pipeline change?" Answer out loud in 60 seconds, then compare.

Model answer

The core fetches and decodes past the branch before it knows the outcome, so a taken branch makes those instructions wrong and flushes them. A longer pipeline has more of them in flight, so it loses more per taken branch. A shorter one, like the M0+'s two stages, loses less per branch but overlaps less work. Real cores add tricks such as branch target forwarding to reduce the cost.
