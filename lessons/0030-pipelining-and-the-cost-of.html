Pipelining and the cost of branches

A pipeline lets the core work on three instructions at once. A branch throws away the work it started on the wrong path, and that is where a loop pays its price.

By the end of this lesson you can count the cycles a taken branch costs in the simulator's 3-stage model, and explain why a loop with a conditional branch slows down each time the branch is taken.

Where we are and why it matters

Lesson 28 showed the core running one instruction at a time through three phases: fetch, decode and execute. Lesson 29 showed what the instruction bits mean. Neither lesson said how long each phase takes, and that question decides how fast your code runs. A motor step loop that must finish in 50 microseconds, a bit-banged protocol that must keep its edges on time, and an interrupt handler that must finish before the next interrupt all depend on counting cycles correctly.

The cost of a branch is the part of that count most often guessed wrong. Every if, every loop and every function call is a branch, so the cost is paid all over a real program. This lesson explains where the cost comes from, using the simulator's simple model, and then checks the model against the Arm timing table for a real Cortex-M3.

The concepts, one at a time

A clock cycle is one tick of the core's clock. The Pico runs its core at 125 MHz, which is 8 nanoseconds per cycle, and the work the core does is measured in these ticks. A pipeline is the split of the fetch, decode and execute work into stages that run at the same time. While one instruction is in the execute stage, the next is in decode, and the one after that is being fetched from memory.

The pipeline's benefit is throughput, the number of instructions finished per cycle. Its cost is latency, the time one instruction takes from fetch to the end. A pipeline makes latency slightly longer and throughput much higher. Without a pipeline, a 3-stage core would finish one instruction every three cycles and leave two of its three stages idle at any moment. With a pipeline, once the first instruction is through, one instruction finishes every cycle. A pipeline is only as good as its guess about what comes next. Straight-line code keeps every stage busy. A branch is the exception, because the instructions fetched after it may be the wrong ones.

The Cortex-M3 has a three-stage pipeline: fetch, decode and execute. Arm's TRM names the three stages in its section on the execution pipeline (Arm Cortex-M3 TRM DDI0337G, §1.3). The Cortex-M0+ has a two-stage pipeline and implements Armv6-M (Arm Cortex-M0+ datasheet). A shorter pipeline has less work in flight to throw away, but it also overlaps less.

Why a branch is different from other instructions

A pipeline keeps several instructions in flight, so the core must decide what to fetch next before the current instruction has finished. For straight-line code the answer is simple: the next address in memory. For a branch the answer depends on the branch's outcome, which the core only knows once the branch reaches execute. A conditional branch such as BNE is taken only when a flag test passes, so the core cannot know in the fetch stage whether to fetch the next instruction in memory or the branch target.

The core makes a guess. The TRM says that for conditional branches "the address is speculatively presented", and that the forwarded result then decides "if the branch path flushes the fetch queue or is preserved" (DDI0337G, §1.4). If the branch is not taken, the guess was right and nothing is lost. If it is taken, the fetched instructions are on the wrong path. The core discards them, and that discarding is called a pipeline flush. The instructions are not executed, but the fetch cycles that brought them in are gone, and the core must start fetching from the target before it can do useful work.

The TRM also describes branch target forwarding (§1.5). For some branch types the core presents the branch's memory access "at least a cycle earlier than when the opcode reaches execute". That shortens the wait for the target, but it does not make the cost zero, and the TRM says conditional branches are still speculated. Read the section before you assume a branch is free.

A worked example: what a loop costs on a Cortex-M3

The TRM gives timings for every Thumb instruction in its instruction timing chapter (Chapter 18, Table 18-1). We will use three rows of that table and check the simulator against them. The rows we need say the following, in the table's own words.

  • Data operations such as ADD, MOV and CMP take 1 cycle in the 16-bit form.
  • Branches take 1 cycle plus any fetch stalls, which we ignore here.
  • For a branch taken, "pipeline reloads (two cycles are added)". So a taken B, BNE or BL takes 1 + 2 = 3 cycles.

Table 18-1 is a Cortex-M3 table. The text also says that "additional cycles can be taken because of fetch stalls", which happen when the memory cannot supply an instruction in time. We assume memory keeps up, so the numbers below are the best case. Real code on a real board can be slower.

Now take the loop in the simulator example below. It starts with MOV R0, #0, then runs an ADD, a CMP and a BNE four times. The BNE is taken on the first three passes and falls through on the fourth. Work out the cycles pass by pass:

  1. Before the loop: MOV R0, #0 takes 1 cycle. Total so far: 1.
  2. Pass 1: ADD takes 1, CMP takes 1, and BNE is taken, so it takes 3. The pass costs 5 cycles. Total: 6.
  3. Pass 2: the same as pass 1, 5 cycles. Total: 11.
  4. Pass 3: the same again, 5 cycles. Total: 16.
  5. Pass 4: ADD takes 1, CMP takes 1, and BNE falls through, so it takes 1. The pass costs 3 cycles. Total: 19.

The same penalty applies to calls and returns. Table 18-1 puts B, BL and BX in one row of 16-bit branches, with the same "two cycles are added" rule when they are taken. A call therefore costs the same flush as a loop's back-edge, and a function that is called inside a hot loop pays it twice per pass, once for the call and once for the return.

The loop runs for 19 cycles in total, counting the MOV. Three taken branches each cost 2 cycles more than an untaken one, so 6 of the 19 cycles are the branch penalty. The other 13 are the work itself: four adds and four compares, plus the four branch instructions' base cycles, plus the initial move. That 6-cycle figure is the number the simulator reports as "cycles lost to branch flushes" for this loop, with the halt added on top.

The simulator's model

The simulator is a teaching model, not a Cortex-M3. It has a 3-stage pipeline, and each taken branch flushes the two instructions that follow it, so it loses 2 cycles. An untaken branch loses nothing in this model. That matches the TRM's "two cycles are added" for a taken branch, which is why the number is 2 and not 1. Real cores differ in detail. The Cortex-M0+ has a two-stage pipeline, so its numbers are different, and we did not check its branch cycle counts for this lesson. Use the datasheet and the TRM for the chip you are building for.

The simulator's pipeline view draws the three stages and marks the flushed instructions with a cross. It is a picture of the model, not a trace of real hardware. The count it prints is the number of taken branches times 2, and it includes the halt at the end of the program. The next section explains the halt.

The simulator's halt, B ., counts as a taken branch too, because it jumps to itself. When you count flushes in the program below, do not count the final halt. The pipeline view adds it to the total, so the total on screen is one branch higher than the loop's real cost.

Common mistakes and how to spot them

  1. Counting the untaken branch as if it costs the same. A beginner adds 2 cycles for every branch, including the one that falls through. The symptom is a predicted cycle count that is too high by two for every loop exit. The fix: charge the penalty only when the branch is taken, and charge the base cycle to every branch.
  2. Forgetting that the halt is a taken branch. The pipeline view on screen counts B ., so its total is one branch higher than the loop's cost. The symptom is that your prediction matches the loop's cost but not the number on screen. The fix: subtract the halt, as the warning above says.
  3. Treating a flush as a wait state. Flash wait states are a separate effect: the memory is slower than the core, so the core waits for it. A flush throws away work the core already did. The symptom is that the loop is slow even though its code is short, and a student blames flash when the cause is taken branches. The fix: count taken branches first, then check the wait states in the datasheet and the clock setup.
  4. Using one core's numbers for another. The 2-cycle penalty comes from the Cortex-M3 pipeline model. A Cortex-M0+ has a shorter pipeline, and its numbers are not the same. The symptom is a timing estimate that is right on one board and wrong on the Pico. The fix: check the timing source for the core in your project.

In real projects

Professional firmware engineers rarely count cycles by hand for a whole program. They count them where timing matters: an interrupt handler, a bit-banged waveform, or the body of a loop that runs at a fixed rate. For interrupts the TRM gives a fixed figure. It says there is "a 12-cycle latency from asserting the interrupt to the first instruction of the ISR executing" (DDI0337G, §5.5.1, Figure 5-2), which is a number a reviewer can check. The rest of the timing is measured on the board with a timer or the debugger, because the cache, the flash wait states and the bus contention all change the result.

A code review of a hot loop often asks two questions: is there a branch in the loop that could be removed, and does the loop's back-edge go to a short distance? Both are about the same cost.

Summary

  • A pipeline overlaps the fetch, decode and execute stages, so one instruction finishes per cycle in steady state.
  • The Cortex-M3 has three pipeline stages (TRM §1.3). The Cortex-M0+ has two.
  • A conditional branch is speculated: the core fetches the next instructions in memory until it knows the outcome (TRM §1.4).
  • A taken branch flushes the instructions behind it. In the Arm timing table the taken branch costs 3 cycles against 1 for an untaken one (Table 18-1).
  • The simulator's model charges 2 cycles per taken branch and includes the halt in the on-screen total.
  • A loop with a taken back-edge pays the penalty on every pass except the last.
  • Flash wait states and flushes are different effects, and the cycle count of a real loop needs both checked.
