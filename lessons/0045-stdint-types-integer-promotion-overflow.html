stdint types, integer promotion, and overflow pitfalls

A uint8_t looks like a small number, but C does its arithmetic in a bigger type first. Forget that, and a sum comes out wrong or a loop never ends.

By the end of this lesson you can predict the value of an arithmetic expression on uint8_t values, find the loop that never ends, and say which integer type a register or a wire format should use.

The idea

The header <stdint.h> gives integer types with an exact width. uint8_t is an unsigned integer of exactly 8 bits with no padding bits. The standard says each uintN_t is defined only when the implementation provides a type of that width, so on a given toolchain you should check which ones exist. cppreference, fixed-width integer types Use exact-width types when the size is part of the contract: a register is 32 bits, a sensor byte is 8 bits. Use plain int for an ordinary counter, where the range is not part of the design.

The trap is the step between the variable and the arithmetic. C does not do arithmetic on a type narrower than int. Before an operator runs, small integer types are promoted to int, or to unsigned int if int cannot hold every value of that type. This is integer promotion, and it happens to every operand of +, - and the other arithmetic operators. cppreference, integer promotions

Promotion, then the store

Read this carefully, because the code below looks like it adds two bytes: 

uint8_t a = 200;
uint8_t b = 100;
int s = a + b;        /* a and b are promoted to int first: s is 300 */
uint8_t c = a + b;    /* 300 is converted to uint8_t, modulo 256: c is 44 */

The sum is not wrapped when it is computed. It is wrapped when it is stored into an 8-bit variable. Unsigned conversion is modulo 2N, where N is the width of the target type, so 300 becomes 300 − 256 = 44. cppreference, conversion to an unsigned type The same rule means uint8_t x = 0; x--; gives 255. Wrapping an unsigned value is well-defined in C. It is a value rule, not an error.

The loop that never ends. uint8_t i; for (i = 0; i < 300; i++) compares i with 300. The variable can only hold 0 to 255. After 255, i++ stores 256 as 0, so i never reaches 300 and the loop never stops. The fix is a counter wide enough for the bound: uint16_t here, or int if the range is not part of the design.

Signed overflow is not wrapping

Unsigned overflow wraps modulo 2N. Signed overflow does not. In C it is undefined behaviour: the program may do anything, and the compiler may assume it never happens. cppreference, overflows in arithmetic operators 

int x = INT_MAX;   /* INT_MAX from <limits.h> */
x = x + 1;        /* undefined behaviour: the result does not fit in int */

The danger is that the compiler's optimiser uses the assumption. A test such as if (x + 1 > x) may be folded to true, so the check you wrote to catch overflow never runs. cppreference says the overflowed operation "may be completely optimized out by the compiler". For embedded code, check a range before the arithmetic, not after.

Signed and unsigned in one comparison

When an operator has a signed and an unsigned operand of the same rank, the signed one is converted to unsigned first. This is the usual arithmetic conversion, and comparisons follow it too. cppreference, usual arithmetic conversions 

int n = -1;
unsigned int u = 1;
if (n < u) { ... }   /* false: n becomes UINT_MAX, which is larger than 1 */

The same rule explains a common bug with size_t in a bounds check, where sizeof(buf) - 1 is unsigned and a negative int index compares as huge. Keep the types of the two sides the same before you compare them.

Which type to use

  1. A register or a wire byte: an exact-width unsigned type, such as uint8_t or uint32_t. The width is the contract.
  2. An ordinary loop counter: int, or a type wide enough for the bound. Never a type narrower than the bound.
  3. A value compared with another: use the same signedness on both sides, and cast explicitly if you must mix them.
You can predict an 8-bit sum before running it: promote to int, add, then wrap only on the store. You can also name the loop that never ends, and the comparison that flips when a negative int meets an unsigned value.
