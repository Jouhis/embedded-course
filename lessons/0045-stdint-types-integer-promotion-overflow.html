stdint types, integer promotion, and overflow pitfalls

A uint8_t looks like a small number, but C does its arithmetic in a bigger type first. Forget that, and a sum comes out wrong or a loop never ends.

By the end of this lesson you can predict the value of an arithmetic expression on uint8_t values, find the loop that never ends, and say which integer type a register or a wire format should use.

Where we are and why it matters

Part 3 is about writing embedded C. You already know the syntax, so this lesson does not explain loops or functions. It explains what the numbers do. Earlier, lesson 36 showed that memory is a row of bytes, and that a register is a fixed group of bits. Lesson 38 showed that a peripheral register has a fixed width, such as 32 bits. A C integer type that is the wrong width gives you a value that the hardware never meant.

Real code runs into this often. A sensor sends one byte per sample, and the program adds the bytes to get a total. A timer counts ticks in a register that wraps every 65,536 ticks. A loop counts to 300 with a byte counter. Each of these works in a quick test and fails in the field, because the type is narrower than the value. The fix is to pick types on purpose, and to know what C does when the numbers do not fit.

Concepts, one at a time

Bits, bytes and width

A bit holds a 0 or a 1. A byte is 8 bits, and an unsigned byte holds the values 0 to 255, which is 28 values counted from 0. In general, an unsigned value of N bits holds 0 to 2N − 1. A 16-bit value holds 0 to 65,535, and a 32-bit value holds 0 to 4,294,967,295.

The C standard's integer types, such as int, do not have a fixed width. An int is at least 16 bits, and on the ARM Cortex-M3 used in this course it is 32 bits. The header <stdint.h> gives types with an exact width: uint8_t is an unsigned integer of exactly 8 bits, uint16_t is 16 bits, and uint32_t is 32 bits. The _t types are only defined where the implementation provides a type of that width, which for these common widths every embedded toolchain does. cppreference, fixed-width integer types Use exact-width types when the size is part of the contract: a register is 32 bits, a sensor byte is 8 bits. Use plain int for an ordinary counter, where the range is not part of the design.

Unsigned values wrap around

When an unsigned value goes above its largest value, it wraps. The rule is modulo arithmetic: the result is the true value modulo 2N, where N is the width of the type. For a uint8_t the modulus is 256, so 256 becomes 0, and 257 becomes 1. The same rule makes 0 minus 1 equal to 255. The C standard defines this as the value of the unsigned type, so it is not an error and it is not undefined. It is the normal arithmetic of that type. cppreference, conversion to an unsigned type

Hardware counters often wrap in the same way. A timer that counts to 65,535 and then restarts is doing modulo 216 arithmetic. That is why the wrap is useful for counters, and why it is dangerous for a loop that expects the value to exceed the wrap point.

Integer promotion: the step before the arithmetic

The trap is the step between the variable and the arithmetic. C does not do arithmetic on a type narrower than int. Before an operator runs, small integer types are promoted to int, or to unsigned int if int cannot hold every value of that type. This is integer promotion, and it happens to every operand of +, - and the other arithmetic operators. cppreference, integer promotions

Signed overflow is a different rule

Unsigned overflow wraps. Signed overflow does not. In C, when the result of a signed operation does not fit in the type, the behaviour is undefined: the standard places no requirement on the result, and the compiler may assume the overflow never happens. An int that holds INT_MAX and is increased by 1 is the standard example. cppreference, overflows in arithmetic operators

Undefined behaviour is a common source of bugs in C. A check that you wrote to detect the overflow may be removed by the optimiser, because the optimiser assumes the overflow cannot happen. The section on mistakes shows this with a real compile.

Comparing signed and unsigned values

When an operator has a signed operand and an unsigned operand of the same size, the signed operand is converted to unsigned first. This is the usual arithmetic conversion, and comparisons follow it too. A negative int becomes a very large unsigned value, so it compares as larger than small positive numbers. cppreference, usual arithmetic conversions

Worked example: 200 plus 100, in binary

Take the example from the figure and do the arithmetic bit by bit. Write 200 in binary: 200 is 128 + 64 + 8, so it is 1100 1000. Write 100 as 64 + 32 + 4, so it is 0110 0100.

The sum is 300, which is 1 0010 1100 in nine bits. Storing it in eight bits keeps the bottom eight, 0010 1100, which is 44. The ninth bit is lost, and that is the entire overflow. The arithmetic was correct in int, and the loss happened at the store.

The code, line by line

The following program tests the example, and its output is what a correct understanding predicts. Read it line by line. 

#include <stdint.h>
#include <stdio.h>

int main(void) {
    uint8_t a = 200;
    uint8_t b = 100;
    int s = a + b;        /* a and b are promoted to int first: s is 300 */
    uint8_t c = a + b;    /* 300 is converted to uint8_t, modulo 256: c is 44 */
    printf("s = %d, c = %u\n", s, c);
    return 0;
}

#include <stdint.h> brings in the exact-width types. #include <stdio.h> brings in printf, which runs on the PC here. On the board you would print through the serial port instead. The two uint8_t variables hold values that fit in a byte, so the declarations are correct.

The line int s = a + b; is the one that surprises most readers. The operands are promoted to int, the addition gives 300, and the result is stored in an int, which holds it. s is 300. The line uint8_t c = a + b; performs the same addition, and the same promotion, and then stores 300 into an 8-bit variable. The store converts the value modulo 256, so c is 44. The two lines look identical, but they differ in the type of the variable that receives the result.

The printf line uses %d for the int and %u for c, which is an unsigned value. When c is passed to printf, it is promoted to int first, as every small argument is. For a positive value such as 44, the printed text is the same either way.

The second program shows the wrap of zero, and the signed and unsigned comparison: 

#include <stdint.h>
#include <stdio.h>

int main(void) {
    uint8_t x = 0;
    x--;                          /* 0 - 1 wraps modulo 256 to 255 */
    int n = -1;
    unsigned int u = 1;
    printf("x = %u, n < u is %d\n", x, n < u);   /* n becomes UINT_MAX first */
    return 0;
}

x-- decrements an unsigned byte from 0. The result, −1, is stored in an 8-bit unsigned variable, and modulo 256 it becomes 255. The comparison n < u converts n to unsigned int first. The value −1 becomes 4,294,967,295 on a 32-bit int, which is larger than 1, so the comparison is false. Compiling this with -Wall -Wextra produces a warning, -Wsign-compare, that points at the comparison. Treat that warning as a bug report, not as noise.

Common mistakes and how to spot them

  1. A byte counter for a longer loop. The code uint8_t i; for (i = 0; i < 300; i++) compares i with 300. The variable can only hold 0 to 255. After 255, i++ stores 256 as 0, so i never reaches 300 and the loop never stops. The symptom is a program that stops printing, or a watchdog reset that happens at the same point each time. The compiler warns about it with -Wextra (-Wtype-limits). The fix is a counter wide enough for the bound: uint16_t here, or int if the range is not part of the design.
  2. A signed overflow check that the optimiser removes. A test such as if (x + 1 > x) is meant to catch an overflow when x is INT_MAX. Because signed overflow is undefined, the compiler may assume the sum is always greater, and it may remove the check. We compiled int plus_one_greater(int x) { return x + 1 > x; } with GCC at -O2, and the output was a function that returns 1 with no comparison in it. The symptom is a guard that never fires in an optimised build. The fix is to check before the addition: test x > INT_MAX - 1 first.
  3. A negative index that passes a size check. A check such as if (index < (int)sizeof(buf)) tests only the top end of the buffer. A negative index such as −1 is below the size, so it passes, and the code then reads before the start of the buffer. The symptom is a corrupted value or a fault that depends on the input. The fix is to test the sign as well, as in if (index >= 0 && index < (int)sizeof(buf)).
  4. Trusting the sum of two bytes. A sensor total built as uint8_t total = a + b + c loses the carry at each store, so the total is wrong by a multiple of 256. The symptom is a total that is always smaller than expected for large inputs. The fix is to sum in a wide type, such as uint32_t total = (uint32_t)a + b + c;, and to convert to a byte only when you must.
The loop that never ends. The byte counter in mistake 1 is a frequent bug in firmware. It works for the first test with a small bound, and it hangs when the bound is raised. Before you change a bound, check the type of every variable the loop touches.

Which type to use

  1. A register or a wire byte: an exact-width unsigned type, such as uint8_t or uint32_t. The width is the contract, so the code and the hardware or protocol must agree on it.
  2. An ordinary loop counter: int, or a type wide enough for the bound. Never a type narrower than the bound.
  3. A value compared with another: use the same signedness on both sides, and cast explicitly if you must mix them.
  4. A sum of many small values: add in a wide type, and narrow the result once at the end, after you have checked its range.

In real projects

Professional embedded teams treat integer types as part of the interface. A structure that matches a register map uses exact-width fields, and a protocol decoder names the width of each field in the wire format. A code review asks, for every arithmetic line on a byte or a short, what type the intermediate value has and where it is narrowed. Teams enable the warnings -Wall -Wextra at least, because they catch the sign comparison and the type-limit loop. Some teams add stricter checks for implicit narrowing and run static analysis on the code, as lesson 83 describes.

Summary

  • An unsigned value of N bits holds 0 to 2N − 1, and unsigned arithmetic wraps modulo 2N, so 256 becomes 0 in a uint8_t.
  • Before an operator runs, small integer types are promoted to int, so uint8_t a = 200 and b = 100 give a + b = 300 in int.
  • The wrap happens at the store. uint8_t c = a + b keeps 300 modulo 256, which is 44.
  • Signed overflow is undefined behaviour, so the optimiser may remove a check such as x + 1 > x. Test for the overflow before the addition.
  • When a signed operand meets an unsigned operand of the same size, the signed value is converted to unsigned first. So int n = -1 compared with unsigned int u = 1 gives n < u as false.
  • A uint8_t i in for (i = 0; i < 300; i++) never ends, because i wraps after 255. A uint16_t counter reaches 300.
  • Use exact-width types, such as uint8_t or uint32_t, where the width is the contract for a register or a wire byte.
  • Add a sum of many small values in a wide type, such as uint32_t total = (uint32_t)a + b + c, and narrow the result to a byte only when you must.
