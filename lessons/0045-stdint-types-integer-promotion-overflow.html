Integer widths, promotion rules and overflow in C

By the end of this lesson you can predict the value of an arithmetic expression on uint8_t values, find the loop that never ends, and say which integer type a register or a wire format should use.

Integer types and hardware widths

Part 3 is about writing embedded C, and since the syntax is already familiar, this lesson does not explain loops or functions but what the numbers do. Lesson 36 showed that memory is a row of bytes and a register a fixed group of bits, and lesson 38 that a peripheral register has a fixed width such as 32 bits, so a C integer type of the wrong width yields a value the hardware never meant.

Real code runs into this often. A sensor sends one byte per sample and the program adds the bytes for a total, a timer counts ticks in a register that wraps every 65 536 ticks, and a loop counts to 300 with a byte counter. Each works in a quick test and fails in the field because the type is narrower than the value, and the remedy is to choose types deliberately and to know what C does when the numbers do not fit.

Bits, bytes and type widths

A bit holds a 0 or a 1, and a byte is 8 bits, so an unsigned byte holds the values 0 to 255, which are 28 values counted from 0. In general an unsigned value of N bits holds

0 ≤ v ≤ 2N − 1(1)

where N is the width in bits, so a 16-bit value holds 0 to 65 535 and a 32-bit value 0 to 4 294 967 295.

The standard C integer types such as int have no fixed width: an int is at least 16 bits, and on the ARM Cortex-M3 used in this course it is 32. The header <stdint.h> provides exact-width types, uint8_t being an unsigned integer of exactly 8 bits, uint16_t 16 bits and uint32_t 32 bits. These _t types are defined only where the implementation provides a type of that width, which every embedded toolchain does for these common widths. cppreference, fixed-width integer types Use exact-width types when the size is part of the contract, as for a 32-bit register or an 8-bit sensor byte, and plain int for an ordinary counter whose range is not part of the design.

Unsigned wrap-around

When an unsigned value exceeds its largest value, it wraps according to modulo arithmetic: the result is the true value modulo 2N, where N is the width of the type. For a uint8_t the modulus is 256, so 256 becomes 0 and 257 becomes 1, and by the same rule 0 minus 1 equals 255. The C standard defines this as the value of the unsigned type, so it is neither an error nor undefined, but the normal arithmetic of that type. cppreference, conversion to an unsigned type

Unsigned arithmetic resembles clock arithmetic: three hours after 23:00 the clock shows 02:00 rather than 26:00, because it counts modulo 24, and a uint8_t counts modulo 256 in the same way, so 255 + 1 is 0 and 0 − 1 is 255. A clock face shows only the hours, however, and nothing in a C variable records that a wrap happened, so the program cannot tell afterwards.

Hardware counters often wrap in the same way, a timer that counts to 65 535 and restarts performing modulo 216 arithmetic. That makes the wrap useful for counters and dangerous for a loop that expects the value to pass the wrap point.

Many devices count milliseconds since boot in a uint32_t, which wraps after 232 ms, about 49.7 days. A timeout written as if (now > start + 500) works for weeks and then misbehaves around the wrap, so the bug appears only on units that have run for seven weeks, while the wrap-safe form if ((uint32_t)(now - start) >= 500) uses the same modulo arithmetic on purpose (lessons 55 and 73 return to it).

Integer promotion

The trap lies in the step between the variable and the arithmetic, because C performs no arithmetic on types narrower than int. Before an operator runs, small integer types are promoted to int, or to unsigned int if int cannot hold every value of the type, and this integer promotion applies to every operand of +, - and the other arithmetic operators. cppreference, integer promotions

Signed overflow

Unsigned overflow wraps, but signed overflow follows a different rule. When the result of a signed operation does not fit in its type, the behaviour in C is undefined, meaning that the standard places no requirement on the result and the compiler may assume the overflow never happens; an int holding INT_MAX and increased by 1 is the standard example. cppreference, overflows in arithmetic operators

Undefined behaviour is a common source of C bugs, because an optimiser that assumes the overflow cannot happen may remove a check written to detect it. The mistakes section shows this with a real compile.

Signed and unsigned comparisons

When an operator has a signed and an unsigned operand of the same size, the signed one is converted to unsigned first. This usual arithmetic conversion applies to comparisons too, so a negative int becomes a very large unsigned value and compares as larger than small positive numbers. cppreference, usual arithmetic conversions

Worked example: 200 plus 100 in binary

We repeat the figure's example bit by bit. In binary 200 is 128 + 64 + 8, or 1100 1000, and 100 is 64 + 32 + 4, or 0110 0100. Before reading the table, predict the value stored in an 8-bit result.

The sum is 300, which is 1 0010 1100 in nine bits. Storing it in eight bits keeps the bottom eight, 0010 1100, or 44, and the lost ninth bit is the entire overflow: the arithmetic was correct in int, and the loss happened at the store.

The test programs line by line

The following program tests the example, and its output matches what a correct understanding predicts. 

#include <stdint.h>
#include <stdio.h>

int main(void) {
    uint8_t a = 200;
    uint8_t b = 100;
    int s = a + b;        /* a and b are promoted to int first: s is 300 */
    uint8_t c = a + b;    /* 300 is converted to uint8_t, modulo 256: c is 44 */
    printf("s = %d, c = %u\n", s, c);
    return 0;
}

#include <stdint.h> brings in the exact-width types and #include <stdio.h> the printf that runs on the PC here, where a board would print through the serial port instead. The two uint8_t variables hold values that fit in a byte, so their declarations are correct.

The line int s = a + b; surprises most readers: the operands are promoted to int, the addition gives 300 and the result goes into an int, which holds it, so s is 300. The line uint8_t c = a + b; performs the same promotion and addition but then stores 300 into an 8-bit variable, converting it modulo 256, so c is 44. The two lines look identical and differ only in the type of the variable receiving the result.

The printf line uses %d for the int and %u for the unsigned c. Like every small argument, c is promoted to int when passed to printf, and for a positive value such as 44 the printed text is the same either way.

The second program shows the wrap of zero and the signed and unsigned comparison. 

#include <stdint.h>
#include <stdio.h>

int main(void) {
    uint8_t x = 0;
    x--;                          /* 0 - 1 wraps modulo 256 to 255 */
    int n = -1;
    unsigned int u = 1;
    printf("x = %u, n < u is %d\n", x, n < u);   /* n becomes UINT_MAX first */
    return 0;
}

x-- decrements an unsigned byte from 0, and the result, −1, stored in an 8-bit unsigned variable becomes 255 modulo 256. The comparison n < u first converts n to unsigned int, turning −1 into 4 294 967 295 on a 32-bit int, which is larger than 1, so the comparison is false. Compiling with -Wall -Wextra produces a -Wsign-compare warning that points at the comparison, and that warning deserves treatment as a bug report rather than noise.

Choosing an integer type

  1. A register or a wire byte: an exact-width unsigned type such as uint8_t or uint32_t, because the width is the contract on which the code and the hardware or protocol must agree.
  2. An ordinary loop counter: int, or any type wide enough for the bound, but never one narrower than the bound.
  3. A value compared with another: the same signedness on both sides, with an explicit cast where they must be mixed.
  4. A sum of many small values: addition in a wide type, narrowing the result once at the end after checking its range.

Common mistakes and how to spot them

A byte counter for a longer loop

A program stops printing, or a watchdog reset happens at the same point every time. In uint8_t i; for (i = 0; i < 300; i++) the variable can hold only 0 to 255, so after 255 i++ stores 256 as 0, i never reaches 300 and the loop never stops, a case the compiler flags with -Wextra (-Wtype-limits). Use a counter wide enough for the bound, uint16_t here or int when the range is not part of the design.

A signed overflow check removed by the optimiser

A guard never fires in an optimised build. A test such as if (x + 1 > x) is meant to catch overflow when x is INT_MAX, but since signed overflow is undefined, the compiler may assume the sum is always greater and drop the test; compiling int plus_one_greater(int x) { return x + 1 > x; } with GCC at -O2 gave a function that returns 1 with no comparison in it. Check before the addition instead, testing x > INT_MAX - 1 first.

A negative index that passes a size check

A value is corrupted, or a fault occurs, depending on the input. A check such as if (index < (int)sizeof(buf)) tests only the top end of the buffer, so a negative index such as −1 passes and the code reads before the start of the buffer. Test the sign as well, as in if (index >= 0 && index < (int)sizeof(buf)).

The sum of bytes trusted

A sensor total is always smaller than expected for large inputs, wrong by a multiple of 256, because uint8_t total = a + b + c loses the carry at the store. Sum in a wide type, as in uint32_t total = (uint32_t)a + b + c;, and convert to a byte only when necessary.

The byte counter of the first mistake is a frequent firmware bug, because it passes the first test with a small bound and hangs once the bound is raised. Before changing a bound, check the type of every variable the loop touches.

Integer types in professional code

Professional embedded teams treat integer types as part of the interface: a structure matching a register map uses exact-width fields, and a protocol decoder names the width of each field in the wire format. Code review asks, for every arithmetic line on a byte or a short, what type the intermediate value has and where it is narrowed. Teams enable at least -Wall -Wextra, which catch the sign comparison and the type-limit loop, and some add stricter checks for implicit narrowing and run static analysis on the code, as lesson 83 describes.

Summary

  • An unsigned value of N bits holds 0 to 2N − 1, and unsigned arithmetic wraps modulo 2N, so 256 becomes 0 in a uint8_t.
  • Before an operator runs, small integer types are promoted to int, so with uint8_t a = 200 and b = 100, a + b is 300 in int.
  • The wrap happens at the store, so uint8_t c = a + b keeps 300 modulo 256, which is 44.
  • Signed overflow is undefined behaviour, so the optimiser may remove a check such as x + 1 > x, and the test must come before the addition.
  • A signed operand meeting an unsigned operand of the same size is converted to unsigned first, so int n = -1 against unsigned int u = 1 makes n < u false.
  • A uint8_t i in for (i = 0; i < 300; i++) never ends because i wraps after 255, while a uint16_t counter reaches 300.
  • Use exact-width types such as uint8_t or uint32_t where the width is the contract of a register or a wire byte.
  • Add many small values in a wide type, as in uint32_t total = (uint32_t)a + b + c, and narrow the result only when necessary.
