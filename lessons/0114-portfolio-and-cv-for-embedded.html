Portfolio and CV for embedded jobs

A hiring manager spends a few minutes on your CV and your GitHub before deciding whether to talk to you. This lesson turns the course's work into evidence they can check in those minutes.

By the end of this lesson you can draft a portfolio README for your capstone (lessons 110 to 113) that passes every item on the checklist in the exercise.

This lesson is concept-only. A CV and a README are not simulated, so there is no Wokwi project. The hands-on part is a written draft, checked against a list and a short quiz. Your capstone is the project you point to, so have its repository open while you work.

Where we are and why it matters

The capstone is the first thing in this course that looks like a real product. It has requirements (lesson 110), drivers and host tests (lesson 111), a real-time control loop (lesson 112), and a Modbus interface with a bootloader and a CI pipeline (lesson 113). Each of those stages produced code, tests and a commit history. None of that helps a hiring manager unless they can find it, read it and check it in a few minutes.

The problem this lesson solves is a translation problem. A candidate who comes from software has real skills, such as testing, code review and continuous integration, but the words they use do not match an embedded job ad. The second problem is trust. A CV that says "experienced with RTOS" is a claim. A repository with a task, a queue and a test that proves the timing is evidence. Good hiring managers look for evidence, and this lesson shows how to make your work easy to check.

What a junior embedded hiring manager looks for

Many software developers move into embedded work and then struggle, not with C, but with the hardware: the electronics, the signals and the tools that show what the chip is really doing. Memfault's engineers say the same thing in their roadmap article, and they advise beginners to start with simple, hands-on projects. The article is written for software engineers who lack hardware knowledge, which is where you start. Interrupt: Embedded Systems Roadmap, Bridging the Gap

The capstone README

Your repository's README is the first thing a reviewer reads. Make the first screen answer three questions: what does this do, can I trust it, and can I run it? The template below puts those answers at the top, then the design, then your reflection. Copy it into your capstone repository, and replace each bracketed placeholder.

Paste this template into your README. Each line in square brackets is a placeholder to fill in.

# Filament dryer controller (capstone)

![tests](https://github.com/[OWNER]/[REPO]/actions/workflows/tests.yml/badge.svg)

[One paragraph: what the device does, for whom, and the board it runs on.]

[Open the simulation in Wokwi](https://wokwi.com/projects/[PROJECT_ID]) · [Demo, under 30 seconds](docs/demo.gif)

Reading the template line by line

A README is read top to bottom, and each block answers one question a reviewer asks in order. The first line is the title: it names the device, not the course. The two badge lines are images that GitHub draws from a workflow's latest run, so a green badge means the named workflow passed on the latest commit. The paragraph under them is the only description most reviewers read, so it must say what the device does and for whom.

The Wokwi link and the demo line are the proof that the thing runs. The link opens the simulation, and the demo is a short recording of the serial output or the display, so a reviewer can see the result without installing anything. The block diagram comes next, because a reviewer scans a diagram faster than a paragraph. The quick start is the first real test of the README: it lists the commands, and a reviewer may copy them.

The design decisions section links each choice to the lesson that taught it, which shows that you chose on purpose. The hardware section asks for part numbers and section numbers, so a reviewer can check a value in a datasheet. The last three sections are the reflection and the licence. They are short on purpose, and the next two parts of this lesson explain how to fill them honestly.

Badge URLs follow GitHub's documented pattern, https://github.com/OWNER/REPOSITORY/actions/workflows/WORKFLOW-FILE/badge.svg, where the file is the workflow in .github/workflows/ (GitHub Docs: workflow status badges). Use your real workflow file names.
A demo GIF or a short video is evidence that the thing works. Record the serial output or the simulated display, not your screen-share face. Keep it short enough to load on a phone.

A worked example: turning one result into a README line

Suppose you want a line in "What I learned" about the heater safety. A weak version says "I made the heater safe". To make it checkable, walk through four steps. First, name the claim: a heater with no gain must be caught as a runaway. Second, find the test that checks it: the capstone's closed-loop tests include test_dead_heater_is_caught_as_runaway in test_closed_loop.c. Third, run it and read the number. The solution prints dead heater: runaway latched at 80.4 s, and the test asserts that the fault appears within 300 seconds. Fourth, write the line with the number and the test name: "A dead heater at full power is latched as a runaway after 80.4 s; the test asserts it within 300 s."

The finished line has three parts a reviewer can check: a number, a test name and a limit. If the reviewer opens the repository, the test is there, and the printed value matches. Each "What I learned" point should be built the same way, with a bug or a measurement behind it.

What makes "What I'd change" convincing

Reviewers trust a candidate who knows the limits of their work. Name one real limit, say why you accepted it, and say what you would test next. A section that only praises the project reads as a sales page.

Commit messages a reviewer can read

The commit history is the other half of the evidence. A reviewer scrolls through the log to see how the project grew, and a log of "fix", "fix again" and "wip" tells them nothing. The Pro Git book, which the course cites for Git, gives a simple convention. The summary line should be a single line of no more than about 50 characters that describes the change. A blank line follows it, and then an optional body that explains why, wrapped to about 72 characters. The summary is written in the imperative mood, as an instruction, so "Add host tests for the I2C driver" is correct and "Added some tests" is not. 

Add host tests for the NTC conversion

The conversion turns an ADC count into tenths of a degree.
The tests use a table of known resistances, so a wrong
coefficient fails on the PC before it reaches the board.

Read the example line by line. The first line is the summary: it names the change in five words, in the imperative, and it fits well inside 50 characters. The second line is blank, which is what tools and reviewers expect as the separator. The last three lines are the body, and they say why the change exists and what it protects against. A reviewer who reads only the summary still learns what changed, and one who reads the body learns the reason.

A CV for a career changer

If you come from software, you already have the skills that junior embedded teams struggle to find: testing habits, continuous integration and code review. The job is to translate them into embedded terms, and to show the hardware work next to them. Keep the structure short. One page, in this order:

  1. Headline and summary: one line on the role you want, and two lines on the strongest evidence you have.
  2. Embedded projects: the capstone, the labs and any board you built, each with a result you can measure.
  3. Experience: your software roles, reworded with embedded terms (table below).
  4. Skills: a short list, using only the keywords you can demonstrate.
  5. Education, courses and links: the course, your GitHub, and a link to your demo.

The translation table below shows the method. Each row keeps the same fact, a skill you already used, and replaces the software word with the embedded one. The embedded wording names the hardware or the target, because that is the word a reviewer is searching for. Do not invent a job you never had. Translate only the work you did.

What you did in softwareThe embedded wording
Wrote unit tests for a web serviceWrote host unit tests for a C driver with a fake I2C device, without a board
Set up CI for a web projectSet up CI that builds the firmware, runs host tests and simulates the board on every push

Quantify whenever you can. A line that says "logged 100 readings per second for 8 hours in a simulated run" is stronger than "built a logger".

Exercise: check your README

Work through the four questions first, then tick each checklist item against your own README. Only tick an item you can point to on the page.

README checklist

  • The first screen says what the device does, in one paragraph.
  • A block diagram shows the inputs, the control task, the outputs and the interface.
  • A build badge and a test badge point to real workflow files.
  • A Wokwi link opens the simulation, or the README says which board to use.
  • A demo, under 30 seconds, shows the real output (serial log or display).
  • The quick start has the exact build and test commands, and I ran them from a clean clone.
  • Every datasheet value has a part number, a document and a section.
  • "What I learned" names a bug or a measurement, not a feeling.
  • "What I'd change" names one real limit and the test I would add.
  • A LICENSE file is in the root, and no secrets (tokens, Wi-Fi passwords) are committed.
  • The commit history reads as a sequence of steps, not "fix" repeated thirty times.

LinkedIn and GitHub hygiene

  • Headline: the role you want and one proof, for example "Embedded C, Cortex-M, FreeRTOS. Capstone: a PID dryer controller with host tests and CI."
  • Pinned repositories: pin the capstone and one smaller lab. Unpin anything that is an unfinished tutorial copy.
  • Licences and third-party code: say which parts are vendor code (SDK, HAL, Unity) and keep their licences. Do not publish a vendor's example code as your own.
  • Datasheets: link to the manufacturer's page instead of uploading a copy of the PDF.
  • Secrets and personal data: search your history for tokens and Wi-Fi passwords before you make a repository public. A committed token must be revoked, not only deleted.
  • Posts: a photo of a working board with one sentence on what it does is enough. Credit the people who helped.

Common mistakes and how to spot them

Each mistake below is one a reviewer sees often. Each entry gives the symptom first, so you can notice it in your own draft before a reviewer does.

Mistake 1: a green badge that tests nothing

Symptom: the test badge is green, but the workflow only compiles the code, or its test step runs an empty command. Cause: the badge shows the workflow's result, and a workflow that never runs the tests will still pass. Fix: open the workflow log, find the line that runs the tests, and check that it prints a count of passed tests. If it does not, fix the workflow before you point to the badge.

Mistake 2: a quick start that was never run

Symptom: a reviewer copies the build command and it fails at the first step, with a missing tool or a path that does not exist. Cause: the commands were typed from memory, in a folder that already had the tools and files. Fix: clone the repository into an empty folder on a clean machine, or at least a clean folder, and run the exact commands in the README. Write down what they print, so the README can say what a passing run looks like.

Mistake 3: a keyword you cannot explain

Symptom: the interviewer asks "how does a Zephyr thread differ from a FreeRTOS task?" and the candidate cannot answer past the word. Cause: the skill list was copied from a job ad, and the keyword was never used in a project. Fix: keep a keyword only if you can point to code that uses it and explain one decision in it. Remove the rest. Lesson 115 has drills that test the same ideas.

Mistake 4: a secret left in the history

Symptom: the file with the Wi-Fi password was deleted in the latest commit, but a search of the history still finds the password in an earlier one. Cause: Git keeps every earlier version of a file, so a deletion in a new commit does not remove the old text from the history. Fix: treat the secret as leaked, revoke or change it, and then remove it from the whole history before the repository is public. Searching only the current files is not enough.

Mistake 5: a vague "What I learned"

Symptom: the section says "I learned a lot about timing and debugging", and the reviewer has nothing to ask about. Cause: the section describes feelings, not results. Fix: write each point with the bug, the measurement or the test that produced it, as the worked example above shows.

Interview drill

"Walk me through your capstone in two minutes." Speak it out loud, then compare.

Model answer outline
  1. Problem first: a filament dryer must hold a set temperature and report over Modbus, safely.
  2. Architecture: the block diagram, with the sensor driver, the PID task, the PWM output and the Modbus task on an RTOS.
  3. One decision with a trade-off: why a PID with a clamped integral, and what it costs (lesson 105).
  4. Evidence: host unit tests for the control code, and CI that runs them on every push (lessons 80 and 82).
  5. One debugging story, with the tool you used.
  6. One limit you accepted, and what you would test next.

Summary

  • A reviewer checks evidence in minutes: a repository, a test, a number, a log. Every claim needs one of these behind it.
  • Use the seven signals as questions. A row with no answer is a gap to close with a small lab, not with a stronger sentence.
  • Keep a keyword only if you can point to code that uses it and explain one decision in that code.
  • A README answers three questions on its first screen: what it does, whether to trust it, and how to run it.
  • Write each "What I learned" point with a number, a bug or a test, and each "What I'd change" point with one real limit.
  • Commit summaries are imperative, about 50 characters, and followed by a blank line and a body that gives the reason.
  • Translate software work into embedded terms only when you did the work, and quantify it when you can.
You have a README template, a CV structure that translates software work into embedded evidence, and a checklist you can run before any application. The capstone is now the thing you point to.
