Portfolio and CV for embedded jobs

A hiring manager spends a few minutes on your CV and your GitHub before deciding whether to talk to you. This lesson turns the course's work into evidence they can check in those minutes.

By the end of this lesson you can draft a portfolio README for your capstone (lessons 110 to 113) that passes every item on the checklist in the exercise.

This lesson is concept-only. A CV and a README are not simulated, so there is no Wokwi project. The hands-on part is a written draft, checked against a list and a short quiz. Your capstone is the project you point to, so have its repository open while you work.

What a junior embedded hiring manager looks for

Many software developers move into embedded work and then struggle, not with C, but with the hardware: the electronics, the signals and the tools that show what the chip is really doing. Memfault's engineers say the same thing in their roadmap article, and they advise beginners to start with simple, hands-on projects. The article is written for software engineers who lack hardware knowledge, which is where you start. Interrupt: Embedded Systems Roadmap, Bridging the Gap

The capstone README

Your repository's README is the first thing a reviewer reads. Make the first screen answer three questions: what does this do, can I trust it, and can I run it? The template below puts those answers at the top, then the design, then your reflection. Copy it into your capstone repository, and replace each bracketed placeholder.

Paste this template into your README. Each line in square brackets is a placeholder to fill in.

Badge URLs follow GitHub's documented pattern, https://github.com/OWNER/REPOSITORY/actions/workflows/WORKFLOW-FILE/badge.svg, where the file is the workflow in .github/workflows/ (GitHub Docs: workflow status badges). Use your real workflow file names.
A demo GIF or a short video is evidence that the thing works. Record the serial output or the simulated display, not your screen-share face. Keep it short enough to load on a phone.

What makes "What I'd change" convincing

Reviewers trust a candidate who knows the limits of their work. Name one real limit, say why you accepted it, and say what you would test next. A section that only praises the project reads as a sales page.

A CV for a career changer

If you come from software, you already have the skills that junior embedded teams struggle to find: testing habits, continuous integration and code review. The job is to translate them into embedded terms, and to show the hardware work next to them. Keep the structure short. One page, in this order:

  1. Headline and summary: one line on the role you want, and two lines on the strongest evidence you have.
  2. Embedded projects: the capstone, the labs and any board you built, each with a result you can measure.
  3. Experience: your software roles, reworded with embedded terms (table below).
  4. Skills: a short list, using only the keywords you can demonstrate.
  5. Education, courses and links: the course, your GitHub, and a link to your demo.
What you did in softwareThe embedded wording
Wrote unit tests for a web serviceWrote host unit tests for a C driver with a fake I2C device, without a board
Set up CI for a web projectSet up CI that builds the firmware, runs host tests and simulates the board on every push
Reviewed pull requestsReviewed firmware changes for shared state, blocking calls in interrupts and missing tests
Investigated a production incidentTraced a field fault from a log and a stacked fault record to the faulting line
Designed an internal APIDesigned a driver interface behind a hardware abstraction layer, with a fake for tests
Wrote scripts for deploymentWrote Python tools that flash, log and check the device over serial

Quantify whenever you can. A line that says "logged 100 readings per second for 8 hours in a simulated run" is stronger than "built a logger".

Exercise: check your README

Work through the four questions first, then tick each checklist item against your own README. Only tick an item you can point to on the page.

README checklist

  • The first screen says what the device does, in one paragraph.
  • A block diagram shows the inputs, the control task, the outputs and the interface.
  • A build badge and a test badge point to real workflow files.
  • A Wokwi link opens the simulation, or the README says which board to use.
  • A demo, under 30 seconds, shows the real output (serial log or display).
  • The quick start has the exact build and test commands, and I ran them from a clean clone.
  • Every datasheet value has a part number, a document and a section.
  • "What I learned" names a bug or a measurement, not a feeling.
  • "What I'd change" names one real limit and the test I would add.
  • A LICENSE file is in the root, and no secrets (tokens, Wi-Fi passwords) are committed.
  • The commit history reads as a sequence of steps, not "fix" repeated thirty times.

LinkedIn and GitHub hygiene

  • Headline: the role you want and one proof, for example "Embedded C, Cortex-M, FreeRTOS. Capstone: a PID dryer controller with host tests and CI."
  • Pinned repositories: pin the capstone and one smaller lab. Unpin anything that is an unfinished tutorial copy.
  • Licences and third-party code: say which parts are vendor code (SDK, HAL, Unity) and keep their licences. Do not publish a vendor's example code as your own.
  • Datasheets: link to the manufacturer's page instead of uploading a copy of the PDF.
  • Secrets and personal data: search your history for tokens and Wi-Fi passwords before you make a repository public. A committed token must be revoked, not only deleted.
  • Posts: a photo of a working board with one sentence on what it does is enough. Credit the people who helped.

"Walk me through your capstone in two minutes." Speak it out loud, then compare.

Model answer outline
  1. Problem first: a filament dryer must hold a set temperature and report over Modbus, safely.
  2. Architecture: the block diagram, with the sensor driver, the PID task, the PWM output and the Modbus task on an RTOS.
  3. One decision with a trade-off: why a PID with a clamped integral, and what it costs (lesson 105).
  4. Evidence: host unit tests for the control code, and CI that runs them on every push (lessons 80 and 82).
  5. One debugging story, with the tool you used.
  6. One limit you accepted, and what you would test next.
