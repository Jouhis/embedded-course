Bare-metal blink with CMSIS only

Lesson 47 used a register struct you wrote yourself. Now you use the vendor's CMSIS names, and you add the two things the STM32 needs before a pin does anything: a clock on the port, and a mode in CRL or CRH.

By the end of this lesson you can enable a GPIO port's clock, set a pin's mode in CRL or CRH, drive two LEDs at different rates from the SysTick counter without a blocking delay, and explain why BSRR is safer than ODR for a shared pin.

Where we are and why it matters

Lesson 47 showed how a C struct can lay itself over a block of memory-mapped registers, so that GPIOC->ODR is a store to a fixed address. Lesson 51 covered GPIO output at a higher level, and lesson 66 built this project's toolchain and showed the device header. This lesson joins those ideas into a program that blinks two LEDs on the real Blue Pill register set.

Work on a real board starts the same way. A new product has a microcontroller with several status LEDs, and each LED needs its port clocked, its pin configured and its timing set without stopping the rest of the firmware. The configuration mistakes in this lesson are the ones engineers make on their first board bring-up, so the symptoms below are worth remembering.

Concepts, one at a time

A GPIO pin is a switch the CPU controls

A GPIO (general-purpose input/output) pin is a metal leg on the chip that the CPU can drive high or low, or read as an input. High means close to the supply voltage, here 3.3 V. Low means close to ground, which is 0 V. An LED in series with a resistor lights when current flows through it, and you control that current by switching the pin. The glossary defines the term in more detail. Glossary: GPIO

The STM32F1 has three ports, A, B and C, and each port has 16 pins numbered 0 to 15. The name PC13 means port C, pin 13. Each pin has its own setting for direction and output type, and the settings live in two configuration registers. The rest of this lesson is about where those bits are and how to write them safely.

Active low: a 0 lights the LED

The Blue Pill's onboard LED is wired between the supply and PC13. Current flows when PC13 is low, so a 0 lights the LED and a 1 turns it off. This is called active low. The external LED on PB0 is the other way round: it sits between PB0 and ground through a 220 Ω resistor, so a 1 lights it and a 0 turns it off. A wrong polarity is the most common reason an LED appears inverted, and the code must match the wiring.

Ohm's law sets the LED current. With a 3.3 V pin, a red LED that drops about 2 V, and 220 Ω in series, the current is (3.3 − 2) ÷ 220 ≈ 5.9 mA. That is comfortably within what an STM32 pin can supply at low speed.

The clock gate: a peripheral is off until you turn it on

Every peripheral on an STM32 has a clock gate, a single bit in the reset and clock control block (RCC) that powers its register block. Lesson 40 described the clock tree that feeds these gates. While a gate is closed, reads return garbage and writes are ignored. The write does not fault, so the program keeps running and the LED never lights. This is the first thing to check when a register write seems to do nothing.

Two registers per port: CRL and CRH

On the RP2040, a pin's function is one field, and its direction and drive are separate registers. The F1 is different. Each pin owns a 4-bit field, and the fields are split between two registers by pin number. Pins 0 to 7 are in CRL, and pins 8 to 15 are in CRH. Pin n starts at bit (n mod 8) × 4. Inside a field, two bits set the mode and two bits set the configuration.

The bit positions come from the device header, which defines GPIO_CRH_MODE13 at bit 20 and GPIO_CRH_CNF13 at bit 22. RM0008 Rev 21 (section 9.2.2) places MODE13 in bits 21:20 and CNF13 in bits 23:22, so the header agrees. The values come from the reference manual, RM0008 Rev 21 (Table 20 and Table 21, section 9.1), and the HAL source agrees with them: its header defines GPIO_SPEED_FREQ_LOW as the MODE bit pattern 10, which is 2 MHz, and its configuration constants give 00 for general-purpose push-pull and 10 for alternate-function push-pull.

MODE and CNF: what the two bits mean

The MODE bits say the direction and the maximum speed. 00 is input, and the output speeds are 10 MHz, 2 MHz and 50 MHz for 01, 10 and 11 (RM0008 Rev 21, section 9.2.2 and Table 21). The HAL confirms that 10 is 2 MHz and 11 is 50 MHz. The CNF bits say what kind of circuit the pin uses. For an output, 00 is general-purpose push-pull, which drives both high and low (RM0008 Rev 21, Table 20). The value 0x2 is binary 0010: CNF 00 and MODE 10. That is a push-pull output at 2 MHz. A 2 MHz output is slow enough for an LED, and it causes less electrical noise than a 50 MHz edge.

Worked example: writing PC13 bit by bit

The code needs to change one field and keep the others. Build the value step by step.

  1. Find the field. PC13 is pin 13, so its field starts at (13 − 8) × 4 = 20, and it covers bits 20 to 23.
  2. Make a mask for the field. Four bits set, shifted to bit 20: 0xF << 20, which is 0x00F00000. Inverting that gives ~(0xF << 20), which is 0xFF0FFFFF. Anding with it clears only the field.
  3. Make the new value. 0x2 << 20 is 0x00200000, which puts binary 0010 into bits 20 to 23.
  4. Combine. (CRH & 0xFF0FFFFF) | 0x00200000. The other seven CRH fields come through unchanged, because the mask keeps every bit outside PC13's field.

The same pattern works for any pin in the register. If the field were written as a plain constant, for example GPIOC->CRH = 0x00200000, every other pin in port C's CRH would be reset to its default, so PC8 to PC15 would lose their settings. The mask is the safe form. 

GPIOC->CRH = (GPIOC->CRH & ~(0xFU << 20)) | (0x2U << 20);   /* PC13: push-pull, 2 MHz */

Read the line from the inside out. 0xFU << 20 is the mask for the field, and the ~ inverts it so that a 0 marks the bits to clear. The & clears those four bits and keeps the rest. 0x2U << 20 is the new value shifted into place, and the | writes it. The U suffix makes each constant unsigned, so the shifts do not fill the top bit with a sign.

Step 1: enable the clock

The clock enable bits sit in RCC->APB2ENR, because the GPIO ports are on the APB2 bus. The device header gives each bit a name, and it lists the positions (RM0008 Rev 21, section 7.3.7, lists the same bits: AFIOEN bit 0, IOPAEN bit 2, IOPBEN bit 3, IOPCEN bit 4 and USART1EN bit 14), which you can check yourself in third_party/cmsis-device-f1/Include/stm32f103xb.h: 

/* from stm32f103xb.h: the bit positions */
RCC_APB2ENR_AFIOEN    /* bit 0 */
RCC_APB2ENR_IOPAEN    /* bit 2 */
RCC_APB2ENR_IOPBEN    /* bit 3 */
RCC_APB2ENR_IOPCEN    /* bit 4 */
RCC_APB2ENR_USART1EN  /* bit 14 */

RCC->APB2ENR |= RCC_APB2ENR_IOPCEN;   /* now GPIOC accepts writes */

The first five lines are names for bits, and the last line is the enable. |= sets bit 4 and leaves the other enable bits alone, so enabling GPIOC does not turn off the USART or any other clock. This is a read-modify-write, which is safe here because only the main code writes this register.

A missing clock enable does not fault. The write is ignored, the pin stays where reset left it, and the LED never lights. When a register write seems to do nothing, check the clock before anything else.

On the Pico, the SDK's gpio_init() does this step for you. On the STM32 you write it, and the code that sets a pin always starts with the clock. The enable bits are the clock gating from the RCC section of the reference manual (RM0008 Rev 21, section 5.3.2 and section 7.3.7). Lesson 40 introduced the clock tree, which is the source of the clock that these gated peripherals receive.

Step 2: the configuration fields

The PB0 pin is pin 0, so it lives in CRL with its field at bit 0. The same mask-and-set pattern applies, with the shift changed to zero: 

GPIOB->CRL = (GPIOB->CRL & ~(0xFU << 0)) | (0x2U << 0);   /* PB0: push-pull, 2 MHz */

The solution computes each shift from the pin number, as (LED_ONBOARD_PIN - 8U) * PIN_FIELD_BITS for PC13 and LED_EXTERNAL_PIN * PIN_FIELD_BITS for PB0, so the code follows the rule rather than a hard-coded number. The starter shows the PC13 line only, and the learner's first task is to write the PB0 line.

Step 3: BSRR or ODR

Lesson 47 introduced both. ODR holds the output level of all 16 pins. Setting one pin with ODR |= bit is a read-modify-write: load, change, store. BSRR does the change in one store: bit n sets pin n, and bit n + 16 resets it. A 0 changes nothing.

For PC13, the set bit is bit 13, so the value 0x00002000 drives the pin high, which turns the LED off. The reset bit is bit 29, so 0x20000000 drives it low, which lights the LED. The header names these GPIO_BSRR_BS13 and GPIO_BSRR_BR13, and it confirms that BR13 is bit 29. RM0008 Rev 21, section 9.2.5, gives the same layout: BS bits 15:0 set the pins and BR bits 31:16 reset them.

Use BSRR for any pin that an interrupt or another task might touch, and for every pin you change in the loop. The risk is real even on one core, because an interrupt can run between the load and the store, and then its change is lost. Lesson 70 puts an interrupt on a button pin, which is this same situation.

Worked example: two LEDs on one timeline

A blocking delay cannot run two LEDs at different rates, so the solution uses a deadline for each LED and a clock that counts milliseconds. Here is a short timeline with the PB0 LED at 150 ms half periods and the PC13 LED at 500 ms half periods. Each row is a moment when a deadline passes.

Time (ms)Deadline reachedActionNext deadline
150PB0Set PB0 high (external LED on)300
300PB0Reset PB0 low (external LED off)450
450PB0Set PB0 high (external LED on)600
500PC13Reset PC13 low (onboard LED on)1000
600PB0Reset PB0 low (external LED off)750

The timeline shows that the PB0 deadlines fire without waiting for the PC13 deadline, and each deadline moves forward by one half period. The onboard LED changes at 500 ms, 1000 ms and so on, while the external LED changes every 150 ms. The two LEDs share one loop, and neither waits for the other.

Step 4: SysTick, without blocking

The template's delay_ms() blocks: while it waits, nothing else runs. Two LEDs at different rates cannot share one blocking delay. Instead, let SysTick count milliseconds, and keep a deadline for each LED. SysTick is the 24-bit countdown built into every Cortex-M core. It reloads from LOAD and sets COUNTFLAG when it reaches zero. Reading CTRL clears the flag (PM0056 Rev 7, section 4.5.1: COUNTFLAG is set when the counter reaches 0 and returns 1 only if that happened since the last read). Arm Cortex-M3 Devices Generic User Guide, and the SysTick section of PM0056 (ST's programming manual for the STM32F10xxx, Rev 7, section 4.5). 

SysTick->LOAD = (SystemCoreClock / 1000U) - 1U;   /* 8000 - 1 at 8 MHz: one millisecond */
SysTick->VAL  = 0;
SysTick->CTRL = SysTick_CTRL_CLKSOURCE_Msk | SysTick_CTRL_ENABLE_Msk;

/* in the loop: one call per millisecond that has passed */
if (SysTick->CTRL & SysTick_CTRL_COUNTFLAG_Msk) { now_ms++; }

Line by line: the first line loads the reload value. The counter counts down from 7999 to 0, which is 8000 cycles, one millisecond at 8 MHz. VAL = 0 clears the counter so the first period starts clean. The CTRL write selects the core clock and enables the counter. The last line is the polling test: COUNTFLAG is set once per wrap, and reading CTRL clears it, so the test both reads and resets the flag. Each time the flag is set, the loop adds one to now_ms.

The solution puts that test in a helper named systick_one_ms_elapsed(). The loop then checks each LED's deadline, and when now_ms reaches it, the code toggles the LED and moves the deadline forward by one half period. A slow LED never holds up a fast one. The loop must poll at least once per millisecond, or it misses a COUNTFLAG. Printing a long line over the serial port can take longer than that, which is why the solution prints only at startup. Lesson 73 covers SysTick in full, with its interrupt.

Code explained: the solution's LED block

if (now_ms >= next_onboard_ms) {
    next_onboard_ms += LED_ONBOARD_HALF_MS;
    onboard_on = !onboard_on;
    GPIOC->BSRR = onboard_on ? (1U << (LED_ONBOARD_PIN + 16U)) : (1U << LED_ONBOARD_PIN);
}

The condition compares the clock with the deadline, and the deadline moves on by a fixed amount rather than being set to now_ms + 500. That choice keeps the blink rate exact: if the loop is late by a millisecond, the next deadline still lands on a multiple of 500. The variable onboard_on records the logical state of the LED, not the pin level, so the code reads clearly. The BSRR line writes the reset bit when the LED should be on, because the LED is active low, and writes the set bit when it should be off.

Common mistakes and how to spot them

Mistake 1: the external LED never lights

PC13 blinks, PB0 stays dark, and the code looks right. The most likely cause is the missing GPIOB clock enable from step 1 of the starter. Because the write is ignored, the mode and the output bits never reach the pin, so the LED sees no change. The symptom is one LED working and the other dead, with no error. The fix is RCC->APB2ENR |= RCC_APB2ENR_IOPBEN; before any GPIOB write. In the debugger, read RCC->APB2ENR: bit 3 should be 1.

Mistake 2: writing CRH with a plain constant

Someone writes GPIOC->CRH = 0x00200000; to configure PC13, and the LED works. Later a different pin on port C stops behaving, for example an input that was set up with a pull-up. The constant reset its field to the default input state. The symptom appears on a pin you did not change. The fix is the mask-and-set pattern, which changes only the field you name.

Mistake 3: the LED is inverted

The onboard LED is on when the program says it should be off. The cause is the polarity. PC13 is active low, so the LED is lit by a reset of the pin, which is the upper half of BSRR. If you write the set bit when you meant to light the LED, you have the polarity backwards. The fix is to name the active level in a constant, such as LED_ACTIVE_LOW, and to write one helper that applies it.

Mistake 4: one LED blinks slower than the timing says

The external LED is meant to blink every 150 ms, and it blinks every 300 ms. The most common cause is a slow loop: a serial print, or a long calculation, takes more than a millisecond, so the loop misses a COUNTFLAG. The deadline logic is correct, but the tick count is wrong. The fix is to keep the loop short, to print only at startup, as this project does, and to move the tick into an interrupt, which lesson 73 does.

In real projects

Teams avoid busy-waiting in product code, because a blocking delay holds up everything else, and a button press or a sensor read is missed while the code waits. The deadline pattern in this lesson is the same design that the super-loop uses in production. It is also what a code reviewer looks for: a delay_ms() inside the main loop is a warning sign, and a deadline or a timer interrupt is the usual fix.

Summary

  • A GPIO pin does nothing until its port's clock bit in RCC->APB2ENR is set.
  • Pins 0 to 7 are configured in CRL, and pins 8 to 15 in CRH. Pin n starts its 4-bit field at (n mod 8) × 4.
  • The value 0x2 in a field is CNF 00 and MODE 10, a push-pull output at 2 MHz.
  • Change one field with a mask and a set, so the other pins in the register keep their settings.
  • In BSRR, bit n sets pin n and bit n + 16 resets it. For PC13, bit 13 sets and bit 29 resets.
  • PC13 is active low, so a reset lights its LED. PB0 is active high, so a set lights it.
  • Deadlines driven by a polled SysTick count let two LEDs run at different rates without a blocking delay.
  • A loop that misses a COUNTFLAG runs slow without any error, so keep the loop short.
