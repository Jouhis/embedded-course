Bare-metal blink with CMSIS only

GPIO through the vendor's register names

By the end of this lesson you can enable a GPIO port's clock, set a pin's mode in CRL or CRH, drive two LEDs at different rates from the SysTick counter without a blocking delay, and explain why BSRR is safer than ODR for a shared pin.

Two LEDs on the Blue Pill registers

Lesson 47 showed how a C struct can lay itself over a block of memory-mapped registers, so that GPIOC->ODR is a store to a fixed address, lesson 51 covered GPIO output at a higher level, and lesson 66 built this project's toolchain and showed the device header. This lesson joins those ideas into a program that blinks two LEDs through the real Blue Pill register set, using the vendor's CMSIS names and adding the two things the STM32 needs before a pin does anything, a clock on the port and a mode in CRL or CRH.

Work on a real board starts the same way, a new product having a microcontroller with several status LEDs, each needing its port clocked, its pin configured and its timing set without stopping the rest of the firmware. The configuration mistakes in this lesson are the ones engineers make at their first board bring-up, so their symptoms are worth remembering.

GPIO pins and ports on the STM32F1

A GPIO (general-purpose input/output) pin is a metal leg of the chip that the CPU can drive high or low or read as an input, high meaning close to the supply voltage, here 3.3 V, and low close to ground, 0 V. An LED in series with a resistor lights when current flows through it, a current controlled by switching the pin, and the glossary defines the term in more detail (Glossary: GPIO).

The STM32F1 has three ports, A, B and C, each with 16 pins numbered 0 to 15, so the name PC13 means port C, pin 13. Each pin has its own direction and output-type setting, held in two configuration registers, and the rest of this lesson concerns where those bits are and how to write them safely.

Active-low and active-high LEDs

The Blue Pill's onboard LED is wired between the supply and PC13, so current flows when PC13 is low, a 0 lighting the LED and a 1 turning it off, which is called active low. The external LED on PB0 works the other way round, sitting between PB0 and ground through a 220 Ω resistor, so a 1 lights it and a 0 turns it off. A wrong polarity is the most common reason an LED appears inverted, so the code must match the wiring.

Ohm's law sets the LED current

I = (Vpin − VF) ÷ R(1)

where Vpin is the 3.3 V pin voltage, VF the LED's forward drop of about 2 V for a red LED and R the 220 Ω resistor, giving (3.3 − 2) ÷ 220 ≈ 5.9 mA, comfortably within what an STM32 pin can supply at low speed.

The peripheral clock gate

Every peripheral on an STM32 has a clock gate, a single bit in the reset and clock control block (RCC) that powers its register block, fed by the clock tree of lesson 40. While a gate is closed, reads return garbage and writes are ignored without a fault, so the program keeps running and the LED never lights, which makes the clock the first thing to check when a register write seems to do nothing.

A peripheral with its clock gated off is like an unplugged machine: its buttons can be pressed, which here means writing its registers, and nothing happens, and on the STM32F1 the writes do not even stick. Enabling the clock in RCC plugs it in, and it has to come first. An unplugged machine is obviously dark, though, whereas a gated peripheral gives no sign at all, which is why the mistake is so easy to miss.

The CRL and CRH configuration registers

On the RP2040 a pin's function is one field, with direction and drive in separate registers, whereas on the F1 each pin owns a 4-bit field, the fields being split by pin number between two registers, pins 0 to 7 in CRL and pins 8 to 15 in CRH. Pin n starts at bit (n mod 8) × 4, and within a field two bits set the mode and two the configuration.

The bit positions come from the device header, which defines GPIO_CRH_MODE13 at bit 20 and GPIO_CRH_CNF13 at bit 22, in agreement with RM0008 Rev 21 (section 9.2.2), which places MODE13 in bits 21:20 and CNF13 in bits 23:22. The values come from the reference manual, RM0008 Rev 21 (Table 20 and Table 21, section 9.1), and the HAL source agrees, its header defining GPIO_SPEED_FREQ_LOW as the MODE bit pattern 10, which is 2 MHz, and its configuration constants giving 00 for general-purpose push-pull and 10 for alternate-function push-pull.

The MODE and CNF bits

The MODE bits set the direction and the maximum speed, 00 being input and 01, 10 and 11 outputs at 10 MHz, 2 MHz and 50 MHz (RM0008 Rev 21, section 9.2.2 and Table 21), with the HAL confirming that 10 is 2 MHz and 11 is 50 MHz. The CNF bits set the kind of circuit the pin uses, 00 for an output being general-purpose push-pull, which drives both high and low (RM0008 Rev 21, Table 20). The value 0x2, binary 0010, is therefore CNF 00 and MODE 10, a push-pull output at 2 MHz, slow enough for an LED and electrically quieter than a 50 MHz edge.

Worked example: the PC13 field bit by bit

The code needs to change one field while keeping the others, so we build the value step by step. Before starting, work out at which bit PC13's field begins.

  1. Find the field. PC13 is pin 13, so its field starts at (13 − 8) × 4 = 20 and covers bits 20 to 23.
  2. Make a mask for the field. Four set bits shifted to bit 20 give 0xF << 20, or 0x00F00000, whose inverse ~(0xF << 20) is 0xFF0FFFFF, so ANDing with it clears only the field.
  3. Make the new value. 0x2 << 20 is 0x00200000, which puts binary 0010 into bits 20 to 23.
  4. Combine. (CRH & 0xFF0FFFFF) | 0x00200000 passes the other seven CRH fields through unchanged, because the mask keeps every bit outside PC13's field.

The same pattern works for any pin in the register, whereas writing the field as a plain constant, for example GPIOC->CRH = 0x00200000, would reset every other pin in port C's CRH to its default, so PC8 to PC15 would lose their settings, which makes the mask the safe form. 

GPIOC->CRH = (GPIOC->CRH & ~(0xFU << 20)) | (0x2U << 20);   /* PC13: push-pull, 2 MHz */

The line reads from the inside out: 0xFU << 20 is the mask for the field, the ~ inverts it so that a 0 marks the bits to clear, and the & clears those four bits and keeps the rest, after which 0x2U << 20 shifts the new value into place and the | writes it. The U suffix makes each constant unsigned, so the shifts never fill the top bit with a sign.

Enabling the GPIO port clocks

The clock enable bits sit in RCC->APB2ENR, because the GPIO ports are on the APB2 bus, and the device header names each bit, at positions that RM0008 Rev 21, section 7.3.7, confirms, AFIOEN at bit 0, IOPAEN at bit 2, IOPBEN at bit 3, IOPCEN at bit 4 and USART1EN at bit 14, all of which can be checked in third_party/cmsis-device-f1/Include/stm32f103xb.h. 

/* from stm32f103xb.h: the bit positions */
RCC_APB2ENR_AFIOEN    /* bit 0 */
RCC_APB2ENR_IOPAEN    /* bit 2 */
RCC_APB2ENR_IOPBEN    /* bit 3 */
RCC_APB2ENR_IOPCEN    /* bit 4 */
RCC_APB2ENR_USART1EN  /* bit 14 */

RCC->APB2ENR |= RCC_APB2ENR_IOPCEN;   /* now GPIOC accepts writes */

The first five lines name bits and the last is the enable, its |= setting bit 4 while leaving the other enable bits alone, so enabling GPIOC does not turn off the USART or any other clock. This read-modify-write is safe here because only the main code writes this register.

A missing clock enable does not fault. The write is ignored, the pin stays where reset left it, and the LED never lights. When a register write seems to do nothing, check the clock before anything else.

On the Pico the SDK's gpio_init() performs this step, whereas on the STM32 the code writes it, so pin setup always starts with the clock. The enable bits are the clock gating from the RCC section of the reference manual (RM0008 Rev 21, section 5.3.2 and section 7.3.7). Lesson 40 introduced the clock tree, which is the source of the clock that these gated peripherals receive.

Configuring PB0 in CRL

PB0 is pin 0, so it lives in CRL with its field at bit 0, and the same mask-and-set pattern applies with the shift changed to zero. 

GPIOB->CRL = (GPIOB->CRL & ~(0xFU << 0)) | (0x2U << 0);   /* PB0: push-pull, 2 MHz */

The solution computes each shift from the pin number, as (LED_ONBOARD_PIN - 8U) * PIN_FIELD_BITS for PC13 and LED_EXTERNAL_PIN * PIN_FIELD_BITS for PB0, so the code follows the rule rather than a hard-coded number. The starter shows only the PC13 line, and writing the PB0 line is the first task.

Atomic pin changes with BSRR

Lesson 47 introduced both registers. ODR holds the output level of all 16 pins, so setting one pin with ODR |= bit is a read-modify-write of load, change and store, whereas BSRR makes the change in one store, bit n setting pin n, bit n + 16 resetting it and a 0 changing nothing.

For PC13 the set bit is bit 13, so 0x00002000 drives the pin high and turns the LED off, while the reset bit is bit 29, so 0x20000000 drives it low and lights the LED. The header names these GPIO_BSRR_BS13 and GPIO_BSRR_BR13, confirming that BR13 is bit 29, and RM0008 Rev 21, section 9.2.5, gives the same layout, BS bits 15:0 setting the pins and BR bits 31:16 resetting them.

BSRR is the register to use for any pin that an interrupt or another task might touch, and for every pin changed in the loop. The risk is real even on one core, because an interrupt can run between the load and the store and its change is then lost, which is exactly the situation of lesson 70, where an interrupt serves a button pin.

Worked example: two LEDs on one timeline

A blocking delay cannot run two LEDs at different rates, so the solution keeps a deadline for each LED and a clock counting milliseconds. The timeline below has the PB0 LED at 150 ms half periods and the PC13 LED at 500 ms, each row being a moment when a deadline passes, so before reading it, predict how many times PB0 toggles before PC13 first does.

Time (ms)Deadline reachedActionNext deadline
150PB0Set PB0 high (external LED on)300
300PB0Reset PB0 low (external LED off)450
450PB0Set PB0 high (external LED on)600
500PC13Reset PC13 low (onboard LED on)1000
600PB0Reset PB0 low (external LED off)750

The PB0 deadlines fire without waiting for the PC13 deadline, each moving forward by one half period, so the onboard LED changes at 500 ms, 1 000 ms and so on while the external LED changes every 150 ms, three times before PC13's first change. The two LEDs share one loop, and neither waits for the other.

A non-blocking millisecond clock from SysTick

The template's delay_ms() blocks, nothing else running while it waits, so two LEDs at different rates cannot share it, and instead SysTick counts milliseconds while each LED keeps a deadline. SysTick is the 24-bit countdown built into every Cortex-M core, reloading from LOAD and setting COUNTFLAG when it reaches zero, and reading CTRL clears the flag (PM0056 Rev 7, section 4.5.1: COUNTFLAG is set when the counter reaches 0 and returns 1 only if that happened since the last read), as described in the Arm Cortex-M3 Devices Generic User Guide and the SysTick section of PM0056 (ST's programming manual for the STM32F10xxx, Rev 7, section 4.5). 

SysTick->LOAD = (SystemCoreClock / 1000U) - 1U;   /* 8000 - 1 at 8 MHz: one millisecond */
SysTick->VAL  = 0;
SysTick->CTRL = SysTick_CTRL_CLKSOURCE_Msk | SysTick_CTRL_ENABLE_Msk;

/* in the loop: one call per millisecond that has passed */
if (SysTick->CTRL & SysTick_CTRL_COUNTFLAG_Msk) { now_ms++; }

The first line loads the reload value, the counter counting down from 7 999 to 0, which is 8 000 cycles or one millisecond at 8 MHz, and VAL = 0 clears the counter so that the first period starts clean. The CTRL write selects the core clock and enables the counter, and the last line is the polling test, in which COUNTFLAG is set once per wrap and reading CTRL clears it, so the test both reads and resets the flag, the loop adding one to now_ms each time it is set.

The solution places that test in a helper named systick_one_ms_elapsed(), and the loop then checks each LED's deadline, toggling the LED when now_ms reaches it and moving the deadline forward by one half period, so a slow LED never holds up a fast one. The loop must poll at least once per millisecond, or it misses a COUNTFLAG. Printing a long line over the serial port can take longer than that, which is why the solution prints only at startup. Lesson 73 covers SysTick in full, with its interrupt.

The solution's LED block line by line

if (now_ms >= next_onboard_ms) {
    next_onboard_ms += LED_ONBOARD_HALF_MS;
    onboard_on = !onboard_on;
    GPIOC->BSRR = onboard_on ? (1U << (LED_ONBOARD_PIN + 16U)) : (1U << LED_ONBOARD_PIN);
}

The condition compares the clock with the deadline, and the deadline advances by a fixed amount rather than being set to now_ms + 500, which keeps the blink rate exact, because a loop that is a millisecond late still puts the next deadline on a multiple of 500. The variable onboard_on records the logical state of the LED rather than the pin level, so the code reads clearly, and the BSRR line writes the reset bit when the LED should be on, the LED being active low, and the set bit when it should be off.

Common mistakes and how to spot them

The external LED never lights

PC13 blinks while PB0 stays dark and the code looks right, the most likely cause being the missing GPIOB clock enable of the starter's step 1, which makes the mode and output writes vanish before they reach the pin, so one LED works and the other is dead with no error. Add RCC->APB2ENR |= RCC_APB2ENR_IOPBEN; before any GPIOB write, and in the debugger check that bit 3 of RCC->APB2ENR reads 1.

CRH written with a plain constant

After GPIOC->CRH = 0x00200000; configures PC13, the LED works, but later a different pin on port C misbehaves, for example an input set up with a pull-up, because the constant reset its field to the default input state, so the symptom appears on a pin nobody changed. Use the mask-and-set pattern, which changes only the named field.

The LED inverted

The onboard LED is on when the program says it should be off, because PC13 is active low and lights on a reset of the pin, the upper half of BSRR, so writing the set bit to light it has the polarity backwards. Name the active level in a constant, such as LED_ACTIVE_LOW, and write one helper that applies it.

One LED blinking slower than its timing

The external LED, meant to blink every 150 ms, blinks every 300 ms, most often because a slow loop, with a serial print or a long calculation taking more than a millisecond, misses a COUNTFLAG, so the deadline logic is correct but the tick count is wrong. Keep the loop short, print only at startup as this project does, and move the tick into an interrupt, as lesson 73 does.

Busy-waiting and deadlines in product code

Teams avoid busy-waiting in product code, because a blocking delay holds up everything else, so a button press or a sensor read is missed while the code waits. The deadline pattern of this lesson is the design the super-loop uses in production, and it is what a code reviewer looks for, a delay_ms() inside the main loop being a warning sign whose usual fix is a deadline or a timer interrupt.

Summary

  • A GPIO pin does nothing until its port's clock bit in RCC->APB2ENR is set.
  • Pins 0 to 7 are configured in CRL and pins 8 to 15 in CRH, pin n starting its 4-bit field at (n mod 8) × 4.
  • The value 0x2 in a field is CNF 00 and MODE 10, a push-pull output at 2 MHz.
  • One field is changed with a mask and a set, so the other pins in the register keep their settings.
  • In BSRR bit n sets pin n and bit n + 16 resets it, so for PC13 bit 13 sets and bit 29 resets.
  • PC13 is active low, so a reset lights its LED, while PB0 is active high, so a set lights it.
  • Deadlines driven by a polled SysTick count let two LEDs run at different rates without a blocking delay.
  • A loop that misses a COUNTFLAG runs slow without any error, so the loop must stay short.
