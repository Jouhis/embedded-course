RS-485 and Modbus RTU

Modbus is the protocol most factory meters, drives and PLCs speak, and RS-485 is the wire it usually runs on. You will write a Modbus slave for the Pico that the lesson's firmware serves over UART0, and talk to it from a Python master on your PC.

By the end of this lesson you can build a Modbus RTU request and response with CRC-16/MODBUS, answer function 03 (read holding registers) and 06 (write single register), and find the end of a frame from the silent interval.

The idea: RS-485 is the wire, Modbus is the language

RS-485 carries each bit as the voltage difference between two wires, A and B, the same differential idea as CAN in lesson 98. It is half-duplex: one pair carries both directions, so only one node may drive the line at a time. A driver stays off unless its driver-enable pin (DE) is high, and the receiver is usually enabled on the same chip by an active-low RE pin. Termination resistors at the two ends stop reflections on a long line, and many nodes can share the bus. These electrical facts are general, so check a transceiver's datasheet before you design a board. The Pico's UART0 is a TTL serial port, not RS-485. In Wokwi there is no transceiver, so the firmware has no DE pin to drive. On a real board you would drive DE high before each reply and low once the last byte has left the shifter.

Modbus defines what the bytes mean. Modbus RTU is the binary version: each byte is sent as-is, with a CRC at the end. The master starts every exchange, and a slave answers only when it is addressed. The Modbus specifications are published by the Modbus organisation (modbus.org specifications): the serial-line specification covers the frame and the timing, and the application protocol specification covers the function codes. This lesson did not open the PDFs, so cite section numbers from the originals when you need them.

The RTU frame

The fields are the slave address (1 to 247; 0 is broadcast), the function code, the data, and a 16-bit CRC. Multi-byte fields are big-endian, which is the opposite of the CRC: the CRC's low byte is sent first. The CRC is CRC-16/MODBUS, with the reflected polynomial 0xA001, an initial value of 0xFFFF and no final XOR. You will check your code against the standard test value: the ASCII string "123456789" gives 0x4B37.

A frame has no start or end byte. The receiver decides that a frame has ended when the line is silent for 3.5 character times. At 115200 baud that is about 334 µs, but the serial-line specification fixes the silence at 1.750 ms for rates above 19200 baud. The firmware uses 1750 µs. Check that value in the specification before you rely on it, because this lesson did not open it.

Function 03 and function 06

FunctionRequest dataResponse data
03 read holding registersstart address, quantity (1 to 125)byte count, then the register values, big-endian
06 write single registerregister address, valuean echo of the request

A request for registers 0 to 1 from slave 1 is 01 03 00 00 00 02 C4 0B. The reply that carries 0x1234 and 0xABCD is 01 03 04 12 34 AB CD 00 20. Those bytes come from the Python code in the project and are repeated in the C host tests, so the two implementations check each other.

When the slave cannot honour a request, it sends an exception: the function code with its high bit set (0x83 for a 03 request), then an exception code. Code 01 is an illegal function, 02 an illegal data address, and 03 an illegal data value (application protocol specification, section 7; not opened for this lesson). A bad CRC or a frame for another address gets no reply at all.

Try it: the host tests first

The frame handler is plain C with no hardware, so you test it on the PC before the board. The project is projects/0099-modbus-rtu-tests. Its starter has the same nine tests as the solution, and six of them fail, because the CRC loop and the function handlers are still marked TODO(learner).

  1. From the workspace root, run python -I tools/build.py projects/0099-modbus-rtu-tests/starter --test. The output ends with 9 Tests 6 Failures 0 Ignored, and 0% tests passed.
  2. Open src/crc16.c and write the inner loop of crc16_modbus(). The check value test is the first to pass. Run the command again.
  3. Open src/modbus.c and handle functions 03 and 06 where the TODO(learner) comment is. Use finish_frame() for the CRC and exception_response() for every error.
  4. You will know it works when the output ends with 9 Tests 0 Failures 0 Ignored, and ctest reports 100% tests passed.
Hint for the CRC loop

XOR each byte into the low byte of crc. Then loop eight times: if the bit that falls off the right end is 1, shift right and XOR with 0xA001, otherwise just shift.

Hint for function 03

The quantity is the value field. Build the response in rsp: address, function, byte count (twice the quantity), then each register big-endian starting at index 3. Pass the total length to finish_frame().

Try it on the Pico, through the simulated serial port

The firmware is in projects/0099-modbus-rtu-slave. It uses the same modbus.c and crc16.c, copied from the host project. The Pico reads frames from UART0 on GP0 and GP1. Its register map is holding register 0 (a counter, +1 each second), register 1 (the LED, bit 0) and register 2 (a sensor value of 2250, which is 22.50 °C in hundredths).

  1. Open projects/0099-modbus-rtu-slave/starter in VS Code and build with Ctrl+Shift+B. The starter builds, but it does not answer yet.
  2. In main.c, write the frame-end test where the TODO(learner) comment is: when the line has been silent for FRAME_SILENCE_US and rx_len is not zero, call modbus_process(), send any reply with uart_write_blocking(), and reset rx_len.
  3. Build again, then start the simulator with F1 → Wokwi: Start Simulator. The serial monitor shows MODBUS SLAVE READY. The simulator forwards UART0 on TCP port 4000 (rfc2217ServerPort = 4000 in wokwi.toml).
  4. In a terminal, install pyserial yourself with pip install pyserial. Then, from the project folder, run python master_modbus.py read 0 3. You will know it works when the master prints three values, with the counter in the first one, and 2250 in the third.
  5. Write the LED register: python master_modbus.py write 1 1 should print echo ok, and the LED on the Pico turns on.
Hint

The timer function is time_us_32(). Compare it with last_byte_us. A reply that is empty means the slave stayed silent: a wrong address or a bad CRC, which is correct behaviour.

You built a Modbus RTU slave whose CRC checks against the standard value, and whose frame handler is tested on the PC first. You also know how a frame ends, and why a bad CRC gets no reply.

"How does a Modbus RTU slave know a frame has ended, and what does it do with a bad CRC?" Answer out loud in 60 seconds, then compare.

Model answer

RTU has no end byte, so the slave waits for a silence of 3.5 character times, which is 1.750 ms above 19200 baud. Then it treats everything received as one frame. It checks the address, then the CRC-16 over all bytes but the last two. A bad CRC means the frame was damaged on the wire, so the slave sends nothing, and the master times out and retries. A correct request for a wrong address also gets no reply.
