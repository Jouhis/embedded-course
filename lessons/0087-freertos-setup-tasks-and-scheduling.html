FreeRTOS setup, tasks and scheduling

A FreeRTOS program is a set of tasks, each with a priority, and a kernel that runs the most urgent ready task. On the Blue Pill that means one tick interrupt, one scheduler and a few lines of configuration.

By the end of this lesson you can create two or more tasks with xTaskCreate(), choose their priorities, write a periodic task with vTaskDelayUntil(), and explain the difference from vTaskDelay(), the idle task and the tick.

Where we are, and why it matters

Lesson 86 showed the problem. A super-loop makes a due job wait for every blocking call ahead of it, and a scheduler fixes that by letting a more urgent job interrupt a less urgent one. This lesson builds that scheduler on the Blue Pill. It uses the SysTick interrupt from lesson 73 as its heartbeat, and the NVIC priority rule from lesson 72, with one important difference that the warnings below explain. Lab 5 moves the Lab 4 monitor onto FreeRTOS, so every task you write here is a pattern you will reuse there.

The project is a small piece of the same design. A periodic blink task toggles the on-board LED every 500 ms, and a report task prints the kernel's tick count once a second over the serial line. A kernel that runs two such tasks correctly is the first step to a device that runs a sensor, a display and a log at the same time.

Concept 1: a task is a loop with a stack and a priority

A task is a C function that never returns. It has its own stack, which is where its local variables and return addresses are kept (lesson 33), and it has a priority. The kernel keeps a control block for each task, called the TCB, which records the task's name, its priority, its stack pointer and where it sits in the kernel's lists. The task does not know it is being shared. It runs as if it owned the core, and the kernel saves and restores its registers when it stops or starts (lesson 88).

A task that does not loop forever must remove itself. The projects in lessons 90 and 91 call vTaskDelete(NULL) when a task has finished its work. A task that returns from its function by accident is a bug, and the kernel has no sensible place to send it.

Concept 2: states, and the ready list

At any moment a task is in one of four states. It is Running when it has the core. It is Ready when it could run now and is waiting for the core. It is Blocked when it is waiting for a time, such as a delay, or for an event, such as a queue item or a semaphore. It is Suspended when another task has parked it until it is resumed. The kernel keeps one ready list for each priority level. Each list holds the Ready tasks of that priority. At every decision point the scheduler looks for the highest-priority list that is not empty, and takes the next task from it. The macro that does this in the kernel is taskSELECT_HIGHEST_PRIORITY_TASK(), at tasks.c line 235 in the kernel version this course uses, V11.2.0 (the version string is in include/task.h line 56). Its loop body, in plain words, is: find the highest priority that has ready tasks, then take the owner of the next entry in that list. The selection is a search over a few lists, not a sort, so it is quick.

Concept 3: priorities run upward in FreeRTOS

A FreeRTOS priority is a number, and a larger number is more urgent. The highest usable priority is configMAX_PRIORITIES − 1. In this course's template, configMAX_PRIORITIES is 5, so the priorities run from 0 to 4. The idle task has priority 0, the lowest, so any task that is ready preempts it.

This is the opposite of the interrupt controller. In lesson 72 you learned that on the NVIC a lower number is more urgent. Both systems are correct within themselves, and the mismatch is a real trap. The priority you pass to xTaskCreate() is a task priority, and it follows the FreeRTOS rule. The priority you give an interrupt with NVIC_SetPriority() follows the Cortex-M rule. Lesson 90 shows where the two meet.

Priority numbers grow upward: 0 is the lowest (the idle task), and configMAX_PRIORITIES − 1 is the highest. Many bugs come from reading "priority 1" as the most urgent, which is the opposite of the NVIC rule in lesson 72, where a lower number is more urgent.

Concept 4: the tick

The tick is the kernel's clock. It is a periodic interrupt, here driven by the Cortex-M SysTick timer (lesson 73), and it fires configTICK_RATE_HZ times per second. The template sets that to 1000, so the tick is 1 ms. The SysTick reload value is set in port.c line 759 as the SysTick clock divided by the tick rate, minus one, the same rule as lesson 73.

On every tick the port calls xTaskIncrementTick() (tasks.c line 4725). That function adds one to the kernel's tick count. If the count wraps to zero, it swaps the delayed lists. Then it checks whether any delayed task's time has come, and moves each such task back to its ready list. If one of the woken tasks has a higher priority than the running task, the function reports that a switch is needed. The SysTick handler in port.c at line 491 then asks for the switch by pending PendSV (line 507). PendSV is the exception that actually performs the switch, and lesson 89 walks through it.

Because the tick is the only thing that wakes a delayed task, the tick sets the resolution of every delay. A 1 ms tick cannot give a 0.5 ms delay. pdMS_TO_TICKS(n) converts milliseconds to ticks, and it is defined in projdefs.h line 42 as n × configTICK_RATE_HZ ÷ 1000, so at a 1 kHz tick it returns exactly n.

A task that becomes ready from a call made by another task, rather than from the tick, can also request the switch. A queue or semaphore call that wakes a higher-priority task yields inside the call, so the switch happens before the call returns to the sender. Lesson 90 shows the interrupt version of the same rule.

With configUSE_TIME_SLICING set to 1 (the default, FreeRTOS.h line 2750), tasks of equal priority take turns at each tick. Tasks of different priority never share the CPU this way: the higher one always wins.

Concept 5: delays, relative and absolute

vTaskDelay(n) blocks the calling task for n ticks, counted from the moment of the call (tasks.c line 2458). If the work before it takes time, the period grows by that time, and the task drifts. Take a task that does 30 ms of work and then calls vTaskDelay(100) each time, where each tick is 1 ms. It wakes at 100 ms after the first call's return, runs for 30 ms again, and sleeps 100 ms again. Its period is 130 ms. After ten cycles it is 1300 ms into a schedule meant to be 1000 ms long.

vTaskDelayUntil(&last, n) keeps an absolute schedule instead. It sets the next wake-up time to last + n, and then it updates last to that time. The 30 ms of work is inside the 100 ms slot, so the wake-ups fall at 100, 200, 300 ms and so on, for as long as the work fits. The macro is defined in task.h at line 933. For a periodic job that must keep its rate, such as a sensor read every 200 ms, this is the call to use.

Concept 6: the idle task

When no task is ready, the kernel must still have something to run. It has a task for that, the idle task, which runs at priority 0 (tskIDLE_PRIORITY, task.h line 199). The kernel creates it in prvCreateIdleTasks() (tasks.c line 3540), which vTaskStartScheduler() calls at line 3703. The xTaskCreate() call that makes it is at line 3654.

The idle task's loop is prvIdleTask() (line 5801). Its main job here is to free the memory of tasks that were deleted, which it does in prvCheckTasksWaitingTermination() (line 5826). It is the place where a low-power WFI instruction could go, through the idle hook, but the template turns the idle hook off (configUSE_IDLE_HOOK 0). You never write the idle task yourself.

Concept 7: the kernel's memory

xTaskCreate() takes a function, a name, a stack depth, an argument, a priority and an optional handle. It allocates the stack and the TCB from the FreeRTOS heap, and makes the task ready (tasks.c line 1740). The stack depth is in words, not bytes. On the Cortex-M3 the port's StackType_t is a 32-bit word (portmacro.h), so a depth of 128 is 512 bytes.

The heap is a fixed block of RAM set by configTOTAL_HEAP_SIZE, which the template sets to 8 KiB. The build selects the allocator heap_4.c, from templates/common/stm32f1.cmake. If the heap is too small for the tasks, xTaskCreate() fails, and the template's malloc-failed hook loops forever. That is one way a project prints nothing.

Concept 8: the template's safety settings

The template's FreeRTOSConfig.h turns on checks that help you find mistakes. configCHECK_FOR_STACK_OVERFLOW is set to 2, which makes the kernel fill each stack with a pattern and check it on each switch. When it finds an overflow it calls vApplicationStackOverflowHook(), which the project defines and which loops forever, so you can attach a debugger and read the task name. configASSERT is defined to disable interrupts and loop forever, so a failed kernel check stops the device where it failed instead of corrupting memory. Both are for development. Lesson 92 shows how to size stacks so the hook never runs.

A worked example: the blink and report tasks

The project has two tasks. blink_task has priority 2 and toggles PC13 every 500 ms. report_task has priority 1 and prints a line once a second. Here is what happens at the start, and on each tick, with the numbers the code uses.

  1. At time 0, main() creates both tasks and calls vTaskStartScheduler(). The scheduler picks the highest-priority ready task, which is blink_task at priority 2.
  2. Blink toggles the LED once, then calls vTaskDelayUntil() with a period of 500 ticks. It blocks, so it leaves the ready list.
  3. Report is now the highest-priority ready task. It prints its first line, showing the tick count 0 and the toggle count 1. It then calls vTaskDelay(1000 ticks) and blocks.
  4. With both tasks blocked, the idle task runs. It does nothing useful except free memory from deleted tasks.
  5. At tick 500, xTaskIncrementTick() finds that blink's delay has ended and moves it to the ready list. Blink's priority 2 is higher than the idle task's 0, so the port pends PendSV and blink runs.
  6. Blink toggles the LED. Its next wake-up is 500 + 500 = 1000 ticks, which is the value last_wake now holds.
  7. At tick 1000, both blink and report are due. Blink has priority 2 and report has priority 1, so blink runs first. Report then prints the line with tick 1000.

Code, line by line

The solution in projects/0087-freertos-tasks/solution/main.c is the code the starter is built from. Read this block first. 

static void blink_task(void *arg) {
    (void)arg;
    TickType_t last_wake = xTaskGetTickCount();
    for (;;) {
        GPIOC->ODR ^= GPIO_ODR_ODR13;
        toggles++;
        vTaskDelayUntil(&last_wake, pdMS_TO_TICKS(BLINK_PERIOD_MS));
    }
}

static void blink_task(void *arg) matches the function type FreeRTOS expects for a task, which takes one void * argument. The static keeps the function private to this file. (void)arg; tells the compiler that the argument is deliberately unused, so the warning is silenced without hiding a real problem.

TickType_t last_wake = xTaskGetTickCount(); reads the tick count at the start of the task and stores it. This is the starting point of the schedule. The variable lives on the task's own stack, so each task has its own copy.

GPIOC->ODR ^= GPIO_ODR_ODR13; toggles the output bit for PC13. The ^= is a read-modify-write: the CPU reads the output data register, flips bit 13, and writes it back. That is safe here only because no other task writes PC13 at the same time. Lesson 91 covers what happens when two tasks share a register this way.

toggles++; counts the toggles in a global variable. The variable is declared volatile, so the compiler reads it from memory each time instead of keeping it in a register, which matters because the report task reads it too. There is one writer and one reader, and that is the only sharing in this project.

vTaskDelayUntil(&last_wake, pdMS_TO_TICKS(BLINK_PERIOD_MS)); does three things. It computes the next wake-up as last_wake + 500, blocks the task until the tick count reaches that value, and writes the new wake-up time back into last_wake. The conversion pdMS_TO_TICKS(500) returns 500 at a 1 kHz tick. 

static void report_task(void *arg) {
    (void)arg;
    for (;;) {
        uart_puts(toggles ? "TASKS OK " : "TASKS waiting ");
        uart_puts("tick=");
        uart_put_u32(xTaskGetTickCount());
        uart_puts(" toggles=");
        uart_put_u32(toggles);
        uart_puts("\r\n");
        vTaskDelay(pdMS_TO_TICKS(REPORT_PERIOD_MS));
    }
}

toggles ? "TASKS OK " : "TASKS waiting " chooses the first word by testing the shared count. The report prints "TASKS OK" once blink has toggled the LED at least once, which is the check the Try-it steps ask you to add. xTaskGetTickCount() returns the tick count, which is milliseconds here because the tick is 1 kHz. vTaskDelay() is correct for the report, because a report that drifts by a millisecond does not matter. 

int main(void) {
    SystemCoreClockUpdate();
    uart_init();
    xTaskCreate(blink_task, "blink", TASK_STACK_WORDS, NULL, BLINK_PRIORITY, NULL);
    xTaskCreate(report_task, "report", TASK_STACK_WORDS, NULL, REPORT_PRIORITY, NULL);
    vTaskStartScheduler();
    for (;;) {}
}

The clock and the UART are set up before any task is created, so that the first task can print. xTaskCreate() is called with the function, a name of at most 12 characters (configMAX_TASK_NAME_LEN), a stack of TASK_STACK_WORDS words, no argument, the priority and no handle. vTaskStartScheduler() starts the tick and the first task. It does not return in normal operation, so the endless loop after it is only a guard for the case where the idle task could not be created.

Common mistakes and how to spot them

Mistake 1: reading priorities the NVIC way. A developer gives the LED task priority 1 because "1 is more urgent", and gives the sensor task priority 3. The symptom is that the LED task keeps running while the sensor task waits, because the LED task is the higher priority. The fix is to remember that FreeRTOS priorities grow upward, and to write the intent into a named constant such as BLINK_PRIORITY, with a comment that says the higher number is more urgent.

Mistake 2: a period built with vTaskDelay(). A periodic job is written as vTaskDelay(pdMS_TO_TICKS(500)), and the team later adds 30 ms of work to the loop. The symptom is a blink that is slower than 500 ms, which shows up only once the work is added. The fix is vTaskDelayUntil() with a stored wake-up time.

Mistake 3: a delay shorter than a tick. The starter file contains a placeholder, vTaskDelay(pdMS_TO_TICKS(1U)), which makes the blink period one tick. That is the wrong period on purpose, and it is the mistake this lesson asks you to find. The symptom on a real board's LED is a light that toggles far too fast to see. A delay of 0.5 ms cannot be written at all with a 1 ms tick: the best the kernel can do is one tick.

Mistake 4: a stack too small for the task. A task is given a stack of 16 words to save memory, and it calls printf with a long format. The symptom is a stack overflow: the overflow hook runs and loops forever, and the serial monitor shows nothing after that point. The fix is to read the high-water mark (lesson 92) and enlarge the stack, not to make the hook quieter.

Mistake 5: a heap too small for the tasks. A project adds three tasks but leaves configTOTAL_HEAP_SIZE at its old value. The symptom is that the device stops before the report prints, and the malloc-failed hook is the one that loops. The fix is to raise the heap, and to check that xTaskCreate() returns pdPASS for each task during bring-up.

In real projects

Production firmware on a Cortex-M usually keeps the FreeRTOS configuration in one file, and reviews every change to it. Reviewers check the tick rate, the heap size, the stack overflow setting and the interrupt priority limit, because each one changes behaviour in every task. Priorities are written down in one table, with the reason for each level, so that a new feature can be placed without guessing.

Periodic tasks are almost always written with an absolute delay such as vTaskDelayUntil(), and a code reviewer will ask why a relative vTaskDelay() was chosen for any job that has a rate.

Summary

  • A task is a function that loops forever, with its own stack and a priority. FreeRTOS priorities grow upward: a larger number is more urgent.
  • The scheduler runs the highest-priority ready task. Equal-priority tasks take turns at each tick when time slicing is on.
  • The tick is the kernel's clock. At 1 kHz one tick is 1 ms, and every delay is a whole number of ticks.
  • vTaskDelay() counts from the call and drifts; vTaskDelayUntil() keeps an absolute schedule for periodic work.
  • The idle task runs at priority 0 when nothing else is ready. You do not write it.
  • Task stacks are in words, a word is 4 bytes on the Cortex-M3, and all stacks and task control blocks come from the heap.
  • The template's stack overflow hook and configASSERT stop the device at the first mistake, which is what you want while you are learning.
