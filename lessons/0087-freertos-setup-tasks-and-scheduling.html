FreeRTOS setup, tasks, and scheduling

Tasks, priorities and the kernel tick

By the end of this lesson you can create two or more tasks with xTaskCreate(), choose their priorities, write a periodic task with vTaskDelayUntil(), and explain the difference from vTaskDelay(), the idle task and the tick.

Building the scheduler on the Blue Pill

Lesson 86 showed the problem, a super-loop making a due job wait for every blocking call ahead of it, and a scheduler fixing that by letting a more urgent job interrupt a less urgent one. This lesson builds that scheduler on the Blue Pill, using the SysTick interrupt of lesson 73 as its heartbeat and the NVIC priority rule of lesson 72, with one important difference that the warnings below explain. Lab 5 moves the Lab 4 monitor onto FreeRTOS, so every task written here is a pattern reused there.

The project is a small piece of that design, a periodic blink task toggling the on-board LED every 500 ms while a report task prints the kernel's tick count once a second over the serial line, and a kernel that runs two such tasks correctly is the first step to a device running a sensor, a display and a log at the same time.

Tasks, stacks and task control blocks

A task is a C function that never returns, with its own stack holding its local variables and return addresses (lesson 33) and a priority. The kernel keeps a control block for each task, the TCB, recording the task's name, its priority, its stack pointer and its place in the kernel's lists, while the task itself does not know it is being shared, running as if it owned the core while the kernel saves and restores its registers whenever it stops or starts (lesson 88).

A task that does not loop forever must remove itself, as the projects of lessons 90 and 91 do by calling vTaskDelete(NULL) when a task has finished its work, whereas a task that returns from its function by accident is a bug, since the kernel has no sensible place to send it.

Task states and the ready lists

At any moment a task is in one of four states, Running when it has the core, Ready when it could run now and is waiting for the core, Blocked when it waits for a time, such as a delay, or an event, such as a queue item or a semaphore, and Suspended when another task has parked it until it is resumed. The figure below shows the moves between the states.

The kernel keeps one ready list per priority level, holding the Ready tasks of that priority, and at every decision point the scheduler finds the highest-priority list that is not empty and takes the next task from it. The kernel macro doing this is taskSELECT_HIGHEST_PRIORITY_TASK(), at tasks.c line 235 in the kernel version this course uses, V11.2.0 (the version string being in include/task.h line 56), and its loop body, in plain words, finds the highest priority with ready tasks and takes the owner of the next entry in that list, a quick search over a few lists rather than a sort.

The states resemble a taxi rank with one road out, the running task being the taxi on the road and the ready tasks waiting in the rank sorted by priority, the best leaving as soon as the road is free, while blocked tasks are taxis at the petrol station that cannot leave until their time or event comes, however high their priority, and suspended tasks are parked off duty until someone returns them to the rank. The comparison breaks on preemption, though, because a taxi on the road finishes its trip, whereas a running task can be pulled off the road the moment a higher-priority task becomes ready.

FreeRTOS task priorities

A FreeRTOS priority is a number in which a larger value is more urgent, the highest usable priority being configMAX_PRIORITIES − 1, so with configMAX_PRIORITIES set to 5 in this course's template the priorities run from 0 to 4. The idle task has priority 0, the lowest, so any ready task preempts it.

This is the opposite of the interrupt controller, on whose NVIC, as lesson 72 showed, a lower number is more urgent, and although both systems are consistent within themselves, the mismatch is a real trap. The priority passed to xTaskCreate() is a task priority following the FreeRTOS rule, while the priority given to an interrupt with NVIC_SetPriority() follows the Cortex-M rule, and lesson 90 shows where the two meet.

Priority numbers grow upward: 0 is the lowest (the idle task), and configMAX_PRIORITIES − 1 is the highest. Many bugs come from reading "priority 1" as the most urgent, which is the opposite of the NVIC rule in lesson 72, where a lower number is more urgent.

The kernel tick

The tick is the kernel's clock, a periodic interrupt here driven by the Cortex-M SysTick timer (lesson 73) and firing configTICK_RATE_HZ times per second, which the template sets to 1000, so the tick is 1 ms. The SysTick reload value is set in port.c line 759 as the SysTick clock divided by the tick rate, minus one, the same rule as in lesson 73.

On every tick the port calls xTaskIncrementTick() (tasks.c line 4725), which adds one to the kernel's tick count, swaps the delayed lists if the count wraps to zero and moves every delayed task whose time has come back to its ready list. If a woken task has a higher priority than the running one, the function reports that a switch is needed, and the SysTick handler in port.c at line 491 requests it by pending PendSV (line 507), the exception that actually performs the switch, which lesson 89 walks through.

Because only the tick wakes a delayed task, it sets the resolution of every delay, so a 1 ms tick cannot give a 0.5 ms delay. pdMS_TO_TICKS(n) converts milliseconds to ticks, defined in projdefs.h line 42 as

ticks = n × configTICK_RATE_HZ ÷ 1000(1)

where n is the delay in milliseconds and configTICK_RATE_HZ the tick rate, so at a 1 kHz tick it returns exactly n.

A task made ready by a call from another task, rather than by the tick, can also request the switch, a queue or semaphore call that wakes a higher-priority task yielding inside the call, so the switch happens before the call returns to the sender, and lesson 90 shows the interrupt version of the same rule.

With configUSE_TIME_SLICING set to 1 (the default, FreeRTOS.h line 2750), tasks of equal priority take turns at each tick. Tasks of different priority never share the CPU this way: the higher one always wins.

Relative and absolute delays

vTaskDelay(n) blocks the calling task for n ticks counted from the moment of the call (tasks.c line 2458), so if the work before it takes time, the period grows by that time and the task drifts. A task doing 30 ms of work and then calling vTaskDelay(100) each time, at 1 ms per tick, wakes 100 ms after the first call's return, runs 30 ms again and sleeps another 100 ms, a period of 130 ms that leaves it 1 300 ms into a schedule meant to be 1 000 ms long after ten cycles.

vTaskDelayUntil(&last, n) instead keeps an absolute schedule, setting the next wake-up to last + n and updating last to that time, so the 30 ms of work lies inside the 100 ms slot and the wake-ups fall at 100, 200 and 300 ms for as long as the work fits. The macro is defined in task.h at line 933, and it is the call to use for a periodic job that must keep its rate, such as a sensor read every 200 ms.

The idle task

When no task is ready, the kernel must still run something, so it has the idle task, at priority 0 (tskIDLE_PRIORITY, task.h line 199), created in prvCreateIdleTasks() (tasks.c line 3540), which vTaskStartScheduler() calls at line 3703, the xTaskCreate() call that makes it being at line 3654.

The idle task's loop is prvIdleTask() (line 5801), whose main job here is freeing the memory of deleted tasks in prvCheckTasksWaitingTermination() (line 5826). It is also where a low-power WFI instruction could go through the idle hook, although the template turns the hook off (configUSE_IDLE_HOOK 0), and you never write the idle task yourself.

Task stacks and the FreeRTOS heap

xTaskCreate() takes a function, a name, a stack depth, an argument, a priority and an optional handle, allocates the stack and the TCB from the FreeRTOS heap and makes the task ready (tasks.c line 1740). The stack depth is in words rather than bytes, the port's StackType_t being a 32-bit word on the Cortex-M3 (portmacro.h), so a depth of 128 is 512 bytes.

The heap is a fixed block of RAM set by configTOTAL_HEAP_SIZE, 8 KiB in the template, with the allocator heap_4.c selected by templates/common/stm32f1.cmake. If the heap is too small for the tasks, xTaskCreate() fails and the template's malloc-failed hook loops forever, which is one way a project ends up printing nothing.

Stack overflow checks and configASSERT

The template's FreeRTOSConfig.h turns on checks that help find mistakes. configCHECK_FOR_STACK_OVERFLOW is set to 2, so the kernel fills each stack with a pattern and checks it on each switch, calling on an overflow vApplicationStackOverflowHook(), which the project defines to loop forever so that a debugger can be attached and the task name read. configASSERT is defined to disable interrupts and loop forever, so a failed kernel check stops the device where it failed instead of corrupting memory, both being development aids, and lesson 92 shows how to size stacks so that the hook never runs.

Worked example: the blink and report tasks at start-up

The project has two tasks, blink_task at priority 2 toggling PC13 every 500 ms and report_task at priority 1 printing a line once a second, and we follow what happens at the start and on each tick with the numbers the code uses. Before reading on, predict which task runs first at tick 1000, when both are due.

  1. Start the scheduler. At time 0, main() creates both tasks and calls vTaskStartScheduler(), which picks the highest-priority ready task, blink_task at priority 2.
  2. Blink blocks. Blink toggles the LED once and calls vTaskDelayUntil() with a period of 500 ticks, blocking and leaving the ready list.
  3. Report runs. Report, now the highest-priority ready task, prints its first line with the tick count 0 and the toggle count 1, then calls vTaskDelay(1000 ticks) and blocks.
  4. Idle runs. With both tasks blocked, the idle task runs, doing nothing useful except freeing memory from deleted tasks.
  5. Tick 500. xTaskIncrementTick() finds that blink's delay has ended and moves it to the ready list, and since its priority 2 exceeds the idle task's 0, the port pends PendSV and blink runs.
  6. Blink reschedules. Blink toggles the LED, its next wake-up being 500 + 500 = 1000 ticks, the value last_wake now holds.
  7. Tick 1000. Both blink and report are due, and blink, at priority 2 against report's 1, runs first, after which report prints the line with tick 1000.

The task code line by line

The solution in projects/0087-freertos-tasks/solution/main.c is the code the starter is built from, and this block comes first. 

static void blink_task(void *arg) {
    (void)arg;
    TickType_t last_wake = xTaskGetTickCount();
    for (;;) {
        GPIOC->ODR ^= GPIO_ODR_ODR13;
        toggles++;
        vTaskDelayUntil(&last_wake, pdMS_TO_TICKS(BLINK_PERIOD_MS));
    }
}

static void blink_task(void *arg) matches the function type FreeRTOS expects for a task, one taking a single void * argument, with static keeping the function private to this file, and (void)arg; tells the compiler that the argument is deliberately unused, silencing the warning without hiding a real problem.

TickType_t last_wake = xTaskGetTickCount(); reads and stores the tick count at the start of the task, the starting point of the schedule, in a variable living on the task's own stack, so each task has its own copy.

GPIOC->ODR ^= GPIO_ODR_ODR13; toggles the output bit for PC13 with a read-modify-write, the CPU reading the output data register, flipping bit 13 and writing it back, which is safe here only because no other task writes PC13 at the same time, the case that lesson 91 covers.

toggles++; counts the toggles in a global variable declared volatile, so the compiler reads it from memory each time instead of keeping it in a register, which matters because the report task reads it too, one writer and one reader being the only sharing in this project.

vTaskDelayUntil(&last_wake, pdMS_TO_TICKS(BLINK_PERIOD_MS)); computes the next wake-up as last_wake + 500, blocks the task until the tick count reaches that value and writes the new wake-up time back into last_wake, the conversion pdMS_TO_TICKS(500) returning 500 at a 1 kHz tick. 

static void report_task(void *arg) {
    (void)arg;
    for (;;) {
        uart_puts(toggles ? "TASKS OK " : "TASKS waiting ");
        uart_puts("tick=");
        uart_put_u32(xTaskGetTickCount());
        uart_puts(" toggles=");
        uart_put_u32(toggles);
        uart_puts("\r\n");
        vTaskDelay(pdMS_TO_TICKS(REPORT_PERIOD_MS));
    }
}

toggles ? "TASKS OK " : "TASKS waiting " chooses the first word by testing the shared count, so the report prints "TASKS OK" once blink has toggled the LED at least once, the check the hands-on steps ask you to add. xTaskGetTickCount() returns the tick count, milliseconds here because the tick is 1 kHz, and vTaskDelay() suits the report, because a report drifting by a millisecond does not matter. 

int main(void) {
    SystemCoreClockUpdate();
    uart_init();
    xTaskCreate(blink_task, "blink", TASK_STACK_WORDS, NULL, BLINK_PRIORITY, NULL);
    xTaskCreate(report_task, "report", TASK_STACK_WORDS, NULL, REPORT_PRIORITY, NULL);
    vTaskStartScheduler();
    for (;;) {}
}

The clock and the UART are set up before any task is created, so that the first task can print, and xTaskCreate() is called with the function, a name of at most 12 characters (configMAX_TASK_NAME_LEN), a stack of TASK_STACK_WORDS words, no argument, the priority and no handle. vTaskStartScheduler() starts the tick and the first task and does not return in normal operation, so the endless loop after it only guards the case where the idle task could not be created.

Common mistakes and how to spot them

Task priorities read the NVIC way

The LED task, meant to be the most urgent, waits while the sensor task runs, because a developer gave the LED task priority 1, reading "1 is more urgent" in the NVIC way, and the sensor task priority 3, which in FreeRTOS makes the sensor task the higher priority. Remember that FreeRTOS priorities grow upward, and write the intent into a named constant such as BLINK_PRIORITY with a comment saying that the higher number is more urgent.

A period built with vTaskDelay

The blink becomes slower than 500 ms once the team adds 30 ms of work to the loop, because the periodic job was written as vTaskDelay(pdMS_TO_TICKS(500)), which counts from the call. Use vTaskDelayUntil() with a stored wake-up time.

A delay shorter than a tick

On a real board the LED toggles far too fast to see, because the starter's placeholder vTaskDelay(pdMS_TO_TICKS(1U)) makes the blink period one tick, the wrong period on purpose and the mistake this lesson asks you to find. A delay of 0.5 ms cannot be written at all with a 1 ms tick, the best the kernel can do being one tick.

A stack too small for the task

The serial monitor shows nothing after a certain point, because a task given a 16-word stack to save memory called printf with a long format, overflowed its stack and sent the overflow hook into its endless loop. Read the high-water mark (lesson 92) and enlarge the stack rather than quietening the hook.

A heap too small for the tasks

The device stops before the report prints, with the malloc-failed hook looping, because a project added three tasks but left configTOTAL_HEAP_SIZE at its old value. Raise the heap and check during bring-up that xTaskCreate() returns pdPASS for each task.

FreeRTOS configuration and priority tables in production

Production firmware on a Cortex-M usually keeps the FreeRTOS configuration in one file and reviews every change to it, checking the tick rate, the heap size, the stack overflow setting and the interrupt priority limit, because each changes the behaviour of every task. Priorities are written down in one table with the reason for each level, so that a new feature can be placed without guessing.

Periodic tasks are almost always written with an absolute delay such as vTaskDelayUntil(), and a reviewer will ask why a relative vTaskDelay() was chosen for any job that has a rate.

Summary

  • A task is a function that loops forever with its own stack and a priority, and FreeRTOS priorities grow upward, a larger number being more urgent.
  • The scheduler runs the highest-priority ready task, and equal-priority tasks take turns at each tick when time slicing is on.
  • The tick is the kernel's clock, at 1 kHz one tick being 1 ms, and every delay is a whole number of ticks.
  • vTaskDelay() counts from the call and drifts, whereas vTaskDelayUntil() keeps an absolute schedule for periodic work.
  • The idle task runs at priority 0 when nothing else is ready, and you do not write it.
  • Task stacks are sized in words of 4 bytes on the Cortex-M3, and all stacks and task control blocks come from the heap.
  • The template's stack overflow hook and configASSERT stop the device at the first mistake, which is what you want while learning.
