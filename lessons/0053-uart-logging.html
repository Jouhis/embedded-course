UART logging

Serial output from firmware and its cost in time

By the end of this lesson you can compute the UART baud divisor from clk_peri, check it against the hardware register, and write a levelled log macro that skips filtered messages before it evaluates them.

Logging as a debugging tool

Lesson 51 drove pins from the SIO and lesson 52 read a button through a pull-up, both single digital levels on one wire. A UART carries a whole byte per frame on the same kind of pins, so the GPIO knowledge carries over, while lesson 46's volatile matters for the flag registers read below and lesson 45's fixed-width integers for the divisor arithmetic.

Logging is the first tool engineers reach for when a product misbehaves in the field, whether a printer stops mid-job, a sensor reads a strange value or a motor controller resets once an hour, because a log line shows what the code did and when. The catch is that the log itself takes time, and in an embedded system time is often the very thing being measured, so firmware engineers learn both how to log and how a log can change the bug it was meant to find.

UART frames and the baud rate

A UART is a universal asynchronous receiver/transmitter, whose transmitter turns a parallel byte into a stream of bits and whose receiver turns the stream back into a byte. Asynchronous means that there is no clock wire, so both ends agree on the bit rate in advance and each frame starts with an edge that tells the receiver when to begin, which is how the RP2040 datasheet describes its PL011-style UART (RP2040 datasheet §4.2.1).

A UART uses two data wires, one per direction, TX carrying bits out of the chip and RX carrying them in. The idle line is held high, and a frame begins with a low start bit, whose falling edge tells the receiver where the bits start, followed by eight data bits, least significant first, and a high stop bit that returns the line to idle. This layout is written 8N1, for eight data bits, no parity and one stop bit, which puts ten bits on the wire for every byte.

The baud rate is the number of bit periods per second, so at 115 200 baud each bit lasts 1 ÷ 115 200 s, about 8.68 µs. Both ends must agree on it, or the receiver samples the bits at the wrong moments and reads garbage, but because the receiver samples near the middle of each bit period, it tolerates a small timing error, though not a large one. A UART's TX line goes to the receiver's RX line, and the grounds must be joined. Wiring TX to TX is the most common wiring error.

The RP2040 UART and its FIFOs

The RP2040 has two UART instances, UART0 and UART1, each with a transmit and a receive FIFO, a first in, first out (FIFO) buffer being a small hardware queue. The transmit FIFO is 8 bits wide and 32 locations deep and the receive FIFO 12 bits wide and 32 deep, the extra 4 bits of each receive entry holding error flags, three for framing, parity and break errors and one for overrun (§4.2.2.4, §4.2.2.5 and §4.2.3.2.3).

The FIFOs let the CPU hand over a burst of bytes and move on while the UART shifts them out at the baud rate, and the CPU sees the FIFO's state through the flag register. For logging the relevant flags in UARTFR are TXFF, bit 5, set when the transmit FIFO is full, BUSY, bit 3, set while the UART is still sending, and TXFE, bit 7, set when the transmit FIFO is empty (§4.2, UARTFR register).

The UART's registers sit at fixed offsets from its base address, as the SIO registers did in lesson 51, and this lesson uses UARTDR at offset 0x000, the data register, UARTFR at 0x018, the flag register, UARTIBRD at 0x024 and UARTFBRD at 0x028, the baud divisors, and UARTLCR_H at 0x02C, the line control register. Writing a byte to UARTDR places it in the transmit FIFO, which is all that printf ultimately does.

The UART's pins are routed through the GPIO function select, UART0 transmit being function 2 on GP0 and UART0 receive function 2 on GP1 (§2.19.2, Table 279). The SDK sets this up in stdio_init_all(), which is why the starter can print without any UART code.

The peripheral clock clk_peri

The UART has its own reference clock, UARTCLK, which on the RP2040 is driven from clk_peri, the peripheral clock, rather than directly from the CPU clock, and the baud rate is derived by dividing it, as the datasheet states (§4.2.7.1). The required divisor therefore depends on the clock frequency the SDK configured at boot, 125 MHz for the Pico SDK's default system clock, and a project that changes the system clock must recompute the divisor or the baud rate will be wrong.

The UART also has a second clock, PCLK, the bus clock through which the CPU reaches the registers. The two clocks are separate, with a constraint between them given in the datasheet, but for this lesson the important point is that the divisor follows UARTCLK rather than the bus.

The fractional baud divisor

The UART obtains its bit period by dividing its reference clock, and a whole-number divider cannot hit every baud rate exactly: 125 MHz divided by 16 times 115 200 is 67.8 rather than a whole number, so a plain integer divider would give a slightly wrong bit period. The PL011 solves this with a fractional divider, dividing by an integer part plus a fraction, and the divisor is

BRD = UARTCLK ÷ (16 × baud)(1)

where UARTCLK is the reference clock frequency and baud the target rate. The factor 16 gives the UART 16 internal ticks per bit, the tick, called Baud16, running at 16 times the baud rate, with the divisor chosen so that Baud16 has the right period (§4.2.3.2.1).

The integer part goes into UARTIBRD, a 16-bit register, and the fraction into the 6-bit UARTFBRD, computed as

FBRD = ⌊frac(BRD) × 64 + 0.5⌋(2)

where frac(BRD) is the fractional part of the divisor and the added 0.5 rounds to the nearest step (§4.2.3.2.1). The fraction moves in steps of 1/64, so the rounding error is at most half a step, 1/128 of a unit, which for a divisor near 68 is about 0.01 %, small enough at the standard rates that the link works. The factor 64 is 26, the width of UARTFBRD, and multiplying by it turns the fraction into an integer that can be stored, so the whole divisor fits in one number scaled by 64.

Worked example: 115 200 baud at 125 MHz

We take the datasheet's own example, with UARTCLK at 125 MHz and a target of 115 200 baud. Before working through it, estimate how far from 115 200 the generated rate will land.

  1. Compute the divisor. Equation (1) gives 125 × 106 ÷ (16 × 115 200) = 125 000 000 ÷ 1 843 200 ≈ 67.817, so UARTIBRD is 67 and the fractional part is 0.817.
  2. Compute the fraction. Equation (2) multiplies 0.817 by 64, giving 52.29, adds 0.5 to reach 52.79 and takes the integer part, so UARTFBRD is 52 and the hardware divides by 67 + 52/64 = 67.8125.
  3. Check the rate. The generated baud rate is 125 000 000 ÷ (16 × 67.8125) ≈ 115 207, an error of 7 parts in 115 200, or about 0.006 %, far inside the tolerance of a receiver that samples near the middle of each bit, which is why the rounding is good enough.
  4. Use integers only. Multiplying everything by 64 gives total64 = 64 × divisor = 4 × clk / baud, here 4 × 125 000 000 ÷ 115 200 ≈ 4 340.28, which rounds to 4 340, and 4 340 ÷ 64 is 67 remainder 52, the quotient being UARTIBRD and the remainder UARTFBRD.

Both values thus come from integer arithmetic alone, which is why the code avoids floating point: the Cortex-M0+ core has no floating-point unit (see the Arm Cortex-M0+ datasheet in the course resources), so every float operation would be a library call. 

/* Integer-only divisor, in 64ths: total64 = 64 * clk / (16 * baud) = 4 * clk / baud */
uint32_t total64 = (4u * clk_hz + baud / 2u) / baud;   /* + baud/2 rounds to nearest */
uint32_t ibrd  = total64 / 64u;                        /* UARTIBRD: 67 for 115200 at 125 MHz */
uint32_t fbrd  = total64 % 64u;                        /* UARTFBRD: 52 */

The first line computes total64, the whole divisor in 64ths, from the numerator 4u * clk_hz, which is 64 × clk over 16 × baud cancelled to 4 × clk over baud. The suffix u makes the constant unsigned, so the arithmetic stays unsigned throughout, and the numerator of about 5 × 108 fits in a 32-bit unsigned integer here, although a faster clock would eventually overflow it, as the hint below explains how to check.

The baud / 2u term performs the rounding, because adding half the divisor before the integer division turns truncation into rounding to nearest, whereas without it the result would always round down and the fraction could be off by up to one step.

The second line takes the integer part, total64 / 64u, a division by 64 equivalent to a right shift by 6, giving 67, and the third takes the remainder, total64 % 64u, the fraction 52. Writing these two values to UARTIBRD and UARTFBRD sets the bit period.

The Pico SDK does the same job in uart_set_baudrate() with a slightly different scheme, a factor of 8 and one extra bit of rounding, but for 115 200 baud at 125 MHz it writes the same 67 and 52 (pico-sdk 2.3.1, uart.c). It then makes a dummy write to UARTLCR_H, because the PL011 latches a new divisor only on a line-control write, so a driver that writes the divisor without that step can keep running at the old rate until the next format change. The code in this lesson checks its result against the two registers.

Blocking output in printf

On the Pico the characters of printf, the standard output function, go through the SDK's stdio layer, which sends each with uart_putc(), a call that waits for room in the transmit FIFO and then writes the byte to UARTDR (pico-sdk 2.3.1, uart.h). The FIFO absorbs a burst, but once it is full, printf waits for the wire to drain while the CPU does nothing useful.

The wire is slow, because the time to send n characters is

t = n × 10 ÷ baud(3)

where 10 is the number of bits per 8N1 frame, so one byte takes 10 ÷ 115 200 ≈ 87 µs and a 40-character line about 3.5 ms. If the FIFO is nearly full when the line starts, the CPU is held for most of that time, so a timer interrupt that does 1 ms of its own work and then logs one line can miss its next deadline. Never call printf from an interrupt handler or in a tight loop with real-time work; lesson 57 covers the rules for interrupt handlers and lesson 55 deadlines in more detail.

At 115 200 baud an 80-character log line takes about 7 ms on the wire, and once the TX FIFO is full, printf waits for it, so a motor controller that logs one line per control step can run its loop seven times slower than planned. Production code therefore logs less often, or hands the text to an interrupt or DMA.

The same effect can hide the bug under investigation, which the next box turns into a rule.

Logging that works on the bench can change the timing you are trying to measure. If you suspect a timing bug, log into a RAM buffer and print it later, or print a single flag, and check the result again without the log.

A levelled log macro

A log macro with levels keeps DEBUG lines in the code while one constant turns them off. Each line has a severity, error, warning, info or debug, and the program sets a threshold above which messages are dropped, so changing the threshold from info to error removes every info and debug line from the output without touching any source line.

The macro is written with the preprocessor, so the level test happens at the call site and the arguments are evaluated only where the macro body uses them. Placing the level check first inside the macro makes a filtered message cost one comparison, with its arguments never evaluated. 

#define LOG(level, ...)                          \
    do {                                       \
        if ((level) <= LOG_LEVEL) {            \
            printf("[%c] ", log_tag(level));    \
            printf(__VA_ARGS__);                  \
            printf("\n");                      \
        }                                         \
    } while (0)

The first line defines LOG with two parameters, level and ..., which collects everything else, and the trailing backslashes join the physical lines into one logical line, as macros require.

The do keyword opens a block that runs once, and the if compares the level with LOG_LEVEL, the levels being numbered from 0 for error to 3 for debug, so a message prints when its number is at most the threshold. The three printf lines print the tag, the message and the newline, and while (0) closes the block and makes the whole macro one statement, without which if (x) LOG(...); else ... would not parse, because the semicolon after the macro would end the if early.

__VA_ARGS__ is replaced by the arguments after the level, a feature of C99 that is valid in the C11 used in this course (cppreference, replacement of macros).

A macro's argument list is text, evaluated only where the macro body uses it, here inside the if. A dropped LOG_LEVEL_DEBUG line therefore never calls the function that builds its arguments, so an expensive expression in a debug line costs nothing while the level is off.

Common mistakes and how to spot them

A baud rate that does not match the clock

The serial monitor shows random characters or nothing at all, because the system clock was changed to 48 MHz in one file while the divisor was still computed for 125 MHz, so the receiver samples at the wrong moments. Compute the divisor from clock_get_hz(clk_peri) at run time, as the lesson's code does, and print it so that it can be checked.

A bare block macro that breaks an if

The compiler reports an else without if at a line that looks correct, because LOG was defined as a bare block in braces and the semicolon after it ends the if. Wrap the body in do { ... } while (0), as the macro here does.

A side effect inside a filtered message

The program behaves differently with debug logging off, although the logged values look right with it on, because LOG(LOG_LEVEL_DEBUG, "n=%d", next_value()) does not call next_value() at all at the INFO level, so the variable never advances. Keep side effects out of log arguments, or compute them before the call when they must always happen.

A log in a real-time path

The tick counter drifts and the serial monitor shows gaps between lines, because a printf was placed in the timer interrupt to see it firing. Set a flag in the interrupt and print from the main loop.

TX wired to TX

The program runs but the serial monitor stays blank, because the chip's TX pin was connected to the monitor's TX, so the chip's output never reaches the monitor's input. Connect TX to RX and RX to TX with a common ground; the lesson's diagram is already correct, so compare any changed wiring with it.

Logging modules in production firmware

Production firmware usually has a logging module rather than scattered printf calls, with levels, a per-module filter and a buffer. Writes go into a RAM ring buffer that a low-priority task or the idle loop drains to the UART, so a log call costs a few stores instead of wire time, and each entry carries a timestamp so that the timeline can be rebuilt after a field failure. Many products also keep a binary log with compact codes in place of text, which takes fewer bytes on the wire and is faster to write.

A code reviewer checks that each log call is safe in the context where it runs, that a filtered message avoids evaluating its arguments, and that the baud rate or divisor is derived from the clock rather than typed in as a magic number. A senior engineer also asks how logging is turned off for production, because a debug build that prints from a timer will fail a timing test that the release build passes.

Summary

  • A UART sends 8N1 frames of a low start bit, eight data bits and a high stop bit, ten bits per byte.
  • The RP2040 has two UARTs with 32-entry FIFOs, the transmit FIFO 8 bits wide and the receive FIFO 12 bits wide to hold error flags.
  • The baud divisor is UARTCLK / (16 × baud), with the integer part in UARTIBRD and the 6-bit fraction in UARTFBRD.
  • For 115 200 baud at 125 MHz the ideal divisor is about 67.817, so UARTIBRD is 67, UARTFBRD is 52 and the hardware divides by 67 + 52/64 = 67.8125.
  • printf waits for FIFO room, so a log in an interrupt can stall the code it is meant to observe.
  • A levelled LOG macro checks the level first, so its arguments are not evaluated when the message is filtered out.
