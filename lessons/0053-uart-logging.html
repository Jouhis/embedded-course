UART logging

A serial line is the cheapest way to see what firmware is doing. It is also slow enough that a careless printf can stall the code it is meant to observe. This lesson shows both sides, and how the baud rate is set in the registers.

By the end of this lesson you can compute the UART baud divisor from clk_peri, check it against the hardware register, and write a levelled log macro that skips filtered messages before it evaluates them.

The idea

A UART sends one byte as a start bit, eight data bits and a stop bit, with no parity in the usual 8N1 setting. That is ten bits on the wire, sent at the baud rate. The RP2040 has two UART instances. Each has a 32-entry transmit FIFO and a 32-entry receive FIFO, and each receive entry carries 4 error bits with its byte (§4.2.1). The FIFOs let the CPU hand over a burst of bytes and move on. The UART clock is clk_peri, not the CPU clock. The baud rate comes from dividing clk_peri, so the divisor depends on the clock you configured (§4.2.7.1).

The baud divisor

The baud generator divides UARTCLK by 16 times the baud rate. The divisor has a 16-bit integer part, written to UARTIBRD, and a 6-bit fraction, written to UARTFBRD. The fraction is the fractional part times 64, rounded: m = int(frac × 64 + 0.5) (§4.2.3.2.1).

The datasheet's worked example uses 115200 baud with UARTCLK at 125 MHz. The divisor is 125 × 10⁶ ÷ (16 × 115200) ≈ 67.817. The integer part is 67, and the fraction 0.817 × 64 + 0.5 rounds to 52. The generated divisor is 67 + 52/64 = 67.8125, which gives a baud rate within 0.006 % of the target (§4.2.7.1). Each registers' value is in 64ths, so the whole divisor is one integer: total64 = 64 × divisor. That is the trick the code below uses, and it avoids floating point on a chip that has no FPU. 

/* Integer-only divisor, in 64ths: total64 = 64 * clk / (16 * baud) = 4 * clk / baud */
uint32_t total64 = (4u * clk_hz + baud / 2u) / baud;   /* + baud/2 rounds to nearest */
uint32_t ibrd  = total64 / 64u;                        /* UARTIBRD: 67 for 115200 at 125 MHz */
uint32_t fbrd  = total64 % 64u;                        /* UARTFBRD: 52 */

The Pico SDK does the same job in uart_set_baudrate(). It writes UARTIBRD and UARTFBRD, then does a dummy write to UARTLCR_H, because the PL011 latches the divisor only on a line-control write (pico-sdk 2.3.1, uart.c). The code in this lesson checks its own result against those two registers.

printf is blocking

The stdio driver sends each character with uart_putc(). That call spins on the transmit-full flag until the byte fits in the FIFO (pico-sdk 2.3.1, uart.h). The FIFO absorbs a burst, but once it is full, printf waits for the wire to empty.

The wire is slow. One byte takes 10 ÷ 115200 ≈ 87 µs. A 40-character line therefore takes about 3.5 ms of wire time, and the CPU is busy for all of it if the FIFO is full. A timer interrupt that runs for 1 ms of its own work and then logs one line can miss its next deadline. Never call printf from an interrupt handler, and never in a tight loop that has real-time work. Lesson 57 covers ISR rules, and lesson 55 covers deadlines.

Logging that works on the bench can change the timing you are trying to measure. If you suspect a timing bug, log into a buffer in RAM and print it later, or print a single flag, and check the result again without the log.

A levelled log macro

A log macro with levels lets you keep DEBUG lines in the code and turn them off with one constant. Put the level check first, inside the macro, so a filtered message costs one comparison, and its arguments are never evaluated. 

#define LOG(level, ...)                          \
    do {                                       \
        if ((level) <= LOG_LEVEL) {            \
            printf("[%c] ", log_tag(level));    \
            printf(__VA_ARGS__);                  \
            printf("\n");                      \
        }                                         \
    } while (0)

The do { ... } while (0) wrapper makes the macro behave as one statement, so if (x) LOG(...); else ... still parses. The __VA_ARGS__ form is C99, and it is valid in the C11 this course uses. cppreference, replacement of macros

The argument list of a macro is text, and it is evaluated only where the macro body uses it. Here that is inside the if. A dropped LOG_LEVEL_DEBUG line never calls the function that builds its arguments, so a costly expression in a debug line is free when the level is off.

Hint for the macro

The starter already provides log_tag(), which turns a level into a letter. The macro needs two printf calls for the message and one for the newline. Use __VA_ARGS__ for the message. Look at the solution's macro if you want to compare.

Hint for the divisor

With clk_hz at 125 000 000 and baud at 115 200, 4 * clk_hz fits in 32 bits. Add baud / 2 before dividing, so the division rounds to nearest. Then split the result into / 64 and % 64.

The reference solution is in projects/0053-uart-logging/solution. Try first, compare after. It also reads UARTIBRD and UARTFBRD back from the hardware and prints a warning if they differ from your calculation.

Model answer

A UART write is blocking. When the transmit FIFO is full, the call spins until bytes leave at the baud rate, and at 115200 that is about 87 µs per byte, so a long line can hold the ISR for milliseconds. I'd move the logging out of the ISR: the ISR records a value or sets a flag, and the main loop prints it. If the output must come from the ISR, I'd write to a RAM ring buffer and drain it from the main loop, or raise the baud rate and keep the lines short. I'd also check the fix against the deadline, since logging itself can change the timing I'm measuring.

RP2040 datasheet, section 4.2 (UART): read 4.2.1 for the FIFO sizes, 4.2.3.2.1 for the divisor, and 4.2.7.1 for the worked 115200 example. Then open uart_set_baudrate() in the Pico SDK source to see the same arithmetic in code.
