UART logging

A serial line is the cheapest way to see what firmware is doing. It is also slow enough that a careless printf can stall the code it is meant to observe. This lesson shows both sides, and how the baud rate is set in the registers.

By the end of this lesson you can compute the UART baud divisor from clk_peri, check it against the hardware register, and write a levelled log macro that skips filtered messages before it evaluates them.

Where we are and why it matters

Lesson 51 drove pins from the SIO, and lesson 52 read a button through a pull-up. Both were digital levels, one wire, one bit. A UART carries a whole byte per frame, and it does it on the same kind of pins, so the GPIO knowledge carries over. Lesson 46 introduced volatile, which matters for the flag registers you will read below, and lesson 45 covered the fixed-width integers that the divisor arithmetic uses.

Logging is the first tool you reach for when a product misbehaves in the field. A printer stops mid-job, a sensor reads a strange value, a motor controller resets once an hour. A log line tells you what the code did and when. The catch is that the log itself takes time, and in an embedded system time is what you are measuring. Firmware engineers therefore learn both how to log and how a log can change the bug it was meant to find.

What a UART is

A UART is a universal asynchronous receiver/transmitter. Each word is the abbreviation for one part of the job. The transmitter turns a parallel byte into a stream of bits. The receiver turns the stream back into a byte. Asynchronous means that there is no clock wire, so both ends agree on the bit rate in advance, and each frame starts with an edge that tells the receiver when to begin. The RP2040 datasheet describes the peripheral as a PL011-style UART that works in this way (RP2040 datasheet §4.2.1).

A UART uses two signal wires for data, one for each direction. TX carries the bits out of the chip, and RX carries bits in. When the line is idle, the transmitter holds it high. A frame begins with a start bit, which is low, so the receiver sees a falling edge and knows where the bits start. Eight data bits follow, least significant bit first. Then comes a stop bit, which is high, so the line returns to idle. This layout is written 8N1: eight data bits, no parity, one stop bit. That is ten bits on the wire for each byte.

The baud rate is the number of bit periods per second. At 115200 baud, each bit lasts 1 ÷ 115200 seconds, which is about 8.68 µs. Both ends must agree on it, or the receiver samples the bits at the wrong moments and reads garbage. The receiver samples near the middle of each bit period, so a small timing error is tolerated, but a large one is not.

A UART's TX line goes to the receiver's RX line, and the grounds must be joined. Crossing the wires over is the most common wiring error: TX connects to RX, never to TX.

The chip's UART and its FIFOs

The RP2040 has two UART instances, UART0 and UART1. Each one has a transmit FIFO and a receive FIFO. A first in, first out (FIFO) buffer is a small queue in hardware. The transmit FIFO is 8 bits wide and 32 locations deep. The receive FIFO is 12 bits wide and 32 locations deep. The extra 4 bits in each receive entry are error flags: three flags for framing, parity and break errors, and one overrun flag (§4.2.2.4, §4.2.2.5 and §4.2.3.2.3).

The FIFOs let the CPU hand over a burst of bytes and move on. The UART shifts them out at the baud rate while the CPU runs other code. The CPU sees the state of the FIFO through the flag register. Two flags matter for logging. TXFF, the transmit FIFO full flag, is bit 5 of UARTFR, and it is set when no room is left. BUSY, bit 3, is set while the UART is still sending. TXFE, bit 7, is set when the transmit FIFO is empty (§4.2, UARTFR register).

The UART's registers sit at fixed offsets from the UART base address, in the same way the SIO registers sit from its base in lesson 51. The ones this lesson uses are UARTDR at offset 0x000, which is the data register; UARTFR at 0x018, the flag register; UARTIBRD at 0x024 and UARTFBRD at 0x028, the baud divisors; and UARTLCR_H at 0x02C, the line control register. Writing a byte to UARTDR puts it in the transmit FIFO, and that is all printf ultimately does.

The UART's pins are routed through the GPIO function select. On the RP2040 the UART0 transmitter is function 2 on GP0, and UART0 receive is function 2 on GP1 (§2.19.2, Table 279). The SDK sets this up for you in stdio_init_all(), which is why the starter can print without any UART code.

The clock: clk_peri, not the CPU clock

The UART has its own reference clock, called UARTCLK. On the RP2040 it is driven from clk_peri, the peripheral clock, and not from the CPU clock directly. The baud rate is derived by dividing this clock, so the divisor you need depends on the clock frequency that the SDK configured at boot. The Pico SDK's default system clock is 125 MHz, but a project that changes the system clock has to recompute the divisor, or the baud rate will be wrong. The datasheet gives the same rule: the baud rate is derived from dividing clk_peri (§4.2.7.1).

The UART also has a second clock, PCLK, which is the bus clock that the CPU uses to reach the registers. The two clocks are separate, and a constraint between them is written in the datasheet. For this lesson, the important point is that the divisor follows UARTCLK, not the bus.

The baud divisor, from first principles

The UART needs a bit period. It gets one by dividing its reference clock. A divider that divides by a whole number cannot hit every baud rate exactly. For example, 125 MHz divided by 16 times 115200 is 67.8 and not a whole number, so a plain integer divider would give a slightly wrong bit period. The PL011 solves this with a fractional divider, which divides by an integer part and a fraction.

The divisor is computed from the formula Baud Rate Divisor = UARTCLK / (16 × Baud Rate). The factor 16 gives the UART 16 internal ticks per bit. The tick, called Baud16, runs at 16 times the baud rate, and the divisor is set so that Baud16 has the right period (§4.2.3.2.1). Each tick is one UARTCLK period.

The integer part goes to UARTIBRD, a 16-bit register. The fraction is a 6-bit value written to UARTFBRD. You get it by taking the fractional part of the divisor, multiplying by 64, and adding 0.5 so the number rounds to nearest (§4.2.3.2.1). The fraction moves in steps of 1/64, so the rounding error is at most half a step, which is 1/128 of the divisor's unit. For a divisor near 68 that is about 0.01 %. The error decides whether the link works, and the datasheet keeps it small for the standard rates.

The factor 64 is 2 to the power of 6, the width of UARTFBRD. The reason to multiply by it is that the fraction becomes an integer you can store, and the whole divisor fits in one number scaled by 64.

A worked example: 115200 baud at 125 MHz

Take the example the datasheet uses, with UARTCLK at 125 MHz and a target of 115200 baud. First compute the divisor: 125 × 106 ÷ (16 × 115200) = 125 000 000 ÷ 1 843 200, which is about 67.817. The integer part is 67, so UARTIBRD is 67. The fractional part is 0.817.

Next, the fraction. Multiply 0.817 by 64, which gives 52.29. Add 0.5 and take the integer part: 52.79 becomes 52. So UARTFBRD is 52. The divisor the hardware actually uses is 67 + 52/64 = 67.8125.

Check the result. The generated baud rate is 125 000 000 ÷ (16 × 67.8125), which is about 115207. The error against 115200 is 7 parts in 115200, or about 0.006 %. A link at 0.006 % error is far inside the tolerance of a receiver, which samples near the middle of each bit. That is why the rounding is good enough.

Now the integer version that the code uses. Multiplying everything by 64 gives total64 = 64 × divisor = 4 × clk / baud. For this example that is 4 × 125 000 000 ÷ 115200, which is about 4340.28, and rounding to nearest gives 4340. Split that into 4340 ÷ 64 = 67 remainder 52. The quotient is UARTIBRD, and the remainder is UARTFBRD. You get both values with integer arithmetic only, which is why the code avoids floating point. The Cortex-M0+ core has no floating-point unit (see the Arm Cortex-M0+ datasheet in the course resources), so each float operation would be a library call. 

/* Integer-only divisor, in 64ths: total64 = 64 * clk / (16 * baud) = 4 * clk / baud */
uint32_t total64 = (4u * clk_hz + baud / 2u) / baud;   /* + baud/2 rounds to nearest */
uint32_t ibrd  = total64 / 64u;                        /* UARTIBRD: 67 for 115200 at 125 MHz */
uint32_t fbrd  = total64 % 64u;                        /* UARTFBRD: 52 */

Line by line. The first line computes total64, the whole divisor in 64ths. The expression 4u * clk_hz is the numerator. It is 64 × clk divided by 16 × baud, cancelled to 4 × clk over baud. The suffix u makes the constant unsigned, so the arithmetic is unsigned all the way down. The numerator is about 5 × 108 here, which fits in a 32-bit unsigned integer. A faster clock would eventually overflow it, and the hint below shows how to check.

The baud / 2u term is the rounding. Adding half the divisor before the integer division turns truncation into rounding to nearest. Without it, the result would always round down, and the fraction would be off by up to one step.

The second line takes the integer part. total64 / 64u divides by 64, which is the same as shifting right by 6, and the result is 67. The third line takes the remainder, total64 % 64u, which is the fraction, 52. Those two values are what the hardware needs. Writing them to UARTIBRD and UARTFBRD sets the bit period.

The Pico SDK does the same job in uart_set_baudrate(). It uses a slightly different scheme, with a factor of 8 and one bit of extra rounding, but for 115200 at 125 MHz it writes the same 67 and 52 (pico-sdk 2.3.1, uart.c). It then does a dummy write to UARTLCR_H, because the PL011 latches the new divisor only on a line-control write. That dummy write is a real step, and a driver that writes the divisor without it can run at the old rate until the next format change. The code in this lesson checks its own result against those two registers.

printf is blocking

printf is the standard output function. On the Pico, its characters go through the SDK's stdio layer, which sends each one with uart_putc(). That call waits for the transmit FIFO to have room, and then writes the byte to UARTDR (pico-sdk 2.3.1, uart.h). The FIFO absorbs a burst, but once it is full, printf waits for the wire to empty. The CPU does nothing useful during that wait.

The wire is slow. One byte takes 10 ÷ 115200 ≈ 87 µs, so a 40-character line takes about 3.5 ms of wire time. If the FIFO is nearly full when the line starts, the CPU is held for most of that time. A timer interrupt that runs for 1 ms of its own work and then logs one line can miss its next deadline. Never call printf from an interrupt handler, and never in a tight loop that has real-time work. Lesson 57 covers the rules for interrupt handlers, and lesson 55 covers deadlines in more detail.

Logging that works on the bench can change the timing you are trying to measure. If you suspect a timing bug, log into a buffer in RAM and print it later, or print a single flag, and check the result again without the log.

A levelled log macro

A log macro with levels lets you keep DEBUG lines in the code and turn them off with one constant. Each line has a severity: error, warning, info or debug. The program sets a threshold, and any message above the threshold is dropped. Changing the threshold from info to error removes every info and debug line from the build's output, and no source lines need to change.

The macro is written with the preprocessor, so the level test happens at the call site, and the arguments are only evaluated where the macro body uses them. Put the level check first, inside the macro, so a filtered message costs one comparison, and its arguments are never evaluated. 

#define LOG(level, ...)                          \
    do {                                       \
        if ((level) <= LOG_LEVEL) {            \
            printf("[%c] ", log_tag(level));    \
            printf(__VA_ARGS__);                  \
            printf("\n");                      \
        }                                         \
    } while (0)

Read the macro one line at a time. The first line defines LOG with two parameters: level, and ..., which collects everything else. The trailing backslash joins the physical lines into one logical line, which is how macros must be written.

The do keyword opens a block that runs once. The if line compares the level with LOG_LEVEL. The levels are numbered from 0 (error) to 3 (debug), so a message prints when its number is less than or equal to the threshold. The three printf lines print the tag, the message, and the newline. The while (0) closes the block, and it makes the whole thing one statement. Without that wrapper, an if (x) LOG(...); else ... would not parse, because the semicolon after the macro would end the if early.

The __VA_ARGS__ word is replaced by the arguments after the level. It is part of C99, and it is valid in the C11 this course uses (cppreference, replacement of macros).

The argument list of a macro is text, and it is evaluated only where the macro body uses it. Here that is inside the if. A dropped LOG_LEVEL_DEBUG line never calls the function that builds its arguments, so a costly expression in a debug line is free when the level is off.

Common mistakes and how to spot them

Mistake 1: a baud rate that does not match the clock. You change the system clock to 48 MHz in one file and leave the divisor computed for 125 MHz. Symptom: the serial monitor shows random characters, or nothing at all. The receiver samples at the wrong moments. Fix: compute the divisor from clock_get_hz(clk_peri) at run time, as the lesson's code does, and print it so you can check it.

Mistake 2: a bare block macro that breaks an if. You define LOG as a bare block with braces, and an if with an else does not compile. Symptom: a compiler error about else without if, pointing at a line that looks correct. Fix: wrap the body in do { ... } while (0), as the macro here does.

Mistake 3: a side effect inside a filtered message. You write LOG(LOG_LEVEL_DEBUG, "n=%d", next_value()), and you expect next_value() to run every time. At the INFO level it does not run at all, so the variable never advances. Symptom: the value in the log is correct when debug is on, and the program behaves differently when it is off. Fix: keep side effects out of log arguments, or compute them before the call when they must always happen.

Mistake 4: a log in a real-time path. You put a printf in the timer interrupt to see it firing. Symptom: the tick counter drifts, and the serial monitor shows lines with gaps. Fix: set a flag in the interrupt, and print from the main loop.

Mistake 5: TX wired to TX. You connect the chip's TX pin to the serial monitor's TX, and nothing appears. Symptom: the program runs, but the serial monitor stays blank, and the wire from the chip never reaches the monitor's input. Fix: TX goes to RX and RX goes to TX, with a common ground. The lesson's diagram already has this correct, so compare any wiring you change with it.

The starter already provides log_tag(), which turns a level into a letter. The macro needs two printf calls for the message and one for the newline. Use __VA_ARGS__ for the message. Look at the solution's macro if you want to compare.

Hint for the divisor

With clk_hz at 125 000 000 and baud at 115 200, 4 * clk_hz fits in 32 bits. Add baud / 2 before dividing, so the division rounds to nearest. Then split the result into / 64 and % 64.

In real projects

Production firmware usually has a logging module, not scattered printf calls. The module has levels, a per-module filter, and a buffer. Writes go into a RAM ring buffer, and a low-priority task or the idle loop drains the buffer to the UART. A log call then costs a few stores, not a wire time. Engineers add timestamps to each entry, so the timeline can be rebuilt after a field failure. Many products also keep a binary log, with compact codes instead of text, because it costs fewer bytes on the wire and is faster to write.

A code reviewer checks three things in logging code. Is the call safe to make from the context it runs in? Does a filtered message avoid its arguments? Is the baud rate or divisor derived from the clock, not typed in as a magic number? A senior engineer also asks how the log is turned off for production, because a debug build that prints from a timer will fail a timing test that the release build passes.

Summary

  • A UART sends 8N1 frames: a low start bit, eight data bits, and a high stop bit, which is ten bits per byte.
  • The RP2040 has two UARTs with 32-entry FIFOs. The transmit FIFO is 8 bits wide, and the receive FIFO is 12 bits wide to hold error flags.
  • The baud divisor is UARTCLK / (16 × baud). The integer part goes to UARTIBRD, and the 6-bit fraction goes to UARTFBRD.
  • For 115200 baud at 125 MHz, the ideal divisor is about 67.817, so UARTIBRD is 67 and UARTFBRD is 52, and the hardware divides by 67 + 52/64 = 67.8125.
  • printf waits for FIFO room, so a log in an interrupt can stall the code it is meant to observe.
  • A levelled LOG macro checks the level first, and its arguments are not evaluated when the message is filtered out.
