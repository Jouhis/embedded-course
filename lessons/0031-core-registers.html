Core registers

A Cortex-M core has sixteen register names and one status register. Knowing what each one holds is the difference between reading a debugger and guessing.

By the end of this lesson you can name the core registers R0 to R12, SP, LR, PC and xPSR, say which xPSR bits hold the NZCV flags, and predict the flags after a CMP.

Where we are and why it matters

Lesson 25 covered storage cells and lesson 26 covered the ALU, the part of the core that adds and subtracts and sets the status flags. Lessons 28 to 30 showed the core fetching, decoding and executing instructions. Every one of those instructions reads and writes registers, so the registers are the working memory of the core. Lesson 29 showed that the 16-bit forms can name only R0 to R7 in their register fields.

The register names matter in practice. A HardFault handler on a real board prints the registers at the moment of the fault, and you must know which value is the return address and which is the faulting program counter to find the bug. A debugger's register pane shows the same names. A compiler warning about a clobbered register is a message about the calling convention, which lesson 33 covers. This lesson gives you the vocabulary and the bit layout you need for those tasks.

What a register is

A register is one of a small set of storage cells inside the CPU core. Each register holds one 32-bit word on a Cortex-M. The ALU reads its inputs from registers and writes its result to a register, so an instruction such as ADD R0, R0, #1 never touches memory. Memory is reached only through loads and stores, which is the RISC style from lesson 29.

Registers are the fastest storage the core has. A register read needs no bus transaction, and the ALU can use the value in the same cycle. A variable in RAM needs a load before the ALU can use it, and that load goes over the bus and may wait for memory. This is why a compiler tries to keep the values of a hot loop in registers, and why a debugger that shows a variable must sometimes read it from memory instead.

The sixteen register names

The core has 13 general-purpose registers, R0 to R12, plus three registers with special roles: the stack pointer (SP), the link register (LR) and the program counter (PC). Together those are the sixteen names. Arm's TRM lists them in its programmer's model, together with one program status register, xPSR (Arm Cortex-M3 TRM DDI0337G, §2.3). The TRM says the general-purpose registers "have no special architecturally-defined uses", although the calling convention gives some of them a role, as lesson 33 explains.

RegisterNameWhat it holds
R0 to R12General-purposeOperands, results and, by convention, function arguments and return values (lesson 33).
R13SP (MSP or PSP)The top of the current stack, which grows down. Banked: SP_main or SP_process.
R14LRThe return address after a BL call, or a special value on exception entry.
R15PCThe address of the instruction the core is working on. Writing it branches.
xPSRProgram statusThe flags and the status fields, read as APSR, IPSR and EPSR (below).

LR is the register that makes a short function cheap. Because a bl puts the return address in a register, a leaf function, which calls nothing, can return with bx lr and never touches the stack. A function that does call something must save LR first, which is the subject of lesson 33. The design choice shows up in every listing: a leaf function ends in bx lr with no push at all.

Two details in the table come from the TRM and from the encodings in lesson 29. The first is that R0 to R7 are "accessible by all instructions that specify a general-purpose register", while R8 to R12 are "not accessible by all 16-bit instructions" (DDI0337G, §2.3.1). That is why movs r8, #1 fails on a Cortex-M0+. The second is that R13, the stack pointer, is a banked register, which is the subject of the next section.

The stack pointer is banked

The stack pointer is not one register. It is an alias for one of two physical registers, and only one is visible at a time. The two are SP_main (MSP), the main stack pointer, and SP_process (PSP), the process stack pointer. The TRM says it directly: "Only one stack, the process stack or the main stack, is visible, using r13, at any time" (DDI0337G, §2.2.1).

Which one is visible depends on the mode. Out of reset all code uses the main stack. The TRM also says that "all exceptions continue to use the main stack" (§2.2.1). A Thumb program that runs in thread mode can switch to the process stack, which an RTOS does so that each task has its own stack. Lesson 35 covers the switch. For this lesson, the only fact you need is that the SP you see in a debugger is the one in use, and inside an interrupt handler it is almost always MSP.

The simulator in this lesson does not switch stacks: its program stays in thread mode on the main stack, so one SP is in use. The simulator does model MSP and PSP, which lesson 35 uses. Keep that in mind when you compare its register panel with a real debugger.

xPSR: three views of one register

xPSR is one 32-bit register, but Arm's TRM describes it as three overlapping views. The APSR holds the condition flags. The IPSR holds the number of the exception being handled. The EPSR holds the Thumb state bit and the bits for interruptible instructions (DDI0337G, Tables 2-1 to 2-3). Because the three views are fields of one register, a read of xPSR gives all of them at once, and a write changes whichever fields you name.

  • APSR, bits 31 to 28: N at bit 31 (negative), Z at bit 30 (zero), C at bit 29 (carry or borrow) and V at bit 28 (overflow). Table 2-1 defines them in that order from bit 31 down. Bit 27 is the Q flag, a sticky saturation flag.
  • IPSR, bits 8 to 0: the number of the active exception. Table 2-2 gives 0 for base level, which is thread mode running the main program, 11 for SVCall and 16 for the first peripheral interrupt. The IPSR field is 9 bits wide.
  • EPSR: the T bit, which is bit 24 and must be set for Thumb code, and the interruptible-instruction and If-Then state bits (Table 2-3).

The TRM says why the flags matter across an interrupt: "Before entering an exception, the processor saves the condition code flags on the stack" (DDI0337G, §2.3). The flags are part of the frame the hardware pushes, so a handler that runs a compare does not corrupt the flags its interrupted code will test when it resumes.

The bitreg widget above shows the flag bits. Click them to see how the value changes. It does not show the IPSR or EPSR, which share the register but are separate fields.

A worked example: the flags after CMP R0, #11

A compare is a subtraction that throws away its result and keeps only the flags. Take R0 = 10 and compare it with 11. Work it in 32-bit binary, because the flags describe 32-bit results.

  1. Write the operands. 10 is 0x0000000A. 11 is 0x0000000B.
  2. Compute the subtraction as the core does: add the bitwise NOT of 11, plus 1. The NOT of 0x0000000B is 0xFFFFFFF4, and adding 1 gives 0xFFFFFFF5. The simulator uses the same rule in its addFlags routine.
  3. Add 0x0000000A + 0xFFFFFFF5. The sum is 0xFFFFFFFF, with no carry out of bit 31.
  4. Read the flags. Bit 31 of the result is 1, so N = 1. The result is not zero, so Z = 0. There was no carry out, so C = 0, which means a borrow happened. The operands have different signs, so there is no signed overflow and V = 0.

The result of the subtraction, 0xFFFFFFFF, is −1 in two's complement, which is what 10 − 11 should be. N = 1 says the result is negative. C = 0 says the unsigned subtraction borrowed, so 10 is less than 11 as an unsigned number. Both facts are true at once, and which one a branch uses depends on which comparison you wrote in C, as the quiz below tests.

Now take SUB R2, R0, R1 with both registers holding 10. The same steps give 10 + 0xFFFFFFF5 + 1 = 0x1_00000000. The low 32 bits are zero and there is a carry out, so R2 = 0, Z = 1 and C = 1. The carry flag is set here because there was no borrow.

Try it in the CPU simulator

The simulator has R0 to R12, SP, LR and PC, plus the four flags N, Z, C and V. It does not have PRIMASK in this lesson's program, and it has no separate IPSR or EPSR. Predict each value before you press the button.

  1. Press Reset, then Instruction twice. Predict R2 after SUB R2, R0, R1, and predict the Z flag. Both are in the register and flag panels.
  2. Press Instruction twice more. The CMP R0, #11 compares 10 with 11 without changing R0. Predict which flag is set. The flag panel will light the one that is set.
Hint

For CMP, compute 10 − 11, which is −1. A negative result sets N. It is not zero, so Z stays clear. Work out C and V from the subtraction too: a borrow clears C, as the worked example showed.

The code, line by line

  • MOV R0, #10 writes the immediate 10 into R0. It is a data operation, so it sets N and Z from its result, which is 10.
  • MOV R1, #10 does the same for R1.
  • SUB R2, R0, R1 computes R0 − R1 into R2. The result is 0, so Z is set and the other flags follow the rule in the worked example.
  • CMP R0, #11 subtracts 11 from R0 and keeps only the flags. R0 is unchanged. It leaves N = 1, Z = 0, C = 0 and V = 0, which is what the worked example predicted.
  • B . is the halt. The branch goes to its own address, so the register and flag panels stay as they are.

Common mistakes and how to spot them

  1. Writing to PC by accident. Writing a value to PC branches to it. A line such as MOV PC, R0 with a stale value in R0 sends the core to an address that holds no code. The symptom is often a HardFault, with a PC value that points into an unused part of the map. The fix: check which register holds the target, and remember that LR holds a return address, not a place to jump to.
  2. Treating LR as preserved across a call. A BL overwrites LR with the return address. A function that calls another function must save LR first, or the return goes to the wrong place. The symptom is a function that returns to the instruction after the wrong call. Lesson 33 shows the fix.
  3. Reading the borrow as a carry. After CMP R0, #11 with R0 = 10, C is 0. A beginner who reads "C set" as "a larger value" gets the unsigned comparison backwards. The symptom is a branch that is taken when it should not be, or the reverse. The fix: remember that for a subtraction C is the NOT of the borrow, and that a branch such as BCS tests C = 1.
  4. Using the wrong stack pointer in a handler. In an interrupt handler the SP is MSP, even if the thread was using PSP. A debugger that shows SP in a handler shows MSP. The symptom is a stack pointer value that does not match the one the task had. The fix: read the stacked frame from the stack the exception used, as lesson 34 explains.

In real projects

The register names are the first thing you read in any crash. On a Cortex-M, the exception entry sequence pushes eight words onto the stack: xPSR, PC, R0, R1, R2, R3, R12 and LR (DDI0337G, §5.5.1). A HardFault handler that prints those eight words gives you the PC of the faulting instruction and the flags at that moment. Most firmware projects have a handler like this, and the names in this lesson are the names its output uses.

A senior engineer reviewing low-level code expects you to know which registers a function may change and which it must preserve, and to read xPSR when a flag matters. In an interview, the question "which registers does a Cortex-M have, and what is special about the stack pointer" is answered by the banked MSP and PSP, not by the list of sixteen names.

Summary

  • A register is a storage cell inside the core, 32 bits wide on a Cortex-M. The ALU works on registers, and loads and stores move data to and from memory.
  • The core has R0 to R12, SP (R13), LR (R14), PC (R15) and xPSR.
  • R0 to R7 are accessible to every instruction. R8 to R12 are not accessible to every 16-bit instruction.
  • SP is banked as MSP and PSP. Out of reset and in every exception, the core uses MSP.
  • xPSR is one register with three views: APSR (flags, N at bit 31, Z at 30, C at 29, V at 28), IPSR (exception number, bits 8 to 0) and EPSR (T bit at 24).
  • For a subtraction, C is set when there is no borrow. A result of 10 − 11 gives N = 1, Z = 0, C = 0 and V = 0.
  • A HardFault handler reads the stacked frame of eight words, which includes the PC of the faulting instruction.

Model answer

R0 to R12 are general-purpose. R13 is the stack pointer, which is banked: there is an MSP for handlers and reset, and a PSP that a thread can use. R14 is the link register, R15 is the PC, and xPSR holds the flags in its top bits and the active exception number in its low bits. The stack pointer is special because the hardware switches it on exception entry and return.
