Core registers

The working storage inside a Cortex-M core

By the end of this lesson you can name the core registers R0 to R12, SP, LR, PC and xPSR, say which xPSR bits hold the NZCV flags, and predict the flags after a CMP.

Registers in the debugger and the fault handler

Lesson 25 covered storage cells and lesson 26 the ALU, the part of the core that adds, subtracts and sets the status flags, while lessons 28 to 30 showed the core fetching, decoding and executing instructions. Every one of those instructions reads and writes registers, which makes the registers the working memory of the core, and lesson 29 showed that the 16-bit forms can name only R0 to R7 in their register fields.

The register names matter in practice. A HardFault handler on a real board prints the registers at the moment of the fault, and finding the bug requires knowing which value is the return address and which the faulting program counter. A debugger's register pane uses the same names, and a compiler warning about a clobbered register refers to the calling convention covered in lesson 33. This lesson supplies the vocabulary and the bit layout those tasks need.

Registers and memory

A register is one of a small set of storage cells inside the CPU core, each holding one 32-bit word on a Cortex-M. The ALU reads its inputs from registers and writes its result to a register, so an instruction such as ADD R0, R0, #1 never touches memory, which is reached only through loads and stores in the RISC style of lesson 29.

Registers are the fastest storage the core has. Reading one needs no bus transaction, so the ALU can use the value in the same cycle, whereas a variable in RAM needs a load over the bus first, and that load may wait for memory. A compiler therefore tries to keep the values of a hot loop in registers, and for the same reason a debugger showing a variable sometimes has to read it from memory instead.

The registers resemble a workbench and memory the warehouse behind it. The bench holds only a few things, but everything on it is within reach at once, and since the ALU works only on what is on the bench, a value in memory is first carried to the bench by a load, worked on, and carried back by a store. Good compiled code keeps its most-used values on the bench. Unlike a bench, though, each register holds exactly one 32-bit word, never a larger item.

The sixteen register names

The core has 13 general-purpose registers, R0 to R12, and three with special roles, the stack pointer (SP), the link register (LR) and the program counter (PC), which together make the sixteen names. Arm's TRM lists them in its programmer's model together with one program status register, xPSR (Arm Cortex-M3 TRM DDI0337G, §2.3), and states that the general-purpose registers "have no special architecturally-defined uses", although the calling convention assigns some of them a role, as lesson 33 explains.

RegisterNameWhat it holds
R0 to R12General-purposeOperands, results and, by convention, function arguments and return values (lesson 33).
R13SP (MSP or PSP)The top of the current stack, which grows down. Banked: SP_main or SP_process.
R14LRThe return address after a BL call, or a special value on exception entry.
R15PCThe address of the instruction the core is working on. Writing it branches.
xPSRProgram statusThe flags and the status fields, read as APSR, IPSR and EPSR (below).

LR is what makes a short function cheap. Because bl places the return address in a register, a leaf function, one that calls nothing, can return with bx lr without ever touching the stack, while a function that does call something must save LR first, the subject of lesson 33. The design choice is visible in compiled code, where a leaf function ends in bx lr with no push at all.

Two details in the table come from the TRM and from the encodings of lesson 29. R0 to R7 are "accessible by all instructions that specify a general-purpose register", while R8 to R12 are "not accessible by all 16-bit instructions" (DDI0337G, §2.3.1), which is why movs r8, #1 fails on a Cortex-M0+. And R13, the stack pointer, is a banked register, which the next section explains.

The banked stack pointer

The stack pointer is not a single register but an alias for one of two physical registers, only one of which is visible at a time: SP_main (MSP), the main stack pointer, and SP_process (PSP), the process stack pointer. The TRM states it directly: "Only one stack, the process stack or the main stack, is visible, using r13, at any time" (DDI0337G, §2.2.1).

Which one is visible depends on the mode. Out of reset all code uses the main stack, and according to the TRM "all exceptions continue to use the main stack" (§2.2.1), while a Thumb program running in thread mode can switch to the process stack, which an RTOS does to give each task its own stack, as lesson 35 covers. For now the key fact is that the SP shown in a debugger is the one in use, and inside an interrupt handler that is almost always MSP.

The simulator in this lesson does not switch stacks; its program stays in thread mode on the main stack, so only one SP is in use, although the simulator does model MSP and PSP for lesson 35. Keep this in mind when comparing its register panel with a real debugger.

The three views of xPSR

xPSR is a single 32-bit register that Arm's TRM describes as three overlapping views. The APSR holds the condition flags, the IPSR holds the number of the exception being handled, and the EPSR holds the Thumb state bit and the bits for interruptible instructions (DDI0337G, Tables 2-1 to 2-3). Because the three views are fields of one register, reading xPSR returns all of them at once, and a write changes whichever fields it names.

  • APSR, bits 31 to 28: N at bit 31 (negative), Z at bit 30 (zero), C at bit 29 (carry or borrow) and V at bit 28 (overflow), defined in that order from bit 31 down in Table 2-1. Bit 27 is the Q flag, a sticky saturation flag.
  • IPSR, bits 8 to 0: the number of the active exception, which Table 2-2 gives as 0 for base level, thread mode running the main program, 11 for SVCall and 16 for the first peripheral interrupt. The field is 9 bits wide.
  • EPSR: the T bit, bit 24, which must be set for Thumb code, and the interruptible-instruction and If-Then state bits (Table 2-3).

The TRM also explains why the flags survive an interrupt: "Before entering an exception, the processor saves the condition code flags on the stack" (DDI0337G, §2.3). The flags are part of the frame the hardware pushes, so a handler that runs a compare does not corrupt the flags the interrupted code will test when it resumes.

Worked example: the flags after CMP R0, #11

A compare is a subtraction that discards its result and keeps only the flags. We take R0 = 10, compare it with 11 and work in 32-bit binary, because the flags describe 32-bit results. Before reading on, predict whether C will be set.

  1. Write the operands: 10 is 0x0000000A and 11 is 0x0000000B.
  2. Compute the subtraction as the core does, adding the bitwise NOT of 11 plus 1. The NOT of 0x0000000B is 0xFFFFFFF4, and adding 1 gives 0xFFFFFFF5; the simulator applies the same rule in its addFlags routine.
  3. Add 0x0000000A + 0xFFFFFFF5, which gives 0xFFFFFFFF with no carry out of bit 31.
  4. Read the flags. Bit 31 of the result is 1, so N = 1; the result is not zero, so Z = 0; there was no carry out, so C = 0, meaning a borrow occurred; and the operands have different signs, so there is no signed overflow and V = 0.

The result 0xFFFFFFFF is −1 in two's complement, as 10 − 11 should be. N = 1 says the result is negative, and C = 0 says the unsigned subtraction borrowed, so 10 is less than 11 as an unsigned number. Both flags are correct, and a branch uses whichever matches the comparison written in C, as the quiz below tests.

For SUB R2, R0, R1 with both registers holding 10, the same steps give 10 + 0xFFFFFFF5 + 1 = 0x1_00000000. The low 32 bits are zero and there is a carry out, so R2 = 0, Z = 1 and C = 1, the carry flag being set because there was no borrow.

Try it in the CPU simulator

Hint

For CMP, compute 10 − 11, which is −1. A negative result sets N and a non-zero one leaves Z clear, and working C and V out from the subtraction shows that a borrow clears C, as in the worked example.

The program line by line

  • MOV R0, #10 writes the immediate 10 into R0, and as a data operation it sets N and Z from its result.
  • MOV R1, #10 does the same for R1.
  • SUB R2, R0, R1 computes R0 − R1 into R2. The result is 0, so Z is set and the other flags follow the rule of the worked example.
  • CMP R0, #11 subtracts 11 from R0 and keeps only the flags, leaving R0 unchanged with N = 1, Z = 0, C = 0 and V = 0, as the worked example predicted.
  • B . is the halt, a branch to its own address, so the register and flag panels stay as they are.

Common mistakes and how to spot them

An accidental write to PC

The program ends in a HardFault with a PC pointing into an unused part of the map. Writing a value to PC branches to it, so a line such as MOV PC, R0 with a stale value in R0 sends the core to an address holding no code. Check which register holds the target, and remember that LR holds a return address, not a general jump target.

LR assumed to survive a call

A function returns to the instruction after the wrong call. A BL overwrites LR with its own return address, so a function that calls another must save LR first, as lesson 33 shows.

The borrow read as a carry

A branch is taken when it should not be, or the reverse. After CMP R0, #11 with R0 = 10, C is 0, and reading "C set" as "larger value" gets the unsigned comparison backwards. For a subtraction C is the inverse of the borrow, and a branch such as BCS tests C = 1.

The wrong stack pointer in a handler

The stack pointer shown in a handler does not match the one the task had. Inside an interrupt handler the SP is MSP even if the thread was using PSP, so a debugger shows MSP there. Read the stacked frame from the stack the exception used, as lesson 34 explains.

Registers in crash dumps and code review

The register names are the first thing read in any crash. On exception entry a Cortex-M pushes eight words onto the stack: xPSR, PC, R0, R1, R2, R3, R12 and LR (DDI0337G, §5.5.1). A HardFault handler that prints those eight words reveals the PC of the faulting instruction and the flags at that moment, and since most firmware projects have such a handler, its output uses exactly the names of this lesson.

A senior engineer reviewing low-level code expects you to know which registers a function may change and which it must preserve, and to read xPSR whenever a flag matters.

Summary

  • A register is a 32-bit storage cell inside a Cortex-M core; the ALU works on registers, while loads and stores move data to and from memory.
  • The core has R0 to R12, SP (R13), LR (R14), PC (R15) and xPSR.
  • R0 to R7 are accessible to every instruction, while R8 to R12 are not accessible to every 16-bit instruction.
  • SP is banked as MSP and PSP, and the core uses MSP out of reset and in every exception.
  • xPSR has three views: APSR (N at bit 31, Z at 30, C at 29, V at 28), IPSR (exception number, bits 8 to 0) and EPSR (T bit at 24).
  • For a subtraction C is set when there is no borrow, so 10 − 11 gives N = 1, Z = 0, C = 0 and V = 0.
  • A HardFault handler reads the stacked frame of eight words, which includes the PC of the faulting instruction.
