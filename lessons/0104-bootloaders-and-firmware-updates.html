Bootloaders and firmware updates

Validated images, hand-over and rollback

By the end of this lesson you can validate an application image header, hand over to the application by setting VTOR and MSP and branching to its reset handler, and explain how a test-then-confirm rollback recovers from a failed update.

Field updates without a debugger

Lesson 42 showed what happens at reset, the core reading the vector table at address 0, taking its first word as the stack pointer and its second as the address of the reset handler and starting to run there, while lesson 68 showed how a linker script places code and data at fixed addresses and lesson 84 the fault handlers and the watchdog, which turn a crash into a recovery. This lesson joins them, because a device running in the field must accept a new firmware image over a serial link or a radio without bricking itself if the new image is broken.

Products of many kinds need this, a printer, a router, a heater controller or a sensor node shipping with firmware that will need fixes after installation, while nobody will connect a debugger to each one. The update must therefore arrive through the normal interface, and the device must decide by itself, before running the new code, whether that code is safe to run, which is the decision a bootloader, a small program, makes.

The bootloader as the first program after reset

After reset the core reads the vector table at address 0 and starts whatever image sits there (lesson 42), and a bootloader makes that image small and fixed, deciding which application runs and able to replace the application with a new one. The application is a separate image in its own flash slot, which the bootloader validates, the boot proceeding only if the image passes. Over-the-air (OTA) updates use the same mechanism. The device downloads a new image into the spare slot, and the bootloader then decides whether to switch to it. The download is a transport problem; the switch is the bootloader's job.

The bootloader is a program like any other with one special role, being the only code that must be trusted to run before anything else, so it is kept small enough to be reviewed completely and written to be updated rarely, because a bug in it can make the device impossible to update at all, which is why many products protect the bootloader's own flash region from ordinary updates.

Flash slots and the metadata area

Flash is the chip's only non-volatile memory, and an update must write a whole new image somewhere without destroying the running one, the usual answer being to divide the flash into regions with fixed roles called slots (glossary: slot), each an area holding one firmware image. With two slots the device can keep a known-good image in slot A while writing the new one into slot B, and a third region, the metadata area, remembers state across resets, such as whether the new image has been tried yet.

The addresses in the figure are not arbitrary, the bootloader sitting at the bottom of flash, where the chip starts executing after reset (lesson 42), and the application slot starting right after it at 0x08004000, 16 KiB above the flash base, since 0x4000 bytes is 16 384, the size of the bootloader region. Each region's start address is the sum of the sizes below it, so the layout is simply a set of additions done once, in the linker script (lesson 68).

MCUboot, the bootloader Zephyr ships, calls the two application slots the primary and the secondary, the primary being the image area the bootloader normally runs from and the secondary holding a new candidate image. MCUboot normally runs only the primary slot, so to run a new image from the secondary it moves the contents into the primary during an upgrade, keeping the old image so that it can go back (MCUboot design: image slots).

The image header and its magic value

Before trusting a slot, the bootloader reads a header at its start, MCUboot's being 32 bytes long, beginning with a magic value, 0x96f3b83d, and holding the load address, the header size, the size of the protected TLVs, the image size, the flags and the version (MCUboot design: image format), each field answering one question, whether this is an image at all, how big it is, which version it is and where it ends.

A magic value is a constant that a valid image stores at a known place, so that a bootloader can tell an image from random flash contents, and since erased flash reads as all ones and an old image left by previous firmware has a different magic, the check is cheap and catches most mistakes. A magic value checks only that a slot looks like an image, though, without proving that the image is intact.

The header in this lesson follows the same idea in a smaller form (projects/0104-bootloader-and-app/solution/app_image.h), with a magic word APP1, 0x41505031 because A is 0x41, P 0x50 and 1 0x31, followed by a version, the address one past the end of the image, the vector table's offset from the header and four reserved words, eight words of four bytes making 32 bytes. The reserved words are where a CRC or a signature would go, which a real image needs, because a magic word alone cannot tell an interrupted download from a complete one, whereas this build leaves them zero, since it does not check a CRC or a signature yet.

The boot decision and rollback

An update that works must still be confirmed, because a new image can boot and then crash later, so a common scheme keeps a trial counter in the metadata, the bootloader running the new image in test mode after an update and decrementing the counter at each boot. If the application confirms itself, setting a confirm flag once it has run correctly for a while, the bootloader keeps it, whereas if the counter runs out without a confirm, the bootloader swaps back to the old image.

Two slots resemble a theatre with a second stage, the new show being set up there while the old one keeps playing, and if the new show collapses during its trial run, before the director signs it off, which plays the part of the confirm, the manager puts the old show back on, so the audience, the user, always gets a show. The comparison breaks on who decides, because a manager watches the show, whereas the bootloader sees only the confirm flag and a counter, so an application that confirms itself too early is kept even if it fails afterwards.

MCUboot's design names the swap types it can perform, test, permanent and revert, with the image-OK flag in the image trailer recording the confirmation (MCUboot design: boot swap types), a test swap running the new image on trial, a permanent swap making it the primary for good and a revert swapping the old image back, so the confirmation is the step that turns a test into a permanent image.

The order matters because of what a bad image costs, since a bootloader that erased the old image before knowing the new one worked would brick the device with any new image carrying a bug in its startup code, leaving no old image to fall back on and no way to reach the bootloader's update path without a debugger. The rule is therefore never to destroy the last known-good image until the new one has proven itself, keeping a way back until then.

The course build does not implement the counter, because it has one slot and no metadata area. The concept is the important part: the device must know when an image has proven itself, and it must have a way back before it erases the old one.

Worked example: the header checks with real numbers

The slot in this project starts at 0x08004000, where the bootloader reads eight words, and suppose that the header holds 0x41505031, the magic, in its first word and 0x200, the vector offset, in its fourth. Before following the steps, predict which value would make the bootloader reject a slot whose header is otherwise correct.

  1. The magic and the offset. The bootloader checks the magic first, which matches, so the slot is at least an image, and then the vector offset against the constant 0x200, which matches as well.
  2. The vector table's position. The vector table lies 0x200 bytes into the slot, at 0x08004200, on the 512-byte boundary it requires, since PM0056 Rev 7, section 4.4.4, says that the table offset is aligned to at least 128 words, with bits 8 to 0 always zero, so an offset of 0x100 cannot be used.
  3. The stack pointer. Word 0 of the table is the initial stack pointer, here 0x20005000, and since the chip's RAM starts at 0x20000000 and is 20 KiB, 0x5000 bytes, the top of RAM is 0x20005000, so the value passes the check that the stack pointer exceeds the RAM base and does not exceed the RAM top, a full-descending stack starting at the top and growing down (lesson 33).
  4. The Thumb bit. Word 1 is the reset handler, the first instruction the application runs, here 0x08004201, whose lowest bit is 1, so the Thumb check passes, Cortex-M cores running only Thumb code with the lowest bit of a function address as the Thumb flag, which is why a clean even address is always a mistake.
  5. The handler's range. The last check requires the handler to lie inside the image, so 0x08004201 must be at least 0x08004000 and below the image end.

With word 1 changed to 0x08004200, the lowest bit would be 0 and the Thumb check would reject the slot, whereas without the check a branch to that address would start executing in the wrong state and fault.

The jump to the application

The hand-over is three register writes and a branch, each with a reason, the application's vector table lying at 0x08004200 with the initial stack pointer in word 0 and the reset handler in word 1 (lesson 42), and in order the bootloader:

  1. disables interrupts, so no bootloader interrupt runs half-way through the hand-over;
  2. writes the application's table address into SCB->VTOR, so that exceptions now use the application's table (PM0056 Rev 7, section 4.4.4, Vector table offset register (SCB_VTOR), listed in RESOURCES.md);
  3. loads the main stack pointer from word 0 with __set_MSP();
  4. branches to the reset handler in word 1. The branch never returns.
/* from the solution's main.c: the hand-over, in order */
__disable_irq();
SCB->VTOR = APP_BASE_ADDR + APP_VECTOR_OFFSET;   /* exceptions use the app's table */
__set_MSP(sp);                                     /* the app's stack starts at its top */
((void (*)(void))(uintptr_t)reset)();              /* branch to the app's Reset_Handler */

__disable_irq() sets the PRIMASK bit, which masks every configurable interrupt, so an interrupt cannot run while the vector table is half-replaced, and SCB->VTOR is the Vector Table Offset Register, writing which moves the table that exceptions use. __set_MSP(sp) sets the main stack pointer, the stack the bootloader was using, to the application's initial value, and the last line casts the address in word 1 to a function pointer and calls it, the bootloader never using the return address that the call leaves in LR, because the application never returns, so the bootloader never resumes.

Setting VTOR is not optional. If it still points at the bootloader's table, the application's first interrupt would enter the bootloader's handler. And if you forget to set MSP, the application starts with the bootloader's stack pointer, which may be in the middle of the bootloader's data.

One link with two flash regions

A real product builds the bootloader and the application as two separate programs that a flash tool joins, either a tool such as srec_cat merging the two Intel HEX files or MCUboot's imgtool signing the application and prepending its header, whereas the Wokwi simulator loads one file (the wokwi.toml firmware key) and arm-none-eabi-objcopy reads one input file at a time, so it cannot merge two images on its own.

This project takes a simpler route giving the same flash image, one link, two regions, the linker script boot.ld defining a BOOT region of 16 KiB at 0x08000000 and an APP region of 48 KiB at 0x08004000, the bootloader's code going in the first region and the application's header, vector table and code in the second, with ASSERTs checking that the header comes first in its slot, while the linker reports an error if the bootloader grows past 16 KiB. The result is one ELF and one .hex, which wokwi.toml loads, and arm-none-eabi-objdump -h build/boot_and_app.elf shows the layout, listing .app_header at 08004000 and .app_vectors at 08004200.

The trade-off is that in one link the application can call the bootloader's functions, such as uart_puts, and the two cannot be updated separately, so a product updating the application in the field keeps them as separate images, the lesson's layout being the same picture with the join done by a tool.

Common mistakes and how to spot them

VTOR left pointing at the bootloader

The serial monitor shows BOOT -> APP OK, and then the output stops or repeats a bootloader message, because an interrupt or fault entered the bootloader's handler instead of the application's after VTOR was left at the bootloader's table. Write SCB->VTOR before enabling interrupts and check the value in the debugger with print/x SCB->VTOR, which should read 0x08004200, whereas an offset of 0x08004100 could never be read back, because bits 8 to 0 of VTOR read as zero (PM0056 Rev 7, section 4.4.4).

MSP not set, or set after the branch

The application runs for a while and then fails in a strange place, often far from the code that changed, because it started with the bootloader's stack pointer, so its first pushes landed in the bootloader's data and overwrote a variable. Call __set_MSP(sp) with word 0 before the branch, and step through the first instruction of app_reset in GDB to confirm that SP reads 0x20005000.

A mismatched vector offset

The bootloader prints BOOT: no valid image, staying in the bootloader, although the application is in flash, because the header states one offset while the linker put the vector table at another. Check that APP_VECTOR_OFFSET in app_image.h matches the ASSERT in boot.ld, which exists so that the linker enforces this for the project.

A reset handler address without the Thumb bit

The check rejects the image, so the bootloader stays put, or, with the check skipped, the hand-over faults at once, because a hand-written image or a wrong symbol gave an even address for the handler. Keep the Thumb check in slot_is_valid(), and never bypass it to make a test pass.

Bootloaders as safety-critical components

A professional bootloader is reviewed as a safety-critical component, being the one part that must always work, so teams keep it small, write its checks as unit tests on the host (lessons 80 and 81) and document the image format as a versioned interface, so that the update tool and the device agree. They also design for power loss during an update, the bootloader having to recover if the power fails halfway through writing slot B, which means that the metadata recording progress is written last and read first.

Summary

  • A bootloader runs first after reset, validates an application image in its own slot and jumps to it.
  • Slots are flash regions with fixed roles, two slots letting the device keep a known-good image while it writes a new one.
  • MCUboot's header is 32 bytes and starts with the magic value 0x96f3b83d, while this course's header is 32 bytes and starts with APP1, 0x41505031.
  • The validation checks the magic, the vector offset, the image end, the stack pointer in RAM and the reset handler's Thumb bit and address.
  • The hand-over disables interrupts, sets VTOR, sets MSP from word 0 and branches to the reset handler through a function pointer.
  • A test-then-confirm update runs the new image on trial and reverts to the old one if it never confirms.
  • The old image is never erased before the new one has proven itself.
MCUboot design (docs.mcuboot.com): read the sections on the image format (the 32-byte header and its magic), image slots, and the boot swap types (test, permanent and revert, with the image-OK flag). It is the reference that the Zephyr project uses for its own bootloader.
