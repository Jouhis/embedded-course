Bootloaders and firmware updates

A device in the field must be updated without a debugger, and it must survive an update that goes wrong. A bootloader owns the reset vector, checks the image it is about to run, and keeps a way back to the last good one. You will build a small bootloader and an application slot, and boot the application from the bootloader.

By the end of this lesson you can validate an application image header, hand over to the application by setting VTOR and MSP and branching to its reset handler, and explain how a test-then-confirm rollback recovers from a failed update.

Where we are and why it matters

Lesson 42 showed what happens at reset: the core reads the vector table at address 0, takes its first word as the stack pointer and its second word as the address of the reset handler, and starts running there. Lesson 68 showed how a linker script places code and data at fixed addresses. Lesson 84 showed the fault handlers and the watchdog, which turn a crash into a recovery. This lesson joins them: a device that is running in the field must accept a new firmware image over a serial link or a radio, and it must not brick itself if the new image is broken.

Products of many kinds need this. A printer, a router, a heater controller or a sensor node ships with firmware that will need fixes after it is installed. Nobody will connect a debugger to each one. The update has to arrive through the normal interface, and the device has to decide, by itself and before it runs the new code, whether that code is safe to run. A bootloader is the small program that makes that decision.

The idea: the bootloader runs first

After reset the core reads the vector table at address 0 and starts whatever image sits there (lesson 42). A bootloader makes that image small and fixed: it decides which application runs, and it can replace the application with a new one. The application is a separate image in its own flash slot. The bootloader validates it, and the boot only proceeds if the image passes. Over-the-air (OTA) updates use the same mechanism. The device downloads a new image into the spare slot, and the bootloader then decides whether to switch to it. The download is a transport problem; the switch is the bootloader's job.

The bootloader is a program like any other, with one special role. It is the only code that must be trusted to run before anything else. Its size is kept small so that it can be reviewed completely, and it is written to be updated rarely, because a bug in the bootloader can make the device impossible to update at all. Many products therefore protect the bootloader's own flash region from ordinary updates.

The flash layout: slots and metadata

Flash is the only non-volatile memory on the chip, and an update has to write a whole new image somewhere without destroying the one that is running. The usual answer is to divide the flash into regions with fixed roles, called slots (glossary: slot). A slot is an area that holds one firmware image. With two slots the device can keep a known-good image in slot A while it writes the new one into slot B. A third region, the metadata area, remembers state across resets, such as whether the new image has been tried yet.

The addresses in the figure are not arbitrary. The bootloader sits at the bottom of flash, where the chip starts executing after reset (lesson 42). The application slot starts right after it, at 0x08004000, which is 16 KiB above the flash base: 0x4000 bytes is 16 384, and that is the size of the bootloader region. Each region's start address is the sum of the sizes below it, so the layout is simply a set of additions done once, in the linker script (lesson 68).

MCUboot, the bootloader Zephyr ships, calls the two application slots the primary and the secondary. The primary slot is the image area the bootloader normally runs from. The secondary slot holds a new candidate image. MCUboot normally runs only the primary slot. To run a new image from the secondary, it moves the contents into the primary during an upgrade, and it keeps the old image so that it can go back (MCUboot design: image slots).

The image header: is this really an application?

Before the bootloader trusts a slot, it reads a header at the slot's start. MCUboot's header is 32 bytes. It begins with a magic value, 0x96f3b83d, and then holds the load address, the header size, the size of the protected TLVs, the image size, the flags and the version (MCUboot design: image format). Each field answers one question: is this an image at all, how big is it, which version is it, and where does it end?

A magic value is a constant that a valid image stores at a known place, so that a bootloader can tell an image from random flash contents. Erased flash reads as all ones, and an old image left behind by a previous firmware has a different magic, so the check is cheap and catches most mistakes. A magic value checks only that a slot looks like an image. It does not prove that the image is intact.

The header in this lesson follows that idea in a smaller form (projects/0104-bootloader-and-app/solution/app_image.h). It has a magic word APP1, which is 0x41505031 because A is 0x41, P is 0x50, and 1 is 0x31. It has a version, the address one past the end of the image, the vector table's offset from the header, and four reserved words. The header is 32 bytes: eight words of four bytes each. The reserved words are where a CRC or a signature would go. A real image needs one of them, because a magic word alone cannot tell an interrupted download from a complete one. This build leaves them zero, because it does not check a CRC or a signature yet.

Boot decision and rollback

An update that works must still be confirmed, because a new image can boot and then crash later. A common scheme keeps a trial counter in the metadata. After an update, the bootloader runs the new image in test mode and decrements the counter at each boot. If the application confirms itself (it sets a confirm flag once it has run correctly for a while), the bootloader keeps it. If the counter runs out without a confirm, the bootloader swaps back to the old image.

Two slots work like a theatre with a second stage. The new show is set up on the second stage while the old one keeps playing. On opening night, if the new show collapses before the interval, which is the confirm, the manager puts the old show back on. The audience, the user, always gets a show.

MCUboot's design names the swap types it can perform: test, permanent and revert, with the image-OK flag in the image trailer recording the confirmation (MCUboot design: boot swap types). A test swap runs the new image on trial. A permanent swap makes the new image the primary for good. A revert swaps the old image back. The confirmation is the step that turns a test into a permanent image.

The order matters because of what a bad image costs. If the bootloader erased the old image before it knew the new one worked, a new image with a bug in its startup code would brick the device, because there is no old image to fall back on and no way to reach the bootloader's update path without a debugger. So the rule is: never destroy the last known-good image until the new one has proven itself, and keep a way back until then.

The course build does not implement the counter, because it has one slot and no metadata area. The concept is the important part: the device must know when an image has proven itself, and it must have a way back before it erases the old one.

Worked example: the header checks with real numbers

Take the slot in this project at its start address, 0x08004000. The bootloader reads eight words from there. Suppose the header holds 0x41505031 in its first word, which is the magic, and 0x200 in its fourth word, which is the vector offset. The bootloader checks the magic first. It matches, so the slot is at least an image. It then checks the vector offset against the constant 0x200, and that matches as well.

Next the bootloader reads the vector table, which is 0x200 bytes into the slot, so at 0x08004200. The table must start on a 512-byte boundary: PM0056 Rev 7, section 4.4.4, says the table offset is aligned to at least 128 words, and bits 8 to 0 of it are always zero, so an offset of 0x100 cannot be used. Word 0 of that table is the initial stack pointer. Suppose it holds 0x20005000. The RAM for this chip starts at 0x20000000 and is 20 KiB, which is 0x5000 bytes, so the top of RAM is 0x20005000. The check is that the stack pointer is greater than the RAM base and no greater than the RAM top. 0x20005000 passes, because a full-descending stack starts at the top and grows down (lesson 33).

Word 1 is the reset handler, the first instruction the application runs. Suppose it holds 0x08004201. The lowest bit is 1, so the Thumb check passes. Cortex-M cores run only Thumb code, and the lowest address bit of a function address is the Thumb flag, which is why a clean even address is always a mistake. The last check says the handler must lie inside the image, so 0x08004201 must be at least 0x08004000 and below the image end. Now change one value. If word 1 were 0x08004200, the lowest bit would be 0, and the Thumb check would reject the slot. A branch to that address would otherwise start executing in the wrong state and fault.

Run the bootloader's checks on the worked example, then load the broken images. Each one fails at a different check, and the checks after it are never reached.

Jumping to the application

The hand-over is three register writes and a branch, and each one has a reason. The application's vector table is at 0x08004200, and its word 0 is the initial stack pointer, word 1 the reset handler (lesson 42). The bootloader:

  1. disables interrupts, so no bootloader interrupt runs half-way through the hand-over;
  2. writes the application's table address into SCB->VTOR, so that exceptions now use the application's table (PM0056 Rev 7, section 4.4.4, Vector table offset register (SCB_VTOR), listed in RESOURCES.md);
  3. loads the main stack pointer from word 0 with __set_MSP();
  4. branches to the reset handler in word 1. The branch never returns.
/* from the solution's main.c: the hand-over, in order */
__disable_irq();
SCB->VTOR = APP_BASE_ADDR + APP_VECTOR_OFFSET;   /* exceptions use the app's table */
__set_MSP(sp);                                     /* the app's stack starts at its top */
((void (*)(void))(uintptr_t)reset)();              /* branch to the app's Reset_Handler */

Line by line: __disable_irq() sets the PRIMASK bit, which masks every configurable interrupt, so an interrupt cannot run while the vector table is half-replaced. SCB->VTOR is the Vector Table Offset Register, and writing it moves the table that exceptions use. __set_MSP(sp) writes the main stack pointer, the stack the bootloader was using, to the application's initial value. The last line casts the address of word 1 to a function pointer and calls it. The bootloader never uses the return address that the call leaves in LR, and the application never returns, so the bootloader never resumes.

Setting VTOR is not optional. If it still points at the bootloader's table, the application's first interrupt would enter the bootloader's handler. And if you forget to set MSP, the application starts with the bootloader's stack pointer, which may be in the middle of the bootloader's data.

The combined image: one link, two regions

A real product builds the bootloader and the application as two separate programs, and a flash tool joins them. Two options work for that: a tool such as srec_cat merges the two Intel HEX files, or MCUboot's imgtool signs the application and prepends its header. The Wokwi simulator loads one file (the wokwi.toml firmware key), and arm-none-eabi-objcopy reads one input file at a time, so it cannot merge two images on its own.

This project takes a simpler route that gives the same flash image: one link, two regions. The linker script boot.ld defines a BOOT region at 0x08000000, 16 KiB, and an APP region at 0x08004000, 48 KiB. The bootloader's code goes in the first region, and the application's header, vector table and code go in the second, with ASSERTs that check the header is first in its slot. The linker reports an error if the bootloader grows past 16 KiB. The result is one ELF and one .hex, and wokwi.toml loads that .hex. You can see the layout yourself: arm-none-eabi-objdump -h build/boot_and_app.elf lists .app_header at 08004000 and .app_vectors at 08004200.

The trade-off: in one link the application can call the bootloader's functions, such as uart_puts, and the two cannot be updated separately. A product that updates the application in the field keeps them as separate images, and the lesson's layout is the same picture with the join done by a tool.

The starter builds the bootloader and the application into one image, as the previous section describes, but its bootloader never accepts the slot. Your job is the two functions that decide and hand over: the header checks from the worked example, and the jump from the section before it.

  1. Open projects/0104-bootloader-and-app/starter in VS Code, build with Ctrl+Shift+B, and start the simulator with F1 → Wokwi: Start Simulator. The monitor prints BOOT: checking application slot, then BOOT: no valid image, staying in the bootloader.
  2. Write slot_is_valid() in main.c, marked TODO(learner). Make the five checks in the order the comment lists, the same order as the worked example: magic, vector offset, image end, stack pointer, reset handler. Return 0 as soon as one fails.
  3. Write jump_to_app(), the second TODO(learner). Read word 0 and word 1 of the application's vector table, then disable interrupts, set SCB->VTOR, set the MSP and call the reset handler through a function pointer, in that order.
  4. Build and run again. You will know it works when the monitor prints BOOT: image valid, jumping and then the application's own line, BOOT -> APP OK.
  5. Now see the other branch. Change the magic check to compare with 0x41505032 (APP2), build and run: the bootloader refuses the slot and stays put, which is what protects a device from a half-written update. Change it back.
You validated an image header, handed the CPU to an application by setting VTOR, MSP and the reset branch, and you know how a rollback keeps a device recoverable after a bad update.

Common mistakes and how to spot them

Mistake 1: VTOR left pointing at the bootloader. The application boots, prints its first line, and then an interrupt or fault enters the bootloader's handler instead of the application's. Symptom: the serial monitor shows BOOT -> APP OK, and then the output stops or repeats a bootloader message. Fix: write SCB->VTOR before you enable interrupts, and check the value in the debugger with print/x SCB->VTOR. It should read 0x08004200. An offset of 0x08004100 could never be read back, because bits 8 to 0 of VTOR read as zero (PM0056 Rev 7, section 4.4.4).

Mistake 2: MSP not set, or set after the branch. The application starts with the bootloader's stack pointer, so its first pushes land in the bootloader's data. Symptom: the application runs for a while and then fails in a strange place, often far from the code that changed, because a variable was overwritten. Fix: call __set_MSP(sp) from word 0 before the branch, and step through the first instruction of app_reset in GDB to confirm SP reads 0x20005000.

Mistake 3: the vector offset does not match. The header says one offset and the linker put the vector table at another. Symptom: the bootloader prints BOOT: no valid image, staying in the bootloader even though the application is in flash. Fix: check that APP_VECTOR_OFFSET in app_image.h matches the ASSERT in boot.ld. The linker enforces this for the project, which is why the ASSERT exists.

Mistake 4: a reset handler address without the Thumb bit. A hand-written image or a wrong symbol gives an even address for the handler. Symptom: the check rejects the image, so the bootloader stays silent, or, if you skip the check, the hand-over faults at once. Fix: keep the Thumb check in slot_is_valid(), and never bypass it to make a test pass.

In real projects

A professional bootloader is reviewed as a safety-critical component, because it is the one part that must always work. Teams keep it small, write its checks as unit tests on the host (lessons 80 and 81), and document the image format as a versioned interface, so the update tool and the device agree. They also design for power loss during an update: the bootloader must recover if the power fails halfway through writing slot B, which means the metadata that records progress is written last and read first.

Summary

  • A bootloader runs first after reset, validates an application image in its own slot, and jumps to it.
  • Slots are flash regions with fixed roles. Two slots let the device keep a known-good image while it writes a new one.
  • MCUboot's header is 32 bytes and starts with the magic value 0x96f3b83d. This course's header is 32 bytes and starts with APP1, 0x41505031.
  • The validation checks the magic, the vector offset, the image end, the stack pointer in RAM, and the reset handler's Thumb bit and address.
  • The hand-over disables interrupts, sets VTOR, sets MSP from word 0, and branches to the reset handler through a function pointer.
  • A test-then-confirm update runs the new image on trial, and reverts to the old one if it never confirms.
  • The old image is never erased before the new one has proven itself.
MCUboot design (docs.mcuboot.com): read the sections on the image format (the 32-byte header and its magic), image slots, and the boot swap types (test, permanent and revert, with the image-OK flag). It is the reference that the Zephyr project uses for its own bootloader.
