Capstone 7: the bootloader and the image layout

A product that cannot be updated in the field has to be replaced in the field. This stage puts a small bootloader in front of the application, so the chip checks a new image before it runs it.

By the end of this lesson you can lay out a bootloader and an application slot in one linker script, read the 32-byte image header and the vector table, explain each step of the jump to the application, and say from a map file and a size report whether an image fits.

Where we are and why it matters

Lesson 117 gave the dryer a bus, so a host can read its status and start a cycle. The firmware is still fixed at the factory. A bug fix, a new feature or a new material table means a new image, and that image has to reach a dryer that is already installed in a customer's workshop. Without a way to update the firmware in the field, every change is a service visit.

The usual answer is a bootloader (lesson 104): a small program that runs first after every reset, checks the application image, and jumps to it only if the image looks valid. The bootloader is the one part of the firmware that an update must never damage, so it is kept small and fixed. Lesson 84 added a watchdog, and the two belong together. When a hung application stops feeding the watchdog, the watchdog resets the chip, and the bootloader is the code that runs again.

The bootloader and the image in one ELF

A product normally keeps the bootloader and the application as two separate images, joined by a flash tool or by a library such as MCUboot (lesson 104). This build keeps both in one ELF and one hex file, so it stays simple to simulate and to flash. The linker script decides where each part of the image goes, and that decision is what this lesson is about.

An ELF file is the standard output of the linker. It holds the code, the data and the addresses they must be loaded at, and it also keeps the symbol names that a debugger uses. The hex file holds the same bytes as text, which is what a programmer tool writes to flash. The linker can also write a map file, which lists where every section and symbol was placed. The map file is the best tool for checking the layout, and you will use it in the size check and in the Try it.

The linker script is boot/boot.ld. It splits the flash into two regions, the same split that lesson 104 described for a combined image:

RegionAddress and sizeWhat is in it
BOOT0x08000000, 16 KBThe startup code, the bootloader's main(), and the initial values of .data.
APP0x08004000, 48 KBThe image header (32 bytes), the application's vector table at +0x200, and everything else: FreeRTOS, the HAL, the drivers and the application.
RAM0x20000000, 20 KBShared by both. The startup code initialises it once, so the jump does not copy anything again.

Flash is the chip's non-volatile memory: the program lives there and survives a power cut. RAM is the working memory, and its contents are lost at reset. The CPU reads flash at fixed addresses, which is why the header and the vector table must sit at fixed offsets. The bootloader does not search the flash for the application. It knows that the slot starts at 0x08004000, and it reads the header from that address.

How the linker places the code

The script places each section by the input file it came from. The bootloader's objects are matched by name (the startup, system and bootloader files) and go to BOOT. Every other input goes to the application slot through the catch-all rules. The .data section needs a special arrangement. Its initial values are stored in BOOT, and the startup code copies them to RAM. C requires initialised global variables to start with their initial values, and RAM loses its contents at reset, so the copy is necessary. Because the RAM is shared, the copy is done once, and the application needs no copy of its own.

Two lines at the end of the script check the layout that the bootloader relies on. They are ASSERT statements, which make the link fail if they are false: 

ASSERT(ADDR(.app_header) == ORIGIN(APP), "the image header must be the first thing in the slot")
ASSERT(ADDR(.app_vectors) == ORIGIN(APP) + 0x200, "the vector table must be at slot + 0x200")

The first line requires the header to be the first thing in the application slot, at 0x08004000, because the bootloader reads it from that address. The second requires the vector table to start 0x200 bytes into the slot. If a later change moves either one, the link fails and no image is produced. This is the cheapest kind of test in the project, because it runs during the build, before any board sees the image.

The image header and the vector table

The bootloader does not trust the application slot until it has read a header. The header sits at the first byte of the slot, and it is a C structure. A static assertion in the same file makes the build fail if the structure is not exactly 32 bytes: 

typedef struct {
    uint32_t magic;          /* must equal APP_IMAGE_MAGIC */
    uint32_t version;        /* (major << 16) | minor */
    uint32_t image_end;      /* address one past the last byte of the image */
    uint32_t vector_offset;  /* the vector table, as an offset from this header */
    uint32_t reserved[4];    /* room for a CRC and a signature (lesson 105); zero here */
} app_header_t;

_Static_assert(sizeof(app_header_t) == 32u, "the image header is 32 bytes");

Every field is a uint32_t, a 32-bit unsigned integer, so the structure has no hidden padding and its size is simply the sum of the fields: 4 + 4 + 4 + 4 + 16 = 32 bytes. The static assertion checks that arithmetic at compile time. The table below gives each field its offset from the start of the header and the value this build stores.

The header, byte by byte

OffsetFieldThis build's value
+0magic0x41505031, the ASCII letters "APP1", so a stray pattern of bytes is unlikely to match
+4version(major << 16) | minor, so 1.0 is 0x00010000
+8image_endThe address one past the last byte of the image, taken from the linker
+12vector_offset0x200, the offset of the vector table from the header (512-byte aligned for VTOR)
+16 to +31reserved[4]Zero here; room for a CRC and a signature (lesson 105)

The magic is four ASCII letters. In the byte order that the table shows, 0x41 is 'A', 0x50 is 'P', 0x50 is 'P' and 0x31 is '1'. Erased flash reads as all ones, and a leftover program has no reason to contain this exact pattern at offset 0, so a match is a useful sign that the slot holds an image of this kind. It is not proof that the image is intact. That is what the later fields and, in a product, a signature are for.

The version is one 32-bit number with the major version in the top half and the minor version in the bottom half. The application draws its version on the display, and the host can read the same value, so a field technician and a host see the same answer. The image_end field lets the bootloader reject an image that claims to run past the end of its slot.

The vector table

The vector table is the list of addresses the CPU reads on reset and on each exception. Word 0 holds the initial stack pointer, which is the top of the stack, and word 1 holds the reset handler, the first code to run (lesson 42). The rest of the table holds the handler for each system exception and each device interrupt. When an interrupt fires, the core reads the entry for that exception number from the active table and branches to it.

The application's table is at +0x200, so its first word is at 0x08004200 (PM0056 Rev 7, section 4.4.4, requires the table offset to be 512-byte aligned). The header is 32 bytes, so the linker leaves 480 bytes of padding between the header and the table. The padding is not code and it is not data. It exists only so the table lands on the required boundary. 

__attribute__((section(".app_vectors"), used))
const vector_fn app_vectors[APP_VECTOR_COUNT] = {
    [0 ... APP_VECTOR_COUNT - 1] = app_fault,
    [0]  = (vector_fn)(uintptr_t)&_estack,
    [1]  = app_reset,
    [11] = SVC_Handler,                       /* SVCall */
    [14] = PendSV_Handler,
    [15] = SysTick_Handler,
    [16 + APP_IRQ_USART1] = USART1_IRQHandler,
};
  • __attribute__((section(".app_vectors"), used)) places the array in the section that boot.ld puts at +0x200. used stops the compiler from discarding it, since nothing in the C code calls it.
  • APP_VECTOR_COUNT is 16 system entries plus 60 device interrupts, 76 entries in all. Each entry is 4 bytes, so the table is 304 bytes, which is the 0x130 that the map file reports for .app_vectors.
  • [0 ... APP_VECTOR_COUNT - 1] = app_fault fills every entry with a handler that loops forever. An interrupt the application does not expect therefore stops in a known place, where a debugger can show it.
  • [0] = &_estack stores the top of RAM as the initial stack pointer. The symbol comes from the linker script, so the value is never typed by hand.
  • [1] = app_reset stores the reset handler. Its address has bit 0 set, as it does for every Thumb function, and the bootloader checks that bit.
  • The entries at 11, 14, 15 and 16 + 37 are the SVCall, PendSV and SysTick exceptions and the USART1 interrupt. The first 16 entries belong to the core, so device interrupt number 37 sits at index 53. The USART1 number is taken from the STM32F1 reference manual, as the header comment records.

What the bootloader checks

Before it jumps, the bootloader checks the header and the two words it will use. The checks run in a fixed order, and any failure stops the boot:

  1. The magic equals APP_IMAGE_MAGIC. If not, the slot holds no image of this kind.
  2. The vector_offset equals 0x200. If not, the header describes a layout that this bootloader cannot jump into.
  3. The image_end lies after the first vector word and no further than the end of the 48 KB slot. This rejects an image that claims to be empty or to run past its slot.
  4. The initial stack pointer, word 0 of the table, lies inside RAM.
  5. The reset handler, word 1, has bit 0 set. Cortex-M cores run only Thumb code, and bit 0 marks a Thumb address.
  6. The reset handler lies inside the image, between the start of the slot and image_end.

Each check removes one way for a bad image to crash the boot. The bootloader does not check a CRC or a signature. The header has room for them, and lesson 105 covers why a signature is the real protection. An image that passes these checks can still be wrong in its contents, so the checks prevent crashes, not tampering.

When every check passes, the bootloader prints BOOT: image valid, jumping over USART1 and makes the jump. When one fails, it prints BOOT: no valid image, staying in the bootloader and loops, so the board waits for a new image rather than running a bad one. Those two lines are the first thing a serial monitor shows, and they tell you which path the boot took.

The application reads its own header from flash and draws FW 1.0 on the bottom line of the display. That is how a field technician checks which image is running, and how the host learns it too.

The jump gives up the bootloader. After __set_MSP() and the branch, the bootloader's code never runs again, and it cannot recover a hung application. A watchdog that resets the chip brings the bootloader back, which is why lesson 84's watchdog and this bootloader belong together.

The jump, step by step

The jump is a short function. Its four steps, in order, are these:

  1. The bootloader disables interrupts, so none runs in the middle of the hand-over.
  2. It points the vector table register (VTOR) at the application's table, so exceptions now use the application's handlers.
  3. It sets the main stack pointer (MSP) to the value in word 0 of that table.
  4. It calls the reset handler from word 1 as a function that never returns.
static void jump_to_app(void) {
    const uint32_t *vectors = (const uint32_t *)(uintptr_t)(APP_BASE_ADDR + APP_VECTOR_OFFSET);
    uint32_t sp = vectors[0];
    uint32_t reset = vectors[1];

    __disable_irq();                                  /* no interrupt may run in the middle of the hand-over */
    SCB->VTOR = APP_BASE_ADDR + APP_VECTOR_OFFSET;    /* exceptions now use the application's table */
    __set_MSP(sp);
    ((void (*)(void))(uintptr_t)reset)();             /* never returns */
}
  • The first line computes the address of the application's table, 0x08004200. The cast through uintptr_t converts the integer to a pointer, which is how C code reads a fixed hardware address.
  • sp and reset copy words 0 and 1 of that table into local variables before anything changes. The later steps then use values that were read while the old state was still in place.
  • __disable_irq() clears the interrupt mask in the core, so no interrupt can start during the steps that follow.
  • SCB->VTOR = ... writes the new table address into the vector table register. From this point on, the core finds every handler in the application's table.
  • __set_MSP(sp) moves the main stack pointer to the top of the application's stack. The bootloader's own stack is left behind.
  • The last line casts reset to a function pointer and calls it. The call does not return, because the application's reset handler never returns. It sets up its own state and then runs app_main().

Each step depends on the one before. If step 2 is skipped, the first interrupt in the application would run a handler from the bootloader's table. If step 3 is skipped, the application starts on the stack pointer the bootloader left behind, not on the top of its own stack. The order is short, and it is also the reason a mistake here shows up as a crash that looks random.

Notice what the jump does not do. It does not copy the application into RAM, and it does not reload .data. Both were handled once, by the startup code, before main() ran. The jump only changes which table and which stack the core uses, and then it hands over control.

Common mistakes and how to spot them

Every one of these has happened to someone building a bootloader. Each entry gives the symptom first, so you can recognise it before you find the cause.

Mistake 1: a stale image on the board

Symptom: you change APP_VERSION to 1.1, rebuild, and the display still reads FW 1.0. Cause: the programmer flashed an old .hex file, often from an earlier build folder, so the header on the board is the old one. Fix: flash the file from the build you just made, check its time stamp, and read the version from the display or from the header in the flash. A version that is not checked on the device is only a guess.

Mistake 2: a header offset that the linker does not match

Symptom: someone changes APP_VECTOR_OFFSET in app_image.h to a new value. The header and the bootloader then agree on the new offset, but the linker still places the table at +0x200, so the bootloader reads its words from the wrong place. The usual result is BOOT: no valid image, staying in the bootloader. If someone moves the table in boot.ld instead, the link fails with the second ASSERT message. Cause: the header, the table and the linker script must agree on one layout. Fix: keep APP_VECTOR_OFFSET, the ALIGN(512) placement and the two ASSERT lines in step. Read the map file to confirm where .app_vectors landed before you flash.

Mistake 3: a hand-written reset address with bit 0 clear

Symptom: the magic, the offset and the stack pointer all look right in the hex file, but the bootloader never jumps. It prints BOOT: no valid image, staying in the bootloader. Cause: someone wrote the vector table by hand, or copied an address from a listing, and the reset handler address has bit 0 clear. The check in step 5 rejects it, because a Cortex-M core cannot run an address without the Thumb bit. Fix: take every table entry from the compiler and the linker, not from a calculation on paper. If you must write a table by hand, set bit 0 on every code address.

Mistake 4: an image that outgrows its region

Symptom: the build stops in the linker, and the message names the region that overflowed, either BOOT or APP. Cause: the application has grown past 48 KB, or the bootloader has grown past 16 KB, so a section no longer fits its region. Fix: look at the size report first, and then read the map file to see which input files grew. Trim the larger ones, or move the boundary in boot.ld and accept that the two regions change size. The linker does not write an image that does not fit, so a bad layout fails the build instead of the board.

Measured: does it fit?

CI builds the same sources in its Debug configuration with a newer toolchain, so its numbers can differ a little from these. The text column is code and constants, data is initialised variables, and bss is zero-initialised variables and the heap. 

   text	   data	    bss	    dec	    hex	filename
  20870	    104	  10148	  31122	   7992	dryer.elf

The size report gives totals, and the map file gives the exact addresses. The map shows that the bootloader uses about 1 KB of its 16 KB, and that the application ends at 0x08008FC0. Working out the free space in the slot is simple arithmetic, and it is worth doing by hand once: 

application end   0x08008FC0
slot start        0x08004000
image span        0x08008FC0 - 0x08004000 = 0x4FC0 = 20416 bytes (about 19.9 KB)
slot size         48 KB = 49152 bytes
free in the slot  49152 - 20416 = 28736 bytes (about 28 KB)

Flash used by both regions together is about 21 KB of the 64 KB part. RAM use is about 10 KB of 20 KB, and that includes the 8 KB FreeRTOS heap that holds the task stacks. The data figure of 104 bytes is stored in BOOT and copied to RAM at startup, so it counts against both regions. That is why the flash total is a little larger than the text section alone.

The text section is the largest term. The linker removes functions that nothing calls (--gc-sections, set in CMakeLists.txt), and the logic is compiled at -Og, which keeps the code easy to step through in a debugger. If the image ever did not fit, the trims are, in order: use -Os for the release build, drop the font to the characters the status screen uses, and move the log strings out of the application. Each trade-off costs debuggability, which is why the course keeps the debug build for the simulator.

The 28 KB of free space is the room that a future feature has to fit into. A plan that needs more than that would need either a smaller application or a larger slot, and the second choice means a different linker script and a new layout that the bootloader must accept. The size report is the first thing to check before a design review asks for a feature.

In real projects

A production bootloader is rarely written from scratch. Teams usually start from an existing open bootloader, such as MCUboot (its design document is listed in RESOURCES.md), and adapt it to their own flash layout and signing keys. MCUboot's design describes primary and secondary image slots and swap types, so that a new image can be written while the old one still boots, and a failed update can be rolled back. This project's header is its own design and is not MCUboot's format, which is worth knowing before you compare the two.

The bootloader is reviewed harder than any other code in the product, because a bug there can make a device unrecoverable in the field. Reviewers ask the same questions every time: what happens if power is lost during the write, what happens if the new image is bad, and what can reach the jump without passing every check. A short bootloader with a clear list of checks is easier to review than a long one, which is one reason this build keeps the list in plain code.

Teams that ship a bootloader also test it with bad images on purpose. A test image with a wrong magic, a wrong offset or a reset address with bit 0 clear should be rejected with the reject message, and a good image should boot. The Try it in this lesson does one of those tests by hand. The bootloader itself runs only on the board, so the host tests in lesson 119 cover the application's logic and not this file.

Summary

  • One linker script, boot.ld, places the bootloader in BOOT at 0x08000000 and the application slot in APP at 0x08004000. Two ASSERT lines fail the link if the layout changes.
  • The image header is 32 bytes: magic, version, image end and vector offset, then four reserved words. The vector table sits 0x200 bytes into the slot, as PM0056 section 4.4.4 requires for VTOR alignment.
  • The bootloader checks six things before the jump: the magic, the offset, the image end, the stack pointer in RAM, the Thumb bit of the reset handler, and that the reset handler lies inside the image. It does not check a CRC or a signature.
  • The jump disables interrupts, moves VTOR, sets MSP from word 0, and calls the reset handler from word 1. The order matters, and the bootloader never runs again after it.
  • A map file and a size report answer the question "does it fit?" The application ends at 0x08008FC0 in the measured build, which leaves about 28 KB free in its slot.
  • When a board runs old code, check the hex file's time stamp first. The header on the board is the one that was flashed, not the one you built.

Try it: the bootloader in the simulator

  1. Build the starter firmware from the workspace root: python -I tools/build.py projects/0117-dryer-modbus-bootloader/starter --clean. The build should finish without errors. Its output folder contains dryer.map, the map file this lesson uses.
  2. Open the map file and search for .app_header and .app_vectors. Expect the header at 0x08004000 with size 0x20, and the vector table at 0x08004200 with size 0x130.
  3. Open projects/0117-dryer-modbus-bootloader/starter in VS Code, press Ctrl+Shift+B to build, then F1 → Wokwi: Start Simulator. On the serial monitor, expect BOOT: checking application slot followed by BOOT: image valid, jumping. The application's own lines follow the jump on a real board. The application runs FreeRTOS, which does not start in the simulator (see lesson 87), so its lines may not appear there. A real board prints DRYER RTOS OK, the first line of the solution's main.c.
  4. Break the header on purpose. In starter/boot/app_vectors.c, change the first field of the header initialiser from APP_IMAGE_MAGIC to 0u. Rebuild and start the simulator again. Expect BOOT: no valid image, staying in the bootloader and no application output. This change touches only the header, so the bootloader's check is the one that fails.
  5. Undo the change, so the magic is APP_IMAGE_MAGIC again, and rebuild. The serial monitor should show the jump again.
Hint for step 4

The first field of the header initialiser in app_vectors.c is the magic. The bootloader compares it with APP_IMAGE_MAGIC in app_image.h, and that comparison is the first of its checks. Change only the header, not the define, so the two sides disagree.
