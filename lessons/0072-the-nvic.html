The NVIC: priorities, preemption, latency

When two interrupts fire at once, the NVIC decides which one runs first and whether a running handler can be interrupted. Get the priority grouping wrong and your timing bugs will only show up under load.

By the end of this lesson you can set the priority grouping and the priority of two interrupt sources with CMSIS, say which one preempts which, and explain the 12-cycle entry cost and tail-chaining, using the Arm and ST sources.

Where we are and why it matters

Lesson 70 made the USART and an external-interrupt pin raise interrupts, and it used a ring buffer so that the main loop could read the events later. Lesson 57 explained what an interrupt is and why a handler must be short, and lesson 34 explained what the core does on entry: it pushes a frame of registers onto the stack and fetches the handler's address from the vector table. This lesson is about the decision the interrupt controller makes before that entry starts.

Every product with more than one interrupt source runs into this problem. A motor controller must read its encoder within a few microseconds, but it also logs data over the UART, and a long logging handler must not make the encoder late. A brake monitor must respond before a slower housekeeping timer. If the priorities are wrong, a bug appears only when two events happen close together, and it does not show up in a short test. That is why this lesson covers the rules as well as the register writes.

Concept 1: the NVIC keeps one priority per source

The NVIC (Nested Vectored Interrupt Controller) is the block inside the Cortex-M core that enables interrupt sources, gives each one a priority, and selects the one to run. Each interrupt source has an enable bit, and a priority register. When a source is pending and enabled, the NVIC compares its priority with the priority of the handler that is running, if there is one. If the new one is more urgent, the core takes it.

The priority register is 8 bits wide for each source, but the STM32F1 does not implement all 8 bits. The device header records this as __NVIC_PRIO_BITS 4U, so only the top four bits are used, and the priority is a value from 0 to 15 (stm32f103xb.h). The Arm TRM says the same thing in a general way: if four bits of priority are implemented, the top four bits of the register set the priority, and the lower four bits are always zero. It gives that example in section 5.3.2. A priority number is not a count of anything. Priority 2 is not "twice as urgent" as priority 4. It only says which one wins when both are pending, and whether one can interrupt the other.

On the Cortex-M3 a lower number is a higher priority. Priority 0 is the most urgent configurable interrupt, and priority 15 is the least urgent on this device. This is the opposite of what many people expect, and it is the first thing to check when a priority looks backwards. The reset value of every priority is 0, which is the most urgent level. A source that you never configure is therefore the most urgent one in the system, not the least, and this is a common trap.

Concept 2: grouping splits the bits into two jobs

The four implemented bits do two jobs, and the priority grouping decides how many bits do each. The grouping is set by the PRIGROUP field of the AIRCR register, which is the Application Interrupt and Reset Control Register. In the CMSIS header, PRIGROUP is bits 10 to 8 of that register (SCB_AIRCR_PRIGROUP_Pos is 8, and its mask is 7). The Arm TRM's Table 5-3 gives the split for each value.

The first job is preemption. The preemption bits decide whether a newly pending interrupt can interrupt a handler that is already running. The second job is the sub-priority. The sub-priority bits only decide which of two pending interrupts runs first when they have the same preemption value and neither is running. A sub-priority can never interrupt a running handler.

For grouping 3 (PRIGROUP = 011), the TRM table gives a general 8-bit example of 16 preemption levels and 16 sub-priority levels. On the STM32F103, which implements only four bits, grouping 3 gives 16 preemption levels and no sub-priority, because all four bits go to preemption. The CMSIS helper NVIC_EncodePriority() computes the same split from the grouping, and it puts the preemption value in the top bits. The STM32F1 HAL also uses this grouping: HAL_Init() calls the group-4 setting, which is the value 3 in the HAL's NVIC_PRIORITYGROUP_4 macro (stm32f1xx_hal_cortex.h, and stm32f1xx_hal.c). So a HAL program starts with grouping 3, and this lesson uses the same grouping on purpose. 

/* Grouping 3 on this device: 4 preemption bits, 0 sub-priority bits. */
NVIC_SetPriorityGrouping(3);
NVIC_SetPriority(TIM2_IRQn,  NVIC_EncodePriority(3, 0, 0));  /* most urgent: may preempt */
NVIC_SetPriority(EXTI0_IRQn, NVIC_EncodePriority(3, 2, 0));  /* lower: can be preempted by TIM2 */
NVIC_EnableIRQ(TIM2_IRQn);
NVIC_EnableIRQ(EXTI0_IRQn);

The first line sets the grouping, which applies to every source. The next two lines set each source's priority, and the helper's arguments are the grouping, the preemption value and the sub-priority value. TIM2 gets preemption value 0 and EXTI0 gets 2. Both sub-priorities are 0, because there are none to set. The last two lines enable the sources, after the priorities are set, so no interrupt can fire at the reset priority of 0.

The reset value of every priority is 0, which is the highest. If you enable two sources and forget to set their priorities, both run at the top level and neither can preempt the other. Set the grouping and the priorities before you enable the sources, as the solution does.

The order also matters for the grouping itself. The stored bits in each priority register do not change when you change PRIGROUP, but their meaning does. If you set the priorities under grouping 4 and then switch to grouping 3, the same stored values now have a different preemption split. Set the grouping once, first, and keep it fixed.

Concept 3: when one interrupt may interrupt another

The TRM states the rule directly in section 5.5: an interrupt can preempt another interrupt in progress only if its preemption priority is higher than that of the interrupt in progress. "Higher" here means a lower number. Equal values do not preempt each other, even if one has been running for a long time, so the running handler always finishes first.

When two interrupts are pending and neither is running, the one with the higher priority starts first. If their preemption values are equal, the sub-priority decides. If that is equal too, the TRM's section 5.3.2 says the lower exception number wins. With grouping 3 there are no sub-priority bits, so two pending interrupts at the same priority run in that fixed hardware order, with the lower interrupt number first.

Nesting is therefore a chain. A handler can be interrupted by a more urgent source, which can itself be interrupted by a still more urgent one, and each handler resumes when the one above it returns. The number of nested handlers is limited by the number of distinct priority levels, which is 16 on this device.

Concept 4: the cost of entering a handler

Latency is the time from the moment an interrupt request is raised to the moment the first instruction of its handler runs. It is a number you can measure, and a deadline is usually written as a bound on it. On the Cortex-M3 the entry sequence takes 12 cycles in the usual case. The TRM gives this in section 5.5 and Figure 5-2: the core pushes the eight-word frame (lesson 34), fetches the vector, and starts the handler, and the TRM counts 12 cycles from the request to the first handler instruction in the execute stage. Arm Cortex-M3 TRM DDI0337G, section 5.5 and Figure 5-2

At 8 MHz, a 12-cycle entry is 12 ÷ 8 000 000 seconds, which is 1.5 µs. That is the time between the button press and the handler's first instruction, if nothing else is running. It is small, but it adds to every interrupt the system takes.

Two cases change the cost. The first is tail-chaining. When one handler finishes and another interrupt is already pending with a higher priority than every stacked frame, the core does not pop the frame and push it again. The TRM, section 5.6, says it skips the pop of eight registers and the push of eight registers, and the new handler starts six cycles after the previous one exits (Figure 5-3). Tail-chaining is a saving, and it is the reason back-to-back interrupts are cheap. The glossary calls it tail-chaining.

The second case is late arrival. A higher-priority interrupt can arrive while the core is still stacking for a lower-priority one, and the TRM's section 5.7 says the stacking is not repeated. The new, more urgent interrupt takes over, and it does not wait for the first handler to start. Late arrival is also a saving, and it shortens the worst case.

Latency excludes the time the CPU spends inside a handler at the same or a higher priority, and that is the number that matters for a deadline. A short handler that is blocked by a long handler at a higher priority misses its deadline, however fast its own code is.

Concept 5: what delays an urgent handler

A higher-priority interrupt does not have to wait for a lower-priority handler to reach a convenient point. With preemption enabled, a more urgent request interrupts the running handler at the next instruction boundary, and the TRM's section 5.5 rule applies at once. So a long handler at priority 2 does not delay a handler at priority 0, as long as the core is not inside a region where interrupts are masked.

The things that do delay an urgent handler are three. The first is a region where interrupts are disabled, such as the PRIMASK bit set by __disable_irq(), which is the tool of a critical section (lesson 57). While it is set, no interrupt at all can start, so a long critical section adds to the latency of every source. The second is a handler at the same or a higher priority, which is already running and cannot be preempted. The third is the entry cost itself, 12 cycles, plus any tail-chain or late-arrival delay.

This is why the solution in this lesson is written with its own short disabled window. The log update in log_event() disables interrupts for a few instructions, because two handlers at different priorities share the log index. The window is short, and that is the trade-off: a little latency for correct shared data.

Worked example: a button, a slow handler and a timer

The solution has three events in play: a button press that raises EXTI0 at priority 2, a timer that raises TIM2 at priority 0 every 10 ms, and a 30 ms busy-wait inside the EXTI0 handler. Walk through one press, with real numbers.

  1. At time 0 the button goes low, and the EXTI0 request is pending. Nothing else is running, so the core enters the EXTI0 handler after the 12-cycle entry, which is 1.5 µs at 8 MHz.
  2. The handler logs EXTI0 enter, sets g_exti_active, and busy-waits for 30 000 µs of the 1 µs stopwatch on TIM3.
  3. Within the next 10 ms the TIM2 update fires. TIM2 has priority 0 and EXTI0 has priority 2, so 0 is lower than 2 and TIM2 preempts. The core stacks a new frame, which is the full entry sequence, and runs the TIM2 handler.
  4. The TIM2 handler sees g_exti_active = 1, so it logs TIM2 nested in EXTI0, and it returns. The core pops the frame and EXTI0 resumes its busy-wait.
  5. The timer fires every 10 ms, so it preempts again during the rest of the 30 ms wait. The log then shows two or three nested entries, and finally EXTI0 exit.

Count the sources of time. The first 1.5 µs is the entry. The busy-wait is 30 ms. Each nested TIM2 costs its own entry of 1.5 µs, plus its short body, plus the exit. The solution is designed so that the timer's latency is the entry cost, and not the 30 ms. If you change the priorities so that TIM2 has the same priority as EXTI0, the nested lines disappear, and the timer waits for the full 30 ms. That is the observation this lesson asks you to make.

Common mistakes and how to spot them

The first mistake is leaving the priorities at their reset value of 0. Both sources then run at the top level, and neither can preempt the other. The symptom in the log is that every TIM2 tick line comes after EXTI0 exit, because TIM2 waits for the handler to finish. The fix is to set the grouping and both priorities before you enable the sources, as the solution does in nvic_start().

The second mistake is reversing the number. A student who expects a higher number to be more urgent gives TIM2 priority 2 and EXTI0 priority 0. The log looks like the first case: TIM2 tick lines come after EXTI0 exit, with no nesting. The startup line gives it away, because it prints TIM2 prio=2 EXTI0 prio=0, which is the reverse of the intent. The fix is to remember that a lower number is more urgent, and to check it with the TRM's statement in section 5.5.

The third mistake is changing the grouping after the priorities are set. The priority bits in each register are unchanged, but the split between preemption and sub-priority changes. The symptom is a pair of sources whose order flips, with no change in their numbers. The fix is to call NVIC_SetPriorityGrouping() once, before any priority is set, and never again.

The fourth mistake is sharing data between handlers at different priorities without a critical section. The log index in the solution is written by both handlers, and a nested handler can interrupt the first while it updates the index. The symptom is a log entry that is missing, duplicated or out of order, and it appears only when the nesting happens, which is rare. The fix is the short PRIMASK window in log_event(), as the solution uses, and it is covered in lesson 57.

The fifth mistake is a long handler at the same priority as an urgent one. Two sources at priority 0 cannot preempt each other, so an urgent source can wait for the whole of a long handler. The symptom is a deadline that is missed by roughly the length of the long handler. The fix is to give the urgent source a higher priority, or to move the long work out of the handler into the main loop, as lesson 70 did with its ring buffer.

In real projects

In production firmware the priority table is written down before the code, in a header or a design document. Each source has a name, a preemption priority and a reason, so a reviewer can check that the most time-critical source is the most urgent. Teams often use a small number of levels, for example one for the motor control, one for the communication and one for the background work, and they leave gaps so that a new source can be inserted later. They also keep their handlers short, so that the latency stays inside the budget.

A senior engineer reviewing interrupt code checks four things. The grouping is set once, before any priority. Every enabled source has a priority that was set on purpose, not the reset value. The shared data is protected by a documented critical section, and its window is short. The latency is measured on the real board, with a timestamp at the entry and the exit of the handler, because a number in a table is not a measurement. Interviewers often ask how a 30 ms handler can make a 100 Hz timer miss its deadline, and the answer usually concerns priority rather than speed.

Summary

  • The NVIC gives each interrupt source an enable bit and a priority. The STM32F1 implements 4 priority bits, so priorities run from 0 to 15.
  • A lower number is more urgent. The reset value 0 is the most urgent, so an unconfigured source is a trap.
  • PRIGROUP in AIRCR splits the bits into preemption and sub-priority. With grouping 3 on this device all four bits are preemption bits.
  • A handler is preempted only by a pending interrupt with a strictly lower preemption value. Equal values never preempt each other.
  • Entry takes 12 cycles (1.5 µs at 8 MHz). Tail-chaining starts the next handler after 6 cycles, and late arrival lets a more urgent request take over during stacking.
  • What delays an urgent handler is masked interrupts (PRIMASK) and handlers at the same or a higher priority, not a lower-priority handler that is running.
  • Set the grouping once, set every priority, and only then enable the sources.

"A 100 Hz timer misses its deadline on a board where a 30 ms handler runs on another interrupt. What do you check first?" Answer out loud in 60 seconds, then compare.

Model answer

First check the priorities. If the timer and the slow handler share a priority, or the timer is numerically higher, the timer cannot preempt the slow one, and it waits up to 30 ms. Fix the grouping and the priorities so that the timer is the most urgent source. Second, check whether the slow handler does work that belongs in the main loop: an ISR should set a flag or push to a queue, not run 30 ms of code. Third, check for critical sections (PRIMASK or BASEPRI) that stretch the disabled window. Measure the latency with a timestamp at the entry and the exit of the timer handler, because the fix is only real when the measured number changes.
