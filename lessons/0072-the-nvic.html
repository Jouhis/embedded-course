The NVIC: priorities, preemption, latency

When two interrupts fire at once, the NVIC decides which one runs first and whether a running handler can be interrupted. Get the priority grouping wrong and your timing bugs will only show up under load.

By the end of this lesson you can set the priority grouping and the priority of two interrupt sources with CMSIS, say which one preempts which, and explain the 12-cycle entry cost and tail-chaining, using the Arm and ST sources.

The idea

The NVIC (Nested Vectored Interrupt Controller) holds one enable bit and one priority value for each interrupt source. When a source fires, the NVIC picks the highest-priority pending interrupt, and the core starts its handler. Lesson 34 explains the stack frame and the entry sequence. This lesson is about the choice the NVIC makes before that sequence starts.

On the Cortex-M3 a lower number is a higher priority. Priority 0 is the most urgent configurable interrupt. The STM32F1 implements 4 priority bits, which the device header records as __NVIC_PRIO_BITS 4U, so each priority is a value from 0 to 15 (stm32f103xb.h). Only the top four bits of the 8-bit priority field are used. The lower four bits read as zero. A priority number is not a count of anything. Priority 2 is not "twice as urgent" as priority 4. It only says which one wins when both are pending, and whether one can interrupt the other.

Preemption and sub-priority

The priority grouping in AIRCR (the PRIGROUP field, bits 10 to 8 of the register) splits the implemented bits into two parts. The preemption part decides whether a new interrupt can interrupt a running handler. The sub-priority part only decides which of two pending interrupts runs first when both have the same preemption value and neither is running. CMSIS sets the grouping with NVIC_SetPriorityGrouping() and builds a value with NVIC_EncodePriority() (core_cm3.h). Arm Cortex-M3 Devices Generic User Guide, the NVIC section 

/* Grouping 3 on this device: 4 preemption bits, 0 sub-priority bits. */
NVIC_SetPriorityGrouping(3);
NVIC_SetPriority(TIM2_IRQn,  NVIC_EncodePriority(3, 0, 0));  /* most urgent: may preempt */
NVIC_SetPriority(EXTI0_IRQn, NVIC_EncodePriority(3, 2, 0));  /* lower: can be preempted by TIM2 */
NVIC_EnableIRQ(TIM2_IRQn);
NVIC_EnableIRQ(EXTI0_IRQn);

A preemption happens only when the new interrupt has a numerically lower preemption value than the one running. Equal values do not preempt each other, even if one has been running for a long time. With grouping 3 there are no sub-priority bits, so two pending interrupts of equal priority run in a fixed hardware order.

The reset value of every priority is 0, which is the highest. If you enable two sources and forget to set their priorities, both run at the top level and neither can preempt the other. Set the grouping and the priorities before you enable the sources, as the solution does.

Latency: 12 cycles and tail-chaining

On the Cortex-M3 the entry sequence takes 12 cycles in the usual case: stacking, the vector fetch and the start of the handler. Tail-chaining (a pending exception starts right after the first one returns, with no pop and push in between) and late arrival (a higher-priority exception arrives while the stacking is in progress) change that cost. The timing diagram and the rules are in the Arm TRM. Arm Cortex-M3 TRM DDI0337G, section 5.5 (Figure 5-2 for the 12-cycle entry), section 5.6 (tail-chaining) and section 5.7 (late arrival) Latency is the time from the interrupt request to the first instruction of the handler. It excludes the time the CPU spends in a higher-priority handler, and that is the number that matters for a deadline.

Latency is not the same as response time. A short handler at a high priority can be delayed by a long handler at a lower priority only if the lower one has no preemption point, which is why the EXTI handler below is written to be preempted. The disabled-interrupt window of a critical section (lesson 57) adds to the latency of every source, so keep it short.

Nested interrupts on real hardware and in this course

On the Cortex-M3 a handler can be preempted by a higher-priority exception, and the CPU then runs nested handlers. The course's own teaching CPU (assets/cpusim.js) does not model nesting, and its notes say so. The Wokwi simulator is a different program, and this course has not checked its nesting behaviour in a lesson, so the demo below prints what the hardware should do and says so in its expected output. If a test fails in the simulator, check the real board first.

Try it in Wokwi

The button on PB0 raises EXTI0. PB0 is routed to EXTI line 0 through the AFIO external-interrupt register (AFIO->EXTICR[0], which the solution sets to the PB value). The pin itself is on the default mapping in the STM32F103x8/xB datasheet, "Pinouts and pin description" table. The EXTI0 handler is slow: it busy-waits for about 30 ms, at priority 2. A timer on TIM2 raises an update interrupt every 10 ms, at priority 0. The log records every event with a sequence number, so the order is visible on the serial monitor.

  2. Your task: in nvic_start(), set the grouping to 3, set TIM2 to priority 0 and EXTI0 to priority 2, using NVIC_EncodePriority. Then press the button.
  3. You will know it works when the serial monitor shows TIM2 nested in EXTI0 between the EXTI0 enter and EXTI0 exit lines. Before you fix the priorities, the starter shows only TIM2 tick lines after the EXTI0 exit.

"A 100 Hz timer misses its deadline on a board where a 30 ms handler runs on another interrupt. What do you check first?" Answer out loud in 60 seconds, then compare.

Model answer

First check the priorities. If the timer and the slow handler share a priority, or the timer is numerically higher, the timer cannot preempt the slow one, and it waits up to 30 ms. Fix the grouping and the priorities so that the timer is the most urgent source. Second, check whether the slow handler does work that belongs in the main loop: an ISR should set a flag or push to a queue, not run 30 ms of code. Third, check for critical sections (PRIMASK or BASEPRI) that stretch the disabled window. Measure the latency with a timestamp at the entry and the exit of the timer handler, because the fix is only real when the measured number changes.

Arm Cortex-M3 Technical Reference Manual, DDI0337G (Keil copy): read section 5.5 for the 12-cycle entry, Figure 5-2, then sections 5.6 and 5.7 for tail-chaining and late arrival. For the register-level view of the priority registers, read PM0056 (the STM32F10xxx Cortex-M3 programming manual), in its NVIC section.
