The NVIC

Interrupt priorities, preemption and latency

By the end of this lesson you can set the priority grouping and the priority of two interrupt sources with CMSIS, say which one preempts which, and explain the 12-cycle entry cost and tail-chaining, using the Arm and ST sources.

Two interrupts at the same moment

Lesson 70 made the USART and an external-interrupt pin raise interrupts, with a ring buffer letting the main loop read the events later, lesson 57 explained what an interrupt is and why a handler must be short, and lesson 34 described what the core does on entry, pushing a frame of registers onto the stack and fetching the handler's address from the vector table. This lesson concerns the decision the interrupt controller makes before that entry starts, when two interrupts fire at once and one must run first.

Every product with more than one interrupt source meets the problem. A motor controller must read its encoder within a few microseconds while also logging data over the UART, so a long logging handler must not make the encoder late, and a brake monitor must respond before a slower housekeeping timer. With the priorities wrong, a bug appears only when two events happen close together and never in a short test, which is why this lesson covers the rules as well as the register writes.

One priority per interrupt source

The NVIC (Nested Vectored Interrupt Controller) is the block inside the Cortex-M core that enables interrupt sources, gives each a priority and selects the one to run. Each source has an enable bit and a priority register, and when a source is pending and enabled, the NVIC compares its priority with that of any running handler, the core taking the new one if it is more urgent.

The priority register is 8 bits wide per source, but the STM32F1 implements only some of them, the device header recording __NVIC_PRIO_BITS 4U, so only the top four bits are used and the priority runs from 0 to 15 (stm32f103xb.h). PM0056 Rev 7 section 4.3.7 (Table 42) agrees that the processor implements only bits 7 to 4 of each priority field, and the Arm TRM puts the same rule generally in section 5.3.2, where, with four bits implemented, the top four bits set the priority and the lower four always read zero. A priority number is not a count of anything. Priority 2 is not "twice as urgent" as priority 4. It only says which one wins when both are pending, and whether one can interrupt the other.

On the Cortex-M3 a lower number is a higher priority (PM0056 Rev 7, section 2.3.5), so priority 0 is the most urgent configurable level and 15 the least urgent on this device, the opposite of what many people expect and the first thing to check when a priority looks backwards. Every priority resets to 0 (PM0056 Rev 7, section 4.3.7), the most urgent level, so a source that is never configured becomes the most urgent in the system rather than the least, a common trap.

Priority grouping into preemption and sub-priority

The four implemented bits do two jobs, and the priority grouping decides how many bits serve each. The grouping is set by the PRIGROUP field of AIRCR, the Application Interrupt and Reset Control Register, which the CMSIS header places at bits 10 to 8 (SCB_AIRCR_PRIGROUP_Pos is 8 and its mask 7), in agreement with PM0056 Rev 7, section 4.4.5, while the Arm TRM's Table 5-3 gives the split for each value.

The first job is preemption, the preemption bits deciding whether a newly pending interrupt can interrupt a handler already running. The second is the sub-priority, whose bits only decide which of two pending interrupts runs first when they share a preemption value and neither is running, so a sub-priority can never interrupt a running handler.

For grouping 3 (PRIGROUP = 011) the TRM table gives a general 8-bit example with 16 preemption levels and 16 sub-priority levels, while on the STM32F103, with only four bits, grouping 3 gives 16 preemption levels and no sub-priority, all four bits going to preemption (PM0056 Rev 7, section 4.4.5, Table 45). The CMSIS helper NVIC_EncodePriority() computes the same split from the grouping, placing the preemption value in the top bits, and the STM32F1 HAL uses the same grouping, HAL_Init() calling the group-4 setting, which is the value 3 in the HAL's NVIC_PRIORITYGROUP_4 macro (stm32f1xx_hal_cortex.h and stm32f1xx_hal.c), so a HAL program starts with grouping 3 and this lesson deliberately uses it too. 

/* Grouping 3 on this device: 4 preemption bits, 0 sub-priority bits. */
NVIC_SetPriorityGrouping(3);
NVIC_SetPriority(TIM2_IRQn,  NVIC_EncodePriority(3, 0, 0));  /* most urgent: may preempt */
NVIC_SetPriority(EXTI0_IRQn, NVIC_EncodePriority(3, 2, 0));  /* lower: can be preempted by TIM2 */
NVIC_EnableIRQ(TIM2_IRQn);
NVIC_EnableIRQ(EXTI0_IRQn);

The first line sets the grouping, which applies to every source, and the next two set each source's priority, the helper's arguments being the grouping, the preemption value and the sub-priority, so TIM2 gets preemption value 0 and EXTI0 gets 2, both with sub-priority 0 because there are none to set. The last two lines enable the sources only after the priorities are set, so that no interrupt can fire at the reset priority of 0.

The reset value of every priority is 0, which is the highest. If you enable two sources and forget to set their priorities, both run at the top level and neither can preempt the other. Set the grouping and the priorities before you enable the sources, as the solution does.

The order also matters for the grouping itself, because the stored bits of each priority register stay the same when PRIGROUP changes while their meaning does not: priorities set under grouping 4 and then read under grouping 3 have a different preemption split. The grouping is therefore set once, first, and kept fixed.

The preemption rule

The TRM states the rule directly in section 5.5: an interrupt can preempt another in progress only if its preemption priority is higher than that of the one in progress, higher meaning a lower number. Equal values never preempt each other, however long one has been running, so the running handler always finishes first (PM0056 Rev 7, section 2.3.6).

The NVIC works like triage in an emergency department: a more urgent patient, a higher preemption priority, interrupts the doctor at once, while a patient of equal urgency waits until the current one is finished, however long that takes, and the sub-priority only decides who is called first from the waiting room without ever interrupting anyone. Real triage can reassess a waiting patient whose condition worsens, though, whereas an interrupt's priority stays fixed unless the code changes it.

When two interrupts are pending and neither is running, the one with the higher priority starts first, the sub-priority deciding between equal preemption values, and if that is equal too, the TRM's section 5.3.2 lets the lower exception number win, PM0056 Rev 7, section 2.3.6, likewise processing the lowest IRQ number first. Grouping 3 leaves no sub-priority bits, so two pending interrupts at the same priority run in that fixed hardware order, the lower interrupt number first.

Nesting therefore forms a chain, a handler being interruptible by a more urgent source, which a still more urgent one can interrupt in turn, each handler resuming when the one above it returns, and the depth of nesting is limited by the number of distinct priority levels, 16 on this device.

Interrupt entry latency, tail-chaining and late arrival

Latency is the time from the moment an interrupt request is raised to the first instruction of its handler, a measurable number in which deadlines are usually written. On the Cortex-M3 the entry sequence usually takes 12 cycles, as the TRM gives in section 5.5 and Figure 5-2, during which the core pushes the eight-word frame (lesson 34), fetches the vector and starts the handler, the TRM counting from the request to the first handler instruction in the execute stage (Arm Cortex-M3 TRM DDI0337G, section 5.5 and Figure 5-2). The entry time is

tentry = Ncycles ÷ fcore(1)

where Ncycles is 12 and fcore the core clock, so at 8 MHz the entry lasts 12 ÷ 8 000 000 s = 1.5 µs, the time between the button press and the handler's first instruction when nothing else is running, small but added to every interrupt the system takes.

Two cases change the cost. The first is tail-chaining: when a handler finishes while another interrupt is already pending with a higher priority than every stacked frame, the core does not pop the frame and push it again, the TRM's section 5.6 stating that it skips the pop and the push of eight registers each, so the new handler starts six cycles after the previous one exits (Figure 5-3), which makes back-to-back interrupts cheap.

The second is late arrival, in which a higher-priority interrupt arrives while the core is still stacking for a lower-priority one, and the TRM's section 5.7 states that the stacking is not repeated, the new, more urgent interrupt taking over without waiting for the first handler to start, which shortens the worst case as well. The entry latency does not include the time spent waiting for a handler at the same or a higher priority, yet that waiting is what usually decides a deadline. A short handler blocked by a long one at a higher priority misses its deadline, however fast its own code is.

What delays an urgent handler

A higher-priority interrupt need not wait for a lower-priority handler to reach a convenient point, because with preemption a more urgent request interrupts the running handler at the next instruction boundary, as the TRM's section 5.5 rule says. A long handler at priority 2 therefore does not delay a handler at priority 0, as long as the core is not inside a region where interrupts are masked.

Three things do delay an urgent handler. The first is a region with interrupts disabled, such as the PRIMASK bit set by __disable_irq() for a critical section (lesson 57), during which no interrupt with a configurable priority can start (PM0056 Rev 7, section 2.1.3), so a long critical section adds to the latency of every source. The second is a running handler at the same or a higher priority, which cannot be preempted, and the third is the entry cost itself, 12 cycles, plus any tail-chain or late-arrival delay.

For this reason the solution keeps its own disabled window short. The log update in log_event() disables interrupts for a few instructions, because two handlers at different priorities share the log index, accepting a little latency in exchange for correct shared data.

Worked example: a button, a slow handler and a timer

The solution has three events in play, a button press raising EXTI0 at priority 2, a timer raising TIM2 at priority 0 every 10 ms and a 30 ms busy-wait inside the EXTI0 handler, and we walk through one press with real numbers. Before reading the steps, predict how many TIM2 lines appear between EXTI0 enter and EXTI0 exit.

  1. Enter EXTI0. At time 0 the button goes low and the EXTI0 request becomes pending, and with nothing else running the core enters the EXTI0 handler after the 12-cycle entry, 1.5 µs at 8 MHz.
  2. Start the slow work. The handler logs EXTI0 enter, sets g_exti_active and busy-waits for 30 000 µs of the 1 µs stopwatch on TIM3.
  3. Preempt. Within the next 10 ms the TIM2 update fires, and since TIM2's priority 0 is lower than EXTI0's 2, TIM2 preempts, the core stacking a new frame in a full entry sequence and running the TIM2 handler.
  4. Return. The TIM2 handler sees g_exti_active = 1, logs TIM2 nested in EXTI0 and returns, after which the core pops the frame and EXTI0 resumes its busy-wait.
  5. Repeat. The timer fires every 10 ms, so it preempts again during the rest of the 30 ms wait, and the log shows two or three nested entries before EXTI0 exit.

Counting the sources of time, the first 1.5 µs is the entry, the busy-wait 30 ms, and each nested TIM2 costs its own 1.5 µs entry, its short body and its exit, so the timer's latency is the entry cost rather than the 30 ms. Giving TIM2 the same priority as EXTI0 makes the nested lines disappear and the timer wait for the full 30 ms, the observation this lesson asks you to make.

Common mistakes and how to spot them

Priorities left at the reset value

Every TIM2 tick line comes after EXTI0 exit, because TIM2 waits for the handler to finish, both sources running at the reset value of 0, the top level, so neither can preempt the other. Set the grouping and both priorities before enabling the sources, as the solution does in nvic_start().

The priority numbers reversed

The log looks like the previous case, with TIM2 tick lines after EXTI0 exit and no nesting, but the startup line gives it away by printing TIM2 prio=2 EXTI0 prio=0, the reverse of the intent, because the author expected a higher number to be more urgent. Remember that a lower number is more urgent, and check it against the TRM's statement in section 5.5.

The grouping changed after the priorities

A pair of sources swaps order with no change to their numbers, because the priority bits in each register stay the same while the split between preemption and sub-priority changes. Call NVIC_SetPriorityGrouping() once, before any priority is set, and never again.

Shared data without a critical section

A log entry is occasionally missing, duplicated or out of order, only when nesting happens, which is rare, because both handlers write the log index and a nested handler can interrupt the first in the middle of its update. Use the short PRIMASK window in log_event(), as the solution does and lesson 57 explains.

A long handler at an urgent source's priority

A deadline is missed by roughly the length of a long handler, because two sources at priority 0 cannot preempt each other, so the urgent source waits for the whole long handler. Give the urgent source a higher priority, or move the long work out of the handler into the main loop, as lesson 70 did with its ring buffer.

Priority tables and latency budgets in products

In production firmware the priority table is written down before the code, in a header or a design document, each source having a name, a preemption priority and a reason, so that a reviewer can check that the most time-critical source is the most urgent. Teams often use a few levels, for example one for motor control, one for communication and one for background work, leaving gaps so that a new source can be inserted later, and they keep their handlers short so that the latency stays inside the budget.

A senior engineer reviewing interrupt code checks that the grouping is set once before any priority, that every enabled source has a deliberately chosen priority rather than the reset value, that shared data is protected by a documented critical section with a short window, and that the latency has been measured on the real board with timestamps at the entry and exit of the handler, because a number in a table is not a measurement. A 30 ms handler can make a 100 Hz timer miss its deadline, and the cause is usually priority rather than speed.

Summary

  • The NVIC gives each interrupt source an enable bit and a priority, and the STM32F1 implements 4 priority bits, so priorities run from 0 to 15.
  • A lower number is more urgent, and the reset value 0 is the most urgent, which makes an unconfigured source a trap.
  • PRIGROUP in AIRCR splits the bits into preemption and sub-priority, and with grouping 3 on this device all four are preemption bits.
  • A handler is preempted only by a pending interrupt with a strictly lower preemption value, so equal values never preempt each other.
  • Entry takes 12 cycles, 1.5 µs at 8 MHz, tail-chaining starts the next handler after 6 cycles, and late arrival lets a more urgent request take over during stacking.
  • An urgent handler is delayed by masked interrupts (PRIMASK) and by handlers at the same or a higher priority, not by a running lower-priority handler.
  • The grouping is set once, every priority is set, and only then are the sources enabled.
