Bit fields, unions, packing, and endianness

A sensor sends bytes, and a register holds bits. C offers bit-fields, unions and packed structs for both, but the standard leaves much of their layout to the compiler. Shifts and masks are the portable way.

By the end of this lesson you can parse a big-endian 16-bit value from a byte buffer with shifts, explain why a bit-field is not a portable register layout, and say what __attribute__((packed)) does and does not change.

Where we are and why it matters

Lesson 45 covered fixed-width types such as uint8_t and uint16_t, and how C promotes small integers before it does arithmetic on them. Lesson 47 showed a struct that overlays a peripheral's register block. This lesson deals with the data that moves between those two worlds: bytes that arrive from a sensor, and single bits inside a register or a status byte.

The problem is common in real work. A temperature sensor on an I2C or UART link sends a short frame: a header, two data bytes, and a status byte. The driver must turn those bytes into numbers, and it must pick out the single bits that mean "valid" or "in error". Many datasheets describe the frame with a table of byte offsets and bit numbers. Your code has to match that table exactly, on every compiler the team uses, for the life of the product. This lesson shows the portable way to do it.

Concepts, one at a time

Bits, bytes and masks

A bit is the smallest unit of storage, holding a 0 or a 1. A byte is eight bits, and it is the unit the memory system reads and writes. Bits inside a byte are numbered from 0 for the least significant bit (the one worth 1) up to 7 for the most significant (worth 128). A value written in hexadecimal shows each byte as two digits: 0xA5 is the bit pattern 1010 0101.

A mask is a constant that selects some bits. To keep only bits 1 and 0 of a byte, AND it with 0x03, which is the pattern 0000 0011. To move a field down to bit 0, shift it right. Masks and shifts are ordinary arithmetic on integers, so the compiler produces exactly the instructions you wrote. The CPU has no notion of "field": it only knows about values, AND, OR, and shift instructions.

What a bit-field is

A bit-field is a struct member with a width in bits. The declaration unsigned mode : 2; asks the compiler for a 2-bit member called mode. It looks like a register map, which is why it is tempting for hardware work. You can write status.mode instead of frame[3] & 0x03.

The problem is that the C standard does not fix where the bits go. The order of bit-fields inside a storage unit is implementation-defined, which means the compiler documents its choice but the standard does not decide it. Whether a bit-field may straddle a boundary between two storage units is also implementation-defined. The alignment of the storage unit is unspecified. Whether a plain int bit-field is signed or unsigned is implementation-defined too. The cppreference page on bit-fields lists each of these. cppreference, bit-field layout

The consequence is direct. The same declaration can put mode at bit 0 with one compiler and at a different bit with another, and the code still compiles and runs. A register map built on bit-fields then depends on the toolchain. For a register, the bit positions are fixed by the chip, so that dependency is the opposite of what you need. The bit positions of a register are set in silicon. The compiler does not get a say, so the C code must express them as numbers, not as a layout the compiler chooses.

Do not describe a hardware register with bit-fields in portable code. Use a fixed-width integer, and name the mask and shift constants. A mask such as 0x03 means the same bits on every compiler that follows the standard.

Byte order: the wire and the CPU

A multi-byte value, such as a 16-bit temperature, is stored as two bytes. Which byte comes first is a convention, and two parties must agree on it. The high byte is the one that carries the larger place values, and the low byte carries the smaller ones. A sensor that sends the high byte first is said to be big-endian on the wire. A sensor that sends the low byte first is little-endian.

Endianness is the order of the bytes of a multi-byte value in memory. A little-endian CPU stores the least significant byte at the lowest address. Cortex-M cores, including the Cortex-M0+ in the RP2040 and the Cortex-M3 in the STM32F1, are little-endian in this course. A sensor's wire format and the CPU's memory format can therefore disagree, and the code that copies bytes between them must account for it.

Padding and packing

Alignment is the rule that a value of a given size must start at an address that is a multiple of its size. A 32-bit value is aligned to 4, and a 16-bit value to 2. The CPU can read an aligned value in one access. An unaligned value may take extra accesses, or the core may refuse the access. To keep members aligned, the compiler inserts padding: unused bytes between struct members. A uint8_t followed by a uint16_t therefore has one byte of padding after the first member.

A packed struct removes that padding, so members sit at the smallest possible alignment. Packing changes where members sit in memory. It does not change the byte order of any member, and it does not make the CPU read unaligned data any faster.

Unions

A union is a type whose members all start at the same address. Its size is the size of its largest member. A union of a uint32_t and an array of four uint8_t lets you name the same four bytes either as one number or as bytes. It looks convenient for splitting a register into bytes, but reading a union member other than the one most recently written is subtle in C, and the result depends on rules you may not want to rely on. The next sections show a plain shift does the same job without the subtlety.

A worked example: one frame, byte by byte

Take the 4-byte frame from the course project. Byte 0 is a header that must equal 0xA5. Bytes 1 and 2 hold the temperature in hundredths of a degree, big-endian. Byte 3 is a status byte: bits 1 and 0 are the mode, and bit 2 is a valid flag. The test frame is: 

frame[0] = 0xA5   header
frame[1] = 0x12   temperature, high byte
frame[2] = 0x34   temperature, low byte
frame[3] = 0x05   status

Step 1: check the header. 0xA5 equals FRAME_HEADER, so the frame is accepted. A bad header, such as 0x5A, is rejected before any byte is read further.

Step 2: build the temperature with shifts. Shift the high byte left by eight bits. 0x12 is 0001 0010, and shifting it left by eight places gives 0x1200: each bit moves up eight positions, and eight zero bits fill the bottom. Now OR in the low byte: 0x1200 | 0x34 = 0x1234. The OR works because the low byte's bits are all zero in 0x1200, so no bit is lost. In decimal, 0x1234 is 1 × 4096 + 2 × 256 + 3 × 16 + 4 = 4660.

Step 3: take the status fields. 0x05 is 0000 0101. The mode is bits 1 and 0, so 0x05 & 0x03 keeps 0000 0001, which is 1. The valid flag is bit 2, so (0x05 >> 2) & 0x01 shifts the byte down two places to 0000 0001 and keeps bit 0, giving 1.

Step 4: see what a plain copy does on a little-endian CPU. The starter uses memcpy(&raw, &frame[1], 2). That copies the two bytes 0x12, 0x34 into memory exactly as they are. Memory now holds 0x12 at the lower address. On a little-endian CPU the lower address is the least significant byte, so the value read back is 0x3412, which is 3 × 4096 + 4 × 256 + 1 × 16 + 2 = 13330. The bytes have swapped, and the temperature is wrong by a factor of about three.

The two results differ only in how the bytes were combined. The shift form combines them as values, so it is correct on any CPU. The copy form combines them in memory, so it depends on the CPU's byte order.

The code, line by line

The project's solution builds the temperature with one expression. Here it is, with each part explained: 

/* frame[1] is the high byte, frame[2] the low byte: big-endian on the wire */
out->temp_centi_c = (uint16_t)(((uint16_t)frame[1] << 8) | (uint16_t)frame[2]);

frame[1] is a uint8_t read from the array. In the expression, it is first converted to uint16_t. C then performs the usual integer promotions, which turn any operand narrower than int into an int. On these cores int is 32 bits, so the 8-bit value fits with room to spare. The cast makes the intended type explicit in the source, so a reader does not need to recall the promotion rules.

The << 8 moves the high byte into bits 15 to 8. Because the value is held in at least 16 bits, nothing falls off the top. The (uint16_t)frame[2] term is the low byte, already in bits 7 to 0, and | combines the two without any carry, because the bit ranges do not overlap. The outer (uint16_t) cast converts the result back to the 16-bit type of the struct member. Nothing in the expression reads memory in a particular byte order, so the code runs the same on a big-endian core.

The starter's line is the one to avoid: 

uint16_t raw;
memcpy(&raw, &frame[1], 2);      /* copies the bytes in host order: wrong on little-endian */
out->temp_centi_c = raw;

memcpy copies 2 bytes starting at &frame[1] into raw. It does no byte reordering. The copy is correct for data that was written by the same CPU in the same byte order, such as a struct moved between two buffers. For a wire format, the sender's order is fixed and the receiver's is not, so the copy is wrong on one of them.

The status lines use masks, and each one names the bits it means: 

out->mode  = frame[3] & 0x03U;          /* bits 1:0: keep the two low bits */
out->valid = (frame[3] >> 2) & 0x01U;   /* bit 2: move it to bit 0, then keep one bit */

The mask 0x03U is binary 0000 0011, so the AND keeps bits 1 and 0 and clears the rest. The U suffix makes the constant unsigned, which keeps the arithmetic unsigned as well. The second line first shifts the byte right by two, so bit 2 becomes bit 0, and then keeps only that bit with 0x01U. Both lines are exact, and a reviewer can check each bit number against the datasheet table.

The starter also rejects a frame with the wrong header. The check comes before the parse, so a bad frame never reaches the output fields. The solution keeps the same order, and the test in main prints bad header rejected when the second frame fails the check.

Packed structs, in one example

Sometimes a driver must describe the whole frame as a struct, so that it can be copied from a buffer in one call. The struct then has to match the wire layout, and packing is the tool for that: 

typedef struct __attribute__((packed)) {
    uint8_t  header;      /* offset 0 */
    uint16_t temp;        /* offset 1 with packing; offset 2 without */
    uint8_t  status;      /* offset 3 with packing; offset 4 without */
} WireFrame;

Without the attribute, the compiler aligns temp to an even address, so it leaves one byte of padding after header. With the attribute, temp sits at offset 1 and status at offset 3, which matches the wire. The GCC manual says a packed member "should have the smallest possible alignment", and for a struct it says each member is placed "to minimize the memory required". GCC manual, common attributes: packed

Packing does two things and not a third. It fixes the offsets of the members. It does not reverse the bytes of temp, so the value in temp is still whatever the bytes in memory say, and you still need the shift form to read a big-endian field. And it creates unaligned members. On a core without unaligned access, a load of temp from an odd address can fault. GCC defines the macro __ARM_FEATURE_UNALIGNED for -mcpu=cortex-m3 but not for -mcpu=cortex-m0plus, which is the compiler's own statement of the difference between the two cores. A safe driver reads the fields with shifts, and uses the packed struct only as a description.

Common mistakes and how to spot them

  1. Copying a wire value with memcpy or a pointer cast. The value is wrong by a byte swap. In the project the symptom is temp=13330 where temp=4660 is expected. The fix is the shift expression. The check is to find every place a multi-byte value is taken from a buffer and confirm it uses shifts.
  2. Casting a byte buffer to a 16-bit pointer. Code such as *(uint16_t *)&frame[1] is unaligned, because frame[1] sits at an odd address when the buffer is aligned. On a core without unaligned access, this can fault, and the debugger shows a HardFault. On a core that allows it, the value is still byte-swapped. The fix is the same shift form.
  3. Losing the low byte in the OR. A line such as raw = frame[1] << 8 | frame[2] can be correct, but a line that shifts the wrong byte, or uses & where it means |, produces a value with the low byte missing. In the project, a temperature of 0x1200, which is 4608, means the low byte was dropped. The symptom is a value that is correct in its high byte and zero in its low byte. Print the value in hexadecimal to see it at once.
  4. A bit-field for a register. The code compiles and the bits are right on one toolchain. On a second compiler, or after an upgrade, the same struct puts the field at a different bit, and the device behaves differently. The symptom appears only after a toolchain change, so it is hard to trace. The fix is a mask and a shift with named constants.
  5. Believing packing fixes the byte order. A team marks a struct packed and expects the big-endian temperature to read correctly. The value is still swapped, because packing moves members and does not reverse their bytes. The symptom is the same 13330 as before. The fix is to read the fields with shifts, and to keep packing for the layout only.

In real projects

Driver code for sensors and radios is mostly parsing. A typical driver reads a frame, checks a header and a checksum, and then extracts fields with masks and shifts. Teams keep these functions small and test them on a PC with a table of frames. The tests use the same functions as the firmware, so a byte-order error shows up on the desk, not on the bench.

Code review checks three things in such a driver. Each multi-byte field must be parsed with shifts, not with a cast. Each mask and shift must name the bit positions from the datasheet, so the reviewer can check them against the table. And any struct that describes a wire frame must say whether it is packed and why. Reviewers also look for bit-fields in any code that touches a register, and they ask for the mask form instead.

The interview question about parsing a big-endian value is standard for embedded roles. The answer that impresses names the shift and OR, explains that the result does not depend on byte order, and states why a pointer cast fails. The model answer at the end of this lesson covers these points.

Summary

  • A bit-field's layout is implementation-defined, so it is not a portable register map. Use a fixed-width integer with named masks and shifts.
  • A wire value is combined with shifts and OR: (hi << 8) | lo. The result is a number, so it does not depend on the CPU's byte order.
  • A copy with memcpy or a pointer cast gives the bytes in host order. On a little-endian Cortex-M, 0x12 0x34 reads as 0x3412, which is 13330.
  • Cortex-M cores are little-endian in this course, and -dM -E prints the macros that say so.
  • A packed struct removes padding and fixes member offsets. It does not change byte order and does not make unaligned access safe.
  • Mask with 0x03U to keep bits 1 and 0, and shift right by 2 to move bit 2 down to bit 0.
  • A union reads the same bytes under two types, which is subtle in C. Use shifts for conversions.

Model answer

Read the two bytes with explicit indices, cast each to uint16_t, shift the high byte left by eight, and OR in the low byte. That works on any CPU, because it combines the bytes as values and never looks at memory order. Casting the buffer to a uint16_t pointer depends on alignment and byte order: an odd address can be unaligned, and on a core without unaligned access the load can fault, while on a little-endian core the bytes come out swapped. A bit-field struct for the same data depends on the compiler's layout, so it is not portable either.
