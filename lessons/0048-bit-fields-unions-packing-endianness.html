Bit fields, unions, packing, and endianness

Bit and byte layout of data in C

By the end of this lesson you can parse a big-endian 16-bit value from a byte buffer with shifts, explain why a bit-field is not a portable register layout, and say what __attribute__((packed)) does and does not change.

Bytes from sensors and bits in registers

Lesson 45 covered fixed-width types such as uint8_t and uint16_t and how C promotes small integers before doing arithmetic on them, and lesson 47 showed a struct overlaying a peripheral's register block. This lesson deals with the data that moves between those two worlds, the bytes that arrive from a sensor and the single bits inside a register or a status byte.

The task comes up often in real work. A temperature sensor on an I2C or UART link sends a short frame of a header, two data bytes and a status byte, and the driver must turn the bytes into numbers and pick out the single bits meaning "valid" or "in error". Datasheets usually describe such a frame with a table of byte offsets and bit numbers, which the code must match exactly on every compiler the team uses for the life of the product, and this lesson shows the portable way to do it.

Bits, bytes and masks

A bit is the smallest unit of storage, holding a 0 or a 1, and a byte is eight bits, the unit the memory system reads and writes. Bits inside a byte are numbered from 0 for the least significant bit, worth 1, up to 7 for the most significant, worth 128, and hexadecimal shows each byte as two digits, so 0xA5 is the bit pattern 1010 0101.

A mask is a constant that selects some bits. ANDing a byte with 0x03, the pattern 0000 0011, keeps only bits 1 and 0, and a right shift moves a field down to bit 0. Masks and shifts are ordinary integer arithmetic, so the compiler produces exactly the instructions written, and the CPU itself has no notion of a field, only of values and of AND, OR and shift instructions.

Bit-fields and their implementation-defined layout

A bit-field is a struct member with a width in bits, so the declaration unsigned mode : 2; asks the compiler for a 2-bit member called mode. It looks like a register map, which makes it tempting for hardware work, since status.mode reads better than frame[3] & 0x03.

The C standard, however, does not fix where the bits go. The order of bit-fields inside a storage unit is implementation-defined, meaning that the compiler documents its choice but the standard does not decide it, and the same holds for whether a bit-field may straddle two storage units and whether a plain int bit-field is signed, while the alignment of the storage unit is unspecified. The cppreference page on bit-fields lists each of these. cppreference, bit-field layout

The consequence is direct: the same declaration can put mode at bit 0 with one compiler and at another bit with a different one, while the code still compiles and runs, so a register map built on bit-fields depends on the toolchain. A register's bit positions are fixed by the chip, which makes that dependency exactly what a driver must avoid. The bit positions of a register are set in silicon and the compiler has no say in them, so the C code must express them as numbers rather than as a layout the compiler chooses.

Do not describe a hardware register with bit-fields in portable code. Use a fixed-width integer with named mask and shift constants, because a mask such as 0x03 selects the same bits on every compiler that follows the standard.

Byte order on the wire and in the CPU

A multi-byte value such as a 16-bit temperature is stored as two bytes, and which comes first is a convention on which both parties must agree. The high byte carries the larger place values and the low byte the smaller ones, so a sensor that sends the high byte first is big-endian on the wire and one that sends the low byte first is little-endian.

Endianness is the order of a multi-byte value's bytes in memory, and a little-endian CPU stores the least significant byte at the lowest address. The Cortex-M cores in this course, the Cortex-M0+ in the RP2040 and the Cortex-M3 in the STM32F1, run little-endian, which the compiler confirms in its predefined macros, printed with arm-none-eabi-gcc -dM -E, where __BYTE_ORDER__ equals __ORDER_LITTLE_ENDIAN__. A sensor's wire format and the CPU's memory format can therefore disagree, and code that copies bytes between them must account for it.

Byte order resembles the way a date is written: 2026-11-09 and 09.11.2026 are the same day in a different order, and either can be read only by someone who knows the convention. The bytes 0x01 0x2C from a sensor likewise mean 300 if the sensor sends the high byte first and 11 265 if the opposite is assumed, so the datasheet states the order and the code must follow it. A date's parts at least differ in range, whereas two bytes look equally plausible either way round, so a byte-order error rarely reveals itself.

Alignment, padding and packing

Alignment is the rule that a value of a given size starts at an address that is a multiple of its size, so a 32-bit value is aligned to 4 and a 16-bit value to 2. The CPU reads an aligned value in one access, whereas an unaligned one may take extra accesses or be refused by the core, so to keep members aligned the compiler inserts padding, unused bytes between struct members, and a uint8_t followed by a uint16_t gets one byte of padding after the first member.

A packed struct removes that padding, placing members at the smallest possible alignment. Packing changes where members sit in memory but neither changes the byte order of any member nor makes the CPU read unaligned data any faster.

Unions

A union is a type whose members all start at the same address, its size being that of its largest member, so a union of a uint32_t and an array of four uint8_t names the same four bytes either as one number or as bytes. That looks convenient for splitting a register into bytes, but reading a member other than the one most recently written is subtle in C and depends on rules you may not want to rely on, and the following sections show that a plain shift does the same job without the subtlety.

Worked example: one frame byte by byte

We take the 4-byte frame from the course project, in which byte 0 is a header that must equal 0xA5, bytes 1 and 2 hold the temperature in hundredths of a degree, big-endian, and byte 3 is a status byte whose bits 1 and 0 are the mode and whose bit 2 is a valid flag. The test frame is as follows. 

frame[0] = 0xA5   header
frame[1] = 0x12   temperature, high byte
frame[2] = 0x34   temperature, low byte
frame[3] = 0x05   status

Before working through it, predict the temperature a plain memory copy would give on a little-endian CPU.

  1. Check the header. 0xA5 equals FRAME_HEADER, so the frame is accepted, whereas a bad header such as 0x5A would be rejected before any further byte is read.
  2. Build the temperature with shifts. The high byte 0x12, 0001 0010, shifted left by eight places becomes 0x1200, every bit moving up eight positions with zeros filling the bottom, and ORing in the low byte gives 0x1200 | 0x34 = 0x1234 with no bit lost, because the low byte's bits are all zero in 0x1200. In decimal 0x1234 is 1 × 4 096 + 2 × 256 + 3 × 16 + 4 = 4 660.
  3. Take the status fields. 0x05 is 0000 0101, so the mode, bits 1 and 0, is 0x05 & 0x03 = 0000 0001, or 1, and the valid flag, bit 2, is (0x05 >> 2) & 0x01, which shifts the byte down to 0000 0001 and keeps bit 0, giving 1.
  4. See what a plain copy does. The starter's memcpy(&raw, &frame[1], 2) copies the bytes 0x12, 0x34 into memory unchanged, with 0x12 at the lower address, which a little-endian CPU treats as the least significant byte, so the value read back is 0x3412, or 3 × 4 096 + 4 × 256 + 1 × 16 + 2 = 13 330, and the temperature is wrong by a factor of about three.

The two results differ only in how the bytes were combined: the shift form combines them as values and is correct on any CPU, while the copy form combines them in memory and depends on the CPU's byte order.

  1. The 4-byte frame arrives. Check the header first: 0xA5 equals FRAME_HEADER, so the frame is accepted.
  2. The temperature is big-endian: high byte first. Shift 0x12 left by eight bits: 0x1200.
  3. OR in the low byte: 0x1200 | 0x34 = 0x1234, which is 4660 hundredths of a degree, 46.60 °C. This joins the bytes as values, so it gives the same answer on any CPU.
  4. The status byte holds two fields. The mode is bits 1 and 0: 0x05 & 0x03 = 1. The valid flag is bit 2: (0x05 >> 2) & 1 = 1.
  5. The starter instead copies the two bytes into a uint16_t with memcpy. Memory now holds 0x12 at the lower address and 0x34 above it, exactly as on the wire.
  6. On a little-endian CPU the lower address is the least significant byte, so the value reads as 0x3412, which is 13330. Same bytes, wrong number: the copy depends on the CPU's byte order.

The parsing code line by line

The project's solution builds the temperature in a single expression. 

/* frame[1] is the high byte, frame[2] the low byte: big-endian on the wire */
out->temp_centi_c = (uint16_t)(((uint16_t)frame[1] << 8) | (uint16_t)frame[2]);

frame[1] is a uint8_t read from the array and first converted to uint16_t, after which the usual integer promotions turn every operand narrower than int into an int, 32 bits on these cores, so the 8-bit value fits with room to spare. The cast states the intended type in the source, sparing the reader from recalling the promotion rules.

The << 8 moves the high byte into bits 15 to 8, and because the value is held in at least 16 bits, nothing falls off the top. The (uint16_t)frame[2] term is the low byte, already in bits 7 to 0, and | combines the two without carry since their bit ranges do not overlap, after which the outer (uint16_t) cast converts the result back to the struct member's 16-bit type. Nothing in the expression reads memory in a particular byte order, so the code behaves identically on a big-endian core.

The starter's version is the one to avoid. 

uint16_t raw;
memcpy(&raw, &frame[1], 2);      /* copies the bytes in host order: wrong on little-endian */
out->temp_centi_c = raw;

memcpy copies 2 bytes from &frame[1] into raw without reordering them. That is correct for data written by the same CPU in the same byte order, such as a struct moved between two buffers, but for a wire format the sender's order is fixed and the receiver's is not, so the copy is wrong on one of them.

The status lines use masks, each naming the bits it means. 

out->mode  = frame[3] & 0x03U;          /* bits 1:0: keep the two low bits */
out->valid = (frame[3] >> 2) & 0x01U;   /* bit 2: move it to bit 0, then keep one bit */

The mask 0x03U is binary 0000 0011, so the AND keeps bits 1 and 0 and clears the rest, and the U suffix makes the constant unsigned, keeping the arithmetic unsigned as well. The second line shifts the byte right by two, so that bit 2 becomes bit 0, and keeps only that bit with 0x01U, and since both lines are exact, a reviewer can check each bit number against the datasheet table.

The starter also rejects a frame with the wrong header, checking before parsing so that a bad frame never reaches the output fields. The solution keeps that order, and the test in main prints bad header rejected when the second frame fails the check.

Packed structs for wire frames

Sometimes a driver must describe the whole frame as a struct so that it can be copied from a buffer in one call, and the struct must then match the wire layout, for which packing is the tool. 

typedef struct __attribute__((packed)) {
    uint8_t  header;      /* offset 0 */
    uint16_t temp;        /* offset 1 with packing; offset 2 without */
    uint8_t  status;      /* offset 3 with packing; offset 4 without */
} WireFrame;

Without the attribute the compiler aligns temp to an even address and leaves one byte of padding after header, whereas with it temp sits at offset 1 and status at offset 3, matching the wire. The GCC manual says that a packed member "should have the smallest possible alignment", and for a struct that each member is placed "to minimize the memory required". GCC manual, common attributes: packed

Packing fixes the member offsets, but it does not reverse the bytes of temp, whose value is still whatever the bytes in memory say, so a big-endian field still needs the shift form. It also creates unaligned members, and on a core without unaligned access a load of temp from an odd address can fault. GCC defines the macro __ARM_FEATURE_UNALIGNED for -mcpu=cortex-m3 but not for -mcpu=cortex-m0plus, which is the compiler's own statement of the difference between the two cores, so a safe driver reads the fields with shifts and uses the packed struct only as a description.

Common mistakes and how to spot them

A wire value copied with memcpy or a pointer cast

The value is wrong by a byte swap, in the project temp=13330 where temp=4660 is expected, because the copy keeps the bytes in host order. Use the shift expression, and check every place where a multi-byte value is taken from a buffer.

A byte buffer cast to a 16-bit pointer

The debugger shows a HardFault on a core without unaligned access, and on a core that allows it the value is still byte-swapped, because *(uint16_t *)&frame[1] reads from an odd address when the buffer is aligned. The fix is again the shift form.

The low byte lost in the combination

The value is correct in its high byte and zero in its low byte, in the project a temperature of 0x1200, or 4608, because a line shifted the wrong byte or used & where it meant |, although raw = frame[1] << 8 | frame[2] itself can be correct. Printing the value in hexadecimal shows the missing byte at once.

A bit-field used for a register

The device behaves differently after a toolchain change or upgrade, a symptom that is hard to trace, because the same struct put the field at a different bit on the new compiler although the bits were right on the first. Use a mask and a shift with named constants.

Packing expected to fix the byte order

A packed struct still yields the same 13330, because packing moves members and does not reverse their bytes. Read the fields with shifts, and keep packing for the layout only.

Frame parsing in production drivers

Driver code for sensors and radios consists mostly of parsing: a typical driver reads a frame, checks a header and a checksum and then extracts fields with masks and shifts. Teams keep these functions small and test them on a PC against a table of frames, using the same functions as the firmware, so that a byte-order error shows up at the desk rather than on the bench.

Code review of such a driver checks that each multi-byte field is parsed with shifts rather than a cast, that each mask and shift names the bit positions from the datasheet so the reviewer can check them against the table, and that any struct describing a wire frame says whether it is packed and why. Reviewers also look for bit-fields in any code that touches a register and ask for the mask form instead.

Summary

  • A bit-field's layout is implementation-defined, so it is not a portable register map, and a fixed-width integer with named masks and shifts should be used instead.
  • A wire value is combined with shifts and OR, as (hi << 8) | lo, giving a number that does not depend on the CPU's byte order.
  • A copy with memcpy or a pointer cast keeps host order, so on a little-endian Cortex-M the bytes 0x12 0x34 read as 0x3412, which is 13330.
  • The Cortex-M cores in this course are little-endian, as the macros printed by -dM -E confirm.
  • A packed struct removes padding and fixes member offsets but changes neither byte order nor the safety of unaligned access.
  • Masking with 0x03U keeps bits 1 and 0, and a right shift by 2 moves bit 2 down to bit 0.
  • A union reads the same bytes under two types, which is subtle in C, so conversions are better done with shifts.
