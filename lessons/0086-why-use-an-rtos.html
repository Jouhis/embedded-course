Why use an RTOS: super-loop vs scheduler

A super-loop is the right design until two jobs have deadlines that the loop cannot meet together. This lesson shows the arithmetic that tells you when that happens, and what a real-time operating system (RTOS) buys you for it.

By the end of this lesson you can work out the worst-case response time of a job in a super-loop, show that it misses a deadline, and say what a scheduler changes and what it costs.

The idea

Lesson 55 gave you a super-loop: one for (;;) that checks a set of deadlines on every pass. It is simple, cheap and easy to test. Its weakness is that every job waits for the others. A job that is due waits until the loop comes round to it, and a long job in the loop delays everything after it.

The measure that matters is the response time: the time from when a job becomes due to when it finishes. It is the waiting time plus the job's own execution time. A deadline is the largest response time the job may have. Real-time means meeting deadlines reliably, not running fast on average (the RTOS literature makes this distinction; the FreeRTOS kernel book covers it in its introduction, see the source below).

A super-loop that misses a deadline

Take the Lab 4 monitor. The sensor must be sampled every 200 ms, and the sensor's data-ready flag is only valid for 50 ms after it is set. The OLED is redrawn every 500 ms, and a full redraw sends 1025 bytes over I2C, which takes about 90 ms at 100 kHz (the Lab 4 hints give the same figure). The loop looks like this: 

/* Illustrative super-loop: not compiled. The Lab 4 app has this shape. */
for (;;) {
    if (due(now, next_sample)) { sample_sensor(); next_sample += 200; }  /* needs ~2 ms, deadline 50 ms after the flag */
    if (due(now, next_draw))   { draw_oled();     next_draw   += 500; }  /* blocks for ~90 ms on I2C */
    if (due(now, next_log))    { log_line();      next_log    += 1000; }
}

Suppose the sample is due at time 200 ms, and the loop has just started the redraw at 199 ms. The redraw blocks the CPU for 90 ms, so the sample starts at 289 ms. Its response time is 289 − 200 = 89 ms, plus its own 2 ms, about 91 ms. That is well past the 50 ms window, so the reading is lost. The loop is not buggy in any line. The response time is the sum of the blocking work that happens to run first.

The worst case is the sum, not the average. A super-loop's worst-case response time for a job is its own time plus the longest path of other work that can run before it. Testing with a fast display would hide the problem.

The same jobs under a scheduler

An RTOS runs each job as a task with its own stack and a priority. A scheduler decides which ready task runs. If the sample task has a higher priority, the scheduler stops the redraw task as soon as the sample task becomes ready, and switches to it. Lesson 87 shows how: xTaskCreate() with a priority, and the tick interrupt that wakes tasks. The response time of the sample becomes the time to the next tick plus the context switch, which is a few microseconds on a Cortex-M3, not the length of the redraw.

This is the core idea, which the FreeRTOS kernel book states as preemption by priority (see the source below). The scheduler does not make the redraw faster. It moves the waiting to the job that can afford to wait.

What a scheduler costs

  • RAM. Every task has a stack. The Lab 5 tasks use 160 to 256 words each, which is 640 to 1024 bytes. A Blue Pill has 20 KiB of RAM (Wokwi's model of the STM32F103C8 gives the same figure), so the stacks are a real budget.
  • Time. Each switch saves and restores registers. Lesson 88 shows the work.
  • Non-determinism, if misused. A scheduler makes timing easier to reason about only if each job's blocking is bounded. A task that waits on a queue with no timeout, or holds a lock while it does I2C, can block a high-priority task for an unbounded or long time.
In industry the question is usually not "use an RTOS or not", but "which jobs need a deadline, and can I bound the blocking of each?" A super-loop with two well-bounded jobs is often the better design.

"A sensor must be read every 10 ms, and the display update takes 40 ms. What do you do?" Answer out loud in 60 seconds, then compare.

Model answer

In a single loop the sensor read can start up to 40 ms late, which misses a 10 ms period. Put the sensor read in a higher-priority task, or in a timer interrupt, so that it preempts the display. Then check the worst case: one tick plus the context switch, which is far below 10 ms. Keep the display task's blocking bounded, for example with a short I2C timeout, and protect the shared bus with a mutex (lesson 90). Also say what it costs: a stack for each task, and the risk of priority inversion.
