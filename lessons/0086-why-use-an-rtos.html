Why use an RTOS: super-loop vs scheduler

A super-loop is the right design until two jobs have deadlines that the loop cannot meet together. This lesson shows the arithmetic that tells you when that happens, and what a real-time operating system (RTOS) buys you for it.

By the end of this lesson you can work out the worst-case response time of a job in a super-loop, show that it misses a deadline, and say what a scheduler changes and what it costs.

Where we are, and why it matters

Lesson 55 gave you the super-loop: one for (;;) that checks a set of deadlines on every pass. Lesson 56 then wrapped the logic of each job in a state machine, so that a job can pause and resume without blocking the others. Together they are a good design. They are simple, cheap in RAM and easy to test on a PC.

The problem appears when a job takes a long time. Lab 4 ports the three-screen monitor to the STM32, and its main loop redraws an SSD1306 OLED display. Lab 5 then moves the same application onto FreeRTOS. This lesson explains why that move is worth making, and what it costs, before you change any code. The same question comes up in a 3D printer's control board, which samples its temperature sensors on a schedule while it also drives a screen. If the screen update holds up the sampling, the reading arrives late.

Concept 1: a job, a deadline, and a response time

A job is one piece of work that must happen repeatedly, such as reading a sensor. It becomes due at a known time. For a sensor sampled every 200 ms, a job is due at 200 ms, 400 ms, 600 ms, and so on. A deadline is the latest moment by which the job must be finished, or the largest amount of time it may take after it becomes due.

The measure that matters is the response time: the time from when a job becomes due to when it finishes, which is its waiting time plus its own execution time. A sensor job that waits 89 ms and then runs for 2 ms has a response time of 91 ms. Whether that is acceptable depends on the deadline, not on the average of many runs.

That is the meaning of real-time in this course. A real-time system meets its deadlines every time, including the worst time. It is not a system that is fast on average. A fast processor that misses one sample in a thousand is not real-time for that sample. In the example that follows, the 50 ms window is an assumption made for the arithmetic, not a figure taken from Lab 4. The point of the example is the method.

Concept 2: blocking work

A blocking call is one that does not return until its work is finished. On a microcontroller the simplest form is a loop that waits for each byte of an I2C transfer. The core executes that waiting loop, one instruction after another, so nothing else on the core runs until the transfer ends. The core is a single resource: the processor fetches and runs one instruction stream at a time, and a loop that spins on a status flag occupies all of it.

The cost of a blocking call is set by the bus speed and the number of bits. An I2C byte is eight data bits plus one acknowledge bit from the receiver, so nine bit times per byte. Lab 4's hint works out a full-screen update this way. The update is eight pages. Each page sends three 2-byte commands and one 129-byte data frame (a control byte and 128 columns), which is 135 bytes. Eight pages make 1080 data bytes, and the 32 transactions add one address byte each, so the update sends 1112 bytes.

At 100 kHz, one bit time lasts 10 µs. The update therefore takes 1112 × 9 bit times, which is 10 008 bit times, and 10 008 × 10 µs is 100.08 ms. Lab 4 rounds this to about 100 ms, and this lesson uses 100 ms in its examples.

Notice what this means for the design. The display code is correct. It draws a whole screen and it works. But while it runs, the core cannot do anything else, and no code in the loop can run until the redraw returns. Nothing is wrong with any single line. The problem is the total time of one path through the code.

Concept 3: the super-loop's worst case

A super-loop runs its jobs in the order they appear in the loop body, and each pass runs only those that are due. A job that becomes due in the middle of a long job waits until the long job returns and the loop comes round to it. So the worst-case response time of a job is its own execution time plus the longest chain of other work that can run before it. The average does not matter for this calculation: the worst case is what a deadline must survive.

Here is a super-loop in the form the Lab 4 monitor has. It is illustrative and not compiled. The helper due() compares the current time with a scheduled time, as in lesson 55. 

/* Illustrative super-loop: not compiled. The Lab 4 app has this shape. */
for (;;) {
    if (due(now, next_sample)) { sample_sensor(); next_sample += 200; }  /* needs ~2 ms, deadline 50 ms after the flag */
    if (due(now, next_draw))   { draw_oled();     next_draw   += 500; }  /* blocks for ~100 ms on I2C */
    if (due(now, next_log))    { log_line();      next_log    += 1000; }
}

Read the three next_ lines closely. Each one adds the period to the previous scheduled time, not to the current time. That keeps the schedule steady: the sample is always scheduled at 200, 400 and 600 ms, even if a pass runs late. Adding the period to now would make every late pass push the schedule later, and the drift would accumulate. Lesson 87 makes the same point for vTaskDelayUntil().

The loop also shows the mechanism that makes the worst case long. At 199 ms the sample was not yet due, so the loop went on to the redraw check and started the redraw. One millisecond later the sample became due, while the redraw was still running. The loop cannot interrupt its own draw call, because the draw call is an ordinary function call that returns only when it is done. The loop has no point at which it can look at the clock again until the redraw is finished.

A worked example with real numbers

Take the events in order. The sample is due at 200 ms. The loop checked the redraw a millisecond earlier, at 199 ms, found it due and started it. The redraw takes 100 ms, so it ends at 299 ms. The sample check runs only after the redraw returns, so the sample starts at 299 ms. It needs 2 ms, so it ends at 301 ms.

Time (ms)What the core is doing
199The loop finds the redraw due and starts it
200The sample becomes due; the core is still in the redraw
299The redraw returns; the loop reaches the sample check and starts it
301The sample finishes

The response time is 301 − 200 = 101 ms. The sample's window is 50 ms, so the reading is late and is lost. The arithmetic is the whole argument: 99 ms of waiting, which is the redraw's remaining time, plus the sample's own 2 ms.

Now change one number. If the redraw took 40 ms instead of 100 ms, it would end at 239 ms, the sample would start then, and it would finish at 241 ms. The response time would be 41 ms, which meets the 50 ms window. The loop code is the same. Only the blocking time changed. That is why a super-loop can pass every test on a bench with a fast display and then fail in the field with a slow bus: the test did not reach the worst case.

Concept 4: what a scheduler changes

An RTOS runs each job as a task. A task is a function that loops forever, with its own stack (the memory where its local variables and return addresses live, lesson 33) and a priority. The scheduler, which is the part of the RTOS that decides which task runs, picks the highest-priority task that is ready to run. A task is ready when it has work to do and is not waiting for a delay or a signal.

Here is the same sample under a scheduler. The sample is a task with priority 3, and the redraw is a task with priority 2. The sample task is blocked on a delay that ends at 200 ms. The kernel counts time with a periodic interrupt called the tick. In this course the tick is 1 kHz, so one tick is 1 ms. When the tick finds that the delay has ended, the kernel makes the sample task ready. Because its priority is higher than the redraw's, the kernel switches to it. The redraw is paused in the middle of its work and resumes later. The sample's response time is at most the time to the next tick, which is 1 ms, plus the cost of the switch.

Notice what the scheduler does not do. It does not make the redraw faster. It does not shorten the 100 ms of bus time. It moves the waiting to the job that can afford to wait. The redraw still takes 100 ms; it simply no longer decides when the sample runs. Concept 5: what a scheduler costs

The first cost is RAM. Every task has a stack, and the stacks come from the kernel's heap. The course's linker script for the Blue Pill, templates/common/stm32f103c8.ld, gives the STM32F103C8 a RAM region of 20 KiB, which is 20 480 bytes. The FreeRTOS projects in this course give each task between 128 and 160 words. A word on the Cortex-M3 is 4 bytes, so 160 words is 640 bytes per task. Four tasks use about 2.5 KiB of the 20 KiB before the kernel's own objects, so the stacks are a real budget that has to be checked.

The second cost is time. Each switch saves the registers of the task that is leaving and restores those of the task that is arriving. Lesson 88 counts that work instruction by instruction.

The third cost is a new kind of bug. A scheduler makes timing easier to reason about only if the blocking of each task is bounded. A task that waits on a queue with no timeout, or holds a lock while it does a slow bus transfer, can block a high-priority task for a long time. Shared data between tasks needs a protocol, and a poorly chosen one can make a high-priority task wait for a low-priority one. Lesson 91 shows that failure.

Concept 6: the question engineers actually ask

In industry the working question is "which jobs have deadlines, and can I bound the blocking of each one?" Whether to use an RTOS follows from the answer. If two or three jobs have deadlines and each of them can be guarded by a short, bounded wait, a scheduler is the clean way to build it. If there is one job with a deadline and the rest is slow and not urgent, a super-loop with a non-blocking display is often the better design, and it costs less RAM and less testing.

Engineers also use analysis to answer the question before they write code. For periodic tasks with a fixed priority order, the classic result is rate-monotonic scheduling, in which the shorter the period, the higher the priority. Lessons 92 and 93 use a version of this analysis, and show how to check the stack and timing budgets on the Blue Pill.

Common mistakes and how to spot them

Mistake 1: testing only the fast path. A developer runs the Lab 4 monitor with the display connected and sees every sample arrive on time. The symptom appears later: a log shows readings that are missing or stale at the same moments the screen is redrawn. The fix is to measure the worst case, not the typical one. Record the tick at which each sample becomes due and the tick at which it starts, and keep the maximum of the difference. Then compare that maximum with the window.

Mistake 2: adding an RTOS to hide a long blocking call. A team sees missed samples and adds tasks, but leaves the 100 ms redraw as one blocking call. The symptom is the same missed deadline, now with random corruption on the I2C bus, because two tasks are using the bus with no lock. The fix is to shorten the blocking call, for example by redrawing only the changed part of the screen, as lesson 55 recommends, or to move the redraw into a low-priority task.

Mistake 3: planning from the average. The average response time of the sample is 5 ms, so the team concludes that the design is safe. The symptom is a spike of 101 ms once every redraw, which the average hides. The fix is to plan with the worst case from the code path, as in the worked example, and to count how many samples miss their window over a long run.

Mistake 4: adding tasks without budgeting stacks. A new feature adds a task with a 128-word stack, and the device works until a particular menu path runs. The symptom is a reset or a hang with no output. The fix is to measure each stack's high-water mark, the fewest free words the stack has ever had (Lab 5 prints it), and to make each stack larger than its measured need.

In real projects

Teams that ship RTOS-based products usually write a timing budget before the code. The budget lists each task, its period or trigger, its priority, its deadline, and the longest time it can block. A code reviewer then asks two questions of every new function: how long can this block, and which lock does it hold while it blocks? A function that calls a slow bus transfer while holding a shared lock is rejected, because it can block every task that needs that lock.

Summary

  • A job has a due time and a deadline. Its response time is the waiting time plus its own execution time.
  • Real-time means meeting every deadline, including the worst case. An average does not show that.
  • In a super-loop, the worst-case wait is the sum of the blocking work that can run first. A blocking call holds the core until it returns.
  • A full update of the Lab 4 OLED sends 1112 bytes. At 100 kHz with 9 bit times per byte, it takes about 100 ms.
  • A scheduler runs the highest-priority ready task, and a higher-priority task preempts a lower one at the next tick or at once from an interrupt. Its response time is bounded by the tick, not by the redraw.
  • A scheduler costs RAM for stacks, time for each switch, and new bugs in shared data.
  • Ask which jobs have deadlines and whether each one's blocking is bounded. Then choose the design.
