Why use an RTOS

Super-loop versus preemptive scheduler

By the end of this lesson you can work out the worst-case response time of a job in a super-loop, show that it misses a deadline, and say what a scheduler changes and what it costs.

A super-loop meets a slow job

Lesson 55 gave you the super-loop, one for (;;) checking a set of deadlines on every pass, and lesson 56 wrapped each job's logic in a state machine so that a job can pause and resume without blocking the others. Together they make a good design, simple, cheap in RAM and easy to test on a PC.

The problem appears when a job takes a long time. Lab 4 ports the three-screen monitor to the STM32 with a main loop that redraws an SSD1306 OLED display, and Lab 5 moves the same application onto FreeRTOS, so this lesson explains, before any code changes, why that move is worth making and what it costs. The same question arises on a 3D printer's control board, which samples its temperature sensors on a schedule while driving a screen, so that a screen update holding up the sampling makes the reading late.

Jobs, deadlines and response times

A job is a piece of work that must happen repeatedly, such as reading a sensor, and it becomes due at a known time, a sensor sampled every 200 ms being due at 200 ms, 400 ms, 600 ms and so on. A deadline is the latest moment by which the job must finish, or the largest time it may take after becoming due.

The measure that matters is the response time

R = twait + C(1)

where twait is the time from when the job becomes due until it starts and C its own execution time, so a sensor job that waits 89 ms and then runs for 2 ms has a response time of 91 ms, and whether that is acceptable depends on the deadline rather than on the average of many runs.

That is the meaning of real-time in this course, a real-time system meeting its deadlines every time, including the worst, rather than being fast on average, so a fast processor that misses one sample in a thousand is not real-time for that sample. The 50 ms window in the following example is an assumption made for the arithmetic rather than a figure from Lab 4, since the point of the example is the method.

Blocking calls and the single core

A blocking call does not return until its work is finished, its simplest form on a microcontroller being a loop that waits for each byte of an I2C transfer. The core executes that waiting loop instruction by instruction, so nothing else runs until the transfer ends, the core being a single resource that fetches and runs one instruction stream at a time, all of it occupied by a loop spinning on a status flag.

The cost of a blocking call is set by the bus speed and the number of bits, an I2C byte being eight data bits plus one acknowledge bit from the receiver, nine bit times per byte. Lab 4's hint works out a full-screen update this way: the update is eight pages, each sending three 2-byte commands and one 129-byte data frame (a control byte and 128 columns), 135 bytes per page, so eight pages make 1 080 data bytes, and the 32 transactions add one address byte each, bringing the update to 1 112 bytes. The transfer time is

t = Nbytes × 9 × tbit(2)

where Nbytes is the number of bytes sent and tbit one bit time, 10 µs at 100 kHz, so the update takes 1 112 × 9 = 10 008 bit times, and 10 008 × 10 µs = 100.08 ms, which Lab 4 rounds to about 100 ms, the figure this lesson uses.

The display code is correct, drawing a whole screen that works, but while it runs the core can do nothing else and no other code in the loop runs until the redraw returns. No single line is wrong, the problem being the total time of one path through the code.

The worst case of a super-loop

A super-loop runs its jobs in the order they appear in the loop body, each pass running only those that are due, so a job becoming due in the middle of a long job waits until the long job returns and the loop comes round to it. The worst-case response time of a job is therefore its own execution time plus the longest chain of other work that can run before it, and the average plays no part in the calculation, since the worst case is what a deadline must survive.

The super-loop below has the form of the Lab 4 monitor, illustrative and not compiled, with the helper due() comparing the current time with a scheduled time, as in lesson 55. 

/* Illustrative super-loop: not compiled. The Lab 4 app has this shape. */
for (;;) {
    if (due(now, next_sample)) { sample_sensor(); next_sample += 200; }  /* needs ~2 ms, deadline 50 ms after the flag */
    if (due(now, next_draw))   { draw_oled();     next_draw   += 500; }  /* blocks for ~100 ms on I2C */
    if (due(now, next_log))    { log_line();      next_log    += 1000; }
}

Each of the three next_ lines adds the period to the previous scheduled time rather than to the current time, which keeps the schedule steady, the sample always being scheduled at 200, 400 and 600 ms even if a pass runs late, whereas adding the period to now would let every late pass push the schedule later, the drift accumulating, a point lesson 87 makes again for vTaskDelayUntil().

The loop also shows why the worst case is long. At 199 ms the sample was not yet due, so the loop went on to the redraw check and started the redraw, and one millisecond later the sample became due while the redraw was still running. The loop cannot interrupt its own draw call, an ordinary function call that returns only when it is done, so it has no point at which to look at the clock again until the redraw finishes.

Worked example: a sample delayed by the redraw

We take the events in order, and before reading the table, predict the sample's response time when a 100 ms redraw starts one millisecond before the sample is due.

  1. Start the redraw. The loop checks the redraw at 199 ms, finds it due and starts it.
  2. The sample becomes due. At 200 ms the sample is due, but the redraw, taking 100 ms, holds the core until 299 ms.
  3. Run the sample. The sample check runs only after the redraw returns, so the sample starts at 299 ms and, needing 2 ms, ends at 301 ms.
Time (ms)What the core is doing
199The loop finds the redraw due and starts it
200The sample becomes due; the core is still in the redraw
299The redraw returns; the loop reaches the sample check and starts it
301The sample finishes

The response time is 301 − 200 = 101 ms, while the sample's window is 50 ms, so the reading is late and lost, the whole argument being the arithmetic of 99 ms of waiting, the redraw's remaining time, plus the sample's own 2 ms.

Changing one number shows the sensitivity. With a 40 ms redraw, it would end at 239 ms and the sample, starting then, would finish at 241 ms, a response time of 41 ms that meets the 50 ms window, with the loop code unchanged and only the blocking time different. That is why a super-loop can pass every bench test with a fast display and then fail in the field with a slow bus, the test never having reached the worst case.

Tasks, priorities and the scheduler

An RTOS runs each job as a task, a function that loops forever with its own stack (the memory holding its local variables and return addresses, lesson 33) and a priority. The scheduler, the part of the RTOS that decides which task runs, picks the highest-priority task that is ready to run, a task being ready when it has work to do and is not waiting for a delay or a signal.

Under a scheduler the same sample becomes a task of priority 3 and the redraw a task of priority 2, the sample task being blocked on a delay that ends at 200 ms. The kernel counts time with a periodic interrupt called the tick, 1 kHz in this course, so one tick is 1 ms, and when the tick finds that the delay has ended, the kernel makes the sample task ready and, its priority being higher than the redraw's, switches to it, pausing the redraw mid-work to resume it later. The sample's response time is then at most the time to the next tick, 1 ms, plus the cost of the switch.

A super-loop resembles one checkout lane where each customer is served from start to finish in order, however small the next customer's basket, while a scheduler resembles a cashier who may pause a slow customer the moment someone with an urgent, small purchase arrives and resume the slow one afterwards, so the urgent customer's wait no longer depends on the longest basket in the queue. The comparison breaks on cost, though, because pausing a customer is free, whereas every task switch costs the core time and every task its own stack.

The scheduler does not make the redraw faster or shorten its 100 ms of bus time, but moves the waiting to the job that can afford it, so the redraw still takes 100 ms while no longer deciding when the sample runs. The costs of a scheduler

The first cost is RAM, because every task has a stack taken from the kernel's heap. The course's Blue Pill linker script, templates/common/stm32f103c8.ld, gives the STM32F103C8 a RAM region of 20 KiB, 20 480 bytes, and the course's FreeRTOS projects give each task between 128 and 160 words, a Cortex-M3 word being 4 bytes, so 160 words is 640 bytes per task. Four tasks use about 2.5 KiB of the 20 KiB before the kernel's own objects, which makes the stacks a real budget to be checked.

The second cost is time, each switch saving the registers of the task leaving and restoring those of the task arriving, work that lesson 88 counts instruction by instruction.

The third cost is a new kind of bug, since a scheduler makes timing easier to reason about only if each task's blocking is bounded. A task waiting on a queue without a timeout, or holding a lock through a slow bus transfer, can block a high-priority task for a long time, and data shared between tasks needs a protocol, a poorly chosen one making a high-priority task wait for a low-priority one, the failure that lesson 91 shows.

Deadlines and bounded blocking in the choice of design

In industry the working question is which jobs have deadlines and whether the blocking of each can be bounded, the choice of an RTOS following from the answer. If two or three jobs have deadlines and each can be guarded by a short, bounded wait, a scheduler is the clean way to build it, whereas with one deadline job and the rest slow and not urgent, a super-loop with a non-blocking display is often the better design, costing less RAM and less testing.

Engineers also answer the question by analysis before writing code, the classic result for periodic tasks with a fixed priority order being rate-monotonic scheduling, in which a shorter period means a higher priority. Lessons 92 and 93 use a version of this analysis and show how to check the stack and timing budgets on the Blue Pill.

Common mistakes and how to spot them

Testing only the fast path

A log later shows readings missing or stale at exactly the moments the screen is redrawn, because the developer ran the Lab 4 monitor with the display connected, saw every sample arrive on time and stopped there. Measure the worst case rather than the typical one, recording the tick at which each sample becomes due and the tick at which it starts, keeping the maximum difference and comparing it with the window.

An RTOS added to hide a long blocking call

The same deadline is still missed, now with random corruption on the I2C bus, because the team added tasks but left the 100 ms redraw as one blocking call, and two tasks use the bus without a lock. Shorten the blocking call, for example by redrawing only the changed part of the screen, as lesson 55 recommends, or move the redraw into a low-priority task.

Planning from the average

A 101 ms spike appears at every redraw, hidden by an average response time of 5 ms from which the team concluded that the design was safe. Plan with the worst case from the code path, as in the worked example, and count how many samples miss their window over a long run.

Tasks added without stack budgets

The device resets or hangs without output when a particular menu path runs, because a new feature added a task with a 128-word stack. Measure each stack's high-water mark, the fewest free words the stack has ever had (Lab 5 prints it), and make each stack larger than its measured need.

Timing budgets in RTOS-based products

Teams shipping RTOS-based products usually write a timing budget before the code, listing each task with its period or trigger, its priority, its deadline and the longest time it can block. A reviewer then asks of every new function how long it can block and which lock it holds while blocking, and rejects a function that calls a slow bus transfer while holding a shared lock, because it can block every task that needs that lock.

Summary

  • A job has a due time and a deadline, and its response time is its waiting time plus its own execution time.
  • Real-time means meeting every deadline, including the worst case, which an average does not show.
  • In a super-loop the worst-case wait is the sum of the blocking work that can run first, since a blocking call holds the core until it returns.
  • A full update of the Lab 4 OLED sends 1 112 bytes, which at 100 kHz and 9 bit times per byte takes about 100 ms.
  • A scheduler runs the highest-priority ready task, a higher-priority task preempting a lower one at the next tick or at once from an interrupt, so its response time is bounded by the tick rather than the redraw.
  • A scheduler costs RAM for stacks, time for each switch and new bugs in shared data.
  • The design follows from which jobs have deadlines and whether each one's blocking is bounded.
