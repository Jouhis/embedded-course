USB fundamentals

Host-polled transfers and self-describing devices

By the end of this lesson you can describe the order of USB enumeration, name the four transfer types and the device classes, and explain why the CDC demo needs a real Pico to show its port.

Devices that describe themselves to the host

Lessons 53 and 70 gave you the UART, a serial port with a fixed baud rate, and lessons 100 and 101 two serial buses sharing a pair of wires. USB works differently, its wires carrying a host-controlled conversation in which the PC asks and each device answers, the device describing itself when it is plugged in, which is why a single Pico can appear on a PC as a serial port without a driver written by you.

The situation is everyday, a USB keyboard, a flash drive, a microcontroller board used for logging and a USB-to-serial adapter all plugging into the same port on the same computer, whose host must learn for each one what it is and how to talk to it without a human telling it. This lesson explains how it finds out and builds a small demo that shows the result on a real board.

The lesson has no simulator task, because Wokwi's USB support is partial (NOTES.md), so it cannot enumerate a device, and the lesson is therefore concept-first, ending with a demo that builds here and runs on a real board.

The host in charge of every transfer

A USB network has one host, normally the PC, with devices hanging off it through hubs, and the host starts every transfer, a device never sending data on its own but answering when asked or queueing a message on an interrupt endpoint until the host polls it. The primer describes the interrupt case directly, saying that a device needing attention must wait until the host polls it before it can report that it needs attention (Beyond Logic, USB in a NutShell, chapter on interrupt transfers). This is the opposite of a serial line, where either side may start a byte. It is also why a USB keyboard reports at a fixed rate: the host polls the interrupt endpoint on a schedule that the endpoint descriptor sets.

USB resembles a classroom with a strict teacher, in which the pupils, the devices, speak only when the teacher asks them by name, the host polling an endpoint, so a pupil with something to say waits for the question, and even a keyboard does not send a key press until the host asks for it. The comparison breaks on timing, though, because a teacher asks when it suits, whereas the host polls an interrupt endpoint on the fixed schedule its descriptor requests.

The primer explaining the host-and-device model, endpoints, descriptors and enumeration in full is USB in a NutShell, whose endpoint, descriptor and enumeration chapters were read for this lesson and supply the facts below, while the USB specification itself, the final reference, was not opened.

Endpoints and transfer types

An endpoint is one source or sink of data on a device, identified by a number and a direction, IN to the host or OUT from it, every device having endpoint 0, the default control endpoint, which the primer says is always a control endpoint and never has a descriptor, while the other endpoints use one of four transfer types, each chosen for a purpose.

Transfer typeTypical useWhat the primer says
ControlEnumeration, configuration, class requestsUsed for setup and requests. Endpoint 0 is always a control endpoint.
InterruptKeyboards, mice, small status messagesPolled at a rate set by the endpoint descriptor, with bounded latency and a small payload. A corrupt packet is retried in the next period.
BulkPrinters, scanners, large blocks of dataError correction and retransmission, using the bandwidth left after the other transfers. No latency guarantee.
IsochronousAudio and video streamsGuaranteed bandwidth and bounded latency. Errors are detected by CRC, but bad data is not retried.

The primer also gives the payload limits, an interrupt endpoint carrying at most 8 bytes per transaction on a low-speed device, 64 on a full-speed device and 1024 on a high-speed device, while the interval at which the host polls an interrupt endpoint comes from its endpoint descriptor, which the next section describes.

Device, configuration, interface and endpoint descriptors

A device has no fixed identity but stores descriptors, small structures the host reads, the device descriptor with the vendor and product IDs and the default class, one or more configuration descriptors, the interface descriptors inside each configuration, each interface being one function with a class, and the endpoint descriptors inside each interface, with the number, direction, transfer type and maximum packet size, while string descriptors give the names a user sees.

Enumeration of a new device

Enumeration is the host's sequence for a new device, made entirely of control transfers on endpoint 0, which the primer describes in the order given below with the requests it uses, chapter 9 of the USB specification being the reference for the request codes.

Enumeration resembles a new pupil's first morning, the teacher asking who they are (the device descriptor), giving them a desk number (the address), asking which subjects they take (the configuration and interface descriptors) and fetching the right textbook (the class driver), and only then does the lesson start. The comparison breaks because a teacher can ask a pupil for a name in passing, whereas a USB host must reset the bus and speak to the device at address 0 before it can ask anything.

Worked example: enumerating a Pico

The steps below follow a Pico from the moment it is plugged in until data can move. Before reading them, predict at which step the device stops answering at address 0.

  1. The reset. The device is plugged in and the host resets the bus, after which the device answers only at address 0, the address every unconfigured device must answer to.
  2. The device descriptor. The host sends a GET_DESCRIPTOR request to address 0 for the device descriptor, which the primer gives as 18 bytes, containing the vendor and product IDs and the default class.
  3. The address. The host sends SET_ADDRESS (request code 0x05) with a new unique address, at which the device answers from then on, leaving address 0 free for the next device.
  4. The configuration descriptor. The host reads the configuration descriptor, one block holding the configuration, every interface descriptor and every endpoint descriptor in order, so that one request returns the whole tree.
  5. The configuration. The host sends SET_CONFIGURATION (request code 0x09) with the chosen configuration value, which activates the device's endpoints, and the host loads a class driver for each interface.

Only after step 5 does data move, so a device that fails at an early step never reaches the point where its class driver is loaded and has no port to open.

  1. The Pico is plugged in and the host resets the bus. Every unconfigured device answers at address 0, so that is where the host talks to it.
  2. GET_DESCRIPTOR for the device descriptor: 18 bytes with the vendor and product IDs and the default class.
  3. SET_ADDRESS (request 0x05) gives the device its own address, 7 here. From now on it answers there, and address 0 is free for the next device that is plugged in.
  4. GET_DESCRIPTOR for the configuration descriptor returns one block: the configuration, every interface and every endpoint, in order.
  5. SET_CONFIGURATION (request 0x09) activates the endpoints, and the host loads a class driver for each interface; for the Pico's CDC interface, the serial driver.
  6. Only now does data move, and a COM port appears on the PC. A device that fails at any earlier step never gets this far, which is why a broken descriptor means no port at all.

Device classes

A class defines how an interface behaves, so that the host can use a standard driver without knowing the vendor, and three classes matter here.

  • CDC, the communications device class, which gives a virtual serial port (a COM port on Windows). The Pico's stdio over USB uses it.
  • HID, the human interface device class, for keyboards, mice and generic input and output reports.
  • MSC, the mass storage class, which makes the device look like a disk.

TinyUSB, the open-source USB stack that the Pico SDK uses, supports all three as device classes along with others (TinyUSB documentation), and its device stack is what the demo below runs on the RP2040.

TinyUSB in the Pico SDK

The Pico SDK wires TinyUSB into the standard I/O library, pico_enable_stdio_usb(target 1) in CMake making printf go to a USB CDC port and pico_enable_stdio_uart(target 0) stopping it from using UART0 at the same time, and the SDK in this workspace (2.3.1) includes TinyUSB under lib/tinyusb, with which the demo builds.

The demo code line by line

The CMake file does three things, set(PICO_NO_PICOTOOL 1) turning off the UF2 converter, so that the build produces an ELF file for the debug probe or the simulator, pico_enable_stdio_usb(usb_cdc_demo 1) making the SDK build TinyUSB's device stack into the program and send printf to a CDC port, and pico_enable_stdio_uart(usb_cdc_demo 0) removing the UART0 path from stdio, so that each character goes to one place only.

The C file is short, and each part does one job.

  • stdio_init_all() starts the stdio drivers that the CMake file selected. With USB selected, that starts TinyUSB, and the port then appears to the host once the device enumerates.
  • while (!stdio_usb_connected() && waited_ms < HOST_WAIT_MS) waits up to three seconds for a terminal to open. stdio_usb_connected() reports whether a host has opened the port, which is the test that matters. The loop sleeps 10 ms at a time, so the wait is measured in milliseconds, not in loop passes.
  • gpio_init and gpio_set_dir set the on-board LED on GP25 as an output. The LED has no role in the USB part, but it gives you a visible sign that the loop is running without a terminal.
  • The first printf reports whether the wait ended with a host present, and how long the wait took. Its format uses %lu with a cast to unsigned long, so the argument matches the conversion it is printed with.
  • The endless loop turns the LED on, prints a line, sleeps 500 ms, turns it off, prints again and sleeps 500 ms. The tick counter goes up once per full cycle, which is once per second.

Try it: build the USB CDC demo

The project projects/0102-usb-cdc-demo prints a line each half-second over USB after waiting up to three seconds for a terminal to open, and since the port cannot be seen in Wokwi, you build it and check the build output.

  1. From the workspace root, run python -I tools/build.py projects/0102-usb-cdc-demo, which ends with the link step and produces build/usb_cdc_demo.elf.
  2. Read main.c, and find in CMakeLists.txt the call that enables the USB stdio and the line that turns UART stdio off.
  3. On a real Pico you need a way to load the program, and since the templates turn picotool off (PICO_NO_PICOTOOL), so that the build makes an ELF rather than a UF2, load it with a debug probe or turn picotool on and build a UF2, then plug the board in and open the new serial port in a terminal at any baud rate. It works when the first line is CDC demo: connected=1 after N ms, with N below 3000, followed by the lines tick 0: LED on and tick 0: LED off, one every 500 ms, the tick number rising by one every second, whereas a first line saying connected=0 means that no terminal opened within three seconds and the program printed anyway.

The Wokwi simulator will not show this port, because its serial monitor is a UART and the Pico's USB support there is only partial (NOTES.md), so the CDC port does not appear in the simulator.

Common mistakes and how to spot them

The port expected in the simulator

The build succeeds while the serial monitor shows nothing from the USB side and no new port appears, so it is easy to conclude that the code is broken, although the cause is that the port simply does not exist in Wokwi. Check the wiring of the UART and the CMake file, then test the port on a real board, since the build output is correct.

Printing before the host listens

The first line is missing, or the terminal opens after the program has already printed its start-up text, because a USB device cannot tell whether a terminal is open, so output sent too early can be lost. Use the demo's wait loop, which checks stdio_usb_connected() for up to three seconds, and look at the first line, where connected=0 says that the wait ran out.

Both stdio targets enabled

Text appears on a pin nobody meant to use, a logic analyser or a second terminal on the UART showing unexpected lines, because pico_enable_stdio_uart(usb_cdc_demo 1) stayed on next to the USB line, so output goes to UART0 as well as to the port. Set the UART target to 0 whenever you choose USB, as this lesson's CMake file does, and check the file after copying a template.

A board that never enumerated

No new port appears on the PC and a terminal opens nothing, because the device failed early in enumeration and so has no port. Check the descriptors and the class choice in the project rather than the printf calls, which cannot run until the port exists.

Class choices and descriptor reviews in USB products

Engineers use a CDC port for logs, a command line and firmware debugging, because the host has a class driver for it, so the device needs no custom driver on the PC, and the same device can present several functions at once, each with its own interface descriptor. The descriptors are therefore part of the product and reviewed like code, since a change to a product ID or a class is seen by the host and every installed driver.

A review of USB firmware looks first at the class choice, CDC for a serial port, HID for input, MSC for storage and a vendor class only when none of those fits, and then checks that the transfer types match the job, interrupt endpoints carrying small, time-bounded messages, bulk endpoints large transfers that can wait and isochronous endpoints streams that must not stall but can drop a packet, so choosing bulk for a stream or isochronous for a file is a finding a senior engineer will raise.

Summary

  • The host starts every transfer, and a device answers or queues a message on an interrupt endpoint until it is polled.
  • Endpoint 0 is the default control endpoint, and enumeration is made of control transfers on it.
  • The four transfer types are control, interrupt, bulk and isochronous, interrupt endpoints being polled, bulk endpoints error-corrected without a latency promise and isochronous endpoints given guaranteed bandwidth without retry.
  • Enumeration reads the device descriptor at address 0, assigns an address with SET_ADDRESS (0x05) and selects a configuration with SET_CONFIGURATION (0x09).
  • The device descriptor is 18 bytes, and one configuration request returns the configuration, interface and endpoint descriptors together.
  • CDC gives a virtual serial port, which the Pico's stdio uses when pico_enable_stdio_usb is set.
  • Wokwi's USB support for the Pico is partial, so the CDC port must be tested on a real board.
