USB fundamentals

A USB device only answers: the host asks, and the device replies. Everything a device can do, from a keyboard to a serial port, is described in descriptors that the host reads at connection time. This lesson covers that model, and it builds a USB serial demo for the Pico that you can run on real hardware.

By the end of this lesson you can describe the order of USB enumeration, name the four transfer types and the device classes, and explain why the CDC demo needs a real Pico to show its port.
Why this lesson has no simulator task. Wokwi's USB support is partial (NOTES.md), so it cannot enumerate a device. The lesson is concept-first, and it ends with a demo that builds here and runs on a real board.

Where we are, and why this matters

Lessons 53 and 70 gave you the UART, a serial port with a fixed baud rate. Lessons 100 and 101 gave you two serial buses that share a pair of wires. USB works differently. Its wires carry a host-controlled conversation, where the PC asks and each device answers, and the device describes itself when it is plugged in. That is why a single Pico can appear on a PC as a serial port with no driver written by you.

This situation is everyday. A USB keyboard, a flash drive, a microcontroller board used for logging, and a USB-to-serial adapter all plug into the same port on the same computer. The host has to know, for each one, what it is and how to talk to it, without a human telling it. The rest of this lesson explains how it finds out, and builds a small demo that shows the result on a real board.

The idea: the host is in charge

A USB network has one host, normally the PC, and devices hang off it through hubs. The host starts every transfer. A device does not send data on its own: it answers when the host asks, or it queues a message on an interrupt endpoint until the host polls it. The primer describes the interrupt case directly: a device that needs attention must wait until the host polls it before it can report that it needs attention (Beyond Logic, USB in a NutShell, chapter on interrupt transfers). This is the opposite of a serial line, where either side may start a byte. It is also why a USB keyboard reports at a fixed rate: the host polls the interrupt endpoint on a schedule that the endpoint descriptor sets.

The primer that explains the host-and-device model, endpoints, descriptors and enumeration in full is USB in a NutShell. Its endpoint, descriptor and enumeration chapters were read for this lesson, and the facts below come from them. The USB specification itself is the final reference, and this lesson did not open it.

Endpoints and transfer types

An endpoint is one source or sink of data on a device, identified by a number and a direction (IN to the host, or OUT from it). Every device has endpoint 0, the default control endpoint, which the primer says is always a control endpoint and never has a descriptor. Other endpoints use one of four transfer types, each chosen for a purpose.

Transfer typeTypical useWhat the primer says
ControlEnumeration, configuration, class requestsUsed for setup and requests. Endpoint 0 is always a control endpoint.
InterruptKeyboards, mice, small status messagesPolled at a rate set by the endpoint descriptor, with bounded latency and a small payload. A corrupt packet is retried in the next period.
BulkPrinters, scanners, large blocks of dataError correction and retransmission, using the bandwidth left after the other transfers. No latency guarantee.
IsochronousAudio and video streamsGuaranteed bandwidth and bounded latency. Errors are detected by CRC, but bad data is not retried.

The primer gives the payload limits too. An interrupt endpoint carries at most 8 bytes per transaction on a low-speed device, 64 on a full-speed device and 1024 on a high-speed device. The interval at which the host polls an interrupt endpoint comes from its endpoint descriptor, which the next section describes.

Descriptors: the device describes itself

A device does not have a fixed identity. It stores descriptors, which are small structures the host reads: the device descriptor (vendor and product IDs, the default class), one or more configuration descriptors, the interface descriptors inside each configuration (each interface is one function with a class), and the endpoint descriptors inside each interface (number, direction, transfer type and maximum packet size). String descriptors give the names a user sees.

Enumeration: how the host meets a new device

Enumeration is the host's sequence for a new device, and it is made entirely of control transfers on endpoint 0. The primer describes the same order, with the requests it uses (chapter 9 of the USB specification is the reference for the request codes).

Worked example: enumerating a Pico

  1. The device is plugged in and the host resets the bus. The device answers only at address 0, the address every unconfigured device must answer to.
  2. The host sends a GET_DESCRIPTOR request to address 0 for the device descriptor, which the primer gives as 18 bytes. It contains the vendor and product IDs and the default class.
  3. The host sends SET_ADDRESS (request code 0x05) with a new unique address. From now on the device answers at that address, and address 0 is free for the next device.
  4. The host reads the configuration descriptor. It is one block that holds the configuration, every interface descriptor and every endpoint descriptor in order, so one request returns the whole tree.
  5. The host sends SET_CONFIGURATION (request code 0x09) with the chosen configuration value. The device's endpoints are now active, and the host loads a class driver for each interface.

Only after step 5 does data move. A device that fails at an early step never reaches the point where its class driver is loaded, so there is no port to open.

Device classes: one protocol, many devices

A class defines how an interface behaves, so the host can use a standard driver without knowing the vendor. Three classes matter here:

  • CDC, the communications device class, which gives a virtual serial port (a COM port on Windows). The Pico's stdio over USB uses it.
  • HID, the human interface device class, for keyboards, mice and generic input and output reports.
  • MSC, the mass storage class, which makes the device look like a disk.

TinyUSB, the open-source USB stack that the Pico SDK uses, supports all three as device classes, along with others (TinyUSB documentation). Its device stack is what the demo below runs on the RP2040.

TinyUSB in the Pico SDK

The Pico SDK wires TinyUSB into the standard I/O library. Setting pico_enable_stdio_usb(target 1) in CMake makes printf go to a USB CDC port. Setting pico_enable_stdio_uart(target 0) stops it from using UART0 at the same time. The SDK in this workspace (2.3.1) includes TinyUSB under lib/tinyusb, and the demo builds with it.

The code, line by line

The CMake file does three things. set(PICO_NO_PICOTOOL 1) turns off the UF2 converter, so the build produces an ELF file for the debug probe or the simulator. pico_enable_stdio_usb(usb_cdc_demo 1) makes the SDK build TinyUSB's device stack into the program and send printf to a CDC port. pico_enable_stdio_uart(usb_cdc_demo 0) removes the UART0 path from stdio, so each character goes to one place only.

The C file is short, and each part does one job:

  • stdio_init_all() starts the stdio drivers that the CMake file selected. With USB selected, that starts TinyUSB, and the port then appears to the host once the device enumerates.
  • while (!stdio_usb_connected() && waited_ms < HOST_WAIT_MS) waits up to three seconds for a terminal to open. stdio_usb_connected() reports whether a host has opened the port, which is the test that matters. The loop sleeps 10 ms at a time, so the wait is measured in milliseconds, not in loop passes.
  • gpio_init and gpio_set_dir set the on-board LED on GP25 as an output. The LED has no role in the USB part, but it gives you a visible sign that the loop is running without a terminal.
  • The first printf reports whether the wait ended with a host present, and how long the wait took. Its format uses %lu with a cast to unsigned long, so the argument matches the conversion it is printed with.
  • The endless loop turns the LED on, prints a line, sleeps 500 ms, turns it off, prints again and sleeps 500 ms. The tick counter goes up once per full cycle, which is once per second.

Try it: build the USB CDC demo

The project is projects/0102-usb-cdc-demo. It prints a line each half-second over USB, and it waits up to three seconds for a terminal to open first. You cannot see the port in Wokwi, so you build it and check the build output.

  1. From the workspace root, run python -I tools/build.py projects/0102-usb-cdc-demo. It ends with the link step, and it produces build/usb_cdc_demo.elf.
  2. Read main.c. Find the call that enables the USB stdio in CMakeLists.txt, and the line that turns UART stdio off.
  3. On a real Pico, you need a way to load the program. The templates turn picotool off (PICO_NO_PICOTOOL), so the build makes an ELF, not a UF2. Load it with a debug probe, or turn picotool on and build a UF2. Then plug the board in, and open the new serial port in a terminal at any baud rate. You will know it works when the first line is CDC demo: connected=1 after N ms, with N below 3000, and then the lines tick 0: LED on and tick 0: LED off follow, one every 500 ms, with the tick number rising by one every second. If the first line says connected=0, no terminal opened within three seconds, and the program prints anyway.
Do not expect the Wokwi simulator to show this port. Its serial monitor is a UART, and the Pico's USB support is only partial there (NOTES.md), so the CDC port does not appear in the simulator.

Common mistakes and how to spot them

The first mistake is to expect the simulator to show the port. The build succeeds, the serial monitor shows nothing from the USB side, and it is easy to conclude that the code is broken. The symptom is an empty serial monitor and no new port in the simulator. The fix is to check the wiring of the UART and the CMake file, then test the port on a real board. The build output is correct, and the port simply does not exist in Wokwi.

The second mistake is to print before the host is listening. A USB device cannot tell whether a terminal is open, so output sent too early can be lost. The symptom is a first line that is missing, or a terminal that opens after the program has already printed its start-up text. The fix is the wait loop in this demo, which checks stdio_usb_connected() for up to three seconds. Look at the first line: connected=0 tells you the wait ran out.

The third mistake is to enable both stdio targets. If pico_enable_stdio_uart(usb_cdc_demo 1) stays on next to the USB line, output goes to UART0 as well as to the port, and a logic analyser or a second terminal on the UART shows lines you did not expect. The symptom is text on a pin nobody meant to use. The fix is to set the UART target to 0 whenever you choose USB, as the CMake file in this lesson does, and to check the file after you copy a template.

The fourth mistake is to flash a board that never enumerated. A device that fails early in enumeration has no port, so a terminal opens nothing. The symptom is no new port on the PC. The fix is to check the descriptors and the class choice in the project, not the printf calls, because the printf calls cannot run until the port exists.

In real projects

Engineers use a CDC port for logs, a command line and firmware debugging, because the host has a class driver for it, so the device needs no custom driver on the PC. The same device can present several functions at once, each with its own interface descriptor. The descriptors are therefore part of the product, and they are reviewed like code. A change to a product ID or a class is a change that the host and every installed driver see.

A review of USB firmware looks at the class choice first: CDC for a serial port, HID for input, MSC for storage, and a vendor class only when none of those fits. It then checks that the transfer types match the job. Interrupt endpoints carry small, time-bounded messages, bulk endpoints carry large transfers that can wait, and isochronous endpoints carry streams that must not stall but can drop a packet. Choosing bulk for a stream, or isochronous for a file, is a finding a senior engineer will raise.

Summary

  • The host starts every transfer. A device answers, or queues a message on an interrupt endpoint until it is polled.
  • Endpoint 0 is the default control endpoint, and enumeration is made of control transfers on it.
  • The four transfer types are control, interrupt, bulk and isochronous. Interrupt endpoints are polled, bulk endpoints are error-corrected with no latency promise, and isochronous endpoints have guaranteed bandwidth without retry.
  • Enumeration reads the device descriptor at address 0, assigns an address with SET_ADDRESS (0x05), and selects a configuration with SET_CONFIGURATION (0x09).
  • The device descriptor is 18 bytes, and one configuration request returns the configuration, interface and endpoint descriptors together.
  • CDC gives a virtual serial port. The Pico's stdio uses it when pico_enable_stdio_usb is set.
  • Wokwi's USB support for the Pico is partial, so the CDC port must be tested on a real board.
