Setting up the STM32 toolchain

Your ARM GCC from lesson 1 can build for an STM32, but the chip's register names, startup code and clock setup come from a few folders in third_party/. This lesson shows what each one is, and how a project pulls them together.

By the end of this lesson you can build and simulate the STM32 CMSIS template on the Blue Pill, name the four third_party/ folders and where each comes from, and change the blink rate and the serial message in the project.

The idea

On the RP2040, the Pico SDK arrives as one package that you point CMake at. The STM32 world splits the same job into layers. The compiler is generic Arm GCC, and it knows nothing about your chip. The chip's own facts come from the vendor and from Arm: register names, interrupt numbers, the startup file and the clock code. You already have the compiler from lesson 1. What this lesson adds is the chip layer on top of it.

The Blue Pill has an STM32F103C8: an ARM Cortex-M3 with 64 KB of flash and 20 KB of RAM. The Wokwi simulator runs that same firmware on a model of it. The part page lists which peripherals the model implements. Its table shows USART, EXTI, RCC and AFIO as simulated, and DMA, the watchdog IWDG, PWR and RTC as not implemented. What is in third_party/

Four folders hold the chip layer. They are copies of public repositories, not code this course wrote, and the lessons never change them. Your project finds them through the shared CMake file, so you can build without installing anything else.

FolderWhat it gives youWhere it comes from
CMSIS_5/CMSIS/Core/IncludeThe Cortex-M core headers: core_cm3.h (NVIC, SysTick, the __IO macro), and cmsis_gcc.h (intrinsics such as __disable_irq).ARM-software/CMSIS_5, a sparse checkout of one folder
cmsis-device-f1The STM32F1 device headers: stm32f103xb.h (every register struct, base address and bit name), stm32f1xx.h, the startup file startup_stm32f103xb.s, and system_stm32f1xx.c (SystemInit and SystemCoreClock).STMicroelectronics/cmsis-device-f1
stm32f1xx-hal-driverThe HAL: Inc/ and Src/ for every STM32F1 peripheral. Used from lesson 69.STMicroelectronics/stm32f1xx-hal-driver
FreeRTOS-KernelThe FreeRTOS kernel, used by the stm32-freertos template from Part 7. Pinned to tag V11.2.0.FreeRTOS/FreeRTOS-Kernel

Check where a folder came from with git -C third_party/<folder> remote -v. Each one shows its origin URL. The snapshot this course was built from is the commit at the head of each repository (git log -1).

How to recreate third_party/

You should not need these commands, because the folders are already here. Keep them for a fresh clone of the course, or if a folder goes missing. Run them from the workspace's third_party/ folder. 

# run from third_party/
git clone --depth 1 https://github.com/STMicroelectronics/cmsis-device-f1
git clone --depth 1 https://github.com/STMicroelectronics/stm32f1xx-hal-driver
git clone --depth 1 --filter=blob:none --sparse https://github.com/ARM-software/CMSIS_5 CMSIS_5
git -C CMSIS_5 sparse-checkout set CMSIS/Core/Include
git clone --depth 1 -b V11.2.0 https://github.com/FreeRTOS/FreeRTOS-Kernel

The sparse checkout gets only the folder the build needs from CMSIS_5, which keeps the download small. --depth 1 keeps only the newest commit, which is all a build uses. Pin a version when you need repeatable builds. For the FreeRTOS clone, the -b V11.2.0 does that. The other three follow the default branch, so the course records the commit it was built from.

The shared CMake files

Every STM32 project in the course uses three files from templates/common/. Read them once, and the rest of Part 5 will make sense.

FileJob
arm-none-eabi.cmakeThe toolchain file. It names the Arm GCC programs (arm-none-eabi-gcc, objcopy, size) and tells CMake this is a bare-metal target.
stm32f1.cmakeThe chip settings: the Cortex-M3 flags (-mcpu=cortex-m3 -mthumb), STM32F103xB, the include paths, the default startup and system files, the linker script, and stm32_postbuild() that writes the .hex. It also defines stm32_use_hal().
stm32f103c8.ldThe linker script: where flash, RAM, the vector table, code and variables go (lesson 41). Lesson 68 writes a smaller one.

A project's CMakeLists.txt is short. It sets the toolchain, includes stm32f1.cmake, and lists its sources. 

cmake_minimum_required(VERSION 3.20)
set(CMAKE_TOOLCHAIN_FILE ${CMAKE_CURRENT_SOURCE_DIR}/../../../templates/common/arm-none-eabi.cmake)
project(blink C ASM)
include(../../../templates/common/stm32f1.cmake)

add_executable(blink main.c ${STM32_STARTUP})
stm32_postbuild(blink)

${STM32_STARTUP} is the list set in stm32f1.cmake: the vendor startup file and the system file. Lesson 68 replaces that list.

How tools/build.py builds it

You do not usually type the CMake commands. Ctrl+Shift+B runs tools/build.py, which looks at the project and picks a path. A project whose CMakeLists.txt calls pico_sdk_init() goes to the Pico SDK. Any other project with a CMakeLists.txt goes to plain CMake with the Arm toolchain, which is every STM32 project.

  1. If build/build.ninja is missing, run cmake -S project -B build -G Ninja. This is the configure step, and it finds the compiler and writes the build rules.
  2. Run cmake --build build. That compiles each source, links blink.elf, and runs the post-build step that writes blink.hex.
  3. The output always lands in build/, because wokwi.toml looks for build/blink.hex and build/blink.elf.

The build also prints the section sizes: text (code and constants in flash), data (initialised variables, which take flash and RAM), and bss (zeroed variables, RAM only). Keep an eye on these as the projects grow.

The Wokwi Blue Pill part

The diagram names the part board-stm32-bluepill. Its onboard LED is on PC13, and the LED is active low: a 0 on the pin lights it. The serial monitor connects to A9 and A10. Pin A9 is USART1 TX, and the simulator shows what it sends. Pin A10 is USART1 RX, and the characters you type in the monitor arrive there. Lesson 70 uses that receive path.

The simulator's clock and the course's clock are different things. The Wokwi docs say the Blue Pill runs at 72 MHz. The templates keep the default 8 MHz internal oscillator (HSI), which is what SystemCoreClock reports. Your baud rate and delay values depend on the clock the code really sets up, not on the chip's maximum.

Model answer

A generic Arm GCC compiles the C and assembly, with the Cortex-M3 flags. The device header gives the register names and the interrupt numbers, and the startup file gives the vector table and the reset handler. The linker script places code, constants and variables in flash and RAM, and the post-build step converts the ELF to a HEX file that the programmer or simulator loads. CMake ties those steps together through a toolchain file and a chip file.

Wokwi: STM32 Blue Pill part: read the description (the chip, the flash and RAM sizes, the onboard LED) and the simulation features table. Its table is the source of the limits in this course's notes. The register facts for later lessons come from the vendor headers, which you can read in third_party/cmsis-device-f1/Include/stm32f103xb.h.
