Setting up the STM32 toolchain

Compiler, vendor headers and build for the Blue Pill

By the end of this lesson you can build and simulate the STM32 CMSIS template on the Blue Pill, name the four third_party/ folders and where each comes from, explain what each build step produces, and change the blink rate and the serial message in the project.

From the Pico SDK to an STM32 build

Lesson 1 set up a compiler, lesson 41 showed the build pipeline in which source files pass through the compiler, the assembler and the linker to become an ELF file, and lesson 40 introduced the clock tree feeding the core and its peripherals. Those lessons concerned the RP2040, where the Pico SDK hides most of the chip-specific work behind one package, and this lesson moves to the STM32, where that work is visible.

A C file saying SysTick->LOAD = 7999; means nothing to a compiler until something tells it what SysTick is, where it lives in memory and what the number does. In industry that information comes from the chip vendor as headers and startup code, which the team's build system pulls in.

The toolchain, the chip layer and the build

On the RP2040 the Pico SDK arrives as one package that CMake is pointed at, whereas the STM32 world splits the same job into layers. The compiler is generic Arm GCC, knowing nothing about the chip, while the chip's own facts, its register names, interrupt numbers, startup file and clock code, come from the vendor and from Arm. You already have the compiler from lesson 1. What this lesson adds is the chip layer on top of it.

The Blue Pill carries an STM32F103C8, an Arm Cortex-M3 with 64 KB of flash and 20 KB of RAM, and the Wokwi simulator runs the same firmware on a model of the chip. The part page gives the chip's speed as 72 MHz and lists which peripherals the model implements, USART, EXTI, RCC, AFIO, I2C, SPI, CRC and WWDG being simulated while DMA, the IWDG watchdog, PWR and RTC are not Wokwi: STM32 Blue Pill part.

Three kinds of file make up the chip layer. A device header is a C header defining every register as a struct field and every bit as a named mask, a startup file holds the first code the chip runs after reset, and a linker script says where the code and variables go in memory. Lessons 67 to 70 use the vendor's versions, and lesson 68 writes its own startup file and linker script.

The compiler and the linker

A compiler translates one C source file into machine code for one target, the Arm GNU toolchain's arm-none-eabi-gcc producing Thumb code for an Arm core without an operating system. The name follows a convention, arm being the target, none meaning no OS and eabi standing for the embedded application binary interface, and the toolchain is the whole set of programs that turns source into firmware, the compiler, the assembler, the linker and the object-copy tool (Glossary: toolchain).

A linker joins the compiled files into one program. Each compiled file leaves some names undefined, main for example calling SystemInit, which lives in another file, and the linker resolves each such name by finding its definition elsewhere. It also decides the final address of every function and variable, reading a linker script to do so, the subject of lesson 68 (Glossary: linker).

The linker's output is an ELF file holding the code, the data, the addresses and the debug symbols, which debuggers and Wokwi read. Flash programmers and simulators often need something smaller, the HEX file, a text format listing each address with the bytes that belong there, and the build makes it from the ELF with objcopy in a post-build step shown below.

Device headers and register names

A peripheral such as the USART has a block of registers at a fixed address, so writing to USART1->DR is a store to that address on the bus, after which the USART hardware sends the byte. The header stm32f103xb.h defines the struct laying out the registers and the base address of the block, so the C name USART1 points at the right place, and a bit name such as USART_SR_TXE is a mask with a single bit set, so USART1->SR & USART_SR_TXE tests that bit.

Without the device header, the hex address of every register and the position of every bit would have to be copied from the reference manual by hand, whereas the vendor writes the names once and every project reuses them. The Cortex-M3 core has registers of its own, such as SysTick, which Arm defines in a second header, core_cm3.h.

The core clock and SystemCoreClock

A timing constant in code means something only with a known clock frequency. The STM32F1 starts on an internal RC oscillator called HSI, running at 8 MHz, and the CMSIS system file keeps the clock frequency in a variable named SystemCoreClock, which in system_stm32f1xx.c starts at 8000000, the HSI value written into it at reset. SystemCoreClockUpdate() recomputes it from the clock registers, so code that uses it stays correct if the clock changes later.

Although the Wokwi part page lists the chip at 72 MHz, the course's templates keep the 8 MHz default and never switch the clock to the PLL, so the core runs at 8 MHz and SystemCoreClock reads 8 MHz on the chip and in the simulator. Every clock-dependent number, such as the SysTick reload and the UART divisor, is therefore computed from that variable rather than typed in.

The shared CMake files

Every STM32 project in the course uses three files from templates/common/, and once they have been read, the rest of Part 5 follows.

FileJob
arm-none-eabi.cmakeThe toolchain file. It names the Arm GCC programs (arm-none-eabi-gcc, objcopy, size) and tells CMake this is a bare-metal target.
stm32f1.cmakeThe chip settings: the Cortex-M3 flags (-mcpu=cortex-m3 -mthumb), STM32F103xB, the include paths, the default startup and system files, the linker script, and stm32_postbuild() that writes the .hex. It also defines stm32_use_hal().
stm32f103c8.ldThe linker script: where flash, RAM, the vector table, code and variables go (lesson 41). Lesson 68 writes a smaller one.

A project's CMakeLists.txt is short, setting the toolchain, including stm32f1.cmake and listing its sources. 

cmake_minimum_required(VERSION 3.20)
set(CMAKE_TOOLCHAIN_FILE ${CMAKE_CURRENT_SOURCE_DIR}/../../../templates/common/arm-none-eabi.cmake)
project(blink C ASM)
include(../../../templates/common/stm32f1.cmake)

add_executable(blink main.c ${STM32_STARTUP})
stm32_postbuild(blink)

The first line sets the minimum CMake version, and the second points CMake at the toolchain file, so that every compile uses Arm GCC rather than the host compiler. project(blink C ASM) names the project blink with C and assembly sources, and the include line brings in the chip settings. add_executable lists the sources, main.c followed by the vendor startup and system files that stm32f1.cmake placed in STM32_STARTUP, and finally stm32_postbuild adds the step that makes the HEX file after linking.

${STM32_STARTUP} is the list set in stm32f1.cmake, holding the vendor startup file and the system file, and lesson 68 replaces it.

The build script tools/build.py

The CMake commands are rarely typed by hand, because Ctrl+Shift+B runs tools/build.py, which inspects the project and picks a path. A project whose CMakeLists.txt calls pico_sdk_init() goes to the Pico SDK, and any other project with a CMakeLists.txt, which includes every STM32 project, goes to plain CMake with the Arm toolchain.

  1. If build/build.ninja is missing, the script runs cmake -S project -B build -G Ninja, the configure step that finds the compiler and writes the build rules.
  2. It then runs cmake --build build, which compiles each source, links blink.elf and runs the post-build step that writes blink.hex.
  3. The output always lands in build/, because wokwi.toml looks for build/blink.hex and build/blink.elf.

The build also prints the section sizes, text for code and constants in flash, data for initialised variables, which take both flash and RAM, and bss for zeroed variables in RAM only, numbers worth watching as the projects grow.

Worked example: one line from main.c to blink.hex

We follow one line of the project through the build, supposing that main.c contains GPIOC->BSRR = GPIO_BSRR_BR13;. Before reading the steps, predict which stage of the build places the address of GPIOC.

  1. Preprocessing. The compiler first expands #include "stm32f1xx.h", pulling in the device header, so GPIO_BSRR_BR13 becomes (0x1UL << 29), the bit 29 mask from the header.
  2. Compiling. Arm GCC turns the expression into Thumb instructions, GPIOC being a pointer to the GPIO struct at the port C base address and the member BSRR lying at a fixed offset from it, so the compiled code is one store to base + offset.
  3. Linking. The address of GPIOC is a constant from the header rather than something in the file, so the linker has nothing to place for it, while it places the function's code in flash, in the .text section, and the startup's vector table at the start of flash.
  4. Making the HEX. The post-build step runs objcopy -O ihex on the ELF, writing blink.hex with the same bytes in text form, which the simulator loads into flash.
  5. Running. The core fetches the store instruction from flash and the bus carries the write to the GPIO block, where bit 29 of BSRR resets pin 13, which on the Blue Pill lights the onboard LED.

Each stage contributes one thing, the header the address and bit position, the compiler the instruction, the linker the placement and objcopy a file the programmer can load, so no stage places the address of GPIOC, which is fixed in the header from the start.

The Wokwi Blue Pill part

The diagram names the part board-stm32-bluepill, whose part page puts the onboard LED on PC13, and the course's projects drive that LED active low, a 0 on the pin lighting it, as the comments in main.c and the BR13 write both show. The serial monitor connects to A9 and A10, A9 being USART1 TX, whose output the simulator displays, and A10 USART1 RX, where characters typed into the monitor arrive, the receive path that lesson 70 uses.

The simulator's clock and the course's clock are different things. The Wokwi docs say the Blue Pill runs at 72 MHz. The templates keep the default 8 MHz internal oscillator (HSI), which is what SystemCoreClock reports. Your baud rate and delay values depend on the clock the code really sets up, not on the chip's maximum.

The template's main.c line by line

The solution's main.c is short enough to read in one sitting, and four pieces of it matter for this lesson. 

#define BLINK_HALF_PERIOD_MS  250U

static void delay_ms(uint32_t ms) {
    SysTick->LOAD = (SystemCoreClock / 1000U) - 1U;   /* 8000 - 1 at 8 MHz */
    SysTick->VAL  = 0;
    SysTick->CTRL = SysTick_CTRL_CLKSOURCE_Msk | SysTick_CTRL_ENABLE_Msk;
    while (ms--) {
        while ((SysTick->CTRL & SysTick_CTRL_COUNTFLAG_Msk) == 0) { }
    }
    SysTick->CTRL = 0;
}

BLINK_HALF_PERIOD_MS is a named constant holding the number of milliseconds the LED stays on or off, so the blink rate is one edit, whereas the number 250 written twice would invite forgetting one of them at the next change.

SysTick->LOAD is the reload value of SysTick, the 24-bit down-counter inside the Cortex-M core, and SystemCoreClock / 1000U is the number of core cycles in one millisecond, 8 000 at 8 MHz. One is subtracted because the counter counts from the reload value down to zero, so a reload of 7 999 gives 8 000 cycles per period. SysTick->VAL = 0 clears the current count, the CTRL write selects the core clock as the source and starts the counter, and the inner loop waits for COUNTFLAG, which the counter sets each time it wraps from zero to the reload value, so each wait lasts one millisecond. 

static void uart_init(void) {
    RCC->APB2ENR |= RCC_APB2ENR_IOPAEN | RCC_APB2ENR_USART1EN;
    GPIOA->CRH = (GPIOA->CRH & ~(0xFU << 4)) | (0xBU << 4);
    USART1->BRR = SystemCoreClock / 115200U;
    USART1->CR1 = USART_CR1_TE | USART_CR1_UE;
}

The first line turns on two clocks, because, as lesson 67 explains, a peripheral whose clock bit is 0 ignores writes. The second sets up PA9, whose field lies in CRH because pin 9 is in the upper half, starting at bit (9 − 8) × 4 = 4, and the value 0xB, binary 1011, gives configuration bits 10 (alternate-function push-pull) and mode bits 11 (50 MHz), while the mask clears the old field before the new value goes in, leaving the other pins' bits unchanged.

USART1->BRR is the baud-rate register, and the integer division 8000000 / 115200 gives the divisor 69 that the code writes, the fraction being lost, a register and clock value that lesson 70 uses again. The last line sets the transmitter enable (TE) and the USART enable (UE), which is all that output needs. 

static void uart_puts(const char *s) {
    while (*s) {
        while ((USART1->SR & USART_SR_TXE) == 0) { }
        USART1->DR = (uint8_t)*s++;
    }
}

uart_puts sends one byte at a time, waiting until the transmit data register is empty (TXE in the status register SR) and then writing the next character to DR. This polling loop spins until the hardware is ready, which is fine for a short startup message but blocks the program while the bytes go out, a cost that lesson 70 removes with interrupts.

Common mistakes and how to spot them

Four mistakes come up again and again in this setup, each with a visible symptom and a fix.

A silent serial monitor

The blink works but the monitor shows nothing, usually because of a missing clock enable, since with RCC_APB2ENR_USART1EN clear the USART ignores the writes to CR1 and DR and no byte leaves the chip. Enable the clock before any USART register access, as uart_init does, and the same rule holds for the GPIO clock of PA9.

Garbled serial text

The monitor shows random-looking symbols, or the right letters with wrong spacing, because the baud divisor does not match the clock the code really runs at: USART1->BRR = 72000000 / 115200U on a chip running at 8 MHz makes the divisor nine times too large and the bit timing wrong. Compute the divisor from SystemCoreClock, after calling SystemCoreClockUpdate(), as main does.

The simulator running the old program

After an edit to main.c the simulator still runs the old blink rate, because Wokwi loads build/blink.hex, which is rewritten only when the build succeeds, so a failed build leaves the old HEX in place. Read the build output for errors before starting the simulator, and stop the simulator before rebuilding.

A delay a thousand times too long or too short

The LED blinks once every few seconds or flickers too fast to see, usually because of a wrong unit, seconds passed where the function expects milliseconds, or SysTick reloaded with the cycle count instead of one less. The reload for a 1 ms period is SystemCoreClock / 1000U − 1U, the same formula as in lessons 67 and 73, so check in the debugger that SysTick->LOAD reads 7 999 at 8 MHz.

Recreating the third_party folders

These commands should not be needed, because the folders are already present, but they serve for a fresh clone of the course or a missing folder, run from the workspace's third_party/ folder. 

# run from third_party/
git clone --depth 1 https://github.com/STMicroelectronics/cmsis-device-f1
git clone --depth 1 https://github.com/STMicroelectronics/stm32f1xx-hal-driver

git clone --depth 1 -b V11.2.0 https://github.com/FreeRTOS/FreeRTOS-Kernel

The sparse checkout fetches only the folder of CMSIS_5 that the build needs, keeping the download small, and --depth 1 keeps only the newest commit, which is all a build uses. Pin a version when you need repeatable builds. For the FreeRTOS clone, the -b V11.2.0 does that. The other three follow the default branch, so the course records the commit it was built from.

Vendor packages in production builds

Vendor headers and startup files are never edited in a product. They come from the vendor in a folder the team pins to a version, a code review rejects any change to them, and changes go into the team's own files, the build picking up the vendor files through the same kind of CMake variables this course uses. A team upgrading the vendor package reads the release notes first, because a renamed register or a moved bit breaks code that compiled before.

Engineers are expected to find the compiler and linker flags in build/CMakeCache.txt and to run the build without an IDE, because a build that works only inside one IDE is hard to run on a build server, the workflow that lesson 79 covers.

Summary

  • The toolchain is the set of programs that turn source into firmware, the compiler, the assembler, the linker and objcopy.
  • The device header names every register and bit, a name such as USART_SR_TXE being a mask whose _Pos companion gives its bit position.
  • The CMSIS system file keeps the clock frequency in SystemCoreClock, and timing numbers come from that variable rather than typed-in constants.
  • The build produces an ELF file for debuggers and Wokwi and a HEX file for loading, made by objcopy -O ihex.
  • Each project sets a toolchain file, a chip file and a list of sources, with the vendor's startup and system files taken from third_party/.
  • A peripheral ignores writes until its clock bit is set, so the clock enable comes first.
  • Baud and timer values are computed from SystemCoreClock, and the build output is read before testing in the simulator.
