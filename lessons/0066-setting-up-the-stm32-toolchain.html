Setting up the STM32 toolchain

Your ARM GCC from lesson 1 can build for an STM32, but the chip's register names, startup code and clock setup come from a few folders in third_party/. This lesson shows what each one is, how the build joins them, and what comes out the other end.

By the end of this lesson you can build and simulate the STM32 CMSIS template on the Blue Pill, name the four third_party/ folders and where each comes from, explain what each build step produces, and change the blink rate and the serial message in the project.

Where we are and why it matters

Lesson 1 set up a compiler, and lesson 41 showed the build pipeline: source files go through the compiler, the assembler and the linker, and come out as an ELF file. Lesson 40 introduced the clock tree that feeds the core and its peripherals. Those lessons were about the RP2040, where the Pico SDK hides most of the chip-specific work behind one package. This lesson moves to the STM32, where you see that work yourself.

A C file that says SysTick->LOAD = 7999; means nothing to a compiler until someone tells it what SysTick is, where it lives in memory, and what the number does. In industry, that information comes from the chip vendor as headers and startup code, and the team's build system pulls it in.

The idea: a toolchain, a chip layer and a build

On the RP2040, the Pico SDK arrives as one package that you point CMake at. The STM32 world splits the same job into layers. The compiler is generic Arm GCC, and it knows nothing about your chip. The chip's own facts come from the vendor and from Arm: register names, interrupt numbers, the startup file and the clock code. You already have the compiler from lesson 1. What this lesson adds is the chip layer on top of it.

The Blue Pill has an STM32F103C8: an ARM Cortex-M3 with 64 KB of flash and 20 KB of RAM. The Wokwi simulator runs that same firmware on a model of the chip. The part page says the chip runs at 72 MHz, and lists which peripherals the model implements: USART, EXTI, RCC, AFIO, I2C, SPI, CRC and WWDG are simulated, while DMA, the watchdog IWDG, PWR and RTC are not. Wokwi: STM32 Blue Pill part

Three kinds of file make up the chip layer. A device header is a C header that defines every register as a struct field and every bit as a named mask. A startup file holds the first code the chip runs after reset. A linker script says where the code and variables go in memory. Lessons 67 to 70 use the first two, and lesson 68 writes its own versions of the last two.

Concepts, one at a time

The compiler and the linker

A compiler translates one C source file into machine code for one target. The Arm GNU toolchain, whose program is arm-none-eabi-gcc, produces Thumb code for an Arm core that has no operating system. The name is a convention: arm is the target, none means no OS, and eabi is the embedded application binary interface. The toolchain is the whole set of programs that turns source into firmware: the compiler, the assembler, the linker and the object-copy tool. Glossary: toolchain

A linker joins the compiled files into one program. Each compiled file leaves some names undefined. main calls SystemInit, which lives in another file, and the linker resolves that name by finding the other file's definition. The linker also decides the final address of every function and variable. The linker reads a linker script to make those decisions, and lesson 68 is about writing one. Glossary: linker

The output of the linker is an ELF file, which holds the code, the data, the addresses and the debug symbols. Debuggers and Wokwi read it. Flash programmers and simulators often need something smaller: the HEX file, which is a text format listing each address and the bytes that go there. The build turns the ELF into the HEX with objcopy, as the post-build step shows below.

Registers are addresses, and headers name them

A peripheral such as the USART has a block of registers at a fixed address. Writing to USART1->DR is a store to that address on the bus, and the USART hardware sends the byte. The header stm32f103xb.h defines the struct that lays out the registers, and the base address of the block, so the C name USART1 points at the right place. A bit name such as USART_SR_TXE is a mask with a single bit set, so USART1->SR & USART_SR_TXE tests that bit.

This is why the device header matters. Without it, you would need the hex address of every register and the position of every bit, copied from the reference manual by hand. The vendor writes those names once, and every project reuses them. The Cortex-M3 core has its own registers, such as SysTick, and Arm defines those in a second header, core_cm3.h.

The clock sets every timing number

A timing constant in code only means something if you know the clock frequency. The STM32F1 starts on an internal RC oscillator called HSI, which runs at 8 MHz. The CMSIS system file keeps the clock frequency in a variable named SystemCoreClock. In system_stm32f1xx.c, that variable starts at 8000000, and the HSI value is written into it at reset. SystemCoreClockUpdate() recomputes it from the clock registers, so code that uses it stays right if the clock changes later.

The Wokwi part page lists the chip at 72 MHz, but the course's templates keep the 8 MHz default. The projects never switch the clock to the PLL, so the core runs at 8 MHz and SystemCoreClock is 8 MHz on the chip and in the simulator. Every number that depends on the clock, such as the SysTick reload and the UART divisor, is computed from that variable, not typed in.

The shared CMake files

Every STM32 project in the course uses three files from templates/common/. Read them once, and the rest of Part 5 will make sense.

FileJob
arm-none-eabi.cmakeThe toolchain file. It names the Arm GCC programs (arm-none-eabi-gcc, objcopy, size) and tells CMake this is a bare-metal target.
stm32f1.cmakeThe chip settings: the Cortex-M3 flags (-mcpu=cortex-m3 -mthumb), STM32F103xB, the include paths, the default startup and system files, the linker script, and stm32_postbuild() that writes the .hex. It also defines stm32_use_hal().
stm32f103c8.ldThe linker script: where flash, RAM, the vector table, code and variables go (lesson 41). Lesson 68 writes a smaller one.

A project's CMakeLists.txt is short. It sets the toolchain, includes stm32f1.cmake, and lists its sources. 

cmake_minimum_required(VERSION 3.20)
set(CMAKE_TOOLCHAIN_FILE ${CMAKE_CURRENT_SOURCE_DIR}/../../../templates/common/arm-none-eabi.cmake)
project(blink C ASM)
include(../../../templates/common/stm32f1.cmake)

add_executable(blink main.c ${STM32_STARTUP})
stm32_postbuild(blink)

Line by line: the first line sets the minimum CMake version, and the second points CMake at the toolchain file, so every compile uses Arm GCC rather than the host compiler. project(blink C ASM) names the project blink and says it has C and assembly sources. The include line brings in the chip settings. add_executable lists the sources: your main.c, then the vendor startup and system files that stm32f1.cmake put in STM32_STARTUP. Last, stm32_postbuild adds the step that makes the HEX file after linking.

${STM32_STARTUP} is the list set in stm32f1.cmake: the vendor startup file and the system file. Lesson 68 replaces that list.

How tools/build.py builds it

You do not usually type the CMake commands. Ctrl+Shift+B runs tools/build.py, which looks at the project and picks a path. A project whose CMakeLists.txt calls pico_sdk_init() goes to the Pico SDK. Any other project with a CMakeLists.txt goes to plain CMake with the Arm toolchain, which is every STM32 project.

  1. If build/build.ninja is missing, run cmake -S project -B build -G Ninja. This is the configure step, and it finds the compiler and writes the build rules.
  2. Run cmake --build build. That compiles each source, links blink.elf, and runs the post-build step that writes blink.hex.
  3. The output always lands in build/, because wokwi.toml looks for build/blink.hex and build/blink.elf.

The build also prints the section sizes: text (code and constants in flash), data (initialised variables, which take flash and RAM), and bss (zeroed variables, RAM only). Keep an eye on these as the projects grow.

A worked trace: from main.c to blink.hex

Follow one line of the project through the build. Suppose main.c contains GPIOC->BSRR = GPIO_BSRR_BR13;. Here is what happens to it, step by step.

  1. Preprocessing. The compiler first expands #include "stm32f1xx.h", which pulls in the device header. GPIO_BSRR_BR13 becomes (0x1UL << 29), which is the bit 29 mask from the header.
  2. Compiling. Arm GCC turns the expression into Thumb instructions. GPIOC is a pointer to the GPIO struct at the port C base address, and the member BSRR is at a fixed offset from that address. The compiled code is one store to the address base + offset.
  3. Linking. The address of GPIOC is not in your file. It is a constant from the header, so the linker does not need to place anything for it. The linker places your function's code in flash, in the .text section, and places the startup's vector table at the start of flash.
  4. Making the HEX. The post-build step runs objcopy -O ihex on the ELF, which writes blink.hex with the same bytes in text form. The simulator loads that file into flash.
  5. Running. The core fetches the store instruction from flash, the bus carries the write to the GPIO block, and bit 29 of BSRR resets pin 13. On the Blue Pill that pin lights the onboard LED, so the LED turns on.

Each file contributes one thing: the header the address and bit position, the compiler the instruction, the linker the placement, and objcopy a file the programmer can load.

The Wokwi Blue Pill part

The diagram names the part board-stm32-bluepill. The part page says its onboard LED is on PC13. The course's projects drive that LED active low: a 0 on the pin lights it, which the comments in main.c and the BR13 write both show. The serial monitor connects to A9 and A10. Pin A9 is USART1 TX, and the simulator shows what it sends. Pin A10 is USART1 RX, and the characters you type in the monitor arrive there. Lesson 70 uses that receive path.

The simulator's clock and the course's clock are different things. The Wokwi docs say the Blue Pill runs at 72 MHz. The templates keep the default 8 MHz internal oscillator (HSI), which is what SystemCoreClock reports. Your baud rate and delay values depend on the clock the code really sets up, not on the chip's maximum.

Reading the solution's main.c

The solution's main.c is short enough to read in one sitting. Four pieces matter for this lesson. 

#define BLINK_HALF_PERIOD_MS  250U

static void delay_ms(uint32_t ms) {
    SysTick->LOAD = (SystemCoreClock / 1000U) - 1U;   /* 8000 - 1 at 8 MHz */
    SysTick->VAL  = 0;
    SysTick->CTRL = SysTick_CTRL_CLKSOURCE_Msk | SysTick_CTRL_ENABLE_Msk;
    while (ms--) {
        while ((SysTick->CTRL & SysTick_CTRL_COUNTFLAG_Msk) == 0) { }
    }
    SysTick->CTRL = 0;
}

BLINK_HALF_PERIOD_MS is a named constant, so the blink rate is one edit. The macro holds the number of milliseconds the LED stays on or off. Without it, the number 250 would appear in two places, and one of them would be forgotten the next time someone changed it.

SysTick->LOAD is the reload value of SysTick, the 24-bit down-counter inside the Cortex-M core. SystemCoreClock / 1000U is the number of core cycles in one millisecond, which is 8000 at 8 MHz. Subtracting one is needed because the counter counts from the reload value down to zero, so a reload of 7999 gives 8000 cycles per period. SysTick->VAL = 0 clears the current count. The CTRL write selects the core clock as the source and starts the counter. The inner loop waits for COUNTFLAG, which the counter sets each time it wraps from zero back to the reload value. Each wait is one millisecond. 

static void uart_init(void) {
    RCC->APB2ENR |= RCC_APB2ENR_IOPAEN | RCC_APB2ENR_USART1EN;
    GPIOA->CRH = (GPIOA->CRH & ~(0xFU << 4)) | (0xBU << 4);
    USART1->BRR = SystemCoreClock / 115200U;
    USART1->CR1 = USART_CR1_TE | USART_CR1_UE;
}

The first line turns on two clocks. Lesson 67 explains why: a peripheral whose clock bit is 0 ignores writes. The second line sets PA9, which is in CRH because pin 9 is in the upper half. The field for pin 9 starts at bit (9 − 8) × 4 = 4. The value 0xB is binary 1011, so the configuration bits are 10 (alternate-function push-pull) and the mode bits are 11 (50 MHz). The mask clears the old field before the new value goes in, which keeps the other pins' bits unchanged.

USART1->BRR is the baud-rate register. The integer division 8000000 / 115200 gives 69, which is the divisor the code writes. The fraction is lost in the division. Lesson 70 uses the same register, and the same clock value appears there. The last line sets the transmitter enable (TE) and the USART enable (UE), and nothing else is needed for output. 

static void uart_puts(const char *s) {
    while (*s) {
        while ((USART1->SR & USART_SR_TXE) == 0) { }
        USART1->DR = (uint8_t)*s++;
    }
}

uart_puts sends one byte at a time. It waits until the transmit data register is empty (TXE in the status register SR), then writes the next character to DR. This is polling: the loop spins until the hardware is ready. Polling is fine for a short startup message, but it blocks the program while the bytes go out, which lesson 70 avoids with interrupts.

Common mistakes and how to spot them

Four mistakes come up again and again in this setup. Each one has a symptom you can see, and a fix.

Mistake 1: the monitor stays silent

The blink works, but the monitor shows nothing, or shows nothing after the first build. The usual cause is a missing clock enable. If RCC_APB2ENR_USART1EN is not set, the USART ignores the writes to CR1 and DR, so no byte leaves the chip. The fix is the clock enable before any USART register access, as uart_init does. The same rule holds for the GPIO clock on PA9.

Mistake 2: the text arrives as garbage

The monitor shows characters that look like random symbols, or the right letters with wrong spacing. The cause is a baud divisor that does not match the clock the code really runs at. If you write USART1->BRR = 72000000 / 115200U while the chip runs at 8 MHz, the divisor is nine times too large, and the bit timing is wrong. The fix is to compute the divisor from SystemCoreClock, and to call SystemCoreClockUpdate() before that, as main does.

Mistake 3: the simulator shows the old program

You edit main.c, start the simulator, and the old blink rate runs. Wokwi loads build/blink.hex, which is only rewritten when the build succeeds. If the build failed, the old HEX stays in place. The fix is to read the build output for an error before you start the simulator, and to stop the simulator before you rebuild.

Mistake 4: a delay that is 1000 times too long or too short

The LED blinks once every few seconds, or flickers too fast to see. The cause is usually a wrong unit: you pass seconds where the function expects milliseconds, or you reload SysTick with the cycle count instead of one less. The formula SystemCoreClock / 1000U − 1U is the reload for a 1 ms period, and it is the same formula in lessons 67 and 73. The fix is to check the reload value in the debugger: SysTick->LOAD should read 7999 at 8 MHz.

In real projects

Vendor headers and startup files are never edited in a product. They come from the vendor, in a folder your team pins to a version, and a code review rejects a change to them. Changes go in your own files, and the build picks the vendor files up through the same CMake variables this course uses. A team that upgrades the vendor package reads the release notes first, because a renamed register or a moved bit breaks code that compiled before.

Engineers are expected to find the compiler and the linker flags in build/CMakeCache.txt and run the build without an IDE, because a build that works only inside one IDE is hard to run on a build server. Lesson 79 covers that workflow.

Summary

  • The toolchain is the set of programs that turn source into firmware: the compiler, the assembler, the linker and objcopy.
  • The device header names every register and bit. A name such as USART_SR_TXE is a mask, and _Pos gives its bit position.
  • The CMSIS system file keeps the clock frequency in SystemCoreClock. Timing numbers come from that variable, not from typed-in constants.
  • The build produces an ELF file for debuggers and Wokwi, and a HEX file for loading, made by objcopy -O ihex.
  • Each project sets a toolchain file, a chip file and a list of sources. The vendor's startup file and the system file come from third_party/.
  • A peripheral ignores writes until its clock bit is set, so the clock enable comes first.
  • Compute baud and timer values from SystemCoreClock, and read the build output before you test in the simulator.
