Lab 6: Port the monitor to Zephyr, and compare the two RTOSes

The Lab 4 monitor already runs on a Pico and a Blue Pill through one HAL. In this lab the same application runs as Zephyr threads on the Pico, and you measure what changed.

By the end of this lab you can run one application as threads on Zephyr, write the board file hal_zephyr.c on Zephyr's GPIO and I2C APIs, describe the OLED and the sensor in a devicetree overlay, and write a structured comparison of Zephyr and FreeRTOS with build-report numbers.

The idea

The application in projects/lab04-port-lab3-to-stm32/app is one super-loop, app_run(). This lab splits its jobs into threads: a button thread, a sensor thread, a UI thread, and a log thread that lives in the board file. The application sources are not copied. The Zephyr CMake file compiles them from the Lab 4 folder, so a change there reaches both ports. Lab 5 moves the same monitor onto FreeRTOS, with its own app.c. Its build is the FreeRTOS column of the comparison below.

The project layout

  1. projects/lab06-port-lab5-to-zephyr/starter: the threads and the board file, with TODO(learner) bodies. The overlay has the buttons, and the OLED and sensor nodes are yours to add.
  2. projects/lab06-port-lab5-to-zephyr/solution: everything finished. It prints LAB6 OK.
  3. Both folders compile ../../lab04-port-lab3-to-stm32/app/*.c. Keep that folder unchanged.

Requirements

  1. Build the starter and the solution for rpi_pico. Both must build with tools/verify_projects.py.
  2. In boards/rpi_pico.overlay, add the SSD1306 OLED at 0x3C as node oled, and the MYS-1 sensor at 0x48 as node mystery, on &i2c0 at 400 kHz. Add a binding for each compatible in dts/bindings.
  3. In hal_zephyr.c, implement every TODO(learner): the pins from aliases led0, sw0 and sw1, the I2C transfers through i2c_write and i2c_read, and the I2C lock.
  4. Use one mutex, i2c_lock, around every I2C transfer, with a timeout longer than one display flush.
  5. Run the log through a message queue, log_q, and a log thread that prints each line. hal_log() must never block.
  6. In src/main.c, run three threads: button_thread posts a bit mask on button_q when a button changes; sensor_thread puts each new sample on sample_q; ui_thread feeds the samples to the UI, redraws every 500 ms and logs every second.
  7. Keep the threads waiting at the start gate until main() has initialised the sensor and the display. Print LAB6 OK once after that.
  8. The diff of ../../lab04-port-lab3-to-stm32/app against the Lab 4 solution must be empty.

Milestones

  1. Milestone 1: the board boots. hal_init(), the log thread and hal_log() work, and the monitor prints LAB6 OK.
  2. Milestone 2: the buttons. Pressing A or B posts to button_q, and the menu moves.
  3. Milestone 3: the sensor. sensor_thread reports samples, and the status line shows LAB6 T= values that change.
  4. Milestone 4: the OLED. The screen shows the temperature on LIVE, without the display flush blocking the sensor.
  5. Milestone 5: the whole device. Check the acceptance criteria, then fill in the comparison below with your own numbers.

Acceptance criteria

  • The serial monitor prints LAB6 OK once, then one status line per second.
  • Button A cycles LIVE, MINMAX and SETPOINT, and the log shows each screen name.
  • On SETPOINT, button B raises the threshold from 28 to 35, then wraps to 20.
  • Removing the sensor's SDA wire makes the LIVE screen show SENSOR ERR within about a second, while the buttons and the log keep working.
  • In the solution, changing the OLED's reg in the overlay to a different address makes the build fail, because of the BUILD_ASSERT lines in hal_zephyr.c. Try it, then put the address back.
  • The app/ diff against Lab 4 is empty.

Hints

Hint for the start gate

A K_THREAD_DEFINE delay is a number of milliseconds, not K_FOREVER. A semaphore that main() gives after init is the simplest gate. Each thread takes it and gives it back.

Hint for the lock timeout

The display flush sends 1025 bytes, which is about 25 ms at 400 kHz. A sensor read that waits behind a flush must not time out, so the lock timeout has to be longer than that.

Hint for the buttons

ui_poll() reads the pins itself and debounces them. The message on button_q is only a wake-up, so the UI thread can respond at once. Post the message when the mask changes.

Hint if the threads stop

If LAB6 OK prints but nothing else does, check that k_sem_give(&app_ready) runs in main(), and that every thread calls wait_for_start() first.

The other comparisons

  • Portability. Zephyr's board file is the devicetree plus a small HAL, and the application uses the same APIs on every board that Zephyr supports. FreeRTOS's port is one kernel with a port layer for each core; the board code is yours.
  • Debugging. Zephyr prints a devicetree trace in zephyr.dts and checks addresses at build time; a wrong reg stops the build. FreeRTOS gives you the raw task list and stack high-water marks, and the code is closer to the registers.
  • Code shape. The Zephyr port needed a start gate and a copy of the status line, because app.c keeps log_status static. Lab 5 avoided the copy by writing its own app.c, which is why its file is longer. Compare the two if you want to see the cost of reuse.
  • When to choose each. Choose Zephyr for a product with several boards, a need for devicetree and Kconfig, and a vendor that ships a Zephyr port (Nordic and NXP do). Choose FreeRTOS for a small kernel with a tiny footprint and a large body of existing code, or when the team already knows it.

"Compare an RTOS port and a super-loop on the same hardware. What do you gain, and what do you pay?" Answer out loud in 60 seconds, then compare.

Model answer

Threads separate the timing of each job, so a slow display flush cannot delay a button press, and each job has its own stack. The costs are RAM for stacks, a scheduler, and the care needed around shared state: the mutex, the queue and the start order. A super-loop uses less RAM and is easier to reason about, but one slow step delays everything else.
