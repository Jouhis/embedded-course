Lab 6: Port the monitor to Zephyr, and compare the two RTOSes

The Lab 4 monitor already runs on a Pico and a Blue Pill through one HAL. In this lab the same application runs as Zephyr threads on the Pico, and you measure what changed.

By the end of this lab you can run one application as threads on Zephyr, write the board file hal_zephyr.c on Zephyr's GPIO and I2C APIs, describe the OLED and the sensor in a devicetree overlay, and write a structured comparison of Zephyr and FreeRTOS with build-report numbers.

Where we are and why it matters

Lab 4 gave the monitor a hardware abstraction layer (HAL). Its application code, in projects/lab04-port-lab3-to-stm32/app, calls functions such as hal_gpio_read and hal_i2c_write, and each board supplies its own implementation of those functions. Lab 5 (lab 5) moved the same monitor onto FreeRTOS. Lesson 86 gave the reasons for an RTOS, and lessons 97 to 99 gave you Zephyr's threads, the devicetree-based drivers, the logger and the test tools.

This lab asks the question a team asks when it changes RTOS. The application already works, so what does a port cost, what does it gain, and can the change be measured? You keep the application source unchanged, write only the board side and the threads, and then compare the two builds with the same tools. The comparison matters because a product team chooses a kernel for years, and the choice has to rest on numbers and on how the code is organised.

The concepts, one at a time

Splitting a super-loop into threads

The application's app_run() is a super-loop: one function that polls every input, updates the state and draws the screen, in turn. It is simple, and it has one weakness. A slow step delays all the others. The OLED flush takes about 25 ms at 400 kHz, so a button press that arrives during a flush waits for it. Threads fix that by giving each job its own stack and its own schedule, as lesson 97 showed. The sensor thread, the UI thread and the button thread then run independently, and the kernel decides which one has the CPU.

The threads still share state, so they still need the tools from lesson 97: a message queue for samples and events, and a mutex for the I2C bus. The application code is shared unchanged, and the port adds the threads in src/main.c. Each thread calls the application's public functions, such as sensor_poll, ui_on_sample and ui_poll, and does nothing else.

The start gate

A thread created with K_THREAD_DEFINE starts when the kernel starts it, and it can begin before main() has set up the sensor and the display. The delay argument of the macro is a number of milliseconds, so it cannot wait for an event. The solution uses a start gate: a semaphore, app_ready, that starts at zero. Each thread takes it and gives it straight back, and main() gives it once the devices are up. Until that give, every thread waits in wait_for_start(), and after it, all of them pass.

Doorbells, not data

The button thread posts a bit mask on button_q when the buttons change, but the UI thread reads the buttons again itself. The message is only a wake-up call, which the solution calls a doorbell. If the message is lost, the UI still polls every 5 ms, so nothing breaks, and the message arrives sooner than the poll would. This is a design choice worth noticing: the message carries a hint, and the state lives where it belongs.

Interrupts, polling and the choice in this port

Lab 5 read the buttons with an interrupt on EXTI12 and EXTI13, as the comparison table below says. Lab 6 polls them every 5 ms in a thread, which ports more simply because the overlay describes each button and the code needs no interrupt setup. Polling is simple and deterministic, but it can miss a press shorter than the scan period. The debounce in ui_poll then works on the samples it sees. A reviewer should ask whether 5 ms is short enough for the product, and the answer depends on the switch.

An I2C bus shared by two threads

The OLED and the MYS-1 share the bus i2c0. The sensor thread and the UI thread both transfer on it, so each transfer must take the lock i2c_lock, and no two transfers may overlap. The lock is a mutex with a timeout, so a stuck device cannot freeze the monitor: hal_i2c_write returns -1 after I2C_LOCK_TIMEOUT_MS (100 ms), as kernel/mutex.c returns -EAGAIN when a timeout expires. The port's hal_i2c_write turns that into -1 (hal_zephyr.c:105-106).

Checks at build time

The application expects the OLED at 0x3C and the MYS-1 at 0x48, and the overlay says the same. The solution makes sure they agree with BUILD_ASSERT. This macro evaluates a constant expression while the program is compiled, and it stops the build if the expression is false (include/zephyr/toolchain/common.h:229). DT_REG_ADDR(DT_NODELABEL(oled)) reads the devicetree address at compile time, so a wrong reg fails the build instead of showing up as SENSOR ERR on a screen.

One application, two ports

The Zephyr CMakeLists.txt compiles the application sources from ../../lab04-port-lab3-to-stm32/app directly, and adds that folder to the include path. Nothing is copied, so a fix in app/ reaches both the FreeRTOS port and the Zephyr port. The only Zephyr-side files are src/main.c and hal_zephyr.c, and the comparison at the end of the lab counts exactly those.

Worked example: the cost of one display flush

The lab's hint about the I2C lock timeout needs a number, so work it out from the code. The SSD1306 framebuffer is 8 pages of 128 bytes, and ssd1306_flush() sends it one page at a time (projects/lab04-port-lab3-to-stm32/app/ssd1306.c). Each page costs four I2C transfers: three 2-byte commands that select the page and the column, and one frame of 129 bytes, which is a control byte followed by the 128 data bytes.

  1. Bytes per page. 3 × 2 + 129 = 135 bytes.
  2. Bytes per flush. 8 × 135 = 1080 bytes, in 8 × 4 = 32 transfers.
  3. Bits on the wire. Each byte is 8 data bits and one acknowledge bit, so 9 clock pulses. That gives 1080 × 9 = 9720 clock pulses.
  4. Time at 400 kHz. 9720 / 400000 = 0.0243 s, which is about 24 ms. Each transfer also sends a start, an address and a stop, so the real time is a little longer, and the lab's figure of about 25 ms is the right size.

Now place the flush on the timeline. The UI thread starts a flush at t = 500 ms, and it runs for about 25 ms. The sensor thread asks for a sample at t = 501 ms. Its read queues behind the flush, and it waits up to about 24 ms for the bus. A lock timeout of 100 ms covers that wait with room to spare, so the read succeeds. A timeout of 10 ms would fail during every redraw, and the LIVE screen would show SENSOR ERR at each 500 ms frame. The 100 ms figure is therefore a reasoned choice: about four times the flush time, which leaves room for the sensor's own transfer.

Code, line by line

BUILD_ASSERT(DT_REG_ADDR(DT_NODELABEL(oled)) == 0x3C, "the Lab 4 application expects the OLED at 0x3C");

DT_NODELABEL(oled) refers to the overlay node with that label, and DT_REG_ADDR reads its first reg cell. The comparison is made at compile time, and the message is printed only when it fails. The same line appears for the MYS-1 at 0x48. 

K_MSGQ_DEFINE(button_q, sizeof(uint8_t), 8, 1);
K_MSGQ_DEFINE(sample_q, sizeof(int32_t), 4, 4);
K_SEM_DEFINE(app_ready, 0, 1);

The button queue holds one byte per message, with room for 8 messages, and it is a doorbell, so a small queue is enough. The sample queue holds one int32_t per sample, in hundredths of a degree, with room for 4 samples. The start gate is a semaphore that starts at 0 and has a limit of 1, so main() gives it once and the threads pass one at a time. 

static void wait_for_start(void)
{
    k_sem_take(&app_ready, K_FOREVER);
    k_sem_give(&app_ready);
}

Each thread calls this before its loop. It takes the gate and returns it at once, so the next thread can pass. Taking and giving the same semaphore is the way to let every waiter through with one give. 

static void button_thread(void *p1, void *p2, void *p3)
{
    wait_for_start();
    uint8_t last = read_buttons();
    while (1) {
        uint8_t now = read_buttons();
        if (now != last) {
            last = now;
            (void)k_msgq_put(&button_q, &now, K_NO_WAIT);
        }
        k_msleep(BUTTON_SCAN_MS);
    }
}

The thread reads the level of both buttons every 5 ms. When the mask changes, it posts the new mask, and the K_NO_WAIT means a full queue drops the doorbell, while the UI still reads the button state itself. The (void) cast tells the reader that the return value is ignored on purpose. 

while (k_msgq_get(&sample_q, &centi, K_NO_WAIT) == 0) {
    ui_on_sample(centi);
}

The UI thread drains the sample queue with K_NO_WAIT in a loop, so it handles every sample that arrived since the last pass and then carries on. A K_FOREVER here would block the UI when there was nothing to show, and the buttons would wait. 

void hal_log(const char *line)
{
    /* ... copy the text into a queue slot ... */
    if (k_msgq_put(&log_q, &item, K_NO_WAIT) != 0) {
        log_dropped++;
    }
}

hal_log copies the line into the queue and returns. The UART is slow, so the printing happens in the log thread, which waits with K_FOREVER on the same queue. A full queue drops the line and counts it in log_dropped, instead of holding the UI until the UART has room. 

int main(void)
{
    hal_init();
    ui_init();
    if (!sensor_init() || !display_init()) {
        hal_log("LAB6 init failed");
        return 0;
    }
    hal_log("LAB6 OK");
    k_sem_give(&app_ready);
    return 0;
}

The order matters. The hardware is set up first, the sensor and display are initialised, and only then does main() open the gate. If either initialisation fails, the threads never start, and the monitor prints the failure. The final k_sem_give is the line that makes the three threads run, so a missing give is the most common cause of a silent monitor.

Common mistakes and how to spot them

A thread that skips the start gate

If one thread, say the sensor thread, does not call wait_for_start(), it runs before main() has initialised the sensor. Its first reads fail, and the screen shows SENSOR ERR for a moment, or the first status lines report errors that then go away. The fix is to call wait_for_start() at the top of every thread, as the solution does.

A lock timeout shorter than the flush

If I2C_LOCK_TIMEOUT_MS is set to 10, the sensor read waits behind the display flush for longer than 10 ms, and hal_i2c_read returns -1. The LIVE screen then shows SENSOR ERR at every redraw, and the flicker lines up with the 500 ms frame. The symptom is a regular flicker, not a dead sensor. The fix is the timeout reasoned out in the worked example.

A blocking log call

If hal_log used K_FOREVER instead of K_NO_WAIT, the UI thread would stop whenever the log queue was full, which happens when the UART is slow and several lines arrive together. The symptom is that the buttons respond late, but only while the log is busy. The fix is the non-blocking put, and the dropped-line counter makes the loss visible rather than silent.

A wrong address in the overlay

If the overlay says reg = <0x3d> for the OLED, the build stops with the BUILD_ASSERT message, the Lab 4 application expects the OLED at 0x3C. You see the problem before you flash anything. Restore the address, and the build passes again.

Missing CONFIG_I2C

Without CONFIG_I2C=y, the I2C driver is not built, and hal_init() prints hal: i2c0 is not ready. The sensor and display then fail to initialise, and the monitor prints LAB6 init failed. The fix is the line in prj.conf, as lesson 98 showed.

A missing give on the start gate

If LAB6 OK prints but nothing else does, the gate was never opened. Every thread is waiting in wait_for_start(), so the kernel has nothing to run. The fix is the k_sem_give(&app_ready) at the end of main(), which the hint below describes.

In real projects

A port like this is a routine task in embedded teams. The application is kept free of kernel calls, so the same code runs on the bench, in a simulator and on another RTOS. A reviewer checks the port for three things: that the application source has no kernel calls, that every shared bus has one lock with a reasoned timeout, and that every log call is non-blocking. Those checks are short, and they catch most of the problems this lab shows.

The comparison table is the part a manager reads. It shows the cost in flash and RAM, the number of queues and threads, and the code that the team must maintain. Numbers from two different chips are never exact, so the table gives both figures and the reason for each, and it says plainly what cannot be compared.

Hints

Hint for the start gate

A K_THREAD_DEFINE delay is a number of milliseconds, not K_FOREVER. A semaphore that main() gives after init is the simplest gate. Each thread takes it and gives it back.

Hint for the lock timeout

The display flush sends 32 I2C transfers, 1,080 bytes in total (8 pages, each with three 2-byte commands and a 129-byte data frame), which is about 25 ms at 400 kHz. A sensor read that waits behind a flush must not time out, so the lock timeout has to be longer than that.

Hint for the buttons

ui_poll() reads the pins itself and debounces them. The message on button_q is only a wake-up, so the UI thread can respond at once. Post the message when the mask changes.

Hint if the threads stop

If LAB6 OK prints but nothing else does, check that k_sem_give(&app_ready) runs in main(), and that every thread calls wait_for_start() first.

The other comparisons

  • Portability. Zephyr's board file is the devicetree plus a small HAL, and the application uses the same APIs on every board that Zephyr supports. FreeRTOS's port is one kernel with a port layer for each core; the board code is yours.
  • Debugging. Zephyr prints a devicetree trace in zephyr.dts and checks addresses at build time; a wrong reg stops the build. FreeRTOS gives you the raw task list and stack high-water marks, and the code is closer to the registers.
  • Code shape. The Zephyr port needed a start gate and a copy of the status line, because app.c keeps log_status static. Lab 5 avoided the copy by writing its own app.c, which is why its file is longer. Compare the two if you want to see the cost of reuse.
  • When to choose each. Choose Zephyr for a product with several boards, a need for devicetree and Kconfig, and a vendor that ships a Zephyr port (Nordic and NXP do). Choose FreeRTOS for a small kernel with a tiny footprint and a large body of existing code, or when the team already knows it.

Summary

  • A port splits the super-loop into threads, and the application source stays unchanged.
  • A start gate, a semaphore that main() gives once the devices are up, holds the threads until they can run.
  • Buttons travel as doorbell messages, and the state is read where it lives.
  • One mutex with a reasoned timeout guards the I2C bus, and the timeout must exceed one display flush (about 25 ms, 1,080 bytes at 400 kHz).
  • The log is non-blocking: K_NO_WAIT drops and counts a line rather than stall the UI.
  • BUILD_ASSERT turns a wrong devicetree address into a build error.
