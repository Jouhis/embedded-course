Memory: stack vs heap, static allocation, and detecting stack overflow

A stack overflow in firmware prints nothing. It overwrites a variable, or a return address, and the bug shows up several functions later. This lesson shows how to see how deep the stack really goes, and why most embedded standards avoid the heap after startup.

By the end of this lesson you can read the Pico's stack bounds from the linker symbols, paint the unused stack and report its high-water mark, and say why malloc() is banned in most firmware after startup.

The idea: three regions in one RAM

The RP2040 has 256 KB of SRAM starting at 0x20000000. The program uses three parts of it. The static data (globals and static variables) has a fixed size and lives for the whole run (lessons 41 and 42 show how the linker places it). The stack holds the call frames, and it grows downward from the top (lesson 33). The heap is the area that malloc() hands out, and it grows upward. The stack and the heap grow toward each other, so a deep stack and a large heap can collide. That is the general case the figure below shows. On the Pico's default layout the core 0 stack is in SCRATCH_Y and the heap is limited to the main RAM, so the two never share an address range; the figure is a schematic of the general rule, not a map of this linker script.

On the Pico, the SDK's linker script reserves a fixed stack for core 0. The default is PICO_STACK_SIZE, which is 0x800, or 2048 bytes, and the stack starts at the top of SCRATCH_Y, a 4 KB bank that ends at 0x20042000, just above the 256 KB main RAM (pico-sdk, src/rp2040/pico_platform/memmap_default.ld and rp2_common/pico_standard_link/script_include; the RP2040 default for PICO_STACK_SIZE is in src/rp2040/pico_platform/include/pico/platform.h, read in the SDK 2.3.1 copy).

Why most standards ban malloc after startup

malloc() is convenient on a PC, where the heap is large and paged. On a microcontroller it causes three problems. First, the heap can fragment: after many allocations and frees of different sizes, there can be enough free bytes in total but no single block big enough, so the call fails late and at random. Second, the time an allocation takes is not fixed, which breaks a real-time deadline. Third, a failed call returns a null pointer that the code must check on every path, and the failure often happens only after months of uptime. MISRA C:2012 rule 21.3 prohibits the allocation and free functions of <stdlib.h>. The rule text is in the paid MISRA document; a tool vendor's summary of it is in the Polyspace rule page.

A common claim is that malloc is "slower". That is not the main reason. The main reason is that the failure happens at a time you do not choose, in a state you did not test.

Static allocation and memory pools

The usual alternative is to allocate everything at startup, from fixed-size arrays. A memory pool is an array of identical blocks with a free list: taking a block and returning one are a few pointer moves, the time is fixed, and no size fragments. The pool's size is part of the design, so the worst case is known before the device ships. 

#define POOL_BLOCKS 8u

typedef struct msg { uint8_t payload[32]; struct msg *next; } msg_t;

static msg_t pool[POOL_BLOCKS];      /* in .bss: reserved at link time, free at run time */
static msg_t *free_list;

static msg_t *pool_take(void) {
    msg_t *m = free_list;
    if (m) free_list = m->next;   /* NULL means the pool is empty: handle it */
    return m;
}

Detecting stack overflow

A stack overflow writes into whatever lies below the stack, so the damage can be silent. Three checks catch it.

  1. Painting and high-water mark. Before the program runs, fill the unused stack with a known pattern. After it runs, the lowest word that no longer holds the pattern is the deepest point the stack reached. Its distance from the top is the high-water mark.
  2. A canary. Put a known word at the lowest reserved address. If the stack ever writes it, the stack has passed its limit. A canary only tells you after the damage. It does not stop the write.
  3. An MPU guard. The Cortex-M MPU can make the bottom of the stack unwritable, so the overflow faults at the moment it happens (lesson 39). The Pico SDK can install that guard for core 0 when PICO_USE_STACK_GUARDS is 1. Its default is 0: the PICO_CONFIG entry in src/rp2350/pico_platform/include/pico/platform.h says so, the RP2040 headers do not define it, and runtime_init.h compiles the guard code only when it is 1. The source is src/rp2_common/pico_runtime_init/runtime_init_stack_guard.c and runtime_init.h in the SDK 2.3.1 copy, and this lesson did not test the guard.

Why memory is the first thing to design

Lessons 33 and 41 showed the stack and the linker from the outside: what a call pushes, and where the linker places the code. This lesson is about the RAM itself. On a PC, a running program can ask the operating system for more memory when it needs it, and the operating system pages it in from disk. An MCU has no such help. It has a fixed amount of RAM, set when the chip was made, and the program must fit inside it on every run, including the worst run. The RP2040 on the Pico has 256 KB of SRAM, and the STM32F103 on the Blue Pill has less. If a program overflows its RAM, nothing tells you at compile time, and the failure may show up much later.

That is why firmware designs memory before it writes code. The question is not "how much does this use today", but "how much does it use in the worst case, and where does each byte live". This lesson gives the vocabulary for that question.

The concepts, one at a time

Static storage

A global variable, or a static variable inside a function, has static storage duration: it exists for the whole run of the program, and its address is fixed by the linker. The linker groups it into two sections. .data holds the initial values, which are copied from flash into RAM at start-up. .bss holds the variables that start at zero, which the start-up code clears to zero. Lesson 42 shows the copy. In both cases the size is known at link time, so the linker can tell you the total before the program runs. That number is the fixed part of your RAM budget.

The stack

The stack holds the frames of the functions that are running: the return address, saved registers and local variables. Each call pushes a frame and each return pops it. The stack pointer, SP, marks the current end. On the Cortex-M the stack grows downward, so a push lowers SP, which is what lesson 33 describes. The size of the stack is fixed by the linker, and nothing checks it while the program runs. If a frame writes below the bottom of the stack, the write goes into whatever is there.

The heap

The heap is the region that malloc() manages. A call asks for a number of bytes and receives a pointer to a block, and a call to free() returns the block. The allocator must track which blocks are free and how big they are, and that bookkeeping is the source of the problems below. On the Pico, the heap starts at the symbol __end__, after the static data, and it ends at __HeapLimit, the end of the main RAM.

Fragmentation

Fragmentation is what happens when free memory is split into pieces that are too small. The total can be large while no single request fits. Here is a worked example with a heap of 300 bytes.

  1. Allocate A, 100 bytes. It takes bytes 0 to 99. Free space: bytes 100 to 299, 200 bytes.
  2. Allocate B, 100 bytes. It takes bytes 100 to 199. Free space: bytes 200 to 299, 100 bytes.
  3. Allocate C, 100 bytes. It takes bytes 200 to 299. Free space: none.
  4. Free A. Bytes 0 to 99 are free. Free space: 100 bytes in one block.
  5. Free C. Bytes 200 to 299 are free. Free space: two blocks of 100 bytes each, 200 bytes in total.
  6. Request D, 150 bytes. The total free space is 200 bytes, but the largest block is 100 bytes. The request fails.

Step 6 is the one that surprises people. A test that frees everything at the end passes, and the failure appears only after a long run with a particular pattern of sizes. The failure is also not reproducible by reading the code, because it depends on the order of the calls.

Predictability

A second reason to avoid malloc() is time. A real-time task has a deadline, and the allocator's search for a free block takes a number of steps that depends on the state of the heap. Two calls with the same size can take different times. A deadline needs a bound, and the heap does not give one in general. Lesson 55 introduced deadlines, and this is one of the things that breaks them.

A memory pool, with numbers

A memory pool avoids both problems. It is an array of blocks of one size, and a free list that links the free ones together. Taking a block is one step, and returning one is one step, so the time is fixed. Because all blocks are the same size, no block can be too small for a request, and no free space splits into unusable pieces. On the Cortex-M, a pointer is 4 bytes, and the msg_t struct in the code below holds 32 bytes of payload and one pointer, so its size is 36 bytes. Eight blocks take 8 × 36 = 288 bytes, and that number is known when the program is compiled.

The high-water mark

The high-water mark is the deepest the stack has ever been. It is the most useful number a firmware team can measure, because the stack size is a design choice and the mark tells you how much margin you have. A tool can measure it only if it can tell used memory from unused. Painting provides that: fill the free stack with a known value, run the program, and look for the first place where the value has changed. The value 0xA5A5A5A5 is an arbitrary pattern that real code does not produce by accident.

The code, line by line

The painting code is short, and each line has one job.

  1. extern char __StackBottom; declares the symbol, which the linker defines. The code takes its address, not its value, and the contents are never read. The type is char only because it is a placeholder for a byte address.
  2. __asm volatile ("mov %0, sp" : "=r"(sp)); reads the stack pointer directly. The painting must know where SP is now, so that it stops above the current frames. The volatile keeps the compiler from moving the read.
  3. *lo = CANARY_WORD; writes the canary into the lowest reserved word. It is written first so that the paint loop, which starts one word higher, does not overwrite it.
  4. for (volatile uint32_t *p = lo + 1; p < hi; p++) *p = PAINT_WORD; fills every word from the canary up to SP minus 64 bytes. The 64-byte margin protects the frames that are still in use.
  5. s_paint_limit = (uint32_t *)hi; remembers where the painted part ends, so the scan later stops there.
  6. In high_water_bytes(), the loop compares each word with the paint. The first word that differs is the lowest word the stack wrote. (uintptr_t)&__StackTop - (uintptr_t)p converts its address into a distance from the top, in bytes.

The stack-frame arithmetic in the disassembly of this build is push {lr} followed by sub sp, #20, which is 4 + 20 = 24 bytes per call. You can check the same thing in the Debug disassembly of your build with arm-none-eabi-objdump -d.

Common mistakes and how to spot them

  1. The heap works for a day, then fails. A device calls malloc() for each message. Tests pass, and after a day in the field malloc() returns NULL, which the code does not expect. The symptom is a rare failure with no matching input. The fix is a pool allocated at start-up, as above, with a check for an empty free list.
  2. The canary is painted over. The paint loop starts at &__StackBottom instead of one word above it. The symptom is CANARY HIT on the first run, before any overflow. The fix is the order in the code: write the canary, then paint from the next word.
  3. The high-water report says 0 bytes. The scan stops at s_paint_limit, and that is never set, or it is set before the paint runs. The symptom is a report of 0 bytes, even though the recursion clearly ran. The fix is to read the stack pointer inside paint_unused_stack(), and to set the limit at the end of the paint.
  4. The canary is taken as protection. A team sees CANARY OK at the end of a test and assumes the stack is safe. The canary only sees a write after it has happened, and a stack overflow can corrupt a variable and return a wrong value long before the canary is checked. The fix is to measure the high-water mark under the worst test, leave margin, and where the hardware offers a guard, enable it.

In real projects

Most embedded code standards restrict dynamic memory. MISRA C:2012 has a rule that prohibits the allocation and free functions in <stdlib.h> (rule 21.3, as summarised in the Polyspace page cited above). In a review, a reviewer who sees malloc() in firmware asks where the memory comes from, what happens when it returns NULL, and what the worst-case heap use is. A good answer is a static bound. Teams also run the high-water measurement in their test builds, record the number, and fail the build when the margin shrinks below an agreed limit. That is the process that turns a stack size into a number someone checked. In an interview, the question "why avoid malloc" is best answered with the fragmentation example, because it shows the failure without relying on speed.

Summary

  • RAM on an MCU is fixed. Designing its use means finding the worst case of each region.
  • Static data is sized at link time. The stack is fixed by the linker and not checked at run time.
  • Fragmentation can leave enough free bytes in total and no block big enough. A pool of equal blocks avoids it and has a fixed time per call.
  • Paint the free stack, run, and find the first changed word to measure the high-water mark.
  • A canary detects an overflow after it happens. An MPU guard can stop the write, where the hardware has one.
  • On the Pico, the stack is in SCRATCH_Y, the main heap ends at the top of main RAM, and the linker symbols give both bounds.

Try it in Wokwi

The project is projects/0078-stack-painting. The starter prints a stack report, but its painting and measurement functions are stubs marked TODO(learner), so it prints STACK PAINT FAIL. The recursion is written for you. In the course's Debug build each call uses a 24-byte frame, and recurse(16) makes 17 calls, so the recursion alone uses 408 bytes of the 2048-byte stack.

  1. Open projects/0078-stack-painting/starter in VS Code (File → Open Folder). Build with Ctrl+Shift+B, then start the simulator with F1 → Wokwi: Start Simulator. The monitor prints STACK PAINT FAIL.
  2. Your task, part 1: in paint_unused_stack(), write the canary into the word at &__StackBottom. Then paint every word from the next one up to current_sp() - PAINT_MARGIN_BYTES with PAINT_WORD. Set s_paint_limit to the top of the painted range.
  3. Your task, part 2: in high_water_bytes(), scan the painted words from the bottom up, skipping the canary. The first word that is not the paint is the deepest point. Return the distance from &__StackTop, or 0 if every word still has the paint.
  4. Build and run. The monitor prints the reserved size and the high-water mark, and then STACK PAINT OK. The high-water mark must be at least 408 bytes, the 17 frames of the recursion. In the solution's Debug build it should read 440 bytes: the 408 plus the 32-byte frame of main(), which sits above the painted region. If your number differs, check the frame sizes in the disassembly before you change the code.
  5. Optional: in canary_intact(), return whether the word at &__StackBottom still holds CANARY_WORD. The last line of the program prints CANARY OK or CANARY HIT after a 128-deep recursion, which writes about 1 KB below the reserved stack. In the starter, canary_intact() is a stub that always returns true, so the line says CANARY OK until you write the check. In the solution, the disassembly places the canary exactly on the depth word of the 85th frame of the overflow, so the solution should print CANARY HIT. This lesson could not run the simulator to confirm that, so treat it as the expected result to check on your run.
Hint for the scan

Walk from lo + 1 up to s_paint_limit, comparing each word with PAINT_WORD. The stack grows down, so the first changed word, reached from the bottom, is the lowest one that the stack wrote. Subtract its address from &__StackTop, cast to uintptr_t, to get bytes.

Hint if the report says 0 bytes

The scan stops at s_paint_limit, so the paint must reach up to that point. If s_paint_limit was never set, the loop does nothing and returns 0. Also check that current_sp() is read in paint_unused_stack(), not earlier in main().

"Why would you avoid malloc in firmware?" Answer out loud in 60 seconds, then compare.

Model answer

On a microcontroller the heap is small and it fragments. After many allocations and frees, an allocation can fail even though the total free memory looks fine, and it fails at a time the test suite did not choose. The allocation time is also not fixed, which breaks deadlines. I would allocate everything at startup from static arrays or a fixed memory pool, so the worst case is known from the design. Then I would check the stack with painting, a high-water mark and a canary, and enable an MPU guard where the hardware has one.
