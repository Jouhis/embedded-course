Memory

Stack, heap and static allocation

By the end of this lesson you can read the Pico's stack bounds from the linker symbols, paint the unused stack and report its high-water mark, and say why malloc() is banned in most firmware after startup.

A fixed amount of RAM

Lessons 33 and 41 showed the stack and the linker from the outside, what a call pushes and where the linker places the code, while this lesson concerns the RAM itself. A PC program can ask the operating system for more memory, which pages it in from disk, but an MCU has a fixed amount of RAM set when the chip was made, and the program must fit inside it on every run, including the worst. The RP2040 on the Pico has 256 KB of SRAM and the STM32F103 on the Blue Pill less, and since nothing reports an overflow at compile time, the failure may surface much later.

Firmware therefore designs its memory before writing code, asking how much the program uses in the worst case and where each byte lives, and this lesson provides the vocabulary for that question.

Static storage in .data and .bss

A global variable, or a static variable inside a function, has static storage duration, existing for the whole run at an address fixed by the linker, which groups it into one of two sections. .data holds variables with initial values, copied from flash into RAM at start-up, and .bss those starting at zero, which the start-up code clears, as lesson 42 shows. In both cases the size is known at link time, so the linker can report the total before the program runs, and that number is the fixed part of the RAM budget.

The stack

The stack holds the frames of the running functions, their return addresses, saved registers and local variables, each call pushing a frame and each return popping it, with the stack pointer, SP, marking the current end. On the Cortex-M the stack grows downward, so a push lowers SP, as lesson 33 describes, and its size is fixed by the linker and checked by nothing at run time, so a frame written below the bottom of the stack lands in whatever lies there.

The heap

The heap is the region that malloc() manages, a call asking for a number of bytes and receiving a pointer to a block, which free() later returns. The allocator must track which blocks are free and how big they are, and that bookkeeping is the source of the problems below. On the Pico the heap starts at the symbol __end__, after the static data, and ends at __HeapLimit, the end of the main RAM.

Heap fragmentation

Fragmentation happens when free memory is split into pieces that are too small, so that the total can be large while no single request fits. We follow a heap of 300 bytes through six calls, and before reading the last step, predict whether a 150-byte request succeeds with 200 bytes free.

  1. Allocate A. A takes 100 bytes, bytes 0 to 99, leaving bytes 100 to 299, 200 bytes, free.
  2. Allocate B. B takes bytes 100 to 199, leaving bytes 200 to 299, 100 bytes, free.
  3. Allocate C. C takes bytes 200 to 299, leaving no free space.
  4. Free A. Bytes 0 to 99 become free, 100 bytes in one block.
  5. Free C. Bytes 200 to 299 become free, giving two blocks of 100 bytes, 200 bytes in total.
  6. Request D. D asks for 150 bytes, and although 200 bytes are free, the largest block is 100 bytes, so the request fails.

Step 6 is the one that surprises people, because a test that frees everything at the end passes and the failure appears only after a long run with a particular pattern of sizes, which reading the code cannot reproduce, since it depends on the order of the calls.

Fragmentation resembles a car park where cars of different sizes come and go all day, so that by evening the free spaces add up to room for a bus but lie scattered between parked cars, and the bus does not fit, which is how a heap ends up after many malloc and free calls of different sizes. The comparison breaks because the parked cars eventually leave, whereas a long-lived allocation can pin a gap in place for the whole run.

Allocation time and deadlines

A second reason to avoid malloc() is time. A real-time task has a deadline, while the allocator's search for a free block takes a number of steps that depends on the state of the heap, so two calls of the same size can take different times, and since a deadline needs a bound that the heap does not give in general, this is one of the things that breaks the deadlines introduced in lesson 55.

Memory pools

A memory pool avoids both problems, being an array of equal-sized blocks with a free list linking the free ones, so that taking or returning a block is one step and its time fixed, and because all blocks share one size, none is too small for a request and no free space splits into unusable pieces. On the Cortex-M a pointer is 4 bytes and the msg_t struct in the code below holds 32 bytes of payload and one pointer, so it occupies 36 bytes, and eight blocks take

RAMpool = N × sizeblock = 8 × 36 B = 288 B(1)

where N is the number of blocks and sizeblock the size of one block, a number known when the program is compiled.

Three regions in one RAM

The RP2040 has 256 KB of SRAM starting at 0x20000000, of which the program uses three parts: the static data (globals and static variables), with a fixed size and a lifetime of the whole run (lessons 41 and 42 show how the linker places it), the stack, holding the call frames and growing downward from the top (lesson 33), and the heap, the area malloc() hands out, growing upward. The stack and the heap therefore grow toward each other, so a deep stack and a large heap can collide, which is the general case the figure shows, whereas on the Pico's default layout the core 0 stack lies in SCRATCH_Y and the heap is limited to the main RAM, so the two never share an address range, the figure being a schematic of the general rule rather than a map of this linker script.

On the Pico the SDK's linker script reserves a fixed stack for core 0, by default PICO_STACK_SIZE, which is 0x800, or 2 048 bytes, starting at the top of SCRATCH_Y, a 4 KB bank that ends at 0x20042000, just above the 256 KB main RAM (pico-sdk, src/rp2040/pico_platform/memmap_default.ld and rp2_common/pico_standard_link/script_include; the RP2040 default for PICO_STACK_SIZE is in src/rp2040/pico_platform/include/pico/platform.h, read in the SDK 2.3.1 copy).

Firmware rules against malloc after startup

malloc() is convenient on a PC, where the heap is large and paged, but on a microcontroller it causes three problems. The heap can fragment, so that after many allocations and frees of different sizes enough bytes are free in total but no single block is big enough, and the call fails late and at random, the time an allocation takes is not fixed, which breaks a real-time deadline, and a failed call returns a null pointer that the code must check on every path, the failure often coming only after months of uptime. MISRA C:2012 rule 21.3 prohibits the allocation and free functions of <stdlib.h>. The rule text is in the paid MISRA document; a tool vendor's summary of it is in the Polyspace rule page.

A common claim is that malloc is "slower". The stronger reason is that the failure happens at a time you do not choose, in a state you did not test.

Static allocation with a memory pool

The usual alternative is to allocate everything at startup from fixed-size arrays, a pool of identical blocks with a free list in which taking and returning a block are a few pointer moves, the time is fixed and no size fragments. The pool's size is part of the design, so the worst case is known before the device ships. 

#define POOL_BLOCKS 8u

typedef struct msg { uint8_t payload[32]; struct msg *next; } msg_t;

static msg_t pool[POOL_BLOCKS];      /* in .bss: reserved at link time, free at run time */
static msg_t *free_list;

static msg_t *pool_take(void) {
    msg_t *m = free_list;
    if (m) free_list = m->next;   /* NULL means the pool is empty: handle it */
    return m;
}

Stack painting, canaries and MPU guards

The high-water mark is the deepest the stack has ever been, the most useful number a firmware team can measure, because the stack size is a design choice and the mark shows how much margin remains. A tool can measure it only by telling used memory from unused, which painting provides, the free stack being filled with a known value, the program run and the first place where the value changed located, the value 0xA5A5A5A5 being an arbitrary pattern that real code does not produce by accident.

A stack overflow writes into whatever lies below the stack, so the damage can be silent, and three checks catch it.

  1. Painting and high-water mark. Before the program runs, the unused stack is filled with a known pattern, and afterwards the lowest word no longer holding it marks the deepest point the stack reached, its distance from the top being the high-water mark.
  2. A canary. A known word placed at the lowest reserved address reveals that the stack passed its limit if it is ever overwritten, though a canary reports only after the damage and does not stop the write.
  3. An MPU guard. The Cortex-M MPU can make the bottom of the stack unwritable, so that the overflow faults at the moment it happens (lesson 39), and the Pico SDK can install that guard for core 0 when PICO_USE_STACK_GUARDS is 1. Its default is 0, as the PICO_CONFIG entry in src/rp2350/pico_platform/include/pico/platform.h says, the RP2040 headers not defining it and runtime_init.h compiling the guard code only when it is 1. The source is src/rp2_common/pico_runtime_init/runtime_init_stack_guard.c and runtime_init.h in the SDK 2.3.1 copy, and this lesson did not test the guard.

Painting the stack resembles the tide line on a harbour wall, since nobody can watch the water all day, but the line it leaves shows the highest it ever reached, just as the first word that no longer holds the startup pattern shows how deep the stack has ever gone. The comparison breaks on timing, though, because the tide line is permanent while the paint records only the runs that happened since startup, so a deeper path that the test never exercised leaves no mark at all.

Linker symbols for the stack and heap bounds

The linker defines the stack and heap bounds as symbols, so code can read them without hard-coding addresses, and the values below come from the built Pico ELF for this lesson, read with arm-none-eabi-nm.

SymbolValue on the PicoMeaning
__StackTop0x20042000One past the highest stack byte. The stack starts here.
__StackBottom0x20041800Lowest byte of the reserved core 0 stack (2048 bytes above it).
__StackLimit0x20040000End of the 256 KB RAM, the upper limit for the heap.
__end__ or end0x200006d0 in this buildStart of the heap, after the static data (section_heap.incl).
__HeapLimit0x20040000Upper limit of the heap.

Lesson 68 explains how such symbols are defined in a script you write yourself, whereas those in this table are defined by the SDK's script, and __end__ depends on the size of the static data in your build.

The painting code line by line

The painting code is short, each line having one job.

  1. extern char __StackBottom; declares the symbol that the linker defines, the code taking its address rather than its value and never reading its contents, the type char serving only as a placeholder for a byte address.
  2. __asm volatile ("mov %0, sp" : "=r"(sp)); reads the stack pointer directly, because the painting must know where SP is now in order to stop above the current frames, and the volatile keeps the compiler from moving the read.
  3. *lo = CANARY_WORD; writes the canary into the lowest reserved word first, so that the paint loop, starting one word higher, does not overwrite it.
  4. for (volatile uint32_t *p = lo + 1; p < hi; p++) *p = PAINT_WORD; fills every word from the canary up to SP minus 64 bytes, the 64-byte margin protecting the frames still in use.
  5. s_paint_limit = (uint32_t *)hi; remembers where the painted part ends, so that the later scan stops there.
  6. In high_water_bytes(), the loop compares each word with the paint, the first word that differs being the lowest the stack wrote, and (uintptr_t)&__StackTop - (uintptr_t)p converts its address into a distance from the top in bytes.

The disassembly of this build shows each frame as push {lr} followed by sub sp, #20, 4 + 20 = 24 bytes per call, which you can check in the Debug disassembly of your own build with arm-none-eabi-objdump -d.

Try it in Wokwi

The project is projects/0078-stack-painting, whose starter prints a stack report but has its painting and measurement functions stubbed out with TODO(learner), so it prints STACK PAINT FAIL. The recursion is written for you, and since each call uses a 24-byte frame in the course's Debug build and recurse(16) makes 17 calls, the recursion alone uses 408 bytes of the 2 048-byte stack.

  1. Open projects/0078-stack-painting/starter in VS Code (File → Open Folder), build with Ctrl+Shift+B and start the simulator with F1 → Wokwi: Start Simulator, and the monitor prints STACK PAINT FAIL.
  2. In paint_unused_stack(), write the canary into the word at &__StackBottom, paint every word from the next one up to current_sp() - PAINT_MARGIN_BYTES with PAINT_WORD and set s_paint_limit to the top of the painted range.
  3. In high_water_bytes(), scan the painted words from the bottom up, skipping the canary, and return the distance of the first word that is not paint from &__StackTop, or 0 if every word still holds the paint.
  4. Build and run, and the monitor prints the reserved size and the high-water mark, then STACK PAINT OK. The high-water mark must be at least 408 bytes, the 17 frames of the recursion, and in the solution's Debug build it should read 440 bytes, the 408 plus the 32-byte frame of main(), which sits above the painted region, so a different number calls for checking the frame sizes in the disassembly before changing the code.
  5. Optionally, make canary_intact() return whether the word at &__StackBottom still holds CANARY_WORD. The program's last line prints CANARY OK or CANARY HIT after a 128-deep recursion that writes about 1 KB below the reserved stack, and since the starter's stub always returns true, the line says CANARY OK until you write the check. In the solution the disassembly places the canary exactly on the depth word of the 85th frame of the overflow, so the solution should print CANARY HIT, but this lesson could not run the simulator to confirm it, so treat it as the expected result to check on your run.
Hint for the scan

Walk from lo + 1 up to s_paint_limit, comparing each word with PAINT_WORD, and since the stack grows down, the first changed word reached from the bottom is the lowest one the stack wrote, whose address subtracted from &__StackTop, both cast to uintptr_t, gives the bytes.

Hint if the report says 0 bytes

The scan stops at s_paint_limit, so the paint must reach up to that point, and if s_paint_limit was never set, the loop does nothing and returns 0. Check also that current_sp() is read in paint_unused_stack() rather than earlier in main().

The reference solution is in projects/0078-stack-painting/solution, so try first and compare afterwards. The solution's expected line is STACK PAINT OK, while the high-water number itself is for you to read rather than copy.

You painted the unused stack, ran code that used it and measured how deep it went from the linker's own bounds, and you can say why a canary is a detector and not a guard.

Common mistakes and how to spot them

A heap that works for a day and then fails

Tests pass, but after a day in the field a rare failure with no matching input appears, because the device calls malloc() for each message and eventually receives a NULL the code does not expect. Replace the heap with a pool allocated at start-up, as above, with a check for an empty free list.

A canary painted over

The program prints CANARY HIT on the first run, before any overflow, because the paint loop starts at &__StackBottom instead of one word above it. Keep the order of the code, writing the canary first and painting from the next word.

A high-water report of 0 bytes

The report says 0 bytes although the recursion clearly ran, because the scan stops at s_paint_limit, which was never set or was set before the paint ran. Read the stack pointer inside paint_unused_stack() and set the limit at the end of the paint.

A canary taken as protection

A team sees CANARY OK at the end of a test and assumes the stack is safe, although the canary only sees a write after it has happened and an overflow can corrupt a variable and return a wrong value long before the canary is checked. Measure the high-water mark under the worst test, leave margin and, where the hardware offers a guard, enable it.

Dynamic memory rules in code standards

Most embedded code standards restrict dynamic memory, MISRA C:2012 prohibiting the allocation and free functions of <stdlib.h> (rule 21.3, as summarised in the Polyspace page cited above). A reviewer who sees malloc() in firmware asks where the memory comes from, what happens when it returns NULL and what the worst-case heap use is, and a good answer is a static bound. Teams also run the high-water measurement in their test builds, record the number and fail the build when the margin shrinks below an agreed limit, which is the process that turns a stack size into a number someone checked.

Summary

  • RAM on an MCU is fixed, so designing its use means finding the worst case of each region.
  • Static data is sized at link time, while the stack is fixed by the linker and not checked at run time.
  • Fragmentation can leave enough free bytes in total with no block big enough, which a pool of equal blocks avoids while also taking a fixed time per call.
  • The high-water mark is measured by painting the free stack, running and finding the first changed word.
  • A canary detects an overflow after it happens, whereas an MPU guard, where the hardware has one, can stop the write.
  • On the Pico the stack lies in SCRATCH_Y, the main heap ends at the top of main RAM, and the linker symbols give both bounds.
