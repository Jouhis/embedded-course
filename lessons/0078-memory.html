Memory: stack vs heap, static allocation, and detecting stack overflow

A stack overflow in firmware prints nothing. It overwrites a variable, or a return address, and the bug shows up several functions later. This lesson shows how to see how deep the stack really goes, and why most embedded standards avoid the heap after startup.

By the end of this lesson you can read the Pico's stack bounds from the linker symbols, paint the unused stack and report its high-water mark, and say why malloc() is banned in most firmware after startup.

The idea: three regions in one RAM

The RP2040 has 256 KB of SRAM starting at 0x20000000. The program uses three parts of it. The static data (globals and static variables) has a fixed size and lives for the whole run (lessons 41 and 42 show how the linker places it). The stack holds the call frames, and it grows downward from the top (lesson 33). The heap is the area that malloc() hands out, and it grows upward. The stack and the heap grow toward each other, so a deep stack and a large heap can collide.

On the Pico, the SDK's linker script reserves a fixed stack for core 0. The default is PICO_STACK_SIZE, which is 0x800, or 2048 bytes, and the stack starts at the top of the scratch RAM at 0x20042000 (pico-sdk, src/rp2040/pico_platform/memmap_default.ld and rp2_common/pico_standard_link/script_include; the default is in src/rp2040/pico_platform/include/pico/platform.h, read in the SDK 2.3.1 copy).

Why most standards ban malloc after startup

malloc() is convenient on a PC, where the heap is large and paged. On a microcontroller it causes three problems. First, the heap can fragment: after many allocations and frees of different sizes, there can be enough free bytes in total but no single block big enough, so the call fails late and at random. Second, the time an allocation takes is not fixed, which breaks a real-time deadline. Third, a failed call returns a null pointer that the code must check on every path, and the failure often happens only after months of uptime. MISRA C:2012 rule 21.3 prohibits the allocation and free functions of <stdlib.h>. The rule text is in the paid MISRA document; a tool vendor's summary of it is in the Polyspace rule page.

A common claim is that malloc is "slower". That is not the main reason. The main reason is that the failure happens at a time you do not choose, in a state you did not test.

Static allocation and memory pools

The usual alternative is to allocate everything at startup, from fixed-size arrays. A memory pool is an array of identical blocks with a free list: taking a block and returning one are a few pointer moves, the time is fixed, and no size fragments. The pool's size is part of the design, so the worst case is known before the device ships. 

#define POOL_BLOCKS 8u

typedef struct msg { uint8_t payload[32]; struct msg *next; } msg_t;

static msg_t pool[POOL_BLOCKS];      /* in .bss: reserved at link time, free at run time */
static msg_t *free_list;

static msg_t *pool_take(void) {
    msg_t *m = free_list;
    if (m) free_list = m->next;   /* NULL means the pool is empty: handle it */
    return m;
}

Detecting stack overflow

A stack overflow writes into whatever lies below the stack, so the damage can be silent. Three checks catch it.

  1. Painting and high-water mark. Before the program runs, fill the unused stack with a known pattern. After it runs, the lowest word that no longer holds the pattern is the deepest point the stack reached. Its distance from the top is the high-water mark.
  2. A canary. Put a known word at the lowest reserved address. If the stack ever writes it, the stack has passed its limit. A canary only tells you after the damage. It does not stop the write.
  3. An MPU guard. The Cortex-M MPU can make the bottom of the stack unwritable, so the overflow faults at the moment it happens (lesson 39). The Pico SDK can install that guard for core 0 when PICO_USE_STACK_GUARDS is 1; the default is 0. The source is src/rp2_common/pico_runtime_init/runtime_init_stack_guard.c and runtime_init.h in the SDK 2.3.1 copy, and this lesson did not test the guard.

The linker symbols

The linker defines the stack and heap bounds as symbols, so code can read them without hard-coding addresses. These are the values from the built Pico ELF for this lesson, read with arm-none-eabi-nm.

SymbolValue on the PicoMeaning
__StackTop0x20042000One past the highest stack byte. The stack starts here.
__StackBottom0x20041800Lowest byte of the reserved core 0 stack (2048 bytes above it).
__StackLimit0x20040000End of the 256 KB RAM, the upper limit for the heap.
__end__ or end0x200006d0 in this buildStart of the heap, after the static data (section_heap.incl).
__HeapLimit0x20040000Upper limit of the heap.

Lesson 68 explains how these are defined in a script you write yourself. The symbols in this table are defined by the SDK's script, and __end__ depends on the size of the static data in your build.

Try it in Wokwi

The project is projects/0078-stack-painting. The starter prints a stack report, but its painting and measurement functions are stubs marked TODO(learner), so it prints STACK PAINT FAIL. The recursion is written for you: each call uses a 24-byte frame, so 16 calls use about 384 bytes of the 2048-byte stack.

  1. Open projects/0078-stack-painting/starter in VS Code (File → Open Folder). Build with Ctrl+Shift+B, then start the simulator with F1 → Wokwi: Start Simulator. The monitor prints STACK PAINT FAIL.
  2. Your task, part 1: in paint_unused_stack(), write the canary into the word at &__StackBottom. Then paint every word from the next one up to current_sp() - PAINT_MARGIN_BYTES with PAINT_WORD. Set s_paint_limit to the top of the painted range.
  3. Your task, part 2: in high_water_bytes(), scan the painted words from the bottom up, skipping the canary. The first word that is not the paint is the deepest point. Return the distance from &__StackTop, or 0 if every word still has the paint.
  4. Build and run. The monitor prints the reserved size and the high-water mark, and then STACK PAINT OK. The high-water mark must be at least 384 bytes, because of the 16 frames.
  5. Optional: in canary_intact(), return whether the word at &__StackBottom still holds CANARY_WORD. The starter's last line prints CANARY OK or CANARY HIT after the 128-frame overflow in the solution, which writes 1 KB below the reserved stack.
Hint for the scan

Walk from lo + 1 up to s_paint_limit, comparing each word with PAINT_WORD. The stack grows down, so the first changed word, reached from the bottom, is the lowest one that the stack wrote. Subtract its address from &__StackTop, cast to uintptr_t, to get bytes.

Hint if the report says 0 bytes

The scan stops at s_paint_limit, so the paint must reach up to that point. If s_paint_limit was never set, the loop does nothing and returns 0. Also check that current_sp() is read in paint_unused_stack(), not earlier in main().

The reference solution is in projects/0078-stack-painting/solution. Try first, compare after. The solution's expected line is STACK PAINT OK; the high-water number itself is for you to read, not to copy.

You painted the unused stack, ran code that used it, and measured how deep it went, from the linker's own bounds. You can say why a canary is a detector and not a guard.

"Why would you avoid malloc in firmware?" Answer out loud in 60 seconds, then compare.

Model answer

On a microcontroller the heap is small and it fragments. After many allocations and frees, an allocation can fail even though the total free memory looks fine, and it fails at a time the test suite did not choose. The allocation time is also not fixed, which breaks deadlines. I would allocate everything at startup from static arrays or a fixed memory pool, so the worst case is known from the design. Then I would check the stack with painting, a high-water mark and a canary, and enable an MPU guard where the hardware has one.
