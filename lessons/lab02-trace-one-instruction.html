Lab 2: Trace one instruction

One line of C, GPIOC->BSRR = GPIO_BSRR_BR13;, becomes an address, an instruction, a bus transfer and a bit in a register. You will follow it all the way to the LED, then read the map file that places it.

By the end of this lab you can trace GPIOC->BSRR = GPIO_BSRR_BR13; on the Blue Pill from the preprocessed C to the Thumb-2 encoding, the APB2 bus, the register bit and the LED, using the real disassembly and map file.

Where we are and why it matters

Lessons 36 to 42 covered each layer of this trace on its own. Lesson 36 described memory and the way the CPU reaches it. Lesson 37 described the buses. Lesson 38 gave the address map, and lesson 41 showed how the build turns C into a file of machine code. This lab joins those layers into one path that you can check on your own build.

The path matters in real work. When an LED does not light, a pin does not change, or a peripheral ignores a write, an engineer has to follow the write from the source line to the hardware. The steps are the same on any microcontroller: find the address, check the instruction, identify the bus, and check the bit. An engineer who can do this in ten minutes finds the bug in the code, the wiring or the clock setup, and does not guess.

The project is projects/lab02-trace-one-instruction. Its starter has the questions as TODO(learner) comments in main.c. Its solution has the answers. Write your answers in your own notes first, then compare.

Concepts, one at a time

Step 1 of the path: the preprocessor makes text

Before the compiler sees your code, the preprocessor runs. It handles the lines that start with #, such as #include and #define. A macro is a name that the preprocessor replaces with text. The replacement is pure text substitution. The preprocessor does not do arithmetic, does not know what a register is, and does not check types.

The ST header stm32f103xb.h defines the names you use. For example, it defines the base address of the GPIOC port as an expression, and it defines the bit that resets pin 13 as a shifted 1. Those are the two names in the lab's one line of C. The lab asks you to see the text the compiler really receives, using the compiler's preprocessor option -E.

Step 2 of the path: the compiler makes instructions

The compiler turns C into machine instructions. An instruction is a fixed pattern of bits that the CPU decodes into one operation, and the rule that maps an operation to those bits is the encoding. The Cortex-M3 in the STM32F103 runs the Thumb-2 instruction set. Thumb-2 mixes 16-bit instructions and 32-bit instructions, so the CPU reads the first 16 bits and decides whether a second 16 bits follow.

The store in this lab is a 16-bit instruction, and the constant that it stores needs a 32-bit instruction. You will decode both by hand, so that the machine code is no longer a mystery. A register is a small storage slot inside the CPU, and a load moves a word from memory into a register. A store moves a register's word out to memory or to a peripheral address. Here the store writes to a peripheral register, not to RAM.

Step 3 of the path: an address is a base plus an offset

A peripheral is a hardware block such as a GPIO port, a timer or a serial port. Its control registers are mapped into the address space, so an ordinary store reaches them. A base address is the start address of that block, and a register offset is the distance of one register from it, in bytes. The address of the register is the base plus the offset.

The C code does not write numbers. It writes through a pointer to a struct. The header defines GPIO_TypeDef as a struct whose fields are the registers in order, each 4 bytes wide, so the compiler computes each field's offset from the struct layout. The fields are CRL, CRH, IDR, ODR, BSRR, BRR and LCKR, so BSRR is the fifth word and sits at offset 16, which is 0x10.

The field is declared with the CMSIS macro __IO, which expands to volatile. Lesson 46 explains why: a hardware register can change, and each access must really happen. The compiler must not cache the value or drop the write. This is why the struct is safe to use for a register.

Step 4 of the path: the bus carries the store

A bus is a set of wires and rules that carry addresses and data between the CPU and memory or peripherals. On the STM32F103, the CPU's store goes out over the bus matrix, and the matrix sends it to the right place. Peripherals sit on two slower buses behind a bridge, the APB bridge. The APB buses are the Advanced Peripheral Bus 1 and 2, called APB1 and APB2 in the header.

The header tells you which bus a peripheral is on, through its base address. APB2PERIPH_BASE is PERIPH_BASE + 0x10000, and GPIOC_BASE is APB2PERIPH_BASE + 0x1000. So GPIOC is on APB2. The bridge takes the access and carries it to the peripheral, and it adds wait cycles that the RP2040 datasheet describes for its own bridge. The STM32's bus timing is in RM0008, which this lab does not cite.

Step 5 of the path: the bit changes the pin

The GPIO block has an output data register, ODR, with one bit for each pin. Writing a bit there sets the pin's level, but writing the whole word changes all 16 pins. To change one pin safely, a program would read ODR, change a bit and write it back. That is a read-modify-write, and it is unsafe when an interrupt can change the register between the read and the write.

The BSRR register avoids the read. Its lower 16 bits set pins, and its upper 16 bits reset pins. A 1 in bit n sets pin n, and a 1 in bit 16 + n resets pin n. Writing zeros does nothing to the other pins, so one store changes one pin and nothing else. The header shows this: GPIO_BSRR_BS13 is bit 13, the set bit for pin 13, and GPIO_BSRR_BR13 is bit 29, the reset bit for pin 13.

Step 6 of the path: the pin drives the LED

A pin is a physical connection on the chip. When the pin is an output, its level is high (near the supply voltage) or low (near 0 V). The LED on the Blue Pill is wired so that a low pin lights it. That is called active low: the active state is the low level. The template comment says the Blue Pill LED is active low, and the solution's comments repeat that claim.

You will check that claim against the schematic in the final step. For now, follow the lab's reasoning. The reset bit drives PC13 low, so the LED lights. The set bit drives PC13 high, so the LED goes off.

Step 7 of the path: the linker places the code

The compiler produces object files, and the linker joins them into one program. It follows a linker script, a file that says which memory each section of the program goes into. A section is a named block, such as .text for code, .data for initialised variables, and .isr_vector for the vector table, the list of addresses the CPU jumps to on reset and on each exception.

Some sections have a run address and a load address. .data runs in RAM, so the CPU reads and writes it there. Its starting values are stored in flash, at the load address, and the startup code copies them to RAM on boot. Lesson 41 explains the linker script line that does this. The linker writes a .map file that lists every section and symbol with its address, and you can search that file for any function.

Worked example: the whole path, with numbers

Here is the path for GPIOC->BSRR = GPIO_BSRR_BR13;, with each step's result. The milestones below ask you to confirm each value on your own build.

  1. Preprocessing. GPIO_BSRR_BR13 becomes (0x1UL << (29U)). The shift gives 0x20000000, which is 1 followed by 29 zero bits, so only bit 29 is set.
  2. Address of GPIOC. APB2PERIPH_BASE is 0x40000000 + 0x10000 = 0x40010000. Then GPIOC_BASE is 0x40010000 + 0x1000 = 0x40011000.
  3. Address of BSRR. The offset of BSRR is 0x10, so the address is 0x40011000 + 0x10 = 0x40011010.
  4. The instructions. The compiler loads 0x40011000 into r4, puts 0x20000000 into r3, and stores r3 at r4 + 16.
  5. The bit. Bit 29 of BSRR is set, which resets pin 13. The other 31 bits of the word are zero, so pins 0 to 12 and 14 to 15 are not changed.

The lab asks you to confirm each step. A useful habit is to write the result in binary as well as hexadecimal. Bit 29 of a 32-bit word is 0010 0000 0000 0000 0000 0000 0000 0000 in binary, which is 0x20000000 in hexadecimal. Each hexadecimal digit is four bits, so the 2 in the top digit is bit 29, and the rest of the digits are zero.

The instructions, decoded bit by bit

The solution's disassembly, produced by arm-none-eabi-objdump -d -S build/blink, contains these three instructions in main. The address on the left is where each instruction sits in flash, and the two numbers on the right are the encoding: 

 8000268:	4c0b      	ldr	r4, [pc, #44]	@ (8000298 <main+0x54>)
 800026a:	f04f 5300 	mov.w	r3, #536870912	@ 0x20000000
 800026e:	6123      	str	r3, [r4, #16]

The first instruction, ldr r4, [pc, #44], loads a word from a literal pool, a small table of constants placed in flash near the code. The address of that word is the program counter plus 44 bytes, which is 0x08000298. The word there is 0x40011000, the GPIOC base. You can see it with the objdump command -s at that address.

The second instruction loads 0x20000000 into r3. It is two halfwords, f04f 5300, so it is a 32-bit instruction. Thumb-2 uses a 32-bit form because the constant is too big to fit in the 16-bit form. The 32-bit form encodes the constant as an 8-bit value with a rotation. In the halfwords, the bits i, imm3 and imm8 form a 12-bit field whose value here is 0x500. Its bits 11 to 7 give the rotation, 10. The 8-bit value is 0x80, and rotating 0x80 right by 10 places moves its bit 7 to bit 29, which is 0x20000000. The check is the same as the arithmetic in the last section.

The third instruction, str r3, [r4, #16], stores r3 at the address r4 + 16. Its encoding is the single halfword 0x6123, which is a 16-bit instruction. Read it from the top bit down: bits 15 to 11 are 01100, the opcode for a store with an immediate offset. Bits 10 to 6 are 00100, which is 4, and the offset is that field times 4, so 16 bytes. Bits 5 to 3 are 100, which is register r4, and bits 2 to 0 are 011, which is register r3.

The Thumb-2 decoder does not need a length field. It reads the first halfword and checks its top bits. If they are 11101, 11110 or 11111, a second halfword follows, so the instruction is 32 bits. The .w on mov.w is the assembler's hint that it chose the wide form. The Armv7-M Architecture Reference Manual in the resources list is the source for these encodings; check your decoding there.

Common mistakes and how to spot them

Each mistake below is one you can make on this lab, and each has a symptom you can see.

  1. Writing a peripheral before its clock is on. The solution sets RCC->APB2ENR with RCC_APB2ENR_IOPCEN before it touches GPIOC. If you remove that line, the store is sent to a peripheral with no clock, and it has no visible effect. The symptom is an LED that never changes, with no error. The fix is to enable the clock of the peripheral before its first register access.
  2. Using a read-modify-write where BSRR is the right tool. A line such as GPIOC->ODR |= (1 << 13); reads ODR, sets bit 13 and writes the word back. It works in a quiet program, but an interrupt that writes another pin between the read and the write is lost. The symptom is a second LED that sometimes flickers or turns off. The fix is the single BSRR write, which needs no read.
  3. Mixing up the set and reset bits. Writing GPIO_BSRR_BS13 sets PC13 high, which turns the LED off. Engineers who think "write 1 to turn it on" then find the LED lit when the code says off. The symptom is an inverted LED. The fix is to check the active level first, then choose the reset bit for "on".
  4. Using the wrong bit position. 0x2000 is GPIO_BSRR_BS13, which is bit 13. Writing 0x2000 where you mean the reset of pin 13 sets the pin instead. The symptom is an LED that does the opposite of the code. The fix is to use the named macro, never the raw number.
The active-low claim comes from the template's comment, and this lab has not checked it against the Blue Pill schematic. Check the board's schematic or the simulator's LED part before you use this claim in an interview answer.

Summary

  • The line GPIOC->BSRR = GPIO_BSRR_BR13; preprocesses to (0x1UL << (29U)), which is 0x20000000, so only bit 29 is set.
  • APB2PERIPH_BASE is 0x40010000 and GPIOC_BASE is 0x40011000, so GPIOC is on APB2 and BSRR sits at 0x40011010, the base plus offset 0x10.
  • The store is the 16-bit Thumb encoding 6123, which is str r3, [r4, #16]. The constant 0x20000000 needs the 32-bit mov.w, encoded as f04f 5300.
  • BSRR sets pins with bits 0 to 15 and resets pins with bits 16 to 31, so bit 29 resets PC13 and leaves the other pins unchanged.
  • The template's comment says PC13 is active low, so the reset bit lights the LED. The lab has not checked that claim against the Blue Pill schematic.
  • One BSRR write needs no read, so an interrupt cannot slip between a read and a write and lose an update, as it can with ODR |= (1 << 13).
  • The map file places main at 0x08000244, the vector table at 0x08000000 with size 0x10c, and the .data load address at 0x08000414.
  • The linker's _estack is 0x20005000, the top of the 20 KiB RAM, where the stack starts.

Step-by-step work

Milestones

  1. M1: preprocess. Run arm-none-eabi-gcc -E -P on main.c with the same defines and include folders as the build. Search the output for BSRR. Expected: a line that reads ((GPIO_TypeDef *)((0x40000000UL + 0x00010000UL) + 0x00001000UL))->BSRR = (0x1UL << (29U));. Write down the expression for the BSRR write.
  2. M2: disassemble. Build the solution, then run arm-none-eabi-objdump -d -S build/blink. Find the str that writes BSRR, and decode its halfword. Expected: a line ending in str r3, [r4, #16] with the encoding 6123.
  3. M3: map. Open build/blink.map and search for main, g_pfnVectors and _sidata. Expected: main at 0x08000244, the vector table at 0x08000000 with size 0x10c, and the .data load address 0x08000414.
  4. M4: simulate. Start the simulator and watch LED on and LED off alternate, once every half second. If the serial monitor prints nothing, check the build file name (see the note in step 5).

Step 1: the preprocessor

The macro GPIO_BSRR_BR13 is defined in the CMSIS header. Expanding main.c with the compiler's preprocessor (arm-none-eabi-gcc -E with the same defines and include paths) gives this line, copied from the lab's real output: 

((GPIO_TypeDef *)((0x40000000UL + 0x00010000UL) + 0x00001000UL))->BSRR = (0x1UL << (29U));

Work the expansion through. GPIOC is GPIO_TypeDef * at GPIOC_BASE, and GPIOC_BASE is APB2PERIPH_BASE + 0x1000. The preprocessor did only text substitution, so the arithmetic is still ahead of the compiler. It folds the constants to 0x40011000, and 0x1UL << 29 to 0x20000000.

Step 2: the instruction

Build the solution, then disassemble it as shown in the previous section. The loop in main contains the three instructions, and each is explained there. Your listing will have different addresses if your code differs, but the instructions and their order should match.

Step 3: the bus and the register bit

The address 0x40011010 lies in the APB2 region, which starts at 0x40010000. The ST header's APB2PERIPH_BASE is PERIPH_BASE + 0x10000, so GPIOC is on the APB2 peripheral bus. The write crosses the core's bus interface, reaches the APB2 bridge, and lands in the GPIOC block at offset 0x10. RP2040 datasheet, section 2.1.3 describes the same kind of bridge on another chip, with the cycle cost of each access. The STM32's bus details are in RM0008 and need the vendor text.

GPIO_BSRR_BR13 is bit 29. BSRR has set bits 0 to 15 and reset bits 16 to 31, so bit 29 resets pin 13. The value 0x20000000 therefore changes only PC13, and the other pins keep their levels.

Step 4: the LED

The template's comment says PC13 is active low, so a low pin lights the LED. The reset bit drives the pin low, and the simulator's board shows the LED on. BS13 sets the pin high again, and the LED goes off.

Step 5: the map file

The linker writes build/blink.map. From the solution's real map, these are the lines you need: 

.isr_vector     0x08000000      0x10c
                0x08000000                g_pfnVectors
.text           0x0800010c      0x2d8
                0x08000244                main
.data           0x20000000        0x4 load address 0x08000414
                0x08000414                _sidata = LOADADDR (.data)
                0x20005000                _estack = (ORIGIN (RAM) + LENGTH (RAM))

Read them against the lessons. The vector table is 268 bytes (0x10c) at the start of flash, and its first word is the stack top. main is at 0x08000244, which the disassembly confirms. The .data section runs in RAM at 0x20000000, but its initial values are loaded from 0x08000414 in flash. Lesson 41 explains the AT> FLASH that makes this possible. The _estack symbol is the top of the 20 KiB RAM, 0x20005000, where the stack starts.

The template's CMake writes the output as build/blink, without the .elf extension, while wokwi.toml names build/blink.elf. If the simulator cannot find the file, ask your teacher before you change any template. It is a known issue for this lab.
