Lab 2: Trace one instruction

One line of C, GPIOC->BSRR = GPIO_BSRR_BR13;, becomes an address, an instruction, a bus transfer and a bit in a register. You will follow it all the way to the LED, then read the map file that places it.

By the end of this lab you can trace GPIOC->BSRR = GPIO_BSRR_BR13; on the Blue Pill from the preprocessed C to the Thumb-2 encoding, the APB2 bus, the register bit and the LED, using the real disassembly and map file.

The idea

Lessons 36 to 42 covered each layer of this trace on its own. This lab joins them. Read the lab in order: the preprocessor makes the address, the compiler and assembler make the instruction, the bus delivers the store, and the register bit drives a pin. The linker then decides where the instruction sits in flash.

The project is projects/lab02-trace-one-instruction. Its starter has the questions as TODO(learner) comments in main.c. Its solution has the answers. Write your answers in your own notes first, then compare.

Requirements

  1. Preprocess main.c and find the full expansion of GPIO_BSRR_BR13 and GPIOC.
  2. Compute the address of GPIOC->BSRR from the base and the offset, and check it against the header.
  3. Find the store instruction in the disassembly, and decode its encoding (16-bit or 32-bit).
  4. Name the bus that carries GPIOC, and the register and bit that the store changes.
  5. Explain, with a source in the header or the board, why driving PC13 low lights the LED.
  6. Read the map file and report the addresses of main, the vector table and the .data load address.

Milestones

  1. M1: preprocess. Expand the macros and write down the final expression for the BSRR write.
  2. M2: disassemble. Find the str that writes BSRR, and decode the instruction.
  3. M3: map. Find main, g_pfnVectors and _sidata in build/blink.map.
  4. M4: simulate. Start the simulator and watch LED on and LED off alternate.

Step 1: the preprocessor

The macro GPIO_BSRR_BR13 is defined in the CMSIS header. Expanding main.c with the compiler's preprocessor (arm-none-eabi-gcc -E with the same defines and include paths) gives this line, copied from the lab's real output: 

((GPIO_TypeDef *)((0x40000000UL + 0x00010000UL) + 0x00001000UL))->BSRR = (0x1UL << (29U));

Work the expansion through. GPIOC is GPIO_TypeDef * at GPIOC_BASE, and GPIOC_BASE is APB2PERIPH_BASE + 0x1000. The preprocessor did only text substitution, so the arithmetic is still ahead of the compiler. It folds the constants to 0x40011000, and 0x1UL << 29 to 0x20000000.

Step 2: the instruction

Build the solution, then disassemble it with arm-none-eabi-objdump -d -S build/blink. The loop in main contains this, copied from the real output: 

 8000268:	4c0b      	ldr	r4, [pc, #44]	@ (8000298 <main+0x54>)
 800026a:	f04f 5300 	mov.w	r3, #536870912	@ 0x20000000
 800026e:	6123      	str	r3, [r4, #16]

Three things happen. ldr r4 loads 0x40011000 from a literal pool at 0x08000298, which is the GPIOC base. mov.w loads the constant 0x20000000 into r3. Then str r3, [r4, #16] stores it at r4 + 16, which is 0x40011010, the BSRR address.

The encoding is the interesting part. The str is the 16-bit Thumb encoding 0x6123: the T1 form holds a 5-bit word offset, here 4, which is byte offset 16, the base register r4, and the source r3. The mov.w is 32-bit, two halfwords f04f 5300, because a 32-bit "modified immediate" is needed for 0x20000000. Check it: the immediate field decodes to a rotated 8-bit value, 0x80 rotated right by 10, which is 0x20000000. The .w suffix on the mnemonic is the assembler's hint that it chose the wide form.

The literal pool is data placed after the function. An ldr with a PC-relative address reads it, because Thumb cannot put a 32-bit constant in one instruction. That is why 0x40011000 appears in the listing as a .word at 0x08000298, not in the code.

Step 3: the bus and the register bit

The address 0x40011010 lies in the APB2 region, which starts at 0x40010000. The ST header's APB2PERIPH_BASE is PERIPH_BASE + 0x10000, so GPIOC is on the APB2 peripheral bus. The write crosses the core's bus interface, reaches the APB2 bridge, and lands in the GPIOC block at offset 0x10. RP2040 datasheet, section 2.1.3 describes the same kind of bridge on another chip, with the cycle cost of each access. The STM32's bus details are in RM0008 and need the vendor text.

GPIO_BSRR_BR13 is bit 29. BSRR has set bits 0 to 15 and reset bits 16 to 31, so bit 29 resets pin 13. The value 0x20000000 therefore changes only PC13, and the other pins keep their levels.

Step 4: the LED

The template's comment says PC13 is active low, so a low pin lights the LED. The reset bit drives the pin low, and the simulator's board shows the LED on. BS13 sets the pin high again, and the LED goes off.

The active-low claim comes from the template's comment, and this lab has not checked it against the Blue Pill schematic. Check the board's schematic or the simulator's LED part before you use this claim in an interview answer.

Step 5: the map file

The linker writes build/blink.map. From the solution's real map, these are the lines you need: 

.isr_vector     0x08000000      0x10c
                0x08000000                g_pfnVectors
.text           0x0800010c      0x2d8
                0x08000244                main
.data           0x20000000        0x4 load address 0x08000414
                0x08000414                _sidata = LOADADDR (.data)
                0x20005000                _estack = (ORIGIN (RAM) + LENGTH (RAM))

Read them against the lessons. The vector table is 268 bytes at the start of flash, and its first word is the stack top. main is at 0x08000244, which the disassembly confirms. The .data section runs in RAM at 0x20000000, but its initial values are loaded from 0x08000414 in flash. Lesson 41 explains the AT> FLASH that makes this possible.

The template's CMake writes the output as build/blink, without the .elf extension, while wokwi.toml names build/blink.elf. If the simulator cannot find the file, ask your teacher before you change any template. It is a known issue for this lab.

Acceptance criteria

  • You can give the preprocessed expression for GPIO_BSRR_BR13, and it equals (0x1UL << 29).
  • You can state the BSRR address 0x40011010 and derive it from the base and offset.
  • You can identify the str r3, [r4, #16] instruction in your own disassembly and say why it is 16 bits wide.
  • You can name APB2 as the bus, and bit 29 as the bit that resets pin 13.
  • You can read main, g_pfnVectors and the .data load address from your own map file.
  • The simulator shows LED on and LED off in turn, or you can explain why it does not.
Hint for step 1

Run arm-none-eabi-gcc -E -P -DSTM32F103xB -mcpu=cortex-m3 -mthumb with the CMSIS include folders, and search the output for BSRR. The -P option removes the line markers.

Hint for step 2

Look for the str that uses r4 as its base. The offset #16 is the BSRR offset, which is 0x10.

Hint for step 5

Search the map file for main, then for _sidata. The load address text on the .data line is the flash location.
