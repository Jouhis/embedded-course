Robustness: watchdogs, HardFault analysis and assertions

A field device fails at 3 a.m. with no debugger attached. Three tools make that failure recoverable and explainable: a watchdog that resets a hung chip, a HardFault handler that records where the crash was, and assertions that name the line that broke an invariant.

By the end of this lesson you can write a HardFault handler that prints the stacked PC and the fault registers, and decode that PC to a source line with arm-none-eabi-addr2line.

Watchdogs: what they are for

A watchdog is a counter that resets the chip when software does not clear it in time. Normal code clears ("kicks" or "refreshes") it on a schedule. If the code hangs in a loop, a lock, or a fault handler that never returns, the kick stops, and the counter reaches zero and resets the system. A reset is a recovery; a hung device is not. A stack overflow is one common cause of such a hang, and lesson 78 shows how to see the stack depth before it becomes one.

The STM32F1 has two watchdogs, described in the reference manual RM0008 (RM0008, the IWDG and WWDG chapters):

WatchdogClockRuleUse it for
Independent (IWDG)Its own low-speed RC, so it keeps running if the main clock stopsOnce started, it cannot be stopped except by a reset. You kick it inside a fixed timeThe last line of defence against a hang
Window (WWDG)Derived from the APB1 clockYou must kick it inside a window. Too early is a reset as well as too lateCatching code that runs too fast, such as a loop that skips its work
In this course's simulator, NOTES.md records that the Blue Pill's IWDG is not simulated, and WWDG is. The Pico's watchdog (hardware_watchdog in the SDK) has not been checked in the simulator, so treat its behaviour here as unverified.

Kick strategies: check in, do not just kick

A watchdog kicked from one timer interrupt proves only that the interrupt runs. A better design checks in: each task sets its own bit when it has made progress, and a supervisor kicks the watchdog only when every expected bit is set, then clears them. If one task hangs, its bit never sets, and the chip resets. This is the "task check-in" pattern, and it tells you which task was stuck when you read the log (lesson 85). Check-in works best when each task has its own event queue and never blocks the others, which is the design of lesson 77.

What a HardFault gives you

On a fault, the core pushes eight words onto the stack before it runs the handler (lesson 34): R0, R1, R2, R3, R12, LR, PC and xPSR. The PC is the address of the instruction that faulted, for a precise fault. Your handler reads those words, and it reads the fault status registers in the System Control Block (lesson 39). Those are the registers you read in an interview answer:

RegisterAddressWhat to look at
HFSR0xE000ED2CBit 30, FORCED: a configurable fault was escalated to HardFault
CFSR0xE000ED28The cause: a MemManage, BusFault or UsageFault bit. UNALIGNED is bit 24
BFAR0xE000ED38The address, valid only when CFSR.BFARVALID (bit 15) is set
MMFAR0xE000ED34The MemManage address; the Blue Pill has no MPU, so ignore it there

The addresses are the SCB base 0xE000ED00 plus the offsets in the CMSIS header (core_cm3.h, SCB_Type). The bit positions come from the same header (SCB_CFSR_UNALIGNED_Pos is 24), and the reference is PM0056, the fault section.

The handler stub

A C function cannot read the stacked frame reliably, because the compiler may save registers in its own prologue first. The handler is therefore a naked function that only picks the right stack pointer and jumps to C. Bit 2 of LR (EXC_RETURN) says whether the frame is on the main stack (MSP) or the process stack (PSP): 

void HardFault_Handler(void) __attribute__((naked));
void HardFault_Handler(void) {
    __asm volatile(
        "tst lr, #4          \n"   /* bit 2 of EXC_RETURN: which stack? */
        "ite eq              \n"
        "mrseq r0, msp       \n"   /* 0: frame is on MSP */
        "mrsne r0, psp       \n"   /* 1: frame is on PSP */
        "b hard_fault_report \n"   /* R0 = pointer to the eight stacked words */
    );
}
The startup file gives HardFault_Handler a weak default that loops forever. Your own definition with the same name overrides it, so you do not edit the startup file. If you forget to define it, a fault makes the chip hang silently.

Assertions that log and reset

An assertion checks an invariant and stops the program when it is false. In firmware, the useful version records the file and line, and then resets, so the field device recovers and the log explains why. A sketch (lesson 85 implements the full version with a log that survives the reset): 

#define ASSERT(expr) do { if (!(expr)) assert_failed(__FILE__, __LINE__); } while (0)

void assert_failed(const char *file, int line) {
    log_line_for(file, line);   /* survives the reset (lesson 85) */
    NVIC_SystemReset();         /* does not return */
}

Use assertions for bugs (a pointer that should never be null). Do not use them for input from the outside world: a bad sensor reading needs an error path, not a reset. Compile-time assertions (_Static_assert) catch layout bugs before the build succeeds, and they cost nothing at run time.

Decoding the stacked PC

The PC in the frame is an address in flash. arm-none-eabi-addr2line maps it to a function and a source line using the debug information in the .elf. The debugger does the same job when you break on a fault, but addr2line works on a log printed from the field, where no debugger is attached.

Decode the address with addr2line

The solution's faulting load is the instruction at 0x08000262. You can find it yourself with objdump (from Git Bash, after building the solution): 

"/c/Program Files (x86)/Arm GNU Toolchain arm-none-eabi/14.2 rel1/bin/arm-none-eabi-objdump.exe" -d build/blink.elf | grep -A7 "<trigger_unaligned_load>:"
...
 8000262:	f8d3 3001 	ldr.w	r3, [r3, #1]

That load reads from 0x20000000 + 1, an odd address, which is the fault. Now decode the address itself. Your build puts the .elf in build/. Run this from the solution folder: 

"/c/Program Files (x86)/Arm GNU Toolchain arm-none-eabi/14.2 rel1/bin/arm-none-eabi-addr2line.exe" -e build/blink.elf -f -C -i 0x08000262
trigger_unaligned_load
C:/Users/juhos/embedded-course/projects/0084-robustness/solution/main.c:89

Line 89 is (void)*p;, the faulting read. These two lines are the real output of the solution's build, produced on this machine. The option -f prints the function name, -C demangles names, and -i follows inlined code. On a real board, the PC that your handler prints should be the same address as the faulting instruction you find with objdump. That is the check to make before you trust the decode.

The same method works on a field log: a crash log prints HardFault PC=0x…, and you run addr2line on the matching .elf from that exact build. A different build has a different .elf, so keep the .elf for every release.

Check the mapping before you trust it. The map file (blink.map, lesson 41) shows where each function sits, and objdump shows the instruction. Two sources agreeing is the evidence you want in a fault report.
You can make a fault announce itself with the address that caused it, and turn that address into a source line. That is the first thing a field crash report needs.

"Walk me through debugging a HardFault on a Cortex-M3 in the field." Answer out loud in 60 seconds, then compare.

Model answer

First, the handler should already have logged the stacked PC, LR and xPSR, plus HFSR, CFSR, BFAR and MMFAR. I read HFSR first, to see whether the fault was forced from a configurable one. Then CFSR, for the cause: an unaligned access, an invalid state, or a bus error. If BFARVALID or MMARVALID is set, the address register holds the faulting address. I take the stacked PC and run addr2line on the .elf from that exact release, to get the function and line, and objdump to see the instruction. Finally I check the caller with LR, and I reproduce the fault on the bench with the same build before I call it fixed.
