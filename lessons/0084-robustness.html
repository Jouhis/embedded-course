Robustness: watchdogs, HardFault analysis and assertions

A field device fails at 3 a.m. with no debugger attached. Three tools make that failure recoverable and explainable: a watchdog that resets a hung chip, a HardFault handler that records where the crash was, and assertions that name the line that broke an invariant.

By the end of this lesson you can write a HardFault handler that prints the stacked PC and the fault registers, and decode that PC to a source line with arm-none-eabi-addr2line.

Where we are and why it matters

This lesson builds on four earlier ones. Lesson 34 showed how the core enters an exception and pushes registers onto the stack. Lesson 39 introduced the faults and the System Control Block (SCB) that reports them. Lesson 42 showed the vector table, which decides where the core goes when a fault happens. Lesson 78 showed how the stack grows into memory, and how a stack that is too deep becomes a hang or a corrupted variable.

This situation is common in the field. A product runs in a customer's building. It resets a few times a month, and a support engineer asks why. No debugger is attached, the serial port is unplugged, and the device is in a cabinet. The firmware has to do three jobs on its own. It must recover, so the device keeps working. It must record evidence, so the next engineer knows what happened. It must check its own assumptions, so that a broken invariant is found where it breaks and not three functions later. Each job has a tool in this lesson: a watchdog, a HardFault handler and an assertion.

Watchdogs: what they are for

A watchdog is a counter that resets the chip if software does not clear it in time (glossary: watchdog). Normal code clears the counter on a schedule. Clearing it is called a kick or a refresh. If the program hangs in a loop, waits on a lock that never opens, or sits in a fault handler that never returns, the kick stops. The counter reaches zero and resets the system. A reset recovers the device. A hung device does not recover. A stack overflow is one common cause of such a hang, and lesson 78 shows how to see the stack depth before it becomes one.

The STM32F1 has two watchdogs. Both are described in the reference manual RM0008 Rev 21, in chapter 19 (the independent watchdog, IWDG) and chapter 20 (the window watchdog, WWDG). The two differ in their clock and in their rules:

WatchdogClockRuleUse it for
Independent (IWDG)Its own low-speed RC, so it keeps running if the main clock stops (section 19.1)Once started, it cannot be stopped except by a reset (sections 5.3.4 and 19.3). You kick it inside a fixed timeThe last line of defence against a hang
Window (WWDG)Derived from the APB1 clockYou must kick it inside a window. Too early is a reset as well as too late (sections 20.1 and 20.3)Catching code that runs too fast, such as a loop that skips its work

The IWDG's counter is a 12-bit value. Its reload register, IWDG_RLR, has a field RL with a mask of 0xFFF, which the device header in third_party/cmsis-device-f1/Include/stm32f103xb.h defines. The manual gives the same field as RL[11:0], with a reset value of 0x0FFF (RM0008 Rev 21, section 19.4.3). The largest reload value is therefore 4095, and the counter counts down from it (section 19.3). That is the number the quiz asks about.

In this course's simulator, NOTES.md records that the Blue Pill's IWDG is not simulated, and WWDG is. The Pico's watchdog (hardware_watchdog in the SDK) has not been checked in the simulator, so treat its behaviour here as unverified.

Kick strategies: check in before kicking

A watchdog kicked from one timer interrupt proves only that the interrupt runs. The main loop could be stuck, and the interrupt would keep the watchdog happy. A better design checks in. Each task sets its own bit when it has made progress. A supervisor kicks the watchdog only when every expected bit is set, and then clears the bits for the next round. If one task hangs, its bit never sets, the kick stops, and the chip resets. This is the task check-in pattern (glossary: task check-in). It also tells you which task was stuck when you read the log in lesson 85.

Check-in works best when each task has its own event queue and never blocks the others, which is the design of lesson 77. A task that blocks on a slow sensor can miss its check-in window, and then the watchdog resets the device for a reason that is not a bug in the task. The design question is how long each task may take between check-ins, and that is a number you write down.

  1. Three tasks each own one check-in bit. The watchdog counts down from its timeout; only the supervisor may kick it.
  2. sensor and comms have done their work and set bits 0 and 1. ui has not yet, so the supervisor does not kick. The watchdog keeps counting down.
  3. ui checks in. All three bits are set, so the supervisor kicks the watchdog and clears the bits for the next round.
  4. In the next round comms gets stuck in a loop. sensor and ui are healthy and set their bits again.
  5. Bit 1 never sets, so the supervisor never kicks. A watchdog kicked from a timer interrupt would still be fed here, because the interrupt keeps running while comms is stuck.
  6. The watchdog expires and resets the chip: the hang is caught, and the reset reason tells you after boot that it was the watchdog.

Concepts: the stacked frame and EXC_RETURN

When a fault happens, the core behaves like any other exception entry. It pushes a fixed set of eight words onto the active stack before it runs the handler (lesson 34; PM0056 Rev 7, section 2.3.7). This set is the stacked frame (glossary: stacked frame). The eight words are R0, R1, R2, R3, R12, LR, PC and xPSR, in that order from the lowest address. Word 0 is at the frame pointer, word 6 is at the frame pointer plus 24 bytes, and word 7 is at 28 bytes.

The PC in the frame is the address of the instruction that was running when the fault happened. For a precise fault, which is the case in this lesson, the instruction that caused the fault is the one whose address is stacked. That is why the PC is the main clue: it tells you where the code was. The LR word holds whatever the link register held, which is not the caller in general, so it is a weaker clue.

The handler needs to know which stack the frame went to. The core chooses the main stack pointer (MSP) or the process stack pointer (PSP) depending on the mode it was in, and it reports the choice in the exception return value, called EXC_RETURN (glossary: EXC_RETURN). Bit 2 of EXC_RETURN is 0 when the frame is on the MSP, and 1 when it is on the PSP (PM0056 Rev 7, section 2.3.7, Table 17). Because the firmware in this lesson has no operating system, the frame goes to the MSP.

Concepts: the fault status registers

The stacked frame says where the code was. The fault status registers say why. They live in the System Control Block (SCB), a block of registers at address 0xE000ED00 (PM0056 Rev 7, section 4.4.15). The CMSIS header defines the SCB as a structure, and each register sits at a fixed offset from that base. The offsets that matter here are these (PM0056 Rev 7, sections 4.4.10 to 4.4.13):

RegisterAddressWhat to look at
CFSR0xE000ED28The cause: bits for MemManage, BusFault and UsageFault events
HFSR0xE000ED2CBit 30, FORCED: a configurable fault was escalated to HardFault. Bit 1, VECTTBL: an error reading the vector table
MMFAR0xE000ED34The MemManage address. The Blue Pill has no MPU, so ignore it there
BFAR0xE000ED38The BusFault address, valid only when CFSR bit 15 (BFARVALID) is set

The CFSR is one 32-bit word with three fields. Each field starts at a fixed bit. The MemManage field starts at bit 0, the BusFault field at bit 8, and the UsageFault field at bit 16. Inside those fields, the bits have their own names. The header gives the positions in the same way for each field: BFARVALID is bit 7 of the BusFault field, so it is bit 15 of CFSR. UNALIGNED is bit 8 of the UsageFault field, so it is bit 24 of CFSR. The header also defines MMARVALID, which is bit 7 of the MemManage field, so bit 7 of CFSR. The manual gives the same field layout (PM0056 Rev 7, section 4.4.10).

The bit positions come from the CMSIS header third_party/CMSIS_5/CMSIS/Core/Include/core_cm3.h. For the fault section of the register descriptions, the reference is the Cortex-M3 programming manual PM0056 Rev 7, sections 4.4.9 to 4.4.13. The offsets and bit positions in this lesson were read from that header, which the course build uses, and they match the names in the code and the values in PM0056.

One more register matters for the lesson's fault. The configuration control register, CCR, sits at offset 0x14 in the SCB. Its bit 3, UNALIGN_TRP, makes an unaligned access fault instead of being fixed up by the core (PM0056 Rev 7, section 4.4.7). The header calls the mask SCB_CCR_UNALIGN_TRP_Msk, and its value is 8. The solution sets this bit on purpose, to create a fault.

The handler stub: why it is naked

The handler has two parts. The first is a small assembly stub that finds the stacked frame. The second is a C function that reads the frame and prints it. The stub must come first, and it must be written so that the compiler does not add anything in front of it. A C function starts with a prologue, which is code the compiler adds to save registers and set up the stack. If the prologue runs before the handler reads the stack pointer, the registers it saves can change the stack the handler is about to read. A naked function (glossary: naked function) has no prologue, so its body controls every register. 

void HardFault_Handler(void) __attribute__((naked));
void HardFault_Handler(void) {
    __asm volatile(
        "tst lr, #4          \n"   /* bit 2 of EXC_RETURN: which stack? */
        "ite eq              \n"
        "mrseq r0, msp       \n"   /* 0: frame is on MSP */
        "mrsne r0, psp       \n"   /* 1: frame is on PSP */
        "b hard_fault_report \n"   /* R0 = pointer to the eight stacked words */
    );
}

The stub's four instructions do the whole job. tst sets the zero flag if bit 2 of LR is clear. ite is the if-then-else instruction for the next two, and mrseq and mrsne copy MSP or PSP into R0, depending on that flag. R0 is the first argument of a C function under the Arm procedure call standard, so b jumps into hard_fault_report with the frame pointer in R0. The jump is a branch and not a call, so no return address is pushed, and the handler never returns to the fault.

The startup file gives HardFault_Handler a weak default that loops forever. The default is an alias of Default_Handler, which runs b Infinite_Loop. Your own definition with the same name overrides the default, so you do not edit the startup file. If you forget to define it, a fault makes the chip hang silently, and the serial monitor shows nothing after the last line the program printed.

Assertions that log and reset

An assertion checks an invariant and stops the program when it is false (glossary: assertion). An invariant is a condition the code assumes is always true, such as "this pointer is not null because the caller checked it". In firmware, the useful version records the file and line, and then resets, so the device recovers and the log explains why. A sketch looks like this. Lesson 85 implements the full version, with a log that survives the reset. 

#define ASSERT(expr) do { if (!(expr)) assert_failed(__FILE__, __LINE__); } while (0)

void assert_failed(const char *file, int line) {
    log_line_for(file, line);   /* survives the reset (lesson 85) */
    NVIC_SystemReset();         /* does not return */
}

NVIC_SystemReset is a CMSIS function. It writes the system reset request bit, SCB_AIRCR_SYSRESETREQ, which is bit 2 of the application interrupt and reset control register. The core then resets. Nothing after the call runs, which is why the function is marked as not returning in the header.

Use assertions for bugs, such as a pointer that should never be null. Do not use them for input from the outside world. A bad sensor reading needs an error path, not a reset. Compile-time assertions, written with _Static_assert, catch layout bugs before the build succeeds, and they cost nothing at run time. The two kinds of assertion answer different questions. A static assertion checks the program's structure, and a run-time assertion checks the state the program reaches.

Decoding the stacked PC

The PC in the frame is an address in flash. The tool arm-none-eabi-addr2line maps that address to a function and a source line, using the debug information in the .elf file. The debugger does the same job when you break on a fault, but addr2line works on a log printed from the field, where no debugger is attached. Its options are: -e names the ELF file, -f prints the function name, -C demangles names, and -i follows inlined code.

A worked example: the crash in the solution

The solution causes a fault on purpose, and the steps are worth following one by one, because each one is a fact you can check in the build.

  1. The fault is armed. trigger_unaligned_load sets bit 3 of the CCR, with SCB->CCR |= SCB_CCR_UNALIGN_TRP_Msk. In the disassembly, this is the orr.w r3, r3, #8 followed by the store to offset 20 (0x14). Bit 3 is the value 8, so the store is the CCR write.
  2. The address is odd. The code makes a pointer to 0x20000001. That address is in RAM, which starts at 0x20000000, and it is one byte past a word boundary. The instruction ldr.w r3, [r3, #1] loads a 32-bit word from that address.
  3. The core refuses the access. With UNALIGN_TRP set, an unaligned word access raises a UsageFault and sets the UNALIGNED bit, bit 24 of CFSR. The solution never sets USGFAULTENA, bit 18 of SHCSR, so the UsageFault is disabled. The core escalates the fault to HardFault and sets HFSR bit 30, FORCED. The solution's comment in main.c describes this path.
  4. The frame is pushed. main runs on the main stack, so the core pushes eight words to MSP. The PC word is the address of the faulting load, 0x08000262, because the fault is precise. The stub reads EXC_RETURN bit 2, finds it clear, and passes MSP to C in R0.
  5. The handler prints. hard_fault_report prints frame word 6, which is the PC. By the bit positions above, the expected CFSR is 0x01000000, with only UNALIGNED set, and the expected HFSR is 0x40000000, with only FORCED set. Those are predictions from the register layout. Check them on a run that reaches the fault, and do not assume them.
  6. The decode checks the address. You can find the faulting instruction with objdump, and then decode the PC with addr2line. Both steps are in the next section.

Common mistakes and how to spot them

Mistake 1: no HardFault_Handler. The developer writes the rest of the program and never defines the handler. The startup file's weak default takes over, and it loops forever. The symptom is a device that stops with no output: the last line printed is the last line before the fault, and nothing else appears. The fix is to define HardFault_Handler in your own code, with the same name, and let it override the default. Do not edit the startup file.

Mistake 2: a C handler with a prologue. The developer writes void HardFault_Handler(void) as an ordinary C function, and reads the stack inside it. The compiler adds a prologue, the prologue saves registers and moves the stack pointer, and the frame the handler reads is no longer the frame the core pushed. The symptom is a PC value that does not match the faulting instruction, or a handler that hangs or prints garbage. The fix is the naked stub above, which passes the true frame pointer to C.

Mistake 3: printing with printf in the handler. The developer uses printf to make the report look tidy. The library may need a heap, a lock or a buffer that the fault left in an unknown state, so the output can be partial or the device can hang. The symptom is a report that stops after the first line, or no report at all. The fix is a plain routine that writes bytes to the UART, as in uart_puts and uart_put_hex32, which depend on nothing else.

Mistake 4: reading BFAR without checking BFARVALID. The developer prints BFAR after every BusFault. The register holds an address only when CFSR bit 15 is set, and otherwise it holds stale or meaningless data. The symptom is an address in the report that has no relation to the crash. The fix is to read CFSR first and print BFAR only when bit 15 is set.

Mistake 5: decoding with the wrong ELF. A field report comes in from release 2.3, and the engineer runs addr2line on the ELF from release 2.4, which is the one on their desk. The tool returns a function and a line that look plausible, and the fix is in the wrong place. The symptom is a fix that does nothing in the field. The fix is to keep the ELF for every release, and to check the decode with objdump on the same file.

Mistake 6: an assertion for bad input. A developer asserts that the sensor reading is in range, and the sensor occasionally reports a bad value. The device resets, and the customer sees a reboot every time the sensor glitches. The symptom is a log full of assertions for values the hardware is allowed to produce. The fix is an error path that rejects the value, and an assertion only where the code itself has broken its own rule.

Mistake 7: kicking the watchdog from an interrupt. The developer kicks the watchdog in a timer interrupt, so the watchdog never resets. The main loop could be stuck, and the report would still be clean. The symptom is a device that hangs in the field and never resets. The fix is task check-in, where each task reports progress and the kick waits for all of them.

In real projects

A product team treats a reset as data. The firmware records the reset reason at boot (lesson 85), and the crash record survives the reset. The team keeps the ELF and the map file for every release, usually in the same archive as the firmware image, so the decode can always be repeated. A field report is then a short list of facts: the reset reason, the PC, the fault registers and the release number. The engineer reads that list before asking the customer for anything else.

Teams also design the watchdog timing as a requirement. Each task has a maximum time between check-ins, the supervisor's kick interval is shorter than the shortest of those, and the values are written in the design document. A reviewer asks what happens when a task is slow as well as when it is stuck.

Summary

  • A watchdog resets a hung chip unless software kicks it in time. The IWDG runs from its own clock and cannot be stopped once started. The WWDG must be kicked inside a window.
  • Check in from every task before the kick, so one stuck task causes a reset.
  • On a fault, the core pushes eight words, and word 6 is the PC of the faulting instruction for a precise fault.
  • EXC_RETURN bit 2 says whether the frame is on MSP or PSP. A naked stub passes the right pointer to C without a prologue.
  • Read HFSR for the escalation, CFSR for the cause, and BFAR only when BFARVALID (CFSR bit 15) is set.
  • A weak HardFault_Handler default loops forever, so define your own handler.
  • Decode the stacked PC with addr2line and the ELF from the same build, then check it with objdump.
  • Assertions are for bugs. Bad input needs an error path, not a reset.

Decode the address with addr2line

The solution's faulting load is the instruction at 0x08000262. You can find it yourself with objdump, from Git Bash, after building the solution. The command below prints the function and the instructions that follow its label. The real output of the build is shown: 

"/c/Program Files (x86)/Arm GNU Toolchain arm-none-eabi/14.2 rel1/bin/arm-none-eabi-objdump.exe" -d build/blink.elf | grep -A7 "<trigger_unaligned_load>:"
08000254 <trigger_unaligned_load>:
 8000254:	4a04      	ldr	r2, [pc, #16]	@ (8000268 <trigger_unaligned_load+0x14>)
 8000256:	6953      	ldr	r3, [r2, #20]
 8000258:	f043 0308 	orr.w	r3, r3, #8
 800025c:	6153      	str	r3, [r2, #20]
 800025e:	f04f 5300 	mov.w	r3, #536870912	@ 0x20000000
 8000262:	f8d3 3001 	ldr.w	r3, [r3, #1]
 8000266:	4770      	bx	lr

Read the listing as the steps above. The ldr r2 loads the SCB base address from a literal pool, the ldr and str at offset 20 read and write the CCR, and orr.w ... #8 sets bit 3. Then mov.w r3, #536870912 loads 0x20000000, the start of RAM, and ldr.w r3, [r3, #1] at 0x08000262 reads the word at 0x20000001. That load is the fault.

Now decode the address itself. Your build puts the .elf in build/. Run this from the solution folder: 

"/c/Program Files (x86)/Arm GNU Toolchain arm-none-eabi/14.2 rel1/bin/arm-none-eabi-addr2line.exe" -e build/blink.elf -f -C -i 0x08000262
trigger_unaligned_load
C:/Users/juhos/embedded-course/projects/0084-robustness/solution/main.c:90

The output names the function, trigger_unaligned_load, and the source line, 90. Line 90 is (void)*p;, the faulting read. Line 89 is the declaration of the pointer p, which does not run a load, so the line that faults is the one below it. These two lines are the real output of the solution's build on this machine. On a real board, the PC that your handler prints should be the same address as the faulting instruction you found with objdump. That is the check to make before you trust the decode.

The same method works on a field log. A crash log prints HardFault PC=0x and an address, and you run addr2line on the matching .elf from that exact build. A different build has a different .elf, so keep the .elf for every release.

Check the mapping before you trust it. The map file (blink.map, lesson 41) shows where each function sits, and objdump shows the instruction. Two sources agreeing is the evidence you want in a fault report.
You can make a fault announce itself with the address that caused it, and turn that address into a source line. That is the first thing a field crash report needs.
