Robustness

Watchdogs, fault handlers and assertions

By the end of this lesson you can write a HardFault handler that prints the stacked PC and the fault registers, and decode that PC to a source line with arm-none-eabi-addr2line.

A field failure without a debugger

This lesson builds on four earlier ones, lesson 34 having shown how the core enters an exception and pushes registers onto the stack, lesson 39 the faults and the System Control Block (SCB) that reports them, lesson 42 the vector table deciding where the core goes on a fault, and lesson 78 how a stack that grows too deep becomes a hang or a corrupted variable.

A product in a customer's building resets a few times a month and a support engineer asks why, but no debugger is attached, the serial port is unplugged and the device sits in a cabinet. The firmware must therefore recover on its own, so that the device keeps working, record evidence, so that the next engineer knows what happened, and check its own assumptions, so that a broken invariant is found where it breaks rather than three functions later, each job having a tool in this lesson, a watchdog, a HardFault handler and an assertion.

Watchdog timers

A watchdog is a counter that resets the chip unless software clears it in time (glossary: watchdog), normal code clearing it on a schedule, which is called a kick or a refresh. If the program hangs in a loop, waits on a lock that never opens or sits in a fault handler that never returns, the kicks stop and the counter reaches zero and resets the system, which recovers the device where a hung one would not. A stack overflow is one common cause of such a hang, and lesson 78 shows how to see the stack depth before it becomes one.

The STM32F1 has two watchdogs, described in the reference manual RM0008 Rev 21 in chapter 19 (the independent watchdog, IWDG) and chapter 20 (the window watchdog, WWDG), which differ in their clock and their rules.

WatchdogClockRuleUse it for
Independent (IWDG)Its own low-speed RC, so it keeps running if the main clock stops (section 19.1)Once started, it cannot be stopped except by a reset (sections 5.3.4 and 19.3). You kick it inside a fixed timeThe last line of defence against a hang
Window (WWDG)Derived from the APB1 clockYou must kick it inside a window. Too early is a reset as well as too late (sections 20.1 and 20.3)Catching code that runs too fast, such as a loop that skips its work

The IWDG's counter is a 12-bit value, its reload register IWDG_RLR having a field RL with a mask of 0xFFF, defined in the device header third_party/cmsis-device-f1/Include/stm32f103xb.h, which the manual gives as RL[11:0] with a reset value of 0x0FFF (RM0008 Rev 21, section 19.4.3). The largest reload value is therefore 4 095, from which the counter counts down (section 19.3), the number the quiz asks about.

In this course's simulator, NOTES.md records that the Blue Pill's IWDG is not simulated, and WWDG is. The Pico's watchdog (hardware_watchdog in the SDK) has not been checked in the simulator, so treat its behaviour here as unverified.

Task check-in before the watchdog kick

A watchdog kicked from one timer interrupt proves only that the interrupt runs, since the main loop could be stuck while the interrupt keeps the watchdog satisfied. A better design checks in, each task setting its own bit when it has made progress and a supervisor kicking the watchdog only when every expected bit is set, then clearing the bits for the next round, so that a hung task never sets its bit, the kick stops and the chip resets. This task check-in pattern (glossary: task check-in) also reveals which task was stuck when the log of lesson 85 is read.

A watchdog resembles a train's dead man's switch, a pedal the driver must press every so often, the system assuming that a driver who stops pressing is unable to act and stopping the train, so kicking the watchdog from a timer interrupt that keeps running while the main loop is stuck amounts to taping the pedal down, satisfying the switch while protecting nothing. The comparison breaks on the response, though, because the train stops and waits for help, whereas a watchdog restarts the chip at once, and a fault that recurs at every boot turns into a reset loop.

Check-in works best when each task has its own event queue and never blocks the others, the design of lesson 77, because a task blocking on a slow sensor can miss its check-in window, and the watchdog then resets the device for a reason that is not a bug in the task. The design question is how long each task may take between check-ins, a number that should be written down.

  1. Three tasks each own one check-in bit. The watchdog counts down from its timeout; only the supervisor may kick it.
  2. sensor and comms have done their work and set bits 0 and 1. ui has not yet, so the supervisor does not kick. The watchdog keeps counting down.
  3. ui checks in. All three bits are set, so the supervisor kicks the watchdog and clears the bits for the next round.
  4. In the next round comms gets stuck in a loop. sensor and ui are healthy and set their bits again.
  5. Bit 1 never sets, so the supervisor never kicks. A watchdog kicked from a timer interrupt would still be fed here, because the interrupt keeps running while comms is stuck.
  6. The watchdog expires and resets the chip: the hang is caught, and the reset reason tells you after boot that it was the watchdog.

The stacked exception frame and EXC_RETURN

On a fault the core behaves as on any other exception entry, pushing a fixed set of eight words onto the active stack before it runs the handler (lesson 34; PM0056 Rev 7, section 2.3.7). This stacked frame (glossary: stacked frame) holds R0, R1, R2, R3, R12, LR, PC and xPSR in that order from the lowest address, word 0 lying at the frame pointer, word 6 at the frame pointer plus 24 bytes and word 7 at 28 bytes.

The PC in the frame is the address of the instruction running when the fault happened, and for a precise fault, the case in this lesson, the instruction that caused the fault is the one whose address is stacked, which makes the PC the main clue to where the code was. The LR word holds whatever the link register held, which in general is not the caller, so it is a weaker clue.

The handler needs to know which stack received the frame, the core choosing the main stack pointer (MSP) or the process stack pointer (PSP) by the mode it was in and reporting the choice in the exception return value EXC_RETURN (glossary: EXC_RETURN), whose bit 2 is 0 when the frame is on the MSP and 1 when it is on the PSP (PM0056 Rev 7, section 2.3.7, Table 17). The firmware in this lesson has no operating system, so the frame goes to the MSP.

The fault status registers

The stacked frame says where the code was, and the fault status registers say why. They live in the System Control Block (SCB), a block of registers at address 0xE000ED00 (PM0056 Rev 7, section 4.4.15), which the CMSIS header defines as a structure with each register at a fixed offset from the base, and the offsets that matter here are listed below (PM0056 Rev 7, sections 4.4.10 to 4.4.13).

RegisterAddressWhat to look at
CFSR0xE000ED28The cause: bits for MemManage, BusFault and UsageFault events
HFSR0xE000ED2CBit 30, FORCED: a configurable fault was escalated to HardFault. Bit 1, VECTTBL: an error reading the vector table
MMFAR0xE000ED34The MemManage address. The Blue Pill has no MPU, so ignore it there
BFAR0xE000ED38The BusFault address, valid only when CFSR bit 15 (BFARVALID) is set

The CFSR is one 32-bit word with three fields, the MemManage field starting at bit 0, the BusFault field at bit 8 and the UsageFault field at bit 16, each with its own named bits, which the header positions the same way for every field. BFARVALID is bit 7 of the BusFault field, so bit 15 of CFSR, UNALIGNED bit 8 of the UsageFault field, so bit 24 of CFSR, and MMARVALID, also defined in the header, bit 7 of the MemManage field, so bit 7 of CFSR, the manual giving the same layout (PM0056 Rev 7, section 4.4.10).

The bit positions come from the CMSIS header third_party/CMSIS_5/CMSIS/Core/Include/core_cm3.h, while the reference for the fault register descriptions is the Cortex-M3 programming manual PM0056 Rev 7, sections 4.4.9 to 4.4.13. The offsets and bit positions in this lesson were read from the header the course build uses, and they match the names in the code and the values in PM0056.

One more register matters for the lesson's fault, the configuration control register, CCR, at offset 0x14 in the SCB, whose bit 3, UNALIGN_TRP, makes an unaligned access fault instead of being fixed up by the core (PM0056 Rev 7, section 4.4.7). The header calls the mask SCB_CCR_UNALIGN_TRP_Msk, with the value 8, and the solution sets this bit on purpose to create a fault.

A naked HardFault handler stub

The handler has two parts, a small assembly stub that finds the stacked frame and a C function that reads and prints it, and the stub must come first, written so that the compiler adds nothing in front of it. A C function starts with a prologue, code the compiler adds to save registers and set up the stack, and a prologue running before the handler reads the stack pointer can change the very stack the handler is about to read, whereas a naked function (glossary: naked function) has no prologue, so its body controls every register. 

void HardFault_Handler(void) __attribute__((naked));
void HardFault_Handler(void) {
    __asm volatile(
        "tst lr, #4          \n"   /* bit 2 of EXC_RETURN: which stack? */
        "ite eq              \n"
        "mrseq r0, msp       \n"   /* 0: frame is on MSP */
        "mrsne r0, psp       \n"   /* 1: frame is on PSP */
        "b hard_fault_report \n"   /* R0 = pointer to the eight stacked words */
    );
}

The stub's four instructions do the whole job. tst sets the zero flag if bit 2 of LR is clear, ite is the if-then-else instruction for the next two, and mrseq and mrsne copy MSP or PSP into R0 according to that flag, R0 being the first argument of a C function under the Arm procedure call standard, so b jumps into hard_fault_report with the frame pointer in R0. The jump is a branch rather than a call, so no return address is pushed and the handler never returns to the fault.

The startup file gives HardFault_Handler a weak default that loops forever. The default is an alias of Default_Handler, which runs b Infinite_Loop. Your own definition with the same name overrides the default, so you do not edit the startup file. If you forget to define it, a fault makes the chip hang silently, and the serial monitor shows nothing after the last line the program printed.

Assertions that log and reset

An assertion checks an invariant and stops the program when it is false (glossary: assertion), an invariant being a condition the code assumes always holds, such as "this pointer is not null because the caller checked it". In firmware the useful version records the file and line and then resets, so the device recovers while the log explains why, and the sketch below shows the idea, which lesson 85 implements in full with a log that survives the reset. 

#define ASSERT(expr) do { if (!(expr)) assert_failed(__FILE__, __LINE__); } while (0)

void assert_failed(const char *file, int line) {
    log_line_for(file, line);   /* survives the reset (lesson 85) */
    NVIC_SystemReset();         /* does not return */
}

NVIC_SystemReset is a CMSIS function that writes the system reset request bit, SCB_AIRCR_SYSRESETREQ, bit 2 of the application interrupt and reset control register, after which the core resets, so nothing after the call runs, which is why the header marks the function as not returning.

Use assertions for bugs, such as a pointer that should never be null. Do not use them for input from the outside world. A bad sensor reading needs an error path, not a reset. Compile-time assertions, written with _Static_assert, catch layout bugs before the build succeeds at no run-time cost, the two kinds answering different questions, a static assertion checking the program's structure and a run-time assertion the state the program reaches.

Decoding the stacked PC with addr2line

The PC in the frame is an address in flash, which the tool arm-none-eabi-addr2line maps to a function and a source line using the debug information in the .elf file. A debugger does the same when breaking on a fault, but addr2line works on a log printed in the field without any debugger, and its options are -e naming the ELF file, -f printing the function name, -C demangling names and -i following inlined code.

Worked example: the deliberate crash in the solution

The solution causes a fault on purpose, and each step is a fact that can be checked in the build. Before following them, predict which fault the core finally reports, given that the UsageFault is never enabled.

  1. Arm the fault. trigger_unaligned_load sets bit 3 of the CCR with SCB->CCR |= SCB_CCR_UNALIGN_TRP_Msk, which in the disassembly is the orr.w r3, r3, #8 followed by the store to offset 20 (0x14), bit 3 being the value 8, so the store is the CCR write.
  2. Use an odd address. The code makes a pointer to 0x20000001, an address in RAM, which starts at 0x20000000, lying one byte past a word boundary, and the instruction ldr.w r3, [r3, #1] loads a 32-bit word from it.
  3. Escalate the fault. With UNALIGN_TRP set, an unaligned word access raises a UsageFault and sets the UNALIGNED bit, bit 24 of CFSR, but since the solution never sets USGFAULTENA, bit 18 of SHCSR, the UsageFault is disabled, so the core escalates the fault to HardFault and sets HFSR bit 30, FORCED, the path described by the solution's comment in main.c.
  4. Push the frame. main runs on the main stack, so the core pushes eight words to MSP, the PC word being the address of the faulting load, 0x08000262, because the fault is precise, and the stub reads EXC_RETURN bit 2, finds it clear and passes MSP to C in R0.
  5. Print the report. hard_fault_report prints frame word 6, the PC, and by the bit positions above the expected CFSR is 0x01000000, with only UNALIGNED set, and the expected HFSR 0x40000000, with only FORCED set, predictions from the register layout that must be checked on a run reaching the fault rather than assumed.
  6. Check the decode. The faulting instruction is found with objdump and the PC decoded with addr2line, both steps following in the hands-on section.

Decoding the address with objdump and addr2line

The solution's faulting load is the instruction at 0x08000262, which you can find yourself with objdump from Git Bash after building the solution, the command below printing the function and the instructions following its label, with the real output of the build. 

"/c/Program Files (x86)/Arm GNU Toolchain arm-none-eabi/14.2 rel1/bin/arm-none-eabi-objdump.exe" -d build/blink.elf | grep -A7 "<trigger_unaligned_load>:"
08000254 <trigger_unaligned_load>:
 8000254:	4a04      	ldr	r2, [pc, #16]	@ (8000268 <trigger_unaligned_load+0x14>)
 8000256:	6953      	ldr	r3, [r2, #20]
 8000258:	f043 0308 	orr.w	r3, r3, #8
 800025c:	6153      	str	r3, [r2, #20]
 800025e:	f04f 5300 	mov.w	r3, #536870912	@ 0x20000000
 8000262:	f8d3 3001 	ldr.w	r3, [r3, #1]
 8000266:	4770      	bx	lr

The listing follows the steps above, the ldr r2 loading the SCB base address from a literal pool, the ldr and str at offset 20 reading and writing the CCR and orr.w ... #8 setting bit 3. Then mov.w r3, #536870912 loads 0x20000000, the start of RAM, and ldr.w r3, [r3, #1] at 0x08000262 reads the word at 0x20000001, the load that faults.

The address itself is decoded from the .elf that your build puts in build/, with the following command run from the solution folder. 

"/c/Program Files (x86)/Arm GNU Toolchain arm-none-eabi/14.2 rel1/bin/arm-none-eabi-addr2line.exe" -e build/blink.elf -f -C -i 0x08000262
trigger_unaligned_load
C:/Users/juhos/embedded-course/projects/0084-robustness/solution/main.c:90

The output names the function, trigger_unaligned_load, and the source line, 90, which is (void)*p;, the faulting read, while line 89 declares the pointer p without running a load, so the faulting line is the one below it. These two lines are the real output of the solution's build on this machine, and on a real board the PC your handler prints should equal the address of the faulting instruction found with objdump, the check to make before trusting the decode.

Check the mapping before you trust it. The map file (blink.map, lesson 41) shows where each function sits, and objdump shows the instruction. Two sources agreeing is the evidence you want in a fault report.

The same method works on a field log, a crash log printing HardFault PC=0x and an address on which addr2line is run with the matching .elf from that exact build, and since a different build has a different .elf, the .elf of every release must be kept.

You can make a fault announce itself with the address that caused it and turn that address into a source line, the first thing a field crash report needs.

Common mistakes and how to spot them

No HardFault_Handler defined

The device stops without output, the last printed line being the last before the fault, because the developer never defined the handler, so the startup file's weak default took over and looped forever. Define HardFault_Handler in your own code under the same name, letting it override the default, without editing the startup file.

A C handler with a prologue

The printed PC does not match the faulting instruction, or the handler hangs or prints garbage, because the developer wrote void HardFault_Handler(void) as an ordinary C function reading the stack, and the compiler's prologue saved registers and moved the stack pointer, so the frame read is no longer the one the core pushed. Use the naked stub above, which passes the true frame pointer to C.

printf in the fault handler

The report stops after its first line, or never appears, because the developer used printf for a tidy report, and the library may need a heap, a lock or a buffer that the fault left in an unknown state. Write bytes to the UART with a plain routine such as uart_puts and uart_put_hex32, which depend on nothing else.

BFAR read without checking BFARVALID

The report contains an address unrelated to the crash, because the developer prints BFAR after every BusFault, although the register holds a valid address only when CFSR bit 15 is set and stale or meaningless data otherwise. Read CFSR first and print BFAR only when bit 15 is set.

A decode with the wrong ELF

A fix does nothing in the field, because a report came in from release 2.3 and the engineer ran addr2line on the ELF of release 2.4, the one on their desk, which returned a plausible function and line in the wrong place. Keep the ELF of every release and check the decode with objdump on the same file.

An assertion for bad input

The log fills with assertions for values the hardware is allowed to produce and the customer sees a reboot at every sensor glitch, because a developer asserted that the sensor reading is in range. Give bad input an error path that rejects the value, and keep assertions for places where the code itself has broken its own rule.

The watchdog kicked from an interrupt

The device hangs in the field and never resets, because the watchdog is kicked from a timer interrupt that keeps running while the main loop is stuck. Use task check-in, in which each task reports progress and the kick waits for all of them.

Reset records and watchdog timing in products

A product team treats a reset as data, the firmware recording the reset reason at boot (lesson 85) while the crash record survives the reset, and the team keeps the ELF and the map file of every release, usually in the same archive as the firmware image, so that the decode can always be repeated. A field report then becomes a short list of facts, the reset reason, the PC, the fault registers and the release number, which the engineer reads before asking the customer for anything else.

Teams also design the watchdog timing as a requirement, each task having a maximum time between check-ins and the supervisor's kick interval being shorter than the shortest of them, with the values written into the design document, and a reviewer asks what happens when a task is slow as well as when it is stuck.

Summary

  • A watchdog resets a hung chip unless software kicks it in time, the IWDG running from its own clock and unstoppable once started, while the WWDG must be kicked inside a window.
  • Every task checks in before the kick, so that one stuck task causes a reset.
  • On a fault the core pushes eight words, word 6 being the PC of the faulting instruction for a precise fault.
  • EXC_RETURN bit 2 says whether the frame is on MSP or PSP, and a naked stub passes the right pointer to C without a prologue.
  • HFSR shows the escalation and CFSR the cause, while BFAR is read only when BFARVALID (CFSR bit 15) is set.
  • The weak HardFault_Handler default loops forever, so firmware defines its own handler.
  • The stacked PC is decoded with addr2line and the ELF of the same build, then checked with objdump.
  • Assertions are for bugs, whereas bad input needs an error path rather than a reset.
