Embedded Rust on the Pico

The same RP2040 and the same vector table, built by a compiler that checks who may touch each peripheral. Setup first, then the parts of a no_std binary, then the compiler catching a mistake.

Optional. Skip this lesson if you want to stay on the C path. It is useful if you plan to apply for firmware jobs that list Rust, or if you want to see what the compiler does for you in C. Parts 1 to 4 are enough to follow it.
By the end of this lesson you can build the Rust blink project on this machine, name the parts of a no_std binary against their C equivalents, and explain why a call to set_high() on an input pin does not compile.

Setup, as done on this machine

Rust is installed with rustup, which manages toolchains and targets. Run these in PowerShell or Git Bash. The first one installs rustup itself; the rest add the parts this course needs. 

winget install -e --id Rustlang.Rustup
rustup toolchain install stable-x86_64-pc-windows-gnu --profile minimal
rustup target add thumbv6m-none-eabi --toolchain stable-x86_64-pc-windows-gnu
rustup component add llvm-tools --toolchain stable-x86_64-pc-windows-gnu

The thumbv6m-none-eabi target is the Armv6-M architecture, which is the Cortex-M0+ core of the RP2040 (Arm Cortex-M0+ processor datasheet). The target is a compiler setting: it tells rustc which instructions and ABI to emit, the same job as -mcpu=cortex-m0plus in GCC. llvm-tools gives you the LLVM binary tools, such as llvm-size, to inspect the ELF.

Why the GNU host toolchain. rustup installs the MSVC toolchain by default on Windows. That toolchain links through Microsoft's linker, which needs Visual Studio. Cargo build scripts (small programs that run on the PC during the build, used by the crates here) are then linked by the same linker, and fail without it. The GNU toolchain (x86_64-pc-windows-gnu) uses MinGW instead, which this machine already has.

What rust-toolchain.toml does. The project file pins the toolchain and target, so anyone who runs cargo build in that folder gets the same compiler: 

[toolchain]
channel = "stable-x86_64-pc-windows-gnu"
targets = ["thumbv6m-none-eabi"]

Also in the project, .cargo/config.toml sets the default target and the linker flags, so you never type --target. This is the same role as a CMake toolchain file: it fixes the target for the whole project.

Build the project from the workspace root with the course build script. It runs cargo build --release (release builds keep debug information, so GDB works): 

python -I tools/build.py projects/0108-embedded-rust-on-the-pico/starter

The output is target/thumbv6m-none-eabi/release/blink, an ELF file with no .elf extension. wokwi.toml points at it, so Wokwi runs the same file that a debugger would load. Open the starter folder in VS Code, press Ctrl+Shift+B to build, then F1 → Wokwi: Start Simulator. For debugging, start the simulator and press F5.

Do not install extra Cargo tools such as probe-rs, flip-link or elf2uf2-rs for this lesson. Wokwi runs the ELF directly, and the course build does not need them.

The parts of a no_std binary

A normal Rust program starts with the standard library, which assumes an operating system. A microcontroller has none, so the project declares #![no_std] (no standard library) and #![no_main] (no C-style main from a runtime). What is left is the same job you already know from C, split into crates.

The pieces, against C

Each row below has a C counterpart from the course. The Rust name is what you will see in the project.

The PAC is generated by svd2rust from the SVD file that the chip vendor publishes. You do not need the tool: the crate is generated and checked in, as CMSIS headers are. The HAL is a separate crate that depends on the PAC (rp2040-hal 0.11.0 docs). The register names come from the RP2040 datasheet.

The .boot2 section is what the blink program puts first in flash with #[link_section = ".boot2"]. The memory.x file reserves the first 256 bytes for it, so the vector table starts at 0x10000100. Lesson 42 covers the startup code that runs after the boot ROM has done its work. The RP2040 datasheet describes the second-stage bootloader in its boot sequence material (RP2040 datasheet, boot sequence), and the rp2040-boot2 crate supplies the 256-byte image itself.

The blink program's main is marked #[hal::entry]. That attribute is the crate's version of int main(void) in C: it puts main behind the reset handler that cortex-m-rt generates.

Why Rust matters for embedded jobs

Rust's main benefit on a microcontroller is that many C mistakes become compile errors, with no run-time cost. Three rules do most of the work:

  1. Ownership of peripherals. Peripherals::take() returns Some only the first time. A second call returns None, so two parts of the program cannot each hold the GPIO block. The rp2040-pac 0.6.0 source shows this: take() returns None once a flag is set, and otherwise hands out the peripherals. The Embedded Rust Book describes the same pattern as a singleton, one instance of a peripheral (Embedded Rust Book, Singletons).
  2. Type-state pins. into_push_pull_output() returns a different type, so a write to the pin is only possible in output mode. The book gives the same kind of example: trying to change the output state of a pin configured in floating input mode "would raise a compile error" (Embedded Rust Book, Static Guarantees). In C, the same bug compiles, and the pin does not change, with no warning.
  3. No data races without unsafe. Safe Rust does not let two parts of the program mutate the same static unless the type shows that access is synchronised. Writing unsafe is then an explicit statement that the programmer takes responsibility. The code that is still unsafe is local, usually register access inside the PAC and HAL.

The fourth point is portability. The embedded-hal 1.0 crate defines traits such as OutputPin. A sensor driver written against those traits runs on any chip whose HAL implements them. That is the idea behind lesson 76's hardware abstraction layer, enforced by the compiler.

The balance. Ownership removes whole classes of bugs, but it does not check your datasheet reading or your timing. Ecosystem maturity is the main limit: rp2040-hal is at version 0.11, and many drivers and RTOS integrations are still young. For safety-critical work, Ferrocene is a Rust toolchain from Ferrous Systems that the vendor markets for that use (Ferrous Systems, Ferrocene). Check its qualification scope with the vendor before you rely on it; lesson 109 explains what a standard such as ISO 26262 asks for. In job ads, C is still the default, and Rust is a differentiator for roles that ask for it. That is a judgement from the market, not a measured figure.

Interrupts and shared state in Rust

Lesson 57 shared a flag between an interrupt and main with volatile, and protected the read-and-clear with a critical section. In Rust, the same job uses a critical_section::Mutex around a RefCell or a Cell. The Mutex hands out its contents only inside a critical section, and the compiler checks that you did not skip it. 

// The button pin is owned here, so only the handler can clear its interrupt.
type ButtonPin = hal::gpio::Pin<Gpio14, FunctionSio<SioInput>, PullUp>;
static BUTTON: Mutex<RefCell<Option<ButtonPin>>> = Mutex::new(RefCell::new(None));

// Written by the handler, read by main.
static BLINK_ENABLED: Mutex<Cell<bool>> = Mutex::new(Cell::new(true));

The Option starts as None, because the pin does not exist until main configures it. main moves the pin into the Mutex, and the handler takes it back out for each event. Moving a value transfers ownership, so main cannot use the pin afterwards. That is the same rule that rejects the snippet further down.

The bank 0 interrupt line is shared by every GPIO in the bank, so the handler checks interrupt_status for its own pin before it acts. The rp2040-hal 0.11 GPIO code defines set_interrupt_enabled, interrupt_status and clear_interrupt on the pin (rp2040-hal 0.11.0, src/gpio/mod.rs, in the crate source under the cargo registry). The interrupt handler is written as #[interrupt] fn IO_IRQ_BANK0(). The attribute comes from the PAC and is the same vector-table entry that lesson 57 used, number 13.

The Mutex is a critical section, and it does not sleep. Keep it short, as lesson 57 says for ISRs. Turning interrupts off for long stretches hurts the latency of everything else.

Worked example: one button press, step by step

The interrupt code is easier to follow as a timeline. Assume the program has just started, the button is released, and the LEDs are blinking. The RP2040's GPIO pull-up holds GP14 high while the switch is open, so the pin reads 1. Pressing the button connects GP14 to ground, and the pin reads 0. The edge from high to low is the event the interrupt is set up to catch.

  1. t = 0 ms. main is inside its loop. Each pass adds 1 to tick, toggles an LED when tick divides evenly, and then waits 50 ms with delay_ms(TICK_MS).
  2. The press. GP14 falls from high to low. The pin's interrupt status for EdgeLow is set in the GPIO block, and because bank 0 is shared, the bank 0 line goes active.
  3. The NVIC runs the handler. The NVIC was unmasked for IO_IRQ_BANK0 (number 13 in the RP2040 vector table), so the core stops main at its next instruction and enters IO_IRQ_BANK0().
  4. The handler checks its pin. It enters the critical section, borrows the pin from the Mutex, and calls interrupt_status(EdgeLow). That returns true, so the handler flips BLINK_ENABLED from true to false.
  5. The handler clears the event. clear_interrupt(EdgeLow) resets the pin's latched status. Without this step, the bank 0 line would still be active when the handler returned, and the handler would run again straight away.
  6. Main sees the flag. Within one loop pass (at most 50 ms later), main reads false, sets both LEDs low, and keeps the tick counter still. Releasing the button does not raise an edge on the falling-edge setting, so the blinking stays paused until the next press.

The timing numbers are the ones the solution uses. With TICK_MS at 50 and LED1_TICKS at 10, LED 1 changes state every 500 ms, so it completes one full blink every second. LED2_TICKS at 5 gives a change every 250 ms, two full blinks per second.

The handler flips the flag on every falling edge, so the second press makes the flag true again and the blinking resumes. Each press is one toggle, which is why the Try-it steps ask you to press the button twice and watch both LEDs stop and restart.

Reading the solution, line by line

You have already seen the handler and the Mutex declarations. The rest of main is the setup sequence, and it is worth reading in order, because each line depends on the one before it.

  • pac::Peripherals::take().unwrap() takes the one owner of the chip's peripherals. unwrap() panics if the call were repeated, which is the singleton rule in action.
  • Watchdog::new(pac.WATCHDOG) and init_clocks_and_plls(XOSC_HZ, ...) start the 12 MHz crystal and configure the PLLs. The clock code takes &mut pac.RESETS because it resets and starts the clock blocks, so the borrow checker keeps other code from using them meanwhile.
  • cortex_m::delay::Delay::new(core.SYST, ...) builds a delay from the SysTick timer, using the system clock frequency the clock setup returned. This is why delay_ms(50) is accurate, rather than a loop that depends on the compiler.
  • pins.gpio25.into_push_pull_output() and pins.gpio15.into_push_pull_output() each consume their pin and return a new value of an output type. The type change is what makes toggle() and set_low() available on those variables only.
  • into_pull_up_input() on GP14 gives an input type with the pull-up enabled, so set_interrupt_enabled(EdgeLow, true) is called on the value that will be moved into the Mutex.
  • The unsafe block around NVIC::unmask is the only line in main that the compiler does not check for you. It must come after the pin is in the Mutex, or the handler could run and find None.
  • The loop reads BLINK_ENABLED inside a short critical section, then either toggles the LEDs or holds them low, and always waits TICK_MS.

Hint for the interrupt

Enable the edge on the pin before you move it into the Mutex. The handler needs interrupt_status and clear_interrupt on the same pin, so you must borrow it from the Mutex with borrow_mut() inside critical_section::with.

Hint for unmasking

The NVIC is re-exported as pac::NVIC. unmask is unsafe, because the interrupt can start at once. Wrap the call in an unsafe block, and do it after the pin is in the Mutex.

The compiler catches it

Take the solution and add one line before the button is used: button.set_high().unwrap();. The pin is an input, so the output methods do not exist on its type. This is the real output of the build, from a scratch copy: 

error[E0599]: no method named `set_high` found for struct `rp2040_hal::gpio::Pin<I, F, P>` in the current scope
  --> src\main.rs:71:12
   |
71 |     button.set_high().unwrap();   // deliberate: GP14 is an input
   |            ^^^^^^^^ method not found in `rp2040_hal::gpio::Pin<Gpio14, FunctionSio<SioInput>, PullUp>`

In C, the equivalent write to GPIO_OE or gpio_put() on an input pin compiles and runs. Nothing stops it, and the bug shows up as a pin that never changes. Here the type of button says it is an input, and set_high belongs only to output types.

Now try the second mistake. Move the button into a variable, then use the original name: 

error[E0382]: use of moved value: `button`
  --> src\main.rs:76:28
   |
70 |     let button = pins.gpio14.into_pull_up_input();
   |         ------ move occurs because `button` has type `rp2040_hal::gpio::Pin<Gpio14, FunctionSio<SioInput>, PullUp>`, which does not implement the `Copy` trait
...
75 |     let _moved = button;   // deliberate: move
   |                  ------ value moved here
76 |     critical_section::with(|cs| BUTTON.borrow(cs).replace(Some(button)));
   |                            ^^^^ value used here after move     ------ use occurs due to use in closure

The pin cannot be used twice, so two parts of the code cannot both hold it. That is the ownership rule in the table above, applied to a single pin. Each mistake stops the build, so the program never reaches the board with a pin used in the wrong mode or after a move.

Common mistakes and how to spot them

The first mistake is unmasking the interrupt before the pin is in the Mutex. The handler then runs, finds None in the Option, and does nothing. Because the clear call sits inside the if let Some branch, the edge is never cleared, so the handler is entered again as soon as it returns. The symptom on the simulator is that main stops making progress: the LEDs freeze and stay that way, because the core keeps returning to the handler. The fix is the order in the solution: configure the pin, move it into the Mutex, and only then call NVIC::unmask.

The second mistake is a handler that forgets to clear its event. A developer copies the handler, removes the clear_interrupt line because it looks optional, and tests with one press. The symptom is the same as above: the handler re-enters without end once the first edge is seen. The fix is to clear the event for the pin that fired, after you have acted on it, and to check interrupt_status first when several pins share the bank.

The third mistake is a shared static mut with no synchronisation. A developer who knows C adds a plain global counter and increments it in main. The build stops with this message, from the scratch copy used for this lesson: 

error[E0133]: use of mutable static is unsafe and requires unsafe function or block
  --> src\main.rs:82:5
   |
82 |     COUNT += 1;
   |     ^^^^^ use of mutable static
   |
   = note: mutable statics can be mutated by multiple threads: aliasing violations or data races will cause undefined behavior

The fix is the Mutex pattern from this lesson, or an explicit unsafe block with a comment that says why no interrupt can race with it. The compiler's note names the risk exactly: an interrupt is another thread of execution for this purpose.

The fourth mistake is a wrong blink period. A developer sets LED2_TICKS to 10 because the number looks like a half period, and LED 2 blinks at 500 ms instead of 250 ms. The symptom is that the two LEDs seem to run at the wrong ratio. The fix is the arithmetic from the quiz: a half period is the number of ticks multiplied by TICK_MS.

In real projects

Teams that ship Rust on microcontrollers usually keep the PAC and HAL from crates.io, and write their own driver crates against embedded-hal 1.0. A driver written this way can be tested on a PC with a fake pin, and then run unchanged on the RP2040 or on another chip. That is the portability point from earlier, and it is what senior engineers look for when they review a driver's trait bounds.

In a code review, the questions are the ones C reviews ask, plus a few specific to ownership. Where is unsafe and why is it correct? Which value owns each peripheral? Does any interrupt handler take a lock that main also takes? An unsafe block with no comment is a review finding in most teams, and the same is true of a Mutex held across a long delay.

In interviews, Rust questions tend to test the model rather than syntax: why a singleton is needed, what type-state prevents, and how a critical section differs from a mutex that sleeps.

Summary

  • Rust on the Pico uses the same RP2040 and the same vector-table idea as the C projects; the crates generate the parts you would write by hand in C.
  • The build uses the GNU host toolchain pinned in rust-toolchain.toml, the thumbv6m-none-eabi target, and the linker flags in .cargo/config.toml.
  • memory.x reserves the 256-byte BOOT2 region at 0x10000000, so the vector table starts at 0x10000100.
  • Peripherals::take() returns Some once; the pin types then say which operations are legal in each mode.
  • A shared flag between an interrupt and main lives in a critical_section::Mutex; shared statics otherwise need an explicit unsafe block.
  • Clear each interrupt event after handling it, and unmask the NVIC line only after the handler's data is in place.
  • The compiler rejects wrong-mode pin calls and use-after-move before the program runs, but it cannot check the datasheet or the timing.

"What does Rust's ownership model buy you on a microcontroller?" Answer out loud in 60 seconds, then compare.

Model answer

It moves a class of bugs from run time to compile time, at no run-time cost. Peripheral singletons mean one owner per peripheral, and type-state pins make a wrong-mode call a compile error. Shared statics must go through a synchronised type such as a critical-section Mutex, or sit in an explicit unsafe block. The limits: it does not check the datasheet or the timing, the unsafe code in the PAC and HAL still has to be right, and the ecosystem is younger than the Pico SDK.
