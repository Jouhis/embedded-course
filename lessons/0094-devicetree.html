Devicetree: describing hardware

In Zephyr, the pin numbers, the bus addresses and the device names are not in the C code. They are in a tree that the build reads first, and this lesson shows how to read it and change it.

By the end of this lesson you can add a node in a board overlay, give it an alias, and read it from C with GPIO_DT_SPEC_GET, then find the merged result in build/zephyr/zephyr.dts.

The idea

A devicetree is a tree of nodes. Each node describes one piece of hardware, and its properties say what it is and where it is. A property called compatible names the binding, which is the schema that says which properties the node must have. The reg property is an address or a bus address. status = "okay" enables a node, and "disabled" turns it off. The format comes from the devicetree specification, and Zephyr's guide is in Zephyr's devicetree pages. Linux uses the same format for ARM boards. If you have read a Linux device tree, the syntax here will look familiar.

What the Pico already says

Open build/zephyr/zephyr.dts after any build. Each line ends with a comment that names the file it came from, so you can trace every value. Three of them matter for this course. The on-board LED is a child of the leds node with gpios = <&gpio0 25 …>, which is GP25, active high. The alias led0 points at it. The I2C bus i2c0 sits at 0x40044000, with clock-frequency set to 100 kHz by the board. Its pins come from a pinctrl group: I2C0_SDA_P4 and I2C0_SCL_P5 in rpi_pico-pinctrl-common.dtsi.

A node with no compatible is a container. A node with a compatible is matched to a binding, and Zephyr generates the macros for it. The difference matters, as the next section shows.

Adding a button with an overlay

The overlay file is boards/rpi_pico.overlay, and the build picks it up automatically for the Pico. The solution adds a second LED on GP16 and a button on GP14. The button is a new node, so it needs a binding. The project's own dts/bindings folder is a devicetree root, because the build adds the application directory to the root list (cmake/modules/pre_dt.cmake). The binding file is dts/bindings/input/vnd,user-button.yaml. 

buttons {
    user_button: button_0 {
        compatible = "vnd,user-button";
        gpios = <&gpio0 14 (GPIO_ACTIVE_LOW | GPIO_PULL_UP)>;
        label = "Button";
    };
};
aliases {
    sw0 = &user_button;
};

Read the gpios line. The first cell is the controller, the second is the pin, and the third is the flags. GPIO_ACTIVE_LOW means the logical value is 1 when the pin reads 0, and GPIO_PULL_UP turns the internal resistor on. The flags are defined in include/zephyr/dt-bindings/gpio/gpio.h.

Leave out the compatible line and the build fails. Our first attempt did exactly that, and the compiler reported undeclared identifiers from DT_N_S_buttons_S_button_0_…. The generated GPIO_DT_SPEC macros exist only for nodes with a binding. The fix was the compatible line plus the binding file.
Adding a binding file does not always take effect in an incremental build. After a new binding, rebuild with --clean (the build script's flag), or the cached list of bindings does not include it.

Reading the nodes from C

The C code never names GP14. It names the alias:

static const struct gpio_dt_spec led1 = GPIO_DT_SPEC_GET(DT_ALIAS(led1), gpios);
static const struct gpio_dt_spec button = GPIO_DT_SPEC_GET(DT_ALIAS(sw0), gpios);

gpio_pin_set_dt(&led1, gpio_pin_get_dt(&button));

GPIO_DT_SPEC_GET builds a struct from the node's gpios property (include/zephyr/drivers/gpio.h:376). gpio_pin_get_dt returns the logical level, so the active-low flag is already applied, and a pressed button reads 1 (gpio.h:1796).

Try it in Wokwi

The starter blinks led0 and has a TODO(learner) note where the overlay's second LED and button go. Add them, then wire the button to the second LED in the loop.

  1. Open projects/0094-devicetree/starter in VS Code.
  2. In boards/rpi_pico.overlay, add the led1 node on GP16, the button node on GP14 with compatible = "vnd,user-button", and the aliases. The binding file is already in dts/bindings/input.
  3. In src/main.c, get the two specs with GPIO_DT_SPEC_GET, configure them, and set led1 to the button's logical level each pass.
  4. Build with Ctrl+Shift+B, then open build/zephyr/zephyr.dts and find led_1. Start the simulator. You'll know it works when the second LED follows the button, and the serial monitor prints "DEVICETREE OK".
Hint

If the build reports undeclared identifiers, check the alias names and the compatible line first. The solution's overlay is the reference.

Model answer

Change the gpios property in the board overlay, which is the devicetree's job, and rebuild. The C code reads the pin through an alias with GPIO_DT_SPEC_GET, so it keeps working. If the new node is a new kind of device, add a binding file for its compatible string, and do a clean build.
