Memory hierarchy: SRAM, flash, caches, and XIP

Your program does not run from the place it was stored. Knowing where each object lives, and what a slow read costs, is the first step to explaining firmware timing.

By the end of this lesson you can name the memory region that holds each kind of C object on an RP2040 or an STM32F103, and explain why a flash read can cost extra cycles while an SRAM read usually does not.

The idea

A Cortex-M core works on registers. Everything else it reads or writes comes from memory on the same bus. Memory is a hierarchy: a few registers inside the core, then fast SRAM (volatile, read and write), then flash (non-volatile, read mostly, slower to read). Some chips add a cache, a small fast copy of recently used flash, between the two. Architecture students will recognise this as the classic memory hierarchy, with the trade-off between capacity, latency and cost. Microcontrollers keep it but drop the large off-chip DRAM level.

The RP2040 has two kinds of memory on chip. The ROM is 16 kB and holds the boot code. The SRAM is 264 kB, split into six banks; the datasheet says software may treat it as one 264 kB region. RP2040 datasheet, section 2.6.1 (ROM) and 2.6.2 (SRAM). Program flash is not on the chip: it is an external serial flash chip on the QSPI interface.

That external flash is reached through execute in place (XIP). Reads to a 16 MB window starting at 0x10000000 are turned into serial flash transfers, and the result goes back to the core. The core runs code from that window without copying it to SRAM first. An internal XIP cache keeps recently read flash, and it is 16 kB, two-way set-associative, with a one-cycle hit. RP2040 datasheet, section 2.6.3 (Flash) and 2.6.3.1 (XIP Cache). A cache miss is the slow case. The datasheet describes it as an external serial access. It does not give a cycle count, so treat "much slower" as the honest claim.

Where your objects live

The compiler and linker decide where each object goes (lesson 41 shows how). The rule is simple, and it is the same on both chips:

C objectWhere it lives at run timeSection
const uint32_t table[4]Flash (read-only).rodata
uint32_t counter = 7;SRAM. The value 7 is stored in flash and copied to SRAM at startup..data
uint32_t zeroed;SRAM, cleared to 0 at startup.bss
A local variableSRAM, on the stackstack
The code of main()Flash (executed in place).text
An initialised global is the tempting mistake. Its starting value sits in flash, but the variable itself lives in SRAM, and it is writable.

STM32F103: flash, SRAM, and wait states

The STM32F103 has its code flash at 0x08000000 and its SRAM at 0x20000000, as the ST device header defines them (FLASH_BASE and SRAM_BASE in stm32f103xb.h). The Blue Pill's linker script gives 64 KB of flash and 20 KB of SRAM: templates/common/stm32f103c8.ld.

Flash is slower than the core at high clock speeds, so the flash controller inserts wait states: extra cycles the core waits before the data arrives. The number of wait states is set by the LATENCY field of FLASH_ACR. The ST HAL raises the latency before it raises the clock, with the comment "Increasing the number of wait states because of higher CPU frequency" in stm32f1xx_hal_rcc.c. The rule is one-way: more clock needs more wait states, and you must set them first.

The exact clock thresholds for each wait-state setting are in the Flash chapter of the STM32F1 reference manual, RM0008. This course has not yet checked them against the vendor's own text, so do not quote numbers from memory. You will find the table yourself in Lab 2 and lesson 43.

The STM32F1 also has a prefetch buffer, enabled by the PRFTBE bit of FLASH_ACR. The device header names it "Prefetch Buffer Enable". It fetches instructions ahead of the core, which hides some of the flash delay on straight-line code. It is not a full cache of data.

You can say, for any C object in a Pico or Blue Pill program, which memory it lives in and why, and you know the one case where an apparently simple read costs several cycles.

Hint

The address ranges are the ones in the ST header: flash from 0x08000000 and SRAM from 0x20000000. An address of a stack local is also in SRAM, but it is near the top of the RAM region, not the bottom.

In the build for this lesson, the const table is at 0x080004B8 and the initialised counter at 0x20000000. Your build should match these numbers, because the toolchain is the same.

"What is execute in place, and why can a flash read make a program slower than the same code in SRAM?" Answer out loud in 60 seconds, then compare.

Model answer

Execute in place means the core fetches instructions straight from a memory-mapped flash window, with no copy to RAM. The flash is external and serial on the RP2040, so a read that misses the cache must go out over the serial bus, and that takes far longer than an SRAM access. A cache hit is fast, so the average speed depends on how often the code hits the cache. Code that is critical for timing is often copied to SRAM for that reason.

RP2040 datasheet: read section 2.6 (Memory), especially 2.6.2 (SRAM, with the striped banks in Table 153), 2.6.3 (Flash) and 2.6.3.1 (XIP Cache). It explains the cache mirrors at 0x10000000 to 0x15000000 in one short table.
