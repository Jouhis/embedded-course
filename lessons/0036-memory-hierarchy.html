Memory hierarchy: SRAM, flash, caches, and XIP

The memories of a microcontroller and the cost of reading each

By the end of this lesson you can name the memory region that holds each kind of C object on an RP2040 or an STM32F103, and explain why a flash read can cost extra cycles while an SRAM read usually does not.

Where code and data are stored

Lesson 31 introduced the core's registers, lesson 34 showed an interrupt writing a frame to memory, and lesson 35 placed the stacks in RAM. All of them assumed that the core can read and write memory without saying what that memory is made of or how long a read takes, and this lesson fills that gap. Lesson 37 then shows the wires that carry each access, and lesson 41 how the linker decides where each object goes.

The underlying problem is timing. A 3D printer's motion code computes step times many thousands of times a second, and if the code doing the arithmetic is stored in flash and runs through a slow path, each step can take longer than planned, so the printer skips steps or moves unevenly. Engineers on such a product must quickly answer where a piece of code or data lives and what one access to it costs, and this lesson provides the vocabulary and facts to answer both for the two chips in this course.

Volatile and non-volatile memory

Memory is either volatile, losing its contents when power is removed, or non-volatile, keeping them. In a microcontroller the fast read-write memory is SRAM, which is volatile, while the program's code and constant data sit in flash, which is non-volatile. The two also differ in how they are written: SRAM accepts single words at the speed of an ordinary bus write, whereas flash is written in larger blocks after an erase, which is slow, so the program is stored in flash and its variables are kept in SRAM.

Levels of the memory hierarchy

A Cortex-M core works on its registers, and everything else it reads or writes comes from memory over the bus. That memory forms a hierarchy, with a few registers inside the core at the top, fast read-write SRAM below them, and below that flash, which is non-volatile, mostly read and slower. Some chips add a cache between the core and the flash, a small fast copy of recently used flash. Each level trades size for speed, and the arrangement works because most reads hit the upper levels. This is the classic memory hierarchy of computer architecture, with its trade-off between capacity, latency and cost. Microcontrollers keep it but drop the large off-chip DRAM level.

Studying with books gives a similar picture. The open page in front of you is a register, the books on your desk are SRAM and the library across town is the external flash, while a cache is the habit of keeping recently used books on the desk, so that most lookups never require the trip. A miss is the day the needed book is still in town. Unlike a library trip, though, a miss costs a fixed and fairly small number of cycles, which the next sections put into numbers.

Wait states

When a memory cannot return data as fast as the core requests it, the core waits, and the extra clock cycles are called wait states. A wait state is normal, the bus telling the core that the answer is not ready yet. A memory with no wait states answers in the cycle the core asks, and each wait state adds one cycle to the access; lesson 37 shows where the bus adds cycles of its own.

Cache hits, misses and associativity

A cache stores copies of recently read data. When the core asks for an address, the cache either holds the data, a hit, or does not, a miss; a hit is fast, while a miss goes out to the slow memory, fetches the data and keeps a copy for next time. The average cost of an access therefore depends on how often the cache hits, not only on the cost of a hit.

A cache can be set-associative, meaning each address maps to one set of entries but can sit in any of a few ways within that set. A two-way set-associative cache has two entries per set and checks both on each lookup. The RP2040's XIP cache is two-way, so two flash addresses that map to the same set can both stay cached, and the datasheet gives its size and hit cost while describing the miss path only as an external serial access.

Execute in place

The RP2040 keeps its program in external flash and reaches it through execute in place (XIP). The datasheet explains that "bus reads to a 16MB memory window starting at 0x10000000 are translated into a serial flash transfer, and the result is returned to the master that initiated the read", so the core can run code from that window without copying it to RAM first. The XIP cache sits in front of the flash and serves recently read code.

The memories of the RP2040

The RP2040 has two kinds of on-chip memory. The 16 kB ROM holds the boot code; the datasheet says it "offers single-cycle read-only bus access" and that attempting to write to it "has no effect (no bus fault is generated)" (section 2.6.1). The 264 kB SRAM is "physically partitioned into six banks", four of 64 kB and two of 4 kB, but "software may treat it as a single 264kB memory region" (section 2.6.2). Program flash is not on the chip at all but in an external serial flash chip on the QSPI interface, reached by the XIP hardware.

The XIP cache is 16 kB, "two way set-associative, 1 cycle hit" (section 2.6.3.1), and the datasheet adds that it "only affects accesses to XIP flash, so software does not have to consider cache coherence, unless performing flash programming operations". That single exception matters later in this lesson. The cache has no effect on RAM, which is why RAM accesses are always fast.

The memories of the STM32F103

The STM32F103 has its code flash at 0x08000000 and its SRAM at 0x20000000, as the ST device header defines them (FLASH_BASE and SRAM_BASE in stm32f103xb.h), in agreement with RM0008 Rev 21, whose section 3.3.1 gives the SRAM start address as 0x2000 0000 and section 3.3.3 the start of main Flash memory as 0x0800 0000. It has neither an XIP window nor a flash cache, and the Blue Pill's linker script gives 64 kB of flash and 20 kB of SRAM (templates/common/stm32f103c8.ld). The core fetches code directly from flash, so the number of wait states, set by the flash controller, matters.

Flash cannot keep up with the core at high clock speeds, so the flash controller inserts wait states according to the LATENCY field of FLASH_ACR, which the header defines as three bits, FLASH_ACR_LATENCY with mask 0x7, and RM0008 Rev 21 (section 3.3.3) places in bits 2:0. The ST HAL raises the latency before raising the clock: the comment in stm32f1xx_hal_rcc.c reads "Increasing the number of wait states because of higher CPU frequency", and the code sets the latency first and then checks it, lowering it only after the clock has been lowered. The rule runs one way, since a faster clock needs more wait states and they must be set first.

The HAL also states the top speed, a maximum SYSCLK and HCLK frequency of 72 MHz for an STM32F10xxx (stm32f1xx_hal_rcc.c, the clock configuration notes), and RM0008 Rev 21 agrees, giving 72 MHz in section 7.2 as the maximum for the AHB domain that carries HCLK. The header names the latency values FLASH_LATENCY_0, FLASH_LATENCY_1 and FLASH_LATENCY_2, and RM0008 Rev 21, section 3.3.3, gives the clock range for each under the LATENCY bits of FLASH_ACR: 000 (zero wait states) for SYSCLK up to 24 MHz, 001 (one wait state) above 24 MHz up to 48 MHz, and 010 (two wait states) above 48 MHz up to 72 MHz. Check these bands against your own copy of the manual in lab 2 and lesson 43.

The STM32F1 also has a prefetch buffer, enabled by the PRFTBE bit of FLASH_ACR, which the device header calls "Prefetch Buffer Enable". RM0008 Rev 21, section 3.3.3, confirms that PRFTBE is bit 4, that the buffer is enabled after reset and that the prefetch block serves instruction fetches over the ICode bus. By fetching instructions ahead of the core, it hides some of the flash delay on straight-line code, although it is not a full data cache.

Memory placement of C objects

The compiler and the linker decide where each object goes, as lesson 41 shows. They group the object's bytes into sections, and the linker script assigns each section to a region according to a rule that is the same on both chips.

C objectWhere it lives at run timeSection
const uint32_t table[4]Flash (read-only).rodata
uint32_t counter = 7;SRAM. The value 7 is stored in flash and copied to SRAM at startup..data
uint32_t zeroed;SRAM, cleared to 0 at startup.bss
A local variableSRAM, on the stackstack
The code of main()Flash (executed in place).text
The initialised global is the tempting mistake: its starting value sits in flash, but the variable itself lives in SRAM and is writable.

Worked example: the average cost of a flash read

The datasheet gives the hit cost of one cycle but not the miss cost, so the numbers below are an illustration chosen to show the arithmetic rather than a measurement or a datasheet value. Suppose a hit takes 1 cycle and a miss 20 cycles. With a fraction h of reads hitting, the average cost per read is

average = h × 1 + (1 − h) × 20(1)

where h is the hit rate between 0 and 1 and the result is in cycles. Before calculating, guess how much worse a 50 % hit rate is than a 95 % one.

  1. At a hit rate of 95 %: 0.95 × 1 + 0.05 × 20 = 0.95 + 1.00 = 1.95 cycles.
  2. At a hit rate of 50 %: 0.5 × 1 + 0.5 × 20 = 10.5 cycles.

The same code with the same cache thus costs more than five times as much when the cache misses half the time, and the hit rate depends on the code: a tight loop that fits in the cache is fast, while a long sequence of different functions can miss again and again.

Step through each access pattern, predicting hit or miss before each press, then switch the same pattern between direct-mapped, 2-way and 4-way and compare the hit rates. The two collision patterns show why the XIP cache has two ways.

The simulator run for this lesson printed the same numbers, with the const table at 0x080004B8 and the counter at 0x20000000. The function show_regions printed as 0x08000271 while the map places its code at 0x08000270, and the extra 1 is the Thumb bit: a function's address in C has bit 0 set to mark Thumb code, while the code itself starts at the even address.

The demo code line by line

The demo's show_regions function is short, and each line makes one point about where things live. 

static const uint32_t flash_table[4] = { 1U, 2U, 3U, 4U };  /* .rodata: stays in flash */
static uint32_t ram_counter = 7U;                            /* .data: copied to SRAM at startup */
static uint32_t ram_zeroed;                                  /* .bss: cleared to 0 in SRAM */

static void show_regions(void) {
    uint32_t stack_local = 9U;   /* lives on the stack, in SRAM */
    print_line("const table (flash):  ", (uint32_t)(uintptr_t)flash_table);
    print_line("global counter (RAM): ", (uint32_t)(uintptr_t)&ram_counter);
    print_line("zeroed global  (RAM): ", (uint32_t)(uintptr_t)&ram_zeroed);
    print_line("stack local    (RAM): ", (uint32_t)(uintptr_t)&stack_local);
    print_line("main() code   (flash):", (uint32_t)(uintptr_t)show_regions);
}

The first line declares the table const, so the compiler places it in the read-only .rodata section, which the linker puts in flash after the code. The static keyword keeps the name local to the file, following the course's rule for helpers.

The second line is an initialised global with a starting value of 7, so the compiler puts it in .data, and the linker gives it a run-time address in SRAM and a load address in flash. The third line has no initialiser and goes in .bss, which takes space in SRAM but stores no value in flash, because startup zeroes it.

Inside the function, uint32_t stack_local = 9U; creates a local, which has no linker-chosen address but lives on the stack in SRAM and disappears when the function returns. The print_line calls take the addresses of these objects, each cast in two steps: uintptr_t is an integer type large enough to hold a pointer, so the first cast turns the pointer into an integer and the second gives the uint32_t that print_line expects. The & operator takes an address, while a function name such as show_regions yields the function's address without it.

The linker script puts these rules into effect. Its line .data : { ... } > RAM AT> FLASH gives the section a run-time address in RAM, the > RAM part, and stores its bytes in flash, the AT> FLASH part. The symbol _sidata is the flash address of those stored bytes and _sdata the start of the section in RAM, and the startup code copies one to the other before main runs, at the LoopCopyDataInit label in startup_stm32f103xb.s. The same file zeroes .bss between _sbss and _ebss, then calls SystemInit and finally main.

You can say for any C object in a Pico or Blue Pill program which memory it lives in and why, and you know the case in which an apparently simple read costs several cycles.

Common mistakes and how to spot them

An initialised global thought to be in flash

RAM fills faster than expected, and the linker reports that the RAM region is full. Someone who reads uint32_t counter = 7; as a constant may make a large table writable without considering RAM, yet every initialised global takes SRAM as well as a copy in flash, and the map file shows which sections use the space. Declare read-only objects const, and check the .data and .bss sizes in the map after each change.

A local expected to start at zero

A counter starts at a different value on each run, or after a change in another function. A global without an initialiser is cleared at startup, but a local lives on the stack and starts with whatever the stack held before. Initialise every local where it is declared, as stack_local = 9U does above.

A pointer to a local returned

A value is correct when read at once and wrong after the next call. The address of stack_local is on the stack near the top of SRAM, and once show_regions returns, the next function call can reuse that space, so a returned &stack_local may later point at different data. Return a value instead, or pass in a buffer the caller owns.

The clock raised without the wait states

A program works at the low clock and fails only at the higher one, often depending on which instruction is fetched. With the latency still at its old value, a faster clock asks the flash for data faster than it can supply it, which is why the HAL sets the latency first. Write the LATENCY field of FLASH_ACR before the clock change, as the HAL does, and read it back to check.

Flash written while running from it

The program crashes right after a flash write. On the RP2040 code runs from flash through the XIP cache, and although software normally need not consider cache coherence, flash programming is the stated exception: erasing or writing the flash the program runs from can make the core fetch half-written or erased instructions. Keep the flash-writing function in RAM using the Pico SDK macro __not_in_flash_func, defined in pico/platform/sections.h in SDK 2.3.1; lesson 41 covers how a function is placed in a section.

Memory placement in production firmware

Professional firmware engineers read the linker map after every significant change, checking how much RAM and flash each section uses, which functions landed in RAM and whether a large table has accidentally become writable. Time-critical code, such as a motor control loop or a timing-sensitive protocol routine, is often placed in RAM because a RAM access has a fixed and short cost, and frequently run interrupt handlers sometimes go there for the same reason. A code reviewer expects read-only data to be declared const and any change to the linker script or startup code to be explained in the commit message.

Summary

  • Volatile memory loses its contents without power: SRAM is volatile and fast, while flash is non-volatile and mostly read.
  • A cache keeps copies of recently read flash; on the RP2040 XIP cache a hit costs one cycle and a miss goes out to the external flash.
  • The RP2040 has 264 kB of SRAM in six banks, 16 kB of ROM and a 16 MB XIP window at 0x10000000.
  • The STM32F103 has code flash at 0x08000000 and SRAM at 0x20000000, and the Blue Pill has 64 kB of flash and 20 kB of SRAM.
  • Initialised globals occupy SRAM with starting values stored in flash for startup to copy, uninitialised globals are zeroed, and locals live on the stack without being zeroed.
  • The LATENCY field of FLASH_ACR sets the flash wait states, raised before the clock goes up and lowered after it comes down.
  • Never write flash while running from it, and keep flash-writing code in RAM.
RP2040 datasheet: read section 2.6 (Memory), especially 2.6.1 (ROM), 2.6.2 (SRAM, with the striped banks in Table 153), 2.6.3 (Flash) and 2.6.3.1 (XIP Cache). Section 2.6.3.1 lists the XIP aliases from 0x10 to 0x15, and section 2.6.2.1 says the cache becomes 16 kB of RAM at 0x15000000 when it is disabled.
