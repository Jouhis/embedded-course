Memory hierarchy: SRAM, flash, caches, and XIP

Your program does not run from the place it was stored. Knowing where each object lives, and what a slow read costs, is the first step to explaining firmware timing.

By the end of this lesson you can name the memory region that holds each kind of C object on an RP2040 or an STM32F103, and explain why a flash read can cost extra cycles while an SRAM read usually does not.

Where we are and why it matters

Lesson 31 introduced the core's registers, and lesson 34 showed that an interrupt writes a frame to memory. Lesson 35 put the stacks in RAM. Every one of those lessons assumed that the core could read and write memory, without saying what that memory was made of or how long a read takes. This lesson fills that gap. The next lesson, 37, shows the wires that carry each access, and lesson 41 shows how the linker decides where each object goes.

The problem is a timing one. A 3D printer's motion code computes step times many thousands of times a second. If the code that does the arithmetic is stored in flash and runs through a slow path, each step can take longer than planned. The printer then skips steps or moves unevenly. Engineers on such a product need to answer two questions quickly. Where does this code and this data live? And what does one access cost? This lesson gives you the vocabulary and the facts to answer both, for the two chips in this course.

The concepts, one at a time

Volatile and non-volatile memory

Memory is either volatile or non-volatile. Volatile memory loses its contents when power is removed. Non-volatile memory keeps them. In a microcontroller, the fast read-and-write memory is SRAM, and it is volatile. The program's code and its constant data sit in flash, which is non-volatile. The two kinds also differ in how they are written. SRAM can be written one word at a time, at the speed of an ordinary bus write. Flash is written in larger blocks, after erasing, which is slow. This is why the program is stored in flash and its variables are kept in SRAM.

The hierarchy: fast and small, slow and large

A Cortex-M core works on its registers. Everything else it reads or writes comes from memory on the same bus. Memory is a hierarchy. At the top are a few registers inside the core. Below them is SRAM, fast and read-write. Below that is flash, non-volatile, read mostly, and slower to read. Some chips add a cache, a small fast copy of recently used flash, between the core and the flash. Each level trades size for speed, and the hierarchy works because most reads hit the top levels. Architecture students will recognise this as the classic memory hierarchy, with the trade-off between capacity, latency and cost. Microcontrollers keep it but drop the large off-chip DRAM level.

Wait states

When a memory cannot return data as fast as the core asks for it, the core waits. The extra clock cycles are called wait states. A wait state is not a bug. It is the bus telling the core that the answer is not ready yet. A memory with no wait states answers in the cycle the core asks. Each wait state adds one cycle to that access. Lesson 37 shows where the bus adds its own cycles.

Cache, and how a hit differs from a miss

A cache stores a copy of recently read data. When the core asks for an address, the cache either has the data (a hit) or does not (a miss). A hit is fast. A miss goes out to the slow memory, fetches the data, and keeps a copy for next time. The average cost of an access depends on how often the cache hits, not on the hit cost alone.

A cache can be set-associative. Each address maps to one set of entries, and within that set the address can sit in any of a few ways. A two-way set-associative cache has two entries per set, so the cache checks two entries on each lookup. The RP2040's XIP cache is two-way, which means that two flash addresses that map to the same set can both stay cached. The datasheet gives its size and its hit cost, and it describes the miss path only as an external serial access.

Execute in place

The RP2040 keeps its program in external flash. The chip reaches that flash through execute in place (XIP). The datasheet explains that "bus reads to a 16MB memory window starting at 0x10000000 are translated into a serial flash transfer, and the result is returned to the master that initiated the read", so the core can run code from that window without first copying it to RAM. The XIP cache sits in front of the flash, so recently read code is served from the cache.

The RP2040 memory, with the datasheet's numbers

The RP2040 has two kinds of memory on the chip. The ROM is 16 kB and holds the boot code. The datasheet says the ROM "offers single-cycle read-only bus access", and that attempting to write to it "has no effect (no bus fault is generated)" (section 2.6.1). The SRAM is 264 kB. The datasheet says it is "physically partitioned into six banks", but "software may treat it as a single 264kB memory region" (section 2.6.2). Four of the banks are 64 kB each, and two are 4 kB each. Program flash is not on the chip. It is an external serial flash chip on the QSPI interface, which the XIP hardware reaches.

The XIP cache is 16 kB, "two way set-associative, 1 cycle hit" (section 2.6.3.1). The datasheet also says that the cache "only affects accesses to XIP flash, so software does not have to consider cache coherence, unless performing flash programming operations". That single exception matters later in this lesson. The cache has no effect on RAM, which is why RAM is always fast.

The STM32F103 memory, from its header

The STM32F103 has its code flash at 0x08000000 and its SRAM at 0x20000000, as the ST device header defines them (FLASH_BASE and SRAM_BASE in stm32f103xb.h). It has no XIP window and no cache for flash. The Blue Pill's linker script gives 64 KB of flash and 20 KB of SRAM (templates/common/stm32f103c8.ld). The core fetches code from flash directly, so the number of wait states matters, and the flash controller sets that number.

Flash is slower than the core at high clock speeds, so the flash controller inserts wait states. The number of wait states is set by the LATENCY field of FLASH_ACR, which the header defines as three bits, FLASH_ACR_LATENCY with mask 0x7. The ST HAL raises the latency before it raises the clock. The comment in stm32f1xx_hal_rcc.c reads "Increasing the number of wait states because of higher CPU frequency", and the code sets the latency first and then checks it. The HAL lowers the latency only after it has lowered the clock. The rule is one-way: more clock needs more wait states, and you must set them first.

The HAL's header also gives the top speed. It says that for an STM32F10xxx the maximum frequency of SYSCLK and HCLK is 72 MHz (stm32f1xx_hal_rcc.c, the clock configuration notes). The header names the latency values FLASH_LATENCY_0, FLASH_LATENCY_1 and FLASH_LATENCY_2, but the clock frequency at which each one is needed is in the reference manual, RM0008. This course has not yet checked that table against the vendor's text, so do not quote thresholds from memory. You will find the table yourself in lab 2 and lesson 43.

The STM32F1 also has a prefetch buffer, enabled by the PRFTBE bit of FLASH_ACR. The device header names it "Prefetch Buffer Enable". It fetches instructions ahead of the core, which hides some of the flash delay on straight-line code. It is not a full cache of data.

Where your objects live

The compiler and the linker decide where each object goes (lesson 41 shows how). They group the object's bytes into sections, and the linker script says which region each section goes to. The rule is simple, and it is the same on both chips:

C objectWhere it lives at run timeSection
const uint32_t table[4]Flash (read-only).rodata
uint32_t counter = 7;SRAM. The value 7 is stored in flash and copied to SRAM at startup..data
uint32_t zeroed;SRAM, cleared to 0 at startup.bss
A local variableSRAM, on the stackstack
The code of main()Flash (executed in place).text
An initialised global is the tempting mistake. Its starting value sits in flash, but the variable itself lives in SRAM, and it is writable.

A worked example with real numbers

Two calculations show how this works in practice. The first is the cost of an access through the XIP cache. The second is the memory map of a real build, which you can check on your own machine.

The average cost of a flash read

The datasheet gives the hit cost, one cycle, but not the miss cost. So the numbers below are an illustration, chosen to show the arithmetic. They are not a measurement and they are not a datasheet value. Suppose a hit takes 1 cycle and a miss takes 20 cycles. If a fraction h of the reads hit, the average cost per read is:

average = h × 1 + (1 − h) × 20

At a hit rate of 95 per cent, the average is 0.95 × 1 + 0.05 × 20 = 0.95 + 1.00 = 1.95 cycles. At a hit rate of 50 per cent, the average is 0.5 × 1 + 0.5 × 20 = 10.5 cycles. The same code, with the same cache, costs more than five times as much when the cache misses half the time. This is why the hit rate depends on the code. A tight loop that fits in the cache is fast. A long sequence of different functions can miss again and again.

The map gives the RAM region as 0x20000000 with a length of 0x5000, which is 20 KB, so the RAM ends at 0x20005000. The stack local at 0x20004FEC is within the last 20 bytes of that region, which is what you expect from a stack that starts at the top of RAM and grows down. The .data section is 8 bytes long, holding ram_counter and the SystemCoreClock variable from the startup code. Its load address, 0x080004E0, is where the starting values are stored in flash, after the read-only data.

The simulator run for this lesson printed the same numbers. The const table is at 0x080004B8 and the counter is at 0x20000000. The function show_regions printed as 0x08000271, and the map places its code at 0x08000270. The extra 1 is the Thumb bit. A function's address in C has bit 0 set to mark Thumb code, and the code itself starts at the even address.

The code, explained line by line

The demo's show_regions function is short, and each line makes one point about where things live. 

static const uint32_t flash_table[4] = { 1U, 2U, 3U, 4U };  /* .rodata: stays in flash */
static uint32_t ram_counter = 7U;                            /* .data: copied to SRAM at startup */
static uint32_t ram_zeroed;                                  /* .bss: cleared to 0 in SRAM */

static void show_regions(void) {
    uint32_t stack_local = 9U;   /* lives on the stack, in SRAM */
    print_line("const table (flash):  ", (uint32_t)(uintptr_t)flash_table);
    print_line("global counter (RAM): ", (uint32_t)(uintptr_t)&ram_counter);
    print_line("zeroed global  (RAM): ", (uint32_t)(uintptr_t)&ram_zeroed);
    print_line("stack local    (RAM): ", (uint32_t)(uintptr_t)&stack_local);
    print_line("main() code   (flash):", (uint32_t)(uintptr_t)show_regions);
}

The first line declares the table const. The compiler places a read-only object in the .rodata section, and the linker puts that section in flash, after the code. The static keyword keeps the name local to this file, which is the course's rule for helpers.

The second line is an initialised global. It has a starting value of 7, so the compiler puts it in .data. The linker gives it a run-time address in SRAM and a load address in flash. The third line has no initialiser. It goes in .bss, which takes space in SRAM and has no value stored in flash, because startup zeroes it.

The function's first line, uint32_t stack_local = 9U;, creates a local. A local has no fixed address that the linker chooses. It lives on the stack, which is in SRAM, and it disappears when the function returns. The print_line calls take the addresses of these objects. Each address is cast in two steps. uintptr_t is an integer type that is large enough to hold a pointer, so the first cast turns the pointer into an integer, and the second cast gives the uint32_t that print_line expects. The & operator takes an address, and the name of a function, such as show_regions, gives the function's address without the operator.

The linker script puts the rules into effect. The line .data : { ... } > RAM AT> FLASH says two things. The section's run-time address is in RAM, which is the > RAM part. Its stored bytes are in flash, which is the AT> FLASH part. The symbol _sidata is the flash address of those stored bytes, and _sdata is the start of the section in RAM. The startup code copies one into the other before main runs. Its LoopCopyDataInit label is in startup_stm32f103xb.s, and the same file zeroes .bss between _sbss and _ebss, then calls SystemInit and then main.

Common mistakes and how to spot them

1. Thinking an initialised global is in flash

The warning above describes this mistake, and it has a cost. A beginner who sees uint32_t counter = 7; and believes it is a constant may make a large table writable without thinking about RAM. Every initialised global takes SRAM as well as a copy in flash. The symptom is a build where RAM fills up faster than expected, and the linker reports that the RAM region is full. The map file shows which sections use the space. The fix is to make the object const when it is read-only, and to check the .data and .bss sizes in the map after each change.

2. Expecting a local variable to start at zero

A global with no initialiser is cleared at startup. A local is not. It lives on the stack, and it starts with whatever value the stack held before. The symptom is a counter that starts at a different value on each run, or after a change in another function. The fix is to initialise every local when you declare it, as stack_local = 9U does above, so that the value is never left to chance.

3. Returning a pointer to a local

The address of stack_local is an address on the stack, near the top of SRAM. When show_regions returns, that space can be reused by the next function call. A function that returns &stack_local gives its caller an address that may later hold different data. The symptom is a value that is correct when read at once and wrong after the next call. The fix is to return a value, or to pass in a buffer that the caller owns.

4. Raising the clock without raising the wait states

The clock and the flash latency have to move together, and the HAL sets the latency first for that reason. A program that raises the clock with the latency still at its old value asks the flash for data faster than the flash can supply it. The symptom is a program that works at the low clock and fails only at the higher one, often in a way that depends on which instruction is fetched. The fix is to write the LATENCY field of FLASH_ACR before the clock change, as the HAL does, and to read it back to check.

5. Writing flash while running from it

On the RP2040, code runs from the flash through the XIP cache. The datasheet says software does not normally need to think about cache coherence, but flash programming is the exception. If a program erases or writes the flash it is running from, the core can fetch half-written or erased instructions. The symptom is a crash that happens right after the write. The fix is to keep the flash-writing function in RAM. The Pico SDK provides a macro for this, __not_in_flash_func, which places a function in RAM (its definition is in pico/platform/sections.h, SDK 2.3.1). Lesson 41 covers how a function is placed in a section.

In real projects

Professional firmware engineers read the linker map after every significant change. They check how much RAM and flash each section uses, which functions landed in RAM, and whether a large table has accidentally become writable. Time-critical code, such as a motor control loop or a timing-sensitive protocol routine, is often placed in RAM, because a RAM access has a fixed and short cost. Interrupt handlers that run often are sometimes placed there for the same reason. A code reviewer asks for two things: that read-only data is declared const, and that any change to the linker script or the startup code is explained in the commit message.

Interviewers ask about this area because it shows whether you understand the cost of an access. The question at the end of this lesson, about XIP, is a common one. A good answer names the cache, says that a hit is fast and a miss is slow, and explains that the average depends on the hit rate. It also mentions that RAM does not go through the cache, and so its cost is steady.

Summary

  • Volatile memory loses its contents when power is removed. SRAM is volatile and fast. Flash is non-volatile and read mostly.
  • A cache keeps copies of recently read flash. A hit costs one cycle on the RP2040 XIP cache, and a miss goes out to the external flash.
  • The RP2040 has 264 kB of SRAM in six banks, 16 kB of ROM, and a 16 MB XIP window at 0x10000000.
  • The STM32F103 has code flash at 0x08000000 and SRAM at 0x20000000. The Blue Pill has 64 KB of flash and 20 KB of SRAM.
  • Initialised globals occupy SRAM and have a starting value stored in flash, which startup copies. Uninitialised globals are zeroed. Locals live on the stack and are not zeroed.
  • The FLASH_ACR LATENCY field sets the flash wait states. Raise it before the clock, and lower it after the clock falls.
  • Do not write flash while you are running from it. Keep flash-writing code in RAM.
You can say, for any C object in a Pico or Blue Pill program, which memory it lives in and why, and you know the one case where an apparently simple read costs several cycles.

"What is execute in place, and why can a flash read make a program slower than the same code in SRAM?" Answer out loud in 60 seconds, then compare.

Model answer

Execute in place means the core fetches instructions straight from a memory-mapped flash window, with no copy to RAM. The flash is external and serial on the RP2040, so a read that misses the XIP cache must go out over the serial interface, and that takes far longer than an SRAM access. A cache hit costs one cycle, so the average speed depends on how often the code hits the cache. RAM does not go through the cache, so its cost is steady. Code that is critical for timing is often copied to or placed in RAM for that reason.

RP2040 datasheet: read section 2.6 (Memory), especially 2.6.1 (ROM), 2.6.2 (SRAM, with the striped banks in Table 153), 2.6.3 (Flash) and 2.6.3.1 (XIP Cache). Section 2.6.3.1 lists the XIP aliases from 0x10 to 0x15, and section 2.6.2.1 says the cache becomes 16 kB of RAM at 0x15000000 when it is disabled.
