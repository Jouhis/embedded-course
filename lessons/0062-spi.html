SPI

A clocked four-wire bus for fast peripherals

By the end of this lesson you can set the SPI clock polarity and phase for a device, compute the SPI bit rate from the SDK's divider, drive a 74HC595 with spi_write_blocking() and a latch pin, and compare bit-bang and hardware timing in a logic-analyzer capture.

The third common serial bus

Lesson 25 built a shift register from flip-flops and then drove a 74HC595 from the Pico by setting a data pin and a clock pin in a loop. Lesson 60 introduced I2C, which needs only two wires but spends bits on addresses and acknowledges, and lesson 61 sent a 1 024-byte picture to a display over I2C at about 25 ms per frame.

Many other parts are built around the third common bus, SPI, among them flash memory chips, ADCs, sensors, SD cards in SPI mode and display controllers, and even the SSD1306 of lesson 61 has a 4-wire SPI interface. SPI has no addresses and no acknowledge bits, so every clock pulse carries data, and since firmware engineers meet it on most boards, the questions in this lesson come up often.

The four SPI wires and full-duplex shifting

SPI, the Serial Peripheral Interface, connects one master to one or more devices with four wires. The master generates the clock on SCK (serial clock), MOSI (master out, slave in) carries bits from the master to the device and MISO (master in, slave out) carries bits back, while the fourth wire, chip select (CS), is pulled low by the master to tell the device to listen. Devices that only receive data have no MISO.

SPI is full duplex, each clock pulse moving one bit from the master to the device and one from the device to the master. Each side contains a shift register holding the byte it sends, and after eight pulses the two registers have swapped contents, so the arrangement forms a ring of shifts in which the bits move one place per clock and the byte that leaves one side enters the other.

In this course the data order is most significant bit first, so bit 7 of the byte goes out first. The Pico's SPI peripheral can shift only in that order, which the SDK enforces in spi_set_format(), so a device needing the other order has its bytes reversed in software.

SPI resembles two people swapping cards across a table, one card per beat of a metronome: on each beat both slide a card across at the same moment, so after eight beats each holds the other's eight cards. Neither can receive without sending, so to read a byte from a device the master sends one too, often a dummy 0x00 or 0xFF. The picture breaks with devices that have no MISO wire, where the master's cards go across and nothing comes back.

Clock polarity and phase

Two settings matter for every SPI device, clock polarity and clock phase. Polarity, CPOL, is the level at which the clock rests between transfers, 0 meaning low and 1 high, and phase, CPHA, selects the clock edge on which the device samples its input, the first edge being the first change away from the idle level and the second the change back. Sampling means reading the input pin at that instant, so the value must be stable then.

The RP2040 datasheet names these bits SPO for clock polarity and SPH for clock phase, SPO = 0 holding the clock low when idle, SPH = 0 capturing data on the first clock edge and SPH = 1 on the second RP2040 datasheet, sections 4.4.3.9.1 (SPO) and 4.4.3.9.2 (SPH). Combining the two bits gives four modes.

The master and the device must agree on the mode, which the device's datasheet states. SPI has no handshake, so the master cannot detect a mismatch by itself, and a mismatch shows up only as wrong data, which is why the mode is the first thing to check in a bad SPI capture.

The 74HC595 shift and storage clocks

Three inputs of the 74HC595 matter here: DS is the serial data input, SHCP the shift clock, on whose low-to-high transition the bit on DS moves into the shift register, and STCP the storage clock, whose low-to-high transition copies the shift register into the eight output latches. The outputs drive the LEDs, so they change only when STCP rises onsemi MC74HC595A datasheet, pin descriptions for A, Shift Clock and Latch Clock, and the chip has no separate chip-select pin.

The data bit must be stable when SHCP rises, so the 595 samples on the rising edge, which with the clock idle low is the first edge. That is CPOL = 0 and CPHA = 0, mode 0, the mode the project uses, and since the SDK's spi_init() sets mode 0 by default, the solution keeps it.

The project wires GP19 to DS, GP18 to SHCP and GP17 to STCP, using the latch on GP17 as the chip select, low before a byte and high after it. What matters for this chip is the rising edge of STCP, which copies the shift register to the outputs, while a low level on STCP does nothing, so holding it low during the transfer is safe, and the rising edge after the last bit is the moment the new pattern appears on the LEDs.

The SPI bit-rate divider

The SPI clock, SSPCLKOUT in the datasheet, is made by dividing the peripheral clock, clk_peri, by two integers, the prescale, an even number from 2 to 254, and the post-divide, from 1 to 256, stored as one more than the register value SCR RP2040 datasheet, section 4.4.3.6.1, bit rate generation. The bit rate is therefore

fSCK = fperi ÷ (CPSDVSR × (SCR + 1))(1)

where fperi is clk_peri, CPSDVSR the prescale and SCR + 1 the post-divide. The datasheet's own example takes a 125 MHz peripheral clock with a prescale of 2, which gives a range up to 62.5 MHz.

With the SDK's default clocks clk_peri runs at 125 MHz, and the divider is not normally set by hand: the code asks for a rate and the SDK finds the divider. spi_init() calls spi_set_baudrate(), which searches for the prescale and the post-divide in two loops, writes both to the registers and returns the rate it actually set, the value to trust. The search is in the SDK source at pico-sdk, hardware_spi/spi.c, lines 42 to 74, with the two loops at lines 51 to 64.

Because the divider is a whole number, the SDK does not always hit the requested rate, which is why the function returns a value, and the solution prints it as at %u Hz so that the rate really set is visible.

Worked example: a 1 MHz request

We take a 125 MHz clk_peri and ask for 1 000 000 Hz, following the two loops of spi_set_baudrate(). Before reading on, predict whether the rate returned will be exactly 1 MHz, slightly above or slightly below.

  1. Find the prescale. The first loop finds the smallest prescale that puts the output in range, testing whether clk_peri is below prescale × 256 × requested rate. For prescale 2 the right side is 2 × 256 × 1 000 000 = 512 000 000, more than 125 000 000, so the loop stops at prescale 2.
  2. Step down the post-divide. The second loop starts at 256 and steps down, testing 125 000 000 ÷ (2 × (post − 1)) and stopping at the first post-divide where the result exceeds 1 000 000. At 64 the test gives 125 000 000 ÷ 126 = 992 063, not above 1 000 000, so the loop continues, and at 63 it gives 125 000 000 ÷ 124 = 1 008 064, above 1 000 000, so the loop stops with a post-divide of 63.
  3. Compute the rate. Equation (1) gives 125 000 000 ÷ (2 × 63) = 992 063 Hz, with SCR = 62 in the register.

A request for 1 MHz therefore returns 992 063 Hz, about 0.8 % slower, which matches the datasheet's arithmetic and is why the returned value should be read. These numbers come from reading the SDK code, not from a measured run.

Bit-bang and hardware SPI compared

Bit-bang means the CPU drives the pins itself, one GPIO write at a time, sending a bit by putting the data on MOSI, raising SCK and lowering it again. Each step is an instruction and the delays in the code set the clock speed, so the method works with any pins, but the clock is only as steady as the code, and interrupts or other work can stretch any bit. Lesson 25 used this method.

Hardware SPI moves that work into the peripheral. The RP2040 has two SPI controllers based on the ARM PrimeCell SSP (PL022) design RP2040 datasheet, section 4.4, each with an 8-entry transmit FIFO, a small hardware queue of bytes waiting to be shifted RP2040 datasheet, section 4.4.1. The CPU writes a byte into the FIFO and the controller shifts it out with an evenly spaced clock, so the CPU does no per-bit work and can do other things while the bits go out, checking the busy flag, which spi_is_busy() reports, only when it needs the bus to be idle.

Worked example: one byte through the 74HC595

The chase in this lesson sends the bytes 0x01, 0x02, 0x04 and so on, one per LED, and we follow the first, 0x01, or 0000 0001 in binary, assuming the shift register starts at zero. Before tracing it, predict on which edge the first LED lights.

  1. Order the bits. With MSB first the bits leave as 0, 0, 0, 0, 0, 0, 0, 1, and the first seven do not show on the LEDs, because the outputs stay unchanged until the latch rises.
  2. Shift them in. On each rising edge of SHCP the chip takes the bit on DS into the shift register and pushes the older bits one place along, so after the seventh edge the register holds seven zeros with the last bit still to come, and after the eighth it holds 0000 0001, while the LEDs still follow only the storage register.
  3. Latch the result. The latch goes low before the byte starts and high after the last bit, so the rising edge of STCP at the end copies 0000 0001 to the output latches and Q0 lights the first LED.
  4. Stream the next byte. The next byte, 0x02, follows the same steps, its bits passing through the shift register while the old pattern still shows on the LEDs, which is how the chip can stream bytes and still show a clean pattern.

The timing is where the two methods differ. Bit-bang makes two sleep_us(1) calls per bit, so eight bits take at least 2 × 8 × 1 = 16 µs before the GPIO writes are counted, whereas hardware SPI at 992 063 Hz takes 8 ÷ 992 063 = 8.06 µs of clock per byte. The solution measures both with time_us_32() and prints the two times, so the gap shows on the serial monitor.

The widget below sends the first byte of the chase, 0x01, and marks the edges on which the device samples MOSI. Set the device to expect another mode and compare: mode 1 reads 0x03, because its edges fall where the master changes the data, while mode 3 happens to read the byte correctly, because it samples on the same rising edge.

The SPI code line by line

The excerpts come from the reference solution, starting with the bit-bang byte, the reference that the hardware version must match. 

static void bitbang_byte(uint8_t value) {
    gpio_put(PIN_LATCH, 0);                  /* chip select low: the 595 will shift, not latch */
    for (int bit = 7; bit >= 0; bit--) {
        gpio_put(PIN_MOSI, (value >> bit) & 1u);   /* data settles while SCK is low */
        sleep_us(BIT_US);
        gpio_put(PIN_SCK, 1);                /* rising edge: the 595 samples DS here */
        sleep_us(BIT_US);
        gpio_put(PIN_SCK, 0);
    }
    gpio_put(PIN_LATCH, 1);                  /* rising edge on the latch: outputs change now */
}

The loop runs from bit 7 down to bit 0, MSB first, (value >> bit) & 1u extracting one bit, which goes to MOSI while SCK is still low so that it is stable before the edge. Setting SCK high makes the rising edge on which the 74HC595 samples DS, and setting it low completes the clock period, the two sleep_us() calls being the half-periods, so the whole bit takes about 2 µs. The latch stays low during the transfer and rises at the end, copying the byte to the LEDs. 

static void hw_byte(uint8_t value) {
    gpio_put(PIN_LATCH, 0);
    spi_write_blocking(SPI_PORT, &value, 1);     /* queue one byte and shift it out */
    while (spi_is_busy(SPI_PORT)) {       /* the last bit must leave first */
        tight_loop_contents();
    }
    gpio_put(PIN_LATCH, 1);
}

The sequence is the same as the bit-bang version with one call in the middle, spi_write_blocking(), which sends one byte. The SDK's implementation writes the byte into the FIFO and then waits until the controller's busy flag clears, so the last bit has left the shifter when the call returns pico-sdk, hardware_spi/spi.c, lines 107 to 125, and the explicit spi_is_busy() loop repeats that wait to make the rule visible in the code. The latch goes high only after the wait, because a rising edge on STCP copies whatever the shift register holds at that moment. 

static void pins_to_spi(void) {
    gpio_set_function(PIN_SCK, GPIO_FUNC_SPI);     /* SCK is now driven by SPI0 */
    gpio_set_function(PIN_MOSI, GPIO_FUNC_SPI);    /* MOSI is now driven by SPI0 */
}

A GPIO pin can be an ordinary output or one of a peripheral's functions, and since the bit-bang phase used the first kind, the pins must be switched to the second before the hardware phase. gpio_set_function() changes the pin's multiplexer setting, and the RP2040 datasheet's Table 279 lists GP18 as SPI0 SCK and GP19 as SPI0 TX, the two pins switched here RP2040 datasheet, section 2.19.2, Table 279. GP17 also has an SPI0 chip-select function, but this project drives it as a plain GPIO, so the peripheral never touches it. 

uint actual_hz = spi_init(SPI_PORT, SPI_HZ);      /* returns the rate it actually set */
spi_set_format(SPI_PORT, 8, SPI_CPOL_0, SPI_CPHA_0, SPI_MSB_FIRST);

spi_init() takes the requested rate, sets the divider and enables the peripheral, returning the rate, which the solution stores for printing. spi_set_format() sets 8 bits per frame, the clock polarity and phase and the bit order, the format being mode 0 from the table above, written as CPOL 0 and CPHA 0. The starter sets CPHA 1 here, the bug to fix, and although the SDK's own spi_init() already sets mode 0, the explicit call makes the choice visible.

Try it in Wokwi

The project projects/0062-spi uses the 74HC595 of lesson 25 on the SPI0 pins, SCK on GP18, MOSI on GP19 and the latch on GP17, driven by hand as chip select, while a logic analyser records the three lines on D0 (SCK), D1 (MOSI) and D2 (latch). The solution runs the chase first with bit-bang and then with hardware SPI at 1 MHz, and prints both times.

  1. Open projects/0062-spi/starter in VS Code (File → Open Folder).
  2. Build with Ctrl+Shift+B and start the simulator with F1 → Wokwi: Start Simulator. The bit-bang phase runs first, so the LEDs chase once before the hardware phase starts.
  3. Write hw_byte() to mirror bitbang_byte(), pulling the latch low, sending one byte with spi_write_blocking(), waiting with spi_is_busy() and raising the latch. Then fix the mode, changing the starter's CPHA 1, which is wrong for the 74HC595, to CPHA 0, with a comment naming the edge on which the 595 samples.
  4. The serial monitor should print SPI OK and a line such as 8 bytes: bit-bang ... us, hardware SPI ... us at 992063 Hz, with the LEDs chasing on the hardware path, a bit-bang time of at least 16 µs and a hardware time of about 8 µs.
  5. Stop the simulator, open the capture file wokwi.vcd in PulseView and use the SPI decoder with SCK on D0, MOSI on D1 and CS on D2. The MOSI bytes should read 0x01, 0x02, 0x04 and so on, MSB first, and if the decoder's mode does not match the capture, the bytes come out wrong, the same mismatch as between master and device.

Common mistakes and how to spot them

The wrong SPI mode

The chase looks shifted or stops being a clean one-LED pattern, and the logic analyser shows the data changing on the edge the chip samples, because the starter's CPHA 1 makes the master change MOSI on the rising edge, the very moment the 74HC595 samples it, so the chip reads each bit one step late. Use mode 0 for the 74HC595, and check the mode in the datasheet of every new device before wiring it up.

The latch raised before the last bit has shifted

The LEDs flicker through partial patterns during the chase, or a byte appears one step early, because a rising edge on STCP copies whatever the shift register holds at that moment, so a latch that rises while the last bit is still shifting captures an incomplete byte. Wait for the busy flag to clear before raising the latch, as the spi_is_busy() loop does.

Pins left as plain GPIO after the bit-bang phase

The hardware phase prints SPI OK, but the LEDs stop on the last bit-bang pattern and the logic analyser shows no clock on D0 during the hardware phase, because SCK and MOSI are still ordinary GPIO outputs and the SPI peripheral has no pin to drive. Call pins_to_spi(), which sets both pins to GPIO_FUNC_SPI, before the first hardware byte.

The requested rate used in a timing budget

A timing calculation that assumes 1 MHz comes out about 0.8 % too short, so a tight protocol budget fails by a small margin, while the serial output shows 992063 Hz rather than 1000000 Hz, because the divider is a whole number and spi_init() returns the rate it actually set. Store the return value and use it in every calculation, as the solution does.

SPI device bring-up and decoding in practice

On a real board the first step with any SPI device is the timing section of its datasheet, which names the mode, the largest clock and the rule for the chip select, sampled on a rising edge by some devices and a falling edge by others. Engineers write the mode and the clock limit next to the init code and reviewers check both, so a driver that uses the SDK's returned rate and names the device's mode in a comment passes review quickly.

A logic analyser decodes SPI, but it needs the right mode and the right chip-select polarity to show correct bytes, the same debugging method as in lesson 60 applied to a faster clock. Keep the capture next to the datasheet and check the first byte, because a decoder showing the bytes shifted by one bit almost always has the wrong mode.

Summary

  • SPI uses SCK, MOSI, MISO and chip select, each clock pulse moving one bit each way, so a byte leaves and arrives in eight pulses.
  • CPOL sets the idle clock level and CPHA the edge on which the device samples, together giving modes 0 to 3, with the device's datasheet setting the mode.
  • The 74HC595 shifts on the rising edge of SHCP and copies to its outputs on the rising edge of STCP, so it needs mode 0.
  • The bit rate is clk_peri ÷ (prescale × post-divide), and the SDK searches for both values and returns the rate actually set, such as 992 063 Hz for a 1 MHz request.
  • Bit-bang costs CPU time per bit with timing that depends on the code, while hardware SPI shifts bytes from its 8-entry FIFO with an even clock.
  • SCK and MOSI must be switched to the SPI function before a hardware transfer, and the latch raised only after the busy flag clears.
RP2040 datasheet, section 4.4 (SPI): read 4.4.3.6.1 for the bit rate, 4.4.3.9.1 and 4.4.3.9.2 for the clock polarity and phase, and Table 279 for the SPI0 pins. Then read spi.c in the Pico SDK for the rate calculation, and the 74HC595's pin descriptions for the two clock edges.
