SPI: displays and shift registers

Lesson 25 shifted a byte into a 74HC595 by toggling two pins in software. SPI does the same job in hardware: the peripheral shifts the bits, and the CPU is free until the byte has gone out.

By the end of this lesson you can set the SPI clock polarity and phase for a device, compute the SPI bit rate from the SDK's divider, drive a 74HC595 with spi_write_blocking() and a latch pin, and compare bit-bang and hardware timing in a logic-analyzer capture.

Where we are and why it matters

Lesson 25 built a shift register from flip-flops, then drove a 74HC595 from the Pico by setting a data pin and a clock pin in a loop. Lesson 60 introduced I2C, which needs only two wires but spends bits on addresses and acknowledge bits. Lesson 61 sent a 1 KB picture to a display over I2C, and that took about 25 ms per frame.

Many other parts are built around the third common bus, SPI: flash memory chips, ADCs, sensors, SD cards in SPI mode, and display controllers. The SSD1306 from lesson 61 also has a 4-wire SPI interface. SPI has no addresses and no acknowledge bits, so every clock pulse carries data. Firmware engineers meet it on almost every board, so the questions in this lesson come up on almost every embedded job.

Concept 1: four wires, and each clock pulse moves a bit both ways

SPI, the Serial Peripheral Interface, connects one master to one or more devices with four wires. The master generates the clock on SCK (serial clock). MOSI (master out, slave in) carries bits from the master to the device. MISO (master in, slave out) carries bits back. The fourth wire is chip select (CS), which the master pulls low to say that this device should listen. Some devices have no MISO, because they only receive data.

SPI is full duplex. Each clock pulse moves one bit from the master to the device and one bit from the device to the master. Inside each side there is a shift register. The master's register holds the byte it sends, and the device's register holds the byte it sends. After eight pulses, the two registers have swapped contents. A computer architecture course would call this a ring of shifts: the bits move one place per clock, and the byte that leaves one side enters the other.

The data order is most-significant bit first in this course, so the bit at position 7 of the byte goes out first. The Pico's SPI peripheral can shift only in that order, which the SDK enforces in spi_set_format(). When a device needs another order, you do it in software.

Concept 2: clock polarity and phase decide the sampling edge

The two settings that matter for every SPI device are clock polarity and clock phase. Polarity, written CPOL, is the level the clock rests at when no transfer is running: 0 means low, 1 means high. Phase, written CPHA, is which clock edge the device samples its input on. The first edge is the first change after the clock leaves its idle level, and the second edge is the change back. "Sample" means reading the input pin at that instant, and the value must be stable then.

The RP2040 datasheet names these bits SPO for clock polarity and SPH for clock phase. SPO = 0 holds the clock low when idle. SPH = 0 means data is captured on the first clock edge, and SPH = 1 means the second RP2040 datasheet, sections 4.4.3.9.1 (SPO) and 4.4.3.9.2 (SPH). Combining the two bits gives four modes:

The master and the device must agree on the mode, and the device's datasheet states which one it expects. The master cannot detect a mismatch by itself, because SPI has no handshake. A mismatch shows up only as wrong data, which is why the first thing to check in a bad SPI capture is the mode.

Concept 3: the 74HC595 wants mode 0

The 74HC595 has three inputs that matter here. DS is the serial data input. SHCP is the shift clock, and a low-to-high transition on it moves the bit on DS into the shift register. STCP is the storage clock, and a low-to-high transition on it copies the shift register into the eight output latches. The outputs drive the LEDs, so they change only when STCP rises onsemi MC74HC595A datasheet, pin descriptions for A, Shift Clock and Latch Clock. The 74HC595 has no separate chip-select pin.

The data bit must be stable when SHCP rises, which means the device samples on the rising edge. With the clock idle low, the rising edge is the first edge. That is CPOL = 0 and CPHA = 0, which is mode 0. The SDK's spi_init() sets mode 0 as its default, and the solution keeps it.

The wiring in this project is GP19 to DS, GP18 to SHCP and GP17 to STCP. GP17 is the 74HC595's latch, and the project uses it as the chip select: it goes low before a byte and high after it. For this chip the rule that matters is the rising edge of STCP, which copies the shift register to the outputs. A low level on STCP does nothing, so holding it low during the transfer is safe. The rising edge after the last bit is the moment the new pattern appears on the LEDs.

Concept 4: the bit rate is a divider on the peripheral clock

The SPI clock, called SSPCLKOUT in the datasheet, is made by dividing the peripheral clock, clk_peri, by two integers. The first divider, the prescale, is an even number from 2 to 254. The second, the post-divide, is a number from 1 to 256 that is stored as one more than the register value SCR RP2040 datasheet, section 4.4.3.6.1, bit rate generation. So the rate is clk_peri ÷ (prescale × post-divide). The datasheet's own example is a 125 MHz peripheral clock with a prescale of 2, which gives a range up to 62.5 MHz.

With the SDK's default clocks, clk_peri runs at 125 MHz. You do not normally set this yourself. You ask for a rate, and the SDK finds the divider. spi_init() calls spi_set_baudrate(), which searches for the prescale and the post-divide in two loops, then writes both values to the registers. It returns the rate it actually set, and that returned value is the one to trust. The search is in the SDK source at pico-sdk, hardware_spi/spi.c, lines 42 to 74, with the two search loops at lines 51 to 64.

The SDK does not always hit the rate you asked for, because the divider is a whole number. That is the reason the function returns a value. The solution prints it as at %u Hz, so the learner sees the rate that was really set.

Worked example: asking for 1 MHz

Take a 125 MHz clk_peri and ask for 1,000,000 Hz. The first loop in spi_set_baudrate() finds the smallest prescale that puts the output in range. Its test is whether clk_peri is below prescale × 256 × requested rate. For prescale 2 the right side is 2 × 256 × 1,000,000 = 512,000,000, which is more than 125,000,000, so the loop stops at prescale 2.

The second loop starts at a post-divide of 256 and steps down until the output would be at most the requested rate. It tests 125,000,000 ÷ (2 × (post − 1)). At post-divide 64 the value is 125,000,000 ÷ 126 = 992,063, which is below 1,000,000, so that is too slow. At post-divide 63 the test value is 125,000,000 ÷ 124 = 1,008,064, which is above 1,000,000, so the loop stops there. The rate the code then sets is 125,000,000 ÷ (2 × 63) = 992,063 Hz.

So a request for 1 MHz returns 992,063 Hz, about 0.8 % slower, and the register holds SCR = 62. This is the same arithmetic the datasheet describes, and it is why the learner should read the returned value. The numbers here come from reading the SDK code. They are not from a measured run.

Concept 5: bit-bang and hardware SPI do the same job at different costs

Bit-bang means the CPU drives the pins itself, one GPIO write at a time. To send one bit it puts the data on MOSI, raises SCK, and lowers SCK again. Each step is an instruction, and the delays in the code set the clock speed. The method works with any pins, but the clock is only as steady as the code, and interrupts or other work can stretch any bit. Lesson 25 used this method.

Hardware SPI moves that work into the peripheral. The RP2040 has two SPI controllers, both based on the ARM PrimeCell SSP (PL022) design RP2040 datasheet, section 4.4. Each has an 8-entry transmit FIFO, which is a small hardware queue of bytes waiting to be shifted RP2040 datasheet, section 4.4.1. The CPU writes a byte into the FIFO, and the controller shifts it out with an evenly spaced clock. The CPU does no per-bit work. It can even do other things while the bits go out, and it checks the busy flag, which spi_is_busy() reports, only when it needs the bus to be idle.

Worked example: one byte, bit by bit

The chase in this lesson sends the bytes 0x01, 0x02, 0x04 and so on, one per LED. Follow the first byte, 0x01, which is 0000 0001 in binary. With MSB first, the bits leave in the order 0, 0, 0, 0, 0, 0, 0, 1. Assume the shift register holds zeros to start with. The first seven bits do not show on the LEDs, because the outputs do not change until the latch rises.

On each rising edge of SHCP, the chip takes the bit on DS into the shift register and pushes the older bits one place along. After the seventh rising edge, the register holds 0000 000 and the last bit is still to come. After the eighth rising edge, the register holds 0000 0001. The LEDs have not changed yet, because the outputs follow only the storage register.

The storage register is copied when STCP rises. In the software, the latch goes low before the byte starts and high after the last bit. So the rising edge of STCP at the end copies 0000 0001 to the output latches, and Q0 lights the first LED. The next byte, 0x02, follows the same steps, and its bit-by-bit pattern leaves the shift register while the old pattern still shows on the LEDs. That overlap is why the chip can stream bytes and still show a clean pattern.

The timing is what differs. Bit-bang does two sleep_us(1) calls per bit, so eight bits take at least 2 × 8 × 1 = 16 µs before the GPIO writes are counted. Hardware SPI at 992,063 Hz takes 8 ÷ 992,063 = 8.06 µs of clock per byte. The solution measures both with time_us_32() and prints the two times, so the learner can see the gap on the serial monitor.

The code, explained line by line

The excerpts come from the reference solution. First, the bit-bang byte. It is the reference that the hardware version must match. 

static void bitbang_byte(uint8_t value) {
    gpio_put(PIN_LATCH, 0);                  /* chip select low: the 595 will shift, not latch */
    for (int bit = 7; bit >= 0; bit--) {
        gpio_put(PIN_MOSI, (value >> bit) & 1u);   /* data settles while SCK is low */
        sleep_us(BIT_US);
        gpio_put(PIN_SCK, 1);                /* rising edge: the 595 samples DS here */
        sleep_us(BIT_US);
        gpio_put(PIN_SCK, 0);
    }
    gpio_put(PIN_LATCH, 1);                  /* rising edge on the latch: outputs change now */
}

The loop runs from bit 7 down to bit 0, which is MSB first. (value >> bit) & 1u extracts one bit, and it goes to MOSI while SCK is still low, so it is stable before the edge. Setting SCK high is the rising edge, and that is the moment the 74HC595 samples DS. Setting SCK low finishes the clock period. The two sleep_us() calls are the half-periods, so the whole bit takes about 2 µs. The latch is low during the transfer and rises at the end, which copies the byte to the LEDs. 

static void hw_byte(uint8_t value) {
    gpio_put(PIN_LATCH, 0);
    spi_write_blocking(SPI_PORT, &value, 1);     /* queue one byte and shift it out */
    while (spi_is_busy(SPI_PORT)) {       /* the last bit must leave first */
        tight_loop_contents();
    }
    gpio_put(PIN_LATCH, 1);
}

This is the same sequence as the bit-bang version, but with one call in the middle. spi_write_blocking() sends one byte. The SDK's implementation writes the byte into the FIFO, then waits until the controller's busy flag clears, so the bit has left the shifter when the call returns pico-sdk, hardware_spi/spi.c, lines 107 to 125. The explicit spi_is_busy() loop repeats that wait, so the learner can see the rule in the code. The latch goes high only after the wait, because a rising edge on STCP copies whatever is in the shift register at that moment. 

static void pins_to_spi(void) {
    gpio_set_function(PIN_SCK, GPIO_FUNC_SPI);     /* SCK is now driven by SPI0 */
    gpio_set_function(PIN_MOSI, GPIO_FUNC_SPI);    /* MOSI is now driven by SPI0 */
}

A GPIO pin can be an ordinary output or one of the peripheral's functions. The bit-bang phase used the first kind, so the pins must be switched to the second kind before the hardware phase. gpio_set_function() changes the pin's multiplexer setting. The RP2040 datasheet's Table 279 lists GP18 as SPI0 SCK and GP19 as SPI0 TX, which are the two pins switched here RP2040 datasheet, section 2.19.2, Table 279. GP17 is also the SPI0 chip-select function, but this project drives it as a plain GPIO, so the peripheral does not touch it. 

uint actual_hz = spi_init(SPI_PORT, SPI_HZ);      /* returns the rate it actually set */
spi_set_format(SPI_PORT, 8, SPI_CPOL_0, SPI_CPHA_0, SPI_MSB_FIRST);

spi_init() takes the requested rate, sets the divider, and enables the peripheral. It returns the rate, which the solution stores for printing. spi_set_format() sets 8 bits per frame, the clock polarity and phase, and the bit order. The format is the mode from Concept 2, written as CPOL 0 and CPHA 0. The starter sets CPHA 1 here, and that is the bug the learner must fix. The SDK's own spi_init() already sets this mode, so the explicit call makes the choice visible.

Common mistakes and how to spot them

Mistake 1: the wrong SPI mode

Symptom: the chase looks shifted, or it stops being a clean one-LED pattern. On a logic analyzer, the data changes on the same edge the chip samples. Cause: the starter's CPHA 1 makes the master change MOSI on the rising edge, which is also when the 74HC595 samples it, so the chip reads each bit one step late. Fix: use mode 0 for the 74HC595, and check the mode in the datasheet of every new device before you wire it up.

Mistake 2: the latch rises before the last bit has shifted

Symptom: the LEDs flicker through partial patterns during the chase, or a byte appears one step early. Cause: a rising edge on STCP copies whatever is in the shift register at that moment. If the latch rises while the last bit is still shifting, the copy holds an incomplete byte. Fix: wait for the busy flag to clear before raising the latch, which is what the spi_is_busy() loop does.

Mistake 3: the pins are still plain GPIO after the bit-bang phase

Symptom: the hardware phase prints SPI OK, but the LEDs stop on the last bit-bang pattern, and the logic analyzer shows no clock on D0 during the hardware phase. Cause: SCK and MOSI are still ordinary GPIO outputs, so the SPI peripheral has no pin to drive. Fix: call pins_to_spi(), which sets both pins to GPIO_FUNC_SPI, before the first hardware byte.

Mistake 4: using the requested rate in the timing budget

Symptom: a timing calculation that assumes 1 MHz is about 0.8 % too short, so a tight protocol budget fails by a small margin. The serial output shows 992063 Hz, not 1000000 Hz. Cause: the divider is a whole number, so spi_init() returns the rate it actually set. Fix: store the return value and use it in every calculation, as the solution does.

In real projects

On a real board, the first step with any SPI device is the datasheet's timing section. It names the mode, the largest clock, and the rule for the chip select, which some devices sample on a rising edge and others on a falling edge. Engineers write the mode and the clock limit next to the init code, and reviewers check both. A driver that uses the SDK's returned rate, and a comment that names the device's mode, passes review quickly.

A logic analyzer decodes SPI, but it needs the right mode and the right chip-select polarity to show correct bytes. This is the same debugging method as lesson 60, applied to a faster clock. Keep the capture next to the datasheet, and check the first byte. A decoder that shows the bytes shifted by one bit almost always has the wrong mode.

Interviews often ask when to bit-bang. The answer is in the Concept 5 trade-off: bit-bang works on any pin and needs no peripheral, but it costs CPU time per bit and its timing depends on other code. Hardware SPI moves the bits without CPU help and keeps the clock even, but the pins and the mode must match the device. Both can be correct, and the choice depends on the job.

Summary

  • SPI uses SCK, MOSI, MISO and chip select. Each clock pulse moves one bit each way, so a byte leaves and arrives in eight pulses.
  • CPOL sets the idle clock level, and CPHA sets which edge the device samples on. Together they give modes 0 to 3, and the device's datasheet sets the mode.
  • The 74HC595 shifts on the rising edge of SHCP and copies to the outputs on the rising edge of STCP, so it needs mode 0.
  • The bit rate is clk_peri ÷ (prescale × post-divide). The SDK searches for both values and returns the rate it actually set, such as 992,063 Hz for a 1 MHz request.
  • Bit-bang costs CPU time per bit, and its timing depends on the code. Hardware SPI shifts the byte from the 8-entry FIFO with an even clock.
  • Switch SCK and MOSI to the SPI function before the hardware transfer, and wait for the busy flag before raising the latch.
You chose the SPI clock mode from the device's edge, derived the bit rate from the SDK source, drove a 74HC595 through a latch and chip select, and compared the software and hardware timing on a logic analyzer. Any SPI display, flash chip or sensor uses the same steps.

"When would you bit-bang a protocol instead of using the hardware SPI peripheral, and what does bit-banging cost?" Answer out loud in 60 seconds, then compare.

Model answer

Bit-banging is the fallback when the pins or peripheral are not available, or when a device needs a timing that the hardware cannot produce, such as an unusual frame or a mode the peripheral does not support. It costs CPU time for every edge, makes timing depend on interrupts and other code, and is hard to keep steady. Hardware SPI shifts the byte with no CPU work per bit and keeps the clock even, but it must be configured with the right mode and rate, and the CPU still has to wait for the transfer to finish before it lowers or raises chip select.

RP2040 datasheet, section 4.4 (SPI): read 4.4.3.6.1 for the bit rate, 4.4.3.9.1 and 4.4.3.9.2 for the clock polarity and phase, and Table 279 for the SPI0 pins. Then read spi.c in the Pico SDK for the rate calculation, and the 74HC595's pin descriptions for the two clock edges.
