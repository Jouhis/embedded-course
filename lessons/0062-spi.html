SPI: displays and shift registers

Lesson 25 shifted a byte into a 74HC595 by toggling two pins in software. SPI does the same job in hardware: the peripheral shifts the bits, and the CPU is free until the byte has gone out.

By the end of this lesson you can set the SPI clock polarity and phase for a device, compute the SPI bit rate from the SDK's divider, drive a 74HC595 with spi_write_blocking() and a chip select pin, and compare bit-bang and hardware timing in a logic-analyzer capture.

The idea

SPI uses four wires: a clock (SCK), the master's output (MOSI), the device's output (MISO), and a chip select (CS) that is low while the device is addressed. A master shifts one byte out on MOSI and reads one in on MISO at the same time, one bit per clock edge. The RP2040's SPI controllers are the PL022 design, which the datasheet describes in section 4.4 RP2040 datasheet, section 4.4. The lesson-25 shift register uses the same pattern: data on one pin, a clock on another, and a separate latch. SPI is that pattern with the clock and data driven by the peripheral.

Clock polarity and phase

Two settings define the clock. CPOL is the clock's idle level: 0 means the clock is low when idle. CPHA is the clock edge on which data is sampled: 0 means the first edge, and 1 means the second. Together they give four modes, 0 to 3 RP2040 datasheet, sections 4.4.3.9.1 (SPO, clock polarity) and 4.4.3.9.2 (SPH, clock phase).

  • Mode 0 (CPOL 0, CPHA 0): idle low, sample on the rising edge. The default in spi_init().
  • Mode 1 (CPOL 0, CPHA 1): idle low, sample on the falling edge.
  • Mode 2 (CPOL 1, CPHA 0): idle high, sample on the falling edge.
  • Mode 3 (CPOL 1, CPHA 1): idle high, sample on the rising edge.

The 74HC595 shifts its register on the rising edge of its shift clock, so it needs mode 0. A device with the other mode reads each bit half a clock late, which shifts the whole byte into the wrong place. The chip select is separate: it goes low before the first clock and high after the last, and many devices use the rising edge of CS as their latch, as the 74HC595 does.

The bit rate

The SPI clock is the peripheral clock divided by two integers. The SDK's spi_set_baudrate() finds a prescale (even, from 2 to 254) and a post-divide (from 1 to 256), so the rate is clk_peri ÷ (prescale × postdiv). It takes the smallest prescale that gives a usable post-divide, then the largest post-divide that does not exceed the requested rate pico-sdk, hardware_spi/spi.c, lines 42 to 64. The function returns the rate it actually set. 

/* from spi.c: baud = clk_peri / (prescale * postdiv), prescale even 2..254, postdiv 1..256 */
uint actual_hz = spi_init(spi0, 1000000);    /* returns what was set, not what was asked */

Bit-bang and hardware, side by side

Bit-bang drives each pin with a GPIO write, and it takes a few CPU cycles per edge plus any delay you add. Hardware SPI loads a byte into the transmit FIFO once, and the peripheral shifts it out with no CPU work per bit. The CPU then waits for the transfer to end, which spi_is_busy() reports.

Try it in Wokwi

The project projects/0062-spi uses the lesson 25 74HC595 with the SPI0 pins. SCK is GP18, MOSI is GP19, and GP17 is the latch, driven by hand as chip select. A logic analyzer records the three lines on D0, D1 and D2. The solution first runs the chase with bit-bang, then with hardware SPI at 1 MHz, and prints both times.

  1. Open projects/0062-spi/starter in VS Code (File → Open Folder).
  2. Build with Ctrl+Shift+B, and start the simulator with F1 → Wokwi: Start Simulator.
  3. Your task: write hw_byte(), so it lowers the latch, sends one byte with spi_write_blocking(), waits with spi_is_busy(), and raises the latch. The starter sets the SPI mode to CPHA 1, which is wrong for the 74HC595. Fix it, and explain the edge in a comment. Then stop the simulator and open wokwi.vcd in PulseView with the SPI decoder, using CS on D2.
  4. You will know it works when the LEDs chase on the hardware path, and the serial monitor prints SPI OK. In PulseView, the MOSI bytes should match the chase: 0x01, 0x02, and so on, MSB first.
Hint for the mode

The 74HC595 samples its data on the rising edge of SHCP, which is SCK here. Work out which mode samples on the first, rising edge with the clock idle low.

Hint for the timing

Compare the two times the solution prints. Bit-bang has two 1 µs delays per bit, so a byte takes at least 16 µs. Hardware SPI at 1 MHz takes about 8 µs per byte. The times are computed from the design, not from a measured run.

"When would you bit-bang a protocol instead of using the hardware SPI peripheral, and what does bit-banging cost?" Answer out loud in 60 seconds, then compare.

Model answer

Bit-banging is the fallback when the pins or peripheral are not available, or when a device needs a timing that the hardware cannot produce, such as an unusual frame or a mode the peripheral does not support. It costs CPU time for every edge, makes timing depend on interrupts and other code, and is hard to keep steady. Hardware SPI shifts the byte with no CPU work per bit and keeps the clock even, but it must be configured with the right mode and rate, and the CPU still has to wait for the transfer to finish before it lowers or raises chip select.

RP2040 datasheet, section 4.4 (SPI): read 4.4.3.9.1 and 4.4.3.9.2 for the clock polarity and phase, and the GPIO function table (Table 279) for the SPI0 pins. Then read spi.c in the Pico SDK for the rate calculation.
