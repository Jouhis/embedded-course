The memory map and memory-mapped registers

A peripheral register is just an address. Once you can compute that address from a base and an offset, the struct syntax in the vendor header stops being magic.

By the end of this lesson you can compute the address of a peripheral register from its base address and offset, write it through a pointer, and check that the raw write and the struct access land on the same address.

Where we are and why it matters

Lesson 36 divided the chip's memory into regions: flash, SRAM and the rest. Lesson 37 showed that each access crosses a bus to reach its target. This lesson closes the loop. The bus delivers an access to a target because of the address, so the address is the one thing that decides what a write does. Lesson 31 introduced the registers, and lesson 35 showed that the stack is an address range too. Everything in this lesson is an address calculation, and the rest of the course uses it to set pins, start clocks and read sensors.

The problem is concrete. A Blue Pill is wired so that a single pin, PC13, drives an LED. To light the LED, the firmware has to write to one register on the GPIO port C. Vendor headers give that register a name, GPIOC->BSRR, and the name hides an address. A developer who reads a driver and cannot find where its writes land cannot debug it. A developer who can compute the address can check any driver in a few minutes. This lesson teaches the calculation.

The concepts, one at a time

The address space and the memory map

The core sees one flat address space of 32-bit addresses. Each address names one byte, and a 32-bit word occupies four consecutive addresses. Each region of the space is assigned to something: flash, SRAM, or a peripheral. That assignment is the memory map. The core does not know what lives at an address. It issues a load or a store, and the bus routes the access to the target that owns that address. Lesson 37 showed the routing.

A memory map is a table in the reference manual, and the vendor header repeats it as a list of constants. Each constant is a name for a base address. The header for the STM32F1 defines FLASH_BASE as 0x08000000, SRAM_BASE as 0x20000000 and PERIPH_BASE as 0x40000000 (stm32f103xb.h). The peripheral region is further divided, and the header builds the division from those three constants. Each named base is an address that the bus knows how to route.

Base address and register offset

A peripheral has a base address, which is the start of its block. Each register inside the block sits at a fixed offset from that base, counted in bytes. The register's address is the base plus the offset. In C you write this sum once, and the rest of the code uses the name. The header and the reference manual both give the base and the offset, and the struct in the header is a way of writing the same sum.

The offset is in bytes, not in words. A register at offset 0x10 is the fifth word of the block, because each word is four bytes. The glossary warns against calling it an index, for exactly this reason.

Memory-mapped registers

A peripheral register is a memory-mapped location. Reading or writing its address talks to the hardware. So the core needs no special instruction for I/O. A store to a GPIO register is an ordinary str instruction, and the bus delivers it to the GPIO block instead of to RAM. This is why the architecture course's load and store model covers peripherals too.

The width of the access matters too. On the RP2040, the datasheet says that memory-mapped IO registers "ignore the width of bus read/write accesses" and "treat all writes as though they were 32 bits in size" (section 2.1.4). So a byte write to an IO register is not a byte write to the register. It is a 32-bit write whose contents include the other three bytes. The rule to remember is to write the full 32-bit word the register expects, unless the register's manual says otherwise.

That table is the datasheet's summary. The datasheet's Table 15, in section 2.2.1, lists the same regions. It calls the region at 0xD0000000 "IOPORT Registers", and section 2.3.1 describes it as the SIO. The SIO block is special. It is the single-cycle IO block attached to the cores' IO ports, not an APB peripheral, so its registers are reached without the bridge (lesson 37).

Within the APB region, each peripheral gets a 16 kB slot. The datasheet explains why: each register block is 4 kB, and the three atomic aliases from lesson 37 take the rest of the slot (section 2.1.2). The clocks block base is 0x40008000 (section 2.15.7), the GPIO bank IO base is 0x40014000 (section 2.19.6.1), and the GPIO pad control base is 0x4001C000 (section 2.19.6.3). The Pico SDK's addressmap.h gives the same values, which is a second source you can check against.

The SIO's GPIO registers are at fixed offsets from 0xD0000000. The datasheet's register list (section 2.3.1.7) gives GPIO_OUT at 0x010, GPIO_OUT_SET at 0x014, GPIO_OUT_CLR at 0x018 and GPIO_OUT_XOR at 0x01C. The SDK's sio.h defines the same four offsets, under the names SIO_GPIO_OUT_OFFSET and so on.

The STM32F103 map, from the header

The ST device header defines the regions. The flash starts at FLASH_BASE = 0x08000000, SRAM at SRAM_BASE = 0x20000000, and the peripheral region at PERIPH_BASE = 0x40000000. APB2 is PERIPH_BASE + 0x10000, GPIOC is APB2PERIPH_BASE + 0x1000, and the RCC is AHBPERIPH_BASE + 0x1000. All of these come from third_party/cmsis-device-f1/Include/stm32f103xb.h.

The header also describes the structure of each block as a C struct. For the GPIO block it defines GPIO_TypeDef, with seven members in this order: CRL, CRH, IDR, ODR, BSRR, BRR and LCKR. Each member is a 32-bit word, so the offsets are 0x00, 0x04, 0x08, 0x0C, 0x10, 0x14 and 0x18. BSRR is the fifth member, at 0x10, and that is the number you use when you compute its address by hand.

A worked example with real numbers

Here is the calculation for the register that lights the Blue Pill LED, from the first principles of the header. Then the same kind of calculation on the RP2040.

  1. Find the bus region. GPIOC is APB2PERIPH_BASE + 0x1000. APB2 is PERIPH_BASE + 0x10000, and PERIPH_BASE is 0x40000000. So APB2 is 0x40010000, and GPIOC is 0x40010000 + 0x1000 = 0x40011000.
  2. Add the offset. The offset of BSRR is 0x10, the fifth word of GPIO_TypeDef. So the address is 0x40011000 + 0x10 = 0x40011010.
  3. Find the bit. The header defines GPIO_BSRR_BR13 with its position as GPIO_BSRR_BR13_Pos = 29, and its value as 0x20000000. So bit 29 is the reset bit for pin 13. The header also defines GPIO_BSRR_BS13 at bit 13, with the value 0x00002000. Writing 0x20000000 resets PC13 and writing 0x00002000 sets it. A zero in any other bit does nothing.
  4. Put the pieces together. One store of 0x20000000 to 0x40011010 resets PC13. The address and the value are both known before the program runs, which is why the register can be written from a pointer.

The same method works for the RP2040's SIO. The base is 0xD0000000 and the offset of GPIO_OUT_CLR is 0x018, so the address is 0xD0000000 + 0x018 = 0xD0000018. A store there clears the output bits you name, in one write, without reading the register first. The SDK defines the same offset as SIO_GPIO_OUT_CLR_OFFSET, which you can use in the same way as the header macro on the STM32.

Writing the address yourself

The C form of a register is a pointer to volatile. A pointer is a variable that holds an address, and the cast is how you tell the compiler that a number is an address of a particular type. volatile tells the compiler that each access must really happen, because the hardware can change the value at any time, and that the access must not be merged or removed (glossary: volatile). Lesson 46 covers why this matters in full.

The solution below writes the register through a pointer, and it also checks that the pointer equals the struct member's address. That check is the proof that the two forms name the same place. 

/* GPIOC base 0x40011000 + BSRR offset 0x10 */
#define GPIOC_BSRR_ADDR  (0x40011000UL + 0x10UL)

/* A write through this pointer is a store to 0x40011010. */
volatile uint32_t *bsrr = (volatile uint32_t *)GPIOC_BSRR_ADDR;
*bsrr = GPIO_BSRR_BR13;     /* bit 29: reset PC13, the LED on the Blue Pill */
A write to BSRR sets or resets only the bits you name, and bits written as 0 leave their pins alone. That is why it is safer than reading the output register, changing one bit and writing it back, which can race an interrupt. The HAL's toggle code relies on this: it writes the set bits and the reset bits for different pins in one store, which works only because a 0 bit does nothing. The bit meanings are in the GPIO section of RM0008.

The code, explained line by line

Take the lines of the solution in order. Each one either computes an address, names a field, or writes to hardware. 

#define GPIOC_BSRR_ADDR  (0x40011000UL + 0x10UL)   /* GPIOC base + BSRR offset */

volatile uint32_t *bsrr = (volatile uint32_t *)GPIOC_BSRR_ADDR;
print_line("BSRR address: ", GPIOC_BSRR_ADDR);
if ((uint32_t)(uintptr_t)&GPIOC->BSRR == GPIOC_BSRR_ADDR) {
    uart_puts("address check OK: &GPIOC->BSRR matches\r\n");
}

The #define line computes the address at compile time. The UL suffix makes each constant an unsigned long, so the sum is an unsigned 32-bit address and does not go negative or overflow in a surprising way. The next line converts the number into a pointer to volatile uint32_t. The type says the target is a 32-bit word, which is the width the register expects.

The print_line call prints the computed address, so you can read it in the serial monitor. The if then compares that number with the address of the struct member. The expression &GPIOC->BSRR asks the compiler for the address it computes for the member. The cast to uintptr_t makes the pointer an integer, so it can be compared with a number. If the two match, the message prints. The check is a unit test in miniature, and it is worth writing whenever you compute an address by hand. 

RCC->APB2ENR |= RCC_APB2ENR_IOPCEN;
GPIOC->CRH = (GPIOC->CRH & ~(0xFU << 20)) | (0x2U << 20);   /* PC13 push-pull output */

The first line turns on the clock for GPIOC, as lesson 37 explains. The second line configures PC13. The configuration register CRH holds a four-bit setting for each of its pins. The header defines the field for pin 13 as GPIO_CRH_MODE13 at bit 20 and GPIO_CRH_CNF13 at bit 22, so the pin's four bits are bits 20 to 23. The expression 0xFU << 20 makes a mask for those four bits, and ~ inverts it, so the & clears the old setting for the pin. The | then writes the new value, 0x2U << 20, which puts 2 in the mode field of pin 13. The solution's comment calls the result a push-pull output. The meaning of each field value is in the GPIO register description of RM0008, which this course has not checked, so read it there before you change the value. 

volatile uint32_t *bsrr = ...;
*bsrr = GPIO_BSRR_BR13;     /* raw write: LED on */
...
*bsrr = GPIO_BSRR_BS13;     /* raw write: LED off */

Each line of the loop is a single store. GPIO_BSRR_BR13 is 0x20000000, which resets PC13 and turns the LED on. The Blue Pill LED is active low, so a low pin lights it, and the solution's header comment says so. GPIO_BSRR_BS13 is 0x00002000, which sets PC13 high and turns the LED off. The loop uses the pointer, so the write happens at the address from the calculation above, and the struct name is used only in the check.

Common mistakes and how to spot them

1. Using the offset as the address

A beginner who writes *(volatile uint32_t *)0x10 = value has forgotten the base. Address 0x10 is in the first region of the map, not in the GPIO block. The write does not reach the pin, and depending on the chip, a store to that region may be ignored or may fault. The symptom is that nothing happens on the board, and in the debugger the address shown is wrong. The fix is to add the base, and to check the printed address against the header before you write.

2. Leaving out volatile

Without volatile, the compiler sees a store to an address and assumes that nothing reads it. It may merge two stores into one, or remove a store it thinks is dead. The delay loops in the solution use a volatile counter for the same reason. The symptom is a program that works in a debug build and fails in an optimised one, for instance an LED that stays on or never blinks. The fix is to make every pointer to a register volatile, as the solution does.

3. Confusing the set bit with the reset bit

Writing GPIO_BSRR_BS13 sets PC13 high, which turns the LED off on a Blue Pill. Writing GPIO_BSRR_BR13 resets it low, which turns the LED on. The names differ by one letter, and a developer who thinks "reset" means "turn off" for an LED will get the opposite result. The symptom is an LED that is on when the code says it is off. The fix is to check the wiring, which decides the polarity, and to use the names in the header.

4. Reading, changing and writing back the output register

The solution avoids this, and the warning above explains it. Reading ODR, changing one bit and writing the whole register back can overwrite a change that an interrupt made in between. The symptom is an output bit that changes back on its own, now and then. The fix is to write BSRR, which changes only the bits named in the write.

5. Writing a byte to a 32-bit register

The RP2040 datasheet says that IO registers "treat all writes as though they were 32 bits in size", so a byte write changes all 32 bits of the register, not only the byte (section 2.1.4). A developer who writes one byte of a control register and expects the other bytes to stay the same will be wrong. The symptom is that bits you did not touch change. The fix is to write the full word, with the bits you want to keep set to their current values, or to use the register's set and clear addresses.

In real projects

Professional code does not write numbers like 0x40011010 in driver files. The base and offset come from the vendor header or a generated peripheral access crate. The glossary calls that crate a PAC, which is the Rust term for the same idea. A reviewer rejects a driver that contains a magic address, because the address is then a fact the next developer must rediscover. A reviewer also checks that every register pointer is volatile, that the set and reset writes use BSRR or the alias, and that the bit names come from the header.

Testing matters here. The address check in the solution is the kind of test a team keeps: it compares the computed address with the header's member address, and it fails the build if the two disagree. The same check can run on a host machine in a unit test, which the course's host-test lessons cover.

Interviewers ask this question because it tests whether you know what a register write does in hardware. The question at the end of this lesson, about memory-mapped registers, is a common one. A good answer says that the address is the base plus the offset, that the bus routes the store to the peripheral, and that the pointer is volatile so the store is not optimised away.

Summary

  • The memory map assigns address ranges to flash, SRAM and peripherals, and the bus routes each access by its address.
  • A register's address is its peripheral's base plus its offset in bytes. The RP2040 SIO base is 0xD0000000, and the STM32 GPIOC base is 0x40011000.
  • On STM32 GPIO, BSRR at offset 0x10 sets the pin with the low bit and resets it with the high bit. BR13 is 0x20000000 and BS13 is 0x00002000.
  • A pointer to a register is volatile, so every access is real and none is removed.
  • IO registers on the RP2040 treat every write as 32 bits, so write the whole word.
  • Use BSRR or the atomic alias to change bits, and check the computed address against the header in code.
  • Keep magic addresses out of drivers. The header macros are the source of truth.

Model answer

A memory-mapped register is a peripheral control register that sits at a fixed address in the memory map, so the core reaches it with ordinary loads and stores. The compiler computes base plus offset, loads that address into a register, and emits a single store, such as str, to it. The bus delivers the store to the GPIO block, which decodes the offset and acts on it. The pointer must be volatile, so the store is not optimised away, and a set or reset through BSRR changes only the bits named in the write.

RP2040 datasheet: read section 2.2 (Address Map) and its Table 15, then the register list at section 2.3.1.7 for the SIO offsets, and section 2.1.4 (Narrow IO Register Writes) for the 32-bit rule. The base and offset arithmetic is the same on the STM32, where the header plays the role of the list.
