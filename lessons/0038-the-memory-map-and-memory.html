The memory map and memory-mapped registers

Peripheral registers as addresses in one address space

By the end of this lesson you can compute the address of a peripheral register from its base address and offset, write it through a pointer, and check that the raw write and the struct access land on the same address.

Addresses behind register names

Lesson 36 divided the chip's memory into regions such as flash and SRAM, and lesson 37 showed each access crossing a bus to its target. This lesson connects the two, because the bus delivers an access according to its address, which makes the address the one thing that decides what a write does. Lesson 31 introduced the registers and lesson 35 showed that the stack is an address range too, and everything in this lesson is address arithmetic that the rest of the course uses to set pins, start clocks and read sensors.

On a Blue Pill a single pin, PC13, drives an LED, and lighting it means writing to one register of GPIO port C. The vendor header gives that register the name GPIOC->BSRR, which hides an address, so a developer who cannot work out where a driver's writes land cannot debug it, while one who can compute the address can check any driver in minutes. This lesson teaches that calculation.

The address space and the memory map

The core sees one flat space of 32-bit addresses, in which each address names one byte and a 32-bit word occupies four consecutive addresses. Each region of the space is assigned to flash, SRAM or a peripheral, and that assignment is the memory map. The core itself does not know what lives at an address; it issues a load or store, and the bus routes the access to whichever target owns the address, as lesson 37 showed.

The memory map is a table in the reference manual, which the vendor header repeats as a list of constants, each naming a base address. The STM32F1 header defines FLASH_BASE as 0x08000000, SRAM_BASE as 0x20000000 and PERIPH_BASE as 0x40000000 (stm32f103xb.h), and builds the subdivision of the peripheral region from those three constants, so every named base is an address the bus knows how to route.

Base addresses and register offsets

A peripheral has a base address, the start of its block, and each register inside the block sits at a fixed offset from that base, counted in bytes. The register's address is therefore

address = base + offset(1)

where both values come from the header or the reference manual. In C the sum is written once and the rest of the code uses the name, and the struct in the header is simply another way of writing it.

The offset counts bytes, not words, so a register at offset 0x10 is the fifth word of the block, since each word is four bytes. This is why the glossary warns against calling the offset an index.

Memory-mapped registers

A peripheral register is a memory-mapped location, so reading or writing its address talks to the hardware and the core needs no special I/O instruction. A store to a GPIO register is an ordinary str, which the bus delivers to the GPIO block instead of RAM, and this is why the load and store model of earlier lessons covers peripherals too.

The width of the access also matters. On the RP2040 the datasheet states that memory-mapped IO registers "ignore the width of bus read/write accesses" and "treat all writes as though they were 32 bits in size" (section 2.1.4), so a byte write to an IO register is really a 32-bit write whose other three bytes come along with it. Write the full 32-bit word a register expects unless its manual says otherwise.

The address space resembles a wall of numbered mailboxes. Most are ordinary storage, where a letter waits until collected, but a few are wired to machines, so a note dropped into box 0x40011010 switches a lamp and opening box 0x40011008 shows what a sensor sees right now. The CPU uses the same load and store for every box, and the address alone decides whether it reaches memory or a machine. Real mailboxes keep their letters, however, while a machine box may hold a different value each time it is opened, or none at all.

The table summarises the datasheet's Table 15 in section 2.2.1, which lists the same regions and calls the region at 0xD0000000 "IOPORT Registers", described in section 2.3.1 as the SIO. The SIO block is special: it is the single-cycle IO block attached to the cores' IO ports rather than an APB peripheral, so its registers are reached without the bridge (lesson 37).

Within the APB region each peripheral receives a 16 kB slot, because each register block is 4 kB and the three atomic aliases of lesson 37 fill the rest of the slot (section 2.1.2). The clocks block base is 0x40008000 (section 2.15.7), the GPIO bank IO base 0x40014000 (section 2.19.6.1) and the GPIO pad control base 0x4001C000 (section 2.19.6.3), and the Pico SDK's addressmap.h gives the same values as a second source to check against.

The SIO's GPIO registers sit at fixed offsets from 0xD0000000. The datasheet's register list (section 2.3.1.7) gives GPIO_OUT at 0x010, GPIO_OUT_SET at 0x014, GPIO_OUT_CLR at 0x018 and GPIO_OUT_XOR at 0x01C, and the SDK's sio.h defines the same four offsets under names such as SIO_GPIO_OUT_OFFSET.

The STM32F103 memory map

The ST device header defines the regions: flash from FLASH_BASE = 0x08000000, SRAM from SRAM_BASE = 0x20000000 and peripherals from PERIPH_BASE = 0x40000000, with APB2 at PERIPH_BASE + 0x10000, GPIOC at APB2PERIPH_BASE + 0x1000 and RCC at AHBPERIPH_BASE + 0x1000, all in third_party/cmsis-device-f1/Include/stm32f103xb.h. RM0008 Rev 21, Table 3 (section 3.3), gives the same boundaries, with GPIO port C at 0x4001 1000 and RCC at 0x4002 1000.

The header also describes each block's structure as a C struct. For GPIO it defines GPIO_TypeDef with seven 32-bit members in order, CRL, CRH, IDR, ODR, BSRR, BRR and LCKR, at offsets 0x00, 0x04, 0x08, 0x0C, 0x10, 0x14 and 0x18. BSRR is the fifth member at 0x10, the number used to compute its address by hand, and RM0008 Rev 21, section 9.2.5, gives the same offset for GPIOx_BSRR.

Worked example: the address of GPIOC BSRR

We compute the register that lights the Blue Pill LED from the header's own definitions, then repeat the method on the RP2040. Before starting, it is worth estimating which region of the map the answer falls in.

  1. Find the bus region. GPIOC is APB2PERIPH_BASE + 0x1000, APB2 is PERIPH_BASE + 0x10000 and PERIPH_BASE is 0x40000000, so APB2 is 0x40010000 and GPIOC is 0x40010000 + 0x1000 = 0x40011000.
  2. Add the offset. BSRR is the fifth word of GPIO_TypeDef at offset 0x10, so by Equation 1 its address is 0x40011000 + 0x10 = 0x40011010.
  3. Find the bit. The header defines GPIO_BSRR_BR13 with GPIO_BSRR_BR13_Pos = 29 and the value 0x20000000, so bit 29 resets pin 13, and RM0008 Rev 21, section 9.2.5, confirms that bits 31 to 16 are BR0 to BR15 and bits 15 to 0 are BS0 to BS15. GPIO_BSRR_BS13 is accordingly bit 13, with the value 0x00002000. Writing 0x20000000 resets PC13 and writing 0x00002000 sets it, while a zero in any other bit does nothing.
  4. Combine the pieces. One store of 0x20000000 to 0x40011010 resets PC13. Both the address and the value are known before the program runs, which is why the register can be written through a pointer.

The same method works for the RP2040's SIO. The base is 0xD0000000 and GPIO_OUT_CLR sits at offset 0x018, so its address is 0xD0000000 + 0x018 = 0xD0000018, and a store there clears the named output bits in one write without reading the register first. The SDK defines the offset as SIO_GPIO_OUT_CLR_OFFSET, used in the same way as the header macro on the STM32.

The explorer repeats the calculation for any register, starting from the worked example, GPIOC->BSRR. Type an address or click a region, and it splits the address into region, peripheral block, base and offset; switch the chip to the RP2040 to see the SIO example. Then answer the drill at the bottom before looking at the map, and use the map to check.

  1. Start from the header's peripheral base, PERIPH_BASE = 0x40000000.
  2. APB2's peripherals start 0x10000 above it, at 0x40010000.
  3. GPIOC is 0x1000 into APB2: its base is 0x40011000.
  4. BSRR is the fifth word of the block, offset 0x10. The register's address is 0x40011010.
  5. The value: BR13, the reset bit for pin 13, is bit 29, so the word to store is 0x20000000.
  6. The core executes one store. The address decides the route: through the bus matrix and the APB2 bridge to the GPIOC block.
  7. BSRR acts on the write: bit 29 clears ODR bit 13. No read was needed, and no other pin changed.
  8. PC13 goes low. The Blue Pill's LED is wired from 3.3 V to PC13, so it is active low: current flows and it lights.

Register access through a volatile pointer

In C a register is accessed through a pointer to volatile. A pointer is a variable holding an address, and a cast tells the compiler that a number is an address of a particular type. volatile tells the compiler that every access must really happen, without being merged or removed, because the hardware can change the value at any time (glossary: volatile), and lesson 46 covers why this matters in full.

The solution below writes the register through such a pointer and also checks that the pointer equals the struct member's address, which confirms that the two forms name the same place. 

/* GPIOC base 0x40011000 + BSRR offset 0x10 */
#define GPIOC_BSRR_ADDR  (0x40011000UL + 0x10UL)

/* A write through this pointer is a store to 0x40011010. */
volatile uint32_t *bsrr = (volatile uint32_t *)GPIOC_BSRR_ADDR;
*bsrr = GPIO_BSRR_BR13;     /* bit 29: reset PC13, the LED on the Blue Pill */
A write to BSRR sets or resets only the bits named in it, and bits written as 0 leave their pins alone. That makes it safer than reading the output register, changing one bit and writing it back, which can race an interrupt. The HAL's toggle code depends on this, writing the set bits and reset bits for different pins in one store, which works only because a 0 bit does nothing; RM0008 Rev 21, section 9.2.5, defines a 0 in a BR or BS bit as "No action on the corresponding ODRx bit".

The solution code line by line

Taking the solution's lines in order, each one computes an address, names a field or writes to hardware. 

#define GPIOC_BSRR_ADDR  (0x40011000UL + 0x10UL)   /* GPIOC base + BSRR offset */

volatile uint32_t *bsrr = (volatile uint32_t *)GPIOC_BSRR_ADDR;
print_line("BSRR address: ", GPIOC_BSRR_ADDR);
if ((uint32_t)(uintptr_t)&GPIOC->BSRR == GPIOC_BSRR_ADDR) {
    uart_puts("address check OK: &GPIOC->BSRR matches\r\n");
}

The #define line computes the address at compile time, with the UL suffix making each constant an unsigned long, so the sum is an unsigned 32-bit address that cannot go negative or overflow unexpectedly. The next line converts the number into a pointer to volatile uint32_t, the type stating that the target is a 32-bit word, the width the register expects.

The print_line call prints the computed address for the serial monitor, and the if compares it with the address of the struct member. &GPIOC->BSRR asks the compiler for the address it computes for the member, and the cast to uintptr_t turns the pointer into an integer so that it can be compared with a number; if the two match, the message prints. The check is a unit test in miniature and is worth writing whenever an address is computed by hand. 

RCC->APB2ENR |= RCC_APB2ENR_IOPCEN;
GPIOC->CRH = (GPIOC->CRH & ~(0xFU << 20)) | (0x2U << 20);   /* PC13 push-pull output */

The first line turns on the GPIOC clock, as lesson 37 explains, and the second configures PC13. The configuration register CRH holds a four-bit setting for each of its pins, and the header places pin 13's fields at GPIO_CRH_MODE13, bit 20, and GPIO_CRH_CNF13, bit 22, so the pin occupies bits 20 to 23. The expression 0xFU << 20 forms a mask for those four bits, ~ inverts it so that the & clears the old setting, and the | writes the new value 0x2U << 20, placing 2 in pin 13's mode field. RM0008 Rev 21, section 9.2.2, confirms the layout, with MODE13 in bits 21:20 and CNF13 in bits 23:22: a MODE value of 10 selects output mode with a 2 MHz maximum speed and a CNF value of 00 general-purpose push-pull output, so the line makes PC13 a push-pull output, as the solution's comment says. 

volatile uint32_t *bsrr = ...;
*bsrr = GPIO_BSRR_BR13;     /* raw write: LED on */
...
*bsrr = GPIO_BSRR_BS13;     /* raw write: LED off */

Each line of the loop is a single store. GPIO_BSRR_BR13, 0x20000000, resets PC13, which turns the LED on because the Blue Pill LED is active low, as the solution's header comment notes, and GPIO_BSRR_BS13, 0x00002000, sets PC13 high and turns the LED off. The loop uses the pointer, so each write goes to the address calculated above, and the struct name appears only in the check.

Common mistakes and how to spot them

The offset used as the address

Nothing happens on the board, and the debugger shows a wrong address. Writing *(volatile uint32_t *)0x10 = value forgets the base, so the store goes to the first region of the map instead of the GPIO block, where depending on the chip it is ignored or faults. Add the base, and check the printed address against the header before writing.

volatile left out

A program works in a debug build and fails in an optimised one, for example with an LED that stays on or never blinks. Without volatile, the compiler assumes nothing reads the stored address, so it may merge two stores or remove one it considers dead, which is also why the solution's delay loops use a volatile counter. Make every register pointer volatile, as the solution does.

The set bit confused with the reset bit

The LED is on when the code says off. Writing GPIO_BSRR_BS13 sets PC13 high, which turns a Blue Pill LED off, and GPIO_BSRR_BR13 resets it low, which turns it on, so the names differ by one letter and reading "reset" as "turn off" gives the opposite result. Check the wiring, which decides the polarity, and use the header's names.

The output register read, changed and written back

An output bit occasionally changes back on its own. Reading ODR, changing one bit and writing the whole register back can overwrite a change an interrupt made in between, as the warning above explains. Write BSRR instead, which changes only the bits named in the write.

A byte written to a 32-bit register

Bits you did not touch change. The RP2040 datasheet states that IO registers "treat all writes as though they were 32 bits in size", so a byte write changes all 32 bits of the register rather than one byte (section 2.1.4). Write the full word with the bits to keep set to their current values, or use the register's set and clear addresses.

Register addresses in production drivers

Professional code does not write numbers such as 0x40011010 in driver files; bases and offsets come from the vendor header or a generated peripheral access crate, which the glossary calls a PAC, the Rust term for the same idea. A reviewer rejects a driver containing a magic address, because the next developer must then rediscover what it means, and also checks that every register pointer is volatile, that set and reset writes use BSRR or the alias, and that the bit names come from the header.

Testing matters here as well. The address check in the solution is the kind of test a team keeps, comparing the computed address with the header's member address and failing the build when they disagree, and the same check can run in a unit test on a host machine, as the course's host-test lessons cover.

Summary

  • The memory map assigns address ranges to flash, SRAM and peripherals, and the bus routes each access by its address.
  • A register's address is its peripheral's base plus its offset in bytes; the RP2040 SIO base is 0xD0000000 and the STM32 GPIOC base 0x40011000.
  • On the STM32 GPIO, BSRR at offset 0x10 sets a pin with its low bit and resets it with its high bit, so BR13 is 0x20000000 and BS13 0x00002000.
  • A register pointer is volatile, so that every access really happens and none is removed.
  • RP2040 IO registers treat every write as 32 bits, so write the whole word.
  • Change bits with BSRR or the atomic alias, and check computed addresses against the header in code.
  • Keep magic addresses out of drivers and treat the header macros as the source of truth.
RP2040 datasheet: read section 2.2 (Address Map) and its Table 15, then the register list at section 2.3.1.7 for the SIO offsets, and section 2.1.4 (Narrow IO Register Writes) for the 32-bit rule. The base and offset arithmetic is the same on the STM32, where the header plays the role of the list.
