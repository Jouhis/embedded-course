Devicetree: describing hardware

In Zephyr, the pin numbers, the bus addresses and the device names are not in the C code. They are in a tree that the build reads first, and this lesson shows how to read it and change it.

By the end of this lesson you can add a node in a board overlay, give it an alias, and read it from C with GPIO_DT_SPEC_GET, then find the merged result in build/zephyr/zephyr.dts.

Where we are and why it matters

Lesson 94 blinked an LED with GPIO_DT_SPEC_GET(DT_ALIAS(led0), gpios), and it said only that the alias found the pin. Lesson 95 showed that Kconfig controls which features exist. This lesson covers the other half of a Zephyr application: the description of the hardware, which says which pins go where, which bus each device sits on, and which devices exist at all. Kconfig answers "which features are compiled in"; the devicetree answers "what is connected to what".

The problem it solves is an old one. In a firmware project without this separation, the pin number of the status LED is written in the C code, in many files. When the board is revised and the LED moves to another pin, every file that names the old pin must change, and every change is a risk. A company with five board revisions and three products sharing one firmware cannot live with that. A devicetree moves the pin numbers out of the C code and into a description that differs from board to board. The C code asks for "the status LED" by a name, and the build finds where that name points.

Nodes, properties and aliases

A devicetree is a tree of nodes, and each node describes one piece of hardware. A node has a name, optional labels, and properties. A property is a name with a value, such as compatible = "vnd,user-button"; or status = "okay";. The glossary defines the term for Zephyr text, and the course uses the single word devicetree. The format comes from the devicetree specification, and Zephyr's pages are linked in the source list at the end of the lesson.

Four properties carry most of the meaning. compatible is a string that names the kind of device, and it selects the binding, which is the schema that says which other properties the node must have. reg gives an address, for a device on a memory-mapped bus. status turns a node on with "okay" or off with "disabled". gpios lists GPIO pins, and it is covered below. A node with no compatible is a container: it groups other nodes and has no binding of its own.

A label is a short name for a node, written before the node's name, such as user_button: button_0. You refer to a labelled node with an ampersand, as in &gpio0. That reference is a phandle, a link from one node to another, and it is how the devicetree says "this LED is on the GPIO port gpio0". An alias is a second name for a node, defined under the aliases node. The C macro DT_ALIAS(led0) looks that name up. Aliases are what the C code uses, so the C code does not depend on the label or the position of the node in the tree.

The format is the same one that Linux uses for ARM boards, so if you have read a Linux device tree, the syntax will look familiar. The differences are in the bindings and in how Zephyr turns the tree into C macros, which is what the rest of this lesson shows.

The files of the Pico, from chip to board

The Pico's description is built from files in three layers, and each layer is a real file in the Zephyr workspace. The first layer is the chip. dts/arm/raspberrypi/rpi_pico/rp2040.dtsi describes the RP2040 itself: its cores, its clocks, its GPIO ports, and its peripherals. For example, the I2C controller i2c0 is defined there with reg = <0x40044000 DT_SIZE_K(4)>, which is a 4 KB block at address 0x40044000, and its compatible is "raspberrypi,pico-i2c" followed by "snps,designware-i2c". Lesson 95 described that DesignWare driver. The GPIO ports are defined in the same file, and their property #gpio-cells = <2> says that each pin reference takes two cells after the port: a pin number and a flags word.

The second layer is the board. boards/raspberrypi/rpi_pico/rpi_pico-common.dtsi turns on the peripherals the Pico uses. It sets current-speed = <115200> on the UART, makes the UART the console, and sets clock-frequency = <I2C_BITRATE_STANDARD> on i2c0. That constant is 100000, which is 100 kHz, from include/zephyr/dt-bindings/i2c/i2c.h. The board's pins are named in boards/raspberrypi/common/rpi_pico-pinctrl-common.dtsi. For the I2C bus, the group i2c0_default sets the pin mux to I2C0_SDA_P4 and I2C0_SCL_P5, which are GP4 and GP5.

The third layer is the LED. boards/raspberrypi/common/rpi_pico-led.dtsi creates a leds node, with a child led0 whose gpios property is <&gpio0 25 GPIO_ACTIVE_HIGH>. That is GP25, and it is active high, so the pin drives the LED when it is high. The same file has the aliases node that names it led0. Lesson 94's blink used exactly that alias.

After the build, all three layers are merged, and the result is in build/zephyr/zephyr.dts. Open it after any build. Each line of the merged file ends with a comment that names the file and line it came from, which is the easiest way to trace a value. For example, the alias led0 reads led0 = &led0; /* in zephyr\boards\raspberrypi\common\rpi_pico-led.dtsi:29 */ in our build.

The rules that control a node

A node with a compatible string is matched to a binding. Zephyr reads the binding files, checks the node's properties against the schema, and generates C macros for the node. This part is easy to miss. A node with no binding is still in the tree, but Zephyr generates no macros for it, so the C code cannot refer to it through the usual helpers. The binding's job is therefore not only to check the node. It is the switch that makes the node usable from C.

The binding files live in folders called bindings. Zephyr's own bindings are in its tree, and an application can add its own in dts/bindings/. The build adds the application folder to the list of devicetree roots, because cmake/modules/pre_dt.cmake puts the application directory in DTS_ROOT, so a binding in the application's dts/bindings folder is found automatically.

The status property is the other switch. A node with status = "disabled" is not turned into a device, and a driver that would use it does not start. The board sets i2c1 to disabled, and i2c0 to "okay". Lesson 94 used the LED node because the board enabled it.

Adding a button with an overlay

The overlay file is boards/rpi_pico.overlay, and the build picks it up automatically for the Pico. An overlay adds to the board's tree or overrides a value in it, and it changes only this application. The board file itself is shared by every project that targets the Pico, so changing it changes them all. That is why changes for one application go in the overlay.

The solution adds a second LED on GP16 and a push button on GP14. The LED is a child of the existing leds node, and the button is a new node with its own buttons parent. The button node needs a binding, and the project supplies one in dts/bindings/input/vnd,user-button.yaml. Here is the button part of the solution's overlay: 

buttons {
    user_button: button_0 {
        compatible = "vnd,user-button";
        gpios = <&gpio0 14 (GPIO_ACTIVE_LOW | GPIO_PULL_UP)>;
        label = "Button";
    };
};
aliases {
    sw0 = &user_button;
};

Line by line. buttons { ... }; adds a container node named buttons to the root. user_button: button_0 is a node with a label, so the overlay can refer to it, and a name, button_0. The compatible line selects the binding. The gpios line is a phandle-array: the first cell is the port, written as the phandle &gpio0, the second is the pin, 14, and the third is a flags word. The flags are GPIO_ACTIVE_LOW and GPIO_PULL_UP, which the macro names in include/zephyr/dt-bindings/gpio/gpio.h. The label is a string for humans. The aliases block gives the name sw0 to the node, and it is the name the C code will use.

The overlay has the LED too. It is a child of leds: led1: led_1 { gpios = <&gpio0 16 GPIO_ACTIVE_HIGH>; label = "Second LED"; };, with the alias led1 = &led1. The pin is GP16, and the LED is active high, the same as the on-board LED.

A worked example: from the overlay to a pin read

Follow the button through the build, with the values as they appear in the merged file. The overlay says <&gpio0 14 (GPIO_ACTIVE_LOW | GPIO_PULL_UP)>. The preprocessor turns the flags into numbers. GPIO_ACTIVE_LOW is bit 0, which is the value 1, and GPIO_PULL_UP is bit 4, which is 16. The sum is 17, written 0x11. Pin 14 is 0xe. So the merged zephyr.dts contains gpios = < &gpio0 0xe 0x11 >;, and the comment next to it names the overlay line that produced it. You can check the arithmetic against the file.

The C code refers to the button as DT_ALIAS(sw0). The alias maps sw0 to the node button_0, and the generated header then has one set of macros for that node. GPIO_DT_SPEC_GET reads the gpios property and builds a struct with three fields: the port, the pin, and the flags. The flags are stored as dt_flags. When the code calls gpio_pin_configure_dt(&button, GPIO_INPUT), the function ORs the stored flags with the flags you pass, so the pull-up and the active-low flag are applied with no extra code (include/zephyr/drivers/gpio.h, line 1208).

Now a press. With the pull-up on, the pin reads high when the button is released, and low when the button connects it to ground. gpio_pin_get_dt() returns the logical level, which takes the active-low flag into account. The header says so: the function returns the logical value, so for an active-low pin a low physical level becomes logical 1 (line 1796, and the description of gpio_pin_get() above it). So a pressed button reads 1, and the code gpio_pin_set_dt(&led1, gpio_pin_get_dt(&button)); lights the second LED while the button is held. The code never names GP14, and it never inverts the value.

Reading the nodes from C

The solution's src/main.c reads the three devices through their aliases:

static const struct gpio_dt_spec led0 = GPIO_DT_SPEC_GET(DT_ALIAS(led0), gpios);
static const struct gpio_dt_spec led1 = GPIO_DT_SPEC_GET(DT_ALIAS(led1), gpios);
static const struct gpio_dt_spec button = GPIO_DT_SPEC_GET(DT_ALIAS(sw0), gpios);

if (gpio_pin_configure_dt(&led0, GPIO_OUTPUT_ACTIVE) < 0 ||
    gpio_pin_configure_dt(&led1, GPIO_OUTPUT_INACTIVE) < 0 ||
    gpio_pin_configure_dt(&button, GPIO_INPUT) < 0) {
    printk("pin configuration failed\n");
    return 0;
}

Each GPIO_DT_SPEC_GET takes an alias and the name of the property, and returns a struct for the first entry in that property. GPIO_OUTPUT_ACTIVE and GPIO_OUTPUT_INACTIVE make the two LEDs outputs, the first starting on and the second starting off. GPIO_INPUT makes the button an input, and the pull-up and active-low flags come from the overlay. The configure calls are combined in one if, so a single failure stops the program with a message.

The loop then does two things. It toggles led0 every 500 ms with a wrap-safe deadline, using the same rule as lesson 73: the code compares signed differences, so the time stays correct when the 32-bit counter wraps. It also copies the button to the second LED every 10 ms with gpio_pin_set_dt(&led1, gpio_pin_get_dt(&button)). The button is read by polling. No driver is bound to the button node, so the code does not use an interrupt for it, and the solution's overlay says so in a comment.

  2. In boards/rpi_pico.overlay, copy the three blocks from the TODO(learner) comment: the led1 node on GP16, the button_0 node on GP14 with compatible = "vnd,user-button", and the aliases led1 and sw0. The binding file is already in dts/bindings/input.

Common mistakes and how to spot them

Mistake 1: no compatible string. A button node without compatible has no binding, so Zephyr generates no GPIO_DT_SPEC macros for it. We built the solution with that line removed. The build failed with undeclared errors for names such as DT_N_S_buttons_S_button_0_P_gpios_IDX_0_VAL_pin. The symptom is a compile failure with a long generated name, and the fix is the compatible line plus the binding file, which is what the solution has.

Mistake 2: a wrong alias name. The macro DT_ALIAS(name) expands to DT_N_ALIAS_ followed by the name. If the overlay defines sw0 and the C code asks for DT_ALIAS(sw1), the name is not defined, and the compiler reports an undeclared identifier that starts with DT_N_ALIAS_. The fix is to make the two names match exactly, and the solution keeps them side by side for that reason.

Mistake 3: a button that reads backwards. If the overlay has GPIO_PULL_UP but not GPIO_ACTIVE_LOW, a press reads 0, and the second LED is on when the button is released and off when it is pressed. The symptom is an inverted response in the simulator. The fix is to add the active-low flag, because the logical value is then the inverse of the physical level. The check is the flags value in zephyr.dts, which should be 0x11 for this button.

Mistake 4: editing the board file. A learner who changes rpi_pico-led.dtsi or rpi_pico.dts for one project changes every project that targets the Pico. The build still passes, so the symptom is a change that surprises a different project later. The fix is to put the change in the overlay, which affects only this application, as the lesson explains.

Mistake 5: an old build after a new binding. A new binding file can be missed by a build that reuses earlier results. If the compiler still reports the old errors after you add the binding, run a clean build with tools/build.py --clean. The clean build is the safe check; do not assume the incremental build has seen the new file.

In real projects

Products that run Zephyr keep one application and one devicetree per board, and the differences between revisions live in the overlays. A new revision of a board that moves a status LED is a change to one file, which the review reads closely, and the C code does not change. Teams also keep a short table of the aliases the application uses, so that the names the code depends on are visible in review. A reviewer looks for three things: a node with no binding that the code uses, a change to a board file that should be an overlay, and an alias that a board does not define, which would break the build for that board.

You changed the Pico's hardware description with an overlay, gave a button a binding, and read both pins from C through aliases without naming a pin number.

Summary

  • A devicetree is a tree of nodes with properties. compatible selects the binding, reg gives an address, status enables or disables a node, and gpios lists a port, a pin and flags.
  • The Pico's description is merged from the chip's file, the board's files and your overlay. The merged result is build/zephyr/zephyr.dts, and each line names its source.
  • A node is usable from C only when it has a compatible and a binding. Without one, the build fails with undeclared generated names.
  • An alias is the name the C code uses, through DT_ALIAS(). Moving a node changes the overlay, not the C code.
  • GPIO_DT_SPEC_GET reads the port, pin and flags from the devicetree. gpio_pin_configure_dt adds the flags to the ones you pass.
  • With GPIO_ACTIVE_LOW, gpio_pin_get_dt() returns logical 1 for a low pin, so a pressed button reads 1.
  • Put changes for one application in boards/<board>.overlay, and leave the shared board files alone.
