Devicetree

A build-time description of the hardware

By the end of this lesson you can add a node in a board overlay, give it an alias, and read it from C with GPIO_DT_SPEC_GET, then find the merged result in build/zephyr/zephyr.dts.

Hardware description outside the C code

Lesson 94 blinked an LED with GPIO_DT_SPEC_GET(DT_ALIAS(led0), gpios), saying only that the alias found the pin, and lesson 95 showed that Kconfig controls which features exist. This lesson covers the other half of a Zephyr application, the description of the hardware, which says which pins go where, which bus each device sits on and which devices exist at all, so that Kconfig answers which features are compiled in while the devicetree answers what is connected to what.

The problem it solves is an old one, because in a firmware project without this separation the status LED's pin number is written into the C code in many files, so when a board revision moves the LED to another pin, every file naming the old pin must change, each change carrying a risk, which a company with five board revisions and three products sharing one firmware cannot live with. A devicetree moves the pin numbers out of the C code into a description that differs from board to board, the C code asking for the status LED by a name and the build finding where that name points.

Nodes, properties and aliases

A devicetree is a tree of nodes, each describing one piece of hardware with a name, optional labels and properties, a property being a name with a value, such as compatible = "vnd,user-button"; or status = "okay";. The glossary defines the term for Zephyr text, the course using the single word devicetree, and the format comes from the devicetree specification, Zephyr's pages being linked in the source list at the end of the lesson.

A devicetree resembles a floor plan of a building written for the software, saying which rooms exist, what each holds and how they connect, so that the same program can find the light switch in any building with a plan, while an overlay is a sticky note on the plan of one particular building saying that this one also has a button by the door. The comparison breaks at the build, though, because a floor plan is consulted while walking around, whereas the devicetree is read once at compile time and turned into C macros, so nothing of it is looked up while the firmware runs.

Four properties carry most of the meaning, compatible being a string naming the kind of device that selects the binding, the schema saying which other properties the node must have, reg giving an address for a device on a memory-mapped bus, status turning a node on with "okay" or off with "disabled" and gpios listing GPIO pins, covered below. A node without compatible is a container that groups other nodes and has no binding of its own.

A label is a short name for a node written before its name, such as user_button: button_0, and a labelled node is referred to with an ampersand, as in &gpio0, the reference being a phandle, a link from one node to another, through which the devicetree says that this LED is on the GPIO port gpio0. An alias is a second name for a node, defined under the aliases node and looked up by the C macro DT_ALIAS(led0), and because the C code uses aliases, it depends on neither the label nor the node's position in the tree.

The format is the one Linux uses for ARM boards, so anyone who has read a Linux device tree will find the syntax familiar, the differences lying in the bindings and in how Zephyr turns the tree into C macros, which the rest of this lesson shows.

The Pico's devicetree files from chip to board

The Pico's description is built from files in three layers, each a real file in the Zephyr workspace, the first being the chip, dts/arm/raspberrypi/rpi_pico/rp2040.dtsi, which describes the RP2040 itself with its cores, clocks, GPIO ports and peripherals. The I2C controller i2c0, for example, is defined there with reg = <0x40044000 DT_SIZE_K(4)>, a 4 KB block at address 0x40044000, and a compatible of "raspberrypi,pico-i2c" followed by "snps,designware-i2c", the DesignWare driver of lesson 95, while the GPIO ports defined in the same file carry the property #gpio-cells = <2>, saying that each pin reference takes two cells after the port, a pin number and a flags word.

The second layer is the board, boards/raspberrypi/rpi_pico/rpi_pico-common.dtsi turning on the peripherals the Pico uses, setting current-speed = <115200> on the UART, making the UART the console and setting clock-frequency = <I2C_BITRATE_STANDARD> on i2c0, a constant of 100000, 100 kHz, from include/zephyr/dt-bindings/i2c/i2c.h. The board's pins are named in boards/raspberrypi/common/rpi_pico-pinctrl-common.dtsi, where the group i2c0_default sets the pin mux of the I2C bus to I2C0_SDA_P4 and I2C0_SCL_P5, GP4 and GP5.

The third layer is the LED, boards/raspberrypi/common/rpi_pico-led.dtsi creating a leds node with a child led0 whose gpios property is <&gpio0 25 GPIO_ACTIVE_HIGH>, GP25, active high, so the pin drives the LED when high, and the same file holding the aliases node that names it led0, exactly the alias lesson 94's blink used.

After the build the three layers are merged into build/zephyr/zephyr.dts, worth opening after any build, because each line of the merged file ends with a comment naming the file and line it came from, the easiest way to trace a value, the alias led0 reading led0 = &led0; /* in zephyr\boards\raspberrypi\common\rpi_pico-led.dtsi:29 */ in our build.

Bindings and the status property

A node with a compatible string is matched to a binding, Zephyr reading the binding files, checking the node's properties against the schema and generating C macros for the node. The part that is easy to miss is that a node without a binding remains in the tree, but Zephyr generates no macros for it, so the C code cannot refer to it through the usual helpers, which makes the binding not only a check of the node but the switch that makes it usable from C.

The binding files live in folders called bindings, Zephyr's own lying in its tree while an application can add its own in dts/bindings/, and since cmake/modules/pre_dt.cmake puts the application directory in DTS_ROOT, the list of devicetree roots, a binding in the application's dts/bindings folder is found automatically.

The status property is the other switch, a node with status = "disabled" not being turned into a device, so a driver that would use it does not start, and the board sets i2c1 to disabled and i2c0 to "okay", while lesson 94 could use the LED node because the board enabled it.

A button added with an overlay

The overlay file is boards/rpi_pico.overlay, picked up automatically by the build for the Pico, adding to the board's tree or overriding a value in it for this application alone. The board file itself is shared by every project targeting the Pico, so changing it changes them all, which is why changes for one application go in the overlay.

The solution adds a second LED on GP16 and a push button on GP14, the LED as a child of the existing leds node and the button as a new node with its own buttons parent, the button node needing a binding, which the project supplies in dts/bindings/input/vnd,user-button.yaml. The button part of the solution's overlay reads as follows. 

buttons {
    user_button: button_0 {
        compatible = "vnd,user-button";
        gpios = <&gpio0 14 (GPIO_ACTIVE_LOW | GPIO_PULL_UP)>;
        label = "Button";
    };
};
aliases {
    sw0 = &user_button;
};

buttons { ... }; adds a container node named buttons to the root, and user_button: button_0 is a node with a label, through which the overlay can refer to it, and a name, button_0, while the compatible line selects the binding. The gpios line is a phandle-array whose first cell is the port, written as the phandle &gpio0, the second the pin, 14, and the third a flags word, here GPIO_ACTIVE_LOW and GPIO_PULL_UP, the macro names from include/zephyr/dt-bindings/gpio/gpio.h. The label is a string for humans, and the aliases block gives the node the name sw0, the name the C code will use.

The overlay also holds the LED as a child of leds, led1: led_1 { gpios = <&gpio0 16 GPIO_ACTIVE_HIGH>; label = "Second LED"; };, with the alias led1 = &led1, on GP16 and active high like the on-board LED.

Worked example: from the overlay to a pin read

The button can be followed through the build with the values as they appear in the merged file. Before working through the steps, predict the flags value that zephyr.dts shows for the button and what gpio_pin_get_dt() returns while it is pressed.

  1. The flags as numbers. The overlay says <&gpio0 14 (GPIO_ACTIVE_LOW | GPIO_PULL_UP)>, and the preprocessor turns the flags into numbers, GPIO_ACTIVE_LOW being bit 0, the value 1, and GPIO_PULL_UP bit 4, the value 16, so their sum is 17, written 0x11, while pin 14 is 0xe.
  2. The merged file. The merged zephyr.dts therefore contains gpios = < &gpio0 0xe 0x11 >;, with a comment naming the overlay line that produced it, so the arithmetic can be checked against the file.
  3. The spec in C. The C code refers to the button as DT_ALIAS(sw0), the alias mapping sw0 to the node button_0, whose macros GPIO_DT_SPEC_GET reads to build a struct with three fields, the port, the pin and the flags, the flags being stored as dt_flags.
  4. The configuration. The call gpio_pin_configure_dt(&button, GPIO_INPUT) ORs the stored flags with the flags passed, so the pull-up and the active-low flag are applied without extra code (include/zephyr/drivers/gpio.h, line 1208).
  5. A press. With the pull-up on, the pin reads high while the button is released and low when the button connects it to ground, and gpio_pin_get_dt() returns the logical level, taking the active-low flag into account, the header saying that for an active-low pin a low physical level becomes logical 1 (line 1796 and the description of gpio_pin_get() above it), so a pressed button reads 1.

The line gpio_pin_set_dt(&led1, gpio_pin_get_dt(&button)); thus lights the second LED while the button is held, although the code never names GP14 and never inverts the value.

Devicetree nodes read from C

The solution's src/main.c reads the three devices through their aliases. 

static const struct gpio_dt_spec led0 = GPIO_DT_SPEC_GET(DT_ALIAS(led0), gpios);
static const struct gpio_dt_spec led1 = GPIO_DT_SPEC_GET(DT_ALIAS(led1), gpios);
static const struct gpio_dt_spec button = GPIO_DT_SPEC_GET(DT_ALIAS(sw0), gpios);

if (gpio_pin_configure_dt(&led0, GPIO_OUTPUT_ACTIVE) < 0 ||
    gpio_pin_configure_dt(&led1, GPIO_OUTPUT_INACTIVE) < 0 ||
    gpio_pin_configure_dt(&button, GPIO_INPUT) < 0) {
    printk("pin configuration failed\n");
    return 0;
}

Each GPIO_DT_SPEC_GET takes an alias and a property name and returns a struct for the first entry in that property, GPIO_OUTPUT_ACTIVE and GPIO_OUTPUT_INACTIVE making the two LEDs outputs, the first starting on and the second off, and GPIO_INPUT making the button an input whose pull-up and active-low flags come from the overlay. The configure calls are combined in one if, so that a single failure stops the program with a message.

The loop toggles led0 every 500 ms with a wrap-safe deadline, by the same rule as lesson 73, comparing signed differences so that the time stays correct when the 32-bit counter wraps, and copies the button to the second LED every 10 ms with gpio_pin_set_dt(&led1, gpio_pin_get_dt(&button)). The button is read by polling, because no driver is bound to the button node, so the code uses no interrupt for it, as a comment in the solution's overlay says.

Try it in Wokwi

The starter blinks led0 and has a TODO(learner) note in the overlay where the second LED and the button go, the wiring already being in the diagram, with the second LED on GP16 through a resistor and the button from GP14 to ground, so you add the overlay nodes and then wire the button to the second LED in the loop.

  1. Open projects/0096-devicetree/starter in VS Code.
  2. In boards/rpi_pico.overlay, copy the three blocks from the TODO(learner) comment, the led1 node on GP16, the button_0 node on GP14 with compatible = "vnd,user-button" and the aliases led1 and sw0, the binding file already being in dts/bindings/input.
  3. In src/main.c, add the two GPIO_DT_SPEC_GET lines that the TODO(learner) comment shows, configure led1 as an output and button as an input, and in the loop set led1 to gpio_pin_get_dt(&button).
  4. Build with Ctrl+Shift+B, open build/zephyr/zephyr.dts and find button_0, whose line should show gpios = < &gpio0 0xe 0x11 > with a comment naming your overlay, then start the simulator, the change having worked when the serial monitor prints DEVICETREE OK and the second LED follows the button.

Common mistakes and how to spot them

A node without a compatible string

The build fails with undeclared errors for long generated names such as DT_N_S_buttons_S_button_0_P_gpios_IDX_0_VAL_pin, which we reproduced by building the solution without that line, because a button node without compatible has no binding, so Zephyr generates no GPIO_DT_SPEC macros for it. Add the compatible line and the binding file, as the solution has.

A wrong alias name

The compiler reports an undeclared identifier starting with DT_N_ALIAS_, because DT_ALIAS(name) expands to DT_N_ALIAS_ followed by the name, so an overlay defining sw0 and C code asking for DT_ALIAS(sw1) leave the name undefined. Make the two names match exactly, which is why the solution keeps them side by side.

A button that reads backwards

The second LED is on while the button is released and off while it is pressed, because the overlay has GPIO_PULL_UP without GPIO_ACTIVE_LOW, so a press reads 0. Add the active-low flag, which makes the logical value the inverse of the physical level, and check the flags value in zephyr.dts, which should be 0x11 for this button.

A board file edited for one project

A different project behaves unexpectedly later, although every build still passes, because a change to rpi_pico-led.dtsi or rpi_pico.dts made for one project changes every project targeting the Pico. Put the change in the overlay, which affects only this application.

An old build after a new binding

The compiler still reports the old errors after a binding has been added, because a build reusing earlier results can miss the new binding file. Run a clean build with tools/build.py --clean, the safe check, rather than assuming that the incremental build has seen the new file.

Overlays and alias tables across board revisions

Products running Zephyr keep one application and one devicetree per board, the differences between revisions living in the overlays, so a new board revision that moves a status LED changes one file, which the review reads closely, while the C code stays the same. Teams also keep a short table of the aliases the application uses, so that the names the code depends on are visible in review, and a reviewer looks for a node without a binding that the code uses, a change to a board file that should be an overlay and an alias that some board does not define, which would break the build for that board.

Summary

  • A devicetree is a tree of nodes with properties, compatible selecting the binding, reg giving an address, status enabling or disabling a node and gpios listing a port, a pin and flags.
  • The Pico's description is merged from the chip's file, the board's files and your overlay into build/zephyr/zephyr.dts, where each line names its source.
  • A node is usable from C only with a compatible and a binding, and without one the build fails with undeclared generated names.
  • An alias is the name the C code uses through DT_ALIAS(), so moving a node changes the overlay rather than the C code.
  • GPIO_DT_SPEC_GET reads the port, pin and flags from the devicetree, and gpio_pin_configure_dt adds the flags to those passed.
  • With GPIO_ACTIVE_LOW, gpio_pin_get_dt() returns logical 1 for a low pin, so a pressed button reads 1.
  • Changes for one application belong in boards/<board>.overlay, leaving the shared board files alone.
