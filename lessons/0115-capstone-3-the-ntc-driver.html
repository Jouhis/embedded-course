Capstone 3: the NTC driver and unit tests

A temperature sensor gives a voltage, and the voltage gives a number that must become a temperature the safety rules can trust. This lesson turns the ADC code of a thermistor into degrees Celsius, checks the conversion against known values on the PC, and shows how a fake replaces the ADC in the test.

By the end of this lesson you can convert a 12-bit NTC reading to hundredths of a degree with the Beta equation, reject open and shorted sensor codes, and write a Unity host test that uses an FFF fake in place of the hardware read.

Where we are and why it matters

Capstone 1 wrote the requirements for the filament dryer. Requirement 2.2 says that an open or shorted temperature sensor must cut the heater and block a start, and that rule can only be met if the code can tell a broken sensor from a real temperature. Capstone 2 (lesson 114) fixed the layers and the pin map. This lesson builds the bottom layer that reads the sensor, and the first piece of pure logic above it. The hardware ideas come from earlier lessons: the voltage divider from lesson 8, the ADC from lesson 58, and host unit tests from lesson 80. The fake that replaces the hardware uses the idea from lesson 81.

Why does this matter in a real product? A chamber reading that is 30 degrees wrong is worse than no reading, because the heater controller and the safety rules both trust it. Most firmware bugs that reach customers do not crash. They print a plausible number that is wrong. Tests on the PC catch that kind of error before any board sees it.

The idea: a driver turns hardware into numbers

A driver is the code that talks to one piece of hardware. Its output should be a plain value with a known meaning, such as an ADC code, a duty cycle or a debounced button level. Everything after the driver works on those values and never on registers. The state machine and the safety checks in this dryer take a temperature in hundredths of a degree and a flag that says whether the sensor is good. They do not know that an ADC exists.

That split is what makes the logic testable. A test passes a number in and checks the number that comes out, on a PC, with no heater attached. The NTC conversion is the cleanest example in this dryer, because it is pure arithmetic: it has no register and no timing. The sensor service in app/sensor.c is the thin layer on top. It reads one ADC code through the hardware abstraction layer (HAL), and then calls the conversion. The HAL is the set of functions in hal.h that the board file implements on the Blue Pill.

The NTC: from an ADC code to degrees Celsius

The sensor is a negative-temperature-coefficient thermistor, called an NTC. Its resistance falls as it warms. The part used here is 10 kΩ at 25 °C, which is the usual reference point. The NTC is wired as a voltage divider with a fixed 10 kΩ series resistor. The series resistor sits between the 3.3 V supply and the output node, which the code calls OUT. The NTC sits between OUT and ground. The 12-bit ADC measures the voltage on OUT.

How the divider turns resistance into a code

A divider puts two resistors in series across a supply. The voltage at the junction is the supply times the lower resistor divided by the total, so a change in either resistor moves the junction voltage (lesson 8). Here the lower resistor is the NTC. When the chamber warms, the NTC resistance falls, the voltage on OUT falls, and the ADC code falls with it. A warm chamber gives a small code and a cold chamber gives a large one. That direction is the first thing to check when a reading looks wrong.

The ADC reports OUT as an integer from 0 to 4095. Code 0 means 0 V and code 4095 means full scale, which is the 3.3 V supply. The code is therefore the OUT voltage as a fraction of full scale, times 4095. Writing the divider in terms of the code gives the relationship the conversion needs. Let full be 4095 and raw be the code. The OUT voltage is 3.3 V times raw divided by full, and it is also 3.3 V times Rntc divided by (Rseries + Rntc). Cancelling the 3.3 V and rearranging gives full ÷ raw = 1 + Rseries ÷ Rntc. So Rntc ÷ Rseries = 1 ÷ (full ÷ raw − 1). The conversion needs only this ratio, which is why the supply voltage does not appear in the code. The ratio is the same at 3.0 V or 3.3 V, as long as the ADC reference matches the supply.

Why a logarithm, and where the beta constant comes from

The third idea is the beta constant, written B. It describes how steeply the NTC resistance changes with temperature. The usual model is R = R25 × eB(1/T − 1/T25), with T in kelvin. The resistance depends exponentially on the reciprocal of the temperature. Taking the natural logarithm of both sides turns the exponential into a straight line: ln(R ÷ R25) = B × (1/T − 1/T25). Solving for 1/T gives the Beta equation: 1/T = ln(R ÷ R25) ÷ B + 1/T25.

That is why the conversion has a logarithm. The divider gives the ratio R ÷ R25, the logarithm undoes the exponential, and the beta constant scales it. The reference temperature T25 is 25 °C, which is 298.15 K, because kelvin is degrees Celsius plus 273.15. The equation is an approximation to the real curve, and its error grows as the temperature moves away from 25 °C. The beta value is printed in the thermistor's datasheet. The Wokwi part defaults to 3950.

The fourth idea is the failure modes. If the sensor is shorted, its resistance is near zero and OUT is pulled to ground, so the code is near zero. If it is open, its resistance is effectively infinite and OUT is pulled up to 3.3 V through the series resistor, so the code is near full scale. Neither value is a temperature. The logarithm of a zero or negative ratio is undefined, so the conversion must refuse those codes rather than return a number.

The Wokwi formula, adapted to 12 bits

The Wokwi docs for the NTC part give the conversion as a short C snippet. It reads the ADC and then computes the temperature with the Beta equation, using a full-scale constant of 1023 and a beta of 3950 Wokwi docs: NTC temperature sensor. The 1023 is the full scale of a 10-bit ADC. The Blue Pill has a 12-bit ADC, so the constant becomes 4095. Nothing else in the formula changes: 

// full = 4095 (12-bit), raw = the ADC code, B = beta (3950), 298.15 K = 25 C
float inv_t = logf(1.0f / (full / (float)raw - 1.0f)) / 3950.0f + 1.0f / 298.15f;
float celsius = 1.0f / inv_t - 273.15f;

The first line is the divider in disguise. The expression full ÷ raw − 1 equals Rseries ÷ Rntc, so its reciprocal is the resistance ratio, and the logarithm of that ratio, divided by B, plus 1 ÷ 298.15, is 1 ÷ T in kelvin. The second line inverts that to kelvin and subtracts 273.15. The beta constant belongs to the thermistor, not to the code, so in a real design it comes from the datasheet of the part that is fitted.

Check the constant. If the code uses 1023 with a 12-bit ADC, the result is wrong in two ways. Above code 1023 the ratio becomes negative, the logarithm is undefined, and the function returns nan, which is not a number. Below 1023 it returns a number that looks plausible and is wrong: a code of 1000 gives −41.08 °C with the 1023 constant, against 52.80 °C with 4095. Lesson 58 made the same mistake on purpose. Write the full-scale constant as a named value, and test a known reading.

A worked example: code 2048

Take code 2048, about half scale. Each step below can be checked on a calculator, and that habit is what catches a wrong constant.

  1. Divide the full scale by the code and subtract 1: 4095 ÷ 2048 − 1 = 1.99951 − 1 = 0.99951.
  2. Take the reciprocal to get Rntc ÷ Rseries: 1 ÷ 0.99951 = 1.00049. The NTC is 1.00049 × 10 kΩ = 10.005 kΩ, very close to the 10 kΩ reference.
  3. Take the natural logarithm: ln(1.00049) = 0.000488. Divide by the beta: 0.000488 ÷ 3950 = 1.24 × 10−7.
  4. Add the reference term: 1 ÷ 298.15 = 0.00335402, so 1 ÷ T = 0.00335414 per kelvin.
  5. Invert to kelvin: 1 ÷ 0.00335414 = 298.139 K. Subtract 273.15: 298.139 − 273.15 = 24.989 °C.

The result is 24.99 °C, which is what the conversion must return to the nearest hundredth. Step 2 shows something worth noticing: the NTC resistance is almost exactly the series resistance, so the temperature is almost exactly the reference temperature. A code near half scale is the easiest one to check by hand.

The code, line by line

Here is the conversion from the reference version of app/ntc.c. The constants are named in the file, and each line of the formula is one line of C. 

if (raw < NTC_RAW_MIN || raw > NTC_RAW_MAX) {
    return false;                          /* open or shorted sensor */
}
float full = (float)NTC_FULL_SCALE_CODE;   /* 4095 */
float inv_t = logf(1.0f / (full / (float)raw - 1.0f)) / NTC_BETA + 1.0f / NTC_T25_KELVIN;
float celsius = 1.0f / inv_t - KELVIN_OFFSET;
*centi_c = (int32_t)lroundf(celsius * 100.0f);
return true;

The if rejects the fault codes: 15 or less, or 4080 or more. The limits are named NTC_RAW_MIN and NTC_RAW_MAX, so the header documents them in one place. The function returns false, and the caller must check that return value before it uses the output. The line that stores full as a float makes the division below a float division. Without the cast, 4095 ÷ 2048 would be integer division and give 1, and the whole conversion would be wrong.

The line with logf computes full ÷ raw − 1, then takes the reciprocal, then the logarithm, then divides by the beta and adds 1 ÷ 298.15. The result is 1 ÷ T in kelvin. The next line inverts it and subtracts KELVIN_OFFSET, which is 273.15, to get degrees Celsius. The final line stores hundredths of a degree. The conversion returns int32_t hundredths, not a float, so the rest of the firmware compares integers. The rounding is done by lroundf(), which rounds to the nearest integer, so 24.989 °C becomes 2499.

The Blue Pill's Cortex-M3 has no floating-point unit, so logf() runs in software and is slow compared with integer code. That is acceptable here, because the sensor is read once every 100 ms.

The fault range and the known values for the tests

A test needs an answer that does not come from the code under test. The values below come from an independent calculation of the same equation in double precision. They are the numbers the host test checks.

The fault range matters as much as the conversion. A code near 0 means OUT is pulled to ground, which is a shorted NTC or a wire to GND. A code near 4095 means OUT is pulled up to 3.3 V through the series resistor, which is an open NTC. The logarithm is undefined at both ends, so the conversion must refuse those codes.

The table also shows what the fault limits do not do. The valid codes from 16 to 4079 convert to temperatures from 239.35 °C down to −62.92 °C. The fault limits exist so that the logarithm never fails, and they say nothing about whether a temperature is plausible for a dryer. The 239 °C end is caught by the over-temperature cutoff in lesson 116. The −62.92 °C end is not caught by any rule in the dryer's safety checks, and lesson 116 returns to that gap.

A pull-up or pull-down that the code does not know about changes which end is the NTC. The conversion above assumes the NTC is the lower resistor, as in the Wokwi part and in lesson 58. If you wire the NTC on top, the same code reads the wrong temperature, and it does so without any error. Check the schematic, not only the code.

Testing with Unity and FFF

The host test project compiles the same app/*.c files as the firmware. That is the rule from lesson 80: the test runs the real code, not a copy. Unity provides the assertions and the test runner, and FFF provides the fakes (lesson 81). Both are plain C and compile with the PC's MinGW gcc. CMock needs Ruby, which this workspace does not install, so the course uses FFF for the hands-on work.

How the test project is built

The project's CMakeLists.txt does three jobs. It builds the application code as a library, it builds one test program for each test file, and it registers each program with CTest, the test runner that comes with CMake. Here is the part that builds the library: 

set(APP ${CMAKE_CURRENT_LIST_DIR}/../../0116-dryer-drivers/starter/app)
add_library(dryer_app STATIC
            ${APP}/ntc.c ${APP}/safety.c ${APP}/control.c ${APP}/dryer.c ${APP}/materials.c
            ${APP}/ui.c ${APP}/debounce.c ${APP}/filters.c ${APP}/format.c)
target_include_directories(dryer_app PUBLIC ${APP})
target_link_libraries(dryer_app PUBLIC m)            # logf and lroundf (the Beta equation)

The first line points at the application folder of the dryer's drivers project, which is where the firmware's own sources live. The add_library line lists the source files that every test links against, so ntc.c is compiled exactly as the firmware compiles it. The target_include_directories line makes ntc.h visible to the tests. The last line links the math library m, which provides logf() and lroundf(). Those two functions are the reason the conversion needs a link step beyond the application's own sources.

The test programs then link against dryer_app and unity, and add_test registers each one. Running python -I tools/build.py <project> --test builds everything and runs CTest, which prints one line per test and a summary. The summary of a passing run reads 100% tests passed out of 8.

A Unity test, line by line

The NTC test file in test/test_ntc.c is short enough to read in full. Its first part sets up the helper and one test: 

static int32_t centi_of(uint16_t raw) {
    int32_t c = -99999;
    TEST_ASSERT_TRUE(ntc_centi_from_raw(raw, &c));
    return c;
}

static void test_half_scale_is_about_25_degrees(void) {
    /* A divider with equal resistors is at R_ntc = 10 kOhm, which is the 25 C reference point. */
    TEST_ASSERT_INT32_WITHIN(5, 2499, centi_of(2048));
}

centi_of() calls the conversion and insists that it succeeded. The starting value of -99999 is a sentinel: if the conversion failed to write the output, the test would see an obviously wrong number rather than a stale zero. TEST_ASSERT_TRUE records a failure and stops the test if the call returned false. The test itself asserts TEST_ASSERT_INT32_WITHIN(5, 2499, centi_of(2048)). Unity's order is delta, expected, actual, so the test passes when the actual value is within 5 hundredths of 2499. The tolerance covers float rounding and the step of the ADC, and it is small enough that a wrong constant of 1023 would fail by tens of degrees.

The file also tests the faults. test_shorted_sensor_is_a_fault asserts that codes 0 and 15 return false, and test_limits_are_valid_readings asserts that codes 16 and 4079 return true. Testing both sides of each limit catches an off-by-one error, which is the most common error at a range boundary.

How a fake replaces the hardware

The conversion itself needs no fake. The sensor service does need one, because sensor_read() calls hal_adc_read_ntc(), and that function reads a register. The register exists only on the Blue Pill, so the PC build cannot link against the board file. The driver test in test/test_drivers.c solves that with an FFF fake. These are the lines that matter: 

DEFINE_FFF_GLOBALS;
FAKE_VALUE_FUNC(uint16_t, hal_adc_read_ntc);   /* a stand-in with this signature */

void setUp(void) {
    RESET_FAKE(hal_adc_read_ntc);
}

hal_adc_read_ntc_fake.return_val = 2048u;       /* the next call returns this code */
...
TEST_ASSERT_EQUAL_INT(1, hal_adc_read_ntc_fake.call_count);   /* exactly one conversion */

DEFINE_FFF_GLOBALS creates the bookkeeping that FFF needs, once per test program. FAKE_VALUE_FUNC is an FFF macro. It creates a function with the same name and return type as hal_adc_read_ntc(), which the linker uses in place of the board file's version. It also creates a struct named hal_adc_read_ntc_fake that records what happened. RESET_FAKE clears that record in setUp(), which Unity calls before every test, so one test cannot leave a call count behind for the next. Lesson 81 introduced the same pattern with a different function.

Setting return_val scripts the answer to the next call. That is how the test chooses the ADC code, and it is the only way the test can reach the 15-or-less and 4080-or-more branches on a PC, because no real sensor is attached. The last line checks call_count, the number of times the code under test called the fake. A driver that converted twice would still produce the right temperature and pass a value check, but it would fail this one. That is why the record is worth keeping. The test calls the real sensor_read() in app/sensor.c, so the path under test is the firmware's own.

Hint for the conversion

Reject the fault codes first. Then compute the three steps in order, in floats: the ratio full ÷ raw − 1, the logarithm of its reciprocal divided by the beta, and the inverse of the sum with 1 ÷ 298.15. The last step multiplies by 100 and rounds. The test for code 2048 accepts 2494 to 2504, so a small rounding difference passes. A difference of tens of degrees means the constant or the reciprocal is wrong.

Hint for a failing test

Print the value your function returns for code 2048 with a temporary printf in a copy of the test, not in the project. Compare it with 2499. If you get 24 or 0, the function is not multiplying by 100. If you get a huge number, check that the float cast is on full.

Common mistakes and how to spot them

1. The 10-bit constant. Symptom: the serial log prints nan for some codes, or a temperature that is wrong by tens of degrees. For example, code 1000 gives −41.08 °C instead of 52.80 °C. Fix: name the full-scale constant 4095, and check that code 2048 gives 24.99 °C.

2. The divider wired the other way. Symptom: the temperature falls as the chamber warms. The formula assumes the NTC is the lower resistor. Fix: check the schematic first. If the NTC is on top, the formula must change, and a test with a known warm code shows the error at once.

3. Ignoring the return value. Symptom: the log shows 0.00 °C during a sensor fault, and the heater acts on it. The fault path of sensor_read() sets the output to zero before it calls the conversion, and the conversion leaves the output alone when it returns false. A caller that ignores the boolean gets 0.00 °C and no warning. Fix: test the return value before using the temperature, as the test's TEST_ASSERT_FALSE lines do.

4. Degrees instead of hundredths. Symptom: the host test fails by about 2475, because the function returned 24 for a reading of 24.99 °C. If the logging code divides the stored value by 100 to print it, the log shows 0.24 °C. Fix: keep the conversion in hundredths, multiply by 100 and round with lroundf() before the cast, and keep the unit in the variable name.

5. Testing a copy of the code. Symptom: all the tests pass, but the firmware prints the wrong temperature. Cause: the test pasted its own copy of the formula, so it tested the copy. Fix: compile the same app/ files in both builds, as this project does, and never write the formula into a test. A test should check a number that came from somewhere else, such as the independent table above.

In real projects

Production firmware usually reads thermistors in one of two ways. Some use a lookup table of ADC codes against temperature, filled from the manufacturer's table and interpolated between the entries. Others use the Steinhart-Hart equation, a fit with three coefficients, because a single beta value is an approximation whose error grows away from the reference temperature. A reviewer will ask which of these you used, over what temperature range it is valid, and where the coefficients came from.

Teams that test firmware keep the conversion and the safety rules as pure functions, so that known values can be checked on a PC in milliseconds, as this lesson does. The tests are a first gate. A board test, with a real thermistor in a heated block, is still needed to find wiring and calibration errors that no PC test can see.

Summary

  • A thermistor and a fixed resistor form a voltage divider, and the ADC code is the OUT voltage as a fraction of full scale.
  • The divider gives the ratio Rntc ÷ Rseries = 1 ÷ (full ÷ raw − 1), which the Beta equation turns into a temperature.
  • The full-scale constant must match the ADC: 4095 for 12 bits, not 1023. Test a known code to catch a wrong constant.
  • The conversion refuses fault codes, because the logarithm of a zero or negative ratio has no meaning, and the caller must check the return value.
  • The conversion returns hundredths of a degree as an integer, rounded with lroundf().
  • Fault limits protect the logarithm. They do not check that a temperature is plausible.
  • A host test compiles the real app/ files, checks independent known values, and uses an FFF fake for the ADC read.
