Capstone 3: the NTC driver and unit tests

Thermistor conversion tested on the host

By the end of this lesson you can convert a 12-bit NTC reading to hundredths of a degree with the Beta equation, reject open and shorted sensor codes, and write a Unity host test that uses an FFF fake in place of the hardware read.

A sensor reading the safety rules can trust

Capstone 1 wrote the requirements for the filament dryer, requirement 2.2 saying that an open or shorted temperature sensor must cut the heater and block a start, a rule that can be met only if the code can tell a broken sensor from a real temperature, while capstone 2 (lesson 114) fixed the layers and the pin map. This lesson builds the bottom layer reading the sensor and the first piece of pure logic above it, using the voltage divider from lesson 8, the ADC from lesson 58 and host unit tests from lesson 80, with a fake replacing the hardware as in lesson 81.

A chamber reading 30 degrees wrong is worse than no reading, because the heater controller and the safety rules both trust it, and most firmware bugs that reach customers do not crash but print a plausible number that is wrong, an error that tests on the PC catch before any board sees it.

Drivers that turn hardware into numbers

A driver is the code that talks to one piece of hardware, its output being a plain value with a known meaning, such as an ADC code, a duty cycle or a debounced button level, so that everything after the driver works on those values and never on registers. The state machine and the safety checks in this dryer take a temperature in hundredths of a degree and a flag saying whether the sensor is good, without knowing that an ADC exists.

That split is what makes the logic testable, a test passing a number in and checking the number that comes out on a PC with no heater attached, and the NTC conversion is the cleanest example in this dryer, because it is pure arithmetic with no register and no timing. The sensor service in app/sensor.c is the thin layer on top, reading one ADC code through the hardware abstraction layer (HAL), the set of functions in hal.h that the board file implements on the Blue Pill, and then calling the conversion.

The NTC and its divider

The sensor is a negative-temperature-coefficient thermistor, an NTC, whose resistance falls as it warms, the part used here being 10 kΩ at 25 °C, the usual reference point. It is wired as a voltage divider with a fixed 10 kΩ series resistor between the 3.3 V supply and the output node, which the code calls OUT, the NTC sitting between OUT and ground, and the 12-bit ADC measuring the voltage on OUT.

From resistance to an ADC code

A divider puts two resistors in series across a supply, the junction voltage being the supply times the lower resistor divided by the total, so a change in either resistor moves the junction voltage (lesson 8), and here the lower resistor is the NTC, so when the chamber warms, the NTC resistance falls, the voltage on OUT falls and the ADC code with it. A warm chamber therefore gives a small code and a cold chamber a large one, the first thing to check when a reading looks wrong.

The ADC reports OUT as an integer from 0 to 4095, code 0 meaning 0 V and code 4095 full scale, the 3.3 V supply, so the code is the OUT voltage as a fraction of full scale times 4095. The OUT voltage is both 3.3 V × raw ÷ full and 3.3 V × Rntc ÷ (Rseries + Rntc), and cancelling the 3.3 V and rearranging gives full ÷ raw = 1 + Rseries ÷ Rntc, so

Rntc ÷ Rseries = 1 ÷ (full ÷ raw − 1)(1)

where full is 4095 and raw the ADC code. The conversion needs only this ratio, which is why the supply voltage does not appear in the code, the ratio being the same at 3.0 V or 3.3 V as long as the ADC reference matches the supply.

The Beta equation

The beta constant, written B, describes how steeply the NTC resistance changes with temperature, the usual model being

R = R25 × eB(1/T − 1/T25)(2)

where R is the NTC resistance, R25 its resistance at the reference temperature T25 and T the temperature in kelvin, so the resistance depends exponentially on the reciprocal of the temperature. Taking the natural logarithm of both sides turns the exponential into a straight line, ln(R ÷ R25) = B × (1/T − 1/T25), and solving for 1/T gives the Beta equation

1/T = ln(R ÷ R25) ÷ B + 1/T25(3)

where the divider gives the ratio R ÷ R25, the logarithm undoes the exponential and the beta constant scales it, which is why the conversion has a logarithm. The reference temperature T25 is 25 °C, 298.15 K, because kelvin is degrees Celsius plus 273.15, and the equation approximates the real curve with an error that grows as the temperature moves away from 25 °C, the beta value being printed in the thermistor's datasheet and the Wokwi part defaulting to 3950.

The failure modes follow from the divider, a shorted sensor having a resistance near zero, so that OUT is pulled to ground and the code is near zero, while an open sensor has an effectively infinite resistance, so that OUT is pulled up to 3.3 V through the series resistor and the code is near full scale. Neither value is a temperature, and since the logarithm of a zero or negative ratio is undefined, the conversion must refuse those codes rather than return a number.

The Wokwi formula for a 12-bit ADC

The Wokwi docs for the NTC part give the conversion as a short C snippet that reads the ADC and computes the temperature with the Beta equation, using a full-scale constant of 1023 and a beta of 3950 Wokwi docs: NTC temperature sensor, 1023 being the full scale of a 10-bit ADC, so for the Blue Pill's 12-bit ADC the constant becomes 4095, with nothing else in the formula changing. 

// full = 4095 (12-bit), raw = the ADC code, B = beta (3950), 298.15 K = 25 C
float inv_t = logf(1.0f / (full / (float)raw - 1.0f)) / 3950.0f + 1.0f / 298.15f;
float celsius = 1.0f / inv_t - 273.15f;

The first line is the divider in disguise, the expression full ÷ raw − 1 equalling Rseries ÷ Rntc, so its reciprocal is the resistance ratio of equation (1), and the logarithm of that ratio divided by B plus 1 ÷ 298.15 is 1 ÷ T in kelvin, which the second line inverts and converts by subtracting 273.15. The beta constant belongs to the thermistor rather than the code, so in a real design it comes from the datasheet of the part that is fitted.

Check the constant. If the code uses 1023 with a 12-bit ADC, the result is wrong in two ways. Above code 1023 the ratio becomes negative, the logarithm is undefined, and the function returns nan, which is not a number. Below 1023 it returns a number that looks plausible and is wrong: a code of 1000 gives −41.08 °C with the 1023 constant, against 52.80 °C with 4095. Lesson 58 made the same mistake on purpose. Write the full-scale constant as a named value, and test a known reading.

Worked example: code 2048

Code 2048 is about half scale, and each step below can be checked on a calculator, a habit that catches a wrong constant. Before following the steps, predict roughly what temperature half scale gives with a 10 kΩ series resistor and a 10 kΩ NTC.

  1. The ratio. Divide the full scale by the code and subtract 1: 4095 ÷ 2048 − 1 = 1.99951 − 1 = 0.99951.
  2. The resistance. The reciprocal gives Rntc ÷ Rseries = 1 ÷ 0.99951 = 1.00049, so the NTC is 1.00049 × 10 kΩ = 10.005 kΩ, very close to the 10 kΩ reference.
  3. The logarithm. ln(1.00049) = 0.000488, which divided by the beta gives 0.000488 ÷ 3950 = 1.24 × 10−7.
  4. The reference term. Adding 1 ÷ 298.15 = 0.00335402 gives 1 ÷ T = 0.00335414 per kelvin.
  5. The temperature. Inverting gives 1 ÷ 0.00335414 = 298.139 K, and subtracting 273.15 gives 298.139 − 273.15 = 24.989 °C.

The result is 24.99 °C, which the conversion must return to the nearest hundredth, and step 2 shows why, since the NTC resistance is almost exactly the series resistance, so the temperature is almost exactly the reference temperature, which makes a code near half scale the easiest one to check by hand.

The conversion code

The conversion from the reference version of app/ntc.c names its constants in the file, each line of the formula being one line of C. 

if (raw < NTC_RAW_MIN || raw > NTC_RAW_MAX) {
    return false;                          /* open or shorted sensor */
}
float full = (float)NTC_FULL_SCALE_CODE;   /* 4095 */
float inv_t = logf(1.0f / (full / (float)raw - 1.0f)) / NTC_BETA + 1.0f / NTC_T25_KELVIN;
float celsius = 1.0f / inv_t - KELVIN_OFFSET;
*centi_c = (int32_t)lroundf(celsius * 100.0f);
return true;

The if rejects the fault codes, 15 or less or 4080 or more, the limits being named NTC_RAW_MIN and NTC_RAW_MAX, so that the header documents them in one place, and the function returns false, a value the caller must check before using the output. Storing full as a float makes the division below a float division, because without the cast 4095 ÷ 2048 would be integer division giving 1, and the whole conversion would be wrong.

The line with logf computes full ÷ raw − 1, takes the reciprocal and the logarithm, divides by the beta and adds 1 ÷ 298.15, giving 1 ÷ T in kelvin, which the next line inverts, subtracting KELVIN_OFFSET, 273.15, to get degrees Celsius, and the final line stores hundredths of a degree. The conversion returns int32_t hundredths rather than a float, so that the rest of the firmware compares integers, the rounding being done by lroundf(), which rounds to the nearest integer, so 24.989 °C becomes 2499.

The Blue Pill's Cortex-M3 has no floating-point unit, so logf() runs in software and is slow compared with integer code, which is acceptable here, because the sensor is read once every 100 ms.

The fault range and the known test values

A test needs an answer that does not come from the code under test, so the values below come from an independent calculation of the same equation in double precision, and they are the numbers the host test checks.

1000Warm: the NTC resistance is much lower52.80 °C

The fault range matters as much as the conversion, a code near 0 meaning that OUT is pulled to ground by a shorted NTC or a wire to GND, and a code near 4095 that OUT is pulled up to 3.3 V through the series resistor by an open NTC, the logarithm being undefined at both ends, so the conversion must refuse those codes.

The table also shows what the fault limits do not do, the valid codes from 16 to 4079 converting to temperatures from 239.35 °C down to −62.92 °C, because the limits exist so that the logarithm never fails and say nothing about whether a temperature is plausible for a dryer. The 239 °C end is caught by the over-temperature cutoff in lesson 116, whereas the −62.92 °C end is caught by no rule in the dryer's safety checks, a gap lesson 116 returns to.

A pull-up or pull-down that the code does not know about changes which end is the NTC. The conversion above assumes the NTC is the lower resistor, as in the Wokwi part and in lesson 58. If you wire the NTC on top, the same code reads the wrong temperature, and it does so without any error. Check the schematic, not only the code.

Testing with Unity and FFF

The host test project compiles the same app/*.c files as the firmware, following the rule from lesson 80 that the test runs the real code rather than a copy, Unity providing the assertions and the test runner and FFF the fakes (lesson 81). Both are plain C and compile with the PC's MinGW gcc, whereas CMock needs Ruby, which this workspace does not install, so the course uses FFF for the hands-on work.

The test project's CMake build

The project's CMakeLists.txt builds the application code as a library, builds one test program for each test file and registers each program with CTest, the test runner that comes with CMake, the part building the library looking like this. 

set(APP ${CMAKE_CURRENT_LIST_DIR}/../../0116-dryer-drivers/starter/app)
add_library(dryer_app STATIC
            ${APP}/ntc.c ${APP}/safety.c ${APP}/control.c ${APP}/dryer.c ${APP}/materials.c
            ${APP}/ui.c ${APP}/debounce.c ${APP}/filters.c ${APP}/format.c)
target_include_directories(dryer_app PUBLIC ${APP})
target_link_libraries(dryer_app PUBLIC m)            # logf and lroundf (the Beta equation)

The first line points at the application folder of the dryer's drivers project, where the firmware's own sources live, and the add_library line lists the source files every test links against, so ntc.c is compiled exactly as the firmware compiles it, while the target_include_directories line makes ntc.h visible to the tests. The last line links the math library m, which provides logf() and lroundf(), the two functions that make the conversion need a link step beyond the application's own sources.

The test programs then link against dryer_app and unity, add_test registering each one, and running python -I tools/build.py <project> --test builds everything and runs CTest, which prints one line per test and a summary reading 100% tests passed out of 8 for a passing run.

The NTC test file

The NTC test file in test/test_ntc.c is short enough to read in full, its first part setting up the helper and one test. 

static int32_t centi_of(uint16_t raw) {
    int32_t c = -99999;
    TEST_ASSERT_TRUE(ntc_centi_from_raw(raw, &c));
    return c;
}

static void test_half_scale_is_about_25_degrees(void) {
    /* A divider with equal resistors is at R_ntc = 10 kOhm, which is the 25 C reference point. */
    TEST_ASSERT_INT32_WITHIN(5, 2499, centi_of(2048));
}

centi_of() calls the conversion and insists that it succeeded, the starting value of -99999 being a sentinel, so that a conversion failing to write the output shows an obviously wrong number rather than a stale zero, while TEST_ASSERT_TRUE records a failure and stops the test if the call returned false. The test itself asserts TEST_ASSERT_INT32_WITHIN(5, 2499, centi_of(2048)), Unity's order being delta, expected, actual, so the test passes when the actual value is within 5 hundredths of 2499, a tolerance covering float rounding and the step of the ADC yet small enough that a wrong constant of 1023 fails by tens of degrees.

The file also tests the faults, test_shorted_sensor_is_a_fault asserting that codes 0 and 15 return false and test_limits_are_valid_readings that codes 16 and 4079 return true, testing both sides of each limit catching an off-by-one error, the most common error at a range boundary.

A fake in place of the ADC read

The conversion itself needs no fake, whereas the sensor service does, because sensor_read() calls hal_adc_read_ntc(), which reads a register that exists only on the Blue Pill, so the PC build cannot link against the board file, a problem the driver test in test/test_drivers.c solves with an FFF fake, of which these are the lines that matter. 

DEFINE_FFF_GLOBALS;
FAKE_VALUE_FUNC(uint16_t, hal_adc_read_ntc);   /* a stand-in with this signature */

void setUp(void) {
    RESET_FAKE(hal_adc_read_ntc);
}

hal_adc_read_ntc_fake.return_val = 2048u;       /* the next call returns this code */
...
TEST_ASSERT_EQUAL_INT(1, hal_adc_read_ntc_fake.call_count);   /* exactly one conversion */

DEFINE_FFF_GLOBALS creates the bookkeeping FFF needs, once per test program, and FAKE_VALUE_FUNC is an FFF macro creating a function with the same name and return type as hal_adc_read_ntc(), which the linker uses in place of the board file's version, together with a struct named hal_adc_read_ntc_fake recording what happened. RESET_FAKE clears that record in setUp(), which Unity calls before every test, so that one test cannot leave a call count behind for the next, the same pattern lesson 81 introduced with a different function.

Setting return_val scripts the answer to the next call, which is how the test chooses the ADC code and the only way it can reach the 15-or-less and 4080-or-more branches on a PC, since no real sensor is attached, and the last line checks call_count, the number of times the code under test called the fake. A driver converting twice would still produce the right temperature and pass a value check but fail this one, which is why the record is worth keeping, and since the test calls the real sensor_read() in app/sensor.c, the path under test is the firmware's own.

Hint for the conversion

Reject the fault codes first. Then compute the three steps in order, in floats: the ratio full ÷ raw − 1, the logarithm of its reciprocal divided by the beta, and the inverse of the sum with 1 ÷ 298.15. The last step multiplies by 100 and rounds. The test for code 2048 accepts 2494 to 2504, so a small rounding difference passes. A difference of tens of degrees means the constant or the reciprocal is wrong.

Hint for a failing test

Print the value your function returns for code 2048 with a temporary printf in a copy of the test, not in the project. Compare it with 2499. If you get 24 or 0, the function is not multiplying by 100. If you get a huge number, check that the float cast is on full.

Common mistakes and how to spot them

The 10-bit constant

The serial log prints nan for some codes, or a temperature wrong by tens of degrees, code 1000 for example giving −41.08 °C instead of 52.80 °C, because the code uses the 10-bit full scale of 1023. Name the full-scale constant 4095, and check that code 2048 gives 24.99 °C.

The divider wired the other way

The temperature falls as the chamber warms, because the NTC is on top of the divider while the formula assumes it is the lower resistor. Check the schematic first, and if the NTC is on top, change the formula, a test with a known warm code showing the error at once.

An ignored return value

The log shows 0.00 °C during a sensor fault and the heater acts on it, because the fault path of sensor_read() sets the output to zero before calling the conversion, which leaves the output alone when it returns false, so a caller ignoring the boolean gets 0.00 °C without any warning. Test the return value before using the temperature, as the test's TEST_ASSERT_FALSE lines do.

Degrees instead of hundredths

The host test fails by about 2475, because the function returned 24 for a reading of 24.99 °C, and if the logging code divides the stored value by 100 to print it, the log shows 0.24 °C. Keep the conversion in hundredths, multiplying by 100 and rounding with lroundf() before the cast, and keep the unit in the variable name.

A test of a copy of the code

All the tests pass but the firmware prints the wrong temperature, because the test pasted its own copy of the formula and so tested the copy. Compile the same app/ files in both builds, as this project does, and never write the formula into a test, which should check a number that came from somewhere else, such as the independent table above.

Lookup tables, Steinhart-Hart and board tests

Production firmware usually reads thermistors in one of two ways, some using a lookup table of ADC codes against temperature, filled from the manufacturer's table and interpolated between the entries, and others the Steinhart-Hart equation, a fit with three coefficients, because a single beta value is an approximation whose error grows away from the reference temperature. A reviewer will ask which of these you used, over what temperature range it is valid and where the coefficients came from.

Teams that test firmware keep the conversion and the safety rules as pure functions, so that known values can be checked on a PC in milliseconds, as this lesson does, the tests being a first gate, whereas a board test with a real thermistor in a heated block is still needed to find wiring and calibration errors that no PC test can see.

Summary

  • A thermistor and a fixed resistor form a voltage divider, and the ADC code is the OUT voltage as a fraction of full scale.
  • The divider gives the ratio Rntc ÷ Rseries = 1 ÷ (full ÷ raw − 1), which the Beta equation turns into a temperature.
  • The full-scale constant must match the ADC, 4095 for 12 bits rather than 1023, and a test of a known code catches a wrong constant.
  • The conversion refuses fault codes, because the logarithm of a zero or negative ratio has no meaning, and the caller must check the return value.
  • The conversion returns hundredths of a degree as an integer, rounded with lroundf().
  • Fault limits protect the logarithm without checking that a temperature is plausible.
  • A host test compiles the real app/ files, checks independent known values and uses an FFF fake for the ADC read.
