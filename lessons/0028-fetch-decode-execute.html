Fetch, decode, execute

The three phases of every instruction

By the end of this lesson you can predict the program counter and a destination register after each phase of a simple instruction, then check your prediction in the CPU simulator.

One instruction from memory to result

The last three lessons supplied the parts the CPU needs. Lesson 26 built the ALU that computes results and flags, lesson 25 showed that a register is a row of flip-flops copying a value on an edge, and lesson 27 showed the buses that carry a fetch from memory. This lesson puts those parts in order, following what the CPU does step by step for one instruction and where in that sequence a register actually changes.

The practical reason is the debugger, which shows the CPU's state between steps. When you single-step a function in GDB, the program counter moves, a register changes and a flag is set, and making sense of that requires knowing which happens in which phase. Someone who believes a register changes when the instruction is fetched looks for a value that has not arrived yet, whereas someone who knows the order can predict the next state, and that prediction is the skill this lesson trains.

The program counter and the instruction register

The CPU runs instructions one at a time in a loop, and the address of the current instruction lives in the program counter (PC). On Arm cores the PC is register R15, which the glossary defines as the register holding the address of the instruction being executed, where a write to it causes a branch. Every instruction moves the PC onwards, either to the next instruction in memory or to a branch target.

A CPU follows a program much as you follow a recipe card with a finger on the next step: read the step, work out what it asks, do it, and move the finger down a line. The finger is the program counter, and a step such as "go back to step 3" is a branch that moves the finger instead of letting it slide to the next line. The comparison breaks on timing, because a cook finishes one step before reading the next, while a real core already reads ahead, as the end of this lesson shows.

The second register involved is the instruction register (IR). It is not one of the programmer's registers but a holding area inside the core that keeps the bits of the current instruction while the control logic works on them. C code never sees it, although a debugger showing the disassembly of the current instruction is effectively displaying its contents.

Each instruction passes through three phases. In the fetch phase the CPU reads the instruction at the address in the PC into the IR. In the decode phase it works out what the bits mean: the operation, the source registers, the destination register and any immediate constant. In the execute phase it performs the operation, writes the result to the destination, updates the flags and either moves the PC on or changes it for a branch. These are the logical phases of one instruction. A real pipeline overlaps them, so while one instruction executes the next is already being decoded, as lesson 30 explains.

Arm's Cortex-M3 Technical Reference Manual uses the same names. Section 1.3 lists "the Fetch stage, the Decode stage, the Execute stage" as the pipeline stages of the M3, and the core is described as having a three-stage pipeline (Arm Cortex-M3 TRM DDI0337G, section 1.2.1 and section 1.3). Section 1.4 describes the prefetch unit, which fetches ahead of the instruction being executed, and that unit is where the real core departs from the simple three-phase model used here.

The hardware behind each phase

Each phase uses circuits from earlier lessons, and knowing which circuit does what tells you which register can change when.

During fetch, the PC drives the address bus, as lesson 27 described. Memory returns the instruction's bits on the data bus, and they are copied into the IR on a clock edge, the flip-flop behaviour of lesson 24. No program register changes, and in this model even the PC stays put, because the core has not yet found out how long the instruction is: a Thumb instruction can be 16 or 32 bits, so the PC advances only once the size is known.

During decode, the bits in the IR go to the control logic. The opcode bits select the operation, the register-number fields choose which registers to read through multiplexers like those of lesson 23, and any immediate field is expanded into a 32-bit value. Decode reads registers and prepares the ALU inputs without writing any register, which matters when stepping through code, because a destination register named in decode has not yet changed.

During execute, the ALU runs the operation on the two operands, as lesson 26 described. The result is written to the destination register on a clock edge, the flags are updated at the same moment, and the PC is set to the next address or to the branch target. Execute is therefore the only phase in which a register changes.

Instruction size and the PC step

Instructions occupy memory, so the PC must move by the size of the instruction just executed. The Thumb instruction set has 16-bit and 32-bit instructions, and the Cortex-M3 implements Thumb-2, which mixes the two (see the glossary entry for Thumb-2). The size can be read only from the bits of the first halfword, which decode examines, so in this model the PC moves during execute, once the size is known, rather than during fetch.

The simulator in this lesson is a teaching model rather than a Cortex-M, and it differs from the real core in four ways worth knowing. First, it updates the PC during execute, so the PC stays on the current instruction while that instruction is fetched and decoded. Second, every instruction is 2 bytes, the size of a 16-bit Thumb instruction, and the instruction set is a small subset with no 32-bit instructions. Third, its memory map is a toy, with code at 0x0, 64 words of RAM at 0x20000000 and a GPIO register at 0x40000000. Fourth, its MOV accepts any 32-bit constant, which a real 16-bit MOV cannot encode: a real 16-bit MOV takes an 8-bit immediate, as lesson 29 shows, and a larger constant is loaded on a real core from a literal pool in code memory with an LDR.

The Step button runs one phase and the Instruction button runs all three phases of one instruction, and in both cases the EXECUTE phase is where a register changes.

Worked example: two plus three, phase by phase

The simulator program in the hands-on section has four instructions and a halt. It sets R0 to 2, adds 3 to R0, writes R0 to the GPIO output register and halts, and we trace the first two instructions using the simulator's PC values. Each instruction is 2 bytes, so the first sits at address 0 and the second at address 2. Before reading the table, predict on which press R0 first shows 2.

6EXECUTER0 = 2 + 3 = 5; N, Z, C and V all clear45

Reading the table row by row, the PC stays at 0 for the first two presses, because it moves only in execute, and becomes 2 at the third press, when the MOV has run. R0 likewise stays unchanged until the third press: decode names R0 and reads the immediate, but the register is written only in execute. The ADD then repeats the pattern, with the fetch at press 4 reading address 2, R0 still at 2 after press 5, and the value 5 appearing at press 6.

The flags follow the same rule. The MOV sets N and Z from its result of 2, so both are clear, and the ADD sets all four flags from its result of 5, none of them set because 5 is positive and non-zero with no carry out and no signed overflow, which you can check against the ALU rules of lesson 26.

After six presses the PC is 4, pointing at the MOV R1 at address 4, and the pattern continues unchanged. A program is nothing more than this loop, run once per instruction, with each instruction's effect appearing in a predictable phase.

Try it in the CPU simulator

The program sets R0 to 2, adds 3 and writes the result to the LEDs. Press Reset, and make a prediction before each press; the phase row shows which of the three phases is running, and the message line describes each phase as it runs.

  1. From reset, press Step once. The FETCH phase lights up while the PC still reads 0. Predict R0 after the third Step, when the EXECUTE phase runs for the MOV, then press Step twice more and check that R0 = 2 and the PC = 2.
  2. Press Instruction once to run the whole MOV, after which the PC moves on to 2, then press Instruction again to run the ADD. Predict R0 first; it should be 5 when the ADD finishes.
  3. Press Instruction twice more, the first press running MOV R1, #0x40000000 and the second the STR. Count the lit LEDs after the STR: 5 is 0b101, so two LEDs should be on.

The diagram above the registers draws the CPU as blocks. After each Step, the wires that carried data in that phase light up and show their values, so you can follow where the instruction goes during fetch, which registers decode selects and which path the result takes back during execute.

Hint

The PC changes only in the execute phase, so it reads 0 after the first Step, and registers also change only in execute, so the value appears on the third press of a Step cycle rather than the first. The B . at the end parks the program on purpose, and the simulator's report that it is branching to itself is the normal way to stop, not an error.

It is worth comparing the simulator with a real Cortex-M, whose PC bookkeeping differs because the real core fetches ahead. The prefetch unit buffers up to three word fetches (Cortex-M3 TRM section 1.4), so the memory system is already reading the next instructions while the current one executes. Read that section before trusting a PC value from a debugger on hardware, and see lesson 32 for real PC values in a disassembly.

Common mistakes and how to spot them

The PC expected to move on the fetch

After one press of Step the PC still reads 0, and the simulator seems stuck. The PC moves in the execute phase, so two more presses of Step change it.

The register expected to change in decode

After stepping past the DECODE of the ADD, R0 still equals 2, and it looks as though the ADD did nothing. Decode names the destination register, but the value is written in execute, so one more step makes R0 equal 5.

The halt mistaken for a crash

After the STR the program reaches B . and the simulator keeps showing the same branch, which looks like a freeze. A branch to itself is the simulator's way of parking the program, and Reset runs it again.

Every instruction assumed to be 4 bytes

You expect the PC to read 4 after the first instruction, assuming 32-bit instructions, but the simulator shows 2. Cortex-M runs only Thumb code, whose instructions are 16 or 32 bits under Thumb-2, and the simulator uses only 2-byte instructions. On a real Cortex-M3 the size depends on the encoding, so read it from the disassembly or the encoding rather than guessing.

A large constant written as an immediate

MOV R1, #0x40000000 works in the simulator, but the real toolchain rejects it because a 16-bit MOV cannot hold that constant. The simulator's wider MOV is a convenience of the model, and on the real core a large constant is loaded with LDR from a literal pool.

The phase model in debugging and performance work

When a debugger stops a program, it shows the PC of the next instruction to execute or of the one that just ran, depending on the core and the stop point. Engineers learn to read this by stepping one instruction at a time and checking the registers after each step, and the phase model of this lesson is the mental picture behind those steps. Lesson 54 covers GDB debugging.

Performance work rests on the same model. A taken branch forces the core to discard the instructions it has fetched past the branch, and that cost is the subject of lesson 30. A reviewer reading a hot loop therefore asks how many instructions each iteration executes and where the branches are, because each taken branch changes the PC and invalidates the fetches behind it.

Summary

  • The program counter (PC) holds the address of the instruction being executed, and the instruction register (IR) holds its bits while the core works on them.
  • Fetch reads the instruction at the PC into the IR and changes no programmer-visible register.
  • Decode works out the operation, the source registers and the destination, and prepares the ALU inputs without writing a register.
  • Execute performs the operation, writes the destination, updates the flags and moves the PC.
  • In the simulator the PC moves in execute, while on a real Cortex-M3 the prefetch unit fetches ahead, so a debugger's PC needs care.
  • The simulator's instructions are 2 bytes and its MOV is wider than a real 16-bit MOV, so a real core loads a large constant with LDR.
