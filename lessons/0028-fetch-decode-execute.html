Fetch, decode, execute

Every instruction goes through the same three phases. If you can predict the program counter and the registers after each phase, you can follow any Cortex-M program in a debugger.

By the end of this lesson you can predict the program counter and a destination register after each phase of a simple instruction, then check your prediction in the CPU simulator.

Where we are and why it matters

The last three lessons gave you the parts the CPU needs. Lesson 26 built the ALU that computes results and flags. Lesson 25 showed that a register is a row of flip-flops that copies a value on an edge. Lesson 27 showed the buses that carry a fetch from memory. This lesson puts those parts in order. It shows what the CPU does, step by step, for one instruction, and where in that sequence a register actually changes.

This matters in practice because the debugger shows you the state of the CPU between steps. When you single-step a function in GDB, the program counter moves, a register changes, and a flag is set, and you need to know which of those happen in which phase to understand what you are looking at. A reader who thinks a register changes when the instruction is fetched will look for a value that has not arrived yet. A reader who knows the order can predict the next state, which is the skill this lesson trains.

You should be able to take any simple instruction and say what the program counter holds, what the instruction register holds and what the destination register holds after each of its three phases.

Concept 1: the program counter points at the next instruction

The CPU runs one instruction at a time, in a loop. The address of the instruction it is working on lives in the program counter (PC). On Arm cores the PC is register R15, and the glossary entry defines it as the register that holds the address of the instruction being executed, where a write to it branches. Every instruction moves the PC onward, either to the next instruction in memory or to a branch target.

The second register you need is the instruction register (IR). It is not one of the programmer's registers. It is a holding area inside the core that keeps the bits of the current instruction while the control logic works on them. You will not see it in your C code, but a debugger that shows the disassembly of the current instruction is showing its contents.

The CPU's loop has three phases for each instruction. In the fetch phase it reads the instruction at the address in the PC into the IR. In the decode phase it works out what the bits mean: the operation, the source registers, the destination register and any immediate constant. In the execute phase it performs the operation, writes the result to the destination, updates the flags, and moves the PC on or changes it for a branch. These are the logical phases of one instruction. A real pipeline overlaps them, so while one instruction executes the next is already being decoded. Lesson 30 covers that.

Arm's Cortex-M3 Technical Reference Manual names the same stages. Section 1.3 lists "the Fetch stage, the Decode stage, the Execute stage" as the pipeline stages of the M3, and says the core has a three-stage pipeline (Arm Cortex-M3 TRM DDI0337G, section 1.2.1 and section 1.3). Section 1.4 describes the prefetch unit, which fetches ahead of the instruction being executed. The simple three-phase model in this lesson is a starting point, and the prefetch unit is where the real core differs.

A CPU follows a program the way you follow a recipe card with your finger on the next step. Read the step (fetch), work out what it asks (decode), do it (execute), and move your finger down one line. Your finger is the program counter. A step such as "go back to step 3" is a branch: it moves the finger instead of letting it slide to the next line.

Concept 2: what the hardware does in each phase

Each phase is a set of circuits you already know, and knowing which circuit does what tells you which register can change when.

Fetch. The PC drives the address bus, as lesson 27 described. Memory returns the bits of the instruction on the data bus, and they are copied into the IR on a clock edge, which is the flip-flop behaviour from lesson 24. Nothing in the program's registers changes. The PC is not moved yet, because the core has not yet worked out how long this instruction is. A Thumb instruction can be 16 or 32 bits, so the PC is advanced only once the size is known.

Decode. The bits in the IR now go to the control logic. The opcode bits say which operation to perform. The register-number fields select which registers to read, through multiplexers of the kind you built in lesson 23. The immediate field, if there is one, is expanded into a 32-bit value. Decode reads registers and prepares the ALU inputs, but it does not write any register. This matters when you step through code: a destination register named in decode is not yet changed.

Execute. The ALU runs the operation on the two operands, as lesson 26 described. The result is written to the destination register on a clock edge, and the flags are updated at the same time. The PC is then set to the next address, or to the branch target. This is the only phase in which a register changes, apart from the PC being set in a branch.

Concept 3: an instruction has a size, and the PC moves by it

Instructions occupy memory, and the PC must move by the size of the instruction just executed. The Thumb instruction set has 16-bit instructions and 32-bit instructions, and the Cortex-M3 implements Thumb-2, which mixes the two (see the glossary entry for Thumb-2). The size is known only from the first halfword's bits, which the decode phase examines, so in this model the PC moves in the execute phase, once the size is known, and not in the fetch phase.

The simulator in this lesson simplifies this. It is a teaching model, not a Cortex-M. It has four differences you need to know. First, it updates the PC during the execute phase, so the PC stays on the current instruction while it is fetched and decoded. Second, every instruction is 2 bytes, which is the size of a 16-bit Thumb instruction, but the instruction set is a small subset with no 32-bit instructions. Third, the memory map is a toy: code at 0x0, 64 words of RAM at 0x20000000 and a GPIO register at 0x40000000. Fourth, MOV accepts any 32-bit constant, which a real 16-bit MOV cannot encode. A real 16-bit MOV takes an 8-bit immediate, and lesson 29 shows the encoding. A larger constant on a real core is loaded from a literal pool in code memory, with an LDR.

The Step button runs one phase. The Instruction button runs all three phases of one instruction. The EXECUTE phase is where a register changes.

Worked example: two plus three, phase by phase

The simulator program in the hands-on section below is four instructions and a halt. It sets R0 to 2, adds 3 to R0, writes R0 to the GPIO output register and halts. Trace the first two instructions, with the PC in the simulator's terms. Each instruction is 2 bytes, so the first sits at address 0 and the second at address 2.

PressPhaseWhat happensPC after the phaseR0 after the phase
1FETCHread the MOV R0, #2 at address 0 into the IR00
2DECODEwork out: destination R0, immediate 200
3EXECUTER0 = 2; N = 0 and Z = 0 are set22
4FETCHread the ADD R0, R0, #3 at address 222
5DECODEwork out: sources R0 and 3, destination R022
6EXECUTER0 = 2 + 3 = 5; N, Z, C and V all clear45

Read the table row by row. The PC stays at 0 for the first two presses, because the PC only moves in execute. It becomes 2 at the third press, when the MOV has run. The R0 column does not change until the third press as well. Decode names R0 and reads the immediate, but the register is written only in the execute phase. Then the same pattern repeats for the ADD. The fetch at press 4 reads address 2, the register is still 2 at press 5, and the value 5 appears at press 6.

The flags follow the same rule. The MOV sets N and Z from its result, which is 2, so both are clear. The ADD sets all four flags from its result, which is 5. None is set, since 5 is positive, not zero, with no carry out and no signed overflow. You can check the ALU rules in lesson 26 against this.

After six presses the PC is 4, and the next instruction is the MOV R1 at address 4. The pattern does not change. A program is nothing more than this loop, run once per instruction, and each instruction's effect appears in a predictable phase.

Try it in the CPU simulator

The program sets R0 to 2, adds 3, and writes the result to the LEDs. Press Reset, then predict before each press. The phase row shows which of the three phases is running, and the message line describes each phase as it runs.

  1. From reset, press Step once. The FETCH phase lights up and the PC still reads 0. Predict R0 after the third press of Step, when the EXECUTE phase runs for the MOV. Then press Step twice more and check: R0 = 2 and the PC = 2.
  2. Press Instruction once. This runs the whole MOV, and the PC moves on to 2. Press Instruction again to run the ADD. Predict R0 before you press: it should be 5 when the ADD finishes.
  3. Press Instruction twice more. The first press runs MOV R1, #0x40000000, and the second runs the STR. Count the LEDs that are lit after the STR. The value 5 is 0b101, so two LEDs should be lit.

The diagram above the registers is the CPU drawn as blocks. After each Step, the wires that carried data in that phase light up and show the value on them. Watch where the instruction goes in the fetch, which registers the decode selects, and which path the result takes back in the execute.

Hint

The PC only changes in the execute phase, so it reads 0 after the first Step. A register only changes in the execute phase too: the value appears on the third press of a Step cycle, not the first. The B . at the end parks the program on purpose. The simulator reports that it is branching to itself, which is the normal way to stop, not an error.

Then compare the simulator with a real Cortex-M. Its PC bookkeeping differs from the simulator's, because the real core fetches ahead. The prefetch unit buffers up to three word fetches (Cortex-M3 TRM section 1.4), so the memory system is already reading the next instructions while the current one executes. Read that section before you trust a PC value from a debugger on the hardware. Lesson 32 shows real PC values in a disassembly.

Common mistakes and how to spot them

Mistake 1: expecting the PC to move on the fetch. Symptom: you press Step once, the PC still reads 0, and you think the simulator is stuck. Fix: the PC moves in the execute phase. Press Step two more times and it changes.

Mistake 2: expecting the register to change in decode. Symptom: you step past the DECODE of the ADD, see R0 still equal to 2, and conclude that the ADD did nothing. Fix: decode names the destination register, but the value is written in execute. Step once more and R0 becomes 5.

Mistake 3: stepping past the halt and calling it a crash. Symptom: after the STR, the program reaches B ., and the simulator keeps showing the same branch. You think it has frozen. Fix: a branch to itself is the simulator's way of parking the program. Use Reset to run it again.

Mistake 4: assuming every instruction is 4 bytes. Symptom: you expect the PC to read 4 after the first instruction, because you assume every instruction is 32 bits. The simulator shows 2. Cortex-M runs only Thumb code, so its instructions are 16 or 32 bits (Thumb-2), and the simulator uses only 2-byte instructions. Fix: the simulator uses 2-byte Thumb instructions. On the real Cortex-M3 the size depends on the encoding: 16 bits for many instructions and 32 bits for others. Read the size from the disassembly or the encoding, not from a guess.

Mistake 5: writing a large constant as an immediate. Symptom: MOV R1, #0x40000000 works in the simulator, but the real toolchain rejects it, because a 16-bit MOV cannot hold that constant. Fix: on the real core, load a large constant with LDR from a literal pool. The simulator's wider MOV is a convenience of the model.

In real projects

When a debugger stops a program, it shows the PC of the next instruction to execute, or of the instruction that just ran, depending on the core and the stop point. Engineers learn to read this by stepping one instruction at a time and checking the registers after each step. Lesson 54 covers GDB debugging. The phase model in this lesson is the mental model behind those steps.

Performance work depends on the same model. A branch that is taken forces the core to throw away the instructions it has fetched past the branch, and that cost is the subject of lesson 30. A reviewer who reads a hot loop asks how many instructions each iteration executes and where the branches are, because each taken branch changes the PC and the fetches behind it.

Summary

  • The program counter (PC) holds the address of the instruction being executed. The instruction register (IR) holds its bits while the core works on them.
  • Fetch reads the instruction at the PC into the IR. It changes no programmer-visible register.
  • Decode works out the operation, the source registers and the destination, and prepares the ALU inputs. It does not write a register.
  • Execute performs the operation, writes the destination, updates the flags and moves the PC.
  • In the simulator, the PC moves in execute. On the real Cortex-M3, the prefetch unit fetches ahead, so a debugger's PC needs care.
  • The simulator's instructions are 2 bytes, and its MOV is wider than a real 16-bit MOV. Use LDR for a large constant on a real core.
