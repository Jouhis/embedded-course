Static analysis: warnings, cppcheck and MISRA C

Tests only find the bugs you thought to test. A compiler and a static checker read every line, and they report the bugs that a test run never reaches.

By the end of this lesson you can run GCC's warning flags and cppcheck on a C file, read each finding, and fix five planted defects.

Where we are and why it matters

The earlier lessons gave you two ways to find bugs. Lesson 80 ran tests that you wrote, and lesson 81 made the tests reach a driver without a sensor. Both answer the question "does this code do what I tested?" Neither answers "what did I not test?" The integer rules in lesson 45 show why that question matters: a sum that wraps, a comparison between a signed and an unsigned value, or a read of a variable that was never set can all compile and run without any visible symptom.

A common case is a code review. A colleague sends a driver with a loop, a switch and a checksum, and the tests pass. A senior engineer reads the code and asks whether the build uses warnings, and what cppcheck says. The answer is expected to be specific. This lesson teaches the tools that give those answers, and how to read their output. The continuous integration pipeline in lesson 82 runs the same checks on every push.

Static analysis means checking code without running it (glossary: static analysis). The compiler's warnings are the first and cheapest kind. They come from the same pass that generates code, so they cost nothing extra. A dedicated analyser such as cppcheck does more work. It builds its own model of the code and reports things the compiler does not look for, such as an array index that is out of range on one path. The two tools answer different questions, and the sample in this lesson has cases where each one finds something the other misses.

The compiler reads the code too: warnings

A warning is the compiler's message that the code compiles but looks wrong. It is not an error: the build still produces a file. Warnings are controlled by flags, and GCC groups many of them. -Wall and -Wextra are the two broad groups. Each flag enables one or a few checks, and some flags are in neither group. A firmware team usually chooses flags on purpose and writes the choice in the build file, so that every developer and the pipeline get the same result.

The table lists the flags this lesson uses, with the group that enables each one. I checked the groups by running GCC 16.2 with and without -Wall and -Wextra, and by compiling small test files. The GCC manual's Warning Options page is the reference.

FlagCatchesIn -Wall or -Wextra?
-WshadowA local name that hides an outer oneNeither
-WconversionAn implicit narrowing, such as int to uint8_tNeither
-Wdouble-promotionfloat silently promoted to doubleNeither
-Wformat=2Format strings that are not literals, and similar printf risksNeither
-Wcast-alignA cast to a pointer type with a stricter alignmentNeither
-Wimplicit-fallthroughA switch case that runs into the next one-Wextra
-Wsign-compareSigned and unsigned values compared-Wextra (in C)
-Wmaybe-uninitializedA variable that may be read before it is set (needs optimisation on)-Wall
-fanalyzerPaths through the code: uninitialised values, bad pointersIts own option

A few of these deserve a sentence each. -Wshadow is the flag for the bug where an inner declaration hides an outer variable, so the loop updates a copy and the outer variable never changes. -Wconversion reports a value that loses bits when it is stored in a smaller type, such as an int stored in a uint8_t. It is strict, and many teams add it to new modules first. -Wformat=2 warns when a printf format string is a variable, because text from outside can contain a format directive the code never meant to expand. -Wcast-align warns when a cast makes a pointer more strictly aligned than the data it points to. On a Cortex-M that can mean a fault on an unaligned access, which lesson 84 returns to.

Turning on -Wconversion adds noise on real code. Many teams use it on new modules and fix the rest over time. Add the flags one at a time, so that you can tell which one produced a warning.

cppcheck: a second reader with its own parser

cppcheck is an open-source static analyser for C and C++ (source and documentation). It reads the code with its own parser and builds its own view of each function, so it finds different problems from the compiler. Its findings come in categories, and the category tells you how strong the claim is. error findings are defects on a path the analyser can see, such as an array index that is out of range. warning findings are likely defects. style findings are about how the code is written, such as a variable that is assigned and then never read.

The course's installed version is 2.22.0. Run it with --enable=warning,style, which switches on the warnings and the style checks. Without that option, cppcheck reports only errors, so a shadowed variable would pass silently. Be careful with the exit code, too: by default cppcheck returns 0 even when it reports findings. The pipeline needs --error-exitcode=1 to fail a job, as lesson 82 explains.

MISRA C: what it is, and what this machine can do

MISRA C is a coding standard for safety-related C, published by MISRA. Its rules are grouped into three categories. In paraphrase: mandatory rules must always be followed, with no deviation allowed; required rules must be followed unless a deviation is formally recorded with a justification; advisory rules are good practice that the team may choose to skip. The rule texts are licensed, so this course does not reproduce them. Read them through your company's copy or the MISRA website. The course's short list is the MISRA C quick list.

cppcheck can check many MISRA C:2012 rules through its addon misra.py, run as --addon=misra. On this machine the addon is not installed: running cppcheck --addon=misra reports "Did not find addon misra.py". Getting the addon from cppcheck's source tree is the next step, and it has not been run for this lesson. In a real project, a deviation is an entry in a record that names the rule, the reason, and the person who approved it, so that a reviewer can check it later.

A worked example: the switch without a break

Start with a defect that the starter's tests do catch, so you can see the mechanism. Here is status_name from the starter, with the bug marked: 

const char *status_name(uint8_t code) {
    const char *name = "unknown";
    switch (code) {
    case 0u:
        name = "idle";          /* DEFECT 3: no break, so case 0 falls into case 1 */
    case 1u:
        name = "running";
        break;
    ...
    }
    return name;
}

Trace the call status_name(0) step by step. The code is 0, so the switch jumps to the label case 0u. Before that point, name holds the pointer to "unknown". The statement name = "idle" runs, so name now points to "idle". There is no break, so execution does not leave the switch. It continues into the code under case 1u, which sets name to "running" and then breaks. The function returns "running". The test expects "idle", and the run prints this line: 

test_analysis.c:25:test_status_idle:FAIL: Expected 'idle' Was 'running'

The message is the symptom, and the cause is one line earlier than the failure. The fall-through is a feature of C switch statements, and sometimes it is intended. In this case the comment says it is not. The fix is a break, or, as in the solution, a return in each case, so that no case can run into the next. The compiler saw the same thing: the GCC 14.2 run in the next section warns on that line.

A worked example: a shadowed total

The next defect is quieter. The starter's sum_samples declares a total before the loop, and then declares another total inside the loop: 

int32_t sum_samples(const int16_t *s, size_t n) {
    int32_t total = 0;                  /* the outer total */
    for (size_t i = 0; i < n; i++) {
        int32_t total = 0;              /* DEFECT 1: a new variable that hides the outer one */
        total += s[i];
    }
    return total;
}

Trace sum_samples with the samples {1, 2, 3}. The outer total is set to 0. On the first pass, the loop body creates an inner total, sets it to 0, and adds 1, so the inner variable holds 1. The inner variable ends when the loop body ends. The second and third passes do the same, and the outer total is still 0. The function returns 0, and the test expects 6. The printed failure is exact: 

test_analysis.c:11:test_sum_of_three_samples:FAIL: Expected 6 Was 0

This is the bug that -Wshadow names. The warning points at line 9, the inner declaration, and the note points back to the outer one. The shadowing is easy to miss in review, because each line looks correct on its own. The fix is to delete the inner declaration, so that the loop updates the one total.

The defects the tests do not catch

The other three defects are the ones the starter's tests do not reach. The starter has six tests, and none calls checksum or frame_build. A green test run tells you nothing about those two functions. Static analysis is the only check that reads them.

Tests are a test drive: they show the car works on the roads you drove. Static analysis is the inspector who reads the whole drawing, including the roads nobody drove, such as an error path or a default: that never runs in a test. Each finds faults the other misses, so teams use both.

checksum starts with uint8_t sum; and no value. The first use of sum reads whatever bytes the stack held before the function ran. On the test machine that value may happen to be zero, and on the board it is something else. This is an uninitialised read, and it is undefined behaviour (lesson 45). Here is what each tool says about it. GCC 14.2 with -O2 reports 'sum' may be used uninitialized, and GCC 16.2 with -fanalyzer reports that the value is used at two lines. Neither tool is wrong, because a read before a write is a real defect in any run where the stack holds something else.

frame_build declares uint8_t frame[3];, which holds indices 0 to 2, and then writes frame[3] when the marker is set. That write is one byte past the end of the array. It is undefined behaviour, and it may overwrite a neighbouring variable on the stack. The write is inside an if, so only one path reaches it. cppcheck follows that path and reports it as an error. GCC does not, with the flags used here.

The last defect is the sign comparison in find_first_negative. The loop index is an int and the length is a size_t, which is unsigned. C converts the signed value to unsigned before the comparison (the usual arithmetic conversions from lesson 45), so a negative index would compare as a huge number. In this loop the index never goes negative, so the bug does not change the answer, but the warning is still right to report it.

Read the two lists side by side. Notice what each tool did not report. cppcheck did not report the sign comparison, and neither GCC run reported the out-of-bounds write on frame[3], which cppcheck did. Neither tool flagged sum = sum + data[i] as a narrowing conversion, because the GCC runs stay quiet on that line with -Wconversion. The solution casts it anyway, so the intent is explicit. Several findings describe the same defect in different words, which is normal. Fixing the defect makes the duplicates go away together. The GCC 16.2 run with -fanalyzer adds two path-based lines about the uninitialised sum, at lines 44 and 46.

The solution, with the same flags, prints no GCC warnings and no cppcheck findings. On the host, its test binary prints 9 Tests 0 Failures 0 Ignored and OK. The three tests that the solution adds check the checksum, the marker byte and the unknown status. Those are the paths that the starter's tests never reached.

  3. Run cppcheck: "/c/Program Files/Cppcheck/cppcheck.exe" --enable=warning,style --quiet src/analysis.c. You should see seven lines, three of them marked error or warning and the rest style. The exit code is 0 even though the findings are there, so read the output rather than the exit code.

Hint

Each defect is a single line, or two lines in the case of the fall-through. The fallthrough needs a break or a return in the case. The uninitialised variable needs a value before the first use. The buffer defect is an array with three elements that is written at index 3, so declare it with four, and make sure the output loop copies all four bytes. The shadowed total needs the inner declaration removed.

Common mistakes and how to spot them

Mistake 1: trusting a clean compile. The build log has no warnings, and the team concludes the code is clean. In this file, the compiler is silent about the out-of-bounds write, and cppcheck reports it as an error. The symptom is a silent build with an error line in the static-analysis job. The fix is to run both tools, because each reads the code differently.

Mistake 2: running cppcheck without style. The developer runs cppcheck --enable=warning, or runs it with no option. The shadowed variable and the unread assignment are reported in the style category, so they never appear. The symptom is a clean report on a file that has a known defect. The fix is --enable=warning,style, which the course uses everywhere.

Mistake 3: fixing every warning by hiding it. A developer adds a cast to quiet -Wconversion, or a (void) to quiet an unused variable, without asking what the value should be. The symptom is a clean build and a wrong answer. The fix is to read the warning, work out the intended value, and then write the code that produces it. The cast in the solution is the right kind of change, because the intent is stated in the code.

Mistake 4: assuming the tests cover what the warnings report. The starter's test run shows 6 Tests 2 Failures, and a developer fixes the two failing tests and stops. The checksum and the marker byte still have no tests, so the uninitialised read and the out-of-bounds write survive. The symptom is a green test run and a warning that never went away. The fix is to treat the static findings as a list of cases that need a test.

Mistake 5: turning on every flag at once. A developer adds -Wconversion and a dozen other flags to an existing project, and the build prints hundreds of lines. The team learns to ignore the output, and the important warning is lost. The symptom is a log that nobody reads. The fix is to add flags one at a time, fix or record each group, and then make the next flag part of the build.

In real projects

In a firmware team, the compiler flags are part of the build configuration, and a change to them is a code change. Reviewers look for the flags first, because a missing -Wshadow or -Wimplicit-fallthrough is an easy gap to close. Static analysis runs in the pipeline (lesson 82), and the team decides which findings block a merge. Safety-related teams add MISRA C rules, and they record each deviation with a reason. A required rule with no deviation record is a review finding in its own right.

Summary

  • A warning is the compiler's message about code that compiles but looks wrong. Flags control the warnings, and the groups -Wall and -Wextra do not include everything.
  • cppcheck has its own parser and reports errors, warnings and style findings. Use --enable=warning,style, and --error-exitcode=1 in a pipeline.
  • A switch case without break falls into the next case. The symptom is a test that expects one string and gets another.
  • A variable declared again in an inner scope hides the outer one, so an update can go to a copy. -Wshadow finds it.
  • An uninitialised local and an array write past its end are undefined behaviour. Compilers and analysers catch some paths, and no tool catches every path.
  • A green test run only covers the paths the tests reach. Static analysis reads every line, so use both.
  • Add warning flags one at a time, and record every deviation from MISRA C with a reason.
