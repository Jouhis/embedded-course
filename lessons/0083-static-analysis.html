Static analysis: warnings, cppcheck and MISRA C

Tests only find the bugs you thought to test. A compiler and a static checker read every line, and they report the bugs that a test run never reaches.

By the end of this lesson you can run GCC's warning flags and cppcheck on a C file, read each finding, and fix five planted defects.

The idea

Static analysis checks code without running it. The compiler's warnings are the first and cheapest kind: they come from the same pass that generates code, so they are free. A dedicated analyser such as cppcheck does more work, and it reports things the compiler does not look for, such as an array index that is out of bounds on one path. A test suite only covers the paths it runs, so the two tools answer different questions.

GCC warning flags

-Wall and -Wextra are the baseline. Several useful flags are not in either group, and firmware teams usually add them. The table lists the ones this lesson uses. Every flag was accepted by GCC 16.2 (the host compiler) and by Arm GNU 14.2 (the board compiler) on this machine. The GCC manual's Warning Options page says which group enables each one.

FlagCatchesIn -Wall or -Wextra?
-WshadowA local name that hides an outer oneNeither
-WconversionAn implicit narrowing, such as int to uint8_tNeither
-Wdouble-promotionfloat silently promoted to doubleNeither
-Wformat=2Format strings that are not literals, and similar printf risksNeither
-Wcast-alignA cast to a pointer type with a stricter alignmentNeither
-Wimplicit-fallthroughA switch case that runs into the next one-Wextra
-Wsign-compareSigned and unsigned values compared-Wextra (in C)
-fanalyzerPaths through the code: uninitialised values, bad pointersIts own option
Turning on -Wconversion adds noise on real code. Many teams use it on new modules and fix the rest over time. Add the flags one at a time, so that you can tell which one produced a warning.

cppcheck

cppcheck is an open-source static analyser for C and C++ (source and documentation). It reads the code with its own parser, so it finds different problems from the compiler. The course's installed version is 2.22.0. Run it with --enable=warning,style, which switches on the warnings and the style checks. Without it, cppcheck reports only errors.

MISRA C: what it is, and what this machine can do

MISRA C is a coding standard for safety-related C, published by MISRA. Its rules are grouped into three categories. Paraphrased, these are: mandatory rules must always be followed, with no deviation allowed; required rules must be followed unless a deviation is formally recorded with a justification; advisory rules are good practice that the team may choose to skip. The rule texts are licensed, so this course does not reproduce them. Read them through your company's copy or the MISRA website.

cppcheck can check many MISRA C:2012 rules through its addon misra.py, run as --addon=misra. On this machine the addon is not installed: the cppcheck 2.22.0 folder has no addons directory, and cppcheck --addon=misra reports "Did not find addon misra.py". Getting the addon from cppcheck's source tree is the next step, and it has not been run for this lesson.

Try it on the starter

  1. Open projects/0083-static-analysis/starter in VS Code. Read src/analysis.c once, without fixing anything. The file has five planted defects, marked with comments.
  2. In Git Bash, run the GCC flags on the file. This uses the Arm compiler from the lesson 1 setup, with the same flags as the host:
    cd projects/0083-static-analysis/starter
    "/c/Program Files (x86)/Arm GNU Toolchain arm-none-eabi/14.2 rel1/bin/arm-none-eabi-gcc.exe" -std=c11 -O2 -mcpu=cortex-m3 -mthumb -Wall -Wextra -Wshadow -Wconversion -Wdouble-promotion -Wformat=2 -Wcast-align -Wimplicit-fallthrough -c src/analysis.c -o /dev/null
  3. Run cppcheck: "/c/Program Files/Cppcheck/cppcheck.exe" --enable=warning,style --quiet src/analysis.c.
  4. Your task: fix each defect so the tests pass. Start with the warnings, then the cppcheck findings. Your goal is the same output as the solution: no warnings and 6 Tests 0 Failures. Then run python -I tools/build.py projects/0083-static-analysis/starter --test to confirm.
Hint

Each defect is a single line. The fallthrough needs a break or a return. The uninitialised variable needs a value before the first use. The buffer defect is an array with three elements that is written at index 3, so declare it with four.

This is the real output on the starter, from the GCC 14.2 flags above (selected lines). The host GCC 16.2 with -fanalyzer adds analyser lines on top of these, including the uninitialised-value paths.

Output of the GCC 14.2 run:

src/analysis.c:9:17: warning: declaration of 'total' shadows a previous local [-Wshadow]
src/analysis.c:16:23: warning: comparison of integer expressions of different signedness: 'int' and 'size_t' {aka 'unsigned int'} [-Wsign-compare]
src/analysis.c:28:14: warning: this statement may fall through [-Wimplicit-fallthrough=]
src/analysis.c:44:13: warning: 'sum' may be used uninitialized [-Wmaybe-uninitialized]

From the same file, cppcheck 2.22.0 with --enable=warning,style (selected lines; it also reports two more unreadVariable and one uninitvar duplicate):

src\analysis.c:59: error: Array 'frame[3]' accessed at index 3, which is out of bounds. [arrayIndexOutOfBounds]
src\analysis.c:60: error: Array 'frame[3]' accessed at index 3, which is out of bounds. [arrayIndexOutOfBounds]
src\analysis.c:30: style: Variable 'name' is reassigned a value before the old one has been used. 'break;' missing? [redundantAssignInSwitch]
src\analysis.c:9: style: Local variable 'total' shadows outer variable [shadowVariable]
src\analysis.c:44: error: Uninitialized variable: sum [legacyUninitvar]

Notice what each tool did not find. cppcheck did not report the sign comparison, and GCC did not report the out-of-bounds write on frame[3], which cppcheck did. Neither tool flagged sum = sum + data[i] as a conversion, because GCC 14.2 and 16.2 both stay quiet on that line; the solution still casts it, so the intent is explicit. Some findings are duplicates in different words, which is normal: fix the defect, and the duplicates go away together.

The solution, with the same flags, prints no GCC warnings and no cppcheck findings. Its tests check the checksum and the marker byte, which the starter's tests do not cover.

You ran two different analysers on one file, read their findings, and fixed five defects, including two that the starter's tests did not catch. That habit is what reviewers look for, and the five review checks that go with it are in lesson 79.

"Which compiler warnings and static analysis do you turn on for firmware, and why?" Answer out loud in 60 seconds, then compare.

Model answer

I build with -Wall -Wextra and treat warnings as errors in CI. I add -Wshadow, -Wimplicit-fallthrough and -Wsign-compare, which catch real bugs in ordinary code, and I add -Wconversion on new modules, because narrowing is where sensor scaling goes wrong. On top of that I run cppcheck with warning and style checks, and MISRA C rules where the project requires them, mainly the mandatory and required categories, with recorded deviations. I say which tools find what: tests cover the paths I run, and static analysis covers paths I did not think of.

GCC manual: Warning Options: read the entries for -Wshadow, -Wconversion and -Wimplicit-fallthrough, and check which group enables each one. The cppcheck project and its manual are at github.com/danmar/cppcheck.
