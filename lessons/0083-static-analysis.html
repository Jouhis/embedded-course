Static analysis

Checking code without running it

By the end of this lesson you can run GCC's warning flags and cppcheck on a C file, read each finding, and fix five planted defects.

Bugs on paths that no test reaches

The earlier lessons gave two ways to find bugs, lesson 80 running tests that you wrote and lesson 81 letting those tests reach a driver without a sensor, both answering whether the code does what was tested but neither revealing what was not tested. The integer rules of lesson 45 show why that gap matters, since a sum that wraps, a comparison between a signed and an unsigned value or a read of a variable never set can all compile and run without any visible symptom.

A typical case is a code review in which a colleague sends a driver with a loop, a switch and a checksum whose tests pass, and a senior engineer asks whether the build uses warnings and what cppcheck says, expecting specific answers. This lesson teaches the tools that give those answers and how to read their output, the continuous integration pipeline of lesson 82 running the same checks on every push.

Static analysis means checking code without running it (glossary: static analysis), the compiler's warnings being the first and cheapest kind, since they come from the same pass that generates code and cost nothing extra. A dedicated analyser such as cppcheck does more work, building its own model of the code and reporting things the compiler does not look for, such as an array index out of range on one path, so the two tools answer different questions, and the sample in this lesson has cases where each finds something the other misses.

GCC warning flags

A warning is the compiler's message that the code compiles but looks wrong, unlike an error leaving the build to produce its file. Warnings are controlled by flags, GCC grouping many of them into the two broad groups -Wall and -Wextra, each flag enabling one or a few checks and some flags belonging to neither group, so a firmware team usually chooses its flags on purpose and writes the choice into the build file, giving every developer and the pipeline the same result.

The table lists the flags this lesson uses with the group that enables each, the groups having been checked by running GCC 16.2 with and without -Wall and -Wextra on small test files, while the GCC manual's Warning Options page is the reference.

FlagCatchesIn -Wall or -Wextra?
-WshadowA local name that hides an outer oneNeither
-WconversionAn implicit narrowing, such as int to uint8_tNeither
-Wdouble-promotionfloat silently promoted to doubleNeither
-Wformat=2Format strings that are not literals, and similar printf risksNeither
-Wcast-alignA cast to a pointer type with a stricter alignmentNeither
-Wimplicit-fallthroughA switch case that runs into the next one-Wextra
-Wsign-compareSigned and unsigned values compared-Wextra (in C)
-Wmaybe-uninitializedA variable that may be read before it is set (needs optimisation on)-Wall
-fanalyzerPaths through the code: uninitialised values, bad pointersIts own option

A few of these deserve a sentence each. -Wshadow catches an inner declaration hiding an outer variable, so that a loop updates a copy while the outer variable never changes, and -Wconversion reports a value losing bits when stored in a smaller type, such as an int stored in a uint8_t, a strict check that many teams add to new modules first. -Wformat=2 warns when a printf format string is a variable, because text from outside can contain a format directive the code never meant to expand, and -Wcast-align warns when a cast makes a pointer more strictly aligned than its data, which on a Cortex-M can mean a fault on an unaligned access, a case lesson 84 returns to.

Turning on -Wconversion adds noise on real code. Many teams use it on new modules and fix the rest over time. Add the flags one at a time, so that you can tell which one produced a warning.

The cppcheck analyser and its finding categories

cppcheck is an open-source static analyser for C and C++ (source and documentation) that reads the code with its own parser and builds its own view of each function, so it finds different problems from the compiler. Its findings come in categories indicating how strong each claim is, error findings being defects on a path the analyser can see, such as an out-of-range array index, warning findings likely defects, and style findings concerning how the code is written, such as a variable assigned and then never read.

The course's installed version is 2.22.0, run with --enable=warning,style to switch on the warnings and style checks, since without that option cppcheck reports only errors and a shadowed variable would pass silently. The exit code also needs care, because by default cppcheck returns 0 even when it reports findings, so a pipeline needs --error-exitcode=1 to fail a job, as lesson 82 explains.

MISRA C and its rule categories

MISRA C is a coding standard for safety-related C, published by MISRA, whose rules fall into three categories, which in paraphrase are mandatory rules, always followed with no deviation allowed, required rules, followed unless a deviation is formally recorded with a justification, and advisory rules, good practice that the team may choose to skip. The rule texts are licensed, so this course does not reproduce them, and they are read through a company copy or the MISRA website, while the course's short list is the MISRA C quick list.

cppcheck can check many MISRA C:2012 rules through its addon misra.py, run as --addon=misra, but on this machine the addon is not installed, cppcheck --addon=misra reporting "Did not find addon misra.py", and fetching the addon from cppcheck's source tree, the next step, has not been done for this lesson. In a real project a deviation is an entry in a record naming the rule, the reason and the person who approved it, so that a reviewer can check it later.

Worked example: a switch case without a break

We start with a defect the starter's tests do catch, to see the mechanism, in status_name from the starter with the bug marked. Before tracing it, predict what status_name(0) returns. 

const char *status_name(uint8_t code) {
    const char *name = "unknown";
    switch (code) {
    case 0u:
        name = "idle";          /* DEFECT 3: no break, so case 0 falls into case 1 */
    case 1u:
        name = "running";
        break;
    ...
    }
    return name;
}
  1. Jump to the case. The code is 0, so the switch jumps to the label case 0u, while name still points to "unknown".
  2. Assign the name. The statement name = "idle" runs, so name now points to "idle".
  3. Fall through. Without a break, execution does not leave the switch but continues into the code under case 1u, which sets name to "running" and then breaks.
  4. Return. The function returns "running" where the test expects "idle", and the run prints the line below.
test_analysis.c:25:test_status_idle:FAIL: Expected 'idle' Was 'running'

The message is the symptom, the cause lying one line before the failure. Fall-through is a feature of C switch statements and sometimes intended, but here the comment says it is not, so the fix is a break, or, as in the solution, a return in each case, so that no case can run into the next. The compiler saw the same thing, the GCC 14.2 run in a later section warning on that line.

Worked example: a shadowed total

The next defect is quieter, the starter's sum_samples declaring a total before the loop and then another inside it. Predict what the function returns for the samples {1, 2, 3} before reading the trace. 

int32_t sum_samples(const int16_t *s, size_t n) {
    int32_t total = 0;                  /* the outer total */
    for (size_t i = 0; i < n; i++) {
        int32_t total = 0;              /* DEFECT 1: a new variable that hides the outer one */
        total += s[i];
    }
    return total;
}

The outer total is set to 0, and on the first pass the loop body creates an inner total, sets it to 0 and adds 1, so the inner variable holds 1 until it ends with the loop body. The second and third passes do the same, leaving the outer total at 0, so the function returns 0 where the test expects 6, and the printed failure says exactly that. 

test_analysis.c:11:test_sum_of_three_samples:FAIL: Expected 6 Was 0

This is the bug that -Wshadow names, its warning pointing at line 9, the inner declaration, with a note pointing back to the outer one. Shadowing is easy to miss in review, because each line looks correct on its own, and the fix deletes the inner declaration, so that the loop updates the single total.

Defects outside the reach of the tests

The other three defects lie where the starter's tests do not reach, since none of its six tests calls checksum or frame_build, so a green test run says nothing about those two functions and static analysis is the only check that reads them.

checksum starts with uint8_t sum; and no value, so its first use of sum reads whatever bytes the stack held before the function ran, which may happen to be zero on the test machine and something else on the board. This uninitialised read is undefined behaviour (lesson 45), reported by GCC 14.2 with -O2 as 'sum' may be used uninitialized and by GCC 16.2 with -fanalyzer as a value used at two lines, and neither tool is wrong, because a read before a write is a real defect in any run where the stack holds something else.

frame_build declares uint8_t frame[3];, holding indices 0 to 2, and then writes frame[3] when the marker is set, one byte past the end of the array, undefined behaviour that may overwrite a neighbouring stack variable. The write sits inside an if, so only one path reaches it, and cppcheck follows that path and reports an error, whereas GCC does not with the flags used here.

The last defect is the sign comparison in find_first_negative, whose loop index is an int while the length is a size_t, which is unsigned, so C converts the signed value to unsigned before comparing (the usual arithmetic conversions of lesson 45) and a negative index would compare as a huge number. In this loop the index never goes negative, so the bug does not change the answer, but the warning is still right to report it.

Tests resemble a test drive, showing that the car works on the roads that were driven, whereas static analysis resembles an inspector reading the whole drawing, including the roads nobody drove, such as an error path or a default: that never runs in a test, so each finds faults the other misses and teams use both. The comparison breaks because an inspector judges the drawing against physics, while an analyser judges code only against the patterns it knows, so a defect outside those patterns passes the inspection unnoticed.

Common mistakes and how to spot them

Trusting a clean compile

The build log is silent while the static-analysis job shows an error line, because the team concluded from a warning-free compile that the code was clean, although in this file the compiler says nothing about the out-of-bounds write that cppcheck reports as an error. Run both tools, because each reads the code differently.

cppcheck run without style checks

The report is clean on a file with a known defect, because the developer ran cppcheck --enable=warning, or no option at all, and the shadowed variable and the unread assignment belong to the style category, so they never appear. Use --enable=warning,style, as the course does everywhere.

Warnings silenced instead of fixed

The build is clean but the answer is wrong, because a developer added a cast to quiet -Wconversion, or a (void) to quiet an unused variable, without asking what the value should be. Read the warning, work out the intended value and write the code that produces it, the cast in the solution being the right kind of change because it states the intent in the code.

Tests assumed to cover the warnings

The test run is green while a warning never goes away, because a developer saw 6 Tests 2 Failures, fixed the two failing tests and stopped, leaving the checksum and the marker byte untested, so the uninitialised read and the out-of-bounds write survive. Treat the static findings as a list of cases that need a test.

Every flag turned on at once

The build log is one that nobody reads, because a developer added -Wconversion and a dozen other flags to an existing project, the build printed hundreds of lines and the team learned to ignore them, losing the important warning. Add flags one at a time, fixing or recording each group before making the next flag part of the build.

Warning policy and analysis in firmware teams

In a firmware team the compiler flags belong to the build configuration, so a change to them is a code change, and reviewers look at the flags first, because a missing -Wshadow or -Wimplicit-fallthrough is an easy gap to close. Static analysis runs in the pipeline (lesson 82), the team deciding which findings block a merge, and safety-related teams add MISRA C rules, recording each deviation with a reason, so that a required rule without a deviation record is a review finding in its own right.

Summary

  • A warning is the compiler's message about code that compiles but looks wrong, controlled by flags, and the groups -Wall and -Wextra do not include everything.
  • cppcheck has its own parser and reports errors, warnings and style findings, run with --enable=warning,style and, in a pipeline, --error-exitcode=1.
  • A switch case without break falls into the next case, the symptom being a test that expects one string and gets another.
  • A variable declared again in an inner scope hides the outer one, so an update can go to a copy, which -Wshadow finds.
  • An uninitialised local and an array write past its end are undefined behaviour that compilers and analysers catch on some paths, though no tool catches every path.
  • A green test run covers only the paths the tests reach, while static analysis reads every line, so both are needed.
  • Warning flags are added one at a time, and every deviation from MISRA C is recorded with a reason.
