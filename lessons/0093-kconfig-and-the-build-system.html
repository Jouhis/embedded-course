Kconfig and the build system

Zephyr has a few hundred features you can switch on or off. Kconfig is the language that declares them, and prj.conf is where you choose the values. Most confusion about Zephyr comes from not knowing which file a value came from.

By the end of this lesson you can turn on logging with prj.conf, explain how a Kconfig symbol gets its final value, and find that value in build/zephyr/.config.

The idea

A Kconfig symbol is a named option with a type, a default, and optional dependencies: config LOG_BACKEND_UART depends on UART_CONSOLE, so the UART log backend does not exist unless the console is on. The Kconfig files of Zephyr and of each module declare thousands of these symbols. The Zephyr Kconfig guide gives the syntax. Kconfig was written for the Linux kernel. Zephyr uses the same language and the same tools (the menuconfig family), but its build runs CMake around it.

Your application sets values in prj.conf. During the build, the tools merge four sources, from the lowest priority to the highest: the Kconfig defaults, the board's defconfig, the overlay config files, and then your prj.conf. The result is one file, build/zephyr/.config. The C code sees the same values through autoconf.h, which the build generates from that file.

What we set, and what it does

The solution's prj.conf turns on the logger, and sets the level and the mode:

CONFIG_GPIO=y
CONFIG_PRINTK=y
CONFIG_LOG=y
CONFIG_LOG_DEFAULT_LEVEL=3
CONFIG_LOG_MODE_IMMEDIATE=y
CONFIG_MAIN_STACK_SIZE=2048

CONFIG_LOG is the global switch: with it off, a LOG_INF() call compiles to nothing. CONFIG_LOG_DEFAULT_LEVEL sets the level for modules that do not name their own (range 0 to 4, default 3, in subsys/logging/Kconfig.filtering). CONFIG_LOG_MODE_IMMEDIATE prints each message where it is logged, instead of queuing it for a thread.

Look at the cost. The same blink with logging on grows from 17.9 KB to 22.3 KB of flash and from 3.9 KB to 5.1 KB of RAM (the build reports of lessons 92 and 93, which are our measurements, not a fixed figure). Options are not free, and the memory report shows the price.

Dependencies explain missing options

Open subsys/logging/backends/Kconfig.uart and you find depends on UART_CONSOLE and default y if !SHELL_BACKEND_SERIAL. Two things follow. Setting CONFIG_LOG_BACKEND_UART=y does nothing unless the console is on. And turning on the serial shell switches the UART log backend off by default, because the shell has its own log path (lesson 97). When an option seems to have no effect, the first question is what it depends on.

Kconfig's select forces a symbol on, and depends on only allows it. Some symbols are hidden until their parent is on. The tools warn you about the first kind of problem, and the second kind shows up only as a missing option in .config.

Try it in Wokwi

The starter has logging off, with a TODO(learner) note. You turn it on, add a log line, and then check the generated file.

  1. Open projects/0093-kconfig-and-build/starter in VS Code.
  2. In prj.conf, add the three lines from the TODO(learner) note: CONFIG_LOG=y, CONFIG_LOG_DEFAULT_LEVEL=3 and CONFIG_LOG_MODE_IMMEDIATE=y.
  3. In src/main.c, add the LOG_INF line for "KCONFIG OK" and the LOG_DBG line for the LED level.
  4. Build: Ctrl+Shift+B. Then open build/zephyr/.config and search for CONFIG_LOG=. You'll know it works when that line reads CONFIG_LOG=y.
  5. Start the simulator (F1 → Wokwi: Start Simulator) and look for the "KCONFIG OK" line in the serial monitor.
Hint

The solution's prj.conf is the answer key, but read it first. If LOG_INF prints nothing, check that CONFIG_LOG=y is in build/zephyr/.config, not only in your file. An edit to prj.conf needs a new build.

Next, the menus. west build -t menuconfig opens the terminal version, and west build -t guiconfig opens a window. Both targets exist in this workspace, and the GUI needs Python's tkinter, which is installed here. We did not run either one interactively, because they wait for a person. Use them to browse the tree and to see which symbols are hidden.

Finally, look at the memory report. cmake --build build --target rom_report prints a tree of every flash symbol, and ram_report does the same for RAM. Both work on this machine. The first lines of the tree show the largest contributors, and the totals match the FLASH: and RAM: lines in the build output.

"A value you set in a config file does not take effect. How do you find out why?" Answer out loud in 60 seconds, then compare.

Model answer

First check the final value in the generated config (build/zephyr/.config), which shows what the build actually used. If the symbol is missing, look at its dependencies: a symbol that depends on a disabled symbol is hidden, and a value outside the allowed range is rejected. Then rebuild from clean, because a stale configuration can keep an old value.
