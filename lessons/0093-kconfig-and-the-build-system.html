Kconfig and the build system

Zephyr has a few hundred features you can switch on or off. Kconfig is the language that declares them, and prj.conf is where you choose the values. Most confusion about Zephyr comes from not knowing which file a value came from.

By the end of this lesson you can turn on logging with prj.conf, explain how a Kconfig symbol gets its final value, and find that value in build/zephyr/.config.

Where we are and why it matters

Lesson 92 built a Zephyr blink with west. The blink used only two options, CONFIG_GPIO and CONFIG_PRINTK, and it printed with printk(), which is the simplest way to write to the console. In a real product you want more than that. You want log messages with a level and a timestamp, you want to choose how much each part of the system says, and you want the image to be as small as the product needs. Each of those is a configuration choice, and each has a cost in flash and RAM.

The same question comes up in every serious product. A sensor board for a field deployment should log only warnings, to save power and flash. A development board should log debug messages, so an engineer can see what is happening. A firmware team with twenty boards needs each board's options to be explicit and reviewable. Zephyr's answer is Kconfig: every option is declared in a file, its value is set in a file, and the build writes the final result to one place. This lesson teaches the language, the merge order, and how to find out why a value is what it is.

What a Kconfig symbol is

A Kconfig symbol is a named build option. Its name starts with CONFIG_ in C and in configuration files. The language that declares symbols was written for the Linux kernel, and Zephyr uses the same language and the same tools. A declaration looks like this: 

config LOG
    bool "Logging"
    select PRINTK if USERSPACE
    help
      Global switch for the logger, when turned off log calls will not be
      compiled in.

The line config LOG names the symbol. bool is its type, which means it is either y (on) or n (off). The string is the prompt, which is the name a menu shows. The select line says that turning on LOG also forces PRINTK on, but only when USERSPACE is on. The help text is what a person reads in the menu. In Zephyr's subsys/logging/Kconfig, the help says the global switch decides whether log calls are compiled in at all, which is what the rest of this lesson relies on.

The other symbol types are int, string and hex. An int can have a range, and the build rejects a value outside it. You will see one of those below, with CONFIG_LOG_DEFAULT_LEVEL, which must be between 0 and 4.

Two more concepts matter. A default gives a symbol its starting value when nothing else sets it. A depends on line says that the symbol can only be set when another symbol is on. For example, subsys/logging/backends/Kconfig.uart says that the UART log backend depends on UART_CONSOLE, so without the console there is no backend to turn on. The Zephyr configuration guide describes the same rules, and it adds that an assignment is only respected when its dependencies are satisfied, with a warning otherwise.

Where a value comes from: the merge

A symbol's value does not come from one place. The build merges several sources into one final configuration, and the Zephyr documentation (doc/build/kconfig/setting.rst in the workspace) lists them in order. The initial configuration starts from three inputs. The first is the board's defconfig, a file in the board folder that sets the symbols that board needs. The second is any CONFIG_ entries passed to CMake on the command line or in the cache. The third is the application configuration, which is prj.conf in the application folder by default. A symbol set in the application configuration takes precedence over the board's defconfig. If no source sets a symbol, its default in the Kconfig files applies.

The application configuration has a few variants. If CONF_FILE is set, its files are used instead of prj.conf. If a file named boards/<BOARD>.conf exists in the application, it is merged with prj.conf. The documentation is the place to check the exact rules for your version, and it is the reason this lesson points at it.

The merged result is saved to build/zephyr/.config. The C code sees the same values through a generated header, autoconf.h, where each enabled symbol becomes a #define such as CONFIG_LOG 1. Two consequences follow. The file .config is the one place that answers "what value did the build use?", and it is more reliable than your memory of which file you edited.

What we set, and what it does

The solution's prj.conf turns on the logger and sets its level and mode:

CONFIG_GPIO=y
CONFIG_PRINTK=y
CONFIG_LOG=y
CONFIG_LOG_DEFAULT_LEVEL=3
CONFIG_LOG_MODE_IMMEDIATE=y
CONFIG_MAIN_STACK_SIZE=2048

Read each line as a symbol assignment. CONFIG_GPIO=y and CONFIG_PRINTK=y were already in lesson 92, so the GPIO driver and printk() are on. CONFIG_LOG=y is the global switch. CONFIG_LOG_DEFAULT_LEVEL=3 sets the level for modules that do not name their own. Its range is 0 to 4 and its default is 3, as subsys/logging/Kconfig.filtering declares. The help text there lists the levels: 0 is off, 1 is error, 2 is warning, 3 is info, and 4 is debug. CONFIG_LOG_MODE_IMMEDIATE=y chooses the mode. The Kconfig file for modes says that in immediate mode a log message is processed in the context of the call, and that the deferred mode is the default. The last line raises the stack of main() to 2048 bytes, which we return to in the cost section.

The solution's comments say the same things in its own words. The file projects/0093-kconfig-and-build/solution/prj.conf comments each line, and it is the reference to compare with after you finish the hands-on task.

A worked example: what CONFIG_LOG does to a log call

Take the first log line in the solution, LOG_INF("KCONFIG OK, blinking every 500 ms");. Trace what the preprocessor does with it, step by step.

  1. The macro. LOG_INF expands to Z_LOG(LOG_LEVEL_INF, ...), which is in include/zephyr/logging/log.h.
  2. The level. The macro that works out the level of this call, _LOG_LEVEL_RESOLVE, checks CONFIG_LOG first. If logging is off, it resolves to LOG_LEVEL_NONE, and the call does nothing. If logging is on, it uses the module's own level, or CONFIG_LOG_DEFAULT_LEVEL when the module names none.
  3. The module. In main.c the line LOG_MODULE_REGISTER(app, LOG_LEVEL_DBG); gives this file its own name, app, and its own level, debug. That level is the compile-time limit for this file, so a LOG_DBG line in it is kept in the binary.
  4. The output. With the logger on and the immediate mode chosen, the message is formatted and sent to the UART backend at once, and it appears on the serial monitor with a timestamp and a level tag.

The numbers matter here. Set CONFIG_LOG_DEFAULT_LEVEL=2 and a module without its own level drops its information messages, while the module that registers LOG_LEVEL_DBG still keeps its debug lines, because its own level wins. That is the rule the Kconfig help describes: the default applies only to modules that do not say what they want.

What logging costs

Options are not free, and the build reports the price. We measured the solution and the starter in the workspace with arm-none-eabi-size on each zephyr.elf. The starter has logging off and a 1024-byte main stack. The solution has logging on and a 2048-byte main stack.

BuildFlash (text plus data)RAM (data plus bss)
Starter: logging off, 1024-byte stack18,196 bytes3,974 bytes
Solution: logging on, 2048-byte stack22,552 bytes5,080 bytes

The flash grows by about 4.4 KB, and that is the logger's code and strings. The RAM grows by about 1.1 KB, but most of that is the stack change: the 2048-byte stack is 1024 bytes more than the starter's. Only the remaining 62 bytes or so come from logging itself. The lesson is that a size table has to say which option caused which change. If you change two options in one step, you cannot tell which one cost what.

These are our measurements of this workspace's builds, not a fixed figure for every Zephyr version. The numbers come from the zephyr.elf files that the build creates, using the Arm GNU toolchain 14.2 that the course installs. The build also prints a memory summary at the end, and the workspace has the targets rom_report and ram_report that print a tree of the largest symbols (cmake/reports/CMakeLists.txt). Use them to see which parts of the image grew.

Dependencies explain missing options

Open subsys/logging/backends/Kconfig.uart and you find the lines depends on UART_CONSOLE and default y if !SHELL_BACKEND_SERIAL. Two things follow. Setting CONFIG_LOG_BACKEND_UART=y does nothing unless the console is on, because the dependency is not satisfied. And the default for the UART backend is on only when the serial shell is off, so turning the shell on switches the UART backend off by default. When an option seems to have no effect, the first question is what it depends on.

Kconfig has two relations between symbols, and they behave differently. A depends on line is a condition: the symbol may be set only when the condition holds. A select line is a force: when the selecting symbol is on, the selected symbol is turned on too. The Zephyr guide has a section on select pitfalls (doc/build/kconfig/tips.rst in the workspace). Its example shows a select forcing a symbol on even though that symbol's new depends on is not met, so a select can bypass the check that a depends on would enforce. The build warns about the first kind of problem when an assignment is ignored, and the second kind shows up only as a symbol you did not expect in .config.

A symbol that depends on a disabled option is not an error by itself. The build prints a warning, the value you wrote is not applied, and the option is missing or n in .config. Read the warnings in the build output, not only the final line.

Where the DesignWare driver lives

The Pico's I2C controller is a Synopsys DesignWare block, and the Zephyr driver for it is in drivers/i2c/Kconfig.dw. That file is sourced from drivers/i2c/Kconfig at line 163, which is inside the if I2C block that begins at line 14. So the DesignWare menu, with the symbol I2C_DW, exists only when the I2C subsystem is on. The subsystem symbol is CONFIG_I2C. If you enable the Pico's I2C in a later lesson and nothing appears, check CONFIG_I2C first.

Common mistakes and how to spot them

Mistake 1: a misspelled symbol. Writing CONFIG_LOG_DEFAULT_LEVL=3, with one letter missing, is an easy typo. We built the solution with that one change, and the build stopped. The output said attempt to assign the value '3' to the undefined symbol LOG_DEFAULT_LEVL, followed by Aborting due to Kconfig warnings. The symptom is a build that fails before any code compiles, and the message names the symbol. The fix is to copy the name from the Kconfig file, not from memory. The search box in menuconfig is a second check.

Mistake 2: a symbol whose dependency is off. Setting CONFIG_LOG_BACKEND_UART=y while CONFIG_UART_CONSOLE is off does not turn the backend on, because the dependency is not met. The symptom is a Kconfig warning in the build output, and no log lines on the serial monitor. The fix is to read the warning, check the symbol's depends on line, and enable the parent first. A quick check is to search .config for the symbol: if the line is missing or says n, the assignment was not applied.

Mistake 3: trusting an old build. The configuration file build/zephyr/.config is reused as long as it is newer than its inputs, as the Zephyr guide explains. If you edit files in a way that does not change the timestamps the build checks, the old values can stay. The symptom is that prj.conf says one thing and .config says another, and a change in the file has no effect. The fix is a clean build: tools/build.py with --clean removes the build folder, and the next build regenerates everything. This is the check behind the interview answer below.

Mistake 4: editing the generated file. A learner who opens build/zephyr/.config and changes a line there will see the change work once. The next build may regenerate the file from prj.conf, and the edit is lost. The symptom is a value that was right and then, after a clean build, is wrong. The fix is to write the value in prj.conf, where it belongs, and treat .config as output to read, not input to edit.

Mistake 5: ignoring the cost. Turning on logging, a larger stack or a feature can push the image past the flash or RAM of the chip. The symptom is a link error that reports the region is full, or a build that succeeds but leaves too little RAM for the stacks. The fix is to read the memory summary after each change and to keep a record of the numbers, as the table above does.

In real projects

Teams that use Zephyr keep their options in prj.conf and board overlay files that are checked into version control, and they review changes to them as they review code. A change to a log level or a stack size is a change to the product's behaviour and its memory budget, so the review asks what the change costs. Many teams also keep a per-build size record, so a change that adds ten kilobytes shows up as a number in the review rather than as a surprise at release.

A common production pattern is a development configuration with debug logging and a release configuration with warnings only, with the difference written as a small overlay file. Another pattern is a configuration check in continuous integration, which builds every board and fails when a warning appears in the Kconfig output. Interviewers like the question that opens the interview answer below, because a good answer shows a method: find the final value, check the dependencies, and rebuild from clean.

Summary

  • A Kconfig symbol has a name starting with CONFIG_, a type, optional defaults, and optional depends on and select lines.
  • The final value comes from the board defconfig, CMake cache entries and the application configuration. A value in prj.conf overrides the board's defconfig, and a symbol with no setting uses its Kconfig default.
  • The file build/zephyr/.config is the final answer, and autoconf.h is generated from it for the C code.
  • CONFIG_LOG is the global switch: when it is off, the log calls do nothing. CONFIG_LOG_DEFAULT_LEVEL sets the level for modules that do not name their own, from 0 to 4.
  • An assignment whose dependencies are not met is ignored with a warning. A misspelled symbol stops the build.
  • Logging and bigger stacks cost flash and RAM. Measure each change, and keep the numbers.
  • When a value does not take effect, read .config, check the dependencies, and do a clean build.

"A value you set in a config file does not take effect. How do you find out why?" Answer out loud in 60 seconds, then compare.

Model answer

First check the final value in the generated config (build/zephyr/.config), which shows what the build actually used. If the symbol is missing, look at its dependencies: an assignment whose depends on is not met is ignored with a warning, so read the build output for that warning. A misspelled name stops the build with an undefined-symbol message. Then rebuild from clean, because a reused .config can keep an old value. Also say that a value outside the declared range is rejected.
