Bench lab 11: Stale DMA data

The DMA fills a buffer while the CPU does other work. If the CPU reads that buffer at the wrong moment, it gets half an old frame and half a new one, or the same frame twice. On the Nucleo-U5 you make both happen, count them, and fix them with double buffering. Then you read about the cache version of the bug, which faster chips add on top.

This bench lab is optional and a stretch. It needs the NUCLEO-U545RE-Q from bench lab 9; a logic analyzer helps but isn't required. It doesn't count towards your progress. Time: about 50 minutes.
By the end of this lab you can show torn and stale DMA frames on a real board, fix them with double buffering and a transfer-complete handshake, and explain why chips with a data cache need cache maintenance as well.

Two kinds of old data

Lesson 74 let the DMA fill a buffer while the CPU did other work, then read the buffer when the transfer-complete interrupt fired. The CPU and the DMA share one buffer, and the rule that makes this safe is about time: the CPU may read the buffer only between "the DMA finished" and "the DMA starts again". Break the rule and two things go wrong:

  • Torn data. The CPU reads while the DMA is writing. The first part of what it reads is the new frame, the rest is the old one. Each value looks fine; the frame as a whole is nonsense.
  • Stale data. The CPU reads again before a new frame has arrived, and processes the same frame twice as if it were fresh. An average looks smoother than it is; a counter counts one event twice.

Lesson 74 was concept-only because Wokwi doesn't simulate the Blue Pill's DMA. The U5 has a general-purpose DMA controller, GPDMA1, and here it runs for real.

The test rig

projects/bench11-stale-dma-data needs no wiring. A producer stands in for a peripheral: every millisecond, the SysTick handler starts a GPDMA1 memory-to-memory copy of one 256-word frame. The frames alternate between two sources, every word 0x55555555 or every word 0xAAAAAAAA, so a frame that contains both was read mid-copy. The main loop is the consumer: it reads a frame, checks it and counts. Once a second the ST-LINK's VCP prints frames produced, frames read, torn, stale and missed.

The DMA set-up is a single block. CTR1 sets 32-bit words with both addresses incrementing, CTR2_SWREQ makes it a memory-to-memory transfer started by software, CBR1 holds the size in bytes, and CCR enables the channel with its transfer-complete interrupt. The channel switches itself off at the end of the block, so the producer arms it again for each frame.

Optional analyzer wiring: D0 on PA6 (CN10 pin 13) is high while a copy runs, D1 on PA7 (CN10 pin 15) is high while the consumer reads, and GND goes to GND. Where the two overlap, that read is torn.

On the board: the starter

  1. Build projects/bench11-stale-dma-data/starter and copy build/dma.bin to the ST-LINK drive, as in bench lab 9. Open the VCP.
  2. Read the counts. The starter has one buffer, and the consumer reads it whenever it likes. Expect about 1000 frames produced per second, many more reads than that, most of them stale, and a steady share of torn ones.
  3. With the analyzer, capture 10 ms and find a read that overlaps a copy. Measure how long one copy takes and how long one read takes: those two numbers decide how often a read is torn.

On the board: double buffering

Fix it with two buffers and a handshake, as the solution does:

  1. Ping-pong. Frame n goes into buffer n % 2. While the CPU reads one buffer, the DMA writes the other.
  2. Publish on completion. The transfer-complete interrupt records which buffer is complete and the frame's number, in volatile variables: the buffer first, then the number.
  3. Wait for a new number. The consumer reads only when the frame number has changed, so it never reads a stale frame. Afterwards it checks that the number hasn't moved on by two, which would mean the DMA lapped it and came back to the buffer it was reading.

Run the solution: torn and stale stay at 0, and missed stays at 0 as long as the consumer keeps up with one frame per millisecond. Then make the consumer slow, with a busy loop of about 3 ms after each read, and watch missed frames appear while torn stays at 0. Skipping frames can be a deliberate design choice; reading torn ones never is. Real peripherals work the same way with a circular transfer and half-transfer and transfer-complete interrupts: the DMA fills one half while the CPU processes the other.

The cache version of the bug

Faster chips add a second way to read old data, and this one isn't about timing. A Cortex-M7, as in the STM32H7 and F7, has a level-1 data cache between the core and SRAM. It keeps copies of recently used memory in lines of 32 bytes (CMSIS, cachel1_armv7.h: __SCB_DCACHE_LINE_SIZE). The DMA writes SRAM and never goes through that cache, so after the first read the CPU can keep reading its cached copy of the buffer, however correct the handshake is.

Your U5 can't show this. Its DCACHE sits in front of external memory only (the OCTOSPI and FMC interfaces), and accesses to internal SRAM bypass it (ST training: STM32U5 system data cache). The rest of this section explains the bug and its two standard fixes, so you recognise it on a chip that has a data cache.

  1. The DMA fills adc_buf. The CPU reads it; the reads miss, so the core loads the buffer's lines into the cache. The first result is right.
  2. The DMA fills adc_buf again. It writes SRAM; the cached lines still hold the first block.
  3. The CPU reads again. The reads hit in the cache and return the first block. The result freezes until something evicts those lines.

The other direction fails too: the CPU's writes to a transmit buffer may still sit in a write-back cache when the DMA reads SRAM. Both bugs depend on what else the program does, so they can vanish when you add a printf to look for them.

Fix 1: cache maintenance

Tell the cache, at the right moments, that its copy is out of date. CMSIS provides the operations for a range of addresses (CMSIS, cachel1_armv7.h):

  • SCB_InvalidateDCache_by_Addr(addr, size) discards the cached copies of those lines, so the next read loads fresh data from SRAM. Call it after the DMA has written the buffer, before the CPU reads it.
  • SCB_CleanDCache_by_Addr(addr, size) writes any modified cached lines back to SRAM. Call it after the CPU has written a buffer, before the DMA reads it.
/* 32-byte aligned and a whole number of lines: invalidate touches nothing else. */
static uint16_t adc_buf[64] __attribute__((aligned(32)));   /* 128 bytes = 4 lines */

void dma_complete(void) {
    SCB_InvalidateDCache_by_Addr(adc_buf, sizeof adc_buf);   /* drop stale copies */
    process(adc_buf, 64);                                    /* now reads SRAM */
}

The alignment isn't decoration. Cache operations work on whole 32-byte lines. If adc_buf started in the middle of a line, invalidating it would also discard the cached copy of whatever variable shares that line, including changes not yet written back. That variable silently reverts to an older value. So a DMA buffer maintained this way must start on a 32-byte boundary and occupy whole lines.

Fix 2: an MPU region that isn't cached

The other approach removes the second copy. The MPU, which lesson 39 introduced for protection, also sets memory attributes per region, including whether a region may be cached. Put all DMA buffers in one section of RAM and make that region non-cacheable: 

/* Region 1: 32 KB at the DMA buffer section, normal memory, not cacheable. */
MPU->RBAR = ARM_MPU_RBAR(1, (uint32_t)&__dma_buffers_start);
MPU->RASR = ARM_MPU_RASR(1, ARM_MPU_AP_FULL, 1, 0, 0, 0, 0, ARM_MPU_REGION_SIZE_32KB);
ARM_MPU_Enable(MPU_CTRL_PRIVDEFENA_Msk);

The arguments follow CMSIS's ARM_MPU_RASR(DisableExec, AccessPermission, TypeExtField, IsShareable, IsCacheable, IsBufferable, SubRegionDisable, Size) (CMSIS, mpu_armv7.h): TEX = 1 with C = 0 and B = 0 is normal memory that isn't cached. An ARMv7-M region must be a power of two in size and aligned to its size, so the linker script (lesson 68) has to place the section accordingly. Every CPU access to those buffers then goes to SRAM, which is slower than a cache hit; for DMA buffers that the CPU reads once, that's usually fine.

You've made a DMA race visible on real hardware, counted it and removed it. When a reading looks impossible, you'll check who was writing the buffer at that moment, and, on a cached chip, which copy you read.

Common mistakes
  1. Reading the buffer because "the DMA is probably done". Wait for the transfer-complete flag or interrupt. Timing that works at one clock speed tears at another.
  2. Publishing the frame number before the buffer index. The consumer can see the new number together with the old index. Write the data first and the "ready" signal last.
  3. "Fixing" either bug with volatile alone. volatile makes the compiler read memory every time; it doesn't stop the DMA writing during the read, and it does nothing about a hardware data cache.
  4. On a cached chip: cleaning when you should invalidate, or the reverse. DMA writes memory: invalidate afterwards. DMA reads memory: clean first. And align the buffers to 32 bytes.

Summary

  • A CPU that reads a DMA buffer while the DMA writes it gets torn frames; one that reads before a new frame arrives gets stale ones.
  • Double buffering with a transfer-complete handshake fixes both: the DMA writes one buffer while the CPU reads the other, and the CPU reads only a newly published frame.
  • Publish the data first and the "ready" signal last, in volatile variables.
  • On a chip with a data cache in front of SRAM, such as a Cortex-M7, invalidate after the DMA writes and clean before it reads, on 32-byte aligned buffers, or put the buffers in a non-cacheable MPU region.
  • The U5's DCACHE serves external memory only, so only the timing version of the bug happens on it.
