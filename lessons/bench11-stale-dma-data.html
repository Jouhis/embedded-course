Bench lab 11: Stale DMA data

On a Cortex-M7 with a data cache, the DMA writes fresh samples to RAM and the CPU keeps reading old ones. This concept lab explains why, and the two standard fixes: cache maintenance and a non-cacheable MPU region.

This bench lab is optional, a stretch, and concept-only. It needs no hardware: an STM32H7 board is outside the bench track's budget, and no board in Wokwi has a data cache. If you do own an H7 (or F7) Nucleo, the last section tells you how to reproduce it. It doesn't count towards your progress. Time: about 30 minutes of reading and the quiz.
By the end of this lab you can explain why a CPU with a data cache can read stale DMA data, and fix it with cache invalidation or with an MPU region that makes the buffer non-cacheable.

Why the bug can't happen on the course's boards

Lesson 74 let the DMA fill a buffer while the CPU did other work, then read the buffer when the transfer-complete interrupt fired. On the Blue Pill's Cortex-M3 and the Pico's cores, that's safe: the CPU reads SRAM directly, so it always sees what the DMA wrote. There's one copy of the data.

A Cortex-M7, as in the STM32H7 and F7, has a level-1 data cache between the core and memory. A cache keeps copies of recently used memory in fast storage inside the core, in lines of 32 bytes (CMSIS, cachel1_armv7.h: __SCB_DCACHE_LINE_SIZE). Now there can be two copies of the buffer: one in SRAM, one in the cache. The DMA controller isn't the CPU: it writes to SRAM and never goes through the core's cache. Nothing updates the CPU's copy.

The failure, step by step

  1. The DMA fills adc_buf with the first block of samples. The CPU reads it to compute an average. The reads miss in the cache, so the core loads the buffer's lines from SRAM into the cache. The first average is right.
  2. The DMA fills adc_buf again with new samples. It writes SRAM; the cached lines still hold the first block.
  3. The CPU reads the buffer again. This time the reads hit in the cache, and return the first block's values. The average doesn't change, however the input changes, until something evicts those lines.

The other direction fails too. If the CPU fills a transmit buffer and starts a DMA transfer to a UART, the CPU's writes may still sit in the cache (a write-back cache writes memory later), and the DMA sends whatever was in SRAM before. Both bugs are timing-dependent: a busy program evicts lines sooner, so the bug can disappear when you add a printf to look for it.

It's a bench-only bug in the strongest sense: it lives in the cache hardware, and the Wokwi boards the course uses have no data cache at all.

Fix 1: cache maintenance

Tell the cache, at the right moments, that its copy is out of date. CMSIS provides the operations for a range of addresses (CMSIS, cachel1_armv7.h):

  • SCB_InvalidateDCache_by_Addr(addr, size) discards the cached copies of those lines, so the next read loads fresh data from SRAM. Call it after the DMA has written the buffer, before the CPU reads it.
  • SCB_CleanDCache_by_Addr(addr, size) writes any modified cached lines back to SRAM. Call it after the CPU has written a buffer, before the DMA reads it.
/* 32-byte aligned and a whole number of lines: invalidate touches nothing else. */
static uint16_t adc_buf[64] __attribute__((aligned(32)));   /* 128 bytes = 4 lines */

void dma_complete(void) {
    SCB_InvalidateDCache_by_Addr(adc_buf, sizeof adc_buf);   /* drop stale copies */
    process(adc_buf, 64);                                    /* now reads SRAM */
}

The alignment isn't decoration. Cache operations work on whole 32-byte lines. If adc_buf started in the middle of a line, invalidating it would also discard the cached copy of whatever variable shares that line, including changes the CPU hadn't yet written back. That variable silently reverts to an older value: a second, worse bug. So a DMA buffer that's maintained this way must start on a 32-byte boundary and occupy whole lines.

Fix 2: an MPU region that isn't cached

The other approach removes the second copy. The MPU, which lesson 39 introduced for protection, also sets memory attributes per region, including whether a region may be cached. Put all DMA buffers in one section of RAM, and make that region non-cacheable: 

/* Region 1: 32 KB at the DMA buffer section, normal memory, not cacheable. */
MPU->RBAR = ARM_MPU_RBAR(1, (uint32_t)&__dma_buffers_start);
MPU->RASR = ARM_MPU_RASR(1, ARM_MPU_AP_FULL, 1, 0, 0, 0, 0, ARM_MPU_REGION_SIZE_32KB);
ARM_MPU_Enable(MPU_CTRL_PRIVDEFENA_Msk);

The arguments follow CMSIS's ARM_MPU_RASR(DisableExec, AccessPermission, TypeExtField, IsShareable, IsCacheable, IsBufferable, SubRegionDisable, Size) (CMSIS, mpu_armv7.h): TEX = 1 with C = 0 and B = 0 is normal memory that isn't cached. An ARMv7-M region must be a power of two in size and aligned to its size, so the linker script (lesson 68) has to place the section accordingly.

Every CPU access to those buffers now goes to SRAM, which is slower than a cache hit. For DMA buffers that's usually fine: the CPU reads each sample once, so the cache wasn't helping much anyway.

If you have an H7 or F7 board

Reproduce it with lesson 74's ADC-and-DMA design: enable the caches with SCB_EnableICache() and SCB_EnableDCache(), fill a buffer by DMA in a loop, and print the average while you turn a potentiometer. The average freezes. Add the invalidation, or the MPU region, and it follows the knob. Then misalign the buffer by 4 bytes and put a counter in the same cache line: watch the counter jump back. The STM32CubeH7 package's examples show the clock and DMA set-up for each Nucleo board.

Common mistakes

  1. Invalidating before the DMA finishes. The CPU may load lines again while the DMA is still writing. Invalidate after completion, right before reading.
  2. Cleaning when you should invalidate, or the reverse. DMA writes memory: invalidate. DMA reads memory: clean first.
  3. Unaligned DMA buffers. Invalidation discards whole 32-byte lines, including neighbours' unsaved changes. Align to 32 and round sizes up.
  4. "Fixing" it with volatile. volatile stops the compiler from caching a value in a register; it does nothing about the hardware data cache.

Summary

  • A Cortex-M7's data cache can hold a copy of a buffer that the DMA has since rewritten in SRAM.
  • DMA writes, CPU reads: invalidate the lines after the transfer. CPU writes, DMA reads: clean the lines before it.
  • Cache operations work on 32-byte lines; DMA buffers must be aligned and padded to whole lines.
  • An MPU region marked non-cacheable removes the problem for every buffer placed in it.
  • volatile doesn't affect the hardware cache; the course's Wokwi boards have no data cache, so the bug never appears there.
You can now explain one of the classic bugs of moving to a faster chip, and fix it two ways. When you meet an H7 at work, you'll check the cache before you suspect the DMA.
