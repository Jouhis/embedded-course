Navigating a reference manual

Finding addresses, bit fields and reset values in chip documentation

By the end of this lesson you can find a peripheral's base address, its register offsets, its reset values and its bit fields in the RP2040 datasheet, and cross-check each one against the STM32 device header.

Checking the numbers yourself

Lessons 38 to 42 assembled the hardware picture: a register is an address (lesson 38), a clock comes from a tree of oscillators and PLLs (lesson 40) and the linker places the variables (lesson 41). Each lesson quoted numbers from a manual or a header that you have so far taken on trust, and this lesson shows how to check them and how to find the next one without help.

On a new board a common problem starts when a colleague writes a register address from memory, or copies one from a forum post about a different chip. The program then writes to a register that does something else, nothing reports an error, and the LED stays dark or a motor turns the wrong way. The defence is a short habit of finding the address and reset state in the manual, confirming them in the header and checking the chip's errata before trusting the peripheral, and teams that work this way find such bugs at the desk rather than on the bench.

The contents of a reference manual

A reference manual describes the chip for the programmer, and although each vendor names the parts differently, it is organised predictably. Four kinds of content matter for this course:

  • an address map showing which region of the 32-bit address space each block occupies (lesson 38);
  • a chapter for each peripheral, with its base address and register list;
  • a register description for each register, with a table of bit fields, their names and their meanings;
  • a reset value for each register, the value it holds after reset, given in the register's own table.

The header file is a different kind of document, giving names, addresses and bit positions as C macros and structs for the compiler. The manual is the specification and the header an implementation of it, so when the two disagree the manual is right and the header has a bug to report. The errata sheet sits beside both and lists known faults the manual does not describe (lesson 44). The manual says what the chip should do, and the errata sheet lists where it does not.

A datasheet compares to a car's brochure and specification sheet, with engine power, size and limits, while the reference manual compares to the workshop manual, explaining how each part works, which bolt holds it and in what order it comes apart. A car is chosen with the first and repaired with the second, and a chip is mostly programmed with the second. The comparison weakens for the RP2040, though, whose single datasheet serves both purposes.

Four lookups in the RP2040 datasheet

The RP2040 datasheet doubles as its reference manual and is short enough to search with a text editor. Four questions cover most needs, and each has a predictable place to look.

The first question shows the method. Table 15 is the address map summary, with the detail in section 2.2.2, and section 2.2.1 lists the regions in order: ROM, XIP, SRAM, APB peripherals, AHB-Lite peripherals, the IOPORT area and the Cortex-M0+ internal registers, starting at 0x00000000, 0x10000000, 0x20000000, 0x40000000, 0x50000000, 0xD0000000 and 0xE0000000. The summary and the detail agree with lesson 38's table, but read the one in the datasheet, because the datasheet is the authority.

Worked example: the SIO block's registers start at 0xD0000000, as section 2.3.1.7 states: "The SIO registers start at a base address of 0xd0000000 (defined as SIO_BASE in SDK)." Its register list places GPIO_OUT at 0x010, GPIO_OUT_SET at 0x014, GPIO_OUT_CLR at 0x018 and GPIO_OUT_XOR at 0x01C, so GPIO_OUT_CLR is at 0xD0000000 + 0x018 = 0xD0000018, the same base-plus-offset sum as in lesson 38.

The third question is the one most people search for first, and the datasheet's register list answers it, each row giving an offset, a name and a short description. Find the row for your register and write the offset down before reading the register's own page, a habit that catches typing mistakes because it leaves a number to compare with the header later.

Register descriptions and field tables

Each register in the datasheet has its own section, headed by its name and its offset from the block base, for example "SIO: GPIO_OUT_SET Register, Offset: 0x014". Below comes a table with one row per bit field, whose columns give the bits, the field name, the access type and the description, while a Reset column on the same page gives the value after reset. The access types, such as RW for read-write and WO for write-only, are defined in Appendix A, "Register Field Types".

A common error is to read the reset value as if it applied uniformly to every bit, whereas it is given for the whole register and each field's bits take their share of it. Read the field table row by row and note the bit positions you need. The bits of GPIO_OUT_SET, for instance, are marked WO, write-only, so they cannot be read back from that register, and the result has to be checked through a readable register such as GPIO_OUT.

RM0008 and the STM32F1 header

The STM32F103 reference manual is RM0008, whose full title, listed in RESOURCES.md, is "STM32F101xx, STM32F102xx, STM32F103xx, STM32F105xx and STM32F107xx advanced ARM-based 32-bit MCUs" (RM0008 Rev 21, title page). It therefore covers the whole family, including features the Blue Pill lacks, with a chapter for each peripheral and a register description for each register in the same style as the RP2040's tables.

In RM0008 Rev 21 the GPIO chapter is chapter 9, with the register descriptions for GPIOx_CRL, CRH, IDR, ODR, BSRR, BRR and LCKR in sections 9.2.1 to 9.2.7 and the register map table in section 9.5. Find the GPIO chapter in your own copy, search the headings for the register names and note the section numbers yourself before checking them against these, because revisions change the numbering and your copy is the one that matters.

The header, third_party/cmsis-device-f1/Include/stm32f103xb.h, is the cross-check. Its GPIO_TypeDef struct lists the GPIO registers in the manual's order, CRL, CRH, IDR, ODR, BSRR, BRR and LCKR, each 4 bytes wide, so the offsets follow from the order: CRH at offset 4 and BSRR at offset 16, or 0x10. RM0008 Rev 21 gives the same offsets, CRL at 0x00 (section 9.2.1), CRH at 0x04 (section 9.2.2) and BSRR at 0x10 (section 9.2.5), and the GPIOC base of 0x40011000 from GPIOC_BASE (the APB2 base plus 0x1000) matches GPIO port C in Table 3 of RM0008 (section 3.3).

The header carries names, addresses and bit positions but not reset values. A few field comments mention a reset state, but the reset value of each register lives only in the manual, so a reset value always comes from RM0008, and the header can confirm only the offset and the bit name.

Worked example: verifying the GPIOC BSRR address

Suppose you need the address of the Blue Pill's BSRR register and want to confirm it before writing code, using only the header and the manual. Before starting, decide which of the two sources each step should use.

  1. Find the base. GPIOC_BASE is APB2PERIPH_BASE + 0x1000, APB2PERIPH_BASE is PERIPH_BASE + 0x10000 and PERIPH_BASE is 0x40000000, so the base is 0x40000000 + 0x10000 + 0x1000 = 0x40011000.
  2. Find the offset. In GPIO_TypeDef, CRL is at 0, CRH at 4, IDR at 8, ODR at 12 and BSRR at 16, so the offset is 0x10.
  3. Add them. 0x40011000 + 0x10 = 0x40011010, the address the compiler computes for GPIOC->BSRR.
  4. Check the manual. Open the GPIO chapter of RM0008, find the register map table, confirm the BSRR offset of 0x10 and the base address in your copy, and note the section number beside your answer. The answer to check against is section 9.2.5 for BSRR at offset 0x10, with the register map in section 9.5, while Table 3 (section 3.3) gives the GPIO port C base as 0x4001 1000.
  5. Check the errata. Look up the GPIO block in the errata sheet for your revision, since a known problem with a register changes how it is used even when the address is right.

Each step has one source: the header for the arithmetic, the struct for the offset, and the manual and errata for the final checks. If any step disagrees with the one before, stop and establish which source is right before writing code.

Cross-checking the RP2040 SDK headers

The RP2040 works the same way, with the SDK's header in the role of the STM32 header. The SDK defines SIO_BASE as 0xD0000000, and its register header gives SIO_GPIO_OUT_SET_OFFSET as 0x14 and SIO_GPIO_OUT_CLR_OFFSET as 0x18, matching the datasheet table that lesson 38 used (src/rp2040/hardware_regs/include/hardware/regs/sio.h, pico-sdk 2.3.1). In an SDK header, check that the base macro matches Table 15 and that the register offset macros match the list in the block's section. A mismatch means one of them is wrong, and the datasheet wins until an erratum or a newer revision says otherwise.

The demo code and its expected output

The project projects/0043-reference-manual prints the addresses the compiler computes for five registers, and its key lines are these. 

print_line("GPIOC base:           ", GPIOC_BASE);
print_line("GPIOC->CRH address:   ", (uint32_t)(uintptr_t)&GPIOC->CRH);
print_line("GPIOC->BSRR address:  ", (uint32_t)(uintptr_t)&GPIOC->BSRR);

The first line prints the base macro directly, and the next two take the address of a struct member, &GPIOC->CRH, which the compiler computes as the base plus the member's offset without reading the register, since only the address is taken. The cast to uintptr_t turns the pointer into an integer that print_hex can print, the remaining lines do the same for RCC->APB2ENR and USART1->DR, and the UART setup routes the output to the serial monitor, as the template describes.

Because the output is the compiler's arithmetic, the expected lines can be computed in advance from the header's base macros and offsets. The RCC base is AHBPERIPH_BASE + 0x1000, or 0x40021000, with APB2ENR as the seventh word of RCC_TypeDef at offset 0x18, and the USART1 base is APB2PERIPH_BASE + 0x3800, or 0x40013800, with DR at offset 4. RM0008 Rev 21 agrees, giving 0x4002 1000 for RCC and 0x4001 3800 for USART1 in Table 3 (section 3.3), the RCC_APB2ENR offset of 0x18 in section 7.3.7 and the USART_DR offset of 0x04 in section 27.6.2.

Try it in Wokwi

The project projects/0043-reference-manual is a single demo that prints the GPIOC base address and the addresses of four registers computed through the structs.

  1. Open projects/0043-reference-manual in VS Code, build with Ctrl+Shift+B, and start the simulator with F1 → Wokwi: Start Simulator.
  2. Before reading the output, write down the expected lines: GPIOC base: 0x40011000, GPIOC->CRH address: 0x40011004, GPIOC->BSRR address: 0x40011010, RCC->APB2ENR address: 0x40021018 and USART1->DR address: 0x40013804, each a base plus an offset from the header.
  3. Compare the serial monitor with your list, which should match on all five lines. If one differs, find the struct member or base macro you used and check its offset.
  4. In your own copy of RM0008, find the GPIO register map and look up the offset and reset value of CRH and BSRR, noting the section number beside each answer; since the header cannot give reset values, the manual is the only source here. The answers to check against are CRH at offset 0x04 with reset value 0x4444 4444 (section 9.2.2) and BSRR at offset 0x10 with reset value 0x0000 0000 (section 9.2.5).
Hint

The fields of GPIO_TypeDef are CRL, CRH, IDR, ODR, BSRR, BRR and LCKR, in that order and each 4 bytes wide, so CRH is at offset 4 and BSRR at 16, or 0x10. For the RCC, count the fields of RCC_TypeDef up to APB2ENR.

Reading the reference manual is the real task, and the simulator only checks it: the demo prints the addresses the compiler computes, so it confirms your reading of the header.

Common mistakes and how to spot them

An address copied from an old example

The code writes to a plausible address, the build passes, and the expected pin does not change, because the address belongs to another peripheral or another chip in the family. Take the base and offset from your own part's manual and header, and write the sum in the code as base + offset, so that a reviewer can check it at a glance.

A reset value sought in the header

A search of the header for the reset value of CRH finds nothing, so a guessed value goes into the initialisation code, which then assumes a state the chip does not start in. Take reset values from the manual's register tables, for example 0x4444 4444 for GPIOx_CRH in RM0008 Rev 21, section 9.2.2, and note the value beside the code that depends on it so that the assumption is visible.

The errata sheet skipped

The code follows the manual exactly, yet the peripheral still fails in one case, such as after a particular boot path or at a particular voltage. Read the errata for a block before using it. The RP2040 datasheet's Appendix B is an example, whose first entry, RP2040-E9, states that booting directly into the XIP cache-as-SRAM alias "causes an immediate bus fault" and gives a workaround that a reader who skipped the appendix would never learn.

Section numbers trusted across revisions

A lesson or a colleague cites "section 2.19.6.1", and in a different revision of the document that section is about something unrelated. Cite the table or register name together with the section number and check the document revision; for the RP2040, the register name in the section heading is the safe key.

Traceable register code in real projects

On a real project every register access in the driver code should trace back to a line in the manual, and code review checks that trace by asking where each number came from. A good answer names the document, its revision, the section and the table, along with the header macro the code uses. Teams keep a short list of the chip's errata next to the driver and consult it whenever a peripheral's setup changes. Vendors also publish SVD files, machine-readable register descriptions from which tools generate headers, but a generated header is still only a cross-check, and the manual remains the source the team answers to.

Summary

  • A reference manual gives the address map, a chapter per peripheral, a register list with offsets, and a table of bit fields and reset values for each register.
  • On the RP2040 the address map is Table 15 in section 2.2, the SIO register list is in section 2.3.1.7 and the errata are in Appendix B.
  • The header gives base macros, offsets as struct members and bit names, but not reset values.
  • Write a register address as base plus offset, and check the offset against both the manual and the header.
  • When the header and the manual disagree, the manual is right and the header has a bug to report.
  • Read a block's errata before relying on it, because a correct address can still hit a known fault.
  • Cite a table or register name with every section number, because section numbers change between revisions.
RP2040 datasheet: read section 2.2 (Address Map, with Table 15), then section 2.3.1.7 (SIO list of registers), then Appendix A (Register Field Types) and Appendix B (Errata). The habits here carry over to RM0008, which is a longer manual.
