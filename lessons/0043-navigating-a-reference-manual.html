Navigating a reference manual

The answer to almost every hardware question is in the reference manual. The skill is knowing which table to open, and how to cross-check it against the header file.

By the end of this lesson you can find a peripheral's base address, its register offsets, its reset values and its bit fields in the RP2040 datasheet, and cross-check each one against the STM32 device header.

Where we are and why it matters

Lessons 38 to 42 gave you the pieces of the hardware picture: a register is an address (lesson 38), a clock comes from a tree of oscillators and PLLs (lesson 40), and the linker places your variables (lesson 41). Each of those lessons quoted a number from a manual or a header, and you have been trusting those numbers. This lesson shows how to check them yourself, and how to find the next one without help.

The problem this lesson solves is a common one on a new board. A colleague writes a register address from memory, or copies one from a forum post for a different chip, and the program writes to a register that does something else. Nothing reports an error. The LED does not light, or a motor drives the wrong way. The defence is a short habit: find the address and the reset state in the manual, confirm it in the header, and check the chip's errata before you trust the peripheral. Teams that work this way find those bugs at the desk, not on the bench.

What a reference manual contains

A reference manual describes the chip for the programmer. It is organised in a predictable way, although each vendor names its parts differently. Four kinds of content matter for this course:

  • an address map, which shows which region of the 32-bit address space each block sits in (lesson 38);
  • a chapter for each peripheral, with its own base address and its register list;
  • a register description for each register, with a table of bit fields, their names and their meanings;
  • a reset value for each register, which is the value the register holds after reset. The manual gives it in the register's own table.

The header file is a different kind of document. It gives names, addresses and bit positions as C macros and structs, which the compiler uses. The manual is the specification. The header is an implementation of that specification. When they disagree, the manual is right, and the header is a bug to report. The errata sheet sits beside both and lists known faults that the manual does not describe (lesson 44). The manual says what the chip should do. The errata sheet says where it does not.

Four questions, four places in the RP2040 datasheet

The RP2040 datasheet doubles as its reference manual, and it is short enough to search with a text editor. Four questions cover most of what you need, and each has a predictable place to look.

Here is the first question worked through. Table 15 is the address map summary, and section 2.2.2 gives the detail. Section 2.2.1 lists the regions in order: ROM, XIP, SRAM, APB peripherals, AHB-Lite peripherals, the IOPORT area and the Cortex-M0+ internal registers. Those start at 0x00000000, 0x10000000, 0x20000000, 0x40000000, 0x50000000, 0xD0000000 and 0xE0000000. The summary and the detail agree with lesson 38's table. Read the table in the datasheet rather than this one, because the datasheet is the authority.

Worked example. The SIO block's registers start at 0xD0000000, as section 2.3.1.7 states: "The SIO registers start at a base address of 0xd0000000 (defined as SIO_BASE in SDK)." In its list of registers, GPIO_OUT is at 0x010, GPIO_OUT_SET at 0x014, GPIO_OUT_CLR at 0x018 and GPIO_OUT_XOR at 0x01C. The address of GPIO_OUT_CLR is therefore 0xD0000000 + 0x018 = 0xD0000018, the same base-plus-offset sum as lesson 38.

The third question is the one most people search for first, and the datasheet's list is the place for it. Each row gives an offset, a name and a short description. Find the row for your register, and write the offset down before you read the register's own page. That habit catches typing mistakes, because you have a number to compare against the header later.

Reading a register description

Each register in the datasheet has its own section. It starts with the register's name and its offset from the block base, for example "SIO: GPIO_OUT_SET Register, Offset: 0x014". Below that comes a table with one row for each bit field, and the table's columns give the bits, the field name, its access type and its description. A Reset column on the same page gives the value the register holds after reset. The access types, such as RW for read-write and WO for write-only, are defined in Appendix A, "Register Field Types".

A common error is to read the reset value as if it applied to every bit. The reset value is given for the register, and each field's bits take their part of it. Read the field table row by row, and write down the bit positions you care about. The bits of GPIO_OUT_SET are marked WO, write-only, so you cannot read them back from that register. Check the result through a readable register, such as GPIO_OUT.

The STM32F1: RM0008 and the header

The STM32F103 reference manual is RM0008. Its full title, listed in RESOURCES.md, is "STM32F101xx, STM32F102xx, STM32F103xx, STM32F105xx and STM32F107xx advanced ARM-based 32-bit MCUs". So the manual covers the whole family, and it contains features that your Blue Pill does not have. Each peripheral has its own chapter, and that chapter has a register description for each register, in the same style as the RP2040 table.

This course has not yet fetched RM0008 to check its chapter and section numbers, its register tables or its reset values. The lesson therefore does not quote any RM0008 section number or reset value. Find the GPIO chapter in your copy, search for the register names in the headings, and write down the section number yourself. Your copy is the one that matters, because revisions change the numbering.

The header, third_party/cmsis-device-f1/Include/stm32f103xb.h, is the cross-check. Its GPIO_TypeDef struct lists the GPIO registers in order: CRL, CRH, IDR, ODR, BSRR, BRR and LCKR, each 4 bytes wide. The struct's field order is the register order in the manual, so the offsets follow from the order. CRH is at offset 4, and BSRR is at offset 16, which is 0x10. The GPIOC base is 0x40011000, from GPIOC_BASE in the same header (APB2 base plus 0x1000).

The header carries names, addresses and bit positions. It does not carry reset values. A few field comments mention a reset state, but the table of reset values for each register lives in the manual only. So when this lesson asks for a reset value, the answer comes from RM0008, and the header can only confirm the offset and the bit name.

A worked example: checking one register

Suppose you need the address of the BSRR register on the Blue Pill, and you want to confirm it before you write code. Work through the steps in order, using only the header and the manual.

  1. Find the base. GPIOC_BASE is APB2PERIPH_BASE + 0x1000. APB2PERIPH_BASE is PERIPH_BASE + 0x10000, and PERIPH_BASE is 0x40000000. So the base is 0x40000000 + 0x10000 + 0x1000 = 0x40011000.
  2. Find the offset. In GPIO_TypeDef, CRL is at 0, CRH at 4, IDR at 8, ODR at 12 and BSRR at 16. The offset is 0x10.
  3. Add them. 0x40011000 + 0x10 = 0x40011010. That is the address the compiler computes for GPIOC->BSRR.
  4. Check the manual. Open the GPIO chapter of RM0008, find the register map table, and confirm that the BSRR offset is 0x10 and that the base address in your copy agrees. Write the section number beside your answer.
  5. Check the errata. Look up the GPIO block in the errata sheet for your revision. A known problem with a register changes how you use it, even when the address is right.

Each step has one source. The arithmetic uses the header, the offset check uses the struct, and the final two steps use the manual and the errata. If any step disagrees with the one before, stop and find out which source is right before you write code.

Cross-checking the RP2040 against the code

The RP2040 works the same way, and the SDK's header plays the role of the STM32 header. Lesson 38 used the SIO register offsets, and the datasheet gives the same numbers in its list. The SDK defines SIO_BASE as 0xD0000000, and its register header gives SIO_GPIO_OUT_SET_OFFSET as 0x14 and SIO_GPIO_OUT_CLR_OFFSET as 0x18, the same as the datasheet table (src/rp2040/hardware_regs/include/hardware/regs/sio.h, pico-sdk 2.3.1). When you read an SDK header, look for two things: the base macro, which should match Table 15, and the register offset macros, which should match the list in the section for that block. A mismatch means one of the two is wrong, and the datasheet wins until an erratum or a newer revision says otherwise.

The code, and what the demo prints

The project projects/0043-reference-manual prints the addresses that the compiler computes for five registers. Its key lines are these: 

print_line("GPIOC base:           ", GPIOC_BASE);
print_line("GPIOC->CRH address:   ", (uint32_t)(uintptr_t)&GPIOC->CRH);
print_line("GPIOC->BSRR address:  ", (uint32_t)(uintptr_t)&GPIOC->BSRR);

The first line prints the base macro directly. The second and third lines take the address of a struct member, &GPIOC->CRH. The compiler computes that address as base plus the member's offset, and it does not read the register, because only the address is taken. The cast to uintptr_t turns the pointer into an integer so that print_hex can print it. The fourth and fifth lines do the same for RCC->APB2ENR and USART1->DR. The UART setup in the file routes the output to the serial monitor, as the template describes.

Because the output is the compiler's arithmetic, you can compute the expected lines yourself. The values below come from the header's base macros and offsets. The RCC base is AHBPERIPH_BASE + 0x1000, which is 0x40021000, and APB2ENR is the seventh word of RCC_TypeDef, at offset 0x18. USART1's base is APB2PERIPH_BASE + 0x3800, which is 0x40013800, and DR is at offset 4.

Try it in Wokwi

The project projects/0043-reference-manual is a single demo. It prints the base address of GPIOC and the addresses of four registers that the struct computes.

  1. Open projects/0043-reference-manual in VS Code, build with Ctrl+Shift+B, and start the simulator with F1 → Wokwi: Start Simulator.
  2. Before you read the output, write down the expected lines: GPIOC base: 0x40011000, GPIOC->CRH address: 0x40011004, GPIOC->BSRR address: 0x40011010, RCC->APB2ENR address: 0x40021018 and USART1->DR address: 0x40013804. Each one is a base plus an offset from the header.
  3. Compare the serial monitor with your list. All five lines should match exactly. If one differs, find the struct member or base macro that you used and check its offset.
  4. Open RM0008 in your own copy and find the GPIO register map. Find the offset of CRH and BSRR and the reset value of each, and write the section number next to each answer. The header cannot give you the reset values, so this is the step where the manual is the only source.
Hint

In the struct GPIO_TypeDef, the fields are CRL, CRH, IDR, ODR, BSRR, BRR and LCKR, in that order, each 4 bytes wide. CRH is at offset 4, and BSRR is at offset 16, which is 0x10. For the RCC, count the fields of RCC_TypeDef until you reach APB2ENR.

Reading a reference manual is the job, and the simulator is only a check. The demo's outputs are the addresses that the compiler computes, so they confirm your reading of the header.

Common mistakes

Mistake 1: copying an address from an old example

Symptom: the code writes to the right-looking address, the build passes, and the pin you expected does not change. The address belongs to a different peripheral, or to a different chip in the same family. Fix: take the base and the offset from your own part's manual and header, and write the sum in the code as base + offset, so a reviewer can check it at a glance.

Mistake 2: reading the reset value from the header

Symptom: you search the header for the reset value of CRH, find nothing, and guess one. Your initialisation code then assumes a state that the chip does not start in. Fix: take reset values from the manual's register table. Write the reset value beside the code that depends on it, so the assumption is visible.

Mistake 3: skipping the errata sheet

Symptom: the code follows the manual exactly, and the peripheral still fails in one case, such as after a certain boot path or at a certain voltage. Fix: read the errata for the block before you use it. The RP2040 datasheet's Appendix B is an example. Its first entry, RP2040-E9, says that booting directly into the XIP cache-as-SRAM alias "causes an immediate bus fault", and it gives a workaround. A manual reader who skipped Appendix B would not know that.

Mistake 4: trusting section numbers across revisions

Symptom: a lesson or a colleague cites "section 2.19.6.1", and you open a different revision of the document and land somewhere unrelated. Fix: cite the table or register name as well as the section number, and check the document revision. For the RP2040, the register name in the section heading is the safe key.

In real projects

On a real project, every register access in the driver code should trace back to a line in the manual. Code review checks that trace by asking where a number came from. A good answer names the document, the revision, the section and the table, and it names the header macro that the code uses. Teams keep a short list of the chip's errata next to the driver, and they check the list when they change a peripheral's setup. Vendors also publish SVD files, machine-readable descriptions of the registers, and tools generate headers from them. The generated header is still only a cross-check. The manual is the source the team answers to.

In interviews, a question about a new microcontroller usually tests this skill directly. The strong answer names the order of the lookups: the address map for the base, the register list for the offset, the register's table for the reset value and fields, the header to confirm, and the errata before the code ships. The candidate who says "I look it up" without naming the source is not yet at the level the job needs.

Summary

  • A reference manual gives the address map, a chapter per peripheral, a register list with offsets, and a table of bit fields and reset values for each register.
  • On the RP2040, the address map is Table 15 in section 2.2, the SIO register list is section 2.3.1.7, and the errata are in Appendix B.
  • The header gives base macros, offsets as struct members and bit names. It does not give reset values.
  • Write a register address as base plus offset, and check the offset against the manual and the header.
  • When the header and the manual disagree, the manual is right, and the header is a bug to report.
  • Read the errata for a block before you rely on it, because a correct address can still hit a known fault.
  • Cite a table or register name with the section number, because section numbers change between revisions.
You can find a register's address, its offset, and its reset value in a reference manual, and you know which part of the header is the cross-check.

"You have a new microcontroller and need the address and reset value of one peripheral register. What do you do?" Answer out loud in 60 seconds, then compare.

Model answer

Find the peripheral's chapter in the reference manual, and its base address in the memory map. Then read the register map table for the offset, and the register's own table for the reset value and the bit fields. Cross-check the offset against the vendor's header file, which should agree, since the header gives the offset but not the reset value. Check the errata sheet for the chip's known problems with that peripheral. Write the address as base plus offset in the code, never as a number copied from elsewhere.

RP2040 datasheet: read section 2.2 (Address Map, with Table 15), then section 2.3.1.7 (SIO list of registers), then Appendix A (Register Field Types) and Appendix B (Errata). This is the best practice on a short manual, and the same habits carry over to RM0008.
