The stack and the AAPCS calling convention

When one function calls another, the two have to agree on where arguments go, which registers must survive the call, and where the return address is kept. That agreement is the calling convention.

By the end of this lesson you can say where the arguments and the return value go in a call, which registers a function must preserve, and what a full-descending stack looks like after a PUSH, then check all of it in the CPU simulator.

Where we are and why it matters

Lesson 32 traced sum_to and showed the caller putting 100 in R0 and calling the function with bl. It said that the calling convention decides where the argument goes, and this lesson gives the rules. Lesson 31 introduced LR and SP as registers with special roles. Lesson 34 will show that the hardware itself uses the stack when an interrupt arrives, so the same rules apply there too.

The calling convention matters on real boards for three reasons. A function that does not follow it silently corrupts its caller, and the bug appears far from the cause. A stack that is too small overwrites other RAM, and the crash appears in an unrelated function. And an RTOS gives each task its own stack, so the stack layout decides how many tasks you can run.

The concepts, one at a time

The stack is a region of RAM

The stack is a region of RAM that a program uses for data that belongs to a function call: its saved registers, its local variables that do not fit in registers, and the return address. Unlike flash, RAM can be written, so the stack can change while the program runs. On the RP2040 the SRAM begins at 0x20000000, and the Pico SDK defines the end of that region as 0x20042000, which is 264 KB (pico-sdk 2.3.1, src/rp2040/hardware_regs/include/hardware/regs/addressmap.h).

The stack pointer, SP (R13), holds the address of the top of the stack, which is the most recent item pushed. The AAPCS describes the stack as full-descending: "The stack implementation is full-descending, with the current extent of the stack held in the register SP" (Arm ABI, AAPCS, "The Stack"). Full means that SP points at the last item pushed. Descending means the stack grows toward lower addresses, so a push first moves SP down and then writes the item. A pop reads the item at SP and then moves SP up.

Two of the AAPCS stack constraints apply to every function. The first is that "SP mod 4 = 0", which means the stack is always word-aligned. The second is that a program "may only store data in the closed interval of the entire stack delimited by [SP, stack base − 1]". In other words, a function may write only to the stack between the current top and the base, never below SP. The stack has a size, and the linker reserves it. The Pico SDK reserves a stack of PICO_STACK_SIZE bytes, whose default is 0x800, which is 2 KB per core (pico-sdk 2.3.1, src/rp2040/pico_platform/include/pico/platform.h).

Caller and callee: who does what

The caller is the function that makes the call. The callee is the function that is called. The AAPCS divides the registers between them. The rules that matter first are these, quoted from the AAPCS "Core registers" section.

RegisterRole under the AAPCSWho must care
R0 to R3Arguments in, result out. "The first four registers r0-r3 (a1-a4) are used to pass argument values into a subroutine" and to return a result. They may be changed freely.The callee may change them. The caller must not expect them to survive the call.
R4 to R8, R10, R11, SP"A subroutine must preserve the contents of the registers r4-r8, r10, r11 and SP."The callee must restore them before it returns.
R9"The role of register r9 is platform specific." On some platforms it is preserved, and on others it is a special register.Check the platform's documentation before you use it.
R12 (IP)"May be used by a linker as a scratch register between a routine and any subroutine it calls."Treat it as changed by any call.
LR (R14)Holds the return address after a bl.A function that calls another must save LR first.

The rule for R4 to R8 is the one that matters most in practice. The callee owns the promise to restore them, and the caller can rely on them after the call. A function that uses R4 for its own work must save R4 on entry and restore it on exit. If it does not, the caller's R4 is changed, and the caller finds the wrong value later, far from the place where it went wrong.

Arguments beyond four go on the stack

The four argument registers are enough for most functions. When a function has more arguments, the rest are placed on the stack. The AAPCS calls the address for the next stacked argument the NSAA, and its parameter-passing rules copy each argument that does not fit in the registers "to memory at the NSAA" (Arm ABI, AAPCS, Parameter Passing, rules C.5 to C.8). The caller reserves that space before the call. So the fifth argument is at the caller's SP when the call starts, and the callee reads it from there.

Return addresses and the link register

A bl writes the return address into LR and then branches. A function returns with bx lr, which branches to the address in LR. A function that calls another function would overwrite LR with its own inner return address, so it must save LR on the stack before its own call, and restore it at the end. The common pattern is push {..., lr} at the start and pop {..., pc} at the end, which pops the saved return address straight into the PC. The pop into PC is the return.

Stack frames and PUSH

A stack frame is the block of words a function or an exception pushes onto the stack. A push instruction takes a list of registers, moves SP down by four bytes for each register in the list, and stores the registers there. A pop reverses it: it loads the registers from the stack and moves SP up. The list is one instruction, so one push {r4, lr} moves SP down by 8 bytes.

The figure shows the course simulator's layout for PUSH {R4, LR} from SP = 0x20000100. The simulator puts R4 at the lowest address, where SP points, and LR in the word above it. The order of the registers inside a real push is a detail of the hardware. Check a real frame in the debugger's memory view before you rely on an offset.

The ABI rule that R4 is preserved is a promise to the caller. A function that uses R4 must push it on entry and pop it before it returns. Forgetting this does not fail on the spot: the caller's R4 is silently wrong later, which is one of the hardest bugs to find.

The table shows three things. First, the BL changes LR and nothing else, and the function changes SP only when it pushes. Second, R4 comes back as 0 after the pop, because the callee restored the value the caller had before the call. The function used R4 for 100, but the caller never sees that. Third, SP returns to 0x20000100, which is what a correct function must do. The final R0 is 107, which is the answer to the quiz on this page.

The return address in LR is 7, not 6. The simulator uses the Thumb convention of setting bit 0 of a return address. The pop {..., pc} then clears bit 0 when it loads the PC, so the program returns to address 6. On the real core, bit 0 of a return address is the Thumb state bit, as lesson 32 described.

The code, line by line

The program in the simulator is the trace above, written in assembly. Read it with the table beside it.

  • main: MOV R0, #3 and MOV R1, #4 put the two arguments into the first two argument registers, as the AAPCS says.
  • BL add_pair calls the function. It saves the return address in LR and jumps. The @ call; LR gets the return address comment is the important part.
  • B . is the halt that the call returns to.
  • add_pair: PUSH {R4, LR} saves the two registers the function must preserve. R4 is the one the function will change, and LR is the one the function's own return depends on.
  • MOV R4, #100 uses R4 for a constant. Because R4 was saved, the caller's R4 can be restored later.
  • ADD R0, R0, R1 and ADD R0, R0, R4 compute the result into R0, which is where the return value goes.
  • POP {R4, PC} restores R4 and loads the saved LR into PC. That is the return, and it also undoes the push, so SP returns to its starting value.
Hint

The arguments are 3 and 4, and the function adds a constant of 100. Work out the final R0 before you look. After the POP, SP should be back to its starting value.

Try it in the CPU simulator

Before you step through, predict the final R0. Then use the stack view to see the frame.

  1. Press Instruction three times. Predict SP and R0 after the BL. The LR value is the return address, with the low bit set, as Thumb addresses are written.
  2. Press Instruction once more, to run PUSH {R4, LR}. Predict SP, then check the stack view: the new top of the stack should hold R4 and then LR.
  3. Press Run or keep pressing Instruction until the halt. Check the final R0 and SP.

The simulator follows the same calling pattern as the real core, with a few teaching simplifications: 2-byte instructions, a small instruction set and one stack pointer in use. The real Cortex-M3 pushes an exception frame on the same stack, which lesson 34 covers.

Common mistakes and how to spot them

  1. Forgetting to save LR in a function that makes a call. The inner bl overwrites LR, so the outer function's bx lr returns into the wrong place. The symptom is a function that returns to an address inside itself, or to garbage, and the bug moves when you change unrelated code. The fix: push LR on entry and pop it into PC on exit, as the simulator's add_pair does.
  2. Changing R4 without restoring it. The warning above describes this one. The symptom is that the caller's variable has the wrong value after the call, while the same value is right in a debugger during the call. The fix: push R4 on entry and pop it on exit. A compiler does this for you, which is why the mistake appears in hand-written assembly and in interrupt code.
  3. Overrunning the stack. A stack that grows past its reserved size writes into whatever lies below it in RAM. On the Pico the SDK reserves 2 KB of stack per core by default, so a deep call chain or a large local array can exceed it. The symptom is random corruption in a variable that is far from the function that caused it, or a HardFault. The fix: keep large arrays out of the stack, check the call depth, and measure the stack's high-water mark, which lesson 92 covers.
  4. Passing the fifth argument where the callee does not look. A caller that puts the fifth argument in R4 instead of on the stack gives the callee the wrong value. The symptom is a correct first four arguments and a wrong later one. The fix: follow the AAPCS rule that arguments beyond the fourth go on the stack, at the caller's SP, in order.
  5. Breaking the alignment rule at an interface. The AAPCS says "SP mod 8 = 0" at a public interface, and the Cortex-M3 has an STKALIGN bit in its Configuration Control Register that makes exception frames 8-byte aligned (DDI0337G, revision history). Hand-written assembly that calls compiled code with an odd-word stack breaks the contract. The symptom appears only in some call paths, which makes it hard to reproduce. The fix: align the stack before the call, and check SP in the debugger at each public entry point.

In real projects

Stack size is a design decision, and it is written down. A team that uses an RTOS gives each task a stack of a size it chose, and it checks the usage with a high-water mark, the deepest the stack reached during a test run. Lesson 92 covers that measurement, and lesson 41 covers the linker script where the main stack is placed. A team with no RTOS still sizes the main stack in the linker script and in its design notes, because the stack is shared by all the code that runs in thread mode and in every interrupt.

In code review, a reviewer checks every push against its matching pop, checks that a function that calls another saves LR, and checks that a function that uses R4 to R8 saves them. A function may change R0 to R3 (arguments and results) and R12 (scratch), and must preserve everything else; the stack must also stay aligned.

Summary

  • The stack is a region of RAM, and SP points at the last item pushed. The AAPCS calls it full-descending.
  • R0 to R3 carry arguments in and the result out. R4 to R8, R10, R11 and SP must be preserved by the callee. R12 is scratch.
  • Arguments beyond the fourth go on the stack at the caller's SP, in order.
  • A bl writes the return address into LR. A function that calls another saves LR, and returns by popping it into PC.
  • The stack must stay word-aligned at all times, and double-word aligned (SP mod 8 = 0) at a public interface.
  • On the Pico the RP2040 SRAM is 264 KB from 0x20000000, and the SDK reserves 2 KB of stack per core by default.
  • A PUSH {R4, LR} moves SP down by 8 bytes, and the matching POP moves it back.
