GPIO output

Driving pins through the RP2040 SIO registers

By the end of this lesson you can drive four LEDs as a binary counter with one masked write per step, and name the SIO register each SDK call writes.

Driving a pin from software

The earlier lessons supplied the pieces: lesson 9 showed how a series resistor limits the current through an LED, lesson 38 that peripherals sit at fixed addresses and that a store to such an address changes the hardware, and lesson 47 how to turn a number into a pointer to a register and read its fields. This lesson combines them for the most common job in embedded code, driving a pin high or low.

Almost every product has a GPIO output that lights an LED, enables a motor driver, selects a chip on an SPI bus or switches a relay. In a real design the output is often the last step of a safety decision, so the way it is written matters as much as the value: a pin that glitches high for a microsecond at boot can start a heater or a motor, and a write that accidentally changes a neighbouring pin can flip a signal another driver is holding. The SDK's GPIO functions were written to avoid those problems, and understanding them requires a look at the registers underneath.

GPIO pins and pads

A general-purpose input/output (GPIO) pin is a package pin that the program can drive or read, connected inside the chip to a small piece of logic called a pad. The pad is the electrical interface between the chip's internal signals and the outside world, shifting the logic level to the pin's supply voltage, supplying enough current and offering some protection against static discharge, as section 2.19.4 of the RP2040 datasheet describes (RP2040 datasheet §2.19.4).

Behind the pad, three settings matter for output. The function select routes the pin either to the Single-cycle IO (SIO) block, which the processor controls directly, or to a peripheral such as a UART or a PWM slice, the direction decides whether the pad's output driver is enabled, and the level is the value the driver puts on the pad when enabled. A plain LED needs the SIO driving the pin, the driver enabled and the level set as required.

The GPIO_OUT and GPIO_OE registers

A GPIO pin is a bit in two registers: GPIO_OUT holds the desired level, and GPIO_OE (output enable) decides whether the pin drives that level or stays an input. Both live in the SIO block starting at 0xD0000000 (RP2040 datasheet §2.3.1.7, Table 16), the address lesson 38 showed, and the offsets that matter here are 0x010 for GPIO_OUT and 0x020 for GPIO_OE. The SIO is not on the main bus. Each core reaches it through its IOPORT, so every SIO access takes exactly one cycle (§2.3.1), whereas a load or store on the AHB-Lite system bus takes two cycles on the M0+ and can wait behind other bus masters.

Bit n of each register belongs to GPIO n, and since the RP2040 has 30 bank-0 GPIOs, numbered 0 to 29, one 32-bit word covers them all. Bit 2 of GPIO_OUT is GP2's level, bit 2 of GPIO_OE its direction, and the same bit of GPIO_IN reads its pad.

A pin behaves like a lamp with two switches in series: GPIO_OUT is the switch that chooses on or off, and GPIO_OE the switch that connects that choice to the lamp at all, so however often the first is flipped, the lamp does not change while the second is open. The comparison ends at the input side, because with GPIO_OE clear the pin listens, and GPIO_IN reads whatever the outside world puts on it.

A pin also needs its function set to SIO in the IO bank, so that the SIO drives it rather than a peripheral such as a UART, and function 5 is SIO for every GPIO (§2.19.2, Table 279). The SDK performs all three steps in gpio_init().

Worked example: the bits for GP2 to GP5

The project's four LEDs sit on GP2 to GP5, and we build the mask for those pins bit by bit. A 1 in bit 0 is 0b0001, and shifting it left by 2 moves it onto GP2, giving 0b000100, or 0x04. The four-bit field is built the same way, (1u << 4) - 1 being 0x0F, a run of four ones, which shifted left by 2 gives 0b111100, or 0x3C, the project's LED_MASK covering bits 2, 3, 4 and 5, which are GP2 to GP5.

Before reading on, predict the value written to the pins for a count of 5. That count is 0b0101, so GP2 should be high for bit 0, GP3 low for bit 1, GP4 high for bit 2 and GP5 low for bit 3. Shifting count left by 2 gives 0b010100, or 0x14, which the AND with the mask leaves unchanged, because every set bit already lies within GP2 to GP5, so 0x14, with bit 4 for GP4 and bit 2 for GP2, is the level pattern the pins must show.

The write must change only the pins in the mask and give them this pattern, which the SDK does with gpio_put_masked(), as the next section explains.

  1. The counter is 5, binary 0101. Its four bits must appear on GP2 to GP5, one LED per bit.
  2. Shift left by 2 so bit 0 of the count lands on GP2: 0101 becomes 0001 0100, 0x14.
  3. The mask is four ones starting at bit 2: ((1u << 4) − 1) << 2 = 0x3C. It names the only pins the write may change.
  4. value & mask is still 0x14: GP2 and GP4 high, GP3 and GP5 low.
  5. gpio_put_masked(0x3C, 0x14) changes only the four masked pins. GP2 and GP4 light; every other pin keeps its level.

The set, clear and toggle aliases

Changing a level with GPIO_OUT |= bit is a read-modify-write in which the CPU loads the whole register, changes one bit and stores it back. The store writes the whole register, including the bits just read, so if an interrupt or the other core changes a different pin between the load and the store, the store restores that pin's old value and undoes the change.

A read-modify-write resembles editing a shared spreadsheet by downloading it, changing one cell and uploading the whole file, which silently wipes any change a colleague made to another cell in the meantime. The SET, CLR and XOR aliases correspond to typing straight into the one cell, so no copy can go stale and nothing else is overwritten. The comparison has a limit, though, because the aliases work on whole bit masks, and a single write can change many cells at once.

The SIO avoids the problem with three extra addresses, each an atomic bit operation on GPIO_OUT: GPIO_OUT_SET at 0x014 performs |=, GPIO_OUT_CLR at 0x018 performs &= ~ and GPIO_OUT_XOR at 0x01C performs ^= (§2.3.1.7, Tables 21 to 23). A mask written to an alias is applied to GPIO_OUT by the hardware in one step, each 1 bit changing its pin and each 0 bit leaving its pin alone, and since the alias does not hold the new level, it never needs to read the port first. This is the idea behind the STM32 BSRR register of lesson 47, where writing 1 to bit n sets a pin. Here a mask written to GPIO_OUT_SET sets every pin whose bit is 1 and leaves every pin whose bit is 0 alone. 

/* Set GP2 high two ways. Both are one store, and neither touches the other pins. */
sio_hw->gpio_set = 1u << 2;     /* GPIO_OUT_SET at 0xD0000014: GPIO_OUT |= (1 << 2)   */
gpio_put(2, 1);                  /* the SDK call; it reaches the same register       */

/* What you must not do with a shared port: a read, a change, then a store. */
sio_hw->gpio_out = sio_hw->gpio_out | (1u << 2);   /* an interrupt between the two accesses can be lost */

sio_hw is a pointer to a struct overlaying the SIO registers, the pattern of lesson 47, and sio_hw->gpio_set is the GPIO_OUT_SET register at offset 0x014. The expression 1u << 2 is the mask with only bit 2 set, 0x04, and storing it to that address sets GP2 while leaving every other bit of GPIO_OUT unchanged. The second line, gpio_put(2, 1), is the SDK's way of saying the same thing, calling gpio_set_mask(), which stores to the same register.

The third example is the mistake to avoid. It reads GPIO_OUT, ORs in bit 2 and stores the whole register back, so an interrupt that changes GP3 between the read and the store has its change undone when the store writes back the old GP3 level. The alias avoids this because the hardware performs the read-modify-write itself, in one step that no other CPU store can interrupt.

The datasheet adds a rule for two writers: if core 0 and core 1 write GPIO_OUT or one of its aliases in the same cycle, the result is as though core 0's write happened first and core 1's write was then applied to that result (§2.3.1.7, Table 20). The alias registers therefore keep the bits that a write did not name, which a plain store would not.

The datasheet also warns about reads. Reading GPIO_OUT returns the last value written to it rather than the level on the pins, so an output pulled the other way by external hardware still reads back the written value, and only GPIO_IN shows what the pin is actually doing.

Direction control with GPIO_OE

The output-enable register follows the same alias pattern, with GPIO_OE_SET at 0x024 setting output-enable bits, GPIO_OE_CLR at 0x028 clearing them and GPIO_OE_XOR at 0x02C toggling them. A set bit makes its pin an output and a clear bit an input, in which case the pad's driver is off and the level in GPIO_OUT has no effect on the pin.

The separation is useful, because the level can be set first and the output enabled afterwards, so the pin never drives an unintended level. The SDK's gpio_init() relies on this, as the next section shows, and with the direction change made last, the pin goes from input straight to the chosen level.

The registers behind the SDK calls

The Pico SDK wraps these registers in small inline functions, and the table lists what the common calls do, as read from the SDK source in src/rp2_common/hardware_gpio/include/hardware/gpio.h (SDK 2.3.1).

SDK callRegister writeNote
gpio_put(pin, 1)GPIO_OUT_SET (or GPIO_OUT_CLR for 0)One store, one bit.
gpio_set_dir(pin, GPIO_OUT)GPIO_OE_SETOne store, one bit.
gpio_set_dir_out_masked(mask)GPIO_OE_SET with maskSeveral pins in one store.
gpio_put_masked(mask, value)Reads GPIO_OUT, then one store to GPIO_OUT_XORFlips only the bits in mask that differ from value. The read is not part of the atomic store.
gpio_init(pin)Direction to input, drive low, then function set to SIOThree steps, in that order, so the pin is an input while its level is set, and it never becomes an output at an unexpected level.
gpio_get(pin)Reads GPIO_IN at 0x004The pad level, not the output register.

The gpio_init() row needs careful reading, because it is easy to get wrong. The function calls gpio_set_dir(gpio, GPIO_IN) first, then gpio_put(gpio, 0) and then gpio_set_function(gpio, GPIO_FUNC_SIO), so the pin is an input while its level is set to 0 and drives nothing until its function is switched to SIO. That order prevents a glitch and is the reason to call gpio_init() before gpio_set_dir() with GPIO_OUT.

gpio_put_masked() is convenient but deserves a careful reading, because its read of GPIO_OUT precedes the XOR store, so if another core or an ISR changes a pin in the mask between the two steps, the result can be wrong. For a pin that another context also changes, use gpio_set_mask() and gpio_clr_mask(), which are one store each.

LED current and the series resistor

An LED is a diode, and once a diode with a forward voltage conducts, it has no fixed resistance, a small change in voltage producing a large change in current. A pin driven straight across an LED would therefore push far more current than the pad is designed to supply, and the series resistor sets the current by taking up the voltage that the LED does not use.

With a 3.3 V pin and a red LED of about 2.0 V forward voltage, the current through a series resistor R is

I = (Vpin − VF) ÷ R(1)

where Vpin is the pin voltage and VF the LED's forward voltage, so 220 Ω passes (3.3 − 2.0) ÷ 220 ≈ 5.9 mA, and lesson 9 covers how to choose that value. The pad's output drive strength is programmable to 2, 4, 8 or 12 mA (§2.19.4), with a reset value of 4 mA set in the pad control register rather than in the SIO. Keep each LED near that current, and never drive an LED from a pin without a series resistor.

The chip also limits the current of its pins. A common mistake is to add LEDs to one pin, or to drive several LEDs at 12 mA each from a single supply, so check the total current against the datasheet's limits before wiring more outputs to the same rail.

A thermostat switches its heater through a relay whose coil needs tens of milliamps, more than the 12 mA a pad can be set to drive, so the pin drives a small transistor and the transistor drives the coil. The firmware is still one gpio_put(HEATER_PIN, 1), because the electronics around the pin decide how much current it must supply, and the pin only has to supply the transistor's base or gate.

Common mistakes and how to spot them

A plain store to GPIO_OUT for one bit

A pin you did not touch goes low when you set another one, because a plain store to GPIO_OUT replaces all 30 bits. Use gpio_put() or the GPIO_OUT_SET alias for one pin and a masked call for several.

The function select forgotten

The serial monitor shows the program running while the LED never lights, although gpio_set_dir(2, GPIO_OUT) and gpio_put(2, 1) were called, because the output-enable bit is set but the pad is still connected to a peripheral or to nothing. Call gpio_init() first, or set the function to SIO with gpio_set_function().

The direction set before the level

A short glitch appears at startup, visible on a logic analyser, or a motor twitches on reset, because the output was enabled on a pin that still held a stale 1 in GPIO_OUT and drove high immediately. Set the level first and enable the output afterwards, the order that gpio_init() uses.

The output register read for the pin level

The program believes a pin is high while the LED is dark, because it read GPIO_OUT, which returns the written value, while a pull-down holds the pin low. Read GPIO_IN with gpio_get() for the pad level, and keep gpio_get_out_level() for debugging.

A shifted value without the mask

An unrelated pin toggles once the counter passes 8, because the counter was shifted left by 2 without the mask and its bit 4 moved to GP6. AND the shifted value with LED_MASK, so that only the four LED pins can change.

GPIO outputs in production code

Production code rarely writes the SIO registers directly but uses the SDK or a hardware abstraction layer (HAL) that wraps the registers in named functions, with the pin numbers kept in one header. A reviewer checks that each output pin has a named constant instead of a bare 2 in a call, that each output gets a safe initial level before its direction is enabled, and that shared ports use aliases or masks rather than read-modify-write wherever an ISR or the second core can touch them.

Senior engineers also check what a pin does during reset and boot, since the pad's reset state and the function it has before the code runs decide what the hardware does in the first milliseconds. A motor driver or a heater must see no glitch while the program starts, so the output stays an input until the code has set its level, which is the reason for the three-step order in gpio_init().

The same registers appear in the STM32 world under different names, the BSRR with its set and reset halves doing the job of the RP2040's alias pair.

Summary

  • A GPIO has a function select, a direction bit in GPIO_OE and a level bit in GPIO_OUT, and the pin drives only when all three are set correctly.
  • The SIO is at 0xD0000000, with GPIO_OUT at offset 0x010, GPIO_OE at 0x020 and GPIO_IN at 0x004.
  • GPIO_OUT_SET, GPIO_OUT_CLR and GPIO_OUT_XOR are atomic bit operations, so a mask changes only the named pins.
  • A plain store to GPIO_OUT replaces all bits, and a read-modify-write can lose a change made by an interrupt or the other core.
  • gpio_init() makes the pin an input, drives its level low and then selects SIO, in that order.
  • An LED needs a series resistor to limit its current, and with 3.3 V and a 2.0 V LED, 220 Ω gives about 5.9 mA.
