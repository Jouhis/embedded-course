GPIO output: the SIO registers under the SDK

Every gpio_put() you have written is a store to a register that holds one bit per pin. Knowing which register, and why the SDK uses the set and clear aliases, is what makes a pin change safe when an interrupt or the second core touches the same port.

By the end of this lesson you can drive four LEDs as a binary counter with one masked write per step, and name the SIO register each SDK call writes.

Where we are and why it matters

The earlier lessons gave you the pieces. Lesson 9 showed how a series resistor limits the current through an LED. Lesson 38 showed that peripherals sit at fixed addresses, and that a store to such an address is what changes the hardware. Lesson 47 turned a number into a pointer to a register and read its fields. This lesson puts those together for the most common job in embedded code: driving a pin high or low.

Almost every product has a GPIO output. It lights an LED, enables a motor driver, selects a chip on an SPI bus, or switches a relay. In a real design the output is often the last step of a safety decision, so the way you write it matters as much as the value. A pin that glitches high for a microsecond at boot can start a heater or a motor. A write that accidentally changes a neighbouring pin can flip another signal that a driver is holding. The SDK's GPIO functions were written to avoid those problems, and to understand them you need to see the registers underneath.

What a GPIO pin is, in hardware

A general-purpose input/output (GPIO) pin is a package pin that the program can drive or read. Inside the chip, each one is connected to a small piece of logic called a pad. The pad is the electrical interface between the chip's internal signals and the outside world. It shifts the logic level to the pin's supply voltage, supplies enough current, and offers some protection against static discharge. The RP2040 datasheet describes it in section 2.19.4 (RP2040 datasheet §2.19.4).

Behind the pad, a GPIO has three decisions that matter for output. The first is which block drives it: the function select routes the pin either to the Single-cycle IO (SIO) block, which the processor controls directly, or to a peripheral such as a UART or a PWM slice. The second is direction: whether the pad's output driver is enabled. The third is level: the value the driver puts on the pad when it is enabled. For a plain LED, you want the SIO to drive the pin, the driver enabled, and the level set to what you need.

The idea: two registers and a function select

A GPIO pin is a bit in two registers. GPIO_OUT holds the level you want, and GPIO_OE (output enable) decides whether the pin drives that level or stays an input. Both live in the SIO block, which starts at 0xD0000000 (RP2040 datasheet §2.3.1.7, Table 16). Lesson 38 showed the SIO address. Here the offsets matter: GPIO_OUT is at 0x010, and GPIO_OE is at 0x020. The SIO is not on the main bus. Each core reaches it through its IOPORT, so every SIO access takes exactly one cycle (§2.3.1). A load or store on the AHB-Lite system bus takes two cycles on the M0+, and it can wait behind other bus masters.

Bit n of each register belongs to GPIO n. The RP2040 has 30 bank-0 GPIOs, numbered 0 to 29, so one 32-bit word covers them all. Bit 2 of GPIO_OUT is GP2, bit 2 of GPIO_OE is GP2's direction, and the same bit position in GPIO_IN reads the pad.

A pin also needs its function set to SIO in the IO bank, so the SIO drives it and not a peripheral such as a UART. Function 5 is SIO for every GPIO (§2.19.2, Table 279). The SDK does all three steps in gpio_init().

A worked example: the bits for GP2 and GP5

Take the project's four LEDs, which sit on GP2 to GP5. The mask for those four pins is built bit by bit. Start with a 1 in bit 0, which is 0b0001. Shift it left by 2 to move it onto GP2, which gives 0b000100, or 0x04. Build the four-bit field the same way: (1u << 4) - 1 is 0x0F, a run of four ones. Shift that left by 2, and you get 0b111100, which is 0x3C. That is the LED_MASK in the project: bits 2, 3, 4 and 5, which are GP2 to GP5.

Now the counter. Suppose count is 5, which is 0b0101. Bit 0 is 1, so GP2 should be high. Bit 1 is 0, so GP3 should be low. Bit 2 is 1, so GP4 should be high. Bit 3 is 0, so GP5 should be low. Shift count left by 2 and you get 0b010100, which is 0x14. ANDing that with the mask leaves 0x14 unchanged, because every set bit is already inside GP2 to GP5. Bit 4 of the result is GP4, bit 2 is GP2, and the value 0x14 is the level pattern the pins must show.

The write has to change only the pins in the mask, and it must write the level pattern to them. The SDK does that with gpio_put_masked(). The next section explains how it does it.

Set, clear and toggle as separate addresses

Changing a level with GPIO_OUT |= bit is a read-modify-write. The CPU loads the whole register, changes one bit and stores it back. That is three steps, and the store writes the whole register, including the bits the CPU just read. If an interrupt, or the other core, changes a different pin between the load and the store, the store puts back the old value of that pin and undoes the change.

The SIO avoids that with three extra addresses, each an atomic bit operation on GPIO_OUT. GPIO_OUT_SET at 0x014 does |=, GPIO_OUT_CLR at 0x018 does &= ~, and GPIO_OUT_XOR at 0x01C does ^= (§2.3.1.7, Tables 21 to 23). You write a mask to the alias, and the hardware applies it to GPIO_OUT in one step. A 1 bit in the mask changes its pin. A 0 bit leaves its pin alone. The register you write does not hold the new level, so the alias never needs to read the port first. This is the idea behind the STM32 BSRR register in lesson 47. There you write 1 to bit n to set a pin. Here you write a mask to GPIO_OUT_SET, and every bit you write as 1 is set, while every 0 leaves its pin alone. 

/* Set GP2 high two ways. Both are one store, and neither touches the other pins. */
sio_hw->gpio_set = 1u << 2;     /* GPIO_OUT_SET at 0xD0000014: GPIO_OUT |= (1 << 2)   */
gpio_put(2, 1);                  /* the SDK call; it reaches the same register       */

/* What you must not do with a shared port: a read, a change, then a store. */
sio_hw->gpio_out = sio_hw->gpio_out | (1u << 2);   /* an interrupt between the two accesses can be lost */

Read the code line by line. sio_hw is a pointer to a struct that overlays the SIO registers, the same pattern as lesson 47. sio_hw->gpio_set is the GPIO_OUT_SET register at offset 0x014. The expression 1u << 2 is the mask with only bit 2 set, which is 0x04. The store writes 0x04 to that address, and the hardware sets GP2 and leaves every other bit of GPIO_OUT unchanged. The second line, gpio_put(2, 1), is the SDK's way to say the same thing. It calls gpio_set_mask(), which stores to the same register.

The third example is the mistake to avoid. It reads GPIO_OUT, ORs in bit 2, and stores the whole register back. Between the read and the store, an interrupt that changes GP3 can happen. The store then writes back the old GP3 level, and the change is lost. The alias avoids this because the hardware does the read-modify-write itself, in one step that cannot be interrupted by another CPU store.

The reference adds one rule for two writers. If core 0 and core 1 write GPIO_OUT or one of its aliases in the same cycle, the result is as though core 0's write happened first and core 1's was then applied to that result (§2.3.1.7, Table 20). The alias registers keep the bits you did not name, which a plain store would not.

The datasheet also warns about a read. Reading GPIO_OUT gives the last value written to it, and not the level on the pins. An output that is pulled the other way by external hardware reads back the value you wrote, so a read of GPIO_OUT cannot tell you what the pin is doing. Use GPIO_IN for that.

Direction: GPIO_OE and its aliases

The output-enable register has the same alias pattern. GPIO_OE_SET at 0x024 sets output-enable bits, GPIO_OE_CLR at 0x028 clears them, and GPIO_OE_XOR at 0x02C toggles them. Setting a bit makes that pin an output, and clearing it makes the pin an input. With the bit clear, the pad's driver is off, so the level in GPIO_OUT has no effect on the pin.

This separation is useful. You can set the level first and then enable the output, so the pin never drives a level you did not intend. The SDK's gpio_init() relies on it, as the next section shows. Make the direction change last, and the pin goes from input straight to the level you chose.

What the SDK calls write

The Pico SDK wraps these registers in small inline functions. Here is what the common calls do, read from the SDK source in src/rp2_common/hardware_gpio/include/hardware/gpio.h (SDK 2.3.1):

SDK callRegister writeNote
gpio_put(pin, 1)GPIO_OUT_SET (or GPIO_OUT_CLR for 0)One store, one bit.
gpio_set_dir(pin, GPIO_OUT)GPIO_OE_SETOne store, one bit.
gpio_set_dir_out_masked(mask)GPIO_OE_SET with maskSeveral pins in one store.
gpio_put_masked(mask, value)Reads GPIO_OUT, then one store to GPIO_OUT_XORFlips only the bits in mask that differ from value. The read is not part of the atomic store.
gpio_init(pin)Direction to input, drive low, then function set to SIOThree steps, in that order, so the pin is an input while its level is set, and it never becomes an output at an unexpected level.
gpio_get(pin)Reads GPIO_IN at 0x004The pad level, not the output register.

The gpio_init() row needs a careful reading, because it is easy to get wrong. The SDK's gpio_init() calls gpio_set_dir(gpio, GPIO_IN) first, then gpio_put(gpio, 0), then gpio_set_function(gpio, GPIO_FUNC_SIO). The pin is an input while its level is set to 0, so the pin does not drive anything until the function is switched to SIO. That order prevents a glitch, and it is the reason to call gpio_init() before you call gpio_set_dir() with GPIO_OUT.

gpio_put_masked() is convenient, but read it carefully. Its read of GPIO_OUT comes before the XOR store, so if another core or an ISR changes a pin in the mask between the two steps, the result can be wrong. For a pin that another context also changes, use gpio_set_mask() and gpio_clr_mask(), which are one store each.

Current, and why the resistor is there

An LED is a diode, and a diode with a forward voltage has no fixed resistance. Once it conducts, a small change in voltage gives a large change in current. A pin driven straight across an LED would therefore push far more current than the pad is designed to supply. The series resistor sets the current by taking up the voltage that the LED does not use.

With a 3.3 V pin and a red LED at about 2.0 V forward voltage, a 220 Ω resistor passes (3.3 − 2.0) ÷ 220 ≈ 5.9 mA. Lesson 9 covers how to choose that value. The pad's output drive strength is programmable, with choices of 2, 4, 8 and 12 mA (§2.19.4). The reset value is 4 mA, and the drive strength is set in the pad control register, not in the SIO. Keep each LED near that current, and never drive LEDs from a pin without a series resistor.

The pin's current is also limited by the chip. A common mistake is to add LEDs to one pin, or to drive several LEDs at 12 mA each from a single supply. Check the total current against the datasheet's limits before you wire more outputs to the same rail.

Common mistakes and how to spot them

Mistake 1: writing GPIO_OUT when you mean to set one bit. A plain store to GPIO_OUT replaces all 30 bits. Symptom: a pin you did not touch goes low when you set another one. Fix: use gpio_put() or the GPIO_OUT_SET alias for one pin, and a masked call for several.

Mistake 2: forgetting the function select. You call gpio_set_dir(2, GPIO_OUT) and gpio_put(2, 1), and the LED stays dark. Symptom: the serial monitor shows the program running and the LED never lights. The output-enable bit is set, but the pad is still connected to a peripheral or to nothing. Fix: call gpio_init() first, or set the function to SIO with gpio_set_function().

Mistake 3: setting the direction before the level. You set the output enable on a pin that still holds a stale 1 in GPIO_OUT, and the pin drives high immediately. Symptom: a short glitch at startup, which can be seen on a logic analyzer, or a motor that twitches on reset. Fix: set the level first, then enable the output, which is the order gpio_init() uses.

Mistake 4: reading the output register to find the pin level. You read GPIO_OUT to check whether a pin is high, and the LED is wired to a pull-down that holds it low. Symptom: the program believes the pin is high while the LED is dark. Fix: read GPIO_IN with gpio_get() for the pad level, and gpio_get_out_level() only for debugging.

Mistake 5: the shifted mask that reaches the wrong pins. You shift the counter left by 2, but you forget the mask, and bit 4 of the counter moves to GP6. Symptom: an unrelated pin toggles when the counter passes 8. Fix: AND the shifted value with LED_MASK, so only the four LED pins can change.

Hint for the shift and mask

Bit 0 of count must go to GP2, so shift count left by LED_FIRST_PIN. LED_MASK is 0x3C, which is bits 2 to 5. Anything the shift moves outside that range must not reach the pins, so AND the shifted value with the mask.

Hint for the direction

gpio_init_mask() handles all four pins at once and leaves them as inputs. The second call, gpio_set_dir_out_masked(), makes the same four pins outputs. Each call is one store to the SIO.

In real projects

Production code rarely writes the SIO registers directly. It uses the SDK, or a hardware abstraction layer (HAL) that wraps the registers in named functions, and it keeps the pin numbers in one header. A reviewer looks for three things. Each output pin has a named constant, so nobody writes a bare 2 in a call. Each output has a safe initial level, set before the direction is enabled. Shared ports use aliases or masks, not read-modify-write, when an ISR or the second core can touch them.

Senior engineers also check what the pin does during reset and boot. The pad's reset state, and the function it has before your code runs, decide what the hardware does in the first milliseconds. A motor driver or a heater must not see a glitch while the program starts, so the output stays an input until the code has set its level. That is the reason for the three-step order in gpio_init().

The same registers appear in the STM32 world under different names. The STM32 BSRR, with its set and reset halves, does the same job as the RP2040 alias pair. An interviewer who asks how you would change one pin without disturbing its neighbours is testing whether you know this pattern, not whether you remember one register name.

Summary

  • A GPIO has a function select, a direction bit in GPIO_OE, and a level bit in GPIO_OUT. The pin drives only when all three are set correctly.
  • The SIO is at 0xD0000000. GPIO_OUT is at 0x010, GPIO_OE at 0x020, and GPIO_IN at 0x004.
  • GPIO_OUT_SET, GPIO_OUT_CLR and GPIO_OUT_XOR are atomic bit operations, so a mask changes only the pins you name.
  • A plain store to GPIO_OUT replaces all bits. A read-modify-write can lose a change made by an interrupt or the other core.
  • gpio_init() makes the pin an input, drives it low, and then selects SIO, in that order.
  • An LED needs a series resistor to limit its current. With 3.3 V and a 2.0 V LED, 220 Ω gives about 5.9 mA.

Model answer

Use the set alias (GPIO_OUT_SET on the RP2040, BSRR on the STM32): one store that names only that pin. A read-modify-write on the whole output register can lose a change that the interrupt makes between the load and the store. For a multi-pin change, use a masked store that touches only the pins in the mask. Do not rely on a masked helper that reads first if another context writes the same pins.

RP2040 datasheet: read section 2.3.1 (SIO) for the one-cycle IOPORT, then section 2.3.1.7 (List of Registers) for the GPIO_OUT, GPIO_OUT_SET, GPIO_OUT_CLR and GPIO_OUT_XOR descriptions in Tables 20 to 23, and section 2.19.2 for the function select (Table 279).
