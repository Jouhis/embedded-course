Capstone 1: requirements and the state machine for a filament-dryer controller

3D-printer filament absorbs water from the air, and wet filament prints badly. A dryer that holds a chamber at 45, 65 or 80 °C is a real product, and this capstone builds one. The first step is a list of what the box must do and how it must fail, written before any code.

By the end of this lesson you can write numbered requirements with acceptance criteria, describe how the dryer must fail, draw a state machine with its transition table, and find the events that a transition table leaves open.

Why a dryer. Nylon, PETG and PLA absorb moisture, and wet filament prints with bubbles and weak layers. Dedicated dryers hold a fixed temperature for hours. The controller is an ordinary embedded design: a sensor, a heater with a power switch, a display, buttons, and safety rules that must hold when a part fails. Much firmware work looks like this.

The idea: write the requirements before the code

A requirement says what the system must do, in a form that can be checked. A design says how. Safety standards look for a chain: every requirement has an acceptance criterion, and every criterion has a test. Functional safety standards such as IEC 61508 make this explicit (lesson 112). You will build that chain in this capstone: the requirements here, the host tests in lessons 115 and 117, and the simulation and continuous integration (CI) in lesson 120.

The dryer has three groups of requirement. The functional ones say what it does for the user, such as drying PLA for four hours. The safety ones say what it does when something is broken, and they are the ones that shape the design. The non-functional ones set limits such as memory, timing and the way the code is checked.

Four words you will use all lesson

A requirement is one statement of what the system must do, written so that a reader can answer yes or no. An acceptance criterion is the measurable condition that makes the answer yes: a number with a unit, a state, a time, or a message on a screen. A test is the procedure that checks the criterion, and a design is the chosen way to meet the requirement. "The dryer must be safe" is not a requirement, because nobody can check it. "A reading of 90.00 °C latches FAULT and the heater command is 0" is one, because a test can supply the reading and look at both outputs.

The chain runs in one direction. Each requirement has at least one criterion, each criterion has a test, and the test runs against the same code that ships. When a reviewer asks "how do you know?", the answer is a row in the table and a test that passes or fails. A safety standard such as IEC 61508 asks for exactly this chain.

How the dryer must fail

Most of the requirements above say what the dryer does when everything works. The safety group says what it does when something breaks, and that is where the design is shaped. The rule is simple to state: a failure moves the outputs to a safe state, the state in which the system is harmless even though it no longer works properly. For this dryer the safe state is heater off, with the fan running so the part cools. The state machine must reach that state from every state in which the heater can be on.

A fault is latched when it stays set after its cause has gone, until a person clears it. Latching matters because a fault that clears itself lets the heater restart on a sensor that flickers. The table lists each failure the requirements cover, how it is detected, and what the dryer does about it.

The table leaves one failure out of the state machine on purpose. A stalled task is not a transition, because a watchdog reset works even when the state machine itself has stopped. Requirement 2.5 therefore relies on the reset, not on the state logic. The cost is that a reset starts the dryer again from start-up, so the start-up code must leave the heater off before anything else runs. A design choice like this belongs in the requirements, so that a reviewer can check it.

Two layers of protection

The checks in the table run on the microcontroller, which is software. A heater that software can switch on must also have a hardware limit that does not depend on software: a thermal fuse or a bimetal cutoff in series with the heater, rated above the setpoint and below the temperature that damages the parts. The physical limit still works when the code, the clock or the sensor has failed, which is the point of it. Software safety is the second layer, and it handles the faults that a fuse cannot see, such as a sensor that reads cold while the chamber is hot.

The same reasoning is behind Klipper's verify_heater on 3D printers: the firmware checks that the heater is actually heating, and it still does not replace a physical thermal protection.

The state machine

A state machine is the cleanest way to describe a controller whose behaviour depends on what happened before. The dryer has five states: IDLE, HEATING (climbing to the setpoint), HOLDING (drying at the setpoint), COOLDOWN (cooling with the fan on), and FAULT (latched, heater off). States, events and transitions

A state is one of a fixed set of situations the machine can be in, such as "heating up". An event is something that happens: a button press, a new temperature reading, or the clock passing a deadline. A transition is the move from one state to another, caused by an event and sometimes guarded by a condition, such as "start pressed, and the sensor reads correctly". The table lists every transition the design allows. Anything not in the table must not happen.

Why use a state machine instead of a few flags such as heating and fault? With flags, the combination of flags is the state, and some combinations are nonsense: heating and faulted at once, or holding with no setpoint. A state machine stores one variable with a fixed set of values, so each state can refuse the actions that are unsafe in it. In FAULT, the start button does nothing unless the cause is gone and the part is cool. A flag-based design has to remember that rule in every branch, and the first branch someone forgets is the bug.

Here is a trace through the machine, with the numbers from the requirements. The operator selects PLA and presses start at time 0, with a good sensor and the chamber at 22 °C. The machine moves from IDLE to HEATING (transition 1). The heater runs at full power until the chamber reaches 44 °C, one degree below the 45 °C setpoint. That moves it to HOLDING (transition 2), and the four-hour timer starts at that moment, not at time 0. When four hours of hold time have passed, it moves to COOLDOWN (transition 3). Now suppose the operator presses stop after one hour of holding instead. The stop is transition 4: HOLDING goes to COOLDOWN with the fan on, and the four-hour timer is abandoned. The machine returns to IDLE only when the chamber is at 40 °C or below (transition 5).

The start and stop button is one physical button that produces two events. In IDLE a press is a start, which is transition 1. In HEATING and HOLDING the same press is a stop, which is transition 4. The table keeps the two events in separate rows, because each has its own result and its own test. Requirement 1.3 says that one button starts and stops the cycle, and the table is where that sentence becomes two checkable rows.

Two rules do most of the safety work. First, a stop leads to a cool-down. A hot part that is cut off dead can stay hot for an hour in an enclosure. Second, a fault is latched in the state machine, not in the sensor reading, so a sensor that comes back does not restart the heater by itself.

Rows the table does not cover yet

Read the table with a question for every cell: what happens if this event arrives in this state? The table answers some of them. For the others, the design must still decide, and the decision should be written down as an explicit "ignore" row. A press of the material button while the dryer is HEATING, for example, has no row, and by the rule above it must not happen. In practice the press is ignored, and the table should say so. The Try it task at the end of this lesson asks you to find every such cell.

Try it: the transition grid (no simulator)

This task needs paper or a plain text file and no simulator. The point is to test the table itself, before any code depends on it. You will need the requirements table and the transition table from this lesson.

  1. Draw a grid. The rows are the five states, IDLE, HEATING, HOLDING, COOLDOWN and FAULT. The columns are three events: the start/stop button, the material button, and a fault (any of the faults in transition 6).
  2. In each cell, write the number of the transition that applies, with its condition if it has one. If no row applies, write gap. Use the transition table only; do not add rows yet.
  3. Count the gaps. Then, for each gap, write the behaviour you want (ignore, or a new state) and one sentence that names the requirement number that supports your choice.
  4. Check the requirements table against the grid. Name one requirement that the grid does not need, and say why. Requirement 1.4 (the display) is an output, not a transition, so it does not belong in the grid.
Hint

Start from the empty cells. Eight of the fifteen cells have a row that applies with no condition. One more has a row that applies only under a condition, so look at the condition as well as the state.

Model answer

There are seven gaps. Of the fifteen cells, eight have an unconditional row: the button in IDLE (1), HEATING (4) and HOLDING (4); the material button in IDLE (8); and the fault in IDLE, HEATING, HOLDING and COOLDOWN (6). The button in FAULT has row 7, but only when the cause is gone and the part is below 60 °C, so it is a conditional cell. Six cells have no row at all. The seven gaps are those six cells plus the failing case of the conditional FAULT cell.

The seven gaps, with a suggested decision for each:

  1. COOLDOWN, start/stop button. Ignore the press. The part is still hot and the cooldown must finish (requirement 1.5).
  2. FAULT, start/stop button, when the cause is still present or the part is 60 °C or above. Ignore the press. This is the rule of requirement 2.6, which the table states only for the accepted case.
  3. HEATING, material button. Ignore it. Material is chosen while idle (requirement 1.3), and changing it mid-cycle would change the setpoint and the hold time.
  4. HOLDING, material button. Ignore it, for the same reason as the previous row.
  5. COOLDOWN, material button. Ignore it, for the same reason.
  6. FAULT, material button. Ignore it, for the same reason.
  7. FAULT, a further fault event. Stay in FAULT. Keep the first fault code, so that the display shows the original cause. This is a design choice that the requirements do not settle, so write it down as one.

The requirement the grid does not need is 1.4 (the display). It is an output that depends on the state, so it appears in the output column of the table and not as a transition.

Common mistakes and how to spot them

1. Requirements without numbers. Symptom: a review asks what "safe" means, and two engineers give two answers. Later, the first test is written with a value somebody guessed. Fix: write each requirement with a number, a unit and a condition, such as "90.00 °C measured at the sensor". If you cannot write a test for a row, the row is not finished.

2. Flags instead of states. Symptom: after an over-temperature trip, the heater comes back on when the operator presses start. The start branch checked the temperature, but nobody tested the fault flag in that branch. Fix: keep one state variable, put every transition in one place, and write one test per row of the table. A flag that a branch forgets to read becomes a row that the tests never cover.

3. The hold timer starts at the press. Symptom: a PLA cycle ends 40 minutes early. The log shows the hold timer started at 0 minutes, while the chamber needed 40 minutes to reach 45 °C. The four hours then end at four hours after the press, so only 3 hours and 20 minutes were spent at the setpoint. Fix: start the hold timer on transition 2, and write a host test that delays the setpoint reading and checks that the hold still lasts the full preset time (requirement 1.2).

4. A sensor that recovers restarts the heater. Symptom: an NTC lead is shaken loose, the sensor fault latches, and then the heater turns on when the lead reconnects, with no button press. Fix: make the fault a state (FAULT), not a reading, and clear it only in transition 7. A host test feeds a sensor fault, then a good reading, and expects FAULT to stay.

In real projects

In a product team, the requirements table is the first document a safety assessor reads. Standards such as IEC 61508 (lesson 112) ask that each safety function is specified, verified and traced to tests. A small team keeps the table in the repository next to the code, and a change to a criterion comes with a change to its test. A reviewer checks two things: does every row have a number, and does every number have a test that fails when the number is wrong?

Reviewers read a state machine twice: once as a diagram and once as a table. The diagram shows the main path, and the table shows the cells. A review that only looks at the diagram misses the cells that have no row, which is where the first defects usually sit. The Try it grid in this lesson is the same check in small.

Physical protection matters as much as software. The hardware cutoff described above, a thermal fuse or a bimetal switch in series with the heater, works without the microcontroller at all. The software checks are a second layer, and a strong design keeps both. Klipper makes the same point on 3D printers: its verify_heater checks that a heater really heats, and the printer still needs its own physical protection.

Summary

  • A requirement is a yes-or-no statement. Its acceptance criterion is the measurable condition, and a test checks the criterion.
  • Safety requirements describe what happens when a part fails. They define the safe state and shape the state machine.
  • A latched fault stays set until a person clears it, after its cause has gone.
  • A state machine stores one state and lists every allowed transition, so unsafe actions are refused by state, not by flags scattered through the code.
  • One physical button can produce different events in different states. Each event needs a row or an explicit ignore.
  • A hardware cutoff and software checks are two separate layers of protection.
