Capstone 1: requirements and the state machine for a filament-dryer controller

Requirements, failure rules and states

By the end of this lesson you can write numbered requirements with acceptance criteria, describe how the dryer must fail, draw a state machine with its transition table, and find the events that a transition table leaves open.

A filament dryer as the capstone product

Lesson 67 taught you to drive a Blue Pill from its registers and lesson 76 to hide those registers behind a hardware abstraction layer (HAL), while lessons 80 and 81 taught host unit tests and fakes, lessons 87 to 91 FreeRTOS tasks, queues and mutexes and lesson 93 deadlines. Lesson 108 gave you a PID controller and lesson 112 explained how a safety standard turns "it must not overheat" into evidence, and this capstone uses all of them on one product.

The product is a filament dryer, a box holding a chamber at 45, 65 or 80 °C for hours, so that a spool of nylon, PETG or PLA gives up the water it has taken from the air, because wet filament prints with bubbles, stringing and weak layers, which is why makers and small print shops buy dryers. A dryer is a good firmware project, because its controller is an ordinary embedded design with the parts most embedded products have, a temperature sensor, a heater switched by a power transistor, a display, buttons and safety rules that must hold when a part fails, and the problem this lesson solves is the first one any real project faces, deciding what the box must do and how it must fail before anyone writes C.

This lesson and lesson 114 design the product on paper, this lesson fixing the behaviour, the requirements, the failure rules and the state machine, and lesson 114 the structure, the layers, the tasks and the pin map, while the first code arrives in lesson 115.

Requirements before code

A requirement says what the system must do in a form that can be checked, whereas a design says how, and safety standards look for a chain in which every requirement has an acceptance criterion and every criterion a test, which functional safety standards such as IEC 61508 make explicit (lesson 112). You will build that chain in this capstone, the requirements here, the host tests in lessons 115 and 117 and the simulation and continuous integration (CI) in lesson 120.

The dryer has three groups of requirement, the functional ones saying what it does for the user, such as drying PLA for four hours, the safety ones what it does when something is broken, which are the ones shaping the design, and the non-functional ones setting limits such as memory, timing and the way the code is checked.

Requirements, criteria, tests and designs

A requirement is one statement of what the system must do, written so that a reader can answer yes or no, and an acceptance criterion the measurable condition making the answer yes, a number with a unit, a state, a time or a message on a screen, while a test is the procedure checking the criterion and a design the chosen way to meet the requirement. "The dryer must be safe" is therefore not a requirement, because nobody can check it, whereas "A reading of 90.00 °C latches FAULT and the heater command is 0" is one, because a test can supply the reading and look at both outputs.

The chain runs in one direction, each requirement having at least one criterion and each criterion a test, which runs against the same code that ships, so when a reviewer asks how you know, the answer is a row in the table and a test that passes or fails, exactly the chain a safety standard such as IEC 61508 asks for.

Failure behaviour and the safe state

Most of the requirements above say what the dryer does when everything works, whereas the safety group says what it does when something breaks, which is where the design is shaped, the rule being that a failure moves the outputs to a safe state, the state in which the system is harmless even though it no longer works properly. For this dryer the safe state is the heater off with the fan running so that the part cools, and the state machine must reach it from every state in which the heater can be on.

A fault is latched when it stays set after its cause has gone, until a person clears it, which matters because a fault that clears itself lets the heater restart on a flickering sensor, and the table lists each failure the requirements cover, how it is detected and what the dryer does about it.

The table leaves one failure out of the state machine on purpose, because a stalled task is not a transition, a watchdog reset working even when the state machine itself has stopped, so requirement 2.5 relies on the reset rather than on the state logic. The cost is that a reset starts the dryer again from start-up, so the start-up code must leave the heater off before anything else runs, a design choice that belongs in the requirements, so that a reviewer can check it.

Hardware and software protection layers

The checks in the table run on the microcontroller, in software, so a heater that software can switch on must also have a hardware limit independent of software, a thermal fuse or a bimetal cutoff in series with the heater, rated above the setpoint and below the temperature that damages the parts. The physical limit still works when the code, the clock or the sensor has failed, which is its purpose, while software safety is the second layer, handling the faults a fuse cannot see, such as a sensor reading cold while the chamber is hot.

The same reasoning is behind Klipper's verify_heater on 3D printers: the firmware checks that the heater is actually heating, and it still does not replace a physical thermal protection.

The dryer state machine

A state machine is the cleanest way to describe a controller whose behaviour depends on what happened before, the dryer having five states, IDLE, HEATING (climbing to the setpoint), HOLDING (drying at the setpoint), COOLDOWN (cooling with the fan on) and FAULT (latched, heater off), every transition having a cause, with the table below as the authoritative list and the diagram showing the main path.

States, events and transitions

A state is one of a fixed set of situations the machine can be in, such as heating up, an event something that happens, a button press, a new temperature reading or the clock passing a deadline, and a transition the move from one state to another, caused by an event and sometimes guarded by a condition, such as the start button pressed with the sensor reading correctly. The table lists every transition the design allows, and anything not in the table must not happen.

A state machine is preferable to a few flags such as heating and fault, because with flags the combination is the state and some combinations are nonsense, heating and faulted at once or holding without a setpoint, whereas a state machine stores one variable with a fixed set of values, so each state can refuse the actions that are unsafe in it. In FAULT, for example, the start button does nothing unless the cause is gone and the part is cool, a rule that a flag-based design has to remember in every branch, the first branch someone forgets being the bug.

A trace through the machine with the numbers from the requirements shows the main path. Before following it, predict when the four-hour timer starts.

  1. Start. The operator selects PLA and presses start at time 0, with a good sensor and the chamber at 22 °C, so the machine moves from IDLE to HEATING (transition 1).
  2. Reaching the setpoint. The heater runs at full power until the chamber reaches 44 °C, one degree below the 45 °C setpoint, which moves the machine to HOLDING (transition 2), the four-hour timer starting at that moment rather than at time 0.
  3. The end of the hold. When four hours of hold time have passed, the machine moves to COOLDOWN (transition 3).
  4. An early stop. If the operator instead presses stop after one hour of holding, transition 4 takes HOLDING to COOLDOWN with the fan on, abandoning the four-hour timer.
  5. Back to idle. The machine returns to IDLE only when the chamber is at 40 °C or below (transition 5).

The start and stop button is one physical button producing two events, a press in IDLE being a start, transition 1, and the same press in HEATING and HOLDING a stop, transition 4, so the table keeps the two events in separate rows, because each has its own result and its own test. Requirement 1.3 says that one button starts and stops the cycle, and the table is where that sentence becomes two checkable rows.

Two rules do most of the safety work, the first being that a stop leads to a cool-down, because a hot part cut off dead can stay hot for an hour in an enclosure, and the second that a fault is latched in the state machine rather than in the sensor reading, so that a sensor that comes back does not restart the heater by itself.

Rows the table does not cover yet

The table should be read with a question for every cell, what happens if this event arrives in this state, which it answers for some cells, whereas for the others the design must still decide and write the decision down as an explicit ignore row. A press of the material button while the dryer is HEATING, for example, has no row, so by the rule above it must not happen, and in practice the press is ignored, which the table should say. The hands-on task at the end of this lesson asks you to find every such cell.

Try it: the transition grid (no simulator)

This task needs paper or a plain text file and no simulator, its point being to test the table itself before any code depends on it, using the requirements table and the transition table from this lesson.

  1. Draw a grid whose rows are the five states, IDLE, HEATING, HOLDING, COOLDOWN and FAULT, and whose columns are three events, the start/stop button, the material button and a fault (any of the faults in transition 6).
  2. In each cell, write the number of the transition that applies, with its condition if it has one, or gap if no row applies, using the transition table only and adding no rows yet.
  3. Count the gaps, and for each one write the behaviour you want (ignore, or a new state) and one sentence naming the requirement number that supports your choice.
  4. Check the requirements table against the grid and name one requirement the grid does not need, saying why, as requirement 1.4 (the display) is an output rather than a transition and so does not belong in the grid.
Hint

Start from the empty cells. Eight of the fifteen cells have a row that applies with no condition. One more has a row that applies only under a condition, so look at the condition as well as the state.

Model answer

There are seven gaps. Of the fifteen cells, eight have an unconditional row: the button in IDLE (1), HEATING (4) and HOLDING (4); the material button in IDLE (8); and the fault in IDLE, HEATING, HOLDING and COOLDOWN (6). The button in FAULT has row 7, but only when the cause is gone and the part is below 60 °C, so it is a conditional cell. Six cells have no row at all. The seven gaps are those six cells plus the failing case of the conditional FAULT cell.

The seven gaps, with a suggested decision for each:

  1. COOLDOWN, start/stop button. Ignore the press. The part is still hot and the cooldown must finish (requirement 1.5).
  2. FAULT, start/stop button, when the cause is still present or the part is 60 °C or above. Ignore the press. This is the rule of requirement 2.6, which the table states only for the accepted case.
  3. HEATING, material button. Ignore it. Material is chosen while idle (requirement 1.3), and changing it mid-cycle would change the setpoint and the hold time.
  4. HOLDING, material button. Ignore it, for the same reason as the previous row.
  5. COOLDOWN, material button. Ignore it, for the same reason.
  6. FAULT, material button. Ignore it, for the same reason.
  7. FAULT, a further fault event. Stay in FAULT. Keep the first fault code, so that the display shows the original cause. This is a design choice that the requirements do not settle, so write it down as one.

The requirement the grid does not need is 1.4 (the display). It is an output that depends on the state, so it appears in the output column of the table and not as a transition.

There is no project for this lesson, so compare your grid with the model answer after finishing and count how many of your seven gaps match.

Common mistakes and how to spot them

Requirements without numbers

A review asks what "safe" means and two engineers give two answers, after which the first test is written with a value somebody guessed, because the requirement had no number. Write each requirement with a number, a unit and a condition, such as "90.00 °C measured at the sensor", and treat a row for which you cannot write a test as unfinished.

Flags instead of states

After an over-temperature trip the heater comes back on when the operator presses start, because the start branch checked the temperature but nobody tested the fault flag in that branch, a flag that a branch forgets to read becoming a row the tests never cover. Keep one state variable, put every transition in one place and write one test per row of the table.

The hold timer started at the press

A PLA cycle ends 40 minutes early, the log showing that the hold timer started at 0 minutes while the chamber needed 40 minutes to reach 45 °C, so the four hours ended four hours after the press and only 3 hours and 20 minutes were spent at the setpoint. Start the hold timer on transition 2, and write a host test that delays the setpoint reading and checks that the hold still lasts the full preset time (requirement 1.2).

A recovering sensor that restarts the heater

An NTC lead is shaken loose and the sensor fault latches, but the heater turns on again when the lead reconnects, with no button press, because the fault was held in the reading rather than in the state. Make the fault a state (FAULT), clear it only in transition 7, and write a host test that feeds a sensor fault and then a good reading and expects FAULT to stay.

Requirements and state-machine reviews

In a product team the requirements table is the first document a safety assessor reads, standards such as IEC 61508 (lesson 112) asking that each safety function be specified, verified and traced to tests, so a small team keeps the table in the repository next to the code, a change to a criterion coming with a change to its test. A reviewer checks whether every row has a number and whether every number has a test that fails when the number is wrong.

Reviewers read a state machine twice, once as a diagram showing the main path and once as a table showing the cells, because a review looking only at the diagram misses the cells without a row, which is where the first defects usually sit, and the grid in this lesson's hands-on task is the same check in small.

Physical protection matters as much as software, the hardware cutoff described above, a thermal fuse or a bimetal switch in series with the heater, working without the microcontroller at all, while the software checks form a second layer, and a strong design keeps both. Klipper makes the same point on 3D printers, its verify_heater checking that a heater really heats while the printer still needs its own physical protection.

Summary

  • A requirement is a yes-or-no statement, its acceptance criterion the measurable condition and a test the check of that criterion.
  • Safety requirements describe what happens when a part fails, defining the safe state and shaping the state machine.
  • A latched fault stays set after its cause has gone, until a person clears it.
  • A state machine stores one state and lists every allowed transition, so unsafe actions are refused by state rather than by flags scattered through the code.
  • One physical button can produce different events in different states, each event needing a row or an explicit ignore.
  • A hardware cutoff and software checks are two separate layers of protection.
