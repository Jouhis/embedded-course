Timing analysis: execution time, deadlines, and rate-monotonic priorities

A periodic task is correct only if every run finishes before its deadline, and the runs that matter most are the slowest ones. This lesson shows how to time a run with a hardware timer, how to assign rate-monotonic priorities, and how to check a task set against the utilisation bound.

By the end of this lesson you can time a code section with TIM2 in microseconds, assign rate-monotonic priorities to periodic tasks, and check a task set against the Liu and Layland utilisation bound n(2^(1/n) − 1).

Where we are and why it matters

Lesson 86 defined a job's deadline and its response time, and it showed that a super-loop can miss a deadline when a long job blocks a short one. Lesson 87 turned each job into a FreeRTOS task, and it introduced the tick and vTaskDelayUntil(). Lesson 91 showed that a mutex can make a high-priority task wait for a low-priority one, and that the wait is extra time a design has to count.

This lesson covers the timing half of a design review. Lesson 92 covered the stack half. The question here is whether each task finishes its work before its deadline on every run. A motor controller that runs its current loop 2 ms late can overheat a winding. A fitness tracker whose display update is 200 ms late is only annoying. The two products set very different deadlines, but the analysis is the same for both. A senior engineer will ask for the measured numbers and the bound, not for a feeling that the system is fast enough.

Work, period and deadline

A periodic task runs at a fixed rate. Its period, T, is the time between the starts of two runs. Its work, C, also called its execution time, is the CPU time that one run needs. Its deadline is the time by which each run must finish. The usual simple case sets the deadline equal to the period, so the task must finish before its next start.

A job's response time is its waiting time plus its own work, as lesson 86 defined it. The deadline is met when the response time is within the deadline. The waiting time comes from the other tasks and interrupts that run first, so the work and the waiting together decide the outcome. A task with a short work time can still miss a deadline if it waits behind something long.

The work of a task is not a single number. It changes with the input, with the branch that is taken, and with any interrupt that arrives during the run. A deadline has to hold for the slowest run that can happen, because the system is wrong on the one run that misses. The average is useful for planning the CPU budget, and it is useless for deciding whether a deadline is met.

Two terms come up in reviews. The worst-case execution time, WCET, is the largest work that a task can need on any run. The measured worst case is the largest work that the tests actually showed. The measured value is never more than the true WCET, and it is only as good as the tests that produced it. This lesson measures the second and uses it as an estimate of the first.

Measuring time: a counter faster than the tick

The tick is the kernel's clock. In this project it runs at 1 kHz, since configTICK_RATE_HZ is 1000, so one tick is 1 ms (lesson 87). That is too coarse for a work time of a fraction of a millisecond. A run that takes 0.3 ms either lies inside one tick or straddles two, and the tick count cannot say which. So the project times its work with a hardware timer, TIM2.

A timer is a counter that is driven by a clock. TIM2 is a 16-bit counter. It counts clock pulses, and when it reaches its reload value it wraps back to zero (lesson 71 covered the counter, the reload register ARR and the wrap). The prescaler, the PSC register, divides the clock before it reaches the counter. Lesson 71 gave the rule: the counter ticks at the clock frequency divided by PSC + 1.

The project's clock is SystemCoreClock, which is 8 MHz here. The project does not configure the phase-locked loop (PLL) that would raise it, so the value stays at the reset default of 8 MHz (the variable is initialised to 8000000 in system_stm32f1xx.c). Dividing 8 MHz by 8 gives 1 MHz, so one count is one microsecond, and the prescaler is 8 − 1 = 7. The code computes that value from the clock rather than writing 7 directly. If someone later changes the clock setup, the one-microsecond count stays true. A hard-coded 7 would silently make every measurement wrong after such a change.

A timer measures elapsed time, not the CPU time of the task. TIM2 keeps counting while another task runs. If a task is preempted in the middle of a measured section, the measured time includes the other task's run. That is the right quantity for a deadline, which is counted in elapsed time. It also means that a large worst value can come from preemption rather than from the work itself, and the mistakes section shows how to tell the difference.

Deadlines, periods and rate-monotonic priorities

The fixed priorities of FreeRTOS decide which task runs when two are ready. The kernel runs the highest-priority ready task (lesson 87). For periodic tasks the standard choice is rate-monotonic assignment: the shorter the period, the higher the priority. The reason is intuitive once you picture it. A task that must run every 10 ms cannot wait behind a task that runs every second, because it would miss its window. A task that runs every second can always wait a few milliseconds.

In FreeRTOS, a larger number means a higher priority, and the port's configMAX_PRIORITIES sets the range. So the 10 ms task gets priority 3, the 100 ms task gets 2, and the 1000 ms report gets 1. The rule is about the period, not about how much the output matters to a reader. A task that prints a lot is not more urgent than a task with a short deadline.

Liu and Layland published the central result in 1973. For independent periodic tasks whose deadlines equal their periods, rate-monotonic priorities are optimal among fixed-priority schemes. They also gave a test, the utilisation bound. Add up the utilisation of every task, where each task's utilisation is its work divided by its period, U = Σ Ci/Ti. If U is at most n(21/n − 1) for n tasks, every task meets its deadline. The right-hand side decreases as n grows, and it approaches ln 2, about 0.693, as n becomes large. 

U = Σ (Ci / Ti)  ≤  n · (21/n − 1)

n = 1: 1.000     n = 2: 0.828     n = 3: 0.780     n → ∞: ln 2 ≈ 0.693

The bound is sufficient, not necessary. A task set above the bound may still be schedulable, and then you need an exact response-time analysis to decide. A set below the bound is always schedulable under rate-monotonic priorities, so the bound is the first check you run, and it costs one line of arithmetic. The bound assumes independent tasks and deadlines equal to periods. When either assumption fails, the bound does not apply, and the design needs a different analysis.

Worked example with numbers

Take the three tasks of the project. The fast task runs every 10 ms, the slow task every 100 ms, and the report task every 1000 ms. The table gives design targets for their work times. These are targets, not measurements. Your report shows the real numbers, and you replace these with them.

TaskPriorityPeriod TWork C (target)C / T
fast310 ms0.3 ms0.030
slow2100 ms3 ms0.030
report11000 ms0.5 ms0.0005

Step 1: the fast task. It uses 0.3 ms out of every 10 ms, so its share is 0.3 divided by 10, which is 0.030.

Step 2: the slow task. It uses 3 ms out of every 100 ms, which is 3 divided by 100. That is 0.030 again.

Step 3: the report task. It uses 0.5 ms out of every 1000 ms, which is 0.0005.

Step 4: the total. 0.030 + 0.030 + 0.0005 = 0.0605. The bound for three tasks is 0.780, so the set passes the test with a wide margin. Even if the real work were ten times longer than the targets, the total would be 0.605 and still under the bound.

Step 5: a measured value that wraps. The timing code subtracts two counter reads, and the counter wraps back to zero every 65,536 microseconds. Suppose the first read is 65000 and the second read, taken after the counter has wrapped once, is 300. Plain subtraction gives 300 − 65000 = −64700, which is not a time. Adding one full wrap, 65536, gives 836. So the elapsed time is 836 µs. The code does this with the 16-bit cast shown in the code section, and the common mistakes section shows what happens without it.

The bound says nothing about the stack, the shared bus or the interrupts, so a passing result is a necessary first step, not a proof of the whole system. Lesson 91 showed that a mutex can make a high-priority task wait for a low-priority one, and that wait is extra time the bound does not include. A review should ask for the blocking time as well, and for the time that interrupts take from each task.

See the bound at work on a task set with longer work times than the project's, so that the bars are visible. The rate-monotonic set meets every deadline. Swap the priorities, or add work until U passes 1, and watch the short task miss.

Reading the code, line by line

The timing code is spread over a few functions in the solution's main.c. The constants come first: 

#define TIMER_TICKS_PER_US 1U       /* the TIM2 prescaler gives 1 count per microsecond */
#define FAST_PERIOD_MS     10U
#define SLOW_PERIOD_MS     100U

TIMER_TICKS_PER_US states the goal of the prescaler in plain words: one count per microsecond. The periods are in milliseconds, which is the unit a reader will check against the design. The U suffix marks each as an unsigned constant.

The timer setup has four lines: 

RCC->APB1ENR |= RCC_APB1ENR_TIM2EN;
TIM2->PSC = (SystemCoreClock / 1000000U) * TIMER_TICKS_PER_US - 1U;
TIM2->ARR = 0xFFFFU;
TIM2->CR1 = TIM_CR1_CEN;

The first line turns on the clock to TIM2 in the reset and clock control block (RCC). Until that bit is set, TIM2 receives no clock, so it does not count. The second line is the prescaler. SystemCoreClock / 1000000U is the number of clock cycles in one microsecond, which is 8 at 8 MHz. Multiplying by TIMER_TICKS_PER_US asks for one count per microsecond, and subtracting one gives the register value 7, because the register stores the divider minus one.

The third line sets the auto-reload value ARR to 0xFFFF. The counter then runs from 0 to 65535 and wraps, which is the 16-bit range that the wrap-safe subtraction depends on. The fourth line sets the counter-enable bit, CEN, in the control register CR1, which starts the counting. The counter runs from then on, whether or not any task is measuring.

The measurement function is the one that uses the counter: 

static void timed_work(uint32_t loops, volatile uint32_t *max_us) {
    uint16_t start = (uint16_t)TIM2->CNT;
    do_work(loops);
    uint32_t elapsed = (uint16_t)((uint16_t)TIM2->CNT - start);
    if (elapsed > *max_us) {
        *max_us = elapsed;
    }
}

The first line reads the counter and stores it as a 16-bit value. The second line runs the work. The third line reads the counter again and subtracts the first reading. The outer (uint16_t) cast makes the result a 16-bit value, so when the counter wrapped during the work, the subtraction comes out right, as the worked example showed. The cast is what makes the function wrap-safe. Without it, the result is a negative or 32-bit difference, and a wrap produces a meaningless number. The function is correct as long as the work is shorter than one full wrap, which is 65.536 ms at one microsecond per count.

The last lines keep the largest value that has been seen. The pointer max_us points at the task's own worst-case variable, so every run can update it. This is the line that implements the rule that a deadline is about the worst case, not the average.

The periodic task ties the timing together. Here is the fast task from the solution: 

static void fast_task(void *arg) {
    (void)arg;
    TickType_t last_wake = xTaskGetTickCount();
    for (;;) {
        timed_work(FAST_WORK_LOOPS, &fast_max_us);
        vTaskDelayUntil(&last_wake, pdMS_TO_TICKS(FAST_PERIOD_MS));
    }
}

last_wake holds the tick at which the task last started. It is set once, before the loop. (void)arg tells the compiler that the parameter is unused, which keeps the warning list clean. Inside the loop, timed_work() runs the work and records its worst time into fast_max_us. The last line controls the timing. vTaskDelayUntil() sleeps until last_wake plus the period, and it then moves last_wake forward by exactly one period. A plain vTaskDelay(10) would instead sleep 10 ms after the work finished, so the period would drift by the work time on every cycle. Over a long run the drift adds up, and the measured rate is wrong. pdMS_TO_TICKS() converts milliseconds to ticks, and with a 1 kHz tick the conversion is the identity, so 10 ms is 10 ticks.

Finally, the priorities are the third and fourth arguments of the three xTaskCreate() calls in main(). The solution sets them as follows: 

xTaskCreate(fast_task, "fast", FAST_STACK_WORDS, NULL, 3U, &fast_handle);
xTaskCreate(slow_task, "slow", SLOW_STACK_WORDS, NULL, 2U, &slow_handle);
xTaskCreate(report_task, "report", REPORT_STACK_WORDS, NULL, 1U, &report_handle);

The shortest period, 10 ms, has the highest number, 3, as rate-monotonic order requires. The report task, with the longest period, has 1. The stack depth argument in the middle is the subject of lesson 92.

Common mistakes and how to spot them

Mistake 1: using a plain delay for a periodic task. A task written with vTaskDelay() runs at a period of work time plus delay time, not at the period you wrote. The symptom appears only over time. Take a task with a 100 ms period that does 2 ms of work per run and calls vTaskDelay(100). Each cycle takes 102 ms, so in 10 seconds it runs about 98 times, not 100. The fix is vTaskDelayUntil(), as the solution uses, with the previous wake time kept between cycles.

Mistake 2: subtracting counter reads without the 16-bit cast. Suppose the first read is 64000 and the counter wraps before the second read, which is 500. Without the cast, the code subtracts in 32 bits and stores 4,294,903,796 µs, which is 232 − 63,500. That number is not a time. The symptom is a single absurd worst value on the report, and it stays there, because the report keeps the largest value it has seen. A wrap lands inside a measurement only some of the time, so the symptom can take a while to appear. The fix is the cast, as in timed_work(), and a test with a start value close to the top of the counter range.

Mistake 3: reporting the average, or the first run. An average hides exactly the bursts that miss a deadline. A report that shows the mean of 1000 runs can look healthy while one run in a thousand is 2 ms late. The symptom is a field failure on the rare late sample, while the bench figures look fine. The fix is to keep the worst value, as the solution does, and to put that value in the report, so that the number a reviewer sees is the one the deadline is checked against.

Mistake 4: equal or reversed priorities. The starter sets the fast and slow tasks both to priority 2 on purpose. With equal priorities and time slicing, the kernel lets the two tasks take turns (lesson 87), so the fast task can be preempted in the middle of its measured section. The timer keeps counting during the preemption, so the measured worst time includes the slow task's run. The symptom is a fast worst value that looks like a slow task's work. The fix is the rate-monotonic order: the 10 ms task gets the higher priority.

Mistake 5: treating a passing bound as a proof. A set below 0.780 with three tasks passes the first test, but the test assumes independent tasks, deadlines equal to periods, and no blocking. A mutex, an interrupt that steals time or a task with a late deadline all sit outside it. The symptom is a design that passes the review and then misses a deadline with a shared bus. The fix is to add the blocking time and the interrupt time to each task's work, and to run the exact analysis when the set is above the bound.

In real projects

Teams that ship real-time products measure the worst-case execution time of each task and interrupt on the real board, with a timer such as the one in this lesson. They compare the sum against the deadlines and keep the table in the design record. A simulator's timing is useful for finding bugs, but it is not a substitute for the board's own measurement, so the figures in a review come from hardware.

Some teams also enable a runtime statistics feature in FreeRTOS, which reports the share of CPU time that each task used. That number is a useful overview, but it is an average over a window, so the worst case still needs its own measurement. Treat the statistics as a complement to the worst-case table, not a replacement.

In a code review, a senior engineer looks for three things. Each periodic task should use a delay until a fixed time, not a delay after the work. The worst case should be the value that is checked, not the average. And the priorities should follow the periods, with the blocking and interrupt time added to the analysis. Remember that the utilisation bound is a sufficient test, that it assumes independent tasks and deadlines equal to periods, and that a mutex or a blocking call adds time the bound does not count.

Summary

  • A periodic task has a period T, a work C and a deadline. The response time is the waiting time plus the work. The deadline must hold for the worst run, not the average.
  • The tick is 1 ms here, too coarse for short work. A timer counts microseconds when its prescaler is set to the clock divided by 1 MHz, which is 8 − 1 = 7 at the project's 8 MHz clock.
  • Subtract two counter reads in unsigned 16-bit arithmetic. At one microsecond per count the wrap time is 65.536 ms, so one measurement must be shorter than that.
  • Keep the worst case. The timer measures elapsed time, so a preempted run includes the other task's work.
  • Use vTaskDelayUntil() for periodic tasks, so the period does not drift with the work time.
  • Rate-monotonic priorities give the shortest period the highest priority. For n tasks, a total utilisation at or below n(21/n − 1) guarantees the deadlines, for independent tasks whose deadlines equal their periods. The bound is sufficient, not necessary.
