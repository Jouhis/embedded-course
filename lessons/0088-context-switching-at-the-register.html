Context switching at the register level

Saving and restoring task registers

By the end of this lesson you can explain which registers the hardware stacks and which the software saves, describe the stack layout after a switch, and step through a two-task round-robin in the simulator, predicting each task's PSP and R4 before you check them.

The mechanics behind a task switch

Lesson 87 created tasks and showed the scheduler choosing the highest-priority ready task, saying that a switch happens while leaving its mechanics for this lesson. A switch has a very specific job, because a task is its registers and its stack, so when the kernel moves the core from task A to task B, the values in R0 to R15 belong to A and B's values must be restored before B runs, without A noticing that it stopped.

The mechanics build on three earlier lessons, lesson 33 having defined the stack and the calling convention that splits the registers into two groups, lesson 34 having shown that the core stacks registers itself when an exception starts, and lesson 35 having introduced the two stack pointers, MSP and PSP, used by tasks and exceptions. A context switch combines those three ideas, once per switch, in a few dozen instructions.

This lesson covers the registers, the stacks and the simulator program, while lesson 89 takes the switch handler line by line, maps it to the FreeRTOS port and explains why the switch runs at the lowest interrupt priority. This lesson comes first, because lesson 89 uses the stack layout, the saved block and the EXC_RETURN values defined here without defining them again.

Core registers as task state

The Cortex-M3 has sixteen core registers visible to a program, R0 to R12, the stack pointer SP (R13), the link register LR (R14) and the program counter PC (R15), together with the program status register xPSR, which holds the condition flags and the number of the exception being handled. There is only one set of these registers, holding A's values while the core runs task A and B's while it runs B.

A task's state is therefore its registers at the moment it stopped plus the stack those registers point into, and a context switch saves one task's state somewhere, loads another's and makes the core continue from there. The glossary's context switch entry gives the Cortex-M3 split in one line, and the rest of this lesson explains why the split falls where it does.

The stack belongs to the state for a practical reason, a task's local variables, the return addresses of the functions it called and its saved registers all sitting on its stack (lesson 33), so a task B resumed with B's registers but A's stack would read A's local variables and return to the wrong place. The kernel therefore gives each task its own stack, and a switch changes both the register values and the stack pointer.

Caller-saved and callee-saved registers

The Arm Procedure Call Standard, the AAPCS, is the contract C functions follow, under which a function may change R0 to R3 and R12 freely, because the caller does not expect them preserved, these being the caller-saved registers, while it must return R4 to R11 and SP with the values it was given, because the caller relies on them, these being the callee-saved registers.

The hardware uses the same split when an exception starts, stacking eight words, the PC, the xPSR, R0 to R3, R12 and LR, which the Cortex-M3 Technical Reference Manual lists in that order in section 5.5.1, Stacking (DDI0337G, the copy hosted by Keil, the list matching Figure 5-1 of that section). Those are the registers a handler may change, so the core saves them for the handler in a fixed number of cycles before any of your code runs, while the hardware leaves the eight callee-saved registers R4 to R11 alone, so a C handler using them must save and restore them itself.

A context switch differs from a handler, because a handler returns to the code it interrupted, which still has the registers it had before, whereas a switch returns to a different task whose R4 to R11 were lost when the core moved to the other one. Only the kernel can save them, so the kernel's handler does, which is why R4 to R11 appear in the switch code.

The main and process stack pointers

The Cortex-M3 has two stack pointers, the main stack pointer (MSP), used by all exception handlers and by thread mode after reset, and the process stack pointer (PSP), which the CONTROL register can select for thread mode. The RTOS gives each task its own stack and runs the tasks on the PSP, so the handler always uses the MSP and the tasks always the PSP (lesson 35).

This is what makes a switch work. When task A is interrupted, the hardware pushes A's eight-word frame onto A's PSP, and the switch handler, running on the MSP, pushes R4 to R11 below that frame on A's stack and saves the new top of A's stack in a variable. It then loads B's saved top of stack, pops B's R4 to R11, sets PSP to point at B's frame and returns, the exception return popping B's eight-word frame from PSP so that B continues, while at no point does the handler's own MSP hold a task's data.

The return is driven by the link register, loaded on exception entry with a special value called EXC_RETURN that says where to return, the course's simulator using 0xFFFFFFF9 to return to thread mode on the MSP and 0xFFFFFFFD to return to thread mode on the PSP. The port makes exactly that change in vPortSVCHandler, the handler the first start reaches through svc 0, ORing 0xD into LR (orr r14, #0xd, in port.c, line 239), which turns the 0xFFFFFFF9 left by the SVC entry into 0xFFFFFFFD. A return with the wrong value pops the frame from the wrong stack, one of the mistakes described below.

The three jobs of the switch handler

Every switch does three things, which are easiest to follow when kept apart.

  1. Save the running task. Push R4 to R11 below its frame and store the new top of stack in a variable.
  2. Choose the next task. In the simulator a small piece of code flips a slot in memory, while in FreeRTOS a call to vTaskSwitchContext() sets the current task pointer.
  3. Restore the next task. Load its stack top, pop its R4 to R11, set PSP to its frame and return, so that the exception return pops that frame.

The order matters, because the choice changes which task is current, so the save must happen before it and the restore after it. The simulator's handler reads the slot naming the running task once, at its start, and writes the slot naming the next task once, before it restores, so with these three jobs in mind its instructions fall into clear groups, the same groups lesson 89 follows in the FreeRTOS handler with line numbers.

A context switch resembles a shift change at a single desk, the leaving worker putting every paper on the desk into their own drawer, the task's stack, and writing on a card where the pile ends, the saved stack pointer in the TCB, while the next worker reads their own card, takes their papers out of their drawer and carries on in the middle of the sentence they were writing. The comparison breaks on who does the work, though, because the workers tidy their own desks, whereas the leaving task does nothing at all, the hardware and the kernel saving its state for it.

The task stack layout after a switch

The figure shows task A's stack after its first switch in the simulator's memory map. The stack grows downward, so the frame lies at the top, at higher addresses, with the saved R4 to R11 block below it, and the PSP points at the lowest word of the frame, R0, each word being 4 bytes, the frame occupying 0x20000060 to 0x2000007F and the saved block 0x20000040 to 0x2000005F.

Two details of the figure are worth checking against the code. The saved block starts at 0x20000040 and the frame 32 bytes higher, a gap of eight words, the size of the R4 to R11 block, and the PSP the kernel stores is the address of the saved block rather than the frame, so restoring the task reads the saved block's address, pops R4 to R11 and then adds 32 to find the frame, the gap in the figure being the reason for that addition.

A hand-built frame for the first switch

A task that has never run has no saved state, yet the first switch must still end with an exception return, which pops a frame from the PSP, so the simulator's setup code builds one frame per task by hand before the first switch. The frame is only a list of values in RAM, and the core cannot tell that a program rather than an interrupt wrote it.

Two of the eight words matter for the first run, the PC slot holding the address of the task's entry point, so that the return jumps to the start of the task, and the xPSR slot holding 0x01000000, with only bit 24, the Thumb bit, set, since the Cortex-M3 runs only Thumb code and a return with the Thumb bit clear would fault. The other six words, R0 to R3, R12 and LR, start at zero, because the task has not set them yet.

A worked check makes the layout concrete. Task A's frame starts at 0x60 and its PC slot lies at 0x78, a difference of 0x18, 24 bytes or six words above the frame's lowest word, the six words below the PC slot being R0, R1, R2, R3, R12 and LR, so the PC slot is the seventh word of the frame, matching the order the hardware stacks, and the same reasoning places the xPSR slot at 0x7C, one word higher.

A real kernel does the same job in C and assembly, the FreeRTOS port building this frame in pxPortInitialiseStack, which lesson 89 reads line by line.

The handler is the switch, saving the running task's R4–R11 under its hardware frame, saving the PSP, loading the other task's PSP and registers and returning, and the first switch starts task A, because nothing has run yet.

LDR R0, =task_a loads the address of the label task_a, exactly as the GNU assembler does, and that address becomes the stacked PC, so the first exception return lands at the start of the task. The simulator program step by step

The setup at the top of main builds two fake hardware frames, one per task, so that the first switch has something to return from, each store being a word write into the simulator's RAM. The first pair of stores writes 2, meaning no task yet, into the current-task slot at 0x20000000, and the PSP slots at 0x20000004 and 0x20000008 then receive the saved-block addresses of the two tasks.

Task A's frame comes next, LDR R0, =task_a loading the address of the label and the store to 0x20000078 putting it in the frame's PC slot, 0x18 bytes above the frame's base at 0x60 and 0x38 bytes above the saved block at 0x40, while the store to 0x2000007C puts 0x01000000 in the xPSR slot, with only the Thumb bit set, the state a Cortex-M3 must be in to run this code. The R0 to R3, R12 and LR slots stay zero, because nothing has set them, and task B's frame is written the same way at 0x200000B8 and 0x200000BC, 32 bytes above its saved block at 0x20000080.

SVC #0 is a supervisor call, an exception that on the simulator jumps to the label SVC_Handler, the core stacking its own frame on the MSP, since it was in thread mode on the MSP at reset, and setting LR to 0xFFFFFFF9. The handler sees CUR equal to 2 and takes the first path, setting the next task to A and loading A's registers from its saved block at 0x20000040, which holds zeros, so R4 starts at 0, and the restore adds 32 to the block's address to find A's frame at 0x20000060, writes that into PSP and returns with 0xFFFFFFFD, which pops the frame, loading PC with task_a, so task A runs for the first time.

Task A executes ADD R4, R4, #1, making R4 equal to 1, and then SVC #0 again, and this time the handler reads CUR as 0, saves R4 to R11 below A's frame at 0x20000040 and stores A's new PSP, the saved block's address. Testing CUR, it sets the next task to B and restores B's block, which holds the R4 that B saved when it yielded (100, from its first visit), and returns to B, which adds 100 and yields again, after which A returns with its R4 restored to 1, so each visit adds to the value saved on the previous visit and the other task's value is never lost.

Common mistakes and how to spot them

R4 to R11 left unsaved

After a switch task A's R4 shows a value from task B in the simulator, for example 100 where A should have 2, and on hardware a loop counter or pointer in a task jumps when another task runs, because the handler stores the stack top and restores the next task while skipping the eight STR lines. Save the block below the frame and restore it from the same offsets.

A saved-block address off by 32 bytes

A task resumes with the wrong PC or xPSR, or faults with the PSP pointing at a strange address, because the saved block was written at the frame address rather than 32 bytes below it, so the restore reads the frame as if it were R4 to R11. Keep the subtraction and the addition symmetrical, the value stored as the PSP being the address of the saved block and the restore adding 32 to reach the frame, as the figure's two addresses show.

The wrong EXC_RETURN value

The handler's own stack gets mixed with the task's and the task's PC is read from the wrong place, because the handler returns with 0xFFFFFFF9, popping the frame from the MSP, while the task runs on the PSP, something the simulator's log makes easy to see by naming the stack it unstacked from. Return with 0xFFFFFFFD for a task on the PSP.

A global variable expected to travel with the task

A counter shared between two tasks through a global variable comes out lower than expected, by an amount depending on the timing of the switches, because the developer assumed the switch keeps it per task, as it does R4, whereas the switch saves registers and stack pointers rather than globals, so both tasks write the same memory. Keep per-task state in the task's own variables or stack, and pass shared data through a kernel object such as a queue (lesson 90) rather than a bare global.

Debugging and reviewing an RTOS port

Engineers debugging an RTOS port rarely step through the switch line by line on hardware, looking instead at the stack around the saved PSP, checking the EXC_RETURN value at the exception return and confirming that the saved block and the frame lie where the layout says. A debugger shows the PSP in a register view and a stack dump around it shows whether the frame is intact, so with the layout from this lesson a stack dump answers the question.

Reviewers of a port check that the saved registers are the callee-saved set, that the stored PSP is the saved block rather than the frame and that every return uses the EXC_RETURN value for the stack the task runs on, checks that need no knowledge of the scheduler, only the register split and the stack layout of this lesson.

Summary

  • A task is its registers and its stack, and a context switch saves one set and restores another.
  • The hardware stacks R0 to R3, R12, LR, PC and xPSR on exception entry, while the kernel saves R4 to R11, because only a switch needs to preserve them for a leaving task.
  • Tasks run on the PSP and handlers on the MSP, and the switch saves the leaving task's stack top and loads the arriving task's.
  • The saved block sits 32 bytes below the hardware frame, so a task's stored PSP points at the block and the restore adds 32 to reach the frame.
  • A first task has a hand-built frame with the PC set to its entry point and xPSR set to 0x01000000.
  • EXC_RETURN chooses the stack for the return, 0xFFFFFFFD for thread mode on the PSP and 0xFFFFFFF9 for the MSP.
