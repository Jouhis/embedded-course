Context switching at the register level

A context switch is two pieces of work: the core saves eight registers on the stack by itself, and the kernel saves the other eight. Then it swaps one stack pointer. You will build that in the CPU simulator, and then find the same code in the FreeRTOS port.

By the end of this lesson you can explain which registers the hardware stacks and which the software saves, step through a two-task round-robin in the simulator, and point to the matching lines of the FreeRTOS Cortex-M3 port.

The idea

A task is only its registers, its stack and its place in the scheduler. A context switch saves the registers of the running task, makes the stack pointer point to the next task's saved state, and restores that state. The last step is a return from the exception, which pops the next task's hardware frame and resumes it.

The Cortex-M3 splits the work. On exception entry, the hardware stacks eight words: xPSR, PC, LR, R12 and R0 to R3 (lesson 34, DDI0337G §5.5.1). These are the registers that a C function is allowed to change without saving, under the AAPCS calling convention (lesson 33). The kernel saves the other eight, R4 to R11, because a C handler is not required to preserve them and the hardware does not touch them. The FreeRTOS port's comment says so directly: "Pop the registers that are not automatically saved on exception entry" (port.c line 234).

Two stacks and one handler

Each task has its own stack, and thread mode uses the process stack (PSP), as lesson 35 showed. When a task is interrupted or yields, the hardware frame is pushed onto its PSP. The handler then pushes R4–R11 below that frame, and saves the resulting PSP in the task's control block. The next task's PSP is loaded, its R4–R11 are popped, and the exception return pops its hardware frame. The stack pointer changes, and the registers follow it.

The FreeRTOS port uses the PendSV exception for the switch, not SVC. PendSV is set to the lowest priority (see the port source below), so the switch waits until every other interrupt has finished. The simulator in this lesson uses SVC for both the first start and every switch. It does not model PendSV priority or interrupt nesting, so the order of exceptions is a simplification.

Try it in the CPU simulator

The program below has two tasks. Each adds to its own R4, which is the only state the test checks: task A adds 1 and task B adds 100. The handler is the switch. It saves the running task's R4–R11 under its hardware frame, saves the PSP, loads the other task's PSP and registers, and returns. The first switch starts task A, because nothing has run yet.

LDR R0, =task_a loads the address of the label task_a, exactly as the GNU assembler does. That address becomes the stacked PC, so the first exception return lands at the start of the task. The RAM layout is: the slots at 0x20000000 (current task, PSP of A, PSP of B), task A's stack ending at 0x20000080, and task B's stack ending at 0x200000C0.

  1. Press Instruction repeatedly. Watch the PSP in the system panel. It changes at each SVC, and the mem panel shows the current task in the first word at 0x20000000.
  2. Press Instruction until SVC_Handler runs for the first time. Predict first: which task starts, and what PSP will the task run on? Then check: task A, at 0x20000060.
  3. Run the program for a while. Each task's R4 counts up in its own steps, and R4 holds the task's value while the other task runs. Predict R4 for task B at its second visit before you check.
Hint

Task A's hardware frame starts at 0x20000060, which is 32 bytes below its stack top. The handler saves R4–R11 in the 32 bytes below that, so task A's saved block starts at 0x20000040. The PSP that a task runs on is always its hardware frame, so the PSP values you see alternate between 0x20000060 and 0x200000A0.

The simulator's data-show list here includes mem, which shows the first 16 words of RAM: the current task and the two saved PSPs are visible there. The task stacks are above that range, so use the system panel for the PSP.

Map it to the FreeRTOS port

The real port does the same work in two handlers, and the file is third_party/FreeRTOS-Kernel/portable/GCC/ARM_CM3/port.c. Read these in order.

  1. Building a task's first frame (pxPortInitialiseStack, lines 182 to 199). The function writes the hardware frame by hand, with portINITIAL_XPSR (0x01000000, line 78) at the top, then the task entry as PC, then LR, R12, R3 to R0 and R4 to R11. It is exactly the layout the simulator program writes with its STR instructions.
  2. Starting the first task (vPortSVCHandler, lines 228 to 241, and prvPortStartFirstTask at line 247). The port's start function is called prvPortStartFirstTask in this kernel version. It sets MSP, enables interrupts and executes svc 0 (line 258). The SVC handler then restores the first task: ldmia r0!, {r4-r11} at line 234, msr psp, r0 at line 235, and orr r14, #0xd at line 239, which makes LR equal to 0xFFFFFFFD, return to thread mode on the PSP.
  3. The switch (xPortPendSVHandler, lines 455 to 485). The handler reads the running task's PSP (mrs r0, psp, line 461) and loads the current TCB address (ldr r3, =pxCurrentTCB, line 464). It saves R4–R11 below the hardware frame with stmdb r0!, {r4-r11} (line 467), and stores the new top of stack into the TCB (str r0, [r2], line 468). Then it calls vTaskSwitchContext (line 473), which picks the next task and changes pxCurrentTCB. The second half loads the new task's stack top from the TCB (lines 478 to 480), pops its R4–R11 (line 480), writes PSP (line 481) and returns with bx r14 (line 483).

Compare the simulator's handler with the port: the layout of the saved block, the store of the PSP in a slot, the choice of the next task, and the final MSR PSP followed by the exception return are the same steps. The simulator keeps the choice in a memory slot; the port calls vTaskSwitchContext(), which is in tasks.c at line 5109.

Why PendSV is at the lowest priority

The port sets PendSV to the lowest priority at line 390 (portNVIC_SHPR3_REG |= portNVIC_PENDSV_PRI), in the same way as SysTick (line 391), and gives SVCall the highest (line 392, portNVIC_SHPR2_REG = 0). The tick handler does not switch tasks itself. It only asks for a switch by pending PendSV (portNVIC_INT_CTRL_REG = portNVIC_PENDSVSET_BIT, near line 507). Because PendSV is the lowest priority, it runs when no other interrupt is active. A switch in the middle of another ISR would save a task while that ISR still uses the same stack, and that is the reason for the design. The ARMv7-M architecture defines the exception priority model that this relies on (Armv7-M Architecture Reference Manual, the exception model chapter; the Cortex-M3 TRM covers the system handler priority registers, SHPR2 and SHPR3).

The port uses BASEPRI (line 471) to mask the kernel's interrupts while vTaskSwitchContext() runs. The simulator has no BASEPRI and no nesting, so a real interrupt can arrive mid-switch on silicon in a way the simulator cannot show.

"What happens in a context switch on a Cortex-M3 with FreeRTOS, step by step?" Answer out loud in 90 seconds, then compare.

Model answer

The tick handler decides a switch is needed and pends PendSV. When no higher-priority interrupt is active, PendSV runs: the running task's PSP is read, R4 to R11 are pushed below the hardware frame that the core stacked on entry, and the new top of stack is stored in the task's control block. vTaskSwitchContext picks the highest-priority ready task and updates pxCurrentTCB. The handler loads the new task's stack top, pops its R4 to R11, writes PSP, and returns with an EXC_RETURN value that pops the hardware frame. The task resumes at the PC it saved. A good answer also says which registers are which: the core saves R0 to R3, R12, LR, PC and xPSR, and the kernel saves R4 to R11, and it says why PendSV is the lowest priority.
