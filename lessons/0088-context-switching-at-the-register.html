Context switching at the register level

A context switch is two pieces of work: the core saves eight registers on the stack by itself, and the kernel saves the other eight. Then it swaps one stack pointer. You will build that in the CPU simulator, and then find the same code in the FreeRTOS port.

By the end of this lesson you can explain which registers the hardware stacks and which the software saves, step through a two-task round-robin in the simulator, and point to the matching lines of the FreeRTOS Cortex-M3 port.

Where we are, and why it matters

Lesson 87 created tasks and showed the scheduler choose the highest-priority ready task. It said that a switch happens, and it left the mechanics for this lesson. A switch has to do something very specific. A task is its registers and its stack. When the kernel moves the core from task A to task B, the values in R0 to R15 belong to A, and B's values must be restored before B runs, without A noticing that it stopped.

The mechanics build on three earlier lessons. Lesson 33 defined the stack and the calling convention that splits the registers into two groups. Lesson 34 showed that the core stacks registers itself when an exception starts. Lesson 35 introduced the two stack pointers, MSP and PSP, that a task and an exception use. A context switch is what happens when those three ideas are used together, once per switch, in a few dozen instructions.

Concept 1: what a task is made of

The Cortex-M3 has sixteen core registers that a program can see: R0 to R12, the stack pointer SP (which is R13), the link register LR (R14) and the program counter PC (R15). The processor also has the program status register xPSR, which holds the condition flags and the number of the exception being handled. There is only one set of these registers. When the core runs task A, they hold A's values. When it runs task B, they hold B's.

So a task's state is its registers at the moment it stopped, plus the stack those registers point into. A context switch is the act of saving one task's state somewhere, loading another's, and making the core continue from there. The context switch entry in the glossary gives the Cortex-M3 split in one line, and the rest of this lesson explains why the split falls where it does.

Concept 2: why the registers are split

The Arm Procedure Call Standard, the AAPCS, is the contract that C functions follow. A function may change R0 to R3 and R12 freely, because the caller does not expect them to be preserved. These are the caller-saved registers. A function must give back R4 to R11, and SP, with the same values it was given, because the caller relies on them. These are the callee-saved registers.

The hardware uses the same split when an exception starts. On exception entry the core stacks eight words: the PC, the xPSR, R0 to R3, R12 and LR. The Cortex-M3 Technical Reference Manual lists them in that order in section 5.5.1, Stacking (DDI0337G, the copy hosted by Keil; the list is the same as Figure 5-1 of that section). Those are the registers a handler is allowed to change, so the core saves them for the handler, and does it in a fixed number of cycles before any of your code runs. The eight callee-saved registers R4 to R11 are not touched by the hardware at all. A C handler that uses them must save and restore them itself.

A context switch is different from a handler. A handler returns to the code it interrupted, which has the same registers it had before. A switch returns to a different task, and that task's R4 to R11 were lost when the core moved to the other one. Only the kernel can save them, so the kernel's handler does. That is why R4 to R11 appear in the switch code.

Concept 3: two stacks and two pointers

The Cortex-M3 has two stack pointers. The main stack pointer (MSP) is used by all exception handlers, and by thread mode after reset. The process stack pointer (PSP) can be selected for thread mode through the CONTROL register. The RTOS gives each task its own stack and runs the tasks on the PSP, so the handler always uses the MSP and the tasks always use the PSP (lesson 35).

This is why a switch works. When task A is interrupted, the hardware pushes A's eight-word frame onto A's PSP. The switch handler then runs on the MSP, and it pushes R4 to R11 below that frame, on A's stack. It saves the new top of A's stack in a variable. It loads B's saved top of stack, pops B's R4 to R11, sets PSP to point at B's frame, and returns. The exception return then pops B's eight-word frame from PSP, and B continues. At no point does the handler's own MSP hold a task's data.

The return is driven by the link register. When an exception starts, LR is loaded with a special value called EXC_RETURN, which says where to return. The course's simulator uses 0xFFFFFFF9 to return to thread mode on the MSP, and 0xFFFFFFFD to return to thread mode on the PSP. The port makes exactly that change in its first-task code: it takes the MSP value and sets the bit that selects the PSP (orr r14, #0xd, in port.c line 239). A return with the wrong value pops the frame from the wrong stack, and that is one of the mistakes below.

Concept 4: the switch handler's three jobs

Every switch does three things, and it helps to keep them apart. First it saves the running task. That is the pushes of R4 to R11 below its frame, and the store of the new stack top. Second it chooses the next task. In the simulator this is a small piece of code that flips a slot in memory. In FreeRTOS it is a call to vTaskSwitchContext(), which sets the current task pointer. Third it restores the next task: a load of its stack top, a pop of its R4 to R11, and a return that pops its frame. Read the simulator's handler with these three jobs in mind, and the instructions fall into clear groups.

Concept 5: the stack layout after a switch

The figure shows task A's stack after its first switch, in the simulator's memory map. The stack grows downward, so the frame is at the top, at higher addresses, and the saved R4 to R11 block is below it. The PSP points at the lowest word of the frame, which is R0. Each word is 4 bytes. The frame is at 0x20000060 to 0x2000007F, and the saved block is at 0x20000040 to 0x2000005F.

Two things in the figure are worth checking against the code. The saved block starts at 0x20000040, not at the frame, and the frame begins 32 bytes higher. That 32-byte gap is eight words, the size of the R4 to R11 block. The second thing is that the PSP the kernel stores is the address of the saved block, not the address of the frame. When the switch restores the task, it reads the saved block's address, pops R4 to R11, and then adds 32 to find the frame. The gap in the figure is the reason that add is there.

Try it in the CPU simulator

The program below has two tasks. Each adds to its own R4, which is the only state the test checks: task A adds 1 and task B adds 100. The handler is the switch. It saves the running task's R4–R11 under its hardware frame, saves the PSP, loads the other task's PSP and registers, and returns. The first switch starts task A, because nothing has run yet.

LDR R0, =task_a loads the address of the label task_a, exactly as the GNU assembler does. That address becomes the stacked PC, so the first exception return lands at the start of the task. The RAM layout is: the slots at 0x20000000 (current task, PSP of A, PSP of B), task A's stack ending at 0x20000080, and task B's stack ending at 0x200000C0.

Hint

Task A's hardware frame starts at 0x20000060, which is 32 bytes below its stack top. The handler saves R4–R11 in the 32 bytes below that, so task A's saved block starts at 0x20000040. The PSP that a task runs on is always its hardware frame, so the PSP values you see alternate between 0x20000060 and 0x200000A0.

The simulator's data-show list here includes mem, which shows the first 16 words of RAM: the current task and the two saved PSPs are visible there. The task stacks are above that range, so use the system panel for the PSP.

Following the program, step by step

The setup at the top of main builds two fake hardware frames, one per task, so that the first switch has something to return from. Each store is a word write into the simulator's RAM. The first pair of stores writes the slot at 0x20000000, which holds the current task, with 2, meaning none yet. Then the PSP slots at 0x20000004 and 0x20000008 get the saved-block addresses of the two tasks.

The frame for task A is written next. LDR R0, =task_a loads the address of the label, and the store to 0x20000078 puts it in the PC slot of the frame, 0x18 bytes above the frame's base at 0x60, which is 0x38 bytes above the saved block at 0x40. The store to 0x2000007C puts the value 0x01000000 in the xPSR slot. That value has only the Thumb bit set, which is the state a Cortex-M3 must be in to run this code. The R0 to R3, R12 and LR slots keep zero, because nothing has set them. Task B's frame is written the same way at 0x200000B8 and 0x200000BC, which is 32 bytes above its saved block at 0x20000080.

SVC #0 is a supervisor call. It is an exception, and on the simulator it jumps to the label SVC_Handler. The core stacks its own frame on the MSP, because it was in thread mode on the MSP at reset, and sets LR to 0xFFFFFFF9. The handler then sees CUR equal to 2 and takes the first path, which sets the next task to A and loads A's registers. Its saved block at 0x20000040 holds zeros, so R4 starts at 0. The restore adds 32 to the block's address to find A's frame at 0x20000060, writes that into PSP, and returns with 0xFFFFFFFD. That return pops the frame, which loads PC with task_a, and task A runs for the first time.

Task A executes ADD R4, R4, #1, which makes R4 equal to 1, and then SVC #0 again. This time the handler reads CUR as 0, so it saves R4 to R11 below A's frame, at 0x20000040, and stores A's new PSP, which is the saved block's address. It sets the next task to B, because the test is on CUR. It restores B's block, which holds the R4 that B saved when it yielded (100, from its first visit), and returns to B. B adds 100 and yields again, and A returns with its R4 restored to 1. Each visit adds to the value that was saved on the previous visit, and the other task's value is never lost.

Code, line by line: the handler

The handler is the part of the program that does the switch, so its lines are explained in the groups of the three jobs.

LDR R1, =0x20000000 and LDR R2, [R1] load the address of the slot and then the value in it, which is the task that was running. CMP R2, #2 and BEQ first test for the very first switch, where there is nothing to save. This is a test on the saved state, not a special case in the hardware.

MRS R0, PSP reads the running task's PSP into R0, which is the address of its hardware frame. SUB R0, R0, #32 moves R0 down eight words, to the room below the frame. The next eight STR lines store R4 to R11 at offsets 0 to 28 from R0. This is the save, and it is the step that the hardware does not do for these registers. The store order matches the load order in restore, so the same offsets find the same values.

LDR R3, =0x20000004 chooses the slot for task A, and CMP and BEQ move to the slot for task B when CUR is 1. STR R0, [R3] stores the new stack top into that slot. This is the store that saves the task's state for next time. The stack top is the only value the kernel needs to find everything else in the block.

The next lines choose the next task. CMP R2, #0 and the pickb branch set R2 to the other task's number, and STR R2, [R1] writes it back to CUR. This is the simulator's version of vTaskSwitchContext(), which picks the next task and changes the current task pointer. The real kernel does this in C, and the simulator does it in four instructions.

restore loads the next task's saved block address and pops R4 to R11 with eight LDR lines. ADD R0, R0, #32 moves R0 up to the next task's frame, because the saved block is below the frame. MSR PSP, R0 sets the PSP to that frame, which the exception return will pop. LDR LR, =0xFFFFFFFD sets the return value to thread mode on the PSP, and BX LR performs the return. The branch to an EXC_RETURN value is what makes the core unstack the frame, and it is the last thing the handler does.

Map it to the FreeRTOS port

The real port does the same work in two handlers, and the file is third_party/FreeRTOS-Kernel/portable/GCC/ARM_CM3/port.c. Read these in order.

  1. Building a task's first frame (pxPortInitialiseStack, lines 182 to 199). The function writes the hardware frame by hand, with portINITIAL_XPSR (0x01000000, line 78) at the top, then the task entry as PC, then LR, R12, R3 to R0 and R4 to R11. The layout is the one the simulator program builds with its STR instructions. The port fills in the parameter as R0 and leaves the other slots for the kernel to use.
  2. Starting the first task (vPortSVCHandler, lines 228 to 241, and prvPortStartFirstTask at line 247). The start function sets MSP back to the top of the stack (line 253), enables interrupts (line 254) and executes svc 0 (line 258). The SVC handler then restores the first task: ldmia r0!, {r4-r11} at line 234, msr psp, r0 at line 235, and orr r14, #0xd at line 239, which makes LR equal to 0xFFFFFFFD, return to thread mode on the PSP.
  3. The switch (xPortPendSVHandler, lines 455 to 485). The handler reads the running task's PSP (mrs r0, psp, line 461) and loads the current TCB address (ldr r3, =pxCurrentTCB, line 464). It saves R4–R11 below the hardware frame with stmdb r0!, {r4-r11} (line 467), and stores the new top of stack into the TCB (str r0, [r2], line 468). Then it masks interrupts with BASEPRI (lines 471 and 472) and calls vTaskSwitchContext (line 473), which picks the next task and changes pxCurrentTCB. The second half loads the new task's stack top from the TCB (lines 478 to 479), pops its R4–R11 (line 480), writes PSP (line 481) and returns with bx r14 (line 483).

Compare the simulator's handler with the port. The layout of the saved block, the store of the stack pointer in a slot, the choice of the next task, and the final MSR PSP followed by the exception return are the same steps. The simulator keeps the choice in a memory slot; the port calls vTaskSwitchContext(), which is in tasks.c at line 5109. The port's xPortPendSVHandler is declared __attribute__((naked)) (line 123), so the compiler adds no prologue and epilogue of its own, because a prologue would push registers onto the stack before the assembly had read the PSP.

Why PendSV is at the lowest priority

The port sets PendSV to the lowest priority at line 390 (portNVIC_SHPR3_REG |= portNVIC_PENDSV_PRI), in the same way as SysTick (line 391), and gives SVCall the highest (line 392, portNVIC_SHPR2_REG = 0). The system handler priority registers are described in the Cortex-M3 TRM, DDI0337G, Table 8-18 on page 8-29: the group for handlers 8 to 11 is at 0xE000ED1C, which holds SVCall, and the group for handlers 12 to 15 is at 0xE000ED20, which holds PendSV and SysTick. The port's names match those addresses.

The tick handler does not switch tasks itself. It only asks for a switch by pending PendSV (portNVIC_INT_CTRL_REG = portNVIC_PENDSVSET_BIT, near line 507). Because PendSV is the lowest priority, it runs only when no other interrupt is active. A switch in the middle of another interrupt would save a task while that interrupt still uses the same stack, which is why the design waits. The port also uses BASEPRI around the call to vTaskSwitchContext(), to mask the kernel's own interrupts while the list operations run.

The simulator has no BASEPRI and no nesting, so a real interrupt can arrive in the middle of the switch on silicon in a way this simulator cannot show. Treat the simulator as a model of the order of operations, not of the timing.

Common mistakes and how to spot them

Mistake 1: not saving R4 to R11. The handler stores the stack top and restores the next task, but it skips the eight STR lines. The symptom in the simulator is that task A's R4 shows a value from task B after the switch, for example 100 where A should have 2. On hardware the symptom is a loop counter or a pointer in the task that jumps when another task runs. The fix is to save the block below the frame and restore it from the same offsets.

Mistake 2: an address off by 32 bytes. The saved block is written at the frame address, not 32 bytes below it, so the restore reads the frame as if it were R4 to R11. The symptom is a task that resumes with the wrong PC or xPSR, or a fault with the PSP pointing at a strange address. The fix is to keep the subtract and the add symmetrical: the value stored as the PSP must be the address of the saved block, and the restore must add 32 to reach the frame. The figure above shows the two addresses.

Mistake 3: the wrong EXC_RETURN. The handler returns with 0xFFFFFFF9, which pops the frame from the MSP, when the task is running on the PSP. The symptom is that the handler's own stack gets mixed with the task's, and the task's PC is read from the wrong place. The simulator reports the stack it unstacked from in its log, which makes this easy to see. The fix is to return with 0xFFFFFFFD for a task on the PSP.

Mistake 4: a switch written in plain C. A developer writes the switch as a C function with asm inside it. The compiler adds a prologue that pushes registers and moves the stack pointer before the assembly runs. The symptom is a task that resumes with values from the handler's own prologue, and it often works in a short test and fails under load. The fix is the naked attribute on the handler, as the port uses, so the assembly is the whole function.

Mistake 5: PendSV at a higher priority than the interrupt it runs inside. A developer sets PendSV to a priority that is more urgent than a peripheral interrupt, so the switch can happen in the middle of that interrupt. The symptom is a rare corruption of the stack of the interrupted handler, which looks like random data. The fix is the lowest priority for PendSV, as the port sets it at line 390.

In real projects

Engineers who debug an RTOS port rarely step through the switch line by line on hardware. They look at the stack around the saved PSP, check the EXC_RETURN value at the exception return, and confirm that the saved block and the frame are where the layout says. A debugger shows the PSP in a register view, and a stack dump around it shows whether the frame is intact. With the layout from this lesson, a stack dump answers the question.

Teams that port FreeRTOS to a new core test the handler with a two-task program like the one above before they trust it. Code review of a port checks the split of saved registers, the priority of the switch exception, and the EXC_RETURN values. The interview drill below walks through the steps in order.

Summary

  • A task is its registers and its stack. A context switch saves one set and restores another.
  • The hardware stacks R0 to R3, R12, LR, PC and xPSR on exception entry. The kernel saves R4 to R11, because only a switch needs to preserve them for a task that is leaving.
  • Tasks run on the PSP and handlers on the MSP. The switch saves the stack top of the leaving task and loads the stack top of the arriving one.
  • The saved block sits 32 bytes below the hardware frame, so the PSP stored for a task points at the block, and the restore adds 32 to reach the frame.
  • EXC_RETURN chooses the stack for the return: 0xFFFFFFFD for thread mode on the PSP, 0xFFFFFFF9 for the MSP.
  • In the FreeRTOS port the switch is xPortPendSVHandler, a naked function at PendSV's lowest priority, which calls vTaskSwitchContext() to choose the next task.

"What happens in a context switch on a Cortex-M3 with FreeRTOS, step by step?" Answer out loud in 90 seconds, then compare.

Model answer

The tick handler decides a switch is needed and pends PendSV. When no higher-priority interrupt is active, PendSV runs: the running task's PSP is read, R4 to R11 are pushed below the hardware frame that the core stacked on entry, and the new top of stack is stored in the task's control block. vTaskSwitchContext picks the highest-priority ready task and updates pxCurrentTCB. The handler loads the new task's stack top, pops its R4 to R11, writes PSP, and returns with an EXC_RETURN value that pops the hardware frame. The task resumes at the PC it saved. A good answer also says which registers are which: the core saves R0 to R3, R12, LR, PC and xPSR, and the kernel saves R4 to R11, and it says why PendSV is the lowest priority.
