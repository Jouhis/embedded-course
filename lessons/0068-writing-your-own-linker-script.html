Writing your own linker script and startup file

Lesson 42 read the vendor's startup file, and lesson 41 read the template's linker script. This lesson writes both, from scratch, in the smallest form that still boots an STM32F103. Then it swaps them into the build.

By the end of this lesson you can write a vector table as an array of function pointers, a reset handler that copies .data and clears .bss, and a linker script that places them, and you can replace the CMSIS startup in a CMake project.

The idea

Two files make the C language's rules true on a Cortex-M. The linker script decides where each piece of the program lives. The startup code, running first, makes the RAM match what the script promised. The vendor's startup and the course's linker script do this for you. Writing your own shows what each line is for.

Part 1: the vector table

On reset, the core reads word 0 of flash as the initial stack pointer, and word 1 as the address of the first code to run. Each later word is the handler for one exception, in the order PM0056 lists them. In C, a table of function pointers does the same job, and lesson 49's callbacks are the same mechanism. PM0056, Cortex-M3 programming manual (exception vector table) 

/* startup.c: the table lives in a section that the linker script places first in flash */
__attribute__((used, section(".isr_vector")))
const isr_fn g_vectors[16] = {
    (isr_fn)(uintptr_t)&_estack,   /* 0: initial stack pointer, a data address */
    Reset_Handler,                 /* 1: first code to run */
    NMI_Handler,                   /* 2 */
    /* ... HardFault, MemManage, BusFault, UsageFault ... */
    SysTick_Handler                /* 15 */
};

Word 0 is the stack pointer, which is a data address, so it needs a cast to the function pointer type. A cast like that is correct here, because the core only reads the word as a number. The used attribute stops the compiler from dropping a table that nothing in C refers to, and the section name puts it where the script expects it.

Every handler you do not write is a weak alias for Default_Handler. A weak symbol is a default definition that a strong one replaces at link time, so a later file can define SysTick_Handler without touching this one. The table has 16 entries here. The external interrupts (IRQ0 onwards) start at index 16, and the CMSIS startup lists all 43 of them for the STM32F103xB. This table is safe only while no external interrupt is enabled.

Part 2: the reset handler

Lesson 42 listed four steps. Here they are in C. The loops use the symbols from the linker script, and only the addresses matter, so the declarations are extern uint32_t with no value. 

void Reset_Handler(void) {
    SystemInit();                                  /* 1. clock first */

    uint32_t *src = &_sidata;                       /* 2. copy .data: flash to RAM */
    for (uint32_t *dst = &_sdata; dst < &_edata; dst++) {
        *dst = *src++;
    }

    for (uint32_t *p = &_sbss; p < &_ebss; p++) {      /* 3. zero .bss */
        *p = 0U;
    }

    main();                                        /* 4. hand over */
    while (1) { }
}
Both loops move one 32-bit word at a time. The linker script aligns the start and end symbols of .data and .bss to 4 bytes, so each loop begins and ends on a word boundary. If a symbol were misaligned, the loop would stop short or copy past the end of the section.

Part 3: the linker script

The script has three jobs. It describes the memory, it assigns each section to a region, and it exports symbols that the startup code uses. Lesson 41 introduced these terms. The key point for .data is the difference between the load address (AT> FLASH, where the initial bytes are stored) and the run address (> RAM, where the program reads them). 

MEMORY {
  FLASH (rx)  : ORIGIN = 0x08000000, LENGTH = 64K
  RAM   (rwx) : ORIGIN = 0x20000000, LENGTH = 20K
}
_estack = ORIGIN(RAM) + LENGTH(RAM);       /* the stack starts at the top of RAM */

SECTIONS {
  .isr_vector : { . = ALIGN(4); KEEP(*(.isr_vector)) } > FLASH
  .text       : { . = ALIGN(4); *(.text*) *(.rodata*) } > FLASH

  _sidata = LOADADDR(.data);               /* where the initial values are in flash */
  .data : {
    _sdata = .;   *(.data*)   _edata = .;  /* where the program runs it, in RAM */
  } > RAM AT> FLASH

  .bss : {
    _sbss = .;    *(.bss*) *(COMMON)  _ebss = .;
  } > RAM
}

KEEP stops the linker from discarding the vector table, which nothing references by name. LOADADDR(.data) reads the flash address that the linker chose for the initial values, and the startup code copies from that address. .bss has no AT>, because zeroed variables store nothing in flash.

In this build of the solution, the linker put .isr_vector at 0x08000000 with a size of 0x40 bytes, the variable g_initialised at 0x20000000 with its load address at 0x080002B4, and g_zeroed at 0x20000008. Your addresses may differ slightly, but the pattern is the same. Find yours in build/blink.map.

This script reserves no heap and no stack. The course's own stm32f103c8.ld reserves a minimum of 0x200 bytes of heap and 0x400 bytes of stack at the top of RAM. Without that reserve, a deep call chain can grow the stack down into .bss, and nothing reports it. Lesson 78 covers stack sizing and detection.

Part 4: swap them into the build

stm32f1.cmake sets two things for you, and you need to replace both. Its STM32_STARTUP list names the CMSIS startup file, and its add_link_options() call passes -T with the course's linker script. A project replaces the first by setting the variable, and the second by clearing the directory's link options and adding its own. The solution's CMakeLists.txt does both. 

set(STM32_STARTUP
  ${CMAKE_CURRENT_SOURCE_DIR}/startup.c
  ${TP}/cmsis-device-f1/Source/Templates/system_stm32f1xx.c
  ${CMAKE_CURRENT_SOURCE_DIR}/../../../templates/common/syscalls.c)

set_property(DIRECTORY PROPERTY LINK_OPTIONS "")
add_link_options(${MCU_FLAGS} -T${CMAKE_CURRENT_SOURCE_DIR}/minimal.ld
                 -Wl,--gc-sections -Wl,-Map=${PROJECT_NAME}.map
                 --specs=nano.specs --specs=nosys.specs)

Two details matter. We keep the CMSIS system_stm32f1xx.c, because SystemInit() and SystemCoreClock are there, and the baud rate depends on that clock. And we add syscalls.c. Without it the nano C library's _write, _read and _close stubs are missing, and the linker prints warnings that they "will always fail". The stubs are not needed by this program, but the library refers to them. Clearing a directory's link options is a blunt tool. It works here because this project wants a different set of link flags from the template. A cleaner design is a variable for the linker script in the shared file, which Part 6 can refactor.

  1. Open projects/0068-own-startup-linker/starter in VS Code, build with Ctrl+Shift+B, and start the simulator with F1 → Wokwi: Start Simulator. The monitor prints the two values and OWN STARTUP FAIL.
  2. Your task. Step 1: write the copy loop from _sidata to _sdata, up to _edata, in startup.c. Step 2: write the clear loop from _sbss to _ebss. Step 3: add the .bss section to minimal.ld, with _sbss and _ebss around its contents. The starter script does not have this section, so step 2 cannot link until step 3 is done.

Hint for the copy loop

The source pointer src already points at _sidata. The destination runs from &_sdata up to, not including, &_edata. Copy one word per step, and advance both pointers.

Hint for the linker script

Copy the pattern of the .data block. A .bss block has _sbss = .; at its start and _ebss = .; at its end, and it uses > RAM with no AT> part.

You wrote a vector table, a reset handler and a linker script, swapped them into the build in place of the vendor's startup, and watched a program check that its initialised and zeroed globals really started right.

"What does a minimal Cortex-M linker script have to define, and what does the startup code need from it?" Answer out loud in 60 seconds, then compare.

Model answer

It needs the memory regions with their origins and lengths, an entry symbol, a vector table section placed first in flash, and the code and constants in flash. For initialised data it needs a RAM run address and a flash load address, and symbols for the start and end of both .data and .bss. It should also set the initial stack pointer to the top of RAM. The startup code uses those symbols to copy .data and clear .bss before main runs. A production script also reserves heap and stack space, so overflow is caught, and this one does not.
