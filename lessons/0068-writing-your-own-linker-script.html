Writing your own linker script and startup file

Lesson 42 read the vendor's startup file, and lesson 41 read the template's linker script. This lesson writes both, from scratch, in the smallest form that still boots an STM32F103. Then it swaps them into the build.

By the end of this lesson you can write a vector table as an array of function pointers, a reset handler that copies .data and clears .bss, and a linker script that places them, and you can replace the CMSIS startup in a CMake project.

Where we are and why it matters

Lesson 41 introduced the linker and its script, and lesson 42 showed that the startup file has a vector table and a reset handler. Lesson 66 used the vendor's startup and the course's linker script without changing either. The C language promises that a global variable starts with the value you wrote in its declaration, and that a global with no value starts at zero. Something has to make that true before main runs, and this lesson shows the two files that do it.

The reason to learn this, rather than just using the vendor's file, is debugging and porting. A bootloader that hands over to an application, a board with external RAM, and a firmware that must fit a tight memory budget all need a startup or a linker script that differs from the vendor's.

Concepts, one at a time

Reset and the vector table

A reset is the event that starts the core from its beginning: power-on, the reset pin, or a watchdog. On a Cortex-M, the core does not read a boot address from a register. It reads two words from the start of flash. Word 0 is the initial value for the stack pointer, and word 1 is the address of the first code to run, the reset handler. Those two words sit at the start of the vector table, a list of handler addresses, one per exception. The rest of the table holds the other exceptions in the order the programming manual lists them (PM0056 Rev 7, section 2.3.4 and Table 16). With BOOT0 low, the boot space is main flash, and the CPU fetches the top-of-stack value from address 0x00000000 and starts code at 0x00000004 (RM0008 Rev 21, section 3.4 and Table 9). PM0056 Rev 7, section 2.3.4, Cortex-M3 programming manual (exception vector table)

Sections: where the compiler puts things

The compiler does not place variables in memory. It groups them into sections, and each section is a named block of bytes with a size and a kind. Code goes in .text, constants in .rodata, initialised globals in .data, and zero-initialised globals in .bss. The linker script assigns each section to a memory region, such as flash or RAM. Section names are conventions, and the script decides where each one goes.

Load address and run address

A global like volatile uint32_t g_initialised = 0xCAFEF00D; has two addresses. Its load address is where its initial value is stored, in flash, so the value survives power-off. Its run address is where the program reads and writes it, in RAM, because flash is slow to write and cannot be changed as a variable. The startup code copies the value from the load address to the run address before main runs. A .bss variable has no load address in flash, because its value is always zero, so the startup clears its run address instead.

Symbols: names the linker gives to addresses

A linker symbol is a name for an address. The linker script defines symbols such as _sdata, the start of .data in RAM, and the startup code refers to them with extern. The startup never uses their values, only their addresses. Writing &_sdata gives the address the linker chose, which is how the two files agree on where things are without sharing a header that lists addresses.

Part 1: the vector table

On reset, the core reads word 0 of flash as the initial stack pointer, and word 1 as the address of the first code to run. Each later word is the handler for one exception, in the order PM0056 lists them (section 2.3.4 and Table 16). In C, a table of function pointers does the same job, and lesson 49's callbacks are the same mechanism. 

/* startup.c: the table lives in a section that the linker script places first in flash */
__attribute__((used, section(".isr_vector")))
const isr_fn g_vectors[16] = {
    (isr_fn)(uintptr_t)&_estack,   /* 0: initial stack pointer, a data address */
    Reset_Handler,                 /* 1: first code to run */
    NMI_Handler,                   /* 2 */
    /* ... HardFault, MemManage, BusFault, UsageFault ... */
    SysTick_Handler                /* 15 */
};

Line by line: __attribute__((used, section(".isr_vector"))) does two things. section puts the array in a section with that name, which the linker script then places at the start of flash. used tells the compiler to keep the array even though nothing in the C code reads it. The line const isr_fn g_vectors[16] declares an array of 16 function pointers. Each entry is four bytes on this 32-bit core, so the table is 64 bytes. The first entry is cast from an address in RAM to a function pointer type, because the core reads that word as a number, not as code. The cast is correct here, because the core never calls this entry.

Entries 7 to 10 and 13 are reserved and must be zero, as the lesson's project comments say. Every handler you do not write is a weak alias for Default_Handler. A weak symbol is a default definition that a strong one replaces at link time, so a later file can define SysTick_Handler without touching this one. The table has 16 entries here. The external interrupts (IRQ0 onwards) start at index 16. The vendor's startup_stm32f103xb.s lists 43 of them, IRQ0 through IRQ42, and this minimal table stops at index 15. That is safe only while no external interrupt is enabled, because an enabled interrupt would jump past the end of the table.

Part 2: the reset handler

Lesson 42 listed four steps. Here they are in C. The loops use the symbols from the linker script, and only the addresses matter, so the declarations are extern uint32_t with no value. 

void Reset_Handler(void) {
    SystemInit();                                  /* 1. clock first */

    uint32_t *src = &_sidata;                       /* 2. copy .data: flash to RAM */
    for (uint32_t *dst = &_sdata; dst < &_edata; dst++) {
        *dst = *src++;
    }

    for (uint32_t *p = &_sbss; p < &_ebss; p++) {      /* 3. zero .bss */
        *p = 0U;
    }

    main();                                        /* 4. hand over */
    while (1) { }
}

Line by line: SystemInit() is the vendor function that sets the clock. It runs first, so the copy and clear loops run at the final clock speed. src starts at the load address in flash. The for loop starts dst at the run address in RAM and stops at _edata, which is the end of .data, so it copies exactly the bytes in that section. *dst = *src++ copies one 32-bit word and advances the source pointer. The third block clears .bss the same way, with zero as the value. Finally main() is called. The trailing loop is a safety net, because main should never return on firmware.

Both loops move one 32-bit word at a time. The linker script aligns the start and end symbols of .data and .bss to 4 bytes, so each loop begins and ends on a word boundary. If a symbol were misaligned, the loop would stop short or copy past the end of the section.

The vendor's startup does one more thing that this minimal version skips: it calls __libc_init_array before main, which runs the C library's constructors. This project has no C++ constructors and no global objects that need one, so skipping it is safe here. A project that uses a library with constructors needs that call.

Worked example: the .data copy, with real addresses

The solution's build writes a map file, build/blink.map, that lists where each section and variable ended up. Its .data section looks like this, with the numbers copied from the build:

Trace the copy loop. src is 0x080002B4, and the loop's first pass copies the word there, 0xCAFEF00D, into dst at 0x20000000. Then src advances by four to 0x080002B8, and dst advances to 0x20000004. The second pass copies 0x007A1200, which is the default clock value, into SystemCoreClock. Now dst equals _edata at 0x20000008, and the loop stops. Two words were copied, and eight bytes of flash were used for the initial values.

The same map file shows that g_zeroed sits at 0x20000008, which is the first address after .data, and that _ebss is at 0x2000000C. The clear loop writes zero to the four bytes in between. Lesson 70 uses SystemCoreClock to compute the baud rate, which is why the clock must be copied correctly before main reads it.

Part 3: the linker script

The script has three jobs. It describes the memory, it assigns each section to a region, and it exports symbols that the startup code uses. The key point for .data is the difference between the load address (AT> FLASH, where the initial bytes are stored) and the run address (> RAM, where the program reads them). 

MEMORY {
  FLASH (rx)  : ORIGIN = 0x08000000, LENGTH = 64K
  RAM   (rwx) : ORIGIN = 0x20000000, LENGTH = 20K
}
_estack = ORIGIN(RAM) + LENGTH(RAM);       /* the stack starts at the top of RAM */

SECTIONS {
  .isr_vector : { . = ALIGN(4); KEEP(*(.isr_vector)) } > FLASH
  .text       : { . = ALIGN(4); *(.text*) *(.rodata*) } > FLASH

  _sidata = LOADADDR(.data);               /* where the initial values are in flash */
  .data : {
    _sdata = .;   *(.data*)   _edata = .;  /* where the program runs it, in RAM */
  } > RAM AT> FLASH

  .bss : {
    _sbss = .;    *(.bss*) *(COMMON)  _ebss = .;
  } > RAM
}

Line by line. MEMORY names the two regions and gives their start and size. The Blue Pill's flash is 64 KB and its RAM is 20 KB, as the part page says. _estack is set to the end of RAM, so the stack starts at the top and grows down. .isr_vector is placed first, at the start of flash, and KEEP stops the linker from discarding the table, which nothing references by name. .text follows, with code and constants in flash. LOADADDR(.data) reads the flash address that the linker chose for the initial values, and the startup code copies from that address. In the .data block, > RAM sets the run address and AT> FLASH sets the load address. .bss has no AT>, because zeroed variables store nothing in flash.

This script reserves no heap and no stack. The course's own stm32f103c8.ld reserves a minimum of 0x200 bytes of heap and 0x400 bytes of stack at the top of RAM. Without that reserve, a deep call chain can grow the stack down into .bss, and nothing reports it. Lesson 78 covers stack sizing and detection.

Part 4: swap them into the build

stm32f1.cmake sets two things for you, and you need to replace both. Its STM32_STARTUP list names the vendor startup file, and its add_link_options() call passes -T with the course's linker script. A project replaces the first by setting the variable, and the second by clearing the directory's link options and adding its own. The solution's CMakeLists.txt does both. 

set(STM32_STARTUP
  ${CMAKE_CURRENT_SOURCE_DIR}/startup.c
  ${TP}/cmsis-device-f1/Source/Templates/system_stm32f1xx.c
  ${CMAKE_CURRENT_SOURCE_DIR}/../../../templates/common/syscalls.c)

set_property(DIRECTORY PROPERTY LINK_OPTIONS "")
add_link_options(${MCU_FLAGS} -T${CMAKE_CURRENT_SOURCE_DIR}/minimal.ld
                 -Wl,--gc-sections -Wl,-Map=${PROJECT_NAME}.map
                 --specs=nano.specs --specs=nosys.specs -Wl,--no-warn-rwx-segments)

Line by line: the set replaces the vendor startup with our startup.c, keeps the vendor's system_stm32f1xx.c, and adds syscalls.c. set_property clears the link options that stm32f1.cmake added for this directory. add_link_options then adds the flags back, with our script after -T. --gc-sections drops unused code, -Map writes the map file we just read, and the --specs flags choose the small C library and its system-call stubs. --no-warn-rwx-segments silences a warning about a memory region that is readable, writable and executable.

Two details matter. We keep the CMSIS system_stm32f1xx.c, because SystemInit() and SystemCoreClock are there, and the baud rate depends on that clock. And we add syscalls.c. Without it, the linker prints warnings: _write is not implemented and will always fail, and the same for _read, _close and _lseek. The project does not call those functions, but the small C library refers to them, so the linker warns. We checked this by linking the solution's objects by hand with and without syscalls.c. Clearing a directory's link options is a blunt tool. It works here because this project wants a different set of link flags from the template. A cleaner design is a variable for the linker script in the shared file, which Part 6 can refactor.

Hint for the copy loop

The source pointer src already points at _sidata. The destination runs from &_sdata up to, not including, &_edata. Copy one word per step, and advance both pointers.

Hint for the linker script

Copy the pattern of the .data block. A .bss block has _sbss = .; at its start and _ebss = .; at its end, and it uses > RAM with no AT> part.

Common mistakes and how to spot them

Mistake 1: the copy loop goes the wrong way

The copy loop has its source and destination swapped, so it copies RAM back into flash. In the simulator the monitor shows g_initialised = 0x00000000 and OWN STARTUP FAIL, because RAM started at zero. The fix is to check which pointer starts at the load address: src starts at _sidata and only ever reads, and dst starts at _sdata and only ever writes. Tracing the first iteration by hand, with the addresses from the map file, catches it in a minute.

Mistake 2: the clear loop is missing and the test still passes

The .bss clear is skipped, and the monitor still prints OWN STARTUP OK. That is because the simulator starts RAM at zero, so an uncleared variable is already zero. The check is only meaningful on real hardware, where RAM holds old values after a reset. The fix is to test on a board, or to write a value into the .bss variable before the reset and check it again. Treat a passing simulator test as weaker evidence for .bss than for .data.

Mistake 3: the linker reports "multiple definition of Reset_Handler"

The build fails with that message, because both the vendor's startup_stm32f103xb.s and your startup.c define Reset_Handler. The cause is a CMake list that still contains the vendor file. The fix is to set STM32_STARTUP to your list, as the solution does, so the vendor file is not compiled. The symptom appears at link time, not in the simulator, so read the build output first.

Mistake 4: the program runs but nothing prints, after a changed linker script

The build succeeds, but the simulator shows nothing, or the program resets over and over. The likely cause is that .isr_vector is not first in flash. If the vector table is not at 0x08000000, the core reads the wrong words at reset. Check the map file: .isr_vector should start at 0x08000000. The fix is to keep the .isr_vector block at the top of the SECTIONS list, with KEEP.

In real projects

Most product firmware uses the vendor's startup file and a linker script that the vendor or the team generates, and few engineers write one from scratch. Custom startup code appears when a project boots from a bootloader in one part of flash and jumps to the application in another, or when the memory map has external RAM that the startup must initialise. In those cases, a reviewer checks three things: that the vector table address matches the bootloader's jump, that the copy and clear loops cover exactly the sections the script defines, and that the stack reserve is large enough for the deepest call chain.

The map file is the main tool. An experienced engineer reads it after every link to check the sizes and addresses of .text, .data and .bss, and confirms that nothing moved unexpectedly. A map file tells you where every symbol is, and how big each section is.

Summary

  • On reset the core reads word 0 of the vector table as the initial stack pointer and word 1 as the reset handler (PM0056 Rev 7, section 2.3.4).
  • Each initialised global has a load address in flash, where its value is stored, and a run address in RAM, where the program uses it.
  • The reset handler copies .data from its load address to its run address, clears .bss, and calls main.
  • The linker script defines the memory regions, places the sections in them, and exports the symbols the startup uses.
  • KEEP stops the linker from discarding the vector table, and LOADADDR gives the flash address of .data.
  • The map file lists where every section and symbol ended up. Read it after each link.
  • The minimal script has no heap or stack reserve, so a deep call chain can corrupt .bss without warning.
