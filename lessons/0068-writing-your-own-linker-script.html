Writing your own linker script and startup file

A minimal vector table, reset handler and memory layout

By the end of this lesson you can write a vector table as an array of function pointers, a reset handler that copies .data and clears .bss, and a linker script that places them, and you can replace the CMSIS startup in a CMake project.

The code that runs before main

Lesson 41 introduced the linker and its script, lesson 42 showed that the startup file holds a vector table and a reset handler, and lesson 66 used the vendor's startup and the course's linker script without changing either. The C language promises that a global variable starts with the value written in its declaration and that a global without one starts at zero, and something has to make that true before main runs, so this lesson writes both files in the smallest form that still boots an STM32F103 and swaps them into the build.

The reason to learn this rather than simply using the vendor's file is debugging and porting, because a bootloader handing over to an application, a board with external RAM and firmware that must fit a tight memory budget all need a startup or a linker script that differs from the vendor's.

Reset and the vector table

A reset is the event that starts the core from the beginning, power-on, the reset pin or a watchdog. A Cortex-M core does not read a boot address from a register but two words from the start of flash, word 0 being the initial value of the stack pointer and word 1 the address of the first code to run, the reset handler. These two words open the vector table, a list of handler addresses, one per exception, whose remaining entries hold the other exceptions in the order the programming manual lists them (PM0056 Rev 7, section 2.3.4 and Table 16). With BOOT0 low the boot space is main flash, so the CPU fetches the top-of-stack value from address 0x00000000 and starts code from the address at 0x00000004 (RM0008 Rev 21, section 3.4 and Table 9) (PM0056 Rev 7, section 2.3.4, Cortex-M3 programming manual (exception vector table)).

Sections and memory regions

The compiler does not place variables in memory but groups them into sections, each a named block of bytes with a size and a kind, code going in .text, constants in .rodata, initialised globals in .data and zero-initialised globals in .bss. The linker script assigns each section to a memory region, such as flash or RAM, so section names are conventions and the script decides where each one goes.

Load addresses and run addresses

A global such as volatile uint32_t g_initialised = 0xCAFEF00D; has two addresses. Its load address is where its initial value is stored, in flash, so that the value survives power-off, and its run address is where the program reads and writes it, in RAM, because flash is slow to write and cannot serve as a variable. The startup code copies the value from the load address to the run address before main runs, while a .bss variable has no load address, its value always being zero, so the startup clears its run address instead.

Linker symbols

A linker symbol is a name for an address. The linker script defines symbols such as _sdata, the start of .data in RAM, which the startup code declares with extern and uses only for their addresses, never their values, so &_sdata gives the address the linker chose. That is how the two files agree on where things are without sharing a header that lists addresses.

The vector table in C

On reset the core reads word 0 of flash as the initial stack pointer and word 1 as the address of the first code to run, each later word being the handler of one exception in the order PM0056 lists them (section 2.3.4 and Table 16). In C a table of function pointers does the same job, the mechanism behind the callbacks of lesson 49. 

/* startup.c: the table lives in a section that the linker script places first in flash */
__attribute__((used, section(".isr_vector")))
const isr_fn g_vectors[16] = {
    (isr_fn)(uintptr_t)&_estack,   /* 0: initial stack pointer, a data address */
    Reset_Handler,                 /* 1: first code to run */
    NMI_Handler,                   /* 2 */
    /* ... HardFault, MemManage, BusFault, UsageFault ... */
    SysTick_Handler                /* 15 */
};

__attribute__((used, section(".isr_vector"))) does two things, section placing the array in a section of that name, which the linker script puts at the start of flash, and used telling the compiler to keep the array although nothing in the C code reads it. const isr_fn g_vectors[16] declares an array of 16 function pointers of four bytes each on this 32-bit core, so the table is 64 bytes, and its first entry is an address in RAM cast to a function pointer type, because the core reads that word as a number rather than code, a cast that is safe since the core never calls the entry.

Entries 7 to 10 and 13 are reserved and must be zero, as the project's comments say, and every handler not written is a weak alias for Default_Handler, a weak symbol being a default definition that a strong one replaces at link time, so a later file can define SysTick_Handler without touching this one. The external interrupts, IRQ0 onwards, start at index 16, the vendor's startup_stm32f103xb.s listing 43 of them, IRQ0 through IRQ42, while this minimal table stops at index 15, which is safe only while no external interrupt is enabled, because an enabled one would jump past the end of the table.

The reset handler in C

Lesson 42 listed four steps, written here in C, with loops that use the linker script's symbols, declared as extern uint32_t without a value, since only their addresses matter. 

void Reset_Handler(void) {
    SystemInit();                                  /* 1. clock first */

    uint32_t *src = &_sidata;                       /* 2. copy .data: flash to RAM */
    for (uint32_t *dst = &_sdata; dst < &_edata; dst++) {
        *dst = *src++;
    }

    for (uint32_t *p = &_sbss; p < &_ebss; p++) {      /* 3. zero .bss */
        *p = 0U;
    }

    main();                                        /* 4. hand over */
    while (1) { }
}

SystemInit() is the vendor function that sets the clock, running first so that the copy and clear loops run at the final clock speed. src starts at the load address in flash, and the for loop starts dst at the run address in RAM and stops at _edata, the end of .data, so it copies exactly the bytes of that section, *dst = *src++ moving one 32-bit word and advancing the source pointer. The third block clears .bss the same way with zero as the value, main() is then called, and the trailing loop is a safety net, because main should never return in firmware.

Both loops move one 32-bit word at a time. The linker script aligns the start and end symbols of .data and .bss to 4 bytes, so each loop begins and ends on a word boundary. If a symbol were misaligned, the loop would stop short or copy past the end of the section.

The vendor's startup does one more thing that this minimal version skips, calling __libc_init_array before main to run the C library's constructors. This project has no C++ constructors and no global objects needing one, so skipping the call is safe here, whereas a project using a library with constructors needs it.

Worked example: the .data copy with real addresses

The solution's build writes a map file, build/blink.map, listing where each section and variable ended up, and its .data section looks as follows, with the numbers copied from the build. Before tracing the loop, predict how many words it copies.

  1. First pass. src is 0x080002B4, so the loop copies the word there, 0xCAFEF00D, into dst at 0x20000000, after which src advances by four to 0x080002B8 and dst to 0x20000004.
  2. Second pass. The loop copies 0x007A1200, the default clock value of 8 000 000, into SystemCoreClock.
  3. Stop. dst now equals _edata at 0x20000008, so the loop ends after two words, eight bytes of flash having held the initial values.
  4. Clear .bss. The map file puts g_zeroed at 0x20000008, the first address after .data, and _ebss at 0x2000000C, so the clear loop writes zero to the four bytes in between.

Lesson 70 uses SystemCoreClock to compute the baud rate, which is why the clock value must be copied correctly before main reads it.

  1. After reset, SRAM holds whatever the power-up left there. The initial values of the globals exist only in flash, at the load address _sidata = 0x080002B4.
  2. The copy loop's first pass reads the word at src, 0xCAFEF00D, and writes it to dst = 0x20000000, the run address of g_initialised. Both pointers advance by four.
  3. The second pass copies 0x007A1200, which is 8,000,000, into SystemCoreClock at 0x20000004. dst is now 0x20000008, which equals _edata, so the loop stops: eight bytes copied.
  4. The clear loop then writes zero from _sbss = 0x20000008 up to _ebss = 0x2000000C, so g_zeroed starts at 0 as C promises.
  5. Only now does Reset_Handler call main. Code that reads SystemCoreClock, such as the baud-rate setup in lesson 70, sees 8,000,000 and not garbage.

The minimal linker script

The script has three jobs, describing the memory, assigning each section to a region and exporting the symbols the startup code uses, and for .data the key point is the difference between the load address (AT> FLASH, where the initial bytes are stored) and the run address (> RAM, where the program reads them). 

MEMORY {
  FLASH (rx)  : ORIGIN = 0x08000000, LENGTH = 64K
  RAM   (rwx) : ORIGIN = 0x20000000, LENGTH = 20K
}
_estack = ORIGIN(RAM) + LENGTH(RAM);       /* the stack starts at the top of RAM */

SECTIONS {
  .isr_vector : { . = ALIGN(4); KEEP(*(.isr_vector)) } > FLASH
  .text       : { . = ALIGN(4); *(.text*) *(.rodata*) } > FLASH

  _sidata = LOADADDR(.data);               /* where the initial values are in flash */
  .data : {
    _sdata = .;   *(.data*)   _edata = .;  /* where the program runs it, in RAM */
  } > RAM AT> FLASH

  .bss : {
    _sbss = .;    *(.bss*) *(COMMON)  _ebss = .;
  } > RAM
}

MEMORY names the two regions with their start and size, the Blue Pill's flash being 64 KB and its RAM 20 KB, as the part page says, and _estack is set to the end of RAM, so the stack starts at the top and grows down. .isr_vector comes first, at the start of flash, with KEEP stopping the linker from discarding the table, which nothing references by name, and .text follows with code and constants in flash. LOADADDR(.data) reads the flash address the linker chose for the initial values, from which the startup code copies, while in the .data block > RAM sets the run address and AT> FLASH the load address, and .bss has no AT>, because zeroed variables store nothing in flash.

This script reserves no heap and no stack. The course's own stm32f103c8.ld reserves a minimum of 0x200 bytes of heap and 0x400 bytes of stack at the top of RAM. Without that reserve, a deep call chain can grow the stack down into .bss, and nothing reports it. Lesson 78 covers stack sizing and detection.

Replacing the vendor startup in CMake

stm32f1.cmake sets two things that both need replacing, its STM32_STARTUP list naming the vendor startup file and its add_link_options() call passing -T with the course's linker script. A project replaces the first by setting the variable and the second by clearing the directory's link options and adding its own, and the solution's CMakeLists.txt does both. 

set(STM32_STARTUP
  ${CMAKE_CURRENT_SOURCE_DIR}/startup.c
  ${TP}/cmsis-device-f1/Source/Templates/system_stm32f1xx.c
  ${CMAKE_CURRENT_SOURCE_DIR}/../../../templates/common/syscalls.c)

set_property(DIRECTORY PROPERTY LINK_OPTIONS "")
add_link_options(${MCU_FLAGS} -T${CMAKE_CURRENT_SOURCE_DIR}/minimal.ld
                 -Wl,--gc-sections -Wl,-Map=${PROJECT_NAME}.map
                 --specs=nano.specs --specs=nosys.specs -Wl,--no-warn-rwx-segments)

The set replaces the vendor startup with our startup.c, keeps the vendor's system_stm32f1xx.c and adds syscalls.c, and set_property clears the link options that stm32f1.cmake added for this directory, after which add_link_options adds the flags back with our script after -T. --gc-sections drops unused code, -Map writes the map file read above, the --specs flags choose the small C library and its system-call stubs, and --no-warn-rwx-segments silences a warning about a memory region that is readable, writable and executable.

Two details matter. The CMSIS system_stm32f1xx.c stays, because SystemInit() and SystemCoreClock live there and the baud rate depends on that clock, and syscalls.c is added, because without it the linker warns that _write is not implemented and will always fail, and the same for _read, _close and _lseek, functions the project never calls but the small C library refers to. We checked this by linking the solution's objects by hand with and without syscalls.c. Clearing a directory's link options is a blunt tool. It works here because this project wants a different set of link flags from the template. A cleaner design is a variable for the linker script in the shared file, which Part 6 can refactor.

Hint for the copy loop

The source pointer src already points at _sidata, and the destination runs from &_sdata up to, but not including, &_edata, so copy one word per step and advance both pointers.

Hint for the linker script

Follow the pattern of the .data block: a .bss block has _sbss = .; at its start and _ebss = .; at its end and uses > RAM without an AT> part.

Common mistakes and how to spot them

The copy loop running the wrong way

The monitor shows g_initialised = 0x00000000 and OWN STARTUP FAIL, because the copy loop has its source and destination swapped and copies RAM, which started at zero, back towards flash. Check which pointer starts at the load address, src starting at _sidata and only reading and dst starting at _sdata and only writing, and trace the first iteration by hand with the addresses from the map file, which catches the error in a minute.

A missing clear loop that still passes

The .bss clear is skipped and the monitor still prints OWN STARTUP OK, because the simulator starts RAM at zero, so an uncleared variable is already zero, and the check means something only on real hardware, where RAM holds old values after a reset. Test on a board, or write a value into the .bss variable before a reset and check it afterwards, and treat a passing simulator test as weaker evidence for .bss than for .data.

Multiple definitions of Reset_Handler

The build fails with "multiple definition of Reset_Handler", because both the vendor's startup_stm32f103xb.s and the project's startup.c define it, the CMake list still containing the vendor file. Set STM32_STARTUP to the project's list, as the solution does, so that the vendor file is not compiled, and since the symptom appears at link time rather than in the simulator, read the build output first.

A silent program after a linker script change

The build succeeds but the simulator shows nothing, or the program resets over and over, most likely because .isr_vector is no longer first in flash, so the core reads the wrong words at reset. Check in the map file that .isr_vector starts at 0x08000000, and keep its block at the top of the SECTIONS list with KEEP.

Custom startup code and map files in products

Most product firmware uses the vendor's startup file and a linker script that the vendor or the team generates, and few engineers write one from scratch. Custom startup code appears when a project boots from a bootloader in one part of flash and jumps to an application in another, or when the memory map includes external RAM that the startup must initialise, and a reviewer then checks that the vector table address matches the bootloader's jump, that the copy and clear loops cover exactly the sections the script defines and that the stack reserve suffices for the deepest call chain.

The map file is the main tool, an experienced engineer reading it after every link to check the sizes and addresses of .text, .data and .bss and to confirm that nothing moved unexpectedly, since it records where every symbol is and how large each section has grown.

Summary

  • On reset the core reads word 0 of the vector table as the initial stack pointer and word 1 as the reset handler (PM0056 Rev 7, section 2.3.4).
  • Each initialised global has a load address in flash, where its value is stored, and a run address in RAM, where the program uses it.
  • The reset handler copies .data from its load address to its run address, clears .bss and calls main.
  • The linker script defines the memory regions, places the sections in them and exports the symbols the startup uses.
  • KEEP stops the linker from discarding the vector table, and LOADADDR gives the flash address of .data.
  • The map file lists where every section and symbol ended up and is worth reading after each link.
  • The minimal script has no heap or stack reserve, so a deep call chain can corrupt .bss without warning.
PM0056, STM32F10xxx Cortex-M3 programming manual: read section 2.3.2 (Exception types, with Table 16), section 2.3.4 (Vector table), and the reset sequence in RM0008 Rev 21, section 3.4 (Table 9).
