The Blue Pill clone warning

Cheap Blue Pills are often clones. One well-known clone, the CS32F103, is described as compatible with the STM32F103 but with inconsistent flash sizes in its datasheet, and some readers report debugging problems with it, in comments rather than tests (CNX Software on the CS32 Blue Pill clone). Before you trust a Blue Pill, read its flash size back with a test program, and check that the ST-LINK can debug it. A board that boots and blinks does not prove the part is genuine. Forum reports say the flash-size register and the real flash can disagree on some clones. Treat those as warnings to test, not as facts about every board.

The logic analyzer

The fx2lafw firmware turns FX2-based clones into logic analyzers, and it works with sigrok tools such as PulseView. The sigrok wiki lists the supported devices and channel counts, and says that all of them use a 24 MHz crystal (sigrok wiki: fx2lafw). Check the listing for the clone you buy, because the wiki is the source of truth for which chips it supports.

Moving a Wokwi project to a real board

The simulator hides three things that a real board does not: the programming step, the debugger, and the wiring. Here is how each one changes.

  1. Flash the Pico with UF2. Hold the BOOTSEL button while you plug the board into USB. The Pico then shows as a mass-storage drive, and you copy the .uf2 file onto it. The board then runs the new program. The Raspberry Pi docs describe BOOTSEL mode as ROM-based and the UF2 copy as the standard method (Raspberry Pi: Pico series).
  2. Flash with picotool, if you want the command line. picotool info shows what is on the board, and picotool load blink.uf2 loads a file (picotool on GitHub). Use the same file you built, not a copy from another project.
  3. Debug with the probe. Connect the Debug Probe's SWD lines to the Pico's SWD header. Then start OpenOCD with the CMSIS-DAP interface and the RP2040 target, connect GDB to port 3333, and reset the target (Raspberry Pi: Debug Probe). This is the same breakpoint and watchpoint work you did with the Wokwi GDB server in lesson 54.

For the STM32 boards, the on-board ST-LINK does the same job. Use the ST programming tools or OpenOCD with an ST-LINK configuration. This build did not check the exact commands for those tools, so read the board's user manual before you run them.

Communities

Hardware questions get better answers from people who have burned a board. These are the ones from the course's resource list, with the question each one answers best.

  • r/embedded: career questions, code critique, and "how is this done in industry".
  • Electronics Stack Exchange: a specific circuit or firmware question with a precise answer.
  • EEVblog forum: hardware and measurement questions.
  • The Interrupt community: firmware professionals, debugging and tooling. Its Slack is linked from the blog.
  • The Zephyr Project community: Zephyr questions, and contributing upstream, which is a strong portfolio signal.
  • Raspberry Pi forums: Pico section: RP2040 and Pico SDK specifics.
  • ST Community: STM32 peripheral and HAL quirks.
  • Embedded.fm podcast: interviews with embedded engineers, which show how the profession thinks.

Ask one question a week in one of these, and answer one when you can. Answering is the fastest way to find out what you do not yet know.

"You have a Wokwi blink working. How do you prove it runs on a real board?" Answer out loud in 60 seconds, then compare.

Model answer

I would build the same source for the real board, then flash the UF2 file with BOOTSEL, or use picotool. I would check the board's LED and its serial output against the simulator's log. If it fails, I would debug over SWD with the probe and GDB, and check the wiring and the pull-ups with the multimeter first. The simulator proves the logic; the board proves the wiring and the timing.
