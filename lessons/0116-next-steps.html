Where we are and why it matters

Almost every project in this course ran in Wokwi. The simulator is a digital model of the chip and its parts, and it runs the same compiled code that a real board runs. That is why it was useful for learning: it let you focus on the logic, the timers and the protocols without a soldering iron. Lessons 53, 54 and 60 all used it, and the capstone in lessons 110 to 113 ran there too.

The problem this lesson solves is the gap between the simulator and a board on your desk. A real board has things the model does not: wires with resistance and capacitance, a supply that can sag, a programmer that must find the chip, and a debugger that connects over a physical port. A project that works in the simulator can still fail on the bench for reasons the simulator never had. This lesson names those reasons and the first step for each, so that the first board you build is a success you can explain.

The Blue Pill clone warning

Cheap Blue Pills are often clones. One well-known clone, the CS32F103, is described as compatible with the STM32F103 but with inconsistent flash sizes in its datasheet, and some readers report debugging problems with it, in comments rather than tests (CNX Software on the CS32 Blue Pill clone). Before you trust a Blue Pill, read its flash size back with a test program, and check that the ST-LINK can debug it. A board that boots and blinks does not prove the part is genuine. Forum reports say the flash-size register and the real flash can disagree on some clones. Treat those as warnings to test, not as facts about every board.

The logic analyzer

The fx2lafw firmware turns FX2-based clones into logic analyzers, and it works with sigrok tools such as PulseView. The sigrok wiki lists the supported devices and channel counts, and says that all of them use a 24 MHz crystal (sigrok wiki: fx2lafw). Check the listing for the clone you buy, because the wiki is the source of truth for which chips it supports.

Moving a Wokwi project to a real board

The simulator hides three things that a real board does not: the programming step, the debugger, and the wiring. Here is how each one changes.

  1. Flash the Pico with UF2. Hold the BOOTSEL button while you plug the board into USB. The Pico then shows as a mass-storage drive, and you copy the .uf2 file onto it. The board then runs the new program. The Raspberry Pi docs describe BOOTSEL mode as ROM-based and the UF2 copy as the standard method (Raspberry Pi: Pico series).
  2. Flash with picotool, if you want the command line. picotool info shows what is on the board, and picotool load blink.uf2 loads a file (picotool on GitHub). Use the same file you built, not a copy from another project.
  3. Debug with the probe. Connect the Debug Probe's SWD lines to the Pico's SWD header. Then start OpenOCD with the CMSIS-DAP interface and the RP2040 target, connect GDB to port 3333, and reset the target (Raspberry Pi: Debug Probe). This is the same breakpoint and watchpoint work you did with the Wokwi GDB server in lesson 54.

For the STM32 boards, the on-board ST-LINK does the same job. Use the ST programming tools or OpenOCD with an ST-LINK configuration. This build did not check the exact commands for those tools, so read the board's user manual before you run them.

Four ideas the board makes real

The table above lists what the simulator hides. Four of those ideas carry most first-board problems, so each one is explained here from the physical side, one at a time.

Idea 1: a line is a wire with resistance and capacitance

In the simulator a wire is ideal: a signal changes instantly and reaches its full level. A real wire has a small capacitance to ground and other wires, and a driver must charge that capacitance through a resistor. The result is a slow edge, not a step. A common I2C arrangement has a pull-up resistor from the line to the supply, and a device that can only pull the line low (an open-drain output). When the device releases the line, the pull-up resistor lets it rise.

Work one example with round numbers. A 10 kΩ pull-up and 100 pF of bus capacitance have a time constant of R × C = 10 000 Ω × 100 × 10−12 F = 1 µs. The edge takes a few time constants to finish, so the time to rise is measured in microseconds. The I2C specification sets a maximum rise time for each speed mode, and the resistor is chosen so the edge fits inside it (UM10204 in RESOURCES.md). Make the resistor too large and the edge is too slow; make it too small and the device must sink too much current when it pulls the line low.

Idea 2: a supply is not a fixed number

The simulator's 3.3 V is exact. On a board the supply depends on the USB port, the cable, the regulator and the load. A sensor that draws a burst of current when it measures can pull the supply down for a moment, and a chip that sees a brownout may reset. The first check is the multimeter on the rails with nothing connected, and the second is the same measurement with the sensor powered. A reading that changes between the two is a supply problem, not a software problem.

Idea 3: a debugger connects to the chip over a few pins

When the simulator runs a debugger, it talks to the chip through a model of the debug port. On a board, the debug probe does the same over real wires. The Pico uses the Arm Serial Wire Debug (SWD) interface, which needs a clock line, a data line and ground. The Raspberry Pi docs name SWCLK, SWDIO and GND for the non-H Pico, and the probe's own UART lines carry the target's serial output back to your computer (Raspberry Pi: Debug Probe, in RESOURCES.md). The probe's ground must be the same as the target's ground, and the docs warn to connect ground first or to remove power from the target.

Idea 4: a logic analyzer samples, and sampling has a limit

A logic analyzer records the level of each channel at a fixed sample rate, then decodes the bits from those samples. The rate sets how finely you can see an edge. A 24 MHz analyzer takes 24 000 000 samples each second. At 100 kHz, one I2C bit lasts 10 µs, which is 240 samples, so the analyzer can show each bit clearly. A signal that changes faster than the sample rate allows cannot be recorded faithfully, so the trace can show a waveform that is not the real one. The fx2lafw firmware, described in the sigrok wiki link in the logic analyzer section above, is the open driver for the FX2 clones this lesson recommends.

Getting a board to show its first output

The first board should run the simplest program that you already know works in the simulator, such as a blink, and it should have only the parts it needs. Build the same source for the board, flash it with the method in the steps above, and then check the output against the simulator's log. If the LED does not blink, check the power and the pin first, then the flash. Only then add a sensor, one part at a time, so that a failure has one suspect.

Common mistakes and how to spot them

Most first-board failures are wiring or power faults, and each one has a symptom you can see before you guess at the code.

Mistake 1: a floating input

Symptom: a button press sometimes registers and sometimes does not, or it reports presses when nobody touches it. Cause: the input has no pull-up, so it floats between high and low while the switch is open (the floating input entry in the glossary). Fix: enable the internal pull-up in software, or add an external pull-up, then debounce the switch as lesson 52 shows.

Mistake 2: TX and RX not crossed

Symptom: the serial monitor is silent, or it shows garbage characters at the wrong speed. Cause: the adapter's RX was connected to the target's RX, so neither side hears the other. The probe's wiring is crossed on purpose: its RX goes to the target's TX, and its TX goes to the target's RX. Fix: cross the pairs, and check that both ends use the same baud rate.

Mistake 3: a probe and a board with different grounds

Symptom: the debugger cannot find the target, or the connection drops when a sensor is plugged in. Cause: the probe and the target do not share a ground, so the signal lines have no common reference. The Raspberry Pi docs warn about this and say to connect ground first or to remove power from the target. Fix: connect ground first, then the SWD lines, and power the target from one supply only.

Mistake 4: a 5 V line on a 3.3 V part

Symptom: the sensor is hot, reads nonsense, or stops responding after the first power-up, and the board may still blink. Cause: a 5 V supply reached a pin or a supply that is rated for 3.3 V, which the simulator never checks. Fix: measure every rail with the multimeter before you connect a part, and check the part's absolute maximum ratings in its datasheet before you connect it.

Mistake 5: flashing a file from another project

Symptom: the board runs a program that is not the one you just changed, and the serial text does not match the source. Cause: the UF2 file came from an older build or another project folder. Fix: build, then copy the .uf2 file from the build folder you just made, and check the board's output against the source.

In real projects

Teams that move a design from simulation to hardware write a bring-up checklist. It lists the rails to measure, the connections to check, and the first program to run, in the order a fault is most likely to show up. Reviewers ask to see that checklist and the measurements that were filled in on it. The checklist is also the evidence that the board was checked before the software was blamed.

The same idea scales up. A team tests its firmware on real boards in a rig that flashes, runs and checks the output automatically, which is called hardware-in-the-loop testing. The simulator plays a smaller version of that role in this course, and CI runs it on every commit (lesson 82). In an interview, the question "how do you know it works on the board?" is best answered with the checklist and one measurement, not with a claim that it works.

Summary

  • The simulator runs the same code, but it hides wiring, power, debugging and the programming step.
  • A line is a wire with resistance and capacitance. A pull-up sets the high level, and the time constant R × C sets how fast the edge rises.
  • SWD needs SWCLK, SWDIO and ground on a non-H Pico. The probe's ground must be shared with the target before any signal is connected.
  • Serial is crossed: the probe's RX goes to the target's TX, and its TX to the target's RX.
  • Measure the rails with nothing connected, then again with the part connected. A difference points to the supply.
  • A logic analyzer records samples at a fixed rate. At 24 MHz, a 100 kHz I2C bit has 240 samples.
  • Bring up one part at a time, from the simplest program, and keep a checklist of the measurements.
