Capstone 2: drivers and unit tests for the dryer

A thermistor gives a number, and the number must become a temperature that the safety rules can trust. This lesson turns the ADC code into °C, drives the heater PWM, debounces the buttons, and tests every piece of pure logic on the PC before the firmware runs it.

By the end of this lesson you can convert a 12-bit NTC reading to °C with the Beta equation, detect an open or shorted sensor, check a timer's PWM arithmetic, and write host unit tests (Unity, with an FFF fake for the hardware) that the firmware and the tests share.

Where we are and why it matters

Lesson 110 wrote the requirements and the layers. This lesson fills the bottom layers and the pure logic above them. You will meet three kinds of code: a thermistor conversion, which is arithmetic on a number from an analogue pin; a set of safety checks, which is logic that must be right every time; and the drivers that connect those to the chip. The hardware ideas come from lessons you already know: the ADC from lesson 58, timers from lesson 71, button debouncing from lesson 52, and the I2C OLED from lesson 61.

Why does this matter for a real product? A temperature that is wrong by 30 degrees is worse than no reading, because the control loop and the safety rules trust it completely. Most firmware bugs that reach customers are not crashes. They are plausible numbers that are wrong. This lesson is about catching those with tests before the hardware ever sees them.

The idea: a driver turns hardware into numbers

A driver is the code that talks to one piece of hardware. Its output should be a plain value with a known meaning: an ADC code, a duty cycle, a stable button level. Everything after the driver, the state machine and the safety checks, works on those values and never on registers. That split is what makes the logic testable: a test passes a number in and checks the number that comes out (lesson 80).

This lesson builds five pieces. The NTC conversion is pure C. The heater PWM, the fan and the buttons are thin wrappers over registers in the board file. The display reuses the SSD1306 driver from Labs 3 to 5. The debounce is the lesson 80 module. The state machine and the safety checks are pure, and they get the most tests.

The file control.c holds an older and simpler idea, kept for comparison: bang-bang control. It switches the heater fully on below the setpoint minus a band, fully off above the setpoint plus the band, and keeps its last state inside the band. That deliberate dead band is hysteresis, and it stops the output from chattering on and off around the setpoint. Bang-bang is easy to test, but it overshoots, because the heater runs at full power until the chamber is already past the setpoint. Lesson 112 replaces it with a PID controller.

The NTC: from an ADC code to degrees Celsius

The sensor is a negative-temperature-coefficient thermistor, an NTC: its resistance falls as it warms. The circuit is a voltage divider. The series resistor sits between 3.3 V and the output pin, and the NTC sits between the output and ground. The ADC reads the output node, so a warm NTC pulls the node down and the code falls with it (lesson 58 builds this divider and reads it on the Pico).

Four ideas before the formula

A thermistor is a resistor whose resistance depends on its temperature. An NTC is a negative-temperature-coefficient thermistor: its resistance falls as it warms. The part used here has 10 kΩ at 25 °C, which is the usual reference point. A voltage divider is two resistors in series across a supply. The voltage at the junction is the supply times the lower resistor divided by the total resistance, so a change in either resistor moves the junction voltage. In this circuit the junction is the OUT pin, and the 10 kΩ series resistor sits between the 3.3 V supply and OUT.

The ADC measures the voltage on OUT and reports it as an integer code. A 12-bit ADC has 4096 codes, numbered 0 to 4095. Code 0 means 0 V, and code 4095 means full scale, which is the 3.3 V supply. The code is therefore the junction voltage as a fraction of full scale, times 4095. You know the code, the supply, the series resistor and the sensor's constant, and the conversion has to turn those into a resistance and then into a temperature.

The third idea is the beta constant, written B. It describes how steeply the NTC's resistance changes with temperature. The Beta equation says that the natural logarithm of the resistance ratio, divided by B, plus one over the reference temperature in kelvin, equals one over the measured temperature in kelvin. The 25 °C reference is 298.15 K, because kelvin is degrees Celsius plus 273.15. The equation is an approximation, and its error grows as you move away from the reference temperature. The beta value is printed in the thermistor's datasheet. The Wokwi part defaults to 3950.

The fourth idea is the failure modes. If the sensor is shorted, its resistance is near zero and the code is near zero. If it is open, its resistance is effectively infinite and the code is near full scale. Neither value is a temperature. The logarithm of a zero or negative ratio is undefined, so the conversion must refuse those codes rather than return a number.

The Wokwi docs give the conversion from an analogue reading to a temperature in one line of C, with the Beta equation and a 10-bit full-scale constant of 1023 Wokwi docs: NTC temperature sensor. The Blue Pill has a 12-bit ADC, so the constant becomes 4095. Nothing else changes: 

// full = 4095 (12-bit), raw = the ADC code, B = beta (3950), 298.15 K = 25 C
float inv_t = logf(1.0f / (full / (float)raw - 1.0f)) / 3950.0f + 1.0f / 298.15f;
float celsius = 1.0f / inv_t - 273.15f;

The first line is the divider in disguise. The divider gives Rntc ÷ Rseries = 1 ÷ (full ÷ raw − 1), so the log is of the resistance ratio, and the Beta equation turns that ratio into a temperature. The beta constant is a property of the thermistor, not of the code, so it goes in the datasheet for the real part.

Check the constant. If the code uses 1023 with a 12-bit ADC, the result is wrong in two ways. Above code 1023 the ratio becomes negative, the logarithm is undefined, and the function returns nan, which is not a number. Below 1023 it returns a number that looks plausible and is wrong: a code of 1000 gives −41 °C with the 1023 constant, against 52.8 °C with 4095. Lesson 58 made this same mistake on purpose. Write the full-scale constant as a named value, and test a known reading.

The conversion, line by line

Here is the conversion from app/ntc.c, with the constants named. Each step is one line of the formula, in order. 

if (raw < NTC_RAW_MIN || raw > NTC_RAW_MAX) {
    return false;                          /* open or shorted sensor */
}
float full = (float)NTC_FULL_SCALE_CODE;   /* 4095 */
float inv_t = logf(1.0f / (full / (float)raw - 1.0f)) / NTC_BETA + 1.0f / NTC_T25_KELVIN;
float celsius = 1.0f / inv_t - KELVIN_OFFSET;
*centi_c = (int32_t)lroundf(celsius * 100.0f);
return true;

The if rejects the fault codes: 15 or less, or 4080 or more. The function returns false, and the caller must check that before it uses the output. The next line stores the full scale as a float, so that the division below is a float division and not an integer one. The line with logf computes full ÷ raw − 1, which equals Rseries ÷ Rntc, and then takes the reciprocal, which gives Rntc ÷ Rseries. The logarithm of that ratio, divided by B, plus 1 ÷ 298.15, is 1 ÷ T in kelvin. Then the code inverts that to kelvin, subtracts 273.15 to get degrees Celsius, and stores hundredths of a degree, rounded with lroundf().

Now the same steps with a real code. Take 2048, about half scale. Step 1: 4095 ÷ 2048 = 1.99951, and minus 1 gives 0.99951. Step 2: the reciprocal is 1.00049, so Rntc is 10 004.9 Ω, very close to the 10 kΩ reference. Step 3: ln(1.00049) = 0.000488, and 0.000488 ÷ 3950 is about 1.24 × 10−7. Step 4: add 1 ÷ 298.15 = 0.00335402, which gives 0.00335414. Step 5: the inverse is 298.139 K, and 298.139 − 273.15 = 24.989 °C. The table below gives that as 24.99 °C. Every intermediate value can be checked on a calculator, and that habit is what catches a wrong constant.

Known values for the tests

A test needs an answer that does not come from the code under test. The values below come from an independent calculation of the same equation, in double precision. They are the numbers the host test checks.

The fault range matters as much as the conversion. A code near 0 means OUT is pulled to ground, which is an NTC that is shorted or a wire to GND. A code near 4095 means OUT is pulled up to 3.3 V through the series resistor, which is an open NTC. The logarithm is undefined at both ends, so the conversion must refuse those codes rather than return a number. The dryer's code returns false for them, and the caller treats the reading as a fault. A reading that is wrong by 30 degrees is more dangerous than no reading. The edge of the valid range deserves a look too. Code 16, the lowest valid code, converts to about 239 °C, which the over-temperature check catches. The fault limits exist so that the logarithm never fails. They say nothing about whether a temperature is plausible, and the safety checks in the next section do that job.

A pull-up or pull-down that the code does not know about changes which end is the NTC. The conversion above assumes the NTC is the lower resistor, as in the Wokwi part and in lesson 58. If you wire the NTC on top, the same code reads the wrong temperature. Check the schematic, not only the code.

The heater PWM: timer arithmetic

A switch that is only ever fully on or fully off cannot give a heater 70 % of its power, unless it is on for 70 % of the time. Pulse-width modulation (PWM) switches the power on and off at a fixed period, and the fraction of each period that the output is high is the duty cycle. A 70 % duty gives 70 % of the average power. The heater's temperature changes over tens of seconds, so a switching rate of 1 kHz is more than fast enough, and it stays above the audible range. Lesson 71 covers the timer blocks. A timer is a counter that counts clock ticks and compares itself with registers. The prescaler (PSC) divides the clock, the auto-reload value (ARR) sets the top of the count, and the compare register (CCR) sets where the output changes. The arithmetic is worth doing once by hand:

  • The timer clock is 8 MHz (the HSI, lesson 67). A prescaler of 7 divides it by 8, giving a counter clock of 1 MHz.
  • The auto-reload value of 999 counts 1000 steps, so the period is 1000 ÷ 1 MHz = 1 ms, which is 1 kHz.
  • In PWM mode 1, the output is high while the counter is below the compare value. A compare of 0 is always low, and a compare of 1000 is always high, because the counter never reaches 1000.

That last point is why the duty is given in permille, from 0 to 1000, and why the driver clamps at 1000. The same hardware gives the 0 % and 100 % endpoints without any special case.

One period, step by step

Take a duty of 250 permille, which is 25 %. The driver writes 250 to the compare register. Each period has 1000 counter steps, numbered 0 to 999, and each step is 1 µs because the counter clock is 1 MHz. For steps 0 to 249 the counter is below 250, so the output is high for 250 µs. For steps 250 to 999 the output is low for 750 µs. The period is 1 ms and the high time is 0.25 ms, so the duty is 0.25 ms ÷ 1 ms = 25 %. The endpoints need no special case: a compare value of 0 keeps the output low for every step, and 1000 keeps it high for every step, because the counter never reaches 1000. A number from 0 to 1000 written to the compare register is therefore already a duty in permille. That is why hal_heater_set_permille() clamps at 1000 and does nothing else.

The board file sets this up with a few register writes, shown here from hw/hal_bluepill.c: 

TIM3->PSC = PWM_PSC;                 /* 7: divide the 8 MHz clock by 8 */
TIM3->ARR = PWM_ARR;                 /* 999: the counter runs from 0 to 999 */
TIM3->CCMR1 = (6U << 4) | TIM_CCMR1_OC1PE;   /* OC1M = 110 (PWM mode 1), preload on */
TIM3->CCER = TIM_CCER_CC1E;          /* let channel 1 drive its output pin */
TIM3->CCR1 = 0U;                     /* start with the heater off */
TIM3->CR1 = TIM_CR1_ARPE;            /* buffer ARR until the next period */
TIM3->EGR = TIM_EGR_UG;              /* load the buffered values now */
TIM3->CR1 |= TIM_CR1_CEN;            /* start counting */

The first two lines are the arithmetic above: PSC gives the 1 MHz counter, and ARR gives the 1 kHz period. The third line selects the output mode. The OC1M field, shifted into place with << 4, holds 110, which is PWM mode 1, and the preload bit makes the compare value take effect at the start of the next period instead of in the middle of one. The fourth line connects channel 1 to its pin, and the fifth sets the heater to off. ARPE buffers the auto-reload value in the same way. The update event written to EGR copies the buffered values into the working registers at once. Only then does CEN start the counter. The order is the lesson: start the counter last, after the values are loaded.

The buttons: one press, one event

A mechanical button bounces for a few milliseconds, so a naive read sees several presses. The debounce module from lesson 80 is an integrator (lesson 52 explains the physics). It counts up while the raw level reads pressed and down while it reads released, and the output changes only when the count reaches 3 for pressed or 0 for released. The button driver then turns a change from released to pressed into one event, and holding the button adds nothing. The events go into a flag that the control task reads once.

Watching the integrator

Take the raw samples from the bounce test in test/test_drivers.c, one per 20 ms tick: 1, 0, 1, 0, 1, 0, which is a bouncing press. The count goes 1, 0, 1, 0, 1, 0. It never reaches 3, so the output stays released. Now a clean press with samples 1, 1, 1, 1. The count goes 1, 2, 3. On the third sample the output becomes pressed, which is one event. The fourth sample adds nothing, because the count saturates at 3. Holding the button for ten seconds still gives one event, because the event is raised on the change from released to pressed, not on the level. At one sample per 20 ms, three agreeing samples take 60 ms, which outlasts most bounces and still feels instant.

The display: the driver from Labs 3 to 5

The SSD1306 driver and its 5 × 7 font come from the Lab 5 code, unchanged except for one job: the font had no F, G, H, W, Y or percent sign, and the status screen needs them. Those glyphs were added in the same table, in the same format. The driver draws into a 1 KB framebuffer and sends it over I2C with a flush, which takes about 90 ms at 100 kHz. Lesson 112 explains why that matters for the schedule.

The text itself is built by ui_compose(), a pure function that fills four strings of 21 characters. The test checks the strings, because the learner reads those strings on the screen, and a wrong character is a visible bug.

Why a flush takes 90 ms

The OLED uses an SSD1306 controller that drives a 128 × 64 pixel panel over I2C (lesson 61). Sending each pixel change as its own I2C transaction would be slow and busy, so the driver keeps a framebuffer in RAM with one bit per pixel. The framebuffer is 128 × 64 ÷ 8 = 1024 bytes. Drawing changes only the framebuffer, which takes almost no time. A flush sends all 1024 bytes to the panel. On I2C, each byte takes nine bit times: eight data bits and one acknowledge bit from the receiver. At the 100 kHz standard-mode clock, 1024 × 9 ÷ 100 000 = 0.092 s, so the data alone takes about 92 ms. The command bytes that set the page and column add a few milliseconds, which is why the header comment says "about 90 ms". Lesson 112 has to schedule around that number.

Text is drawn with a 5 × 7 font. Each character is five columns of pixels plus one blank column, which is six pixels, and 128 ÷ 6 gives 21 characters per line. That is why ui_compose() fills four strings of up to 21 characters. The font stores one byte per column of eight pixels (lesson 61 explains how a column byte is built). The F, G, H, W and Y letters and the percent sign were added to the table for the status screen, in the same format as the others.

The safety checks: pure logic with a test per rule

safety_check() returns the first fault it finds, in a fixed order: sensor, over-temperature, stale sample, then the heater runaway. The runaway rule is Klipper's verify_heater idea (klipper3d.org Config_Reference, [verify_heater]): while the heater is at full power and far below the setpoint, the temperature must rise by 2 °C within the window, and a rise restarts the window. Klipper's defaults are a 2 °C gain and a window of 20 s for extruders, and 60 s for the heated bed; the dryer uses 60 s with the 2 °C gain. A chamber has more thermal mass than a nozzle, so the longer window is the honest number. The state machine in dryer.c latches whatever the check returns.

Two checks, worked through

Stale sample. The control task produces a sample every 100 ms, and the safety check receives the age of the newest sample. With a limit of 500 ms, an age of 480 ms is fine and an age of 510 ms is a fault. The check is a plain comparison of two numbers, so a test can supply any age without a heater or a clock.

Heater runaway. Suppose the setpoint is 45.00 °C, the chamber reads 25.00 °C, and the heater is at full power. The check opens a window at time 0 with a reference of 25.00 °C. At 30 s the chamber reads 26.00 °C, which is short of the 2.00 °C rise, so the window stays open. At 35 s the chamber reads 27.10 °C. That is 2.10 °C above the reference, so the rise has happened: the window restarts at 35 s with a reference of 27.10 °C. If the chamber then stays at 27.20 °C, the new window expires 60 s later, at 95 s, and the check returns FAULT_RUNAWAY. A slow but healthy heater that gains 2 °C every minute never trips. A dead heater trips 60 s after its window opened. The band protects the other case: once the chamber is within 5 °C of the setpoint, the check resets, because a heater near its setpoint is not expected to keep climbing.

Testing with Unity and FFF

The host test project compiles the same app/*.c files as the firmware (lesson 80's rule: the test runs the real code). Unity gives the assertions and FFF gives the fakes (lesson 81). CMock would generate fakes from headers, but it needs Ruby, which this workspace does not install, so the course uses FFF for the hands-on work.

The driver tests are the place for FFF. sensor_read() and buttons_sample() call hal_adc_read_ntc() and hal_button_pressed(), which exist only on the board. The test defines those two functions as FFF fakes, so the driver code runs on the PC with a scripted ADC code and a scripted button level. A fake records its calls, so a test can also check that the driver asked for one conversion, not two.

How a fake replaces the hardware

The driver test in test/test_drivers.c shows how a fake stands in for the board. These are the lines that matter: 

FAKE_VALUE_FUNC(uint16_t, hal_adc_read_ntc);   /* a stand-in with this signature */
hal_adc_read_ntc_fake.return_val = 2048u;       /* the next call returns this code */
...
TEST_ASSERT_EQUAL_INT(1, hal_adc_read_ntc_fake.call_count);   /* exactly one conversion */

FAKE_VALUE_FUNC is an FFF macro. It creates a function with the same name and signature as hal_adc_read_ntc(), plus a record of its calls, and the record is stored in a struct named hal_adc_read_ntc_fake. The PC build has no board file, so the test supplies this definition, and the linker uses it. Setting return_val scripts the answer to the next call, which is how the test chooses the ADC code. The last line checks call_count, the number of times the code under test called the fake. A driver that converted twice would pass the value check and fail this one, which is why the record is worth keeping. The test calls the real sensor_read() in app/sensor.c, so the path under test is the firmware's own.

Common mistakes and how to spot them

1. The 10-bit constant. Symptom: the serial log prints nan, or a temperature that is wrong by tens of degrees. Fix: name the full-scale constant 4095, and check that code 2048 gives 24.99 °C.

2. The divider wired the other way. Symptom: the temperature falls as the chamber warms. The formula assumes the NTC is the lower resistor. Fix: check the schematic first. If the NTC is on top, the formula must change, and a test with a known warm code will show it.

3. A held button counts as several presses. Symptom: in the simulator, one press of the material button advances the preset two or three times. Fix: raise the event only on the change from released to pressed, and keep the integrator's saturation. The test test_a_held_press_is_one_event catches this on the PC.

4. Runaway window that never restarts. Symptom: a healthy heater trips RUNAWAY about a minute after it starts, even though the chamber is rising. Fix: check the restart branch, which must reset the reference to the current time and temperature. Then write a test that feeds a steady 2 °C rise every minute and expects no fault.

5. Testing a copy of the code. Symptom: all the tests pass, but the firmware prints the wrong temperature. Cause: the test pasted its own copy of the formula, so it tested the copy. Fix: compile the same app/ files in both builds, as this project does, and never write the formula into a test.

In real projects

Production firmware often reads thermistors in one of two ways. Some use a lookup table of ADC codes against temperature, filled from the manufacturer's table. Others use a fit with three coefficients, the Steinhart–Hart equation, because a single beta value is an approximation whose error grows away from the reference temperature. A reviewer will ask which of these you used, and over what range it is valid.

Teams that test firmware keep the conversion and the safety rules as pure functions, so that known values can be checked on a PC in milliseconds, as this lesson does. The runaway rule is the same idea in production: the heater must make visible progress, or the device stops. Klipper's verify_heater, from the source that this lesson cites, is the printer-world version of it.

In an interview, expect "how do you know your temperature conversion is right?" A strong answer names independent known values, the fault codes at both ends of the range, and the rule that the test calls the production code rather than a copy.

Summary

  • A thermistor's resistance is turned into a voltage by a divider, and the ADC code is that voltage as a fraction of full scale.
  • The Beta equation turns the resistance ratio into a temperature. The constant must match the ADC: 4095 for 12 bits, not 1023.
  • The conversion refuses fault codes, because the logarithm of a zero or negative ratio has no meaning.
  • PWM is a duty cycle set by the compare register; a value from 0 to 1000 is a duty in permille, with no special cases at the ends.
  • A debounce is an integrator: the output changes only when the count reaches its limit, so a held button gives one event.
  • Safety checks run in a fixed order, return the first fault, and the runaway check keeps a window that restarts on each real rise.
  • Fakes replace hardware in host tests, and a test should call the same code the firmware runs.

Hint for the conversion

Reject the fault codes first, then compute the three steps of the formula in order, in floats. The final step multiplies by 100 and rounds with lroundf(), because the result is stored in hundredths of a degree. A test with raw 2048 should give 2499 or 2500, and that tolerance is in the test.

Hint for the safety order

Return the first fault you find, and do the cheap checks first. The runaway check has state: it must reset its window whenever the heater is not at full power or the chamber is near the setpoint, and it must restart the window after a rise of 2 °C. A test that sets the time 60 s after the window opened tells you whether the window logic is right.

Model answer

I put the logic in plain C that takes values as inputs and returns values, and I keep registers behind a small HAL interface. The host build compiles the same logic files, and the HAL is either replaced by fakes, such as FFF functions that return scripted values and record their calls, or not called at all, because the logic is pure. Then Unity checks the outputs, including the fault cases and the boundaries. The hardware tests still run on the board, but the logic is covered on the PC in milliseconds, and CI runs it on every commit.
