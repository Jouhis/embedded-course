Mutexes, priority inversion and deadlock

The most famous RTOS bug was a spacecraft that kept resetting on Mars, caused by a high-priority task waiting for a low-priority one while a medium-priority task ran. The fix was a single setting on a mutex. This lesson shows the bug in the simulator, the fix on the Blue Pill, and how to avoid deadlock.

By the end of this lesson you can explain priority inversion with three tasks, show it in UART output, fix it by using a mutex with priority inheritance, and state a lock-ordering rule that prevents deadlock.

The idea

A mutex is a lock: at most one task holds it, and a task that takes it while it is held waits. FreeRTOS implements a mutex as a semaphore with an owner. The owner is recorded, which lets the kernel do one thing a binary semaphore cannot: priority inheritance. While a high-priority task waits on a mutex, the owner runs at the waiter's priority, so no medium task can preempt it. The FreeRTOS kernel book describes mutexes and this inheritance in its chapter on mutexes; the source is queue.c, where the mutex is a queue with a special item size.

The bug is priority inversion. A high-priority task H waits for a resource held by a low-priority task L. A medium-priority task M is ready and does not need the resource. Because M outranks L, L cannot run, so H waits for M, which has nothing to do with the resource. The higher task is effectively running at the lowest level.

Three tasks, one resource

The project projects/0090-priority-inversion reproduces this exactly. Low (priority 1) takes the resource and holds it for 200 ms. Medium (priority 2) starts at 20 ms and burns 300 ms of CPU. High (priority 3) starts at 50 ms and needs the resource for 10 ms. The lock is first a binary semaphore, then a mutex.

What the UART shows

Run the solution and it prints a timeline for each phase. Expect numbers close to these, and read the high-task wait in each phase; the exact values depend on the tick and the simulator's timing.

In phase 1, high asks at 50 ms and waits until medium finishes at 320 ms: a wait of 270 ms. In phase 2, low runs at priority 3 from 50 ms and releases at 200 ms, so high waits 150 ms. The fix does not make high run at once; it bounds the wait by the holding time of the resource.

The fix: a mutex

Phase 2 changes one line: xSemaphoreCreateMutex() in place of xSemaphoreCreateBinary(). The take and give calls are the same. The owner is recorded, so when high blocks, the kernel raises low's priority to 3 (inheritance), and medium can no longer preempt it.

Do not use a mutex in an interrupt, and do not use a binary semaphore to protect shared data. The most common interview mistake is "a semaphore is a lock too", which is true in the simplest sense and wrong for priority inversion.

The Mars Pathfinder story

In July 1997 the Mars Pathfinder lander began resetting shortly after it started collecting data. Mike Jones, reporting on a talk by Wind River's David Wilner, wrote in the RISKS Digest (volume 19, issue 49, December 1997) that a high-priority bus task was blocked on a mutex held by a low-priority meteorological task, while a medium-priority communications task kept preempting it. The mutex had priority inheritance disabled. Jones also credited earlier work by researchers at Carnegie Mellon for the diagnosis and the fix. Glenn Reeves, who led the Pathfinder software team, replied in the same thread: the team reproduced the failure in the lab, and the fix was a change to the setting that creates that mutex, so that it has priority inheritance.

The source is the RISKS Digest post, which is primary; the story is also told in many course notes. Read the original post and Reeves's reply, and note the difference between the account of the talk and the account of the team's work.

Deadlock and lock ordering

Deadlock is a cycle of waiting. Task 1 holds lock A and waits for B. Task 2 holds B and waits for A. Neither can proceed, and no timeout is involved. Four conditions must hold together: mutual exclusion, hold and wait, no preemption of a lock, and a circular wait. The simplest prevention is to break the last one with a lock ordering rule: every task takes locks in the same global order, for example always A before B. If every task obeys it, no cycle can form.

  • Take locks in a fixed order, and document the order next to the locks.
  • Hold each lock for as short a time as possible; never call a blocking function inside a critical section.
  • Use timeouts on lock takes in code that might be stuck, and handle the timeout as an error, not as a retry loop.

Model answer

Priority inversion happens when a high-priority task waits for a resource held by a low-priority task, and a medium-priority task that does not need the resource preempts the low one. The high task then waits for the medium task's whole run. A mutex records its owner. When a high task blocks on it, the kernel raises the owner to the waiter's priority, so the medium task cannot preempt the owner, and the waiting time is bounded by the owner's critical section. A binary semaphore has no owner, so the kernel cannot raise anyone's priority; any task can give it, and it is for signalling. The Mars Pathfinder resets in 1997 were this bug on a VxWorks mutex with inheritance turned off. A good answer also mentions lock ordering against deadlock.
