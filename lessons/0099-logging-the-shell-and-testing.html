Logging, the shell, and testing with ztest and Twister

Diagnostics and host tests for Zephyr firmware

By the end of this lesson you can register a shell command that drives the LED, write a ztest case for a conversion function, and explain what Twister needs to run it, including why it cannot run on Windows.

Diagnostics on the desk, in the field and in CI

Lesson 53 printed text from the Pico over its UART one call at a time, lesson 85 explained why a deployed device needs logs it can send back and lesson 80 introduced unit tests that run on a PC, while lesson 95 taught Kconfig, the switches that turn each of these features on or off, and lesson 96 showed how the board describes its UART. This lesson puts those pieces to work in Zephyr.

The problem is practical, because with a board on your desk a shell lets you type led on and see the result without a rebuild for each test, with a board in a cabinet at a customer's site the same log lines and command set tell what it did, and with no board at all, the normal state of a CI server, a unit test can check the logic the firmware depends on, so each tool solves a different part of the same problem.

Log levels and modules

A log message is a line of text the firmware emits on purpose, each having a level saying how serious it is, of which Zephyr defines four, LOG_LEVEL_ERR as 1, LOG_LEVEL_WRN as 2, LOG_LEVEL_INF as 3 and LOG_LEVEL_DBG as 4 (include/zephyr/logging/log_core.h:40-46), a lower number being more serious and a higher one more detailed.

Each source file that logs is a module, LOG_MODULE_REGISTER(app, LOG_LEVEL_INF) naming this file's module app and giving it a level, and a message prints when its level is at most the module's level (include/zephyr/logging/log_core.h:201), so a module at level INF prints errors, warnings and info while dropping debug messages. The macros LOG_ERR, LOG_WRN, LOG_INF and LOG_DBG each carry one level (include/zephyr/logging/log.h).

The global switch is CONFIG_LOG, with which off every log macro compiles to nothing, costing no flash and no time, and modules that name no level take CONFIG_LOG_DEFAULT_LEVEL, which the solution sets to 3, so a level in code is a decision about one file, whereas a level in Kconfig is a decision about the whole build.

Log backends

A backend is the output a log message reaches, Zephyr having a UART backend, which writes straight to a serial port, and a shell backend, which sends messages through the shell's output, and the two cannot write to the same port without mixing their text. The UART backend, the symbol LOG_BACKEND_UART, has its default set in subsys/logging/backends/Kconfig.uart, where the line default y if !SHELL_BACKEND_SERIAL makes it on by default only when the serial shell is not.

The lesson's project turns on the shell, so the logs must go through the shell's backend, which is the reason for CONFIG_SHELL_LOG_BACKEND=y in prj.conf, a symbol defined in subsys/shell/Kconfig at line 288, and a learner who turns on the logger but forgets this line sees nothing, because the UART backend is off and the shell backend is not selected.

The Zephyr shell and its commands

A shell reads text from a serial port, splits it into a command and its arguments and calls a function you wrote for that command, running in its own thread, which the kernel starts for you, so main() can return. Its prompt is uart:~$ (the default in subsys/shell/backends/Kconfig.backends), and the serial backend uses the UART that the board names with zephyr,shell-uart, &uart0 on the Pico (boards/raspberrypi/rpi_pico/rpi_pico-common.dtsi:21).

A command is a function of the form int handler(const struct shell *sh, size_t argc, char **argv), the type that shell_cmd_handler declares (include/zephyr/shell/shell.h:267), in which argv[0] is the command name, which argc also counts. It is registered with SHELL_CMD_REGISTER (shell.h:465) as a plain command, or with SHELL_CMD_ARG_REGISTER when the shell should check the argument count, while a command with subcommands, such as led on, is built with SHELL_STATIC_SUBCMD_SET_CREATE (shell.h:502).

The shell resembles a service hatch in the side of a machine, which a technician opens to type a command and read the answer without rebuilding or reflashing anything, and a product usually closes or locks the hatch before shipping, because anyone at the serial port could open it too. The comparison breaks because a hatch shows only what is behind it, whereas the shell offers exactly the commands the firmware registered and nothing more.

Unit tests with ztest

A unit test checks one function with chosen inputs and compares the result with an expected value, which makes firmware testable only where the logic is separate from the hardware. The MYS-1 conversion is a good example, taking a number and returning a number without touching any register, and lesson 80 made the same argument for the host, ztest being Zephyr's framework for the same job.

ZTEST_SUITE groups tests under one name and ZTEST defines one test case (subsys/testsuite/ztest/include/zephyr/ztest_test.h:289 and :789), while zassert_equal(a, b, message), one of the assertion macros in ztest_assert.h (:346), compares two values. The ztest documentation says that these macros "will instantly fail the test if the related assertion fails", so the test case stops at that line, the failure is reported with its file and line and the next test runs.

The Twister test runner

Twister is Zephyr's test runner, which reads a description file in each test folder, builds the test for each platform the description names and runs each with the harness it names. The description file here is testcase.yaml, and although Zephyr's 4.5 documentation names tests.yaml as the file and calls testcase.yaml deprecated, Twister still scans for both names (scripts/pylib/twister/twisterlib/testplan.py:167), so the project's older name still works.

The platform that runs on a PC is native_sim, which compiles the code into a Linux process, so the test runs at PC speed, the ztest documentation saying that unit tests run as native applications and are "therefore only supported for Linux", and arch/posix/CMakeLists.txt stopping the configure step on other hosts with the message The POSIX architecture only works on Linux (lines 4 and 5). On the Twister command line -p (--platform) selects the platform (doc/develop/twister/index.rst).

Worked example: 1 440 counts to 22.50 degrees

The MYS-1 reports temperature in units of 1/64 degree as a signed 16-bit number (datasheet section 4.1, projects/0063-mystery-sensor/MYSTERY-SENSOR-DATASHEET.html), and the conversion must produce hundredths of a degree, so that the shell can print two decimal places without floating point, the value in hundredths being

centi = raw × 100 ÷ 64(1)

where raw is the sensor's signed count and the multiplication comes first. Before following the steps, predict what the shell prints for a raw value of 1440 if the division is done first instead.

  1. The raw count. The sensor says 1440, so raw = 1440.
  2. Scaling to hundredths. Multiplying by 100 first gives 1440 × 100 = 144000.
  3. Dividing by 64. 144000 / 64 = 2250 exactly, 2 250 hundredths, or 22.50 degrees, which 1440 / 64 = 22.5 confirms.
  4. Printing. The shell takes the magnitude, 2250, and prints 2250 / 100 = 22 and 2250 % 100 = 50, giving 22.50 C.

Done the wrong way, dividing first, 1440 / 64 = 22 in integer arithmetic, the fraction .5 being dropped, and 22 × 100 = 2200, so the monitor prints 22.00 C, an error of half a degree that comes purely from the order of the two operations, which is why the solution's comment says to multiply first.

The negative case shows the signed type at work, the count -64 being -1.00 C, whereas if the raw value is read as an unsigned 16-bit number, the same bits are 65472, 0xFFC0, and 65472 × 100 / 64 gives 102300, which prints as 1023.00 C, the warning the datasheet also gives in section 4.1.

The application and test code line by line

The solution is in projects/0099-logging-shell-ztest/solution, the conversion living in src/temp_format.c while the application in src/main.c only parses and prints. 

LOG_MODULE_REGISTER(app, LOG_LEVEL_INF);
static const struct gpio_dt_spec led = GPIO_DT_SPEC_GET(DT_ALIAS(led0), gpios);

LOG_MODULE_REGISTER makes this file's module app at level INF, so the file's LOG_INF prints and its LOG_DBG does not, and the LED is found through the led0 alias, as in lesson 96, so the code names no pin. 

static int cmd_led_on(const struct shell *sh, size_t argc, char **argv)
{
    ARG_UNUSED(argc);
    ARG_UNUSED(argv);
    gpio_pin_set_dt(&led, 1);
    shell_print(sh, "LED on");
    return 0;
}

This is a shell handler with the signature given above, ARG_UNUSED marking the two arguments this command does not read, so the compiler does not warn, and gpio_pin_set_dt(&led, 1) setting the logical level 1, which the overlay's active-high flag turns into a driven high pin. shell_print writes to the same session that sent the command, which is why the reply appears in the monitor and not on a different port. 

SHELL_STATIC_SUBCMD_SET_CREATE(sub_led,
    SHELL_CMD(on, NULL, "Turn the LED on", cmd_led_on),
    SHELL_CMD(off, NULL, "Turn the LED off", cmd_led_off),
    SHELL_CMD(toggle, NULL, "Toggle the LED", cmd_led_toggle),
    SHELL_SUBCMD_SET_END
);
SHELL_CMD_REGISTER(led, &sub_led, "Control the LED", NULL);

The subcommand set is a list of three children, on, off and toggle, the NULL in each entry meaning that the child has no children of its own, and SHELL_CMD_REGISTER adds the parent, led, to the root of the shell, its last argument being NULL because the parent has no handler of its own, only the subcommands, so typing led on selects the first child while led alone prints the list. 

static int cmd_temp(const struct shell *sh, size_t argc, char **argv)
{
    if (argc != 2) {
        shell_error(sh, "usage: temp <raw count>");
        return -EINVAL;
    }
    long raw = strtol(argv[1], NULL, 0);
    if (raw < INT16_MIN || raw > INT16_MAX) {
        shell_error(sh, "raw count must fit in 16 bits");
        return -ERANGE;
    }

The first check counts the command name, so argc == 2 means one argument, and strtol(argv[1], NULL, 0) converts the text to a number, base 0 accepting both decimal (1440) and hexadecimal (0x5a0). The range check comes before the cast, because a value outside the 16-bit range would be cut to the wrong number, and the shell error function prints a message and returns a negative code, which the shell reports back. 

    int32_t centi = mys_raw_to_centi_c((int16_t)raw);
    int32_t mag = centi < 0 ? -centi : centi;
    LOG_DBG("raw %ld -> %d centi-C", raw, (int)centi);
    shell_print(sh, "%s%ld.%02ld C", centi < 0 ? "-" : "",
                (long)(mag / 100), (long)(mag % 100));
    return 0;
}
SHELL_CMD_ARG_REGISTER(temp, NULL, "Convert a MYS-1 raw count to degrees C", cmd_temp, 2, 0);

The conversion runs on the value cast to int16_t, so the sign is kept, and the magnitude is printed with %02ld, so 50 prints as 50 and 5 would print as 05, the sign being handled separately because printing a negative number's integer and fraction parts directly would give the wrong fraction. The LOG_DBG line is silent at level INF and costs nothing in a release build with logging off, while SHELL_CMD_ARG_REGISTER takes the minimum argument count, 2, including the command name, and the maximum optional count, 0. 

int32_t mys_raw_to_centi_c(int16_t raw)
{
    return ((int32_t)raw * CENTI_PER_DEGREE) / COUNTS_PER_DEGREE;
}

This is src/temp_format.c, the function the test calls, in which the cast to int32_t happens before the multiply, so that the product of the 16-bit input and 100 fits in 32 bits, and the multiply comes before the divide, as in the worked example, while the absence of any hardware call is what makes the function testable on a PC. 

ZTEST_SUITE(temp_format, NULL, NULL, NULL, NULL, NULL);

ZTEST(temp_format, test_room_temperature)
{
    zassert_equal(mys_raw_to_centi_c(1440), 2250, "1440 counts should be 22.50 C");
}

ZTEST_SUITE declares the suite without setup or teardown, because the conversion keeps no state, and ZTEST defines the test case, whose body calls zassert_equal with a third argument printed on failure. The solution also has a negative case, -64 → -100, and a range case checking 32767 → 51198 (the exact value 51198.4375 rounded toward zero) and -32768 → -51200, each chosen to test an edge of the arithmetic.

Try it in Wokwi

The starter has the shell on and several TODO(learner) notes, and you turn on the logger, write the LED commands and the temperature command and fill in the formula and one test.

  1. Open projects/0099-logging-shell-ztest/starter in VS Code and, in prj.conf, uncomment or add CONFIG_LOG=y, CONFIG_LOG_DEFAULT_LEVEL=3 and CONFIG_SHELL_LOG_BACKEND=y, from the TODO(learner) note.
  2. In src/main.c, replace the two placeholder bodies in cmd_led_on and cmd_led_off with gpio_pin_set_dt and the messages LED on and LED off.
  3. Add the toggle entry to the subcommand set, calling gpio_pin_toggle_dt.
  4. In cmd_temp, check argc, parse argv[1] with strtol(argv[1], NULL, 0), convert it with mys_raw_to_centi_c and print the degrees with the sign and the two decimals.
  5. In main(), replace the TODO(learner) note with LOG_INF("shell ready"), so that the log line appears before the prompt.
  6. In src/temp_format.c, return raw * 100 / 64, multiplying first, and in tests/temp_format/src/test_temp_format.c add the negative test from the TODO(learner) note.
  7. Build with Ctrl+Shift+B, start the simulator and type help, then led on and temp 1440, the changes having worked when led appears in the help list, the LED turns on after led on and the monitor prints 22.50 C, while the line shell ready printed at start is your check for step 5.
Hint

The shell only sees commands it was given. If help does not list led, check that the SHELL_CMD_REGISTER line is still in the file. For the formula, multiply first and divide last: raw * 100 / 64. For the negative test, the expected value for -64 is -100.

The reference solution is in projects/0099-logging-shell-ztest/solution, to be compared after you have tried. Typing into the simulator's serial monitor depends on how Wokwi routes input to the Pico's UART, which we did not verify here without a simulator token, so if your shell does not respond, check the serial monitor's input box and the RX/TX wiring in diagram.json first. Run the host test on Linux or WSL, as the Twister section explains, and compare its summary line with the one the test prints.

Common mistakes and how to spot them

Shell calls without the shell symbols

The link fails with undefined reference to shell_fprintf_impl, a message that looks like a code bug, because shell_print is a macro expanding to a call to shell_fprintf_impl (include/zephyr/shell/shell.h:1287 and :1393), a function that exists only when CONFIG_SHELL is on, so the cause is a missing Kconfig line. Add CONFIG_SHELL=y to prj.conf, as the solution's prj.conf has it and the starter's comment describes.

Logs missing from the monitor

A LOG_INF line never appears while the shell works, because the serial shell turns the UART log backend off by default, so the log messages go nowhere unless the shell log backend is selected. Add CONFIG_SHELL_LOG_BACKEND=y, and type help as a quick check, since a reply from the shell shows that the port works and only the backend selection is wrong.

Division before multiplication

The monitor prints 22.00 C rather than 22.50 C for temp 1440 and the test test_room_temperature fails with a message naming the expected value, because the conversion was written as raw / 64 * 100, which drops the fraction. Use the solution's expression, multiplying first and dividing last, the failing test line being the fastest way to see the mistake.

The count read as unsigned

The output is 1023.00 C for a raw value of -64 and the negative-temperature test fails, saying what it expected, because the parameter was declared uint16_t, so -64 arrives as 65472. Keep the raw type signed, as the datasheet says, and check the negative case every time the conversion changes.

native_sim run on Windows

The configure step stops with The POSIX architecture only works on Linux, because native_sim is a Linux process and the test was run on a Windows PC. Run the test on Linux or in WSL, a Linux environment inside Windows, while the Pico build still works on Windows, which is why the test folder also lists rpi_pico.

Log levels, shell access and tests in released products

Production teams keep the logger at a level matching the release, debug messages being cut at build time while error and warning messages stay on, so that a field report contains the lines that matter, and the shell is often kept to a development image or behind a build flag, because an open command line is a security risk in the field. Lesson 106 covers security in general.

Unit tests in CI are the usual form of this lesson's test, a server building each test for a Linux host, running it and reporting the result, the pipeline lesson 82 describes. The test folder starts small and grows with each bug it catches, and reviewers ask for a test with each change to conversion or parsing logic, looking first at the edge cases.

Summary

  • A log message has a level, ERR 1, WRN 2, INF 3 and DBG 4, and a module at level INF prints the first three.
  • With CONFIG_LOG off the log macros compile to nothing, and since the UART log backend is off by default when the serial shell is on, CONFIG_SHELL_LOG_BACKEND must be selected.
  • A shell command is a handler taking (sh, argc, argv), argc counting the command name, and SHELL_CMD_ARG_REGISTER checks the count.
  • The arithmetic runs in the order that keeps the fraction, multiplying by 100 and then dividing by 64.
  • ZTEST defines a test case, and a failed zassert stops that test at once.
  • Twister runs tests from a description file, and native_sim needs a Linux host.
  • Hardware-free logic is kept separate, so the same function runs in the shell, on the board and in a host test.
